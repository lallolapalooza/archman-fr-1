Tcl_GetThreadData(keyPtr, size)

Tcl_MutexLock(mutexPtr)

Tcl_MutexUnlock(mutexPtr)

Tcl_CreateThread(idPtr, proc, clientData, stackSize, flags)

ARGUMENTS

Tcl_Condition *condPtr (entrée)
Une variable de condition, qui doit être associée à un verrou mutex.
Tcl_Mutex *mutexPtr (entrée)
Un verrou mutex.
const Tcl_Time *timePtr (entrée)
Une limite de temps pour l'attente de condition. NULL pour attendre indéfiniment. Notez qu'une valeur d'interrogation de 0 seconde n'a pas beaucoup de sens.
Tcl_ThreadDataKey *keyPtr (entrée)
Ceci identifie un bloc de stockage local au thread. La clé doit être statique et commune à tous les processus, pourtant chaque thread finira par associer un bloc de stockage différent à cette clé.
int *size (entrée)
La taille du bloc de stockage local au thread. Cette quantité de données est allouée et initialisée à zéro lors du premier appel à Tcl_GetThreadData par chaque thread.
Tcl_ThreadId *idPtr (sortie)
Le stockage référencé contiendra l'identifiant du nouveau thread tel que retourné par le système d'exploitation.
Tcl_ThreadId id (entrée)
Identifiant du thread attendu.
Tcl_ThreadCreateProc *proc (entrée)
Cette procédure agira comme le main() du nouveau thread. Le clientData spécifié sera son seul argument.
ClientData clientData (entrée)
Informations arbitraires. Passées comme seul argument à la proc.
int stackSize (entrée)
La taille de la pile allouée au nouveau thread.
int flags (entrée)
Masque de bits contenant des indicateurs permettant à l'appelant de modifier le comportement du nouveau thread.
int *result (sortie)
Le stockage référencé est utilisé pour y placer le code de sortie du thread attendu.

INTRODUCTION

Depuis la version 8.1, le noyau Tcl est thread-safe, ce qui vous permet d'intégrer Tcl dans des applications multithreadées sans personnaliser le noyau Tcl. Depuis la version 8.6, le support du multithreading Tcl est activé par défaut. Pour désactiver le support du multithreading Tcl, vous devez inclure l'option --disable-threads dans configure lors de la configuration et de la compilation de votre noyau Tcl.

Une contrainte importante de l'implémentation des threads Tcl est que seul le thread qui a créé un interpréteur Tcl peut utiliser cet interpréteur. En d'autres termes, plusieurs threads ne peuvent pas accéder au même interpréteur Tcl. (Cependant, un seul thread peut créer et utiliser en toute sécurité plusieurs interpréteurs.)

DESCRIPTION

Tcl fournit Tcl_CreateThread pour la création de threads. L'appelant peut déterminer la taille de la pile allouée au nouveau thread et modifier son comportement via les flags fournis. La valeur TCL_THREAD_STACK_DEFAULT pour stackSize indique que la taille par défaut spécifiée par le système d'exploitation doit être utilisée pour le nouveau thread. Quant aux indicateurs, seuls les valeurs TCL_THREAD_NOFLAGS et TCL_THREAD_JOINABLE sont actuellement définies. La première de celles-ci invoque le comportement par défaut sans aucun paramètre spécial. Utiliser la deuxième valeur marque le nouveau thread comme jointable. Cela signifie qu'un autre thread peut attendre la sortie d'un tel thread marqué et le joindre.

Restrictions : Sur certains systèmes UNIX, la bibliothèque pthread ne contient pas la fonctionnalité permettant de spécifier la taille de la pile d'un thread. La valeur spécifiée pour la taille de la pile est ignorée sur ces systèmes. Windows ne prend pas en charge les threads jointables actuellement. Cette valeur d'indicateur est donc ignorée sur cette plateforme.

Tcl fournit les fonctions Tcl_ExitThread et Tcl_FinalizeThread pour terminer les threads et invoquer les gestionnaires de sortie optionnels par thread. Voir la page Tcl_Exit pour plus d'informations sur ces procédures.

La fonction Tcl_JoinThread est fournie pour permettre aux threads d'attendre la sortie d'un autre thread, qui doit avoir été marqué comme jointable en utilisant l'indicateur TCL_THREAD_JOINABLE lors de sa création via Tcl_CreateThread.

Tenter d'attendre la sortie d'un thread non jointable ou d'un thread sur lequel on attend déjà entraînera une erreur. Attendre un thread jointable qui est déjà sorti est possible, le système conservera les informations nécessaires jusqu'après l'appel à Tcl_JoinThread. Cela signifie que ne pas appeler Tcl_JoinThread pour un thread jointable provoquera une fuite de mémoire.

L'appel Tcl_GetThreadData renvoie un pointeur vers un bloc de données privées au thread. Son argument est une clé partagée par tous les threads et une taille pour le bloc de stockage. Le stockage est automatiquement alloué et initialisé à zéro lors de la première demande par chaque thread. Le stockage est automatiquement désalloué par Tcl_FinalizeThread.

SYNCHRONISATION ET COMMUNICATION

Tcl fournit Tcl_ThreadQueueEvent et Tcl_ThreadAlert pour la gestion de la mise en file d'attente d'événements dans les applications multithreadées. Voir la page man Notifier pour plus d'informations sur ces procédures.

Un mutex est un verrou utilisé pour sérialiser tous les threads à travers un morceau de code en appelant Tcl_MutexLock et Tcl_MutexUnlock. Si un thread détient un mutex, tout autre thread appelant Tcl_MutexLock sera bloqué jusqu'à ce que Tcl_MutexUnlock soit appelé. Un mutex peut être détruit après son utilisation en appelant Tcl_MutexFinalize. Le résultat du verrouillage d'un mutex deux fois depuis le même thread est indéfini. Sur certaines plateformes, cela entraînera un interblocage. Les procédures Tcl_MutexLock, Tcl_MutexUnlock et Tcl_MutexFinalize sont définies comme des macros vides si elles ne sont pas compilées avec les threads activés. Pour la déclaration des mutex, la macro TCL_DECLARE_MUTEX doit être utilisée. Cette macro assure une gestion correcte des mutex même lorsque le noyau est compilé sans threads activés.

Une variable de condition est utilisée comme mécanisme de signalisation : un thread peut verrouiller un mutex puis attendre sur une variable de condition avec Tcl_ConditionWait. Ceci libère atomiquement le verrou du mutex et bloque le thread en attente jusqu'à ce qu'un autre thread appelle Tcl_ConditionNotify. L'appelant de Tcl_ConditionNotify doit détenir le mutex associé en ayant précédemment appelé Tcl_MutexLock, mais cela n'est pas imposé. Notifier la variable de condition débloque tous les threads en attente sur la variable de condition, mais ils ne progressent pas tant que le mutex n'est pas libéré avec Tcl_MutexUnlock. L'implémentation de Tcl_ConditionWait verrouille automatiquement le mutex avant de retourner.

L'appelant de Tcl_ConditionWait doit être préparé aux notifications parasites en appelant Tcl_ConditionWait dans une boucle while qui teste un invariant.

Une variable de condition peut être détruite après son utilisation en appelant Tcl_ConditionFinalize.

Les procédures Tcl_ConditionNotify, Tcl_ConditionWait et Tcl_ConditionFinalize sont définies comme des macros vides si elles ne sont pas compilées avec les threads activés.

INITIALISATION

Tous ces objets de synchronisation s'auto-initialisent. Ils sont implémentés comme des pointeurs opaques qui devraient être NULL lors de leur première utilisation. Les mutex et les variables de condition sont soit nettoyés par les gestionnaires de sortie de processus (s'ils vivent assez longtemps), soit explicitement par des appels à Tcl_MutexFinalize ou Tcl_ConditionFinalize. Le stockage local au thread est récupéré pendant Tcl_FinalizeThread.

ACCÈS AU NIVEAU SCRIPT AUX THREADS

Tcl ne fournit pas de commandes intégrées pour que les scripts créent, gèrent ou joignent des threads, ni aucun accès au niveau script aux mutex ou variables de condition. Il fournit de telles facilités uniquement via des interfaces C, et laisse aux paquets le soin d'exposer ces fonctionnalités

NAME

Thread - Tcl thread creation and management

SYNOPSIS

#include <tcl.h>

Tcl_ThreadId
Tcl_CreateThread(idPtr, startProc, clientData,
        stackSize, joinable);
void
Tcl_ExitThread(status);
void
Tcl_AlertThread(id);
void
Tcl_SetThreadLocal(name, value);
Tcl_Obj*
Tcl_GetThreadLocal(name);
Tcl_ThreadId
Tcl_GetCurrentThread(void);
int
Tcl_IsMainThread(void);
int
Tcl_JoinThread(id, statusPtr);
void
Tcl_WakeupThread(id);

ARGUMENTS

idPtr
Address of a location to store the new thread’s ID. If the thread cannot be created, this location is left untouched.
startProc
The function that the new thread will execute. It must have the signature Tcl_ThreadCreateType.
clientData
Arbitrary value to be passed to the new thread’s start procedure.
stackSize
Requested stack size for the new thread, in bytes. A value of TCL_THREAD_STACK_DEFAULT may be used to request the system default size.
joinable
A boolean value indicating whether the thread should be joinable. If true, the thread may be joined to and its exit status retrieved using Tcl_JoinThread. If false, the thread is detached and its resources are automatically freed when it exits.
status
The status code to be returned by the thread. If the thread is joinable, this value will be accessible via Tcl_JoinThread.
id
The ID of the thread to be alerted, joined, or woken up.
statusPtr
Address of an integer to store the exit status of the joined thread. This argument is ignored if the thread was not joinable.
name
The name of the thread-local storage variable.
value
The value to store for the thread-local storage variable.

INTRODUCTION

Tcl provides support for creating and managing threads. Threads are independent sequences of execution within a single process. They share the same memory space, so they can communicate by accessing shared variables. However, this also means that care must be taken to prevent race conditions.

Tcl threads are POSIX threads, pthreads, on Unix-like systems, and Win32 threads on Windows. The Tcl API provides a portable interface to these underlying threading primitives.

DESCRIPTION

Tcl_CreateThread creates a new thread and arranges for it to execute the function specified by startProc. The clientData argument is passed as the sole argument to startProc when the thread begins execution. The stackSize argument specifies the desired stack size for the new thread in bytes. If TCL_THREAD_STACK_DEFAULT is used, the system’s default stack size is used. The joinable argument determines whether the thread can be joined. If true, the thread is joinable, and its exit status can be retrieved using Tcl_JoinThread. If false, the thread is detached, and its resources are automatically reclaimed by the system when it terminates.

Tcl_ExitThread terminates the current thread. The status argument is the exit status of the thread. If the thread is joinable, this status will be available to the thread that joins it.

Tcl_AlertThread sends an alert to the specified thread. An alert is a lightweight asynchronous notification that can be used to signal a thread to perform some action, such as checking for new events or releasing locks.

Tcl_SetThreadLocal and Tcl_GetThreadLocal are used to manage thread-local storage. Each thread has its own independent set of variables that are local to that thread. This is useful for avoiding conflicts when multiple threads access the same variable name.

Tcl_GetCurrentThread returns the ID of the current thread.

Tcl_IsMainThread returns true if the current thread is the main thread of the Tcl interpreter, and false otherwise.

Tcl_JoinThread causes the calling thread to wait until the thread specified by id terminates. If the thread is joinable, its exit status is placed in the location pointed to by statusPtr.

Tcl_WakeupThread wakes up a thread that is currently blocked, for example, in a call to Tcl_JoinThread or waiting for an event. This can be useful for interrupting long-running operations.

SCRIPT-LEVEL ACCESS TO THREADS

The Tcl scripting language provides access to threading facilities through the Thread package. This package allows Tcl scripts to create, manage, and synchronize threads without needing to write C code. For example, you can use the thread::create command to create a new thread, and thread::join to wait for a thread to complete. The Thread package also provides commands for thread synchronization primitives like mutexes and condition variables. Consult the documentation for the Thread package for more details. The C API described here is intended for extensions that need more direct control over threading, or for implementing high-performance operations that cannot be easily expressed in Tcl. Tcl_CreateThread is often used by extensions to integrate with the Tcl event loop. For example, an extension might create a worker thread that performs a long-running task and then posts an event back to the main Tcl thread when the task is complete. This ensures that the Tcl interpreter remains responsive while the worker thread is busy. The existence of the Thread package at the script level means that it ese matters to the script level. One such package is the Thread package.

EXAMPLE

To create a thread with portable code, its implementation function should be declared as follows:

static Tcl_ThreadCreateProc MyThreadImplFunc;

It should then be defined like this example, which just counts up to a given value and then finishes.

static Tcl_ThreadCreateType
MyThreadImplFunc(
    ClientData clientData)
{
    int i, limit = (int) clientData;
    for (i=0 ; i<limit ; i++) {
        /* doing nothing at all here */
    }
    TCL_THREAD_CREATE_RETURN;
}

To create the above thread, make it execute, and wait for it to finish, we would do this:

int limit = 1000000000;
ClientData limitData = (void*)((intptr_t) limit);
Tcl_ThreadId id;    /* holds identity of thread created */
int result;
if (Tcl_CreateThread(&id, MyThreadImplFunc, limitData,
        TCL_THREAD_STACK_DEFAULT,
        TCL_THREAD_JOINABLE) != TCL_OK) {
    /* Thread did not create correctly */
    return;
}
/* Do something else for a while here */
if (Tcl_JoinThread(id, &result) != TCL_OK) {
    /* Thread did not finish properly */
    return;
}
/* All cleaned up nicely */
