Nom

Tk2portableTk - comment rendre votre code Tk portable vers d'autres langages interprétés.

Auteur

Ilya Zakharevich <ilya@math.ohio-state.edu> a contribué une grande partie de ce document. Merci beaucoup.

Description

pTk est une tentative de rendre Tk utile depuis d'autres langages. Actuellement, tk4.0 fonctionne sous Perl en utilisant cette approche. Ci-dessous, Lang est la notation pour un langage externe à travers lequel pTk relie le code Tk. Ceci est la notation pour un langage externe via lequel pTk relie le code Tk.

Le problème principal avec le code développé pour TCL avec des langages autres que le C est le manque de types de données : presque tout est "char*". Cela rend la traduction automatique impossible. Cependant, si vous définissez "typedef" plusieurs nouveaux symboles pour qu'ils soient "char*", vous pouvez continuer à utiliser votre code en TCL, et ainsi la traduction automatique sera possible.

Un autre problème avec l'approche "tout est une chaîne" est l'impossibilité d'avoir un résultat qui dise "Non Applicable" sans déclencher une erreur. Par conséquent, différentes commandes Tk renvoient différentes valeurs de chaîne signifiant "une erreur s'est produite", comme "", " " ou "??". D'autres langages peuvent être plus flexibles, donc dans portableTk, vous devez informer le compilateur ce que le retour que vous souhaitez signifie "erreur" (voir "Définition des variables").

Actuellement, portableTk utilise plusieurs approches différentes pour simplifier la traduction : plusieurs fonctions TCL qui sont particulièrement dangereuses à utiliser sont indéfinies, vous pouvez donc facilement trouver des endroits qui nécessitent une mise à jour pour utiliser des fonctions indépendantes du langage basées sur les avertissements du compilateur. Enfin, une manière d'utiliser ces fonctions indépendantes en TCL correctement sera également fournie. La fin de ce document fournit un point de départ pour ce projet.

Structure de pTk, portage de votre code

pTk, qui est un portage de Tk, est très particulier quant à la portabilité du code vers portableTk. Le problème est qu'il y a actuellement très peu d'espoir d'unifier les modifications de retour vers Tk, donc une stratégie spéciale est nécessaire pour maintenir ce portage. N'utilisez pas cette stratégie pour porter votre propre code.

pTk est produit à partir de Tk via un processus en deux étapes : premièrement, quelques modifications manuelles (le résultat est dans le sous-répertoire "mTk"), et deuxièmement, la conversion automatique par le script "munge" (écrit en Perl). Ainsi, le sous-répertoire "pTk/mTk" contient du code avec une différence minimale par rapport au code Tk original, ce qui facilite le merge(1) des différences entre les versions de Tk dans le code modifié.

Il semble que la stratégie pour le code portable devrait être exactement l'inverse : en partant du code TCL, appliquez "munge", puis éditez le code résultant. Il est probablement également possible de cibler votre code vers portableTk à partir de zéro, car cela permettra de l'exécuter sous de nombreux Languages.

La seule raison pour laquelle quelqu'un voudrait voir le contenu du répertoire "pTk/mTk" est de trouver quelles constructions ne sont pas prises en charge par "munge". D'un autre côté, le répertoire "pTk" contient du code conforme à portableTk, vous pouvez donc y jeter un œil pour trouver des exemples de code.

span class="Li">"munge" est le script qui convertit les constructions les plus courantes de Tk en leurs équivalents "portableTk". Pour que votre code soit conforme, vous devriez suivre les conventions de Tk en matière d'indentation et de noms de variables, en particulier, le tableau d'arguments pour le "...CmdProc" doit s'appeler "argv".

Pour plus de détails sur ce que "munge" peut faire, voir "Traduction de quelques fonctions TCL".

Données de langage

Les types de données suivants sont définis :

"Tcl_Obj *"
est le type principal de langage. C'est un type dont votre fonction C reçoit des pointeurs pour les arguments lors de l'appel de la fonction correspondante du Lang. Le type de configuration correspondant est "TK_CONFIG_LANGARG". C'est aussi un type qui contient des informations sur le contenu de la variable Lang.
"Var"
est un substitut pour un "char *" contenant le nom de la variable. Dans Lang, c'est un objet contenant une référence à une autre variable Lang.
"LangResultSave"
????
"LangCallback"
"LangCallback*" est un substitut pour un "char *" contenant un appel à une commande. Le type de configuration correspondant est "TK_CONFIG_CALLBACK".
"LangFreeProc"
Est le type que "Lang_SplitList" définit. Avant de l'appeler, déclarez

Args *args;
LangFreeProc *freeProc = NULL;
...
code = Lang_SplitList(interp, value,
    &argc, &args, &freeProc);

Après avoir utilisé les valeurs extraites, appelez-le

if (args != NULL && freeProc) (*freeProc)(argc,args);

Il n'est pas garanti que les "args" survivront à la suppression de "value".

Définition des variables

void LangFreeArg (Tcl_Obj *, Tcl_FreeProc *freeProc)
Tcl_Obj *  LangCopyArg (Tcl_Obj *);
void Tcl_AppendArg (Tcl_Interp *interp, Tcl_Obj *)

Ces deux fonctions sont équivalentes, sauf si s est une chaîne vide. Dans ce cas, "LangSetDefault" se comporte comme "LangSetString" avec "s==NULL", c'est-à-dire qu'elle définit la valeur actuelle de la variable de Lang à faux.

void LangSetInt(Tcl_Obj * *,int)
void LangSetDouble(Tcl_Obj * *,double)

Les fonctions Lang séparent les données non initialisées et initialisées en comparant les données avec "NULL". Ainsi, la déclaration d'un "Tcl_Obj *" devrait ressembler à

Tcl_Obj * arg = NULL;

si vous souhaitez utiliser cet "arg" avec les fonctions ci-dessus. Une fois que vous avez terminé, vous devriez utiliser "LangFreeArg" avec "TCL_DYNAMIC" comme "freeProc".

NAME

pTk - Tcl/Tk compatibility module

Author

Jan Wagner <jan@wagner.name>

DESCRIPTION

This module is intended to allow C code written for Tcl/Tk to be compiled and run under Perl Tk.

The API is a set of C functions.

Structure of pTk, porting your code

The module provides a C API that is a subset of the Tcl C API. The objects are of type "Tcl_Obj *".

To port your code, you should include the "pTk.h" header file.

The objects are created using the following functions:

ListFactory *ListFactoryNew(void)
void ListFactoryAppend(ListFactory *, Tcl_Obj * *)
void ListFactoryFinish(ListFactory *)
void ListFactoryFree(ListFactory *)
ListFactory *ListFactoryNew(void)
void ListFactoryAppendCopy(ListFactory *, Tcl_Obj * *arg)
ListFactory *ListFactoryNewLevel(ListFactory *)
ListFactory *ListFactoryEndLevel(ListFactory *)
void ListFactoryResult(Tcl_Interp *, ListFactory *)

The difference is that a call to "ListFactoryFinish" should precede the actual usage of the value of "ListFactory", and there are two different ways to append an "Tcl_Obj *" to a "ListFactory": ListFactoryAppendCopy() guarantees that the value of "arg" is copied to the list, but ListFactoryAppend() may append to the list a reference to the current value of "arg". If you are not going to change the value of "arg" after appending, the call to ListFactoryAppend may be quicker.

As in TCL, the call to ListFactoryFree() does not free the "ListFactory", only the objects it references.

The functions ListFactoryNewLevel() and ListFactoryEndLevel() return a pointer to a "ListFactory" to fill. The argument of ListFactoryEndLevel() cannot be used after a call to this function.

DStrings

Production of strings are still supported in portableTk.

Accessing "Tcl_Obj *"s

The following functions for getting a value of an "Tcl_Obj *" may be provided:

double LangDouble(Tcl_Obj *)
int LangInt(Tcl_Obj *)
long LangLong(Tcl_Obj *)
int LangIsList(Tcl_Obj * arg)

The function LangIsList() is supported only partially under TCL, since there is no data types. It checks whether there is a space inside the string "arg".

Assigning numbers to "Tcl_Obj *"s

While LangSetDouble() and LangSetInt() are supported ways to assign numbers to assign an integer value to a variable, for the sake of efficiency under TCL it is supposed that the destination of these commands was massaged before the call so it contains a long enough string to sprintf() the numbers inside it. If you are going to immediately use the resulting "Tcl_Obj *", the best way to do this is to declare a buffer in the beginning of a block by

dArgBuffer;

and assign this buffer to the "Tcl_Obj *" by

void LangSetDefaultBuffer(Tcl_Obj * *)

You can also create the buffer(s) manually and assign them using

void LangSetBuffer(Tcl_Obj * *, char *)

This is the only choice if you need to assign numeric values to several "Tcl_Obj *"s simultaneously. The advantage of the first approach is that the above declarations can be made "nop"s in different languages.

Note that if you apply "LangSetDefaultBuffer" to an "Tcl_Obj *" that contains some value, you can create a leak if you do not free that "Tcl_Obj *" first. This is a non-problem in real languages, but can be a trouble in "TCL", unless you use only the above API.

Creating new "Tcl_Obj *"s

The API for creating a new "Tcl_Obj *" is

void LangNewArg(Tcl_Obj * *, LangFreeProc *)

The API for creating a new "Tcl_Obj *" is absent. Just initialize "Tcl_Obj *" to be "NULL", and apply one of "LangSet..." methods.

After you use this "Tcl_Obj *", it should be freed thusly:

"LangFreeArg(arg, freeProc)".

Evaluating a list

Use

int LangArgEval(Tcl_Interp *, Tcl_Obj * arg)

Here "arg" should be a list to evaluate, in particular, the first element should be a "LangCallback" massaged to be an "Tcl_Obj *". The arguments can be send to the subroutine by reference or by value in different languages.

Getting result as "Tcl_Obj *"

Use "Tcl_ArgResult". It is not guaranteed that result survives this operation, so the "Tcl_Obj *" you get should be the only mean to access the data from this moment on. After you use this "Tcl_Obj *", you should free it with "freeProc" "LANG_DYNAMIC" (you can do LangSet...() in between).
