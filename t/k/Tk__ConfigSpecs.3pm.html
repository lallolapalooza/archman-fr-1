NOM

Tk::ConfigSpecs - Définition du comportement de 'configure' pour les widgets composites.

SYNTAXE

sub Populate
{
 my ($composite,$args) = @_;
 ...
 $composite->ConfigSpecs('-attribut' => [ ou,nomBD,classeBD,defaut ]);
 $composite->ConfigSpecs('-alias' => '-autreAttribut');
 $composite->ConfigSpecs('PAR_DEFAUT' => [ ou ]);
 $composite->ConfigSpecs($sousWidget->ConfigSpecs);
 ...
}
$composite->configure(-attribut => valeur);

DESCRIPTION

L'objectif est de rendre la méthode configure du widget composite aussi similaire que possible à la méthode configure d'un widget Tk normal. (Voir Tk::options pour une description de ce comportement.) Pour ce faire, les attributs que le composite accepte dans son ensemble doivent être définis.

Définition des ConfigSpecs pour une classe.

Typiquement, un widget aura un ou plusieurs appels comme suit

$composite->ConfigSpecs(-attribut =>[ou,nomBD,classeBD,defaut]);

dans sa méthode Populate. Lorsque ConfigSpecs est appelé de cette manière (avec arguments), les arguments sont utilisés pour construire ou augmenter/remplacer une table de hachage pour le widget. (Plus d'une paire -option=>valeur peut être spécifiée dans un seul appel.)

nomBD, classeBD et défaut ne sont utilisés que par ConfigDefault décrit ci-dessous, ou pour répondre aux commandes configure d'« enquête ».

Il peut s'agir de l'une des valeurs ci-dessous, ou d'une liste de telles valeurs entourées de [].

Les valeurs actuellement autorisées pour ou sont :

'ADVERTISED'
Applique configure aux sous-widgets *annoncés*.
'DESCENDANTS'
Applique configure récursivement à tous les descendants.
'CALLBACK'
La définition de l'attribut effectue "Tk::Callback->new($valeur)" avant de le stocker dans "$composite->{Configure}{-attribut}". Ceci est approprié pour les attributs "-command => ..." qui sont gérés par le composite et non transmis à un sous-widget. (Par exemple, Tk::Tiler a "-yscrollcommand" pour lui permettre d'avoir une barre de défilement attachée.)

Ceci peut être le premier de plusieurs mots-clés « de validation » (par exemple, font, cursor, anchor etc.) que Tk prend en charge pour le code C.

'ENFANTS'
Applique configure à tous les enfants. (Les enfants sont les descendants immédiats d'un widget.)
'METHODE'
Appelle "$cw->attribut(valeur)"

C'est le cas le plus général. Avoir simplement une méthode de la classe composite portant le même nom que l'attribut. La méthode peut faire n'importe quelle validation et avoir les effets secondaires de votre choix. (Il est probablement utile de « mettre en file d'attente » en utilisant afterIdle pour des effets secondaires plus complexes.)

'PASSIF'
Stocke simplement la valeur dans "$composite->{Configure}{-attribut}".

Cette forme est également un espace réservé utile pour les attributs que vous ne gérez actuellement qu'au moment de la création.

'SOI-MÊME'
Applique configure au widget de base (par exemple, Frame) qui est à la base du composite. (C'est le comportement par défaut pour la plupart des attributs, ce qui fait qu'un simple Frame se comporte comme vous vous y attendriez.) Notez qu'une fois que vous avez spécifié ConfigSpecs pour un attribut, vous devez explicitement inclure 'SOI-MÊME' dans la liste si vous voulez que l'attribut s'applique au composite lui-même (cela évite les problèmes de récursion infinie ennuyeux).
$référence (blessé)
Appelle $référence->configure(-attribut => valeur)

Un cas courant est lorsque $référence est un sous-widget.

$référence peut également être le résultat de

Tk::Config->new(methode_set,methode_get,args,...);

La classe Tk::Config est utilisée pour implémenter tous les types de mots-clés ci-dessus. La classe a des méthodes "configure" et "cget", elle permet donc au code de niveau supérieur d'appeler *toujours* l'une de ces méthodes sur un *objet* quelconque.

référence de hachage
Définition : 
$cw->ConfigSpecs(
        ...
        -option => [ { -optionX=>$w1, -optionY=>[$w2, $w3] },
                        nomBD classeBD defaut ],
        ...
        );

Ainsi, "$cw->configure(-option => valeur)" fait réellement

$w1->configure(-optionX => valeur);
$w2->configure(-optionY => valeur);
$w3->configure(-optionY => valeur);
'autrechaîne'
Appelle 
$composite->SousWidget('autrechaîne')->configure( -attribut => valeur );

Bien que cela soit présent pour une compatibilité ascendante avec Tk-b5, il est probablement préférable d'utiliser directement la référence du sous-widget. Le seul cas pour conserver cette forme est de permettre une couche d'abstraction supplémentaire - peut-être avoir un sous-widget 'courant' - ce n'est pas prouvé.

Alias
"ConfigSpecs( -alias => '-autreAttribut' )" est utilisé pour rendre "-alias" équivalent à "-autreAttribut". Par exemple, les alias 
-fg => '-foreground',
-bg => '-background'

sont fournis automatiquement (s'ils ne sont pas déjà spécifiés).

Déléguer toutes les options d'une classe de widget à un sous-widget

$composite->ConfigSpecs($sousWidget->ConfigSpecs);

Ceci génère une liste d'arguments composite ConfigSpecs, un pour chaque option valide dans la classe de $sousWidget, et délègue ladite option à $sousWidget. Voir Tk::Widget et les ConfigSpecs de la méthode widget. La duplication des clés ConfigSpecs composite et ConfigSpecs widget donnera des résultats indéfinis.

Valeurs par défaut

Lorsque la méthode Populate retourne, ConfigDefault est appelée. Ceci appelle

$composite->ConfigSpecs;

(sans arguments) pour retourner une référence à un hachage. Les entrées du hachage prennent la forme :

'-attribut' => [ ou, nomBD, classeBD, defaut ]

ConfigDefault ignore complètement 'ou' (et aussi l'entrée PAR_DEFAUT) et vérifie la base de données 'options' pour le compte du widget, et si une entrée est présente correspondant à nomBD/classeBD

-attribut => valeur

est ajoutée à la liste des options que new appliquera finalement au widget. De même, s'il n'y a pas de correspondance et que défaut est défini, cette valeur par défaut sera ajoutée.

Les entrées d'alias dans le hachage sont utilisées pour convertir les valeurs spécifiées par l'utilisateur pour l'alias en valeurs pour l'attribut réel.

Configure au moment de new()

Une fois que le contrôle revient à new, la liste des options fournies par l'utilisateur, augmentées de celles de ConfigDefault, sont appliquées au widget en utilisant la méthode configure ci-dessous.

Les widgets sont plus flexibles et plus similaires à Tk s'ils gèrent la majorité de leurs attributs de cette manière.

Configuration des composites

Une fois les étapes ci-dessus réalisées, les appels de la forme :

$composite->configure( -attribut => valeur );

devraient se comporter comme n'importe quel autre widget du point de vue du code utilisateur. configure sera géré par Tk::Derived::configure comme suit :

$composite->ConfigSpecs;

est appelé (sans arguments) pour retourner une référence à un hachage. -attribut est recherché dans ce hachage. Si -attribut n'est pas présent dans le hachage, alors 'PAR_DEFAUT' est recherché à la place. (Les alias sont également essayés et provoquent une redirection vers l'attribut alias.) Le résultat doit être une référence à une liste comme :

[ ou, nomBD, classeBD, defa
Tk::ConfigSpecs(3pm)

NAME

Tk::ConfigSpecs - Description of how Tk::composite widgets handle configuration specifications

SYNOPSIS

package Tk::MyComposite;
use Tk::Derived;
use base 'Tk::composite';

sub Populate {
    my ($self, $args) = @_;
    # ... create child widgets ...
    $self->SUPER::Populate(@$args);
}

# ... then define the ConfigSpecs hash
# For example, if you want to map -foreground and -background to the
# children of a composite widget, you'd do something like:
sub ConfigSpecs {
    return (
        # ... other options ...
        -foreground => [qw(FG background)], # maps -foreground to child's -background
        -background => [qw(BG background)], # maps -background to child's -background
        # ... other options ...
    );
}

DESCRIPTION

Composite widgets in Tk are widgets that are made up of other, simpler widgets. The Tk::composite module provides a mechanism for easily defining how options passed to the composite widget should be handled.

The ConfigSpecs sub is used to define how options passed to a composite widget are translated into options for its constituent child widgets.

A ConfigSpecs sub should return a list of key-value pairs, where the key is the option name as it will be used by the composite widget, and the value is a list of names that specify how to get or set the option on the child widgets.

The format of the value list is:

where
This is the target widget or widgets. It can be a single widget name (e.g., '-button'), a list of widget names (e.g., ['-button', '-label']), or a special value 'SELF' which means the composite widget itself.
method
This is the method to call on the target widget(s). Common methods are 'configure' or 'cget'.
attribute
This is the attribute name to get or set on the target widget(s). This can be a string (e.g., '-background') or a coderef. If it's a coderef, it will be called with the value passed to the composite widget's configure/cget method, and its return value will be used.
[default]
An optional default value for the attribute if it's not specified.

Let's break down an example:

-foreground => [qw(FG background)],

This specification means:

  • When the composite widget is configured with the -foreground option, ...
  • ...the value should be applied to the -background attribute of the child widget named FG.

Here's another example:

-text => ['label', 'configure', 'text'],

This means:

  • When the composite widget is configured with the -text option, ...
  • ...the value should be set for the -text attribute of the child widget named label, using its configure method.

At this stage only where is of interest, it maps to a list of object references (maybe only one) foreach one

$object->configure( -attribute => value );

is evaled.

Inquiring attributes of composites

$composite->cget( '-attribute' );

This is handled by Tk::Derived::cget in a similar manner to configure. At present if where is a list of more than one object it is ignored completely and the "cached" value in

$composite->{Configure}{-attribute}.

is returned.

CAVEATS

The "-background" and "-foreground" option values are automatically propagated down to all composite widget's children. This may be sometimes not desirable, especially if some subwidgets should use own color schemes, either by using explicit options or by option database definitions. If this is the case, then just add

-foreground => 'SELF',
-background => 'SELF',

to "ConfigSpecs".

It is the author's intention to port as many of the "Tix" composite widgets as make sense. The mechanism described above may have to evolve in order to make this possible, although now aliases are handled I think the above is sufficient.
