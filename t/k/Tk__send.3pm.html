NOM

Tk::send - Exécuter une commande dans une application différente

SYNOPSIS

    $result = $widget->send(?options,?app=>cmd?arg arg ...?)

DESCRIPTION

Cette méthode organise l'envoi de cmd (et des args) à l'application nommée par app. Elle renvoie le résultat ou une erreur (d'où le fait que ce qui précède devrait probablement être 'encapsulé' dans un eval{} et que $@ devrait être vérifié). App peut être le nom de n'importe quelle application dont la fenêtre principale se trouve sur l'écran contenant la fenêtre principale de l'expéditeur ; elle n'a pas besoin d'être dans le même processus. Si aucun argument arg n'est présent, la chaîne à envoyer est entièrement contenue dans l'argument cmd. Si un ou plusieurs arguments arg sont présents, ils sont concaténés en les séparant par des espaces pour former la chaîne à envoyer.

Si les arguments initiaux de l'appel commencent par ``-'', ils sont traités comme des options. Les options suivantes sont actuellement définies :

-async
Demande une invocation asynchrone. Dans ce cas, la commande send s'achèvera immédiatement sans attendre que cmd se termine dans l'application cible ; aucun résultat ne sera disponible et les erreurs dans la commande envoyée seront ignorées. Si l'application cible est dans le même processus que l'application d'envoi, l'option -async est ignorée.
--
Ne sert à rien d'autre qu'à terminer la liste des options. Cette option n'est nécessaire que si app pouvait contenir un caractère ``-'' en début de chaîne.

NOMS D'APPLICATION

Le nom d'une application est défini initialement à partir du nom du programme ou du script qui a créé l'application. Vous pouvez interroger et modifier le nom d'une application avec la méthode appname.

QU'EST-CE QU'UNE TRANSMISSION (SEND)

Le mécanisme send a été conçu pour permettre aux applications Tcl/Tk de s'envoyer des scripts Tcl mutuellement. Cela ne se traduit pas très bien en perl/Tk. Perl/Tk "envoie" une chaîne à app, ce qui se passe en conséquence dépend de l'application réceptrice. Si l'autre application est une application Tcl/Tk4.*, elle sera traitée comme un script Tcl. Si l'application "autre" est une application perl/Tk (y compris les envois à soi-même), alors la chaîne est passée comme argument à un appel de méthode de la forme suivante :

$mainwindow->Receive(string);

Il existe une méthode Tk::Receive par défaut (AutoLoaded) qui renvoie une erreur à l'application d'envoi. Une application particulière peut définir sa propre méthode Receive dans n'importe quelle classe de l'arbre d'héritage de MainWindow pour faire ce qu'elle juge bon. Par exemple, elle pourrait evaluer la chaîne, éventuellement dans un "compartiment" Safe.

Si une application Tcl/Tk "envoie" quelque chose à une application perl/Tk, alors l'application perl/Tk devrait tenter d'interpréter la chaîne entrante comme un script Tcl. Les cas simples ne devraient pas être trop difficiles à émuler (diviser par les espaces et considérer le premier élément comme "commande" et les autres éléments comme arguments).

SÉCURITÉ

La commande send est potentiellement une faille de sécurité sérieuse, car toute application capable de se connecter à votre serveur X peut envoyer des scripts à vos applications. D'où le comportement par défaut décrit ci-dessus. (Avec la disponibilité de Safe, il peut être judicieux d'assouplir un peu le comportement par défaut.)

L'évaluation (eval) sans surveillance de ces "scripts" entrants peut amener perl à lire et écrire des fichiers et à invoquer des sous-processus sous votre nom. Le contrôle d'accès basé sur l'hôte, tel que celui fourni par xhost, est particulièrement peu sûr, car il permet à quiconque ayant un compte sur des hôtes particuliers de se connecter à votre serveur, et s'il est désactivé, il permet à quiconque, n'importe où, de se connecter à votre serveur. Afin de fournir au moins un peu de sécurité, Tk core vérifie le contrôle d'accès utilisé par le serveur et rejette les transmissions entrantes sauf si (a) le contrôle d'accès de type xhost est activé (c'est-à-dire que seuls certains hôtes peuvent établir des connexions) et (b) la liste des hôtes activés est vide. Cela signifie que les applications ne peuvent pas se connecter à votre serveur à moins d'utiliser une autre forme d'autorisation comme celle fournie par xauth.

VOIR AUSSI

"eval" dans perlfunc, Safe, les directives de sécurité de l'administrateur système/de l'entreprise, etc.
