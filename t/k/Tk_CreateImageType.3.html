Tk_CreateImageType(3) Procédures de la bibliothèque Tk Tk_CreateImageType(3)

NOM

Tk_CreateImageType, Tk_GetImageMasterData, Tk_GetImageModelData, Tk_InitImageArgs - définir un nouveau type d'image

SYNOPIS

#include <tk.h>

Tk_CreateImageType(typePtr)

ClientData
Tk_GetImageMasterData(interp, name, typePtrPtr)

ClientData
Tk_GetImageModelData(interp, name, typePtrPtr)

Tk_InitImageArgs(interp, argc, argvPtr)

ARGUMENTS

const Tk_ImageType *typePtr (entree)
Structure qui définit le nouveau type d'image. Pour Tk 8.4 et antérieur, cela doit être statique : un pointeur vers cette structure est conservé par le code image. Dans Tk 8.5, cette limitation a été assouplie.
Tcl_Interp *interp (entree)
Interpréteur dans lequel l'image a été créée.
const char *name (entree)
Nom de l'image existante.
Tk_ImageType **typePtrPtr (sortie)
Pointe vers un mot dans lequel stocker un pointeur vers les informations de type pour l'image donnée, si elle existe.
int argc (entree)
Nombre d'arguments
char ***argvPtr (entree/sortie)
Pointeur vers la liste d'arguments

DESCRIPTION

Tk_CreateImageType est appelée pour définir un nouveau type d'image. Un type d'image correspond à une valeur particulière de l'argument type pour la commande image create. Il peut exister un nombre quelconque de types d'images différents, et de nouveaux types peuvent être définis dynamiquement en appelant Tk_CreateImageType. Par exemple, il pourrait y avoir un type pour les bitmaps 2 couleurs, un autre pour les images multicolores, un autre pour les images tramées, un autre pour la vidéo, et ainsi de suite.

Le code qui implémente un nouveau type d'image est appelé un *gestionnaire d'images* (*image manager*). Il se compose d'une collection de procédures et de trois types différents de structures de données. La première structure de données est une structure Tk_ImageType, qui contient le nom du type d'image et des pointeurs vers cinq procédures fournies par le gestionnaire d'images pour traiter les images de ce type :

typedef struct Tk_ImageType {
    const char *name;
    Tk_ImageCreateProc *createProc;
    Tk_ImageGetProc *getProc;
    Tk_ImageDisplayProc *displayProc;
    Tk_ImageFreeProc *freeProc;
    Tk_ImageDeleteProc *deleteProc;
} Tk_ImageType;
Les champs de cette structure seront décrits dans les sous-sections ultérieures de cette entrée.

La deuxième structure de données majeure manipulée par un gestionnaire d'images est appelée un *modèle d'image* (*image model*); elle contient des informations générales sur une image particulière, telles que les valeurs des options de configuration spécifiées dans une commande image create. Il y aura généralement une de ces structures pour chaque invocation de la commande image create.

La troisième structure de données liée aux images est une *instance d'image* (*image instance*). Il y aura généralement une de ces structures pour chaque utilisation d'une image dans un widget particulier. Il est possible qu'une même image apparaisse simultanément dans plusieurs widgets, ou même plusieurs fois dans le même widget. De plus, différentes instances peuvent se trouver sur des écrans ou des affichages différents. La structure de données d'instance d'image décrit des éléments qui peuvent varier d'une instance à l'autre, tels que les couleurs et les contextes graphiques pour le redessin. Il y a généralement une structure d'instance pour chaque option -image spécifiée pour un widget ou un élément de canevas.

Les sous-sections suivantes décrivent plus en détail les champs d'une Tk_ImageType.

NOM

typePtr->name fournit un nom pour le type d'image. Une fois que Tk_CreateImageType est retournée, ce nom peut être utilisé dans les commandes image create pour créer des images du nouveau type. S'il existait déjà un type d'image portant ce nom, alors le nouveau type d'image remplace l'ancien.

CREATEPROC

typePtr->createProc fournit l'adresse d'une procédure que Tk appellera chaque fois que image create est invoquée pour créer une image du nouveau type. typePtr->createProc doit correspondre au prototype suivant :

typedef int Tk_ImageCreateProc(
        Tcl_Interp *interp,
        const char *name,
        int objc,
        Tcl_Obj *const objv[],
        const Tk_ImageType *typePtr,
        Tk_ImageMaster model,
        ClientData *modelDataPtr);
L'argument interp est l'interpréteur dans lequel la commande image a été invoquée, et name est le nom de la nouvelle image, qui a été soit spécifié explicitement dans la commande image, soit généré automatiquement par la commande image. Les arguments objc et objv décrivent toutes les options de configuration pour la nouvelle image (tout ce qui suit l'argument de nom de image). L'argument model est un jeton qui fait référence aux informations de Tk sur cette image ; le gestionnaire d'images doit renvoyer ce jeton à Tk lors de l'invocation de la procédure Tk_ImageChanged. Typiquement, createProc analysera objc et objv et créera une structure de données de modèle d'image pour la nouvelle image. createProc peut stocker une valeur arbitraire d'un mot dans *modelDataPtr, qui sera renvoyée au gestionnaire d'images lors de l'invocation d'autres rappels. Typiquement, la valeur est un pointeur vers la structure de données du modèle pour l'image.

Si createProc rencontre une erreur, elle doit laisser un message d'erreur dans le résultat de l'interpréteur et retourner TCL_ERROR ; sinon, elle doit retourner TCL_OK.

createProc doit appeler Tk_ImageChanged afin de définir la taille de l'image et demander un redessin initial.

GETPROC

typePtr->getProc est invoquée par Tk chaque fois qu'un widget appelle Tk_GetImage pour utiliser une image particulière. Cette procédure doit correspondre au prototype suivant :

typedef ClientData Tk_ImageGetProc(
        Tk_Window tkwin,
        ClientData modelData);
L'argument tkwin identifie la fenêtre dans laquelle l'image sera utilisée et modelData est la valeur retournée par createProc lorsque le modèle d'image a été créé. getProc créera généralement une structure de données pour la nouvelle instance, incluant des éléments tels que les ressources nécessaires pour afficher l'image dans la fenêtre donnée. getProc renvoie un jeton d'un mot pour l'instance, qui est typiquement l'adresse de la structure de données de l'instance. Tk renverra cette valeur au gestionnaire d'images lors de l'invocation de ses procédures displayProc et freeProc.

DISPLAYPROC

typePtr->displayProc est invoquée par Tk chaque fois qu'une image doit être affichée (c'est-à-dire chaque fois qu'un widget appelle Tk_RedrawImage). displayProc doit correspondre au prototype suivant :

typedef void Tk_ImageDisplayProc(
        ClientData instanceData,
        Display *display,
        Drawable drawable,
        int imageX,
        int imageY,
        int width,
        int height,
        int drawableX,
        int drawableY);
L'argument instanceData sera identique à la valeur retournée par getProc lors de la création de l'instance. display et drawable indiquent où afficher l'image ; drawable peut être un pixmap plutôt que la fenêtre spécifiée à getProc (c'est généralement le cas, car la plupart des widgets utilisent la double mise en mémoire tampon pour leur redessin afin d'obtenir des effets visuels plus fluides). imageX, imageY, width et height identifient la région de l'image qui doit être redessinée. Cette région sera toujours dans les limites de la taille de l'image telle que spécifiée dans le dernier appel à Tk_ImageChanged. drawableX et drawableY indiquent où dans drawable l'image doit être affichée ; displayProc doit afficher la région donnée de l'image de telle sorte que le point (imageX, imageY) dans l'image apparaisse à (drawableX, drawableY) dans drawable.

FREEPROC

typePtr->freeProc contient l'adresse d'une procédure que Tk appellera lorsqu'une instance d'image sera libérée (c'est-à-dire lorsque Tk_FreeImage sera invoquée). Cela peut se produire, par exemple, lorsqu'un widget est supprimé ou qu'un élément d'image dans un canevas est supprimé, ou lorsque l'image affichée dans un widget ou un élément de canevas est modifiée. freeProc doit correspondre au prototype suivant :

typedef void Tk_ImageFreeProc(
        ClientData instanceData,
        Display *display);
L'argument instanceData est le jeton retourné par getProc lors de la création de l'instance. display est le même affichage que celui utilisé pour getProc. La procédure freeProc est responsable de la libération de toutes les ressources associées à cette instance d'image, telles que les contextes graphiques ou les pixmaps.

DELETEPROC

typePtr->deleteProc contient l'adresse d'une procédure que Tk appellera lorsque le modèle d'une image est supprimé (c'est-à-dire lorsque image delete est invoqué ou lorsque le nom d'une image est utilisé pour en créer une nouvelle). deleteProc doit correspondre au prototype suivant :

typedef void Tk_ImageDeleteProc(
        Tcl_Interp *interp,
        ClientData modelData);
L'argument modelData est la valeur qui a été stockée dans *modelDataPtr par createProc lorsque le modèle d'image a été créé. La procédure deleteProc est responsable de la libération de toutes les ressources associées au modèle d'image, telles que la structure de données du modèle elle-même. Elle ne doit *pas* libérer les ressources des instances, car cela est géré par freeProc.

TK_GETIMAGEMASTERDATA

La procédure Tk_GetImageMasterData recherche un type d'image existant nommé name et renvoie les données du modèle pour cette image. Elle renvoie également un pointeur vers la structure Tk_ImageType utilisée pour ce type d'image dans *typePtrPtr. S'il n'existe aucune image portant le nom name, ou si le type d'image correspondant n'a pas été enregistré, elle renvoie NULL.

C'est une fonction utilitaire pour les gestionnaires d'images qui ont besoin de récupérer les informations d'un autre type d'image.

TK_GETIMAGEMODELDATA

La procédure Tk_GetImageModelData est un alias obsolète pour Tk_GetImageMasterData.

TK_INITIMAGEARGS

La procédure Tk_InitImageArgs est une procédure utilitaire qui analyse les arguments de la ligne de commande argc et argvPtr (qui sont censés être des chaînes de caractères) et les transforme en un tableau de pointeurs vers des objets Tcl. Elle place le nombre d'arguments dans l'élément 0 du tableau et le tableau résultant dans l'élément 1 du tableau. Elle renvoie TCL_OK en cas de succès, ou TCL_ERROR en cas d'erreur, laissant un message d'erreur dans l'interpréteur.

Cette procédure est rarement utilisée directement, car les types d'images plus récents utilisent généralement les arguments d'objets Tcl.

KEYWORDS

image type, Tk_ImageType, Tk_ImageCreateProc, Tk_ImageGetProc, Tk_ImageDisplayProc, Tk_ImageFreeProc, Tk_ImageDeleteProc

NOM

Tk_ImageFreeProc, Tk_ImageDeleteProc, Tk_GetImageMasterData, Tk_ImageModel, USE_OLD_IMAGE

SYNOPSIS

typedef void Tk_ImageFreeProc(ClientData instanceData, Display *display);
typedef void Tk_ImageDeleteProc(ClientData modelData);
typedef int Tk_ImageCreateProc(Tcl_Interp *interp, char *name, int argc, char **argv, Tk_ImageType *typePtr, Tk_ImageMaster model, ClientData *modelDataPtr);

ARGUMENTS

instanceData : valeur renvoyée par getProc lors de la création de l'instance.
display : affichage contenant la fenêtre de l'instance.
modelData : valeur stockée dans *modelDataPtr par createProc lors de la création de l'instance.
typePtr : valeur passée à Tk_CreateImageType lors de l'enregistrement du type d'image.
model : valeur de Tk_ImageMaster pour l'instance.
modelDataPtr : pointeur vers la structure de données du modèle d'image.

DESCRIPTION

L'instanceData sera la même que la valeur renvoyée par getProc lors de la création de l'instance, et display est l'affichage contenant la fenêtre de l'instance. freeProc doit libérer les ressources associées à l'instance, car elle ne sera plus jamais utilisée.

Le modelData sera la même que la valeur stockée dans *modelDataPtr par createProc lors de la création de l'instance. deleteProc doit libérer les ressources associées à l'image.

TK_GETIMAGEMODELDATA

La fonction Tk_GetImageMasterData peut être appelée pour récupérer des informations sur une image. Par exemple, un gestionnaire d'images peut utiliser cette fonction pour localiser ses informations de modèle d'image pour une image. Si une image nommée name existe dans l'interpréteur fourni par interp, alors *typePtrPtr sera rempli avec les informations de type de l'image (la valeur de typePtr passée à Tk_CreateImageType lors de l'enregistrement du type d'image) et la valeur de retour est la valeur de ClientData renvoyée par createProc lors de la création de l'image (il s'agit généralement d'un pointeur vers la structure de données du modèle d'image). Si une telle image n'existe pas, NULL est renvoyé et NULL est stocké dans *typePtrPtr.

Tk_GetImageModelData est synonyme de Tk_GetImageMasterData.

PRISE EN CHARGE DE L'INTERFACE DE LEGACY

Dans Tk 8.2 et les versions antérieures, la définition de Tk_ImageCreateProc était incompatible, avec le prototype suivant :

typedef int Tk_ImageCreateProc(Tcl_Interp *interp, char *name, int argc, char **argv, Tk_ImageType *typePtr, Tk_ImageMaster model, ClientData *modelDataPtr);
Les programmes et bibliothèques plus anciens peuvent encore contenir du code qui définit des types d'images étendus en utilisant l'ancienne interface. Le fichier d'en-tête Tk continuera de prendre en charge cette ancienne interface si elle est compilée avec la macro USE_OLD_IMAGE définie.

Tk_ImageModel est synonyme de Tk_ImageMaster.

Lorsque la prise en charge de l'interface ancienne est activée, vous pouvez voir la procédure Tk_InitImageArgs en cours d'utilisation. Il s'agissait d'un outil de migration utilisé pour créer des extensions avec des stubs pouvant être chargés dans des interps avec toutes les versions de Tk 8.1 et ultérieures. Tk 8.5 ne fournit plus cette procédure, mais utilise une macro pour convertir tout appel à cette procédure en un commentaire vide. Toute extension avec un type d'image étendu via l'ancienne interface qui est compilée contre les en-têtes Tk 8.5 et liée à la bibliothèque de stubs Tk 8.5 produira un fichier qui ne peut être chargé que dans les interps avec Tk 8.5 ou version ultérieure ; c'est-à-dire les règles de compatibilité des stubs normales. Si un développeur souhaite générer un fichier qui peut être chargé dans des interps avec Tk 8.4 ou version antérieure, il doit utiliser les en-têtes et les bibliothèques Tk 8.4.

Tout nouveau code écrit aujourd'hui doit éviter d'utiliser les anciennes interfaces. Leur prise en charge sera perdue dans Tk 9.
