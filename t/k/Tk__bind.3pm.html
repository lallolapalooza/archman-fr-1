bind(3) Documentation Perl fournie par la communauté bind(3)

NOM

Tk::bind - Organiser les événements X pour appeler des rappels

SYNTAXE

Récupérer les liaisons :

    $widget->bind

    $widget->bind(tag)

    $widget->bind(séquence)

    $widget->bind(tag,séquence)

Associer et détruire les liaisons :

    $widget->bind(séquence,rappel)

    $widget->bind(tag,séquence,rappel)

DESCRIPTION

La méthode bind associe des rappels aux événements X. Si rappel est spécifié, bind organisera l'évaluation de rappel chaque fois que les événements spécifiés par séquence se produiront dans la ou les fenêtres identifiées par $widget ou par tag. Si rappel est une chaîne vide, la liaison actuelle pour séquence est détruite, rendant séquence non liée. Dans tous les cas où un argument rappel est fourni, bind retourne une chaîne vide.

Si séquence est spécifié sans rappel, alors le rappel actuellement lié à séquence est retourné, ou undef est retourné s'il n'y a pas de liaison pour séquence. Si ni séquence ni rappel ne sont spécifiés, la valeur de retour est une liste dont les éléments sont toutes les séquences pour lesquelles il existe des liaisons pour tag.

Si aucun tag n'est spécifié, bind fait référence à $widget. Si tag est spécifié, il s'agit généralement d'un nom de classe et bind fait référence à toutes les instances de la classe sur la MainWindow associée à $widget. (Il est possible pour tag d'être un autre "objet widget", mais cette pratique est dépréciée.) La fonction Perl ref($objet) peut être utilisée pour obtenir le nom de la classe de n'importe quel objet. Chaque fenêtre a une liste de tags associée, et une liaison s'applique à une fenêtre particulière si son tag fait partie de ceux spécifiés pour la fenêtre. Bien que la méthode bindtags puisse être utilisée pour attribuer un ensemble arbitraire de tags de liaison à une fenêtre, les tags de liaison par défaut offrent le comportement suivant :

Si un tag est le nom d'une fenêtre interne, la liaison s'applique à cette fenêtre.

Si le tag est le nom d'une fenêtre de niveau supérieur, la liaison s'applique à la fenêtre de niveau supérieur et à toutes ses fenêtres internes.

Si le tag est le nom d'une classe de widgets, telle que Tk::Button, la liaison s'applique à tous les widgets de cette classe ;

Si tag a la valeur all, la liaison s'applique à toutes les fenêtres descendantes de la MainWindow de l'application.

MOTIFS D'ÉVÉNEMENT

L'argument séquence spécifie une séquence d'un ou plusieurs motifs d'événements, avec un espace blanc optionnel entre les motifs. Chaque motif d'événement peut prendre l'une des trois formes. Dans le cas le plus simple, il s'agit d'un seul caractère ASCII imprimable, tel que a ou [. Le caractère ne peut pas être un espace blanc ou le caractère <. Cette forme de motif correspond à un événement KeyPress pour le caractère particulier. La deuxième forme de motif est plus longue mais plus générale. Elle a la syntaxe suivante :

    '<modificateur-modificateur-type-détail>'

Le motif d'événement complet est entouré d'accolades, et doit normalement être mis entre guillemets, car les accolades sont spéciales pour Perl. À l'intérieur des accolades se trouvent zéro ou plusieurs modificateurs, un type d'événement et une information supplémentaire (détail) identifiant un bouton ou une keysym particulière. N'importe lequel des champs peut être omis, tant qu'au moins l'un des champs type et détail est présent. Les champs doivent être séparés par des espaces blancs ou des tirets.

La troisième forme de motif est utilisée pour spécifier un événement virtuel nommé et défini par l'utilisateur ; voir Tk::event pour plus de détails. Elle a la syntaxe suivante :

    '<<nom>>'

Le motif d'événement virtuel complet est entouré de doubles accolades. À l'intérieur des accolades se trouve le nom défini par l'utilisateur de l'événement virtuel. Les modificateurs, tels que Shift ou Control, ne peuvent pas être combinés avec un événement virtuel pour le modifier. Les liaisons sur un événement virtuel peuvent être créées avant que l'événement virtuel ne soit défini, et si la définition d'un événement virtuel change dynamiquement, toutes les fenêtres liées à cet événement virtuel répondront immédiatement à la nouvelle définition.

MODIFICATEURS

Les modificateurs consistent en n'importe laquelle des valeurs suivantes :

Control        Mod2, M2
Shift          Mod3, M3
Lock           Mod4, M4
Button1, B1    Mod5, M5
Button2, B2    Meta, M
Button3, B3    Alt
Button4, B4    Double
Button5, B5    Triple
Mod1,    M1    Quadruple

Lorsque plusieurs valeurs sont listées, séparées par des virgules, les valeurs sont équivalentes. La plupart des modificateurs ont les significations X évidentes. Par exemple, Button1 exige que le bouton 1 soit enfoncé lorsque l'événement se produit. Pour qu'une liaison corresponde à un événement donné, les modificateurs de l'événement doivent inclure tous ceux spécifiés dans le motif d'événement. Un événement peut également contenir des modificateurs supplémentaires non spécifiés dans la liaison. Par exemple, si le bouton 1 est enfoncé alors que les touches Shift et Control sont enfoncées, le motif <Control-Button-1> correspondra à l'événement, mais <Mod1-Button-1> ne correspondra pas. Si aucun modificateur n'est spécifié, alors n'importe quelle combinaison de modificateurs peut être présente dans l'événement.

Meta et M font référence à celui des modificateurs M1 à M5 qui est associé aux touches Meta sur le clavier (keysyms Meta_R et Meta_L). S'il n'y a pas de touches Meta, ou si elles ne sont associées à aucun modificateur, alors Meta et M ne correspondra à aucun événement. De même, le modificateur Alt fait référence au modificateur associé aux touches Alt sur le clavier (keysyms Alt_L et Alt_R).

Les modificateurs Double, Triple et Quadruple sont une commodité pour spécifier des doubles clics de souris et d'autres événements répétés. Ils provoquent la répétition d'un motif d'événement donné 2, 3 ou 4 fois, et imposent également une exigence de temps et d'espace sur la séquence : pour qu'une séquence d'événements corresponde à un motif Double, Triple ou Quadruple, tous les événements doivent se produire à bref délai et sans mouvement de souris important entre les deux. Par exemple, <Double-Button-1> équivaut à <Button-1><Button-1> avec l'exigence supplémentaire de temps et d'espace.

TYPES D'ÉVÉNEMENT

Le champ type peut être n'importe quel type d'événement X standard, avec quelques abréviations supplémentaires. Ci-dessous se trouve une liste de tous les types valides ; lorsque deux noms apparaissent ensemble, ils sont synonymes.

Activate            Destroy            Map
ButtonPress, Button Enter              MapRequest
ButtonRelease       Expose             Motion
Circulate           FocusIn            MouseWheel
CirculateRequest    FocusOut           Property
Colormap            Gravity            Reparent
Configure           KeyPress, Key      ResizeRequest
ConfigureRequest    KeyRelease         Unmap
Create              Leave              Visibility
Deactivate

La plupart des événements ci-dessus ont les mêmes champs et comportements que les événements dans le système de fenêtrage X. Vous pouvez trouver des descriptions plus détaillées de ces événements dans n'importe quel livre de programmation X Window. Quelques-uns des événements sont des extensions au système d'événements X pour prendre en charge des fonctionnalités uniques aux plateformes Macintosh et Windows. Nous fournissons un peu plus de détails sur ces événements ici. Ils incluent :

Activate
Deactivate

Ces deux événements sont envoyés à chaque sous-fenêtre d'une fenêtre de niveau supérieur lorsqu'elles changent d'état. En plus de la fenêtre de focus, les plateformes Macintosh et Windows ont une notion de fenêtre active (qui a souvent, mais pas nécessairement, le focus). Sur Macintosh, les widgets dans la fenêtre active ont une apparence différente de celle des widgets dans les fenêtres inactives. L'événement Activate est envoyé à toutes les sous-fenêtres d'une fenêtre de niveau supérieur lorsqu'elle passe de l'état inactif à l'état actif. De même, l'événement Deactive est envoyé lors du changement

Tk::bind - perlTk - man page

NAME

Tk::bind

bind - define event handlers for widget events

SYNOPSIS

    $widget->bind(sequence => callback, ...)
    $widget->bind(sequence, callback)

DESCRIPTION

The bind method is used to associate Perl subroutines (or other callbacks) with events that occur on a widget. When an event occurs that matches a given sequence, the associated callback is invoked. The callback will be invoked with the widget as its first argument, and then with any arguments that Tk passes on to the callback.

Multiple bindings may be defined for the same widget, and a single sequence may be associated with multiple callbacks. The bindings are checked in order of decreasing precedence. A binding's precedence is determined by the specificity of its sequence, and by the tags associated with the widget.

The argument list for bind consists of pairs of sequence and callback arguments. The sequence is a string describing the event, and the callback is a Perl subroutine reference. For example:

    $widget->bind('<Button-1>', sub { print "Button 1 clicked!\n" });
    $widget->bind('<KeyPress-a>', \&my_handler);

When there are multiple bindings defined for a widget, the bindings are checked in the order they are defined. The first binding that matches the event is executed, and no further bindings are checked unless the callback explicitly invokes Tk->continue.

The callback may also be a string containing a Perl expression to be evaluated.

See also Tk::callbacks for a discussion of different types of callbacks, and Tk::bindtags for how to control the order in which bindings are checked.

EVENT PATTERNS

An event pattern is a string consisting of zero or more modifier keys, followed by an event type, followed by an optional detail field. The parts of the pattern are separated by dashes. For example, <Control-Button-1> is an event pattern.

MODIFIERS

The following are recognized modifier keys: Shift, Control, Alt, Meta, Button-1, Button-2, Button-3, Button-4, Button-5.

The modifiers Button-1 through Button-5 refer to the mouse buttons.

EVENT TYPES

The following are recognized event types:

Activate
The widget has been entered or left by the mouse pointer.
ButtonPress
A mouse button has been pressed.
ButtonRelease
A mouse button has been released.
Circulate
A window has been circulated (raised or lowered).
Colormap
The colormap associated with the window has changed.
Configure
The geometry of the window has changed.
Destroy
The window is being destroyed.
Enter
The mouse pointer has entered the widget.
Expose
Part of the window has become visible.
FocusIn
The widget has gained keyboard focus.
FocusOut
The widget has lost keyboard focus.
KeyPress
A key has been pressed.
KeyRelease
A key has been released.
Leave
The mouse pointer has left the widget.
Map
The window has been mapped (made visible).
MappingNotify
A keyboard mapping has changed.
Motion
The mouse pointer has moved.
MouseWheel
The mouse wheel has been rotated.
Property
A window property has changed.
Reparent
The window has been reparented.
Unmap
The window has been unmapped (made invisible).
Visibility
The visibility of the window has changed.

The event type can optionally be followed by a detail field. For example, <ButtonPress-1> refers to the first button press event, while <KeyPress-a> refers to the 'a' key press event. The detail field can be a specific key name (e.g., 'a', 'Return', 'Shift_L'), or a button number (e.g., 1, 2, 3).

Virtual events are also supported. They are denoted by names enclosed in double angle brackets, e.g., <<Paste>>. Virtual events can be defined using eventAdd.

BINDING CALLBACKS AND SUBSTITUTIONS

When a callback is invoked, Tk passes a number of arguments to it. The first argument is the widget that the event occurred on. The remaining arguments depend on the event type.

For certain event types, Tk performs substitutions in the callback string. These substitutions are similar to those performed by tk_menu_popup.

  • %W: The name of the widget.
  • %x: The X coordinate of the mouse pointer relative to the widget.
  • %y: The Y coordinate of the mouse pointer relative to the widget.
  • %A: The detail field of the event (e.g., the key pressed, or the button number).
  • %T: The type of the event.
  • %E: The full event name (e.g., <ButtonPress-1>).
  • %K: The key symbol, if applicable.

If the callback is a Perl subroutine reference, Tk will call the subroutine with the widget as the first argument, followed by the event arguments. If the callback is a string, Tk will evaluate the string as a Perl expression.

The return value of the callback controls the processing of matching callbacks. If return is invoked, then the current callback is terminated but Tk will continue processing callbacks associated with other tag's. If Tk->break is invoked within a callback, then that callback terminates and no other callbacks will be invoked for the event. (Tk->break is implemented via perl's die with a special value which is "caught" by the perl/Tk "glue" code.)

MULTIPLE MATCHES

If more than one binding matches a particular event and they have the same tag, then the most specific binding is chosen and its callback is evaluated. The following tests are applied, in order, to determine which of several matching sequences is more specific: (a) an event pattern that specifies a specific button or key is more specific than one that doesn't; (b) a longer sequence (in terms of number of events matched) is more specific than a shorter sequence; (c) if the modifiers specified in one pattern are a subset of the modifiers in another pattern, then the pattern with more modifiers is more specific. (d) a virtual event whose physical pattern matches the sequence is less specific than the same physical pattern that is not associated with a virtual event. (e) given a sequence that matches two or more virtual events, one of the virtual events will be chosen, but the order is undefined.

If the matching sequences contain more than one event, then tests (c)-(e) are applied in order from the most recent event to the least recent event in the sequences. If these tests fail to determine a winner, then the most recently registered sequence is the winner.

If there are two (or more) virtual events that are both triggered by the same sequence, and both of those virtual events are bound to the same window tag, then only one of the virtual events will be triggered, and it will be picked at random:

$widget->eventAdd('<<Paste>>' => '<Control-y>');
$widget->eventAdd('<<Paste>>' => '<Button-2>');
$widget->eventAdd('<<Scroll>>' => '<Button-2>');
$widget->bind('Tk::Entry','<<Paste>>',sub { print 'Paste'});
$widget->bind('Tk::Entry','<<Scroll>>', sub {print 'Scroll'});

If the user types Control-y, the <<Paste>> binding will be invoked, but if the user presses button 2 then one of either the <<Paste>> or the <<Scroll>> bindings will be invoked, but exactly which one gets invoked is undefined.

If an X event does not match any of the existing bindings, then the event is ignored. An unbound event is not considered to be an error.

MULTI-EVENT SEQUENCES AND IGNORED EVENTS

When a sequence specified in a bind method contains more than one event pattern, then its callback is executed whenever the recent events (leading up to and including the current event) match the given sequence. This means, for example, that if button 1 is clicked repeatedly the sequence <Double-ButtonPress-1> will match each button press but the first. If extraneous events that would prevent a match occur in the middle of an event sequence then the extraneous events are ignored unless they are KeyPress or ButtonPress events. For example, <Double-ButtonPress-1> will match a sequence of presses of button 1, even though there will be ButtonRelease events (and possibly Motion events) between the ButtonPress events. Furthermore, a KeyPress event may be preceded by any number of other KeyPress events for modifier keys without the modifier keys preventing a match. For example, the event sequence aB will match a press of the a key, a release of the a key, a press of the Shift key, and a press of the b key: the press of Shift is ignored because it is a modifier key. Finally, if several Motion events occur in a row, only the last one is used for purposes of matching binding sequences.

ERRORS

If an error occurs in executing the callback for a binding then the Tk::Error mechanism is used to report the error. The Tk::Error mechanism will be executed at same call level, and associated with the same MainWindow as as the callback was invoked.

CAVEATS

Note that for the Canvas widget, the call to bind has to be fully qualified. This is because there is already a bind method for the Canvas widget, which binds individual canvas tags.

    $canvas->Tk::bind
