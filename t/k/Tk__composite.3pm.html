DESCRIPTION

L'intention derrière un composite est de créer un widget de plus haut niveau, parfois appelé "super-widget" ou "méga-widget". Le plus souvent, un composite sera construit sur d'autres widgets en les utilisant, par opposition à la spécialisation sur ceux-ci. Par exemple, le widget composite fourni LabEntry est composé d'un Entry et d'un Label ; il n'est ni une sorte de Label, ni une sorte de Entry.

La plupart du travail d'un widget composite consiste à créer des sous-widgets, à organiser la distribution des options de configuration aux sous-widgets appropriés et à gérer les options de configuration spécifiques au composite.

DÉTAILS DE LA GLOIRE

Selon votre connaissance de Perl/Tk, cette section peut être éclairante ou déroutante.

Widget Composite

Comme Perl/Tk utilise beaucoup une approche orientée objet, il n'est pas surprenant que la création d'un composite passe par une méthode new(). Cependant, le composite ne définit normalement pas lui-même une méthode new() : il suffit généralement d'en hériter de Tk::Widget.

C'est ce qui se passe lorsque le composite utilise

use base qw/ Tk::Frame /;  # ou Tk::Toplevel

pour spécifier sa chaîne d'héritage. Pour compléter l'initialisation du widget, il doit appeler la méthode Construct de la classe Widget. Cette méthode accepte le nom de la nouvelle classe à créer, c'est-à-dire le nom du paquet de votre widget composite :

Construct Tk::Widget 'MyNewWidget';

Ici, MyNewWidget est le nom du paquet (également appelé la classe du widget). Cela définira une méthode constructeur pour MyNewWidget, normalement nommée d'après la classe du widget. L'instanciation de ce composite dans le code client ressemblerait alors à ceci :

$mw = MainWindow->new;       # crée une fenêtre principale de niveau supérieur
$self = $mw->MyNewWidget();  # crée une instance du
                             # widget composite MyNewWidget

Chaque fois qu'un composite est instancié dans le code client, Tk::Widget::new() sera appelé via le constructeur de classe du widget. Cette méthode new appellera

$self->Populate(\%args);

où %args sont les arguments passés au constructeur du widget. Notez que Populate reçoit une référence vers le tableau associatif contenant tous les arguments.

Populate est généralement défini dans la classe (paquet) du composite, qui crée les sous-widgets caractéristiques de la classe.

Création de sous-widgets

La création de sous-widgets se fait généralement dans Populate(). Le composite appelle généralement la méthode constructeur du sous-widget soit directement, pour les sous-widgets "privés", soit indirectement via la méthode Component pour les sous-widgets qui doivent être annoncés aux clients.

Populate peut appeler Delegates pour diriger les appels vers les méthodes des sous-widgets choisis. Pour des composites simples, généralement la plupart, sinon toutes les méthodes, sont dirigées vers un seul sous-widget - par exemple, ScrListbox dirige toutes les méthodes vers le Listbox central afin que les appels $composite->get(...) appellent $listbox->get(...).

Définition des options de méga-widget

Populate doit également appeler ConfigSpecs() pour spécifier la manière dont les options de type configuration doivent être gérées dans le composite. Une fois que Populate est retourné, la méthode Tk::Frame::ConfigDefault parcourt les entrées de ConfigSpecs et remplit le tableau associatif %$args avec les valeurs par défaut des options provenant des ressources X (.Xdefaults, etc.).

Lorsque Populate retourne à Tk::Widget::new(), un appel à $self->configure(%$args) est effectué, ce qui définit *toutes* les options.
