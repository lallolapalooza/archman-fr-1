NOM

Tk::Internals - ce que fait l'interface Perl Tk lorsque vous appelez des fonctions Tk.

Ces informations sont plus que nulles pour les utilisateurs de "perlTk", mais peuvent être d'une certaine aide pour ceux qui s'intéressent à l'utilisation d'une source Tk modifiée avec "perlTk".

Ce document est en cours de rédaction. On pense que les informations sont pertinentes pour la version de "portableTk" disponible au moment de sa création. Tous les détails sont susceptibles d'être modifiés.

DESCRIPTION

Pré-compilation
Avant l'étape de compilation proprement dite, un script analyse la source et extrait les sous-commandes des différentes commandes. Ces informations résident dans le fichier "pTk/Methods.def".
Compilation
Pendant la compilation, le fichier ci-dessus est inclus dans la source de la routine de démarrage de la bibliothèque dynamique (ou statique). Plus précisément, le code de démarrage du module "Tk" appelle la sous-routine Boot_Glue() du module "tkGlue.c", et cette sous-routine inclut le fichier (avec les définitions de macros appropriées).
À l'intérieur de "use Tk;"
Le module initialise le code C, puis charge les bibliothèques Perl. Le cœur du code Perl est contenu dans la bibliothèque "Tk::Widget", tous les widgets héritent de ce module. Le code pour les fenêtres de plus haut niveau est chargé depuis "Tk::MainWindow".

Lors de l'initialisation du code de liaison C, les codes "Xevent::?" et une poignée de routines "Tk::Widget" et "Tk::Image" sont définis. (Beaucoup plus de XSUB sont créés à partir du code "Tk.xs".) Les sous-commandes des widgets sont liées à Perl sur la base de la liste incluse depuis "pTk/Methods.def". En fait, toutes les sous-commandes sont liées à des XSUB qui sont liées à la même sous-routine C XStoWidget(), mais qui ont des parties de données différentes.

Pendant l'initialisation du code Perl, la méthode "Tk::Widget::import" est appelée. Cet appel requiert tout le code des packages de widgets particuliers.

Le code des packages de widgets appelle une commande obscure comme

(bless \"Text")->WidgetClass;

Cette commande (en fait Tk::Widget::WidgetClass()) crée trois routines : Tk::Widget::Text(), Tk::Widget::isText(), et Tk::Text::isText(). La première est essentiellement le "new" de "Tk::Text", les deux autres retournent des constantes. Elle place également la classe dans le dépôt.

À l'intérieur de "$top = MainWindow->new;"
C'est assez intuitif. Cet appel va directement à "Tk::MainWindow::new", qui appelle le XSUB "Tk::MainWindow::CreateMainWindow", qui appelle la sous-routine C Tk_CreateMainWindow(). C'est une sous-routine "Tk", donc ici la magie noire prend fin (presque).

La seule magie noire restante est que la routine d'initialisation "Tk" crée beaucoup de commandes, mais la sous-routine de création est usurpée par "portableTk" et les commandes sont créées dans le package "Tk". Elles sont associées à des XSUB qui sont liées à l'une des trois sous-routines C XStoSubCmd(), XStoBind(), ou XStoTk(), mais qui ont des parties de données différentes.

Le résultat de l'appel est béni dans "Tk::MainWindow", comme il se doit.

À l'intérieur de "$top->title('Text demo');"
Le package "Tk::Toplevel" définit beaucoup de sous-routines à la volée sur une certaine liste. Toutes les commandes de la liste sont converties en sous-commandes correspondantes de la méthode "wm" du widget. Ici, la sous-commande est une commande avec un deuxième argument particulier (dans ce cas, "title"). Rappelez-vous que le premier argument est $self.

Maintenant, "Tk::Toplevel" @ISA "Tk::Widget", qui à son tour @ISA "Tk". Donc, un appel à "$top->wm('title','Text demo')" appelle "Tk::wm", qui est défini lors de l'appel à Tk_CreateMainWindow(). Comme décrit ci-dessus, le XSUB associé à XStoSubCmd() est appelé.

Cette routine C est définie dans "tkGlue.c". Elle récupère la partie de données du XSUB, crée un "SV" avec le nom de la commande, et appelle Call_Tk() avec les données du XSUB comme premier argument, et avec le nom du XSUB empilé sur la pile Perl à l'endroit où "tk" s'attend à le trouver. (En fait, elle peut également réorganiser les arguments si elle pense que c'est ce que vous voulez).

La procédure ultérieure extrait le nom de la procédure "tk" et "clientData" du premier argument et effectue un appel, en utilisant la pile Perl comme "argv" pour la procédure. Beaucoup de magie noire s'opère ensuite pour convertir le résultat de la procédure en un tableau Perl de retour.

À l'intérieur de "$text = $top->Text(background => $txtBg);"
Ci-dessus, nous avons discuté de la façon dont la commande "Tk::Widget::Text" est créée. La commande ci-dessus l'appelle via l'héritage. Elle est traduite en 
Tk::Text::new($top, background => $txtBg);

Le package "Tk::Text" n'a pas de méthode "new", donc "Tk::Widget::new" est appelé. À son tour, il appelle "Tk::Text->DoInit($top)", qui est "Tk::Widget::DoInit(Tk::Text,$top)", qui initialise les liaisons si nécessaire. Ensuite, il crée le nom du widget de la forme ".text0", et appelle "Tk::text('.text0', background => $txtBg)" (notez la casse minuscule). Le résultat de l'appel est béni dans "Tk::Text", et la méthode "bindtags" pour cet objet est appelée.

Maintenant, la seule chose à discuter est de savoir qui définit les méthodes "text" et "bindtags". La réponse est qu'elles sont définies dans "tkWindow.c", et ces commandes sont créées dans le package "Tk" dans le même passage qui a créé la commande "Tk::wm" décrite ci-dessus.

Ainsi, le même code C qui correspond au traitement des commandes TCL correspondantes est appelé ici aussi (cette fois via l'interface "XStoTk").

À l'intérieur de "$text->insert('insert','Hello, world!');"
Comme nous l'avons discuté ci-dessus, les sous-commandes des procédures de widget correspondent au XSUB "XStoWidget". Ce XSUB substitue le premier argument $text (qui est une référence de table de hachage) à une valeur appropriée de cette table, ajoute l'argument supplémentaire après le premier qui contient le nom de la sous-commande extraite de la partie données du XSUB, et appelle la sous-routine Tk C correspondante via "Call_Tk".
