Tcl-perl(3) Documentation Perl fournie par l'utilisateur Tcl-perl(3)

NOM

Tcl vs perl - documentation très ancienne et suspecte sur le portage.

DESCRIPTION

Ce n'est pas vraiment un fichier .pod, ni Tcl vs perl, c'est une copie de la comparaison de John entre le portage original perl/Tk de Malcolm et celui actuel. Il est également obsolète par endroits.

De : john@WPI.EDU (John Stoffel )
Voici quelques réflexions sur la nouvelle extension Tk et sur la façon dont je pense que
l'organisation des commandes se présente. La plupart du temps, j'en suis satisfait, cela
rend certaines choses plus organisées et plus cohérentes avec tcl/tk, mais
puisque le langage sous-jacent est si différent, je ne pense pas que nous devions suivre exactement
le modèle tcl/tk pour appeler le langage.
La structure de base du programme Tk est la suivante :
    require Tk;
    $top = MainWindow->new();
    #
    # créer des widgets
    #
    Tk::MainLoop;
    sub method1 {
    }
    sub methodN {
    }
C'est à peu près la même chose que tkperl5a5, avec quelques changements cosmétiques de nom
et quelques changements de noms et d'usages de commandes plus utiles. Une comparaison rapide
sans ordre particulier suit :
tkperl5a5                             Tk
-------------------------------       -----------------------------------
$top=tkinit(name,display,sync);       $top=MainWindow->new();
tkpack $w, ... ;              $w->pack(...)
$w = Class::new($top, ...);   $w = $top->Class(...);
tkmainloop;                   Tk::MainLoop;
tkbind($w,"<key>",sub);               $w->bind("<key>",sub);
tkdelete($w, ...);            $w->delete(...);
$w->scanmark(...);            $w->scan("mark", ...);
$w->scandragto(...);          $w->scan("dragto", ...);
$w->tkselect();                       $w->Select();
$w->selectadjust(...);                $w->selection("adjust", ...);
$w->selectto(...);            $w->selection("to", ...);
$w->selectfrom(...);          $w->selection("from", ...);
$w->tkindex(...);             $w->index(...);
tclcmd("xxx",...);              &Tk::xxx(...)    # toutes les commandes Tk, mais pas de Tcl du tout
tclcmd("winfo", xxx, $w, ...);  $w->xxx(...);
                              $w->mark(...);
                              $w->tag(...);
$w->grabstatus();             $w->grab("status");
$w->grabrelease(...);         $w->grab("release", ...);
focus($w);                    $w->focus;
update();                     Tk->update();
idletasks();                  Tk->update("idletasks");
wm("cmd",$w, ...);            $w->cmd(...);
destroy($w);                  $w->destroy();
                              Tk::option(...);
                                $w->OptionGet(name,Class)
                              $w->place(...)
                              Tk::property(...);
$w = Entry::new($parent,...)
est maintenant
$w = $parent->Entry(...)
Comme cela permet à new d'être hérité d'une classe Window.
  -method=>x,-slave=>y
 est maintenant
  -command => [x,y]
Le premier élément de la liste est traité comme "méthode" si y est une référence d'objet.
(Vous pouvez aussi avoir -command => [a,b,c,d,e] ; b..e sont passés en tant qu'arguments).
Les références d'objets sont maintenant des hashes plutôt que des scalaires et il n'y en a
jamais qu'une par fenêtre. Tcl_CmdInfo et PathName sont des entrées dans le hash.
(Cela permet aux classes dérivées de
ré-blesser le hash et d'y conserver leurs propres éléments.)
"Tcl_Interp" de Tk est en fait une référence à la fenêtre ".".
Vous pouvez trouver toutes les fenêtres Tk qui en descendent car leurs références d'objets sont ajoutées (par PathName) dans ce hash.
$w->MainWindow retourne ce hash à partir de n'importe quelle fenêtre.
Je pense que cela devrait s'étendre à plusieurs tkinits / Tk->news
avec différents Display - si le code Tk le fait.
Enfin, "bind" passe la fenêtre comme argument "extra" (ou unique). Ainsi
Tk::Button->bind(<Any-Enter>,"Enter");
Lie les événements Enter à Tk::Button::Enter par défaut
mais est appelé comme $w->Enter, donc une classe dérivée de Button peut simplement
définir sa propre méthode Enter. &EvWref et les variables globales associées et les conditions de concurrence ne sont plus nécessaires.
Une chose à surveiller : les commandes liées aux événements avec $widget->bind
suivent le même modèle, mais reçoivent des arguments supplémentaires :
$widget->bind(<Any-1>,[sub {print shift}, $one, $two ]);
Lorsque sub est appelé, il a :
   $widget $one $two
passés.
Le premier argument supplémentaire est une référence au hash par widget qui sert d'objet
Perl pour le widget.
Chaque fois qu'un XEvent, une référence à une classe spéciale est placée
dans le hash du widget. Elle peut être récupérée par la méthode $w->XEvent.
Les méthodes de la classe XEvent sont les
caractères spéciaux Tcl/Tk %.
Ainsi :
$widget->bind(<Any-KeyPress>,
              sub {
               my $w = shift;
               my $e = $w->XEvent;
               print $w->PathName," ",$e->A," pressed ,$e->xy,"\n");
              });
XEvent->xy est un cas spécial qui retourne "@" . $e->x . "," . $e->y
qui est courant dans le package Text.
En raison du passage d'un hash de widget béni aux sous-programmes "bound", ceux-ci peuvent être
liés à des méthodes (éventuellement héritées) de la classe du widget :
Class->bind(<Any-Down>,Down);
sub Class::Down
{
 my $w = shift;
 # gérer la flèche vers le bas
}
Aussi :
-command et similaires peuvent prendre une liste dont le premier élément peut être une référence à
une sous-routine ou un nom de méthode. Les éléments restants sont passés comme arguments à la
sous-routine au moment de l'"invocation". Ainsi :
$b= $w->Button(blah blah, '-command' => [sub{print shift} , $fred ]);
Devrait faire l'affaire, à condition que $fred soit défini au moment de la création du bouton.
Ainsi, le premier élément de la liste est équivalent à -method de Malcolm et le second
serait son -slave. Tout élément supplémentaire est un bonus et évite
d'avoir à passer une référence à un tableau/hash comme esclave.
