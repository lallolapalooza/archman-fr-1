NOM

Tk_CreateItemType, Tk_GetItemTypes - définir un nouveau type d'élément de canevas

SYNOPSIS

#include <tk.h>

Tk_CreateItemType(typePtr)

Tk_ItemType *
Tk_GetItemTypes()

ARGUMENTS

Tk_ItemType *typePtr (entree)
Structure définissant le nouveau type d'élément de canevas.

INTRODUCTION

Tk_CreateItemType est appelée pour définir un nouveau type d'élément de canevas décrit par l'argument typePtr. Un type d'élément correspond à une valeur particulière de l'argument type de la commande de widget create pour les canevas, et le code qui implémente un type d'élément de canevas est appelé un gestionnaire de type. Tk définit plusieurs types d'éléments intégrés, tels que rectangle et text et image, mais Tk_CreateItemType permet de définir des types d'éléments supplémentaires. Une fois que Tk_CreateItemType retourne, le nouveau type d'élément peut être utilisé dans des widgets de canevas nouveaux ou existants, tout comme les types d'éléments intégrés.

Tk_GetItemTypes retourne un pointeur vers le premier élément de la liste de tous les types d'éléments actuellement définis pour les canevas. Les entrées de la liste sont reliées entre elles par leurs champs nextPtr, la fin de la liste étant marquée par un nextPtr NULL.

Vous trouverez peut-être plus facile de comprendre le reste de cette entrée de manuel en consultant le code d'un type d'élément de canevas existant tel que bitmap (dans le fichier tkCanvBmap.c) ou text (tkCanvText.c). Le moyen le plus simple de créer un nouveau gestionnaire de type est de copier le code d'un type existant et de le modifier pour le nouveau type.

Tk fournit un certain nombre de procédures utilitaires pour l'utilisation des gestionnaires de type de canevas, telles que Tk_CanvasCoords et Tk_CanvasPsColor ; celles-ci sont décrites dans des entrées de manuel séparées.

STRUCTURES DE DONNÉES

Un gestionnaire de type consiste en une collection de procédures qui fournissent un ensemble standard d'opérations sur les éléments de ce type. Le gestionnaire de type traite trois types de structures de données. La première structure de données est un Tk_ItemType ; elle contient des informations telles que le nom du type et des pointeurs vers les procédures standard implémentées par le gestionnaire de type :

typedef struct Tk_ItemType {
    const char *name;
    int itemSize;
    Tk_ItemCreateProc *createProc;
    const Tk_ConfigSpec *configSpecs;
    Tk_ItemConfigureProc *configProc;
    Tk_ItemCoordProc *coordProc;
    Tk_ItemDeleteProc *deleteProc;
    Tk_ItemDisplayProc *displayProc;
    int alwaysRedraw;
    Tk_ItemPointProc *pointProc;
    Tk_ItemAreaProc *areaProc;
    Tk_ItemPostscriptProc *postscriptProc;
    Tk_ItemScaleProc *scaleProc;
    Tk_ItemTranslateProc *translateProc;
    Tk_ItemIndexProc *indexProc;
    Tk_ItemCursorProc *icursorProc;
    Tk_ItemSelectionProc *selectionProc;
    Tk_ItemInsertProc *insertProc;
    Tk_ItemDCharsProc *dCharsProc;
    Tk_ItemType *nextPtr;
} Tk_ItemType;

Les champs d'une structure Tk_ItemType sont décrits plus en détail plus loin dans cette entrée de manuel. Lorsque Tk_CreateItemType est appelée, son argument typePtr doit pointer vers une structure avec tous les champs initialisés à l'exception de nextPtr, que Tk définit pour relier tous les types ensemble en une liste. La structure doit être en mémoire permanente (soit allouée statiquement, soit allouée dynamiquement mais jamais libérée) ; Tk conserve un pointeur vers cette structure.

La deuxième structure de données manipulée par un gestionnaire de type est un enregistrement d'élément. Pour chaque élément dans un canevas, il existe un enregistrement d'élément. Tous les éléments d'un type donné ont généralement des enregistrements d'élément avec la même structure, mais des types différents ont généralement des formats différents pour leurs enregistrements d'élément. La première partie de chaque enregistrement d'élément est un en-tête avec une structure standard définie par Tk via le type Tk_Item ; le reste de l'enregistrement d'élément est défini par le gestionnaire de type. Un gestionnaire de type doit définir ses enregistrements d'élément avec un Tk_Item comme premier champ. Par exemple, l'enregistrement d'élément pour les éléments bitmap est défini comme suit :

typedef struct BitmapItem {
    Tk_Item header;
    double x, y;
    Tk_Anchor anchor;
    Pixmap bitmap;
    XColor *fgColor;
    XColor *bgColor;
    GC gc;
} BitmapItem;

La sous-structure header contient des informations utilisées par Tk pour gérer l'élément, telles que son identifiant, ses étiquettes, son type et sa boîte englobante. Les champs commençant par x appartiennent au gestionnaire de type : Tk ne les lira ni ne les écrira jamais. Le gestionnaire de type ne devrait pas avoir besoin de lire ni d'écrire aucun des champs de l'en-tête, à l'exception de quatre champs dont les noms sont x1, y1, x2 et y2. Ces champs définissent une boîte englobante pour les éléments en utilisant des coordonnées entières de canevas : l'élément ne doit pas couvrir de pixels dont la coordonnée x est inférieure à x1 ou la coordonnée y est inférieure à y1, ni de pixels dont la coordonnée x est supérieure ou égale à x2 ou la coordonnée y est supérieure ou égale à y2. Il appartient au gestionnaire de type de maintenir la boîte englobante à jour à mesure que l'élément est déplacé et reconfiguré.

Chaque fois que Tk appelle une procédure d'un gestionnaire de type, elle lui passe un pointeur vers un enregistrement d'élément. L'argument est toujours passé sous forme de pointeur vers un Tk_Item ; le gestionnaire de type le convertira généralement en pointeur vers son propre type spécifique, tel que BitmapItem.

La troisième structure de données utilisée par les gestionnaires de type a le type Tk_Canvas ; elle sert de handle opaque pour le widget de canevas dans son ensemble. Les gestionnaires de type n'ont pas besoin de connaître le contenu de cette structure. Un handle Tk_Canvas est généralement passé aux procédures d'un gestionnaire de type, et le gestionnaire de type peut passer le handle en retour aux procédures de la bibliothèque telles que Tk_CanvasTkwin pour obtenir des informations sur le canevas.

CHAMPS TK_ITEMTYPE

NOM

Cette section et les suivantes décrivent en détail chacun des champs d'une structure Tk_ItemType. Le champ name fournit un nom sous forme de chaîne pour le type d'élément. Une fois que Tk_CreateImageType retourne, ce nom peut être utilisé dans les commandes de widget create pour créer des éléments du nouveau type. S'il existait déjà un type d'élément portant ce nom, le nouveau type d'élément remplace l'ancien.

DRAPEAUX (DANS ALWAYSREDRAW)

Le champ typePtr->alwaysRedraw (nommé ainsi pour des raisons historiques) contient une collection de bits de drapeau qui modifient la manière dont le cœur du canevas interagit avec l'élément. Les bits suivants sont définis :

1
Indique que l'élément doit toujours être redessiné lorsqu'une partie du canevas est redessinée, plutôt que seulement lorsque la boîte englobante de l'élément chevauche la zone en cours de redessinage. Ceci est utilisé par les éléments de fenêtre, par exemple, qui doivent démasquer les sous-fenêtres qui ne sont pas à l'écran.
TK_CONFIG_OBJS
Indique que les opérations qui prendraient normalement une chaîne (ou un tableau de chaînes) prennent en fait une référence Tcl_Obj (ou un tableau de telles références). Les opérations auxquelles cela s'applique sont le configProc, le coordProc, le createProc, le indexProc et le insertProc.
TK_MOVABLE_POINTS
Indique que l'élément supporte les méthodes dCharsProc, indexProc et insertProc avec la même sémantique que les types de lignes et de polygones intégrés de Tk, et que par conséquent des points de coordonnées individuels peuvent être déplacés. Ne doit pas être défini si l'une des méthodes ci-dessus est NULL.

ITEMSIZE

typePtr->itemSize donne la taille en octets des enregistrements d'élément de ce type, y compris l'en-tête Tk_Item. Tk utilise cette taille pour allouer de l'espace mémoire pour les éléments du type. Tous les enregistrements d'élément pour un type donné doivent avoir la même taille. Si des champs de longueur variable sont nécessaires pour un élément (tel qu'une liste de points pour un polygone), le gestionnaire de type peut allouer un objet séparé de longueur variable et y conserver un pointeur dans l'enregistrement d'élément.

CREATEPROC

INTRODUCTION

Tk canvas items are implemented by means of type managers. Each type manager is a structure containing pointers to procedures that implement the various operations for a particular item type, such as creating, deleting, displaying, configuring, and reporting coordinates for items. Tk provides a default set of item types (e.g., rectangles, text, bitmaps, windows), but you can add your own custom item types by defining and registering a new type manager.

This document describes the interface between Tk and the type managers for canvas items.

TYPE MANAGERS

A type manager is defined by the following C structure:

typedef struct Tk_ItemType {
    const char *name;                /* Name of item type (e.g., "rectangle") */
    Tk_ItemCreateProc *createProc;     /* Called to create item */
    Tk_ItemConfigProc *configProc;     /* Called to configure item */
    Tk_ItemDeleteProc *deleteProc;     /* Called to delete item */
    Tk_ItemDisplayProc *displayProc;   /* Called to display item */
    Tk_ItemPointProc *pointProc;     /* Called to find distance to item */
    Tk_ItemAreaProc *areaProc;       /* Called to find item's relation to area */
    Tk_ItemCoordsProc *coordsProc;     /* Called to get/set coordinates */
    Tk_ItemPostscriptProc *postscriptProc; /* Called to generate Postscript */
    int itemSize;                /* Size of item structure */
    int alwaysRedraw;            /* Flags controlling redisplay behavior */
} Tk_ItemType;

Most of the fields in this structure are pointers to procedures that Tk will invoke to perform operations on items of this type. The following sections describe each of these procedures and fields.

NAME

The name field holds a pointer to a null-terminated string containing the name of the item type. This name is used in Tcl commands, such as the create subcommand of the canvas widget command.

CREATEPROC

typePtr->createProc points to a procedure for Tk to call whenever a new item of this type is created. typePtr->createProc must match the following prototype:

typedef int Tk_ItemCreateProc(
        Tcl_Interp *interp,
        Tk_Canvas canvas,
        Tk_Item *itemPtr,
        int objc,
        Tcl_Obj *const objv[]);

The interp argument is the interpreter in which the canvas's create widget command was invoked, and canvas is a handle for the canvas widget. itemPtr is a pointer to a newly-allocated item of size typePtr->itemSize. Tk has already initialized the item's header (the first sizeof(Tk_ItemType) bytes). The objc and objv arguments describe all of the arguments to the create command after the type argument. Note that if TK_CONFIG_OBJS is not set in the typePtr->alwaysRedraw field, the objv parameter will actually contain a pointer to an array of constant strings. For example, in the widget command:

.c create rectangle 10 20 50 50 -fill black

objc will be 6 and objv[0] will contain the integer object 10.

createProc should use objc and objv to initialize the type-specific parts of the item record and set an initial value for the bounding box in the item's header. It should return a standard Tcl completion code and leave an error message in the interpreter result if an error occurs. If an error occurs Tk will free the item record, so createProc must be sure to leave the item record in a clean state if it returns an error (e.g., it must free any additional memory that it allocated for the item).

CONFIGSPECS

Each type manager must provide a standard table describing its configuration options, in a form suitable for use with Tk_ConfigureWidget. This table will normally be used by typePtr->createProc and typePtr->configProc, but Tk also uses it directly to retrieve option information in the itemcget and itemconfigure widget commands. typePtr->configSpecs must point to the configuration table for this type. Note: Tk provides a custom option type tk_CanvasTagsOption for implementing the -tags option; see an existing type manager for an example of how to use it in configSpecs.

CONFIGPROC

typePtr->configProc is called by Tk whenever the itemconfigure widget command is invoked to change the configuration options for a canvas item. This procedure must match the following prototype:

typedef int Tk_ItemConfigureProc(
        Tcl_Interp *interp,
        Tk_Canvas canvas,
        Tk_Item *itemPtr,
        int objc,
        Tcl_Obj *const objv[],
        int flags);

The interp argument identifies the interpreter in which the widget command was invoked, canvas is a handle for the canvas widget, and itemPtr is a pointer to the item being configured. objc and objv contain the configuration options. Note that if TK_CONFIG_OBJS is not set in the typePtr->alwaysRedraw field, the objv parameter will actually contain a pointer to an array of constant strings. For example, if the following command is invoked:

.c itemconfigure 2 -fill red -outline black

objc is 4 and objv contains the string objects -fill through black. objc will always be an even value. The flags argument contains flags to pass to Tk_ConfigureWidget; currently this value is always TK_CONFIG_ARGV_ONLY when Tk invokes typePtr->configProc, but the type manager's createProc procedure will usually invoke configProc with different flag values.

typePtr->configProc returns a standard Tcl completion code and leaves an error message in the interpreter result if an error occurs. It must update the item's bounding box to reflect the new configuration options.

COORDPROC

typePtr->coordProc is invoked by Tk to implement the coords widget command for an item. It must match the following prototype:

typedef int Tk_ItemCoordProc(
        Tcl_Interp *interp,
        Tk_Canvas canvas,
        Tk_Item *itemPtr,
        int objc,
        Tcl_Obj *const objv[]);

The arguments interp, canvas, and itemPtr all have the standard meanings, and objc and objv describe the coordinate arguments. Note that if TK_CONFIG_OBJS is not set in the typePtr->alwaysRedraw field, the objv parameter will actually contain a pointer to an array of constant strings. For example, if the following widget command is invoked:

.c coords 2 30 90

objc will be 2 and objv will contain the integer objects 30 and 90.

The coordProc procedure should process the new coordinates, update the item appropriately (e.g., it must reset the bounding box in the item's header), and return a standard Tcl completion code. If an error occurs, coordProc must leave an error message in the interpreter result.

DELETEPROC

typePtr->deleteProc is invoked by Tk to delete an item and free any resources allocated to it. It must match the following prototype:

typedef void Tk_ItemDeleteProc(
        Tk_Canvas canvas,
        Tk_Item *itemPtr,
        Display *display);

The canvas and itemPtr arguments have the usual interpretations, and display identifies the X display containing the canvas. deleteProc must free up any resources allocated for the item, so that Tk can free the item record. deleteProc should not actually free the item record; this will be done by Tk when deleteProc returns.

DISPLAYPROC

typePtr->displayProc is invoked by Tk to redraw an item on the screen. It must match the following prototype:

typedef void Tk_ItemDisplayProc(
        Tk_Canvas canvas,
        Tk_Item *itemPtr,
        Display *display,
        Drawable dst,
        int x,
        int y,
        int width,
        int height);

The canvas and itemPtr arguments have the usual meaning. display identifies the display containing the canvas, and dst specifies a drawable in which the item should be rendered; typically this is an off-screen pixmap, which Tk will copy into the canvas's window once all relevant items have been drawn. x, y, width, and height specify a rectangular region in canvas coordinates, which is the area to be redrawn; only information that overlaps this area needs to be redrawn. Tk will not call displayProc unless the item's bounding box overlaps the redraw area, but the type manager may wish to use the redraw area to optimize the redisplay of the item.

Because of scrolling and the use of off-screen pixmaps for double-buffered redisplay, the item's coordinates in dst will not necessarily be the same as those in the canvas. displayProc should call Tk_CanvasDrawableCoords to transform coordinates from those of the canvas to those of dst.

Normally an item's displayProc is only invoked if the item overlaps the area being displayed. However, if bit zero of typePtr->alwaysRedraw is 1, (i.e. “typePtr->alwaysRedraw & 1 == 1”) then displayProc is invoked during every redisplay operation, even if the item does not overlap the area of redisplay; this is useful for cases such as window items, where the subwindow needs to be unmapped when it is off the screen.

POINTPROC

typePtr->pointProc is invoked by Tk to find out how close a given point is to a canvas item. Tk uses this procedure for purposes such as locating the item under the mouse or finding the closest item to a given point. The procedure must match the following prototype:

typedef double Tk_ItemPointProc(
        Tk_Canvas canvas,
        Tk_Item *itemPtr,
        double *pointPtr);

canvas and itemPtr have the usual meaning. pointPtr points to an array of two numbers giving the x and y coordinates of a point. pointProc must return a real value giving the distance from the point to the item, or 0 if the point lies inside the item.

AREAPROC

typePtr->areaProc is invoked by Tk to find out the relationship between an item and a rectangular area. It must match the following prototype:

typedef int Tk_ItemAreaProc(
        Tk_Canvas canvas,
        Tk_Item *itemPtr,
        double *rectPtr);

canvas and itemPtr have the usual meaning. rectPtr points to an array of four real numbers; the first two give the x and y coordinates of the upper left corner of a rectangle, and the second two give the x and y coordinates of the lower right corner. areaProc must return -1 if the item lies entirely outside the given area, 0 if it lies partially inside and partially outside the area, and 1 if it lies entirely inside the area.

POSTSCRIPTPROC

typePtr->postscriptProc is invoked by Tk to generate Postscript for an item during the postscript widget command. If the type manager is not capable of generating Postscript then typePtr->postscriptProc should be NULL. The procedure must match the following prototype:

typedef int Tk_ItemPostscriptProc(
        Tcl_Interp *interp,
        Tk_Canvas canvas,
        Tk_Item *itemPtr,
        int prepass);

The interp, canvas, and itemPtr arguments all have st

et des significations standard ; prepass sera décrit ci-dessous. Si postscriptProc se termine avec succès, il doit ajouter le Postscript pour l'élément aux informations dans le résultat de l'interpréteur (par exemple, en appelant Tcl_AppendResult, pas Tcl_SetResult) et retourner TCL_OK. Si une erreur se produit, postscriptProc doit effacer le résultat et remplacer son contenu par un message d'erreur ; puis il doit retourner TCL_ERROR.

Tk fournit une collection de procédures utilitaires pour simplifier postscriptProc. Par exemple, Tk_CanvasPsColor générera du Postscript pour définir la couleur actuelle à une couleur Tk donnée et Tk_CanvasPsFont configurera les informations de police. Lors de la génération de Postscript, le gestionnaire de type est libre de changer l'état graphique de l'interpréteur Postscript, car Tk place des commandes gsave et grestore autour du Postscript pour l'élément. Le gestionnaire de type peut utiliser directement les coordonnées x du canevas dans son Postscript, mais il doit appeler Tk_CanvasPsY pour convertir les coordonnées y de l'espace du canevas (où l'origine est en haut à gauche) vers l'espace Postscript (où l'origine est en bas à gauche).

Afin de générer du Postscript conforme aux Adobe Document Structuring Conventions, Tk génère en fait du Postscript en deux passes. Il appelle le postscriptProc de chaque élément lors de chaque passe. Le seul but de la première passe est de collecter les informations de police (ce qui est fait par Tk_CanvasPsFont) ; le Postscript réel est discardé. Tk définit l'argument prepass de postscriptProc à 1 pendant la première passe ; le gestionnaire de type peut utiliser prepass pour ignorer toute génération de Postscript sauf les appels à Tk_CanvasPsFont. Pendant la seconde passe, prepass sera 0, donc le gestionnaire de type doit générer un Postscript complet.

SCALEPROC

typePtr->scaleProc est appelé par Tk pour redimensionner un élément de canevas pendant la commande de widget scale. La procédure doit correspondre au prototype suivant :

typedef void Tk_ItemScaleProc(
        Tk_Canvas canvas,
        Tk_Item *itemPtr,
        double originX,
        double originY,
        double scaleX,
        double scaleY);

Les arguments canvas et itemPtr ont la signification habituelle. originX et originY spécifient une origine par rapport à laquelle l'élément doit être redimensionné, et scaleX et scaleY donnent les facteurs d'échelle x et y. L'élément doit ajuster ses coordonnées de telle sorte qu'un point de l'élément qui avait auparavant les coordonnées x et y aura les nouvelles coordonnées x′ et y′, où

x′ = originX + scaleX × (x − originX)
y′ = originY + scaleY × (y − originY)

scaleProc doit également mettre à jour la boîte englobante dans l'en-tête de l'élément.

TRANSLATEPROC

typePtr->translateProc est appelé par Tk pour translater un élément de canevas pendant la commande de widget move. La procédure doit correspondre au prototype suivant :

typedef void Tk_ItemTranslateProc(
        Tk_Canvas canvas,
        Tk_Item *itemPtr,
        double deltaX,
        double deltaY);

Les arguments canvas et itemPtr ont la signification habituelle, et deltaX et deltaY donnent les montants qui doivent être ajoutés à chaque coordonnée x et y dans l'élément. Le gestionnaire de type doit ajuster les coordonnées de l'élément et mettre à jour la boîte englobante dans l'en-tête de l'élément.

INDEXPROC

typePtr->indexProc est appelé par Tk pour convertir une spécification d'index de chaîne en un index numérique, par exemple lors de la commande de widget index. Il n'est pertinent que pour les types d'éléments qui prennent en charge du texte ou des coordonnées indexables ; typePtr->indexProc peut être spécifié comme NULL pour les types d'éléments non textuels s'ils ne prennent pas en charge l'adressage détaillé des coordonnées. La procédure doit correspondre au prototype suivant :

typedef int Tk_ItemIndexProc(
        Tcl_Interp *interp,
        Tk_Canvas canvas,
        Tk_Item *itemPtr,
        Tcl_Obj *indexObj,
        int *indexPtr);

Les arguments interp, canvas et itemPtr ont tous la signification habituelle. indexObj contient une description textuelle d'un index, et indexPtr pointe vers une valeur entière qui doit être remplie avec un index numérique. Notez que si TK_CONFIG_OBJS n'est pas défini dans le champ typePtr->alwaysRedraw, le paramètre indexObj contiendra en fait un pointeur vers une chaîne constante. Il appartient au gestionnaire de type de décider quelles formes d'index sont supportées (par exemple, nombres, insert, sel.first, end, etc.). indexProc doit retourner un code d'achèvement Tcl et définir le résultat de l'interpréteur en cas d'erreur.

ICURSORPROC

typePtr->icursorProc est appelé par Tk pendant la commande de widget icursor pour définir la position du curseur d'insertion dans un élément textuel. Il n'est pertinent que pour les types d'éléments qui prennent en charge un curseur d'insertion ; typePtr->icursorProc peut être spécifié comme NULL pour les types d'éléments qui ne prennent pas en charge un curseur d'insertion. La procédure doit correspondre au prototype suivant :

typedef void Tk_ItemCursorProc(
        Tk_Canvas canvas,
        Tk_Item *itemPtr,
        int index);

canvas et itemPtr ont les significations habituelles, et index est un index dans le texte de l'élément, tel que retourné par un appel précédent à typePtr->insertProc. Le gestionnaire de type doit positionner le curseur d'insertion dans l'élément juste avant le caractère donné par index. La décision d'afficher ou non réellement le curseur d'insertion est déterminée par d'autres informations fournies par Tk_CanvasGetTextInfo.

SELECTIONPROC

typePtr->selectionProc est appelé par Tk lors de la récupération de sélections ; il doit retourner tout ou partie du texte sélectionné dans l'élément (le cas échéant). Il n'est pertinent que pour les types d'éléments qui prennent en charge du texte ; typePtr->selectionProc peut être spécifié comme NULL pour les types d'éléments non textuels. La procédure doit correspondre au prototype suivant :

typedef int Tk_ItemSelectionProc(
        Tk_Canvas canvas,
        Tk_Item *itemPtr,
        int offset,
        char *buffer,
        int maxBytes);

canvas et itemPtr ont les significations habituelles. offset est un décalage en octets dans la sélection où 0 fait référence au premier octet de la sélection ; il identifie le premier caractère à retourner dans cet appel. buffer pointe vers une zone mémoire où stocker les octets demandés, et maxBytes spécifie le nombre maximum d'octets à retourner. selectionProc doit extraire jusqu'à maxBytes caractères de la sélection et les copier dans maxBytes ; il doit retourner un compte du nombre d'octets réellement copiés, qui peut être inférieur à maxBytes s'il n'y a pas offset+maxBytes octets dans la sélection.

INSERTPROC

typePtr->insertProc est appelé par Tk pendant la commande de widget insert pour insérer du nouveau texte ou de nouvelles coordonnées dans un élément de canevas. Il n'est pertinent que pour les types d'éléments qui prennent en charge la méthode insert ; typePtr->insertProc peut être spécifié comme NULL pour les autres types d'éléments. La procédure doit correspondre au prototype suivant :

typedef void Tk_ItemInsertProc(
        Tk_Canvas canvas,
        Tk_Item *itemPtr,
        int index,
        Tcl_Obj *obj);

canvas et itemPtr ont les significations habituelles. index est un index dans le texte de l'élément, tel que retourné par un appel précédent à typePtr->insertProc, et obj contient le nouveau texte à insérer juste avant le caractère donné par index. Notez que si TK_CONFIG_OBJS n'est pas défini dans le champ typePtr->alwaysRedraw, le paramètre obj contiendra en fait un pointeur vers une chaîne constante à insérer. DCHARSPROC

typePtr->dCharsProc est appelé par Tk pendant la commande de widget dchars pour supprimer une plage de texte d'un élément de canevas ou une plage de coordonnées d'un élément tracé. Il n'est pertinent que pour les types d'éléments qui prennent en charge le texte ; typePtr->dCharsProc peut être spécifié comme NULL pour les types d'éléments non textuels qui ne souhaitent pas prendre en charge la suppression de coordonnées. La procédure doit correspondre au prototype suivant :

typedef void Tk_ItemDCharsProc(
        Tk_Canvas canvas,
        Tk_Item *itemPtr,
        int first,
        int last);

canvas et itemPtr ont les significations habituelles. first et last donnent les indices du premier et du dernier octet à supprimer, tels que retournés par des appels précédents à typePtr->indexProc.
