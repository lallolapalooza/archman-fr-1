Tk_CreateErrorHandler(3) Procédures de la bibliothèque Tk Tk_CreateErrorHandler(3)

NOM

Tk_CreateErrorHandler, Tk_DeleteErrorHandler - gérer les erreurs de protocole X

SYNOPIS

#include <tk.h>

Tk_ErrorHandler
Tk_CreateErrorHandler(display, error, request, minor, proc, clientData)

Tk_DeleteErrorHandler(handler)

ARGUMENTS

Display *display (in)
Affichage dont les erreurs doivent être gérées.
int error (in)
Ne correspond que si les événements d'erreur ont cette valeur dans le champ error_code. Si -1, alors correspond à n'importe quelle valeur error_code.
int request (in)
Ne correspond que si les événements d'erreur ont cette valeur dans le champ request_code. Si -1, alors correspond à n'importe quelle valeur request_code.
int minor (in)
Ne correspond que si les événements d'erreur ont cette valeur dans le champ minor_code. Si -1, alors correspond à n'importe quelle valeur minor_code.
Tk_ErrorProc *proc (in)
Procédure à appeler chaque fois qu'un événement d'erreur est reçu pour display et correspond à error, request et minor. NULL signifie ignorer toute erreur correspondante.
ClientData clientData (in)
Valeur arbitraire d'un mot à passer à proc.
Tk_ErrorHandler handler (in)
Jeton pour le gestionnaire d'erreurs à supprimer (valeur de retour d'un appel précédent à Tk_CreateErrorHandler).

DESCRIPTION

Tk_CreateErrorHandler organise l'appel d'une procédure particulière (proc) lorsque certaines erreurs de protocole se produisent sur un affichage particulier (display). Les erreurs de protocole se produisent lorsque le protocole X est utilisé incorrectement, par exemple en tentant de mapper une fenêtre qui n'existe pas. Voir la documentation Xlib pour XSetErrorHandler pour plus d'informations sur les types d'erreurs qui peuvent survenir. Pour que proc soit appelé pour gérer une erreur particulière, cinq conditions doivent être remplies :

[1]
L'erreur doit concerner display.
[2]
Soit l'argument error de Tk_CreateErrorHandler a été -1, soit l'argument error correspond au champ error_code de l'événement d'erreur.
[3]
Soit l'argument request de Tk_CreateErrorHandler a été -1, soit l'argument request correspond au champ request_code de l'événement d'erreur.
[4]
Soit l'argument minor de Tk_CreateErrorHandler a été -1, soit l'argument minor correspond au champ minor_code de l'événement d'erreur.
[5]
La requête de protocole à laquelle l'erreur se rapporte doit avoir été faite lorsque le gestionnaire était actif (voir ci-dessous pour plus d'informations).

Proc doit avoir des arguments et un résultat correspondant au type suivant :

typedef int Tk_ErrorProc(
        ClientData clientData,
        XErrorEvent *errEventPtr);
Le paramètre clientData de proc est une copie de l'argument clientData donné à Tcl_CreateErrorHandler lors de la création du rappel. Typiquement, clientData pointe vers une structure de données contenant des informations spécifiques à l'application nécessaires pour traiter l'erreur. ErrEventPtr est un pointeur vers l'événement d'erreur X. La procédure proc doit retourner une valeur entière. Si elle retourne 0, cela signifie que proc a géré l'erreur complètement et qu'il n'est pas nécessaire de prendre d'autres mesures pour cette erreur. Si elle retourne une valeur non nulle, cela signifie que proc n'a pas pu gérer l'erreur.

Si une valeur NULL est spécifiée pour proc, toutes les erreurs correspondantes seront ignorées : cela produira le même résultat que si une procédure avait été spécifiée qui retourne toujours 0.

Si plusieurs gestionnaires correspondent à une erreur particulière, ils sont appelés à tour de rôle. Les gestionnaires seront appelés dans l'ordre inverse de leur création : le gestionnaire déclaré le plus récemment en premier. Si un gestionnaire retourne 0, les gestionnaires suivants (plus anciens) ne seront pas appelés. Si aucun gestionnaire ne retourne 0, Tk appelle le gestionnaire d'erreurs par défaut de X, qui affiche un message d'erreur et arrête le programme. Si vous souhaitez avoir un gestionnaire par défaut qui traite les erreurs qu'aucun autre gestionnaire ne peut traiter, déclarez-le en premier.

La documentation X stipule que « le gestionnaire d'erreurs ne doit pas appeler de fonctions (directement ou indirectement) sur l'affichage qui généreront des requêtes de protocole ou qui rechercheront des événements d'entrée ». Cette restriction s'applique aux gestionnaires déclarés par Tk_CreateErrorHandler ; désobéissez-y à vos risques et périls.

Tk_DeleteErrorHandler peut être appelé pour supprimer un gestionnaire d'erreurs précédemment créé. L'argument handler identifie le gestionnaire d'erreurs et doit être une valeur retournée par un appel précédent à Tk_CreateEventHandler.

Un gestionnaire d'erreurs particulier s'applique aux erreurs résultant des requêtes de protocole générées entre l'appel à Tk_CreateErrorHandler et l'appel à Tk_DeleteErrorHandler. Cependant, le rappel réel à proc peut ne pas se produire avant l'appel à Tk_DeleteErrorHandler, en raison de la mise en mémoire tampon dans le client et le serveur. Si un événement d'erreur concerne une requête de protocole effectuée juste avant d'appeler Tk_DeleteErrorHandler, l'événement d'erreur peut ne pas avoir été traité avant l'appel à Tk_DeleteErrorHandler. Lorsque cette situation se présente, Tk sauvegardera des informations sur le gestionnaire et appellera le proc du gestionnaire plus tard lorsque l'événement d'erreur arrivera enfin. Si une application souhaite supprimer un gestionnaire d'erreurs et être certaine que toutes les erreurs pertinentes ont été traitées, elle doit d'abord appeler Tk_DeleteErrorHandler, puis appeler XSync ; cela videra les requêtes et erreurs mises en mémoire tampon, mais entraînera une pénalité de performance car elle nécessite une communication vers et depuis le serveur X. Après l'appel à XSync, Tk est garanti de ne pas appeler les gestionnaires d'erreurs supprimés avant l'appel à XSync.

Pour que le mécanisme de gestion des erreurs de Tk fonctionne correctement, il est essentiel que le code de l'application n'appelle jamais XSetErrorHandler directement ; les applications ne doivent utiliser que Tk_CreateErrorHandler.
