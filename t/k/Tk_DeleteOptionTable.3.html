ARGUMENTS

Tcl_Interp *interp (in)
Un interpréteur Tcl. La plupart des procédures ne l'utilisent que pour retourner des messages d'erreur ; s'il est NULL, aucun message d'erreur n'est retourné. Pour Tk_CreateOptionTable, la valeur ne peut pas être NULL ; elle indique l'interpréteur dans lequel la table d'options sera utilisée.
const Tk_OptionSpec *templatePtr (in)
Pointe vers un tableau d'informations statiques décrivant les options de configuration prises en charge. Utilisé pour construire une Tk_OptionTable. Les informations pointées par cet argument doivent exister pendant toute la durée de vie de la Tk_OptionTable.
Tk_OptionTable optionTable (in)
Jeton d'une table d'options. Doit avoir été retourné par un appel précédent à Tk_CreateOptionTable.
char *recordPtr (in/out)
Pointe vers une structure dans laquelle les valeurs des options de configuration sont stockées ; les champs de cet enregistrement sont modifiés par des procédures telles que Tk_SetOptions et lus par des procédures telles que Tk_GetOptionValue.
Tk_Window tkwin (in)
Pour les options telles que TK_OPTION_COLOR, cet argument indique la fenêtre dans laquelle l'option sera utilisée. Si optionTable n'utilise aucune option dépendant de la fenêtre, une valeur NULL peut être fournie pour cet argument.
int objc (in)
Nombre de valeurs dans objv.
Tcl_Obj *const *objv (in)
Arguments de la ligne de commande pour définir les options de configuration.
Tk_SavedOptions *savePtr (out)
Si non NULL, la structure pointée par cet argument est remplie avec les anciennes valeurs de toutes les options qui ont été modifiées, et les anciennes valeurs sont restaurées automatiquement si une erreur survient dans Tk_SetOptions.
int *maskPtr (out)
Si non NULL, le mot pointé par maskPtr est rempli avec le OU bit à bit des champs typeMask pour les options qui ont été modifiées.
Tk_SavedOptions *savedPtr (in/out)
Pointe vers une structure précédemment remplie par Tk_SetOptions avec les anciennes valeurs des options modifiées.
Tcl_Obj *namePtr (in)
La valeur de cet objet est le nom d'une option particulière. Si NULL est passé à Tk_GetOptionInfo, des informations sont retournées pour toutes les options. Ne doit pas être NULL lors de l'appel à Tk_GetOptionValue.
type name type (in)
Le nom du type d'un enregistrement.
field name field (in)
Le nom d'un champ dans les enregistrements de type type.

DESCRIPTION

Ces procédures gèrent la plupart des détails de l'analyse des options de configuration telles que celles des widgets Tk. Étant donné une description des options prises en charge, ces procédures gèrent tous les détails de l'analyse des options et du stockage de leurs valeurs dans une structure C associée au widget ou à l'objet. Les procédures ont été principalement conçues pour les widgets dans Tk, mais elles peuvent également être utilisées pour d'autres types d'objets qui ont des options de configuration. Dans le reste de cette page de manuel, « widget » sera utilisé pour désigner l'objet dont les options sont gérées ; en pratique, l'objet peut ne pas être réellement un widget. Le terme « enregistrement de widget » est utilisé pour désigner la structure de niveau C dans laquelle sont stockées les informations relatives à un widget ou objet particulier.

Notez que la manière la plus simple d'apprendre à utiliser ces procédures est de regarder un exemple fonctionnel. Dans Tk, l'exemple le plus simple est le code qui implémente la famille de widgets bouton, qui se trouve dans tkButton.c. D'autres exemples se trouvent dans tkSquare.c et tkMenu.c.

Afin d'utiliser ces procédures, le code qui implémente le widget doit contenir un tableau statique de structures Tk_OptionSpec. C'est un modèle qui décrit les différentes options prises en charge par cette classe de widgets ; il existe un modèle séparé pour chaque type de widget. Le modèle contient des informations telles que le nom de chaque option, son type, sa valeur par défaut et l'endroit où la valeur de l'option est stockée dans l'enregistrement du widget. Voir MODÈLES ci-dessous pour plus de détails.

Afin de traiter les options de configuration efficacement, le modèle statique doit être augmenté d'informations supplémentaires disponibles uniquement au moment de l'exécution. La procédure Tk_CreateOptionTable crée ces informations dynamiques à partir du modèle et retourne un jeton Tk_OptionTable qui décrit les informations statiques et dynamiques. Toutes les autres procédures, telles que Tk_SetOptions, prennent un jeton Tk_OptionTable en argument. Typiquement, Tk_CreateOptionTable est appelée la première fois qu'un widget d'une classe particulière est créé et la Tk_OptionTable résultante est utilisée à l'avenir pour tous les widgets de cette classe. Une Tk_OptionTable ne peut être utilisée que dans un seul interpréteur, fourni par l'argument interp à Tk_CreateOptionTable. Lorsqu'une table d'options n'est plus nécessaire, Tk_DeleteOptionTable doit être appelée pour libérer toutes ses ressources. Toutes les tables d'options d'un interpréteur Tcl sont libérées automatiquement si l'interpréteur est supprimé.

Tk_InitOptions est appelée lorsqu'un nouveau widget est créé pour définir les valeurs par défaut. Tk_InitOptions reçoit un jeton pour une table d'options (optionTable) et un pointeur vers un enregistrement de widget (recordPtr), qui est la structure C contenant les informations sur ce widget. Tk_InitOptions utilise les informations de la table d'options pour choisir une valeur par défaut appropriée pour chaque option, puis elle stocke la valeur par défaut directement dans l'enregistrement du widget, écrasant toute information déjà présente dans l'enregistrement du widget. Tk_InitOptions retourne normalement TCL_OK. Si une erreur s'est produite lors de la définition des valeurs par défaut (par exemple, parce qu'une valeur par défaut était erronée), alors TCL_ERROR est retourné et un message d'erreur est laissé dans le résultat de interp si interp n'est pas NULL. Pour toute option de configuration d'un widget ayant TK_OPTION_DONT_SET_DEFAULT défini dans son champ flags, l'initialisation ci-dessus est complètement ignorée, voir ci-dessous.

Tk_SetOptions est appelée pour modifier les options de configuration en fonction des informations spécifiées dans une commande Tcl. La commande peut être celle qui crée un nouveau widget, ou une commande qui modifie les options d'un widget existant. Les arguments objc et objv décrivent les valeurs des arguments de la commande Tcl. Objv doit contenir un nombre pair d'objets : le premier objet de chaque paire donne le nom d'une option et le second objet donne la nouvelle valeur pour cette option. Tk_SetOptions recherche chaque nom dans optionTable, vérifie que la nouvelle valeur de l'option est conforme au type dans optionTable, et stocke la valeur de l'option dans l'enregistrement du widget donné par recordPtr. Tk_SetOptions retourne normalement TCL_OK. Si une erreur s'est produite (telle qu'un nom d'option inconnu ou une valeur d'option illégale), alors TCL_ERROR est retourné et un message d'erreur est laissé dans le résultat de interp si interp n'est pas NULL.

Tk_SetOptions possède deux fonctionnalités supplémentaires. Premièrement, si l'argument maskPtr n'est pas NULL, alors il pointe vers une valeur entière qui est remplie avec des informations sur les options qui ont été modifiées. Pour chaque option dans le modèle passé à Tk_CreateOptionTable, il y a un champ typeMask. Les bits de ce champ sont définis par le code qui implémente le widget ; par exemple, chaque bit peut correspondre à une option de configuration particulière. Alternativement, les bits peuvent être utilisés fonctionnellement. Par exemple, un bit peut être utilisé pour le redessin : toutes les options qui affectent l'affichage du widget, de sorte que la modification de l'option nécessite que le widget soit redessiné, pourraient avoir ce bit défini. Un autre bit pourrait indiquer que la géométrie du widget doit être recalculée, et ainsi de suite. Tk_SetOptions effectue un OU bit à bit des champs typeMask

MODÈLES

Le tableau de structures Tk_OptionSpec passé à Tk_CreateOptionTable via l'argument templatePtr décrit les options de configuration prises en charge par un type particulier de widgets. Chaque structure spécifie une option de configuration et possède les champs suivants :

typedef struct {
    Tk_OptionType type;
    const char *optionName;
    const char *dbName;
    const char *dbClass;
    const char *defValue;
    int objOffset;
    int internalOffset;
    int flags;
    const void *clientData;
    int typeMask;
} Tk_OptionSpec;
Le champ type indique quel type d'option de configuration il s'agit (par exemple, TK_OPTION_COLOR pour une valeur de couleur ou TK_OPTION_INT pour une valeur entière). Le type détermine comment la valeur de l'option est analysée (plus d'informations dans le paragraphe suivant). Le champ optionName est une chaîne telle que -font ou -bg ; c'est le nom utilisé dans les commandes Tcl et passé aux fonctions via les arguments objc ou namePtr. Les champs dbName et dbClass sont utilisés par Tk_InitOptions pour rechercher une valeur par défaut pour cette option dans la base de données d'options ; si dbName est nul, Tk_InitOptions n'utilise pas la base de données pour cette option. Le champ defValue spécifie une valeur par défaut pour cette option si elle n'est pas spécifiée dans la base de données d'options. Les champs objOffset et internalOffset indiquent où la valeur de cette option doit être stockée dans les tables d'enregistrement (plus d'informations dans le paragraphe suivant) ; les valeurs de ces champs doivent toujours être générées à l'aide de la macro Tk_Offset. Le champ flags contient des informations supplémentaires pour contrôler le traitement de cette option de configuration (plus de détails dans le paragraphe suivant). Le clientData fournit des données spécifiques au type nécessaires pour certains types. Par exemple, pour les types TK_OPTION_COLOR, clientData est une chaîne spécifiant la valeur par défaut pour les écrans monochromes. Plus de détails peuvent être trouvés dans les descriptions des différents types. Le dernier champ, typeMask, est utilisé par Tk_SetOptions pour renvoyer des informations sur les options qui ont été modifiées ; voir la description de Tk_SetOptions pour plus de détails.

Lorsque Tk_InitOptions et Tk_SetOptions stockent la valeur d'une option dans la table d'enregistrement, elles peuvent le faire de l'une des deux manières. Si le champ objOffset de la structure Tk_OptionSpec est supérieur ou égal à zéro, la valeur de l'option est stockée sous forme de (Tcl_Obj *) à l'emplacement de la table d'enregistrement donné par objOffset. Si le champ internalOffset de la structure Tk_OptionSpec est supérieur ou égal à zéro, la valeur de l'option est stockée sous une forme interne spécifique au type à l'emplacement donné par internalOffset. Par exemple, si le type de l'option est TK_OPTION_INT, la forme interne est un entier. Si le champ objOffset ou internalOffset est négatif, la valeur n'est pas stockée sous cette forme. Au moins l'un des décalages doit être supérieur ou égal à zéro.

Le champ flags se compose d'un ou plusieurs bits ORés. Les indicateurs suivants sont pris en charge :

TK_OPTION_NULL_OK
Si ce bit est défini pour une option, une chaîne vide est acceptée comme valeur pour cette option et la forme interne sera un pointeur vers NULL, une valeur zéro ou None, selon le type de l'option. Si le bit n'est pas défini, les chaînes vides génèrent des erreurs. TK_OPTION_NULL_OK est généralement utilisé pour permettre la désactivation d'une fonctionnalité, par exemple, la définition d'une valeur de pointeur à None afin qu'une fenêtre hérite du curseur de son parent. Tous les types d'options ne prennent pas en charge l'indicateur TK_OPTION_NULL_OK ; pour ceux qui le font, cela est indiqué explicitement dans les descriptions suivantes.
TK_OPTION_DONT_SET_DEFAULT
Si ce bit est défini pour une option, la valeur par défaut n'est pas définie dans Tk_InitOptions pour cette option. La base de données d'options, aucune valeur par défaut systématique, ni le optionTable ne sont utilisés pour assigner une valeur par défaut à cette option. On suppose que l'appelant a déjà fourni une valeur par défaut dans le code du widget.

Le champ type de chaque structure Tk_OptionSpec détermine comment la valeur de cette option de configuration est analysée. Les valeurs valides pour type et les actions correspondantes sont décrites ci-dessous. Si le type nécessite une valeur tkwin à passer à des procédures telles que Tk_SetOptions, ou s'il utilise le champ clientData de la structure Tk_OptionSpec, cela est indiqué explicitement ; sinon, le type nécessite à la fois tkwin et clientData.

TK_OPTION_ANCHOR
La valeur doit être une position standard telle que ne ou center. La forme interne est une valeur Tk_Anchor telle que renvoyée par Tk_GetAnchorFromObj.
TK_OPTION_BITMAP
La valeur doit être un nom de bitmap Tk standard. La forme interne est un jeton Pixmap tel que renvoyé par Tk_AllocBitmapFromObj. Ce type d'option nécessite que tkwin soit fourni aux procédures telles que Tk_SetOptions, et il prend en charge l'indicateur TK_OPTION_NULL_OK.
TK_OPTION_BOOLEAN
La valeur doit être une valeur booléenne standard telle que true ou no. La forme interne est un entier avec la valeur 0 ou 1. Note : si le champ objOffset n'est pas utilisé, les informations sur la valeur d'origine de cette option seront perdues.
TK_OPTION_BORDER
La valeur doit être un nom de couleur standard tel que red ou #ff8080. La forme interne est un jeton Tk_3DBorder tel que renvoyé par Tk_Alloc3DBorderFromObj. Ce type d'option nécessite que tkwin soit fourni aux procédures telles que Tk_SetOptions, et il prend en charge l'indicateur TK_OPTION_NULL_OK.
TK_OPTION_COLOR
La valeur doit être un nom de couleur standard tel que red ou #ff8080. La forme interne est un jeton Tk_3DBorder tel que renvoyé par Tk_Alloc3DBorderFromObj. Ce type d'option nécessite que tkwin soit fourni aux procédures telles que Tk_SetOptions, et il prend en charge l'indicateur TK_OPTION_NULL_OK.

Si un campo de un registro de widget tiene su desplazamiento almacenado en la objOffset o internalOffset del struct Tk_OptionSpec, los procedimientos descritos aquí gestionarán todos los asuntos de alojamiento de almacenamiento y gestión de recursos asociados con dicho campo. Cuando se cambia el valor de una opción, Tk_SetOptions (o Tk_FreeSavedOptions) liberará automáticamente cualquier recurso asociado con el valor antiguo, como Tk_Fonts para opciones TK_OPTION_FONT o memoria dinámica para opciones TK_OPTION_STRING. Cuando una opción se almacena como objeto mediante el campo objOffset, el registro de widget comparte el objeto apuntado por el valor objv del llamado a Tk_SetOptions. La cuenta de referencias del objeto se incrementa al almacenar un puntero a él en el registro de widget y se decrementa cuando la opción se modifica. Cuando el widget se elimina, debe llamarse Tk_FreeConfigOptions, que liberará los recursos asociados con todas las opciones y decrementará las cuentas de referencias para cualquier objeto.

Sin embargo, el código de widget es responsable de almacenar NULL o None en todos los campos de puntero y token antes de invocar Tk_InitOptions. Esto es necesario para permitir un correcto cierre en el escaso caso en el que ocurra un error en Tk_InitOptions.

OBJOFFSET VS. INTERNALOFFSET

En la mayoría de los casos, es más sencillo utilizar el campo internalOffset del struct Tk_OptionSpec que el campo objOffset. Esto permite que la forma interna del valor esté disponible inmediatamente para el código de widget, evitando que se extraiga cada vez que se use el valor. Sin embargo, hay dos casos donde el campo objOffset es útil. La primera situación se produce en opciones de TK_OPTION_PIXELS. En este caso, la forma interna es un valor entero en pixeles válido solo para una pantalla específica. Si se recupera el valor de la opción, se devuelve como un número simple. Por ejemplo, después de la orden .b configure -borderwidth 2m, la orden .b configure -borderwidth podría devolver 7, que es el valor entero en pixeles correspondiente a 2m. Sin embargo, esto pierde el valor original independiente de la pantalla. Por lo tanto, para opciones TK_OPTION_PIXELS, es mejor usar el campo objOffset. En este caso, el valor original de la opción se mantiene en el objeto y puede ser recuperado cuando se obtenga la opción. En la mayoría de los casos es conveniente usar el campo internalOffset, ya que el valor entero está disponible inmediatamente para uso en el código de widget (alternativamente, se puede usar Tk_GetPixelsFromObj para extraer el valor entero del objeto cuando se necesite). Se debe tener en cuenta que el problema de perder información durante las recuperaciones solo existe para opciones TK_OPTION_PIXELS.

La segunda razón para usar el campo objOffset es para implementar nuevos tipos de opciones no soportados por estos procedimientos. Para implementar un nuevo tipo de opción, se puede usar TK_OPTION_STRING como tipo en el struct Tk_OptionSpec y establecer el campo objOffset pero no el internalOffset. Luego, después de llamar a Tk_SetOptions, se debe convertir el objeto a forma interna uno mismo.

Las widgets Ttk no soportan el mecanismo de internalOffset. Los valores de opciones de widgets Ttk siempre se almacenan como Tcl_Obj *, lo que implica que debe usarse el campo objOffset.

CUSTOM OPTION TYPES

Los aplicaciones pueden extender los tipos de configuración prediseñados con tipos adicionales escribiendo procedimientos para parsear, imprimir, liberar copias guardadas y restaurar los valores de los tipos. Creando un estructura que apunte a esos procedimientos:

typedef struct Tk_ObjCustomOption {
    const char *name;
    Tk_CustomOptionSetProc *setProc;
    Tk_CustomOptionGetProc *getProc;
    Tk_CustomOptionRestoreProc *restoreProc;
    Tk_CustomOptionFreeProc *freeProc;
    ClientData clientData;
} Tk_ObjCustomOption;
typedef int Tk_CustomOptionSetProc(
    ClientData clientData,
    Tcl_Interp *interp,
    Tk_Window tkwin,
    Tcl_Obj **valuePtr,
    char *recordPtr,
    int internalOffset,
    char *saveInternalPtr,
    int flags);
typedef Tcl_Obj *Tk_CustomOptionGetProc(
    ClientData clientData,
    Tk_Window tkwin,
    char *recordPtr,
    int internalOffset);
typedef void Tk_CustomOptionRestoreProc(
    ClientData clientData,
    Tk_Window tkwin,
    char *internalPtr,
    char *saveInternalPtr);
typedef void Tk_CustomOptionFreeProc(
    ClientData clientData,
    Tk_Window tkwin,
    char *internalPtr);

La estructura Tk_ObjCustomOption contiene seis campos: un nombre para el tipo de opción personalizada; punteros a los cuatro procedimientos; y un valor clientData para pasar a esos procedimientos cuando se invoquen. El campo clientData es utilizado como valor.

Si un campo de un registro de widget tiene su desplazamiento almacenado en el campo objOffset o internalOffset del struct Tk_OptionSpec, los procedimientos descritos aquí se encargarán de toda la gestión de almacenamiento y de recursos asociada con dicho campo. Cuando se cambia el valor de una opción, Tk_SetOptions (o Tk_FreeSavedOptions) liberará automáticamente cualquier recurso asociado con el valor antiguo, como las fuentes Tk para las opciones TK_OPTION_FONT o la memoria dinámica para las opciones TK_OPTION_STRING. Cuando una opción se almacena como un objeto mediante el campo objOffset, el registro del widget comparte el objeto al que apunta el valor objv de la llamada a Tk_SetOptions. La cuenta de referencias del objeto se incrementa al almacenar un puntero a él en el registro del widget y se decrementa cuando la opción se modifica. Cuando el widget se destruye, se debe llamar a Tk_FreeConfigOptions, que liberará los recursos asociados con todas las opciones y decrementará las cuentas de referencias para cualquier objeto.

Sin embargo, el código del widget es responsable de almacenar NULL o None en todos los campos de puntero y token antes de invocar Tk_InitOptions. Esto es necesario para permitir una limpieza adecuada en el caso poco probable de que ocurra un error en Tk_InitOptions.
