DESCRIPTION

Tk_FindPhoto retourne un handle opaque qui est utilisé pour identifier une image photo particulière aux autres procédures. Le paramètre est le nom de l'image, c'est-à-dire le nom spécifié à la commande image create photo, ou assigné par cette commande si aucun nom n'a été spécifié. Si imageName n'existe pas ou n'est pas une image photo, Tk_FindPhoto retourne NULL.

Tk_PhotoPutBlock est utilisé pour fournir des blocs de données d'image à afficher. L'appel affecte une zone de l'image de taille width x height pixels, dont le coin supérieur gauche est aux coordonnées (x,y). Tous les width, height, x et y doivent être non négatifs. Si une partie de cette zone se trouve en dehors des limites actuelles de l'image, l'image sera étendue pour inclure la zone, à moins que l'utilisateur n'ait spécifié une taille d'image explicite avec les options de configuration du widget -width et/ou -height (voir photo(n)) ; dans ce cas, la zone est silencieusement coupée aux limites de l'image.

Le paramètre block est un pointeur vers une structure Tk_PhotoImageBlock, définie comme suit :

typedef struct {
    unsigned char *pixelPtr;
    int width;
    int height;
    int pitch;
    int pixelSize;
    int offset[4];
} Tk_PhotoImageBlock;
Le champ pixelPtr pointe vers le premier pixel, c'est-à-dire le pixel en haut à gauche du bloc. Les champs width et height spécifient les dimensions du bloc de pixels. Le champ pixelSize spécifie la différence d'adresse entre deux pixels horizontalement adjacents. Il doit être de 4 pour les données d'image RVB et de 2 pour les données d'image en niveaux de gris. D'autres valeurs sont possibles, si les décalages dans le tableau offset sont ajustés en conséquence (par exemple, pour des données rouges, vertes et bleues stockées dans des plans différents). L'utilisation d'une telle disposition est fortement déconseillée, cependant. En raison d'un bug, cela pourrait ne pas fonctionner correctement si un canal alpha est fourni. (voir la section BOGUES ci-dessous). Le champ pitch spécifie la différence d'adresse entre deux pixels verticalement adjacents. Le tableau offset contient les décalages de l'adresse d'un pixel vers les adresses des octets contenant les composantes rouge, verte, bleue et alpha (transparence). Si les décalages pour le rouge, le vert et le bleu sont égaux, l'image est interprétée comme étant en niveaux de gris. S'ils diffèrent, des données RVB sont supposées. Normalement, les décalages seront de 0, 1, 2, 3 pour les données RVB et de 0, 0, 0, 1 pour les niveaux de gris. Il est possible de fournir des données d'image sans canal alpha en définissant le décalage de l'alpha sur une valeur négative et en ajustant le champ pixelSize en conséquence. Cette utilisation est cependant déconseillée (voir la section BOGUES ci-dessous).

Le paramètre compRule de Tk_PhotoPutBlock spécifie une règle de composition qui indique quoi faire avec les pixels transparents. La valeur TK_PHOTO_COMPOSITE_OVERLAY indique que le contenu précédent de l'image photo doit transparaître, et la valeur TK_PHOTO_COMPOSITE_SET indique que le contenu précédent de l'image photo doit être complètement ignoré, et que les valeurs du bloc doivent être copiées directement.

Les valeurs fournies pour les paramètres width et height de Tk_PhotoPutBlock ne correspondent pas nécessairement aux valeurs spécifiées dans block. Si elles sont plus petites, Tk_PhotoPutBlock extrait un sous-bloc des données d'image fournies. Si elles sont plus grandes, les données fournies sont répliquées (de manière pavée) pour remplir la zone spécifiée. Ces règles fonctionnent indépendamment dans les directions horizontale et verticale.

Tk_PhotoPutBlock retourne normalement TCL_OK, bien que s'il ne parvient pas à allouer suffisamment de mémoire pour contenir l'image résultante, TCL_ERROR soit retourné à la place et, si l'argument interp n'est pas NULL, un message d'erreur soit placé dans le résultat de l'interpréteur.

Tk_PhotoPutZoomedBlock fonctionne comme Tk_PhotoPutBlock sauf que l'image peut être réduite ou agrandie pour l'affichage. Les paramètres subsampleX et subsampleY permettent de réduire la taille de l'image par sous-échantillonnage. Tk_PhotoPutZoomedBlock n'utilisera que les pixels de l'image d'entrée dont les coordonnées X sont des multiples de subsampleX, et dont les coordonnées Y sont des multiples de subsampleY. Par exemple, une image de 512x512 pixels peut être réduite à 256x256 en définissant subsampleX et subsampleY à 2.

Les paramètres zoomX et zoomY permettent d'agrandir l'image par réplication de pixels. Chaque pixel de l'image d'entrée (éventuellement sous-échantillonnée) sera écrit dans un bloc de zoomX pixels de large et zoomY pixels de haut de l'image affichée. Le sous-échantillonnage et le zoom peuvent être utilisés ensemble pour des effets spéciaux.

Tk_PhotoGetImage peut être utilisé pour récupérer les données d'image d'une image photo. Tk_PhotoGetImage remplit la structure pointée par le paramètre blockPtr avec des valeurs qui décrivent l'adresse et la disposition des données d'image que l'image photo a stockées en interne. Les valeurs sont valides jusqu'à ce que l'image soit détruite ou que sa taille soit modifiée.

Il est possible de modifier une image en écrivant directement dans les données pointées par le champ pixelPtr. La taille de l'image ne peut toutefois pas être modifiée de cette manière. De plus, les modifications apportées en écrivant directement dans pixelPtr ne seront pas visibles immédiatement, mais seulement après un appel à Tk_ImageChanged ou après un événement qui provoque le redessin des widgets concernés. DESCRIPTION

Ces procédures sont des fonctions d'aide pour la création et la manipulation de l'objet image de type photo dans Tk. Elles sont généralement appelées par un gestionnaire de format d'image personnalisé.

La structure TkPhotoImageBlock est définie comme suit :

typedef struct TkPhotoImageBlock {
    char *pixelPtr;           /* Début des données des pixels. */
    char *pitchPtr;           /* Pointeur vers le début de la ligne suivante. */
    int width;                /* Largeur en pixels. */
    int height;               /* Hauteur en pixels. */
    int nchan;                /* Nombre de canaux par pixel. */
    int offset[4];            /* Décalages pour chaque canal (R, G, B, A). */
    int pixelSize;            /* Taille en octets d'un pixel. */
} TkPhotoImageBlock;

Tk_PhotoImageInstall installe un format d'image nommé « photo » dans l'interpréteur interp. Cela doit être fait avant que des images de type photo puissent être créées. imageHandle doit être le handle retourné par Tk_AllocPhotoImage.

Tk_PhotoPutBlock et Tk_PhotoPutZoomedBlock copient un bloc de pixels dans l'image photo. blockPtr pointe vers une structure TkPhotoImageBlock qui décrit les données des pixels. Tk_PhotoPutZoomedBlock met à l'échelle les pixels si le facteur de zoom zoom est supérieur à 1. La largeur et la hauteur de l'image sont ajustées automatiquement en fonction des données fournies. Il est possible de faire plusieurs appels à ces fonctions pour construire progressivement une image. Si vous devez modifier une partie des données d'une image existante, vous devez d'abord obtenir une copie des données de l'image à l'aide de Tk_PhotoGetImage, modifier la copie des données de l'image, puis la réécrire à l'aide de Tk_PhotoPutBlock ou Tk_PhotoPutZoomedBlock.

Tk_PhotoGetImage renvoie 1 pour la compatibilité avec la procédure correspondante dans le widget photo existant.

Tk_PhotoBlank vide toute la zone de l'image photo. Les zones vides d'une image photo sont transparentes.

Tk_PhotoExpand demande que l'image du widget soit étendue pour avoir au moins une taille de width x height pixels. La largeur et/ou la hauteur ne sont pas modifiées si l'utilisateur a spécifié une largeur ou une hauteur d'image explicite avec les options de configuration -width et/ou -height, respectivement. Si les données de l'image sont fournies en de nombreux petits blocs, il est plus efficace d'utiliser Tk_PhotoExpand ou Tk_PhotoSetSize au début plutôt que de laisser l'image s'étendre par petits incréments successifs à mesure que les blocs d'image sont fournis.

Tk_PhotoExpand renvoie normalement TCL_OK, bien que si elle ne peut pas allouer suffisamment de mémoire pour contenir l'image résultante, TCL_ERROR soit renvoyé à la place et, si l'argument interp n'est pas NULL, un message d'erreur est placé dans le résultat de l'interpréteur.

Tk_PhotoSetSize spécifie la taille de l'image, comme si l'utilisateur avait spécifié les valeurs width et height données aux options de configuration -width et -height. Une valeur de zéro pour width ou height ne modifie pas la largeur ou la hauteur de l'image, mais permet à la largeur ou à la hauteur d'être modifiée par des appels ultérieurs à Tk_PhotoPutBlock, Tk_PhotoPutZoomedBlock ou Tk_PhotoExpand.

Tk_PhotoSetSize renvoie normalement TCL_OK, bien que si elle ne peut pas allouer suffisamment de mémoire pour contenir l'image résultante, TCL_ERROR soit renvoyé à la place et, si l'argument interp n'est pas NULL, un message d'erreur est placé dans le résultat de l'interpréteur.

Tk_PhotoGetSize renvoie les dimensions de l'image dans *widthPtr et *heightPtr.

PORTABILITÉ

Dans Tk 8.3 et versions antérieures, Tk_PhotoPutBlock et Tk_PhotoPutZoomedBlock avaient des signatures différentes. Si vous souhaitez compiler du code qui utilise l'ancienne interface avec 8.4 sans mettre à jour votre code, compilez-le avec le drapeau -DUSE_COMPOSITELESS_PHOTO_PUT_BLOCK. Le code lié à l'aide de Stubs à des versions antérieures de Tk continuera de fonctionner.

Dans Tk 8.4, Tk_PhotoPutBlock, Tk_PhotoPutZoomedBlock, Tk_PhotoExpand et Tk_PhotoSetSize ne prenaient pas d'argument interp ni ne renvoyaient de code de résultat. Si une mémoire insuffisante était disponible pour une image, Tk paniquait. Ce comportement est toujours pris en charge si vous compilez votre extension avec le drapeau supplémentaire -DUSE_PANIC_ON_PHOTO_ALLOC_FAILURE. Le code lié à l'aide de Stubs à des versions antérieures de Tk continuera de fonctionner.

BOGUES

La structure Tk_PhotoImageBlock utilisée pour fournir les données d'image à Tk_PhotoPutBlock promet une grande flexibilité dans la disposition des données (par exemple, des plans séparés pour les canaux rouge, vert, bleu et alpha). Malheureusement, l'implémentation ne tient pas cette promesse. Le problème est que le champ pixelSize est utilisé (incorrectement) pour déterminer si l'image a un canal alpha. Actuellement, si le décalage pour le canal alpha est supérieur ou égal à pixelSize, tk_PhotoPutblock suppose qu'aucune donnée alpha n'est présente et rend l'image complètement opaque. Cela signifie que pour les dispositions où les canaux sont séparés (ou toute autre disposition exotique où pixelSize doit être inférieur au décalage alpha), le canal alpha ne sera pas lu correctement. Afin d'être prudent si ce problème est corrigé dans une future version, il est fortement recommandé de toujours fournir des données alpha - même si l'image n'a pas de transparence - et d'utiliser uniquement la disposition « standard » avec un pixelSize de 2 pour les données en niveaux de gris et 4 pour les données RVB avec des offsets de 0, 0, 0, 1 ou 0, 1, 2, 3 respectivement.
