NOM

Tk::fileevent - Exécuter un rappel lorsque qu'un descripteur de fichier devient lisible ou écrivable

SYNTAXE

$widget->fileevent(fileHandle,readable?,callback?)

$widget->fileevent(fileHandle,writable?,callback?)

DESCRIPTION

Cette commande est utilisée pour créer des gestionnaires d'événements de fichier. Un gestionnaire d'événements de fichier est une liaison entre un descripteur de fichier et un rappel, de telle sorte que le rappel est évalué chaque fois que le descripteur de fichier devient lisible ou écrivable. Les gestionnaires d'événements de fichier sont le plus souvent utilisés pour permettre de recevoir des données d'un autre processus sur une base événementielle, afin que le récepteur puisse continuer à interagir avec l'utilisateur tout en attendant l'arrivée des données. Si une application invoque "<>", "sysread" ou "read" sur un descripteur de fichier bloquant alors qu'aucune donnée d'entrée n'est disponible, le processus bloquera ; jusqu'à ce que les données d'entrée arrivent, il ne pourra pas traiter d'autres événements, et apparaîtra donc à l'utilisateur comme s'il était figé. Avec fileevent, le processus peut savoir quand des données sont présentes et n'invoquer gets ou read que lorsqu'ils ne bloqueront pas.

L'argument fileHandle de fileevent fait référence à un descripteur de fichier ouvert, tel que la valeur de retour d'une commande open ou socket précédente. Si l'argument callback est spécifié, alors fileevent crée un nouveau gestionnaire d'événements : callback sera évalué chaque fois que le descripteur de fichier deviendra lisible ou écrivable (selon l'argument de fileevent). Dans ce cas, fileevent renvoie une chaîne vide. Les gestionnaires d'événements readable et writable pour un fichier sont indépendants et peuvent être créés et supprimés séparément. Cependant, il ne peut y avoir qu'un seul gestionnaire readable et un seul gestionnaire writable pour un fichier à un moment donné dans un interpréteur donné. Si fileevent est appelé alors que le gestionnaire spécifié existe déjà dans l'interpréteur appelant, le nouveau rappel remplace l'ancien.

Si l'argument callback n'est pas spécifié, fileevent renvoie le rappel actuel pour fileHandle, ou une chaîne vide s'il n'y en a pas. Si l'argument callback est spécifié comme une chaîne vide, le gestionnaire d'événements est supprimé, de sorte qu'aucun rappel ne sera invoqué. Un gestionnaire d'événements de fichier est également automatiquement supprimé chaque fois que son descripteur de fichier est fermé ou que son interpréteur est supprimé.

Un descripteur de fichier est considéré comme lisible s'il y a des données non lues disponibles sur le périphérique sous-jacent. Un descripteur de fichier est également considéré comme lisible si une condition de fin de fichier ou d'erreur est présente sur le fichier ou le périphérique sous-jacent. Il est important que callback vérifie ces conditions et les gère de manière appropriée ; par exemple, s'il n'y a pas de vérification spéciale pour la fin de fichier, une boucle infinie peut se produire où callback ne lit aucune donnée, revient, et est immédiatement réinvoqué.

Un descripteur de fichier est considéré comme écrivable si au moins un octet de données peut être écrit sur le fichier ou le périphérique sous-jacent sans bloquer, ou si une condition d'erreur est présente sur le fichier ou le périphérique sous-jacent.

Les E/S événementiels fonctionnent mieux pour les descripteurs de fichier qui ont été placés en mode non bloquant. En mode bloquant, une commande "print" peut bloquer si vous lui donnez plus de données que le fichier ou le périphérique sous-jacent ne peut en accepter, et une commande "<>", "sysread" ou "read" bloquera si vous tentez de lire plus de données que ce qui est prêt ; aucun événement ne sera traité pendant que les commandes bloquent. En mode non bloquant, "print", "<>", "sysread" et "read" ne bloquent jamais. Voir la documentation des commandes individuelles pour des informations sur la façon dont elles gèrent les descripteurs de fichier bloquants et non bloquants.

Le rappel pour un événement de fichier est exécuté dans le contexte de $widget avec lequel fileevent a été invoqué. Si une erreur survient lors de l'exécution du rappel, le mécanisme Tk::Error est utilisé pour signaler l'erreur. De plus, le gestionnaire d'événements de fichier est supprimé s'il renvoie une erreur ; ceci est fait afin d'éviter les boucles infinies dues à des gestionnaires défectueux.

BOGUES

Sur les plateformes Windows, fileevent est limité dans les types de descripteurs de fichier qui fonctionnent correctement. La mise des descripteurs de fichier en mode non bloquant n'est implémentée que sur un sous-ensemble de plateformes UNIX (voir Tk::IO).

CRÉDITS

fileevent est basé sur la commande addinput créée par Mark Diekhans.
