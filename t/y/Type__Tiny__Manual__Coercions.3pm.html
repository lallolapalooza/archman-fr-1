NOM

Type::Tiny::Manual::Coercions - informations avancées sur les coercitions

MANUEL

Cette section du manuel suppose que vous avez déjà lu Type::Tiny::Manual::UsingWithMoo.

Type::Tiny adopte une approche légèrement différente des contraintes de type par rapport à Moose. Dans Moose, il existe un espace de noms unique et plat pour les contraintes de type. Moose définit une contrainte de type appelée Str pour les chaînes de caractères et une contrainte de type appelée ArrayRef pour les références de tableau. Si vous souhaitez définir des chaînes de caractères différemment (peut-être que vous pensez que la chaîne vide ne compte pas vraiment comme une chaîne, ou peut-être que vous pensez que les objets qui surchargent "q[""]" devraient être considérés comme des chaînes de caractères), alors vous ne pouvez pas l'appeler Str ; vous devez choisir un nom différent.

Avec Type::Tiny, deux bibliothèques de types peuvent chacune offrir une contrainte de type chaîne de caractères avec leurs propres définitions de ce qui compte comme une chaîne de caractères, et vous pouvez choisir laquelle importer, ou les importer toutes les deux avec des noms différents :

use Some::Types qw( Str );
use Other::Types "Str" => { -as => "Str2" };

Cela pourrait sembler être un petit avantage de Type::Tiny, mais là où cette philosophie globale versus locale fait vraiment la différence, ce sont les coercions.

Imaginons que pour une partie de votre application qui traite de la lecture de données de nom d'utilisateur et de mot de passe, vous ayez besoin d'une chaîne de caractères de type « nom d'utilisateur:mot de passe ». Vous pourriez souhaiter accepter une référence de tableau "[$username, $password]" et la contraindre en une chaîne de caractères en utilisant "join ":", @$arrayref". Mais une autre partie de votre application traite de la lecture de fichiers journaux et souhaite contraindre une chaîne de caractères à partir d'une référence de tableau en utilisant "join "\n", @$arrayref". Ce sont toutes deux des manières parfaitement sensées de contraindre une référence de tableau. Dans Moose, une façon typique de faire cela serait :

package My::UserManager {
  use Moose;
  use Moose::Util::TypeConstraints;

  coerce 'Str',
    from 'ArrayRef', via { join ":", @$_ };

  ...;
}

package My::LogReader {
  use Moose;
  use Moose::Util::TypeConstraints;

  coerce 'Str',
    from 'ArrayRef', via { join "\n", @$_ };

  ...;
}

Cependant, parce que dans Moose tous les types et toutes les coercions sont globaux, si ces deux classes sont chargées, une seule d'entre elles fonctionnera. Une classe annulera la coercion de l'autre. Laquelle des deux « gagne » dépendra de l'ordre de chargement.

Il est possible de résoudre cela avec des types natifs Moose, mais cela demande un travail supplémentaire. (La solution consiste pour My::UserManager et My::LogReader à créer chacun un sous-type de Str et à définir la coercion sur ce sous-type plutôt que directement sur Str.)

Type::Tiny résout cela de deux manières :

1.
Type::Tiny permet aux bibliothèques de types de « protéger » leurs contraintes de types pour empêcher le code externe d'ajouter de nouvelles coercions. 
$type->coercion->freeze();

Vous pouvez figer les coercions pour l'ensemble de votre bibliothèque de types en utilisant :

__PACKAGE__->make_immutable;

Si vous essayez d'ajouter des coercions à une contrainte de type qui a des coercions figées, cela provoquera une erreur.

use Types::Standard qw( Str ArrayRef );

Str->coercion->add_type_coercions(
  ArrayRef, sub { join "\n", @$_ },
);
2.
Type::Tiny facilite le modèle mentionné ci-dessus consistant à ajouter des coercions à un sous-type. 
use Types::Standard ( Str ArrayRef );

my $subtype = Str->plus_coercions(
  ArrayRef, sub { join "\n", @$_ },
);

La méthode "plus_coercions" crée un nouveau type enfant, y ajoute de nouvelles coercions, copie les coercions existantes du type parent, puis fige les coercions pour le nouveau type enfant.

Le résultat final est que vous avez maintenant une « copie » de Str qui peut contraindre à partir de ArrayRef, mais d'autres copies de Str ne seront pas affectées par votre coercion.

Définir des coercions au sein des bibliothèques de types

Certaines coercions, comme joindre une référence de tableau pour faire une chaîne de caractères, ne seront pas des coercions sur lesquelles tout le monde sera d'accord. Joindre avec un saut de ligne entre eux comme ci-dessus ? Ou avec deux-points, une tabulation, un espace, un autre caractère ? Cela dépend beaucoup de votre application.

D'autres, comme contraindre un objet Path::Tiny à partir d'une chaîne de caractères, seront probablement très évidentes. C'est ce genre de coercion qu'il est logique de définir au sein de la bibliothèque elle-même afin qu'elle soit disponible pour tous les packages qui utilisent la bibliothèque.

my $pt = __PACKAGE__->add_type(
  Type::Tiny::Class->new(
    name    => 'Path',
    class   => 'Path::Tiny',
  ),
);

$pt->coercion->add_type_coercions(
  Str, q{ Path::Tiny::path($_) },
);

$pt->coercion->freeze;

Ajuster les coercions en dehors des bibliothèques de types

La méthode "plus_coercions" crée une nouvelle contrainte de type avec des coercions supplémentaires. Si le type original avait déjà des coercions, les nouvelles coercions ont une priorité plus élevée.

Il existe également une méthode "plus_fallback_coercions" qui fait la même chose que "plus_coercions" mais ajoute les nouvelles coercions avec une priorité inférieure à celle des coercions existantes.

Type::Tiny::Class fournit une méthode "plus_constructors" comme raccourci pour contraindre via une méthode constructeur. Les deux suivants sont identiques :

Path->plus_constructors( Str, "new" )

Path->plus_coercions( Str, q{ Path::Tiny->new($_) } )

Pour créer une contrainte de type sans coercions existantes particulières, vous pouvez utiliser "minus_coercions". Ce qui suit utilise le type Datetime défini dans Type::Tiny::Manual::Libraries, en supprimant la coercion de Int mais en conservant les coercions de Undef et Dict.

use Types::Standard qw( Int );
use Example::Types qw( Datetime );

has start_date => (
  is      => 'ro',
  isa     => Datetime->minus_coercions( Int ),
  coerce  => 1,
);

Il existe également une méthode "no_coercions" qui crée un sous-type sans aucune coercion. C'est surtout utile soit pour créer une « ardoise vierge » pour "plus_coercions" :

my $Path = Path->no_coercions->plus_coercions( Str, sub { ... } );

Soit pour désactiver les coercions pour Type::Params. Type::Params contraindra toujours automatiquement un paramètre s'il existe une coercion pour ce type.

use Types::Standard qw( Object );
use Types::Common::String qw( UpperCaseStr );
use Type::Params qw( signature_for );

signature_for set_account_name => (
  method     => Object,
  positional => [ UpperCaseStr->no_coercions ],
);

sub set_account_name ( $self, $name ) {
  $self->_account_name( $name );
  $self->db->update( $self );
  return $self;
}

# Cela mourra au lieu de contraindre à partir de minuscules
$robert->set_account_name( 'bob' );

Coercions Nommées

Un compromis entre la définition d'une coercion dans la bibliothèque de types ou leur définition dans le package qui utilise la bibliothèque de types consiste pour une bibliothèque de types à définir une collection nommée de coercions qui peuvent être ajoutées facultativement à une contrainte de type.

{
  package MyApp::Types;
  use Type::Library
    -extends => [ 'Types::Standard' ];

  __PACKAGE__->add_coercion(
    name              => "FromLines",
    type_constraint   => ArrayRef,
    type_coercion_map => [
      Str,     q{ [split /\n/] },
      Undef,   q{ [] },
    ],
  );
}

Cet ensemble de coercions a un nom et peut être importé et utilisé :

use MyApp::Types qw( ArrayRef FromLines );

has lines => (
  is      => 'ro',
  isa     => ArrayRef->plus_coercions( FromLines ),
  coerce  => 1,
);

Types::Standard définit une coercion nommée MkOpt conçue pour être utilisée pour OptList.

use Types::Standard qw( OptList MkOpt );
my $OptList = OptList->plus_coercions( MkOpt );

Coercions Paramétrées

Les coercions nommées peuvent également être paramétrables.

my $ArrayOfLines = ArrayRef->plus_coercions( Split[ qr{\n} ] );

Types::Standard définit les coercions paramétrables Split et Join.

Type::Tiny::Manual::Coercions - Coercions

MANUAL

Viewing the source code for Types::Standard should give you hints as to how they are implemented.

"Deep" Coercions

Certain parameterized type constraints can automatically acquire coercions if their parameters have coercions. For example:

ArrayRef[ Int->plus_coercions( Num, q{int($_)} ) ]

... does what you mean!

The parameterized type constraints that do this magic include the following ones from Types::Standard:

  • ScalarRef
  • ArrayRef
  • HashRef
  • Map
  • Tuple
  • CycleTuple
  • Dict
  • Optional
  • Maybe

Imagine we're defining a type Paths in a type library:

__PACKAGE__->add_type(
  name      => 'Paths',
  parent    => ArrayRef[Path],
);

The Path type has a coercion from Str, so Paths should be able to coerce from an arrayref of strings, right?

Wrong! Although ArrayRef[Path] could coerce from an arrayref of strings, Paths is a separate type constraint which, although it inherits from ArrayRef[Path] has its own (currently empty) set of coercions.

Because that is often not what you want, Type::Tiny provides a shortcut when declaring a subtype to copy the parent type constraint's coercions:

__PACKAGE__->add_type(
  name      => 'Paths',
  parent    => ArrayRef[Path],
  coercion  => 1,   # inherit
);

Now Paths can coerce from an arrayref of strings.

Deep Caveat

Currently there exists ill-defined behaviour resulting from mixing deep coercions and mutable (non-frozen) coercions. Consider the following:

class_type Path, { class => "Path::Tiny" };
coerce Path,
   from Str, via { "Path::Tiny"->new($_) };

declare Paths, as ArrayRef[Path], coercion => 1;

coerce Path,
   from InstanceOf["My::File"], via { $_->get_path };

An arrayref of strings can now be coerced to an arrayref of Path::Tiny objects, but is it also now possible to coerce an arrayref of My::File objects to an arrayref of Path::Tiny objects?

Currently the answer is "no", but this is mostly down to implementation details. It's not clear what the best way to behave in this situation is, and it could start working at some point in the future.

This is why you should freeze coercions.

Chained Coercions

Consider the following type library:

package Types::Geometric {
   use Type::Library -base, -declare => qw(
      VectorArray
      VectorArray3D
      Point
      Point3D
   );
   use Type::Utils;
   use Types::Standard qw( Num Tuple InstanceOf );

   declare VectorArray,
      as Tuple[Num, Num];

   declare VectorArray3D,
      as Tuple[Num, Num, Num];

   coerce VectorArray3D,
      from VectorArray, via {
         [ @$_, 0 ];
      };

   class_type Point, { class => "Point" };

   coerce Point,
      from VectorArray, via {
         Point->new(x => $_->[0], y => $_->[1]);
      };

   class_type Point3D, { class => "Point3D" };

   coerce Point3D,
      from VectorArray3D, via {
         Point3D->new(x => $_->[0], y => $_->[1], z => $_->[2]);
      },
      from Point, via {
         Point3D->new(x => $_->x, y => $_->y, z => 0);
      };
}

Given an arrayref "[1, 1]" you might reasonably expect it to be coercible to a Point3D object; it matches the type constraint VectorArray so can be coerced to VectorArray3D and thus to Point3D.

However, Type::Coercion does not automatically chain coercions like this. Firstly, it would be incompatible with Moose's type coercion system which does not chain coercions. Secondly, it's ambiguous; in our example, the arrayref could be coerced along two different paths (via VectorArray3D or via Point); in this case the end result would be the same, but in other cases it might not. Thirdly, it runs the risk of accidentally creating loops.

Doing the chaining manually though is pretty simple. Firstly, we'll take note of the "coercibles" method in Type::Tiny. This method called as "VectorArray3D->coercibles" returns a type constraint meaning "anything that can be coerced to a VectorArray3D".

So we can define the coercions for Point3D as:

coerce Point3D,
   from VectorArray3D->coercibles, via {
      my $tmp = to_VectorArray3D($_);
      Point3D->new(x => $tmp->[0], y => $tmp->[1], z => $tmp->[2]);
   },
   from Point, via {
      Point3D->new(x => $_->x, y => $_->y, z => 0);
   };

... and now coercing from "[1, 1]" will work.
