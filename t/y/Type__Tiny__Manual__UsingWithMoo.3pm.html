NOM

Type::Tiny::Manual::UsingWithMoo - utilisation de base de Type::Tiny avec Moo

MANUEL

Contraintes de Type

Considérez la classe Moo de base suivante :

package Horse {
  use Moo;
  use namespace::autoclean;

  has name       => ( is => 'ro' );
  has gender     => ( is => 'ro' );
  has age        => ( is => 'rw' );
  has children   => ( is => 'ro', default => sub { [] } );
}

Un code comme celui-ci semble assez simple :

my $br = Horse->new(name => "Bold Ruler", gender => 'm', age => 16);
push @{ $br->children },
  Horse->new(name => 'Secretariat', gender => 'm', age => 0);

Cependant, dès que vous vous éloignez d'une utilisation très simple de la classe, les choses peuvent commencer à mal tourner. Lorsque nous ajoutons un nouveau cheval à "@{ $br->children }", nous supposons que "$br->children" a retourné un tableau référencé.

Et si le code qui a créé le cheval $br l'avait instancié comme ceci ?

my $br = Horse->new(name => "Bold Ruler", children => 'no');

C'est pour cette raison qu'il est utile que la classe Horse effectue une vérification de base sur ses propres attributs.

package Horse {
  use Moo;
  use Types::Standard qw( Str Num ArrayRef );
  use namespace::autoclean;

  has name       => ( is => 'ro', isa => Str );
  has gender     => ( is => 'ro', isa => Str );
  has age        => ( is => 'rw', isa => Num );
  has children   => (
    is      => 'ro',
    isa     => ArrayRef,
    default => sub { return  [] },
  );
}

Maintenant, si vous instanciez un cheval comme ceci, cela provoquera une erreur :

my $br = Horse->new(name => "Bold Ruler", children => 'no');

La première contrainte de type que nous avons utilisée ici est Str. C'est une contrainte de type qui exige que les valeurs soient des chaînes de caractères.

Notez que même si "undef" n'est pas une chaîne de caractères, la chaîne vide est bien une chaîne de caractères et vous voudrez souvent vérifier qu'une chaîne n'est pas vide. Nous aurions pu faire ceci :

use Types::Common::String qw( NonEmptyStr );
has name => ( is => 'ro', isa => NonEmptyStr );

Alors que la plupart des contraintes de type que nous utiliserons dans ce manuel sont définies dans Types::Standard, la bibliothèque de types Types::Common::String définit également de nombreuses contraintes de type utiles.

Nous avons exigé que l'âge du cheval soit un nombre. C'est aussi une contrainte de type courante et utile. Si nous voulons nous assurer qu'il s'agit d'un nombre entier, nous pouvons utiliser :

use Types::Standard qw( Int );
has age => ( is => 'rw', isa => Int );

Ou parce que les nombres négatifs ont peu de sens comme âge :

use Types::Common::Numeric qw( PositiveOrZeroInt );
has age => ( is => 'rw', isa => PositiveOrZeroInt );

La bibliothèque Types::Common::Numeric définit de nombreux sous-types utiles de Int et Num, tels que PositiveInt et PositiveOrZeroInt.

La dernière contrainte de type que nous avons utilisée dans cet exemple est ArrayRef. Cela exige que la valeur soit une référence à un tableau.

Types::Standard fournit également les contraintes de type HashRef et CodeRef. Un exemple d'utilisation de cette dernière :

package Task {
  use Moo;
  use Types::Standard qw( CodeRef Bool );
  has on_success => ( is => 'ro', isa => CodeRef );
  has on_failure => ( is => 'ro', isa => CodeRef );
  has finished   => ( is => 'ro', isa => Bool, default => 0 );
  ...;
}

my $task = Task->new(
  on_success => sub { ... },
  on_failure => sub { ... },
  ...,
);

La contrainte de type Bool accepte "1" comme valeur vraie, et "0", "", ou undef comme valeurs fausses. Aucune autre valeur n'est acceptée.

Il existe une contrainte de type Object qui accepte n'importe quel objet blessé.

package Horse {
  use Moo;
  use Types::Standard qw( Object );
  use namespace::autoclean;

  ...;  # name, gender, age, children
  has father => ( is => 'ro', isa => Object );
  has mother => ( is => 'ro', isa => Object );
}

Enfin, une autre contrainte de type utile à connaître est Any :

use Types::Standard qw( Any );
has stuff => ( is => 'rw', isa => Any );

Cette contrainte de type autorise n'importe quelle valeur ; elle est essentiellement la même que de ne faire aucune vérification de type, mais elle rend votre intention plus claire. Dans la mesure du possible, Type::Tiny optimisera cette vérification de type, elle devrait donc avoir peu (voire pas) d'impact sur les performances.

Types Paramétrés

Imaginons que nous voulions suivre les victoires de courses de nos chevaux :

package Horse {
  use Moo;
  use Types::Standard qw( Str Num ArrayRef );
  use namespace::autoclean;

  ...;  # name, gender, age, children
  has wins => (
    is      => 'ro',
    isa     => ArrayRef,
    default => sub { return [] },
  );
}

Nous pouvons créer un cheval comme ceci :

my $br = Horse->new(
  name    => "Bold Ruler",
  gender  => 'm',
  age     => 4,
  wins    => ["Futurity Stakes 1956", "Juvenile Stakes 1956"],
);

La liste des victoires est un tableau référencé de chaînes de caractères. La contrainte de type ArrayRef empêche qu'elle soit définie comme un hashref, par exemple, mais elle ne garantit pas que tout dans le tableau référencé est une chaîne de caractères. Pour ce faire, nous devons paramétrer la contrainte de type :

has wins => (
  is      => 'ro',
  isa     => ArrayRef[Str],
  default => sub { return [] },
);

Grâce au type paramétré ArrayRef[Str], le constructeur provoquera une erreur si le tableau référencé que vous lui passez contient autre chose qu'une chaîne de caractères.

Une autre façon d'écrire ceci est :

has wins => (
  is      => 'ro',
  isa     => ArrayRef->of(Str),
  default => sub { return [] },
);

La façon dont vous choisissez est largement une préférence de style. TIMTOWTDI !

Notez que bien que le constructeur et toute méthode de définition/accès effectuent des vérifications de type, il est possible de les contourner en utilisant :

push @{ $br->wins }, $not_a_string;

Le constructeur n'est pas appelé ici, et bien que l'accesseur *soit* appelé, il est appelé comme lecteur, pas comme écrivain, il n'a donc jamais l'occasion d'inspecter la valeur ajoutée. (Il est possible d'utiliser "tie" pour résoudre ce problème, mais cela sera couvert plus tard.)

Et bien sûr, si vous accédez directement au hashref sous-jacent de l'objet, toutes les garanties sont annulées :

$br->{wins} = $not_an_arrayref;

Les contraintes de type ont donc des limites. Une conception d'API prudente (et le fait de ne pas contourner l'API appropriée) peut aider.

La contrainte de type HashRef peut également être paramétrée :

package Design {
  use Moo;
  use Types::Standard qw( HashRef Str );
  has colours => ( is => 'ro', isa => HashRef[Str] );
}

my $eiffel65 = Design->new(
  colours => { house => "blue", little_window => "blue" },
);

La contrainte de type HashRef[Str] garantit que les *valeurs* du hashref sont des chaînes de caractères ; elle ne vérifie pas les clés du hashref car les clés dans les hashrefs de Perl sont toujours des chaînes de caractères !

Si vous avez besoin de contraindre les clés, il est possible d'utiliser une contrainte Map paramétrée :

use Types::Common::String qw( NonEmptyStr );
use Types::Standard qw( Map );
has colours => ( is => 'ro', isa => Map[NonEmptyStr, NonEmptyStr] );

Map prend deux paramètres ; le premier est un type à vérifier contre les clés et le second est un type à vérifier contre les valeurs.

Une autre contrainte de type utile est la contrainte de type Tuple.

use Types::Standard qw( ArrayRef Tuple );
use Types::Common::Numeric qw( PositiveInt );
use Types::Common::String qw( NonEmptyStr );

has wins => (
  is      => 'ro',
  isa     => ArrayRef[ Tuple[PositiveInt, NonEmptyStr] ],
  default => sub { return [] },
);

La contrainte de type Tuple[PositiveInt, NonEmptyStr] vérifie qu'une valeur est un tableau référencé de deux éléments où le premier élément est un entier positif et le second élément est une chaîne de caractères non vide. Par exemple :

my $br = Horse->new(
  name    => "Bold Ruler",
  wins    => [
    [ 1956, "Futurity Stakes" ],
    [ 1956, "Juvenile Stakes" ],
  ],
);

Comme vous pouvez le constater, les contraintes de type paramétrées peuvent être imbriquées à une profondeur arbitraire, bien sûr, plus vos vérifications deviennent détaillées, plus elles seront lentes.

La méthode "add_win" sera encapsulée avec du code qui vérifie les arguments entrants, lançant une exception s'ils ne répondent pas aux exigences. Elle effectuera également des coercitions si les types en ont (et vous n'avez même pas besoin de vous souvenir de "coerce => 1" ; c'est automatique) et peut même ajouter des valeurs par défaut :

signature_for add_win => (
  method     => true,
  positional => [
    PositiveInt,
    NonEmptyStr,
    NonEmptyStr, { default => sub { "Eddie" } },
  ],
);

La syntaxe généralisée pour les paramètres positionnels dans "signature_for" est :

signature_for $method_name => (
  %general_options,
  positional => [
    TypeForFirstParam,  \%options_for_first_param,
    TypeForSecondParam, \%options_for_second_param,
    ...,
  ],
);

Comme raccourci pour l'option "{ optional => true }", vous pouvez simplement utiliser Optional comme pour Tuple.

signature_for add_win => (
  method     => true,
  positional => [
    PositiveInt,
    NonEmptyStr,
    Optional[NonEmptyStr],
  ],
);

Vous pouvez également utiliser 0 (ou "builtin::false" si votre Perl est suffisamment récent) et 1 (ou "builtin::true") comme raccourcis pour Optional[Any] et Any. Ce qui suit vérifie que le premier paramètre est un entier positif, que le deuxième paramètre est requis (mais on ne se soucie pas de sa valeur) et qu'un troisième paramètre est autorisé mais pas requis.

signature_for thingy => ( positional => [ PositiveInt, 1, 0 ] );

Il est possible d'accepter un nombre variable de valeurs en utilisant Slurpy :

package Horse {
  use Types::Common::Numeric qw( PositiveInt );
  use Types::Common::String qw( NonEmptyStr );
  use Types::Standard qw( ArrayRef Slurpy );
  use Type::Params qw( signature_for );
  use constant { true => !!1, false => !!0 };
  ...;

  signature_for add_wins_for_year => (
    method     => true,
    positional => [
      PositiveInt,
      Slurpy[ ArrayRef[NonEmptyStr] ],
    ],
  );

  sub add_wins_for_year ( $self, $year, $races ) {
    for my $race ( $races->@* ) {
      push $self->wins->@*, [ $year, $race ];
    }
    return $self;
  }
}

Cela serait appelé comme suit :

$bold_ruler->add_wins_for_year(
  1956,
  "Futurity Stakes",
  "Juvenile Stakes",
);

Les paramètres supplémentaires sont "slurpés" dans un arrayref et vérifiés par rapport à ArrayRef[NonEmptyStr]. Notez qu'avec un arrayref slurpy comme celui-ci, la méthode reçoit les valeurs sous forme d'arrayref même si elles ont été passées sous forme de liste.

Les paramètres optionnels ne sont autorisés qu'après les paramètres requis, et les paramètres Slurpy ne sont autorisés qu'à la fin. (Et il ne peut y avoir qu'un seul paramètre Slurpy !)

Pour les méthodes qui acceptent plus d'un ou deux paramètres, il est souvent judicieux de les fournir sous forme de hash. Par exemple :

$horse->add_win(
  year    => 1956,
  race    => "Futurity Stakes",
  jockey  => "Eddie",
);

Cela peut rendre votre code plus lisible.

Pour accepter des paramètres nommés, utilisez l'option "named" au lieu de "positional".

package Horse {
  use Types::Common::Numeric qw( PositiveInt );
  use Types::Common::String qw( NonEmptyStr );
  use Type::Params qw( signature_for );
  use constant { true => !!1, false => !!0 };
  ...;

  signature_for add_win => (
    method     => true,
    named      => [
      year    => PositiveInt,
      race    => NonEmptyStr,
      jockey  => NonEmptyStr, { optional => true },
    ],
  );

  sub add_win ( $self, $arg ) {
    my $win = [
      $arg->year,
      $arg->race,
      $arg->has_jockey ? $arg->jockey : (),
    ];
    push $self->wins->@*, $win;
    return $self;
  }
}

L'option "named" regroupera tous vos arguments nommés dans un objet $arg. Elle permet d'appeler votre méthode avec une liste de paires nom-valeur ou un hashref :

$horse->add_win(
  year    => 1956,
  race    => "Futurity Stakes",
  jockey  => "Eddie",
);

$horse->add_win( {
  year    => 1956,
  race    => "Juvenile Stakes",
} );

Il est également possible que votre vérification accepte des paramètres nommés mais reçoive une liste positionnelle de paramètres, en utilisant "named_to_list".

package Horse {
  use Types::Common::Numeric qw( PositiveInt );
  use Types::Common::String qw( NonEmptyStr );
  use Type::Params qw( signature_for );
  use constant { true => !!1, false => !!0 };
  ...;

  signature_for add_win => (
    method     => true,
    named      => [
      year    => PositiveInt,
      race    => NonEmptyStr,
      jockey  => NonEmptyStr, { optional => true },
    ],
    named_to_list => true,
  );

  sub add_win ( $self, $year, $race, $jockey ) {
    my $win = [
      $year,
      $race,
      $jockey ? $jockey : (),
    ];
    push $self->wins->@*, $win;
    return $self;
  }
}

...;

$horse->add_win(
  year    => 1956,
  race    => "Futurity Stakes",
  jockey  => "Eddie",
);

Les paramètres nommés optionnels et Slurpy sont supportés comme vous vous y attendez.

Pour plus d'informations sur Type::Params, et les alternatives tierces, voir Type::Tiny::Manual::Params.

NOTES

Sur des versions très anciennes de Moo, "coerce => 1" n'est pas supporté. Au lieu de cela, vous devrez fournir une coderef ou un objet de surcharge "&{}" pour coercer. Type::Tiny peut vous fournir un objet surchargé.

package Horse {
  use Moo;
  use Types::Standard qw( Str Num ArrayRef Bool );
  use namespace::autoclean;

  ...;  # name, gender, age, children, wins
  has is_alive => (
    is      => 'rw',
    isa     => Bool,
    coerce  => Bool->coercion,  # objet surchargé
  );
}

Si vous avez une version très ancienne de Moo, veuillez mettre à niveau vers au moins Moo 1.006000, qui était la version qui a ajouté le support pour "coerce => 1".
