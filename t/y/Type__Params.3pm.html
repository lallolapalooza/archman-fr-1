NOM

Type::Params - validation de signature de sous-routine à l'aide des contraintes et coercions de type Type::Tiny

SYNOPSIS

use v5.36;
use builtin qw( true false );

package Horse {
  use Moo;
  use Types::Standard qw( Object );
  use Type::Params -sigs;
  use namespace::autoclean;

  ...;   # définir les attributs, etc.

  signature_for add_child => (
    method     => true,
    positional => [ Object ],
  );

  sub add_child ( $self, $child ) {
    push $self->children->@*, $child;
    return $self;
  }
}

package main;

my $boldruler = Horse->new;

$boldruler->add_child( Horse->new );

$boldruler->add_child( 123 );   # meurt (123 n'est pas un Objet !)

STATUT

Ce module est couvert par la politique de stabilité de Type-Tiny.

DESCRIPTION

Ceci documente les détails du paquet Type::Params. Type::Tiny::Manual est un meilleur point de départ si vous débutez.

Type::Params utilise les contraintes de Type::Tiny pour valider les paramètres d'une sous-routine. Il adopte l'approche légèrement peu orthodoxe de séparer la validation en deux étapes :

1.
Compilation de la spécification du paramètre en un coderef ; puis
2.
Utilisation du coderef pour valider les paramètres.

La première étape est lente (elle peut prendre quelques millisecondes), mais elle ne doit être effectuée que la première fois que la sous-routine est appelée. La seconde étape est rapide ; selon mes benchmarks, plus rapide même que la version XS de Params::Validate.

Avec l'API moderne, vous devez rarement vous soucier des deux étapes qui sont séparées en interne.

Notez que la plupart des exemples dans cette documentation utilisent des fonctionnalités modernes de Perl telles que les signatures de sous-routines, le déréférencement postfixe et les mots-clés "true" et "false" de builtin. Sur Perl version 5.36+, vous pouvez activer toutes ces fonctionnalités en utilisant :

use v5.36;
use experimental 'builtin';
use builtin 'true', 'false';

Type::Params prend en charge les versions plus anciennes de Perl (jusqu'à 5.8), mais vous devrez peut-être ajuster la syntaxe de certains exemples.

API MODERNE

L'API moderne peut être exportée en utilisant :

use Type::Params -sigs;

Ou :

use Type::Params -v2;

Ou en demandant des fonctions par leur nom :

use Type::Params qw( signature signature_for );

Deux raccourcis optionnels peuvent être exportés :

use Type::Params qw( signature_for_func signature_for_method );

Ou :

use Type::Params -sigplus;

"signature_for $nom_de_fonction => ( %spéc )"

Enveloppe une fonction existante dans du code supplémentaire qui met en œuvre tous les aspects de la signature de la sous-routine, y compris le déballage des arguments de @_, l'application des valeurs par défaut, la coercition et la validation des valeurs.

"signature_for( \@fonctions, %opts )" est un raccourci utile si vous avez plusieurs fonctions avec la même signature.

signature_for [ 'add_nums', 'subtract_nums' ] => (
  positional => [ Num, Num ],
);

Bien qu'utilisée normalement dans un contexte vide, "signature_for" retourne une valeur.

my $meta = signature_for add_nums => (
  positional => [ Num, Num ],
);

sub add_nums ( $x, $y ) {
  return $x + $y;
}

Ou lorsqu'elle est utilisée avec plusieurs fonctions :

my @metas = signature_for [ 'add_nums', 'subtract_nums' ] => (...);

Il s'agit d'un objet Type::Params::Signature béni qui offre certaines possibilités d'introspection. Examiner "$meta->coderef->code" peut être utile pour voir ce que fait la signature en interne.

Options de spécification de signature

La spécification de signature est une hash qui doit contenir une clé "positional", "named" ou "multiple" indiquant si votre fonction accepte des paramètres positionnels, nommés ou prend en charge plusieurs conventions d'appel, mais peut également inclure d'autres options.

"positional" ArrayRef

Ceci est conceptuellement une liste de contraintes de type, une pour chaque paramètre positionnel. Par exemple, une signature pour une fonction qui accepte deux entiers :

signature_for myfunc => ( positional => [ Int, Int ] );

Cependant, chaque contrainte de type est facultativement suivie d'un hashref d'options qui affectent ce paramètre. Par exemple :

signature_for myfunc => ( positional => [
  Int, { default => 40 },
  Int, { default =>  2 },
] );

Les contraintes de type peuvent être données comme des chaînes de caractères, qui seront recherchées en utilisant "dwim_type" de Type::Utils.

signature_for myfunc => ( positional => [
  'Int', { default => 40 },
  'Int', { default =>  2 },
] );

Voir la section ci-dessous pour plus d'informations sur les options de paramètre.

Les paramètres facultatifs doivent suivre les paramètres requis, et peuvent être spécifiés en utilisant soit la contrainte de type paramétrable Optional, l'option de paramètre "optional", soit en fournissant une valeur par défaut.

# Les trois paramètres sont effectivement facultatifs.
signature_for myfunc => ( positional => [
  Optional[Int],
  Int, { optional => true },
  Int, { default  => 42 },
] );

Un seul paramètre glouton peut être fourni à la fin, en utilisant la contrainte de type paramétrable Slurpy, ou l'option de paramètre "slurpy" :

signature_for myfunc => ( positional => [
  Int,
  Slurpy[ ArrayRef[Int] ],
] );
signature_for myfunc => ( positional => [
  Int,
  ArrayRef[Int], { slurpy => true },
] );

L'option "positional" peut également être abrégée en "pos".

Donc, "signature_for myfunc => ( pos => [...] )" peut être utilisé à la place de la plus longue "signature_for myfunc => ( positional => [...] )".

signature_for add_numbers => ( pos => [ Num, Num ] );

sub add_numbers ( $num1, $num2 ) {
  return $num1 + $num2;
}

say add_numbers( 2, 3 );   # dit 5

"named" ArrayRef

Ceci est conceptuellement une liste de paires de noms et de contraintes de type, une paire nom+type pour chaque paramètre nommé. Par exemple, une signature pour une fonction qui accepte deux entiers :

signature_for myfunc => ( named => [ foo => Int, bar => Int ] )

Cependant, chaque contrainte de type est facultativement suivie d'un hashref d'options qui affectent ce paramètre. Par exemple :

signature_for myfunc => ( named => [
  foo => Int, { default => 40 },
  bar => Int, { default =>  2 },
] );

Les contraintes de type peuvent être données comme des chaînes de caractères, qui seront recherchées en utilisant "dwim_type" de Type::Utils.

signature_for myfunc => ( named => [
  foo => 'Int', { default => 40 },
  bar => 'Int', { default =>  2 },
] );

Les paramètres facultatifs et gloutons sont autorisés, mais contrairement aux paramètres positionnels, ils ne doivent pas être à la fin.

Voir la section ci-dessous pour plus d'informations sur les options de paramètre.

Si une signature utilise des paramètres nommés, les valeurs sont fournies à la fonction sous forme d'un seul objet paramètre :

signature_for add_numbers => ( named => [ num1 => Num, num2 => Num ] );

sub add_numbers ( $arg ) {
  return $arg->num1 + $arg->num2;
}

say add_numbers(   num1 => 2, num2 => 3   );   # dit 5
say add_numbers( { num1 => 2, num2 => 3 } );   # dit aussi 5

"named_to_list" ArrayRef|Bool

L'option "named_to_list" est ignorée pour les signatures utilisant des paramètres positionnels, mais pour les signatures utilisant des paramètres nommés, elle permet de les fournir à la fonction sous forme de liste de valeurs au lieu d'un seul objet :

signature_for add_numbers => (
  named         => [ num1 => Num, num2 => Num ],
  named_to_list => true,
);

sub add_numbers ( $num1, $num2 ) {
  return $num1 + $num2;
}

say add_numbers(   num1 => 2, num2 => 3   );   # dit 5

Vous pouvez considérer "add_numbers" ci-dessus comme une fonction qui accepte des paramètres nommés de l'extérieur, mais qui reçoit des paramètres positionnels de l'intérieur.

Vous pouvez utiliser une référence de tableau pour contrôler l'ordre dans lequel les paramètres seront fournis. (Par défaut, ils sont retournés dans l'ordre dans lequel ils ont été définis.)

signature_for add_numbers => (
  named         => [ num1 => Num, num2 => Num ],
  named_to_list => [ qw( num2 num1 ) ],
);

sub add_numbers ( $num2, $num1 ) {
  return $num1 + $num2;
}

say add_numbers(   num1 => 2, num2 => 3   );   # dit 5
say add_numbers( { num1 => 2, num2 => 3 } );   # dit aussi 5

"list_to_named" Bool

Pour une fonction qui accepte des paramètres nommés, permet de les fournir alternativement sous forme de liste d'une manière « fais-ce-que-tu-veux ».

signature_for add_numbers => (
  named         => [ num1 => Num, num2 => Num ],
  list_to_named => true,
);

sub add_numbers ( $arg ) {
  return $arg->num1 + $arg->num2;
}

say add_numbers( num1 => 5, num2 => 10 );      # dit 15
say add_numbers( { num1 => 5, num2 => 10 } );  # dit aussi 15
say add_numbers( 5, num2 => 10 );              # dit encore 15
say add_numbers( 5, { num2 => 10 } );          # devinez quoi ? dit 15
say add_numbers( 10, num1 => 5 );              # 14. je plaisante ! 15
say add_numbers( 10, { num1 => 5 } );          # encore un 15
say add_numbers( 5, 10 );                      # surprise, dit 15

# MAUVAIS : l'argument list_to_named ne peut pas être à la fin.
say add_numbers( { num1 => 5 }, 10 );

# MAUVAIS : l'argument list_to_named est dupliqué.
say add_numbers( 5, 10, { num1 => 5 } );

Là où une référence de hachage ou un hachage de paramètres nommés est attendu, tout paramètre qui ne semble pas correspondre à ce modèle sera traité comme un paramètre positionnel « furtif », et sera essayé la première fois qu'un paramètre nommé semble manquer.

Cette fonctionnalité est normalement appliquée uniquement aux paramètres requis. Elle peut être contrôlée manuellement paramètre par paramètre à l'aide de l'option "in_list".

Type::Params tente d'être intelligent pour déterminer dans quel ordre les paramètres positionnels furtifs ont été donnés.

signature_for add_to_ref => (
  named         => [ ref => ScalarRef[Num], add => Num ],
  list_to_named => true,
);

sub add_to_ref ( $arg ) {
  $arg->ref->$* += $arg->num;
}

my $sum = 0;
add_to_ref( ref => \$sum, add => 1 );
add_to_ref( \$sum, add => 2 );
add_to_ref( \$sum, 3 );
add_to_ref( 4, \$sum );
add_to_ref( 5, sum => \$sum );
add_to_ref( add => 5, sum => \$sum );
say $sum; # 21

Cette approche est quelque peu plus lente, mais elle a le potentiel de fonctions très « fais-ce-que-tu-veux ».

Notez que "list_to_named" et "named_to_list" peuvent tous deux être utilisés dans la même signature car leurs significations ne sont pas contradictoires.

signature_for add_to_ref => (
  named         => [ ref => ScalarRef[Num], add => Num ],
  list_to_named => true,
  named_to_list => true,
);

sub add_to_ref ( $ref, $num ) {
  $ref->$* += $num;
}

"head" Int|ArrayRef

"head" fournit une liste supplémentaire de paramètres positionnels non optionnels au début de @_. Ceci est souvent utilisé pour les appels de méthodes. Par exemple, si vous souhaitez définir une signature pour :

$object->my_method( foo => 123, bar => 456 );

Vous pourriez l'écrire ainsi :

signature_for my_method => (
  head    => [ Object ],
  named   => [ foo => Optional[Int], bar => Optional[Int] ],
);

sub my_method ( $self, $arg ) {
  ...;
}

Si "head" est défini comme un nombre au lieu d'une référence de tableau, c'est le nombre d'arguments supplémentaires au début :

signature_for stash_foobar = (
  head    => 2,
  named   => [ foo => Optional[Int], bar => Optional[Int] ],
);

sub stash_foobar ( $self, $ctx, $arg ) {
  $ctx->stash->{foo} = $arg->foo if $arg->has_foo;
  $ctx->stash->{bar} = $arg->bar if $arg->has_bar;
  return $self;
}

...;

$app->stash_foobar( $context, foo => 123 );

Dans ce cas, aucune vérification de type n'est effectuée sur ces arguments supplémentaires ; seule la présence de ces arguments est vérifiée.

"tail" Int|ArrayRef

Une "tail" est comme une "head" sauf qu'elle concerne les arguments à la *fin* de @_.

signature_for my_method => (
  head    => [ Object ],
  named   => [ foo => Optional[Int], bar => Optional[Int] ],
  tail    => [ CodeRef ],
);

sub my_method ( $self, $arg, $callback ) {
  ...;
}

$object->my_method( foo => 123, bar => 456, sub { ... } );

"method" Bool|TypeTiny

Bien que "head" puisse être utilisé pour les signatures de méthodes, une manière plus déclarative est de définir "method => true".

Si vous souhaitez spécifier qu'il s'agit d'une méthode d'objet, destinée à être appelée uniquement sur des objets bénis, vous pouvez utiliser "method => Object", en utilisant le type Object de Types::Standard. Si vous souhaitez spécifier qu'il s'agit d'une méthode de classe, utilisez alors "method => Str", en utilisant le type Str de Types::Standard. ("method => ClassName" est peut-être plus clair, mais c'est une vérification plus lente.)

signature_for my_method => (
  method  => true,
  named   => [ foo => Optional[Int], bar => Optional[Int] ],
);

sub my_method ( $self, $arg ) {
  ...;
}

L'option "method" a quelques autres différences subtiles avec "head". Tous les paramètres par défaut qui sont des références de code seront appelés comme des méthodes sur l'invocant au lieu d'être appelés sans arguments. L'option "package" sera interprétée légèrement différemment.

Il est possible d'utiliser à la fois "method" et "head" dans la même signature. L'invocant est interprété comme étant *avant* la "head".

Un raccourci est fourni pour "method => true", bien qu'il active également quelques autres options.

use Type::Params qw( signature_for_method );

signature_for_method my_method => (
  named => [ foo => Optional[Int], bar => Optional[Int] ],
);

sub my_method ( $self, $arg ) {
  ...;
}

"description" Str

C'est la description de la référence de code qui apparaîtra dans les traces de pile. Par défaut, c'est « validation des paramètres pour X », où X est le nom de la sous-routine. Généralement, la valeur par défaut convient.

"package" Str

Ceci vous permet d'ajouter des signatures à des fonctions dans d'autres packages :

signature_for foo => ( package "Some::Package", ... );

Si "method" est vrai et que Some::Package ne contient pas de sous-routine nommée « foo », alors Type::Params parcourra la hiérarchie d'héritage, à la recherche de « foo ».

Si des contraintes de type sont spécifiées sous forme de chaînes, Type::Params recherchera les types importés par ce package.

# Attend que le type MyInt soit connu par Some::Package.
signature_for foo => ( package "Some::Package", pos => [ 'MyInt' ] );

Ceci est également supporté :

signature_for "Some::Package::foo" => ( ... );

"fallback" CodeRef|Bool

Si la sous-routine enveloppée ne peut pas être trouvée, alors "signature_for" générera généralement une erreur. Si vous voulez qu'elle « fonctionne quand même » dans cette situation, utilisez l'option "fallback". "fallback => \&alternative_coderef_to_wrap" enveloppera plutôt une autre référence de code si l'originale ne peut pas être trouvée. "fallback => true" est un raccourci pour "fallback => sub {}". Un exemple où cela pourrait être utile est si vous ajoutez des signatures à des méthodes héritées d'une classe parente, mais que vous n'êtes pas sûr à 100 % qu'elles existeront (peut-être en fonction de la version de la classe parente).

signature_for add_nums => (
  positional => [ Num, Num ],
  fallback   => sub { $_[0] + $_[1] },
);

"on_die" Maybe[CodeRef]

Habituellement, lorsque la vérification de la signature rencontre une erreur, elle lance une exception, qui est un objet Error::TypeTiny béni.

Si vous fournissez une référence de code "on_die", alors l'objet Error::TypeTiny lui sera passé à la place.

signature_for add_numbers => (
  positional => [ Num, Num ],
  on_die     => sub {
    my $error = shift;
    print "Crise existentielle : $error\n";
    exit( 1 );
  },
);

sub add_numbers ( $num1, $num2 ) {
  return $num1 + $num2;
}

say add_numbers();   # a une crise existentielle

Si votre référence de code "on_die" ne sort pas ou ne lance pas d'exception, elle peut plutôt retourner une liste qui sera utilisée comme paramètres pour votre fonction.

signature_for add_numbers => (
  positional => [ Num, Num ],
  on_die     => sub { return ( 40, 2 ) },
);

sub add_numbers ( $num1, $num2 ) {
  return $num1 + $num2;
}

say add_numbers();   # 42

Ce n'est probablement pas très utile.

"strictness" Bool|Str

Si vous définissez "strictness" sur faux, alors certaines vérifications de signature ne seront tout simplement jamais effectuées. La vérification initiale du nombre correct de paramètres, ainsi que les vérifications de type sur les paramètres qui ne se coerceront pas, peuvent être ignorées.

Si vous la définissez sur vrai ou si vous ne la définissez pas du tout, alors ces vérifications seront toujours effectuées.

Alternativement, elle peut être définie sur le nom entièrement qualifié entre guillemets d'une variable globale Perl ou d'une constante, et cela sera compilé dans la référence de code comme une condition pour activer les vérifications strictes.

signature_for my_func => (
  strictness => '$::CHECK_TYPES',
  positional => [ Int, ArrayRef ],
);

sub my_func ( $int, $aref ) {
  ...;
}

# Les vérifications de type sont ignorées
{
  local $::CHECK_TYPES = false;
  my ( $number, $list ) = my_func( {}, {} );
}

# Les vérifications de type sont effectuées
{
  local $::CHECK_TYPES = true;
  my ( $number, $list ) = my_func( {}, {} );
}

Une utilisation recommandée de "strictness" est avec Devel::StrictMode.

use Devel::Stri
ctMode qw( STRICT );

state $signature = signature(
  strictness => STRICT,
  positional => [ Int, ArrayRef ],
);
```

"multiple"
    ArrayRef|HashRef


Cette option permet à votre signature de prendre en charge plusieurs conventions d'appel. Chaque entrée du tableau est une signature alternative, sous forme de hashref :


signature_for my_func => (
  multiple => [
    {
      positional    => [ ArrayRef, Int ],
    },
    {
      named         => [ array => ArrayRef, index => Int ],
      named_to_list => true,
    },
  ],
);

sub my_func ( $aref, $int ) {
  ...;
}


Cette signature permettra à votre fonction d'être appelée comme suit :


your_function( $arr, $ix );
your_function( array => $arr, index => $ix );
your_function( { array => $arr, index => $ix } );


Parfois, les alternatives renverront les paramètres dans des ordres différents :


signature_for my_func => (
  multiple => [
    { positional => [ ArrayRef, Int ] },
    { positional => [ Int, ArrayRef ] },
  ],
);


Alors, comment votre sub sait-elle comment elle a été appelée ? Une option consiste à utiliser la variable globale "${^_TYPE_PARAMS_MULTISIG}" qui sera définie sur l'index de la signature utilisée :


sub my_func {
  my ( $arr, $ix ) = ${^_TYPE_PARAMS_MULTISIG} == 1 ? reverse( @_ ) : @_;
  ...;
}


Si vous préférez utiliser des noms identificateurs au lieu d'un index numérique, vous pouvez les spécifier en utilisant "ID" :


signature_for my_func => (
  multiple => [
    { ID => 'one', positional => [ ArrayRef, Int ] },
    { ID => 'two', positional => [ Int, ArrayRef ] },
  ],
);


Ou en utilisant un hashref :


signature_for my_func => (
  multiple => {
    one => { positional => [ ArrayRef, Int ] },
    two => { positional => [ Int, ArrayRef ] },
  },
);


Une solution plus élégante consiste à utiliser une reference de code "next" pour réorganiser les résultats de la signature alternative dans l'ordre souhaité :


signature_for my_func => (
  multiple => [
    { positional => [ ArrayRef, Int ] },
    { positional => [ Int, ArrayRef ], next => sub { reverse @_ } },
  ],
);

sub my_func ( $arr, $ix ) {
  ...;
}


Bien que conceptuellement "multiple" soit une reference de tableau de hashrefs, il est également possible d'utiliser des references de tableau dans la reference de tableau.


multiple => [
  [ ArrayRef, Int ],
  [ Int, ArrayRef ],
]


Lorsque une reference de tableau est utilisée ainsi, c'est un raccourci pour une signature positionnelle.


Les references de code peuvent également être utilisées :


signature_for my_func => (
  multiple => [
    [ ArrayRef, Int ],
    { positional => [ Int, ArrayRef ], next => sub { reverse @_ } },
    sub { ... },
    sub { ... },
  ],
);


Les references de code doivent être des subs qui renvoient une liste de paramètres en cas de succès et lèvent une exception en cas d'échec.


Les signatures suivantes sont équivalentes :


signature_for my_func => (
  multiple => [
    { method => true, positional => [ ArrayRef, Int ] },
    { method => true, positional => [ Int, ArrayRef ] },
  ],
);

signature_for my_func => (
  method   => true,
  multiple => [
    { positional => [ ArrayRef, Int ] },
    { positional => [ Int, ArrayRef ] },
  ],
);


L'option "multiple" peut également être abrégée en "multi". Ainsi, "signature( multi => [...] )" peut être utilisé à la place de la plus longue "signature( multiple => [...] )". Trois frappes entières sauvées !


(Note : dans les anciennes versions de Type::Params, "${^_TYPE_PARAMS_MULTISIG}" s'appelait "${^TYPE_PARAMS_MULTISIG}". Ce dernier nom n'est plus supporté.)


"message" Str


Utilisé uniquement par les signatures "multiple". Le message d'erreur à lancer lorsqu'aucune signature ne correspond.


"bless" Bool|ClassName,
    "class" ClassName|ArrayRef, et
    "constructor" Str


Les paramètres nommés sont généralement retournés sous forme d'objet "blessed" :


signature_for add_numbers => ( named => [ num1 => Num, num2 => Num ] );

sub add_numbers ( $arg ) {
  return $arg->num1 + $arg->num2;
}


La classe dans laquelle ils sont "blessed" est construite à la volée par Type::Params. Cependant, ces trois options de signature vous donnent plus de contrôle sur ce processus.


Premièrement, si vous définissez "bless => false" et ne définissez pas "class" ou "constructor", alors $arg sera simplement un hashref non "blessed".


signature_for add_numbers => (
  named        => [ num1 => Num, num2 => Num ],
  bless        => false,
);

sub add_numbers ( $arg ) {
  return $arg->{num1} + $arg->{num2};
}


C'est un bon gain de vitesse, mais avoir des méthodes appropriées pour chaque paramètre nommé est un moyen utile de détecter les noms mal orthographiés.


Si vous souhaitez créer manuellement une classe au lieu de vous fier à Type::Params qui en génère une à la volée, vous pouvez le faire :


package Params::For::AddNumbers {
  sub num1 ( $self ) {
    return $self->{num1};
  }
  sub num2 ( $self ) {
    return $self->{num2};
  }
  sub sum ( $self ) {
    return $self->num1 + $self->num2;
  }
}

signature_for add_numbers => (
  named        => [ num1 => Num, num2 => Num ],
  bless        => 'Params::For::AddNumbers',
);

sub add_numbers ( $arg ) {
  return $arg->sum;
}


Notez que "Params::For::AddNumbers" ici n'inclut pas de méthode "new" car Type::Params appellera directement "bless( $arg, $opts{bless} )".


Si vous souhaitez que Type::Params utilise un constructeur approprié, vous devriez utiliser l'option "class" à la place :


package Params::For::AddNumbers {
  use Moo;
  has [ 'num1', 'num2' ] => ( is => 'ro' );
  sub sum {
    my $self = shift;
    return $self->num1 + $self->num2;
  }
}

signature_for add_numbers => (
  named        => [ num1 => Num, num2 => Num ],
  class        => 'Params::For::AddNumbers',
);

sub add_numbers ( $arg ) {
  return $arg->sum;
}


Si vous souhaitez utiliser un constructeur nommé différemment de "new", utilisez alors :


signature_for add_numbers => (
  named        => [ num1 => Num, num2 => Num ],
  class        => 'Params::For::AddNumbers',
  constructor  => 'new_from_hashref',
);


Ou comme raccourci :


signature_for add_numbers => (
  named        => [ num1 => Num, num2 => Num ],
  class        => [ 'Params::For::AddNumbers' => 'new_from_hashref' ],
);


Il est peu probable que vous souhaitiez utiliser l'une de ces options, à l'exception de "bless => false".


"returns" TypeTiny,
    "returns_scalar" TypeTiny, et
    "returns_list" TypeTiny


Celles-ci peuvent être utilisées pour spécifier le type retourné par votre fonction.


signature_for round_number => (
  pos          => [ Num ],
  returns      => Int,
);

sub round_number ( $num ) {
  return int( $num );
}


Si votre fonction renvoie différents types en contexte scalaire et liste, vous pouvez utiliser "returns_scalar" et "returns_list" pour indiquer des types de retour séparés dans des contextes différents.


signature_for my_func => (
  pos             => [ Int, Int ],
  returns_scalar  => Int,
  returns_list    => Tuple[ Int, Int, Int ],
);


La contrainte "returns_list" est définie en utilisant une contrainte de type de type ArrayRef ou HashRef, même si elle renvoie une liste et non une seule référence.


Si votre fonction est appelée dans un contexte vide (void), alors sa valeur de retour n'a pas d'importance et ne doit pas être vérifiée par type.


"allow_dash" Bool


Pour tous les paramètres nommés ou alias de type "mot", crée automatiquement un alias avec un tiret préfixé.


signature_for withdraw_funds => (
  named      => [ amount => Num, account => Str ],
  allow_dash => true,
);

sub withdraw_funds ( $arg ) {
  ...;
}

withdraw_funds(  amount => 11.99,  account => 'ABC123' );
withdraw_funds( -amount => 11.99,  account => 'ABC123' );
withdraw_funds(  amount => 11.99, -account => 'ABC123' );
withdraw_funds( -amount => 11.99, -account => 'ABC123' );


N'a aucun effet sur les noms qui ne sont pas de type "mot". Les noms de type "mot" sont ceux qui correspondent à "/\A[^\W0-9]\w*\z/" ; essentiellement tout ce que Perl autorise comme nom de variable normal non qualifié.


Options de paramètres


Dans les listes de paramètres pour les options de signature
    "positional" et
    "named", chaque paramètre peut être suivi d'un hashref d'options spécifiques à ce paramètre :


signature_for my_func => (
  positional => [
    Int, \%options_for_first_parameter,
    Int, \%options_for_other_parameter,
  ],
  %more_options_for_signature,
);
signature_for my_func => (
  named => [
    foo => Int, \%options_for_foo,
    bar => Int, \%options_for_bar,
  ],
  %more_options_for_signature,
);


Les options suivantes sont supportées pour les paramètres.


"optional" Bool


Une option *appelée* optionnel !


Cela rend un paramètre optionnel :


signature_for add_nums => (
  positional => [
    Int,
    Int,
    Bool, { optional => true },
  ],
);

sub add_nums ( $num1, $num2, $debug ) {
  my $sum = $num1 + $num2;
  warn "$sum = $num1 + $num2" if $debug;
  return $sum;
}

add_nums( 2, 3, 1 );   # affiche un avertissement
add_nums( 2, 3, 0 );   # pas d'avertissement
add_nums( 2, 3    );   # pas d'avertissement


Types::Standard fournit également un type paramétrable Optional qui pourrait être une manière plus élégante de faire cela :


signature_for add_nums => ( pos => [ Int, Int, Optional[Bool] ] );


Dans les signatures avec des paramètres positionnels, tous les paramètres optionnels doivent être définis *après* les paramètres non optionnels. L'option "tail" fournit une solution de contournement pour les paramètres requis à la fin de @_.


Dans les signatures avec des paramètres nommés, l'ordre des paramètres optionnels et non optionnels n'a pas d'importance.


"slurpy" Bool


Une signature peut contenir un seul paramètre slurpy, qui regroupe tous lesarguments que l'appelant fournit à votre fonction.


Dans les signatures avec des paramètres positionnels, les paramètres
    "slurpy" doivent toujours avoir une contrainte de type ArrayRef ou
    HashRef, doivent toujours apparaître à la fin de la liste des
    paramètres positionnels, et fonctionnent comme suit :


signature_for add_nums => (
  positional => [
    Num,
    ArrayRef[Num], { slurpy => true },
  ],
);

sub add_nums ( $first_num, $other_nums ) {
  my $sum = $first_num;
  for my $other ( $other_nums->@* ) {
    $sum += $other;
  }
  return $sum;
}

say add_nums( 1 );            # dit 1
say add_nums( 1, 2 );         # dit 3
say add_nums( 1, 2, 3 );      # dit 6
say add_nums( 1, 2, 3, 4 );   # dit 10


Dans les signatures avec des paramètres nommés, les paramètres
    "slurpy" doivent toujours avoir une contrainte de type HashRef et
    fonctionnent comme suit :


use builtin qw( true false );

signature_for process_data => (
  method => true,
  named  => [
    input   => FileHandle,
    output  => FileHandle,
    flags   => HashRef[Bool], { slurpy => true },
  ],
);

sub process_data ( $self, $arg ) {
  warn "Début du traitement des données" if $arg->flags->{debug};
  ...;
}

$widget->process_data(
  input  => \*STDIN,
  output => \*STDOUT,
  debug  => true,
);


La contrainte de type Slurpy de Types::Standard peut être
    utilisée comme raccourci pour spécifier les paramètres "slurpy" :


signature_for add_nums => (
  positional => [ Num, Slurpy[ ArrayRef[Num] ] ],
)


Le type Slurpy[Any] est traité spécialement et considéré comme
    un ArrayRef "slurpy" dans les signatures avec des paramètres
    positionnels, et un HashRef "slurpy" dans les signatures avec des
    paramètres nommés, mais bénéficie d'optimisations supplémentaires pour la
    vitesse.


"default"
    CodeRef|ScalarRef|Ref|Str|Undef


Une valeur par défaut peut être fournie pour un paramètre.


signature_for my_func => (
  positional => [
    Int,
    Int, { default => "666" },
    Int, { default => "999" },
  ],
);


Les valeurs par défaut prises en charge sont toutes les chaînes de
    caractères (y compris numériques), "undef",
    et les hashrefs et arrayrefs vides. Les hashrefs et arrayrefs non vides ne
    sont pas autorisés comme valeurs par défaut.


Alternativement, vous pouvez fournir un coderef pour générer une valeur
    par défaut :


signature_for my_func => (
  positional => [
    Int,
    Int, { default => sub { 6 * 111 } },
    Int, { default => sub { 9 * 111 } },
  ]
);


Ce coderef peut générer n'importe quelle valeur, y compris des
    arrayrefs non vides et des hashrefs non vides. Pour undef, les chaînes de
    caractères simples, les nombres et les structures vides, éviter d'utiliser
    un coderef rendra le traitement de votre paramètre plus rapide.


Au lieu d'un coderef, vous pouvez utiliser une référence à une chaîne de
    code source Perl :


signature_for my_func => (
  positional => [
    Int,
    Int, { default => \ '6 * 111' },
    Int, { default => \ '9 * 111' },
  ],
);


Les valeurs par défaut seront validées par rapport à la
    contrainte de type, et potentiellement coercées.


Tout paramètre avec une valeur par défaut sera automatiquement optionnel,
    car il n'est pas logique de fournir une valeur par défaut pour des paramètres
    requis.


Notez que la présence de quelconque valeur par défaut dans une
    signature (même si elle n'est jamais utilisée) peut la ralentir, car
    Type::Params devra construire un nouveau tableau au lieu de simplement
    retourner @_.


"default_on_undef"
    Bool


Normalement, les valeurs par défaut ne sont appliquées que lorsqu'un
    paramètre est manquant (pensez à "exists"
    pour les hashes ou si le tableau est trop court). Définir
    "default_on_undef" sur true déclenchera
    également la valeur par défaut si un paramètre est fourni mais indéfini.


Si l'appelant souhaite légitimement fournir undef comme valeur, il n'est
    pas recommandé d'utiliser cette option.


"coerce" Bool


En parlant de coercition, l'option "coerce"
    vous permet d'indiquer qu'une valeur doit être forcée dans le bon type :


signature_for my_func => (
  positional => [
    Int,
    Int,
    Bool, { coerce => true },
  ],
);


Définir "coerce" sur false désactivera la
    coercition.


Si "coerce" n'est pas spécifié, donc
    n'est ni vrai ni faux, alors la coercition sera activée si la contrainte de
    type a une coercition, et désactivée sinon.


Notez que la présence de quelconque coercition dans une signature
    (même si elle n'est jamais utilisée) peut la ralentir, car Type::Params devra
    construire un nouveau tableau au lieu de simplement retourner @_.


"clone" Bool


Si ceci est défini sur true, il clonera en profondeur les valeurs
    entrantes via "dclone" de Storable (un module
    de base depuis Perl 5.7.3).


Dans l'exemple ci-dessous, $arr est une référence
    vers un clone de @numbers, donc pousser des nombres
    supplémentaires dedans laisse @numbers inchangé.


signature_for foo => (
  positional => [ ArrayRef, { clone => true } ],
);

sub foo ( $arr ) {
  push @$arr, 4, 5, 6;
}

my @numbers = ( 1, 2, 3 );
foo( \@numbers );
print "@numbers\n";  ## 1 2 3


Notez que le clonage ralentira considérablement votre signature.


"name" Str


Ceci remplace le nom d'un paramètre nommé. Je ne sais pas pourquoi vous
    voudriez faire cela.


La signature suivante a deux paramètres : "foo"
    et "bar". Le nom "fool"
    est complètement ignoré.


signature_for my_func => (
  named => [
    fool   => Int, { name => 'foo' },
    bar    => Int,
  ],
);


Vous pouvez cependant également nommer des paramètres positionnels, qui
    n'ont généralement pas de nom.


signature_for my_func => (
  positional => [
    Int, { name => 'foo' },
    Int, { name => 'bar' },
  ],
);


Les noms des paramètres positionnels ne sont pas réellement utilisés
    pour quoi que ce soit pour le moment, mais pourraient être intégrés dans les
    messages d'erreur ou similaires à l'avenir.


"getter" Str


Pour les signatures avec des paramètres nommés, spécifie le nom de la
    méthode utilisée pour récupérer la valeur de ce paramètre depuis l'objet
    $arg.


signature_for process_data => (
  method => true,
  named  => [
    input   => FileHandle,    { getter => 'in' },
    output  => FileHandle,    { getter => 'out' },
    flags   => HashRef[Bool], { slurpy => true },
  ],
);

sub process_data ( $self, $arg ) {
  warn "Début du traitement des données" if $arg->flags->{debug};

  my ( $in, $out ) = ( $arg->in, $arg->out );
  ...;
}

$widget->process_data(
  input  => \*STDIN,
  output => \*STDOUT,
  debug  => true,
);


Ignoré par les signatures avec des paramètres positionnels.


"predicate" Str


L'objet $arg fourni par les signatures avec des
    paramètres nommés inclura également des méthodes "has" pour tous les
    arguments optionnels. Par exemple :


signature_for process_data => (
  method => true,
  named  => [
    input   => Optional[ FileHandle ],
    output  => Optional[ FileHandle ],
    flags   => Slurpy[ HashRef[Bool] ],
  ],
);

sub process_data ( $self, $arg ) {

  if ( $self->has_input and $self->has_output ) {
    ...;
  }

  ...;
}


La définition d'une option "predicate"
    vous permet de choisir un nom différent pour cette méthode au lieu de
    "has_*".


Il est également possible de définir un
    "predicate" pour les paramètres non optionnels,
    qui n'ont normalement pas de méthode "has".


Ignoré par les signatures avec des paramètres positionnels.


"alias"
    Str|ArrayRef[Str]


Une liste de noms alternatifs pour le paramètre, ou un seul nom
    alternatif.


signature_for add_numbers => (
  named => [
    first_number   => Int, { alias => [ 'x' ] },
    second_number  => Int, { alias =>   'y'   },
  ],
);

sub add_numbers ( $arg ) {
  return $arg->first_number + $arg->second_number;
}

say add_numbers( first_number => 40, second_number => 2 );  # 42
say add_numbers( x            => 40, y             => 2 );  # 42
say add_numbers( first_number => 40, y             => 2 );  # 42
say add_numbers( first_number => 40, x => 1, y => 2 );      # meurt !


Ignoré par les signatures avec des paramètres positionnels.


"in_list" Bool


En conjonction avec "list_to_named",
    détermine si ce paramètre peut être fourni comme faisant partie de la liste
    des paramètres positionnels "furtifs". Si
    "list_to_named" n'est pas utilisé,
    "in_list" est ignoré.


Par défaut à false si le paramètre est optionnel ou a une valeur par
    défaut. Par défaut à true si le paramètre est requis.


"strictness" Bool|Str


Remplace l'option de signature "strictness"
    sur une base par paramètre.





"signature_for_func   $function_name => ( %spec )"


Comme "signature_for" et vaut par
    défaut "method => false".


Si la signature a des paramètres nommés, elle utilisera par défaut
    "list_to_named" et
    "allow_dash" à true.


signature_for_func add_to_ref => (
  named         => [ ref => ScalarRef[Num], add => Num ],
  named_to_list => true,
);

sub add_to_ref ( $ref, $add ) {
  $ref->$* += $add;
}

my $sum = 0;
add_to_ref( ref => \$sum, add => 1 );
add_to_ref( \$sum, 2 );
add_to_ref( 3, \$sum );
add_to_ref( 4, { -ref => \$sum } );
say $sum; # 10


Le comportement exact de "signature_for_func"
    est instable et peut changer dans les futures versions de Type::Params.






"signature_for_method   $function_name => ( %spec )"


Comme "signature_for" mais vaut par
    défaut &qu
ot;méthode => vrai".


Si la signature a des paramètres nommés, elle mettra également
    par défaut "list_to_named" et
    "allow_dash" à vrai.


package Calculateur {
  use Types::Standard qw( Num ScalarRef );
  use Type::Params qw( signature_for_method );

  ...;

  signature_for_method add_to_ref => (
    named         => [ ref => ScalarRef[Num], add => Num ],
    named_to_list => vrai,
  );

  sub add_to_ref ( $self, $ref, $add ) {
    $ref->$* += $add;
  }
}

my $calc = Calculateur->new;
my $sum = 0;
$calc->add_to_ref( ref => \$sum, add => 1 );
$calc->add_to_ref( \$sum, 2 );
$calc->add_to_ref( 3, \$sum );
$calc->add_to_ref( 4, { -ref => \$sum } );
say $sum; # 10


Le comportement exact de
    "signature_for_method" est instable et peut
    changer dans les futures versions de Type::Params.






signature(   %spec )


La fonction "signature" permet
    un contrôle plus précis des signatures. Au lieu d'envelopper automatiquement
    votre fonction, elle retourne un coderef auquel vous pouvez passer
    @_.


Ce qui suit est à peu près équivalent :


signature_for add_nums => ( pos => [ Num, Num ] );

sub add_nums ( $x, $y ) {
  return $x + $y;
}


Et :


sub add_nums {
  state $signature = signature( pos => [ Num, Num ] );
  my ( $x, $y ) = $signature->( @_ );

  return $x + $y;
}


Perl autorise une manière légèrement archaïque d'appeler des
    coderefs sans utiliser de parenthèses, ce qui peut être légèrement plus
    rapide au détriment d'être plus obscur :


sub add_nums {
  state $signature = signature( pos => [ Num, Num ] );
  my ( $x, $y ) = &$signature; # important : pas de parenthèses !

  return $x + $y;
}


Si vous avez besoin de supporter Perl 5.8, qui n'avait pas le mot-clé
    "state" :


my $__add_nums_sig;
sub add_nums {
  $__add_nums_sig ||= signature( pos => [ Num, Num ] );
  my ( $x, $y ) = &$__add_nums_sig;

  ...;
}


Cela vous donne plus de contrôle sur comment et quand la signature
    est construite et utilisée, et ce qui est fait des valeurs qu'elle dépaquette.


En particulier, notez que si votre fonction n'est jamais appelée,
    la signature n'est même jamais construite, ce qui signifie que pour les
    fonctions que vous utilisez rarement, le coût d'avoir la signature est
    moindre.


À partir de 2025, vous voudrez probablement utiliser
    "signature_for" plutôt que
    "signature" dans la plupart des cas.


Options de spécification de signature supplémentaires


Il existe certaines options qui n'ont aucun sens pour
    "signature_for", et ne sont utiles que pour
    "signature". D'autres peuvent se comporter
    légèrement différemment. Elles sont notées ici.


"returns" TypeTiny,
    "returns_scalar" TypeTiny, et
    "returns_list" TypeTiny


Parce que "signature" n'est pas
    capable d'envelopper complètement votre fonction, les options
    "returns",
    "returns_scalar" et
    "returns_list" ne peuvent rien faire. Vous
    devriez les considérer comme étant uniquement de la documentation.


"subname" Str


Le nom de la sous-routine dont nous sommes censés vérifier les
    paramètres. Ceci est utile dans les traces de pile, etc. Par défaut, c'est
    l'appelant.


"package" Str


Fonctionne de la même manière qu'en
    "signature_for", mais il vaut la peine de le
    mentionner à nouveau car il est étroitement lié à
    "subname".


"caller_level" Int


Si vous enveloppez "signature"
    pour pouvoir vérifier les signatures pour le compte d'un autre package, alors
    définir "caller_level" à 1 (ou plus, selon
    le niveau d'enveloppement !) peut être une alternative à la définition manuelle
    de "package" et
    "subname".


"next" Bool|CodeLike


Ceci peut être utilisé pour chaîner des coderefs. Si vous comprenez
    "on_die", cela agit comme un
    "on_live".


sub add_numbers {
  state $sig = signature(
    positional => [ Num, Num ],
    next => sub {
      my ( $num1, $num2 ) = @_;

      return $num1 + $num2;
    },
  );

  my $sum = $sig->( @_ );
  return $sum;
}

say add_numbers( 2, 3 );   # dit 5


S'il est défini à vrai au lieu d'un coderef, a un comportement légèrement
    différent :


sub add_numbers {
  state $sig = signature(
    positional => [ Num, Num ],
    next       => vrai,
  );

  my $sum = $sig->(
    sub { return $_[0] + $_[1] },
    @_,
  );
  return $sum;
}

say add_numbers( 2, 3 );   # dit 5


Cela semble étrange. Pourquoi serait-ce utile ? Eh bien, cela fonctionne
    bien avec le mot-clé "around" de Moose.


sub add_numbers {
  return $_[1] + $_[2];
}

around add_numbers => signature(
  method     => vrai,
  positional => [ Num, Num ],
  next       => vrai,
  package    => __PACKAGE__,
  subname    => 'add_numbers',
);

say __PACKAGE__->add_numbers( 2, 3 );   # dit 5


Notez la façon dont "around" fonctionne
    dans Moose : il attend un coderef enveloppant comme dernier argument. Ce
    coderef enveloppant attend ensuite qu'on lui donne une référence à la fonction
    originale comme premier paramètre.


Cela peut permettre, par exemple, à un rôle de fournir une signature
    enveloppant une méthode définie dans une classe.


C'est assez complexe, et vous l'utiliserez probablement peu, mais cela
    s'est avéré utile pour les outils qui intègrent Type::Params avec des modificateurs
    de méthode de type Moose.


Notez que "next" est le mécanisme que
    "signature_for" utilise en interne pour connecter
    la signature à la sous-routine enveloppée, donc utiliser
    "next" avec
    "signature_for" est une bonne recette pour
    les maux de tête.


Si vous utilisez des signatures "multiple",
    "next" est utile pour chaque signature
    "interne" pour organiser les paramètres dans le bon ordre. Cette
    utilisation de "next" est supportée pour
    "signature_for".


L'option "goto_next" est supportée comme
    alias historique pour "next".


"want_source" Bool


Au lieu de retourner un coderef, retourne une chaîne de code source
    Perl. Pratique pour le débogage.


"want_details" Bool


Au lieu de retourner un coderef, retourne un hashref de choses
    incluant le coderef. Ceci est principalement pour les personnes qui étendent
    Type::Params et je n'entrerai pas dans trop de détails sur ce que contient ce
    hashref.


"want_object" Bool


Au lieu de retourner un coderef, retourne un objet
    Type::Params::Signature. C'est la version plus moderne de
    "want_details".







API   LEGALE


Les fonctions suivantes étaient l'API avant Type::Params v2. Elles sont
    toujours supportées, mais leur utilisation est maintenant déconseillée.


Si vous ne fournissez pas du tout de liste d'importation, vous importerez
    "compile" et
    "compile_named" :


use Type::Params;


Ceci fait la même chose :


use Type::Params -v1;


Ceci importe "compile",
    "compile_named", et
    "compile_named_oo" :


use Type::Params -compile;


Ceci importe
    "wrap_subs" et
    "wrap_methods" :


use Type::Params -wrap;




compile(   @pos_params )


Équivalent à "signature( positional =>
    \@pos_params )".


"compile( \%spec, @pos_params )"
    est équivalent à "signature( %spec, positional =>
    \@pos_params )".






compile_named(   @named_params )


Équivalent à "signature( bless => 0,
    named => \@named_params )".


"compile_named( \%spec, @named_params
    )" est équivalent à "signature( bless
    => faux, %spec, named => \@named_params )".






compile_named_oo(   @named_params )


Équivalent à "signature( bless => vrai,
    named => \@named_params )".


"compile_named_oo( \%spec, @named_params
    )" est équivalent à "signature( bless
    => vrai, %spec, named => \@named_params )".






"validate(   \@args, @pos_params )"


Équivalent à "signature( positional =>
    \@pos_params )->( @args )".


La fonction "validate" n'a jamais
    été recommandée et n'est pas exportée sauf si demandée par nom.






"validate_named(   \@args, @named_params )"


Équivalent à "signature( bless => faux,
    named => \@named_params )->( @args )".


La fonction "validate_named" n'a jamais
    été recommandée et n'est pas exportée sauf si demandée par nom.








API    LEGACY




"wrap_subs(   func1 => \@params1, func2 => \@params2, ... )"


Équivalent à :


signature_for func1 => ( positional => \@params1 );
signature_for func2 => ( positional => \@params2 );


Une légère différence est qu'au lieu de tableaux références, vous pouvez
    fournir le résultat de l'une des fonctions "compile" :


wrap_subs( func1 => compile_named( @params1 ) );


"wrap_subs" n'est pas exporté
    sauf sur demande explicite.






"wrap_methods(   func1 => \@params1, func2 => \@params2, ... )"


Équivalent à :


signature_for func1 => ( method => 1, positional => \@params1 );
signature_for func2 => ( method => 1, positional => \@params2 );


Une légère différence est qu'au lieu de tableaux références, vous pouvez
    fournir le résultat de l'une des fonctions "compile" :


wrap_methods( func1 => compile_named( @params1 ) );


"wrap_methods" n'est pas exporté
    sauf sur demande explicite.






multisig(   @alternatives )


Équivalent à :


signature( multiple => \@alternatives )


"multisig( \%spec, @alternatives
    )" est équivalent à "signature( %spec,
    multiple => \@alternatives )".








CONTRAINTES    DE TYPE


Bien que Type::Params ne soit pas une véritable bibliothèque de types, il
    exporte deux contraintes de type. Leur utilisation n'est plus recommandée.




Invocant


Type::Params exporte un type Invocant sur demande. Cela vous donne
    une contrainte de type qui accepte les noms de classe *et* les objets
    blessés.


use Type::Params qw( compile Invocant );

signature_for my_method => (
  method     => Invocant,
  positional => [ ArrayRef, Int ],
);

sub my_method ($self_or_class, $arr, $ix) {
  return $arr->[ $ix ];
}


"Invocant" n'est pas exporté
    sauf sur demande explicite.


Recommandation : utiliser Defined de Types::Standard
    à la place.






ArgsObject


Type::Params exporte une contrainte de type paramétrable
    ArgsObject. Elle accepte les types d'objets retournés par les vérifications
    de paramètres pour les paramètres nommés.


use v5.36;

package Foo {
  use Moo;
  use Type::Params 'ArgsObject';

  has args => (
    is  => 'ro',
    isa => ArgsObject['Bar::bar'],
  );
}

package Bar {
  use Types::Standard -types;
  use Type::Params 'signature_for';

  signature_for bar => ( named => [ xxx => Int, yyy => ArrayRef ] );

  sub bar ( $got ) {
    return 'Foo'->new( args => $got );
  }
}

Bar::bar( xxx => 42, yyy => [] );


Le paramètre "Bar::bar" fait référence à l'appelant lorsque
    la vérification est compilée, plutôt que lors de la vérification des
    paramètres.


"ArgsObject" n'est pas exporté
    sauf sur demande explicite.


Recommandation : utiliser Object de Types::Standard
    à la place.








ENVIRONNEMENT



  
"PERL_TYPE_PARAMS_XS"

  
Affecte la construction des accesseurs pour les objets $arg.
      S'il est défini sur vrai, utilisera Class::XSAccessor. S'il est défini sur
      faux, utilisera du Perl pur. Si cette variable d'environnement n'existe pas,
      utilisera Class::XSAccessor.
    
Si Class::XSAccessor n'est pas installé ou est trop ancien, du Perl
        pur sera toujours utilisé en solution de repli.
