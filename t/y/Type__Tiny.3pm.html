NOM

Type::Tiny - contrainte de type minuscule, mais compatible avec Moo(se)

SYNOPIS

use v5.36;

package Horse {
  use Moo;
  use Types::Standard qw( Str Int Enum ArrayRef Object );
  use Type::Params qw( signature_for );
  use namespace::autoclean;

  has name => (
    is       => 'ro',
    isa      => Str,
    required => 1,
  );

  has gender => (
    is       => 'ro',
    isa      => Enum[qw( f m )],
  );

  has age => (
    is       => 'rw',
    isa      => Int->where( '$_ >= 0' ),
  );

  has children => (
    is       => 'ro',
    isa      => ArrayRef[Object],
    default  => sub { return [] },
  );

  # signature de méthode
  signature_for add_child => (
    method     => Object,
    positional => [ Object ],
  );

  sub add_child ( $self, $child ) {
    push $self->children->@*, $child;
    return $self;
  }
}

package main;

my $boldruler = Horse->new(
  name    => "Bold Ruler",
  gender  => 'm',
  age     => 16,
);

my $secretariat = Horse->new(
  name    => "Secretariat",
  gender  => 'm',
  age     => 0,
);

$boldruler->add_child( $secretariat );

STATUT

Ce module est couvert par la politique de stabilité de Type-Tiny.

DESCRIPTION

Ceci documente les internes de la classe Type::Tiny. Type::Tiny::Manual est un meilleur point de départ si vous êtes novice.

Type::Tiny est une petite classe pour créer des objets de contrainte de type de type Moose, compatibles avec Moo, Moose et Mouse.

use Scalar::Util qw(looks_like_number);
use Type::Tiny;

my $NUM = "Type::Tiny"->new(
   name       => "Number",
   constraint => sub { looks_like_number($_) },
   message    => sub { "$_ n'est pas un nombre" },
);

package Ermintrude {
   use Moo;
   has favourite_number => (is => "ro", isa => $NUM);
}

package Bullwinkle {
   use Moose;
   has favourite_number => (is => "ro", isa => $NUM);
}

package Maisy {
   use Mouse;
   has favourite_number => (is => "ro", isa => $NUM);
}

Type::Tiny est conforme à Type::API::Constraint, Type::API::Constraint::Coercible, Type::API::Constraint::Constructor, et Type::API::Constraint::Inlinable.

Peut-être n'aurons-nous plus besoin d'avoir des versions MooseX, MouseX et MooX séparées pour tout ? On peut espérer...

Constructeur

new(%attributs)
Fonction de constructeur style Moose.

Attributs

Les attributs sont des valeurs nommées qui peuvent être passées au constructeur. Pour chaque attribut, il existe une méthode de lecture correspondante. Par exemple :

my $type = Type::Tiny->new( name => "Foo" );
print $type->name, "\n";   # affiche "Foo"

Attributs importants

Ce sont les attributs qui vous intéressent le plus probablement lorsque vous créez vos propres contraintes de type, et que vous lisez lorsque vous traitez des objets de contrainte de type.

"constraint"
Code référence pour valider une valeur ($_) par rapport à la contrainte de type. Le code référence ne sera appelé que si la valeur est connue pour passer toute contrainte de type parente (voir "parent" ci-dessous).

Alternativement, une chaîne de code Perl vérifiant $_ peut être passée comme paramètre au constructeur, et sera convertie en code référence.

Par défaut, c'est "sub { 1 }" - c'est-à-dire un code référence qui accepte toutes les valeurs.

"parent"
Attribut optionnel ; contrainte de type parente. Par exemple, une contrainte de type "Integer" pourrait avoir un parent "Number".

Si fourni, doit être un objet Type::Tiny.

"inlined"
Un code référence qui retourne une chaîne de code Perl appropriée pour intégrer ce type. Optionnel.

(Le code référence sera appelé dans un contexte de liste et peut en fait retourner une liste de chaînes qui seront jointes avec "&&". Si le premier élément de la liste est indéfini, il sera substitué par la vérification intégrée du type parent.)

Si "constraint" (ci-dessus) est un code référence généré via Sub::Quote, alors Type::Tiny *peut* être capable de générer automatiquement "inlined" pour vous. Si "constraint" (ci-dessus) est une chaîne, il le pourra.

"name"
Le nom de la contrainte de type. Ceux-ci doivent être conformes à certaines règles de nommage (ils doivent commencer par une lettre majuscule et continuer en utilisant uniquement des lettres, des chiffres 0-9 et des underscores).

Optionnel ; s'il n'est pas fourni, ce sera une contrainte de type anonyme.

"display_name"
Un nom à afficher pour la contrainte de type lors de sa conversion en chaîne. Ceux-ci n'ont pas besoin d'être conformes à des règles de nommage. Optionnel ; un nom par défaut sera calculé à partir du "name".
"library"
Le nom du paquet de la bibliothèque de types à laquelle ce type est associé. Optionnel. À titre informatif uniquement : définir cet attribut n'installe pas le type dans le paquet.
"deprecated"
Indicateur booléen optionnel indiquant si une contrainte de type est dépréciée. Type::Library émettra un avertissement si vous tentez d'importer une contrainte de type dépréciée, mais sinon le type continuera de fonctionner normalement. Il n'y aura pas d'avertissements de dépréciation chaque fois que vous validez une valeur, par exemple. S'il est omis, il prend par défaut le statut de dépréciation du parent (ou faux s'il n'y a pas de parent).
"message"
Code référence qui retourne un message d'erreur lorsque $_ ne valide pas par rapport à la contrainte de type. Optionnel (il existe une valeur par défaut raisonnablement sensée.)
"coercion"
Un objet Type::Coercion associé à ce type.

En général, cet attribut ne doit pas être passé au constructeur ; vous devriez vous fier à l'objet de coercition par défaut construit paresseusement.

Vous pouvez passer "coercion => 1" au constructeur pour hériter des coercions du parent de la contrainte. (Cela nécessite que la contrainte parente ait une coercition.)

Si un tableau est passé au constructeur ("coercion => [ ... ]"), alors l'objet de coercition sera construit paresseusement et ce tableau sera transmis à sa méthode "add_type_coercions". Si un code est passé au constructeur ("coercion => sub { ... }"), alors l'objet de coercition sera construit paresseusement et ce code sera utilisé comme coercition depuis Any.

"sorter"
Un code référence qui peut être passé à deux valeurs conformes à cette contrainte de type et retourne -1, 0, ou 1 pour les mettre en ordre. Alternativement, un tableau contenant une paire de codes références — un trieur et un pré-processeur pour la transformée de Schwarzian. Optionnel.

L'idée est de permettre ceci :

@sorted = Int->sort( 2, 1, 11 );    # => 1, 2, 11
@sorted = Str->sort( 2, 1, 11 );    # => 1, 11, 2
"type_default"
Un code référence qui retourne une valeur par défaut raisonnable pour ce type. Par exemple, pour un type Counter, une valeur par défaut raisonnable pourrait être "0" : 
my $Size = Type::Tiny->new(
  name          => 'Size',
  parent        => Types::Standard::Enum[ qw( XS S M L XL ) ],
  type_default  => sub { return 'M'; },
);

package Tshirt {
  use Moo;
  has size => (
    is       => 'ro',
    isa      => $Size,
    default  => $Size->type_default,
  );
}

Les types enfants hériteront d'une valeur par défaut de type de leur parent à moins que l'enfant n'ait une "constraint". Si un type n'a ni n'hérite d'une valeur par défaut de type, alors appeler "type_default" retournera indéfini.

Comme cas spécial, ceci :

$type->type_default( @args )

Retournera :

sub {
  local $_ = \@args;
  $type->type_default->( @_ );
}

Beaucoup des types définis dans Types::Standard et d'autres bibliothèques de types groupées ont des valeurs par défaut de type

NAME

Type::Tiny - A tiny, fast, and powerful type constraint library

VERSION

v0.037

SYNOPSIS

  use Type::Tiny;

  # Basic types
  my $int_type = Type::Tiny::Int;
  my $str_type = Type::Tiny::Str;
  my $array_type = Type::Tiny::ArrayRef;

  # Checking values
  $int_type->check(123);   # returns true
  $int_type->check('abc'); # returns false

  # Getting error messages
  $int_type->validate('abc'); # returns 'abc' does not pass type Int'
  $int_type->validate(123);   # returns undef

  # Coercion
  my $coerced_value = $int_type->coerce('123'); # returns 123 (as an Int)

  # Custom types
  my $positive_int = Type::Tiny->new(
      name    => 'PositiveInt',
      isa     => 'Int',
      constraint => sub { $_[0] > 0 },
      message => sub { $_[0] . ' is not a positive integer' },
  );
  $positive_int->check(5);    # returns true
  $positive_int->check(-5);   # returns false
  $positive_int->validate(-5); # returns '-5 is not a positive integer'

  # Parameterized types
  my $array_of_ints = Type::Tiny::ArrayRef->parameterize( Type::Tiny::Int );
  $array_of_ints->check([1, 2, 3]); # returns true
  $array_of_ints->check([1, 'a', 3]); # returns false

  # Unions and Intersections
  use Type::Tiny ':all'; # Import all constants like ALL, UNDEF, etc.

  my $numeric = Int | Float; # Union
  my $non_empty_string = Str & where(sub { length $_[0] }); # Intersection

  # You can also use operators like & and |
  my $non_empty_string_again = Str & 'length $_[0]';

DESCRIPTION

Type::Tiny is a very small, very fast, and very powerful library for defining and using type constraints. It is intended as a replacement for Moose::Meta::TypeConstraint and Mouse::Meta::TypeConstraint, and aims to provide most of their functionality (and in some cases, improve upon it) with significantly less overhead.

The primary difference is that Type::Tiny objects are plain Perl objects, and do not rely on Moose or Mouse themselves. This means you can use Type::Tiny in any Perl project, even those that do not use a full-blown OO framework.

The API is largely compatible with Moose and Mouse, so migration should be straightforward.

Constructor

The constructor for Type::Tiny is fairly simple:

"new(%attributes)"
Creates a new type constraint object. The following attributes are supported:
"name"
A string representing the name of the type constraint (e.g. "Int", "ArrayRef[Int]"). Used in error messages.
"isa"
A string or an arrayref of strings representing the base Perl type(s) that this type constraint should accept. For example, 'SCALAR', 'ARRAYREF', 'HASHREF', 'CODE', 'GLOB', 'LVALUE', 'REF'. If this is present, then the type constraint will automatically pass if the value passes the specified Perl type. It's also possible to specify 'Int' or 'Float', which are handled specially to mimic Perl's auto-vivification of numbers.
"constraint"
A coderef that takes a single argument (the value being checked) and returns true if the value passes the constraint, and false otherwise. This is the core of the type check.
"message"
A coderef that takes a single argument (the value being checked) and returns a string explaining why the value failed the constraint. This coderef is only called if the "constraint" coderef returns false.
"parent"
The parent type constraint object. This is used for building complex types like parameterized types (e.g. "ArrayRef[Int]"). Usually, you won't set this directly; instead, you'll use methods like "parameterize" or the overloaded operators.
"coerce"
A coderef that takes a single argument (the value being coerced) and returns the coerced value. This coderef is only called if the value does *not* already pass the type constraint.
"inline_cache"
A hashref used for caching the inlined version of the type constraint. You generally do not need to interact with this directly.
"do_not_bless_into"
If set to a package name, Type::Tiny will not bless the value into that package, even if it would normally do so. This is primarily useful for preventing `bless $value, $packagename` when building types like `ArrayRef[ClassName]` from being called when `$value` is already blessed into `$packagename`.
"compiler"
A coderef that takes a Type::Tiny object and returns a coderef that represents the type check. This is used for optimizing type checks by inlining them. You generally do not need to interact with this directly, as Type::Tiny provides a default compiler.
"sorter"
A coderef used to sort type constraints. This is used internally for optimizing unions and intersections. You generally do not need to interact with this directly.
"deep_check"
A coderef used for deeper validation, particularly useful for complex parameterized types. It receives the value, the type constraint, and the variable name (if provided). It should return a hashref where keys are variable names and values are error messages or undef if the check passes. The details of this API are not yet finalized, but discovering them is left as an exercise for the reader.
"my_methods"
Experimental hashref of additional methods that can be called on the type constraint object.
"exception_class"
The class used to throw an exception when a value fails its type check. Defaults to "Error::TypeTiny::Assertion", which is usually good. This class is expected to provide a "throw_cb" method compatible with the method of that name in Error::TypeTiny.

If a parent type constraint has a custom "exception_class", then this will be "inherited" by its children.

Attributes related to parameterizable and parameterized types

The following additional attributes are used for parameterizable (e.g. "ArrayRef") and parameterized (e.g. "ArrayRef[Int]") type constraints. Unlike Moose, these aren't handled by separate subclasses.

"constraint_generator"
Coderef that is called when a type constraint is parameterized. When called, it is passed the list of parameters, though any parameter which looks like a foreign type constraint (Moose type constraints, Mouse type constraints, etc, and coderefs(!!!)) is first coerced to a native Type::Tiny object.

Note that for compatibility with the Moose API, the base type is not passed to the constraint generator, but can be found in the package variable $Type::Tiny::parameterize_type. The first parameter is also available as $_.

Types can be parameterized with an empty parameter list. For example, in Types::Standard, "Tuple" is just an alias for "ArrayRef" but "Tuple[]" will only allow zero-length arrayrefs to pass the constraint. If you wish "YourType" and "YourType[]" to mean the same thing, then do:

return $Type::Tiny::parameterize_type unless @_;

The constraint generator should generate and return a new constraint coderef based on the parameters. Alternatively, the constraint generator can return a fully-formed Type::Tiny object, in which case the "name_generator", "inline_generator", and "coercion_generator" attributes documented below are ignored.

Optional; providing a generator makes this type into a parameterizable type constraint. If there is no generator, attempting to parameterize the type constraint will throw an exception.

"name_generator"
A coderef which generates a new display_name based on parameters. Called with the same parameters and package variables as the "constraint_generator". Expected to return a string.

Optional; the default is reasonable.

"inline_generator"
A coderef which generates a new inlining coderef based on parameters. Called with the same parameters and package variables as the "constraint_generator". Expected to return a coderef.

Optional.

"coercion_generator"
A coderef which generates a new Type::Coercion object based on parameters. It is passed the parent type, child type, and list of parameters. It should have access to the same package variables as the "constraint_generator". Expected to return a blessed object.

Optional.

"deep_explanation"
This API is not finalized. Coderef used by Error::TypeTiny::Assertion to peek inside parameterized types and figure out why a value doesn't pass the constraint.
"parameters"
In parameterized types, returns an arrayref of the parameters.

Lazy generated attributes

The following attributes should not be usually passed to the constructor; unless you're doing something especially unusual, you should rely on the default lazily-built return values.

"compiled_check"
Coderef to validate a value ($_[0]) against the type constraint. This coderef is expected to also handle all validation for the parent type constraints.
"definition_context"
Hashref of information indicating where the type constraint was originally defined. Type::Tiny will generate this based on "caller" if you do not supply it. The hashref will ordinarily contain keys "package", "file", and "line".

For parameterized types and compound types (e.g. unions and intersections), this may not be especially meaningful information.

"complementary_type"
A complementary type for this type. For example, the complementary type for an integer type would be all things that are not integers, including floating point numbers, but also alphabetic strings, arrayrefs, filehandles, etc.
"moose_type", "mouse_type"
Objects equivalent to this type constraint, but as a Moose::Meta::TypeConstraint or Mouse::Meta::TypeConstraint.

It should rarely be necessary to obtain a Moose::Meta::TypeConstraint object from Type::Tiny because the Type::Tiny object itself should be usable pretty much anywhere a Moose::Meta::TypeConstraint is expected.

Methods

Predicate methods

These methods return booleans indicating information about the type constraint. They are each tightly associated with a particular attribute. (See "Attributes".)

"has_parent", "has_library", "has_inlined", "has_constraint_generator", "has_inline_generator", "has_coercion_generator", "has_parameters", "has_message", "has_deep_explanation", "has_sorter"
Simple Moose-style predicate methods indicating the presence or absence of an attribute.
"has_coercion"
Predicate method with a little extra DWIM. Returns false if the coercion is a no-op.
"is_anon"
Returns true iff the type constraint does not have a "name".
"is_parameterized", "is_parameterizable"
Indicates whether a type has been parameterized (e.g. "ArrayRef[Int]") or could potentially be (e.g. "ArrayRef").
"has_parameterized_from"
Useless alias for "is_parameterized".

Validation and coercion

The following methods are used for coercing and validating values against a type constraint:

check($value)
Returns true iff the value passes the type constraint.
validate($value)
Returns the error message for the value; returns an explicit undef if the value passes the type constraint.
assert_valid($value)
Like check($value) but dies if the value does not pass the type constraint.

Yes, that's three very similar methods. Blame Moose::Meta::TypeConstraint whose API I'm attempting to emulate. :-)

assert_return($value)
Like assert_valid($value) but returns the value if it passes the type constraint.

This seems a more useful behaviour than assert_valid($value). I would have just changed assert_valid($value) to do this, except that there are edge cases where it could break Moose compatibility.

get_message($value)
Returns the error message for the value; even if the value passes the type constraint.
"validate_explain($value, $varname)"
Like "validate" but instead of a string error message, returns an arrayref of strings explaining the reasoning why the value does not meet the type constraint, examining parent types, etc.

The $varname is an optional string like '$foo' indicating the name of the variable being checked.

coerce($value)
Attempt to coerce $value to this type.
assert_coerce($value)
Attempt to coerce $value to this type. Throws an exception if this is not possible.

Child type constraint creation and parameterization

These methods generate new type constraint objects that inherit from the constraint they are called upon:

create_child_type(%attributes)
Construct a new Type::Tiny object with this object as its parent.
where($coderef)
Shortcut for creating an anonymous child type constraint. Use it like "HashRef->where(sub { exists($_->{name}) })". That said, you can get a similar result using overloaded "&": 
HashRef & sub { exists($_->{name}) }

Like the "constraint" attribute, this will accept a string of Perl code:

HashRef->where('exists($_->{name})')
"child_type_class"
The class that create_child_type will construct by default.
parameterize(@parameters)
Creates a new parameterized type; throws an exception if called on a non-parameterizable type.
union(@types)
Creates a new union type constraint. This is equivalent to using the "|" operator.
intersection(@types)
Creates a new intersection type constraint. This is equivalent to using the "&" operator.
complement
Returns the complementary type constraint.

Overloaded operators

Type::Tiny overloads the following operators:

"\|"
Union operator. Equivalent to union.
"&"
Intersection operator. Equivalent to intersection.
"~"
Coercion operator. Equivalent to coerce. 
    Int ~ Str # Coerce Int to Str
"!"
Complement operator. Equivalent to complement.
"[]"
Parameterization operator. Equivalent to parameterize. 
    ArrayRef[Int] # Parameterize ArrayRef with Int

Other methods

"name", "isa", "constraint", "message", "parent", "coerce", "exception_class", "constraint_generator", "name_generator", "inline_generator", "coercion_generator", "parameters", "definition_context", "compiled_check", "complementary_type", "moose_type", "mouse_type"
Accessors for the corresponding attributes.
"display_name"
Returns a string representation of the type constraint. This is usually the same as the name attribute, but may be more descriptive for parameterized or composite types.
"inline_code"
Returns a string of Perl code that can be used to perform the type check. This is used for optimizing type checks by inlining them.
"find_type($name)"
Given a type name (e.g., "Int"), finds the corresponding Type::Tiny object. This is useful for resolving type names within parameterized types.

BUGS AND LIMITATIONS

There are no known bugs in Type::Tiny.

Limitations:

  • Type::Tiny does not provide a way to create new named types directly. You typically define them in your own modules and then export them.
  • The "deep_explanation" API is not yet finalized.

Méthodes d'introspection des relations de types

Ces méthodes vous permettent de déterminer la relation d'une contrainte de type avec d'autres contraintes de type dans une hiérarchie organisée :

equals($other), is_subtype_of($other), is_supertype_of($other), is_a_type_of($other)
Compare deux types. Voir Moose::Meta::TypeConstraint pour ce que tout cela signifie. (OK, Moose ne définit pas "is_supertype_of", mais vous avez compris l'idée, n'est-ce pas ?)

Notez que ces méthodes ont un côté légèrement "ça marche comme on pense" (DWIM). Si vous créez deux objets Type::Tiny::Class qui testent la même classe, ils sont considérés comme égaux. Et :

my $subtype_of_Num = Types::Standard::Num->create_child_type;
my $subtype_of_Int = Types::Standard::Int->create_child_type;
$subtype_of_Int->is_subtype_of( $subtype_of_Num );  # vrai
strictly_equals($other), is_strictly_subtype_of($other), is_strictly_supertype_of($other), is_strictly_a_type_of($other)
Versions plus strictes des fonctions de comparaison de types. Elles ne tiennent compte que de l'héritage explicite via "parent". 
my $subtype_of_Num = Types::Standard::Num->create_child_type;
my $subtype_of_Int = Types::Standard::Int->create_child_type;
$subtype_of_Int->is_strictly_subtype_of( $subtype_of_Num );  # faux
"parents"
Retourne une liste de toutes les contraintes ancêtres de cette contrainte de type. Par exemple, si appelée sur la contrainte de type "Str", elle retournerait la liste "(Value, Defined, Item, Any)".

En raison d'un malentendu historique, cela diffère de l'implémentation Moose de la méthode "parents". Dans Moose, "parents" ne retourne que les contraintes de type parent immédiates, et comme les contraintes de type n'ont qu'un seul parent immédiat, c'est effectivement un alias pour "parent". Le module d'extension MooseX::Meta::TypeConstraint::Intersection est le seul endroit où plusieurs contraintes de type sont retournées ; et elles sont retournées sous forme d'arrayref en violation de la documentation de la classe de base. Je conserve mon comportement car il semble plus utile.

find_parent($coderef)
Parcourt les contraintes de type parent, *y compris l'invocant lui-même*, et retourne l'ancêtre le plus proche où le coderef évalue à vrai. Dans le coderef, l'ancêtre actuellement vérifié est $_. Retourne undef s'il n'y a pas de correspondance.

En contexte de liste, retourne également le nombre de contraintes de type qui ont été parcourues avant que la contrainte correspondante ne soit trouvée.

"find_constraining_type"
Trouve la contrainte de type ancêtre la plus proche (y compris le type lui-même) qui a un coderef "constraint".

Équivaut à :

$type->find_parent(sub { not $_->_is_null_constraint })
"coercibles"
Retourne une contrainte de type qui est l'union des contraintes de type qui peuvent être coercées vers celle-ci (y compris celle-ci). Si cette contrainte de type n'a pas de coercions, elle se retourne elle-même.
"type_parameter"
Dans les contraintes de type paramétrées, retourne le premier élément de la liste de paramètres ; sinon, retourne undef. Par exemple : 
( ArrayRef[Int] )->type_parameter;    # retourne Int
( ArrayRef[Int] )->parent;            # retourne ArrayRef

Notez que les contraintes de type paramétrables peuvent légitimement prendre plusieurs paramètres (plusieurs des contraintes de type paramétrables dans Types::Standard le font). Cette méthode ne retourne que le premier paramètre. L'attribut "parameters", documenté dans "Attributes related to parameterizable and parameterized types", retourne un arrayref de tous les paramètres.

"parameterized_from"
Alias plus difficile à épeler pour "parent" qui ne fonctionne que pour les types paramétrés.

Indice pour ceux qui sous-classent Type::Tiny : Depuis la version 1.006000, les méthodes permettant de déterminer le sous-type, le supertype et l'égalité des types ne doivent *pas* être surchargées dans les sous-classes de Type::Tiny. Ceci est dû au problème de l'héritage en diamant. Si X et Y sont tous deux des sous-classes de Type::Tiny, elles doivent *toutes deux* être consultées pour déterminer comment les contraintes de type sont liées ; seule l'une d'elles ne devrait pas surcharger ces méthodes. Voir le code source de Type::Tiny::Enum pour un exemple de la façon dont les sous-classes peuvent donner des indices sur les relations de types à Type::Tiny. Résumé : ajouter un coderef à @Type::Tiny::CMP. Ce coderef recevra deux contraintes de type. Il devrait alors retourner l'une des constantes Type::Tiny::CMP_SUBTYPE (le premier type est un sous-type du second type), Type::Tiny::CMP_SUPERTYPE (le second type est un sous-type du premier type), Type::Tiny::CMP_EQUAL (les deux types sont exactement les mêmes), Type::Tiny::CMP_EQUIVALENT (les deux types sont effectivement les mêmes), ou Type::Tiny::CMP_UNKNOWN (votre coderef n'a pas pu établir de relation).

Fonction d'introspection des relations de types

"Type::Tiny::cmp($type1, $type2)"
La relation sous-type/supertype entre les types entraîne un ordre partiel des contraintes de type.

Cette fonction retournera l'une des constantes : Type::Tiny::CMP_SUBTYPE (le premier type est un sous-type du second type), Type::Tiny::CMP_SUPERTYPE (le second type est un sous-type du premier type), Type::Tiny::CMP_EQUAL (les deux types sont exactement les mêmes), Type::Tiny::CMP_EQUIVALENT (les deux types sont effectivement les mêmes), ou Type::Tiny::CMP_UNKNOWN (aucune relation n'a pu être établie). En contextes numériques, celles-ci s'évaluent à -1, 1, 0, 0 et 0, ce qui les rend potentiellement utilisables avec "sort" (bien que vous puissiez avoir besoin de supprimer les avertissements concernant le traitement de la chaîne vide comme valeur numérique).

Méthodes de traitement de listes

grep(@list)
Filtre une liste pour ne retourner que les éléments qui passent le test de type. 
@integers = Int->grep(@list);
first(@list)
Filtre la liste pour retourner le premier élément de la liste qui passe le test de type, ou undef si aucun ne passe. 
$first_lady = Woman->first(@people);
map(@list)
Coerce une liste d'éléments. Ne fonctionne que sur les types qui ont une coercion. 
@truths = Bool->map(@list);
sort(@list)
Trie une liste d'éléments selon le mécanisme de tri préféré du type, ou si le type n'a pas de coderef de tri, utilise le type parent. Si aucune contrainte de type ancêtre n'a de sorter, lève une exception. Les contraintes de type "Str", "StrictNum", "LaxNum" et "Enum" incluent des sorters. 
@sorted_numbers = Num->sort( Num->grep(@list) );
rsort(@list)
Comme "sort" mais en ordre inverse.
any(@list)
Retourne vrai si n'importe lequel des éléments de la liste correspond au type. 
if ( Int->any(@numbers) ) {
  say "il y avait au moins un entier";
}
all(@list)
Retourne vrai si tous les éléments de la liste correspondent au type. 
if ( Int->all(@numbers) ) {
  say "ils étaient tous des entiers";
}
assert_any(@list)
Comme "any" mais au lieu de retourner un booléen, retourne la liste originale entière si au moins un élément correspond au type, et meurt si aucun ne correspond.
assert_all(@list)
Comme "all" mais au lieu de retourner un booléen, retourne la liste originale si tous les éléments correspondent au type, mais meurt dès qu'il en trouve un qui ne correspond pas.

Méthodes d'imbrication

Les méthodes suivantes sont utilisées pour générer des chaînes de code Perl qui peuvent être collées dans des sous-routines *stringy* "eval"uées pour effectuer des vérifications de type :

"can_be_inlined"
Retourne un booléen indiquant si ce type peut être imbriqué.
inline_check($varname)
Crée une vérification de contrainte de type pour une variable particulière sous forme de chaîne de code Perl. Par exemple : 
print( Types::Standard::Num->inline_check('$foo') );

affiche la sortie suivante :

(!ref($foo) && Scalar::Util::looks_like_number($foo))

Pour la compatibilité Moose, il existe un alias "_inline_check" pour cette méthode.

inline_assert($varname)
Très similaire à "inline_check" mais génère une instruction de la forme : 
... or die ...;

Peut également être appelée comme "inline_assert($varname, $typevarname, %extras)". Dans ce cas, elle générera une chaîne de

f code qui peut inclure $typevarname qui est censé être le nom d'une variable contenant le type lui-même. (C'est un peu compliqué, mais cela permet de produire une chaîne utile même si le type n'est pas inlineable.) Les %extras sont des options supplémentaires à passer au constructeur de Error::TypeTiny::Assertion et doivent être des paires clé-valeur de chaînes uniquement, sans références ni undefs.

Autres méthodes

"qualified_name"
Pour les contraintes de type non anonymes qui ont une bibliothèque, renvoie un nom qualifié du genre "MaLib::MonType". Sinon, renvoie le même que "name".
isa($class), can($method), AUTOLOAD(@args)
Si Moose est chargé, la combinaison de ces méthodes est utilisée pour simuler un Moose::Meta::TypeConstraint.

Si Mouse est chargé, "isa" simule Mouse::Meta::TypeConstraint.

DOES($role)
Surchargé pour annoncer le support de divers rôles.

Voir aussi Type::API::Constraint, etc.

"TIESCALAR", "TIEARRAY", "TIEHASH"
Ceux-ci sont fournis comme des points d'accroche qui enveloppent Type::Tie. Ils permettent aux éléments suivants de fonctionner : 
use Types::Standard qw(Int);
tie my @list, Int;
push @list, 123, 456;   # ok
push @list, "Hello";    # dies
exportables( $base_name )
Renvoie une liste des fonctions qu'une bibliothèque de types devrait exporter si elle contient cette contrainte de type.

Exemple :

[
  { name => 'Int',        tags => [ 'types' ],  code => sub { ... } },
  { name => 'is_Int',     tags => [ 'is' ],     code => sub { ... } },
  { name => 'assert_Int', tags => [ 'assert' ], code => sub { ... } },
  { name => 'to_Int',     tags => [ 'to' ],     code => sub { ... } },
]

$base_name est optionnel, mais vous permet d'obtenir une liste des exportables en utilisant un nom spécifique. Ceci est utile si la contrainte de type a un nom qui ne serait pas un nom de fonction Perl valide.

"exportables_by_tag( $tag, $base_name )"
Filtre "exportables" par un nom d'étiquette spécifique. En contexte de liste, renvoie tous les exportables correspondants. En contexte scalaire, renvoie un seul exportable correspondant et meurt si plusieurs exportables correspondent, ou si aucun ne correspond !

"hand_optimized_type_constraint"
"has_hand_optimized_type_constraint"

Fonctions

•
"check_parameter_count_for_parameterized_type( $lib, $typename, $args, $max, $min )"

Fonction utilitaire utilisée par certains types de Types::Standard, etc.

Lèvera une exception Error::TypeTiny::WrongNumberOfParameters faisant référence à "$lib::\$typename\[]" si $args est supérieur à $max ou inférieur à $min, s'ils sont définis. Si $args est une référence de tableau, la longueur du tableau sera utilisée.

Surcharge

  • La conversion en chaîne est surchargée pour renvoyer le nom qualifié.
  • La conversion en booléen est surchargée pour renvoyer toujours vrai.
  • La conversion en référence de code est surchargée pour appeler "assert_return".
  • Sur Perl 5.10.1 et supérieur, la correspondance intelligente (smart match) est surchargée pour appeler "check".
  • L'opérateur "==" est surchargé pour appeler "equals".
  • Les opérateurs "<" et ">" sont surchargés pour appeler "is_subtype_of" et "is_supertype_of".
  • L'opérateur "~" est surchargé pour appeler "complementary_type".
  • L'opérateur "|" est surchargé pour construire une union de deux contraintes de type. Voir Type::Tiny::Union.
  • L'opérateur "&" est surchargé pour construire l'intersection de deux contraintes de type. Voir Type::Tiny::Intersection.
  • L'opérateur "/" fournit un support magique pour Devel::StrictMode. Si $ENV{PERL_STRICT} (ou quelques autres variables d'environnement) est vrai, alors il renvoie l'opérande de gauche. Normalement, il renvoie l'opérande de droite.

Les versions précédentes de Type::Tiny surchargeaient l'opérateur "+" pour appeler "plus_coercions" ou "plus_fallback_coercions" selon le cas. Le support pour cela a été supprimé après la version 0.040.

Constantes

"Type::Tiny::SUPPORT_SMARTMATCH"
Indique si la surcharge de correspondance intelligente (smart match) est prise en charge par votre version de Perl.

Variables de paquet

$Type::Tiny::DD
Cette variable est undef par défaut mais peut être définie à une référence de code que Type::Tiny et les modules associés utiliseront pour afficher des structures de données dans des messages d'erreur, par exemple.

Sinon, Type::Tiny utilise sa propre routine pour afficher les structures de données. $DD peut alors être défini à un nombre pour limiter la longueur des affichages. (Limite par défaut : 72.)

Il s'agit d'une variable de paquet (plutôt que de méthodes de classe get/set) pour permettre une localisation facile.

$Type::Tiny::AvoidCallbacks
Si cette variable est définie à vrai (vous devriez généralement le faire dans une portée "local"), elle sert d'indicateur pour les contraintes de type, lors de la génération de code inline, pour éviter de faire des appels de rappel à des variables et des fonctions définies en dehors du code inline lui-même.

Cela devrait avoir pour effet que "$type->inline_check('$foo')" renvoie une chaîne de code capable de vérifier le type sur des installations Perl qui n'ont pas Type::Tiny installé. Ceci est destiné à permettre l'utilisation de Type::Tiny avec des choses comme Mite.

La variable fonctionne sur la base de l'honneur. Les types doivent explicitement la vérifier et décider de générer un code différent en fonction de sa valeur vraie. Les types groupés dans Types::Standard, Types::Common::Numeric, et Types::Common::String le font tous. (StrMatch ne peut parfois pas le faire et émettra un avertissement s'il a besoin de s'appuyer sur des rappels alors qu'on lui demande de ne pas le faire.)

La plupart des utilisateurs normaux peuvent ignorer ceci.

$Type::Tiny::SafePackage
Il s'agit de la chaîne "package Type::Tiny;" qui est parfois insérée dans des chaînes de code inline pour éviter les conflits de noms d'espace. Dans la plupart des cas, vous n'avez pas besoin de changer cela. Cependant, si vous inlinisez du code de contrainte de type, enregistrez ce code dans des modules Perl, et les téléchargez sur CPAN, vous pourriez vouloir le changer pour éviter des problèmes avec l'indexeur CPAN. La plupart des utilisateurs normaux de Type::Tiny n'ont pas besoin d'en être conscients.
