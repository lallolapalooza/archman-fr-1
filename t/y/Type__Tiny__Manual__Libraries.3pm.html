NOM

Type::Tiny::Manual::Libraries - définir vos propres bibliothèques de types

MANUEL

Définir un type

Un type est un objet et vous pouvez en créer un nouveau en utilisant le constructeur :

use Type::Tiny;

my $type = Type::Tiny->new(%args);

Une liste complète des arguments disponibles se trouve dans la documentation de Type::Tiny, mais les plus importants pour commencer sont :

"name"
Le nom de votre nouveau type. Type::Tiny utilise une convention de noms UpperCamelCase pour les contraintes de type. Le nom du type peut également commencer par un ou deux tirets bas pour indiquer un type destiné à un usage interne uniquement. Les types utilisant des caractères non-ASCII peuvent poser des problèmes sur les anciennes versions de Perl (avant 5.8).

Bien que ce soit facultatif et que les types puissent être anonymes, un nom est requis pour qu'une contrainte de type soit ajoutée à une bibliothèque de types.

"constraint"
Une référence de code vérifiant $_ et retournant un booléen. Alternativement, une chaîne de code Perl peut être fournie.

Si vous avez bien suivi, vous pouvez probablement deviner que la chaîne de code Perl peut entraîner des vérifications de type plus efficaces.

"parent"
Une contrainte de type existante dont hériter. Une valeur devra passer la contrainte parente avant que sa propre contrainte ne soit appelée. 
my $Even = Type::Tiny->new(
  name       => 'EvenNumber',
  parent     => Types::Standard::Int,
  constraint => sub {
    # dans ce sub, nous n'avons pas besoin de vérifier que $_ est un Int
    # car le parent s'en chargera !

    $_ % 2 == 0
  },
);

Bien que le "parent" soit facultatif, il est judicieux, lorsque cela est possible, d'hériter d'une contrainte de type existante pour bénéficier d'éventuelles optimisations ou implémentations XS qu'elles pourraient fournir.

Définir une bibliothèque

Une bibliothèque est un module Perl qui exporte des contraintes de type sous forme de subs. Types::Standard, Types::Common::Numeric, et Types::Common::String sont des bibliothèques de types fournies avec Type::Tiny.

Pour créer une bibliothèque de types, créez un paquet qui hérite de Type::Library.

package MyTypes {
  use Type::Library -base;

  ...; # vos définitions de types vont ici
}

Le drapeau "-base" est juste un raccourci pour :

package MyTypes {
  use Type::Library;
  our @ISA = 'Type::Library';
}

Vous pouvez ajouter des types comme ceci :

package MyTypes {
  use Type::Library -base;

  my $Even = Type::Tiny->new(
    name       => 'EvenNumber',
    parent     => Types::Standard::Int,
    constraint => sub {
      # dans ce sub, nous n'avons pas besoin de vérifier que $_ est un Int
      # car le parent s'en chargera !

      $_ % 2 == 0
    },
  );

  __PACKAGE__->add_type($Even);
}

Il existe un raccourci pour ajouter des types s'ils sont destinés à être des objets Type::Tiny bénis et non, par exemple, une sous-classe de Type::Tiny. Vous pouvez simplement passer %args directement à "add_type".

package MyTypes {
  use Type::Library -base;

  __PACKAGE__->add_type(
    name       => 'EvenNumber',
    parent     => Types::Standard::Int,
    constraint => sub {
      # dans ce sub, nous n'avons pas besoin de vérifier que $_ est un Int
      # car le parent s'en chargera !

      $_ % 2 == 0
    },
  );
}

La méthode "add_type" retourne le type qu'elle vient d'ajouter, de sorte qu'il puisse être stocké dans une variable.

my $Even = __PACKAGE__->add_type(...);

Cela peut être utile si vous souhaitez utiliser $Even comme type parent pour un autre type que vous allez définir plus tard.

Voici un exemple plus large :

package Example::Types {
  use Type::Library -base;
  use Types::Standard -types;
  use DateTime;

  # Type::Tiny::Class est une sous-classe de Type::Tiny pour créer
  # des types de type InstanceOf. C'est un peu mieux car
  # il fait des choses cool comme passer $type->new(%args)
  # au constructeur de la classe.
  #
  my $dt = __PACKAGE__->add_type(
    Type::Tiny::Class->new(
      name    => 'Datetime',
      class   => 'DateTime',
    )
  );

  my $dth = __PACKAGE__->add_type(
    name    => 'DatetimeHash',
    parent  => Dict[
      year       => Int,
      month      => Optional[ Int ],
      day        => Optional[ Int ],
      hour       => Optional[ Int ],
      minute     => Optional[ Int ],
      second     => Optional[ Int ],
      nanosecond => Optional[ Int ],
      time_zone  => Optional[ Str ],
    ],
  );

  my $eph = __PACKAGE__->add_type(
    name    => 'EpochHash',
    parent  => Dict[ epoch => Int ],
  );

  # On ne peut pas juste utiliser la méthode "plus_coercions" car cela crée
  # un nouveau type enfant anonyme pour y ajouter les coercitions. Nous voulons
  # les ajouter au type qui existe dans cette bibliothèque.
  #
  $dt->coercion->add_type_coercions(
    Int,    q{ DateTime->from_epoch(epoch => $_) },
    Undef,  q{ DateTime->now() },
    $dth,   q{ DateTime->new(%$_) },
    $eph,   q{ DateTime->from_epoch(%$_) },
  );

  __PACKAGE__->make_immutable;
}

"make_immutable" gèle les coercitions de tous les types du paquet, donc aucun code extérieur ne peut altérer les coercitions, et cela permet à Type::Tiny de faire des optimisations sur les coercitions, sachant qu'elles ne seront pas modifiées ultérieurement. Vous devriez toujours faire cela à la fin.

La bibliothèque exportera les types Datetime, DatetimeHash et EpochHash. Le type Datetime aura des coercitions depuis Int, Undef, DatetimeHash et EpochHash.

Extension des bibliothèques

Type::Utils fournit une fonction utile "extends".

package My::Types {
  use Type::Library -base;
  use Type::Utils qw( extends );

  BEGIN { extends("Types::Standard") };

  # définissez vos propres types ici
}

La fonction "extends" (que vous devriez généralement utiliser dans un bloc "BEGIN { }") charge non seulement une autre bibliothèque de types, mais ajoute également tous les types qu'elle contient à votre bibliothèque.

Cela signifie que le code utilisant My::Types ci-dessus n'a pas besoin de faire :

use Types::Standard qw( Str );
use My::Types qw( Something );

Il peut simplement faire :

use My::Types qw( Str Something );

Car tous les types de Types::Standard ont été copiés dans My::Types et sont également disponibles là-bas.

"extends" peut recevoir une liste de bibliothèques ; vous pouvez hériter de plusieurs bibliothèques existantes. Elle peut également reconnaître et importer des types des bibliothèques MooseX::Types, MouseX::Types et Specio::Exporter.

Depuis Type::Library 1.012, il existe un raccourci pour "extends".

package My::Types {
  use Type::Library -extends => [ 'Types::Standard' ];

  # définissez vos propres types ici
}

Le drapeau "-extends" prend un tableau de bibliothèques de types à étendre. Il implique automatiquement "-base", vous n'avez donc pas besoin d'utiliser les deux.

Messages d'erreur personnalisés

Une contrainte de type peut avoir des messages d'erreur personnalisés. C'est assez simple :

Type::Tiny->new(
  name       => 'EvenNumber',
  parent     => Types::Standard::Int,
  constraint => sub {
    # dans ce sub, nous n'avons pas besoin de vérifier que $_ est un Int
    # car le parent s'en chargera !

    $_ % 2 == 0
  },
  message   => sub {
    sprintf '%s n'est pas un nombre pair', Type::Tiny::_dd($_);
  },
);

La référence de code du message prend simplement une valeur dans $_ et retourne une chaîne. Elle peut utiliser Type::Tiny::_dd() comme moyen d'afficher joliment une valeur. (Ne soyez pas rebuté par le trait de soulignement dans le nom de la fonction. _dd() fait maintenant partie officiellement prise en charge de l'API de Type::Tiny.)

Vous n'avez pas besoin de fournir une référence de code de message d'erreur à moins que vous ne vouliez vraiment des messages d'erreur personnalisés. Le

default sub devrait être raisonnable.

Inlining

Dans Perl, les appels de sous-routines sont relativement coûteux en termes d'utilisation de mémoire et de CPU. Le type PositiveInt hérite de Int qui hérite de Num qui hérite de Str qui hérite de Defined qui hérite de Item qui hérite de Any.

Vous pourriez donc penser que pour vérifier si $value est un PositiveInt, il faut le vérifier tout le long de la chaîne d'héritage. Mais c'est ici qu'intervient l'une des grandes optimisations de Type::Tiny. Type::Tiny peut enchaîner un ensemble de vérifications avec un eval sous forme de chaîne, et obtenir une seule référence de sous-routine qui peut effectuer toutes les vérifications en une seule fois.

C'est pourquoi, lorsque Type::Tiny vous donne le choix entre utiliser une référence de sous-routine ou une chaîne de code Perl, vous devriez généralement choisir la chaîne de code Perl. Une seule référence de sous-routine peut « casser la chaîne ».

Mais ces chaînes de code Perl générées automatiquement ne sont pas toujours aussi efficaces qu'elles pourraient l'être. Par exemple, imaginez que HashRef soit défini comme suit :

my $Defined = Type::Tiny->new(
  name       => 'Defined',
  constraint => 'defined($_)',
);
my $Ref = Type::Tiny->new(
  name       => 'Ref',
  parent     => $Defined,
  constraint => 'ref($_)',
);
my $HashRef = Type::Tiny->new(
  name       => 'HashRef',
  parent     => $Ref,
  constraint => 'ref($_) eq "HASH"',
);

Alors la vérification combinée est :

defined($_) and ref($_) and ref($_) eq "HASH"

En pratique, c'est encore plus compliqué, car Type::Tiny doit localiser et définir $_ au préalable.

Mais en pratique, la vérification suivante devrait être suffisante :

ref($_) eq "HASH"

Il est possible pour le type HashRef d'avoir plus de contrôle sur la chaîne de code générée.

my $HashRef = Type::Tiny->new(
  name       => 'HashRef',
  parent     => $Ref,
  constraint => 'ref($_) eq "HASH"',
  inlined    => sub {
    my $varname = pop;
    sprintf 'ref(%s) eq "HASH"', $varname;
  },
);

La référence de sous-routine inlinée reçoit le nom d'une variable à vérifier. Cela peut être '$_' ou '$var' ou "$some{deep}{thing}[0]". Comme elle reçoit le nom d'une variable à vérifier, au lieu de vérifier toujours $_, cela permet une vérification très efficace pour les types paramétrés.

Bien que dans ce cas, la référence de sous-routine d'inlining renvoie simplement une chaîne, techniquement elle renvoie une liste de chaînes. S'il y a plusieurs chaînes, Type::Tiny les joindra dans une grande instruction "&&".

À titre spécial, si le premier élément de la liste de chaînes renvoyée est `undef`, alors Type::Tiny substituera la chaîne d'inlining de la contrainte de type parente à sa place. Ainsi, une référence de sous-routine d'inlining pour les nombres pairs pourrait être :

Type::Tiny->new(
  name       => 'EvenNumber',
  parent     => Types::Standard::Int,
  constraint => sub { $_ % 2 == 0 },
  inlined    => sub {
    my $varname = pop;
    return (undef, "$varname % 2 == 0");
  },
);

Même si vous fournissez une référence de sous-routine sous forme de chaîne, une référence de sous-routine d'inlining a le potentiel de générer un code plus efficace, vous devriez donc envisager d'en fournir une.

Pré-déclaration des types

use Type::Library -base,
  -declare => qw( Foo Bar Baz );

Cela déclare les types Foo, Bar et Baz au moment de la compilation afin qu'ils puissent être utilisés en toute sécurité comme des mots nus dans votre bibliothèque de types.

Cela permet également aux types définis récursivement de fonctionner (la plupart du temps !).

use Type::Library -base,
  -declare => qw( NumericArrayRef );
use Types::Standard qw( Num ArrayRef );

__PACKAGE__->add_type(
  name     => NumericArrayRef,
  parent   => ArrayRef->of( Num | NumericArrayRef ),
);

(Prise en charge des définitions de types récursives ajoutée dans Type::Library 1.009_000.)

Types paramétrables

C'est probablement le concept le plus « méta » qui sera abordé. Construire votre propre contrainte de type qui peut être paramétrée comme ArrayRef ou HasMethods.

La contrainte de type que nous allons construire sera MultipleOf[$i] qui vérifie qu'un entier est un multiple de $i.

__PACKAGE__->add_type(
  name       => 'MultipleOf',
  parent     => Int,

  # Cette référence de sous-routine reçoit le contenu des crochets.
  constraint_generator => sub ( $i ) {
    assert_Int $i;
    # doit retourner une référence de sous-routine à utiliser comme contrainte pour le
    # type paramétré
    return sub { $_ % $i == 0 };
  },

  # optionnel mais recommandé
  inline_generator => sub ( $i ) {
    return sub {
      my $varname = pop;
      return (undef, "$varname % $i == 0");
    };
  },

  # probablement la partie la plus complexe
  coercion_generator => sub ( $parent_type, $child_type, $i ) {
    require Type::Coercion;
    return Type::Coercion->new(
      type_coercion_map => [
        Num, qq{ int($i * int(\$_/$i)) }
      ],
    );
  },
);

Nous pouvons maintenant définir un nombre pair comme ceci :

__PACKAGE__->add_type(
  name     => 'EvenNumber',
  parent   => __PACKAGE__->get_type('MultipleOf')->of(2),
  coercion => 1,  # hériter du parent
);

Notez qu'il est possible pour une contrainte de type d'avoir une "constraint" *et* un "constraint_generator".

BaseType          # utilise la contrainte
BaseType[]        # constraint_generator sans arguments
BaseType[$x]      # constraint_generator avec un argument

Dans l'exemple MultipleOf ci-dessus, MultipleOf[] sans nombre lèverait une erreur à cause de assert_Int(shift) qui ne trouve pas d'entier.

Mais il est certainement possible que BaseType[] ait un sens et soit distinct de "BaseType".

Par exemple, Tuple est juste le même que ArrayRef et accepte n'importe quel arrayref comme valide. Mais Tuple[] n'acceptera que des arrayrefs avec zéro élément. (Tout comme Tuple[Any,Any] n'acceptera que des arrayrefs avec deux éléments.)
