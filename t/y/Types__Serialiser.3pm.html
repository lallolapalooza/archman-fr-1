NOM

Types::Serialiser - types de données simples pour les formats de sérialisation courants

SYNOPSIS

DESCRIPTION

Ce module fournit des types de données supplémentaires utilisés par les formats de sérialisation courants tels que JSON ou CBOR. L'idée est d'avoir un dépôt de constantes et de conteneurs simples/petits qui peuvent être partagés par différentes implémentations afin qu'elles deviennent interopérables entre elles.

CONSTANTES SCALAIRES SIMPLES

Les constantes scalaires simples sont des valeurs qui sont surchargées pour agir comme des valeurs Perl simples, mais qui ont un type (de classe) pour les différencier des scalaires Perl normaux. Ceci est nécessaire car elles ont des représentations différentes dans les formats de sérialisation.

Dans ce qui suit, les fonctions avec zéro ou un argument ont un prototype de "()" et "($)", respectivement, agissant donc comme des constantes et des opérateurs unaires.

BOULEENS (classe Types::Serialiser::Boolean)

Ce type n'a que deux instances, vrai et faux. Une représentation naturelle pour celles-ci en Perl est 1 et 0, mais les formats de sérialisation doivent être capables de les différencier des simples nombres.

$Types::Serialiser::true, Types::Serialiser::true
Cette valeur représente la valeur "vraie". Dans la plupart des contextes, elle agit comme le nombre 1. Il vous appartient de décider si vous utilisez la forme variable ($Types::Serialiser::true) ou la forme constante ("Types::Serialiser::true").

La constante est représentée par une référence à un scalaire contenant 1 – les implémentations sont autorisées à tester directement cela.

$Types::Serialiser::false, Types::Serialiser::false
Cette valeur représente la valeur "fausse". Dans la plupart des contextes, elle agit comme le nombre 0. Il vous appartient de décider si vous utilisez la forme variable ($Types::Serialiser::false) ou la forme constante ("Types::Serialiser::false").

La constante est représentée par une référence à un scalaire contenant 0 – les implémentations sont autorisées à tester directement cela.

Types::Serialiser::as_bool $valeur
Convertit un scalaire Perl en booléen, ce qui est une commodité syntaxique utile. Strictement équivalent à : 
$valeur ? $Types::Serialiser::true : $Types::Serialiser::false
$est_bool = Types::Serialiser::is_bool $valeur
Retourne vrai si et seulement si $valeur est soit $Types::Serialiser::true soit $Types::Serialiser::false.

Par exemple, vous pourriez différencier une valeur vrai de Perl d'une "Types::Serialiser::true" en utilisant ceci :

$valeur && Types::Serialiser::is_bool $valeur
$est_vrai = Types::Serialiser::is_true $valeur
Retourne vrai si et seulement si $valeur est $Types::Serialiser::true.
$est_faux = Types::Serialiser::is_false $valeur
Retourne vrai si et seulement si $valeur est $Types::Serialiser::false.

ERREUR (classe Types::Serialiser::Error)

Cette classe n'a qu'une seule instance, "error". Elle est utilisée pour signaler une erreur d'encodage ou de décodage. En CBOR par exemple, un objet qui n'a pas pu être encodé sera représenté par une valeur indéfinie CBOR, qui est représentée par la valeur d'erreur en Perl.

$Types::Serialiser::error, Types::Serialiser::error
Cette valeur représente la valeur "erreur". L'accès aux valeurs de ce type lèvera une exception.

La constante est représentée par une référence à un scalaire contenant "undef" – les implémentations sont autorisées à tester directement cela.

$est_erreur = Types::Serialiser::is_error $valeur
Retourne vrai si et seulement si $valeur est $Types::Serialiser::error.

NOTES POUR LES UTILISATEURS XS

La manière recommandée de détecter si un scalaire est l'un de ces objets est de vérifier si le stash est le stash "Types::Serialiser::Boolean" ou "Types::Serialiser::Error", puis de suivre la référence du scalaire pour voir s'il vaut 1 (vrai), 0 (faux) ou "undef" (erreur).

Bien qu'il soit possible d'utiliser un test isa, comparer directement les pointeurs de stash est plus rapide et garantit le bon fonctionnement.

Pour des raisons historiques, le stash "Types::Serialiser::Boolean" est juste un alias pour "JSON::PP::Boolean". Lors de l'affichage, le nom de la classe sera généralement "JSON::PP::Boolean", mais les tests isa et la comparaison des pointeurs de stash fonctionneront normalement (c'est-à-dire Types::Serialiser::true ISA JSON::PP::Boolean, mais aussi ISA Types::Serialiser::Boolean).

UN PROTOCOLE DE SERIALISATION D'OBJETS GENERIQUE

Cette section explique le protocole de sérialisation d'objets utilisé par CBOR::XS. Il est conçu pour être suffisamment générique pour supporter tout type de sérialiseur d'objets génériques.

Ce protocole est appelé "le protocole de sérialisation d'objets Types::Serialiser".

ENCODAGE

Lorsque l'encodeur rencontre un objet qu'il ne peut pas encoder autrement (par exemple, CBOR::XS peut encoder quelques types spéciaux lui-même et tentera d'abord d'utiliser le protocole de sérialisation spécial "TO_CBOR"), il recherchera la méthode "FREEZE" sur l'objet.

Notez que la méthode "FREEZE" sera normalement appelée *pendant* l'encodage, et *ne DOIT PAS* modifier la structure de données qui est encodée d'une quelconque manière, sous peine de corruption de mémoire ou pire.

Si elle existe, elle sera appelée avec deux arguments : l'objet à sérialiser et une chaîne de caractères constante indiquant le nom du modèle de données. Par exemple, CBOR::XS utilise "CBOR", et les modules JSON et JSON::XS (ou tout autre sérialiseur JSON) utiliseraient "JSON" comme deuxième argument.

La méthode "FREEZE" peut alors retourner zéro ou plusieurs valeurs pour identifier l'instance de l'objet. Le sérialiseur est alors censé encoder le nom de la classe et toutes ces valeurs de retour (qui doivent être encodables dans le format) en utilisant la forme appropriée pour les objets Perl. En CBOR par exemple, il existe un numéro de tag enregistré pour les objets Perl encodés.

Les valeurs retournées par "FREEZE" doivent être sérialisables avec le sérialiseur qui l'appelle. Par conséquent, il est recommandé d'utiliser des types simples tels que des chaînes de caractères et des nombres, et éventuellement des références de tableaux et des hachages (en gros, le modèle de données JSON). Vous pouvez toujours utiliser un format plus complexe pour un modèle de données spécifique en vérifiant le deuxième argument, le modèle de données.

Le "modèle de données" n'est pas la même chose que le "format de données" - le modèle de données indique quels types et quelles sortes de valeurs de retour peuvent être retournés par "FREEZE". Par exemple, en "CBOR", il est permis de retourner des valeurs CBOR taguées, tandis que JSON ne les supporte pas du tout, donc "JSON" serait un nom de modèle de données valide (mais trop limité) pour "CBOR::XS". De même, un format de sérialisation qui supporte un modèle de données plus ou moins identique à JSON pourrait utiliser "JSON" comme modèle de données sans rien perdre.

DÉCODAGE

Lorsque le décodeur rencontre alors un tel objet Perl encodé, il devrait rechercher la méthode "THAW" sur le nom de classe stocké, et l'invoquer avec le nom de classe, la chaîne constante pour identifier le modèle de données/format de données, et toutes les valeurs de retour renvoyées par "FREEZE".

EXEMPLES

Voir la section "SERIALISATION D'OBJETS" dans la page de manuel CBOR::XS pour plus de détails, un exemple d'implémentation, et des exemples de code.

Voici une paire d'exemples de méthodes "FREEZE"/"THAW" :

sub My::Object::FREEZE {
   my ($self, $model) = @_;
   ($self->{type}, $self->{id}, $self->{variant})
}
sub My::Object::THAW {
   my ($class, $model, $type, $id, $variant) = @_;
   $class->new (type => $type, id => $id, variant => $variant)
}
