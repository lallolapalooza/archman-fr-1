NOM

Type::Tiny::Manual::Params - informations avancées sur Type::Params

MANUEL

Pour commencer avec Type::Params, veuillez lire Type::Tiny::Manual::UsingWithMoo qui couvrira une grande partie des bases, même si vous n'utilisez pas Moo.

"multiple"

L'option "multiple" vous permet de spécifier plusieurs façons d'appeler une sous-routine.

signature_for repeat_string => (
  multiple => [
    { positional => [ Str, Int ] },
    { named => [ string => Str, count => Int ], named_to_list => true },
  ],
);

sub repeat_string ( $string, $count ) {
  return $string x $count;
}

repeat_string(            "Hello",          42  );    # fonctionne
repeat_string(  string => "Hello", count => 42  );    # fonctionne
repeat_string({ string => "Hello", count => 42 });    # fonctionne
repeat_string( qr/hiya/ );                            # échoue

Elle combine plusieurs vérifications et essaie chacune jusqu'à ce qu'une fonctionne.

"list_to_named"

Dans de nombreux cas, les conventions d'appel multiples offertes par "multiple" peuvent être implémentées plus facilement en utilisant "list_to_named".

signature_for repeat_string => (
  list_to_named => true,
  named         => [ string => Str, count => Int ],
  named_to_list => true,
);

sub repeat_string ( $string, $count ) {
  return $string x $count;
}

# Façons standards d'appeler la fonction :
repeat_string(  string => "Hello", count => 42  );
repeat_string({ string => "Hello", count => 42 });

# Celles-ci devraient aussi fonctionner :
repeat_string( "Hello", count => 42 );
repeat_string( "Hello", { count => 42 } );
repeat_string( 42, string => "Hello" );
repeat_string( 42, { string => "Hello" } );
repeat_string( "Hello", 42 );

# Ceci ne fonctionnera pas pour le moment car "42" apparaît en premier, il est donc considéré comme
# la chaîne, mais "Hello" n'est pas un entier valide !
repeat_string( 42, "Hello" );

"list_to_named" fonctionne en trois étapes. Lors de la recherche de la table de hachage ou du hachage de paramètres nommés, s'il y a d'autres paramètres avant, ceux-ci sont mis de côté dans une liste de paramètres positionnels "sournois".

Plus tard, lors de la validation des paramètres nommés, si certains semblent manquants, la liste des paramètres positionnels sournois est examinée et, si possible, le paramètre est pris à partir de là.

Enfin, après que tous les paramètres nommés ont été traités, s'il reste des paramètres positionnels qui n'étaient pas nécessaires, une erreur est déclenchée.

"signature"

"signature" permet de définir la signature à l'intérieur de la sous-routine elle-même, potentiellement à la volée, ce qui est parfois utile.

Au lieu de ceci :

signature_for foobar => (
  positional => [ Int, Str ],
);

sub foobar ( $foo, $bar ) {
  ...;
}

Vous faites ceci :

sub foobar {
  my $check = signature( positional => [ Int, Str ] );
  my ( $foo, $bar ) = $check->( @_ );
  ...;
}

Ou utilisez "state $check" si vous savez que la vérification sera la même à chaque fois.

Fonctions versus Méthodes

Pour les sous-routines destinées à être appelées comme fonctions :

signature_for my_sub => ( method => false, ... );

signature_for my_sub => ( ... ); # c'est le défaut de toute façon

Pour les sous-routines destinées à être appelées comme méthodes sur un objet béni :

signature_for my_method => ( method => Object, ... );

Et pour les sous-routines destinées à être appelées comme méthodes sur une classe :

signature_for my_method => ( method => ClassName, ... );

signature_for my_method => ( method => Str, ... );  # plus rapide, moins lisible

Les éléments suivants sont également autorisés, indiquant que la sous-routine est destinée à être appelée comme méthode, mais vous ne voulez pas effectuer de vérifications de type sur l'invocant :

signature_for my_method => ( method => builtin::true, ... );

signature_for my_method => ( method => 1, ... );

Des raccourcis sont disponibles :

use Type::Params qw( signature_for_func signature_for_method );

signature_for_func my_function => ( ... );

signature_for_method my_method => ( ... );

Paramètres Mixtes Nommés et Positionnels

Les options "head" et "tail" permettent des paramètres positionnels requis au début ou à la fin d'une liste de paramètres nommés :

signature_for my_func => (
  head  => [ Int ],
  named => [
    foo => Int,
    bar => Optional[Int],
    baz => Optional[Int],
  ],
);

my_func( 42, foo => 21 );                 # ok
my_func( 42, foo => 21, bar  => 84 );     # ok
my_func( 42, foo => 21, bar  => 10.5 );   # pas ok
my_func( 42, foo => 21, quux => 84 );     # pas ok

Alternativement, "list_to_named" (voir ci-dessus) peut être utile.

Signatures Proper

Ne souhaiteriez-vous pas que vos sous-routines puissent ressembler à cela ?

sub set_name ( Object $self, Str $name ) {
  $self->{name} = $name;
}

Eh bien, voici quelques solutions pour les signatures de sous-routines qui fonctionnent avec Type::Tiny...

Zydeco

Zydeco est une boîte à outils de syntaxe OO Perl avec le support de Type::Tiny intégré partout.

package MyApp {
  use Zydeco;

  class Person {
    has name ( type => Str );

    method rename ( Str $new_name ) {
      printf( "%s sera maintenant appelé %s\n", $self->name, $new_name );
      $self->name( $new_name );
    }

    coerce from Str via {
      $class->new( name => $_ )
    }
  }

  class Company {
    has owner ( type => 'Person' );
  }
}

my $acme = MyApp->new_company( owner => "Robert" );
$acme->owner->rename( "Bob" );

Kavorka

Kavorka est une implémentation de signatures de sous-routines écrite pour utiliser nativement "dwim_type" de Type::Utils pour les contraintes de type, et profiter des fonctionnalités de Type::Tiny telles que l'inlining et les coercions.

method set_name ( Str $name ) {
  $self->{name} = $name;
}

Les signatures de Kavorka offrent beaucoup plus de flexibilité et un peu plus de vitesse que Type::Params. (La vitesse provient de l'inlining de presque toutes les vérifications de type dans le corps de la sous-routine déclarée.)

Kavorka inclut également la prise en charge de la vérification de type de la valeur retournée.

Kavorka peut également être utilisé dans le cadre de Moops, un cadre plus large pour la programmation orientée objet en Perl.

Function::Parameters

Function::Parameters offre le support pour Type::Tiny et MooseX::Types.

use Types::Standard qw( Str );
use Function::Parameters;

method set_name ( Str $name ) {
    $self->{name} = $name;
}

Attribute::Contract

Kavorka et Function::Parameters nécessitent une version relativement récente de Perl. Attribute::Contract prend en charge les versions plus anciennes en utilisant beaucoup moins de magie.

Vous voulez Attribute::Contract 0.03 ou supérieur.

use Attribute::Contract -types => [qw/Object Str/];

sub set_name :ContractRequires(Object, Str) {
    my ($self, $name) = @_;
    $self->{name} = $name;
}

Attribute::Contract inclut également la prise en charge de la vérification de type de la valeur retournée.

Type::Params versus X

Params::Validate

Type::Params n'est pas vraiment un remplacement direct pour Params::Validate ; l'API diffère trop pour l'affirmer. Pourtant, il remplit une tâche similaire, il est donc logique de les comparer.

  • Type::Params sera généralement plus rapide si vous avez une sous-routine qui est appelée de manière répétée, mais peut être un peu plus lente que Params::Validate pour les sous-routines qui ne sont appelées que quelques fois. C'est parce qu'il effectue un certain travail la première fois que votre sous-routine est appelée pour rendre les appels subséquents

NAME

Type::Tiny::Manual::Params – comparing parameter-validation modules

MANUAL

This document compares Type::Tiny's parameter validation system to some other modules that provide similar functionality.

Params::Validate

Params::Validate is a venerable old module that has been around for a long time. It's generally considered to be slow, but it's also quite flexible.

  • Params::Validate is generally considered to be slow.
  • It has a lot of features, but they are often implemented in a somewhat clunky way.
  • It doesn't have a built-in way of dealing with type constraints. You have to use constants such as "ARRAYREF", "HASHREF", etc.
  • It doesn't appear to have a particularly natural way of validating a mix of positional and named parameters.
  • It doesn't have a way of coercing parameters.

Type::Params

Type::Params is a module that provides a way of validating parameters to subroutines using Type::Tiny type constraints.

  • It uses Type::Tiny's type constraints, so you can use the same constraints for both parameters and attributes.
  • It allows you to mix positional and named parameters.
  • It supports slurpy parameters.
  • It allows you to coerce parameters. For example, if you expect a Path::Tiny object, you could coerce it from a string.
  • If you are primarily writing object-oriented code, using Moose or similar, and you are using Type::Tiny type constraints for your attributes, then using Type::Params allows you to use the same constraints for method calls.
  • Type::Params comes bundled with Types::Standard, which provides a much richer vocabulary of types than the type validation constants that come with Params::Validate. For example, Types::Standard provides constraints like "ArrayRef[Int]" (an arrayref of integers), while the closest from Params::Validate is "ARRAYREF", which you'd need to supplement with additional callbacks if you wanted to check that the arrayref contained integers.

    Whatsmore, Type::Params doesn't just work with Types::Standard, but also any other Type::Tiny type constraints.

Params::ValidationCompiler

Params::ValidationCompiler does basically the same thing as Type::Params.

  • Params::ValidationCompiler and Type::Params are likely to perform fairly similarly. In most cases, recent versions of Type::Params seem to be slightly faster, but except in very trivial cases, you're unlikely to notice the speed difference. Speed probably shouldn't be a factor when choosing between them.
  • Type::Params's syntax is more compact: 
    state $check = signature(
  pos => [
    Object,
    Optional[Int],
    Slurpy[ArrayRef],
  ],
);

    Versus:

    state $check = validation_for(
  params => [
    { type => Object },
    { type => Int,      optional => 1 },
    { type => ArrayRef, slurpy => 1 },
  ],
);
  • Params::ValidationCompiler probably has slightly better exceptions.
