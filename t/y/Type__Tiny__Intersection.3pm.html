Type::Tiny::Intersection(3) Documentation Perl fournie par l'utilisateur Type::Tiny::Intersection(3)

NOM

Type::Tiny::Intersection - contraintes de type intersection

SYNTAXE

Utilisation via le surcharge de l'opérateur "&" :

package Local::Stash {
  use Moo;
  use Types::Common qw( LowerCaseStr StrLength );

  has identifier => (
    is   => 'ro',
    isa  => (LowerCaseStr) & (StrLength[4, 8]),
  );
}

my $x = Local::Stash->new( data => {} );  # pas ok
my $y = Local::Stash->new( data => [] );  # pas ok

Il est conseillé d'entourer chaque type à intersecter de parenthèses pour éviter que Perl n'interprète le "&" comme le sigil d'une référence de sous-routine.

Utilisation de l'interface orientée objet de Type::Tiny::Intersection :

package Local::Stash {
  use Moo;
  use Types::Common qw( LowerCaseStr StrLength );
  use Type::Tiny::Intersection;

  my $ShortLcStr = Type::Tiny::Intersection->new(
    name             => 'AnyData',
    type_constraints => [ LowerCaseStr, StrLength[4, 8] ],
  );

  has identifier => (
    is   => 'ro',
    isa  => $ShortLcStr,
  );
}

Utilisation de l'interface fonctionnelle de Type::Utils :

package Local::Stash {
  use Moo;
  use Types::Common qw( LowerCaseStr StrLength );
  use Type::Utils;

  my $ShortLcStr = intersection ShortLcStr => [ LowerCaseStr, StrLength[4, 8] ];

  has identifier => (
    is   => 'ro',
    isa  => $ShortLcStr,
  );
}

STATUT

Ce module est couvert par la politique de stabilité de Type-Tiny.

DESCRIPTION

Contraintes de type d'intersection.

Les contraintes de type d'intersection ne sont pas très utiles souvent. Considérons l'intersection de HashRef et ArrayRef. Une valeur ne passera que si elle est à la fois une référence de table de hachage et une référence de tableau. Étant donné qu'aucune de ces contraintes de type n'accepte "undef" ou des objets surchargés, aucune valeur possible ne peut satisfaire les deux.

Ce qui ne veut pas dire que les intersections ne sont jamais utiles, mais cela arrive assez rarement.

Ce paquet hérite de Type::Tiny ; voir ce dernier pour la plupart des documentations. Les principales différences sont listées ci-dessous :

Constructeur

Le constructeur "new" de Type::Tiny fonctionne toujours, bien sûr. Mais il existe également :

new_by_overload(%attributs)
Comme le constructeur "new", mais renverra parfois une autre contrainte de type qui n'est pas strictement une instance de Type::Tiny::Intersection, mais qui encapsule néanmoins la même signification. Ce constructeur est utilisé par la surcharge de l'opérateur "&" de Type::Tiny.

Attributs

"type_constraints"
Tableau de contraintes de type.

Lorsqu'il est passé au constructeur, si l'une des contraintes de type dans l'intersection est elle-même une contrainte de type d'intersection, elle est "déploiée" dans la nouvelle intersection.

"constraint"
Contrairement à Type::Tiny, vous ne *pouvez pas* passer une sous-routine de contrainte au constructeur. Utilisez plutôt la valeur par défaut.
"inlined"
Contrairement à Type::Tiny, vous ne *pouvez pas* passer une sous-routine d'intégration au constructeur. Utilisez plutôt la valeur par défaut.
"parent"
Contrairement à Type::Tiny, vous ne *pouvez pas* passer une sous-routine d'intégration au constructeur. Un parent sera plutôt calculé automatiquement.

(Techniquement, n'importe lequel des types de l'intersection pourrait être traité comme un type parent ; nous choisissons arbitrairement le premier.)

Méthodes

stringifies_to($constraint)
Voir Type::Tiny::ConstrainedObject.
numifies_to($constraint)
Voir Type::Tiny::ConstrainedObject.
"with_attribute_values($attr1 => $constraint1, ...)"
Voir Type::Tiny::ConstrainedObject.

Surcharge

•
La transformation en tableau appelle "type_constraints".
