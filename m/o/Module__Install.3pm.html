Module::Install(3) Documentation Perl fournie par l'utilisateur Module::Install(3)

NOM

Module::Install - Installateur de modules Perl autonome et extensible

SYNTAXE

Dans votre Makefile.PL : (Utilisation recommandée)

use inc::Module::Install;
# Définir les métadonnées
name           'Votre-Module';
all_from       'lib/Votre/Module.pm';
# Dépendances spécifiques
requires       'File::Spec'  => '0.80';
test_requires  'Test::More'  => '0.42';
recommends     'Text::CSV_XS'=> '0.50';
no_index       'directory'   => 'demos';
install_script 'myscript';
WriteAll;

Mettre à niveau rapidement un ancien installateur ExtUtil::MakeMaker :

use inc::Module::Install;
WriteMakefile( ... );

AVERTISSEMENT

Veuillez noter que bien que Module::Install ait été pionnier dans de nombreuses idées géniales en son temps, ses principaux avantages ont été mieux réalisés par l'outil d'auteur Dist::Zilla, et ses variantes Dist::Milla et Minilla. Ces outils permettent à l'auteur de construire et de maintenir des distributions avec la commodité DWIM (Do What I Mean), tandis que la distribution est installée directement par ExtUtils::MakeMaker ou des outils d'installation similaires, évitant ainsi la complexité de regrouper l'installateur. Dist::Zilla dispose en outre d'un système de plugins plus robuste qui facilite le suivi des modifications apportées à la spécification CPAN::Meta et l'ajout de nouvelles fonctionnalités. L'utilisation de Module::Install pour de nouvelles distributions est donc déconseillée par les mainteneurs.

DESCRIPTION

Module::Install est un package pour écrire des installateurs pour les distributions CPAN (ou similaires à CPAN) qui sont propres, simples, minimalistes, agissent de manière strictement correcte avec ExtUtils::MakeMaker, et fonctionneront sur toute installation Perl version 5.005 ou plus récente.

L'intention est de rendre aussi facile que possible pour les auteurs CPAN (et en particulier pour les auteurs CPAN débutants) d'avoir des installateurs qui suivent toutes les meilleures pratiques pour l'installation des distributions, mais qui impliquent autant de DWIM (Do What I Mean) que possible lors de leur écriture.

Écrire des installateurs Module::Install

Le moyen le plus rapide de commencer avec Module::Install est de copier la "SYNTAXE" ci-dessus et de l'enregistrer sous le nom de votre propre Makefile.PL. Modifiez ensuite le fichier pour l'adapter à votre cas particulier, en utilisant la liste des commandes documentées dans "COMMANDES_COMMUNES" ci-dessous.

Si tout ce que vous voulez faire est d'écrire un installateur, allez-y maintenant. Vous n'avez pas vraiment besoin du reste de cette description, sauf si vous êtes intéressé par les détails.

Comment ça marche

La motivation derrière Module::Install est que les distributions doivent interagir avec un grand nombre de versions différentes de Perl et de l'infrastructure d'installation de modules, principalement CPAN.pm, CPANPLUS.pm, ExtUtils::MakeMaker et Module::Build.

Ceux-ci ont accumulé des profils de fonctionnalités et de bugs **très** variés au fil des ans, et il est maintenant très difficile d'écrire un installateur qui fonctionnera correctement en utilisant uniquement les versions installées de ces modules.

Par exemple, la version de CPAN.pm fournie avec Perl 5.005 a maintenant plus de 5 ans et est considérée comme très boguée, pourtant elle existe encore sur un nombre considérable de machines héritées.

Plutôt que d'essayer de cibler un installateur spécifique et/ou de vous faire ajouter des expressions de contournement complexes à chaque morceau de code d'installation que vous écrivez, Module::Install copiera une partie de lui-même dans chaque distribution de module qu'il crée.

Cela permet d'utiliser de nouvelles améliorations dans vos installateurs, quelle que soit l'ancienneté du système sur lequel une distribution est installée, au prix d'une légère augmentation de la taille de votre distribution.

Historique

Ce module a été initialement écrit par Brian Ingerson comme un remplacement intelligent et direct pour ExtUtils::MakeMaker.

Pour plus d'informations, voir la section de Brian Creating Module Distributions with Module::Install dans le numéro de juin 2003 de The Perl Journal (http://www.drdobbs.com/web-development/creating-module-distributions-with-modul/184416018)

Pour **beaucoup** plus d'informations, et quelques opinions personnelles sur le module et sa création, voir Module::Install::Philosophy.

COMMANDES_COMMUNES

Les commandes suivantes sont les plus couramment utilisées dans les installateurs.

Ce n'est en aucun cas une liste exhaustive, car de nombreux plugins fournissent des commandes pour travailler avec plus de détails que ce dont vous auriez normalement besoin.

nom

name 'Mon-Module';

La commande name est une commande obligatoire, généralement la première.

Elle fournit le nom de votre distribution, qui pour un module comme Votre::Module serait normalement "Votre-Module".

Ce schéma de nommage n'est pas gravé dans le marbre et vous devriez noter que les distributions constituent en fait un schéma de nommage distinct de celui des modules.

Par exemple, les modules LWP sont inclus dans une distribution nommée "libwww-perl".

all_from

all_from 'lib/Mon/Module.pm';

Pour la plupart des distributions Perl simples qui présentent un module ou une classe dominant comme base, vous pouvez obtenir le maximum de fonctionnalité Do What I Mean en utilisant la commande all_from, qui tentera d'extraire autant de métadonnées que possible du code Perl et du POD dans ce module principal.

Fonctionnellement, "all_from" est équivalent à "abstract_from" + "author_from" + "version_from" + "license_from" + "perl_version_from". Voir ci-dessous pour les détails.

Si l'une de ces valeurs est déjà définie **avant** que "all_from" ne soit utilisée, elles seront conservées et **ne** seront **pas** écrasées.

abstract

abstract 'Cette distribution fait quelque chose';

Toutes les distributions ont un résumé (abstract), une brève description de la distribution dans son ensemble. Il fait généralement entre 30 et 70 caractères.

La commande "abstract" est utilisée pour définir explicitement le résumé de la distribution, du moins en ce qui concerne le fichier de métadonnées de la distribution.

abstract_from

abstract_from 'lib/Mon/Module.pm';

La commande "abstract_from" récupère le résumé d'un fichier particulier contenu dans le package de distribution. Le plus souvent, cela se fait à partir du module principal, où "Module::Install" lira le POD et utilisera tout ce qui se trouve dans la section "=head1 NAME" (avec le nom du module retiré si nécessaire).

"abstract_from" est défini dans le cadre de "all_from".

author

author 'Adam Kennedy <adamk@cpan.org>';

Les métadonnées de la distribution contiennent des informations sur l'auteur principal de la distribution, ou le mainteneur principal si l'auteur d'origine n'est plus impliqué. Elle doit généralement être spécifiée sous la forme d'une adresse e-mail.

Si vous ne souhaitez pas divulguer une adresse e-mail réelle, vous devriez utiliser l'adresse "CPANID@cpan.org" que vous recevez automatiquement lorsque vous obtenez votre compte PAUSE.

La commande "author" est utilisée pour définir explicitement cette valeur.

author_from

author_from 'lib/Mon/Module.pm';

La commande "author_from" récupère l'auteur d'un fichier particulier contenu dans le package de distribution. Le plus souvent, cela se fait en utilisant le module principal, où Module::Install lira le POD et utilisera tout ce qu'il peut trouver dans la section "=head1 AUTHOR".

version

version '0.01';

La directive "version" est utilisée pour spécifier la version de la distribution, la distinguant de la version de tout module à l'intérieur de la distribution.

Cependant, dans presque tous les cas, vous souhaiterez qu'elle corresponde à la version du module principal de la distribution, ce que vous pouvez faire en utilisant "version_from".

version_from

version_from 'lib/My/Module.pm';

La directive "version_from" récupère la version de la distribution à partir d'un fichier spécifique contenu dans le paquet de distribution. Le plus souvent, cela se fait à partir du module principal.

"version_from" recherchera la première fois que $VERSION est défini et utilisera la même valeur, en utilisant une technique compatible avec d'autres outils d'analyse de version de modules.

license

license 'perl';

La directive "license" spécifie la licence de la distribution.

Dans la plupart des cas, cette valeur sera 'perl', ce qui signifie « identique à celle de Perl lui-même ». D'autres valeurs autorisées incluent 'gpl', 'lgpl', 'bsd', 'MIT' et 'artistic'.

Cette valeur est toujours considérée comme un résumé, et il est courant d'inclure un fichier LICENSE dans la distribution, qui contient la licence complète de la distribution.

Il est également rappelé que si la distribution est destinée à être téléchargée sur CPAN, elle doit être sous une licence open source conforme à l'OSI. Les logiciels commerciaux ne sont pas autorisés sur CPAN.

license_from

license_from 'lib/My/Module.pm';

La directive "license_from" récupère la licence de la distribution à partir d'un fichier spécifique contenu dans le paquet de distribution. Le plus souvent, cela se fait à partir du module principal.

"license_from" recherchera dans le fichier spécifié une section de licence ou de copyright et cherchera diverses chaînes identifiant le type général de licence.

Actuellement, il ne prend en charge que les 6 valeurs mentionnées dans le résumé de "license".

perl_version

perl_version '5.006';

La directive "perl_version" est utilisée pour spécifier la version minimale de l'interprétation Perl requise par votre distribution.

Lors de la spécification de la version, vous devez essayer d'utiliser la chaîne de version normalisée. Les parties de version de Perl sont à 3 chiffres, donc une dépendance Perl 5.6 deviendra '5.006' et une version Perl 5.10.2 deviendra '5.010002'.

perl_version_from

perl_version_from 'lib/My/Module.pm'

La directive "perl_version_from" récupère la version minimale de l'interprétation Perl à partir d'un fichier spécifique contenu dans le paquet de distribution. Le plus souvent, cela se fait à partir du module principal.

La version minimale est détectée en recherchant les appels à la pragma "use 5.xxx" dans le fichier du module.

recommends

recommends 'Text::CSV_XS' => '0.50'

La directive "recommends" indique un module d'exécution optionnel qui fournit des fonctionnalités supplémentaires. Les dépendances recommandées ne sont pas nécessaires pour construire ou tester votre distribution, mais sont considérées comme « agréables à avoir ».

Comme pour "requires", la dépendance est basée sur un module, pas sur une distribution. Une version zéro indique que n'importe quelle version du module est recommandée.

requires

requires 'List::Util' => 0;
requires 'LWP'        => '5.69';

La directive "requires" indique une dépendance d'exécution normale de votre distribution sur un autre module. La plupart des distributions incluront une de ces instructions, indiquant les modules nécessaires pour CPAN (ou autres).

Une dépendance "requires" peut être énoncée comme suit : « Si vous voulez installer et utiliser cette distribution, vous devez d'abord installer ces modules ».

Notez que la dépendance est basée sur un module, pas sur une distribution. Cela garantit que votre dépendance est toujours correcte, même si le module est déplacé ou mélangé avec une autre distribution, ce qui est parfois possible.

Une dépendance de version zéro indique que n'importe quelle version du module est suffisante. Les versions doivent généralement être citées pour plus de clarté.

test_requires

test_requires 'Test::More' => '0.47';

La directive "test_requires" indique une dépendance de script de test pour votre distribution. Le format de spécification est identique à celui de "requires".

La directive "test_requires" est différente de "requires" en ce qu'elle indique un module qui n'est nécessaire que pendant le test de la distribution (souvent une courte période de temps) mais qui n'est pas nécessaire après l'installation de la distribution.

La directive "testrequires" est utilisée pour permettre à l'installeur d'avoir de la flexibilité dans la manière dont il fournit le module, et pour permettre aux empaqueteurs (Debian, FreeBSD, ActivePerl, etc.) de ne conserver que les dépendances nécessaires à l'exécution en temps réel.

La directive "include" est parfois utilisée en conjonction avec "test_requires" pour inclure un module bien testé dans le paquet de distribution lui-même, afin que l'utilisateur l'installe directement depuis CPAN.

configure_requires

configure_requires 'File::Spec' => '0.80';

La directive "configure_requires" indique une dépendance de configuration pour votre distribution. Le format de spécification est identique à celui de "requires".

La directive "configure_requires" est utilisée pour résoudre le dilemme de la façon d'utiliser un module CPAN dans votre Makefile.PL, alors que vous devez charger Makefile.PL (et donc le module CPAN) pour savoir que vous en avez besoin.

Traditionnellement, cela ne pouvait pas être résolu et les scripts Makefile.PL devaient donc s'appuyer sur des approches de dénominateur commun, ou inclure ces dépendances avec la commande "include".

La directive "configure_requires" crée une entrée dans la clé spéciale "configure_requires: dans le fichier META.yml de la distribution.

Bien qu'une grande partie de META.yml soit considérée comme consultative, un client CPAN traitera le contenu de "configure_requires: comme faisant autorité et installera les modules mentionnés avant d'exécuter "Makefile.PL" (à partir duquel il détermine ensuite d'autres dépendances).

Veuillez noter que la prise en charge de "configure_requires: dans les clients CPAN n'est pas encore complètement complète au moment de la rédaction et ne peut pas encore être entièrement fiable.

Comme Module::Install lui-même ne prend en charge que 5.005, une instruction équivalente de "configure_requires( perl => '5.005' ); " sera ajoutée silencieusement à votre distribution.

requires_external_bin

requires_external_bin 'cvs';

Dans le cadre de son rôle de langage de liaison principal, de nombreux modules Perl exécutent des commandes ou des programmes sur le système hôte.

La directive "requires_external_bin" est utilisée pour vérifier qu'une commande particulière est disponible sur le système hôte.

Alors qu'un module Perl manquant est résoluble au moment de la compilation, un binaire externe manquant ne l'est pas, et donc l'exécution de "Makefile.PL" échouera avec un résultat 'NA' (Non Applicable).

À l'avenir, cette commande ajoutera également des informations supplémentaires aux métadonnées de la distribution, permettant aux auto-packageurs spécifiques aux systèmes d'exploitation de découvrir automatiquement les paquets non-Perl nécessaires en tant que dépendances.

install_script

# The following are equivalent
install_script 'script/scriptname'

La directive "install_script" fournit un support pour l'installation de scripts qui deviendront des commandes dans le terminal, à la fois sous Unix et sous Windows (dans ce dernier cas, via un fichier .bat).

Notez qu'il est courant de ne pas ajouter un suffixe .pl à ces scripts, afin qu'ils soient plus naturels à utiliser.

Dans l'exemple ci-dessus, le programme script/scriptname pourrait être exécuté après l'installation simplement en faisant ce qui suit :

> scriptname
Running scriptname 0.01...
>

Conformément à la convention, les scripts doivent être placés dans un répertoire /script à l'intérieur de votre distribution. Pour prendre en charge moins de types d'entrée, si un script est situé dans le répertoire script, vous ne devez vous y référer que par son nom.

# The following are equivalent
install_script 'foo';
install_script 'script/foo';

no_index

no_index directory => 'examples';
no_index package   => 'DB';

Souvent, une distribution fournit des scripts d'exemple ou des modules de test (.pm) ainsi que les modules de librairie réels.

Dans presque tous les cas, vous ne voulez pas que ceux-ci soient indexés dans l'index CPAN, les archives principales de Perl.

ist, ou affiché sur https://metacpan.org/ ou http://search.cpan.org/ sites, vous voulez simplement qu'ils vous accompagnent.

La commande "no_index" est utilisée pour indiquer les répertoires ou les fichiers qui pourraient contenir des fichiers .pm non-bibliothèque ou d'autres fichiers que l'indexeur CPAN et les sites tels que https://metacpan.org/ ou http://search.cpan.org/ devraient explicitement ignorer.

La situation la plus courante est d'ignorer les répertoires d'exemples ou de démonstration, mais une variété de situations différentes peut nécessiter une entrée "no_index".

Une autre utilisation courante pour "no_index" est d'empêcher l'indexeur PAUSE de se plaindre lorsque votre module apporte des modifications à l'intérieur d'un bloc « package DB ». Ceci est utilisé pour interagir avec le débogueur de certaines manières spécifiques.

Consultez la documentation de META.yml pour plus de détails sur les valeurs autorisées pour "no_index".

Les répertoires inc, t et share (si "install_share" est utilisé) sont automatiquement mis en « no_index » pour vous s'ils sont trouvés et ne nécessitent pas de commande explicite.

Pour résumer, si vous pouvez le voir sur https://metacpan.org/ ou http://search.cpan.org/ et que vous ne devriez pas pouvoir le voir, vous avez besoin d'une entrée "no_index" pour le supprimer.

installdirs, install_as_*

installdirs 'site'; # le défaut
install_as_core;    # alias pour installdirs 'perl'
install_as_cpan;    # alias pour installdirs 'site'
install_as_site;    # alias pour installdirs 'site'
install_as_vendor;  # alias pour installdirs 'vendor'

Les commandes "installdirs" et "install_as" spécifient l'emplacement où le module doit être installé ; ceci est l'équivalent de l'option "INSTALLDIRS" d'ExtUtils::MakeMaker. Pour presque tous les modules réguliers, le défaut est recommandé, et n'a pas besoin d'être modifié. Les modules à double vie (noyau et CPAN), ainsi que les modules spécifiques au vendeur, peuvent avoir besoin d'utiliser les autres options.

En cas de doute, n'utilisez pas cette option.

WriteAll

La commande "WriteAll" est généralement la dernière commande du fichier ; elle écrit META.yml et Makefile afin que l'utilisateur puisse exécuter la séquence d'installation "make", "make test", "make install".

EXTENSIONS

Toutes les extensions appartiennent à l'espace de noms **Module::Install::***, et héritent de **Module::Install::Base**. Il existe trois catégories d'extensions :

Extensions Standard

Les méthodes définies par une extension standard peuvent être appelées comme des fonctions simples dans Makefile.PL ; un objet singleton correspondant sera automatiquement créé. D'autres extensions peuvent également invoquer ses méthodes comme leurs propres méthodes :

# délègue à $other_extension_obj->method_name(@args)
$self->method_name(@args);

Lors de la première invocation d'une méthode d'extension, une version sans POD de celle-ci sera incluse dans le répertoire inc/Module/Install/, et devient *fixe* - c'est-à-dire, même si l'utilisateur avait installé une version différente de la même extension, celle incluse sera toujours utilisée à la place.

Si l'auteur souhaite mettre à jour les extensions dans inc/ avec celles installées, il suffit de relancer "perl Makefile.PL" ; **Module::Install** détermine si vous êtes un auteur par l'existence du répertoire inc/.author/. Les utilisateurs finaux peuvent réinitialiser tout et devenir auteurs en tapant "make realclean" et "perl Makefile.PL".

Extensions Privées

Ces extensions prennent la forme de **Module::Install::PRIVATE** et **Module::Install::PRIVATE::***.

Les auteurs sont encouragés à placer toutes les magies existantes de Makefile.PL dans de telles extensions (par exemple, Module::Install::PRIVATE pour les parties communes ; Module::Install::PRIVATE::DISTNAME pour les fonctions spécifiques à une distribution).

Les extensions privées ne doivent pas être publiées sur CPAN ; placez-les simplement quelque part dans votre @INC, sous le répertoire "Module/Install/", et commencez à utiliser leurs fonctions dans Makefile.PL. Comme les extensions standard, elles ne seront jamais installées sur la machine de l'utilisateur final, et donc ne entreront jamais en conflit avec les extensions privées d'autres personnes.

Extensions Administratives

Les extensions sous l'espace de noms **Module::Install::Admin::*** ne sont jamais incluses avec la distribution. Leurs méthodes ne sont pas directement accessibles depuis Makefile.PL ou d'autres extensions ; elles sont invoquées comme suit :

# délègue à $other_admin_extension_obj->method_name(@args)
$self->admin->method_name(@args);

Ces méthodes ne prennent effet que pendant l'exécution de l'*initialisation*, lorsque inc/ est en cours de remplissage ; elles sont ignorées pour les utilisateurs finaux. Encore une fois, pour réinitialiser tout, lancez simplement "perl Makefile.PL" en tant qu'auteur.

Les scripts (généralement des one-liners dans Makefile) qui souhaitent distribuer des fonctions **AUTOLOAD** dans des extensions administratives (au lieu d'extensions standard) devraient utiliser le module **Module::Install::Admin** directement. Voir Module::Install::Admin pour les détails.

EXTENSIONS

Des informations détaillées sont fournies pour tous (certains) des modules pertinents via leur propre documentation POD.

Module::Install::AutoInstall

Fournit auto_install() pour télécharger et installer automatiquement les prérequis.

Module::Install::Base

La classe de base pour toutes les extensions

Module::Install::Bundle

Fournit la famille de commandes "bundle", vous permettant d'intégrer une autre distribution CPAN dans votre distribution.

Module::Install::Fetch

Gère la récupération au moment de l'installation de fichiers à partir de serveurs distants via FTP et HTTP.

Module::Install::Include

Fournit la famille de commandes "include" pour intégrer des modules qui ne sont nécessaires qu'au moment de la construction dans votre distribution et qui ne seront pas installés.

Module::Install::Inline

Fournit "&Inline->write" pour remplacer la fonctionnalité de **Inline::MakeMaker** pour la création de modules basés sur **Inline** (et le nettoyage).

Cependant, vous devriez l'appeler avec "WriteAll( inline => 1 )".

Module::Install::Makefile

Fournit "&Makefile->write" pour générer un Makefile pour votre distribution.

Module::Install::Metadata

Fournit "&Meta->write" pour générer un fichier META.yml pour votre distribution.

Module::Install::PAR

Crée des paquets binaires de modules précompilés à partir du répertoire blib construit, et télécharge ceux existants pour éviter de recompiler.

Module::Install::Run

Détermine si les commandes sont disponibles sur la machine de l'utilisateur, et les exécute via **IPC::Run3**.

Module::Install::Scripts

Gère l'empaquetage et l'installation de scripts dans divers répertoires bin.

Module::Install::Win32

Fonctions pour installer des modules sous Win32 et trouver/installer nmake.exe pour les utilisateurs qui en ont besoin.

Module::Install::WriteAll

Fournit "WriteAll", qui écrit tous les fichiers requis, tels que META.yml et Makefile.

"WriteAll" prend quatre paramètres nommés optionnels :

"check_nmake" (par défaut à vrai)
Si vrai, invoque des fonctions du même nom.

L'utilisation de ce paramètre n'est plus recommandée.

"inline" (par défaut à faux)
Si vrai, invoque "&Inline->write" pour les modules Inline.
"meta" (par défaut à vrai)
Si vrai, écrit un fichier "META.yml".
"sign" (par défaut à faux)
Si vrai, invoque la commande "sign" pour signer numériquement erm... quelque chose.

FAQ

Quels sont les avantages de l'utilisation de Module::Install ?

Voici un bref aperçu des raisons :

  • Il est très facile pour les débutants à apprendre.
  • Il fait tout ce que ExtUtils::MakeMaker fait.
  • Il fait tout avec une syntaxe beaucoup plus simple.
  • Il analyse automatiquement les métadonnées.
  • Il ne nécessite aucune installation pour les utilisateurs finaux.
  • Il est garanti d'être compatible avec le futur.
  • Il met à jour automatiquement votre MANIFEST.
  • Il est facile de distribuer des scripts.
  • Il inclut des modules de prérequis (moins de dépendances à installer).
  • Il installe automatiquement les modules de prérequis.
  • Il prend en charge les modules basés sur Inline.
  • Il prend en charge les fichiers de données partagés avec File::ShareDir.
  • Il prend en charge les binaires précompilés.
  • Il gère les problèmes d'installation sous Windows.

En réduisant et en simplifiant la syntaxe, Module::Install rend le travail nécessaire pour maintenir vos Makefile.PL minimal.

Et si vous maintenez plus d'un module qui nécessite des astuces d'installation non standard, vous pouvez créer un module spécifique pour masquer cette complexité.

Module::Install n'est pas encore à 1.00, est-il sûr de l'utiliser ?

Tant que vous effectuerez périodiquement des versions incrémentielles pour obtenir les corrections de bugs et les nouvelles fonctionnalités, oui.

Si vous ne prévoyez pas de faire de versions incrémentielles, il pourrait être judicieux de continuer à attendre un peu.

MANUEL DE CUISINE / EXEMPLES

Voici de vrais exemples de fichiers Makefile.PL utilisant Module::Install.

Method::Alias

Method::Alias est un module utilitaire de très petite taille, avec le Makefile.PL le plus petit possible.

use inc::Module::Install;
name          'Method-Alias';
all_from      'lib/Method/Alias.pm';
test_requires 'Test::More' => '0.42';

File::HomeDir

File::HomeDir localise votre répertoire personnel sur toutes les plateformes. Il nécessite un installateur capable de gérer différentes dépendances sur différentes plateformes.

use inc::Module::Install;
name          'File-HomeDir';
all_from      'lib/File/HomeDir.pm';
requires      'File::Spec' => '0.80';
test_requires 'Test::More' => '0.47';
if ( $MacPerl::Version ) {
    # Needed on legacy Mac OS 9
    requires 'Mac::Files' => 0;
}
if ( $^O eq 'MXWin32' ) {
    # Needed on Windows platforms
    requires 'Win32::TieRegistry' => 0;
}
WriteAll;

Comme cela ajouterait des dépendances significatives (c'est-à-dire pugs !), cela devrait être distribué en tant que distribution distincte.

Examiner en détail les documents POD.

Tester les répertoires Makefile.PL récursifs.

Le test nécessite un grand nombre de scripts de test.

Dépendances des bibliothèques partagées (libxml/libxml.dll etc.) et des binaires afin que les programmes d'empaquetage automatique debian/Win32/etc puissent créer les dépendances au niveau du paquet correspondant.

EU::MM 6.06_03+ prend en charge nativement le fichier META.yml. Tester s'il le prend également en charge.
