NOM

Module::Build::API - Référence API pour les auteurs de modules

DESCRIPTION

Je liste ici certaines des méthodes les plus importantes de "Module::Build". Normalement, vous n'aurez pas besoin de les utiliser à moins de vouloir créer une sous-classe de "Module::Build". Mais comme l'une des raisons pour lesquelles j'ai créé ce module en premier lieu était de permettre la création de sous-classes (et facilement), j'écrirai certainement plus de documentation au fur et à mesure que l'interface se stabilisera.

CONSTRUCTEURS

current()
[version 0.20]

Cette méthode renvoie une représentation raisonnable de l'objet "Module::Build" actuellement en cours d'exécution, représentant la compilation actuelle. Vous pouvez utiliser cet objet pour interroger sa méthode "notes()", vous renseigner sur les modules installés, etc. C'est un excellent moyen de partager des informations entre différentes parties de votre processus de compilation. Par exemple, vous pouvez poser une question à l'utilisateur pendant "perl Build.PL", puis utiliser sa réponse lors d'un test de régression :

# Dans Build.PL :
my $color = $build->prompt("Quelle est votre couleur préférée ?");
$build->notes(color => $color);
# Dans t/colortest.t :
use Module::Build;
my $build = Module::Build->current;
my $color = $build->notes('color');
...

La façon dont la méthode current() est actuellement implémentée, il peut y avoir de légères différences entre l'objet $build dans Build.PL et celui dans "t/colortest.t". Notre objectif est de minimiser ces différences dans les futures versions de Module::Build, alors s'il vous plaît, signalez toute anomalie que vous trouvez.

Une mise en garde importante : dans son implémentation actuelle, current() ne fonctionnera **PAS** correctement si vous avez quitté le répertoire à partir duquel "Module::Build" a été appelé.

new()
[version 0.03]

Crée un nouvel objet Module::Build. Les arguments de la méthode new() sont listés ci-dessous. La plupart des arguments sont facultatifs, mais vous devez fournir soit l'argument "module_name", soit "dist_name" et l'un des arguments "dist_version" ou "dist_version_from". En d'autres termes, vous devez fournir suffisamment d'informations pour déterminer à la fois un nom de distribution et une version.

add_to_cleanup
[version 0.19]

Une référence de tableau de fichiers à nettoyer lors de l'exécution de l'action "clean". Voir aussi la méthode add_to_cleanup().

allow_pureperl
[version 0.4005]

Un booléen indiquant que le module est toujours fonctionnel sans ses parties xs. Lorsqu'un module XS est compilé avec --pureperl_only, il échouera sinon.

auto_configure_requires
[version 0.34]

Ce paramètre détermine si Module::Build s'ajoutera automatiquement à configure_requires (et build_requires) si Module::Build n'est pas déjà présent. La version requise sera la dernière version « majeure », telle que définie par la version décimale tronquée à deux décimales (par exemple, 0.34, au lieu de 0.3402). La valeur par défaut est vraie.

auto_features
[version 0.26]

Ce paramètre prend en charge la définition de fonctionnalités (voir "feature($name)") automatiquement sur la base d'un ensemble de prérequis. Par exemple, pour un module qui pourrait utiliser optionnellement MySQL ou des bases de données PostgreSQL, vous pourriez utiliser "auto_features" comme ceci :

my $build = Module::Build->new
  (
   ...autre chose ici...
   auto_features => {
     pg_support    => {
                       description => "Interface avec les bases de données Postgres",
                       requires    => { 'DBD::Pg' => 23.3,
                                        'DateTime::Format::Pg' => 0 },
                      },
     mysql_support => {
                       description => "Interface avec les bases de données MySQL",
                       requires    => { 'DBD::mysql' => 17.9,
                                        'DateTime::Format::MySQL' => 0 },
                      },
   }
  );

Pour chaque fonctionnalité nommée, les prérequis requis seront vérifiés, et s'il n'y a pas d'échecs, la fonctionnalité sera activée (mise à 1). Sinon, les échecs seront affichés à l'utilisateur et la fonctionnalité sera désactivée (mise à 0).

Voir la documentation de "requires" pour les détails sur la façon dont les exigences peuvent être spécifiées.

autosplit
[version 0.04]

Un argument facultatif "autosplit" spécifie un fichier qui doit être traité par la fonction AutoSplit::autosplit(). Si plusieurs fichiers doivent être divisés, l'argument peut être donné sous forme de tableau des fichiers à diviser.

En général, je ne considère pas l'autosplit comme une bonne idée, car il n'est pas toujours clair que l'autosplit atteigne les avantages en matière de performance visés. Il peut même nuire aux performances dans des environnements comme mod_perl, où autant de code que possible d'un module doit être chargé au démarrage.

build_class
[version 0.28]

La classe Module::Build ou sous-classe à utiliser dans le script de compilation. Par défaut, "Module::Build" ou le nom de la classe passé à ou créé par un appel à "subclass()". Cette propriété est utile si vous écrivez une sous-classe personnalisée de Module::Build et que vous avez un problème de démarrage - c'est-à-dire que votre sous-classe nécessite des modules qui ne sont peut-être pas installés lorsque "perl Build.PL" est exécuté, mais que vous les avez listés dans "build_requires" afin qu'ils soient disponibles lorsque "./Build" est exécuté.

build_requires
[version 0.07]

Les modules listés dans cette section sont nécessaires pour compiler et installer le module donné, mais ne sont pas nécessaires pour son utilisation régulière. C'est en fait une distinction importante - elle permet un contrôle plus strict sur le corps des modules installés et facilite la vérification correcte des dépendances sur les distributions binaires/packagées du module.

Voir la documentation de "PREREQUISITES" dans Module::Build::Authoring pour les détails sur la façon dont les exigences peuvent être spécifiées.

configure_requires
[version 0.30]

Les modules listés dans cette section doivent être installés *avant* de configurer cette distribution (c'est-à-dire avant d'exécuter le script Build.PL). Il pourrait s'agir d'une version minimale spécifique de "Module::Build" ou de tout autre module dont Build.PL a besoin pour faire son travail. Les clients comme "CPAN.pm" ou "CPANPLUS" devront extraire "configure_requires" du fichier META.yml et installer ces éléments avant d'exécuter "Build.PL".

Module::Build peut s'ajouter automatiquement à configure_requires. Voir "auto_configure_requires" pour les détails.

Voir la documentation de "PREREQUISITES" dans Module::Build::Authoring pour les détails sur la façon dont les exigences peuvent être spécifiées.

test_requires
[version 0.4004]

Les modules listés dans cette section doivent être installés avant de tester la distribution.

Voir la documentation de "PREREQUISITES" dans Module::Build::Authoring pour les détails sur la façon dont les exigences peuvent être spécifiées.

create_packlist
[version 0.28]

Si es verdadero, este parámetro indica a Module::Build que cree un archivo .packlist durante la acción "install", así como lo hace "ExtUtils::MakeMaker". El archivo se crea en una subdirectorio de la ubicación de instalación de "arch". Se usa por otros herramientas (CPAN, CPANPLUS, etc.) para determinar qué archivos son parte de una instalación.

El valor por defecto es verdadero. Este parámetro fue introducido en Module::Build versión 0.2609; previamente no se creaban archivos .packlist por Module::Build.

c_source
[version 0.04]

Un argumento opcional "c_source" especifica una carpeta o una referencia a un array de directorios que contengan fuentes de C que el resto del proceso de construcción pueda depender. Cualquier archivo ".c" en la carpeta se compilará a archivos objeto. El directorio se agregará al camino de búsqueda durante las etapas de compilación y vinculación de cualquier archivo C o XS.

[version 0.3604]

Una lista de directorios puede especificarse utilizando una referencia de array anónima de strings.

conflicts
[version 0.07]

Los módulos listados en esta sección conflicten en forma seria con el módulo dado. "Module::Build" (o algún otro herramienta de alto nivel) rechazará instalar el módulo dado si también está instalado este módulo/version.

Vea la documentación sobre "PREREQUISITES" en Module::Build::Authoring para detalles sobre cómo especificar requisitos.

create_license
[version 0.31]

Este parámetro indica a Module::Build que crea automáticamente un archivo LICENSE en el nivel superior de su distribución, que contenga el texto completo de la licencia elegida por el autor. Esto requiere "Software::License" en la máquina del autor, y también requiere que el parámetro "license" especifique una licencia que el programa conozca.

create_makefile_pl
[version 0.19]

Este parámetro permite usar "Module::Build::Compat" durante la acción "distdir" (o "dist") para crear automáticamente un archivo Makefile.PL para compatibilidad con "ExtUtils::MakeMaker". El valor del parámetro debe ser uno de los estilos mencionados en la documentación de Module::Build::Compat.

El uso de este parámetro se desaconseja.

create_readme
[version 0.22]

Este parámetro indica a Module::Build que crea automáticamente un archivo README en el nivel superior de su distribución. Actualmente, simplemente utiliza "Pod::Text" (o "Pod::Readme" si está instalado) en el archivo indicado por "dist_version_from" y lo coloca en el archivo README. Esto no es el único estilo recomendado para escribir un README, pero parece ser uno común en CPAN.

Si genera un README de esta manera, probablemente sea buena idea crear un archivo INSTALL separado si la información no está en el archivo generado README.

dist_abstract
[version 0.20]

Esta debería ser una descripción breve de la distribución. Se usa cuando se genera el metadato para META.yml y PPD. Si no se especifica, "Module::Build" busca el número de versión de la distribución en la sección de POD del módulo desde el cual obtiene la versión. Si encuentra una sección de POD marcada con "=head1 NAME", busca la primera línea que coincida con "\s+-\s+(.+)" y usa el texto capturado como abstracto.

dist_author
[version 0.20]

Esta debería ser algo como "John Doe <jdoe@example.com>", o si hay múltiples autores, una referencia anónima de strings puede especificarse. Se usa cuando se genera el metadato para META.yml y PPD. Si no se especifica, "Module::Build" busca el número de versión de la distribución en el módulo desde el cual obtiene la versión. Si encuentra una sección de POD marcada con "=head1 AUTHOR", usa el contenido de esta sección.

dist_name
[version 0.11]

Especifica el nombre de esta distribución. Los autores casi nunca tendrán que establecerlo directamente, pueden usar "module_name" para establecer "dist_name" a un valor default razonable. Sin embargo, algunas distribuciones aglomeradas como "libwww-perl" o "bioperl" tienen nombres que no corresponden directamente a un nombre de módulo, así que "dist_name" puede establecerse independientemente.

dist_suffix
[version 0.37]

Especifica un sufijo opcional a incluir después del número de versión en el nombre de la carpeta (y tarball) de la distribución. El único sufijo actual reconocido por PAUSE es 'TRIAL', que indica que la distribución no debe ser indexada. Ejemplo:

Foo-Bar-1.23-TRIAL.tar.gz

Este hará lo correcto automáticamente según "dist_version" y "release_status". Cuando "dist_version" no tenga un guion y "release_status" no sea 'stable', el valor por defecto de "dist_suffix" será 'TRIAL'. De lo contrario, se usarán los valores por defecto, que desactivan el sufijo.

En general, los autores deberían establecer este solo si debido a un propósito específico deben sobrescribir el comportamiento por defecto.

dist_version
[version 0.11]

Especifica un número de versión para la distribución. Vea "module_name" o "dist_version_from" para formas de establecerlo automáticamente a partir de una variable $VERSION en un módulo. De alguna manera o por otra, se necesita establecer un número de versión.

dist_version_from
[version 0.11]

Especifica un archivo para buscar la versión de la distribución. Los autores casi nunca tendrán que establecerlo directamente, pueden usar "module_name" para establecerlo a un valor default razonable.

La versión se extrae de este archivo según las mismas reglas que ExtUtils::MakeMaker y "CPAN.pm". Implica encontrar la primera línea que coincida con el patrón regular:

/([\$*])(([\w\:\']*)\bVERSION)\b.*\=/

eval()-ing esa línea, luego verificando el valor de la variable $VERSION. Tan feo como lo es, pero todos los módulos en CPAN dependen de este proceso, así que no hay oportunidad real de cambiar a algo mejor.

Si el archivo de destino de "dist_version_from" contiene más de una declaración de paquete, la versión devuelta será la que corresponda al módulo configurado "module_name"。

dynamic_config
[version 0.07]

Un flag booleano que indica si Build.PL debe ejecutarse para determinar los requisitos o si pueden ser determinados solo consultando su archivo de metadatos. La razón principal para establecer este valor a verdadero es que tu módulo agrega o elimina requisitos dinámicamente en Build.PL. Si el flag no se omite, se considerará verdadero (true), ya que es un modo más seguro de comportamiento.

Actualmente "Module::Build" no hace nada con este flag; es el trabajo de herramientas de alto nivel como "CPAN.pm" lo que lo hace útil. También puede ser muy útil para el análisis estático. Vea "dynamic_config" en CPAN::Meta::Spec para detalles sobre el campo de metadato.

extra_compiler_flags
extra_linker_flags
[version 0.19]

Estos parámetros pueden contener referencias a arrays (o strings, en los cuales se dividirán en arrays) para pasar a través de los pasos de compilación y vinculación de código C. Por ejemplo, para decir al compilador que tu código es C++, podrías hacer:

my $build = Module::Build->new
  (
   module_name          => 'Foo::Bar',
   extra_compiler_flags => ['-x', 'c++'],
  );

Para vincular tu código XS con glib podrías escribir algo así:

my $build = Module::Build->new
  (
   module_name          => 'Foo::Bar',
   dynamic_config       => 1,
   extra_compiler_flags => scalar `glib-config --cflags`,
   extra_linker_flags   => scalar `glib-config --libs`,
  );
extra_manify_args
[version 0.4006]

Cualquier argumento adicional a pasar a "Pod::Man->new()" durante la construcción de páginas man. Una elección común podría ser "utf8 => 1" para obtener soporte para Unicode.

get_options
[version 0.26]

Puedes pasar opciones de línea de comandos arbitrarias a Build.PL o a Build, y estas se almacenarán en el objeto Module::Build y pueden ser accedidas mediante el método args(). Sin embargo, a veces quieres más flexibilidad en el procesamiento de argumentos que lo permite. En tales casos, usa el parámetro "get_options" para pasar un mapa de argumentos.

spécifications, et la liste des arguments à Build.PL ou Build sera traitée selon ces spécifications avant d'être transmise au propre traitement des arguments de "Module::Build".

Les clés de hachage de spécification d'options prises en charge sont :

type
Le type d'option. Les types sont ceux pris en charge par Getopt::Long ; consultez sa documentation pour une liste complète. Les types typiques sont "=s" pour les chaînes, "+" pour les options additives, et "!" pour les options négatives. Si le type n'est pas spécifié, il sera considéré comme booléen, c'est-à-dire qu'aucun argument ne sera pris et une valeur de 1 sera assignée lorsque l'option sera rencontrée.
store
Une référence à un scalaire dans lequel stocker la valeur passée à l'option. Si elle n'est pas spécifiée, la valeur sera stockée sous le nom de l'option dans le hachage renvoyé par la méthode args().
default
Une valeur par défaut pour l'option. Si aucune valeur par défaut n'est spécifiée et aucune option n'est passée, alors la clé de l'option n'existera pas dans le hachage renvoyé par args().

Vous pouvez combiner des références à vos propres variables ou sous-routines avec des spécifications non référencées, pour lesquelles le résultat sera également stocké dans le hachage renvoyé par args(). Par exemple :

my $loud = 0;
my $build = Module::Build->new
  (
   module_name => 'Foo::Bar',
   get_options => {
                   Loud =>     { store => \$loud },
                   Dbd  =>     { type  => '=s'   },
                   Quantity => { type  => '+'    },
                  }
  );
print STDERR "HEY, ARE YOU LISTENING??\n" if $loud;
print "We'll use the ", $build->args('Dbd'), " DBI driver\n";
print "Are you sure you want that many?\n"
  if $build->args('Quantity') > 2;

Les arguments pour une telle spécification peuvent être appelés ainsi :

perl Build.PL --Loud --Dbd=DBD::pg --Quantity --Quantity --Quantity

AVERTISSEMENT : Toute spécification d'option qui entre en conflit avec les options propres à Module::Build (définies par ses propriétés) lèvera une exception. Utilisez des noms d'options en majuscules pour éviter les conflits involontaires avec de futures options de Module::Build.

Consultez la documentation de Getopt::Long pour plus de détails sur son utilisation.

include_dirs
[version 0.24]

Spécifie tout répertoire supplémentaire dans lequel rechercher les fichiers d'en-tête C. Peut être donné sous forme de chaîne indiquant un seul répertoire, ou sous forme de référence de liste indiquant plusieurs répertoires.

install_path
[version 0.19]

Vous pouvez définir les chemins pour les éléments installables individuels en utilisant le paramètre "install_path" :

my $build = Module::Build->new

meta_add
[version 0.28]

Un hachage de paires clé/valeur qui doit être ajouté au fichier META.yml lors de l'action "distmeta". Toutes les entrées existantes portant les mêmes noms seront remplacées.

Voir la section "MODULE METADATA" pour plus de détails.

meta_merge
[version 0.28]

Un hachage de paires clé/valeur qui doit être fusionné dans le fichier META.yml lors de l'action "distmeta". Toutes les entrées existantes portant les mêmes noms seront remplacées.

La seule différence entre "meta_add" et "meta_merge" réside dans leur comportement sur les entrées de type hachage et tableau : "meta_add" effacera complètement la valeur existante du hachage ou du tableau, mais "meta_merge" fusionnera les données fournies dans la valeur existante du hachage ou du tableau.

Voir la section "MODULE METADATA" pour plus de détails.

module_name
[version 0.03]

Le "module_name" est un raccourci pour définir les valeurs par défaut de "dist_name" et "dist_version_from", reflétant le fait que la majorité des distributions CPAN sont centrées autour d'un seul module "principal". Par exemple, si vous définissez "module_name" à "Foo::Bar", alors "dist_name" sera par défaut "Foo-Bar" et "dist_version_from" sera par défaut "lib/Foo/Bar.pm". "dist_version_from" sera à son tour utilisé pour définir "dist_version".

Définir "module_name" ne remplacera pas un paramètre "dist_*" que vous spécifiez explicitement.

needs_compiler
[version 0.36]

Le paramètre "needs_compiler" indique si un compilateur est requis pour construire la distribution. La valeur par défaut est fausse, à moins que des fichiers XS ne soient trouvés ou que le

"c_source", auquel cas il est vrai. Si vrai, ExtUtils::CBuilder est automatiquement ajouté à "build_requires" si nécessaire.

Pour une distribution où un compilateur est *optionnel*, par exemple une distribution double XS/pure-Perl, "needs_compiler" devrait être explicitement défini sur une valeur fausse.

PL_files
[version 0.06]

Un paramètre optionnel spécifiant un ensemble de fichiers ".PL" dans votre distribution. Ceux-ci seront exécutés comme scripts Perl avant le traitement du reste des fichiers de votre distribution, avec le nom du fichier qu'ils génèrent comme argument. Ils sont généralement utilisés comme modèles pour créer d'autres fichiers dynamiquement, de sorte qu'un fichier comme "lib/Foo/Bar.pm.PL" puisse créer le fichier "lib/Foo/Bar.pm".

Les fichiers sont spécifiés avec les fichiers ".PL" comme clés de hachage, et les fichiers qu'ils génèrent comme valeurs de hachage, comme suit :

my $build = Module::Build->new
  (
   module_name => 'Foo::Bar',
   ...
   PL_files => { 'lib/Foo/Bar.pm.PL' => 'lib/Foo/Bar.pm' },
  );

Notez que les spécifications de chemin sont *toujours* données au format Unix, et non dans le style du système local.

Si vos scripts ".PL" ne créent aucun fichier, ou s'ils créent des fichiers avec des noms inattendus, ou même s'ils créent plusieurs fichiers, vous pouvez l'indiquer afin que Module::Build puisse gérer correctement ces fichiers créés :

PL_files => {
             'lib/Foo/Bar.pm.PL' => 'lib/Foo/Bar.pm',
             'lib/something.PL'  => ['/lib/something', '/lib/else'],
             'lib/funny.PL'      => [],
            }

Voici un exemple de fichier PL simple.

my $output_file = shift;
open my $fh, ">", $output_file or die "Can't open $output_file: $!";
print $fh <<'END';
#!/usr/bin/perl
print "Hello, world!\n";
END

Les fichiers PL ne sont pas installés par défaut, il est donc sûr de les placer dans *lib/* et *bin/*.

pm_files
[version 0.19]

Un paramètre optionnel spécifiant l'ensemble des fichiers ".pm" de cette distribution, spécifié comme une référence de hachage dont les clés sont les emplacements des fichiers dans la distribution, et dont les valeurs sont leurs emplacements logiques basés sur leur nom de paquet, c'est-à-dire où ils seraient trouvés dans une distribution de style Module::Build "normale". Ce paramètre est principalement destiné à supporter des structures de fichiers alternatives.

Par exemple, si vous avez une distribution de style ancien "MakeMaker" pour un module appelé "Foo::Bar" et un fichier *Bar.pm* au niveau supérieur de la distribution, vous pourriez spécifier votre structure dans votre "Build.PL" comme ceci :

my $build = Module::Build->new
  (
   module_name => 'Foo::Bar',
   ...
   pm_files => { 'Bar.pm' => 'lib/Foo/Bar.pm' },
  );

Notez que les valeurs doivent inclure "lib/", car c'est là qu'elles seraient trouvées dans une distribution de style Module::Build "normale".

add_property
[version 0.31] 
package 'My::Build';
use base 'Module::Build';
__PACKAGE__->add_property( 'pedantic' );
__PACKAGE__->add_property( answer => 42 );
__PACKAGE__->add_property(
   'epoch',
    default => sub { time },
    check   => sub {
        return 1 if /^\d+$/;
        shift->property_error( "'$_' n'est pas un temps epoch" );
        return 0;
    },
);

Ajoute une propriété à une classe "Module::Build". Les propriétés sont ces attributs d'un objet "Module::Build" qui peuvent être passés au constructeur et qui ont des méthodes d'accès pour obtenir et définir. Toutes les propriétés de base, telles que "module_name" et "license", sont définies en utilisant cette méthode.

Le premier argument de add_property() est toujours le nom de la propriété. Le deuxième argument peut être une valeur par défaut pour la propriété, ou une liste de paires clé-valeur. Les clés prises en charge sont :

"default"
La valeur par défaut. Peut éventuellement être spécifié comme une référence à une sous-routine, auquel cas la valeur renvoyée par l'exécution de la sous-routine sera utilisée. Si vous avez besoin que la valeur par défaut soit une référence à une sous-routine, utilisez simplement une référence à une sous-routine pour la renvoyer, par exemple : 
default => sub { sub { ... } },
"check"
Une sous-routine qui vérifie si la valeur spécifiée pour la propriété est valide. Pendant l'exécution de la sous-routine, la nouvelle valeur sera incluse dans la variable $_. Si la valeur est correcte, la sous-routine de vérification "check" doit renvoyer vrai. Si la valeur n'est pas correcte, elle doit envoyer un message d'erreur à "property_error() et renvoyer faux.

Lorsque cette méthode est appelée, une nouvelle propriété est installée dans la classe "Module::Build", et une méthode d'accès est créée pour obtenir ou définir la propriété sur l'objet de construction.

print $build->pedantic, $/;
$build->pedantic(0);

Si la valeur par défaut est une référence de hachage, cela génère une méthode d'accès spéciale, où des paires clé-valeur individuelles peuvent être définies ou récupérées :

print "stuff{foo} is: ", $build->stuff( 'foo' ), $/;
$build->stuff( foo => 'bar' );
print $build->stuff( 'foo' ), $/; # Outputs "bar"

Vous pouvez également définir l'ensemble complet des paires clé-valeur directement :

$build->stuff( { foo => 'bar', baz => 'yo' } );

Dans les deux cas, si un "check" a été spécifié pour la propriété, il sera appliqué à l'ensemble du hachage. Par conséquent, la sous-routine de vérification devrait ressembler à ceci :

check => sub {
      return 1 if defined $_ && exists $_->{foo};
      shift->property_error(qq{La propriété "stuff" nécessite "foo"});
      return 0;
},

check_installed_status($module, $version)
[version 0.11]

Cette méthode retourne une référence de hachage indiquant si une dépendance de version sur un module donné est satisfaite. L'argument $module est donné sous forme de chaîne de caractères comme "Data::Dumper" ou "perl", et l'argument $version peut prendre l'une des formes décrites dans "requires" ci-dessus. Cela permet une vérification de version très fine.

La référence de hachage retournée a la structure suivante :

{
 ok => $la_dépendance_est_satisfaite,
 have => $version_déjà_installée,
 need => $version_demandée, # Identique à l'argument $version entrant
 message => $message_d_erreur_informatif,
}

Si aucune version de $module n'est actuellement installée, la valeur "have" sera la chaîne "<none>". Sinon, la valeur "have" sera simplement la version du module installé. Notez que cela signifie que si $module est installé mais ne définit pas de numéro de version, la valeur "have" sera "undef" - c'est pourquoi nous n'utilisons pas "undef" pour le cas où $module n'est pas du tout installé.

Cette méthode peut être appelée soit comme une méthode d'objet ("$build->check_installed_status($module, $version)") soit comme une méthode de classe ("Module::Build->check_installed_status($module, $version)").

check_installed_version($module, $version)
[version 0.05]

Comme check_installed_status(), mais retourne simplement vrai ou faux selon que le module $module satisfait la dépendance $version.

Si la vérification réussit, la valeur de retour est la version réelle de $module installée sur le système. Cela vous permet de faire ce qui suit :

my $installed = $build->check_installed_version('DBI', '1.15');
if ($installed) {
  print "Félicitations, la version $installed de DBI est installée.\n";
} else {
  die "Désolé, vous devez installer DBI.\n";
}

Si la vérification échoue, nous retournons faux et définissons $@ avec un message d'erreur informatif.

Si $version est une valeur non vraie (notamment zéro) et qu'une version de $module est installée, nous retournons vrai. Dans ce cas, si $module ne définit pas de version, ou si sa version est zéro, nous retournons la valeur spéciale "0 mais vrai", qui est numériquement zéro, mais logiquement vraie.

En général, vous préférerez peut-être utiliser "check_installed_status" si vous avez besoin d'informations détaillées, ou cette méthode si vous avez juste besoin d'une réponse oui/non.

get_metadata()
[version 0.36]

Cette méthode renvoie une référence de hash de métadonnées qui peut être utilisée pour créer un flux de données YAML. Elle est fournie aux auteurs pour qu'ils puissent remplacer ou personnaliser les champs de META.yml. Par exemple.

package My::Builder;
use base 'Module::Build';
sub get_metadata {
  my $self, @args = @_;
  my $data = $self->SUPER::get_metadata(@args);

  return $data;
}

Les arguments valides incluent :

  • "fatal" -- indique si les champs de métadonnées requis manquants doivent entraîner une erreur fatale ou non. Pour la création de META, cela devrait généralement être le cas, mais pour la création de MYMETA pour les utilisateurs finaux, cela ne devrait pas être fatal.

prereq_failures()
[version 0.11]

Renvoie une structure de données contenant des informations sur les prérequis échoués (de l'un des types décrits ci-dessus), ou "undef" si tous les prérequis sont remplis.

La structure de données renvoyée est une référence de hash. Les clés de premier niveau sont le type de prérequis échoué, l'un de "requires", "build_requires", "conflicts", ou "recommends". Les valeurs associées sont des références de hash dont les clés sont les noms des modules requis (ou en conflit). Les valeurs associées de ceux-ci sont des références de hash indiquant des informations sur l'échec. Par exemple :

{
 have => '0.42',
 need => '0.59',
 message => 'Version 0.42 est installée, mais nous avons besoin de la version 0.59',
}
>

ou

{
 have => '<none>',
 need => '0.59',
 message => 'La prérequis Foo n'est pas installé',
}

if ( $build->prereq_failures->{requires}{Foo::Bar} ) { ...
# Vérifie s'il y a eu des échecs
if ( $build->prereq_failures ) { ...
# Affiche les messages pour tous les échecs
my $failures = $build->prereq_failures;
while (my ($type, $list) = each %$failures) {
  while (my ($name, $hash) = each %$list) {
    print "Échec pour $name: $hash->{message}\n";
  }
}

prompt($message, $default)
[version 0.12]

Pose une question à l'utilisateur et retourne sa réponse sous forme de chaîne. Le premier argument spécifie le message à afficher à l'utilisateur (par exemple, "Où gardez-vous votre argent ?"). rscan_dir($dir, $pattern)
[version 0.28]

Utilise "File::Find" pour parcourir le répertoire $dir, retournant une référence vers un tableau d'entrées correspondant à $pattern. $pattern peut être une expression régulière (utilisant "qr//" ou simplement une chaîne de caractères) ou une référence vers une sous-routine qui retournera vrai pour les entrées désirées. $m->rscan_dir('t');
