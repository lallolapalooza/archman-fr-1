NOM

Module::Install::API - Référence des commandes pour Module::Install

DESCRIPTION

Module::Install a de nombreuses commandes dispersées dans les extensions. Certaines commandes courantes sont décrites dans le pod principal de Module::Install, mais vous devez souvent en connaître davantage pour faire ce que vous voulez.

Ce document d'API liste et décrit toutes les commandes publiques *supportées*, regroupées par leur nature ou leur importance.

Si vous êtes un auteur de module et que vous souhaitez utiliser Module::Install dans vos distributions, ce document est celui qu'il faut consulter.

Si vous êtes un utilisateur (ou un contributeur) de distributions utilisant Module::Install, vous voudrez peut-être aussi consulter Module::Install::FAQ où vous trouverez certains problèmes courants que vous pourriez rencontrer.

Remarque : les commandes non listées ici doivent être considérées comme des commandes privées pour les développeurs de Module::Install, ou *non supportées* pour diverses raisons (certaines sont expérimentales et à moitié construites, certaines sont mal implémentées (par conception ou par implémentation), certaines sont simplement obsolètes, etc.). Vous pouvez en trouver certaines utilisées largement, mais leur utilisation est déconseillée. Vous avez été prévenu.

COMMANDES POUR FOURNIR LES DONNÉES DE BASE

La plupart de celles-ci sont également décrites dans le pod principal de Module::Install. Essentiellement, (à peu près) tout ce que vous devez savoir est la commande all_from qui tente d'extraire toutes les métadonnées nécessaires d'un fichier de module, mais vous pouvez également spécifier un par un ce qui n'est pas écrit dans le module et ne peut pas être extrait (vous préférez généralement écrire ces commandes avant all_from() pour ne pas être averti du manque d'informations).

all_from (Module::Install::Metadata)

all_from 'lib/Foo/Bar.pm';

all_from prend un chemin de fichier de module et tente d'en extraire les métadonnées, y compris le nom de la distribution, la version du module, la version minimale de Perl requise pour le module, les informations sur les auteurs, une licence, une brève description du module. Voir les commandes suivantes pour les détails d'extraction.

name, name_from, module_name (Module::Install::Metadata)

name 'Foo-Bar';
name_from 'lib/Foo/Bar.pm';

name prend un nom de distribution. Il diffère souvent légèrement d'un nom de module (un nom de module est séparé par deux points ; un nom de distribution est séparé par des tirets). Il suffit de remplacer tous les deux points de votre module principal par des tirets.

name_from prend un chemin de fichier de module et recherche la déclaration "package" la plus élevée pour en extraire un nom de module, puis le convertit en nom de distribution.

Vous pouvez également définir optionnellement module_name pour spécifier le nom du module principal (si vous préférez un schéma de nommage différent pour votre distribution). Cette valeur est transmise directement à ExtUtils::MakeMaker en arrière-plan en tant qu'attribut "NAME" (Module::Install crée généralement cet attribut à partir du nom de la distribution défini par name ou name_from).

abstract, abstract_from (Module::Install::Metadata)

abstract 'une courte description de la distribution';
abstract_from 'lib/Foo/Bar.pm';

abstract prend une chaîne de caractères pour décrire ce qu'est le module/distribution. abstract_from prend un chemin de fichier de module et recherche une chaîne qui suit le nom du module et un tiret pour la séparation dans la section "NAME" du pod.

La valeur définie par abstract ou abstract_from est transmise à ExtUtils::MakeMaker en tant qu'attribut "ABSTRACT".

version, version_from (Module::Install::Metadata)

version '0.01';
version_from 'lib/Foo/Bar.pm';

version prend une chaîne de version pour la distribution. version_from prend un chemin de fichier de module et recherche l'instruction "$VERSION" du module.

La valeur définie par version ou version_from est transmise à ExtUtils::MakeMaker en tant qu'attribut "VERSION". version_from (et all_from) définit également un attribut "VERSION_FROM" pour vérifier l'intégrité de la distribution.

perl_version, perl_version_from (Module::Install::Metadata)

perl_version '5.008';
perl_version_from 'lib/Foo/Bar.pm';

perl_version prend la version minimale de Perl requise pour la distribution. perl_version_from prend un chemin de fichier de module et recherche une instruction "use <perl_version>" (ou "require <perl_version>") du module (remarque : Module::Install ne prend désormais en charge que Perl 5.005 et versions ultérieures).

La valeur définie par perl_version ou perl_version_from est transmise à ExtUtils::MakeMaker en tant qu'attribut "MIN_PERL_VERSION" (si applicable).

author, author_from (Module::Install::Metadata)

author 'Jean Dupont <jean.dupont at cpan.org>';
author_from 'lib/Foo/Bar.pm';

author prend une chaîne de caractères pour décrire les auteurs. Vous pouvez définir plusieurs auteurs avec un seul author ou avec plusieurs author (vous pouvez aussi utiliser l'alias authors si vous préférez).

author_from prend un chemin de fichier de module et recherche une section "AUTHOR" (ou "AUTHORS") dans le pod (et aussi les sections de licence/copyright si aucune section d'auteur n'est trouvée) pour en extraire un auteur.

La valeur définie par author ou author_from est concaténée et transmise à ExtUtils::MakeMaker en tant qu'attribut "AUTHOR".

license, license_from (Module::Install::Metadata)

license 'perl';
license_from 'lib/Foo/Bar.pm';

license prend un nom de licence abrégé incluant "perl", "artistic", "apache", "(l)gpl", "bsd", "mit", "mozilla", "open_source", et ainsi de suite. Si vous ne spécifiez pas (de préférence) une licence particulière, ce sera "unknown".

license_from prend un chemin de fichier de module et recherche une section "LICENSE" (ou "LICENCE") dans le pod (et aussi une section "COPYRIGHT" si aucune section d'auteur n'est trouvée) pour en extraire une licence.

La valeur définie par license ou license_from est transmise à ExtUtils::MakeMaker en tant qu'attribut "LICENSE" (si applicable). N'oubliez pas non plus que si la distribution est destinée à être envoyée sur CPAN, elle doit être une licence acceptée par l'OSI. Les logiciels commerciaux ne sont pas autorisés sur CPAN.

COMMANDES POUR FOURNIR LES DÉPENDANCES

La plupart de celles-ci sont également décrites dans le pod principal.

requires (Module::Install::Metadata)

requires 'Foo::Bar';
requires 'Foo::Baz' => '1.00';

requires commandes

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

prend un nom de module dont votre distribution dépend, ainsi que sa version minimale requise, le cas échéant. Vous pouvez ajouter un nombre arbitraire de "requires". Vous pouvez même ajouter plusieurs dépendances sur le même module avec des versions requises différentes (qui seront triées plus tard, cependant). Notez que cette dépendance est basée sur un module, et non sur une distribution. Cela n'a généralement pas d'importance, et vous n'avez qu'à appeler un module dont vous avez vraiment besoin (vous obtiendrez alors toute la distribution à laquelle il appartient), mais parfois vous pourriez avoir besoin d'appeler tous les modules dont le module requis dépend implicitement.

Les valeurs définies par requires sont transmises à ExtUtils::MakeMaker sous forme d'attribut "PREREQ_PM".

build_requires, test_requires (Module::Install::Metadata)

build_requires 'ExtUtils::Foo::Bar';
build_requires 'ExtUtils::Foo::Baz' => '1.00';
test_requires  'Test::Foo::Bar';
test_requires  'Test::Foo::Baz' => '1.00';

La commande build_requires prend également un nom de module et une version minimale requise, le cas échéant. La différence avec la commande "requires" est que build_requires est destiné aux modules dont vous aurez besoin lors de la construction de la distribution, ou lors des tests, et qui, en théorie, ne sont pas requis à l'exécution. Cette distinction est davantage destinée aux autres gestionnaires de paquets du système qu'à CPAN, d'où vous voudrez généralement tout installer pour une réutilisation future (sauf si vous êtes trop paresseux pour tester les distributions).

Au moment de la rédaction, "test_requires" n'est qu'un alias pour "build_requires", mais cela pourrait changer à l'avenir.

Les valeurs définies par build_requires et test_requires sont transmises à ExtUtils::MakeMaker sous forme d'attribut "BUILD_REQUIRES", qui peut se rabattre sur "PREREQ_PM" si votre ExtUtils::MakeMaker n'est pas assez récent.

configure_requires (Module::Install::Metadata)

configure_requires 'ExtUtils::Foo::Bar';
configure_requires 'ExtUtils::Foo::Baz' => '1.00';

La commande configure_requires prend également un nom de module et une version minimale requise, le cas échéant. La différence avec la commande "requires" est que configure_requires est destiné aux modules dont vous aurez besoin pour exécuter "perl Makefile.PL". Cet attribut n'a de sens que pour les dernières chaînes d'outils CPAN qui analysent "META.yml" avant d'exécuter "perl Makefile.PL".

Les valeurs définies par configure_requires sont transmises à ExtUtils::MakeMaker sous forme d'attribut "CONFIGURE_REQUIRES", qui peut se rabattre sur "PREREQ_PM" si votre ExtUtils::MakeMaker n'est pas assez récent.

recommends (Module::Install::Metadata)

recommends 'ExtUtils::Foo::Bar';
recommends 'ExtUtils::Foo::Baz' => '1.00';

La commande recommends prend également un nom de module et une version minimale requise, le cas échéant. Au moment de la rédaction, "recommends" est purement consultatif, écrit uniquement dans "META.yml". Les modules recommandés ne seront **pas** généralement installés par les chaînes d'outils CPAN actuelles (d'autres gestionnaires de paquets du système pourraient éventuellement vous demander de les installer).

features, feature (Module::Install::Metadata)

feature( 'prise en charge du répertoire partagé',
  -default => 1,
  'File::ShareDir' => '1.00',
);
features(
  'Support JSON', [
    -default => 0,
    'JSON::MaybeXS' => '1.003003',
  ],
  'Support YAML', [
    'YAML' => '0',
  ],
);

La commande feature prend une chaîne de caractères pour décrire à quoi sert la fonctionnalité, et un tableau de modules (optionnels) et leurs versions recommandées, le cas échéant. La commande features prend un tableau composé d'une description et d'un tableau de modules.

Au moment de la rédaction, "feature" et "features" ne fonctionnent que lorsque auto_install (voir ci-dessous) est activé. Ils sont utilisés pour permettre aux utilisateurs de la distribution de choisir ce qu'ils installent avec la distribution. Cela peut être utile si la distribution a de nombreuses fonctionnalités optionnelles qui peuvent ne pas fonctionner sur toutes les plateformes, ou qui nécessitent trop de modules pour les utilisateurs moyens.

Cependant, inviter les utilisateurs entrave l'installation automatique ou les tests de fumée, et est considéré comme une mauvaise pratique (il est préférable de donner des valeurs par défaut raisonnables).

Bien que les modules "feature"d soient optionnels et puissent être choisis lors de l'installation, les modules choisis sont traités de la même manière que ceux définis par la commande "requires". (Ils ne sont pas listés dans la section "recommends" de "META.yml"). Cela pourrait changer à l'avenir.

Vous pouvez ajouter "-default => [01]" dans un tableau de modules requis dans les fonctionnalités (feature(s)), pour définir une valeur par défaut pour l'invite.

COMMANDES POUR ÉCRIRE LES MÉTADONNÉES

Ce sont les commandes pour écrire les fichiers méta réels.

WriteAll (Module::Install::WriteAll)

use inc::Module::Install;

all_from 'lib/Foo/Bar.pm';

WriteAll;

La commande WriteAll est généralement la dernière commande dans "Makefile.PL". Elle peut prendre plusieurs attributs, mais vous n'avez généralement pas à vous en soucier, sauf si vous voulez écrire un Makefile pour un module basé sur Inline. Elle écrit "Makefile", "META.yml", et "MYMETA.yml" (ou "MYMETA.json") si vous avez défini une variable d'environnement expérimentale "X_MYMETA".

WriteMakefile (Module::Install::MakeMaker)

use inc::Module::Install;

requires 'Foo::Baz';  # à la Module::Install

WriteMakefile(        # à la ExtUtils::MakeMaker
  NAME => 'Foo::Bar',
  VERSION_FROM => 'lib/Foo/Bar.pm',
);

Si vous êtes familier avec ExtUtils::MakeMaker et souhaitez généralement vous en tenir à sa manière, vous pouvez le faire. Utilisez autant de la magie de Module::Install que vous le souhaitez, puis revenez à l'ancienne méthode. Ça marche tout simplement.

write_mymeta_yaml, write_mymeta_json (Module::Install::Metadata)

write_mymeta_yaml;
write_mymeta_json;

La commande write_mymeta_yaml et la commande write_mymeta_json servent à écrire respectivement "MYMETA.yml" et "MYMETA.json", qui sont de nouvelles améliorations pour les chaînes d'outils CPAN qui permettront éventuellement aux modules de chaînes d'outils de savoir quels modules sont requis sans avoir à analyser Makefile, etc. Elles sont principalement destinées à un usage interne (dans la commande "WriteAll") mais vous pouvez explicitement écrire ces commandes dans votre Makefile.PL.

COMMANDES POUR MODIFIER LE MAKEFILE

makemaker_args (Module::Install::Makefile)

makemaker_args(
  PREREQ_FATAL => 1,
  dist => { PREOP => 'pod2text lib/Foo/Bar.pm > README' },
);

La commande makemaker_args est utilisée dans la commande "WriteMakefile", et prend n'importe quel attribut qu'ExtUtils::MakeMaker comprend. Voir ExtUtils::MakeMaker pour les attributs disponibles.

preamble, postamble (Module::Install::Makefile)

preamble "# mon préambule\n";
postamble qq{my_done ::
\t\$(PERL) -e "print qq/fait\\n/"\n};

Les commandes preamble et postamble prennent une chaîne de caractères à intégrer dans le "Makefile". Vous pouvez y ajouter des cibles personnalisées. Voir les manuels appropriés pour savoir comment écrire un Makefile.

COMMANDES POUR LES TESTS

Celles-ci servent à définir les fichiers de test.

tests (Module::Install::Metadata)

tests 't/*.t t/*/*.t';

La commande tests prend une chaîne de caractères pour spécifier les fichiers de test. Vous pouvez utiliser des caractères génériques, et si vous souhaitez exécuter des tests dans plusieurs répertoires, concaténez les spécifications avec des espaces.

Si vous n'avez pas défini "tests" par un moyen quelconque (avec la commande explicite "tests", ou des extensions comme Module::Install::AuthorTests ou Module::Install::ExtraTests), et si vous avez un répertoire "xt", Module::Install ajoute silencieusement les tests de ce répertoire lorsque vous êtes en mode auteur, ou lorsque vous effectuez des tests de publication (avec la variable d'environnement "RELEASE_TESTING").

La valeur définie par tests est transmise à ExtUtils::MakeMaker sous forme d'attribut "test".

tests_recurisve (Module::Install::Makefile)

tests_recursive;
tests_recursive('t');

La commande tests_recursive peut prendre un répertoire

EXEMPLES

Ceci est un exemple de Makefile.PL qui utilise la plupart des commandes ci-dessus:

  use inc::Module::Install;

  all_from 'lib';

  requires 'Test::More';
  build_requires 'Module::Install::Tester';

  install_script 'script/foo';
  install_share 'share';
  install_share 'dist', 'templates';

  no_index 'directory' => 't/tmp';

  resources
    homepage    => 'http://example.com',
    repository  => 'http://github.com/foo/bar';

  # XS Support
  cc_lib_paths('libs');
  cc_inc_paths('include');
  libs '-lfoo';

COMMANDS TO TWEAK TESTING

test_requires (Module::Install::Metadata)

test_requires 'Test::More';
test_requires 'Test::MockObject', 0.10;

test_requires command declares dependencies required only for testing. ExtUtils::MakeMaker has no corresponding attribute, but Module::Install provides it in "META.yml". This command takes a module name and an optional version constraint.

test_files (Module::Install::Test)

test_files 'test/*.t';

test_files command takes a glob pattern, and installs files matching the pattern into the "t" directory. As of this writing, you can't use this command with other test related commands.

COMMANDS TO TWEAK DIRECTORIES TO INSTALL

installdirs (Module::Install::Metadata)

installdirs 'site';

installdirs command takes a directory type, and changes a directory to install modules and so on, though you usually don't need to use this. The value set by installdirs is passed to ExtUtils::MakeMaker as an "INSTALLDIRS" attribute.

install_as_core, install_as_cpan, install_as_site, install_as_vendor (Module::Install::Metadata)

install_as_core;   # = installdirs 'perl';
install_as_cpan;   # = installdirs 'site';
install_as_site;   # = installdirs 'site';
install_as_vendor; # = installdirs 'vendor';

install_as_* commands are aliases of the corresponding commands shown in the comments above.

COMMANDS TO INSTALL SUBORDINATE FILES

These are to install files other than the ones under the "lib" directory.

install_script (Module::Install::Scripts)

install_script('foo');
install_script('script/foo');

install_script command takes a script file name, and installs it into a "script" directory for your Perl installation. If your script is in a "script" directory, you can omit the "script/" part.

The value set by install_script is passed to ExtUtils::MakeMaker as an "EXE_FILES" attribute.

install_share (Module::Install::Share)

install_share;
install_share('templates');
install_share('dist', 'templates');
install_share('module', 'My::WebApp', 'share');

install_share command may take a directory type (either "dist" or "module"), a module name if necessary, and a directory ("share" by default), and installs files under the directory into a "share" directory for the type, which is usually in a directory your perl is installed in (but this may not be true if you're using local::lib and the likes).

You can access these shared files via File::ShareDir's "dist_file" or "module_file" according to the type. Note also that a shared directory is usually read-only. You can't use this as a private temporary directory.

COMMANDS FOR AUTO INSTALLATION

auto_install (Module::Install::AutoInstall)

auto_install;

The auto_install command is used to allow users to install dependencies of a local project when you run "make" after "<perl Makefile.PL">. In the past this was the only sane way to pull extra dependencies without installing the actual module, although now there are some alternatives (which however do not completely replace "auto_install"). For example you can use "cpan ." (with newer CPAN) or "cpanm --installdeps ." (with App::cpanminus).

"auto_install" also enables feature(s) commands to choose what you install (keep in mind that using feature() in CPAN distributions is generally considered a bad practice).

COMMANDS TO SUBDIRECTORY INSTALLATION

Module::Install 0.96 and above installs distributions in the subdirectories by default as ExtUtils::MakeMaker does. You also can specify what to install one by one.

build_subdirs (Module::Install::Makefile)

build_subdirs 'win32' if $^O eq 'MSWin32';

build_subdirs command takes subdirectories where projects you want to install are in. The values set by build_subdirs are passed to ExtUtils::MakeMaker as a "DIR" attribute.

COMMANDS TO PROVIDE OTHER OPTIONAL META DATA

These are to provide optional meta data mainly used by the PAUSE indexer and the CPAN search site. See also the META-spec page (http://module-build.sourceforge.net/META-spec.html) for details.

no_index (Module::Install::Metadata)

no_index file      => 'lib/My/Test/Module.pm';
no_index directory => 'templates';
no_index package   => 'Test::Foo::Bar';
no_index namespace => 'Test::Foo::Bar';

no_index command takes a hash to describe what should be excluded from the PAUSE index etc. Module::Install provides several "no_index" directories by default, including "inc", "share", "(x)t", "test", example(s), "demo".

resources (Module::Install::Metadata)

resources
  license     => "http://dev.perl.org/licenses",
  homepage    => "http://yourproject.host.org",
  bugtracker  => "http://rt.cpan.org/NoAuth/Bugs.html?Dist=Foo-Bar",
  repository  => "http://yourhost.com/myscm",
  MailingList => "http://yourhost.com/listinfo/foo-bar";

resources command takes a hash that contains various URLs for the related resources. Keys in lower-case are reserved. These resources are written in the "META.yml".

homepage, bugtracker, repository (Module::Install::Metadata)

homepage   'http://example.com';
bugtracker 'http://rt.cpan.org';
repository 'http://github.com/foo/bar';

homepage, bugtracker, and "repository" commands take a URL for the corresponding resource.

COMMANDS TO BUNDLE DISTRIBUTIONS

There are several commands to bundle modules/distributions in your distribution, but they are still broken in general. Don't use them for now.

COMMANDS FOR XS SUPPORT

libs (Module::Install::Makefile), cc_lib_paths, cc_lib_links (Module::Install::Compiler)

libs '-lz';
libs [qw/-lz -Llibs/];
cc_lib_paths 'libs';
cc_lib_links qw/z iconv/;

libs command takes a string, or an array reference of strings to be passed to ExtUtils::MakeMaker as a "LIBS" attribute. cc_lib_paths and cc_lib_links are its alternatives, both of which take an array of strings. "cc_lib_paths" is for upper-cased "-L" (directories), and "cc_lib_links" is for lower-cased "-l" (libraries).

inc (Module::Install::Makefile), cc_inc_paths (Module::Install::Compiler)

inc '-I. -Iinclude';
cc_inc_paths qw/. include/;

inc command takes a string to be passed to ExtUtils::MakeMaker as an "INC" attribute. cc_inc_paths is its alternative, and takes an array of directories.

cc_optimize_flags (Module::Install::Compiler)

cc_optimize_flags '-O2';

cc_optimize_flags takes a string to be passed to ExtUtils::MakeMaker as an "OPTIMIZE" attribute.

ppport (Module::Install::Compiler)

ppport;

ppport command is used to bundle "ppport.h" to a distribution.

requires_external_cc (Module::Install::External)

requires_external_cc;

requires_external_cc command is used to indicate that a distribution requires an external C compiler.

Module::Install::External

Module::Install::External

La commande "requires_external_cc" vérifie si l'utilisateur dispose d'un compilateur fonctionnel répertorié dans Config et, dans le cas contraire, quitte le "Makefile.PL".

La commande "can_cc" indique si l'utilisateur dispose d'un compilateur fonctionnel ou non.

La commande "clean_files" prend une chaîne ou un tableau de chaînes, concaténées avec des espaces, et passe le résultat à ExtUtils::MakeMaker comme un attribut "clean". La commande "realclean_files" fait de même pour un attribut "realclean".

La commande "can_use" prend un nom de module et éventuellement une version, et vérifie si le module (avec la version si applicable) est installé ou non.

La commande "can_run" prend un chemin d'exécutable et vérifie si l'exécutable est disponible ou non.

La commande "requires_external_bin" prend un chemin d'exécutable et quitte le "Makefile.PL" si aucun n'est disponible.
