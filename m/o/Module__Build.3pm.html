NOM

Module::Build - Construire et installer des modules Perl

SYNOPSIS

Processus standard pour construire et installer des modules :

perl Build.PL
./Build
./Build test
./Build install

Ou, si vous êtes sur une plateforme (comme DOS ou Windows) qui ne nécessite pas la notation "./", vous pouvez faire ceci :

perl Build.PL
Build
Build test
Build install

DESCRIPTION

"Module::Build" est un système pour construire, tester et installer des modules Perl. Il se veut une alternative à "ExtUtils::MakeMaker". Les développeurs peuvent modifier le comportement du module par héritage. Il ne nécessite pas non plus de "make" sur votre système - la plupart du code de "Module::Build" est pur-perl et écrit de manière très portable.

Voir "COMPARISON" pour plus de comparaisons entre "Module::Build" et d'autres outils d'installation.

Pour installer "Module::Build", et tout autre module qui utilise "Module::Build" pour son processus d'installation, faites ce qui suit :

perl Build.PL       # Le script 'Build.PL' crée le script 'Build'
./Build             # Nécessite ./ pour s'assurer que nous utilisons ce script "Build"
./Build test        # et non un autre qui se trouverait dans le PATH
./Build install

Cela illustre la configuration initiale et l'exécution de trois 'actions'. Dans ce cas, les actions exécutées sont 'build' (l'action par défaut), 'test', et 'install'. D'autres actions définies jusqu'à présent incluent :

clean                          manifest_skip
code                           manpages
config_data                    pardist
diff                           ppd
dist                           ppmdist
distcheck                      prereq_data
distclean                      prereq_report

distsign                       skipcheck
disttest                       test
docs                           testall

Vous pouvez exécuter l'action 'help' pour obtenir une liste complète des actions.

ACTIONS

Il y a quelques principes généraux à l'œuvre ici. Premièrement, chaque tâche lors de la construction d'un module est appelée une "action". Ces actions sont listées ci-dessus ; elles correspondent aux tâches de construction, de test, d'installation, d'empaquetage, etc.

Deuxièmement, les arguments sont traités de manière très systématique. Les arguments sont toujours des paires clé=valeur. Ils peuvent être spécifiés au moment de "perl Build.PL" (c'est-à-dire "perl Build.PL destdir=/mon/endroit/secret"), auquel cas leurs valeurs persistent pendant toute la durée de vie du script "Build". Ils peuvent également être spécifiés lors de l'exécution d'une action particulière (c'est-à-dire "Build test verbose=1"), auquel cas leurs valeurs ne persistent que pendant la durée de vie de cette commande. Les paramètres de la ligne de commande par action ont la priorité sur les paramètres spécifiés au moment de "perl Build.PL".

Le processus de construction repose également fortement sur le module "Config.pm". Si l'utilisateur souhaite remplacer certaines des valeurs de "Config.pm", elle peut le spécifier ainsi :

perl Build.PL --config cc=gcc --config ld=gcc

Les actions de construction suivantes sont fournies par défaut.

build
[version 0.01]

Si vous exécutez le script "Build" sans arguments, il exécute l'action "build", qui à son tour exécute les actions "code" et "docs".

Ceci est analogue à la cible make all de "MakeMaker".

clean
[version 0.01]

Cette action nettoiera tous les fichiers que le processus de construction aurait pu créer, y compris le répertoire "blib/" (mais sans inclure le répertoire "_build/" et le script "Build" lui-même).

code
[version 0.20]

Cette action construit votre base de code.

Par défaut, elle crée simplement un répertoire "blib/" et copie tous les fichiers ".pm" et ".pod" de votre répertoire "lib/" dans le répertoire "blib/". Elle compile également tous les fichiers ".xs" de "lib/" et les place dans "blib/". Bien sûr, vous avez besoin d'un compilateur C fonctionnel (probablement le même qui a construit perl lui-même) pour que la compilation fonctionne correctement.

L'action "code" exécute également tous les fichiers ".PL" de votre répertoire lib/. Typiquement, ceux-ci créent d'autres fichiers, nommés de la même manière mais sans le suffixe ".PL". Par exemple, un fichier lib/Foo/Bar.pm.PL pourrait créer le fichier lib/Foo/Bar.pm. Les fichiers ".PL" sont traités en premier, de sorte que tous les fichiers ".pm" (ou d'autres types que nous traitons) seront copiés correctement.

config_data
[version 0.26]

...

diff
[version 0.14]

Cette action comparera les fichiers sur le point d'être installés avec leurs homologues installés. Pour les fichiers .pm et .pod, une différence sera affichée (cela nécessite actuellement un programme 'diff' dans votre PATH). Pour les autres fichiers comme les fichiers binaires compilés, nous signalons simplement s'ils diffèrent.

Un paramètre "flags" peut être passé à l'action, lequel sera passé au programme 'diff'. Consultez la documentation de votre 'diff' pour les paramètres qu'il acceptera - un bon paramètre est "-u" :

./Build diff flags=-u
dist
[version 0.02]

Cette action est utile pour les auteurs de modules qui souhaitent empaqueter leur module pour une distribution source via un support comme CPAN. Elle créera une archive tar des fichiers listés dans

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

MANIFEST et compresse l'archive à l'aide de la compression GZIP.

Par défaut, cette action utilise le module "Archive::Tar". Cependant, vous pouvez forcer l'utilisation des exécutables binaires "tar" et "gzip" en fournissant un paramètre explicite "tar" (et optionnellement "gzip") :

./Build dist --tar C:\chemin\vers\tar.exe --gzip C:\chemin\vers\zip.exe
distcheck
[version 0.05]

Indique quels fichiers sont dans le répertoire de compilation mais pas dans le fichier MANIFEST, et vice versa. (Voir "manifest" pour plus de détails.)

distclean
[version 0.05]

Exécute l'action 'realclean' puis l'action 'distcheck'.

distdir
[version 0.05]

Crée un "répertoire de distribution" nommé "$dist_name-$dist_version" (si ce répertoire existe déjà, il sera d'abord supprimé), puis copie tous les fichiers listés dans le fichier MANIFEST dans ce répertoire. C'est à partir de ce répertoire que l'archive de distribution est créée.

distinstall
[version 0.37]

Exécute l'action 'distdir', puis se déplace dans ce répertoire et exécute un "perl Build.PL", suivi des actions 'build' et 'install' dans ce répertoire. Utilisez PERL_MB_OPT ou .modulebuildrc pour définir les options qui doivent être appliquées lors des sous-processus.

distmeta
[version 0.21]

Crée le fichier META.yml qui décrit la distribution.

META.yml est un fichier contenant divers éléments de métadonnées sur la distribution. Les métadonnées incluent le nom de la distribution, sa version, son résumé, ses prérequis, sa licence, et diverses autres informations sur la distribution. Ce fichier est créé en tant que META.yml dans un format YAML simplifié.

Le fichier META.yml doit également être listé dans MANIFEST - sinon, un avertissement sera émis.

La version actuelle de la spécification META.yml peut être trouvée sur CPAN sous le nom CPAN::Meta::Spec.

distsign
[version 0.16]

Utilise "Module::Signature" pour créer un fichier SIGNATURE pour votre distribution, et ajoute le fichier SIGNATURE au MANIFEST de la distribution.

disttest
[version 0.05]

Exécute l'action 'distdir', puis se déplace dans ce répertoire et exécute un "perl Build.PL", suivi des actions 'build' et 'test' dans ce répertoire. Utilisez PERL_MB_OPT ou .modulebuildrc pour définir les options qui doivent être appliquées lors des sous-processus.

docs
[version 0.20]

Cela générera la documentation (par exemple, les pages de manuel Unix et les documents HTML) pour tous les éléments installables sous blib/ qui contiennent du POD. S'il n'y a pas de cibles d'installation "bindoc" ou "libdoc" définies (comme ce sera le cas sur les systèmes qui ne supportent pas les pages de manuel Unix), aucune action ne sera entreprise pour les pages de manuel. S'il n'y a pas de cibles d'installation "binhtml" ou "libhtml" définies, aucune action ne sera entreprise pour les documents HTML.

fakeinstall
[version 0.02]

C'est exactement comme l'action "install", mais cela ne fera rien en réalité, cela indiquera seulement ce qu'il aurait fait si vous aviez réellement exécuté l'action "install".

help
[version 0.03]

Cette action affichera simplement un message destiné à vous aider à utiliser le processus de compilation. Elle vous montrera également une liste des actions de compilation disponibles.

Avec un argument optionnel spécifiant un nom d'action (par exemple, "Build help test"), l'action 'help' vous montrera toute la documentation POD qu'elle peut trouver pour cette action.

html
[version 0.26]

Cela générera la documentation HTML pour tous les fichiers binaires ou de bibliothèque sous blib/ qui contiennent du POD. La documentation HTML ne sera installée que si les chemins d'installation peuvent être déterminés à partir des valeurs de "Config.pm". Vous pouvez également fournir ou remplacer les chemins d'installation sur la ligne de commande en spécifiant des valeurs "install_path" pour les cibles d'installation "binhtml" et/ou "libhtml".

Avec un argument optionnel "html_links" défini à une valeur fausse, vous pouvez sauter la recherche d'autres documentations à lier, car cela peut perdre beaucoup de temps s'il n'y a pas de liens à générer de toute façon :

./Build html --html_links 0
install
[version 0.01]

Cette action utilisera "ExtUtils::Install" pour installer les fichiers depuis "blib/" dans le système. Voir "INSTALL PATHS" pour les détails sur la manière dont Module::Build détermine où installer les choses, et comment influencer ce processus.

Si vous voulez que le processus d'installation recherche dans @INC d'autres versions des éléments que vous installez et essaie de les supprimer, vous pouvez utiliser le paramètre "uninst", qui demande à "ExtUtils::Install" de le faire :

./Build install uninst=1

Cela peut être une bonne idée, car cela aide à éviter que plusieurs versions d'un module ne soient présentes sur votre système, ce qui peut être une situation confuse.

installdeps
[version 0.36]

Cette action utilisera le paramètre "cpan_client" comme commande pour installer les prérequis manquants. Il vous sera demandé si vous souhaitez installer les dépendances optionnelles.

L'option "cpan_client" vaut par défaut 'cpan' mais peut être définie comme une option ou dans .modulebuildrc. Il doit s'agir d'une commande shell qui prend une liste de modules à installer comme arguments (par exemple, 'cpanp -i' pour CPANPLUS). Si la partie programme est un chemin relatif (par exemple, 'cpan' ou 'cpanp'), elle sera localisée par rapport au programme perl qui a exécuté Build.PL.

/opt/perl/5.8.9/bin/perl Build.PL
./Build installdeps --cpan_client 'cpanp -i'
# installe dans 5.8.9
manifest
[version 0.05]

Il s'agit d'une action destinée aux auteurs de modules, et non aux personnes qui installent des modules. Elle mettra à jour le MANIFEST avec les fichiers actuellement présents dans la distribution. Vous pouvez utiliser un fichier MANIFEST.SKIP pour exclure certains fichiers ou répertoires de l'inclusion dans le MANIFEST. MANIFEST.SKIP doit contenir un ensemble d'expressions régulières, une par ligne. Si un fichier dans le répertoire de distribution correspond à l'une des expressions régulières, il ne sera pas inclus dans le MANIFEST.

Voici un point de départ raisonnable pour MANIFEST.SKIP, vous pouvez y ajouter vos propres éléments :

^_build
^Build$
^blib
~$
\.bak$
^MANIFEST\.SKIP$
CVS

Voir les actions "distcheck" et "skipcheck" si vous souhaitez savoir ce que ferait l'action "manifest", sans rien faire effectivement.

manifest_skip
[version 0.3608]

Il s'agit d'une action destinée aux auteurs de modules, et non aux personnes qui installent des modules. Elle générera un fichier MANIFEST.SKIP modèle s'il n'en existe pas déjà un.

manpages
[version 0.28]

Cela générera les pages de manuel pour tous les fichiers binaires ou de bibliothèque sous blib/ qui contiennent du POD. Les pages de manuel ne seront installées que si les chemins d'installation peuvent être déterminés à partir des valeurs de "Config.pm". Vous pouvez également fournir ou remplacer les chemins d'installation en spécifiant leurs valeurs sur la ligne de commande avec les cibles d'installation "bindoc" et "libdoc".

pardist
[version 0.2806]

Génère une distribution binaire PAR pour une utilisation avec PAR ou PAR::Dist.

Cela nécessite que le module PAR::Dist (version 0.17 et supérieure) soit installé sur votre système.

ppd
[version 0.20]

Construit un fichier PPD pour votre distribution.

Cette action accepte un argument optionnel "codebase" qui est utilisé dans le fichier PPD généré pour spécifier l'URL (généralement relative) de la distribution. Par défaut, cette valeur est le nom de la distribution sans aucune information de chemin.

Exemple :

./Build ppd --codebase "MSWin32-x86-multi-thread/Module-Build-0.21.tar.gz"
ppmdist
[version 0.23]

Génère une distribution binaire PPM et un fichier de description PPD. Cette action invoque également l'action "ppd", elle peut donc accepter le même argument "codebase" décrit sous cette action.

Cela utilise le même mécanisme que l'action "dist" pour tar & zip sa sortie, vous pouvez donc fournir des paramètres "tar" et/ou "gzip" pour affecter le résultat.

prereq_data
[version 0.32]

Ceci

Gardez toute la structure du fichier.

prereq_report
[version 0.28]

Cette action imprime une liste de toutes les prérequis, les versions nécessaires et les versions actuellement installées. Ceci peut être utile pour vérifier la configuration de votre système avant une build, ou lors de la compilation d'informations pour un rapport d'erreur.

pure_install
[version 0.28]

Cette action est identique à l'action "install". Dans le futur, lorsque "install" commencera à écrire dans le fichier $(INSTALLARCHLIB)/perllocal.pod, "pure_install" ne le fera pas, et ce sera la seule différence entre les deux.

realclean
[version 0.01]

Cette action est seulement similaire à l'action "clean", mais elle supprime également le répertoire "_build" et le script "Build". Si vous exécutez l'action "realclean", vous repartez de zéro, vous devrez donc recréer le script "Build".

retest
[version 0.2806]

C'est juste similaire à l'action "test", mais ne construit pas d'abord la distribution et n'ajoute pas blib/ au chemin de chargement, donc cela testera par rapport à une version précédemment installée de la distribution. Ceci peut être utile pour vérifier si une version installée fonctionne toujours, ou pour voir si de nouvelles versions d'une distribution passent toujours les anciens tests de régression, et ainsi de suite.

skipcheck
[version 0.05]

Rapporte quels fichiers sont ignorés en raison des entrées dans le fichier MANIFEST.SKIP (voir "manifest" pour les détails).

test
[version 0.01]

Ceci utilisera "Test::Harness" ou "TAP::Harness" pour exécuter tous les tests de régression et rapporter leurs résultats. Les tests peuvent être définis aux endroits habituels : un fichier nommé "test.pl" dans le répertoire racine, ou plusieurs fichiers se terminant par ".t" dans un répertoire "t/".

Si vous voulez que les tests soient 'verbose', c'est-à-dire qu'ils affichent des détails d'exécution des tests au lieu de seulement des informations résumées, passez l'argument "verbose=1".

Si vous voulez exécuter les tests dans le debugger de perl, passez l'argument "debugger=1".

Si vous voulez que Module::Build trouve des fichiers de test avec des extensions de noms différentes, passez l'argument "test_file_exts" avec un tableau d'extensions, comme "[qw( .t .s .z )]".

Si vous voulez que le test soit exécuté avec "TAP::Harness" au lieu de "Test::Harness", passez l'argument "tap_harness_args" comme une référence d'arguments à passer au constructeur de "TAP::Harness".

De plus, si un fichier nommé "visual.pl" existe dans le répertoire racine, il sera exécuté comme un script Perl et sa sortie sera affichée à l'utilisateur. C'est un bon endroit pour mettre des tests de vitesse ou d'autres tests qui n'utilisent pas le format "Test::Harness" pour la sortie.

Pour outrepasser le choix des tests à exécuter, vous pouvez passer un argument "test_files" avec une valeur de liste séparée par des espaces des scripts de test à exécuter. Ceci est particulièrement utile en développement, lorsque vous ne voulez exécuter qu'un seul test pour voir si vous avez corrigé un certain bug :

./Build test --test_files t/something_failing.t

Vous pouvez également passer plusieurs arguments "test_files" séparément :

./Build test --test_files t/one.t --test_files t/two.t

ou utiliser un motif glob() :

./Build test --test_files 't/01-*.t'
testall
[version 0.2807]

[Note : les actions 'testall' et les exemples de code ci-dessous sont en état alpha, voir http://www.nntp.perl.org/group/perl.module.build/2007/03/msg584.html]

Exécute l'action "test" plus chacune des actions "test$type" définies par les valeurs de la clé "test_types".

Actuellement, vous devez définir la méthode ACTION_test$type vous-même et les énumérer dans le paramètre "test_types".

my $mb = Module::Build->subclass(
  code => q(
    sub ACTION_testspecial { shift->generic_test(type => 'special'); }
    sub ACTION_testauthor  { shift->generic_test(type => 'author'); }
  )
)->new(
  ...
  test_types  => {
    special => '.st',
    author  => ['.at', '.pt' ],
  },
  ...
testcover
[version 0.26]

Exécute l'action "test" avec "Devel::Cover", générant un rapport de couverture de code qui montre quelles parties du code ont été effectivement exécutées pendant les tests.

Pour passer des options à "Devel::Cover", définissez la variable d'environnement $DEVEL_COVER_OPTIONS :

DEVEL_COVER_OPTIONS=-ignore,Build ./Build testcover
testdb
[version 0.05]

C'est un synonyme de l'action "test" avec l'argument "debugger=1".

testpod
[version 0.25]

Ceci vérifie tous les fichiers décrits dans l'action "docs" et produit une sortie au format "Test::Harness". Si vous êtes l'auteur d'un module, c'est utile à exécuter avant de créer une nouvelle version.

testpodcoverage
[version 0.28]

Ceci vérifie la couverture de pod de la distribution et produit une sortie au format "Test::Harness". Si vous êtes l'auteur d'un module, c'est utile à exécuter avant de créer une nouvelle version.

versioninstall
[version 0.16]

** Note : comme "only.pm" est très nouveau et que nous avons récemment ajouté le support ici, cette fonctionnalité est considérée comme expérimentale. **

Si vous avez installé le module "only.pm" sur votre système, vous pouvez utiliser cette action pour installer un module dans des arborescences de bibliothèques spécifiques à la version. Cela signifie que vous pouvez avoir plusieurs versions d'un module installées et en utiliser une spécifique comme ceci :

use only MyModule => 0.55;

Pour outrepasser les répertoires d'installation par défaut dans "only::config", spécifiez le paramètre "versionlib" lors de l'exécution du script "Build.PL" :

perl Build.PL --versionlib /my/version/place/

Pour spécifier quelle version du module installer, spécifiez le paramètre "version" lors de l'exécution du script "Build.PL" :

perl Build.PL --version 0.50

Voir la documentation de "only.pm" pour plus d'informations sur les installations spécifiques par version.

OPTIONS

Options en Ligne de Commande

Les options suivantes peuvent être utilisées lors de toute invocation de "Build.PL" ou du script Build, pendant n'importe quelle action. Pour des informations sur d'autres options spécifiques à une action, voir la documentation de l'action correspondante.

NOTE : il y a un support préliminaire pour les options utilisant le style plus familier des options longues. De nombreuses options peuvent être précédées du préfixe "--", et les tirets sont remplacés par des traits de soulignement (par exemple, "--use_rcfile"). De plus, les arguments pour les options booléennes sont facultatifs, et les options booléennes peuvent être niées en préférant "no" ou "no-" (par exemple, "--noverbose" ou "--no-verbose").

quiet
Supprime les messages informatifs de la sortie.
verbose
Affiche des informations supplémentaires sur Build dans la sortie. "verbose" désactive "quiet".
cpan_client
Définit le "cpan_client" à utiliser avec l'action "installdeps". Voir "installdeps" pour plus de détails.
use_rcfile
Charge le fichier d'options ~/.modulebuildrc. Cette option peut être définie à false pour empêcher le chargement du fichier de ressources personnalisé.
allow_mb_mismatch
Supprime la vérification de démarrage qui contrôle la version de Module::Build actuellement exécutée.
g sous est la même version qui a été initialement appelée lors de la construction de la distribution (c'est-à-dire lorsque le script "Build.PL" a été exécuté pour la première fois). Depuis la version 0.3601, une divergence entraîne un avertissement au lieu d'une erreur fatale, donc cette option supprime simplement l'avertissement.
debug
Affiche les informations de débogage de Module::Build sur STDOUT, telles qu'une trace des actions de construction exécutées.

Fichier d'options par défaut (.modulebuildrc)

[version 0.28]

Lorsque Module::Build démarre, il recherche d'abord un fichier, $ENV{HOME}/.modulebuildrc. S'il n'est pas trouvé là, il recherche dans le fichier .modulebuildrc dans les répertoires référencés par les variables d'environnement "HOMEDRIVE" + "HOMEDIR", "USERPROFILE", "APPDATA", "WINDIR", "SYS$LOGIN". Si le fichier existe, les options spécifiées seront utilisées comme valeurs par défaut, comme si elles étaient tapées sur la ligne de commande. Les valeurs par défaut peuvent être remplacées en spécifiant de nouvelles valeurs sur la ligne de commande.

Le nom de l'action doit figurer en début de ligne, suivi d'un espace quelconque, puis des options. Les options sont données de la même manière que sur la ligne de commande. Elles peuvent être séparées par un espace quelconque, y compris des sauts de ligne, tant qu'il y a un espace au début de chaque ligne de continuation. Tout ce qui suit une marque dièse ("#") est considéré comme un commentaire et est supprimé avant l'analyse. Si plusieurs lignes commencent par le même nom d'action, ces lignes sont fusionnées en un seul ensemble d'options.

Outre les actions régulières, il existe deux pseudo-actions spéciales : la clé "*" (astérisque) désigne toutes les options globales qui doivent être appliquées à toutes les actions, et la clé 'Build_PL' spécifie les options à appliquer lorsque vous appelez "perl Build.PL".

*           verbose=1   # options globales
diff        flags=-u
install     --install_base /home/ken
            --install_path html=/home/ken/docs/html
installdeps --cpan_client 'cpanp -i'

Si vous souhaitez placer votre fichier de ressources dans un emplacement différent, vous pouvez définir la variable d'environnement "MODULEBUILDRC" avec le chemin absolu complet du fichier contenant vos options.

Variables d'environnement

MODULEBUILDRC
[version 0.28]

Spécifie un emplacement alternatif pour un fichier d'options par défaut, comme décrit ci-dessus.

PERL_MB_OPT
[version 0.36]

Options de ligne de commande appliquées à Build.PL ou à toute action Build. La chaîne est divisée comme le ferait le shell (par exemple, par des espaces) et le résultat est ajouté avant les arguments réels de la ligne de commande.

CHEMINS D'INSTALLATION

[version 0.19]

Lorsque vous appelez l'action "build" de Module::Build, il doit déterminer où installer les choses. En bref, les emplacements d'installation par défaut sont déterminés à partir de Config.pm, et ils peuvent être remplacés en utilisant le paramètre "install_path". Un paramètre "install_base" vous permet de spécifier une racine d'installation alternative comme /home/foo, et un "destdir" vous permet de spécifier un répertoire d'installation temporaire comme /tmp/install au cas où vous souhaiteriez créer des packages installables groupés.

Nativement, Module::Build fournit des emplacements d'installation par défaut pour les types d'éléments installables suivants :

lib
Habituellement des fichiers de modules Perl purs se terminant par .pm.
arch
Fichiers de modules "dépendants de l'architecture", généralement produits en compilant du code XS, Inline, ou similaire.
script
Programmes écrits en Perl pur. Afin d'améliorer la réutilisation, essayez de les rendre aussi petits que possible - placez le code dans des modules lorsque cela est possible.
bin
"Programmes exécutables dépendants de l'architecture", c'est-à-dire du code C compilé ou quelque chose de similaire. Assez rare de le voir dans une distribution Perl, mais cela arrive.
bindoc
Documentation pour les éléments dans "script" et "bin". Généralement générée à partir du POD dans ces fichiers. Sous Unix, ce sont des pages de manuel appartenant à la catégorie 'man1'.
libdoc
Documentation pour les éléments dans "lib" et "arch". C'est généralement généré à partir du POD dans les fichiers .pm. Sous Unix, ce sont des pages de manuel appartenant à la catégorie 'man3'.
binhtml
C'est la même chose que "bindoc" ci-dessus, mais s'applique aux documents HTML.
libhtml
C'est la même chose que "libdoc" ci-dessus, mais s'applique aux documents HTML.

Quatre autres paramètres vous permettent de contrôler divers aspects de la manière dont les chemins d'installation sont déterminés :

installdirs
Les destinations par défaut pour ces éléments installables proviennent des entrées de "Config.pm" de votre système. Vous pouvez sélectionner parmi trois ensembles différents d'emplacements par défaut en définissant le paramètre "installdirs" comme suit : 
                        'installdirs' réglé sur :
                 core          site                vendor
            utilise les valeurs par défaut suivantes de Config.pm :
lib     => installprivlib  installsitelib      installvendorlib
arch    => installarchlib  installsitearch     installvendorarch
script  => installscript   installsitescript   installvendorscript
bin     => installbin      installsitebin      installvendorbin
bindoc  => installman1dir  installsiteman1dir  installvendorman1dir
libdoc  => installman3dir  installsiteman3dir  installvendorman3dir
binhtml => installhtml1dir installsitehtml1dir installvendorhtml1dir [*]
libhtml => installhtml3dir installsitehtml3dir installvendorhtml3dir [*]
* Sous certains OS (par ex. MSWin32), la destination des documents HTML est
  déterminée par l'entrée C<Config.pm> C<installhtmldir>.

La valeur par défaut de "installdirs" est "site". Si vous créez des distributions vendor de packages de modules, vous pouvez vouloir faire quelque chose comme ceci :

perl Build.PL --installdirs vendor

ou

./Build install --installdirs vendor

Si vous installez une version mise à jour d'un module qui était inclus avec Perl lui-même (c'est-à-dire un "module core"), alors vous pouvez définir "installdirs" sur "core" pour écraser le module à son emplacement actuel.

(Notez que la ligne 'script' est différente de "MakeMaker" - malheureusement, il n'existe pas d'entrée "installsitescript" ou "installvendorscript" dans "Config.pm", donc nous utilisons les entrées "installsitebin" et "installvendorbin" pour au moins obtenir la localisation générale correcte. À l'avenir, si "Config.pm" ajoute des entrées plus appropriées, nous commencerons à les utiliser.)

install_path
Une fois les valeurs par défaut définies, vous pouvez les remplacer.

Sur la ligne de commande, cela ressemblerait à ceci :

perl Build.PL --install_path lib=/foo/lib --install_path arch=/foo/lib/arch

ou ceci :

./Build install --install_path lib=/foo/lib --install_path arch=/foo/lib/arch
install_base
Vous pouvez également définir l'ensemble des chemins d'installation en fournissant le paramètre "install_base" pour pointer vers un répertoire sur votre système. Par exemple, si vous définissez "install_base" sur "/home/ken" sur un système Linux, vous installerez comme suit : 
lib     => /home/ken/lib/perl5
arch    => /home/ken/lib/perl5/i386-linux
script  => /home/ken/bin
bin     => /home/ken/bin
bindoc  => /home/ken/man/man1
libdoc  => /home/ken/man/man3
binhtml => /home/ken/html
libhtml => /home/ken/html

Notez que c'est *différent* de la manière dont le paramètre "PREFIX" de "MakeMaker" fonctionne. "install_base" vous donne simplement une disposition par défaut sous le répertoire que vous spécifiez, ce qui peut avoir peu de rapport avec la disposition "installdirs=site".

La disposition exacte sous le répertoire que vous spécifiez peut varier selon le système - nous essayons de faire ce qui est "sensé" sur chaque plateforme.

destdir
Si vous souhaitez tout installer d'abord dans un répertoire temporaire (par exemple, si vous souhaitez créer une arborescence de répertoires à partir de laquelle un gestionnaire de packages comme "rpm" ou "dpkg" pourrait créer un package), vous pouvez utiliser le paramètre "destdir" : 
perl Build.PL --destdir /tmp/foo

ou

./Build install --destdir /tmp/foo

Cela installera effectivement dans "/tmp/foo/$sitelib", "/tmp/foo/$sitearch", et similaires, sauf qu'il utilisera "File::Spec" pour que les noms de chemin fonctionnent correctement sur la plateforme sur laquelle vous installez.

INSTALL PATHS

--prefix dir

Fourni pour la compatibilité avec l'argument PREFIX de "ExtUtils::MakeMaker". "prefix" doit être utilisé lorsque vous souhaitez que Module::Build installe vos modules, votre documentation et vos scripts au même endroit que le mécanisme PREFIX de "ExtUtils::MakeMaker".

Les commandes suivantes sont équivalentes.

perl Build.PL --prefix /tmp/foo
perl Makefile.PL PREFIX=/tmp/foo

En raison de la nature complexe de la logique de préfixage, le comportement de PREFIX dans "MakeMaker" a subtilement évolué au fil du temps. La logique --prefix de Module::Build est équivalente à la logique PREFIX trouvée dans "ExtUtils::MakeMaker" 6.30.

Les mainteneurs de "MakeMaker" comprennent les problèmes liés au mécanisme PREFIX et ont ajouté le support INSTALL_BASE dans la version 6.31 de "MakeMaker", sortie en 2006.

Si vous n'avez pas besoin de maintenir la compatibilité avec les anciennes versions (pré-6.31) de "ExtUtils::MakeMaker" ou si vous commencez une nouvelle installation Perl, nous vous recommandons plutôt d'utiliser "install_base" (et "INSTALL_BASE" dans "ExtUtils::MakeMaker"). Voir "Installing in the same location as ExtUtils::MakeMaker" dans Module::Build::Cookbook pour plus d'informations.

COMPARISON

Une comparaison entre "Module::Build" et d'autres installateurs de distributions CPAN.

  • ExtUtils::MakeMaker nécessite "make" et l'utilisation d'un Makefile. "Module::Build" ne le nécessite pas, tout comme d'autres installateurs pure-perl suivant la spécification Build.PL tels que Module::Build::Tiny. En pratique, cela n'est généralement pas un problème pour l'utilisateur final, car "make" est déjà requis pour installer la plupart des modules CPAN, même sous Windows.
  • ExtUtils::MakeMaker est un module de base dans toutes les versions de Perl 5 et doit maintenir la compatibilité pour installer la majorité des modules CPAN. "Module::Build" a été ajouté au cœur de Perl dans la version 5.10 et retiré du cœur dans la version 5.20, et (comme ExtUtils::MakeMaker) n'est mis à jour que pour corriger les problèmes critiques et maintenir la compatibilité. "Module::Build" et d'autres installateurs non-core comme Module::Build::Tiny sont installés depuis CPAN en se déclarant comme une dépendance de la phase "configure", et de cette manière, tout installateur peut être utilisé à la place d'ExtUtils::MakeMaker.
  • La personnalisation du processus de construction avec ExtUtils::MakeMaker implique de surcharger certaines méthodes qui forment le Makefile en définissant les sous-programmes dans l'espace de noms "MY::", ce qui nécessite une connaissance approfondie de Makefile, mais permet une personnalisation ciblée de l'ensemble de la construction. La personnalisation de "Module::Build" implique de sous-classer "Module::Build" lui-même, d'ajouter ou de surcharger des méthodes pure-perl qui représentent les actions de construction, lesquelles sont invoquées comme arguments passés au script généré "./Build". C'est un concept plus simple, mais qui nécessite de redéfinir les actions de construction standard pour invoquer vos personnalisations. Module::Build::Tiny ne permet pas de personnalisation.
  • "Module::Build" offre plus de fonctionnalités et une meilleure expérience pour les auteurs de distributions que ExtUtils::MakeMaker. Cependant, des outils spécifiquement conçus pour l'auteurisation, tels que Dist::Zilla et ses dérivés Dist::Milla et Minilla, offrent ces fonctionnalités et plus encore, et génèrent un script de configuration (Makefile.PL/Build.PL) qui utilisera l'un ou l'autre des différents installateurs séparément du côté de l'utilisateur final. App::ModuleBuildTiny est un outil d'auteurisation autonome alternatif pour les distributions utilisant Module::Build::Tiny, qui ne nécessite qu'un simple Build.PL de deux lignes.
