NOM

Module::Runtime - gestion des modules au moment de l'exécution

SYNTAXE

use Module::Runtime qw(
    $module_name_rx is_module_name check_module_name
    module_notional_filename require_module);
if($module_name =~ /\A$module_name_rx\z/o) { ...
if(is_module_name($module_name)) { ...
check_module_name($module_name);
$notional_filename = module_notional_filename($module_name);
require_module($module_name);
use Module::Runtime qw(use_module use_package_optimistically);
$bi = use_module("Math::BigInt", 1.31)->new("1_234");
$widget = use_package_optimistically("Local::Widget")->new;
use Module::Runtime qw(
    $top_module_spec_rx $sub_module_spec_rx
    is_module_spec check_module_spec
    compose_module_name);
if($spec =~ /\A$top_module_spec_rx\z/o) { ...
if($spec =~ /\A$sub_module_spec_rx\z/o) { ...
if(is_module_spec("Standard::Prefix", $spec)) { ...
check_module_spec("Standard::Prefix", $spec);
$module_name = compose_module_name("Standard::Prefix", $spec);

DESCRIPTION

Les fonctions exportées par ce module traitent de la gestion des modules Perl au moment de l'exécution, qui est normalement gérée au moment de la compilation. Ce module évite d'utiliser d'autres modules, de sorte qu'il puisse être utilisé dans une infrastructure de bas niveau.

Les parties de ce module qui traitent des noms de modules appliquent la même syntaxe que celle utilisée pour les barewords dans le code source Perl. En principe, cette syntaxe peut varier entre les versions de Perl, et ce module applique la syntaxe du Perl sur lequel il s'exécute. En pratique, la syntaxe utilisable n'a pas encore changé. Il y a une intention de prendre en charge les noms de modules Unicode à l'avenir, mais cela n'a pas encore abouti à une installation cohérente.

Les fonctions de ce module dont le but est de charger des modules incluent des solutions de contournement pour trois anciens bugs du cœur de Perl concernant "require". Ces solutions de contournement sont appliquées sur toute version de Perl où les bugs existent, sauf pour un cas où l'un des bugs ne peut pas être correctement contourné en Perl pur.

Syntaxe des noms de modules

La syntaxe des noms de modules utilisables n'a pas changé de Perl 5.000 à Perl 5.19.8. La syntaxe est entièrement composée de caractères ASCII. Depuis Perl 5.6, il y a eu une tentative de permettre l'utilisation de caractères Unicode non-ASCII dans le code source Perl, mais elle était fondamentalement défectueuse (comme l'intégralité de la gestion Unicode de Perl 5.6) et est restée pratiquement inutilisable jusqu'à ce qu'elle reçoive une attention dans la série Perl 5.15. Bien que Unicode soit maintenant constamment accepté par le parseur dans certains endroits, il reste défectueux pour les noms de modules. De plus, aucun travail n'a encore été effectué sur la manière de mapper les noms de modules Unicode en noms de fichiers, donc à cet égard également, les noms de modules Unicode sont inutilisables.

La syntaxe du nom du module est précisément : la chaîne doit consister en un ou plusieurs segments séparés par "::" ; chaque segment doit consister en un ou plusieurs caractères d'identifiant (alphanumériques ASCII plus "_") ; le premier caractère de la chaîne ne doit pas être un chiffre. Ainsi, ""IO::File"", ""warnings"", et ""foo::123::x_0"" sont tous des noms de modules valides, tandis que ""IO::"" et ""1foo::bar"" ne le sont pas. Les séparateurs "'" ne sont pas autorisés par ce module, bien qu'ils restent utilisables dans le code source Perl, étant traduits en "::" dans le parseur.

Bugs du cœur corrigés

Le premier bug corrigé est le bug du cœur [perl #68590], qui provoque une fuite de l'état lexical d'un fichier vers un autre qui est "require"d/"use"d à partir de celui-ci. Ce bug est présent de Perl 5.6 à Perl 5.10, et est corrigé dans Perl 5.11.0. De Perl 5.9.4 à Perl 5.10.0, aucune solution de contournement satisfaisante n'est possible en Perl pur. La solution de contournement signifie que les modules chargés via ce module ne subissent pas cette pollution de leur état lexical. Les modules chargés d'autres manières, ou via ce module sur les versions de Perl où la solution de contournement en Perl pur est impossible, restent vulnérables. Le module Lexical::SealRequireHints fournit une solution complète pour ce bug.

Le deuxième bug corrigé provoque certains types d'échecs lors du chargement de modules, principalement des erreurs de compilation dans le module chargé, qui sont enregistrées dans %INC comme si elles avaient réussi, de sorte que les tentatives ultérieures de charger le même module indiquent immédiatement le succès. Ce bug est présent jusqu'à Perl 5.8.9, et est corrigé dans Perl 5.9.0. La solution de contournement signifie qu'une erreur de compilation dans un module chargé via ce module ne sera pas mise en cache comme un succès. Les modules chargés d'autres manières restent susceptibles de produire des entrées %INC erronées, et s'il existe une entrée erronée, elle induira ce module en erreur s'il est utilisé pour retenter le chargement.

Le troisième bug corrigé provoque la mauvaise prise en compte du contexte au niveau du fichier d'un module chargé, si "require" est invoqué dans un emplacement qui hérite du contexte d'une portée supérieure. Ce bug est présent jusqu'à Perl 5.11.2, et est corrigé dans Perl 5.11.3. La solution de contournement signifie qu'un module chargé via ce module verra toujours le bon contexte. Les modules chargés d'autres manières restent vulnérables.

EXPRESSIONS RÉGULIÈRES

Ces expressions régulières n'incluent pas d'ancres, donc pour vérifier si une chaîne entière correspond à un élément de syntaxe, vous devez fournir vous-même les ancres.

$module_name_rx
Correspond à un nom de module Perl valide en syntaxe bareword.
$top_module_spec_rx
Correspond à une spécification de module à utiliser avec "compose_module_name", où aucun préfixe n'est utilisé.
$sub_module_spec_rx
Correspond à une spécification de module à utiliser avec "compose_module_name", où un préfixe est utilisé.

FONCTIONS

Gestion de base des modules

is_module_name(ARG)
Retourne une valeur vraie indiquant si ARG est une chaîne simple respectant la syntaxe des noms de modules Perl telle que décrite pour "$module_name_rx".
is_valid_module_name(ARG)
Alias obsolète pour "is_module_name".
check_module_name(ARG)
Vérifie si ARG est une chaîne simple respectant la syntaxe des noms de modules Perl telle que décrite pour "$module_name_rx". Retourne normalement si c'est le cas, ou "die" si ce n'est pas le cas.
module_notional_filename(NAME)
Génère un nom de fichier relatif notionnel pour un module, qui est utilisé dans certaines interfaces du cœur de Perl. Le NOM est une chaîne, qui doit être un nom de module valide (un ou plusieurs segments séparés par "::"). Si ce n'est pas un nom valide, la fonction "die".

Le nom de fichier notionnel pour le module nommé est généré et retourné. Ce nom de fichier est toujours au style Unix, avec des séparateurs de répertoire "/" et un suffixe ".pm". Ce type de nom de fichier peut être utilisé comme argument pour "require", et est la clé qui apparaît dans %INC pour identifier un module, indépendamment de la syntaxe locale réelle du nom de fichier.

require_module(NAME)
Ceci est essentiellement la forme bareword de "require", sous forme d'exécution. Le NOM est une chaîne, qui doit être un nom de module valide (un ou plusieurs segments séparés par "::"). Si ce n'est pas un nom valide, la fonction "die".

Le module spécifié par NOM est chargé, s'il n'a pas déjà été chargé, de la manière de la forme bareword de

Chargement optimiste de modules

use_module(NAME,VERSION=undef)
Charge le module nommé NAME, si ce n'est pas déjà fait. S'il est fourni, VERSION doit être la version la plus ancienne acceptable du module. Si le module est chargé, ou s'il avait déjà été chargé, il est retourné. Si le chargement échoue, ou si la version n'est pas satisfaite, la fonction "die".

Ce qui suit est une comparaison avec l'utilisation de "use" directement : 

use Module::Runtime qw(use_module);
my $package = use_module("Math::BigInt", 1.31);
# ... maintenant vous pouvez utiliser $package
est à peu près l'équivalent de : 
use Math::BigInt 1.31;
# ... maintenant vous pouvez utiliser "Math::BigInt"
Bien qu'il y ait des différences subtiles dans le comportement des erreurs et la manière dont les informations sont retournées. Ce qui est retourné par "use_module" est l'objet package.

use_package_optimistically(NAME)
Charge le module nommé NAME, si ce n'est pas déjà fait. S'il est chargé, ou s'il avait déjà été chargé, il est retourné. Si le chargement échoue, la fonction "die". La différence avec "use_module" est qu'il n'y a pas de paramètre de version.

Vérification de spécifications de modules

is_module_spec(PREFIX,ARG)
Retourne une valeur vraie indiquant si ARG est une chaîne satisfaisant la syntaxe du nom de module, potentiellement avec un préfixe PREFIX. (Voir la description de "compose_module_name".)
check_module_spec(PREFIX,ARG)
Vérifie si ARG est une chaîne satisfaisant la syntaxe du nom de module, potentiellement avec un préfixe PREFIX. Retourne normalement si c'est le cas, ou "die" si ce n'est pas le cas.
compose_module_name(PREFIX,SPEC)
Compose un nom de module complet à partir d'un PREFIX et d'une spécification SPEC. Le PREFIX est une chaîne qui sera le nom du module le plus haut niveau, et la SPEC est ce qui suit.

Par exemple, si le préfixe est ""Standard::"", et que la spécification est ""Path::Tiny"", le nom de module retourné est ""Standard::Path::Tiny"". Si la spécification est ""Base"", le nom de module retourné est ""Standard::Base"".

Si le PREFIX est vide, la SPEC est utilisée telle quelle.

La fonction produira une erreur si le PREFIX se termine par "::", ou si la SPEC commence par "::".

Le <i>NOM</i> est traité comme dans « require_module » ci-dessus : il doit s'agir d'un nom de module, et le module nommé est chargé comme par la forme bareword de « require ». <p>Si une <i>VERSION</i> est spécifiée, la méthode « VERSION » du module chargé est appelée avec la <i>VERSION</i> spécifiée comme argument. Ceci sert normalement à s'assurer que la version chargée est au moins la version requise. C'est la même fonctionnalité fournie par le paramètre <i>VERSION</i> de « use ».</p> <p>En cas de succès, le nom du module est retourné. Ceci est différent de « require_module », et est fait pour que l'appel entier à « use_module » puisse être utilisé comme nom de classe pour appeler un constructeur, comme dans l'exemple du synopsis.</p></dd> <dt id="use_package_optimistically(NAME_,">use_package_optimistically(NOM[, VERSION])</dt> <dd>Ceci est un analogue de « use_module » pour la situation où il y a une incertitude quant à savoir si un package/classe est défini dans son propre module ou par un autre moyen. Il tente de faire en sorte que le package nommé soit disponible, soit en chargeant un module, soit en ne faisant rien et en espérant. <p>Une tentative est faite pour charger le module nommé (comme par la forme bareword de « require »). Si le module ne peut pas être trouvé, il est supposé que le package était en fait déjà chargé par d'autres moyens, et aucune erreur n'est signalée. C'est la partie optimiste.</p> <p><i>Attention</i> ce chargement facultatif de module est susceptible de provoquer un comportement peu fiable, y compris des problèmes de sécurité. Il interagit particulièrement mal avec la présence de « . » dans « @INC », qui était l'état par défaut dans les Perls antérieurs à 5.25.11. Si un package est en fait défini par un moyen autre qu'un module, alors l'application de cette fonction à celui-ci provoque une tentative spurious de charger un module qui est censé être inexistant. Si un module existe en fait sous ce nom, il sera chargé involontairement. Si « . » est dans « @INC » et que ce code est exécuté avec le répertoire courant étant l'un des répertoires écrivables par un utilisateur malveillant (tel que <tt>/tmp</tt>>), alors l'utilisateur malveillant peut facilement faire exécuter du code arbitraire par la victime, en créant un fichier de module sous le nom prévisible chargé spurious dans le répertoire écrivable. En général, le chargement facultatif de modules doit être évité.</p> <p>C'est en grande partie la même opération qui est effectuée par le pragma de base pour s'assurer que les classes de base spécifiées sont disponibles. Le comportement de base a été simplifié dans la version 2.18, puis amélioré dans la version 2.20, et à ces deux occasions cette fonction a changé pour correspondre.</p> <p>Si une <i>VERSION</i> est spécifiée, la méthode « VERSION » du package chargé est appelée avec la <i>VERSION</i> spécifiée comme argument. Ceci sert normalement à s'assurer que la version chargée est au moins la version requise. En cas de succès, le nom du package est retourné. Ces aspects de la fonction fonctionnent comme « use_module ».</p></dd></dl> </section> <section class="Ss"> <h2 class="Ss" id='Module_name_composition'>Composition du nom de module</h2> <dl class="Bl-tag"> <dt id="is_module_spec(PREFIX,">is_module_spec(PREFIXE, SPEC)</dt> <dd>Retourne une valeur booléenne indiquant si <tt>SPEC</tt> est une entrée valide pour « compose_module_name ». La présence d'un <tt>PREFIXE</tt> affecte la validité de <tt>SPEC</tt>, mais la valeur exacte du préfixe n'est pas importante, donc cette fonction traite <tt>PREFIXE</tt> comme une valeur booléenne.</dd> <dt id="is_valid_module_spec(PREFIX,">is_valid_module_spec(PREFIXE, SPEC)</dt> <dd>Alias obsolète pour « is_module_spec ».</dd> <dt id="check_module_spec(PREFIX,">check_module_spec(PREFIXE, SPEC)</dt> <dd>Vérifie si <tt>SPEC</tt> est une entrée valide pour « compose_module_name ». Retourne normalement si c'est le cas, ou « die » si ce n'est pas le cas.</dd> <dt id="compose_module_name(PREFIX,">compose_module_name(PREFIXE, SPEC)</dt> <dd>Cette fonction est destinée à faciliter la spécification d'un nom de module Perl au moment de l'exécution. Les utilisateurs ont un plus grand besoin d'abréviations et de sensibilité au contexte que les programmeurs, et les noms de modules Perl deviennent un peu lourds. <tt>SPEC</tt> est ce que l'utilisateur spécifie, et cette fonction le traduit en un nom de module sous forme standard, qu'elle retourne. <p><tt>SPEC</tt> a une syntaxe à peu près celle d'un nom de module standard : il doit se composer d'un ou plusieurs segments de nom, chacun composé d'un ou plusieurs caractères identificateurs. Cependant, « / » est autorisé comme séparateur, en plus du « :: » standard. Les deux séparateurs sont entièrement interchangeables.</p> <p>De plus, si <tt>PREFIXE</tt> n'est pas « undef », il doit s'agir d'un nom de module sous forme standard, et il est préfixé au nom spécifié par l'utilisateur.
