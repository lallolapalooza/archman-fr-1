NOM

Module::Build::Cookbook - Exemples d'utilisation de Module::Build

DESCRIPTION

"Module::Build" n'est pas conceptuellement très compliqué, mais les exemples sont toujours utiles. Les recettes suivantes devraient aider les développeurs et/ou les installateurs à assembler les pièces des autres parties de la documentation.

RECETTES DE BASE

Installation de modules utilisant Module::Build

Dans la plupart des cas, vous pouvez simplement exécuter les commandes suivantes :

perl Build.PL
./Build
./Build test
./Build install

Il n'y a rien de compliqué ici : d'abord vous exécutez un script appelé Build.PL, puis vous exécutez un script (nouvellement généré) appelé Build en lui passant divers arguments.

Les commandes exactes peuvent varier un peu selon la façon dont vous invoquez les scripts perl sur votre système. Par exemple, si vous avez plusieurs versions de perl installées, vous pouvez installer pour les répertoires de bibliothèque d'une version perl particulière comme suit :

/usr/bin/perl5.8.1 Build.PL
./Build
./Build test
./Build install

Sous Windows, où le répertoire courant est toujours recherché en premier pour les scripts, vous ferez probablement ceci :

perl Build.PL
Build
Build test
Build install

Sur les anciens Mac OS (version 9 ou inférieure) utilisant MacPerl, vous pouvez double-cliquer sur le script Build.PL pour créer le script Build, puis double-cliquer sur le script Build pour exécuter ses actions "build", "test" et "install".

Le script Build sait quel perl a été utilisé pour exécuter Build.PL, vous n'avez donc pas besoin de ré-invoquer le script Build avec le chemin complet de perl à chaque fois. Si vous l'invoquez avec le mauvais chemin perl, vous obtiendrez un avertissement ou une erreur fatale.

Modification des valeurs de Config.pm

"Module::Build" s'appuie fortement sur diverses valeurs de "Config.pm" de perl pour faire son travail. Par exemple, les chemins d'installation par défaut sont donnés par "installsitelib" et "installvendorman3dir" et leurs compagnons, les paramètres du linker et du compilateur C sont donnés par "ld", "lddlflags", "cc", "ccflags", et ainsi de suite. Si vous êtes assez sûr de savoir ce que vous faites, vous pouvez dire à "Module::Build" de prétendre qu'il y a des valeurs différentes dans Config.pm de ce qui est réellement là, en passant des arguments pour le paramètre "--config" sur la ligne de commande :

perl Build.PL --config cc=gcc --config ld=gcc

Dans le script "Build.PL", la même chose peut être accomplie en passant des valeurs pour le paramètre "config" à new() :

my $build = Module::Build->new
  (
   ...
   config => { cc => 'gcc', ld => 'gcc' },
   ...
  );

Dans le code de construction personnalisé, la même chose peut être accomplie en appelant la méthode "config" dans Module::Build :

$build->config( cc => 'gcc' );     # Définir
$build->config( ld => 'gcc' );     # Définir
...
my $linker = $build->config('ld'); # Obtenir

Installation de modules utilisant l'interface programmaticque

Si vous avez besoin de construire, tester et/ou installer des modules à partir d'un autre code perl (par opposition à l'utilisateur qui tape les commandes d'installation dans le shell), vous pouvez utiliser l'interface programmaticque. Créez un objet Module::Build (ou un objet d'une sous-classe personnalisée de Module::Build) puis invoquez sa méthode dispatch() pour exécuter diverses actions.

my $build = Module::Build->new
  (
   module_name => 'Foo::Bar',
   license     => 'perl',
   requires    => { 'Some::Module'   => '1.23' },
  );
$build->dispatch('build');
$build->dispatch('test', verbose => 1);
$build->dispatch('install');

Le premier argument de dispatch() est le nom de l'action, et tous les arguments suivants sont des paramètres nommés.

C'est l'interface que nous utilisons pour tester Module::Build lui-même dans les tests de régression.

Installation dans un répertoire temporaire

Pour créer des paquets pour des gestionnaires de paquets comme "rpm" de RedHat ou "deb" de Debian, vous pourriez avoir besoin d'installer dans un répertoire temporaire d'abord, puis de créer le paquet à partir de cette installation temporaire. Pour ce faire, spécifiez le paramètre "destdir" à l'action "install" :

./Build install --destdir /tmp/my-package-1.003

Ceci ajoute essentiellement le répertoire /tmp/my-package-1.003 devant tous les chemins d'installation.

Installation dans un répertoire non standard

Pour installer dans un répertoire non standard (par exemple, si vous n'avez pas la permission d'installer dans les répertoires du système), vous pouvez utiliser les paramètres "install_base" ou "prefix" :

./Build install --install_base /foo/bar

Voir "INSTALL PATHS" dans Module::Build pour une discussion beaucoup plus complète sur la façon dont les chemins d'installation sont déterminés.

Installation au même endroit que ExtUtils::MakeMaker

Avec l'introduction de "--prefix" dans Module::Build 0.28 et "INSTALL_BASE" dans "ExtUtils::MakeMaker" 6.31, il est facile de les faire tous les deux s'installer aux mêmes endroits.

Tout d'abord, assurez-vous d'avoir au moins la version 0.28 de Module::Build installée et la version 6.31 de "ExtUtils::MakeMaker". Les versions antérieures ont des comportements d'installation différents (et dans certains cas, assez étranges).

Les indicateurs d'installation suivants sont équivalents entre "ExtUtils::MakeMaker" et "Module::Build".

MakeMaker             Module::Build
PREFIX=...            --prefix ...
INSTALL_BASE=...      --install_base ...
DESTDIR=...           --destdir ...
LIB=...               --install_path lib=...
INSTALLDIRS=...       --installdirs ...
INSTALLDIRS=perl      --installdirs core
UNINST=...            --uninst ...
INC=...               --extra_compiler_flags ...
POLLUTE=1             --extra_compiler_flags -DPERL_POLLUTE

Par exemple, si vous installez actuellement des modules "MakeMaker" avec cette commande :

perl Makefile.PL PREFIX=~
make test
make install UNINST=1

Vous pouvez installer au même endroit avec Module::Build en utilisant ceci :

perl Build.PL --prefix ~
./Build test
./Build install --uninst 1

"prefix" par rapport à "install_base"

Le comportement de "prefix" est compliqué et dépend de la configuration de votre Perl. Les chemins d'installation résultants varieront d'une machine à l'autre, et même de différentes installations de Perl sur la même machine. Pour cette raison, il est difficile de documenter où "prefix" placera vos modules.

En revanche, "install_base" a des emplacements d'installation prévisibles et faciles à expliquer. Maintenant que "Module::Build" et "MakeMaker" ont tous deux "install_base", il y a peu de raisons d'utiliser "prefix" autre que pour préserver votre inst existante

allation locations. If you are starting a fresh Perl installation we encourage you to use "install_base". If you have an existing installation installed via "prefix", consider moving it to an installation structure matching "install_base" and using that instead.

Exécuter un fichier de test unique

"Module::Build" prend en charge l'exécution d'un seul test, ce qui vous permet de traquer les erreurs plus rapidement. Utilisez le format suivant :

./Build test --test_files t/mytest.t

En outre, vous pourriez vouloir exécuter le test en mode verbeux pour obtenir une sortie plus informative :

./Build test --test_files t/mytest.t --verbose 1

Je l'exécute si fréquemment que je définis l'alias de shell suivant :

alias t './Build test --verbose 1 --test_files'

Ainsi, je peux simplement exécuter "t t/mytest.t" pour exécuter un seul test.

RECETTES AVANCÉES

Créer une distribution compatible CPAN.pm

Les nouvelles versions de CPAN.pm comprennent comment utiliser un script Build.PL, mais les anciennes ne le font pas. Si les auteurs souhaitent aider les utilisateurs ayant des versions anciennes, une forme de Makefile.PL devrait être fournie. Le moyen le plus simple d'y parvenir est d'utiliser le paramètre "create_makefile_pl" de "Module::Build->new()" dans le script "Build.PL", qui peut créer diverses saveurs de Makefile.PL lors de l'action "dist".

Comme meilleure pratique, nous recommandons d'utiliser le style "traditionnel" de Makefile.PL, sauf si votre distribution a des besoins qui ne peuvent pas être satisfaits de cette manière.

Le module "Module::Build::Compat", qui fait partie de la distribution de "Module::Build", est responsable de la création de ces Makefile.PL. Veuillez consulter Module::Build::Compat pour plus de détails.

Modifier l'ordre du processus de construction

La propriété "build_elements" spécifie les étapes que "Module::Build" suivra lors de la construction d'une distribution. Pour modifier l'ordre de construction, modifiez l'ordre des entrées de cette propriété :

# Process files pod first
my @e = @{$build->build_elements};
my ($i) = grep {$e[$_] eq 'pod'} 0..$#e;
unshift @e, splice @e, $i, 1;

Actuellement, "build_elements" a la valeur par défaut suivante :

[qw( PL support pm xs pod script )]

Soyez prudent lorsque vous modifiez cette propriété, car il peut y avoir des dépendances d'ordre non évidentes (et non documentées !) dans le code de "Module::Build".

Ajouter de nouveaux types de fichiers au processus de construction

Parfois, vous pourriez avoir des types de fichiers supplémentaires que vous souhaitez installer aux côtés des types standard comme les fichiers .pm et .pod. Par exemple, vous pourriez avoir un fichier Bar.dat contenant des données relatives au module "Foo::Bar" et vous aimeriez qu'il se retrouve sous forme de Foo/Bar.dat quelque part dans le chemin @INC de Perl afin que "Foo::Bar" puisse y accéder facilement à l'exécution. Le code suivant d'un exemple de fichier "Build.PL" montre comment y parvenir :

use Module::Build;
my $build = Module::Build->new
  (
   module_name => 'Foo::Bar',
   ...other stuff here...
  );
$build->add_build_element('dat');
$build->create_build_script;

Cela trouvera tous les fichiers .dat dans le répertoire lib/, les copiera dans le répertoire blib/lib/ lors de l'action "build", et les installera lors de l'action "install".

Si vos fichiers supplémentaires ne sont pas situés dans le répertoire "lib/" de votre distribution, vous pouvez explicitement indiquer où ils se trouvent, tout comme vous le feriez pour les fichiers .pm ou .pod :

use Module::Build;
my $build = new Module::Build
  (
   module_name => 'Foo::Bar',
   dat_files => {'some/dir/Bar.dat' => 'lib/Foo/Bar.dat'},
   ...other stuff here...
  );
$build->add_build_element('dat');
$build->create_build_script;

Si vos fichiers supplémentaires doivent en fait être créés sur la machine de l'utilisateur, ou s'ils nécessitent un autre type de traitement spécial, vous voudrez probablement créer une sous-classe de "Module::Build" et créer une méthode spéciale pour les traiter, nommée "process_${kind}_files()" :

use Module::Build;
my $class = Module::Build->subclass(code => <<'EOF');
  sub process_dat_files {
    my $self = shift;
    ... locate and process *.dat files,
    ... and create something in blib/lib/
  }
EOF
my $build = $class->new
  (
   module_name => 'Foo::Bar',
   ...other stuff here...
  );
$build->add_build_element('dat');
$build->create_build_script;

Si vos fichiers supplémentaires ne vont pas dans lib/ mais dans un autre endroit, voir "Ajouter de nouveaux éléments au processus d'installation" pour savoir comment les faire réellement installer.

Veuillez noter que ces exemples utilisent certaines capacités de Module::Build qui sont apparues pour la première fois dans la version 0.26. Avant cela, cela pouvait encore être fait, mais les cas simples nécessitaient un peu plus d'efforts.

Ajouter de nouveaux éléments au processus d'installation

Par défaut, Module::Build crée sept sous-répertoires du répertoire blib pendant le processus de construction : lib, arch, bin, script, bindoc, libdoc et html (certains d'entre eux peuvent être manquants ou vides s'il n'y a rien à y mettre). Tout ce qui est copié dans ces répertoires pendant la construction sera éventuellement installé lors de l'action "install" (voir "INSTALL PATHS" dans Module::Build.

Si vous avez besoin de créer un nouveau type personnalisé d'élément installable, par exemple "conf", alors vous devez indiquer à Module::Build où les éléments de blib/conf/ doivent être installés. Pour ce faire, utilisez le paramètre "install_path" de la méthode new() :

my $build = Module::Build->new
  (
   ...other stuff here...
   install_path => { conf => $installation_path }
  );

Ou vous pouvez appeler la méthode install_path() plus tard :

$build->install_path(conf => $installation_path);

L'utilisateur peut également spécifier le chemin sur la ligne de commande :

perl Build.PL --install_path conf=/foo/path/etc

La partie importante, cependant, est que le chemin d'installation doit être défini *d'une manière ou d'une autre*, sinon rien dans le répertoire blib/conf/ ne sera installé, et une erreur d'exécution lors de l'action "install" en résultera.

Voir également "Ajouter de nouveaux types de fichiers au processus de construction" pour savoir comment créer les éléments dans blib/conf/ en premier lieu.

EXEMPLES SUR CPAN

Plusieurs distributions sur CPAN utilisent bien diverses fonctionnalités de Module::Build. Elles peuvent servir d'exemples concrets pour les autres.

SVN-Notify-Mirror

http://search.cpan.org/~jpeacock/SVN-Notify-Mirror/

John Peacock, auteur de la distribution "SVN-Notify-Mirror", dit :

1. En utilisant "auto_features", je vérifie si deux modules optionnels sont disponibles - SVN::Notify::Config et Net::SSH ;
2. Si le module S::N::Config est chargé, je génère automatiquement des fichiers de test pour celui-ci pendant la construction (en utilisant la propriété "PL_files").
3. Si la "feature" ssh est disponible, je demande si l'utilisateur souhaite effectuer les tests ssh (car cela nécessite une petite configuration préliminaire) ;
4. Seulement si l'utilisateur a la "feature" ssh et répond oui aux tests, je génère un fichier de test.
Je suis sûr que je n'aurais pas pu gérer cette complexité avec EU::MM, mais c'était très facile à faire avec M::B.

Modifier une action

Parfois, vous pourriez avoir besoin qu'une action, disons "./Build install", fasse quelque chose d'inhabituel. Par exemple, vous pourriez avoir besoin de changer la propriété d'un fichier ou de faire quelque chose de spécifique à votre application.

Vous pouvez créer une sous-classe de "Module::Build" à la volée en utilisant la méthode subclass() et remplacer les méthodes qui effectuent les actions. Vous devrez peut-être lire "Module::Build::Authoring" et "Module::Build::API" pour trouver les méthodes que vous souhaitez remplacer. Toutes les méthodes "action" sont implémentées par une méthode appelée "ACTION_" suivie du nom de l'action, voici donc un exemple de la façon dont cela fonctionnerait pour l'action "install" :

# Build.PL
use Module::Build;
my $class = Module::Build->subclass(
    class => "Module::Build::Custom",
    code => <<'SUBCLASS' );
sub ACTION_install {
    my $self = shift;
    # YOUR CODE HERE
    $self->SUPER::ACTION_install;
}
SUBCLASS
$class->new(
    module_name => 'Your::Module',
    # rest of the usual Module::Build parameters
)->create_build_script;

Ajouter une action

Vous pouvez ajouter une nouvelle action "./Build" simplement en écrivant la méthode correspondante dans votre sous-classe. Utilisez "depends_on" pour déclarer qu'une autre action doit avoir été exécutée avant votre action.
