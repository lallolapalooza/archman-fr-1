NAME

Moo - Orienté objet minimaliste (avec compatibilité Moose)

SYNOPSIS

package Cat::Food;
use Moo;
use strictures 2;
use namespace::clean;
sub feed_lion {
  my $self = shift;
  my $amount = shift || 1;
  $self->pounds( $self->pounds - $amount );
}
has taste => (
  is => 'ro',
);
has brand => (
  is => 'ro',
  isa => sub {
    die "Seulement SWEET-TREATZ supporté !" unless $_[0] eq 'SWEET-TREATZ'
  },
);
has pounds => (
  is => 'rw',
  isa => sub { die "$_[0] est trop de nourriture pour chat !" unless $_[0] < 15 },
);
1;

Et ailleurs :

my $full = Cat::Food->new(
    taste  => 'DELICIOUS.',
    brand  => 'SWEET-TREATZ',
    pounds => 10,
);
$full->feed_lion;
say $full->pounds;

DESCRIPTION

"Moo" est un système orienté objet extrêmement léger. Il vous permet de définir des objets et des rôles de manière concise avec une syntaxe pratique qui évite les détails du système d'objets de Perl. "Moo" contient un sous-ensemble de Moose et est optimisé pour un démarrage rapide.

"Moo" évite les dépendances sur les modules XS afin de permettre des implémentations simples. Le nom "Moo" repose sur l'idée qu'il fournit presque, mais pas tout à fait, les deux tiers de Moose. Par conséquent, le Moose::Manual peut servir de guide efficace pour "Moo" en dehors des chapitres MOP et Types.

Contrairement à Mouse, ce module ne cherche pas la compatibilité syntaxique de surface totale avec Moose, mais préfère une interopérabilité complète via les capacités d'inflation de métaclasses décrites dans "MOO ET MOOSE".

Pour une liste complète des différences mineures entre la syntaxe de surface de Moose et Moo, voir "INCOMPATIBILITÉ AVEC MOOSE".

POURQUOI MOO EXISTE

Si vous souhaitez un système orienté objet avec un métaprotocole riche, Moose est déjà admirable.

Mais si vous ne voulez pas utiliser Moose, vous n'avez peut-être pas envie d'un « métaprotocole réduit » comme Mouse l'offre, mais vous n'avez probablement pas envie d'un « métaprotocole » du tout, ce que Moo fournit.

  • Un script en ligne de commande ou un script CGI où un démarrage rapide est essentiel
  • Du code conçu pour être déployé en un seul fichier via App::FatPacker
  • Un module CPAN qui peut être utilisé par d'autres dans les situations mentionnées ci-dessus

"Moo" maintient une compatibilité transparente avec Moose, donc si vous installez et chargez Moose, vous pouvez utiliser les classes et rôles Moo dans le code Moose sans modification.

Moo — Orienté objet minimaliste — vise à faciliter la mise à niveau vers Moose lorsque vous avez besoin de plus que les fonctionnalités minimales offertes par Moo.

MOO ET MOOSE

Si Moo détecte que Moose est chargé, il enregistrera automatiquement les métaclasses pour vos paquets Moo et Moo::Role, vous devriez donc pouvoir les utiliser dans le code Moose sans modification.

Moo créera également des contraintes de type pour les classes et rôles Moo, de sorte que dans les classes Moose "isa => 'MyMooClass'" et "isa => 'MyMooRole'" fonctionneront de la même manière que dans les classes et rôles Moose.

L'héritage d'une classe Moose ou la consommation d'un rôle Moose fonctionneront également.

L'héritage d'une classe Mouse ou la consommation d'un rôle Mouse fonctionneront également. Cependant, notez que nous ne fournissons pas de métaclasses ou de métarôles Mouse, donc l'autre sens ne fonctionne pas. Cette fonctionnalité existe pour les utilisateurs d'Any::Moose qui migrent vers Moo ; permettre aux utilisateurs de Mouse d'utiliser les classes Moo n'est pas une priorité pour nous.

Cela signifie qu'il n'y a pas besoin de quelque chose comme Any::Moose pour le code Moo — les codes Moo et Moose devraient interagir sans problème. Pour gérer le code Mouse, vous aurez probablement besoin d'un rôle ou d'une classe Moo vide ou d'étendre/consommer le code Mouse, car il n'enregistre pas de véritables métaclasses Moose comme le fait Moo.

Si vous avez besoin de désactiver la création de métaclasses, ajoutez :

no Moo::sification;

à votre code avant de charger Moose, mais gardez à l'esprit que ce commutateur est global et désactive complètement le mécanisme, vous ne le placerez donc pas dans le code de la bibliothèque.

MOO ET CLASS::XSACCESSOR

Si une version récente de Class::XSAccessor est disponible, elle sera utilisée pour générer des accesseurs simples, des lecteurs et des écrivains pour de meilleures performances. Les accesseurs simples sont ceux qui n'ont pas de valeurs par défaut différées, de validations de type ou de coercitions, ou de déclencheurs. Les lecteurs simples sont ceux qui n'ont pas de valeurs par défaut différées. Les accesseurs et lecteurs générés par Class::XSAccessor se comporteront légèrement différemment : ils rejetteront les tentatives de les appeler avec le mauvais nombre de paramètres.

MOO VS ANY::MOOSE

Any::Moose chargera Mouse normalement, et Moose dans un programme utilisant Moose — théoriquement, il permet d'obtenir le temps de démarrage de Mouse sans désavantage pour les utilisateurs de Moose.

Cependant, cela ne fonctionne pas complètement, car la sélection dépend de l'ordre de chargement — le système d'inflation de métaclasses expliqué plus haut dans "MOO ET MOOSE" est considérablement plus fiable.

Par conséquent, si vous souhaitez écrire un module CPAN qui démarre rapidement ou qui n'a que des dépendances Perl pures mais qui est également entièrement utilisable par les utilisateurs de Moose, vous devriez utiliser Moo.

Pour une explication complète, consultez l'article https://shadow.cat/blog/matt-s-trout/moo-versus-any-moose, qui explique les différentes stratégies plus en détail et fournit un exemple direct où Moo réussit et Any::Moose échoue.

MÉTHODES PUBLIQUES

Moo fournit plusieurs méthodes pour toute classe qui l'utilise.

new

Foo::Bar->new( attr1 => 3 );

ou

Foo::Bar->new({ attr1 => 3 });

Le constructeur de classe. Par défaut, il accepte les attributs comme une table clé-valeur, ou comme une liste de paires clé-valeur. Vous pouvez le personnaliser avec la méthode BUILDARGS.

does

if ($foo->does('Some::Role1')) {
  ...
}

Retourne vrai si l'objet compose le rôle passé.

DOES

if ($foo->DOES('Some::Role1') || $foo->DOES('Some::Class1')) {
  ...
}

Similaire à "does", mais retourne également vrai pour les rôles composés et les superclasses.

meta

my $meta = Foo::Bar->meta;
my @methods = $meta->get_method_list;

Retourne un objet qui se comportera comme un objet de métaclasse Moose pour la classe. Si une méthode autre que "make_immutable" est appelée, l'objet sera transparentement mis à niveau vers un instanciateur réel de Moose::Meta::Class, chargeant Moose si nécessaire. "make_immutable" lui-même est un NOP, car nous générons des métaclasses qui sont déjà immuables, et les utilisateurs qui sont allés au-delà de Moose avaient une tendance défavorable à charger accidentellement Moose en l'appelant.

MÉTHODES DE CYCLE DE VIE

Il existe plusieurs méthodes que vous pouvez définir dans votre classe pour contrôler la création et la destruction des objets. Elles doivent être utilisées à la place de tenter de modifier "new" ou "DESTROY" vous-même.

BUILDARGS

around BUILDARGS => sub {
  my ( $orig, $class, @args ) = @_;
  return { attr1 => $args[0] }
    if @args == 1 && !ref $args[0];
  return $class->$orig(@args);
};
Foo::Bar->new( 3 );

Cette méthode de classe est utilisée pour transformer les arguments de "new" en une table de valeurs d'attributs.

L'implémentation par défaut transforme les arguments en une table de valeurs d'attributs.

SOUS-ROUTINES IMPORTÉES

hérite

hérite 'Parent::Class';

Déclare une classe de base. Plusieurs superclasses peuvent être passées pour l'héritage multiple, mais veuillez envisager d'utiliser plutôt des rôles. La classe sera chargée mais aucune erreur ne sera déclenchée si la classe ne peut pas être trouvée et qu'il existe déjà des subs dans la classe.

Appeler hérite plus d'une fois REMPLACERA vos superclasses, ne les ajoutera pas comme le ferait 'use base'.

avec

avec 'Some::Role1';

ou

avec 'Some::Role1', 'Some::Role2';

Compose un ou plusieurs rôles Moo::Role (ou Role::Tiny) dans la classe actuelle. Une erreur sera levée si ces rôles ne peuvent pas être composés car ils ont des définitions de méthodes conflictuelles. Les rôles seront chargés en utilisant le même mécanisme que celui utilisé par "hérite".

a

a attribut => (
  est => 'ro',
);

Déclare un attribut pour la classe.

package Foo;
use Moo;
a 'attribut' => (
  est => 'ro'
);
package Bar;
use Moo;
hérite 'Foo';
a '+attribut' => (
  défaut => sub { "blah" },
);

En utilisant la notation "+", il est possible de remplacer un attribut.

a [qw(attribut1 attribut2 attribut3)] => (
  est => 'ro',
);

En utilisant une référence de tableau avec plusieurs noms d'attributs, il est possible de déclarer plusieurs attributs avec les mêmes options.

Les options pour "a" sont les suivantes :

"est"
obligatoire, peut être "ro", "lazy", "rwp" ou "rw".

"ro" signifie "lecture seule" et génère un accesseur qui plante si vous essayez d'écrire dessus - c'est-à-dire un getter uniquement - en mettant par défaut "lecteur" au nom de l'attribut.

"lazy" génère un lecteur comme "ro", mais définit également "lazy" à 1 et "constructeur" à "_build_${nom_attribut}" pour permettre des attributs générés à la demande. Cette fonctionnalité était ma tentative de corriger mon incompétence lors de la conception originale de "lazy_build", et est également implémentée par MooseX::AttributeShortcuts. Il n'y a cependant rien qui vous empêche d'utiliser "lazy" et "constructeur" vous-même avec "rwp" ou "rw" - c'est juste que ce n'est généralement pas une bonne idée, donc nous ne fournissons pas de raccourci pour cela.

"rwp" signifie "lecture-écriture protégée" et génère un lecteur comme "ro", mais définit également "écrivain" à "_set_${nom_attribut}" pour les attributs conçus pour être écrits de l'intérieur de la classe, mais en lecture seule de l'extérieur. Cette fonctionnalité provient de MooseX::AttributeShortcuts.

"rw" signifie "lecture-écriture" et génère un getter/setter normal en mettant par défaut l'"accesseur" au nom de l'attribut spécifié.

"est_un"
Prend une reference de code qui est utilisée pour valider l'attribut. Contrairement à Moose, Moo n'inclut pas de système de types de base, donc au lieu de faire "est_un => 'Num'", on devrait faire : 
use Scalar::Util qw(looks_like_number);
...
est_un => sub {
  die "$_[0] n'est pas un nombre !" unless looks_like_number $_[0]
},

Notez que la valeur de retour pour "est_un" est ignorée. C'est seulement si la sous-routine plante que la validation de type échoue.

Compatible avec Sub::Quote

Étant donné que Moo n'exécute **pas** la vérification "est_un" avant "coerce" si une sous-routine de coercition a été fournie, les vérifications "est_un" ne sont pas structurelles à votre code et peuvent, si désiré, être omises dans les builds de débogage (bien que si cela entraîne un bug non intercepté causant la rupture de votre programme, les auteurs de Moo ne garantissent rien sauf que vous gardez les deux moitiés).

Si vous souhaitez des types nommés compatibles avec Moose ou de style MooseX::Types, regardez Type::Tiny.

Pour que vos entrées "est_un" soient automatiquement mappées sur des objets Moose::Meta::TypeConstraint nommés (plutôt que sur le comportement par défaut de création d'un type anonyme), définissez :

$Moo::HandleMoose::TYPE_MAP{$coderef_est_un} = sub {
  require MooseX::Types::Something;
  return MooseX::Types::Something::TypeName();
};

Notez que cet exemple est purement illustratif ; tout ce qui renvoie un objet Moose::Meta::TypeConstraint ou quelque chose d'assez similaire pour satisfaire Moose convient.

"coerce"
Prend une référence de code destinée à coercer l'attribut. L'idée de base est de faire quelque chose comme ce qui suit : 
coerce => sub {
  $_[0] % 2 ? $_[0] : $_[0] + 1
},

Notez que Moo exécutera toujours votre coercition : c'est pour permettre aux entrées "est_un" d'être utilisées uniquement pour piéger les bugs, tandis que les coercitions sont toujours structurelles à votre code. Nous appliquons cependant toute vérification "est_un" fournie après l'exécution de la coercition pour nous assurer qu'elle a renvoyé une valeur valide.

Compatible avec Sub::Quote

Si l'option "est_un" est un objet béni fournissant une méthode "coerce" ou "coercion", alors l'option "coerce" peut être définie à juste 1.

"gère"
Prend une chaîne 
gère => 'RobotRole'

Où "RobotRole" est un rôle qui définit une interface qui devient la liste des méthodes à gérer.

Prend une liste de méthodes

gère => [ qw( un deux ) ]

Prend une référence de hash

gère => {
  un => 'un',
}
"déclencheur"
Prend une référence de code qui sera appelée chaque fois que l'attribut est défini. Cela inclut le constructeur, mais pas les valeurs par défaut ou construites. La référence de code sera invoquée sur l'objet avec la nouvelle valeur comme argument.

Si vous définissez cela à juste 1, cela génère un déclencheur qui appelle la méthode "_trigger_${nom_attribut}" sur $self. Cette fonctionnalité provient de MooseX::AttributeShortcuts.

Notez que Moose passe également l'ancienne valeur, le cas échéant ; cette fonctionnalité n'est pas encore prise en charge.

Compatible avec Sub::Quote

"défaut"
Prend une référence de code qui sera appelée avec $self comme seul argument pour peupler un attribut si aucune valeur pour cet attribut n'a été fournie au constructeur. Alternativement, si l'attribut est paresseux, "défaut" s'exécute lorsque l'attribut est récupéré pour la première fois si aucune valeur n'a encore été fournie.

Si un scalaire simple est fourni, il sera intégré en tant que chaîne. Toute référence non-code (hash, array) entraînera une erreur - dans ce cas, utilisez plutôt une référence de code qui renvoie la valeur souhaitée.

Notez que si votre défaut est déclenché pendant new(), il n'y a aucune garantie que d'autres attributs aient déjà été peuplés, vous ne devriez donc pas compter sur leur existence.

Compatible avec Sub::Quote

ATTRIBUTES

"predicate"
Prend un nom de méthode qui renverra vrai si un attribut a une valeur.

Si vous définissez ceci à juste 1, le prédicat est automatiquement nommé "has_${nom_attribut}" si le nom de votre attribut ne commence pas par un trait de soulignement, ou "_has_${nom_attribut_sans_trait_de_soulignement}" s'il le fait. Cette fonctionnalité provient de MooseX::AttributeShortcuts.

"builder"
Prend un nom de méthode qui sera appelé pour créer l'attribut - fonctionne exactement comme default sauf qu'au lieu d'appeler 
$default->($self);

Moo appellera

$self->$builder;

Les fonctionnalités suivantes proviennent de MooseX::AttributeShortcuts :

Si vous définissez ceci à juste 1, le builder est automatiquement nommé "_build_${nom_attribut}".

Si vous définissez ceci à un objet coderef ou convertible en code, cette variable sera installée sous "$class::_build_${nom_attribut}" et le builder sera défini au même nom.

"clearer"
Prend un nom de méthode qui effacera l'attribut.

Si vous définissez ceci à juste 1, le clearer est automatiquement nommé "clear_${nom_attribut}" si le nom de votre attribut ne commence pas par un trait de soulignement, ou "_clear_${nom_attribut_sans_trait_de_soulignement}" s'il le fait. Cette fonctionnalité provient de MooseX::AttributeShortcuts.

NOTE : Si l'attribut est "lazy", il sera régénéré à partir de "default" ou "builder" la prochaine fois qu'il sera accédé. S'il n'est pas lazy, il sera "undef".

"lazy"
Booléen. Définissez ceci si vous souhaitez que les valeurs de l'attribut soient obtenues paresseusement. C'est généralement une bonne idée si vous avez un "builder" qui nécessite qu'un autre attribut soit défini.
"required"
Booléen. Définissez ceci si l'attribut doit être passé lors de l'instanciation de l'objet.
"reader"
Le nom de la méthode qui retourne la valeur de l'attribut. Si vous aimez les méthodes style Java, vous pourriez définir ceci à "get_foo"
"writer"
La valeur de cet attribut sera le nom de la méthode pour définir la valeur de l'attribut. Si vous aimez les méthodes style Java, vous pourriez définir ceci à "set_foo".
"weak_ref"
Booléen. Définissez ceci si vous souhaitez que la référence contenue par l'attribut soit affaiblie. Utilisez ceci lorsque des références circulaires, qui causent des fuites de mémoire, sont possibles.
"init_arg"
Prend le nom de la clé à rechercher lors de l'instanciation de l'objet. Une utilisation courante est de donner à un attribut souligné un nom d'initialisation non souligné. "undef" signifie qu'il est ignoré de passer la valeur lors de l'instanciation.
"moosify"
Prend soit un coderef, soit un tableau de coderefs destiné à transformer les spécifications d'attributs données si nécessaire lors de la mise à niveau vers un rôle ou une classe Moose. Vous ne devriez pas en avoir besoin par défaut, mais il est fourni comme moyen d'extensibilité possible.

avant

before foo => sub { ... };

Voir "before method(s) => sub { ... };" dans Class::Method::Modifiers pour la documentation complète.

autour

around foo => sub { ... };

Voir "around method(s) => sub { ... };" dans Class::Method::Modifiers pour la documentation complète.

après

after foo => sub { ... };

Voir "after method(s) => sub { ... };" dans Class::Method::Modifiers pour la documentation complète.

SUB CITATION CONSCIENTE

"quote_sub" dans Sub::Quote nous permet de créer des coderefs qui sont "inlineables", nous donnant un coup de pouce pratique et sans XS. Toute option sensible à Sub::Quote peut en tirer parti.

Pour ce faire, vous pouvez écrire

use Sub::Quote;
use Moo;
use namespace::clean;
has foo => (
  is => 'ro',
  isa => quote_sub(q{ die "Pas <3" unless $_[0] < 3 })
);

qui sera intégré sous forme de

do {
  local @_ = ($_[0]->{foo});
  die "Pas <3" unless $_[0] < 3;
}

ou pour éviter de localiser @_,

has foo => (
  is => 'ro',
  isa => quote_sub(q{ my ($val) = @_; die "Pas <3" unless $val < 3 })
);

qui sera intégré sous forme de

do {
  my ($val) = ($_[0]->{foo});
  die "Pas <3" unless $val < 3;
}

Voir Sub::Quote pour plus d'informations, y compris comment passer des captures lexicales qui seront également compilées dans la sous-routine.

NETTOYAGE DES IMPORTATIONS

Moo ne nettoiera pas les sous-routines importées pour vous ; vous devrez le faire manuellement. La manière recommandée de le faire est de déclarer vos imports en premier, puis "use Moo", puis "use namespace::clean". Tout ce qui est importé avant namespace::clean sera effacé. Tout ce qui est importé ou déclaré après sera toujours disponible.

package Record;
use Digest::MD5 qw(md5_hex);
use Moo;
use namespace::clean;
has name => (is => 'ro', required => 1);
has id => (is => 'lazy');
sub _build_id {
  my ($self) = @_;
  return md5_hex($self->name);
}
1;

Par exemple, si vous importiez ces sous-routines après namespace::clean comme ceci

use namespace::clean;
use Digest::MD5 qw(md5_hex);
use Moo;

alors toute "Record" $r aurait des méthodes telles que "$r->md5_hex()", "$r->has()" et "$r->around()" - presque certainement pas ce que vous avez l'intention !

Les rôles Moo se comportent légèrement différemment. Puisque leurs méthodes sont composées dans la classe consommatrice, elles peuvent faire un peu plus pour vous automatiquement. Tant que vous déclarez vos imports avant d'appeler "use Moo::Role", ces imports et ceux fournis par Moo::Role lui-même ne seront pas composés dans les classes consommatrices, il n'est donc généralement pas nécessaire d'utiliser namespace::clean.

Concernant namespace::autoclean : les anciennes versions de namespace::autoclean gonflaient les classes Moo en classes Moose complètes, perdant les avantages de Moo. Si vous souhaitez utiliser namespace::autoclean avec une classe Moo, assurez-vous d'utiliser la version 0.16 ou plus récente.

INCOMPATIBILITÉS AVEC MOOSE

TYPES

Il n'y a pas de système de types intégré. "isa" est vérifié avec un coderef ; si vous avez besoin de types complexes, Type::Tiny peut fournir des types, des bibliothèques de types, et fonctionnera de manière transparente avec Moo et Moose. Type::Tiny peut être considéré comme le successeur de MooseX::Types et fournit une API similaire, de sorte que vous pouvez écrire

use Types::Standard qw(Int);
has days_to_live => (is => 'ro', isa => Int);

INCOMPATIBILITÉS D'API

"initializer" n'est pas pris en charge dans le cœur car l'auteur le considère comme une mauvaise idée et les meilleures pratiques de Moose recommandent de l'éviter. Pendant ce temps "trigger" ou "coerce" sont plus susceptibles de répondre à vos besoins.

Aucun support pour "super", "override", "inner", ou "augment" - l'auteur considère augment comme une mauvaise idée, et override peut être traduit :

override foo => sub {
  ...
  super();
  ...
};
around foo => sub {
  my ($orig, $self) = (shift, shift);
  ...
  $self->$orig(@_);
  ...
};

La méthode "dump" n'est pas fournie par défaut. L'auteur suggère de charger Devel::Dwarn dans "main::" (via "perl -MDevel::Dwarn ..." par exemple) et d'utiliser "$obj->$::Dwarn()" à la place.

"default" ne prend en charge que les coderefs et les scalaires simples, car passer une référence de hachage ou de tableau comme valeur par défaut est presque toujours incorrect car la valeur est alors partagée entre tous les objets utilisant cette valeur par défaut.

"lazy_build" n'est pas pris en charge ; vous êtes plutôt encouragé à utiliser l'option "is => 'lazy'" prise en charge par Moo et MooseX::AttributeShortcuts.

"auto_deref" n'est pas pris en charge car l'auteur le considère comme une mauvaise idée et il est considéré comme une meilleure pratique de l'éviter depuis un certain temps.

"documentation" apparaîtra dans une métaclasse Moose créée à partir de votre classe mais sera sinon ignorée. Là encore, Moose l'ignore également, c'est donc sans doute pas une incompatibilité.

Étant donné que "coerce" n'exige pas que "isa" soit défini mais Moose l'exige, le gonflement de la métaclasse pour coerce seul est un peu insensé et si vous tentez de sous- typer le résultat, cela échouera presque certainement.

Gestion des avertissements : lorsque vous "use Moo", nous activons strict et warnings, de manière similaire à Moose. Les auteurs recommandent l'utilisation de "strictures", qui active les avertissements FATAL, et plusieurs pragmas supplémentaires lorsqu'il est utilisé en développement : indirect, multidimensionnel et bareword::filehandles.

De plus, Moo prend en charge un ensemble de raccourcis d'options d'attributs destinés à réduire le code répétitif courant. L'ensemble des raccourcis est le même que dans le module Moose MooseX::AttributeShortcuts à partir de sa version 0.009+. Donc, si vous :

package MyClass;
use Moo;
use strictures 2;

Moo(3pm) — Arch manual pages

MOO AND MOOSE

This is probably the most important difference to understand. Moo is very nearly a drop-in replacement for Moose. The major difference is that Moo does not try to provide the full Moose metamodel.

Moose has a complicated object system. Moo has a simpler one. Moo is designed for the 80% of use cases, while Moose is designed for the 100%.

If you are coming from Moose, then the following is what you need to know.

CLASS DECLARATION

The nearest Moose invocation would be:

package MyClass;
use Moose;
use warnings FATAL => "all";
use MooseX::AttributeShortcuts;

or, if you're inheriting from a non-Moose class,

package MyClass;
use Moose;
use MooseX::NonMoose;
use warnings FATAL => "all";
use MooseX::AttributeShortcuts;

META OBJECT

There is no meta object. If you need this level of complexity you need Moose - Moo is small because it explicitly does not provide a metaprotocol. However, if you load Moose, then

Class::MOP::class_of($moo_class_or_role)

will return an appropriate metaclass pre-populated by Moo.

IMMUTABILITY

Finally, Moose requires you to call

__PACKAGE__->meta->make_immutable;

at the end of your class to get an inlined (i.e. not horribly slow) constructor. Moo does it automatically the first time ->new is called on your class. ("make_immutable" is a no-op in Moo to ease migration.)

An extension MooX::late exists to ease translating Moose packages to Moo by providing a more Moose-like interface.

COMPATIBILITY WITH OLDER PERL VERSIONS

Moo is compatible with perl versions back to 5.6. When running on older versions, additional prerequisites will be required. If you are packaging a script with its dependencies, such as with App::FatPacker, you will need to be certain that the extra prerequisites are included.

MRO::Compat
Required on perl versions prior to 5.10.0.
Devel::GlobalDestruction
Required on perl versions prior to 5.14.0.
