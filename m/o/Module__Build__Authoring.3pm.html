Module::Build::Authoring(3pm) Documentation utilisateur Perl contribuée Module::Build::Authoring(3pm)

NOM

Module::Build::Authoring - Autorisation des modules Module::Build

DESCRIPTION

Lors de la création d'un script "Build.PL" pour un module, un code tel que le suivant est généralement utilisé :

use Module::Build;
my $build = Module::Build->new
  (
   module_name => 'Foo::Bar',
   license  => 'perl',
   requires => {
                'perl'          => '5.6.1',
                'Some::Module'  => '1.23',
                'Other::Module' => '>= 1.2, != 1.5, < 2.0',
               },
  );
$build->create_build_script;

Un module simple pourrait réussir à obtenir quelque chose comme ceci pour son script "Build.PL" :

use Module::Build;
Module::Build->new(
  module_name => 'Foo::Bar',
  license     => 'perl',
)->create_build_script;

Le modèle utilisé par "Module::Build" est assez similaire à celui de "MakeMaker", avec les correspondances suivantes :

 En Module::Build                 En ExtUtils::MakeMaker
---------------------------      ------------------------
 Build.PL (script initial)        Makefile.PL (script initial)
 Build (script perl court)        Makefile (fichier de configuration long)
 _build/ (informations d'état enregistrées)       configuration dans le Makefile

Toute sorte de personnalisation peut être effectuée simplement en héritant de "Module::Build" et en ajoutant une méthode nommée, par exemple, "ACTION_test", qui remplacera l'action par défaut "test". Vous pourriez également ajouter une méthode nommée "ACTION_whatever", et ensuite vous pouvez exécuter l'action "Build" whatever.

Pour plus d'informations sur la compatibilité avec "ExtUtils::MakeMaker", voir Module::Build::Compat et http://www.makemaker.org/wiki/index.cgi?ModuleBuildConversionGuide.

STRUCTURE

Module::Build crée une hiérarchie de classes qui facilite la personnalisation. Voici la hiérarchie des classes parent-enfant sous forme d'art ASCII :

/--------------------\
|   Ton::Père         |  (Si tu hérites de Module::Build)
\--------------------/
         |
         |
/--------------------\  (Ne définit aucune fonctionnalité
|   Module::Build    |   propre - détermine seulement quels modules
\--------------------/   doivent être chargés.)
         |
         |
/-----------------------------------\  (Certaines valeurs de $^O peuvent
|   Module::Build::Platform::$^O    |   définir des fonctionnalités spéciales.
\-----------------------------------/   Sinon, c'est ...::Default, une
         |                              classe de passage par laquelle
         |
/--------------------------\
|   Module::Build::Base    |  (La majeure partie de la fonctionnalité de Module::Build
\--------------------------/   y est définie.)

HÉRITAGE

Actuellement, il existe deux façons d'hériter de Module::Build. La première façon consiste à créer un module régulier (dans un fichier ".pm") qui hérite de Module::Build et d'utiliser la classe de ce module au lieu d'utiliser directement Module::Build :

------ dans Build.PL : ----------
#!/usr/bin/perl
use lib q(/no/std/lib/path);
use Mon::Builder;  # Ou n'importe quel nom que tu veux
my $build = Mon::Builder->new
  (
   module_name => 'Foo::Bar',  # Tous les arguments réguliers...
   license     => 'perl',
   dist_author => 'A N Autre <moi@ici.net.au>',
   requires    => { Carp => 0 }
  );
$build->create_build_script;

C'est relativement simple et c'est la meilleure approche si ta classe Mon::Builder contient beaucoup de code. La méthode create_build_script() garantira que la valeur actuelle de @INC (y compris le "/no/std/lib/path") sera propagée au script de build, de sorte que Mon::Builder puisse être trouvé lorsqu'il est exécuté lors de l'action build. Si tu constates que tu as besoin de faire un "chdir" vers différents répertoires dans tes méthodes ou actions héritées, assure-toi de revenir au répertoire d'origine (disponible via la méthode base_dir()) avant de rendre le contrôle à la classe parente. Il est important d'éviter les problèmes avec la sérialisation des données.

Pour de petites additions, Module::Build fournit une méthode subclass() qui te permet d'hériter de Module::Build de manière plus pratique sans avoir à créer un fichier séparé pour ton module :

------ dans Build.PL : ----------
#!/usr/bin/perl
use Module::Build;
my $class = Module::Build->subclass
  (
   class => 'Mon::Builder',
   code => q{
     sub ACTION_foo {
       print "Je suis en train de faire du foo à mort !\n";
     }
   },
  );
my $build = $class->new
  (
   module_name => 'Foo::Bar',  # Tous les arguments réguliers...
   license     => 'perl',
   dist_author => 'A N Autre <moi@ici.net.au>',
   requires    => { Carp => 0 }
  );
$build->create_build_script;

En arrière-plan, cela crée en fait un fichier ".pm", car le code que tu fournis doit persister après l'exécution de Build.PL pour être utile.

Voir aussi la documentation de la méthode subclass() dans Module::Build::API.

PRÉREQUIS

Types de prérequis

Pour spécifier quelles versions d'autres modules sont utilisées dans cette distribution, plusieurs types de prérequis peuvent être définis avec les paramètres suivants :

configure_requires
Éléments qui doivent être installés avant la configuration de cette distribution (c'est-à-dire avant l'exécution du script Build.PL). Il peut s'agir d'une version spécifique de "Module::Build" ou de tout module dont Build.PL a besoin pour fonctionner. Les clients tels que "CPAN.pm" ou "CPANPLUS" s'attendent à ce que "configure_requires" soit défini dans le fichier META.yml et qu'ils installent ces éléments avant d'exécuter Build.PL.

Si configure_requires n'est pas spécifié, la version actuelle de Module::Build est automatiquement ajoutée à configure_requires.

build_requires
Éléments nécessaires pour compiler et tester cette distribution, mais qui ne sont pas nécessaires après l'installation. Cela peut aider les utilisateurs qui ne souhaitent installer ces éléments que temporairement. Cela permet également de réduire la largeur du graphe de dépendances CPAN si tout n'est pas regroupé sous "requires".
requires
Éléments nécessaires au fonctionnement de base.
recommends
Éléments recommandés pour des fonctionnalités améliorées, mais il existe des moyens d'utiliser cette distribution sans les avoir installés. On peut aussi penser à cela comme « peut utiliser » ou « est conscient de » ou « modifie le comportement en présence de ».
test_requires
Éléments nécessaires pour les tests.
conflicts
Éléments qui peuvent causer des problèmes lors de l'installation de cette distribution. C'est assez rare.

Format des prérequis

Les prérequis sont donnés dans une référence de hachage où les clés sont les noms des modules et les valeurs sont des spécificateurs de version :

requires => {
             Foo::Module => '2.4',
             Bar::Module => 0,
             Ken::Module => '>= 1.2, != 1.5, < 2.0',
             perl => '5.6.0'
            },

NOM

Module::Build

DESCRIPTION

Module::Build est un système de construction de modules Perl qui permet la création de modules avec une approche de construction modulaire. Ce système offre une interface pour automatiser la construction, le test et l'installation de modules, et permet également la création de modules personnalisés avec une structure de construction flexible.

STRUCTURE

Module::Build est structuré en plusieurs composants principaux, notamment :

  • "Build" : le cœur de l'outil qui gère la construction, les tests et l'installation des modules.
  • "ConfigData" : un module qui permet de sauvegarder et d'accéder aux données de configuration des modules.
  • "Cookbook" : un guide de construction qui contient des exemples et des explications sur l'utilisation de Module::Build.
  • "API" : une interface de programmation qui permet d'appeler des méthodes de construction depuis le code.
  • "ExtUtils::MakeMaker" : une extension qui permet d'utiliser le système de construction de Makefile.

SUBCLASSING

Module::Build permet de créer des classes personnalisées pour représenter des modules de construction. Ces classes peuvent hériter de la classe de base "Module::Build" et posséder leurs propres méthodes de construction, de test et d'installation.

PREREQUISITES

Pour utiliser Module::Build, les éléments suivants sont requis :

  • Perl
  • Un environnement de développement
  • Un module de construction (tel que ExtUtils::MakeMaker)

SAUVEGARDE DES INFORMATIONS DE CONFIGURATION

Module::Build fournit un moyen pratique de sauvegarder des informations de configuration auxquelles votre installation de modules (ou vos tests de régression) peuvent accéder. Si votre processus de construction appelle les méthodes "feature()" ou "config_data()", un module "Foo::Bar::ConfigData" sera automatiquement créé, où "Foo::Bar" est le nom du module de configuration tel que passé à la fonction "new()". Ce module donne accès aux données sauvegardées par ces méthodes et permet de mettre à jour les valeurs. Il existe également un utilitaire nommé "config_data" distribué avec Module::Build qui offre une interface en ligne de commande pour cette même fonctionnalité. Consultez également la documentation générée du module "Foo::Bar::ConfigData" et le document du script "config_data" pour plus d'informations.

DÉMARRAGE DU DÉVELOPPEMENT DE MODULES

Lorsque vous commencez à développer un nouveau module, il est généralement peu pratique de créer manuellement un répertoire pour tous les fichiers. Certains générateurs de modules sont disponibles : le plus ancien est "h2xs", qui est inclus avec Perl depuis longtemps. Son nom reflète l'idée que les modules étaient à l'origine conçus comme un moyen d'encapsuler une bibliothèque C en extensions Perl (d'où le "h" dans le nom) dans une extension Perl (d'où le "xs" dans le nom).

Actuellement, "h2xs" a été largement remplacé par des modules tels que "ExtUtils::ModuleMaker" et "Module::Starter". Ces derniers ont des variations dans leur support pour "Module::Build".

AUTOMATISATION

Un avantage de Module::Build est que, comme il est implémenté sous forme de méthodes Perl, vous pouvez invoquer ces méthodes directement si vous souhaitez installer un module de manière non interactive. Par exemple, le script Perl suivant invoquera l'ensemble du processus de construction et d'installation :

my $build = Module::Build->new(module_name => 'MyModule');
$build->dispatch('build');
$build->dispatch('test');
$build->dispatch('install');

Si une étape de ce processus rencontre une erreur, elle lèvera une exception fatale.

Vous pouvez également passer des arguments dans le cadre du processus de construction :

my $build = Module::Build->new(module_name => 'MyModule');
$build->dispatch('build');
$build->dispatch('test', verbose => 1);
$build->dispatch('install', sitelib => '/my/secret/place/');

La construction et l'installation de modules dans ce mode évitent la création du fichier "Build".

MIGRATION

Remarque : si vous souhaitez fournir à la fois "Makefile.PL" et "Build.PL" pour votre distribution, vous devrez probablement ajouter ce qui suit à "WriteMakefile" dans votre "Makefile.PL" afin que "MakeMaker" n'essaie pas d'exécuter votre "Build.PL" comme un fichier ".PL" normal :

PL_FILES => {},

Vous pourriez également être intéressé par la documentation de "Module::Build::Compat", qui peut automatiquement créer plusieurs couches de compatibilité "Makefile.PL" différentes.
