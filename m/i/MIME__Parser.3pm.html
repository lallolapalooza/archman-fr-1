NOM

MIME::Parser - classe expérimentale pour l'analyse de flux MIME

SYNOPIS

Avant de lire le reste, vous devriez consulter MIME::Tools pour vous assurer que vous comprenez où cette classe se situe dans le schéma général des choses. Allez-y, faites-le maintenant. J'attendrai.

Prêt ? Ok...

Exemples d'utilisation de base

### Créer un nouvel objet parser :
my $parser = new MIME::Parser;
### Lui dire où placer les choses :
$parser->output_under("/tmp");
### Analyser un fichier d'entrée :
$entity = $parser->parse(\*STDIN);
### Félicitations : vous avez maintenant une entité (potentiellement multipart) !
$entity->dump_skeleton;          # pour le débogage

Exemples d'entrée

### Analyser depuis des filehandles :
$entity = $parser->parse(\*STDIN);
$entity = $parser->parse(IO::File->new("some command|");
### Analyser depuis n'importe quel objet supportant getline() et read() :
$entity = $parser->parse($myHandle);
### Analyser un message MIME en mémoire :
$entity = $parser->parse_data($message);
### Analyser un message MIME dans un fichier :
$entity = $parser->parse_open("/some/file.msg");
### Analyser un message MIME à partir d'un pipeline :
$entity = $parser->parse_open("gunzip - < file.msg.gz |");
### Analyser une entrée déjà divisée (comme "deliver" vous donnerait ceci) :
$entity = $parser->parse_two("msg.head", "msg.body");

Exemples de contrôle de sortie

### Garder les corps de message en mémoire (sortie par défaut sur disque) :
$parser->output_to_core(1);
### Sortir chaque corps de message dans un répertoire par message :
$parser->output_under("/tmp");
### Sortir chaque corps de message dans le même dossier :
$parser->output_dir("/tmp");
### Changer la façon dont les fichiers sans nom sont nommés :
$parser->output_prefix("msg");
### Placer les fichiers temporaires ailleurs :
$parser->tmp_dir("/var/tmp/mytmpdir");

Exemples de récupération d'erreurs

### Mécanisme normal :
eval { $entity = $parser->parse(\*STDIN) };
if ($@) {
    $results  = $parser->results;
    $decapitated = $parser->last_head;  ### obtenir l'en-tête supérieur le plus proche
}
### Mécanisme ultra-tolérant :
$parser->ignore_errors(1);
$entity = eval { $parser->parse(\*STDIN) };
$error = ($@ || $parser->last_error);
### Nettoyer tous les fichiers créés par l'analyse :
eval { $entity = $parser->parse(\*STDIN) };
...
$parser->filer->purge;

Exemples d'options du parser

### Essayer de décoder les en-têtes MIME (conformément à RFC 2047) :
$parser->decode_headers(1);             ### la valeur par défaut est fausse
### Analyser les objets "message/rfc822" comme des flux MIME internes :
$parser->extract_nested_messages(0);    ### la valeur par défaut est vraie
### Rechercher uuencode dans les messages "text" et l'extraire :
$parser->extract_uuencode(1);           ### la valeur par défaut est fausse
### Devrions-nous ignorer les erreurs normales ?
$parser->ignore_errors(0);              ### la valeur par défaut est vraie

Exemples divers

### Convertir un objet Mail::Internet en un MIME::Entity :
my $data = join('', (@{$mail->header}, "\n", @{$mail->body}));
$entity = $parser->parse_data(\$data);

DESCRIPTION

Vous pouvez hériter de cette classe pour créer vos propres sous-classes qui analysent les flux MIME en objets MIME::Entity.

INTERFACE PUBLIQUE

Construction

new ARGS...
Méthode de classe. Crée un nouvel objet parser. Une fois que vous l'avez fait, vous pouvez définir divers paramètres avant l'analyse. Par exemple : 
my $parser = new MIME::Parser;
$parser->output_dir("/tmp");
$parser->output_prefix("msg1");
my $entity = $parser->parse(\*STDIN);

Tous les arguments sont transmis à init(). N'annulez pas cela dans vos sous-classes ; annulez plutôt init().

init ARGS...
Méthode d'instance. Initialise un nouvel objet MIME::Parser. Ceci est appelé automatiquement lors de la création d'un nouvel objet ; vous pouvez l'annuler. Si vous l'annulez, assurez-vous d'appeler la méthode héritée.
init_parse
Méthode d'instance. Est appelée automatiquement lorsque l'une des méthodes parse() de haut niveau est appelée, pour réinitialiser le parser à un état "prêt".

Modification de la manière dont les messages sont analysés

decode_headers [YESNO]
Méthode d'instance. Contrôle si le parser tentera de décoder les en-têtes MIME (conformément à RFC 2047) de manière transparente lorsqu'il les rencontre. Ce n'est pas recommandé pour deux raisons très importantes :
  • L'endommagement de l'extraction d'informations des champs MIME. Si vous décodez les en-têtes complètement en octets, vous pourriez transformer un en-tête MIME analysable comme ceci : 
    Content-type: text/plain; filename="=?ISO-8859-1?Q?Hi=22Ho?="

    en quelque chose d'inanalysable ; dans ce cas :

    Content-type: text/plain; filename="Hi"Ho"
  • C'est une perte d'informations. Une chaîne encodée contenant à la fois des caractères latins et russes se transformera en une chaîne malformée qui ne peut pas être rendue.

Historique. Cette option était la seule façon de gérer les pièces jointes avec des caractères non ASCII avant MIME-tools 5.4xx. Cependant, depuis MIME-tools 5.4xx, ce n'est plus nécessaire.

Paramètres. Si YESNO est vrai, le décodage est effectué. Cependant, vous recevrez un avertissement si vous n'utilisez pas l'une des valeurs spéciales comme :

"I_NEED_TO_FIX_THIS"
       Pour simplement réduire au silence et le faire. Non recommandé.
       Offert uniquement à ceux qui ont besoin de maintenir d'anciens scripts en cours d'exécution.
"I_KNOW_WHAT_I_AM_DOING"
       Pour simplement réduire au silence et le faire. Non recommandé.
       Offert à ceux qui savent vraiment ce qu'ils font.

Si YESNO est faux (par défaut), aucun décodage n'est tenté. Sans argument, il renvoie simplement l'état actuel. Rappelez-vous : vous pouvez toujours décoder les en-têtes *après* l'analyse (voir MIME::Head::decode()), ou décoder les mots à la demande (voir MIME::Words).

extract_nested_messages OPTION
Méthode d'instance. Certains messages MIME contiennent une partie de type "message/rfc822", "message/partial" ou "message/external-body" : littéralement le texte d'un message de courrier/actualités/etc. intégré. Cette option contrôle si (et comment) nous analysons ce message intégré.

Si l'OPTION est fausse, nous traitons ce message comme s'il s'agissait d'un document "text/plain", sans essayer de décoder son contenu.

Si l'OPTION est vraie (par défaut), le corps de "message/rfc822" ou "message/partial" est analysé avec ce parser, créant un objet entité. Ce qui se passe ensuite dépend de la valeur de l'OPTION :

NEST ou 1
La valeur par défaut. Le message contenu est transformé en la seule "partie" de l'entité "message/rfc822" (comme si le message conteneur était un type spécial de "multipart"). Vous pouvez récupérer la sous-entité en appelant la méthode parts() sur l'entité "message/rfc822".

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

Merci à Andreas Koenig pour avoir suggéré cette méthode.

extract_uuencode [YESNO]
Méthode d'instance. Si défini à true, alors lorsqu'un message dont le type de contenu effectif est « text/plain » et dont l'encodage est 7bit/8bit/binary est rencontré, le corps encodé sera analysé pour voir s'il contient des données encodées en uu (généralement signalées par une ligne « begin XXX »).

Si c'est le cas, le message encodé est décomposé en un multipart, où le texte avant la première ligne « begin XXX » devient la première partie, et toutes les sections « begin...end » suivantes deviennent les parties suivantes. Le nom de fichier (s'il est spécifié) sera accessible par les moyens normaux.

ignore_errors [YESNO]
Méthode d'instance. Contrôle si l'analyseur essaiera d'ignorer les erreurs normalement graves, les traitera comme des avertissements et continuera l'analyse.

Si YESNO est true (la valeur par défaut), de nombreuses erreurs de syntaxe sont tolérées. Si c'est false, les erreurs graves lèvent des exceptions. Sans argument, renvoie la valeur actuelle.

decode_bodies [YESNO]
Méthode d'instance. Contrôle si l'analyseur doit décoder les corps d'entité. Si cette valeur est false (la valeur par défaut est true), tous les corps d'entité seront conservés dans leur contenu encodé d'origine.

Pour éviter le double encodage côté sortie, MIME::Body->is_encoded est défini à false, ce qui indique à MIME::Body de ne pas ré-encoder les données si l'encodage a été demandé. Ceci est particulièrement utile lorsqu'il est important que le contenu ne soit pas modifié, par exemple si vous souhaitez en calculer des signatures OpenPGP.

ATTENTION : les significations changent considérablement si vous analysez des messages MIME avec cette option activée, car MIME::Entity et MIME::Body verront *toujours* des données encodées maintenant, alors que le comportement par défaut est de travailler avec des données décodées (et de les encoder uniquement si demandé). Vous devrez décoder les données vous-même si vous souhaitez les avoir décodées.

Par conséquent, utilisez-le uniquement si vous savez exactement ce que vous faites, et si vous êtes sûr d'en avoir vraiment besoin.

Analyse d'une source d'entrée

parse_data DATA
Méthode d'instance. Analyse un message MIME déjà en mémoire. Crée en interne un gestionnaire de fichier en mémoire à l'aide de PerlIO.

Vous pouvez fournir les DATA de n'importe quelle manière...

  • Un scalaire contenant le message. Une référence à ce scalaire sera utilisée en interne.
  • Une référence à un scalaire contenant le message. Cette référence sera utilisée en interne.
  • OBSOLÈTE

    Une référence à un tableau de scalaires. Le tableau est concaténé en interne dans une chaîne temporaire, et une référence à la nouvelle chaîne est utilisée en interne.

    Il est plus efficace de passer une référence à un scalaire, je vous recommande donc de restructurer votre code pour utiliser cette interface. Si vous devez absolument passer un tableau, il peut être préférable d'utiliser IO::ScalarArray dans le code qui appelle parse()

Renvoie le MIME::Entity analysé en cas de succès.

parse INSTREAM
Méthode d'instance. Prend un flux MIME et le divise en ses entités constitutives.

L'INSTREAM peut être fourni sous forme de IO::File, de descripteur de fichier glob (comme « \*STDIN »), ou de tout objet lié à l'interface IO (qui implémente au minimum getline() et read()).

Renvoie le MIME::Entity analysé en cas de succès. Lance une exception en cas d'erreur. Si le message contient trop de parties (tel que défini par max_parts), renvoie undef.

parse_open EXPR
Méthode d'instance. Interface pratique pour parse(). Il suffit de donner à cette méthode toute expression qui peut être utilisée comme deuxième argument à open() pour ouvrir un descripteur de fichier en lecture.

Renvoie le MIME::Entity analysé en cas de succès. Lance une exception en cas d'erreur.

parse_two HEADFILE, BODYFILE
Méthode d'instance. Interface pratique pour parse_open(), pour les programmes exécutés sous des gestionnaires de courrier comme deliver, qui divisent le message de courrier en un fichier d'en-tête et un corps. Il suffit de donner à cette méthode les chemins des fichiers correspondants.

Avertissement : on suppose qu'une fois les fichiers concaténés, il y aura une ligne vide séparant la partie en-tête et le corps.

Avertissement : la nouvelle implémentation lit les fichiers dans un tableau de lignes pour la portabilité, au lieu d'utiliser 'cat'. Cela peut poser problème si vos messages sont volumineux.

Renvoie le MIME::Entity analysé en cas de succès. Lance une exception en cas d'erreur.

Spécification de la destination de sortie

Avertissement : dans les versions 5.212 et antérieures, cela était géré par des méthodes de MIME::Parser. Cependant, comme de nombreux utilisateurs ont demandé un contrôle fin sur la manière dont cela est effectué, la logique a été séparée de l'analyseur et placée dans sa propre classe, MIME::Parser::Filer. Chaque MIME::Parser gère une instance d'une classe dérivée de MIME::Parser::Filer pour gérer la sortie sur disque (voir MIME::Parser::Filer pour les détails.)

L'avantage est que le code de MIME::Parser ne sera pas encombré par de nombreuses choses liées au disque. L'inconvénient est que la manière dont vous remplacez le comportement par défaut changera.

Pour l'instant, toutes les méthodes publiques normales sont toujours fournies, mais beaucoup ne sont que des stubs qui créent ou délèguent à la classe MIME::Parser::Filer sous-jacente.

filer [FILER]
Méthode d'instance. Obtient/définit l'objet FILER utilisé pour gérer la sortie sur disque. Il s'agira d'une sous-classe de MIME::Parser::Filer.
output_dir DIRECTORY
Méthode d'instance. Crée des messages qui sont enregistrés directement dans le DIRECTORY donné. Elle y parvient en définissant l'objet sous-jacent de filer() à une nouvelle instance de MIME::Parser::FileInto, et passe les arguments à sa méthode new().

Note : Cette méthode remplace l'objet sous-jacent, vous devez donc l'appeler avant de modifier les attributs de l'objet, tels que le préfixe de sortie ; sinon, ces modifications seront perdues.

output_under BASEDIR, OPTS...
Méthode d'instance. Crée des messages qui sont enregistrés directement dans des sous-répertoires de BASEDIR, un par message. Elle y parvient en définissant l'objet sous-jacent de filer() à une nouvelle instance de MIME::Parser::FileUnder, et passe les arguments à sa méthode new().

Note : Cette méthode remplace l'objet sous-jacent, vous devez donc l'appeler avant de modifier les attributs de l'objet, tels que le préfixe de sortie ; sinon, ces modifications seront perdues.

output_path HEAD
Méthode d'instance, OBSOLÈTE. Étant donné une en-tête MIME pour un fichier à extraire, génère un chemin de sortie approprié pour le fichier extrait. Identique à la forme préférée : 
$parser->filer->output_path(...args...);

Nous déléguons cela à l'objet sous-jacent filer()

output_prefix [PREFIX]
Méthode d'instance, OBSOLÈTE. Obtient/définit la courte chaîne que tous les répertoires de fichiers extraits commenceront par (en supposant qu'il n'y a pas de « nom recommandé » meilleur). Identique à la forme préférée : 
$parser->filer->output_prefix(...args...);

Nous déléguons cela à l'objet sous-jacent filer()

evil_filename NAME
Méthode d'instance, OBSOLÈTE. Identique à la forme préférée : 
$parser->filer->evil_filename(...args...);

Nous déléguons cela à l'objet sous-jacent filer()

max_parts NUM
Méthode d'instance. Limite le nombre de parties MIME à analyser.

Normalement, les instances de cette classe analysent un message jusqu'à la fin. Les messages avec de nombreuses parties MIME peuvent entraîner une consommation excessive de mémoire. Si vous appelez cette méthode, l'analyse s'arrêtera avec die() si un message contient plus de NUM parties.

Si NUM est défini à -1 (la valeur par défaut), aucune limite n'est définie.

Sans argument, renvoie la valeur actuelle sous forme d'entier.

output_to_core YESNO
Méthode d'instance. Normalement, les instances de cette classe écrivent toutes leurs données de corps décodées dans des fichiers sur disque (via MIME::Body::File). Cependant, vous pouvez modifier ce comportement en appelant cette méthode avant l'analyse :

Si YESNO est false (la valeur par défaut), toutes les données de corps vont dans des fichiers sur disque.

Si YESNO est true, toutes les données de corps vont dans des structures de données en mémoire. C'est un peu risqué (que se passe-t-il si quelqu'un vous envoie un MPEG ou...

Fichier tar

tar_file
Méthode d'instance. Conserve la configuration du fichier tar sous forme de valeur booléenne.

tmp_to_core

tmp_to_core [YESNO]
Méthode d'instance. new_tmpfile() doit-il créer des fichiers temporaires sur disque ou utiliser des fichiers en mémoire ? Normalement, nous autorisons la création de fichiers temporaires sur disque, car elle permet de gérer de gros fichiers joints même lorsque le noyau est limité.

use_inner_files

use_inner_files [YESNO]
SUPPRIMÉ.

Méthode d'instance.

MIME::Parser ne prend plus en charge IO::InnerFile, mais cette méthode est conservée pour la compatibilité ascendante. Elle ne fait rien.

Spécification des classes à instancier

interface RÔLE,[VALEUR]
Méthode d'instance. Lors de l'analyse, l'analyseur crée normalement des instances de certaines classes, comme MIME::Entity. Cependant, vous pourriez vouloir créer une sous-classe de l'analyseur qui utilise vos propres classes expérimentales head, entity, etc. (par exemple, votre classe "head" peut fournir des méthodes supplémentaires orientées MIME).

Si tel est votre souhait, c'est cette méthode que votre sous-classe doit appeler lors de l'initialisation. En voici un exemple :

package MyParser;
@ISA = qw(MIME::Parser);
...
sub init {
    my $self = shift;
    $self->SUPER::init(@_);        ### effectuer l'initialisation du parent
    $self->interface(ENTITY_CLASS => 'MIME::MyEntity');
    $self->interface(HEAD_CLASS   => 'MIME::MyHead');
    $self;                         ### retourner
}

Sans valeur, renvoie la valeur actuellement associée à ce RÔLE.

new_body_for HEAD

new_body_for HEAD
Méthode d'instance. Compte tenu de l'en-tête d'une partie que nous analysons, renvoie un nouvel objet de type MIME::Body (quelle que soit sa sous-classe) pour recevoir les données de cette partie.

Si vous avez défini l'option output_to_core sur false (la valeur par défaut), nous appelons output_path() et créons un objet MIME::Body::File dans ce fichier.

Si vous avez défini l'option output_to_core sur true avant l'analyse, vous obtenez un objet MIME::Body::InCore.

Si vous voulez que l'analyseur fasse quelque chose de différent, vous pouvez redéfinir cette méthode dans une sous-classe.

Création de fichiers temporaires

tmp_dir REPERTOIRE
Méthode d'instance. Crée tous les fichiers temporaires générés par cet analyseur dans le répertoire spécifié.

Si elle est appelée sans arguments, renvoie la valeur actuelle.

new_tmpfile

new_tmpfile
Méthode d'instance. Renvoie un handle IO pour stocker des données temporaires pendant l'analyse.

Par défaut, utilise MIME::Tools::tmpopen() pour créer un nouveau fichier temporaire, sauf si tmp_to_core() l'indique, mais vous pouvez la redéfinir. Vous ne devriez pas en avoir besoin.

L'emplacement où sont stockés les fichiers temporaires peut être modifié par défaut lors de l'analyse par l'analyseur avec tmp_dir().

Résultats de l'analyse et récupération des erreurs

last_error
Méthode d'instance. Renvoie l'erreur (le cas échéant) qui a été ignorée lors de la dernière analyse.

ambiguous_content

ambiguous_content
Méthode d'instance. Renvoie vrai si le message le plus récent a une ou plusieurs entités avec un contenu ambigu. Consultez la documentation de la méthode ambiguous_content de MIME::Entity pour plus de détails.

Remarque : bien que ces deux appels à ambiguous_content renvoient le même résultat :

$entity = $parser->parse($whatever_stream);
$parser->ambiguous_content();
$entity->ambiguous_content();

Le premier est plus rapide car il renvoie simplement les résultats détectés lors de l'analyse, tandis que le second exécute le code qui vérifie explicitement le contenu ambigu.

last_head

last_head
Méthode d'instance. Renvoie l'en-tête MIME le plus élevé du dernier flux tenté d'analyser. Il est utile pour répondre aux utilisateurs qui envoient des messages MIME mal formés. 
### Analyser un flux d'entrée :
eval { $entity = $parser->parse(\*STDIN) };
if (!$entity) {    ### l'analyse a échoué !
    my $decapitated = $parser->last_head;
    ...
}

results

results
Méthode d'instance. Renvoie un objet contenant de nombreuses informations sur la dernière entité analysée. Il s'agira d'une instance de la classe MIME::Parser::Results.

OPTIMISATION DE VOTRE ANALYSEUR

Maximiser la vitesse

Meilleurs mécanismes d'entrée :

parse()                    OUI (si vous lui donnez un globref ou une sous-classe de IO::File)
parse_open()               OUI
parse_data()               NON  (voir ci-dessous)
parse_two()                NON  (voir ci-dessous)

Meilleures configurations :

decode_headers()           *** (pas de différence réelle ; 0 est légèrement plus rapide)
extract_nested_messages()  0   (peut être légèrement plus rapide, mais vous voulez généralement le mettre à 1)
output_to_core()           0   (sera beaucoup plus rapide)
tmp_to_core()              0   (sera beaucoup plus rapide)

L'E/S native est beaucoup plus rapide que l'E/S orientée objet. Il est beaucoup plus rapide d'utiliser <$foo> que $foo->getline. Pour la compatibilité ascendante, ce module doit continuer à utiliser l'E/S orientée objet dans la plupart des cas, mais si vous utilisez parse() avec un fichier réel (chaîne, globref ou sous-classe de IO::File), MIME::Parser peut effectuer des optimisations importantes.

L'appel parse_two() est très inefficace. Il s'agit actuellement uniquement d'une interface pour parse_data(). Si votre système le prend en charge, vous êtes *beaucoup* mieux loti en faisant quelque chose comme :

$parser->parse_open("/bin/cat msg.head msg.body |");

Minimiser la mémoire

Meilleurs mécanismes d'entrée :

parse()                    OUI
parse_open()               OUI
parse_data()               NON  (les E/S en mémoire videront le cœur)
parse_two()                NON  (les E/S en mémoire videront le cœur)

Meilleures configurations :

decode_headers()           *** (pas de différence réelle)
extract_nested_messages()  *** (pas de différence réelle)
output_to_core()           0   (utilisera beaucoup moins de mémoire)
                                tmp_to_core est 1)
tmp_to_core()              0   (utilisera beaucoup moins de mémoire)

Maximiser la tolérance au mauvais MIME

Meilleurs mécanismes d'entrée :

parse()                    *** (peu importe)
parse_open()               *** (peu importe)
parse_data()               *** (peu importe)
parse_two()                *** (peu importe)

Meilleures configurations :

decode_headers()           0   (évite le problème des mauvaises encodages d'en-têtes)
extract_nested_messages()  0   (évite les problèmes avec les mauvais messages imbriqués, mais vous voulez souvent le mettre à 1)
output_to_core()           *** (peu importe)
tmp_to_core()              *** (peu importe)

You can veto tmpfiles entirely. You can set tmp_to_core() true: this will always use in-core I/O for the buffering (warning: this will slow down the parsing of messages with large attachments).

Final resort. You can always override new_tmpfile() in a subclass.

WARNINGS

Multipart messages are always read line-by-line
Multipart document parts are read line-by-line, so that the encapsulation boundaries may easily be detected. However, bad MIME composition agents (for example, naive CGI scripts) might return multipart documents where the parts are, say, unencoded bitmap files... and, consequently, where such "lines" might be veeeeeeeeery long indeed.

A better solution for this case would be to set up some form of state machine for input processing. This will be left for future versions.

Multipart parts read into temp files before decoding
In my original implementation, the MIME::Decoder classes had to be aware of encapsulation boundaries in multipart MIME documents. While this decode-while-parsing approach obviated the need for temporary files, it resulted in inflexible and complex decoder implementations.

The revised implementation uses a temporary file (a la tmpfile()) during parsing to hold the encoded portion of the current MIME document or part. This file is deleted automatically after the current part is decoded and the data is written to the "body stream" object; you'll never see it, and should never need to worry about it.

Some folks have asked for the ability to bypass this temp-file mechanism, I suppose because they assume it would slow down their application. I considered accommodating this wish, but the temp-file approach solves a lot of thorny problems in parsing, and it also protects against hidden bugs in user applications (what if you've directed the encoded part into a scalar, and someone unexpectedly sends you a 6 MB tar file?). Finally, I'm just not convinced that the temp-file use adds significant overhead.

Fuzzing of CRLF and newline on input
RFC 2045 dictates that MIME streams have lines terminated by CRLF ("\r\n"). However, it is extremely likely that folks will want to parse MIME streams where each line ends in the local newline character "\n" instead.

An attempt has been made to allow the parser to handle both CRLF and newline-terminated input.

Fuzzing of CRLF and newline on output
The "7bit" and "8bit" decoders will decode both a "\n" and a "\r\n" end-of-line sequence into a "\n".

The "binary" decoder (default if no encoding specified) still outputs stuff verbatim... so a MIME message with CRLFs and no explicit encoding will be output as a text file that, on many systems, will have an annoying ^M at the end of each line... but this is as it should be.

Inability to handle multipart boundaries that contain newlines
First, let's get something straight: this is an evil, EVIL practice, and is incompatible with RFC 2046... hence, it's not valid MIME.

If your mailer creates multipart boundary strings that contain newlines when they appear in the message body, give it two weeks notice and find another one. If your mail robot receives MIME mail like this, regard it as syntactically incorrect MIME, which it is.

Why do I say that? Well, in RFC 2046, the syntax of a boundary is given quite clearly:

boundary := 0*69<bchars> bcharsnospace
bchars := bcharsnospace / " "
bcharsnospace :=    DIGIT / ALPHA / "'" / "(" / ")" / "+" /"_"
             / "," / "-" / "." / "/" / ":" / "=" / "?"

All of which means that a valid boundary string cannot have newlines in it, and any newlines in such a string in the message header are expected to be solely the result of folding the string (i.e., inserting to-be-removed newlines for readability and line-shortening only).

Yet, there is at least one brain-damaged user agent out there that composes mail like this:

MIME-Version: 1.0
Content-type: multipart/mixed; boundary="----ABC-
 123----"
Subject: Hi... I'm a dork!
This is a multipart MIME message (yeah, right...)
----ABC-
 123----
Hi there!

We have got to discourage practices like this (and the recent file upload idiocy where binary files that are part of a multipart MIME message aren't base64-encoded) if we want MIME to stay relatively simple, and MIME parsers to be relatively robust.

Thanks to Andreas Koenig for bringing a baaaaaaaaad user agent to my attention.
