NOM

MIME::Entity - classe pour les messages MIME analysés et décodés

SYNTAXE

Avant de lire la suite, vous devriez consulter MIME::Tools pour vous assurer que vous comprenez où ce module s'inscrit dans le schéma général des choses. Allez-y, faites-le maintenant. J'attendrai.

Prêt ? Ok...

### Créer une entité :
$top = MIME::Entity->build(From    => 'moi@monhost.com',
                           To      => 'toi@tonhost.com',
                           Subject => "Bonjour, infirmière !",
                           Data    => \@mon_message);
### Y joindre des éléments :
$top->attach(Path     => $chemin_gif,
             Type     => "image/gif",
             Encoding => "base64");
### Le signer :
$top->sign;
### L'afficher :
$top->print(\*STDOUT);

DESCRIPTION

Une sous-classe de Mail::Internet.

Ce paquet fournit une classe pour représenter les entités de message MIME, telles que spécifiées dans les RFC 2045, 2046, 2047, 2048 et 2049.

EXEMPLES

Exemples de construction

Créer un document pour un fichier texte ASCII 7 bits ordinaire (beaucoup de choses sont mises par défaut pour nous) :

$ent = MIME::Entity->build(Path=>"message-anglais.txt");

Créer un document pour un fichier texte avec des caractères 8 bits (Latin-1) :

$ent = MIME::Entity->build(Path     =>"message-francais.txt",
                           Encoding =>"quoted-printable",
                           From     =>'jean.luc@inria.fr',
                           Subject  =>"C'est bon !");

Créer un document pour un fichier GIF (la description est complètement facultative ; notez que nous devons spécifier le type de contenu et l'encodage car ils ne sont pas les valeurs par défaut) :

$ent = MIME::Entity->build(Description => "Une jolie image",
                           Path        => "./docs/mime-sm.gif",
                           Type        => "image/gif",
                           Encoding    => "base64");

Créer un document dont vous avez déjà le texte, en utilisant "Data" :

$ent = MIME::Entity->build(Type        => "text/plain",
                           Encoding    => "quoted-printable",
                           Data        => ["Première ligne.\n",
                                          "Deuxième ligne.\n",
                                          "Dernière ligne.\n"]);

Créer un message multipart, avec la structure entière donnée explicitement :

### Créer le niveau supérieur et définir les en-têtes de courrier :
$top = MIME::Entity->build(Type     => "multipart/mixed",
                           From     => 'moi@monhost.com',
                           To       => 'toi@tonhost.com',
                           Subject  => "Bonjour, infirmière !");
### Pièce jointe #1 : un document texte simple :
$top->attach(Path=>"./testin/short.txt");
### Pièce jointe #2 : un fichier GIF :
$top->attach(Path        => "./docs/mime-sm.gif",
             Type        => "image/gif",
             Encoding    => "base64");
### Pièce jointe #3 : texte que nous allons créer avec du texte que nous avons sous la main :
$top->attach(Data => $contenu);

Supposez que vous ne sachiez pas à l'avance que vous aurez des pièces jointes ? Pas de problème : vous pouvez également "joindre" à des parties uniques :

$top = MIME::Entity->build(From    => 'moi@monhost.com',
                           To      => 'toi@tonhost.com',
                           Subject => "Bonjour, infirmière !",
                           Data    => \@mon_message);
if ($chemin_GIF) {
    $top->attach(Path     => $chemin_GIF,
                 Type     => 'image/gif');
}

Copier une entité (en-têtes, parties... tout sauf les données de corps externes) :

my $deepcopy = $top->dup;

Exemples d'accès

### Obtenir l'en-tête, un MIME::Head :
$head = $ent->head;
### Obtenir le corps, sous forme de MIME::Body ;
$bodyh = $ent->bodyhandle;
### Obtenir le type MIME prévu (déclaré dans l'en-tête) :
$type = $ent->mime_type;
### Obtenir le type MIME effectif (au cas où le décodage aurait échoué) :
$eff_type = $ent->effective_type;
### Obtenir le préambule, les parties et l'épilogue :
$preamble   = $ent->preamble;          ### référence à un tableau de lignes
$num_parts  = $ent->parts;
$first_part = $ent->parts(0);          ### une entité
$epilogue   = $ent->epilogue;          ### référence à un tableau de lignes

Exemples de manipulation

Manipuler les données du corps :

### Lire les données du corps (non encodées) :
if ($io = $ent->open("r")) {
    while (defined($_ = $io->getline)) { print $_ }
    $io->close;
}
### Écrire les données du corps (non encodées) :
if ($io = $ent->open("w")) {
    foreach (@lines) { $io->print($_) }
    $io->close;
}
### Supprimer les fichiers pour toutes les données externes (sur disque) :
$ent->purge;

Manipuler la signature :

### Le signer (supprime automatiquement toute signature existante) :
$top->sign(File=>"$ENV{HOME}/.signature");
### Supprimer toute signature dans les 15 lignes de la fin :
$top->remove_sig(15);

Manipuler les en-têtes :

### Calculer les longueurs de contenu pour les parties uniques en fonction des corps :
###   (Faites ceci juste avant d'imprimer !)
$entity->sync_headers(Length=>'COMPUTE');

Manipuler la structure :

### Si c'est un multipart à 0 ou 1 partie, le réduire à une partie unique :
$top->make_singlepart;
### Si c'est une partie unique, l'étendre en un multipart avec 1 partie :
$top->make_multipart;

Supprimer des parties :

### Supprimer certaines parties d'un message multipart :
my @keep = grep { keep_part($_) } $msg->parts;
$msg->parts(\@keep);

Exemples de sortie

Imprimer vers des descripteurs de fichiers :

### Imprimer le message entier :
$top->print(\*STDOUT);
### Imprimer seulement l'en-tête :
$top->print_header(\*STDOUT);
### Imprimer seulement le corps (encodé)... inclut aussi les parties !
$top->print_body(\*STDOUT);

Transformer en chaîne de caractères... notez que "stringify_xx" peut aussi s'écrire "xx_as_string" ; les méthodes sont synonymes, et aucune forme ne sera dépréciée.

Si vous définissez la variable $MIME::Entity::BOUNDARY_DELIMITER sur une chaîne, cette chaîne sera utilisée comme délimiteur de fin de ligne en sortie. Si elle n'est pas définie, la fin de ligne sera un caractère de nouvelle ligne (\n)

NOTE que $MIME::Entity::BOUNDARY_DELIMITER ne s'applique qu'aux parties structurelles des données MIME générées par ce paquet et à la sortie encodée en Base64 ; si une partie utilise en interne un délimiteur de fin de ligne différent et est sortie telle quelle, la fin de ligne n'est pas changée pour correspondre à $MIME::Entity::BOUNDARY_DELIMITER.

### Transformer le message entier en chaîne :
print $top->stringify;              ### ou $top->as_string
### Transformer seulement l'en-tête en chaîne :
print $top->stringify_header;       ### ou $top->header_as_string
### Transformer seulement le corps (encodé)... inclut aussi les parties !
print $top->stringify_body;         ### ou $top->body_as_string

Débogage :

### Afficher les informations de débogage :
$entity->dump_skeleton(\*STDERR);

INTERFACE PUBLIQUE

Construction

new [SOURCE]
Méthode de classe. Crée une nouvelle entité MIME vide. Fondamentalement, ceci utilise le constructeur de Mail::Internet...

Si SOURCE est une référence à un tableau (ARRAYREF), il est supposé être un tableau de lignes qui sera utilisé pour créer à la fois l'en-tête et un corps en mémoire.

Sinon, si SOURCE est défini, il est supposé être un descripteur de fichier à partir duquel l'en-tête et le corps en mémoire doivent être lus.

Note : dans les deux cas, le corps ne sera pas analysé : simplement lu !

ambiguous_content
Méthode d'instance.

Retourne vrai si cette entité ou l'une de ses parties, récursivement a un "MIME::Head" qui indique un contenu ambigu.

Notez attentivement la différence entre :

$entity->head

->contenu_ambigu();

et

$entité->contenu_ambigu();

Le premier renvoie vrai uniquement si les en-têtes de cette entité spécifique indiquent une ambiguïté. Le second renvoie vrai si cette entité ou l'une de ses parties, récursivement a des en-têtes qui indiquent une ambiguïté.

add_part ENTITÉ, [OFFSET]
Méthode d'instance. En supposant que nous sommes un message multipart, ajoute une partie de corps (une MIME::Entity) au tableau des parties de corps. Renvoie la partie qui vient d'être ajoutée.

Si OFFSET est positif, la nouvelle partie est ajoutée à cet offset à partir du début du tableau de parties. Si elle est négative, elle compte à partir de la fin du tableau. (Un INDEX de -1 placera la nouvelle partie à la toute fin du tableau, -2 la placera comme avant-dernière dans le tableau, etc.) Si OFFSET n'est pas donné, la nouvelle partie est ajoutée à la fin du tableau. Merci à Jason L Tibbitts III pour le support d'OFFSET.

Attention : en général, vous ne voudrez attacher des parties qu'à des entités avec un type de contenu "multipart/*").

attach PARAMHASH
Méthode d'instance. La manière vraiment rapide et simple de créer des messages multipart. Le PARAMHASH est utilisé pour "construire" une nouvelle entité ; cette méthode est essentiellement équivalente à : 
$entité->add_part(ref($entité)->build(PARAMHASH, Top=>0));

Note : normalement, vous attachez à des entités multipart ; cependant, si vous attachez quelque chose à une entité monopartie (comme joindre un GIF à un message texte), la monopartie sera automatiquement coercée en multipart.

build PARAMHASH
Méthode de classe/d'instance. Une manière passe-partout rapide et simple de créer une entité. Utilisez-la comme suit pour construire une entité monopartie "normale" : 
$ent = MIME::Entity->build(Type     => "image/gif",
                           Encoding => "base64",
                           Path     => "/chemin/vers/xyz12345.gif",
                           Filename => "saveme.gif",
                           Disposition => "attachment");

Et comme suit pour construire une entité "multipart" :

$ent = MIME::Entity->build(Type     => "multipart/mixed",
                           Boundary => "---1234567");

Un en-tête MIME minimal sera créé. Si vous souhaitez ajouter ou modifier des champs d'en-tête par la suite, vous pouvez bien sûr le faire via l'objet head sous-jacent... mais hey, il y a maintenant une syntaxe plus jolie !

$ent = MIME::Entity->build(Type          =>"multipart/mixed",
                           From          => $myaddr,
                           Subject       => "Salut !",
                           'X-Certified' => ['SINED',
                                             'SEELED',
                                             'DELIVERED']);

Normalement, un champ d'en-tête "X-Mailer" est généré, contenant le nom et la version de cette boîte à outils (plus la version RCS de ce module). Cela permettra de retracer jusqu'à nous toute mauvaise MIME que nous générerions. Vous pouvez bien sûr écraser cet en-tête avec le vôtre :

$ent = MIME::Entity->build(Type        => "multipart/mixed",
                           'X-Mailer'  => "monprog 1.1");

Ou le supprimer entièrement :

$ent = MIME::Entity->build(Type       => "multipart/mixed",
                           'X-Mailer' => undef);

OK, assez de battage publicitaire. Les paramètres sont :

(FIELDNAME)
Tout champ que vous souhaitez placer dans l'en-tête du message, tiré de la liste standard des champs d'en-tête (vous n'avez pas à vous soucier de la casse) : 
Bcc           Encrypted     Received      Sender
Cc            From          References    Subject
Comments      Keywords      Reply-To      To
Content-*     Message-ID    Resent-*      X-*
Date          MIME-Version  Return-Path
              Organization

Pour donner aux utilisateurs expérimentés un pouvoir de veto, ces champs seront définis après ceux que je définis... alors faites attention : ne définissez aucun champ MIME (comme "Content-type") à moins de savoir ce que vous faites !

Pour spécifier un nom de champ qui n'est pas dans la liste ci-dessus, même un qui est identique à une option ci-dessous, donnez-le simplement avec un ":" final, comme "Mon-champ:". En cas de doute, cela indique toujours un champ de courrier (et cela y ressemble aussi un peu).

Boundary
Entités multipart uniquement. Facultatif. La chaîne de délimitation. Conformément à la RFC-2046, elle doit uniquement contenir les caractères "[0-9a-zA-Z'()+_,-./:=?]" et l'espace (vous serez averti, et votre délimiteur sera ignoré, si ce n'est pas le cas). Si vous omettez ceci, une chaîne aléatoire sera choisie... ce qui est probablement plus sûr.
Charset
Facultatif. L'ensemble de caractères.
Data
Entités monoparties uniquement. Facultatif. Une alternative à Path (voir ci-après) : les données réelles, sous forme de scalaire ou de référence à un tableau (dont les éléments sont joints pour former le scalaire réel). Le corps est ouvert sur les données en utilisant MIME::Body::InCore.

Notez que pour les parties texte, le scalaire ou le tableau de données est supposé être encodé dans un jeu de caractères approprié (comme si par "Encode::encode") plutôt qu'une chaîne Perl native. L'encodage que vous utilisez doit, bien sûr, correspondre à l'option "charset" de l'en-tête "MIME-Type".

Description
Facultatif. Le texte de la description du contenu. Si vous ne la spécifiez pas, le champ n'est pas mis dans l'en-tête.
Disposition
Facultatif. La disposition du contenu de base ("attachment" ou "inline"). Si vous ne la spécifiez pas, elle est par défaut "inline" pour des raisons de compatibilité descendante. Merci à Kurt Freytag d'avoir suggéré cette fonctionnalité.
Encoding
Facultatif. L'encodage du transfert de contenu. Si vous ne le spécifiez pas, une valeur par défaut raisonnable est mise en place. Vous pouvez également donner la valeur spéciale '-SUGGEST', pour qu'elle soit choisie de manière intensive en analysant les données elles-mêmes.
Filename
Entités monoparties uniquement. Facultatif. Le nom de fichier recommandé. Remplace tout nom extrait de "Path". L'information est stockée aux emplacements obsolètes (content-type) et préférés (content-disposition). Si vous souhaitez explicitement éviter un nom de fichier recommandé (même lorsque Path est utilisé), fournissez-le comme vide ou undef.
Id
Facultatif. Définit l'identifiant de contenu.
Path
Entités monoparties uniquement. Facultatif. Le chemin vers le fichier à joindre. Le corps est ouvert sur ce fichier en utilisant MIME::Body::File.
Top
Facultatif. Est-ce une entité de niveau supérieur ? Si oui, elle doit porter une version MIME. La valeur par défaut est vraie. (NB : regardez comment attach() l'utilise.)
Type
Facultatif. Le type de contenu de base ("text/plain", etc.). Si vous ne le spécifiez pas, il est par défaut "text/plain" conformément à la RFC 2045. Faites-vous une faveur : mettez-le.
dup
Méthode d'instance. Duplique l'entité. Effectue une copie profonde et récursive, mais attention : les données externes dans les bodyhandles ne sont pas copiées dans de nouveaux fichiers ! Modifier les données dans le fichier de données d'une entité, ou purger cette entité, affectera sa copie. Les entités avec des données en mémoire n'ont probablement pas à s'en inquiéter.

Accès

body [VALEUR]
Méthode d'instance. Obtient le corps encodé (prêt pour le transport), sous forme de tableau de lignes. Renvoie une référence à un tableau. Chaque entrée du tableau est une ligne terminée par un saut de ligne.

Ceci est une structure de données en lecture seule : modifier son contenu n'aura aucun effet. Son contenu est identique à ce qui est imprimé par print_body().

Fourni pour la compatibilité avec Mail::Internet, afin que des méthodes comme smtpsend() fonctionnent. Notez cependant que si VALEUR est donné, une exception fatale est lancée, car vous ne pouvez pas utiliser cette méthode pour définir les lignes du message encodé.

Si vous souhaitez les données brutes (non encodées) du corps, utilisez la méthode bodyhandle() pour obtenir et utiliser un MIME::Body. Le type de contenu de l'entité vous indiquera si ce corps est mieux lu comme du texte (via getline()) ou des données brutes (via read()).

bodyhandle [VALEUR]
Méthode d'instance. Obtient ou définit un objet abstrait représentant le corps du message. Le corps contient les données du message décodées.

Notez que toutes les entités n'ont pas de corps ! Une entité aura soit un corps, soit des parties : pas les deux. Cette méthode ne renverra un objet que si cette entité peut avoir un corps ; sinon, elle renverra indéfini. La possibilité pour une entité donnée d'avoir un corps est déterminée par (1) son type de contenu, et (2) si le parseur a été chargé ou non d'extraire les messages imbriqués :

Type:        | Extraire imbriqués ? | bodyhandle() | parts()
-----------------------------------------------------------------------
multipart/*  | -                    | undef        | 0 ou plus MIME::Entity
message/*    | vrai                 | undef        | 0 ou 1 MIME::Entity
message/*    | faux                 | MIME::Body   | liste vide
(autre)      | -                    | MIME::Body   | liste vide

Si "VALEUR" n'est pas donné, le bodyhandle actuel est renvoyé, ou undef si l'entité ne peut pas avoir de corps.

METHODS

body
Instance method. Returns the entity's body, or undef if it doesn't have one. The return value is an instance of MIME::Body.

See "bodyhandle" for a discussion of parts vs. bodies.

body_header
Instance method. Returns the entity's body header, or undef if it doesn't have one. The return value is an instance of MIME::Head.

See "parts" for more info.

effective_type [MIMETYPE]
Instance method. Set/get the effective MIME type of this entity. This is usually identical to the actual (or defaulted) MIME type, but in some cases it differs. For example, from RFC-2045: 
Any entity with an unrecognized Content-Transfer-Encoding must be
treated as if it has a Content-Type of "application/octet-stream",
regardless of what the Content-Type header field actually says.

Why? because if we can't decode the message, then we have to take the bytes as-is, in their (unrecognized) encoded form. So the message ceases to be a "text/foobar" and becomes a bunch of undecipherable bytes -- in other words, an "application/octet-stream".

Such an entity, if parsed, would have its effective_type() set to "application/octet_stream", although the mime_type() and the contents of the header would remain the same.

If there is no effective type, the method just returns what mime_type() would.

Warning: the effective type is "sticky"; once set, that effective_type() will always be returned even if the conditions that necessitated setting the effective type become no longer true.

epilogue [LINES]
Instance method. Get/set the text of the epilogue, as an array of newline-terminated LINES. Returns a reference to the array of lines, or undef if no epilogue exists.

If there is a epilogue, it is output when printing this entity; otherwise, a default epilogue is used. Setting the epilogue to undef (not []!) causes it to fallback to the default.

head [VALUE]
Instance method. Get/set the head.

If there is no VALUE given, returns the current head. If none exists, an empty instance of MIME::Head is created, set, and returned.

Note: This is a patch over a problem in Mail::Internet, which doesn't provide a method for setting the head to some given object.

is_multipart
Instance method. Does this entity's effective MIME type indicate that it's a multipart entity? Returns undef (false) if the answer couldn't be determined, 0 (false) if it was determined to be false, and true otherwise. Note that this says nothing about whether or not parts were extracted.

NOTE: we switched to effective_type so that multiparts with bad or missing boundaries could be coerced to an effective type of "application/x-unparseable-multipart".

mime_type
Instance method. A purely-for-convenience method. This simply relays the request to the associated MIME::Head object. If there is no head, returns undef in a scalar context and the empty array in a list context.

Before you use this, consider using effective_type() instead, especially if you obtained the entity from a MIME::Parser.

open READWRITE
Instance method. A purely-for-convenience method. This simply relays the request to the associated MIME::Body object (see MIME::Body::open()). READWRITE is either 'r' (open for read) or 'w' (open for write).

If there is no body, returns false.

parts
parts INDEX
parts ARRAYREF
Instance method. Return the MIME::Entity objects which are the sub parts of this entity (if any).

If no argument is given, returns the array of all sub parts, returning the empty array if there are none (e.g., if this is a single part message, or a degenerate multipart). In a scalar context, this returns you the number of parts.

If an integer INDEX is given, return the INDEXed part, or undef if it doesn't exist.

If an ARRAYREF to an array of parts is given, then this method sets the parts to a copy of that array, and returns the parts. This can be used to delete parts, as follows:

### Delete some parts of a multipart message:
$msg->parts([ grep { keep_part($_) } $msg->parts ]);

Note: for multipart messages, the preamble and epilogue are not considered parts. If you need them, use the preamble() and epilogue() methods.

Note: there are ways of parsing with a MIME::Parser which cause certain message parts (such as those of type "message/rfc822") to be "reparsed" into pseudo-multipart entities. You should read the documentation for those options carefully: it is possible for a diddled entity to not be multipart, but still have parts attached to it!

See "bodyhandle" for a discussion of parts vs. bodies.

parts_DFS
Instance method. Return the list of all MIME::Entity objects included in the entity, starting with the entity itself, in depth-first-search order. If the entity has no parts, it alone will be returned.

Thanks to Xavier Armengou for suggesting this method.

preamble [LINES]
Instance method. Get/set the text of the preamble, as an array of newline-terminated LINES. Returns a reference to the array of lines, or undef if no preamble exists (e.g., if this is a single-part entity).

If there is a preamble, it is output when printing this entity; otherwise, a default preamble is used. Setting the preamble to undef (not []!) causes it to fallback to the default.

Manipulation

make_multipart [SUBTYPE], OPTSHASH...
Instance method. Force the entity to be a multipart, if it isn't already. We do this by replacing the original [singlepart] entity with a new multipart that has the same non-MIME headers ("From", "Subject", etc.), but all-new MIME headers ("Content-type", etc.). We then create a copy of the original singlepart, strip out the non-MIME headers from that, and make it a part of the new multipart. So this: 
From: me
To: you
Content-type: text/plain
Content-length: 12
Hello there!

Becomes something like this:

From: me
To: you
Content-type: multipart/mixed; boundary="----abc----"
------abc----
Content-type: text/plain
Content-length: 12
Hello there!
------abc------

The actual type of the new top-level multipart will be "multipart/SUBTYPE" (default SUBTYPE is "mixed").

Returns 'DONE' if we really did inflate a singlepart to a multipart. Returns 'ALREADY' (and does nothing) if entity is already multipart and Force was not chosen.

If OPTSHASH contains Force=>1, then we always bump the top-level's content and content-headers down to a subpart of this entity, even if this entity is already a multipart. This is apparently of use to people who are tweaking messages after parsing them.

make_singlepart
Instance method. If the entity is a multipart message with one part, this tries hard to rewrite it as a singlepart, by replacing the content (and content headers) of the top level with those of the part. Also crunches 0-part multiparts into singleparts.

Returns 'DONE' if we really did collapse a multipart to a singlepart. Returns 'ALREADY' (and does nothing) if entity is already a singlepart. Returns '0' (and does nothing) if it can't be made into a singlepart.

purge
Instance method. Recursively purge (e.g., unlink) all external (e.g., on-disk) body parts in this message. See MIME::Body::purge() for details.

Note: this does not delete the directories that those body parts are contained in; only the actual message data files are deleted. This is because some parsers may be customized to create intermediate directories while others are not, and it's impossible for this class to know what directories are safe to remove. Only your application program truly knows that.

If you really want to "clean everything up", one good way is to use MIME::Parser::file_under(), and then do this before parsing your next message:

$parser->filer->purge();

I wouldn't attempt to read those body files after you do this, for obvious reasons. As of MIME-tools 4.x, each body's path is undefined after this operation. I warned you I might do this; truly I did.

Thanks to Jason L. Tibbitts III for suggesting this method.

remove_sig [NLINES]
Instance method, override. Attempts to remove a user's signature from the body of a message.

It does this by looking for a line matching "/^-- $/" within the last "NLINES" of the message. If found then that line and all lines after it will be removed. If "NLINES" is not given, a default value of 10 will be used. This would be of most use in auto-reply scripts.

For MIME entity, this method is reasonably cautious: it will only attempt to un-sign a message with a content-type of "text/*".

If you send remove_sig() to a multipart entity, it will relay it to the first part (the others usually being the "attachments").

Warning: currently slurps the whole message-part into core as an array of lines, so you probably don't want to use this on extremely long messages.

Returns truth on success, false on error.

s

Signe

sign PARAMHASH
Méthode d'instance, écraser. Ajoute une signature au message. Les paramètres sont :
Joindre
Au lieu d'ajouter le texte, ajoute le contenu en tant que pièce jointe au message. L'état sera "inline" et la description indiquera qu'il s'agit d'une signature. Le comportement par défaut est d'ajouter la signature au texte du message (ou à la première partie si elle est multipart). Spécifique à MIME ; nouveau dans cette sous-classe.
Fichier
Utilise le contenu de ce fichier comme signature. Lance une erreur si le fichier ne peut être lu. Comme la méthode de la superclasse.
Forcer
Signe même si le type de contenu n'est pas "text/*". Utilisable pour les types non standard comme "x-foobar", mais faites-le avec prudence ! Spécifique à MIME ; nouveau dans cette sous-classe.
Supprimer
Normalement, nous essayons de supprimer toute signature existante. Si la valeur est vraie, elle vous donne le paramètre NLINES de l'appel à remove_sig. Si la valeur est zéro mais définie, cela indique qu'aucune signature existante ne sera supprimée. Si elle n'est pas définie, la suppression s'effectue avec la valeur par défaut de 10 lignes. Nouveau dans cette sous-classe.
Signature
Utilise ce texte comme signature. Vous pouvez le fournir comme scalaire ou comme référence à un tableau de lignes se terminant par un retour à la ligne. Comme la méthode de la superclasse.

Cette méthode est assez prudente pour les messages MIME : elle n'essaiera de signer un message qu'avec un type de contenu de "text/*", à moins que "Force" ne soit spécifié.

Si vous envoyez ce message à une entité multipart, il sera transmis à la première partie (les autres étant généralement les « pièces jointes »).

Attention : actuellement, il charge l'intégralité de la partie du message sous forme de tableau de lignes en mémoire, vous ne voudrez donc probablement pas l'utiliser sur des messages très longs.

Retourne vrai en cas de succès, faux en cas d'échec.

suggérer_encodage
Méthode d'instance. Retourne une suggestion d'encodage appropriée basée sur le type de contenu effectif.

"text" et "message" types ont leurs corps analysés ligne par ligne pour les caractères 8 bits et les lignes longues ; l'absence de l'un ou l'autre signifie que le message est 7 bits ok. Les autres types sont choisis indépendamment de leur corps :

type principal:      7bit ok?    encodage suggéré :
-----------------------------------------------------------
text              oui         7bit
text              non         quoted-printable
message           oui         7bit
message           non         binaire
multipart         *          binaire (en cas de certaines parties problématiques)
image, etc...    *          base64
synchroniser_en-têtes OPTIONS
Méthode d'instance. Effectue une variété de tâches qui garantissent que les en-têtes MIME d'une entité « arbre » sont synchronisés avec les parties qu'ils décrivent. Cela peut être aussi coûteux que l'impression si cela implique la pré-encodage des parties ; cependant, l'objectif est de produire un format MIME propre. Vous l'utiliserez généralement uniquement si vous traitez et transmettez du MIME provenant d'une source externe.

OPTIONS est un hash décrivant ce qui doit être fait.

Longueur
L'un des champs MIME officiels non officiels est "Content-Length". Normalement, ce champ ne vous importe pas ; cependant, si vous préparez une sortie destinée à HTTP, cela peut être le cas. La valeur de cette option indique ce qui sera fait :

COMPUTER signifie définir un champ "Content-Length" pour chaque partie non multipart dans l'entité, et le laisser vide pour chaque partie multipart dans l'entité.

EFFACER signifie que tous les champs "Content-Length" seront laissés vides. C'est rapide, indolore et sûr.

Toute valeur fausse (par défaut) signifie qu'aucune action ne sera effectuée.

Non standard
Tout champ d'en-tête commençant par "Content-" est, selon les RFC, un champ MIME. Cependant, certains sont non standard et peuvent poser des problèmes à certains lecteurs MIME qui les interprètent différemment.

EFFACER signifie que tous ces champs seront laissés vides. Ceci est effectué *avant* Longueur (voir ci-dessus) et est traité.

Toute valeur fausse (par défaut) signifie qu'aucune action ne sera effectuée.

Retourne une valeur vraie si tout s'est bien passé, faux sinon.

nettoyer_corps
Méthode d'instance, écraser. Actuellement non implémentée pour les messages MIME. Ne fait rien et retourne false.

Sortie

dump_skeleton [FICHIERPOINTEUR]
Méthode d'instance. Imprime le squelette de l'entité dans le descripteur de fichier FILEHANDLE, ou dans celui actuellement sélectionné s'il n'est pas fourni.

Chaque entité est imprimée avec un niveau d'indentation approprié, et les attributs suivants sont utilisés :

Content-type: multipart/mixed
Effective-type: multipart/mixed
Body-file: NONE
Subject: Hey there!
Num-parts: 2

Ceci est vraiment utile pour le débogage ; je ne fais aucune garantie quant à la cohérence du format de sortie au fil du temps.

imprimer [FLUXDE SORTIE]
Méthode d'instance, écraser. Imprime l'entité dans le flux de sortie OUTSTREAM, ou dans le fichier de sortie actuel s'il n'est pas fourni. OUTSTREAM peut être un fichier ou tout objet qui répond au message print().

L'entité est imprimée comme un flux MIME valide ! Cela signifie que l'en-tête est toujours imprimé en premier, et le corps (s'il existe) sera encodé si l'en-tête l'indique. Par exemple, votre sortie pourrait ressembler à ceci :

Subject: Greetings
Content-transfer-encoding: base64
SGkgdGhlcmUhCkJ5ZSB0aGVyZSEK

Si cette entité a un type MIME de "multipart/*", les préambules, parties et épilogues seront imprimés avec des délimiteurs appropriés entre chacun. Tout corps de partie est ignoré :

Content-type: multipart/mixed; boundary="*----*"
Content-transfer-encoding: 7bit
[Préambule]
--*----*
[Entité : Partie 0]
--*----*
[Entité : Partie 1]
--*----*--
[Épilogue]

Si cette entité a un type MIME de seule partie et aucune partie jointe, nous avons affaire à une entité de seule partie normale : le corps est imprimé selon l'en-tête. S'il n'y a pas de corps, un avertissement est émis et le corps est considéré comme vide :

Content-type: image/gif
Content-transfer-encoding: base64
[Corps encodé]

Si cette entité a un type MIME de seule partie mais possède également des parties, nous avons probablement affaire à une seule partie « re-analysée », généralement de type "message/*" (vous pouvez obtenir de telles entités si vous définissez l'option parse_nested_messages(NEST) sur true dans l'analyseur). Dans ce cas, les parties seront imprimées avec des lignes vides comme séparateurs, et tout corps de partie est ignoré :

Content-type: message/rfc822
Content-transfer-encoding: 7bit
[Entité : Partie 0]
[Entité : Partie 1]

Dans tous les cas, lorsque vous imprimez une « partie » de l'entité, cette méthode est appelée récursivement.

Remarque : la sortie n'est très probablement *pas* identique à toute entrée que vous avez analysée pour obtenir cette entité. Si vous construisez un gestionnaire de courrier, il est de votre responsabilité de conserver ces informations.

imprimer_corps [FLUXDE SORTIE]
Méthode d'instance, écraser. Imprime le corps de l'entité dans le flux de sortie OUTSTREAM, ou dans le fichier de sortie actuel s'il n'est pas fourni. OUTSTREAM peut être un fichier ou tout objet qui répond au message print().

Le corps est imprimé pour être inclus dans un flux MIME valide ; cela signifie que le corps sera encodé si l'en-tête l'indique.

Attention : par « corps », on entend « ce qui suit après l'en-tête ». Un corps multipart inclut les représentations imprimées de ses sous-parties.

Attention : le corps est *stocké* sans encodage ; cependant, le but est que l'encodage soit utilisé pour déterminer comment le corps est *imprimé*. Cela signifie que la méthode print() garantit toujours que vous obtenez un flux prêt pour sendmail dont le corps est cohérent avec son en-tête. Si vous souhaitez obtenir le *corps de texte* directement, vous pouvez le lire à partir du descripteur de corps ou utiliser :

$ent->bodyhandle->print($fluxdesortie);

qui utilise des appels read() pour extraire les informations, et fonctionnera donc aussi bien avec les corps texte que binaires.

Attention : veuillez fournir un OUTSTREAM. Cette méthode d'écrasement diffère de celle de Mail::Internet, qui sort sur STDOUT si aucun descripteur de fichier de sortie n'est fourni : cela peut prêter à confusion.

imprimer_en-tête [FLUXDE SORTIE]
Méthode d'instance, héritée. Imprime l'en-tête dans le flux de sortie OUTSTREAM. Vous devez fournir l'OUTSTREAM !
chaîner
Méthode d'instance. Retourne l'entité sous forme de chaîne, exactement comme "imprimer" le ferait. Le corps sera nécessairement encodé et contiendra toutes les sous-parties. Vous pouvez également utiliser as_string().
chaîner_corps
Méthode d'instance. Retourne le corps du message encodé sous forme de chaîne, exactement comme "imprimer_corps" le ferait. Vous pouvez également utiliser body_as_string().

Si vous souhaitez le *corps non encodé*, et que vous travaillez avec un message de seule partie (comme image/gif), vous pouvez le lire à partir du descripteur de corps ou utiliser :

$ent->bodyhandle->print($fluxdesortie);

qui utilise des appels read() pour extraire les informations, et fonctionnera donc aussi bien avec les corps texte que binaires.

NOTES

Sous le capot

Un MIME::Entity est composé des éléments suivants:

  • Un head, qui est une référence à un objet MIME::Head contenant les informations d'en-tête.
  • Un bodyhandle, qui est une référence à un objet MIME::Body contenant les données de corps décodées. Ceci n'est défini que si le message est de type « singlepart »: 
    application/*
audio/*
image/*
text/*
video/*
  • Un tableau de parts, où chaque partie est un objet MIME::Entity. Le nombre de parties ne sera non nul que si le content-type n'est pas l'un des types « singlepart »: 
    message/*        (doit avoir exactement une partie)
multipart/*      (doit avoir une ou plusieurs parties)

Le problème à deux corps

MIME::Entity et Mail::Internet voient les corps des messages différemment, ce qui peut entraîner une certaine confusion et des inconvénients. Bien que je ne puisse pas modifier le comportement de MIME::Entity sans casser beaucoup de code existant, nous allons ouvrir la porte à des questions...

Quelle est la différence entre un « message » et une « entity » ?
Un message est la donnée telle qu'elle est envoyée ou reçue ; généralement, cela signifie un flux de lignes terminées par des sauts de ligne. Une entity est la représentation d'un message sous forme d'objet.

Cela signifie que lorsque vous imprimez une « entity » dans un fichier, vous obtenez un « message » ; et lorsque vous analysez un message depuis un fichier, vous obtenez une « entity ».

Qu'est-ce qu'un corps de message ?
Mail::Internet : La partie du message imprimée après l'en-tête.

MIME::Entity : La partie du message imprimée après l'en-tête.

Comment le corps d'un message est-il stocké dans une entity ?
Mail::Internet : Sous forme de tableau de lignes.

MIME::Entity : Cela dépend du type de contenu du message. Pour les types « container » (« multipart/* », « message/* »), nous stockons les entities contenantes sous forme de tableau de « parts », accessible via la méthode parts(), où chaque partie est un objet MIME::Entity. Pour les types « singlepart » (« text/* », « image/* », etc.), le corps non encodé est référencé par un objet MIME::Body, accessible via la méthode bodyhandle() :

                  bodyhandle()   parts()
Content-type:     renvoie:       renvoie:
------------------------------------------------------------
application/*     MIME::Body     vide
audio/*           MIME::Body     vide
image/*           MIME::Body     vide
message/*         undef          liste MIME::Entity (généralement 1)
multipart/*       undef          liste MIME::Entity (généralement >0)
text/*            MIME::Body     vide
video/*           MIME::Body     vide
x-*/*             MIME::Body     vide

À titre d'exception, « message/* » est actuellement ambigu : selon l'analyseur, un « message/* » peut être traité comme un singlepart avec un MIME::Body et aucune partie. Utilisez bodyhandle() comme dernier recours.

Que renvoie la méthode body() ?
Mail::Internet : Sous forme de tableau de lignes, prêt à être envoyé.

MIME::Entity : Sous forme de tableau de lignes, prêt à être envoyé.

Quelle est la meilleure façon d'obtenir les données du corps ?
Mail::Internet : Utilisez la méthode body().

MIME::Entity : Cela dépend de ce que vous voulez... les données encodées (telles qu'elles sont transportées), ou les données décodées ? Continuez à lire...

Comment obtenir les données du corps encodées ?
Mail::Internet : Utilisez la méthode body().

MIME::Entity : Utilisez la méthode body(). Vous pouvez également utiliser :

$entity->print_body()
$entity->stringify_body()   ### alias $entity->body_as_string()
Comment obtenir les données du corps décodées ?
Mail::Internet : Utilisez la méthode body().

MIME::Entity : Utilisez la méthode bodyhandle() ! Si la méthode bodyhandle() renvoie vrai, alors cette valeur est un MIME::Body qui peut être utilisé pour accéder aux données via la méthode open(). Si la méthode bodyhandle() renvoie une valeur indéfinie, alors l'entity est probablement un « container » qui n'a pas de données de corps réelles (par exemple, un message « multipart ») : dans ce cas, vous devriez accéder aux composants via la méthode parts(). Ainsi, à partir de cela :

if ($bh = $entity->bodyhandle) {
    $io = $bh->open;
    ...accéder aux données décodées via $io->getline ou $io->read...
    $io->close;
}
else {
    foreach my $part (@parts) {
        ...faire quelque chose avec la partie...
    }
}

Vous pouvez également utiliser :

if ($bh = $entity->bodyhandle) {
    $unencoded_data = $bh->as_string;
}
else {
    ...faire quelque chose avec les parties...
}
Que renvoie la méthode body() ?
Mail::Internet : Le corps encodé du message, sous forme de tableau de lignes.

MIME::Entity : Le corps encodé du message, sous forme de tableau de lignes.

Qu'imprime print_body() ?
Mail::Internet : Exactement ce que renvoie body().

MIME::Entity : Exactement ce que renvoie body().

Si j'ai une entity qui peut être à la fois singlepart et multipart. Comment imprimer uniquement le « ce qui suit l'en-tête » ?
Mail::Internet : Utilisez print_body().

MIME::Entity : Utilisez print_body().

Pourquoi MIME::Entity est-il si différent de Mail::Internet ?
Parce que les flux MIME attendent des données non textuelles... potentiellement une quantité considérable de celles-ci, comme un fichier tar.

Parce que les messages MIME peuvent être composés de plusieurs parties, qui peuvent être facilement gérées comme des objets MIME::Entity.

Parce que dans le monde plus simple de Mail::Internet, les données du message et sa représentation imprimée sont identiques... et dans le monde de MIME, ce n'est pas le cas.

Parce qu'analyser des parties de messages MIME à la volée ou formater des parties de messages MIME pour la sortie est une tâche non triviale.

C'est déroutant. Les deux classes peuvent-elles être plus compatibles ?
Pas facilement ; leurs implémentations sont nécessairement assez différentes. Mail::Internet est une méthode simple et efficace pour gérer un message de courrier « boîte noire »... dont vous ne vous souciez pas trop des données internes. MIME::Entity, en revanche, se soucie beaucoup du contenu du message : c'est son travail !

Problèmes de conception

Certaines choses ne peuvent être ignorées
Dans les messages multipart, le « preamble » est la partie qui précède la première délimitation d'encapsulation, et l'« epilogue » est la partie qui suit la dernière délimitation d'encapsulation.

Selon la RFC 2046 :

Il y a apparemment de la place pour des informations supplémentaires avant la première délimitation d'encapsulation et après la dernière. Ces zones doivent généralement être vides et les implémentations doivent ignorer tout ce qui apparaît avant la première ou après la dernière délimitation.
    

    
Dans le monde des normes et de la pratique, c'est la norme. Maintenant, pour la pratique :

    
Certains « MIME » mailers peuvent incorrectement placer une « partie » dans le préambule. Puisque nous devons tout analyser de toute façon, à l'avenir, nous pourrions permettre à l'option de l'analyseur de créer des objets spécialisés MIME::Entity pour le préambule et l'épilogue avec de faux objets MIME::Head.

    
Pour l'instant, même si c'est conforme au MIME, je ne changerai probablement pas la façon dont nous travaillons.
