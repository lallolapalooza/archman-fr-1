NOM

MIME-tools - modules pour l'analyse (et la création !) d'entités MIME

SYNTAXE

Voici un code assez basique pour analyser un message MIME, et écrire ses composants décodés dans un répertoire donné :

use MIME::Parser;
### Créer un analyseur, et définir quelques options d'analyse :
my $parser = new MIME::Parser;
$parser->output_under("$ENV{HOME}/mimemail");
### Analyser l'entrée :
$entity = $parser->parse(\*STDIN) or die "l'analyse a échoué\n";
### Examiner l'entité de niveau supérieur (et les parties qu'elle contient) :
$entity->dump_skeleton;

Voici un code qui compose et envoie un message MIME contenant trois parties : un fichier texte, un GIF attaché, et un peu plus de texte :

use MIME::Entity;
### Créer le niveau supérieur, et configurer les en-têtes d'e-mail :
$top = MIME::Entity->build(Type    =>"multipart/mixed",
                           From    => "moi\@monhost.com",
                           To      => "toi\@tonhost.com",
                           Subject => "Bonjour, infirmière !");
### Partie n°1 : un simple document texte :
$top->attach(Path=>"./testin/short.txt");
### Partie n°2 : un fichier GIF :
$top->attach(Path        => "./docs/mime-sm.gif",
             Type        => "image/gif",
             Encoding    => "base64");
### Partie n°3 : du texte littéral :
$top->attach(Data=>$message);
### L'envoyer :
open MAIL, "| /usr/lib/sendmail -t -oi -oem" or die "open: $!";
$top->print(\*MAIL);
close MAIL;

Pour plus d'exemples, regardez les scripts dans le répertoire examples de la distribution MIME-tools.

DESCRIPTION

MIME-tools est une collection de modules Perl5 MIME:: pour analyser, décoder, et générer des messages MIME simples ou multipart (même imbriqués). (Oui, mes petits, cela signifie que vous pouvez envoyer des messages avec des fichiers GIF attachés).

EXIGENCES

Vous devrez avoir les éléments suivants installés sur votre système :

File::Path
File::Spec
IPC::Open2              (facultatif)
MIME::Base64
MIME::QuotedPrint
Net::SMTP
Mail::Internet, ...     de la distribution MailTools.

Consultez le Makefile.PL dans votre distribution pour la liste la plus complète des modules prérequis et leurs numéros de version.

Pour illustrer, l'analyse fonctionne ainsi :

  • L'« analyseur » analyse le flux MIME. Un analyseur est une instance de "MIME::Parser". Vous lui donnez un flux d'entrée (comme un descripteur de fichier) pour analyser un message : si l'analyse réussit, le résultat est une « entité ».
  • Un message analysé est représenté par une « entité ». Une entité est une instance de "MIME::Entity" (une sous-classe de "Mail::Internet"). Si le message avait des « parties » (par exemple, des pièces jointes), alors ces parties sont aussi des « entités », contenues dans l'entité de niveau supérieur. Chaque entité a une « tête » et un « corps ».
  • La « tête » de l'entité contient des informations sur le message. Une « tête » est une instance de "MIME::Head" (une sous-classe de "Mail::Header"). Elle contient des informations de l'en-tête du message : type de contenu, expéditeur, ligne d'objet, etc.
  • Le « corps » de l'entité sait où se trouvent les données du message. Vous pouvez demander à « ouvrir » cette source de données pour la *lecture* ou l'*écriture*, et vous obtiendrez un « descripteur d'E/S ».
  • Vous pouvez ouvrir() un « corps » et obtenir un « descripteur d'E/S » pour lire/écrire les données du message. Ce descripteur est un objet qui est essentiellement comme un IO::Handle... il peut être de n'importe quelle classe, tant qu'il supporte un petit ensemble standard de méthodes pour lire ou écrire depuis la source de données sous-jacente.

Un message multipart typique contenant deux parties - une salutation textuelle et un fichier GIF « attaché » - serait un arbre d'objets MIME::Entity, chacun ayant sa propre MIME::Head. Comme ceci :

.--------.
| MIME:: | Content-type: multipart/mixed
| Entity | Subject: Joyeux Samhain !
`--------'
     |
     `----.
    parts |
          |   .--------.
          |---| MIME:: | Content-type: text/plain; charset=us-ascii
          |   | Entity | Content-transfer-encoding: 7bit
          |   `--------'
          |   .--------.
          |---| MIME:: | Content-type: image/gif
              | Entity | Content-transfer-encoding: base64
              `--------' Content-disposition: inline;
                           filename="hs.gif"

Analyse des messages

Vous commencez généralement par créer une instance de MIME::Parser et en définissant certains paramètres d'analyse : quel répertoire pour enregistrer les fichiers extraits, comment nommer les fichiers, etc.

Vous donnez ensuite à cette instance un descripteur de fichier lisible sur lequel se trouve un message MIME. Si tout se passe bien, vous obtiendrez un objet MIME::Entity (une sous-classe de Mail::Internet), qui se compose de...

  • Une MIME::Head (une sous-classe de Mail::Header) qui contient les données d'en-tête MIME.
  • Un MIME::Body, qui est un objet qui sait où se trouvent les données du corps. Vous demandez à cet objet de s'« ouvrir » pour la lecture, et il vous donnera un « descripteur d'E/S » pour lire les données : cela pourrait être de n'importe quelle classe, tant qu'il est conforme à un sous-ensemble de l'interface IO::Handle.

Si le message original était un document multipart, l'objet MIME::Entity aura une liste non vide de « parties », chacune étant à son tour une MIME::Entity (qui pourrait également être une entité multipart, etc., etc...).

En interne, l'analyseur (dans MIME::Parser) demande des instances de MIME::Decoder chaque fois qu'il a besoin de décoder un fichier codé. MIME::Decoder a une correspondance entre les codages supportés (par exemple, 'base64') et les classes dont les instances peuvent les décoder. Vous pouvez ajouter à cette correspondance pour essayer de nouveaux codages/expérimentaux. Vous pouvez également utiliser MIME::Decoder par vous-même.

Composition des messages

Toute la composition des messages se fait via la classe MIME::Entity. Pour les messages à partie unique, vous pouvez utiliser le constructeur MIME::Entity/build pour créer très facilement des entités MIME.

Pour les messages multipart, vous pouvez commencer par créer une entité "multipart" de niveau supérieur avec MIME::Entity::build(), puis utiliser la méthode similaire MIME::Entity::attach() pour attacher des parties à ce message. Veuillez noter : ce que la plupart des gens considèrent comme « un message texte avec un fichier GIF attaché » est *réellement* un message multipart avec 2 parties : la première étant le message texte, et la seconde le fichier GIF.

Lors de la construction d'une entité MIME, vous devrez pro

vide deux informations très importantes : le type de contenu et le codage de transfert de contenu. Le type est généralement facile à déterminer, car il est directement lié au format du fichier ; par exemple, un fichier HTML est "text/html". Le codage, cependant, est plus délicat... par exemple, certains fichiers HTML sont conformes au codage "7bit", mais d'autres peuvent avoir des lignes très longues et nécessiteraient d'être envoyés en "quoted-printable" pour assurer la fiabilité.

Consultez la section sur le codage/décodage pour plus de détails, ainsi que le "MANUEL MIME" ci-dessous.

Envoi d'e-mails

Étant donné que MIME::Entity hérite directement de Mail::Internet, vous pouvez utiliser les mécanismes normaux de Mail::Internet pour envoyer des e-mails. Par exemple :

$entity->smtpsend;

Support de codage/décodage

La classe MIME::Decoder peut également être utilisée pour *encoder* ; cela se fait lors de l'impression des entités MIME. Tous les codages standard sont pris en charge (voir "MANUEL MIME" ci-dessous pour les détails) :

Encodage :       | Normalement utilisé lorsque le contenu du message est :
-------------------------------------------------------------------
7bit             | Données 7 bits avec moins de 1000 caractères/ligne, ou multipart.
8bit             | Données 8 bits avec moins de 1000 caractères/ligne.
binary           | Données 8 bits avec des lignes longues (ou pas de sauts de ligne).
quoted-printable | Fichiers texte avec des caractères 8 bits (par ex., texte Latin-1).
base64           | Fichiers binaires.

Le choix de l'encodage pour un document donné dépend largement (1) de ce que vous savez du contenu du document (texte ou binaire) et (2) si vous avez besoin que le message résultant ait un encodage fiable pour le transport d'e-mails Internet 7 bits.

En général, seuls "quoted-printable" et "base64" garantissent un transport fiable de toutes les données ; les trois autres codages "sans encodage" transmettent simplement les données, et ne sont fiables que si ces données sont en ASCII 7 bits avec moins de 1000 caractères par ligne, et n'entrent pas en conflit avec les délimiteurs multipart.

J'ai envisagé de faire en sorte que le type de contenu et l'encodage puissent être déduits automatiquement du chemin du fichier, mais cela semble être une source de problèmes... ou du moins, une source de problèmes pour Mail::Cap...

Journalisation des messages

MIME-tools est une boîte à outils vaste et complexe qui tente de traiter une grande variété d'entrées externes. Il est parfois utile de voir ce qui se passe réellement en coulisses. Il existe plusieurs types de messages enregistrés par la boîte à outils elle-même :

Messages de débogage
Ceux-ci sont imprimés directement sur STDERR, avec le préfixe "MIME-tools: debug".

Les messages de débogage ne sont enregistrés que si vous avez activé le "débogage" dans la configuration de MIME::Tools.

Messages d'avertissement
Ceux-ci sont enregistrés par le mécanisme standard Perl warn() pour indiquer une situation inhabituelle. Ils ont tous le préfixe "MIME-tools: warning".

Les messages d'avertissement ne sont enregistrés que si $^W est défini sur vrai et que MIME::Tools n'est pas configuré pour être "silencieux".

Messages d'erreur
Ceux-ci sont enregistrés par le mécanisme standard Perl warn() pour indiquer qu'un problème s'est réellement produit. Ils ont tous le préfixe "MIME-tools: error".

Les messages d'erreur ne sont enregistrés que si $^W est défini sur vrai et que MIME::Tools n'est pas configuré pour être "silencieux".

Messages d'utilisation
Contrairement aux avertissements "typiques" ci-dessus, qui signalent des problèmes de traitement des données, les avertissements d'utilisation servent à alerter les développeurs sur les méthodes obsolètes et les invocations suspectes.

Les messages d'utilisation ne sont actuellement enregistrés que si $^W est défini sur vrai et que MIME::Tools n'est pas configuré pour être "silencieux".

Lorsqu'un MIME::Parser (ou l'une de ses classes auxiliaires internes) souhaite signaler un message, il le fait généralement en enregistrant le message dans l'objet MIME::Parser::Results juste avant d'appeler la fonction appropriée ci-dessus. Cela signifie que chaque exécution d'analyse a son propre journal de traces qui peut être examiné pour détecter les problèmes.

Configuration de la boîte à outils

Si vous souhaitez ajuster le fonctionnement de cette boîte à outils (par exemple, pour activer le débogage), utilisez les routines du module MIME::Tools.

débogage
Active ou désactive le débogage. Par défaut, c'est faux (désactivé). 
MIME::Tools->debugging(1);
silencieux
Active ou désactive la notification des messages d'avertissement/erreur. Par défaut, c'est vrai, ce qui signifie que ces messages sont supprimés. 
MIME::Tools->quiet(1);
version
Retourne la version de la boîte à outils. 
print MIME::Tools->version, "\n";

CHOSES À FAIRE

Jetez un œil aux exemples

La distribution MIME-Tools est livrée avec un répertoire "examples". Les scripts qui s'y trouvent sont assez sommairement conçus, mais ils vous donneront quelques idées sur la façon d'utiliser l'analyseur.

Exécutez avec les avertissements activés

Exécutez *toujours* votre script Perl avec "-w". Si vous voyez un avertissement concernant une méthode obsolète, modifiez votre code dès que possible. Cela facilitera énormément les mises à niveau.

Évitez les encodages non standard

N'essayez pas d'encoder au format MIME en utilisant les encodages MIME non standard. Ce n'est tout simplement pas une bonne pratique si vous voulez que les gens puissent lire vos messages.

Prévoyez les exceptions levées

Par exemple, si votre code de traitement des e-mails ne doit absolument pas planter, alors effectuez l'analyse MIME comme suit :

$entity = eval { $parser->parse(\*INPUT) };

L'analyse est un processus complexe, et certains composants peuvent lever des exceptions en cas de problèmes graves. Comme ce qui est "grave" est subjectif, il est préférable de *capturer* les exceptions possibles plutôt que de me demander de propager "undef" dans la pile. L'utilisation d'exceptions dans les modules réutilisables est une de ces questions religieuses sur lesquelles nous ne serons jamais tous d'accord ; heureusement, c'est pour cela que "eval{}" est utile.

Vérifiez les résultats de l'analyse pour les avertissements/erreurs

À partir de la version 5.3xx, l'analyseur s'efforce de vous fournir une MIME::Entity. En cas de problème, il enregistre des avertissements/erreurs dans l'objet "résultats" sous-jacent (voir MIME::Parser::Results). Examinez cet objet après chaque analyse. Imprimez les avertissements et les erreurs, *surtout* si les messages ne s'analysent pas comme vous le pensiez.

Ne prévoyez pas d'imprimer exactement ce que vous avez analysé !

L'analyse est une opération (légèrement) avec perte. En raison d'éléments tels que les ambiguïtés dans le codage base64, ce qui suit ne va *pas* restituer son entrée inchangée dans tous les cas :

$entity = $parser->parse(\*STDIN);
$entity->print(\*STDOUT);

Si vous utilisez MIME::Tools pour traiter des e-mails, n'oubliez pas de sauvegarder les données que vous analysez si vous souhaitez les renvoyer inchangées. Ceci est vital pour des choses comme les e-mails signés PGP.

Comprenez comment les caractères internationaux sont représentés

La norme MIME permet aux chaînes de texte dans les en-têtes de contenir des caractères de n'importe quel jeu de caractères, en utilisant des séquences spéciales qui ressemblent à ceci :

=?ISO-8859-1?Q?Keld_J=F8rn_Simonsen?=

Pour être cohérent avec les classes Mail::Field existantes, MIME::Tools ne décode *pas* automatiquement ces chaînes, car le faire perdrait l'information du jeu de caractères et interférerait avec l'analyse des champs (voir "decode_headers" dans MIME::Parser pour une explication complète). Cela signifie que vous devez être prêt à gérer ces chaînes encodées.

La question la plus fréquente alors est : **comment décoder ces chaînes encodées ?** La réponse dépend de ce que vous voulez décoder : ASCII, Latin1, UTF-8, etc. Soyez conscient que votre représentation "cible" peut ne pas prendre en charge tous les jeux de caractères possibles que vous pourriez rencontrer ; par exemple, Latin1 (ISO-8859-1) n'a aucun moyen de représenter les caractères Big5 (chinois). Une pratique courante consiste à représenter les caractères "non traduisibles" par des "?", ou à les ignorer complètement.

Pour décoder les chaînes dans certaines des représentations d'octets occidentales les plus courantes (par exemple, Latin1, Latin2, etc.), vous pouvez utiliser les décodeurs de MIME::WordDecoder (voir MIME::WordDecoder). Le moyen le plus simple est d'utiliser unmime(), une fonction enveloppant votre décodeur "par défaut", comme suit :

use MIME::WordDecoder;
...
$subject = unmime $entity->head->get('subject');

Un endroit où cela est fait automatiquement est lors de l'extraction du nom de fichier recommandé pour une partie lors de l'analyse. C'est pourquoi vous devriez commencer par configurer le meilleur décodeur "par défaut" si la cible par défaut de Latin1 ne vous convient pas.

CHOSES QUE JE FAIS ET QUE VOUS DEVRIEZ SAVOIR

JE FAIS CELA QUE VOUS DEVRIEZ SAVOIR

Fuzzing des CRLF et des retours à la ligne en entrée

La RFC 2045 stipule que les flux MIME ont des lignes terminées par CRLF ("\r\n"). Cependant, il est très probable que les gens voudront analyser des flux MIME où chaque ligne se termine par le caractère de retour à la ligne local "\n" à la place.

Une tentative a été faite pour permettre à l'analyseur de gérer à la fois les entrées terminées par CRLF et par retour à la ligne.

Fuzzing des CRLF et des retours à la ligne lors du décodage

Les décodeurs "7bit" et "8bit" décoderont à la fois une séquence de fin de ligne "\n" et une séquence de fin de ligne "\r\n" en un "\n".

Le décodeur "binary" (par défaut si aucun encodage n'est spécifié) sort toujours les choses telles quelles... donc un message MIME avec des CRLF et aucun encodage explicite sera sorti comme un fichier texte qui, sur de nombreux systèmes, aura un ^M gênant à la fin de chaque ligne... mais c'est comme ça que ça doit être.

Fuzzing des CRLF et des retours à la ligne lors de l'encodage/composition

TODO FIXME Tous les encodeurs génèrent actuellement la séquence de fin de ligne comme un "\n", en supposant que l'agent de messagerie local effectuera la conversion du retour à la ligne en CRLF lors de l'envoi du courrier. Cependant, il devrait probablement y avoir une option pour générer CRLF conformément à la RFC 2045.

Incapacité à gérer les délimiteurs multipart avec des retours à la ligne intégrés

Soyons clairs : c'est une pratique perverse, TRÈS PERVERSE. Si votre expéditeur crée des chaînes de délimiteurs multipart qui contiennent des retours à la ligne, donnez-lui un préavis de deux semaines et trouvez-en un autre. Si votre robot de messagerie reçoit du courrier MIME comme ceci, considérez-le comme syntaxiquement incorrect, ce qu'il est.

Ignorer les en-têtes non-header

Les gens aiment donner à l'analyseur des messages bruts directement depuis POP3 ou depuis une boîte aux lettres. Il y a souvent des informations non-header prévisibles devant les vrais headers; par exemple, la ligne initiale "From" dans le message suivant :

From - Wed Mar 22 02:13:18 2000
Return-Path: <eryq@zeegee.com>
Subject: Hello

L'analyseur ignore simplement ces éléments silencieusement. Peut-être qu'il ne devrait pas, mais la plupart des gens semblent vouloir ce comportement.

Fuzzing des préambules multipart vides

Veuillez noter qu'il y a actuellement une ambiguïté dans la façon dont les préambules sont analysés. Les fragments de message suivants les deux sont considérés comme ayant un préambule vide (où "\n" indique un caractère de retour à la ligne) :

Content-type: multipart/mixed; boundary="xyz"\n
Subject: This message (#1) has an empty preamble\n
\n
--xyz\n
...
Content-type: multipart/mixed; boundary="xyz"\n
Subject: This message (#2) also has an empty preamble\n
\n
\n
--xyz\n
...

Dans les deux cas, la première ligne complètement vide (après le "Subject") marque la fin de l'en-tête.

Mais nous devrions clairement ignorer la deuxième ligne vide dans le message #2, car elle remplit le rôle de "la nouvelle ligne qui n'est là que pour s'assurer que le délimiteur est au début d'une ligne". De tels retours à la ligne ne font jamais partie du contenu précédant le délimiteur ; par conséquent, il n'y a pas de contenu de préambule "content" dans le message #2.

Cependant, il semble clair que le message #1 n'a pas non plus de contenu de préambule "content", et n'est en fait qu'une représentation compacte d'un préambule vide.

Utilisation d'un fichier temporaire pendant l'analyse

Pourquoi ne pas tout faire en mémoire ? Bien que la quantité de mémoire disponible sur un système même modeste continue de croître, la taille des pièces jointes continue de croître avec elle. Je voulais m'assurer que même les utilisateurs de petits systèmes puissent traiter le décodage de sons et de fichiers vidéo de plusieurs mégaoctets. Cela signifie ne pas être limité par la mémoire.

Depuis la version 5.3xx publiée, MIME::Parser se débrouille avec un seul fichier temporaire ouvert par analyseur. Ce fichier temporaire fournit une sorte d'espace de travail infini pour traiter la partie du message actuelle. C'est rapide et léger, mais vous devriez le savoir de toute façon.

Pourquoi est-ce que je suppose que les objets MIME sont des objets d'email ?

Achim Bohnet a souligné un jour que les en-têtes MIME ne font que stocker une collection d'attributs, et pourraient donc être représentés par des objets qui n'héritent pas de Mail::Header.

Je suis d'accord en principe, mais la RFC 2045 dit le contraire. Les en-têtes de la RFC 2045 [MIME] sont un sous-ensemble syntaxique des en-têtes de la RFC 822 [email]. Peut-être qu'un meilleur nom pour ces modules aurait été RFC1521:: au lieu de MIME::, mais nous sommes un peu au-delà de ce stade maintenant.

Lorsque j'ai initialement écrit ces modules pour le CPAN, j'ai longuement hésité à savoir s'ils devaient réellement hériter de Mail::Internet (alors à la version 1.17). Grâce à Graham Barr, qui a gracieusement fait évoluer MailTools 1.06 pour qu'il soit plus adapté au MIME, l'unification a été réalisée lors de la sortie de MIME-tools 2.0. Les avantages en termes de réutilisation seuls ont été considérables.

Vous devez analyser (ou créer) du MIME, mais vous n'êtes pas tout à fait au fait des spécificités ? Pas de problème...

Glossaire

Voici quelques définitions adaptées de la RFC 1521 (prédécesseur de la RFC 204[56789] actuelle définissant le MIME) expliquant la terminologie que nous utilisons ; chacune est accompagnée de l'équivalent dans les termes du module MIME ::...

pièce jointe
Une "pièce jointe" est un terme courant pour toute partie d'un message multipart -- sauf, peut-être, pour la première partie, qui transporte normalement un message utilisateur décrivant les pièces jointes qui suivent (par exemple : "Salut mec, voici le fichier GIF que je t'avais promis.").

Dans notre système, une pièce jointe n'est qu'une MIME::Entity sous l'entité de niveau supérieur, probablement l'une de ses parties.

corps
Le "corps" d'une entité est la partie de l'entité qui suit l'en-tête et qui contient le contenu réel du message. Par exemple, si votre message MIME a une pièce jointe de fichier GIF, alors le corps de cette pièce jointe est le fichier GIF codé en base64 lui-même.

Un corps est représenté par une instance de MIME::Body. Vous obtenez le corps d'une entité en lui envoyant un message bodyhandle().

partie du corps
Une des parties du corps d'une /entité multipart. Une partie du corps a un /header et un /body, il est donc logique de parler du corps d'une partie du corps.

Étant donné qu'une partie du corps est juste une sorte d'entité, elle est représentée par une instance de MIME::Entity.

entité
Une "entité" signifie soit un /message, soit une partie de corps. Toutes les entités ont un /header et un /body.

Une entité est représentée par une instance de MIME::Entity. Il existe des méthodes d'instance pour récupérer l'en-tête (un MIME::Head) et le corps (un MIME::Body).

en-tête
C'est la partie supérieure du message MIME, qui contient le "Content-type", "Content-transfer-encoding", etc. Chaque entité MIME a un en-tête, représenté par une instance de MIME::Head. Vous obtenez l'en-tête d'une entité en lui envoyant un message head().
message
Un "message" signifie généralement le message complet (ou "de niveau supérieur") transféré sur un réseau.

Il n'existe actuellement pas de package explicite pour les "messages" ; sous MIME::, les messages sont des flux de données qui peuvent être lus à partir de fichiers ou de descripteurs de fichiers. Vous pouvez considérer que le MIME::Entity retourné par le MIME::Parser représente le message complet.

Types de contenu

Cela indique quel type de données se trouve dans le message MIME, généralement sous la forme type majeur/type mineur. Les types majeurs standard sont présentés ci-dessous. Une liste plus complète peut être trouvée dans la RFC-2046.

application
Données qui ne rentrent dans aucune autre catégorie, en particulier les données destinées à être traitées par un type de programme d'application. "application/octet-stream", "application/gzip", "application/postscript"...
audio
Données audio. "audio/basic"...
image
Données graphiques. "image/gif", "image/jpeg"...
message
Un message, généralement un autre message email ou MIME. "message/rfc822"...
multipart
Un message contenant d'autres messages. "multipart/mixed", "multipart/alternative"...
texte
Données textuelles, destinées à être lues par des humains. "text/plain", "text/html"...
vidéo

NAME

MIME::Tools - A collection of modules for manipulating MIME messages.

SYNOPSIS

    use MIME::Parser;
    my $parser = new MIME::Parser;
    my $message = $parser->parse_data($mime_data);
    # or
    my $message = $parser->parse_open(\*STDIN);
    # or
    my $message = $parser->parse_file("message.txt");

    # ... do something with the message ...

    use MIME::Entity;
    my $entity = MIME::Entity->build(
        From     => 'user@host.com',
        To       => 'friend@host.org',
        Subject  => 'A test message',
        Comment  => 'This is a test message',
        Type     => 'text/plain',
        Bodyfile => 'some_file.txt',
    );
    $entity->print(\*STDOUT);

    # ... or read an existing entity and modify it ...
    my $entity = MIME::Entity->build( 'file' => 'old_message.txt');
    $entity->prune("message/partial");
    $entity->replace_header('X-Mailer' => 'MIME::Tools');
    $entity->update_mime_header();
    $entity->print(\*STDOUT);

DESCRIPTION

MIME::Tools is a collection of Perl modules that help you parse and create MIME (Multipurpose Internet Mail Extensions) messages. MIME is defined in RFCs 2045-2049 and is the standard way of encoding non-ASCII text and arbitrary binary data in email. It is also used by many other Internet protocols.

The modules are designed to be used by other programs, but they also provide a simple command-line interface for converting between various formats.

The modules are:

MIME::Entity
This is the primary object. It represents a MIME message or part. A MIME message can be a simple text document or a complex multipart message containing text, images, audio, video, and other files.
MIME::Head
Represents the header section of a MIME message or part. Allows access to the various header fields.
MIME::Body
Represents the body section of a MIME message or part. The body can be plain text or encoded (e.g., base64, quoted-printable).
MIME::Parser
The main entry point for parsing MIME messages. It takes raw MIME data (from a file, a string, or a filehandle) and turns it into a MIME::Entity object.
MIME::Decoder
A base class for various content transfer encoding decoders. Specific decoders (like MIME::Base64, MIME::QuotedPrint) inherit from this.
MIME::Encoder
A base class for various content transfer encoding encoders. Specific encoders (like MIME::Base64, MIME::QuotedPrint) inherit from this.
MIME::Type
Provides a way to determine and manipulate MIME types.

It also requires the following modules:

MIME::Base64
Provided with Perl 5.003+.
Mail::Header

Mail::Internet
From the MailTools package.

A QUICK TOUR

The MIME::Parser module is the primary way to read MIME messages. You create a parser object and tell it where to find the message data. The parser returns a MIME::Entity object representing the entire message.

You can then traverse the MIME::Entity object, which represents a tree structure. Each node in the tree is either a simple MIME part (a leaf node) or a multipart entity (an internal node). You can access the headers and body of each part, and you can iterate over the children of a multipart entity.

The MIME::Entity module provides methods for creating new MIME messages, modifying existing ones, and printing them out.

THINGS YOU SHOULD DO

Use MIME::Parser to parse incoming MIME messages.

Use MIME::Entity to create outgoing MIME messages.

Use the type() method to determine the MIME type of a part, and subparts() to iterate over the children of a multipart part.

Use the head() method to get the header object, and the body() method to get the body object.

Use the decode() method of a MIME::Body object to get the decoded content.

THINGS I DO THAT YOU SHOULD KNOW ABOUT

I try to automatically determine the correct MIME type for files when you create them.

I use the quoted-printable encoding by default for text messages, because it's more readable than base64.

I will automatically encode attachments using base64.

I will try to make a multipart/alternative message if you give me both plain text and HTML versions of a message.

I try to be smart about line endings, but I can't always get it right.

A MIME PRIMER

MIME is a standard for encoding non-ASCII data in email. It defines several things:

MIME Types
These specify the type of data in a message part. For example, "text/plain", "image/gif", "video/mpeg".

Content transfer encodings

This is how the message body is packaged up for safe transit. There are the 5 major MIME encodings. A more-comprehensive listing may be found in RFC-2045.

7bit
No encoding is done at all. This label simply asserts that no 8-bit characters are present, and that lines do not exceed 1000 characters in length (including the CRLF).
8bit
No encoding is done at all. This label simply asserts that the message might contain 8-bit characters, and that lines do not exceed 1000 characters in length (including the CRLF).
binary
No encoding is done at all. This label simply asserts that the message might contain 8-bit characters, and that lines may exceed 1000 characters in length. Such messages are the least likely to get through mail gateways.
base64
A standard encoding, which maps arbitrary binary data to the 7bit domain. Like "uuencode", but very well-defined. This is how you should send essentially binary information (tar files, GIFs, JPEGs, etc.).
quoted-printable
A standard encoding, which maps arbitrary line-oriented data to the 7bit domain. Useful for encoding messages which are textual in nature, yet which contain non-ASCII characters (e.g., Latin-1, Latin-2, or any other 8-bit alphabet).

SEE ALSO

MIME::Parser, MIME::Head, MIME::Body, MIME::Entity, MIME::Decoder, Mail::Header, Mail::Internet

The MIME format is documented in RFCs 1521-1522, and more recently in RFCs 2045-2049.

The MIME header format is an outgrowth of the mail header format documented in RFC 822.
