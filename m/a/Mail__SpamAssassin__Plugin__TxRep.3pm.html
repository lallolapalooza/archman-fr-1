NOM

Mail::SpamAssassin::Plugin::TxRep - Normaliser les scores de spam en fonction des enregistrements de réputation de l'expéditeur

SYNTAXE

Le plugin TxRep (Réputation) est conçu comme un remplacement amélioré du plugin AWL (AutoWelcomeList). Ce plugin ajuste le score final d'un message de spam en recherchant et en prenant en compte la réputation de l'expéditeur.

Pour tester TxRep, vous devez d'abord désactiver le plugin AWL (s'il est actif) et copier sa base de données. AWL est chargé dans v310.pre et peut être désactivé en commentant la ligne :

# loadplugin   Mail::SpamAssassin::Plugin::AWL

Lorsque AWL n'est pas désactivé, TxRep ne peut pas s'exécuter.

TxRep doit être activé en commentant la ligne suivante dans v341.pre :

loadplugin   Mail::SpamAssassin::Plugin::TxRep

Utilisez le fichier de configuration fourni 60_txreputation.cf ou ajoutez ces lignes à un fichier .cf :

header         TXREP   eval:check_senders_reputation()
describe       TXREP   Score normalisé basé sur la réputation de l'expéditeur
tflags         TXREP   userconf noautolearn
priority       TXREP   1000

DESCRIPTION

Ce plugin est conçu pour remplacer l'ancien plugin AWL - AutoWelcomeList. Bien que le concept et la portée soient différents, le but est le même : normaliser les scores de spam basés sur l'historique des expéditeurs précédents. Le nom a été intentionnellement changé de « liste blanche » à « réputation » pour éviter toute confusion, car le score de spam peut être ajusté dans les deux sens.

Le plugin TxRep enregistre le score moyen de SpamAssassin pour les expéditeurs. Les expéditeurs sont enregistrés en utilisant plusieurs identifiants ou combinaisons de ceux-ci : l'adresse e-mail de l'expéditeur, l'adresse IP source et/ou un bloc d'adresses IP sources, le nom de domaine de l'expéditeur, la signature DKIM et le nom HELO. TxRep utilise cette moyenne pour réduire la variabilité des scores des messages et modifie le score final vers la moyenne historique. Cela améliore la précision du filtrage des e-mails.

Comparé au plugin AWL d'origine, plusieurs changements conceptuels ont été implémentés dans TxRep :

1. Scoring - Dans AWL, bien qu'il enregistre le nombre de messages reçus de chaque expéditeur, lors du calcul du score correctif pour un nouveau message, il n'en tient pas compte d'une manière ou d'une autre. Par exemple, un expéditeur qui a précédemment envoyé un message ham avec un score de -5, puis un deuxième message avec un score de +10, AWL produira un score correctif qui le rapprochera de -5. Avec le facteur par défaut « auto_welcomelist_factor » de 0.5, le résultat ne serait que de 2.5. Et ce serait exactement le même même si l'expéditeur avait envoyé 1 000 messages avec une moyenne de -5. TxRep tente de tirer le meilleur parti des données collectées, en ajustant le score final non seulement avec le score moyen de réputation stocké dans la base de données, mais aussi en tenant compte du nombre de messages déjà vus de l'expéditeur. Vous pouvez voir la formule exacte dans la section « txrep_factor ».

2. Apprentissage - AWL ignore tout apprentissage de spam/ham. En fait, il agit à l'encontre de celui-ci, ce qui conduit souvent à une situation frustrante, où un utilisateur étiquette à plusieurs reprises tous les messages d'un expéditeur comme spam (resp. ham), mais pour tout nouveau message de l'expéditeur, AWL ajustera le score du message à la moyenne historique, qui n'inclut pas les apprentissages. Ceci a été modifié dans TxRep, et chaque apprentissage de spam/ham est enregistré dans la base de données de réputation, et est donc pris en compte dans les futurs e-mails de l'expéditeur. Voir la section « APPRENTISSAGE SPAM / HAM » pour plus de détails.

3. Auto-apprentissage - dans certaines situations, SpamAssassin peut déclarer un message comme spam ou ham clair, et lancer le processus d'apprentissage automatique, afin que le message puisse être réévalué. AWL, par conception, n'a effectué aucun ajustement d'apprentissage automatique. Ce plugin lira la base de données de réputation en fonction de la valeur définie par « txrep_learn_penalty » ou « txrep_learn_bonus ». Les seuils d'apprentissage automatique peuvent être ajustés, ou l'apprentissage automatique peut être complètement désactivé via la configuration « txrep_autolearn ».

4. Réapprentissage - les messages qui ont été mal appris ou appris automatiquement peuvent être réappris. Les anciennes réputations sont supprimées de la base de données et de nouvelles sont ajoutées à la place. Le réapprentissage fonctionne mieux lorsque le suivi des messages est activé via l'option « txrep_track_messages ». Sans cela, le score réappris est simplement ajouté à la réputation, sans supprimer les anciennes.

5. Ancienneté - avec AWL, tout enregistrement historique d'un expéditeur a le même poids. Cela signifie que les changements de comportement des expéditeurs ou les règles modifiées de SA peuvent prendre beaucoup de temps à être reflétés, ou être pratiquement annulés par la normalisation d'AWL, en particulier pour les expéditeurs ayant un grand nombre de messages historiques et une faible fréquence récente. Cela devient également particulièrement inefficace lorsque l'administrateur détecte de nouveaux modèles dans certains messages et applique de nouvelles règles pour les étiqueter comme spam ou ham. AWL élimine pratiquement l'effet des nouvelles règles en ajustant le score à la moyenne historique (incorrecte). Seul l'ajustement du facteur « auto_welcomelist_factor » à des valeurs plus basses aiderait, mais cela réduirait également l'impact global d'AWL et ferait douter de son objectif. TxRep, en plus de remplacer le facteur « txrep_factor » (remplacement du facteur « auto_welcomelist_factor »), introduit également le facteur « txrep_dilution_factor » pour aider à gérer ce problème progressivement, en réduisant l'impact des enregistrements passés. Plus de détails peuvent être trouvés dans la description du facteur ci-dessous.

6. Liste de blocage et liste de bienvenue - lorsqu'une demande de liste de blocage ou de bienvenue est effectuée via l'API SpamAssassin, AWL ajuste le score total historique du courrier sans IP (et les enregistrements supprimés associés à une IP), mais lors de la réception de nouveaux enregistrements avec IP, ceux-ci sont ajoutés, ce qui fait que l'enregistrement bloqué est désactivé pendant le scan. TxRep utilise toujours l'enregistrement du courrier sans IP ainsi que celui associé à une IP, la signature DKIM ou le SPF pass (sauf si le facteur de réputation EMAIL est défini sur 0). AWL utilise la valeur 100 (resp. -100) pour la liste de blocage (resp. bienvenue). TxRep augmente la valeur proportionnellement au facteur de réputation EMAIL. Il est expliqué en détail dans la section « LISTE DE BIENVENUE » dans LISTE DE BLOCAGE. TxRep peut également bloquer ou accueillir des adresses IP, des noms de domaine et des noms HELO sans point.

7. Identification de l'expéditeur - AWL identifie un expéditeur en fonction de l'adresse e-mail utilisée et de l'adresse IP source (sa partie définie par la configuration du masque est plus précise). Le but principal de cette mesure est d'éviter d'attribuer de faux scores aux espions qui usurpent des adresses e-mail connues. L'inconvénient survient avec les expéditeurs qui envoient depuis des lieux fréquemment changés ou même lorsqu'ils se connectent à des adresses IP dynamiques non définies par le masque. Leur score est difficile, voire parfois impossible, à suivre. Un autre inconvénient est, par exemple, un espion qui envoie continuellement du spam depuis la même adresse IP, mais avec différentes adresses e-mail. AWL ne trouvera pas leurs scores précédents, à moins qu'il n'utilise à nouveau la même adresse e-mail. TxRep utilise plusieurs identifiants et crée des entrées de base de données séparées pour chacun. Il n'enregistre pas seulement les combinaisons adresse e-mail/IP comme dans AWL, mais aussi l'adresse e-mail indépendante (indépendamment de l'adresse IP source), l'adresse IP indépendante (indépendamment de l'adresse e-mail utilisée), le nom de domaine de l'adresse e-mail, la signature DKIM et le nom HELO de la machine connectée. L'influence de chaque identifiant individuel peut être ajustée à l'aide de facteurs de poids décrits dans la section « POIDS DE RÉPUTATION ».

8. Suivi des messages - TxRep (facultativement) assure le suivi des identifiants des messages déjà analysés et appris. Ceci est utile pour éviter de réévaluer le score de réputation en réanalysant ou en réapprenant simplement le même message plusieurs fois. Dans le même temps, cela permet de réapprendre les messages qui ont été mal appris ou de les réapprendre après que les seuils d'apprentissage ou le bonus aient été modifiés. Voir l'option « txrep_track_messages ».

DESCRIPTION

Chaque utilisateur peut avoir des exigences très différentes et recevoir des courriels de types très divers. En particulier, lors de l'utilisation des plugins Bayesian et AWL, l'efficacité est bien meilleure lorsque SpamAssassin apprend le spam et le ham séparément pour chaque utilisateur. Cependant, le désavantage est que les expéditeurs et les courriels déjà appris plusieurs fois par différents utilisateurs devront être réappris sans aucune histoire reconnue, chaque fois qu'ils arrivent à un autre utilisateur. TxRep utilise les avantages des deux systèmes. Il peut utiliser des stockages doubles : le stockage commun global, où tous les courriels traités par SpamAssassin sont enregistrés, et un stockage local séparé pour chaque utilisateur, avec des données de réputation provenant uniquement de ses courriels. Voir plus de détails dans le réglage ""txrep_user2global_ratio"".

10. Welcomelisting sortant - lorsqu'un utilisateur local envoie des messages à une adresse électronique, nous supposons qu'il doit également voir la réponse éventuelle, d'où la nécessité de bien vouloir lister l'adresse du destinataire. Lorsque SpamAssassin est également utilisé pour analyser les courriels sortants, lorsque les utilisateurs locaux utilisent le serveur SMTP où SA est installé pour envoyer des courriels, et lorsque les réseaux internes sont définis, TxREP améliorera la réputation de toutes les adresses 'À' et 'Cc' des messages provenant des réseaux internes. Les détails peuvent être trouvés dans le réglage ""txrep_welcomelist_out"".

Les deux plugins (AWL et TxREP) ne peuvent pas coexister. Il est nécessaire de désactiver l'AWL pour permettre le fonctionnement de TxRep. TxRep réutilise la gestion de la base de données du module AWL d'origine, ainsi que certains de ses paramètres liés aux modules de gestion de base de données. Par défaut, TxRep crée sa propre base de données, mais la liste blanche automatique d'origine peut être réutilisée comme point de départ. La base de données AWL peut être renommée avec le nom défini dans les réglages TxRep, et TxRep commencera à l'utiliser. La base de données de la liste blanche automatique d'origine doit être sauvegardée pour permettre de revenir à l'état d'origine.

Le fichier spamassassin/Plugin/TxRep.pm remplace à la fois spamassassin/Plugin/AWL.pm et spamassassin/AutoWelcomelist.pm. Deux autres fichiers AWL, spamassassin/DBBasedAddrList.pm et spamassassin/SQLBasedAddrList.pm, sont toujours nécessaires.

BALISES DE MODÈLE

Ce module de plugin ajoute les "balises" suivantes qui peuvent être utilisées comme espaces réservés dans certaines options. Voir Mail::SpamAssassin::Conf pour plus d'informations sur les BALISES DE MODÈLE.

_TXREPXXXY_         Modificateur TXREP
_TXREPXXXYMEAN_     Score moyen sur lequel la modification TXREP est basée
_TXREPXXXYCOUNT_    Nombre de messages sur lesquels la modification TXREP est basée
_TXREPXXXYPRESCORE_ Score avant TXREP
_TXREPXXXYUNKNOWN_  Nouvel expéditeur (non trouvé dans la liste TXREP)

La partie XXX de la balise prend la forme de l'un des identifiants suivants, en fonction de la réputation vérifiée : EMAIL, EMAILIP, IP, DOMAIN, ou HELO. L'identifiant suffixe Y est utilisé uniquement dans le cas d'un stockage double et prend la forme de U (pour les réputations du stockage utilisateur) ou G (pour les réputations du stockage global).

PRÉFÉRENCES UTILISATEUR

Les options suivantes peuvent être utilisées dans les fichiers de configuration globaux ("local.cf") et spécifiques à l'utilisateur ("user_prefs") pour personnaliser la façon dont SpamAssassin traite les messages électroniques entrants.

use_txrep
0 | 1                 (par défaut : 0)

Utiliser ou non le système de réputation TxRep. TxRep suit le score moyen à long terme de chaque expéditeur, puis décale le score des nouveaux messages vers cette moyenne à long terme. Cela peut augmenter ou diminuer le score des messages, en fonction du comportement à long terme du correspondant particulier.

Notez que certains tests sont ignorés lors de la détermination du score final du message :

- règles avec tflags défini à 'noautolearn'
txrep_factor
plage [0..1]           (par défaut : 0.5)

Jusqu'où régresser un message vers la moyenne à long terme de l'expéditeur. Essentiellement, l'algorithme consiste à suivre le score total à long terme et le nombre de messages pour l'expéditeur ("total" et "count"), puis une fois que nous avons entièrement calculé le score de ce message ("score"), nous calculons le score final pour le message comme suit :

scorefinal = score + facteur * (total + score)/(compte + 1)

Ainsi, si "facteur" = 0.5, nous nous déplacerons à mi-chemin entre le score calculé et la nouvelle valeur moyenne. Si "facteur" = 0.3, nous nous déplacerons environ d'un tiers du chemin du score vers la moyenne. "facteur" = 1 signifie utiliser la moyenne à long terme, y compris le nouveau score non ajusté ; "facteur" = 0 signifie utiliser uniquement le score calculé, désactivant ainsi la moyenne des scores, tout en enregistrant la réputation dans la base de données.

txrep_dilution_factor
plage [0.7..1.0]               (par défaut : 0.98)

À chaque nouveau courriel d'un expéditeur donné, les enregistrements historiques de réputation sont "dilués", ou "dilués", d'une certaine fraction donnée par ce facteur. Cela signifie que l'influence des anciens enregistrements diminuera progressivement avec chaque nouveau message de l'expéditeur donné. Ceci est important pour permettre une gestion plus flexible des changements dans le comportement de l'expéditeur, ou de nouvelles améliorations ou changements des règles locales de SA.

Sans aucune expiration de dilution (facteur de dilution défini à 1), le score du nouveau message est simplement ajouté au score total de l'expéditeur donné dans la base de données de réputation. Lorsque la dilution est utilisée (facteur < 1), l'impact de la moyenne historique de réputation est réduit par le facteur avant de calculer la nouvelle moyenne, qui à son tour est ensuite utilisée pour ajuster le nouveau score total à stocker dans la base de données.

nouveau_total = (ancien_compte + 1) * (nouveau_score + dilution * ancien_total) / (dilution * ancien_compte + 1)

En d'autres termes, cela signifie que plus un message est ancien, moins son score de spam original a d'impact sur la nouvelle moyenne. Par exemple, si nous définissons le facteur à 0.9 (ce qui signifie une dilution de 10 %), le score du nouveau message sera enregistré à 100 %, le dernier score du même expéditeur à 90 %, l'avant-dernier à 81 % (0.9 * 0.9 = 0.81), et par exemple le 10ème dernier message juste à 35 %.

Sur les systèmes stables, nous recommandons de maintenir le facteur proche de 1 (mais toujours inférieur à 1). Sur les systèmes où l'ajustement des règles de SA et l'apprentissage du spam sont encore en cours, des facteurs plus bas aideront la réputation à s'adapter plus rapidement à toute modification. En même temps, cela réduira également l'impact de la réputation historique.

txrep_learn_penalty
plage [0..200]         (par défaut : 20)

Lorsque SpamAssassin est entraîné pour un message SPAM, le score de pénalité donné sera ajouté au score de réputation total de l'expéditeur, indépendamment du score de spam réel. L'impact de la pénalité sera d'autant plus faible que le nombre de messages que l'expéditeur a déjà dans la base de données TxRep est élevé.

txrep_learn_bonus
plage [0..200]         (par défaut : 20)

Lorsque SpamAssassin est entraîné pour un message HAM, le score de pénalité donné sera déduit du score de réputation total de l'expéditeur, indépendamment du score de spam réel. L'impact de la pénalité sera d'autant plus faible que le nombre de messages que l'expéditeur a déjà dans la base de données TxRep est élevé.

txrep_autolearn
plage [0..5]                   (par défaut : 0)

Lorsque SpamAssassin déclare un message comme spam clair ou ham pendant l'analyse du message, et lance le processus d'auto-apprentissage, les scores de réputation de l'expéditeur du message donné seront ajustés par la valeur de l'option ""txrep_learn_penalty"", resp. le ""txrep_learn_bonus"" de la même manière que lors de l'apprentissage manuel. La valeur 0 de cette option désactive l'ajustement de réputation par auto-apprentissage - seul le score calculé avant l'auto-apprentissage sera stocké dans la base de données de réputation.

txrep_track_messages
0 | 1                 (par défaut : 1)

TxRep doit-il suivre les messages déjà analysés et/ou appris. Lorsque cette option est activée, un enregistrement supplémentaire dans la base de données de réputation sera créé pour éviter les ajustements de score erronés dus à l'analyse répétée du même message, et pour permettre le réapprentissage correct des messages qui ont été précédemment mal appris, ou qui doivent être réappris après modification de la pénalité ou du bonus d'apprentissage.

txrep_welcomelist_out
plage [0..200]         (par défaut : 10)

Précédemment txrep_whitelist_out qui fonctionnera de manière interchangeable jusqu'à la version 4.1.

Lorsque la valeur de ce réglage est supérieure à zéro, les destinataires des messages envoyés depuis les réseaux internes seront mis sur liste blanche en améliorant leur score de réputation total avec le nombre de points définis par ce réglage. Comme l'adresse IP et d'autres identifiants de l'expéditeur ne sont pas connus lors de l'envoi du courriel, seule la réputation du courriel autonome est mise sur liste blanche. Le nom de domaine est intentionnellement également laissé inchangé. La mise sur liste blanche sortante ne peut fonctionner que lorsque SpamAssassin est configuré pour analyser également les courriels sortants, lorsque les utilisateurs locaux utilisent le serveur SMTP pour envoyer des courriels, et lorsque les "internal_networks" sont définis dans la configuration de SpamAssassin. L'amélioration de la réputation se produit à chaque message envoyé depuis les réseaux internes, donc plus il y a de messages envoyés au destinataire, meilleure sera la réputation de son adresse électronique.

LISTE NOIRE / LISTE BLANCHE

Lorsque SpamAssassin est invité à bloquer ou à ajouter un utilisateur à la liste blanche, le plugin TxRep ajoute un score de 100 (pour le blocage) ou -100 (pour la liste blanche) à l'adresse e-mail de l'expéditeur. S'il n'y a pas d'adresse IP, la valeur est multipliée par le ratio du score de réputation total sur le score de réputation de l'e-mail individuel.

poids_total = poids_email + poids_email_ip + poids_domaine + poids_ip + poids_helo
reputation_bloquee = 100 * poids_total / poids_email

Si une adresse e-mail individuelle est bloquée ou ajoutée à la liste blanche, tous les enregistrements de la base de données associés à une adresse e-mail liée à une adresse IP, une signature DKIM ou un SPF réussi sont supprimés. Seul l'enregistrement individuel est conservé.

En plus du blocage ou de l'ajout à la liste blanche d'adresses e-mail individuelles, la même méthode peut être utilisée pour bloquer ou ajouter à la liste blanche des adresses IP, des domaines et des noms HELO (seuls les noms HELO sans point sont autorisés).

Lors de l'ajout d'adresses e-mail ou de domaines à la liste blanche ou noire, vous pouvez les lier à une signature DKIM ou à un enregistrement SPF spécifié, en ajoutant après l'identifiant le domaine de signature ou le tag 'spf' comme suit :

spamassassin --add-addr-to-blocklist=spamming.biz,spf
spamassassin --add-addr-to-welcomelist=friend@good.org,good.org

Lorsqu'un message contient à la fois une signature DKIM et un SPF réussi, la signature DKIM a la priorité, de sorte que l'enregistrement lié au tag 'spf' ne sera pas vérifié. Seules les adresses e-mail et les domaines peuvent être liés à DKIM ou SPF. Les enregistrements d'adresses IP et de noms HELO n'ont pas de DKIM/SPF.

En cas de double stockage, le blocage ou la liste blanche s'effectue uniquement dans le stockage par défaut.

LOGIQUE DE RÉPUTATION

1. L'identifiant le plus significatif est le même que pour AWL, c'est-à-dire la combinaison de l'adresse e-mail et de l'adresse IP source, ou sa partie définie par le paramètre de masque IPv4 ou IPv6.

2. Aucune vérification d'IP n'est effectuée pour la réputation d'e-mail individuelle.

3. Aucune vérification de signature n'est effectuée pour la réputation par IP ou pour la réputation par nom HELO.

4. La pondération de la réputation par e-mail IP, et non la pondération individuelle de la réputation par e-mail seule, est utilisée lorsqu'aucune adresse IP n'est disponible (la réputation par e-mail IP est l'indicateur principal et a le poids le plus élevé).

5. Aucune vérification d'IP n'est effectuée sur les e-mails signés (la signature authentifie l'adresse e-mail plutôt que l'adresse IP).

6. Aucune vérification d'IP n'est effectuée sur un SPF réussi (nous supposons que le propriétaire du domaine est responsable de toutes les adresses IP qu'il autorise à envoyer, c'est pourquoi nous utilisons la signature DKIM/SPF).

APPRENTISSAGE SPAM / HAM

Lorsque SpamAssassin est invité à apprendre (ou réapprendre) un message donné comme spam ou ham, toutes les réputations pertinentes pour le message (email, email_ip, domain, ip, helo) dans les stockages globaux et utilisateur seront mises à jour en utilisant respectivement les valeurs "txrep_learn_penalty" et "rxrep_learn_bonus". La nouvelle réputation d'une propriété d'expéditeur donnée (email, domain,...) sera le résultat respectif de l'une des formules suivantes :

nouvelle_réputation = ancienne_réputation + learn_penalty
nouvelle_réputation = ancienne_réputation - learn_bonus

Le plugin TxRep suit actuellement chaque message individuellement, par conséquent, il ne détecte pas lorsque vous apprenez le message de manière répétée. Il ajoutera/soustraira le score de pénalité/bonus chaque fois que le message sera soumis à l'apprenant de spam.

OPTIMISATION DE TXREP

TxRep peut être optimisé pour la vitesse et la simplicité, ou pour la précision dans l'attribution des scores de réputation.

Tout d'abord, TxRep peut être rapidement désactivé et réactivé via l'option ""use_txrep"". Cela peut être fait globalement, ou individuellement dans les "user_prefs" respectives. Désactiver TxRep ne détruit pas la base de données, il peut donc être réactivé ultérieurement.

Sur de nombreux systèmes, le stockage basé sur SQL peut être plus rapide que le stockage Berkeley DB par défaut, vous devriez donc envisager de le configurer.

Ensuite, plusieurs paramètres peuvent réduire le nombre d'enregistrements stockés dans la base de données, réduisant ainsi la taille du stockage et le temps de traitement :

1. Définir ""txrep_user2global_ratio"" à zéro désactivera le stockage double, divisant ainsi par deux les besoins en espace disque et les temps de traitement de ce plugin.

2. Vous pouvez désactiver toutes les "PONDÉRATIONS DE RÉPUTATION" sauf une. EMAIL_IP est l'option la plus spécifique, c'est donc le choix le plus probable dans ce cas, mais vous pourriez baser le système de réputation sur n'importe lequel des scores restants. Chacune des réputations activées ajoute une nouvelle entrée à la base de données pour chaque nouvel identifiant. Ainsi, par exemple, si le nombre de domaines enregistrés et notés peut être important, le nombre d'adresses IP stockées sera probablement plus élevé et nécessitera plus d'espace de stockage.

3. La désactivation de ""txrep_track_messages"" évite de stocker une entrée séparée pour chaque message analysé, réduisant ainsi également les besoins en espace disque et le temps de traitement.

4. La désactivation de l'option ""txrep_autolearn"" permettra d'économiser du temps de traitement sur les messages qui déclenchent le processus d'apprentissage automatique.

5. La désactivation de ""txrep_welcomelist_out"" réduira le temps de traitement des connexions sortantes.

6. Conserver l'option ""auto_welcomelist_distinguish_signed"" activée peut aider à réduire légèrement la taille de la base de données, car pour les messages signés, l'adresse IP d'origine est ignorée, donc aucune entrée de base de données supplémentaire n'est nécessaire pour chaque adresse IP distincte (respectivement un bloc d'adresses IP masquées).

Étant donné que TxRep réutilise l'architecture de stockage de l'ancien plugin AWL, pour initialiser le stockage SQL, les mêmes instructions s'appliquent également à TxRep. Bien que l'ancienne table AWL puisse être réutilisée pour TxRep, par défaut, TxRep s'attend à ce que la table SQL soit nommée "txrep".

Pour installer une nouvelle table SQL pour TxRep, exécutez le fichier SQL approprié pour votre système dans le répertoire /sql.

Si vous obtenez une erreur de syntaxe sur une version plus ancienne de MySQL, utilisez TYPE=MyISAM au lieu de ENGINE=MyISAM à la fin de la commande. Vous pouvez également utiliser d'autres types d'ENGINE (en fonction de ce qui est disponible sur votre système). Par exemple, le moteur MEMORY stocke toute la table dans la mémoire du serveur, atteignant des performances similaires à celles de Redis. Vous devrez vous soucier de la réplication de la table RAM sur disque via un cronjob, pour éviter la perte de données au redémarrage. Le moteur InnoDB est utilisé par défaut, offrant une grande évolutivité (taille de la base de données et concurrence des accès). En conjonction avec une valeur élevée de innodb_buffer_pool ou avec le plugin memcached (MySQL v5.6+), il peut également offrir des performances comparables à celles de Redis.
