NOM

Mail::SpamAssassin::Plugin::SPF - effectue des tests de vérification SPF

SYNOPIS

loadplugin     Mail::SpamAssassin::Plugin::SPF

DESCRIPTION

Ce plugin vérifie un message par rapport aux enregistrements Sender Policy Framework (SPF) publiés par les propriétaires de domaine dans le DNS pour lutter contre la falsification d'adresses e-mail et faciliter l'identification des spams.

Il est recommandé d'utiliser un filtre MTA (pypolicyd-spf / spf-engine etc), de sorte que ce plugin puisse réutiliser les résultats des en-têtes Received-SPF et/ou Authentication-Results tels quels. Sinon, le débit pourrait en pâtir, les recherches DNS effectuées par ce plugin ne sont pas asynchrones. Ces en-têtes aideront également lorsque SpamAssassin ne parviendra pas à détecter correctement EnvelopeFrom.

PARAMÈTRES UTILISATEUR

welcomelist_from_spf user@example.com
Précédemment whitelist_from_spf qui fonctionnera de manière interchangeable jusqu'à la version 4.1.

Fonctionne de manière similaire à welcomelist_from, sauf qu'en plus de faire correspondre une adresse d'expéditeur, une vérification des enregistrements SPF du domaine doit réussir. Le premier paramètre est une adresse à inclure dans la liste d'accueil, et le second est une chaîne de caractères correspondant au rDNS du relais.

Comme welcomelist_from, plusieurs adresses par ligne, séparées par des espaces, sont acceptées. Plusieurs lignes "welcomelist_from_spf" sont également acceptées.

Les en-têtes vérifiés pour les adresses welcomelist_from_spf sont les mêmes que ceux utilisés pour les vérifications SPF (Envelope-From, Return-Path, X-Envelope-From, etc.).

Puisque cette liste d'accueil nécessite une vérification SPF, les tests réseau doivent être activés. Il est également requis que votre chemin de confiance soit correctement configuré. Voir la section sur "trusted_networks" pour plus d'informations sur les chemins de confiance.

ex:

welcomelist_from_spf joe@example.com fred@example.com
welcomelist_from_spf *@example.com
def_welcomelist_from_spf user@example.com
Précédemment def_whitelist_from_spf qui fonctionnera de manière interchangeable jusqu'à la version 4.1.

Identique à "welcomelist_from_spf", mais utilisé pour les entrées de liste d'accueil par défaut dans la distribution SpamAssassin. Le score de la liste d'accueil est plus bas, car elles sont souvent la cible de spoofing par les spammeurs.

unwelcomelist_from_spf user@example.com
Précédemment unwhitelist_from_spf qui fonctionnera de manière interchangeable jusqu'à la version 4.1.

Utilisé pour supprimer une entrée "welcomelist_from_spf" ou "def_welcomelist_from_spf". L'adresse e-mail spécifiée doit correspondre exactement à l'adresse utilisée précédemment.

Utile pour supprimer des entrées par défaut indésirables d'une configuration distribuée par une configuration locale ou spécifique au site ou par "user_prefs".

PARAMÈTRES ADMINISTRATEUR

spf_timeout n (par défaut: 5)
Combien de secondes attendre pour qu'une requête SPF se termine, avant que l'analyse ne continue sans le résultat SPF. Une valeur numérique est éventuellement suffixée par une unité de temps (s, m, h, d, w, indiquant secondes (par défaut), minutes, heures, jours, semaines).
ignore_received_spf_header (0|1) (par défaut: 0)
Par défaut, pour éviter les recherches DNS inutiles, le plugin essaiera d'utiliser les résultats SPF trouvés dans tous les en-têtes "Received-SPF" qu'il trouve dans le message et qui n'auraient pu être ajoutés que par un relais interne.

Définissez cette option à 1 pour ignorer tous les en-têtes "Received-SPF" présents et pour que le plugin effectue lui-même la vérification SPF.

Notez que sauf si le plugin trouve un "identity=helo", ou une identité non prise en charge, il supposera que le résultat est un résultat de vérification SPF mfrom. Les seules identités prises en charge sont "mfrom", "mailfrom" et "helo".

use_newest_received_spf_header (0|1) (par défaut: 0)
Par défaut, lors de l'utilisation des en-têtes "Received-SPF", le plugin tentera d'utiliser les en-têtes "Received-SPF" les plus anciens (tout en bas) ajoutés par les relais internes, qu'il peut analyser, car ils sont les plus susceptibles d'être exacts. Ceci est fait de sorte que si vous avez une configuration de courrier entrant où l'un de vos MX principaux ne connaît pas un MX secondaire (ou vos MX ne connaissent pas une sorte de relais de transfert que SA considère comme fiable+interne) mais que SA est conscient de la frontière de domaine réelle (paramètre internal_networks) SA utilisera les résultats les plus précis.

Utilisez cette option pour commencer avec les en-têtes "Received-SPF" les plus récents (tout en haut), en descendant jusqu'à ce que les résultats soient analysés avec succès.

has_check_for_spf_errors
Ajoute une vérification de capacité pour "if can()" pour check_for_spf_permerror, check_for_spf_temperror, check_for_spf_helo_permerror et check_for_spf_helo_permerror
has_check_spf_skipped_noenvfrom
Ajoute une vérification de capacité pour "if can()" pour check_spf_skipped_noenvfrom
check_spf_skipped_noenvfrom
Vérifie si les vérifications SPF ont été ignorées parce que EnvelopeFrom ne peut pas être déterminé.
