NOM

Mail::SpamAssassin::Plugin - Classe de base des plugins SpamAssassin

SYNOPIS

Configuration SpamAssassin :

loadplugin MonPlugin /chemin/vers/monplugin.pm

Code Perl :

package MyPlugin;
use Mail::SpamAssassin::Plugin;
our @ISA = qw(Mail::SpamAssassin::Plugin);
sub new {
  my ($class, $mailsa) = @_;
  # le boilerplate habituel d'objet perl pour créer un objet sous-classe
  $class = ref($class) || $class;
  my $self = $class->SUPER::new($mailsa);
  bless ($self, $class);
  # puis enregistrer une règle d'évaluation, si désiré...
  $self->register_eval_rule ("check_for_foo");
  # et retourner le nouvel objet plugin
  return $self;
}
...méthodes...
1;

DESCRIPTION

Ceci est la classe de base pour les plugins SpamAssassin ; tous les plugins doivent être des objets implémentant cette classe.

Cette classe fournit des méthodes stub sans opération pour tous les callbacks qu'un plugin peut recevoir. On s'attend à ce que votre plugin remplace une ou plusieurs de ces stubs pour effectuer ses actions.

SpamAssassin implémente une chaîne de plugins ; chaque événement de callback est passé séquentiellement à chacun des objets plugin enregistrés. Tout plugin peut appeler "$self->inhibit_further_callbacks()" pour bloquer la livraison de cet événement aux plugins suivants dans la chaîne. Ceci est utile si le plugin a géré l'événement, et qu'il ne sera plus nécessaire pour les plugins ultérieurs de le traiter.

Si vous cherchez à écrire une simple règle d'évaluation, passez directement à register_eval_rule(), ci-dessous.

INTERFACE

Dans toutes les APIs de plugin ci-dessous, "options" fait référence à une référence vers une table de hachage contenant des paires nom-valeur. Ceci est utilisé pour garantir la compatibilité future, en ce sens que nous pouvons ajouter de nouvelles options à l'avenir sans affecter les objets construits selon une version antérieure de l'API.

Par exemple, voici comment imprimer l'élément "line" dans une méthode parse_config() :

sub parse_config {
  my ($self, $opts) = @_;
  print "MonPlugin: parse_config a reçu ".$opts->{line}."\n";
}

MÉTHODES

Les méthodes suivantes peuvent être remplacées par les sous-classes pour gérer les événements.

$plugin = MyPluginClass->new ($objet_mailsa)
Constructeur. Les plugins qui doivent s'enregistrer eux-mêmes devront définir leur propre constructeur ; le constructeur par défaut de la classe parente fonctionnera bien pour les plugins qui remplacent simplement une méthode.

Notez que les sous-classes doivent fournir le $objet_mailsa au constructeur de la classe parente, comme ceci :

my $self = $class->SUPER::new($objet_mailsa);

Note sur le cycle de vie : les plugins qui auront besoin de stocker un état par scan ne devraient pas le stocker sur l'objet Plugin ; il devrait plutôt être stocké sur l'objet PerMsgStatus, voir check_start() ci-dessous. Il est également recommandé de stocker les paramètres de configuration sur l'objet Conf ; voir parse_config().

$plugin->parse_config ( { options ... } )
Analyse une ligne de configuration qui n'a pas encore été traitée. "options" est une référence vers une table de hachage contenant ces options :
line
La ligne de texte de configuration à analyser. Les espaces blancs en début et fin, ainsi que les commentaires, sont supprimés.
key
La clé de configuration ; c'est-à-dire le premier "mot" de la ligne.
value
La valeur de configuration ; tout ce qui suit le premier "mot" et les espaces blancs qui le suivent.
conf
L'objet "Mail::SpamAssassin::Conf" sur lequel les données de configuration doivent être stockées.
user_config
Un booléen : 1 si on lit la configuration d'un utilisateur, 0 si on lit les fichiers de configuration système.

Si la ligne de configuration était un paramètre géré par ce plugin, l'implémentation de la méthode devrait appeler "$self->inhibit_further_callbacks()".

Si le paramètre n'est pas géré par ce plugin, la méthode devrait retourner 0 afin qu'un plugin ultérieur puisse le gérer, ou afin que SpamAssassin puisse afficher un message d'avertissement à l'utilisateur si aucun plugin ne le comprend.

Note sur le cycle de vie : il est suggéré de stocker la configuration sur l'objet "Mail::SpamAssassin::Conf" utilisé, plutôt que sur l'objet plugin lui-même. Celui-ci peut être trouvé comme "$plugin->{main}->{conf}", ou comme "conf" dans la référence de table de hachage $options ci-dessus. En le stockant sur "conf", cela permet de gérer correctement la priorité de la configuration par utilisateur et globale.

$plugin->bayes_learn ( { options ... } )
Appelé à la fin d'une opération d'apprentissage bayésien.

Cette phase est le meilleur endroit pour mapper la valeur brute (originale) du jeton à la valeur hachée SHA1.

toksref
Référence au hash retourné par l'appel à tokenize. Le hash a le format suivant : 
{
  'Valeur de hachage SHA1' => 'valeur brute (originale)',
  ...
}

NOTE : Cette structure de données a changé depuis son introduction initiale dans la version 3.0.0. Les valeurs ne sont plus des hashes anonymes perl, mais une chaîne unique contenant la valeur brute du jeton. Vous pouvez tester la compatibilité ascendante en vérifiant si la valeur d'une clé est une référence à un HASH perl, par exemple :

if (ref($toksref->{$sometokenkey}) eq 'HASH') {...

Si c'est le cas, vous utilisez l'ancienne interface, sinon vous utilisez l'interface actuelle.

isspam
Valeur booléenne indiquant la nature du message représenté par les jetons. Si vrai, le message a été désigné comme spam, faux pour le non-spam. Notez que lorsque la fonction est scan, la valeur isspam n'est pas valide.

Imprime des informations sur la base de données d'entraînement de l'utilisateur actuel sur "stdout". Est appelé par "sa-learn --dump".
magic
Est défini à 1 si le nom-valeur des métadonnées "magic" doit être imprimé.
toks
Est défini à 1 si la base de données des jetons doit être imprimée.
regex
Est undef pour imprimer tous les jetons, ou une valeur spécifiant un sous-ensemble de jetons réguliers.
$plugin->learner_close ()
Ferme toutes les bases de données ouvertes.
quiet
Est défini à 1 si les messages d'avertissement doivent être supprimés.

APIS D'AIDE

Ces fonctions permettent aux plugins d'enregistrer des symboles d'événements spécifiques, ou de contrôler le comportement de la chaîne de callbacks.

$plugin->register_eval_rule ($nameofevalsub, $ruletype)
Les plugins qui implémentent un test d'évaluation doivent appeler cette fonction, afin que SpamAssassin appelle l'objet lorsqu'il rencontre ce test d'évaluation. Voir la section REGISTERING EVAL RULES pour plus de détails.

Depuis la version 4.0, le paramètre facultatif $ruletype peut être spécifié pour garantir que la fonction d'évaluation ne soit pas appelée avec le mauvais type depuis la configuration, par exemple, un utilisateur utilisant "header FOO eval:foobar()" au lieu de "body FOO eval:foobar()". Une incohérence entraînera un échec de lint. $ruletype peut être l'un des suivants :

$Mail::SpamAssassin::Conf::TYPE_HEAD_EVALS
$Mail::SpamAssassin::Conf::TYPE_BODY_EVALS  (autorise body et rawbody)
$Mail::SpamAssassin::Conf::TYPE_RAWBODY_EVALS
$Mail::SpamAssassin::Conf::TYPE_FULL_EVALS
$plugin->register_generated_rule_method ($nameofsub)
Dans certaines circonstances, les plugins peuvent trouver utile de compiler des fonctions Perl à partir des règles d'objets de classification en temps réel. Il est important de supprimer ces fonctions une fois que l'objet "Mail::SpamAssassin" a été supprimé, mais cette API le permet.

Une fois que la méthode $nameofsub a été générée, appelez cette API avec le nom de la méthode (y compris la portée complète du paquet). Cela indique qu'il s'agit d'un extrait de code temporaire généré, construit à partir des règles SpamAssassin, et lorsque Mail::SpamAssassin::finish() est appelé, la méthode sera supprimée.

Cette API a été ajoutée dans SpamAssassin 3.2.0.

$plugin->register_method_priority($methodname, $priority)
Indique que la méthode $methodname de l'objet actuel a une priorité de callback de $priority.

Elle est utilisée par le gestionnaire de plugins pour déterminer l'ordre relatif des callbacks ; les plugins ayant des priorités plus basses sont appelés avant ceux ayant des priorités plus élevées. Chaque méthode peut avoir une valeur de priorité différente. La valeur par défaut est 0. L'ordre des callbacks pour les méthodes ayant la même priorité est indéfini.

Souvent, vous n'avez besoin de vous en soucier que si vous souhaitez vous assurer que votre méthode de plugin est appelée avant l'implémentation d'un autre plugin pour cette méthode. Elle doit être appelée depuis le constructeur de votre plugin.

Cette API a été ajoutée dans SpamAssassin 3.2.0.

$plugin->inhibit_further_callbacks()
Indique au gestionnaire de plugins d'inhiber l'invocation d'autres plugins dans la chaîne de plugins pour le callback actuel. Souvent utilisé lors de l'analyse de la configuration avec parse_config().

ENREGISTREMENT

Mail::SpamAssassin::Plugin::dbg($message)
Imprime un message de débogage $message, si l'objet SpamAssassin s'exécute avec le débogage activé.

NOTE : Cette fonction n'est pas disponible dans l'espace de noms général des plugins et ne peut pas être appelée via $self->dbg(). Si un plugin souhaite imprimer des informations de débogage, il doit appeler Mail::SpamAssassin::Plugin::dbg($msg).

Mail::SpamAssassin::Plugin::info($message)
Imprime un message d'information $message, si l'objet SpamAssassin s'exécute avec les messages d'information activés.

NOTE : Cette fonction n'est pas disponible dans l'espace de noms général des plugins et ne peut pas être appelée via $self->info(). Si un plugin souhaite imprimer des informations de débogage, il doit appeler Mail::SpamAssassin::Plugin::info($msg).

En général, il est préférable que les plugins utilisent le module "Mail::SpamAssassin::Logger" pour importer "dbg" et "info" directement, comme ceci :

use Mail::SpamAssassin::Logger;
dbg("un message");
info("un autre message");

ENREGISTREMENT DES RÈGLES D'ÉVALUATION

Les plugins qui implémentent un test d'évaluation doivent enregistrer les méthodes qui peuvent être appelées à partir des configurations des objets de règles, dans le constructeur de la classe du plugin.

Par exemple,

$plugin->register_eval_rule ('check_for_foo', $Mail::SpamAssassin::Conf::TYPE_HEAD_EVALS)

provoquera l'appel de "$plugin->check_for_foo()" pour la règle SpamAssassin suivante :

header   FOO_RULE     eval:check_for_foo()

Note : les règles d'évaluation reçoivent les arguments suivants :

Mail::SpamAssassin::Plugin(3pm)

REGISTERING EVAL RULES

When using the eval rule type, the callback method will be called with the following arguments:

- L'objet plugin lui-même
- L'objet "Mail::SpamAssassin::PerMsgStatus" appelant la règle
- arguments standard pour le type de règle utilisé
- tous les arguments tels que spécifiés dans le fichier de configuration

En d'autres termes, la méthode de test eval devrait ressembler à ceci :

sub check_for_foo {
  my ($self, $permsgstatus, ...arguments...) = @_;
  ...code retournant 0 (manqué), 1 (atteint), ou undef (fonction asynchrone)
}

La règle eval doit retourner 1 pour un succès, ou 0 si la règle n'est pas atteinte. Le cas spécial de "return undef" doit être utilisé lorsque le résultat n'est pas encore prêt et qu'il sera déclaré plus tard avec les fonctions PerMsgStatus got_hit() ou rule_ready() - voir leur documentation pour plus d'informations. Assurez-vous de ne pas retourner undef par erreur.

Notez que les en-têtes peuvent être accédés en utilisant la méthode get() sur l'objet "Mail::SpamAssassin::PerMsgStatus", et le corps par get_decoded_stripped_body_text_array() et d'autres méthodes similaires. De même, l'objet "Mail::SpamAssassin::Conf" contenant la configuration actuelle peut être accédé via "$permsgstatus->{main}->{conf}".

L'état d'un seul message en cours d'analyse doit être stocké sur l'objet $permsgstatus, et non sur l'objet $self, car $self persiste entre les opérations d'analyse. Voir la 'note sur le cycle de vie' de la méthode check_start() ci-dessus.

ARGUMENTS STANDARD POUR LES TYPES DE RÈGLES

Les plugins seront appelés avec les mêmes arguments qu'un EvalTest standard. Différents types de règles reçoivent des informations différentes par défaut :

- tests d'en-tête : aucun argument supplémentaire
- tests de corps : message entièrement rendu sous forme de référence de tableau
- tests de corps brut : message entièrement décodé sous forme de référence de tableau
- tests complets : message vierge sous forme de référence scalaire

Les arguments du fichier de configuration seront passés après les arguments standard.

COMPATIBILITÉ ASCENDANTE

Notez que si vous écrivez un plugin et que vous avez besoin de déterminer si une méthode d'assistance particulière est prise en charge sur "Mail::SpamAssassin::Plugin", vous pouvez le faire ainsi :

if ($self->can("nom_de_la_methode")) {
  eval {
    $self->nom_de_la_methode();        # etc.
  }
} else {
  # prendre une action de repli
}

La même chose s'applique aux API publiques sur des objets d'autres types, tels que "Mail::SpamAssassin::PerMsgStatus".
