DESCRIPTION

Un objet "Mail::Message" contient des informations de message au format MIME, selon RFC2822. Tout ce qui n'est pas spécifié en relation avec le stockage des messages dans des dossiers est implémenté dans cette classe. Les méthodes relatives aux dossiers sont implémentées dans l'extension Mail::Box::Message.

Ceci est une version de maintenance pour l'ancienne interface. Lisez https://github.com/markov2/perl5-Mail-Box/wiki/ pour savoir comment passer à la version 4.

Les méthodes principales sont get(), pour obtenir des informations d'un champ d'en-tête de message, et decoded(), pour obtenir le contenu destiné d'un message. Il existe de nombreuses autres fonctions qui peuvent aider votre programme.

La manipulation complexe de messages, comme la construction de réponses et de réexpéditions, est implémentée dans des modules séparés qui s'auto-ajoutent à cette classe. Cela signifie que vous pouvez utiliser ces méthodes comme si elles appartenaient à cette classe. Ces modules ajoutent des fonctionnalités aux objets de message de tous les types.

$obj->clone(%options)
Crée une copie de ce message. Un objet "Mail::Message" est renvoyé. Les en-têtes et le corps, le journal et le niveau de trace sont repris. Les étiquettes sont copiées avec le message, mais les drapeaux de suppression et de modification ne le sont pas.

ATTENTION : toute copie d'un message (ou d'une partie) sera toujours un objet "Mail::Message". Par exemple, le clone d'un Mail::Box::Message est détaché du dossier d'origine. Lors de l'utilisation de Mail::Box::addMessage() avec le message copié, le clone sera automatiquement converti dans le type correct pour être ajouté.

Voir aussi Mail::Box::Message::copyTo() et Mail::Box::Message::moveTo().

-Option      --Valeur par défaut
 shallow       false
 shallow_body  false
 shallow_head  false
shallow => BOOLEAN
Lors d'une copie shallow, les en-têtes et le corps du message ne sont pas clonés, mais partagés. Cela peut être dangereux : par exemple, dans certains types de dossiers, les champs d'en-tête sont utilisés pour stocker des drapeaux de dossier. Si l'un des clones shallow modifie les drapeaux, cela mettra à jour l'en-tête et sera donc visible dans les deux.

Il existe des situations où une copie shallow peut être utilisée en toute sécurité. Par exemple, lors de l'utilisation de Mail::Box::Message::moveTo() et que vous êtes sûr que le message d'origine ne peut pas devenir inaccessible après le déplacement.

shallow_body => BOOLEAN
Un bon critère, car il n'est pas permis de modifier le corps d'un message : seul un nouveau corps peut être défini avec body().
shallow_head => BOOLEAN
Seul l'en-tête est réutilisé, pas le corps. Cela peut être un mauvais critère, car les champs d'en-tête peuvent être mis à jour, par exemple lorsque les étiquettes changent.

Le message

$obj->container()
Si le message fait partie d'un autre message, "container" retourne la référence au corps contenant.

» exemple :

my Mail::Message $msg = ...
unless $msg->body->isMultipart or return;
my $part   = $msg->body->part(2);
$part->body->isMultipart or return;
my $nested = $part->body->part(3);
$nested->container;  # retourne $msg->body
$nested->toplevel;   # retourne $msg
$msg->container;     # retourne undef
$msg->toplevel;      # retourne $msg
$msg->isPart;        # retourne false
$part->isPart;       # retourne true
$obj->endsOnNewline()
[3.018] Retourne "true" lorsque le message imprimé a un saut de ligne final ("\n"). Dans de rares cas, ce n'est pas le cas. Par exemple, lorsque le corps est lu à partir d'un fichier qui a été généré sans saut de ligne final.
$obj->isDummy()
Les messages factices sont utilisés pour combler les lacunes dans les listes chaînées et autres, où seul un identifiant de message est connu, mais pas l'emplacement de l'en-tête ou des données du corps.

Cette méthode est également disponible pour les objets Mail::Message::Dummy, où elle retournera "true". Sur toute extension de "Mail::Message", elle retournera "false".

$obj->isPart()
Retourne "true" si le message fait partie d'un autre message. C'est le cas pour les extensions Mail::Message::Part de "Mail::Message".
$obj->messageId()
Récupère l'identifiant du message. Chaque message a un identifiant de message unique. Cet identifiant est principalement utilisé pour reconnaître les fils de discussion.
$obj->partNumber()
Retourne une chaîne représentant l'emplacement de cette partie. Dans le cas où le message principal est un message unique, '"undef"' est retourné. Lorsqu'il s'agit d'un multipart, '1' jusqu'au nombre de multiparts est retourné. Une partie imbriquée à plusieurs niveaux peut par exemple retourner '2.5.1'.

Habituellement, cette chaîne est très courte. La numérotation suit la conception d'IMAP4, voir RFC2060 section 6.4.5.

$obj->print( [$fh] )
Imprime le message dans le HANDLE DE FICHIER, qui par défaut est le handle de fichier sélectionné, sans l'encapsulation parfois requise par un dossier.
$message->print(\*STDERR); # vers la sortie d'erreur
$message->print; # vers le fichier sélectionné 
my $out = IO::File->new('out', 'w');
$message->print($out);      # pas d'encapsulation : pas de dossier
$message->write($out);      # avec encapsulation : est un dossier.
$obj->send( [$mailer], %options )
Transmet le message à tout ce qui se trouve à l'extérieur de ce programme Perl. Retourne "false" en cas d'échec d'envoi, même après plusieurs tentatives.

Le $mailer optionnel est un objet Mail::Transport::Send. Si le $mailer n'est pas spécifié, un sera créé et conservé comme défaut pour les messages suivants.

Les %options sont spécifiques au mailer, et un mélange de ce qui est utilisable pour la création de l'objet mailer et pour l'envoi lui-même. Par conséquent, pour les options possibles, voir Mail::Transport::Send::new() et Mail::Transport::Send::send(). Cet objet fournit également une méthode trySend() qui offre un contrôle de plus bas niveau.

» exemple :

$message->send;

est une version courte (mais moins flexible) de

my $mailer = Mail::Transport::SMTP->new(@smtpopts);
$mailer->send($message, @sendopts);

Voir l'exemple/send.pl dans la distribution de Mail::Box.

» exemple :

$message->send(via => 'sendmail')
$obj->size()
Retourne une taille estimée du message entier en octets. Dans de nombreux cas, les fonctions qui traitent davantage le message, par exemple send() ou print(), devront ajouter/modifier des lignes d'en-tête ou ajouter des caractères CR, de sorte que la taille n'est qu'une estimation avec une marge de quelques pour cent du résultat réel.

Le calcul suppose que chaque fin de ligne est représentée par un caractère (comme UNIX, MacOS, et parfois Cygwin), et non par deux caractères (comme Windows et parfois Cygwin). Si vous écrivez le message dans un fichier sur un système qui utilise CR et LF pour terminer une seule ligne (toutes les versions de Windows), le résultat dans ce fichier sera au moins nrLines() plus grand que ce que cette méthode retourne.

$obj->toplevel()
Retourne une référence au message principal, qui sera le message courant si le message ne fait pas partie d'un autre message.
$obj->write( [$fh] )
Écrit le message dans le HANDLE DE FICHIER, qui par défaut est le $fh sélectionné, avec toutes les informations environnantes nécessaires pour le placer correctement dans un fichier de dossier.

Dans la plupart des cas, le résultat de "write" sera le même qu'avec print(). La principale exception concerne les messages de dossier Mbox, qui seront imprimés avec leur ligne 'From ' initiale et un blanc final. Chaque ligne de leur corps commençant par 'From ' aura un '>' ajouté devant.

L'en-tête

$obj->bcc()
Retourne les adresses spécifiées sur la ligne d'en-tête "Bcc" (ou les lignes). Une liste d'objets Mail::Address est retournée. "Bcc" signifie *Blind Carbon Copy* : les destinataires du message qui ne sont pas listés dans les messages réellement envoyés. Ainsi, ce champ sera vide pour les messages reçus, mais peut être présent dans les messages que vous construisez vous-même.
$obj->cc()
Retourne les adresses spécifiées sur la ligne d'en-tête "Cc" (ou les lignes). Une liste d'objets Mail::Address est retournée. "Cc" signifie *Carbon Copy* ; les personnes adressées sur cette ligne reçoivent le message à titre informatif, et ne sont généralement pas censées répondre à son contenu.
$obj->date()
Méthode supprimée pour des raisons de cohérence. Utilisez timestamp() ou "$msg->head->get('Date')".
$obj->destinations()
Retourne une liste d'objets Mail::Address contenant les informations combinées des adresses actives "To", "Cc" et "Bcc". Les adresses dupliquées sont supprimées si détectables.
$obj->from()
Retourne les adresses des expéditeurs. Il est possible d'avoir plus d'une adresse spécifiée dans le champ "From" du message, conformément à la spécification. Par conséquent, une liste d'objets Mail::Address est retournée, qui a généralement une longueur de 1.

Si vous n'avez besoin que d'une seule adresse d'un expéditeur, par exemple pour créer une ligne "message original par" dans le corps d'un message transféré construit, utilisez sender().

» exemple : utilisation de from() pour obtenir toutes les adresses d'expéditeur

my @from = $message->from;
$obj->get($fieldname)
Retourne la valeur stockée dans le champ d'en-tête spécifié. Le $fieldname n'est pas sensible à la casse. Le *corps déplié* du champ est retourné, débarrassé de tous attributs. Voir Mail::Message::Field::body().

Si le champ apparaît plusieurs fois dans l'en-tête, seule la dernière occurrence est retournée. Si vous avez besoin d'une gestion plus complexe des champs, appelez Mail::Message::Head::get() vous-même. Voir study() si vous voulez être intelligent, en faisant un travail meilleur (mais plus lent).

» exemple : le raccourci get() pour les champs d'en-tête

print $msg->get('Content-Type'), "\n";

Est équivalent à :

print $msg->head->get('Content-Type')->body, "\n";

Le corps

$obj->body( [$body] )
Retourne le corps de ce message. ATTENTION : ceci retourne un objet qui peut être encodé : utilisez decoded() pour obtenir un corps avec des données utilisables.

Avec des options, un nouveau $body est défini pour ce message. Ceci n'est pas pour un usage normal, sauf si vous comprenez les conséquences : vous changez le contenu du message sans changer son identifiant de message. Le chemin correct est via

$message = Mail::Message->buildFromBody($body);  # ou
$message = Mail::Message->build($body);          # ou
$message = $origmsg->forward(body => $body);

Le $body doit être une (sous-)classe de Mail::Message::Body. Dans ce cas, l'information du corps spécifié est copiée dans les en-têtes. Le corps objet sera encodé si nécessaire, car les messages écrits sur fichier ou transmis ne doivent pas contenir de données binaires. Le corps converti est retourné.

Si $body est "undef", le corps actuel du message sera extrait du message. Toutes les relations seront coupées. Le corps est retourné et peut être attaché à un autre message.

» exemple :

my $body      = $msg->body;
my @encoded   = $msg->body->lines;
my $new       = Mail::Message::Body->new(mime_type => 'text/html');
my $converted = $msg->body($new);
$obj->contentType()
Retourne la ligne d'en-tête du type de contenu, ou "text/plain" s'il n'est pas défini. Les paramètres sont retirés.
$obj->decoded(%options)
Décode le corps de ce message et le retourne en tant qu'objet de corps. C'est un raccourci pour "$msg->body->decoded". Toutes les %options sont passées.
$obj->encode(%options)
Chiffre le message dans un certain format. Consultez les détails sur la page de manuel dédiée à Mail::Message::Body::Encode. Les %options qui peuvent être spécifiées ici sont celles de la méthode Mail::Message::Body::encode().
$obj->isMultipart()
Vérifie si ce message est un message multipart (a des pièces jointes). Pour le savoir, il suffit d'avoir l'en-tête du message ; il n'est pas nécessaire de lire le corps pour le détecter.
$obj->isNested()
Retourne "true" pour les messages de type "message/rfc822" et les parties de message.
$obj->parts( [<'ALL'|'ACTIVE'|'DELETED'|'RECURSE'|$filter>] )
Retourne les *parties* de ce message. Cela peut être un peu inhabituel : retourne le message lui-même s'il n'est pas multipart.

En général, le terme *partie* est utilisé avec les messages *multipart* : messages encapsulés dans le corps d'un message. Pour abstraire ce concept : cette méthode retourne toutes les combinaisons d'en-tête-corps trouvées dans ce message, à l'exception des enveloppes multipart et message/rfc822. Les objets retournés sont des "Mail::Message" et "Mail::Message::Part".

L'option par défaut est '"ALL"', qui retourne le message lui-même pour les messages simples, le contenu imbriqué d'un objet message/rfc822, ou les parties d'un multipart sans récursion. En cas de '"RECURSE"', les parties des multipart sont collectées récursivement. Cette option ne peut pas être combinée avec les autres options, qui pourraient vous manquer : dans ce cas, vous devrez tester vous-même.

'"ACTIVE"' et '"DELETED"' vérifient le drapeau supprimé dans les messages et les parties. Le $filter est un bloc de code référence qui est appelé pour chaque partie du message ; chaque partie comme '"RECURSE"' retourne.

» exemple :

my @parts = $msg->parts;           # $msg non multipart : retourne ($msg)
my $parts = $msg->parts('ACTIVE'); # retourne ($msg)
$msg->delete;
my @parts = $msg->parts;           # retourne ($msg)
my $parts = $msg->parts('ACTIVE'); # retourne ()

Drapeaux

$obj->delete()
Marque le message comme devant être supprimé, ce qui est un raccourci pour
$msg->label(deleted => time); La suppression réelle ne se produit que lors d'une synchronisation de dossier. Consultez également deleted().

L'heure de la suppression actuelle est stockée comme valeur, mais n'est pas toujours conservée dans le dossier (cela dépend de l'implémentation). Lorsque le même message est supprimé plusieurs fois, la première heure de suppression est conservée.

» exemple :

$message->delete;
$message->deleted(1);  # exactement la même chose
$message->label(deleted => 1);
delete $message;
$obj->deleted( [BOOLEAN] )
Définit le drapeau de suppression pour ce message. Sans argument, la méthode retourne la même chose que isDeleted(), ce qui est préféré. Lorsqu'une valeur "true" est fournie, delete() est appelée.

» exemple :

$message->deleted(1);          # supprimer
$message->delete;              # supprimer (préféré)
$message->deleted(0);          # désactiver
if($message->deleted) {...}    # vérifier
if($message->isDeleted) {...}  # vérifier (préféré)
$obj->isDeleted()
Est un raccourci pour
$msg->label('deleted')

Pour certains types de dossiers, vous pourrez obtenir l'heure de suppression en retour. Cela dépend de l'implémentation.

» exemple :

next if $message->isDeleted;
if(my $when = $message->isDeleted) {
   print scalar localtime $when;
}
$obj->isModified()
Retourne si ce message est marqué comme modifié. Les modifications sont des changements dans les lignes d'en-tête, lorsqu'un nouveau corps est défini pour le message (dangereux), ou lorsque des étiquettes sont modifiées.
$obj->label($label|PAIRS)
Retourne...
e de la $label, éventuellement après avoir défini certaines valeurs. En cas de définition de valeurs, vous spécifiez des "PAIRS" clé-valeur.

Les étiquettes sont utilisées pour stocker des informations sur la gestion du message au sein du dossier. Des indicateurs sur le fait qu'un message a été lu, répondu ou planifié pour suppression.

Certaines étiquettes sont tirées des lignes "Status" et "X-Status" de l'en-tête. Les types de dossiers comme MH définissent un fichier d'étiquettes séparé, et Maildir ajoute des lettres au nom du fichier du message. Mais les étiquettes MailBox sont toujours les mêmes.

» exemple:

print $message->label('seen');
if($message->label('seen')) {...};
$message->label(seen => 1);
$message->label(deleted => 1);  # identique à $message->delete
$obj->labels()
Retourne toutes les étiquettes connues. En contexte SCALAR, elle retourne les connaissances sous forme de référence à un hash. C'est une référence aux données originales, mais vous ne devez *pas* modifier ces données directement : appelez "label" pour les modifications !

En contexte LIST, vous obtenez une liste de noms qui sont définis. Soyez prévenus qu'ils n'évalueront pas tous à "true", bien que la plupart d'entre eux le feront.

$obj->labelsToStatus()
Lorsque les étiquettes ont été modifiées, cela peut affecter les lignes d'en-tête "Status" et/ou "X-Status" des messages mbox. Lisez la relation entre ces champs et les étiquettes dans le chapitre DETAILS.

La méthode n'affectera soigneusement que le résultat de modified() lorsqu'il y a un réel changement des indicateurs, donc pas pour chaque appel à label().

$obj->modified( [BOOLEAN] )
Retourne (éventuellement après définition) si ce message est marqué comme modifié. Voir isModified().
$obj->statusToLabels()
Met à jour les étiquettes en fonction des lignes de statut dans l'en-tête. Voir la description dans le chapitre DETAILS.

Internes

$obj->clonedFrom()
Retourne le message qui est l'original de ce message, lorsque celui-ci a été créé par une opération clone().
$class->coerce($message, %options)
Force la conversion d'un $message en Mail::Message. Dans certains cas, par exemple lorsque vous ajoutez un message à un dossier, cette conversion est automatiquement appelée pour garantir que le bon type de message est stocké.

Le message converti est retourné en cas de succès, sinon "undef". Le message converti peut être une version reblessée du message original ou un nouvel objet. Si le message doit être spécialisé, par exemple d'un Mail::Message général en un Mail::Box::Mbox::Message, aucune copie n'est nécessaire. Cependant, pour convertir un objet Mail::Internet en Mail::Message, beaucoup de copie et de conversion auront lieu.

Les MESSAGEs valides qui peuvent être convertis en objets Mail::Message sont de type

  • Tout type de Mail::Box::Message
  • Objets MIME::Entity, utilisant Mail::Message::Convert::MimeEntity
  • Objets Mail::Internet, utilisant Mail::Message::Convert::MailInternet
  • Objets Email::Simple, utilisant Mail::Message::Convert::EmailSimple
  • Objets Email::Abstract

Les Mail::Message::Part, qui sont des extensions de "Mail::Message", peuvent également être convertis directement à partir d'un Mail::Message::Body.

» exemple:

my $folder  = Mail::Box::Mbox->new;
my $message = Mail::Message->build(...);
my $coerced = Mail::Box::Mbox::Message->coerce($message);
$folder->addMessage($coerced);

Remplacement plus simple pour les deux lignes précédentes :

my $coerced = $folder->addMessage($message);
$obj->isDelayed()
Vérifie si le message est retardé (pas encore lu du fichier). Retourne "true" ou "false", en fonction du type de corps.

DESCRIPTION

The MailBox distribution is a set of classes that implement a mailbox interface. The primary goal is to make it easy to access the content of the mailbox, regardless of the underlying storage mechanism. The MailBox distribution supports for instance:

  • Mbox folders (as used by many Unix mail programs)
  • Maildir folders (as used by Qmail and Postfix)
  • MH folders (as used by the MH mail system)
  • DBX folders (as used by Outlook Express)
  • POP3 access
  • IMAP4 access
  • Network access to mailboxes

The core of the MailBox distribution is the Mail::Box class. It provides access to a folder. The folder is a collection of messages. Each message is represented by an object from a subclass of Mail::Message.

The messages are stored in a folder. A folder is represented by an object from a subclass of Mail::Box. For example, a Mail::Box::Mbox object represents an mbox folder.

The class structure for message access is:

Mail::Box::Folder      (abstract base class)
 |
 |-Mail::Box::Mbox
 |-Mail::Box::Maildir
 |-Mail::Box::MH
 |-Mail::Box::Dbx
 |-Mail::Box::POP3
 |-Mail::Box::IMAP4
 |-Mail::Box::Net
 |
 `-Mail::Box::File      (abstract base class for file system folders)
        |
        |-Mail::Box::MH
        |-Mail::Box::Maildir
        |-Mail::Box::Dir       (base class for Maildir and MH)
                |
                `-Mail::Box::MH
        `-Mail::Box::Mbox

The structure of a message itself is described next.

Message structure

A message object is composed of a header and a body. The header contains meta-information about the message, like the sender, the receivers, when it was transported, how it was transported, etc. Headers can grow quite large.

In MailBox, each message object manages exactly one header object (a Mail::Message::Head) and one body object (a Mail::Message::Body). The header contains a list of header fields, which are represented by Mail::Message::Field objects.

The body

The body contains the "payload": the data to be transferred. The data can be encoded, only accessible with a specific application, and may use some weird character-set, like Vietnamese; the MailBox distribution tries to assist you with handling these e-mails without the need to know all the details. This additional information ("meta-information") about the body data is stored in the header. The header contains more information, for instance about the message transport and relations to other messages.

Message object implementation

The general idea about the structure of a message is

Mail::Message
 |  |
 |  `-has-one--Mail::Message::Body
 |
 `----has-one--Mail::Message::Head
                 |
                 `-has-many--Mail::Message::Field

However: there are about 7 kinds of body objects, 3 kinds of headers and 3 kinds of fields. You will usually not see too much of these kinds, because they are merely created for performance reasons and can be used all the same, with the exception of the multipart bodies.

A multipart body is either a Mail::Message::Body::Multipart (mime type "multipart/*") or a Mail::Message::Body::Nested (mime type "message/rfc822"). These bodies are more complex:

Mail::Message::Body::Multipart
 |
 `-has-many--Mail::Message::Part
              |  |
              |  `-has-one--Mail::Message::Body
              |
              `----has-one--Mail::Message::Head

Before you try to reconstruct multiparts or nested messages yourself, you can better take a look at Mail::Message::Construct::Rebuild.

Message class implementation

The class structure of messages is very close to that of folders. For instance, a Mail::Box::File::Message relates to a Mail::Box::File folder.

As extra level of inheritance, it has a Mail::Message, which is a message without location. And there is a special case of message: Mail::Message::Part is a message encapsulated in a multipart body.

The message types are:

Mail::Box::Mbox::Message            Mail::Box::POP3::Message
|  Mail::Box::Dbx::Message      Mail::Box::IMAP4::Message  |
|  |                                                    |  |
Mail::Box::File::Message             Mail::Box::Net::Message
        |                                      |
        |       Mail::Box::Maildir::Message    |
        |       |   Mail::Box::MH::Message     |
        |       |   |                          |
        |       Mail::Box::Dir::Message        |
        |                |                     |
        `------------.   |   .-----------------'
                     |   |   |
                  Mail::Box::Message    Mail::Message::Part
                         |                     |
                         |       .-------------'
                         |       |
                     Mail::Message
                         |
                         |
                   Mail::Reporter (general base class)

By far most folder features are implemented in Mail::Box, so available to all folder types. Sometimes, features which appear in only some of the folder types are simulated for folders that miss them, like sub-folder support for MBOX.

Two strange other message types are defined: the Mail::Message::Dummy, which fills holes in Mail::Box::Thread::Node lists, and a Mail::Box::Message::Destructed, this is an on purpose demolished message to reduce memory consumption.

Labels

Labels (also named "Flags") are used to indicate some special condition on the message, primary targeted on organizational issues: which messages are already read or should be deleted. There is a very strong user relation to labels.

The main complication is that each folder type has its own way of storing labels. To give an indication: MBOX folders use "Status" and "X-Status" header fields, MH uses a ".mh-sequences" file, MAILDIR encodes the flags in the message's filename, and IMAP has flags as part of the protocol.

Besides, some folder types can store labels with user defined names, where other lack that feature. Some folders have case-insensitive labels, other don't. Read all about the specifics in the manual page of the message type you actually have.

Predefined labels

To standardize the folder types, MailBox has defined the following labels, which can be used with the label() and labels() methods on all kinds of messages:

  • deleted

    This message is flagged to be deleted once the folder closes. Be very careful about the concept of 'delete' in a folder context : it is only a flag, and does not involve immediate action! This means, for instance, that the memory which is used by Perl to store the message is not released immediately (see destruct() if you need to).

    The methods delete(), deleted(), and isDeleted() are only short-cuts for managing the "delete" label (as of MailBox 2.052).

  • draft

    The user has prepared this message, but is has not been send (yet). This flag is not automatically added to a message by MailBox, and has only a meaning in user applications.

  • flagged

    Messages can be flagged for some purpose, for instance as result of a search for spam in a folder. The Mail::Box::messages() method can be used to collect all these flagged messages from the folder.

    Probably it is more useful to use an understandable name (like "spam") for these selections, however these self-defined labels can not stored in all folder types.

  • old

    The message was already in the folder when it was opened the last time, so was not recently added to the folder. This flag will never automatically be set by MailBox, because it would probably conflict with the user's idea of what is old.

  • passed

    Not often used or kept, this flag indicates that the message was bounced or forwarded to someone else.

  • replied

    The user (or application) has sent a message back to the sender of the message, as response of this one. This flag is automatically set if you use reply(), but not with forward() or bounce().

  • seen

    When this flag is set, the receiver of the message has consumed the message. A mail user agent (MUA) will set this flag when the user has opened the message once.

Status and X-Status fields

Mbox folders have no special means of storing information about messages (except the message separator line), and therefore have to revert to adding fields to the message header when something special comes up. This feature is also enabled for POP3, although whether that works depends on the POP server.

All applications which can handle mbox folders support the "Status" and "X-Status" field convensions. The following encoding is used:

Flag   Field       Label
R      Status   => seen    (Read)
O      Status   => old     (not recent)
A      X-Status => replied (Answered)
F      X-Status => flagged

There is no special flag for "deleted", which most other folders support: messages flagged to be deleted will never be written to a folder file when it is closed.

NAME

Mail::Message - a message object of the Mail::* distribution

INHERITANCE

Mail::Message is a subclass of Mail::Base.

SYNOPSIS

  use Mail::Message;

  my $message = Mail::Message->new();
  my $message = Mail::Message->new( {
      From    => 'me@example.com',
      To      => 'you@example.com',
      Subject => 'Hello World',
  });

  $message->subject('New Subject');
  $message->add('X-Mailer', 'MyMailer v1.0');

  # Read message from file
  my $message = Mail::Message->new( file => 'message.txt' );

  # Write message to file
  $message->file('message.txt');

  # Access parts of the message
  print $message->from.io->string, "\n";
  print $message->subject, "\n";
  print $message->content.io->string, "\n";

  # Iterate over headers
  my $header = $message->head;
  while (my $field = $header->{(1)}) {
      print $field->tag, ': ', $field->value, "\n";
  }

  # Iterate over parts (for MIME messages)
  my $parts = $message->parts;
  for my $part (@$parts) {
      # ...
  }

DESCRIPTION

This class represents a single email message. It supports access to headers and the message body. It can be parsed from files or strings, and written back to files or strings.

A message is composed of a header section and a body section. The header section contains a list of fields, each with a tag (e.g. "Subject") and a value. The body section can be plain text, HTML, or a multipart structure containing other messages (parts).

This class provides a flexible way to create, manipulate, and inspect email messages.

METHODS

See Mail::Message::Construct, Mail::Message::Head, and Mail::Message::Body.

DETAILS

This class extends the functionality of Mail::Base by providing message-specific features.
