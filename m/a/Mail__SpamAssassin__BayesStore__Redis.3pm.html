NOM

Mail::SpamAssassin::BayesStore::Redis - Implémentation du module de stockage bayésien Redis

DESCRIPTION

Ce module implémente un module de stockage bayésien basé sur Redis.

Apache SpamAssassin v3.4.0 introduit la prise en charge d'une base de données Bayes sur un serveur Redis, fonctionnant localement ou accessible via le réseau. Similaire aux backends SQL, la base de données peut être utilisée simultanément par plusieurs hôtes exécutant SpamAssassin.

L'implémentation actuelle ne prend en charge qu'une base de données Bayes globale, c'est-à-dire que les sous-bases de données par destinataire ne sont pas prises en charge. Le serveur Redis 2.6.* prend en charge l'accès via IPv4 ou via un socket Unix, à partir de la version 2.8.0 de Redis, IPv6 est également pris en charge. Gardez à l'esprit que le serveur Redis n'offre que des contrôles d'accès limités, il est donc conseillé de laisser le serveur Redis se lier uniquement à une interface de bouclage, ou d'utiliser d'autres mécanismes pour limiter l'accès, tels que des règles de pare-feu locales.

Le backend Redis pour Bayes peut exploiter le support du scripting Lua dans un serveur Redis, améliorant ainsi les performances. Le support Lua est disponible dans le serveur Redis depuis la version 2.6. En l'absence de support Lua, le backend Redis utilise des commandes Redis traditionnelles regroupées (pipelined), il devrait donc fonctionner avec un serveur Redis version 2.4 (non testé), bien que cela ne soit pas recommandé pour les sites très fréquentés.

L'expiration des jetons et des entrées d'ID de message 'vus' est laissée au serveur Redis. Aucune disposition n'est prévue pour l'expiration manuelle d'une base de données, il est donc fortement recommandé de laisser le réglage bayes_auto_expire à sa valeur par défaut 1 (c'est-à-dire activé).

Exemple de configuration :

bayes_store_module  Mail::SpamAssassin::BayesStore::Redis
bayes_sql_dsn       server=127.0.0.1:6379;password=foo;database=2
bayes_token_ttl 21d
bayes_seen_ttl   8d
bayes_auto_expire 1

Un serveur redis avec support Lua (2.6 ou supérieur) est recommandé pour des raisons de performance.

La variable de configuration bayes_sql_dsn a été détournée pour nos besoins :

bayes_sql_dsn
  Paramètres de configuration optionnels affectant une connexion à un serveur redis.
  Il s'agit d'une liste de paires option=valeur séparées par des points-virgules, où une option
  peut être : server, password, database. Les options non reconnues sont ignorées silencieusement.
  L'option 'server' spécifie un socket sur lequel un serveur redis écoute.
  Il peut s'agir du chemin absolu d'un socket Unix, ou d'une paire hôte:port,
  où un hôte peut être une adresse IPv4 ou IPv6 ou un nom d'hôte.
  Une adresse IPv6 doit être entre crochets, par exemple [::1]:6379
  (le support IPv6 dans un serveur redis est disponible depuis la version 2.8.0).
  Par défaut, connexion à un socket INET sur 127.0.0.1, port 6379.
  La valeur de l'option 'password' est envoyée dans une commande AUTH au serveur redis
  lors de la connexion si le serveur demande une authentification. Un mot de passe est
  envoyé en texte brut et un serveur redis n'offre qu'une authentification rudimentaire optionnelle.
  Pour limiter l'accès à un serveur redis, utilisez son option 'bind' pour
  vous lier à une interface spécifique (typiquement une interface de bouclage),
  ou utilisez un pare-feu basé sur l'hôte.
  La valeur de l'option 'database' peut être un entier non négatif (petit),
  qui est passé au serveur redis avec une commande SELECT lors de la connexion,
  et choisit un index de sous-base de données. L'index de base de données par défaut est 0.
  Exemple : server=localhost:6379;password=foo;database=2
bayes_token_ttl
  Contrôle l'expiration des jetons (valeur TTL en SECONDES, envoyée telle quelle à Redis)
  lorsque bayes_auto_expire est vrai. La valeur par défaut est de 3 semaines (mais vérifiez
  Mail::SpamAssassin::Conf.pm pour être sûr).
bayes_seen_ttl
  Contrôle l'expiration des 'vus' (valeur TTL en SECONDES, envoyée telle quelle à Redis)
  lorsque bayes_auto_expire est vrai. La valeur par défaut est de 8 jours (mais vérifiez
  Mail::SpamAssassin::Conf.pm pour être sûr).

L'expiration est effectuée en interne dans Redis en utilisant les paramètres *_ttl mentionnés ci-dessus, mais uniquement si bayes_auto_expire est vrai (ce qui est le cas par défaut). C'est pourquoi --force-expire etc. ne fait rien, et les comptes de jetons et les valeurs atime sont affichés comme zéro dans les statistiques.

LIMITATIONS : Seul le stockage bayésien global est implémenté, le bayésien par utilisateur n'est pas disponible actuellement. La sauvegarde (sa-learn --backup, ou --dump) d'une base de données volumineuse peut ne pas être possible si toutes les clés ne tiennent pas dans la mémoire du processus.

get_storage_variables

public instance (@) get_storage_variables ()

Description : Cette méthode récupère les différentes variables administratives utilisées par le processus et la base de données Bayes.

Les valeurs retournées dans le tableau sont dans l'ordre suivant :

0 : nombre de scans 1 : nombre de spams 2 : nombre de ham 3 : nombre de jetons dans la base 4 : dernier temps d'expiration 5 : temps du jeton le plus ancien dans la base 6 : version de la base de données
