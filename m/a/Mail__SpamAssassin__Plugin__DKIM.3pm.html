NOM

Mail::SpamAssassin::Plugin::DKIM - effectuer des tests de vérification DKIM

SYNTAXE

loadplugin Mail::SpamAssassin::Plugin::DKIM [/chemin/vers/DKIM.pm]

En tenant compte des signatures de tous les domaines de signature :

full   DKIM_SIGNED           eval:check_dkim_signed()
full   DKIM_VALID            eval:check_dkim_valid()
full   DKIM_VALID_AU         eval:check_dkim_valid_author_sig()
full   DKIM_VALID_EF         eval:check_dkim_valid_envelopefrom()

En tenant compte des signatures ARC (Authenticated Received Chain, RFC 8617) de tous les domaines de signature :

full   ARC_SIGNED            eval:check_arc_signed()
full   ARC_VALID             eval:check_arc_valid()

En tenant compte des signatures de domaines de signature spécifiés uniquement : (les guillemets peuvent être omis pour les noms de domaine ne contenant que des lettres, des chiffres, des points et des tirets)

full   DKIM_SIGNED_MY1       eval:check_dkim_signed('dom1','dom2',...)
full   DKIM_VALID_MY1        eval:check_dkim_valid('dom1','dom2',...)
full   DKIM_VALID_AU_MY1     eval:check_dkim_valid_author_sig('d1','d2',...)
full   __DKIM_DEPENDABLE     eval:check_dkim_dependable()

Pratiques de signature de domaine d'auteur (ADSP) de tous les domaines d'auteur :

header DKIM_ADSP_NXDOMAIN    eval:check_dkim_adsp('N')
header DKIM_ADSP_ALL         eval:check_dkim_adsp('A')
header DKIM_ADSP_DISCARD     eval:check_dkim_adsp('D')
header DKIM_ADSP_CUSTOM_LOW  eval:check_dkim_adsp('1')
header DKIM_ADSP_CUSTOM_MED  eval:check_dkim_adsp('2')
header DKIM_ADSP_CUSTOM_HIGH eval:check_dkim_adsp('3')

Pratiques de signature de domaine d'auteur (ADSP) de domaines d'auteur spécifiés uniquement :

header DKIM_ADSP_MY1         eval:check_dkim_adsp('*','dom1','dom2',...)
describe DKIM_SIGNED   Le message a une signature DKIM ou DK, pas nécessairement valide
describe DKIM_VALID    Le message a au moins une signature DKIM ou DK valide
describe DKIM_VALID_AU Le message a une signature DKIM ou DK valide du domaine de l'auteur
describe DKIM_VALID_EF Le message a une signature DKIM ou DK valide du domaine envelope-from
describe __DKIM_DEPENDABLE     Une défaillance de validation non attribuable à une troncature
describe DKIM_ADSP_NXDOMAIN    Domaine non présent dans le DNS et aucune signature valide du domaine d'auteur
describe DKIM_ADSP_ALL         Le domaine signe tous les courriels, aucune signature valide du domaine d'auteur
describe DKIM_ADSP_DISCARD     Le domaine signe tous les courriels et suggère de supprimer les courriels sans signature valide du domaine d'auteur, aucune signature valide du domaine d'auteur
describe DKIM_ADSP_CUSTOM_LOW  adsp_override est CUSTOM_LOW, aucune signature valide du domaine d'auteur
describe DKIM_ADSP_CUSTOM_MED  adsp_override est CUSTOM_MED, aucune signature valide du domaine d'auteur
describe DKIM_ADSP_CUSTOM_HIGH adsp_override est CUSTOM_HIGH, aucune signature valide du domaine d'auteur

Pour la compatibilité avec les versions antérieures à 3.3.0, les éléments suivants sont des synonymes :

ANCIEN : eval:check_dkim_verified = NOUVEAU : eval:check_dkim_valid
ANCIEN : eval:check_dkim_signall  = NOUVEAU : redondant, sémantiquement toujours vrai

La règle d'évaluation __DKIM_DEPENDABLE mérite une explication. La règle renvoie vrai lorsque les signatures sont fournies par un appelant, OU ALORS lorsque les signatures sont obtenues par ce plugin ET soit il n'y a pas de signatures, soit une règle __TRUNCATED était fausse. En d'autres termes : __DKIM_DEPENDABLE est vrai lorsque les signatures échouées ne peuvent pas être attribuées à une troncature de message lors de la fourniture d'un message à SpamAssassin. Il peut être consulté pour éviter les faux positifs sur de grands messages tronqués avec une implémentation simplifiée d'ADSP par des règles faites à la main.

DESCRIPTION

Ce plugin SpamAssassin implémente les recherches DKIM telles que décrites par la RFC 4871, ainsi que les recherches historiques DomainKeys, telles que décrites par la RFC 4870, grâce au support des deux types de signatures par les versions plus récentes du module Mail::DKIM.

Il nécessite le module CPAN "Mail::DKIM" pour fonctionner. Un grand merci à Jason Long pour ce module.

TAGS

Les balises suivantes sont ajoutées à l'ensemble, disponibles pour être utilisées dans les rapports, les champs d'en-tête, d'autres plugins, etc. :

_DKIMIDENTITY_
  Identifiant d'agent ou d'utilisateur (AUID) (la balise 'i') des signatures valides ;
_DKIMDOMAIN_
  Identifiant du domaine de signature (SDID) (la balise 'd') des signatures valides ;
_DKIMSELECTOR_
  Sélecteur DKIM (la balise 's') des signatures valides ;

Les identités et les domaines des signatures qui ont échoué à la vérification ne sont pas inclus dans ces balises. Les doublons sont éliminés (par exemple, lorsqu'il y a une ou plusieurs signatures valides du même signataire, une seule copie est incluse dans une balise). Notez qu'il peut y avoir plus d'une signature dans un message - actuellement, elles sont fournies sous forme de liste séparée par des espaces, bien que ce comportement puisse changer.

PARAMETRES UTILISATEUR

welcomelist_from_dkim auteur@example.com [domaine-signature]
Précédemment whitelist_from_dkim qui fonctionnera de manière interchangeable jusqu'à la version 4.1.

Fonctionne de manière similaire à welcomelist_from, sauf qu'en plus de faire correspondre une adresse d'auteur (From) au motif dans le premier paramètre, le message doit également porter une signature valide Domain Keys Identified Mail (DKIM) créée par un domaine de signature (SDID, c'est-à-dire la balise d=) qui nous est acceptable.

Une seule entrée welcomelist est autorisée par ligne, comme dans "welcomelist_from_rcvd". Plusieurs lignes "welcomelist_from_dkim" sont autorisées. Les caractères de style glob de fichiers sont autorisés pour l'adresse From (le premier paramètre), tout comme avec "welcomelist_from_rcvd".

Le deuxième paramètre (le domaine de signature) n'accepte pas les caractères génériques de style glob de fichiers complets, bien qu'un simple préfixe '*.' (ou juste un '.') avant un nom de domaine soit reconnu et implique n'importe quel sous-domaine du domaine spécifié (mais pas le domaine lui-même).

Si aucun paramètre de domaine de signature n'est spécifié, la seule signature acceptable sera une signature de domaine d'auteur (parfois appelée signature de premier parti), qui est une signature où le domaine de signature (SDID) d'une signature correspond au domaine de l'adresse de l'auteur (c'est-à-dire l'adresse dans un champ d'en-tête From).

Étant donné que cette liste de bienvenue nécessite une vérification DKIM, les tests réseau doivent être activés.

Exemples de liste de bienvenue basés sur une signature de domaine d'auteur (premier parti) :

welcomelist_from_dkim joe@example.com
welcomelist_from_dkim *@corp.example.com
welcomelist_from_dkim *@*.example.com

Exemples de liste de bienvenue basés sur des signatures de tiers :

welcomelist_from_dkim jane@example.net      example.org
welcomelist_from_dkim rick@info.example.net example.net
welcomelist_from_dkim *@info.example.net    example.net
welcomelist_from_dkim *@*                   mail7.remailer.example.com
welcomelist_from_dkim *@*                   *.remailer.example.com
def_welcomelist_from_dkim auteur@example.com [domaine-signature]
Précédemment def_whitelist_from_dkim qui fonctionnera de manière interchangeable jusqu'à la version 4.1.

Identique à "welcomelist_from_dkim", mais utilisé pour les entrées de liste de bienvenue par défaut dans la distribution SpamAssassin. Le score de la liste de bienvenue est plus bas, car ceux-ci sont souvent des cibles d'abus de services de messagerie publics qui signent leur courrier.

adsp_override domain [signing-practices]
Actuellement, peu de domaines publient leurs pratiques de signature (RFC 5617 - ADSP), en partie à cause de la nouveauté du RFC ADSP, en partie parce qu'ils pensent que peu vérifieront leur contenu, et en partie par crainte que certains ne perdent du courrier en raison de problèmes dans leurs procédures de vérification de signature ou de manipulation de courrier par des expéditeurs hors de leur contrôle.

Cependant, les utilisateurs pourraient bénéficier de connaître les pratiques de signature d'un domaine (auteur), par exemple pour reconnaître de faux e-mails prétendant provenir de certains domaines qui sont des cibles populaires de phishing, comme les institutions financières. Cependant, comme les pratiques de signature sont rarement publiées ou sont faibles, il n'est pas justifié de les rechercher dans le DNS.

Pour surmonter ce problème de poule ou d'œuf, le mécanisme "adsp_override" permet aux utilisateurs de SpamAssassin de remplacer les pratiques de signature publiées ou par défaut d'un domaine. Cela permet de spécifier manuellement une pratique de signature plus forte (ou plus faible) qu'un domaine ne souhaite pas publier (explicitement ou par défaut), et permet également d'économiser une requête DNS.

Notez que ADSP (publié ou remplacé) n'est interrogé que pour les messages qui ne contiennent pas de signature DKIM valide du domaine auteur.

Selon le RFC 5617, les pratiques de signature peuvent être l'une des suivantes : "unknown", "all" et "discardable".

"unknown" : Le domaine peut signer tout ou partie de ses courriels - les courriels de ce domaine peuvent ou non avoir une signature de domaine auteur. C'est la valeur par défaut si le domaine existe dans le DNS mais qu'aucune entrée ADSP n'est trouvée.

"all" : Tous les courriels de ce domaine sont signés avec une signature de domaine auteur.

"discardable" : Tous les courriels de ce domaine sont signés avec une signature de domaine auteur. De plus, si un message arrive sans signature de domaine auteur valide, le domaine encourage vivement les destinataires à rejeter le message.

La requête ADSP peut également déterminer qu'un domaine est "hors périmètre" (c'est-à-dire que le domaine n'existe pas (NXDOMAIN) dans le DNS).

Pour remplacer les pratiques de signature d'un domaine dans un fichier de configuration SpamAssassin, spécifiez un "adsp_override" pour chaque domaine d'émission à remplacer.

Son premier argument est un nom de domaine. Le domaine auteur est comparé à celui-ci, la comparaison est insensible à la casse. Ce n'est pas une expression régulière ou un joker de fichier, mais une correspondance limitée peut toujours être utilisée : si cet argument commence par "*." (ou est un simple "*"), le domaine auteur correspond s'il s'agit d'un sous-domaine (à un ou plusieurs niveaux) de l'argument. Sinon (avec un préfixe astérisque), la correspondance doit être exacte (pas un sous-domaine).

Un second paramètre optionnel est l'un des termes suivants (insensible à la casse) : "nxdomain", "unknown", "all", "discardable", "custom_low", "custom_med", "custom_high".

L'absence de ce second paramètre implique "discardable". Si un domaine n'est pas spécifié dans une directive "adsp_override" et ne publie explicitement aucun enregistrement ADSP, alors "unknown" est impliqué pour les domaines valides, et "nxdomain" pour les domaines inexistants dans le DNS. (Note : la validation de domaine n'est effectuée qu'avec les versions de Mail::DKIM 0.37 ou ultérieures (en fait depuis 0.36_5), donc "nxdomain" n'est jamais rencontré avec d'anciennes versions).

La configuration forte "discardable" est utile pour les domaines connus pour signer leurs e-mails et les envoyer directement aux destinataires (pas aux listes de diffusion), et qui sont des cibles fréquentes de tentatives de phishing, comme les institutions financières. "discardable" convient également aux domaines connus pour ne pas envoyer d'e-mails.

Lorsqu'un message ne contient pas de signature valide par le domaine auteur (le domaine dans le champ From), les pratiques de signature associées au domaine auteur déterminent quelle règle parmi les suivantes est activée et contribue à son score : DKIM_ADSP_NXDOMAIN, DKIM_ADSP_ALL, DKIM_ADSP_DISCARD, DKIM_ADSP_CUSTOM_LOW, DKIM_ADSP_CUSTOM_MED, DKIM_ADSP_CUSTOM_HIGH. Pas plus d'une de ces règles ne peut être activée pour les messages ayant un auteur (mais voir ci-dessous). Les trois dernières peuvent résulter uniquement de la configuration donnée dans une directive "adsp_override" (pas d'une requête DNS), et peuvent servir de moyen pratique de fournir un score différent si les scores attribués à DKIM_ADSP_ALL ou DKIM_ADSP_DISCARD ne conviennent pas à certains domaines.

Le RFC 5322 autorise un message à avoir plus d'un auteur - plusieurs adresses peuvent être listées dans un seul champ From. Le RFC 5617 définit qu'un message avec plusieurs auteurs a plusieurs pratiques de signature de domaine, mais ne prescrit pas comment elles doivent être combinées. En présence de plusieurs pratiques de signature, plus d'une des règles DKIM_ADSP_* peut être activée.

Par mesure de sécurité contre l'activation des règles DKIM_ADSP_* lorsqu'il y a une raison connue d'échec de la vérification de signature locale, l'ADSP du domaine est considéré comme 'unknown' lorsque les requêtes DNS sont désactivées ou lorsqu'un problème temporaire survient lors de l'obtention d'une clé publique de l'auteur. De même, l'ADSP est considéré comme 'unknown' lorsque ce plugin a effectué sa propre vérification de signature (les signatures n'ont pas été transmises à SA par un appelant) et qu'une méta-règle __TRUNCATED a été activée, indiquant que l'appelant a intentionnellement passé un message tronqué à SpamAssassin, ce qui était une raison probable d'échec de la vérification de signature.

Exemple :

adsp_override *.mydomain.example.com   discardable
adsp_override *.neversends.example.com discardable
adsp_override ebay.com
adsp_override *.ebay.com
adsp_override ebay.co.uk
adsp_override *.ebay.co.uk
adsp_override paypal.com
adsp_override *.paypal.com
adsp_override amazon.com
adsp_override ealerts.bankofamerica.com
adsp_override americangreetings.com
adsp_override egreetings.com
adsp_override bluemountain.com
adsp_override hallmark.com   all
adsp_override *.hallmark.com all
adsp_override youtube.com    custom_high
adsp_override google.com     custom_low
adsp_override gmail.com      custom_low
adsp_override googlemail.com custom_low
adsp_override yahoo.com      custom_low
adsp_override yahoo.com.au   custom_low
adsp_override yahoo.se       custom_low
adsp_override junkmailerkbw0rr.com nxdomain
adsp_override junkmailerd2hlsg.com nxdomain
# désactive effectivement les requêtes DNS ADSP pour tous les autres domaines :
adsp_override *              unknown
score DKIM_ADSP_ALL          2.5
score DKIM_ADSP_DISCARD     25
score DKIM_ADSP_NXDOMAIN     3
score DKIM_ADSP_CUSTOM_LOW   1
score DKIM_ADSP_CUSTOM_MED   3.5
score DKIM_ADSP_CUSTOM_HIGH  8
dkim_minimum_key_bits n (default: 1024)
La taille minimale en bits d'une clé de signature valide pour laquelle elle est considérée pour le welcome listing. De plus, la fonction d'évaluation check_dkim_valid() retournera false lorsqu'elle est appelée avec des domaines explicitement listés, et la fonction d'évaluation check_dkim_valid_author_sig() retournera false lorsque la clé est courte (indépendamment de ses arguments). Le réglage de l'option sur 0 désactive la vérification des tailles de clés.

Notez que l'option n'a aucun effet lorsque la fonction d'évaluation check_dkim_valid() est appelée sans arguments (comme dans une règle DKIM_VALID). La présence de toute signature valide dans un message n'a aucune valeur de réputation (sans être associée à un domaine particulier), quelle que soit la taille de la clé - n'importe qui peut préfixer sa propre signature dans une copie d'un e-mail d'un tiers et le transférer, ce qui le rend tout aussi peu fiable que sans cette signature. C'est aussi une raison pour laquelle une règle DKIM_VALID a un score proche de zéro, c'est-à-dire qu'un succès dans la règle n'est qu'informatif. Cette option est également évaluée dans les vérifications de signature ARC.

PARAMÈTRES ADMINISTRATEUR

dkim_timeout n (default: 5)
Combien de secondes il attend pour qu'une requête DKIM se termine avant de continuer l'analyse sans le résultat DKIM. Une valeur numérique est facultative, suivie d'une unité de temps (s, m, h, d, w, indiquant secondes (par défaut), minutes, heures, jours, semaines).
