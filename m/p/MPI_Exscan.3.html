MPI_Exscan, MPI_Iexscan - Réalise un balayage exclusif (réduction partielle)

Paramètres d'entrée

  • sendbuf: Buffer d'envoi (optionnel).
  • count: Nombre d'éléments dans le buffer d'envoi (entier).
  • datatype: Type de données des éléments du buffer d'envoi (handle).
  • op: Opération (handle).
  • comm: Communicateur (handle).

Paramètres de sortie

  • recvbuf: Buffer de réception (optionnel).
  • request: Requête (handle, non bloquant uniquement).
  • ierror: Fortran uniquement : État d'erreur (entier).

Description

MPI_Exscan est utilisé pour effectuer une réduction exclusive (réduction partielle) sur les données distribuées entre les processus appelants. L'opérateur retourne, dans le recvbuf du processus de rang i, le résultat de la réduction (calculé selon l'opération op) des valeurs dans les sendbuf des processus de rang 0, ..., i-1. Comparez cela avec la fonction MPI_Scan, qui calcule sur le rang 0, ..., i (inclusif). Les types d'opérations pris en charge, leurs significations et les contraintes sur les buffers d'envoi et de réception sont les mêmes que pour MPI_Reduce.

La valeur dans recvbuf du processus 0 est indéterminée et non fiable, car recvbuf n'est pas significatif pour le processus 0. La valeur de recvbuf du processus 1 est toujours la valeur dans sendbuf du processus 0.

Utilisation de l'option en place

L'option « en place » pour les communicateurs internes est spécifiée en passant MPI_IN_PLACE dans l'argument sendbuf. Dans ce cas, les données d'entrée sont prises depuis la réception et remplacées par les données de sortie.

Remarque : MPI_IN_PLACE est un type spécial ; il a les mêmes restrictions d'utilisation que MPI_BOTTOM.

En conséquence de l'option « en place » qui convertit le buffer de réception en un buffer d'envoi et de réception, une liaison Fortran incluant INTENT doit les marquer comme INOUT, et non comme OUT.

Notes

MPI ne spécifie pas quel processus effectue l'opération. En particulier, les deux processus 0 et 1 peuvent participer au calcul même si les résultats des recvbuf des deux processus sont dégénérés. Par conséquent, tous les processus, y compris 0 et 1, doivent fournir le même op.

On peut argumenter mathématiquement que la définition de MPI_Exscan est insatisfaisante car la valeur de sortie dans le processus 0 est indéterminée. La valeur de sortie mathématiquement correcte dans le processus 0 serait l'élément neutre de l'opération de réduction. Cependant, une telle définition ne fonctionnerait pas avec des fonctions d'opération personnalisées op car MPI ne pourrait pas « connaître » la valeur neutre pour ces opérations personnalisées.

Notes sur les opérations collectives

Les fonctions de réduction de type MPI_Op ne retournent pas de valeur d'erreur. Par conséquent, si les fonctions détectent une erreur, elles ne peuvent qu'appeler MPI_Abort ou ignorer silencieusement le problème. Par conséquent, si le gestionnaire d'erreurs est modifié de MPI_ERRORS_ARE_FATAL à autre chose (par exemple, MPI_ERRORS_RETURN), aucune erreur ne peut être indiquée.

La raison de cette situation est le problème de performance dans la garantie que toutes les routines de réduction retournent la même valeur d'erreur.

Erreurs

La plupart des routines MPI retournent une valeur d'erreur ; pour les routines C, la valeur de retour est le résultat de la fonction, et pour les routines Fortran, le dernier argument est la valeur d'erreur.

Avant que la valeur d'erreur ne soit retournée, le gestionnaire d'erreurs associé à l'objet de communication actuel (par exemple, communicateur, fenêtre, fichier) est appelé. S'il n'y a pas d'objet de communication associé à l'appel MPI, l'appel est considéré comme associé à MPI_COMM_SELF et appellera le gestionnaire d'erreurs associé à MPI_COMM_SELF. Lorsque MPI_COMM_SELF n'est pas initialisé (c'est-à-dire avant MPI_Init/MPI_Init_thread, après MPI_Finalize, ou lorsque le modèle de session est utilisé exclusivement), l'erreur déclenche le gestionnaire d'erreurs initial. Le gestionnaire d'erreurs initial peut être modifié en appelant MPI_Comm_set_errhandler sur MPI_COMM_SELF lors de l'utilisation du modèle du monde, ou sur l'argument CLI mpi_initial_errhandler de mpiexec ou sur la clé d'information MPI_Comm_spawn/MPI_Comm_spawn_multiple. Si aucun gestionnaire d'erreurs approprié n'est défini, le gestionnaire d'erreurs MPI_ERRORS_RETURN est appelé pour les fonctions MPI I/O et le gestionnaire d'erreurs MPI_ERRORS_ABORT pour toutes les autres fonctions MPI.

Open MPI inclut trois gestionnaires d'erreurs prédéfinis qui peuvent être utilisés :

  • MPI_ERRORS_ARE_FATAL Provoque l'abandon du programme par tous les processus connectés à MPI.
  • MPI_ERRORS_ABORT Un gestionnaire d'erreurs qui peut être invoqué sur un communicateur, une fenêtre, un fichier ou une session. Lorsqu'il est invoqué sur un communicateur, il agit comme si MPI_Abort avait été appelé sur ce communicateur. S'il est invoqué sur une fenêtre ou un fichier, il agit comme si MPI_Abort avait été appelé sur un communicateur contenant le groupe de processus dans la fenêtre ou le fichier correspondant. S'il est invoqué sur une session, il arrête uniquement le processus local.
  • MPI_ERRORS_RETURN Retourne un code d'erreur à l'application.

Les applications MPI peuvent également implémenter leurs propres gestionnaires d'erreurs en appelant :

  • MPI_Comm_create_errhandler puis MPI_Comm_set_errhandler
  • MPI_File_create_errhandler puis MPI_File_set_errhandler
  • MPI_Session_create_errhandler puis MPI_Session_set_errhandler ou dans M
