Paramètres d'entrée

  • sendbuf: Buffer d'envoi (choix).
  • count: Nombre d'éléments dans le buffer d'entrée (entier).
  • datatype: Type de données des éléments du buffer d'envoi (handle).
  • op: Opération (handle).
  • comm: Communicateur (handle).

Paramètres de sortie

  • recvbuf: Buffer de réception (choix).
  • request: Requête (handle, non bloquant seulement).
  • ierror: Uniquement en Fortran : Statut d'erreur (entier).

Description

MPI_Exscan effectue une réduction exclusive (réduction partielle) sur les données distribuées entre les processus appelants. Le résultat est renvoyé dans le recvbuf du processus de rang i, qui contient la réduction (calculée selon la fonction op) des valeurs dans les sendbuf des processus de rangs 0, ..., i-1. Comparez avec la fonction MPI_Scan, qui calcule sur le rang 0, ..., i (inclusif). Les types d'opérations supportés, leurs sémantiques et les restrictions sur les buffers d'envoi et de réception sont les mêmes que pour MPI_Reduce.

La valeur dans recvbuf du processus 0 est indéfinie et non fiable car recvbuf n'est pas significatif pour le processus 0. La valeur de recvbuf du processus 1 est toujours la valeur dans sendbuf du processus 0.

Utilisation de l'option "en place"

L'option « en place » pour les communicateurs internes est spécifiée en passant MPI_IN_PLACE dans l'argument sendbuf. Dans ce cas, les données d'entrée sont tirées du buffer de réception et remplacées par les données de sortie.

Remarque : MPI_IN_PLACE est un type spécial ; il a les mêmes restrictions que MPI_BOTTOM.

Suite à l'utilisation de l'option « en place », le buffer de réception devient un buffer d'envoi et de réception. Une signature de liaison Fortran incluant INTENT doit les marquer comme INOUT, et non comme OUT.

Notes

MPI ne spécifie pas quel processus calcule quelle opération. En particulier, les deux processus 0 et 1 peuvent participer au calcul même si les résultats pour les deux processus recvbuf sont dégénérés. Par conséquent, tous les processus, y compris 0 et 1, doivent fournir le même op.

On peut argumenter mathématiquement que la définition de MPI_Exscan est insatisfaisante car la valeur dans recvbuf du processus 0 est indéfinie. La valeur « mathématiquement correcte » pour le processus 0 serait l'élément neutre de l'opération de réduction. Cependant, une telle définition ne fonctionnerait pas correctement avec des fonctions d'opération personnalisées op, car MPI ne pourrait pas « connaître » la valeur neutre pour ces opérations personnalisées.

Notes sur les opérations collectives

Les fonctions de réduction de type MPI_Op ne renvoient pas de valeur d'erreur. Par conséquent, si les fonctions détectent une erreur, elles ne peuvent qu'appeler MPI_Abort ou ignorer le problème. Par conséquent, si le gestionnaire d'erreurs est changé de MPI_ERRORS_ARE_FATAL à autre chose (par exemple, MPI_ERRORS_RETURN), aucune erreur ne peut être signalée.

La raison est le problème de performance dans la garantie que toutes les routines collectives renvoient la même valeur d'erreur.

Erreurs

La plupart des routines MPI renvoient une valeur d'erreur ; en C, le résultat de la fonction et en Fortran, le dernier argument.

Avant de renvoyer la valeur d'erreur, le gestionnaire d'erreurs associé à l'objet de communication (par exemple, communicateur, fenêtre, fichier) utilisé est appelé. S'il n'y a pas d'objet de communication associé à l'appel MPI, l'appel est considéré comme associé à MPI_COMM_SELF et appellera le gestionnaire d'erreurs associé à MPI_COMM_SELF. Lorsque MPI_COMM_SELF n'est pas initialisé (c'est-à-dire avant MPI_Init/MPI_Init_thread, après MPI_Finalize, ou lorsque le modèle de sessions est utilisé exclusivement), l'erreur déclenche le gestionnaire d'erreurs initial. Le gestionnaire d'erreurs initial peut être changé en appelant MPI_Comm_set_errhandler sur MPI_COMM_SELF lors de l'utilisation du modèle du monde, ou l'argument mpi_initial_errhandler de mpiexec ou la clé info de MPI_Comm_spawn/MPI_Comm_spawn_multiple. Si aucun autre gestionnaire d'erreurs approprié n'est configuré, le gestionnaire d'erreurs MPI_ERRORS_RETURN est appelé pour les fonctions d'E/S MPI et le gestionnaire d'erreurs MPI_ERRORS_ABORT pour toutes les autres fonctions MPI.

Open MPI inclut trois gestionnaires d'erreurs prédéfinis qui peuvent être utilisés :

  • MPI_ERRORS_ARE_FATAL Arrête tous les processus MPI connectés.
  • MPI_ERRORS_ABORT Un gestionnaire d'erreurs qui peut être invoqué sur un communicateur, une fenêtre, un fichier ou une session. Lorsqu'il est invoqué sur un communicateur, il agit comme si MPI_Abort avait été appelé sur ce communicateur. S'il est invoqué sur une fenêtre ou un fichier, il agit comme si MPI_Abort avait été appelé sur un communicateur contenant le groupe de processus dans la fenêtre ou le fichier correspondant. S'il est invoqué sur une session, il arrête uniquement le processus local.
  • MPI_ERRORS_RETURN Renvoie un code d'erreur à l'application.

Les applications MPI peuvent également implémenter leurs propres gestionnaires d'erreurs en appelant :

  • MPI_Comm_create_errhandler puis MPI_Comm_set_errhandler
  • MPI_File_create_errhandler puis MPI_File_set_errhandler
  • MPI_Session_create_errhandler et
hen MPI_Session_set_errhandler ou à MPI_Session_init
  • MPI_Win_create_errhandler puis MPI_Win_set_errhandler

    • Notez que MPI ne garantit pas qu'un programme MPI puisse continuer après une erreur.

    Voir la page man MPI pour une liste complète des codes d'erreur MPI.

    Voir la section Gestion des erreurs de la norme MPI-3.1 pour plus d'informations.
