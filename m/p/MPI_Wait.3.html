MPI_WAIT(3) Open MPI MPI_WAIT(3)

MPI_Wait — Attend la fin d'un envoi ou d'une réception MPI.

SYNTAXE

Syntaxe C

#include <mpi.h>
int MPI_Wait(MPI_Request *request, MPI_Status *status)

Syntaxe Fortran

USE MPI
! ou la forme plus ancienne: INCLUDE 'mpif.h'
MPI_WAIT(REQUEST, STATUS, IERROR)
     INTEGER REQUEST, STATUS(MPI_STATUS_SIZE), IERROR

Syntaxe Fortran 2008

USE mpi_f08
MPI_Wait(request, status, ierror)
     TYPE(MPI_Request), INTENT(INOUT) :: request
     TYPE(MPI_Status) :: status
     INTEGER, OPTIONAL, INTENT(OUT) :: ierror

PARAMÈTRE D'ENTRÉE

•
request: Requête (handle).

PARAMÈTRES DE SORTIE

  • status: Objet de statut (statut).
  • ierror: Fortran uniquement : Statut d'erreur (entier).

DESCRIPTION

Un appel à MPI_Wait retourne lorsque l'opération identifiée par la requête est terminée. Si l'objet de communication associé à cette requête a été créé par un appel d'envoi ou de réception non bloquant, alors l'objet est désalloué par l'appel à MPI_Wait et le handle de requête est mis à MPI_REQUEST_NULL.

L'appel retourne, dans status, des informations sur l'opération terminée. Le contenu de l'objet de statut pour une opération de réception peut être accédé comme décrit dans la sous-section "Statut de retour" du chapitre "Communication Point-à-Point" du Standard MPI. L'objet de statut pour une opération d'envoi peut être interrogé par un appel à MPI_Test_cancelled (voir la section "Sonde et Annulation" du Standard MPI).

Si votre application n'a pas besoin d'examiner le champ status, vous pouvez économiser des ressources en utilisant la constante prédéfinie MPI_STATUS_IGNORE comme valeur spéciale pour l'argument status.

Il est permis d'appeler MPI_Wait avec un argument de requête nul ou inactif. Dans ce cas, l'opération retourne immédiatement avec un statut vide.

NOTES

Le retour réussi de MPI_Wait après un MPI_Ibsend implique que le buffer d'envoi utilisateur peut être réutilisé, c'est-à-dire que les données ont été envoyées ou copiées dans un buffer attaché avec MPI_Buffer_attach. Notez qu'à ce stade, nous ne pouvons plus annuler l'envoi (pour plus d'informations, voir la section "Sonde et Annulation" du Standard MPI). Si une réception correspondante n'est jamais postée, alors le buffer ne peut pas être libéré. Ceci va un peu à l'encontre de l'objectif énoncé de MPI_Cancel (pouvoir toujours libérer l'espace du programme qui a été engagé envers le sous-système de communication).

Exemple : Utilisation simple d'opérations non bloquantes et de MPI_Wait.

CALL MPI_COMM_RANK(comm, rank, ierr)
IF(rank == 0) THEN
    CALL MPI_ISEND(a(1), 10, MPI_REAL, 1, tag, comm, request, ierr)
    **** do some computation ****
    CALL MPI_WAIT(request, status, ierr)
ELSE IF (rank == 1) THEN
    CALL MPI_IRECV(a(1), 15, MPI_REAL, 0, tag, comm, request, ierr)
    **** do some computation ****
    CALL MPI_WAIT(request, status, ierr)
END IF

ERREURS

Presque toutes les routines MPI retournent une valeur d'erreur ; les routines C comme résultat de retour de la fonction et les routines Fortran dans le dernier argument.

Avant que la valeur d'erreur ne soit retournée, le gestionnaire d'erreurs MPI actuel associé à l'objet de communication (par exemple, communicateur, fenêtre, fichier) est appelé. Si aucun objet de communication n'est associé à l'appel MPI, alors l'appel est considéré comme attaché à MPI_COMM_SELF et appellera le gestionnaire d'erreurs MPI associé. Lorsque MPI_COMM_SELF n'est pas initialisé (c'est-à-dire avant MPI_Init/MPI_Init_thread, après MPI_Finalize, ou lors de l'utilisation exclusive du modèle Sessions) l'erreur déclenche le gestionnaire d'erreurs initial. Le gestionnaire d'erreurs initial peut être modifié en appelant MPI_Comm_set_errhandler sur MPI_COMM_SELF lors de l'utilisation du modèle World, ou l'argument CLI mpi_initial_errhandler pour mpiexec ou la clé d'information pour MPI_Comm_spawn/MPI_Comm_spawn_multiple. Si aucun autre gestionnaire d'erreurs approprié n'a été défini, alors le gestionnaire d'erreurs MPI_ERRORS_RETURN est appelé pour les fonctions E/S MPI et le gestionnaire d'erreurs MPI_ERRORS_ABORT est appelé pour toutes les autres fonctions MPI.

Open MPI inclut trois gestionnaires d'erreurs prédéfinis qui peuvent être utilisés :

  • MPI_ERRORS_ARE_FATAL Provoque l'arrêt du programme de tous les processus MPI connectés.
  • MPI_ERRORS_ABORT Un gestionnaire d'erreurs qui peut être invoqué sur un communicateur, une fenêtre, un fichier ou une session. Lorsqu'il est appelé sur un communicateur, il agit comme si MPI_Abort était appelé sur ce communicateur. S'il est appelé sur une fenêtre ou un fichier, il agit comme si MPI_Abort était appelé sur un communicateur contenant le groupe des processus de la fenêtre ou du fichier correspondant. S'il est appelé sur une session, il n'aborte que le processus local.
  • MPI_ERRORS_RETURN Retourne un code d'erreur à l'application.

Les applications MPI peuvent également implémenter leurs propres gestionnaires d'erreurs en appelant :

  • MPI_Comm_create_errhandler puis MPI_Comm_set_errhandler
  • MPI_File_create_errhandler puis MPI_File_set_errhandler
  • MPI_Session_create_errhandler puis MPI_Session_set_errhandler ou à MPI_Session_init
  • MPI_Win_create_errhandler puis MPI_Win_set_errhandler

Notez que MPI ne garantit pas qu'un programme MPI puisse continuer après une erreur.

Voir la page man MPI pour une liste complète des codes d'erreur MPI.

Voir la section Gestion des erreurs de la norme MPI-3.1 pour plus d'informations.

Notez que conformément à la section "Statut de retour" du chapitre "Communication Point-à-Point" du Standard MPI, les erreurs MPI sur les requêtes passées à MPI_Wait ne définissent pas le champ status.MPI_ERROR dans le status retourné. Le code d'erreur est toujours passé au gestionnaire d'erreurs backend et peut être renvoyé à l'appelant via la valeur de retour de MPI_Wait si le gestionnaire d'erreurs backend le retourne. Le gestionnaire d'erreurs MPI prédéfini MPI_ERRORS_RETURN présente par exemple ce comportement.
