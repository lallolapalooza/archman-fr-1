NOM

Locale::Messages - Obtention de messages de traduction Gettext

SYNOPIS

use Locale::Messages qw(:locale_h :libintl_h);
gettext $msgid;
dgettext $textdomain, $msgid;
dcgettext $textdomain, $msgid, LC_MESSAGES;
ngettext $msgid, $msgid_plural, $count;
dngettext $textdomain, $msgid, $msgid_plural, $count;
dcngettext $textdomain, $msgid, $msgid_plural, $count, LC_MESSAGES;
pgettext $msgctxt, $msgid;
dpgettext $textdomain, $msgctxt, $msgid;
dcpgettext $textdomain, $msgctxt, $msgid, LC_MESSAGES;
npgettext $msgctxt, $msgid, $msgid_plural, $count;
dnpgettext $textdomain, $msgctxt, $msgid, $msgid_plural, $count;
dcnpgettext $textdomain, $msgctxt, $msgid, $msgid_plural, $count, LC_MESSAGES;
textdomain $textdomain;
bindtextdomain $textdomain, $directory;
bind_textdomain_codeset $textdomain, $encoding;
bind_textdomain_filter $textdomain, \&filter, $data;
turn_utf_8_on ($variable);
turn_utf_8_off ($variable);
nl_putenv ('OUTPUT_CHARSET=koi8-r');
my $category = LC_CTYPE;
my $category = LC_NUMERIC;
my $category = LC_TIME;
my $category = LC_COLLATE;
my $category = LC_MONETARY;
my $category = LC_MESSAGES;
my $category = LC_ALL;

DESCRIPTION

Le module Locale::Messages est un wrapper vers l'interface de traduction de messages conforme à Uniforum, utilisée par exemple dans GNU gettext et Solaris de Sun. Il est intentionnellement conçu pour permettre à Locale::Messages(3) de basculer entre différentes implémentations des modules de bibliothèque sous-jacents, mais cette fonctionnalité n'est pas encore implémentée.

Normalement, vous ne devriez pas utiliser ce module directement, mais l'interface de haut niveau Locale::TextDomain(3) offre une interface plus simple. Cette description reste donc brève. Veuillez consulter la documentation du manuel gettext disponible à l'adresse http://www.gnu.org/manual/gettext/ pour des informations détaillées et de fond sur le sujet.

Le module sous-jacent Locale::gettext_pp(3) fournit l'implémentation Perl de gettext() et des fonctions associées.

FONCTIONS

Le module n'exporte rien par défaut. Chaque fonction doit être explicitement importée ou via une étiquette d'exportation ("EXPORT TAGS").

gettext MSGID
Renvoie la traduction de MSGID. Exemple : 
print gettext "Hello World!\n";

Si aucune traduction ne peut être trouvée, le MSGID original est renvoyé, c'est-à-dire que la fonction ne produit jamais d'erreur et ne corrompt jamais votre message original.

Note pour Perl 5.6 et versions ultérieures : La chaîne renvoyée aura toujours le drapeau UTF-8 désactivé par défaut. Pour modifier ce comportement, consultez la documentation de la fonction bind_textdomain_filter().

Une erreur courante est la suivante :

print gettext "Hello $name!";

Perl interpolera la variable $name avant que la fonction ne voie la chaîne. Aucune traduction ne sera trouvée si le message dans le catalogue de traduction ne contient pas "Hello Tom!", "Hello Dick!" ou "Hello Harry!".

L'utilisation de printf() et de ses fonctions associées présente ses propres problèmes :

print sprintf (gettext ("This is the %s %s."), $color, $thing);

(L'exemple est stupide car $color et $thing ne seront pas traduits ici ...).

En anglais, l'adjectif (la couleur) précède le nom, mais dans de nombreuses autres langues (par exemple, le français ou l'italien) l'ordre est différent. C'est pourquoi le traducteur de messages pourrait avoir du mal à trouver une traduction qui fonctionne et qui ne soit pas stupide dans la langue cible. De nombreuses implémentations de printf() en C permettent de changer l'ordre des arguments, et un traducteur français pourrait dire :

"C'est le %2$s %1$s."

Le printf() de Perl implémente cette fonctionnalité depuis la version 5.8 ou ultérieure. Par conséquent, vous ne pouvez l'utiliser que si vous êtes sûr que votre logiciel fonctionnera avec Perl 5.8 ou une version ultérieure.

Un autre inconvénient de l'utilisation de printf() est la syntaxe ardue (bien que ce ne soit pas pour vous, mais cela pourrait l'être pour les traducteurs de votre logiciel).

Voir la description de la fonction "__x()" dans Locale::TextDomain(3) pour une meilleure façon de résoudre ce problème.

Les identifiants de messages non ASCII ...

Vous devez noter que la fonction (et toutes les autres fonctions similaires de ce module) effectue une comparaison octet par octet du MSGID pour rechercher dans le catalogue de traduction, indépendamment du fait que les drapeaux UTF-8 soient activés ou non, que la chaîne semble être en UTF-8, que la pragma utf8(3pm) soit utilisée ou toute autre méthode d'identification de jeux de caractères des versions futures ou passées de perl(1).

L'utilisation d'autres caractères non ASCII dans le code Perl est un appel au désastre, un cauchemar de compatibilité. De plus, GNU gettext n'a introduit que récemment le support des jeux de caractères non ASCII dans les sources, et le support de cette fonctionnalité peut ne pas être disponible partout. Si vous souhaitez utiliser des MSGID dans des jeux de caractères non ASCII, il est judicieux de choisir UTF-8. Cela minimisera le risque que perl(1) lui-même ne les corrompe et garantira également que vous pourrez traduire votre projet dans n'importe quelle langue cible ultérieure.

D'autres fonctionnalités de jeux de caractères peuvent théoriquement fonctionner. Cependant, l'utilisation d'un jeu de caractères différent dans le code Perl qui n'est pas utilisé dans vos catalogues de traduction sera inexplicable car la recherche s'effectue octet par octet et les chaînes avec des caractères non ASCII ne seront pas trouvées.

Même si vous résolvez tous ces problèmes, un dernier obstacle demeure : l'API de traduction du runtime gettext ne permet pas de spécifier le jeu de caractères des fichiers sources (y compris les chaînes originales). Par conséquent, - sans indication du jeu de caractères d'entrée - les chaînes non traduites ne seront pas converties dans le jeu de caractères de sortie. Autrement dit : si le jeu de caractères de sortie (non déterminable) diffère du jeu de caractères des fichiers sources, la sortie peut être un mélange des deux jeux de caractères. Il est inutile d'essayer de résoudre ce problème dans la version Perl pure des fonctions gettext. Car la compatibilité entre Perl et C est un prix trop élevé à payer.

Tout cela se résume à ceci : n'utilisez que des caractères ASCII dans vos chaînes de traduction !

dgettext TEXTDOMAIN, MSGID
Identique à gettext(), mais recherche le message pour le TEXTDOMAIN spécifié au lieu du domaine par défaut. Si vous avez des doutes sur ce qu'est un textdomain, vous devriez lire attentivement Locale::TextDomain(3).
dcgettext TEXTDOMAIN, MSGID, CATEGORY
Identique à dcgettext(), mais recherche le message dans la CATEGORY spécifiée au lieu de la catégorie par défaut "LC_MESSAGES".
ngettext MSGID, MSGID_PLURAL, COUNT
Obtient la traduction appropriée pour COUNT éléments. Dans les anciens logiciels, on trouve souvent quelque chose comme ceci :

print "$count file(s) deleted.\n";

ou

printf "$count file%s deleted.\n", $count == 1 ? '' : 's';

Le premier exemple semble inadéquat, le second ne fonctionne qu'en anglais et dans les langues ayant des règles de pluriel similaires. Avant ngettext(), la pratique recommandée pour les programmes internationalisés était :

if ($count == 1) {
    print gettext "One file deleted.\n";
} else {
    printf gettext "%d files deleted.\n";
}

C'est une nuisance pour le programmeur et ce n'est toujours pas toujours suffisant pour une traduction adéquate. De nombreuses langues ont des idées complètement différentes sur les nombres. Certaines (français, italien, ...) traitent 0 et 1 de manière similaire, d'autres ne font aucune distinction (coréen, coréen, chinois, ...) d'autres encore ont deux formes plurielles ou plus (russe, letton, tchèque, polonais, ...). printf (ngettext ("One file deleted.\n",
                 "%d files deleted.\n",
                 $count), # argument to ngettext!
        $count);          # argument to printf!

En anglais, ou si aucune traduction ne peut être trouvée, le premier argument (MSGID) est choisi si $count est un, le second sinon. Pour les autres langues, la forme plurielle correcte (de 1, 2, 3, 4, ...) est automatiquement choisie également. Vous n'avez pas besoin de connaître les règles de pluriel dans la langue cible, ngettext() s'en chargera.

Ceci est suffisant la plupart du temps, mais vous devrez faire preuve de créativité dans des cas comme

printf "%d file(s) deleted, and %d file(s) created.\n";
dngettext TEXTDOMAIN, MSGID, MSGID_PLURAL, COUNT
Comme ngettext() mais récupère la traduction à partir du textdomain spécifié au lieu du domaine par défaut.
dcngettext TEXTDOMAIN, MSGID, MSGID_PLURAL, COUNT, CATEGORY
Comme dngettext() mais récupère la traduction à partir de la catégorie spécifiée, au lieu de la catégorie par défaut "LC_MESSAGES".
pgettext MSGCTXT, MSGID
Retourne la traduction de MSGID, étant donné le contexte de MSGCTXT.

Les deux éléments sont utilisés comme une clé unique dans le catalogue de messages.

Ceci permet au traducteur d'avoir deux entrées pour des mots qui peuvent se traduire par différents mots étrangers en fonction de leur contexte. Par exemple, le mot "View" peut être un nom ou un verbe, qui peut être utilisé dans un menu comme File->View ou View->Source.

pgettext "Verb: To View", "View\n";
pgettext "Noun: A View", "View\n";

Les lignes ci-dessus rechercheront toutes deux des entrées différentes dans le catalogue de messages.

Une utilisation typique concerne les programmes GUI. Imaginez un programme avec un menu principal et la notoire entrée "Open" dans le menu "File". Maintenant, imaginez qu'il y ait une autre entrée de menu Preferences->Advanced->Policy où vous avez le choix entre les alternatives "Open" et "Closed". En anglais, "Open" est le texte adéquat aux deux endroits. Dans d'autres langues, il est très probable que vous ayez besoin de deux traductions différentes. Par conséquent, vous écririez maintenant :

pgettext "File|", "Open";
pgettext "Preferences|Advanced|Policy", "Open";

En anglais, ou si aucune traduction ne peut être trouvée, le deuxième argument (MSGID) est retourné.

La fonction a été introduite avec la version 1.17 de libintl-perl.

dpgettext TEXTDOMAIN, MSGCTXT, MSGID
Comme pgettext(), mais récupère le message pour le TEXTDOMAIN spécifié au lieu du domaine par défaut.

La fonction a été introduite avec la version 1.17 de libintl-perl.

dcpgettext TEXTDOMAIN, MSGCTXT, MSGID, CATEGORY
Comme dpgettext() mais récupère le message à partir de la CATEGORY spécifiée au lieu de la catégorie par défaut "LC_MESSAGES".

La fonction a été introduite avec la version 1.17 de libintl-perl.

npgettext MSGCTXT, MSGID, MSGID_PLURAL, COUNT
Comme ngettext() avec l'ajout du contexte comme dans pgettext().

En anglais, ou si aucune traduction ne peut être trouvée, le deuxième argument (MSGID) est choisi si $count est un, le troisième sinon.

La fonction a été introduite avec la version 1.17 de libintl-perl.

dnpgettext TEXTDOMAIN, MSGCTXT, MSGID, MSGID_PLURAL, COUNT
Comme npgettext() mais récupère la traduction à partir du textdomain spécifié au lieu du domaine par défaut.

La fonction a été introduite avec la version 1.17 de libintl-perl.

dcnpgettext TEXTDOMAIN, MSGCTXT, MSGID, MSGID_PLURAL, COUNT, CATEGORY
Comme dnpgettext() mais récupère la traduction à partir de la catégorie spécifiée, au lieu de la catégorie par défaut "LC_MESSAGES".

La fonction a été introduite avec la version 1.17 de libintl-perl.

textdomain TEXTDOMAIN
Définit le textdomain par défaut (initialement 'messages').
bindtextdomain TEXTDOMAIN, DIRECTORY
Lie TEXTDOMAIN à DIRECTORY. Hein ? Un exemple : 
bindtextdomain "my-package", "./mylocale";

Supposons que la locale sélectionnée (en fait la locale sélectionnée pour la catégorie "LC_MESSAGES") du programme soit 'fr_CH', alors le catalogue de messages sera attendu dans ./mylocale/fr_CH/LC_MESSAGES/my-package.mo.

bind_textdomain_codeset TEXTDOMAIN, ENCODING
Définit l'encodage de sortie pour TEXTDOMAIN à ENCODING.
bind_textdomain_filter TEXTDOMAN, CODEREF, DATA
bind_textdomain_filter TEXTDOMAN, CODEREF
Par défaut, Locale::Messages désactivera le flag utf-8 de tous les messages renvoyés. Si vous souhaitez modifier ce comportement, vous pouvez passer une référence à une sous-routine qui effectue différentes actions - par exemple, activer le flag utf-8, ou le laisser inchangé. La fonction de rappel sera appelée avec DATA comme premier argument, et la chaîne potentiellement traduite comme second argument. Elle devrait renvoyer la chaîne potentiellement modifiée.

Si vous souhaitez qu'une méthode d'objet soit appelée, passez l'objet lui-même dans le paramètre data et écrivez une fonction wrapper. Exemple :

sub wrapper { 
    my ($string, $obj) = @_;

    $obj->filterMethod ($string);
}
my $obj = MyPackage->new;
bind_textdomain_filter ('mydomain', \&wrapper, $obj);

La fonction ne peut pas échouer et renvoie toujours une valeur vraie.

Attention : Si vous utilisez la fonction pour définir le flag utf-8, il est de votre responsabilité de vous assurer que la sortie est bien en utf-8. Vous ne devriez l'utiliser que si vous avez défini la variable d'environnement OUTPUT_CHARSET à "utf-8". De plus, vous devriez appeler bind_textdomain_codeset() avec "utf-8" comme deuxième argument.

Steven Haryanto a écrit un module Locale::TextDomain::UTF8(3pm) qui traite du même problème.

Cette fonction a été introduite dans libintl-perl 1.16 et ne fait pas partie de l'API standard gettext.

turn_utf_8_on VARIABLE
Retourne VARIABLE mais avec le flag UTF-8 (connu uniquement dans Perl >=5.6) garanti d'être activé. Cette fonction ne s'intègre pas vraiment dans le module, mais elle est souvent utile néanmoins.

Le flag ne signifie pas que la chaîne est réellement en utf-8 valide !

La fonction a été introduite avec la version 1.16 de libintl-perl.

turn_utf_8_off VARIABLE
Retourne VARIABLE mais avec le flag UTF-8 (connu uniquement dans Perl >=5.6) garanti d'être désactivé. Cette fonction ne s'intègre pas vraiment dans le module, mais elle est souvent utile néanmoins.

La fonction a été introduite avec la version 1.07 de libintl-perl.

select_package PACKAGE
Par défaut, Locale::Messages tentera de charger la version XS de l'implémentation gettext, c'est-à-dire Locale::gettext_xs(3) et se rabattra sur l'implémentation pure Perl Locale::gettext_pp(3). Vous pouvez outrepasser ce comportement en passant la chaîne "gettext_pp" ou "gettext_xs" à la fonction select_package(). Passer "gettext_pp" ici préférera l'implémentation pure Perl.

Vous voudrez normalement l'utiliser dans un bloc BEGIN de votre script principal.

La fonction a été introduite avec la version 1.03 de libintl-perl et ne fait pas partie de l'API standard gettext.

À partir de la version 1.22, vous pouvez passer d'autres noms de paquets que "gettext_pp" ou "gettext_xs" et utiliser un backend complètement différent. Il incombe à l'appelant de s'assurer que le paquet sélectionné offre la même interface que les deux paquets standard.

Un paquet qui offre cette fonctionnalité est Locale::gettext_dumb(3pm).

nl_putenv ENVSPEC
Ressemble à la fonction ANSI C putenv(3). Le seul but de cette fonction est de contourner certaines idiosyncrasies dans le traitement de l'environnement des systèmes Windows. Si vous souhaitez définir ou supprimer des variables d'environnement de manière portable, utilisez cette fonction au lieu de manipuler directement %ENV.

L'argument ENVSPEC peut avoir trois formes différentes.

LANGUAGE=fr_CH
Ceci définirait la variable d'environnement "LANGUAGE" à "fr_CH".
LANGUAGE=
Normalement, cela définirait la variable d'environnement "LANGUAGE" à une chaîne vide. Sous Windows, cependant, la variable d'environnement sera supprimée à la place (et ne sera plus présente dans %ENV). Comme les variables d'environnement vides sont inutiles dans libintl-perl, considérez cette utilisation comme obsolète.
LANGUAGE
Ceci supprimera la variable d'environnement LANGUAGE. Si vous êtes familier avec l'implémentation défectueuse de putenv(3) (resp. _putenv()) dans

Le fichier standard de la bibliothèque C de MS-Windows, vous pourriez soupçonner qu'il s'agit d'un argument invalide. Ce n'est pas le cas !

La fonction renvoie true en cas de succès et false en cas d'échec. Les raisons possibles d'échec incluent une syntaxe invalide ou, uniquement sous Windows, un échec d'allocation d'espace pour un nouveau bloc de variables d'environnement ($! sera alors défini).

Pourquoi tous ces efforts ? Les versions 32 bits de MS-DOS (actuellement Windows 95/98/ME/NT/2000/XP/CE/.NET) conservent deux blocs distincts de variables d'environnement par processus. Lequel de ces blocs est considéré comme le « correct » dépend d'une option de compilation de l'interpréteur Perl. Cependant, si vous avez construit la version XS Locale::gettext_xs(3) sous Windows, la bibliothèque sous-jacente pourrait utiliser un bloc différent, et les modifications que vous auriez apportées à %ENV ne seraient pas visibles par la bibliothèque.

La fonction nl_putenv() est principalement un moyen amusant de dire :

LANGUAGE=some_value

mais elle essaie de faire de son mieux pour transmettre cette information à la bibliothèque gettext. Sur d'autres systèmes d'exploitation, cette fonction n'opère que sur %ENV, tandis que sous Windows, elle appellera la fonction C _putenv() (après avoir effectué un nettoyage de ses arguments), avant de manipuler %ENV.

Veuillez noter que votre %ENV est automatiquement mis à jour par nl_putenv().

Cette fonction a été introduite dans la version 1.10 de libintl-perl.

setlocale
Modifie et interroge la locale du programme, voir la documentation de setlocale() dans POSIX(3pm) à la place.

Sur certains systèmes, un appel C à setlocale() - avec le support du préprocesseur C - est en réalité un appel à libintl_setlocale(), qui est un wrapper vers le système setlocale(3). Le non-appel à libintl_setlocale() peut causer certains problèmes. Sur de tels systèmes, Locale::Messages::setlocale() appellera le wrapper libintl_setlocale(). Si vous voulez éviter des problèmes, vous devriez toujours appeler l'implémentation de setlocale() dans Locale::Messages(3pm).

Voir https://rt.cpan.org/Public/Bug/Display.html?id=83980 ou https://savannah.gnu.org/bugs/?38162, et https://savannah.gnu.org/bugs/?func=detailitem&item_id=44645 pour une discussion de ce problème.

Cette fonction a été introduite dans la version 1.24 de libintl-perl.

CONSTANTES

Vous pouvez (peut-être) obtenir les mêmes constantes de POSIX(3); voir là-bas une description détaillée.

LC_CTYPE
LC_NUMERIC
LC_TIME
LC_COLLATE
LC_MONETARY
LC_MESSAGES
Cette catégorie de locales a été la raison pour laquelle ces constantes de POSIX(3) ont été incluses ici. Même si elle était présente dans votre système C inclus dans locale.h, elle n'était pas fournie par POSIX(3). Perl 5.8 et versions ultérieures semblent exporter la constante si elle est disponible, bien qu'elle ne soit pas documentée dans POSIX(3).

Locale::Messages(3) tente de faire un effort pour stimuler la valeur de cette catégorie pour tous les systèmes et suppose par défaut la valeur arbitraire 1729.

LC_ALL
Si vous spécifiez la catégorie LC_ALL comme premier argument à POSIX::setlocale(), *toutes* les catégories de locales seront immédiatement affectées.

TAGS D'EXPORTATION

Le module n'exporte rien à moins qu'il ne soit explicitement demandé. Vous pouvez importer des groupes de fonctions via deux tags :

use Locale::Messages (':locale_h')
Importe les fonctions normalement définies dans le fichier d'inclusion C locale.h :

dgettext()
dcgettext()

dngettext()

dcpgettext()
npgettext()
dnpgettext()
dcnpgettext()

use Locale::Messages (':libintl_h')

UTILISATION

Un exemple complet :

1: use Locale::Messages qw(:locale_h :libintl_h);
2: use POSIX qw (setlocale);
3: setlocale (LC_MESSAGES, '');
4: textdomain ('my-package');
5: bindtextdomain ('my-package' => '/usr/local/share/locale');
6:
7: print gettext ("Hello world!\n");

Pas à pas : La ligne 1 importe les fonctions et constantes nécessaires. À la ligne 3, on définit la langue pour la catégorie LC_MESSAGES aux paramètres par défaut de l'utilisateur. Pour les programmes C, on lit souvent que LC_ALL est la meilleure catégorie ici, mais cela changera également la langue pour LC_NUMERIC et de nombreux autres programmes ne fonctionneront pas correctement après avoir modifié cette catégorie dans Perl ; choisissez votre propre poison !

À la ligne 4, nous indiquons que tous les messages (traductions) sans spécification explicite de domaine doivent être récupérés du catalogue de messages pour le domaine 'my-package'. La ligne 5 a pour effet de rechercher le catalogue de messages dans le dossier '/usr/local/share/locale'.

Si l'utilisateur a sélectionné la langue 'fr_CH' et si le fichier '/usr/local/share/locale/fr_CH/LC_MESSAGES/my-package.mo' existe et contient un fichier objet GNU avec une traduction pour la chaîne 'Hello world!\n', alors la ligne 7 imprimera la traduction française (pour la Suisse CH) sur STDOUT.

La documentation de GNU gettext explique comment extraire les chaînes traduisibles de vos fichiers Perl et comment créer des catalogues de messages.

Un autre exemple moins portable : Si votre système utilise la GNU libc, vous devriez pouvoir trouver plusieurs fichiers nommés 'libc.mo', le catalogue de messages pour la bibliothèque elle-même. Si vous avez trouvé ces fichiers dans '/usr/share/locale', vous pouvez essayer ce qui suit :

use Locale::Messages qw(:locale_h :libintl_h);
use POSIX qw (setlocale);
setlocale LC_MESSAGES, "";
textdomain "libc";
# Le suivant n'est vraiment pas nécessaire, car c'est l'un des répertoires de recherche par défaut.
bindtextdomain libc => '/usr/share/locale';
bind_textdomain_codeset libc => 'iso-8859-1';
print gettext ("No such file or directory");

Voir Locale::TextDomain(3pm) pour des méthodes plus simples.
