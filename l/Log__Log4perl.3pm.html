RÉSUMÉ

Log::Log4perl fournit une API puissante pour la journalisation de votre application

DESCRIPTION

Log::Log4perl vous permet de contrôler et de régler le comportement de journalisation de votre système depuis l'extérieur. Il implémente le populaire paquet de journalisation (basé sur Java) Log4j en Perl pur.

Pour un guide détaillé sur l'utilisation de Log::Log4perl, veuillez lire :

http://www.perl.com/pub/a/2002/09/11/log4perl.html

La journalisation est meilleure qu'un débogueur si vous voulez savoir ce qui se passe dans votre code pendant son exécution. Cependant, les paquets de journalisation traditionnels sont trop statiques et génèrent beaucoup de messages de journalisation dans vos fichiers journaux qui ne vous aident pas.

Log::Log4perl est différent. Il vous permet de contrôler le nombre de messages de journalisation générés à trois niveaux différents :

  • À partir d'un emplacement central de votre système (soit dans un fichier de configuration, soit dans le code d'initialisation), vous spécifiez quels composants (classes, fonctions) de votre système doivent générer des journaux.
  • Vous définissez le niveau de détail de ces composants en spécifiant des niveaux de journalisation.
  • Vous spécifiez également quels appender (récepteurs) vous souhaitez alimenter vos messages de journalisation (« Imprimer à l'écran et aussi les ajouter à /tmp/my.log ») et quel format (« Écrire d'abord la date, puis le nom du fichier et le numéro de ligne, puis le message de journalisation ») ils devraient avoir.

C'est un mécanisme très puissant et flexible. Vous pouvez activer et désactiver vos journaux à tout moment, spécifier le niveau de détail et le faire dépendre du sous-système qui s'exécute actuellement.

Je vais vous donner un exemple : Vous pourriez rencontrer un problème dans le composant "MySystem::Helpers::ScanDir". Activer des messages de débogage détaillés dans tout le système génère une multitude de messages inutiles qui ralentissent votre système. Cependant, avec Log::Log4perl, vous pouvez dire au système : « Enregistrez uniquement les erreurs graves dans le fichier journal. Ouvrez un nouveau fichier journal, activez les messages de débogage complets dans le composant "MySystem::Helpers::ScanDir" et placez tous les messages qui en proviennent dans le nouveau fichier journal ». Et tout cela est possible en modifiant des paramètres dans un fichier de configuration, que votre système peut relire même pendant son exécution !

Comment l'utiliser

Le paquet "Log::Log4perl" peut être initialisé de deux manières : soit via des commandes Perl, soit via un fichier de configuration de style "log4j".

Initialisation via un fichier de configuration

C'est le moyen le plus simple de préparer votre système à utiliser "Log::Log4perl". Utilisez un fichier de configuration comme celui-ci :

############################################################
# Un logger simple avec un appender Log::Log4perl::Appender::File
# en Perl.
############################################################
log4perl.rootLogger=ERROR, LOGFILE

log4perl.appender.LOGFILE=Log::Log4perl::Appender::File
log4perl.appender.LOGFILE.filename=/var/log/myerrs.log
log4perl.appender.LOGFILE.mode=append

log4perl.appender.LOGFILE.layout=PatternLayout
log4perl.appender.LOGFILE.layout.ConversionPattern=[%r] %F %L %c - %m%n

Ces lignes définissent votre logger par défaut qui ajoute les erreurs graves à "/var/log/myerrs.log", en utilisant le format

[millisecs] source-filename line-number class - message newline

En supposant que ce fichier de configuration soit enregistré sous le nom "log.conf", vous devez le lire dans la section d'initialisation de votre code en utilisant les commandes suivantes :

use Log::Log4perl;
Log::Log4perl->init("log.conf");

Une fois que cette opération a été effectuée quelque part dans le code, vous pouvez obtenir des objets logger n'importe où dans le code. Notez qu'il n'est pas nécessaire de transporter une référence de logger avec votre fonction et votre méthode. Vous pouvez obtenir un logger à tout moment via un mécanisme de singleton :

package My::MegaPackage;
use Log::Log4perl;
sub some_method {
    my($param) = @_;
    my $log = Log::Log4perl->get_logger("My::MegaPackage");
    $log->debug("Message de débogage");
    $log->info("Message d'information");
    $log->error("Message d'erreur");
    ...
}

Avec le fichier de configuration ci-dessus, "Log::Log4perl" écrira « Message d'erreur » dans le fichier spécifié, mais ne fera rien pour les appels à "debug()" et "info()", car le niveau de journalisation a été défini sur "ERROR" pour tous les composants sur la première ligne du fichier de configuration présenté ci-dessus.

Pourquoi "Log::Log4perl->get_logger" et non "Log::Log4perl->new" ? Nous ne voulons pas créer un nouvel objet à chaque fois. En programmation OO, nous créons généralement un objet une fois et utilisons sa référence pour appeler ses méthodes. Cependant, cela nécessite de passer l'objet à toutes les fonctions et méthodes que nous utilisons. Et la dernière chose que nous voulons est de polluer chaque fonction/méthode que nous utilisons avec un handle vers le "Logger" :

sub function {  # Brrr !!
    my($logger, $some, $other, $parameters) = @_;
}

Au lieu qu'une fonction/méthode demande une référence au logger, elle appelle simplement la méthode statique get_logger($category) du logger pour obtenir une référence à l'objet logger unique d'une certaine catégorie. Ceci est appelé un singleton si vous êtes fan de Gamma.

Comment le logger sait-il quels messages enregistrer et lesquels supprimer ? "Log::Log4perl" fonctionne avec l'héritage : Le fichier de configuration ci-dessus ne spécifie rien à propos de "My::MegaPackage". Et pourtant, nous avons défini un logger de catégorie "My::MegaPackage". Dans ce cas, "Log::Log4perl" remontera la hiérarchie de l'espace de noms ("My" puis nous arrivons à la racine) pour déterminer si un niveau de journalisation est défini quelque part. Dans le cas ci-dessus, le niveau de journalisation à la racine (la racine définit toujours un niveau de journalisation, mais pas nécessairement un appender) définit que le niveau de journalisation doit être "ERROR" – ce qui signifie que DEBUG et INFO sont supprimés. Notez que cet « héritage » est indépendant de l'héritage de Perl, mais est simplement lié à l'espace de noms du logger. Au fait, si vous n'êtes jamais en doute sur la catégorie d'un logger, utilisez "$logger->category()" pour la récupérer.

Niveaux de journalisation

Log4perl has six logging levels, that can be used to categorize log messages:

  • TRACE
  • DEBUG
  • INFO
  • WARN
  • ERROR
  • FATAL

These levels are ordered. Any message logged with a level that is equal to or higher than the configured logging level will be processed. All other messages will be ignored.

For example, if your configured logging level is "INFO", then messages logged with debug() and trace() will be suppressed. Messages logged with info(), warn(), error() and fatal() will be processed, because their priority is higher or equal than the configured setting.

If your configured logging level is "WARN", then messages logged with info(), debug(), and trace() will be suppressed. fatal(), error() and warn() will make their way through, because their priority is higher or equal than the configured setting.

Instead of calling the methods

$logger->trace("...");  # Log a trace message
$logger->debug("...");  # Log a debug message
$logger->info("...");   # Log a info message
$logger->warn("...");   # Log a warn message
$logger->error("...");  # Log a error message
$logger->fatal("...");  # Log a fatal message

you could also call the log() method with the appropriate level using the constants defined in "Log::Log4perl::Level":

use Log::Log4perl::Level;
$logger->log($TRACE, "...");
$logger->log($DEBUG, "...");
$logger->log($INFO, "...");
$logger->log($WARN, "...");
$logger->log($ERROR, "...");
$logger->log($FATAL, "...");

This form is rarely used, but it comes in handy if you want to log at different levels depending on an exit code of a function:

$logger->log( $exit_level{ $rc }, "...");

As for needing more logging levels than these predefined ones: It's usually best to steer your logging behaviour via the category mechanism instead.

If you need to find out if the currently configured logging level would allow a logger's logging statement to go through, use the logger's "is_level()" methods:

$logger->is_trace()    # True if trace messages would go through
$logger->is_debug()    # True if debug messages would go through
$logger->is_info()     # True if info messages would go through
$logger->is_warn()     # True if warn messages would go through
$logger->is_error()    # True if error messages would go through
$logger->is_fatal()    # True if fatal messages would go through

Example: "$logger->is_warn()" returns true if the logger's current level, as derived from either the logger's category (or, in absence of that, one of the logger's parent's level setting) is $WARN, $ERROR or $FATAL.

Also available are a series of more Java-esque functions which return the same values. These are of the format "isLevelEnabled()", so "$logger->isDebugEnabled()" is synonymous to "$logger->is_debug()".

These level checking functions will come in handy later, when we want to block unnecessary expensive parameter construction in case the logging level is too low to log the statement anyway, like in:

if($logger->is_error()) {
    $logger->error("Erroneous array: @super_long_array");
}

If we had just written

$logger->error("Erroneous array: @super_long_array");

then Perl would have interpolated @super_long_array into the string via an expensive operation only to figure out shortly after that the string can be ignored entirely because the configured logging level is lower than $ERROR.

The to-be-logged message passed to all of the functions described above can consist of an arbitrary number of arguments, which the logging functions just chain together to a single string. Therefore

$logger->debug("Hello ", "World", "!");  # and
$logger->debug("Hello World!");

are identical.

Note that even if one of the methods above returns true, it doesn't necessarily mean that the message will actually get logged. What is_debug() checks is that the logger used is configured to let a message of the given priority (DEBUG) through. But after this check, Log4perl will eventually apply custom filters and forward the message to one or more appenders. None of this gets checked by is_xxx(), for the simple reason that it's impossible to know what a custom filter does with a message without having the actual message or what an appender does to a message without actually having it log it.

Journaliser et mourir ou avertir

Often, when you croak / carp / warn / die, you want to log those messages. Rather than doing the following:

$logger->fatal($err) && die($err);

you can use the following:

$logger->logdie($err);

And if instead of using

warn($message);
$logger->warn($message);

to both issue a warning via Perl's warn() mechanism and make sure you have the same message in the log file as well, use:

$logger->logwarn($message);

Since there is an ERROR level between WARN and FATAL, there are two additional helper functions in case you'd like to use ERROR for either warn() or die():

$logger->error_warn();
$logger->error_die();

Finally, there's the Carp functions that, in addition to logging, also pass the stringified message to their companions in the Carp package:

$logger->logcarp();        # warn w/ 1-level stack trace
$logger->logcluck();       # warn w/ full stack trace
$logger->logcroak();       # die w/ 1-level stack trace
$logger->logconfess();     # die w/ full stack trace

Récepteurs

If you don't define any appenders, nothing will happen. Appenders will be triggered whenever the configured logging level requires a message to be logged and not suppressed.

"Log::Log4perl" doesn't define any appenders by default, not even the root logger has one.

"Log::Log4perl" already comes with a standard set of appenders:

Log::Log4perl::Appender::Screen
Log::Log4perl::Appender::ScreenColoredLevels
Log::Log4perl::Appender::File
Log::Log4perl::Appender::Socket
Log::Log4perl::Appender::DBI
Log::Log4perl::Appender::Synchronized
Log::Log4perl::Appender::RRDs

to log to the screen, to files and to databases.

On CPAN, you can find additional appenders like

Log::Log4perl::Layout::XMLLayout

by Guido Carls <gcarls@cpan.org>. It allows for hooking up Log::Log4perl with the graphical Log Analyzer Chainsaw (see "Can I use Log::Log4perl with log4j's Chainsaw?" in Log::Log4perl::FAQ).

Exemple de récepteur

Now let's assume that we want to log info() or higher prioritized messages in the "Foo::Bar" category to both STDOUT and to a log file, say "test.log". In the initialization section of your system, just define two appenders using the readily available "Log::Log4perl::Appender::File" and "Log::Log4perl::Appender::Screen" modules:

use Log::Log4perl;
   # Configuration in a string ...
my $conf = q(
  log4perl.category.Foo.Bar          = INFO, Logfile, Screen
  log4perl.appender.Logfile          = Log::Log4perl::Appender::File
  log4perl.appender.Logfile.filename = test.log
  log4perl.appender.Logfile.layout   = Log::Log4perl::Layout::PatternLayout
  log4perl.appender.Logfile.layout.ConversionPattern = [%r] %F %L %m%n
  log4perl.appender.Screen         = Log::Log4perl::Appender::Screen
  log4perl.appender.Screen.stderr  = 0
  log4perl.appender.Screen.layout = Log::Log4perl::Layout::SimpleLayout
);
   # ... passed as a reference to init()
Log::Log4perl::init( \$conf );

Once the initialization shown above has happened once, typically in the startup code of your system, just use the defined logger anywhere in your system:

##########################
# ... in some function ...
##########################
my $log = Log::Log4perl::get_logger("Foo::Bar");
  # Logs both to STDOUT and to the file test.log
$log->info("Important Info!");

The "layout" settings specified in the configuration section define the format in which the message is going to be logged by the specified appender. The format shown for the file appender is logging not only the message but also the number of milliseconds since the program has started (%r), the name of the file the call to the logger has happened and the line number there (%F and %L), the message itself (%m) and a OS-specific newline character (%n):

[187] ./myscript.pl 27 Important Info!

The screen appender above, on the other hand, uses a "SimpleLayout", which logs the debug level, a hyphen (-) and the log message:

INFO - Important Info!

For more detailed info on layout formats, see "Log Layouts".

In the configuration sample above, we chose to define a category logger ("Foo::Bar"). This will cause only messages originating from this specific category logger to be logged in the defined format and locations.

Configuration via Log::Log4perl::Config

Fichiers de configuration

Comme indiqué ci-dessus, vous pouvez définir "Log::Log4perl" comme logger à la fois depuis votre code Perl et depuis des fichiers de configuration. Ces derniers ont l'avantage que vous pouvez modifier le comportement du système de journalisation sans interférer avec le code lui-même. Ainsi, même si votre code est exécuté par quelqu'un qui n'a aucune connaissance de Perl, il peut toujours adapter le comportement du module à ses besoins.

"Log::Log4perl" a été conçu pour comprendre la configuration de "Log4j" — telle qu'utilisée dans l'implémentation Java originale. Au lieu de répéter la description du format dans [2], je ne vais lister que trois exemples (dérivés de [2]) qui devraient également illustrer son fonctionnement :

log4j.rootLogger=DEBUG, A1
log4j.appender.A1=org.apache.log4j.ConsoleAppender
log4j.appender.A1.layout=org.apache.log4j.PatternLayout
log4j.appender.A1.layout.ConversionPattern=%-4r %-5p %c %x - %m%n

Cela permet d'avoir des messages de priorité "DEBUG" ou supérieure dans la hiérarchie racine et de les écrire sur la console. "ConsoleAppender" est un appender Java, mais "Log::Log4perl" passe par un processus complexe en interne pour les mapper à ses classes correspondantes en Perl, comme "Log::Log4perl::Appender::Screen" dans ce cas.

Deuxième exemple :

log4perl.rootLogger=DEBUG, A1
log4perl.appender.A1=Log::Log4perl::Appender::Screen
log4perl.appender.A1.layout=PatternLayout
log4perl.appender.A1.layout.ConversionPattern=%d %-5p %c - %m%n
log4perl.logger.com.foo=WARN

Cela définit deux loggers : le logger racine et le logger "com.foo". Le logger racine est facilement activé avec des messages de débogage, mais le logger "com.foo" garantit que seul le message est envoyé à l'appender s'il provient du composant "Com::Foo" et de ses sous-composants, s'il est de priorité warn ou supérieure.

Notez que le logger "com.foo" ne définit pas d'appender. Par conséquent, le message ne fera que remonter au logger racine, qui le passera à l'appender correspondant de la catégorie racine en utilisant le format qui lui est défini.

Troisième exemple :

log4j.rootLogger=DEBUG, stdout, R
log4j.appender.stdout=org.apache.log4j.ConsoleAppender
log4j.appender.stdout.layout=org.apache.log4j.PatternLayout
log4j.appender.stdout.layout.ConversionPattern=%5p (%F:%L) - %m%n
log4j.appender.R=org.apache.log4j.RollingFileAppender
log4j.appender.R.File=example.log
log4j.appender.R.layout=org.apache.log4j.PatternLayout
log4j.appender.R.layout.ConversionPattern=%p %c - %m%n

Le logger racine définit deux appenders : "stdout", qui utilise "org.apache.log4j.ConsoleAppender" (finalement mappé par "Log::Log4perl" à "Log::Log4perl::Appender::Screen"), pour écrire sur la console. Et "R", un "org.apache.log4j.RollingFileAppender" (mappé par "Log::Log4perl" à "Log::Dispatch::FileRotate" avec l'attribut "File" spécifiant le fichier journal).

Voir Log::Log4perl::Config pour plus d'exemples et d'explications de syntaxe.

Mise en forme des messages de journalisation

Si le moteur de journalisation transmet un message à un appender, parce qu'il pense qu'il doit être enregistré, l'appender ne fait pas que l'écrire au hasard. Il existe des moyens de dire à l'appender comment formater le message et y ajouter des données intéressantes : la date et l'heure de l'événement, le fichier, le numéro de ligne, le niveau de débogage du logger, et d'autres.

Actuellement, deux mises en forme sont définies dans "Log::Log4perl" : "Log::Log4perl::Layout::SimpleLayout" et "Log::Log4perl::Layout::PatternLayout" :

"Log::Log4perl::SimpleLayout"
formate un message de manière simple et le précède du niveau de débogage et d'un tiret : ""$level - $message", par exemple "FATAL - Can't open password file".
"Log::Log4perl::Layout::PatternLayout"
dans ce cas, il est très puissant et permet une mise en forme de style "printf" très flexible. La chaîne de mise en forme peut contenir plusieurs modèles qui seront remplacés par le moteur de journalisation au moment où le message doit être enregistré :

%c Catégorie de l'événement de journalisation.
%C Nom complet du paquet (ou de la classe) de l'appelant
%d Date actuelle au format yyyy/MM/dd hh:mm:ss
%F Fichier où l'événement de journalisation s'est produit
%H Nom d'hôte (si Sys::Hostname est disponible)
%l Nom complet de la méthode appelante suivi du
   nom du fichier source de l'appelant et du numéro de ligne entre
   parenthèses.
%L Numéro de ligne dans le fichier où l'instruction de journalisation a été émise
%m Le message à enregistrer
%m{chomp} Le message à enregistrer, avec suppression d'un retour à la ligne final
%M Méthode ou fonction où la requête de journalisation a été émise
%n Nouvelle ligne (indépendante de l'OS)
%p Priorité de l'événement de journalisation
%P ID du processus courant
%r Nombre de millisecondes écoulées depuis le début du programme jusqu'à l'événement de journalisation
%R Nombre de millisecondes écoulées depuis le dernier événement de journalisation jusqu'à l'événement courant
%T Une trace de la pile des fonctions appelées
%x Le NDC le plus haut (voir ci-dessous)
%X{key} L'entrée 'key' du MDC (voir ci-dessous)
%% Un signe de pourcentage littéral (%)

NDC et MDC sont expliqués dans "Nested Diagnostic Context (NDC)" et "Mapped Diagnostic Context (MDC)".

De plus, %d peut être ajusté pour n'afficher que des caractéristiques spécifiques d'une date selon SimpleDateFormat en Java (http://java.sun.com/j2se/1.3/docs/api/java/text/SimpleDateFormat.html).

Ainsi, %d{HH:mm} n'affiche que les heures et les minutes de la date actuelle, tandis que %d{yy, EEEE} affiche une année à deux chiffres suivie d'un jour formaté (comme "Wednesday").

Des options similaires sont disponibles pour réduire la catégorie affichée ou limiter les composants de chemin de fichier, comme %F{1} n'affiche que le nom du fichier sans les composants du chemin, tandis que %F enregistre le chemin complet. %c{2} n'enregistre que les deux derniers composants de la catégorie actuelle, transformant "Foo::Bar::Baz" en "Bar::Baz" et économisant ainsi de l'espace.

Si ces modèles ne suffisent pas, vous pouvez définir les vôtres dans le fichier de configuration comme ceci :

log4perl.PatternLayout.cspec.U = sub { return "UID $<" }

Voir Log::Log4perl::Layout::PatternLayout pour plus de détails sur les spécificateurs personnalisés.

Note : les sous-routines que vous définissez ici seront exécutées dans l'espace de noms "main", vous devez donc spécifier entièrement les noms de fonctions et de variables si elles se trouvent dans des paquets différents.

NOTE DE SÉCURITÉ : cette fonctionnalité permet d'insérer du code Perl arbitraire dans le fichier de configuration. Dans le cas rare où les utilisateurs accédant à votre fichier de configuration sont différents de ceux qui écrivent votre code et n'ont pas les droits d'exécution, vous pourriez vouloir appeler

Log::Log4perl::Config->allow_code(0);

avant d'appeler init(). Alternativement, vous pouvez fournir un ensemble limité d'opcodes Perl qui peuvent être insérés dans le fichier de configuration, comme décrit dans "Restreindre les opcodes autorisés dans un hook Perl".

Tous les modèles sont quantifiables, comme dans printf. Suivant cette tradition, "%-20c" réservera 20 caractères pour la catégorie et la justifiera à gauche.

Pour plus de détails sur la journalisation et sur la manière d'utiliser la mise en forme flexible et simple, consultez le site web original de "log4j" à l'adresse :

SimpleLayout http://logging.apache.org/log4j/1.2/apidocs/org/apache/log4j/SimpleLayout.html et PatternLayout http://logging.apache.org/log4j/1.2/apidocs/org/apache/log4j/PatternLayout.html

Pénalités

La journalisation a un coût. "Log::Log4perl" a été optimisé pour garantir une efficacité maximale, que la journalisation soit activée ou désactivée.

Mais vous devez être conscient qu'à chaque fois que votre code rencontre une instruction de journalisation — même si la journalisation est désactivée ou non — il y a un léger impact. "Log::Log4perl" est conçu pour maintenir cet impact aussi minime qu'il soit imperceptible pour la plupart des applications.

Voici quelques techniques qui aident "Log::Log4perl" à éviter les retards inutiles :

Vous pouvez gagner un temps considérable si :

Le logger enregistre quelque chose comme :

    # Coûteux en mode non-debug !
for (@super_long_array) {
    $logger->debug("Element: $_");
}

et <super_long_array> est assez grand, donc parcourir ce tableau coûte cher. Seul vous, le programmeur, savez que si le niveau de logging actuel du composant est supérieur à "debug", vous pouvez sauter complètement cette boucle "for". Dans ce cas, utilisez :

    # Pas cher en mode non-debug !
if($logger->is_debug()) {
    for (@super_long_array) {
        $logger->debug("Element: $_");
    }
}

Si vous craignez que la génération des paramètres pour la fonction de logging ne soit coûteuse, utilisez des closures :

    # Passé comme référence de sous-routine
use Data::Dumper;
$logger->debug(sub { Dumper($data) } );

Cela ne décomposera $data via Dumper() que lorsque ce sera réellement nécessaire, parce que ce sera loggué.

De plus, Log::Log4perl permet de spécifier les arguments pour les fonctions logger dans la syntaxe de filtre de sortie de message :

$logger->debug("Structure : ",
               { filter => \&Dumper,
                 value  => $someref });

De cette façon, juste avant que Log::Log4perl n'envoie le message aux appenders, il recherchera tous les arguments pour trouver des références de hachage et les traitera de manière spéciale :

Il invoquera la fonction donnée comme référence avec la clé "filter" (Data::Dumper::Dumper()) et passera à ce filtre la valeur arrivée avec la clé nommée "value" comme argument. Le hachage anonyme dans l'appel précédent sera remplacé par la valeur de retour de la fonction de filtre.

Catégories

Les catégories sont également appelées "Loggers" dans Log4perl, les deux font référence au même concept et ces mots sont utilisés de manière interchangeable. "Log::Log4perl" utilise des *catégories* pour déterminer si une instruction de log dans un composant doit être exécutée ou supprimée au niveau de logging actuel. La plupart du temps, ces catégories sont simplement les classes dans lesquelles se trouvent les instructions de log :

package Candy::Twix;
sub new {
    my $logger = Log::Log4perl->get_logger("Candy::Twix");
    $logger->debug("Creating a new Twix bar");
    bless {}, shift;
}

# ...
package Candy::Snickers;
sub new {
    my $logger = Log::Log4perl->get_logger("Candy.Snickers");
    $logger->debug("Creating a new Snickers bar");
    bless {}, shift;
}
# ...
package main;
Log::Log4perl->init("mylogdefs.conf");
    # => "LOG> Creating a new Snickers bar"
my $first = Candy::Snickers->new();
    # => "LOG> Creating a new Twix bar"
my $second = Candy::Twix->new();

Notez que vous pouvez séparer la hiérarchie des catégories en utilisant des points comme en Java (.) ou des doubles deux-points (::) comme en Perl. Les deux notations sont équivalentes et gérées de manière identique en interne.

Cependant, les catégories servent uniquement à utiliser l'héritage : si vous appelez un logger dans une sous-catégorie, il remontera la hiérarchie et appellera les appenders appropriés. En interne, les catégories ne sont absolument pas liées à la hiérarchie de classes du programme — elles sont simplement virtuelles. Vous pouvez utiliser des catégories arbitraires, par exemple dans le programme suivant, qui n'est pas de style OO, mais procédural :

sub print_portfolio {
    my $log = Log::Log4perl->get_logger("user.portfolio");
    $log->debug("Quotes requested: @_");
    for(@_) {
        print "$_: ", get_quote($_), "\n";
    }
}
sub get_quote {
    my $log = Log::Log4perl->get_logger("internet.quotesystem");
    $log->debug("Fetching quote: $_[0]");
    return yahoo_quote($_[0]);
}

Le logger dans la première fonction, "print_portfolio", est assigné à la catégorie "user.portfolio" (virtuelle). Selon la configuration de "Log4perl", cela appellera un appender "user.portfolio", un appender "user" ou un assigné à la racine — sans aucun rapport avec la hiérarchie de classes du programme. Le logger dans la seconde fonction suit la catégorie "internet.quotesystem" — même si elle pourrait être liée à d'autres fonctions Internet, pas à l'existence d'une classe de ce nom.

Cependant, gardez à l'esprit que vous ne devez pas dépasser la limite : si vous développez un système orienté objet, l'utilisation de la hiérarchie de classes est généralement votre meilleure option. Pensez aux personnes qui reprendront votre code à l'avenir : la hiérarchie de classes est probablement ce qu'elles connaissent le mieux, il leur sera donc facile d'ajuster le logging à leurs besoins.

Désactiver un composant

"Log4perl" vous permet non seulement d'activer ou de désactiver sélectivement les messages de log *par catégories*, mais vous pouvez également utiliser le mécanisme pour désactiver le logging de messages *par composants*, tout en gardant les messages actifs dans des catégories supérieures. Ce mécanisme est utile si vous constatez qu'en augmentant le niveau de logging d'une catégorie haute (c'est-à-dire proche de la racine), un composant enregistre plus que prévu :

Voici comment cela fonctionne :

############################################################
# Désactiver le logging dans une catégorie inférieure mais le maintenir actif dans les catégories supérieures.
############################################################
log4perl.rootLogger=DEBUG, LOGFILE
log4perl.logger.deep.down.the.hierarchy = ERROR, LOGFILE
# ... Définir les appenders ...

De cette façon, les messages émis depuis "Deep::Down::The::Hierarchy" et en dessous ne seront enregistrés que s'ils sont de niveau "ERROR" ou supérieur, tandis que dans d'autres composants du système, même les messages "DEBUG" seront enregistrés.

Valeurs de retour

Toutes les méthodes de logging renvoient des valeurs indiquant si le message est réellement parvenu à un ou plusieurs appenders. Si le message a été supprimé en raison de restrictions de niveau, "undef" est renvoyé.

Par exemple :

my $ret = $logger->info("Message");

renverra "undef" si le niveau système de la catégorie actuelle n'est pas "INFO" ou plus permissif. Si Log::Log4perl a envoyé le message à un ou plusieurs appenders, le nombre d'appenders est renvoyé.

Si les appenders décident de refuser le message avec un seuil d'appender, la valeur retournée par la méthode de logging les exclura. Cela signifie que si vous avez un appender qui a un seuil d'appender et que vous logguez un message qui passe le seuil du niveau système mais pas le seuil de l'appender, il sera retourné 0 par la méthode de log.

Le résumé final est le suivant : les méthodes de log retournent une valeur *vraie* si le message est parvenu à un ou plusieurs appenders et une valeur *fausse* si ce n'est pas le cas. Cela permet des constructions comme :

$logger->fatal("@_") or print STDERR "@_\n";

ce qui garantira que le message fatal ne sera pas perdu si le niveau actuel est inférieur à FATAL ou sera imprimé deux fois si le niveau est acceptable mais qu'un appender pointe déjà vers STDERR.

Pièges avec les catégories

Soyez prudent lorsque vous utilisez uniquement les catégories système sans examiner leur comportement avec les méthodes héritées. Si vous le faites, vous rencontrerez des problèmes avec les méthodes héritées. Imaginez la configuration de classe suivante :

use Log::Log4perl;
###########################################
package Bar;
###########################################
sub new {
    my($class) = @_;
    my $logger = Log::Log4perl::get_logger(__PACKAGE__);
    $logger->debug("Creating instance");
    bless {}, $class;
}
###########################################
package Bar::Twix;
###########################################
our @ISA = qw(Bar);
###########################################
package main;
###########################################
Log::Log4perl->init(\ qq{
log4perl.category.Bar.Twix = DEBUG, Screen
log4perl.appender.Screen = Log::Log4perl::Appender::Screen
log4perl.appender.Screen.layout = SimpleLayout
});
my $bar = Bar::Twix->new();

"Bar::Twix" hérite de tout de "Bar", y compris du constructeur new(). Bien que cela puisse sembler évident, cela ne produira aucun résultat. La raison est que l'appel à get_logger() dans le paquet "Bar" obtiendra toujours un logger de la catégorie "Bar", même si vous l'appelez via le paquet "Bar::Twix", ce qui amènera Perl à remonter la hiérarchie de classes pour exécuter Bar::new(). Étant donné que nous n'avons défini le comportement de logging que pour "Bar::Twix" dans le fichier de configuration, rien ne se passera.

Ce problème peut être résolu en changeant la méthode get_logger() dans Bar::new() pour obtenir un logger de la catégorie correspondant à la *véritable* classe de l'objet, comme ceci :

    # ... dans Bar::new() ...
my $logger = Log::Log4perl::get_logger( $class );

Dans les méthodes autres que les constructeurs, le nom de la classe réelle de l'objet peut être obtenu en appelant ref() sur la référence de l'objet, donc :

package BaseClass;
use Log::Log4perl qw( get_logger );
sub new {
    bless {}, shift;
}
sub method {
    my( $self ) = @_;
    get_logger( ref $self )->debug( "message" );
}
package SubClass;
our @ISA = qw(BaseClass);

est le modèle recommandé pour s'assurer que

my $sub = SubClass->new();
$sub->meth();

commence à logger si la catégorie "SubClass" (et non la catégorie "BaseClass") est active au niveau DEBUG.

Initialiser une fois et une seule

Il est important de reconnaître que Log::Log4perl est initialisé une fois et une seule, typiquement au démarrage d'un programme ou d'un système. Appeler init() plus d'une fois provoquera une boucle.

Astuces Curieuses

Voici une collection d'astuces utiles pour l'utilisateur avancé de Log::Log4perl. Pour plus d'informations, consultez la FAQ, soit dans la distribution (Log::Log4perl::FAQ), soit sur http://log4perl.sourceforge.net.

Raccourcis

Lorsque vous obtenez une instance d'un logger, au lieu de dire:

use Log::Log4perl;
my $logger = Log::Log4perl->get_logger();

il est plus pratique d'importer la méthode get_logger() de Log::Log4perl dans votre espace de noms actuel:

use Log::Log4perl qw(get_logger);
my $logger = get_logger();

Note: Pour obtenir le logger racine, utilisez get_logger(""), appelez-le sans paramètres (get_logger()) pour obtenir le logger d'une catégorie nommée comme le paquet actuel. get_logger() est équivalent à get_logger(__PACKAGE__).

Initialisation alternative

Au lieu d'avoir init() qui lit un fichier de configuration en spécifiant un nom de fichier ou en lui passant une référence vers un fichier ouvert ("Log::Log4perl->init( \*FILE )"), vous pouvez également passer une référence à une chaîne contenant le contenu du fichier:

Log::Log4perl->init( \$config_text );

De plus, si vous avez des paires clé-valeur de configuration de type "name=value" dans un hash, vous pouvez initialiser Log::Log4perl avec une référence à ce hash:

my %key_value_pairs = (
    "log4perl.rootLogger"       => "ERROR, LOGFILE",
    "log4perl.appender.LOGFILE" => "Log::Log4perl::Appender::File",
    ...
);
Log::Log4perl->init( \%key_value_pairs );

Vous pouvez également utiliser une URL, voir ci-dessous:

Utilisation de LWP pour analyser les URL

La fonction init() prend désormais également en charge les URL, par exemple http://www.erols.com/enno/xsa.xml. Elle utilise LWP pour télécharger le fichier, puis appelle parse() sur la chaîne résultante. Par défaut, elle utilisera un LWP::UserAgent créé comme suit:

use LWP::UserAgent;
$LWP_USER_AGENT = LWP::UserAgent->new;
$LWP_USER_AGENT->env_proxy;

Note: env_proxy lit les configurations de proxy à partir des variables d'environnement, ce qui est ce dont Log4perl a besoin pour passer à travers le pare-feu. Si vous souhaitez utiliser un autre agent LWP::UserAgent, vous pouvez le définir avec:

Log::Log4perl::Config::set_LWP_UserAgent($my_agent);

Actuellement, LWP est utilisé lorsque le nom de fichier (passé à parsefile) commence par l'un des schémas d'URL suivants: http, https, ftp, wais, gopher, ou file (suivi de deux points)..

N'utilisez pas cette fonctionnalité avec init_and_watch().

Rechargement automatique des fichiers de configuration modifiés

Au lieu d'initialiser statiquement Log::Log4perl en utilisant:

Log::Log4perl->init($conf_file);

il existe un moyen de faire vérifier périodiquement Log::Log4perl la configuration et de la recharger si nécessaire:

Log::Log4perl->init_and_watch($conf_file, $delay);

Dans ce mode, Log::Log4perl examinera le fichier de configuration $conf_file toutes les $delay secondes pour détecter les changements via l'heure de modification du fichier. Si le fichier a été mis à jour, il sera rechargé et remplacera la configuration actuelle de Log::Log4perl.

Ce mode pratique fonctionne comme suit: à chaque appel d'une fonction de logger (debug(), is_debug(), etc.), Log::Log4perl vérifiera si l'intervalle de délai a expiré. Si c'est le cas, il exécutera une vérification -M file sur le fichier de configuration. Si l'heure de modification du fichier a été modifiée, la configuration actuelle sera vidée et le nouveau contenu du fichier sera chargé.

Cependant, cette commodité a un coût: l'appel de time() à chaque appel d'une fonction de journalisation, en particulier celles qui sont "supprimées" (!), rend ces appels Log4perl 40% plus lents.

Pour atténuer cet impact sur les performances, init_and_watch() peut être configuré pour écouter un signal Unix afin de recharger la configuration:

Log::Log4perl->init_and_watch($conf_file, 'HUP');

Cela configurera un gestionnaire de signaux pour SIGHUP et rechargera la configuration si l'application reçoit ce signal, par exemple via la commande "kill":

kill -HUP pid

où "pid" est l'identifiant du processus de l'application. Cela ramène la vitesse d'exécution normale de Log::Log4perl pour les logs supprimés à environ 85%. Pour plus de détails, consultez la section Performance. Pour plus d'informations sur le gestionnaire de signaux, recherchez la section SIGNAL MODE dans Log::Log4perl::Config::Watch.

Si vous avez un délai légèrement long entre les vérifications des fichiers de configuration physiques ou si vous ne souhaitez pas utiliser le signal associé au moniteur de configuration, vous pouvez forcer un rechargement de configuration au prochain moment possible en appelant:

Log::Log4perl::Config->watcher->force_next_check();

Une chose à noter: si le fichier de configuration contient une erreur de syntaxe ou une autre erreur grave, une application en cours d'exécution s'arrêtera avec "die" si cette configuration corrompue est chargée pendant l'exécution, soit par un signal, soit si le délai a expiré et que le changement est détecté. Ce comportement pourrait changer à l'avenir.

Pour permettre à l'application d'intercepter et de contrôler un rechargement de configuration en mode init_and_watch, un rappel peut être spécifié:

Log::Log4perl->init_and_watch($conf_file, 10, { 
        preinit_callback => \&callback });

Si Log4perl détecte que la configuration doit être rechargée, il appellera la fonction preinit_callback sans paramètres. Si le rappel renvoie une valeur vraie, Log4perl procédera et rechargera la configuration. Si le rappel renvoie une valeur fausse, Log4perl conservera l'ancienne configuration et évitera de la recharger jusqu'au prochain cycle. Dans le rappel, une application peut effectuer toutes les vérifications possibles, y compris accéder au fichier de configuration, qui est disponible via "Log::Log4perl::Config->watcher()->file()".

Substitution de variables

Pour éviter d'avoir à répéter des expressions identiques chaque fois que vous les utilisez, les fichiers de configuration Log::Log4perl prennent en charge la substitution de variables simples. Les nouvelles variables sont simplement définies en ajoutant des lignes:

varname = value

après avoir utilisé:

${varname}

après avoir utilisé:

${varname}

voici un exemple:

layout_class   = Log::Log4perl::Layout::PatternLayout
layout_pattern = %d %F{1} %L> %m %n

log4perl.category.Bar.Twix = WARN, Logfile, Screen
log4perl.appender.Logfile  = Log::Log4perl::Appender::File
log4perl.appender.Logfile.filename = test.log
log4perl.appender.Logfile.layout = ${layout_class}
log4perl.appender.Logfile.layout.ConversionPattern = ${layout_pattern}
log4perl.appender.Screen  = Log::Log4perl::Appender::Screen
log4perl.appender.Screen.layout = ${layout_class}
log4perl.appender.Screen.layout.ConversionPattern = ${layout_pattern}

C'est un moyen pratique de définir deux appenders avec la même configuration de layout sans avoir à répéter les définitions de modèle.

Mantén toda la estructura del archivo. "${varname}" intentará primero encontrar una variable explícitamente definida. Si eso falla, buscará en tu entorno de shell una variable con ese nombre. Si también falla, se ejecutará el programa die().

Ganchos Perl en el Archivo de Configuración

Si algunos de los valores utilizados en el archivo de configuración de Log4perl necesitan ser modificados dinámicamente por el programa, usa ganchos Perl:

log4perl.appender.File.filename = \
    sub { return getLogfileName(); }

Cada valor que empiece con la cadena "sub {..." se interpreta como código Perl a ejecutar cuando el programa analiza la configuración mediante Log::Log4perl::init(). El valor de retorno de la función se utiliza por Log::Log4perl como el valor de configuración.

El código Perl se ejecuta en el paquete "main", y las funciones de otros paquetes deben ser llamadas con notación fully-qualified.

Aquí hay un ejemplo más, usando una variable de entorno como nombre de usuario para un appender DB:

log4perl.appender.DB.username = \
    sub { $ENV{DB_USER_NAME } }

Sin embargo, ten en cuenta la diferencia entre estos fragmentos de código y los utilizados para la conversión de especificadores de usuario como se discute en Log::Log4perl::Layout::PatternLayout: mientras que los fragmentos anteriores se ejecutan *una vez* cuando se llama a Log::Log4perl::init(), los especificadores de conversión se ejecutan *cada vez* que se renderiza un mensaje según el PatternLayout.

NOTA DE SEGURIDAD: esta característica significa que se puede incluir código Perl arbitrario en el archivo de configuración. En el raro caso en que los usuarios que tienen acceso al archivo de configuración sean distintos de los que escriben el código y no tengan permisos de ejecución, podrías querer establecer:

Log::Log4perl::Config->allow_code(0);

antes de llamar a init(). Alternativamente, puedes proporcionar un conjunto restringido de operadores Perl que puedan incluirse en el archivo de configuración, como se describe en "Restringir qué operadores pueden estar en un Hook Perl".

Restringir qué Opcodes pueden estar en un Hook Perl

El valor que pases a Log::Log4perl::Config->allow_code() determina si el código incluido en el archivo de configuración se ejecuta sin restricciones o en un compartimento Safe. Por defecto, se asume un valor de '1', que ejecuta normalmente 'eval' sin restricciones. Un valor de '0' evita que se ejecute cualquier código incluido.

Si quieres tener un control fino sobre lo que puede y no puede incluirse en el código incluido, utiliza los siguientes métodos:

Log::Log4perl::Config->allow_code( $allow );
Log::Log4perl::Config->allowed_code_ops($op1, $op2, ... );
Log::Log4perl::Config->vars_shared_with_safe_compartment( [ \%vars | $package, \@vars ] );
Log::Log4perl::Config->allowed_code_ops_convenience_map( [ \%map | $name, \@mask ] );

Log::Log4perl::Config->allowed_code_ops() toma una lista de máscaras de operadores que se pueden ejecutar en el compartimento. Las máscaras de operadores deben especificarse como se describe en Opcode:

Log::Log4perl::Config->allowed_code_ops(':subprocess');

Este ejemplo permite operaciones Perl como backticks, system, fork y waitpid en el compartimento. Sin embargo, probablemente no quieras usar esta máscara, ya que permitiría exactamente lo que el compartimento Safe está diseñado para evitar.

Log::Log4perl::Config->vars_shared_with_safe_compartment() toma los símbolos que deben exportarse al compartimento Safe antes de que se ejecute el código. Las claves de esta tabla hash son los nombres de paquetes en los que se encuentran los símbolos, y los valores son referencias a los nombres literales de los símbolos. Para mayor comodidad, los valores predeterminados exportan la tabla '%ENV' del paquete 'main' al compartimento:

Log::Log4perl::Config->vars_shared_with_safe_compartment(
  main => [ '%ENV' ],
);

Log::Log4perl::Config->allowed_code_ops_convenience_map() es un método de ayuda que mapea nombres convenientes a máscaras de operadores. Actualmente, los siguientes nombres convenientes están definidos:

safe        = [ ':browse' ]
restrictive = [ ':default' ]

Para mayor comodidad, si Log::Log4perl::Config->allow_code() se llama con un valor que es una clave del mapa definido previamente con Log::Log4perl::Config->allowed_code_ops_convenience_map(), los operadores permitidos se establecen según el valor definido en el mapa. Si esto es confuso, considera lo siguiente:

use Log::Log4perl;

my $config = <<'END';
 log4perl.logger = INFO, Main
 log4perl.appender.Main = Log::Log4perl::Appender::File
 log4perl.appender.Main.filename = \
     sub { "example" . getpwuid($<) . ".log" }
 log4perl.appender.Main.layout = Log::Log4perl::Layout::SimpleLayout
END

$Log::Log4perl::Config->allow_code('restrictive');
Log::Log4perl->init( \$config );       # fallará
$Log::Log4perl::Config->allow_code('safe');
Log::Log4perl->init( \$config );       # saldrá

La razón por la que la primera llamada a init() falla es porque el nombre 'restrictive' se mapea a una máscara de operador ':default'. getpwuid() no está incluida en ':default', por lo que init() fallará. El nombre 'safe' se mapea a una máscara de operador ':browse', que permite la ejecución de getpwuid(), por lo que init() se ejecutará correctamente.

allowed_code_ops_convenience_map() puede invocarse de varias maneras:

allowed_code_ops_convenience_map()

allowed_code_ops_convenience_map( \%map )

allowed_code_ops_convenience_map( $name )
Devuelve la máscara de operadores para el nombre conveniente dado, o undef si no se encuentra tal nombre en el mapa.
allowed_code_ops_convenience_map( $name, \@mask )
Agrega el par nombre/máscara dado al mapa de nombres convenientes. Si el nombre ya existe en el mapa, su valor se reemplaza con la nueva máscara.

igual que vars_shared_with_safe_compartment():

vars_shared_with_safe_compartment()
Devuelve el mapa completo de paquetes a variables como una referencia a hash en contexto escalar o un hash en contexto de lista.

Reemplaza el mapa completo de paquetes a variables con la referencia proporcionada.

Cambiar el Nivel de Registro en un Logger

Log4perl proporciona algunas funciones internas para ajustar rápidamente el nivel de registro mientras se ejecuta un programa Perl.

Ahora, algunos usuarios podrían argumentar que se deberían ajustar los niveles desde fuera del archivo de configuración de Log4perl, pero Log4perl es el favorito de todos.

El ajuste de niveles en tiempo de ejecución se realiza generalmente al inicio, o en respuesta a algún tipo de entrada externa (como un comando de diagnóstico "more logging" para diagnosticar).

Puedes obtener el nivel de registro de un objeto logger con:

$current_level = $logger->level();

y puedes establecerlo con el mismo método, siempre que primero importes las constantes de nivel de Log::Log4perl con:

use Log::Log4perl::Level;

Luego, puedes establecer el nivel de un logger a una de las constantes:

$logger->level($ERROR); # uno de DEBUG, INFO, WARN, ERROR, FATAL

Para *incrementar* el nivel de registro actual, usa:

$logger->more_logging($delta);

y para *decrementar* el nivel, usa:

$logger->less_logging($delta);

El $delta debe ser un número positivo (por ahora, podríamos arreglar esto más adelante ;)).

También hay dos funciones equivalentes:

$logger->inc_level($delta);
$logger->dec_level($delta);

Estas se incluyen para permitirte elegir entre leer y escribir. Algunos preferirán more/less_logging, ya que son más claros en lo que hacen y permiten al programador no preocuparse tanto sobre qué es un nivel y si un nivel más alto significa más o menos registros. Sin embargo, otros que entienden y tienen mucho código que maneja niveles podrían preferir los métodos inc_level() y dec_level() porque quieren trabajar con niveles y no preocuparse por si eso significa más o menos registros.

Aunque esto es una discusión, típicamente usarás more_logging() o inc_level() así:

my $v = 0; # nivel de verbosidad por defecto.

GetOptions("v+ => \$v, ...);
if( $v ) {
  $logger->more_logging($v); # incrementa el nivel de registro una vez por cada -v en ARGV
}

Sin embargo, Log4perl proporciona una forma agradable de crear niveles personalizados mediante la función create_custom_level(). Sin embargo, esto debe realizarse antes de la primera llamada a init() o get_l

Niveaux de journalisation globaux

Comme mesure assez drastique pour réduire (ou augmenter) le niveau de journalisation dans l'ensemble du système avec une seule option de configuration, utilisez le mot-clé "threshold" dans le fichier de configuration de Log4perl :

log4perl.threshold = ERROR

Cela définit le niveau du système (ou le niveau de la hiérarchie selon la documentation de log4j) à ERROR, supprimant ainsi le droit de tous les journaleurs du système d'enregistrer des messages de niveau inférieur.

Mode simple

À des fins pédagogiques (notamment pour [1]), j'ai placé le mode ":easy" dans "Log::Log4perl", qui initialise uniquement un seul journaleur racine avec un niveau défini et un appendeur d'écran incluant une disposition standard :

### Début de section
use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init($ERROR);  # Définit le niveau du journaleur racine à ERROR
### Section d'application
my $logger = get_logger();
$logger->fatal("Ceci sera enregistré.");
$logger->debug("Ceci ne sera pas enregistré.");

Cela affichera quelque chose comme :

2002/08/04 11:43:09 ERROR> script.pl:16 main::función - Ceci sera enregistré.

Bien que cela ait été testé comme fonctionnant bien pour familiariser les utilisateurs avec "Log::Logperl", en évitant efficacement que les utilisateurs ne se sentent submergés par de multiples paramètres (catégories, appendeurs, niveaux, dispositions), l'objectif de "Log::Log4perl" est de permettre aux utilisateurs d'utiliser les catégories dès le début pour s'habituer au concept. Par conséquent, gardez-le bien caché dans la page man (avec gratitude si vous avez lu ceci jusqu'à la fin).

Journaliseurs furtifs

Parfois, les gens sont paresseux. Si vous voulez profiter de la commodité de "Log::Log4perl" sans avoir à maintenir un fichier de configuration log4perl ou un 5 lignes défini pour ajouter vos messages à un fichier, vous pouvez utiliser les fonctionnalités suivantes :

use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init( { level   => $DEBUG,
                            file    => ">>test.log" } );
    # Journalise dans test.log via un journaliseur furtif
DEBUG("Debuggez ceci !");
INFO("Informez ceci !");
WARN("Avertissez ceci !");
ERROR("Erreur ceci !");
some_function();
sub some_function {
        # Ainsi ici
    FATAL("Fatalité ceci !");
}

En mode ":easy", "Log::Log4perl" instanciera un journaliseur furtif et introduira les fonctions pratiques "TRACE", DEBUG(), INFO(), WARN(), ERROR(), FATAL() et "ALWAYS" dans l'espace de noms du paquet. Ces fonctions ne prennent que des messages comme arguments et les transmettent aux méthodes des journaliseurs furtifs ("debug()).

Si un message ne doit pas être bloqué, quel que soit le niveau de journalisation, utilisez la fonction "ALWAYS" qui correspond à un niveau de journalisation "OFF" :

ALWAYS "Ceci sera imprimé indépendamment du niveau de journalisation";

La méthode "easy_init" peut être appelée avec une valeur de niveau unique pour créer un appendeur STDERR et un journaliseur racine comme dans :

Log::Log4perl->easy_init($DEBUG);

ou, comme illustré ci-dessous (et dans l'exemple précédent), avec une référence de hachage, spécifiant des valeurs pour "level" (le niveau du journaliseur), "file" (la destination de l'appendeur), "category" (la catégorie du journaliseur et "layout" pour la spécification de la disposition de l'appendeur. Toutes les paires clé-valeur sont facultatives, avec la valeur par défaut de $DEBUG pour "level", "STDERR" pour "file", "" (catégorie racine) pour "category" et "%d %m%n" pour "layout" :

Log::Log4perl->easy_init( { level    => $DEBUG,
                            file     => ">>test.log",
                            utf8     => 1,
                            category => "Bar::Twix",
                            layout   => '%F{1}-%L-%M: %m%n' } );

Le paramètre "file" accepte des noms de fichiers précédés de ">" (écrasement) et ">>" (ajout) comme arguments. Cela entraînera la création d'un appendeur "Log::Log4perl::Appender::File" en coulisses. Les termes "STDOUT" et "STDERR" (sans ">" ni ">>") sont également reconnus, qui utiliseront et configureront correctement "Log::Log4perl::Appender::Screen". L'option "utf8", si elle est définie sur une valeur vraie, exécutera une commande "binmode" sur le handle de fichier pour définir une discipline de ligne utf8 dans le fichier, sinon un message d'avertissement de 'wide character in print' sera affiché et vous n'obtiendrez probablement pas la sortie attendue.

Les journaliseurs furtifs peuvent être utilisés dans différents paquets ; il suffit de s'assurer d'appeler la fonction "use" dans chaque paquet qui utilise les services faciles de "Log::Log4perl" :

package Bar::Twix;
use Log::Log4perl qw(:easy);
sub eat { DEBUG("Twix mjam"); }
package Bar::Mars;
use Log::Log4perl qw(:easy);
sub eat { INFO("Mars mjam"); }
package main;
use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init( { level    => $DEBUG,
                            file     => ">>test.log",
                            category => "Bar::Twix",
                            layout   => '%F{1}-%L-%M: %m%n' },
                          { level    => $DEBUG,
                            file     => "STDOUT",
                            category => "Bar::Mars",
                            layout   => '%m%n' },
                        );
Bar::Twix::eat();
Bar::Mars::eat();

Comme montré ci-dessus, "easy_init() acceptera un nombre quelconque de définitions de journaliseurs différentes sous forme de références de hachage.

Ils disposent également des fonctions LOGWARN(), LOGDIE() et LOGEXIT() en mode ":easy", combinant une requête de journalisation avec une instruction Perl ultérieure warn(), die() ou exit(). Par exemple :

if($all_is_lost) {
    LOGDIE("Problème terrible");
}

enregistrera le message si le journaliseur du paquet est au moins "FATAL" mais die() (incluant la sortie traditionnelle vers STDERR) dans tous les cas ensuite.

Voir "Journaliser et mourir ou avertir" pour les fonctions similaires logdie() et logwarn() pour les journaliseurs normaux (c'est-à-dire non furtifs).

De même, LOGCARP(), LOGCLUCK(), LOGCROAK() et LOGCONFESS() sont fournis en mode ":easy", facilitant l'utilisation de logcarp(), logcluck(), logcroak() et logconfess() avec des journaliseurs furtifs.

Lorsque vous utilisez Log::Log4perl en mode simple, veuillez vous assurer de comprendre les implications de "Pièges avec les catégories".

De plus, ces fonctions de commodité sont aussi rapides que les méthodes standard de "Log::Log4perl", avec aucun coût de performance.

Contexte de diagnostic imbriqué (NDC)

Si vous constatez que votre application pourrait bénéficier d'une pile globale (c'est-à-dire spécifique aux threads) de données auxquelles vos journaliseurs à travers le système peuvent accéder facilement, utilisez les Contextes de Diagnostic Imbriqués (NDC). Consultez également "Contexte de diagnostic mappé (MDC)", qui pourrait être encore plus utile.

Par exemple, lors du traitement d'une requête de client Web, il sera probablement utile de disposer de l'adresse IP de l'utilisateur dans tous les journaux au sein du code lié à cette requête. Au lieu de transmettre ces données entre vos fonctions d'application, vous pouvez simplement utiliser le mécanisme NDC global (mais spécifique aux threads). Cela vous permet de placer des éléments de données (généralement des scalaires) sur votre pile en utilisant :

Log::Log4perl::NDC->push("San");
Log::Log4perl::NDC->push("Francisco");

et vous pourrez ensuite récupérer ces valeurs à partir du dossier %x dans la disposition PatternLayout. Avec les valeurs de la pile et un format de disposition tel que "%x %m%n", l'appel :

$logger->debug("rocks");

finira par être

San Francisco rocks

dans l'appendeur de log.

Le mécanisme de pile permet des structures imbriquées. Assurez-vous simplement qu'à la fin de la requête, vous diminuez la pile un par un en appelant

Log::Log4perl::NDC->pop();
Log::Log4perl::NDC->pop();

ou que vous videz toute la pile NDC en appelant

Log::Log4perl::NDC->remove();

Même si vous oubliez de le faire, "Log::Log4perl" ne fera pas croître la pile indéfiniment, mais la limitera à un maximum, défini dans "Log::Log4perl::NDC" (actuellement 5). Un appel à push() sur une pile pleine remplacera simplement l'élément le plus haut par la nouvelle valeur.

Encore une fois, la pile est toujours disponible via le placeholder "%x" dans la classe Log::Log4perl::Layout::PatternLayout chaque fois qu'un logger se déclenche. Il remplacera "%x" par la liste séparée par des espaces des valeurs dans la pile. Il le fait en appelant simplement

Log::Log4perl::NDC->get();

en interne. Voir les détails sur la façon dont cette fonctionnalité standard de log4j est implémentée dans Log::Log4perl::NDC.

Mapped Diagnostic Context (MDC)

Tout comme le NDC discuté précédemment stocke des informations spécifiques au thread dans une structure de pile, le MDC implémente une table de hachage pour stocker des paires clé/valeur.

La méthode statique

Log::Log4perl::MDC->put($key, $value);

stocke $value sous une clé $key, avec laquelle elle peut être récupérée plus tard (éventuellement dans une partie totalement différente du système) en appelant la méthode "get" :

my $value = Log::Log4perl::MDC->get($key);

Si aucune valeur n'a été stockée précédemment sous $key, la méthode "get" renverra "undef".

Typiquement, les valeurs MDC sont récupérées plus tard via le placeholder "%X{...}" dans "Log::Log4perl::Layout::PatternLayout". Si la méthode get() renvoie "undef", le placeholder s'étendra à la chaîne "[undef]".

Une application qui reçoit une requête web pourrait stocker l'hôte distant comme

Log::Log4perl::MDC->put("remote_host", $r->headers("HOST"));

à son début et si la disposition de l'appendeur ressemble à

log4perl.appender.Logfile.layout.ConversionPattern = %X{remote_host}: %m%n

alors une instruction de log comme

DEBUG("Content delivered");

enregistrera quelque chose comme

adsl-63.dsl.snf.pacbell.net: Content delivered

plus tard dans le programme.

Pour plus de détails, veuillez consulter Log::Log4perl::MDC.

Restauration des instructions Log4perl masquées

Parfois, des scripts doivent être déployés dans des environnements sans que Log::Log4perl soit encore installé. D'un autre côté, vous ne voulez pas vous passer de vos instructions Log4perl - elles vous seront utiles plus tard.

Alors, déployez simplement votre script avec les instructions Log4perl commentées avec le motif "###l4p", comme dans

###l4p DEBUG "It works!";
# ...
###l4p INFO "Really!";

Si Log::Log4perl est disponible, utilisez la balise ":resurrect" pour que Log4perl restaure ces instructions enterrées avant que le script ne commence à s'exécuter :

use Log::Log4perl qw(:resurrect :easy);
###l4p Log::Log4perl->easy_init($DEBUG);
###l4p DEBUG "It works!";
# ...
###l4p INFO "Really!";

Cela activera un filtre source et imprimera effectivement

2004/11/18 22:08:46 It works!
2004/11/18 22:08:46 Really!

Dans les environnements où Log::Log4perl est absent, commentez simplement la première ligne et le script s'exécutera néanmoins (mais bien sûr sans logging) :

# use Log::Log4perl qw(:resurrect :easy);
###l4p Log::Log4perl->easy_init($DEBUG);
###l4p DEBUG "It works!";
# ...
###l4p INFO "Really!";

car tout est maintenant un commentaire régulier. Alternativement, placez la ligne magique de résurrection de commentaire Log::Log4perl dans la variable d'environnement PERL5OPT de votre shell, par exemple pour bash :

set PERL5OPT=-MLog::Log4perl=:resurrect,:easy
export PERL5OPT

Cela réveillera le géant au sein d'un script autrement silencieux comme le suivant :

#!/usr/bin/perl
###l4p Log::Log4perl->easy_init($DEBUG);
###l4p DEBUG "It works!";

À partir de "Log::Log4perl" 1.12, vous pouvez même forcer *tous* les modules chargés par un script à faire restaurer leurs instructions Log4perl cachées. Pour que cela se produise, chargez "Log::Log4perl::Resurrector" *avant* de charger des modules :

use Log::Log4perl qw(:easy);
use Log::Log4perl::Resurrector;
use Foobar; # Toutes les instructions Log4perl cachées ici seront
            # décommentées avant le chargement de Foobar.
Log::Log4perl->easy_init($DEBUG);
...

Consultez la page de manuel "Log::Log4perl::Resurrector" pour plus de détails.

Accès aux appendeurs définis

Tous les appendeurs définis dans le fichier de configuration ou via du code Perl peuvent être récupérés par la méthode de classe appender_by_name(). Ceci est utile si vous souhaitez manipuler ou interroger les propriétés de l'appendeur après que la configuration Log4perl ait été chargée via init().

Notez qu'en interne, Log::Log4perl utilise la classe wrapper "Log::Log4perl::Appender" pour contrôler les vrais appendeurs (comme "Log::Log4perl::Appender::File" ou "Log::Dispatch::FileRotate"). La classe "Log::Log4perl::Appender" a un attribut "appender", pointant vers le vrai appendeur.

La raison est que les appendeurs externes comme "Log::Dispatch::FileRotate" ne prennent pas en charge tous les mécanismes de contrôle des appendeurs de Log::Log4perl (comme les seuils d'appendeur).

La méthode mentionnée précédemment appender_by_name() renvoie une référence à l'objet appendeur *réel*. Si vous souhaitez accéder à la classe wrapper (par exemple, si vous souhaitez modifier le seuil de l'appendeur), utilisez plutôt le hash $Log::Log4perl::Logger::APPENDER_BY_NAME{...}, qui contient des références à tous les objets wrappers d'appendeur.

Modification des seuils d'appendeur

Pour définir le seuil d'un appendeur, utilisez sa méthode threshold() :

$app->threshold( $FATAL );

Pour ajuster commodément *tous* les seuils d'appendeur (par exemple, parce qu'un script utilise more_logging()), utilisez

   # diminuer les seuils de tous les appendeurs
Log::Log4perl->appender_thresholds_adjust(-1);

Cela diminuera les seuils de tous les appendeurs du système d'un niveau, c'est-à-dire WARN deviendra INFO, INFO deviendra DEBUG, etc. Pour ne modifier que ceux sélectionnés, utilisez

   # diminuer les seuils des appendeurs sélectionnés
Log::Log4perl->appender_thresholds_adjust(-1, ['AppName1', ...]);

et passez les noms des appendeurs affectés dans une référence à un tableau.

Configuration avancée dans Perl

L'initialisation de Log::Log4perl peut certainement aussi se faire depuis Perl. Après tout, c'est ce que fait "Log::Log4perl::Config" en coulisses. Les parseurs de fichiers de configuration de Log::Log4perl utilisent une API publiquement disponible pour configurer les catégories, les appendeurs et les mises en page de Log::Log4perl.

Voici un exemple de configuration de deux appendeurs avec la même mise en page en Perl, sans utiliser de fichier de configuration du tout :

########################
# Section d'initialisation
########################
use Log::Log4perl;
use Log::Log4perl::Layout;
use Log::Log4perl::Level;
   # Définir un logger de catégorie
my $log = Log::Log4perl->get_logger("Foo::Bar");
   # Définir une mise en page
my $layout = Log::Log4perl::Layout::PatternLayout->new("[%r] %F %L %m%n");
   # Définir un appendeur de fichier
my $file_appender = Log::Log4perl::Appender->new(
                        "Log::Log4perl::Appender::File",
                        name      => "filelog",
                        filename  => "/tmp/my.log");
   # Définir un appendeur stdout
my $stdout_appender =  Log::Log4perl::Appender->new(
                        "Log::Log4perl::Appender::Screen",
                        name      => "screenlog",
                        stderr    => 0);
   # Définir un appendeur mixte stderr/stdout
my $mixed_stdout_stderr_appender = Log::Log4perl::Appender->new(
                        "Log::Log4perl::Appender::Screen",
                        name      => "screenlog",
                        stderr    => { ERROR => 1, FATAL => 1 });
   # Faire en sorte que les deux appendeurs utilisent la même mise en page (pourraient être différentes)
$stdout_appender->layout($layout);
$file_appender->layout($layout);
$log->add_appender($stdout_appender);
$log->add_appender($file_appender);
$log->level($INFO);

Veuillez noter que la classe de l'objet appendeur est passée sous forme de *chaîne* à "Log::Log4perl::Appender" comme *premier* argument. En coulisses, "Log::Log4perl::Appender" créera l'objet "Log::Log4perl::Appender::*" (ou "Log::Dispatch::*") nécessaire et transmettra les paires nom-valeur que nous avons fournies à "Log::Log4perl::Appender->new()" après le premier argument.

Le nom "name" est optionnel et si vous n'en fournissez pas, "Log::Log4perl::Appender->new()" en créera un unique pour vous. Les noms et valeurs des paramètres supplémentaires dépendent des exigences de la classe d'appendeur particulière et peuvent être consultés dans leurs pages de manuel.

Une note annexe : si vous vous demandez si "Log::Log4perl::Appender->new()" prendra également en charge l'argument "min_level" de l'appendeur.

t;Log::Dispatch::*" appelés en coulisses -- oui, c'est le cas. C'est parce que nous voulons que les objets "Log::Dispatch" enregistrent aveuglément tout ce que nous leur envoyons ("debug" est leur niveau le plus bas) car nous, dans "Log::Log4perl", voulons garder le contrôle et décider quand et quoi enregistrer.

L'appel à la méthode layout() de l'appendeur spécifie le format (en tant qu'objet "Log::Log4perl::Layout::PatternLayout" créé précédemment) dans lequel le message est enregistré dans l'appendeur spécifié. Si vous ne spécifiez pas de mise en page, le logger utilisera par défaut "Log::Log4perl::SimpleLayout", qui enregistre le niveau de débogage, un tiret (-) et le message de log.

Les mises en page sont des objets, voici comment les créer :

    # Créer une mise en page simple
my $simple = Log::Log4perl::SimpleLayout();
    # créer une mise en page flexible :
    # ("yyyy/MM/dd hh:mm:ss (file:lineno)> message\n")
my $pattern = Log::Log4perl::Layout::PatternLayout("%d (%F:%L)> %m%n");

Chaque appendeur a exactement une mise en page qui lui est assignée. Vous assignez la mise en page à l'appendeur en utilisant l'objet layout() de l'appendeur :

my $app =  Log::Log4perl::Appender->new(
              "Log::Log4perl::Appender::Screen",
              name      => "screenlog",
              stderr    => 0);
    # Assigner la mise en page flexible précédemment définie
$app->layout($pattern);
    # Ajouter l'appendeur à un logger précédemment défini
$logger->add_appender($app);
    # ... et vous êtes prêt à partir !
$logger->debug("Blah");
    # => "2002/07/10 23:55:35 (test.pl:207)> Blah\n"

Il est également possible de supprimer des appendeurs d'un logger :

$logger->remove_appender($appender_name);

supprimera un appendeur, spécifié par son nom, d'un logger donné. Veuillez noter que cela ne supprime *pas* un appendeur du système.

Pour éradiquer un appendeur du système, vous devez appeler "Log::Log4perl->eradicate_appender($appender_name)" qui supprimera d'abord l'appendeur de tous les loggers du système, puis supprimera toutes les références que Log4perl en détient.

Pour supprimer un logger du système, utilisez "Log::Log4perl->remove_logger($logger)". Une fois que la référence restante $logger disparaît, le logger s'autodétruira. Si le logger en question est un logger discret, tous ses raccourcis de commodité (DEBUG, INFO, etc.) deviendront des opérations nulles.

Et quand à Log::Dispatch::Config?

"Log::Dispatch::Config" de Tatsuhiko Miyagawa est une implémentation de logger simplifiée très astucieuse, couvrant une partie de la fonctionnalité de log4j. Parmi les choses que "Log::Log4perl" peut faire mais pas "Log::Dispatch::Config", il y a :

  • Vous ne pouvez pas assigner de catégories aux loggers. Pour les petits systèmes, c'est bien, mais si vous ne pouvez pas activer et désactiver la journalisation détaillée dans seulement un minuscule sous-système de votre environnement, vous manquez une fonctionnalité très utile de log4j.
  • Définir des seuils d'appendeur. Important si vous voulez résoudre des problèmes comme « enregistrer tous les messages de niveau FATAL sur STDERR, plus enregistrer tous les messages DEBUG de "Foo::Bar" dans un fichier de log ». Si vous n'avez pas de seuils d'appendeur, il n'y a aucun moyen d'éviter d'encombrer STDERR avec des messages DEBUG.
  • Spécifications de PatternLayout conformément à la norme (par exemple, "%d{HH:mm}").

En résumé : Log::Dispatch::Config convient aux petits systèmes ayant des besoins de journalisation simples. Cependant, si vous concevez un système avec de nombreux sous-systèmes que vous devez contrôler indépendamment, vous adorerez les fonctionnalités de "Log::Log4perl", qui est tout aussi facile à utiliser.

Utiliser Log::Log4perl avec des fonctions et des classes enveloppantes

Si vous n'utilisez pas "Log::Log4perl" comme décrit ci-dessus, mais à partir d'une fonction enveloppante, la mise en page de modèle générera des données incorrectes pour %F, %C, %L, et similaires. La raison est que les loggers de "Log::Log4perl" supposent une profondeur d'appel statique à l'application qui les utilise.

Si vous utilisez une (ou plusieurs) fonction(s) enveloppante(s), "Log::Log4perl" indiquera où votre fonction de logger a appelé les loggers, et non où votre application a appelé votre enveloppe :

use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init({ level => $DEBUG,
                           layout => "%M %m%n" });
sub mylog {
    my($message) = @_;
    DEBUG $message;
}
sub func {
    mylog "Hello";
}
func();

affiche

main::mylog Hello

mais ce n'est probablement pas ce que votre application attend. Vous préféreriez plutôt

main::func Hello

car la fonction "func" a appelé votre fonction de journalisation.

Mais ne désespérez pas, il y a une solution : enregistrez simplement votre package enveloppant auprès de Log4perl au préalable. Si Log4perl découvre alors qu'il est appelé depuis une enveloppe enregistrée, il montera automatiquement à l'image d'appel suivante.

Log::Log4perl->wrapper_register(__PACKAGE__);
sub mylog {
    my($message) = @_;
    DEBUG $message;
}

Alternativement, vous pouvez augmenter la valeur de la variable globale $Log::Log4perl::caller_depth (par défaut 0) d'un pour chaque enveloppe qui se trouve entre votre application et "Log::Log4perl", puis "Log::Log4perl" compensera la différence :

sub mylog {
    my($message) = @_;
    local $Log::Log4perl::caller_depth =
          $Log::Log4perl::caller_depth + 1;
    DEBUG $message;
}

Notez également que si vous écrivez une sous-classe de Log4perl, comme

package MyL4pWrapper;
use Log::Log4perl;
our @ISA = qw(Log::Log4perl);

et que vous souhaitez appeler get_logger() dans votre code, comme

use MyL4pWrapper;
sub get_logger {
    my $logger = Log::Log4perl->get_logger();
}

alors l'appel à get_logger() obtiendra un logger pour la catégorie "MyL4pWrapper", et non pour le package appelant la classe enveloppante comme dans

package UserPackage;
my $logger = MyL4pWrapper->get_logger();

Pour que l'appel ci-dessus à get_logger renvoie un logger pour la catégorie « UserPackage », vous devez indiquer à Log4perl que « MyL4pWrapper » est une classe enveloppante Log4perl :

use MyL4pWrapper;
Log::Log4perl->wrapper_register(__PACKAGE__);
sub get_logger {
      # Obtient maintenant un logger pour la catégorie du package appelant
    my $logger = Log::Log4perl->get_logger();
}

Cette fonctionnalité fonctionne à la fois pour les classes de relais Log4perl comme l'enveloppe décrite ci-dessus, et pour les enveloppes qui héritent de Log4perl utilisent la fonction get_logger de Log4perl par héritage, de manière similaire.

Accès aux internes

Les méthodes suivantes ne sont utiles que si vous souhaitez inspecter/modifier les internes de Log::Log4perl. Soyez prudent et ne perturbez pas son fonctionnement interne.

"Log::Log4perl->appenders()"
Pour savoir quels imageurs sont actuellement définis (pas seulement pour un logger particulier, mais globalement), une méthode appenders() est disponible pour retourner une référence à un hash mappant les noms des imageurs à leurs références d'objet Log::Log4perl::Appender.

Astuces de triche

infiltrate_lwp()
Le célèbre module LWP::UserAgent n'est pas compatible avec Log::Log4perl. Souvent, cependant, surtout lors du débogage de problèmes liés au Web, il serait utile d'obtenir un aperçu de ce qui se passe à l'intérieur de LWP::UserAgent. Idéalement, LWP::UserAgent jouerait même dans le cadre Log::Log4perl.

Un appel à "Log::Log4perl->infiltrate_lwp()" fait exactement cela. D'une manière assez rudimentaire, il prend le tapis sous LWP::UserAgent et transforme ses messages "debug/conn" en appels debug() des loggers de la catégorie "LWP::UserAgent". De même, les messages "trace" de "LWP::UserAgent" sont transformés en appels de la méthode "Log::Log4perl" info(). Notez que cela ne fonctionne que pour les versions de LWP::UserAgent antérieures à 5.822, car ces versions (et probablement les versions ultérieures) manquent complètement de fonctions de débogage.

Suppression des messages LOGDIE 'en double'
Si un script avec une configuration Log4perl simple utilise logdie() pour attraper les erreurs et arrêter le traitement, comme dans 
use Log::Log4perl qw(:easy) ;
Log::Log4perl->easy_init($DEBUG);

shaky_function() or LOGDIE "It failed!";

il y a un problème cosmétique : le message est imprimé deux fois :

2005/07/10 18:37:14 It failed!
It failed! at ./t line 12

La solution évidente est d'utiliser LOGEXIT() au lieu de LOGDIE(), mais il existe également une balise spéciale pour Log4perl qui supprime le second message :

use Log::Log4perl qw(:no_extra_logdie_message);

Cela fait que logdie() et logcroak() appellent exit() au lieu de die(). Pour modifier le code de sortie du script dans ces occasions, définissez la variable $Log::Log4perl::LOGEXIT_CODE à la valeur souhaitée, la valeur par défaut étant 1.

Redéfinir des valeurs sans causer d'erreurs
L'analyseur de fichiers de configuration de Log4perl possède quelques mécanismes de sécurité de base pour s'assurer que les configurations sont plus ou moins saines.

L'une de ces mesures de sécurité consiste à intercepter les valeurs redéfinies. Par exemple, si vous écrivez d'abord

log4perl.category = WARN, Logfile

et quelques lignes plus tard

log4perl.category = TRACE, Logfile

alors vous pourriez avoir involontairement écrasé le fichier

VALEUR

et Log4perl mourra avec une erreur (les configurations suspectes provoquent toujours une erreur). Maintenant, il se peut que ce soit intentionnel, par exemple lorsque vous regroupez plusieurs fichiers de configuration et que vous souhaitez réellement que la première valeur remplace la seconde. Dans ce cas, utilisez

use Log::Log4perl qw(:nostrict);

pour mettre Log4perl dans un mode plus permissif.

Empêcher croak/confess de stringifier
Les fonctions logcroak/logconfess stringifient leurs arguments avant de les passer aux fonctions croak/confess de Carp. Cela peut gêner si vous souhaitez lancer un objet ou un hashref comme exception, dans ce cas utilisez : 
$Log::Log4perl::STRINGIFY_DIE_MESSAGE = 0;
eval {
      # lance { foo => "bar" }
      # sans stringification
    $logger->logcroak( { foo => "bar" } );
};

EXEMPLE

Un exemple simple à copier-coller pour commencer :

use Log::Log4perl qw(get_logger);

my $conf = q(
log4perl.category.Bar.Twix         = WARN, Logfile
log4perl.appender.Logfile          = Log::Log4perl::Appender::File
log4perl.appender.Logfile.filename = test.log
log4perl.appender.Logfile.layout = \
    Log::Log4perl::Layout::PatternLayout
log4perl.appender.Logfile.layout.ConversionPattern = %d %F{1} %L> %m %n
);

Log::Log4perl::init(\$conf);

my $logger = get_logger("Bar::Twix");
$logger->error("Blah");

Cela enregistrera quelque chose comme

2002/09/19 23:48:15 t1 25> Blah

dans le fichier journal "test.log", que Log4perl ajoutera ou créera s'il n'existe pas déjà.

INSTALLATION

Si vous souhaitez utiliser des appenders externes fournis avec "Log::Dispatch", vous devez installer "Log::Dispatch" (version 2.00 ou supérieure) depuis CPAN, qui dépend lui-même de "Attribute-Handlers" et "Params-Validate". Et de nombreux autres modules, c'est pourquoi nous fournissons maintenant Log::Log4perl avec ses propres appenders standard et ce n'est que si vous souhaitez en utiliser d'autres que vous devrez passer par le processus d'installation de "Log::Dispatch".

Log::Log4perl nécessite "Test::More", "Test::Harness" et "File::Spec", mais ils sont déjà fournis avec les versions assez récentes de perl. Sinon, tout sera automatiquement récupéré depuis CPAN si vous utilisez le shell CPAN (CPAN.pm), car ils sont listés comme dépendances.

"Time::HiRes" (version 1.20 ou supérieure) n'est requis que si vous avez besoin des horodatages précis du paramètre %r dans "Log::Log4perl::Layout::PatternLayout".

L'installation manuelle se fait comme d'habitude avec

perl Makefile.PL
make
make test
make install
