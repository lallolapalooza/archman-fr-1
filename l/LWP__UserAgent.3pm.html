LWP::UserAgent(3) Documentation Perl fournie par l'utilisateur LWP::UserAgent(3)

NOM

LWP::UserAgent - Classe d'agent utilisateur web

SYNOPIS

use strict;
use warnings;
use LWP::UserAgent ();
my $ua = LWP::UserAgent->new(timeout => 10);
$ua->env_proxy;
my $response = $ua->get('http://example.com');
if ($response->is_success) {
    print $response->decoded_content;
}
else {
    die $response->status_line;
}

Couches de sécurité supplémentaires (notez le "cookie_jar" et le "protocols_allowed") :

use strict;
use warnings;
use HTTP::CookieJar::LWP ();
use LWP::UserAgent       ();
my $jar = HTTP::CookieJar::LWP->new;
my $ua  = LWP::UserAgent->new(
    cookie_jar        => $jar,
    protocols_allowed => ['http', 'https'],
    timeout           => 10,
);
$ua->env_proxy;
my $response = $ua->get('http://example.com');
if ($response->is_success) {
    print $response->decoded_content;
}
else {
    die $response->status_line;
}

DESCRIPTION

LWP::UserAgent est une classe implémentant un agent utilisateur web. Les objets LWP::UserAgent peuvent être utilisés pour envoyer des requêtes web.

En utilisation normale, l'application crée un objet LWP::UserAgent, puis le configure avec des valeurs pour les délais d'attente, les proxys, le nom, etc. Elle crée ensuite une instance de HTTP::Request pour la requête qui doit être effectuée. Cette requête est ensuite passée à l'une des méthodes de requête de l'agent utilisateur, qui l'envoie en utilisant le protocole pertinent, et renvoie un objet HTTP::Response. Il existe des méthodes pratiques pour envoyer les types de requêtes les plus courants : "get" dans LWP::UserAgent, "head" dans LWP::UserAgent, "post" dans LWP::UserAgent, "put" dans LWP::UserAgent et "delete" dans LWP::UserAgent. Lors de l'utilisation de ces méthodes, la création de l'objet requête est masquée, comme montré dans le synopsis ci-dessus.

L'approche de base de la bibliothèque est d'utiliser la communication de style HTTP pour tous les schémas de protocole. Cela signifie que vous construirez des objets HTTP::Request et recevrez des objets HTTP::Response même pour des ressources non-HTTP comme gopher et ftp. Afin d'obtenir une similitude encore plus grande avec les communications de style HTTP, les menus gopher et les répertoires de fichiers sont convertis en documents HTML.

MÉTHODES DE CONSTRUCTEUR

Les méthodes de constructeur suivantes sont disponibles :

clone

my $ua2 = $ua->clone;

Renvoie une copie de l'objet LWP::UserAgent.

ATTENTION : Veuillez noter que la méthode clone ne copie pas et ne clone pas votre attribut "cookie_jar". En raison des restrictions limitées sur ce qui peut être utilisé pour votre cookie jar, il n'y a aucun moyen de cloner l'attribut. L'attribut "cookie_jar" sera "undef" dans la nouvelle instance d'objet.

new

my $ua = LWP::UserAgent->new( %options )

Cette méthode construit un nouvel objet LWP::UserAgent et le renvoie. Des arguments clé/valeur peuvent être fournis pour définir l'état initial. Les options suivantes correspondent aux méthodes d'attribut décrites ci-dessous :

CLÉ                     PAR DEFAUT
-----------             --------------------
agent                   "libwww-perl/#.###"
conn_cache              undef
cookie_jar              undef
cookie_jar_class        HTTP::Cookies
default_headers         HTTP::Headers->new
from                    undef
local_address           undef
max_redirect            7
max_size                undef
no_proxy                []
parse_head              1
protocols_allowed       undef
protocols_forbidden     undef
proxy                   {}
requests_redirectable   ['GET', 'HEAD']
send_te                 1
show_progress           undef
ssl_opts                { verify_hostname => 1 }
timeout                 180

Les options supplémentaires suivantes sont également acceptées : Si l'option "env_proxy" est passée avec une valeur vraie, alors les paramètres proxy sont lus à partir des variables d'environnement (voir "env_proxy" dans LWP::UserAgent). Si "env_proxy" n'est pas fourni, la variable d'environnement "PERL_LWP_ENV_PROXY" contrôle si "env_proxy" dans LWP::UserAgent est appelé lors de l'initialisation. Si la valeur de l'option "keep_alive" est définie et non nulle, alors un "LWP::ConnCache" est mis en place (voir "conn_cache" dans LWP::UserAgent). La valeur "keep_alive" est transmise comme "total_capacity" pour le cache de connexion.

"proxy" doit être défini comme un arrayref de paires clé/valeur. "no_proxy" prend un arrayref de domaines.

ATTRIBUTS

Les paramètres des attributs de configuration modifient le comportement de LWP::UserAgent lors de l'envoi des requêtes. La plupart d'entre eux peuvent également être initialisés par des options passées au constructeur.

Les méthodes d'attribut suivantes sont fournies. La valeur de l'attribut reste inchangée si aucun argument n'est donné. La valeur de retour de chaque méthode est l'ancienne valeur de l'attribut.

agent

my $agent = $ua->agent;
$ua->agent('Checkbot/0.4 ');    # ajouter le défaut à la fin
$ua->agent('Mozilla/5.0');
$ua->agent("");                 # ne pas s'identifier

Obtenir/définir le jeton produit qui est utilisé pour identifier l'agent utilisateur sur le réseau. La valeur de l'agent est envoyée comme en-tête "User-Agent" dans les requêtes.

Par défaut, c'est une chaîne de la forme "libwww-perl/#.###", où "#.###" est substitué par le numéro de version de cette bibliothèque.

Si la chaîne fournie se termine par un espace, la chaîne par défaut "libwww-perl/#.###" lui est ajoutée.

La chaîne de l'agent utilisateur doit être un ou plusieurs identifiants de produit simples avec un numéro de version optionnel séparé par le caractère "/".

conn_cache

my $cache_obj = $ua->conn_cache;
$ua->conn_cache( $cache_obj );

Obtenir/définir l'objet LWP::ConnCache à utiliser. Voir LWP::ConnCache pour les détails.

cookie_jar

my $jar = $ua->cookie_jar;
$ua->cookie_jar( $cookie_jar_obj );

Obtenir/définir l'objet cookie jar à utiliser. La seule exigence est que l'objet cookie jar doit implémenter les méthodes extract_cookies($response) et add_cookie_header($request). Ces méthodes seront alors invoquées par l'agent utilisateur lors de l'envoi des requêtes et de la réception des réponses. Normalement, il s'agira d'un objet HTTP::Cookies ou d'une de ses sous-classes. Vous êtes toutefois encouragé à utiliser HTTP::CookieJar::LWP à la place. Voir "BONNES PRATIQUES" pour plus d'informations.

use HTTP::CookieJar::LWP ();
my $jar = HTTP::CookieJar::LWP->new;
my $ua = LWP::UserAgent->new( cookie_jar => $jar );
# ou après la création de l'objet
$ua->cookie_jar( $cookie_jar );

Par défaut, il n'y a pas de cookie jar, c'est-à-dire qu'aucun en-tête "Cookie" n'est automatiquement ajouté aux requêtes.

Si $jar contient une référence de hachage non blessée, un nouvel objet cookie jar est créé automatiquement pour vous. L'objet est de la classe définie avec l'argument du constructeur "cookie_jar_class", qui est par défaut HTTP::Cookies.

$ua->cookie_jar({ file => "$ENV{HOME}/.cookies.txt" });

est en fait juste un raccourci pour :

require HTTP::Cookies;
$ua->cookie_jar(HTTP::Cookies->new(file => "$ENV{HOME}/.cookies.txt"));

Comme décrit ci-dessus et dans "BONNES PRATIQUES", vous devriez définir "cookie_jar_class" à "HTTP::CookieJar::LWP" pour obtenir un cookie jar plus sûr.

my $ua = LWP::UserAgent->new( cookie_jar_class => 'HTTP::CookieJar::LWP' );
$ua->cookie_jar({}); # HTTP::CookieJar::LWP ne prend pas d'arguments

Ceux-ci peuvent également être combinés dans le constructeur, donc

un conteneur est créé à l'instanciation.

my $ua = LWP::UserAgent->new(
  cookie_jar_class => 'HTTP::CookieJar::LWP',
  cookie_jar       =>  {},
);

identifiants

my $creds = $ua->credentials();
$ua->credentials( $netloc, $realm );
$ua->credentials( $netloc, $realm, $uname, $pass );
$ua->credentials("www.example.com:80", "Some Realm", "foo", "secret");

Récupère/définit le nom d'utilisateur et le mot de passe à utiliser pour un domaine.

Le $netloc est une chaîne de la forme "<hôte>:<port>". Le nom d'utilisateur et le mot de passe ne seront transmis qu'à ce serveur.

en-tête_par_défaut

$ua->default_header( $field );
$ua->default_header( $field => $value );
$ua->default_header('Accept-Encoding' => scalar HTTP::Message::decodable());
$ua->default_header('Accept-Language' => "no, en");

Ceci est juste un raccourci pour "$ua->default_headers->header( $field => $value )".

en-têtes_par_défaut

my $headers = $ua->default_headers;
$ua->default_headers( $headers_obj );

Récupère/définit l'objet d'en-têtes qui fournira les valeurs d'en-tête par défaut pour toute requête envoyée. Par défaut, il s'agira d'un objet HTTP::Headers vide.

de

my $from = $ua->from;
$ua->from('foo@bar.com');

Récupère/définit l'adresse e-mail de l'utilisateur humain qui contrôle l'agent utilisateur demandeur. L'adresse doit être utilisable par machine, telle que définie dans la RFC2822 https://tools.ietf.org/html/rfc2822. La valeur "de" est envoyée en tant qu'en-tête "From" dans les requêtes.

Par défaut, aucun en-tête "From" n'est envoyé. Voir "default_headers" dans LWP::UserAgent pour l'interface plus générale qui permet de définir n'importe quel en-tête par défaut.

adresse_locale

my $address = $ua->local_address;
$ua->local_address( $address );

Récupère/définit l'interface locale à utiliser pour les connexions réseau. L'interface peut être spécifiée comme un nom d'hôte ou une adresse IP. Cette valeur est passée comme argument "LocalAddr" à IO::Socket::INET.

max_redirection

my $max = $ua->max_redirect;
$ua->max_redirect( $n );

Lit ou définit la limite de l'objet quant au nombre de fois où il obéira aux réponses de redirection lors d'un cycle de requête donné.

Par défaut, la valeur est 7. Cela signifie que si vous appelez "request" dans LWP::UserAgent et que la réponse est une redirection ailleurs qui est à son tour une redirection, et ainsi de suite sept fois, LWP abandonne après cette septième requête.

taille_max

my $size = $ua->max_size;
$ua->max_size( $bytes );

Récupère/définit la limite de taille pour le contenu de la réponse. Par défaut, la valeur est "undef", ce qui signifie qu'il n'y a pas de limite. Si le contenu de la réponse retourné est partiel, parce que la limite de taille a été dépassée, un en-tête "Client-Aborted" sera ajouté à la réponse. Le contenu peut finir par être plus long que "max_size" car nous abandonnons une fois qu'une partie de données ajoutée fait dépasser la longueur de la limite. L'en-tête "Content-Length", s'il est présent, indiquera la longueur du contenu complet et ne sera normalement pas identique à length($res->content).

analyser_head

my $bool = $ua->parse_head;
$ua->parse_head( $boolean );

Récupère/définit une valeur indiquant si nous devons initialiser les en-têtes de réponse à partir de la section <head> des documents HTML. Par défaut, la valeur est vraie. *Ne désactivez pas cela* à moins de savoir ce que vous faites.

protocoles_autorisés

my $aref = $ua->protocols_allowed;      # obtenir les protocoles autorisés
$ua->protocols_allowed( \@protocols );  # autoriser UNIQUEMENT ceux-ci
$ua->protocols_allowed(undef);          # supprimer la liste
$ua->protocols_allowed(['http',]);      # autoriser UNIQUEMENT http

Par défaut, un objet n'a ni liste de "protocols_allowed", ni liste de "protocols_forbidden" dans LWP::UserAgent.

Lit (ou définit) la liste des protocoles que cet agent utilisateur autorisera exclusivement. Les noms de protocoles ne sont pas sensibles à la casse.

Par exemple : "$ua->protocols_allowed( [ 'http', 'https'] );" signifie que cet agent utilisateur *autorisera uniquement* ces protocoles, et les tentatives d'utilisation de cet agent utilisateur pour accéder à des URL avec d'autres schémas (comme "ftp://...") entraîneront une erreur 500.

Notez qu'avoir une liste de "protocols_allowed" fait que tout "protocols_forbidden" dans la liste LWP::UserAgent est ignoré.

protocoles_interdits

my $aref = $ua->protocols_forbidden;    # obtenir la liste interdite
$ua->protocols_forbidden(\@protocols);  # ne pas autoriser ceux-ci
$ua->protocols_forbidden(['http',]);    # Toutes les requêtes http obtiennent un 500
$ua->protocols_forbidden(undef);        # supprimer la liste

Lit (ou définit) la liste des protocoles que cette méthode de requête de l'agent utilisateur *n'autorisera pas*. Les noms de protocoles ne sont pas sensibles à la casse.

Par exemple : "$ua->protocols_forbidden( [ 'file', 'mailto'] );" signifie que cet agent utilisateur *n'autorisera pas* ces protocoles, et les tentatives d'utilisation de cet agent utilisateur pour accéder à des URL avec ces schémas entraîneront une erreur 500.

requêtes_redirection_autorisées

my $aref = $ua->requests_redirectable;
$ua->requests_redirectable( \@requests );
$ua->requests_redirectable(['GET', 'HEAD',]); # par défaut

Lit ou définit la liste des noms de requêtes de l'objet pour lesquels "redirect_ok" dans LWP::UserAgent autorisera la redirection. Par défaut, il s'agit de "['GET', 'HEAD']", conformément à la RFC 2616 https://tools.ietf.org/html/rfc2616. Pour inclure "POST", considérez :

push @{ $ua->requests_redirectable }, 'POST';

envoyer_te

my $bool = $ua->send_te;
$ua->send_te( $boolean );

Si vrai, enverra un en-tête "TE" avec la requête. Par défaut, la valeur est vraie. Définissez-la à faux pour désactiver l'en-tête "TE" pour les systèmes qui ne peuvent pas le gérer.

afficher_progression

my $bool = $ua->show_progress;
$ua->show_progress( $boolean );

Récupère/définit une valeur indiquant si une barre de progression doit être affichée sur le terminal lors du traitement des requêtes. Par défaut, la valeur est fausse.

options_ssl

my @keys = $ua->ssl_opts;
my $val = $ua->ssl_opts( $key );
$ua->ssl_opts( $key => $value );

Récupère/définit les options pour les connexions SSL. Sans argument, retourne la liste des clés d'options actuellement définies. Avec un seul argument, retourne la valeur actuelle pour l'option donnée. Avec 2 arguments, définit la valeur de l'option et retourne l'ancienne. Définir une option à la valeur "undef" supprime cette option.

Les options liées par LWP sont :

"verify_hostname" => $bool
Lorsque VRAI, LWP s'assurera pour les schémas de protocoles sécurisés qu'il se connecte à des serveurs ayant un certificat valide correspondant au nom d'hôte attendu. Si FAUX, aucune vérification n'est effectuée et vous ne pouvez pas être sûr de communiquer avec le pair attendu. Le comportement sans vérification était le défaut pour libwww-perl-5.837 et les versions antérieures.

Cette option est initialisée à partir de la variable d'environnement "PERL_LWP_SSL_VERIFY_HOSTNAME". Si cette variable d'environnement n'est pas définie, alors "verify_hostname" est défini par défaut à 1.

Veuillez noter que récemment, l'effet global de cette option par rapport à la gestion SSL a changé. À partir de la version 6.11 de LWP::Protocol::https, qui est un module externe, la vérification des certificats SSL a été harmonisée pour fonctionner en synchronisation avec IO::Socket::SSL. Avec ce changement, la définition de cette option ne désactive plus toutes les vérifications de certificats SSL, seulement les vérifications de noms d'hôtes. Pour désactiver toutes les vérifications, utilisez l'option "SSL_verify_mode" dans l'attribut "ssl_opts". Par exemple : "$ua-"ssl_opts(SSL_verify_mode => IO::Socket::SSL::SSL_VERIFY_NONE);>

"SSL_ca_file" => $path
Le chemin vers un fichier contenant les certificats d'autorité de certification. Un réglage par défaut pour cette option est fourni en vérifiant les variables d'environnement "PERL_LWP_SSL_CA_FILE" et "HTTPS_CA_FILE" dans cet ordre.
"SSL_ca_path" => $path
Le chemin vers un répertoire contenant des fichiers contenant les certificats d'autorité de certification. Un réglage par défaut pour cette option est fourni en vérifiant les variables d'environnement "PERL_LWP_SSL_CA_PATH" et "HTTPS_CA_DIR" dans cet ordre.

D'autres options peuvent être définies et sont traitées directement par l'implémentation du socket SSL utilisée. Voir IO::Socket::SSL ou Net::SSL pour les détails.

Le cœur de libwww-perl ne regroupe plus de plugins de protocole pour SSL. Vous devrez installer LWP::Protocol::https séparément pour activer la prise en charge du traitement des URL https.

TEMPS D'ATTENTE

my $secs = $ua->timeout;
$ua->timeout( $secs );

Obtenir/définir la valeur d'attente en secondes. La valeur par défaut est de 180 secondes, soit 3 minutes.

S'il n'y a aucune activité sur la connexion au serveur pendant "timeout" secondes, la requête est abandonnée. Cela signifie que le temps nécessaire pour la transaction complète et la requête dans la méthode LWP::UserAgent peut être plus long.

Lorsqu'une requête expire, un objet de réponse est renvoyé. L'objet de réponse aura un code d'état HTTP standard (500). Cette réponse aura l'en-tête "Client-Warning" défini sur la valeur de la "Internal response". Voir la description de la méthode "get" dans la méthode LWP::UserAgent pour plus de détails.

La désactivation du temps d'attente n'est pas prise en charge, mais vous pouvez définir une valeur arbitrairement grande.

ATTRIBUTS DE PROCURATION

Les méthodes suivantes définissent les attributs lorsque les requêtes passent par un serveur proxy.

env_proxy

$ua->env_proxy;

Charge les valeurs de proxy des environnements système *_proxy. Vous pouvez spécifier des proxies comme ceci (utilisation de la syntaxe shell) :

gopher_proxy=http://proxy.example.org/
wais_proxy=http://proxy.example.org/
no_proxy="localhost,example.com"
export gopher_proxy wais_proxy no_proxy

Les utilisateurs de csh ou tcsh devraient utiliser la commande "setenv" pour définir ces variables d'environnement.

Sur les systèmes où les variables d'environnement sont insensibles à la casse, il existe un conflit entre les variables d'environnement CGI et l'en-tête "HTTP_PROXY" normalement utilisé par "env_proxy". Par conséquent, "HTTP_PROXY" n'est pas respecté pour les scripts CGI. La variable "CGI_HTTP_PROXY" peut être utilisée à la place.

no_proxy

$ua->no_proxy( @domains );
$ua->no_proxy('localhost', 'example.com');
$ua->no_proxy(); # efface la liste des domaines

Ne pas utiliser de proxy pour les requêtes vers les domaines donnés, y compris leurs sous-domaines. Appeler "no_proxy" sans domaines efface la liste des domaines.

proxy

$ua->proxy(\@schemes, $proxy_url)
$ua->proxy(['http', 'ftp'], 'http://proxy.sn.no:8001/');
# Pour un seul schéma :
$ua->proxy($scheme, $proxy_url)
$ua->proxy('gopher', 'http://proxy.sn.no:8001/');
# Pour définir plusieurs proxies en même temps :
$ua->proxy([
    ftp => 'http://ftp.example.com:8001/',
    [ 'http', 'https' ] => 'http://http.example.com:8001/',
]);

Définit/obtient l'URL du proxy pour un schéma.

La première forme spécifie que l'URL sera utilisé comme proxy pour les méthodes d'accès listées dans le premier argument de la fonction, c'est-à-dire "http" et "ftp".

La deuxième forme montre une manière courte de spécifier l'URL du proxy pour un schéma d'accès unique.

La troisième forme démontre la configuration de plusieurs proxies en un seul appel. C'est aussi la seule forme acceptée par le constructeur.

GESTIONNAIRES

Les gestionnaires sont du code qui est inséré à différentes étapes lors du traitement des requêtes. Les fonctions suivantes sont fournies pour gérer les gestionnaires actifs :

add_handler

$ua->add_handler( $phase => \&cb, %matchspec )

Ajouter un gestionnaire à invoquer dans la phase de traitement spécifiée. Pour la manière de spécifier %matchspec, voir la section "Matching" dans HTTP::Config.

Les valeurs possibles pour $phase et leurs callbacks correspondants sont les suivantes. Notez que les gestionnaires sont documentés dans l'ordre où ils sont exécutés, qui est :

request_preprepare
request_prepare
request_send
response_header
response_data
response_done
response_redirect
request_preprepare => sub { my($request, $ua, $handler) = @_; ... }
Le gestionnaire est appelé avant "request_prepare" et autres initialisations standard de la requête. Il peut être utilisé pour définir des en-têtes et des attributs dont le gestionnaire "request_prepare" dépend. L'initialisation du proxy doit être effectuée ici ; mais en général, n'enregistrez pas de gestionnaires pour cette phase.
request_prepare => sub { my($request, $ua, $handler) = @_; ... }
Le gestionnaire est appelé avant l'envoi de la requête et peut modifier n'importe quelle partie de la requête comme il le souhaite. Il peut être utilisé pour ajouter certains en-têtes à certaines requêtes.

La méthode peut affecter un nouvel objet de requête à $_[0] pour remplacer complètement celui qui est envoyé.

La valeur retournée par le callback est ignorée. Si une exception est levée, la requête sera abandonnée et la méthode de requête retournera un code "400 Bad request".

request_send => sub { my($request, $ua, $handler) = @_; ... }
Ce gestionnaire a l'opportunité de gérer les requêtes avant qu'elles ne soient envoyées aux gestionnaires de protocole. Il doit renvoyer un objet HTTP::Response s'il souhaite terminer le traitement ; sinon, il ne renvoie rien.

Les gestionnaires "response_header" et "response_data" ne seront pas invoqués pour cette réponse, mais le "response_done" le sera.

response_header => sub { my($response, $ua, $handler) = @_; ... }
Ce gestionnaire est appelé juste après la réception des en-têtes de la réponse, mais avant toute donnée. Le gestionnaire peut définir des gestionnaires pour les données et peut lever une erreur pour abandonner la requête.

Le gestionnaire peut définir la valeur "$response->{default_add_content}" pour contrôler si les données reçues doivent être ajoutées directement à l'objet de réponse. Cette valeur sera initialement fausse si la méthode "$ua->request()" a été appelée avec un argument $content_file ou "$content_cb" ; sinon, elle sera vraie.

response_data => sub { my($response, $ua, $handler, $data) = @_; ... }
Ce gestionnaire est invoqué pour chaque bloc de données reçu dans la réponse. Le gestionnaire peut lever une erreur pour abandonner la requête.

Ce gestionnaire doit renvoyer une valeur vraie pour être appelé à nouveau pour les blocs suivants de la même requête.

response_done => sub { my($response, $ua, $handler) = @_; ... }
Ce gestionnaire est appelé après que la réponse ait été reçue, mais avant d'essayer toute manipulation de redirection. Le gestionnaire peut être utilisé pour extraire des informations ou modifier la réponse.
response_redirect => sub { my($response, $ua, $handler) = @_; ... }
Ce gestionnaire est appelé dans "$ua->request" après "response_done". Si le gestionnaire renvoie un objet HTTP::Request, nous recommencerons le traitement de cette requête.

Pour tous ceux-ci, $handler est une référence à la fonction de gestionnaire qui est actuellement en cours d'exécution.

get_my_handler

$ua->get_my_handler( $phase, %matchspec );
$ua->get_my_handler( $phase, %matchspec, $init );

Retourne le gestionnaire correspondant sous forme de référence de hachage.

Si $init est passé comme une valeur vraie, il crée et ajoute le gestionnaire s'il ne le trouve pas. Si $init est une référence de sous-routine, elle est alors appelée avec le gestionnaire créé comme argument. Cette sous-routine peut remplir le hachage avec des champs supplémentaires ; en particulier le callback. Si $init est une référence de hachage, elle fusionne les hachages.

handlers

$ua->handlers( $phase, $request )
$ua->handlers( $phase, $response )

Retourne les gestionnaires qui s'appliquent à la requête ou à la réponse dans la phase spécifiée.

remove_handler

$ua->remove_handler( undef, %matchspec );
$ua->remove_handler( $phase, %matchspec );
$ua->remove_handler(); # SUPPRIME TOUS LES GESTIONNAIRES DANS TOUTES LES PHASES

Supprime les gestionnaires qui correspondent à %matchspec spécifié. Si $phase n'est pas spécifié, supprime les gestionnaires de toutes les phases.

Vous devriez faire attention lorsque vous appelez cette fonction avec un %matchspec qui n'est pas suffisamment spécifique, car cela pourrait supprimer plus de gestionnaires que vous ne le souhaitez. Il est probablement préférable d'utiliser la méthode "set_my_handler" dans la méthode LWP::UserAgent.

Les gestionnaires supprimés sont retournés.

set_my_handler

$ua->set_my_handler( $phase, $cb, %matchspec );
$ua->set_my_handler($phase, undef); # supprime le gestionnaire pour la phase

Définit des gestionnaires privés à la sous-routine en cours d'exécution. Cela fonctionne en définissant par défaut un champ "owner" à la sous-routine portant le nom de la sous-routine appelée. Vous pouvez passer une valeur explicite "owner" pour la remplacer.

Si $cb est passé comme "undef", cela supprime le gestionnaire.

Les méthodes décrites dans cette section sont utilisées pour la distribution des requêtes via l'agent utilisateur. Les méthodes de requête suivantes sont fournies :

Cette méthode utilise la fonction DELETE() de HTTP::Request::Common pour construire la requête. Consultez HTTP::Request::Common pour plus de détails sur la façon de passer le contenu du formulaire et d'autres fonctionnalités avancées.

get

my $res = $ua->get( $url );
my $res = $ua->get( $url , $field_name => $value, ... );

Cette méthode envoie une requête "GET" sur l'URL donné. Des arguments supplémentaires peuvent être utilisés pour initialiser les en-têtes de la requête. Ceux-ci sont donnés sous forme de paires clé-valeur séparées. La valeur renvoyée est un objet réponse. Consultez HTTP::Response pour une description de l'interface qu'elle offre.

Même si LWP ne parvient pas à se connecter au serveur spécifié dans l'URL ou en cas d'erreurs dans d'autres gestionnaires de protocole, un objet réponse est toujours renvoyé. Ces réponses internes utilisent des codes d'état HTTP standard, de sorte qu'elles ne peuvent pas être différenciées par la valeur du code d'état de la réponse. Les réponses internes générées par LWP auront l'en-tête Client-Warning défini sur la valeur Internal response. Si vous souhaitez différencier ces réponses internes de celles réellement générées par un serveur distant, vous devez tester cette valeur d'en-tête.

Les noms de champ commençant par ":" sont spéciaux. Ceux-ci n'initialisent pas les en-têtes de la requête mais déterminent comment le contenu de la réponse est traité. Les noms de champ spéciaux suivants sont reconnus :

':content_file'   => $filename # ou $filehandle
':content_cb'     => \&callback
':read_size_hint' => $bytes

Si un $filename ou un $filehandle est fourni avec l'option ":content_file", le contenu de la réponse y sera stocké au lieu de l'objet réponse. Le $filehandle peut également être un objet avec un descripteur de fichier ouvert, comme un objet File::Temp. Si un callback est fourni avec l'option ":content_cb", cette fonction sera appelée pour chaque fragment de contenu de réponse reçu du serveur. Si aucune de ces options n'est fournie, le contenu de la réponse sera accumulé dans l'objet réponse lui-même. Cela peut ne pas convenir pour des corps de réponse très volumineux. Une seule des options ":content_file" ou ":content_cb" peut être spécifiée. Le contenu des réponses qui ne sont pas réussies sera toujours accumulé dans l'objet réponse lui-même, indépendamment des options ":content_file" ou ":content_cb" fournies. Notez que les erreurs lors de l'écriture dans le fichier de contenu (par exemple, en raison d'une permission refusée ou d'un disque plein) seront signalées via les en-têtes Client-Aborted ou X-Died, et non via la méthode is_success.

L'option ":read_size_hint" est passée au module de protocole, qui tentera de lire les données du serveur par morceaux de cette quantité. Une valeur plus petite pour ":read_size_hint" entraînera un plus grand nombre d'appels à la fonction de rappel.

La fonction de rappel est appelée avec trois arguments : un morceau de données, une référence à l'objet réponse et une référence à l'objet protocole. La fonction de rappel peut interrompre la requête en appelant die(). Le message d'exception apparaîtra dans l'en-tête X-Died de l'objet réponse renvoyé par la méthode "$ua->get()".

head

my $res = $ua->head( $url );
my $res = $ua->head( $url , $field_name => $value, ... );

Cette méthode envoie une requête "HEAD" sur l'URL donné. Sinon, elle fonctionne comme la méthode "get" de la méthodologie LWP::UserAgent décrite précédemment.

is_protocol_supported

my $bool = $ua->is_protocol_supported( $scheme );

Vous pouvez utiliser cette méthode pour vérifier si l'objet agent utilisateur actuel prend en charge le "scheme" spécifié. (Le "scheme" peut être une chaîne (comme "http" ou "ftp") ou peut être une référence objet à un objet URI.)

Si la prise en charge d'un schéma est déterminée par la liste des protocoles autorisés ou interdits dans l'objet agent utilisateur, et par les capacités de LWP, alors cette méthode renverra vrai uniquement si LWP prend en charge ce protocole et qu'il est autorisé pour cet objet particulier.

is_online

my $bool = $ua->is_online;

Teste si vous avez accès à Internet. Renvoie 1 (vrai) si les heuristiques intégrées déterminent que l'agent utilisateur est capable d'accéder à Internet (via HTTP) ou renvoie 0 (faux).

Voir aussi LWP::Online.

mirror

my $res = $ua->mirror( $url, $filename );

Cette méthode obtiendra le document identifié par l'URL et le stockera dans un fichier nommé $filename. Si le fichier existe déjà, la requête contiendra un en-tête "If-Modified-Since" correspondant à l'heure de modification du fichier. Si le document sur le serveur n'a pas changé depuis ce moment, rien ne sera fait. Si le document a été mis à jour, il sera téléchargé à nouveau. L'heure de modification du fichier sera forcée pour correspondre à l'heure du serveur.

Utilise la méthode "move" de File::Copy pour tenter de remplacer le fichier $filename de manière atomique.

La valeur renvoyée est un objet HTTP::Response.

S'arrête si la réponse à la requête de document contient un en-tête "X-Died".

NOM

LWP::UserAgent

SYNTAXE

use LWP::UserAgent;

DESCRIPTION

LWP::UserAgent est un module Perl qui fournit une interface simple pour effectuer des requêtes HTTP. Il vous permet de créer et d'envoyer des requêtes à divers serveurs web, de gérer les redirections et de gérer les cookies. Le module est conçu pour être facile à utiliser tout en offrant de la flexibilité aux utilisateurs avancés.
