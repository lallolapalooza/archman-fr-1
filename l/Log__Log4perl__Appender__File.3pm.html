Log__Log4perl__Appender__File(3pm)

Appender::File(3) Documentation fournie par les utilisateurs de Perl Appender::File(3)

Nom

Log::Log4perl::Appender::File - Écrit dans un fichier

SYNTAXE

use Log::Log4perl::Appender::File;
my $app = Log::Log4perl::Appender::File->new(
  filename  => 'file.log',
  mode      => 'append',
  autoflush => 1,
  umask     => 0222,
);
$file->log(message => "Log me\n");

DESCRIPTION

Ceci est un appendeur simple pour écrire dans un fichier.

La méthode log() prend un seul scalaire. Si un caractère de nouvelle ligne doit terminer le message, il doit être ajouté explicitement.

Lors de la destruction de l'objet, le handle de fichier utilisé pour accéder au fichier est vidé et fermé.

Si vous souhaitez passer à un nouveau fichier journal, utilisez la méthode file_switch($newfile) qui ferme d'abord le handle de fichier de l'ancien fichier, puis en ouvre un nouveau vers le fichier spécifié.

OPTIONS

filename
Nom du fichier journal.
mode
Les messages sont ajoutés au fichier si $mode est défini sur "append". S'il est défini sur "clobber", le fichier sera écrasé. S'il est défini sur "pipe", le fichier sera traité comme un exécutable pour faire passer la sortie dans un pipe. Le mode par défaut est "append".
autoflush
"autoflush", s'il est défini sur une valeur vraie, active le vidage des données dans le fichier chaque fois que la méthode log() est appelée. "autoflush" est activé par défaut.
syswrite
"syswrite", s'il est défini sur une valeur vraie, garantit que l'appendeur utilise syswrite() au lieu de print() pour enregistrer le message. syswrite() est généralement mappé à la fonction write() du système d'exploitation et garantit qu'aucun autre processus n'écrit dans le même fichier pendant que write() est occupé. Cela peut être plus sûr que d'avoir à utiliser des mesures de synchronisation comme des sémaphores (voir: Appendeur synchronisé).
umask
Définit le "umask" à utiliser lors de la création du fichier, déterminant ainsi les permissions du fichier. S'il est défini sur 0022 (par défaut), les nouveaux fichiers auront les permissions "rw-r--r--". S'il est défini sur 0000, les nouveaux fichiers auront les permissions "rw-rw-rw-".
owner
S'il est défini, indique que le propriétaire du nouveau fichier journal doit être différent de l'utilisateur actuel du processus exécutant le programme. Cela n'a de sens que si le processus s'exécute en tant que root. Les valeurs numériques et les noms d'utilisateur sont acceptables. Log4perl ne tente pas de changer le propriétaire des fichiers existants.
group
S'il est défini, indique que le groupe du nouveau fichier journal doit être différent du groupe actuel du processus exécutant le programme. Cela n'a de sens que si le processus s'exécute en tant que root. Les valeurs numériques et les noms de groupe sont acceptables. Log4perl ne tente pas de changer le groupe de propriété des fichiers existants.
utf8
Si vous imprimez des chaînes Unicode, le fichier de sortie doit être configuré en mode ":utf8" : 
my $app = Log::Log4perl::Appender::File->new(
  filename  => 'file.log',
  mode      => 'append',
  utf8      => 1,
);
binmode
Pour manipuler le handle de sortie à l'aide de binmode(), utilisez le paramètre binmode : 
my $app = Log::Log4perl::Appender::File->new(
  filename  => 'file.log',
  mode      => 'append',
  binmode   => ":utf8",
);

Une valeur de ":utf8" pour "binmode" est équivalente à la spécification du paramètre "utf8" (voir ci-dessus).

recreate
Normalement, si un appendeur de fichier enregistre dans un fichier et que ce fichier est déplacé vers un autre emplacement (par exemple, via "mv"), le handle de fichier de l'appendeur suivra automatiquement le nouvel emplacement.

Cela peut être indésirable. Lorsque vous utilisez un utilitaire de rotation de fichiers externe, l'appendeur doit créer un nouveau fichier sous l'ancien nom et commencer à y enregistrer. Si la valeur de "recreate" est définie sur une valeur vraie, "Log::Log4perl::Appender::File" fera exactement cela. Par défaut, elle est fausse. Examinez l'option "recreate_check_interval" pour optimiser les performances avec cette fonctionnalité.

recreate_check_interval
En mode "recreate", l'appendeur doit vérifier continuellement si le fichier sur lequel il écrit se trouve toujours au même endroit. Cette vérification est relativement coûteuse, car elle doit appeler "stat" sur le nom de fichier et déterminer si son inode a changé. Le faire à chaque appel à "log() peut être prohibitivement coûteux. La définition sur une valeur entière positive N ne vérifiera le fichier que toutes les N secondes. Par défaut, c'est 30.

Évidemment, l'appendeur continuera à écrire dans un fichier déplacé jusqu'à ce que la prochaine vérification ait lieu, au pire des cas, cela peut se produire "recreate_check_interval" secondes après que le fichier a été déplacé ou supprimé. Si cela est indésirable, définir "recreate_check_interval" sur 0 fera vérifier le fichier par l'appendeur à chaque appel à "log().

recreate_check_signal
En mode "recreate", si cette option est définie sur un nom de signal (par exemple, "USR1"), l'appendeur recréera un fichier journal manquant lorsqu'il recevra le signal. Utilise moins de ressources que le polling constant. Les limitations courantes avec la gestion des signaux en Perl s'appliquent. Voir la FAQ pour utiliser cette option avec l'utilitaire de rotation de logs "newsyslog".
recreate_pid_write
L'utilitaire populaire de rotation de logs "newsyslog" attend un fichier pid pour envoyer un signal au programme lorsque ses logs ont été rotés. Cette option attend un chemin vers un fichier dans lequel le pid du programme actuel sera écrit. Voir la FAQ pour utiliser cette option avec l'utilitaire de rotation de logs "newsyslog".
create_at_logtime
L'appendeur de fichier crée typiquement son fichier journal dans son constructeur, c'est-à-dire lors de l'initialisation de Log4perl init(). Ceci est souhaitable dans presque tous les cas, car cela garantit que les problèmes de permission sont détectés immédiatement, et non après des jours/semaines/mois de fonctionnement lorsque l'appendeur de fichier doit enregistrer quelque chose et échoue en raison d'un problème évident dès le démarrage.

Cependant, il existe de rares cas où le fichier ne doit pas être créé au moment de l'initialisation de Log4perl init(), par exemple si l'appendeur ne peut pas être utilisé par l'utilisateur actuel bien qu'il soit défini dans le fichier de configuration. Si "create_at_logtime" est défini sur une valeur vraie, l'appendeur de fichier tentera de créer le fichier au moment du log. À noter que ce réglage permet que les problèmes de permission soient ignorés jusqu'au moment du log, ce qui peut être indésirable.

header_text

NOM

SYNOPSIS

use Log::Log4perl::Appender::File;

DESCRIPTION

Log::Log4perl::Appender::File est un module qui fournit un appender de fichier pour le système de journalisation Log::Log4perl.
