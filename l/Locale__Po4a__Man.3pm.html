NOM

Locale::Po4a::Man - convertir des pages de manuel en texte en PO

DESCRIPTION

Le projet po4a a pour but de faciliter les traductions (et plus intéressant encore, la maintenance de ces traductions) en utilisant les outils gettext dans des domaines où on ne s'attendait pas à les trouver.

Locale::Po4a::Man est un module qui aide à la traduction de documents au format nroff (le langage des pages de manuel) vers d'autres langues humaines.

TRADUCTION AVEC PO4A::MAN

Ce module essaie de rendre la vie du traducteur plus facile. Pour ce faire, le texte présenté au traducteur n'est pas une copie littérale du texte trouvé dans la page de manuel. En fait, les parties les plus brutes du format nroff sont cachées, de sorte que le traducteur ne puisse pas les endommager.

Texte justifié

Les paragraphes non indentés sont réécrits automatiquement pour le traducteur. Cela peut entraîner de petites différences dans le résultat final, car les règles de justification utilisées par groff ne sont pas très claires. Par exemple, deux espaces après une parenthèse peuvent être conservés.

Cependant, la différence ne portera que sur la position des espaces supplémentaires dans un paragraphe justifié, et je pense que cela vaut la peine.

Spécifications de police

La première modification concerne les spécifications de police. En nroff, il existe plusieurs façons de spécifier si un terme donné doit être écrit en petit, en gras ou en italique. Dans le texte à traduire, il n'y a qu'une seule façon, tirée du format de documents Perl (POD) :

I<texte> -- texte en italique
équivalent à \fItexte\fP ou ".I texte"
B<texte> -- texte en gras
équivalent à \fBtexte\fP ou ".B texte"
R<texte> -- texte normal
équivalent à \fRtexte\fP
CW<texte> -- texte à chasse fixe
équivalent à \f(CWtexte\fP ou ".CW texte"

Note : Le style CW n'est pas disponible sur tous les périphériques groff. Son utilisation n'est pas recommandée. Il est disponible pour votre commodité.

Traduction automatique de caractères

Po4a traduit automatiquement certains caractères pour faciliter la traduction ou la relecture de la traduction. Voici la liste des traductions :

tirets
Les tirets (-) et les signes moins (\-) dans les pages de manuel sont traduits en tirets simples (-) dans le fichier PO. Ensuite, lorsque la traduction est insérée dans le document de sortie, tous les tirets sont traduits en signes moins roff (\-).
espaces insécables
Les traducteurs peuvent utiliser des espaces insécables dans leurs traductions. Ces espaces insécables (0xA0 en latin1) sont traduits en espaces insécables roff ('\ ').
transaltération des guillemets
Les caractères "" et '' sont traduits en \*(lq et \*(rq.
Pour éviter ces traductions, les traducteurs peuvent insérer un caractère de chasse nulle roff (c'est-à-dire en utilisant `\&` ou `\&` respectivement).

Insertion de '<' et '>' dans les traductions

Comme ces caractères sont utilisés pour délimiter des parties sous modification de police, vous ne pouvez pas les utiliser tels quels. Utilisez E<lt> et E<gt> à la place (comme dans POD, d'ailleurs).

OPTIONS ACCEPTÉES PAR CE MODULE

Voici les options spécifiques à ce module :

debug
Active le débogage de certains mécanismes internes du module. Consultez le code source pour savoir quelles parties peuvent être déboguées.
verbose
Augmente la verbosité.
groff_code
Cette option contrôle le comportement du module lorsqu'il détecte une section .de, .ie ou .if. Elle peut prendre les valeurs suivantes :
fail
C'est la valeur par défaut. Le module échouera lorsqu'une section .de, .ie ou .if sera détectée.
verbatim
Indique que les sections .de, .ie ou .if doivent être copiées telles quelles de l'original vers le document traduit.
translate
Indique que les sections .de, .ie ou .if seront proposées à la traduction. Vous ne devriez utiliser cette option que s'il y a une chaîne traduisible dans l'une de ces sections. Sinon, il est recommandé d'utiliser le mode verbatim.
generated
Cette option indique que le fichier a été généré, et que po4a n'essaiera pas de détecter si les pages de manuel ont été générées à partir d'un autre format. Cette option est obligatoire pour utiliser po4a sur des pages de manuel générées. Note : Traduire des pages générées au lieu des sources est souvent plus fragile, et par conséquent, ce n'est pas une bonne idée.
mdoc
Cette option est uniquement utile pour les pages mdoc.
Cette option sélectionne une prise en charge plus stricte du format mdoc, indiquant à po4a de ne pas traduire la section 'NAME'. Les pages mdoc dont la section 'NAME' est traduite ne généreront pas d'en-tête ou de pied de page.
Selon la page groff_mdoc, les sections NAME, SYNOPSIS et DESCRIPTION sont obligatoires. Il n'y a pas de problèmes connus avec les sections traduites de SYNOPSIS ou DESCRIPTION, mais vous pouvez aussi spécifier ces sections comme suit :
-o mdoc=NAME,SYNOPSIS,DESCRIPTION
Ce problème de mdoc peut aussi être résolu avec une addition comme suit :
PO4A-HEADER:mode=before;position=^.Dd
.TH DOCUMENT_TITLE 1 "Mois jour, année" OS "Nom de Section"

Les options suivantes spécifient le comportement d'une macro définie par l'utilisateur (avec une demande .de) ou d'une macro classique non prise en charge par po4a. Elles ont comme argument une liste de macros séparées par des virgules. Par exemple :

-o noarg=FO,OB,AR -o translate_joined=BA,ZQ,UX

Note : si une macro n'est pas prise en charge par po4a et que vous considérez qu'il s'agit d'une macro roff standard, vous devez utiliser & à la place.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

le soumettre à l'équipe de développement de po4a.

untranslated
untranslated indique que cette macro (ainsi que ses arguments) n'a pas à être traduite.
noarg
noarg est similaire à untranslated, à la différence que po4a vérifiera qu'aucun argument n'est ajouté à cette macro.
translate_joined
translate_joined indique que po4a doit proposer la traduction des arguments de la macro.
translate_each
Avec translate_each, les arguments seront également proposés à la traduction, à la différence que chacun sera traduit séparément.
no_wrap
Cette option prend comme argument une liste de couples séparés par des virgules debut:fin, où debut et fin sont des commandes qui délimitent le début et la fin d'une section qui ne doit pas être réalignée.

Note : aucun test n'est effectué pour s'assurer qu'une commande fin correspond à sa commande debut ; toute commande de fin arrête le mode no_wrap. Si vous avez une macro debut (respectivement fin) qui n'a pas de fin (respectivement debut), vous pouvez spécifier une commande fin (comme fi) ou debut (comme nf) existante comme substitut. Ces macros (et leurs arguments) ne seront pas traduites.

inline
Cette option spécifie une liste de macros séparées par des virgules qui ne doivent pas interrompre le paragraphe courant. La chaîne à traduire contiendra alors foo <.bar baz qux> quux, où bar est la commande qui doit être intégrée (inlined), et baz qux ses arguments.
unknown_macros
Cette option indique comment po4a doit se comporter lorsqu'une macro inconnue est trouvée. Par défaut, po4a échoue avec un avertissement. Elle peut prendre les valeurs suivantes : failed (la valeur par défaut), untranslated, noarg, translate_joined, ou translate_each (voir ci-dessus pour une explication de ces valeurs).

AUTORISER DES PAGES DE MANUEL COMPATIBLES AVEC PO4A::MAN

Ce module est encore très limité, et le restera toujours, car ce n'est pas un véritable interpréteur nroff. Il serait possible de créer un véritable interpréteur nroff, pour permettre aux auteurs d'utiliser toutes les macros existantes, ou même d'en définir de nouvelles dans leurs pages, mais nous n'avons pas voulu le faire. Ce serait trop difficile, et nous avons pensé que ce n'était pas nécessaire. Nous pensons que si les auteurs de pages de manuel veulent voir leurs productions traduites, ils devront peut-être s'adapter pour faciliter le travail des traducteurs.

Ainsi, l'analyseur de pages de manuel implémenté dans po4a a quelques limitations connues que nous ne sommes pas vraiment enclins à corriger, et qui constitueront certains pièges que vous devrez éviter si vous voulez que les traducteurs prennent en charge votre documentation.

Ne pas programmer en nroff

nroff est un langage de programmation complet, avec définition de macros, conditionnelles, etc. Comme cet analyseur n'est pas un interpréteur nroff complet, il échouera sur les pages utilisant ces fonctionnalités (il y a environ 200 pages de ce type sur ma machine).

Cacher du texte de po4a

Parfois, l'auteur sait que certaines parties ne sont pas traduisibles, et ne devraient pas être extraites par po4a. Par exemple, une option peut accepter un argument other, et other peut également apparaître comme dernier élément d'une liste. Dans le premier cas, other ne devrait pas être traduisible. Et dans le second cas, other devrait être traduit.

Dans un tel cas, l'auteur peut empêcher po4a d'extraire certaines chaînes, en utilisant des constructions groff spéciales :

.if !'po4a'hide' .B other

(cela nécessitera l'option -o groff_code=verbatim)

Une nouvelle macro peut également être définie pour automatiser cela :
.de IR_untranslated
. IR \\$@
..

.IR_untranslated \-q ", " \-\-quiet

(cela nécessitera les options -o groff_code=verbatim et -o untranslated=IR_untranslated ; avec cette construction, le conditionnel .if !'po4a'hide' n'est pas strictement nécessaire puisque po4a n'analysera pas l'intérieur de la définition de la macro)

ou en utilisant un alias :
.als IR_untranslated IR

.IR_untranslated \-q ", " \-\-quiet

Cela nécessitera l'option -o untranslated=als,IR_untranslated.

Conclusion

Pour résumer cette section, restez simple et n'essayez pas d'être trop malin en rédigeant vos pages de manuel. Beaucoup de choses sont possibles en nroff, et non prises en charge par cet analyseur. Par exemple, n'essayez pas d'utiliser \c pour interrompre le traitement du texte (comme le font 40 pages sur ma machine). Ou, assurez-vous de mettre les arguments de la macro sur la même ligne que la macro elle-même. Je sais que c'est valide en nroff, mais cela compliquerait trop l'analyseur pour être géré.

Bien sûr, une autre possibilité est d'utiliser un autre format, plus adapté aux traducteurs (comme POD utilisant po4a::pod, ou l'une de la famille XML comme SGML), mais grâce à po4a::man, ce n'est plus nécessaire. Cela dit, si le format source de votre documentation est POD ou XML, il pourrait être judicieux de traduire le format source et non celui généré. Dans la plupart des cas, po4a::man détectera les pages générées et émettra un avertissement. Il refusera même de traiter les pages générées à partir de POD, car celles-ci sont parfaitement gérées par po4a::pod, et parce que leur équivalent nroff définit de nombreuses nouvelles macros pour lesquelles je n'ai pas voulu écrire de prise en charge. Sur ma machine, 1432 des 4323 pages sont générées à partir de POD et seront ignorées par po4a::man.

Dans la plupart des cas, po4a::man détectera le problème et refusera de traiter la page, en émettant un message adapté. Dans certains cas rares, le programme se terminera sans avertissement, mais la sortie sera erronée. Ces cas sont appelés des « bugs » ;) Si vous rencontrez un tel cas, assurez-vous de le signaler, avec une correction lorsque possible…

ÉTAT DE CE MODULE

Ce module peut être utilisé pour la plupart des pages de manuel existantes.

Des tests sont régulièrement exécutés sur des machines Linux :

  • un tiers des pages sont refusées car elles ont été générées à partir d'un autre format pris en charge par po4a (par exemple, POD ou SGML).
  • 10 % des pages restantes sont rejetées avec une erreur (par exemple, une macro groff n'est pas prise en charge).
  • Ensuite, moins de 1 % des pages sont acceptées silencieusement par po4a, mais avec des problèmes significatifs (c'est-à-dire des mots manquants ou des nouveaux mots insérés).
  • Les autres pages sont généralement traitées sans différences plus importantes que des différences d'espacement ou des sauts de ligne réalignés (problèmes de police dans moins de 10 % des pages traitées).

NOM

Locale::Po4a::Man - Traduction de pages de manuel au format po4a

DESCRIPTION

Ce module gère la traduction de pages de manuel au format po4a.

Il hérite de Locale::Po4a::Common et implémente les méthodes spécifiques pour analyser et générer des pages de manuel.

ATTRIBUTS

  • in_encoding : Encodage des fichiers d'entrée.
  • out_encoding : Encodage des fichiers de sortie.
  • input_dir : Répertoire contenant les fichiers d'entrée.
  • output_dir : Répertoire où seront placés les fichiers de sortie.
  • source_lang : Langue source.
  • lang : Langue cible.
  • is_recursive : Booléen indiquant si la recherche doit être récursive.
  • po_dir : Répertoire contenant les fichiers .po.
  • po_encoding : Encodage des fichiers .po.
  • template_dir : Répertoire contenant les modèles.
  • template_encoding : Encodage des fichiers de modèle.

MÉTHODES

  • new(...) : Constructeur.
  • parse(...) : Analyse le fichier d'entrée et extrait les chaînes à traduire.
  • render(...) : Génère le fichier de sortie traduit.
  • process_entry(...) : Traite une entrée de catalogue de traduction.
  • process_file(...) : Traite un fichier entier.
  • get_default_po_directory() : Renvoie le répertoire .po par défaut.
  • get_default_template_directory() : Renvoie le répertoire de modèle par défaut.

DIAGNOSTICS

Les erreurs courantes incluent des problèmes de lecture de fichiers, des problèmes d'encodage et des chemins de répertoires incorrects.

EXEMPLES

Voici un exemple d'utilisation :

use Locale::Po4a::Man;

my $man = Locale::Po4a::Man->new(
    lang        => 'fr',
    input_dir   => '/usr/share/man/man1',
    output_dir  => '/home/user/translated_man/fr/man1',
    po_dir      => '/home/user/po/fr',
);

$man->process_file('ls.1.gz');

DÉPENDANCES

  • Locale::Po4a::Common
  • Getopt::Long
  • File::Basename
  • File::Find
  • Pod::Parser
  • Text::Wrap
