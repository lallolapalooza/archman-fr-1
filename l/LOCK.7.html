NOM

LOCK - verrouiller une table

SYNTAXE

LOCK [ TABLE ] [ ONLY ] nom [ * ] [, ...] [ IN mode_verrou MODE ] [ NOWAIT ]
où mode_verrou est l'un des suivants :
    ACCESS SHARE | ROW SHARE | ROW EXCLUSIVE | SHARE UPDATE EXCLUSIVE
    | SHARE | SHARE ROW EXCLUSIVE | EXCLUSIVE | ACCESS EXCLUSIVE

DESCRIPTION

LOCK TABLE obtient un verrouillage au niveau de la table, attendant si nécessaire que tout verrouillage conflictuel soit libéré. Si NOWAIT est spécifié, LOCK TABLE n'attend pas pour acquérir le verrou désiré : s'il ne peut être acquis immédiatement, la commande est annulée et une erreur est générée. Une fois obtenu, le verrou est conservé pour le reste de la transaction courante. (Il n'existe pas de commande UNLOCK TABLE ; les verrous sont toujours libérés à la fin de la transaction.)

Lorsqu'une vue est verrouillée, toutes les relations apparaissant dans la requête de définition de la vue sont également verrouillées de manière récursive avec le même mode de verrouillage.

Lors de l'acquisition automatique des verrous pour les commandes qui référencent des tables, PostgreSQL utilise toujours le mode de verrouillage le moins restrictif possible. LOCK TABLE est utile dans les cas où vous pourriez avoir besoin d'un verrouillage plus restrictif. Par exemple, supposons qu'une application exécute une transaction avec le niveau d'isolation READ COMMITTED et qu'elle doive s'assurer que les données d'une table restent stables pendant la durée de la transaction. Pour y parvenir, vous pourriez obtenir un verrouillage SHARE sur la table avant d'interroger. Cela empêchera les modifications concurrentes des données et garantira que les lectures ultérieures de la table voient une vue stable des données validées, car le mode de verrouillage SHARE entre en conflit avec le verrouillage ROW EXCLUSIVE acquis par les rédacteurs, et votre instruction LOCK TABLE nom IN SHARE MODE attendra jusqu'à ce que tout détenteur concurrent de verrouillage en mode ROW EXCLUSIVE valide ou annule sa transaction. Ainsi, une fois que vous avez obtenu le verrou, il n'y a aucune écriture non validée en suspens ; de plus, aucune ne peut commencer tant que vous n'avez pas libéré le verrou.

Pour obtenir un effet similaire lors de l'exécution d'une transaction aux niveaux d'isolation REPEATABLE READ ou SERIALIZABLE, vous devez exécuter l'instruction LOCK TABLE avant d'exécuter toute instruction SELECT ou de modification de données. La vue des données d'une transaction REPEATABLE READ ou SERIALIZABLE sera figée au début de sa première instruction SELECT ou de modification de données. Un LOCK TABLE ultérieur dans la transaction empêchera toujours les écritures concurrentes – mais il ne garantira pas que ce que la transaction lit correspond aux dernières valeurs validées.

Si une transaction de ce type doit modifier les données de la table, elle doit utiliser le mode de verrouillage SHARE ROW EXCLUSIVE au lieu du mode SHARE. Cela garantit qu'une seule transaction de ce type s'exécute à la fois. Sans cela, une interdiction (deadlock) est possible : deux transactions pourraient toutes deux acquérir le mode SHARE, puis être incapables d'acquérir également le mode ROW EXCLUSIVE pour effectuer leurs mises à jour. (Notez que les verrous d'une transaction n'entrent jamais en conflit, donc une transaction peut acquérir le mode ROW EXCLUSIVE lorsqu'elle détient le mode SHARE – mais pas si quelqu'un d'autre détient le mode SHARE.) Pour éviter les interdictions, assurez-vous que toutes les transactions acquièrent des verrous sur les mêmes objets dans le même ordre, et si plusieurs modes de verrouillage sont impliqués pour un seul objet, alors les transactions doivent toujours acquérir le mode le plus restrictif en premier.

Plus d'informations sur les modes de verrouillage et les stratégies de verrouillage sont disponibles dans la Section 13.3.

PARAMÈTRES

nom

Le nom (éventuellement qualifié par un schéma) d'une table existante à verrouiller. Si ONLY est spécifié avant le nom de la table, seule cette table est verrouillée. Si ONLY n'est pas spécifié, la table et toutes ses tables descendantes (le cas échéant) sont verrouillées. Optionnellement, * peut être spécifié après le nom de la table pour indiquer explicitement que les tables descendantes sont incluses.

La commande LOCK TABLE a, b ; est équivalente à LOCK TABLE a ; LOCK TABLE b ;. Les tables sont verrouillées une par une dans l'ordre spécifié dans la commande LOCK TABLE.

mode_verrou

Le mode de verrouillage spécifie avec quels verrous ce verrouillage est en conflit. Les modes de verrouillage sont décrits dans la Section 13.3.

Si aucun mode de verrouillage n'est spécifié, alors ACCESS EXCLUSIVE, le mode le plus restrictif, est utilisé.

NOWAIT

Spécifie que LOCK TABLE ne doit pas attendre que des verrous conflictuels soient libérés : si les verrous spécifiés ne peuvent pas être acquis immédiatement sans attendre, la transaction est annulée.

NOTES

Pour verrouiller une table, l'utilisateur doit avoir le privilège requis pour le mode_verrou spécifié. Si l'utilisateur a les privilèges MAINTAIN, UPDATE, DELETE ou TRUNCATE sur la table, tout mode_verrou est autorisé. Si l'utilisateur a le privilège INSERT sur la table, ROW EXCLUSIVE MODE (ou un mode moins conflictuel comme décrit dans la Section 13.3) est autorisé. Si un utilisateur a le privilège SELECT sur la table, ACCESS SHARE MODE est autorisé.

L'utilisateur effectuant le verrouillage sur une vue doit avoir le privilège correspondant sur la vue. De plus, par défaut, le propriétaire de la vue doit avoir les privilèges pertinents sur les relations de base sous-jacentes, tandis que l'utilisateur effectuant le verrouillage n'a besoin d'aucune permission sur les relations de base sous-jacentes. Cependant, si la vue est définie avec security_invoker sur true (voir CREATE VIEW), l'utilisateur effectuant le verrouillage, plutôt que le propriétaire de la vue, doit avoir les privilèges pertinents sur les relations de base sous-jacentes.

LOCK TABLE est inutile en dehors d'un bloc de transaction : le verrou serait conservé uniquement jusqu'à la fin de l'instruction. Par conséquent, PostgreSQL signale une erreur si LOCK est utilisé en dehors d'un bloc de transaction. Utilisez BEGIN et COMMIT (ou ROLLBACK) pour définir un bloc de transaction.

LOCK TABLE ne traite que les verrous au niveau de la table, et donc les noms de modes impliquant ROW sont tous des mésusages. Ces noms de modes doivent généralement être lus comme indiquant l'intention de l'utilisateur d'acquérir des verrous au niveau des lignes au sein de la table verrouillée. De même, le mode ROW EXCLUSIVE est un verrouillage de table partageable. Gardez à l'esprit que tous les modes de verrouillage ont des sémantiques identiques en ce qui concerne LOCK TABLE, ne différant que par les règles sur les modes qui entrent en conflit avec lesquels. Pour des informations sur la façon d'acquérir un verrouillage de ligne réel, voir la Section 13.3.2 et La clause de verrouillage dans la documentation de SELECT(7).

EXEMPLES

Obtenir un verrouillage SHARE sur une table de clé primaire lors de l'exécution d'insertions dans une table de clé étrangère :

BEGIN WORK;
LOCK TABLE films IN SHARE MODE;
SELECT id FROM films
    WHERE name = 'Star Wars: Episode I - La Menace Fantôme';
-- Faire ROLLBACK si l'enregistrement n'a pas été renvoyé
INSERT INTO films_user_comments VALUES
    (_id_, 'SUPER ! Je l''attendais depuis si longtemps !');
COMMIT WORK;

Prendre un verrouillage SHARE ROW EXCLUSIVE sur une table de clé primaire lors de l'exécution d'une opération de suppression :

BEGIN WORK;
LOCK TABLE films IN SHARE ROW EXCLUSIVE MODE;
DELETE FROM films_user_comments WHERE id IN
    (SELECT id FROM films WHERE rating < 5);
DELETE FROM films WHERE rating < 5;
COMMIT WORK;

COMPATIBILITÉ

Il n'y a pas de LOCK TABLE dans la norme SQL, qui utilise plutôt SET TRANSACTION pour spécifier les niveaux de concurrence des transactions. PostgreSQL prend également en charge cela ; voir SET TRANSACTION (SET_TRANSACTION(7)) pour les détails.

À l'exception des modes de verrouillage ACCESS SHARE, ACCESS EXCLUSIVE et SHARE UPDATE EXCLUSIVE, les modes de verrouillage PostgreSQL et la syntaxe LOCK TABLE sont compatibles avec ceux d'Oracle.
