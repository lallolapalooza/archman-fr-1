Paquet: perl-libintl-perl

Locale::TextDomain(3) Documentation Perl fournie par l'utilisateur Locale::TextDomain(3)

NOM

Locale::TextDomain - Interface Perl pour la traduction de messages Uniforum

SYNTAXE

use Locale::TextDomain ('mon-paquet', @repertoire_locales);

use Locale::TextDomain qw (mon-paquet);

my $traduit = __"Bonjour le monde !\n";

my $alt = $__{"Bonjour le monde !\n"};

my $alt2 = $__->{"Bonjour le monde !\n"};
my @liste = (N__"Bonjour",
            N__"Monde");

printf (__n ("un fichier lu", 
             "%d fichiers lus", 
             $nb_fichiers),
        $nb_fichiers);
print __nx ("un fichier lu", "{num} fichiers lus", $nb_fichiers,
            num => $nb_fichiers);
my $contexte_traduit = __p ("Verbe, voir", "Voir");
printf (__np ("Fichiers lus depuis les systèmes de fichiers",
              "un fichier lu", 
              "%d fichiers lus", 
              $nb_fichiers),
        $nb_fichiers);
print __npx ("Fichiers lus depuis les systèmes de fichiers",
             "un fichier lu", 
             "{num} fichiers lus", 
             $nb_fichiers,
             num => $nb_fichiers);

DESCRIPTION

Le module Locale::TextDomain(3pm) fournit une interface de haut niveau pour la traduction de messages Perl.

Domaines de texte

Lorsque vous demandez une traduction pour une chaîne donnée, le système utilisé dans libintl-perl suit une stratégie standard pour trouver un catalogue de messages approprié contenant la traduction : Sauf si vous définissez explicitement un nom pour le catalogue de messages, libintl-perl supposera que votre catalogue s'appelle 'messages' (sauf si vous avez modifié la valeur par défaut à autre chose via Locale::Messages(3pm), méthode textdomain()).

Vous pourriez penser que cette stratégie par défaut laisse place à l'optimisation et vous avez raison. Ce serait beaucoup plus intelligent si plusieurs progiciels, tous avec leurs catalogues de messages individuels, pouvaient être installés sur un système, et il devrait également être possible que des composants tiers de votre logiciel (comme les modules Perl) puissent charger leurs catalogues de messages, également, sans interférer avec les vôtres.

La solution est claire, vous devez attribuer un nom unique à votre base de données de messages, et vous devez spécifier ce nom au moment de l'exécution. Ce nom unique est le soi-disant domaine de texte de votre progiciel. Le nom est en fait arbitraire mais vous devriez suivre ces directives de meilleures pratiques pour assurer une interopérabilité maximale :

Sécurité du système de fichiers
En pratique, les domaines de texte sont mappés en noms de fichiers, et vous devriez donc vous assurer que le domaine de texte que vous choisissez est un nom de fichier valide sur chaque système qui exécutera votre logiciel.
Sensibilité à la casse
Les domaines de texte sont toujours sensibles à la casse (c'est-à-dire 'Package' et 'PACKAGE' ne sont pas identiques). Cependant, puisque les catalogues de messages seront stockés sur des systèmes de fichiers, qui peuvent ou non distinguer la casse lors de la recherche de noms de fichiers, vous devriez éviter les conflits potentiels ici.
Le domaine de texte doit correspondre au nom CPAN
Si votre logiciel est listé comme un module sur CPAN, vous devriez simplement choisir le nom sur CPAN comme domaine de texte. Le domaine de texte pour libintl-perl est donc 'libintl-perl'. Mais s'il vous plaît, remplacez tous les points ('.') dans votre nom de paquet par un tiret bas car ...
Domaines Internet comme solution de repli
... si votre logiciel n'est pas un module listé sur CPAN, en dernier recours, vous devriez utiliser le schéma de paquet Java(tm), c'est-à-dire choisir un domaine Internet dont vous êtes propriétaire (ou demander au propriétaire d'un domaine Internet) et concaténer votre domaine de texte préféré avec le domaine Internet inversé. Exemple : Votre entreprise exploite le site web 'www.foobar.org' et est propriétaire du domaine 'foobar.org'. Le domaine de texte pour le logiciel 'barfoos' de votre entreprise devrait donc être 'org.foobar.barfoos'.

Si votre logiciel est susceptible d'être installé en différentes versions sur le même système, il est probablement judicieux d'ajouter des informations de version à votre domaine de texte.

D'autres systèmes sont moins stricts quant au schéma de nommage des domaines de texte mais le phénomène connu sous le nom de Perl est en fait une pléthore de petits modules spécialisés et il est probablement plus sage de postuler un modèle d'espace de noms pour éviter le chaos.

Liaison des domaines de texte aux répertoires

Une fois que le système connaît le domaine de texte du message que vous souhaitez traduire dans la langue de l'utilisateur, il doit encore trouver le catalogue de messages correct. Par défaut, libintl-perl recherchera la chaîne dans la base de données de traduction située dans les répertoires /usr/share/locale et /usr/local/share/locale (dans cet ordre).

Il n'est ni garanti que ces répertoires existent sur la machine cible, ni que la routine d'installation ait un accès en écriture à ces emplacements. Vous pouvez donc indiquer à libintl-perl de rechercher d'autres répertoires avant les répertoires par défaut. La spécification d'un répertoire de recherche différent est appelée liaison d'un domaine de texte à un répertoire.

À partir de la version 1.20, Locale::TextDomain étend la stratégie par défaut par une approche spécifique à Perl. Si File::ShareDir est installé, il recherchera dans les sous-répertoires nommés locale et LocaleData (dans cet ordre) dans le répertoire retourné par "File::ShareDir::dist_dir ($textdomain)" (si File::ShareDir est installé), et vérifiera s'il y a une base de données contenant le message pour votre domaine de texte. Cela vous permet d'installer votre base de données dans le répertoire partagé spécifique à Perl en utilisant la directive "install_share" de Module::Install ou le plugin ShareDir de Dist::Zilla.

Si File::ShareDir n'est pas disponible, ou si Locale::TextDomain ne parvient pas à trouver les fichiers de traduction dans le répertoire File::ShareDir, il recherchera ensuite dans chaque répertoire trouvé dans le chemin d'inclusion standard @INC, et vérifiera s'il existe une base de données contenant le message pour votre domaine de texte. Exemple : Si le chemin /usr/lib/perl/5.8.0/site_perl se trouve dans votre @INC, vous pouvez installer vos fichiers de traduction dans /usr/lib/perl/5.8.0/site_perl/LocaleData, et ils seront trouvés au moment de l'exécution.

UTILISATION

Il est crucial de se rappeler que vous utilisez Locale::TextDomain(3) comme spécifié dans la section "SYNTAXE", c'est-à-dire que vous devez l' utiliser, pas l' exiger. Le module se comporte de manière assez différente par rapport aux autres modules.

La différence la plus significative est la signification de la liste passée comme argument à la fonction use(). Elle fonctionne en fait comme suit :

use Locale::TextDomain (DOMAINE_DE_TEXTE, REPERTOIRE, ...)

Le premier argument (la première chaîne passée à use()) est le domaine de texte de votre paquet, facultativement suivi d'une liste de répertoires à rechercher à la place des répertoires spécifiques à Perl (voir ci-dessus : /LocaleData ajouté à un répertoire File::ShareDir et à chaque chemin dans @INC).

Si vous êtes l'auteur d'un paquet 'barfoos', vous mettrez probablement la ligne

use Locale::TextDomain 'barfoos';

respectivement pour les modules non-CPAN

use Locale::TextDomain 'org.foobar.barfoos';

dans chaque module de votre paquet qui contient des chaînes traduisibles. Si votre module a été correctement installé, y compris les catalogues de messages, il sera alors capable de récupérer ces traductions au moment de l'exécution.

Si vous n'avez pas installé la base de données de traduction dans un répertoire LocaleData du répertoire File::ShareDir ou du chemin d'inclusion standard @INC (ou dans les répertoires système /usr/share/locale resp. /usr/local/share/locale), vous devez explicitement spécifier un chemin de recherche en donnant les noms des répertoires (sous forme de chaînes !) comme arguments supplémentaires à use() :

use Locale::TextDomain qw (barfoos ./dir1 ./dir2);

Alternativement, vous pouvez appeler la fonction bindtextdomain() avec des arguments appropriés (voir l'entrée pour bindtextdomain() dans "FONCTIONS" de Locale::Messages). Si vous le faites, vous devriez passer "undef" comme argument supplémentaire afin d'éviter des recherches inutiles :

use Locale::TextDomain ('barfoos', undef

FONCTIONS EXPORTÉES

Toutes les fonctions ont des noms plutôt étranges dans le but d'être courts, des opérateurs et de ne pas entrer en conflit avec des fonctions existantes dans votre espace de noms. Vous comprendrez cela lorsque vous internationaliserez votre premier programme ou module Perl. La préparation d'un programme ressemble plus à la balisage de chaînes comme traduisibles qu'à l'insertion d'appels de fonctions. Allons-y:

__ MSGID
NOTE: C'est un double sous_underscore !

La fonction de base et la plus utilisée. C'est un raccourci pour un appel à gettext() resp. dgettext(), et elle renvoie simplement la traduction pour MSGID. Si votre ancien code ressemble à ceci :

print "permission denied";

Désormais, vous écrivez :

print __"permission denied";

Et c'est tout, la chaîne sera affichée dans la langue préférée de l'utilisateur, à condition que vous ayez installé une traduction pour celle-ci.

Évidemment, vous pouvez utiliser des parenthèses :

print __("permission denied");

Ou même :

print (__("permission denied"));

À mon avis, la première version sans parenthèses est la meilleure.

__x MSGID, ID1 => VAL1, ID2 => VAL2, ...
L'une des meilleures caractéristiques de Perl est sa capacité à interpoler des variables dans des chaînes : 
print "This is the $color $thing.\n";

Cette caractéristique peut vous amener à penser que vous pouvez maintenant écrire :

print __"This is the $color $thing.\n";

Cependant, ce serait bien, mais ce n'est pas possible. Rappelez-vous que la fonction __() sert à la fois d'opérateur pour traduire des chaînes et de cadre pour des chaînes traduisibles. Si la chaîne précédente est extraite de votre code Perl, la forme non interpolée sera incluse dans le catalogue de messages car, lors de l'analyse de votre code, il est imprévisible quelles valeurs auront les variables $thing et $color au moment de l'exécution (c'est probablement l'une des raisons pour lesquelles vous avez écrit votre programme).

Cependant, au moment de l'exécution, Perl intercalera les valeurs avant même que __() (resp. la fonction subséquente gettext()) ne voie la chaîne d'origine. Par conséquent, quelque chose comme "This is the red car.\n" sera recherché dans le catalogue de messages, ne sera pas trouvé (car seul "This is the $color $thing.\n" est inclus dans la base de données), et la chaîne non traduite sera renvoyée. Honnêtement, comme il s'agit presque toujours d'une erreur, le programme xgettext(1) s'arrêtera avec une erreur fatale lorsqu'il rencontrera une telle chaîne dans votre code.

Il existe deux solutions à ce problème :

printf __"This is the %s %s.\n", $color, $thing;

mais cela présente plusieurs inconvénients : votre traducteur ne verra que la chaîne isolée et sans le contexte complet, il est presque impossible de l'interpréter correctement. En fait, les logiciels GNU emacs et autres avec la capacité d'éditer des fichiers de traduction PO vous permettront de voir le contexte dans le code source, mais il est plus probable que votre traducteur recherche un projet de traduction plus simple lorsqu'il rencontre fréquemment de tels messages.

Et même si elle comprend le programme sous-jacent, qu'en est-il si elle doit réorganiser la couleur et la chose, comme en français :

msgid "This is the red car.\n";
msgstr "Cela est la voiture rouge.\n"

Zut alors ! Bien qu'il soit possible de réorganiser les arguments de printf() et similaires, cela nécessite une syntaxe que vous ne voulez pas apprendre.

Alors, quoi? Le backend Perl pour gettext de GNU a défini un format alternatif pour les chaînes interpolables :

"This is the {color} {thing}.\n";

Au lieu de variables Perl, vous utilisez des placeholders entre accolades, puis vous appelez :

print __x ("This is the {color} {thing}.\n",
           thing => $thang,
           color => $color);

La fonction __x() prendra le hash supplémentaire et remplacera toutes les occurrences des clés du hash entre accolades par les valeurs correspondantes. Simple, lisible, compréhensible par les traducteurs, que demander de plus ? Et si le traducteur oublie, écrit mal ou endommage une "variable", la fonction msgfmt(1), qui est utilisée pour compiler le fichier de traduction textuel en sa représentation binaire, s'énervera même face à ces erreurs et refusera la compilation de la traduction.

__n MSGID, MSGID_PLURAL, COUNT
Ouf ! Cela semble compliqué... Mieux vaut l'expliquer avec un exemple. Revisons votre ancien code : 
if ($files_deleted > 1) {
    print "All files have been deleted.\n";
} else {
    print "One file has been deleted.\n";
}

Votre intention est claire, vous voulez éviter le compliqué "1 files deleted". C'est correct en anglais, mais dans d'autres langues, il y a plus d'un pluriel. Par exemple, en russe, il y a une distinction entre 1 fichier, 3 fichiers ou 6 fichiers. Vous utiliserez trois formes différentes du nom "fichier" dans chaque cas. [Note : Si vous le savez, vous comprendrez aussi le reste, même si cette simplification est un peu compliquée...].

C'est pourquoi la fonction ngettext() existe, dont __n() est un raccourci :

print __n"One file has been deleted.\n",
         "All files have been deleted.\n",
         $files_deleted;

Alternativement :

print __n ("One file has been deleted.\n",
           "All files have been deleted.\n",
           $files_deleted);

L'effet est toujours le même : libintl-perl trouvera la forme correcte pour votre langue utilisateur et le texte sera toujours affiché correctement.

__nx MSGID, MSGID_PLURAL, COUNT, VAR1 => VAL1, VAR2 => VAL2, ...
En réunissant tout ce qui précède : 
print __nx ("One file has been deleted.\n",
            "{count} files have been deleted.\n",
            $num_files,
            count => $num_files);

La fonction __nx() choisit la forme plurielle correcte (également pour l'anglais) et peut interpoler des variables dans les chaînes.

Bien que vous vouliez regarder l'ordre des arguments : le premier est la chaîne au singulier, le second est la chaîne au pluriel. Le troisième argument est un entier indiquant le nombre d'éléments. Ce troisième argument est *uniquement* utilisé pour choisir la forme correcte. Les arguments optionnels suivants forment le hash utilisé pour l'interpolation. Initialement, il est souvent déroutant que la variable qui stocke le nombre d'éléments apparaisse généralement répétée dans le hash d'interpolation.

__xn MSGID, MSGID_PLURAL, COUNT, VAR1 => VAL1, VAR2 => VAL2, ...
Fait exactement la même chose que __nx(). En réalité, c'est une faute de frappe courante promue au rang de fonctionnalité.
__p MSGCTXT, MSGID
C'est beaucoup plus comme __. Le "p" signifie "particulier" et MSGCTXT est utilisé pour fournir un contexte aux traducteurs. Cela peut être nécessaire lorsque votre chaîne est courte et pourrait représenter plusieurs significations. Par exemple :

print __p"Verb, to view", "View";
print __p"Noun, a view", "View";

L'exemple précédent peut être "View" dans un menu où View->Source et File->View sont des formes différentes de "View", qui nécessitent probablement d'être traduites différemment.

Une utilisation typique concerne les programmes d'interface graphique. Imaginez un programme avec un menu principal et l'entrée notable "Open" dans le menu Fichier. Imaginez maintenant une autre entrée de menu Préférences->Avancé->Politique où vous avez le choix entre les alternatives "Open" et "Closed". En anglais, "Open" est le texte approprié dans les deux cas. Dans d'autres langues, il est très probable que vous ayez besoin de deux traductions distinctes. Par conséquent, vous écririez maintenant :

__p"File|", "Open";
__p"Preferences|Advanced|Policy", "Open";

En anglais, ou s'il n'y a pas de traduction, le deuxième argument (MSGID) est renvoyé.

Cette fonction a été introduite dans libintl-perl 1.17.

__px MSGCTXT, MSGID, VAR1 => VAL1, VAR2 => VAL2, ...
Comme __p(), mais prend en charge le remplacement de variables dans la chaîne, comme __x(). 
print __px("Verb, to view", "View {file}", file => $filename);

Voir __p() et __x() pour plus de détails.

Cette fonction a été introduite

Le module exporte plusieurs variables dans son espace de noms :

%__
Une table de hachage liée. Ses clés sont vos messages originaux, et ses valeurs sont vos traductions : 
my $title = "<h1>$__{'My Homepage'}</h1>";

Ceci est beaucoup mieux pour votre équipe de traduction que :

my $title = __"<h1>My Homepage</h1>";

Dans ce dernier cas, le code HTML sera transformé en texte dans le catalogue de traduction, et vos traducteurs devront faire attention à la syntaxe HTML lorsqu'ils traduiront les chaînes de caractères.

Attention : N'utilisez pas cette table de hachage en dehors des chaînes avec guillemets doubles ! Le code de la table de hachage liée dépend du bon fonctionnement de la fonction caller() (voir https://perldoc.cpan.org/perlfunc/caller.html), et cette fonction renverra des résultats incorrects si la valeur de la table de hachage liée est l'argument d'une fonction d'un autre paquet, par exemple :

my $result = Other::Package::do_it ($__{'Some string'});

Le code de la table de hachage liée considérera « Other::Package » comme le paquet appelant, au lieu de votre propre paquet. Par conséquent, il recherchera le message dans le domaine de texte incorrect. Il n'y a pas de remède à cette erreur. Par conséquent :

N'utilisez pas cette table de hachage interpolée dans des chaînes de caractères !

$__
Une référence à "%__", au cas où vous préféreriez : 
my $title = "<h1>$__->{'My Homepage'}</h1>";

MÉTHODES DE CLASSE

Les méthodes de classe suivantes sont définies :

options
Renvoie une liste séparée par des espaces de toutes les options « --keyword » et « --flag » pour xgettext(1) lors de l'extraction des chaînes localisées avec Locale::TextDomain.

Cette option devrait être nommée xgettextDefaultOptions. Par rapport à une utilisation typique, un nom plus court a été choisi :

xgettext `perl -MLocale::TextDomain -e 'print Locale::TextDomain->options'`

Voir https://www.gnu.org/software/gettext/manual/html_node/xgettext-Invocation.html pour plus d'informations sur les options « --keyword » et « --flag » de xgettext(1).

Si vous souhaitez désactiver l'utilisation des mots-clés par défaut de xgettext, vous devez passer une option « --keyword="" » à xgettext avant les options renvoyées par cette méthode.

En cas de doute sur l'utilité de cette méthode, vérifiez le résultat en ligne de commande :

perl -MLocale::TextDomain -e 'print Locale::TextDomain->options'

Rien que vous ne puissiez taper vous-même.

Cette méthode a été ajoutée dans libintl-perl 1.28.

keywords
Renvoie une liste séparée par des espaces de toutes les options « --keyword » pour xgettext(1) afin que les chaînes localisées soient correctement extraites.

Cette méthode a été ajoutée dans libintl-perl 1.28.

flags
Renvoie une liste séparée par des espaces de toutes les options « --flag » pour xgettext(1) afin que les chaînes localisées soient correctement étiquetées.

Cette méthode a été ajoutée dans libintl-perl 1.28.

PERFORMANCE

La traduction de messages peut être une tâche coûteuse en temps, prenez cet exemple :

1: use Locale::TextDomain ('my-domain');
2: use POSIX (:locale_h);
3: 
4: setlocale (LC_ALL, '');
5: print __"Hello world!\n";

Ceci sera généralement rapide, mais dans des cas extrêmes, cela peut prendre plusieurs secondes. Un scénario de pire cas serait un utilisateur chinois sur un terminal qui comprend le jeu de caractères Big5-HKSCS. Votre traducteur chinois a choisi de coder les traductions dans le jeu de caractères EUC-TW.

Que se passe-t-il en temps réel ? Tout d'abord, la bibliothèque recherche et charge un catalogue de messages (potentiellement volumineux) pour votre domaine de texte 'my-domain'. Ensuite, elle recherche la traduction de « Hello world!\n », la trouve codée en EUC-TW. Comme cela diffère du jeu de caractères de sortie Big5-HKSCS, elle chargera d'abord une table de conversion contenant plusieurs centaines de codes caractères pour EUC-TW, puis fera de même avec la table de conversion plus petite mais toujours très grande pour Big5-HKSCS, convertira la traduction en temps réel de EUC-TW vers Big5-HKSCS, puis enfin renverra la traduction convertie.

Un scénario pire mais réaliste. Et pour ces cinq lignes de code, il n'y a pas grand-chose à faire pour le rendre plus rapide. Vous devez cependant comprendre *quand* chaque étape se produira, afin de pouvoir organiser votre code en conséquence.

Vous avez appris dans la section « DESCRIPTION » que la ligne 1 est responsable de la localisation de votre base de messages. Cependant, l'utilisation de use() ne fera que vous rappeler vos configurations. Elle ne recherchera aucun répertoire, ne chargera aucun catalogue ni table de conversion.

Quelque part dans votre code, il y aura toujours un appel à POSIX::setlocale(), et la performance de cet appel peut être coûteuse en temps, en fonction de l'architecture de votre système. Sur certains systèmes, cela prendra très peu de temps, sur d'autres seulement un temps considérable pour le premier appel, et sur d'autres encore, cela pourra toujours être coûteux en temps. Étant donné que vous ne pouvez pas savoir comment setlocale() est implémenté sur le système cible, vous devriez réduire les appels à setlocale() au minimum.

La ligne 5 demande la traduction de votre chaîne. C'est seulement maintenant que la bibliothèque charge réellement le catalogue de messages, et c'est seulement maintenant qu'elle charge éventuellement les tables de conversion nécessaires. Et à partir de maintenant, toutes ces informations seront stockées en mémoire. Cette stratégie est utilisée tout le temps dans libintl-perl, et vous pouvez la décrire comme « chargement au premier accès ». Obtenir la traduction suivante prendra très peu de ressources.

Cependant, même si la récupération de la traduction est un peu cachée par un appel de fonction qui ressemble à un appel d'opérateur, il s'agit toujours d'un appel de fonction, et cela implique même une chaîne d'appels de fonctions. Par conséquent, l'exemple suivant peut être pratiquement mauvais :

foreach (1 .. 100_000) {
    print __"Hello world!\n";
}

Cet exemple introduit un surcoût important dans votre programme. Il est préférable de le faire ainsi :

my $string = __"Hello world!\n";
foreach (1 .. 100_000) {
    print $string;
}

La traduction ne changera jamais, il n'est pas nécessaire de la récupérer à chaque fois. Même si libintl-perl stockera la traduction lue à partir du système de fichiers, vous pouvez toujours éviter le surcoût des appels de fonction.
