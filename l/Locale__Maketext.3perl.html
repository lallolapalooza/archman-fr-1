Locale::Maketext(3perl) Manuel du programmeur Perl Locale::Maketext(3perl)

NOM

Locale::Maketext - cadre de localisation

SYNOPSIS

package MyProgram;
use strict;
use MyProgram::L10N;
 # ...qui hérite de Locale::Maketext
my $lh = MyProgram::L10N->get_handle() || die "Quelle langue ?";
...
# Et puis n'importe quel message que votre programme émet, comme :
warn $lh->maketext( "Impossible d'ouvrir le fichier [_1]: [_2]\n", $f, $! );
...

DESCRIPTION

C'est une caractéristique commune des applications (qu'elles soient exécutées directement ou via le Web) d'être « localisées » — c'est-à-dire de présenter une interface anglaise pour un locuteur anglais, une interface allemande pour un locuteur allemand, et ainsi de suite pour toutes les langues pour lesquelles l'application est programmée. Locale::Maketext est un cadre pour la localisation de logiciels ; il fournit les outils pour organiser et accéder aux morceaux de texte et au code de traitement de texte nécessaires pour produire des applications localisées.

Pour mieux comprendre le concept de Maketext et comment tous ses composants s'emboîtent, vous aimerez peut-être lire Locale::Maketext::TPJ13, puis lire la documentation suivante.

Vous voudrez peut-être aussi lire le code source de "File::Findgrep" et ses modules constitutifs — c'est un exemple complet (bien que petit) qui utilise Maketext.

APERÇU RAPIDE

La conception de base de Locale::Maketext est orientée objet, et Locale::Maketext est une classe abstraite, dont les classes de projet sont dérivées, et qui sont utilisées dans vos modules. La classe de projet (avec un nom comme "TkBocciBall::Localize", qui est ensuite utilisée dans votre module) est la classe de base pour toutes les classes de langue de votre projet (avec des noms comme "TkBocciBall::Localize::it", "TkBocciBall::Localize::en", "TkBocciBall::Localize::fr", etc.).

Une classe de langue est une classe qui contient un dictionnaire de phrases sous forme de données de classe, et potentiellement aussi des méthodes utiles pour interpréter des phrases dans le dictionnaire ou pour traiter du texte dans cette langue.

Un objet appartenant à une classe de langue est appelé un « gestionnaire de langue » ; c'est typiquement un objet léger.

La norme d'action consiste à appeler :

use TkBocciBall::Localize;  # la classe de projet de localisation
$lh = TkBocciBall::Localize->get_handle();
 # En fonction de la langue de l'utilisateur, etc., cela instancie un gestionnaire de langue parmi les classes disponibles,
 # et toutes les valeurs par défaut que vous déclarez.
die "Impossible de créer un gestionnaire de langue ??" unless $lh;

Dès lors, la fonction "maketext" est utilisée pour accéder aux entrées de n'importe quel dictionnaire de langue (qui appartient au gestionnaire de langue que vous avez obtenu). Ainsi, ceci :

print $lh->maketext("You won!"), "\n";

…imprime le texte correct pour cette langue. Si l'objet dans $lh appartient à la classe "TkBocciBall::Localize::fr" et que %TkBocciBall::Localize::fr::Lexicon contient "You won!" => "Tu as gagné!", alors le code ci-dessus dira joyeusement à l'utilisateur « Tu as gagné! ».

MÉTHODES

Locale::Maketext offre une variété de méthodes, qui se divisent en trois catégories :

  • Méthodes pour construire des gestionnaires de langue.
  • "maketext" et autres méthodes pour accéder aux données de %Lexicon d'un gestionnaire de langue.
  • Méthodes que vous pourriez trouver utile d'utiliser, à partir de routines de vos propres que vous placez dans les entrées de %Lexicon.

Celles-ci sont couvertes dans la section suivante.

Méthodes de construction

Celles-ci sont liées à la construction d'un gestionnaire de langue :

  • $lh = YourProjClass->get_handle( ...langtags... ) || die "Quelle est la langue ?";

    Cela tente de charger des classes basées sur les balises de langue que vous donnez (comme "("en-US", "sk", "kon", "es-MX", "ja", "i-klingon"", et pour la première classe qui se résout, renvoie YourProjClass::language->new().

    Si la liste complète des balises de langue fournies est parcourue sans trouver de classes pour ces balises exactes, elle tente alors les classes de langue « superordonnées ». Ainsi, si la classe "en-US" (c'est-à-dire YourProjClass::en_us) n'existe pas, ni les classes pour d'autres éléments de cette liste, nous essayons la classe superordonnée, "en" (c'est-à-dire YourProjClass::en), et ainsi de suite pour les autres balises de langue dans la liste donnée : "es" (les autres balises de notre exemple listent n'ayant pas de superordonnées).

    Si aucune de ces balises de langue ne mène à une classe chargeable, nous essayons les classes dérivées de YourProjClass->fallback_languages() et, en cas d'échec, nous utilisons les classes nommées par YourProjClass->fallback_language_classes(). Donc, dans le cas (probablement très rare) où cela échoue, nous renverrons undef.

  • $lh = YourProjClass->get_handle() || die "Quelle est la langue ?";

    Lorsque "get_handle" est appelé avec un paramètre vide, de la magie opère :

    Si "get_handle" sent qu'il exécute un programme appelé comme CGI, il essaie d'obtenir les balises de langue à partir de la variable d'environnement "HTTP_ACCEPT_LANGUAGE", et prétend que celles-ci ont été passées à "get_handle".

    Sinon (c'est-à-dire s'il n'est pas CGI), il essaie plusieurs méthodes spécifiques à l'OS pour obtenir les balises de langue de l'environnement actuel, puis prétend que celles-ci étaient les valeurs passées à "get_handle".

    Actuellement, ce contenu système d'exploitation consiste à regarder dans les variables d'environnement "LANG" et "LANGUAGE" ; et en cas de systèmes Windows (où ces variables sont généralement inutilisées), il essaie également d'utiliser le module Win32::Locale pour obtenir une balise de langue pour la langue/région système actuelle dans l'onglet « Régions et Préférences » (ou « Intercontinental ? ») du panneau de configuration. J'aimerais que vous puissiez suggérer d'autres idées sur la façon de faire en sorte que cela fasse la bonne chose sur d'autres systèmes d'exploitation qui prennent en charge la localisation.

    Si vous utilisez la localisation dans un projet qui maintient un fichier de configuration, vous pourriez envisager quelque chose comme ceci dans votre classe de projet :

    sub get_handle_via_config {
  my $class = $_[0];
  my $chosen_language = $Config_settings{'language'};
  my $lh;
  if($chosen_language) {
    $lh = $class->get_handle($chosen_language)
     || die "Impossible de trouver un gestionnaire de langue pour \"$chosen_language\""
          . " ou un type similaire";
  } else {
    # Le fichier de configuration est manquant, peut-être ?
    $lh = $class->get_handle()
     || die "Impossible d'obtenir un gestionnaire de langue";
  }
  return $lh;
}
  • $lh = YourProjClass::langname->new();

    Cela construit un gestionnaire de langue. Vous ne l'appelez généralement pas directement, mais cela permet à "get_handle" de trouver une classe de langue à utiliser, puis d'appeler "new() dessus.

  • $lh->init();

    Ceci est appelé par "new() pour initialiser de nouveaux gestionnaires de langue. Si vous définissez une méthode init dans votre classe, n'oubliez pas qu'il est généralement bon d'appeler $lh->SUPER::init dessus (probablement au début), afin que toutes les classes puissent initialiser un nouvel objet de manière indépendante.

  • YourProjClass->fallback_languages()

    Le "get_handle" ajoute la valeur renvoyée par cette fonction à la liste des langues passées à "get_handle". Sauf si vous remplacez cette fonction, votre classe de projet héritera de "fallback_languages" de Locale::Maketext, qui renvoie actuellement "('i-default', 'en', 'en-US')" (où "i-default" est défini dans la RFC 2277).

Cette méthode (en la faisant retourner le nom d'une balise de langue qui a une classe de langue existante) peut être utilisée pour s'assurer que "get_handle" parviendra toujours à construire un descripteur de langue (en supposant que vos classes de langue se trouvent dans un répertoire @INC approprié). Ou vous pouvez utiliser la méthode suivante :

  • VotreProjClass->fallback_language_classes()

    "get_handle" ajoute la valeur de retour de cette méthode à la fin de la liste des classes qu'elle essaiera d'utiliser. Sauf si vous remplacez cette méthode, votre classe de projet héritera de "fallback_language_classes" de Locale::Maketext, qui retourne actuellement une liste vide, "()". En définissant ceci à une certaine valeur (à savoir, le nom d'une classe de langue chargeable), vous pouvez être sûr que "get_handle" parviendra toujours à construire un descripteur de langue.

    • La méthode "maketext"

    C'est la méthode la plus importante de Locale::Maketext :

    $text = $lh->maketext(I<clé>, ...paramètres pour cette phrase...);

    Ceci recherche dans le %Lexicon du descripteur de langue $lh et de toutes ses superclasses, à la recherche d'une entrée dont la clé est la chaîne de caractères clé. En supposant qu'une telle entrée est trouvée, diverses choses se produisent alors, en fonction de la valeur trouvée :

    Si la valeur est une référence scalaire, le scalaire est déréférencé et retourné (et tous les paramètres sont ignorés).

    Si la valeur est une référence de code, nous retournons &$value($lh, ...paramètres...).

    Si la valeur est une chaîne qui ne ressemble pas à une Notation entre crochets, nous la retournons (après l'avoir remplacée par une référence scalaire, dans son %Lexicon).

    Si la valeur ressemble effectivement à une Notation entre crochets, alors nous la compilons en une sous-routine, remplaçons la chaîne dans le %Lexicon par la nouvelle référence de code, et retournons ensuite &$new_sub($lh, ...paramètres...).

    La Notation entre crochets est discutée dans une section ultérieure. Notez qu'essayer de compiler une chaîne en Notation entre crochets peut lancer une exception si la chaîne n'est pas syntaxiquement valide (par exemple, si les crochets ne sont pas équilibrés).

    De plus, appeler &$coderef($lh, ...paramètres...) peut lancer n'importe quel type d'exception (si, par exemple, le code de cette sous-routine essaie de diviser par zéro). Mais une exception très courante se produit lorsque vous avez un texte en Notation entre crochets qui demande d'appeler une méthode "foo", mais qu'il n'y a pas une telle méthode. (Par exemple, "Vous avez [quatn,_1,boule]." lancera une exception en essayant d'appeler $lh->quatn($_[1],'boule') -- vous vouliez probablement dire "quant".) "maketext" intercepte ces exceptions, mais seulement pour rendre le message d'erreur plus lisible, moment auquel il relance l'exception.

    Une exception peut être lancée si la clé n'est pas trouvée dans aucun des %Lexicon de $lh. Ce qui se passe lorsqu'une clé n'est pas trouvée est discuté dans une section ultérieure, "Controlling Lookup Failure".

    Notez qu'il peut vous être utile dans certains cas de remplacer la méthode "maketext" par une "méthode après", si vous souhaitez traduire des encodages, voire des scripts :

    package YrProj::zh_cn; # Chinois avec glyphes de style PRC
use base ('YrProj::zh_tw');  # Style Taiwan
sub maketext {
  my $self = shift(@_);
  my $value = $self->maketext(@_);
  return Chineeze::taiwan2mainland($value);
}

    Ou vous voudrez peut-être la remplacer par quelque chose qui intercepte toutes les exceptions, si c'est essentiel pour votre programme :

    sub maketext {
  my($lh, @stuff) = @_;
  my $out;
  eval { $out = $lh->SUPER::maketext(@stuff) };
  return $out unless $@;
  ...sinon traiter l'exception...
}

    Mis à part ces deux situations, je n'imagine pas qu'il soit utile de remplacer la méthode "maketext". (Si vous rencontrez une situation où cela est utile, je serais intéressé de l'entendre.)

    $lh->fail_with ou $lh->fail_with(PARAM)
    $lh->failure_handler_auto
    Ces deux méthodes sont discutées dans la section "Controlling Lookup Failure".
    $lh->denylist(@list) <ou> $lh->blacklist(@list)
    $lh->allowlist(@list) <ou> $lh->whitelist(@list)
    Ces méthodes sont discutées dans la section "Bracket Notation Security".

    Méthodes utilitaires

    Ce sont des méthodes que vous trouverez peut-être utiles, généralement à partir de routines de %Lexicon (qu'elles soient exprimées en Notation entre crochets ou non).

    $language->quant($number, $singular)
    $language->quant($number, $singular, $plural)
    $language->quant($number, $singular, $plural, $negative)
    Ceci est généralement destiné à être appelé depuis l'intérieur de la Notation entre crochets (qui est discutée plus loin), comme dans 
    "Votre recherche a trouvé [quant,_1,document] !"

    C'est pour quantifier un nom (c'est-à-dire, dire combien il y en a, tout en donnant la forme correcte). Le comportement de cette méthode est pratique pour l'anglais et quelques autres langues d'Europe occidentale, et vous devriez la remplacer pour les langues où elle n'est pas adaptée. N'hésitez pas à lire le code source, mais l'implémentation actuelle est fondamentalement telle que ce pseudocode la décrit :

    si $number est 0 et qu'il y a un $negative,
   retourne $negative;
sinon si $number est 1,
   retourne "1 $singular";
sinon si il y a un $plural,
   retourne "$number $plural";
sinon
   retourne "$number " . $singular . "s";
#
# ...sauf que nous appelons en fait numf pour
#  convertir $number en chaîne avant de le retourner.

    Ainsi, pour l'anglais (avec Notation entre crochets) "...[quant,_1,file]..." est bien (pour 0 cela retourne "0 files", pour 1 cela retourne "1 file", et pour plus cela retourne "2 files", etc.)

    Mais pour "directory", vous voudriez "[quant,_1,directory,directories]" afin que notre méthode "quant" élémentaire ne pense pas que le pluriel de "directory" soit "directorys". Et vous pourriez trouver que la sortie sonne mieux si vous spécifiez une forme négative, comme dans :

    "[quant,_1,file,files,No files] matched your query.\n"

    N'oubliez pas de tenir compte de l'accord verbal (ou des adjectifs, dans d'autres langues), comme dans :

    "[quant,_1,document] were matched.\n"

    Car si _1 est un, vous obtenez "1 document were matched". Un piratage acceptable ici est de faire quelque chose comme ceci :

    "[quant,_1,document was, documents were] matched.\n"
    $language->numf($number)
    Ceci retourne le nombre donné formaté proprement selon les conventions de cette langue. La méthode par défaut de Maketext se contente principalement de prendre la forme normale en chaîne du nombre (en appliquant sprintf "%G" uniquement pour les très grands nombres), puis d'ajouter des virgules si nécessaire. (Sauf que nous appliquons "tr/,./.,/" si $language->{'numf_comma'} est vrai ; c'est un peu un hack qui est utile pour les langues qui expriment deux millions comme "2.000.000" et non comme "2,000,000").

    Si vous voulez quelque chose de plus sophistiqué, envisagez de remplacer ceci par quelque chose qui utilise Number::Format, ou fait quelque chose de complètement différent.

    Notez que numf est appelé par quant pour convertir en chaîne tous les nombres quantifiés.

    $language->numerate($number, $singular, $plural, $negative)
    Ceci retourne la forme de nom donnée qui est appropriée pour la quantité $number selon les conventions de cette langue. "numerate" est utilisé en interne par "quant" pour quantifier les noms. Utilisez-le directement -- généralement à partir de la notation entre crochets -- pour éviter l'appel implicite de "quant" à "numf" et la sortie d'une quantité numérique.
    $language->sprintf($format, @items)
    Ceci est juste un wrapper autour de la fonction normale de Perl "sprintf". Il est fourni afin que vous puissiez utiliser "sprintf" en Notation entre crochets : 
    "Impossible d'accéder au datanode [sprintf,%10x=~[%s~],_1,_2] !\n"

    retournant...

    Impossible d'accéder au datanode      Stuff=[thangamabob] !
    $language->language_tag()
    Actuellement, ceci prend simplement la dernière partie de ref($language), remplace les underscores par des tirets, et le retourne. Donc si $language est un objet de la classe Hee::HOO::Haw::en_us, $language->language_tag() retourne "en-us". (Oui, la représentation habituelle pour cette balise de langue est "en-US", mais la casse n'est jamais considérée comme significative dans la comparaison des balises de langue.)

    Vous pouvez remplacer ceci comme bon vous semble ; Maketext ne l'utilise pour rien.

    $language->encoding()
    Actuellement, ceci n'est pas utilisé pour quoi que ce soit, mais il est fourni (avec une valeur par défaut de "(ref($language) && $language->{'encoding'}) or "iso-8859-1"" ) comme une sorte de suggestion qu'il peut être utile/nécessaire d'associer des encodages à vos descripteurs de langue (que ce soit sur une base par classe ou même par descripteur.)

    Attributs et internes des descripteurs de langue

    Un descripteur de langue est un objet flyweight -- c'est-à-dire qu'il ne porte pas (nécessairement) de données d'intérêt, autre que d'être membre de la classe à laquelle il appartient.

    Un descripteur de langue est implémenté comme une table de hachage bénie. Les sous-classes des vôtres peuvent stocker toutes les données que vous souhaitez dans la table. Actuellement, la seule entrée de table utilisée par une méthode Maketext cruciale est "fail", donc n'hésitez pas à utiliser tout le reste comme bon vous semble.

    Rappelez-vous : N'ayez pas peur de lire le code source de Maketext s'il y a un point sur lequel cette documentation n'est pas claire. Cette documentation est beaucoup plus longue que le code source du module lui-même.

    HIÉRARCHIES DE CLASSES DE LANGUES

    Voici les hypothèses de Locale::Maketext sur la hiérarchie des classes formées par toutes vos classes de langue :

    • Vous devez avoir une classe de base de projet, que vous chargez puis utilisez comme premier argument lors de l'appel à YourProjClass->get_handle(...). Cette classe doit dériver (directement ou indirectement) de Locale::Maketext. Peu importe comment cette classe est nommée, bien que nous supposions qu'elle est le composant de localisation de votre Super Mega Programme, de bons noms pour cette classe pourraient être SuperMegaProgram::Localization, SuperMegaProgram::L10N, SuperMegaProgram::I18N, SuperMegaProgram::International, ou même SuperMegaProgram::Languages ou SuperMegaProgram::Messages.
    • Les classes de langue sont ce que YourProjClass->get_handle essaiera de charger. Il recherche chaque étiquette de langue (en ignorant si ce n'est pas une étiquette de langue ou de localisation !), la convertit en minuscules, remplace les tirets par des traits de soulignement, et l'ajoute à YourProjClass. « :: ». Ainsi, ceci : 
      $lh = YourProjClass->get_handle(
  'en-US', 'fr', 'kon', 'i-klingon', 'i-klingon-romanized'
);

      tentera de charger les classes YourProjClass::en_us (notez la casse !), YourProjClass::fr, YourProjClass::kon, YourProjClass::i_klingon et YourProjClass::i_klingon_romanized. (Et s'arrêtera au premier qui se charge réellement.)

    • Je suppose que chaque classe de langue dérive (directement ou indirectement) de votre classe de projet, et définit également son @ISA, son %Lexicon ou les deux. Mais j'anticipe qu'il n'y aura pas de conséquences graves si ces hypothèses ne sont pas remplies.
    • Les classes de langue peuvent dériver d'autres classes de langue (bien qu'elles devraient avoir « use Thatclassname » ou « use base qw(...classes...) »). Elles peuvent dériver de la classe de projet. Elles peuvent dériver d'une classe séparée. Ou bien, par héritage multiple, elles peuvent dériver de n'importe quel mélange de celles-ci.
    • Je ne vois aucun problème avec l'héritage multiple dans la hiérarchie des classes de langue. (Bien que Perl se plaindra avec rudesse s'il y a un cycle dans la hiérarchie : c'est-à-dire, si une classe est un ancêtre d'elle-même.)

    ENTRÉES DANS CHAQUE %LEXICON

    Une entrée typique de %Lexicon est destinée à représenter une phrase, avec un certain nombre (0 ou plus) de paramètres. Une entrée est accessible via une clé de chaîne dans $lh->maketext(key, ...parameters...), qui doit retourner une chaîne généralement destinée à être utilisée pour la « sortie » vers l'utilisateur - qu'elle soit destinée à être imprimée sur STDOUT, écrite dans un fichier ou placée dans un widget d'interface graphique.

    Alors que la clé doit être une valeur de chaîne (car c'est une contrainte de base que Perl impose aux clés de hachage), la valeur de l'entrée dans le %Lexicon peut être de plusieurs types : un scalaire défini, un référenceur de scalaire ou une référence de code. L'utilisation de ces types est expliquée plus haut, dans la section « La méthodologie « maketext » ». La notation entre crochets pour les chaînes est discutée dans la section suivante.

    Bien que vous puissiez utiliser n'importe quel identifiant unique pour les clés de %Lexicon (comme &_min_larger_max_error), il est utile si la clé est elle-même une valeur valide, comme cet exemple de message d'erreur :

    "Minimum ([_1]) is larger than maximum ([_2])!\n",

    Comparé à ce code qui utilise un identifiant arbitraire...

    die $lh->maketext( "_min_larger_max_error", $min, $max )
 if $min > $max;

    ...à ce code qui utilise une clé comme valeur...

    die $lh->maketext(
 "Minimum ([_1]) is larger than maximum ([_2])!\n",
 $min, $max
) if $min > $max;

    La deuxième option est, en bref, plus lisible. En particulier, il est évident que le nombre de paramètres que vous donnez à cette phrase (deux) est le nombre de paramètres qu'elle souhaite recevoir. (Comme vous voyez _1 et _2 dans la clé.)

    De plus, une fois que le projet sera largement terminé et que vous commencerez à le localiser, vous pourrez collecter toutes les différentes clés que vous utilisez et les transmettre à un traducteur ; et si ce que le traducteur reçoit est ceci :

    "Minimum ([_1]) is larger than maximum ([_2])!\n",
 => "",   # fill in something here, Jacques!

    plutôt que ceci, plus confus :

    "_min_larger_max_error"
 => "",   # fill in something here, Jacques

    Je pense que les clés comme valeurs de %Lexicon rendent les entrées complètes de %Lexicon plus lisibles :

    "Minimum ([_1]) is larger than maximum ([_2])!\n",
 => "Le minimum ([_1]) est plus grand que le maximum ([_2])!\n",

    De plus, avoir des valeurs valides comme clés est très utile si vous configurez un %AUTO lexicon. Les lexiques %AUTO sont discutés dans une section ultérieure.

    Je pense que j'utilise toujours des clés qui sont des valeurs valides de %Lexicon. Une exception notable est lorsque la valeur est assez longue. Par exemple, pour obtenir le bloc complet de données qu'un programme en ligne de commande peut retourner lorsqu'on lui donne un commutateur inconnu, j'utilise généralement une clé courte et auto-explicative comme &_USAGE_MESSAGE. À ce stade, je définirai cette entrée %Lexicon dans la classe de projet::L10N::en (puisque l'anglais est toujours ma langue de projet) :

    '_USAGE_MESSAGE' => <<'EOSTUFF',
...long long message...
EOSTUFF

    et je peux ensuite l'utiliser comme ceci :

    getopt('oDI', \%opts) or die $lh->maketext('_USAGE_MESSAGE');

    Attention : notez que le %Lexicon de chaque classe hérite et étend les entrées %Lexicon de ses superclasses. Ce n'est pas parce qu'il s'agit de hachages spéciaux, mais parce que vous y accédez via la méthodologie « maketext », qui recherche des entrées dans tous les %Lexicon de la classe de langue et de toutes ses classes ancêtres. (C'est parce que le concept de « données de classe » n'est pas directement implémenté dans Perl, mais est laissé à l'implémentation des systèmes de classes selon ce que chaque système voit.)

    Note : vous pouvez avoir des éléments stockés dans un %Lexicon en plus des phrases de sortie : par exemple, si votre programme communique avec le clavier, posant une question « O/N », vous aurez probablement besoin de savoir ce qui équivaut à « O[ui]/N[on] » dans n'importe quelle langue. Vous auriez également besoin de savoir ce que « o » et « n » équivalent. Vous pouvez stocker ces informations dans le %Lexicon (par exemple, sous les clés « ~answer_y » et « ~answer_n », et les formes longues comme « ~answer_yes » et « ~answer_no », où « ~ » est juste un caractère ad-hoc pour indiquer aux programmeurs/traducteurs qu'il ne s'agit pas de phrases de sortie).

    Ou, au lieu de stocker cela dans le %Lexicon de la classe de langue, vous pouvez (et, dans certains cas, devriez vraiment) représenter la même partie de la connaissance sous forme de code dans une méthode de la classe de langue. (Cela laisse une distinction claire entre le %Lexicon comme ce que nous savons dire, et le reste des éléments de la classe %Lexicon comme ce que nous savons faire.) Considérez cet exemple d'un processeur de réponses aux questions françaises « oui/non » :

    sub y_or_n {
  return undef unless defined $_[1] and length $_[1];
  my $answer = lc $_[1];  # Smash case
  return 1 if $answer eq 'o' or $answer eq 'oui';
  return 0 if $answer eq 'n' or $answer eq 'non';
  return undef;
}

    ...qui est ensuite appelé dans un constructeur comme ceci :

    my $response;
until(defined $response) {
  print $lh->maketext("Open the pod bay door (y/n)? ");
  $response = $lh->y_or_n( get_input_from_keyboard_somehow() );
}
if($response) { $pod_bay_door->open()         }
else          { $pod_bay_door->leave_closed() }

    D'autres données que vous pourriez stocker dans un %Lexicon peuvent être des noms de fichiers pour des ressources destinées aux langues :

    ...
"_main_splash_png"
  => "/styles/en_us/main_splash.png",
"_main_splash_imagemap"
  => "/styles/en_us/main_splash.incl",
"_general_graphics_path"
  => "/styles/en_us/",
"_alert_sound"
  => "/styles/en_us/hey_there.wav",
"_forward_icon"
 => "left_arrow.png",
"_backward_icon"
 => "right_arrow.png",
# En d'autres langues, gauche est
#  BACKWARDS, et droite est FOREWARDS.
...

    Vous pourriez également faire de même pour exprimer des touches d'accès rapide ou autre chose (puisque coder « q » comme touche de sortie pour la fonction qui ferme un écran/menu/programme n'est utile que si votre langue associe « q » à « quit » !)

    NOTATION ENTRE CROCHETS

    La notation entre crochets est une caractéristique clé de Locale::Maketext. Je fais référence à la notation entre crochets comme un substitut à l'utilisation du formatage sprintf. Tout ce que vous faites avec la notation entre crochets peut être fait avec un bloc de sous-routine, mais la notation entre crochets est plus concise.

    La notation entre crochets est similaire à un mini système de modèles (au sens de Text::Template, pas au sens de C++ templates), où le texte normal est essentiellement transmis tel quel, mais le texte dans des régions spéciales est interprété de manière spéciale. Dans la notation entre crochets, vous utilisez des crochets (« [...] »), et non des accolades (« {...} ») pour indiquer des sections spéciales interprétées.

    Par exemple, ici toutes les zones considérées comme littérales sont soulignées par « ^ », et toutes les régions entre crochets spéciales sont soulignées par « X » :

    "Minimum ([_1]) is larger than maximum ([_2])!\n",
 ^^^^^^^^^ XX ^^^^^^^^^^^^^^^^^^^^^^^^^^ XX ^^^^

    Lorsque cette chaîne est compilée à partir de la notation entre crochets en une sous-routine Perl réelle, elle devient essentiellement :

    sub {
  my $lh = $_[0];
  my @params = @_;
  return join '',
    "Minimum (",
    ...code ici...,
    ") is larger than maximum (",
    ...code ici...,
    ")!\n",
}
# à appeler par $lh->maketext(KEY, params...))

    En d'autres termes, le texte en dehors des groupes entre crochets devient des littéraux de chaîne. Le texte à l'intérieur des crochets est plus complexe et suit actuellement ces règles :

    • Les groupes de crochets vides ou contenant uniquement des espaces sont ignorés. (Exemples : « [] », « [ ] », ou un [ et un ] avec des espaces, des tabulations ou des espaces entre eux.)

      Sinon, chaque groupe est considéré comme un groupe séparé par des virgules d'éléments, et chaque élément est interprété comme suit :

    • Un élément qui est « _digits » ou « _-digits » est interprété comme $_[value]. C'est-à-dire, « _1 » devient $_[1], et « _-3 » est interprété comme $_[-3] (au sens de Perl).

    SÉCURITÉ DE LA NOTATION ENTRE CROCHETS

    Locale::Maketext n'utilise aucune syntaxe spéciale pour différencier les méthodes de notation entre crochets des méthodes normales de classe ou d'objet. Cette conception le rend vulnérable aux attaques de formatage lorsqu'il est utilisé pour traiter des chaînes fournies par des utilisateurs non fiables.

    Locale::Maketext prend en charge les fonctionnalités de liste noire (denylist) et de liste blanche (allowlist) pour limiter les méthodes pouvant être appelées en tant que méthodes de notation entre crochets.

    Par défaut, Locale::Maketext refuse toutes les méthodes dans l'espace de noms Locale::Maketext qui commencent par le caractère '_' et toutes les méthodes qui incluent les caractères séparateurs de l'espace de noms de Perl.

    Le refus par défaut de Locale::Maketext empêche également l'utilisation des méthodes suivantes en notation entre crochets :

    denylist
encoding
fail_with
failure_handler_auto
fallback_language_classes
fallback_languages
get_handle
init
language_tag
maketext
new
allowlist
whitelist
blacklist

    Cette liste peut être étendue en refusant des méthodes supplémentaires « connues comme mauvaises » ou en autorisant des méthodes « connues comme bonnes ».

    Pour empêcher que certaines méthodes ne soient appelées en notation entre crochets, utilisez la méthode denylist() :

    my $lh = MyProgram::L10N->get_handle();
$lh->denylist(qw{my_internal_method my_other_method});
$lh->maketext('[my_internal_method]'); # génère une erreur

    Pour limiter les méthodes de notation entre crochets à une liste spécifique, utilisez la méthode allowlist() :

    my $lh = MyProgram::L10N->get_handle();
$lh->allowlist('numerate', 'numf');
$lh->maketext('[_1] [numerate, _1,shoe,shoes]', 12); # fonctionne
$lh->maketext('[my_internal_method]'); # génère une erreur

    Les méthodes refusées par denylist() ne peuvent pas être autorisées par allowlist().

    NOTE : denylist() est la méthode préférée par rapport à l'ancienne méthode non inclusive blacklist(). blacklist() pourrait être supprimée dans une future version de ce package et devrait donc être évitée.

    NOTE : allowlist() est la méthode préférée par rapport à l'ancienne méthode non inclusive whitelist(). whitelist() pourrait être supprimée dans une future version de ce package et devrait donc être évitée.

    LEXICONS AUTOMATIQUES

    Si maketext recherche dans un %Lexicon individuel une entrée pour key (où key ne commence pas par un tiret bas), et n'en trouve aucune, mais trouve une entrée « _AUTO » => some_true_value, alors nous définissons effectivement $Lexicon{key} = key à ce moment-là, puis utilisons cette valeur comme si elle avait été présente depuis le début. Cela se produit avant même de regarder dans d'éventuels %Lexicons de super-classe !

    (Ceci est destiné à être un peu comme le mécanisme AUTOLOAD dans le système d'appel de fonctions de Perl – ou, vu autrement, comme le module AutoLoader.)

    Je peux imaginer divers cas où vous ne souhaitez pas que la recherche soit possible (car l'échec normalement signifie que maketext déclenche un "die", bien que voir la section suivante pour plus de contrôle à ce sujet). Mais voici une situation où les lexiques _AUTO sont particulièrement utiles :

    Pendant que vous écrivez une application, vous décidez comment émettre les messages dont vous avez besoin. Normalement, vous écririez ceci :

    if(-e $filename) {
  go_process_file($filename)
} else {
  print qq{Couldn't find file "$filename"!\n};
}

    mais vous anticipez déjà la localisation de celui-ci, vous écririez :

    use ThisProject::I18N;
my $lh = ThisProject::I18N->get_handle();
 # Supposons que les choses sont configurées ainsi...
...
if(-e $filename) {
  go_process_file($filename)
} else {
  print $lh->maketext(
    qq{Couldn't find file "[_1]"!\n}, $filename
  );
}

    Maintenant, juste après avoir écrit les lignes ci-dessus, vous devriez normalement ouvrir le fichier ThisProject/I18N/en.pm et y ajouter immédiatement une entrée :

    "Couldn't find file \"[_1]\"!\n"
=> "Couldn't find file \"[_1]\"!\n"

    Mais je trouve que c'est une distraction du travail principal – à moins que vous n'ayez également à faire tourner le programme plusieurs fois avant de décider exactement le texte que vous voulez utiliser dans les messages (auquel cas vous auriez à modifier trois lignes de code : l'appel à maketext avec cette clé et puis...)

    LEXICONS EN LECTURA SOLA

    Si su léxico es una tabla asociativa enlazada (tied hash), el simple acto de almacenar en caché el valor compilado puede ser catastrófico. Por ejemplo, una tabla asociativa enlazada de tipo GDBM_File que sea un LECTOR GDBM_READER colapsará con algo como:

    gdbm store returned -1, errno 2, key "..." at ...

    Solo tiene que activar la caché externa fuera de la tabla asociativa del léxico en sí, de esta manera:

    sub init {
    my ($lh) = @_;
    ...
    $lh->{'use_external_lex_cache'} = 1;
    ...
}

    Y luego, en lugar de almacenar el valor compilado en la tabla asociativa del léxico, lo almacenará en $lh->{'_external_lex_cache'}.

    CONTROL DE FALLOS DE BÚSQUEDA

    Si llama a $lh->maketext(key, ...parámetros...), y no existe una entrada key en la clase $lh's %Lexicon, ni en la tabla asociativa %Lexicon de la superclase, y si no puede auto-crear key (porque comienza con "_", o porque ninguno de sus léxicos tiene "_AUTO => 1"), entonces ha fallado en encontrar una forma normal de crear key para maketext. Lo que sucede en estas condiciones de fallo depende del atributo "fail" del objeto $lh.

    Si el manejador de idioma no tiene un atributo "fail", maketext lanzará una excepción (es decir, llamará a "die", mencionando la key cuya búsqueda falló, y el número de línea donde se llamó a $lh->maketext(key,...)).

    Si el manejador de idioma tiene un atributo "fail" cuyo valor es un coderef, entonces $lh->maketext(key,...parámetros...) se aborta y llama:

    return $that_subref->($lh, $key, @params);

    De lo contrario, el valor del atributo "fail" debe ser una cadena que indique el nombre de un método, de modo que $lh->maketext(key,...parámetros...) se detenga con:

    return $lh->$that_method_name($phrase, @params);

    El atributo "fail" se puede configurar con el método "fail_with":

    # Establecer a un coderef:
$lh->fail_with( \&failure_handler );
# Establecer a un nombre de método:
$lh->fail_with( 'failure_method' );
# Establecer a nada (es decir, para que el fallo lance una excepción simple)
$lh->fail_with( undef );
# Obtener el valor actual
$handler = $lh->fail_with();

    Ahora, ¿qué quiere hacer con estos manejadores? Quizás desee registrar qué clave falló para qué clase y luego lanzar una excepción. Quizás no le guste "die" y prefiera enviar el mensaje de error a STDOUT (o a donde quiera) y solo llamar a exit(). Quizás no quiera lanzar "die" en absoluto! Quizás pueda usar un manejador como este:

    # Hacer que todas las búsquedas recurran a un valor en inglés,
# pero solo después de que lo registremos para posterior señalización.
my $lh_backup = ThisProject->get_handle('en');
open(LEX_FAIL_LOG, ">>donde/lex.log") || die "GNAARGH $!";
sub lex_fail {
  my($failing_lh, $key, $params) = @_;
  print LEX_FAIL_LOG scalar(localtime), "\t",
     ref($failing_lh), "\t", $key, "\n";
  return $lh_backup->maketext($key,@params);
}

    Algunos usuarios han expresado que la idea de tener un atributo "fail" parece una complicación puntual. Sin embargo, quiero que Locale::Maketext sea utilizable en proyectos de software de cualquier escala y tipo; y diferentes proyectos de software tienen diferentes ideas sobre qué hacer en condiciones de fallo. Podría simplemente decir que el fallo siempre lanza una excepción, y que si quiere ser cauteloso, simplemente envíe cada llamada a $lh->maketext a un eval { }.

    Sin embargo, quiero que los programadores se reserven el derecho (a través del atributo "fail") de tratar el fallo como algo distinto de una excepción de igual gravedad que una configuración no legible o un recurso esencial inaccesible.

    Un valor potencial útil para el atributo "fail" es el nombre de un método "failure_handler_auto". Este es un método definido en la propia clase Locale::Maketext. Puede configurarlo con:

    $lh->fail_with('failure_handler_auto');

    Luego, cuando llame a $lh->maketext(key, ...parámetros...) y no exista una entrada key en ninguno de esos léxicos, maketext devuelve:

    return $lh->failure_handler_auto($key, @params);

    Pero failure_handler_auto, en lugar de morir o no hacer nada, compila $key, lo almacena en caché en:

    $lh->{'failure_lex'}{$key} = $compiled

    y luego llama al valor almacenado en caché y devuelve eso. (Es decir, si $key parece notación de corchetes, $compiled es un sub, y devolvemos &{$compiled}(@params); pero si $key es solo una cadena normal, simplemente la devolvemos.)

    El efecto de usar "failure_auto_handler" es como un léxico AUTO, excepto que 1) compila $key incluso si comienza con "_", y 2) tiene un registro en el nuevo hashref $lh->{'failure_lex'} de todas las claves que han fallado para este objeto. Esto debería evitar que su programa colapse, siempre que sus claves no sean realmente inválidas como código de corchetes, y siempre que no intenten llamar a métodos que no existen.

    "failure_auto_handler" no es necesariamente lo que usted quiere, pero espero que al menos le muestre que el fallo de maketext se puede mitigar de muchas maneras flexibles. Si puede formalizar exactamente lo que quiere, debería poder expresarlo como un manejador de fallos. Incluso puede hacerlo por defecto para todos los objetos de una clase específica, estableciendo este atributo en esa clase:

    sub init {
  my $lh = $_[0];  # un nuevo manejador
  $lh->SUPER::init();
  $lh->fail_with('my_clever_failure_handler');
  return;
}
sub my_clever_failure_handler {
  ...haz lo que quieras...
}

    CÓMO USAR MAKETEXT

    Aquí tienes una lista de verificación breve sobre cómo utilizar Maketext para localizar aplicaciones:

    • Decida qué sistema utilizará para sus claves de léxico. Si lo prefiere, puede usar identificadores opacos (si es nostálgico de "catgets"), pero tengo mejores sugerencias en la sección "Entries in Each Lexicon". Suponiendo que elige claves significativas que también son valores (como "Minimum ([_1]) is larger than maximum ([_2])!\n"), tendrá que decidir en qué idioma deben estar. A efectos de argumento, llamaré a este idioma inglés, específicamente inglés estadounidense, "en-US".
    • Cree una clase para su proyecto de localización. Este es el nombre de la clase que utilizará en el estilo: 
      use Projname::L10N;
my $lh = Projname::L10N->get_handle(...) || die "Language?";
      Suponiendo que llame a su clase Projname::L10N, cree una clase mínimamente consistente: 
      package Projname::L10N;
use base qw(Locale::Maketext);
...cualquier método que su clase quiera compartir entre todos los idiomas...
# y, suponiendo que quiera que la clase base sea un léxico _AUTO, como se discute en varias secciones anteriores:
1;
    • Cree una clase para las claves internas de su proyecto. Nombre la clase después de la etiqueta de idioma en minúsculas, con los guiones cambiados a guiones. Suponiendo que su primer idioma sea inglés estadounidense, debería llamar a esta clase Projname::L10N::en_us. Ella debe ser mínimamente consistente: 
      package Projname::L10N::en_us;
use base qw(Projname::L10N);
%Lexicon = (
  '_AUTO' => 1,
);
1;

      (Para el resto de esta sección, asumiré que la clase "primera clase de idioma" de Projname::L10N::en_us tiene un léxico _AUTO.)

    • Revise el código de su programa. En cada lugar donde escribiría: 
      print "Foobar $thing stuff\n";
      reemplácelo con un uso de maketext, sin interpolación de variables en la clave: 
      print $lh->maketext("Foobar [_1] stuff\n", $thing);

      Si se aburre de decir constantemente "print $lh->maketext", considere hacer un wrapper funcional, como:

      use Projname::L10N;
our $lh;
$lh = Projname::L10N->get_handle(...) || die "Language?";
sub pmt (@) { print( $lh->maketext(@_) }
 # "pmt" es abreviatura de "Print MakeText"
$Carp::Verbose = 1;
 # así, si maketext falla, verá la llamada a pmt

      Además de frases completas para la salida, cualquier cosa dependiente del idioma debe estar en la clase Projname::L10N::en_us, ya sea como métodos o como entradas de léxico; esto se discute en la sección "Entries in Each Lexicon".

    • Una vez que el programa esté en su mayor parte terminado, y una vez que la localización del primer idioma funcione correctamente (a través de los datos y métodos de Projname::L10N::en_us), puede preparar los datos para la traducción. Si su primer idioma no es un léxico _AUTO, entonces ya tiene todos los mensajes explícitamente en el léxico (o de lo contrario lanzará una excepción al llamar a $lh->maketext para mensajes que no estén allí). Pero si usó (siguiendo el consejo) un léxico _AUTO, entonces tendrá que hacer una lista de todas las frases que hasta ahora ha permitido que _AUTO genere para usted. Hay muchas formas de hacer esto. La forma más sencilla es simplemente buscar en el código cada ocurrencia:

      grep -e '$_AUTO' ...
