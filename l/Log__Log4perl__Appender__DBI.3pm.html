NOM

Log::Log4perl::Appender::DBI - implémente l'ajout à une base de données

SYNTAXE

  my $config = q{
   log4j.category = WARN, DBAppndr
   log4j.appender.DBAppndr             = Log::Log4perl::Appender::DBI
   log4j.appender.DBAppndr.datasource  = DBI:CSV:f_dir=t/tmp
   log4j.appender.DBAppndr.username    = bobjones
   log4j.appender.DBAppndr.password    = 12345
   log4j.appender.DBAppndr.sql         = \
      insert into log4perltest           \
      (loglevel, custid, category, message, ipaddr) \
      values (?,?,?,?,?)
   log4j.appender.DBAppndr.params.1 = %p    
                                 #2 est custid de l'appel log()
   log4j.appender.DBAppndr.params.3 = %c
                                 #4 est le message de log()
                                 #5 est ipaddr de log()
   log4j.appender.DBAppndr.usePreparedStmt = 1
    #--ou--
   log4j.appender.DBAppndr.bufferSize = 2
   #passe simplement le tableau d'éléments de message dans l'instruction log
   log4j.appender.DBAppndr.layout    = Log::Log4perl::Layout::NoopLayout
   log4j.appender.DBAppndr.warp_message = 0
   #support des attributs du pilote
   log4j.appender.DBAppndr.attrs.f_encoding = utf8
  };
  Log::Log4perl::init ( \$config ) ;                                      
  my $logger = Log::Log4perl->get_logger () ;                             
  $logger->warn( $custid, 'problème majeur !!', $ip_addr );

AVERTISSEMENT

Ceci est un module très jeune et il existe de nombreuses variations dans les configurations avec différentes bases de données et méthodes de connexion, alors assurez-vous de tester soigneusement ! Tout commentaire est bienvenu !

DESCRIPTION

Il s'agit d'un objet Log::Dispatch spécialisé, personnalisé pour fonctionner avec log4perl et ses capacités, basé à l'origine sur Log::Dispatch::DBI de Tatsuhiko Miyagawa mais avec des modifications importantes.

Il s'agit d'une tentative de compromis entre ce que faisait Log::Dispatch::DBI et ce que fait JDBCAppender de log4j. Notez que la documentation de log4j indique que JDBCAppender « sera très probablement entièrement remplacé à l'avenir ».

L'utilisation la plus simple est la suivante :

log4j.category = WARN, DBAppndr
log4j.appender.DBAppndr            = Log::Log4perl::Appender::DBI
log4j.appender.DBAppndr.datasource = DBI:CSV:f_dir=t/tmp
log4j.appender.DBAppndr.username   = bobjones
log4j.appender.DBAppndr.password   = 12345
log4j.appender.DBAppndr.sql        = \
   INSERT INTO logtbl                \
      (loglevel, message)            \
      VALUES ('%c','%m')
log4j.appender.DBAppndr.layout    = Log::Log4perl::Layout::PatternLayout
$logger->fatal('message fatal');
$logger->warn('message d'avertissement');
===============================
|FATAL|message fatal          |
|WARN |message d'avertissement |
===============================

Mais les inconvénients de cette utilisation sont :

  • Mieux vaut être sûr qu'il n'y a pas de guillemets dans votre message de journal, sinon votre insertion pourrait avoir des conséquences imprévues ! C'est une manière très peu sûre de gérer les insertions dans la base de données, utiliser des espaces réservés et lier les valeurs est beaucoup mieux, continuez à lire. (Notez que la documentation de log4j avertit « Soyez prudent avec les guillemets dans vos messages ! ») *.
  • Ce n'est pas très performant, une instruction est créée et exécutée pour chaque appel de journal.
  • Le seul paramètre d'exécution que vous obtenez est le message %m, en réalité vous souhaitez probablement enregistrer des données spécifiques dans des colonnes de table spécifiques.

Alors essayons d'utiliser des espaces réservés et indiquons au journal de créer une gestion d'instruction préparée au début et de la réutiliser (tout comme le fait Log::Dispatch::DBI)

log4j.appender.DBAppndr.sql = \
   INSERT INTO logtbl \
      (custid, loglevel, message) \
      VALUES (?,?,?)
#---------------------------------------------------
#maintenant les valeurs liées :
                              #1 est le custid
log4j.appender.DBAppndr.params.2 = %p    
                              #3 est le message
#---------------------------------------------------
log4j.appender.DBAppndr.layout    = Log::Log4perl::Layout::NoopLayout
log4j.appender.DBAppndr.warp_message = 0

log4j.appender.DBAppndr.usePreparedStmt = 1


$logger->warn( 1234, 'message d'avertissement' );

Maintenant, voyez comment nous utilisons les espaces réservés « ? » dans notre instruction ? Cela signifie que nous n'avons pas à nous soucier des messages qui ressemblent à

entrée invalide : 1234';drop table custid;

endommager notre base de données !

Normalement, une liste d'éléments dans l'instruction de journalisation est concaténée en une seule chaîne, mais en réglant "warp_message" sur 0 et en utilisant NoopLayout, cela signifie que dans

$logger->warn( 1234, 'message d'avertissement', 'bgates' );

les éléments individuels de la liste seront toujours disponibles pour l'annexe DBI par la suite. (Si "warp_message" n'est pas réglé sur 0, le comportement par défaut est de joindre les éléments de la liste en une seule chaîne. Si PatternLayout ou SimpleLayout sont utilisés, leur tentative de render() votre disposition entraînera quelque chose comme « ARRAY(0x841d8dc) » dans vos journaux. Plus d'informations sur "warp_message" se trouvent dans Log::Log4perl::Appender.)

Dans votre instruction d'insertion, vous pouvez mélanger des espaces réservés « ? » avec des spécificateurs de conversion (%c, %p, etc.) comme vous le souhaitez - le journal correspondra aux points d'interrogation aux paramètres que vous avez définis dans le fichier de configuration et remplira le reste avec les valeurs de votre liste. S'il y a plus d'espaces réservés « ? » que de valeurs dans votre message, il utilisera `undef` pour les restants. Par exemple,

log4j.appender.DBAppndr.sql =                 \
   insert into log4perltest                   \
   (loglevel, message, datestr, subpoena_id)\
   values (?,?,?,?)
log4j.appender.DBAppndr.params.1 = %p
log4j.appender.DBAppndr.params.3 = %d
log4j.appender.DBAppndr.warp_message=0
$logger->info('arrêtez-le !', $subpoena_id);

résulte en le premier espace réservé « ? » étant lié à %p, le deuxième à « arrêtez-le ! », le troisième à la date de « %d », et le quatrième à votre $subpoenaid. Si vous oubliez le $subpoena_id et enregistrez simplement

$logger->info('arrêtez-le !');

alors vous obtenez simplement `undef` dans la quatrième colonne.

Si l'instruction de journalisation est également traitée par d'autres annexes non-DBI, elles joindront simplement la liste en une chaîne, jointe par $Log::Log4perl::JOIN_MSG_ARRAY_CHAR (par défaut une chaîne vide).

Et voyez le "usePreparedStmt" ? Cela crée une gestion d'instruction lors de la création de l'objet journal et la réutilise simplement. Cela peut cependant poser problème pour les processus de longue durée comme les serveurs web, auquel cas vous pouvez utiliser ce paramètre à la place

log4j.appender.DBAppndr.bufferSize=2

Ceci copie le comportement JDBCAppender de log4j, il accumule ce nombre d'instructions de journal et les écrit toutes en une seule fois. Si votre instruction INSERT utilise uniquement des espaces réservés « ? » et aucun spécificateur de conversion %x, elle devrait être assez efficace car le journal peut réutiliser la même gestion d'instruction pour les insertions.

Si le programme se termine alors que le tampon n'est que partiellement rempli, le bloc DESTROY devrait vider les instructions restantes, si le bloc DESTROY s'exécute bien sûr.

* Pendant que j'écrivais ceci, Danko Mannhaupt sortait son JDBCAppender amélioré pour log4j (http://www.mannhaupt.com/danko/projects/) qui surmonte de nombreux inconvénients de l'JDBCAppender original.

DESCRIPTION 2

Ou une autre façon de dire la même chose :

L'idée est que si vous enregistrez dans une table de base de données, vous voulez probablement des parties spécifiques de vos informations de journal dans des colonnes particulières. À cette fin, vous passez une liste à l'instruction de journal, comme

$logger->warn('problème majeur !!',$userid,$subpoena_nr,$ip_addr);

et les membres du tableau tombent dans les positions définies par les espaces réservés dans votre instruction SQL. Vous pouvez également définir des informations dans le fichier de configuration comme

log4j.appender.DBAppndr.params.2 = %p

auquel cas ces espaces réservés numérotés seront remplis avec les valeurs spécifiées, et le reste des espaces réservés sera rempli avec les valeurs du tableau de votre instruction de journal.

NOM

Log::Log4perl::Appender::DBI

SYNOPSIS

Utilisez ce module pour créer un appender DBI pour Log4perl.

use Log::Log4perl::Appender::DBI;

ATTENTION

Si vous utilisez "log4j.appender.DBAppndr.usePreparedStmt", ce module crée un sth lors de son démarrage et le conserve pendant toute la durée du programme. Pour les processus de longue durée (par exemple, mod_perl), les connexions peuvent devenir obsolètes, mais si "Log::Log4perl::Appender::DBI" essaie d'écrire un message et découvre que la connexion à la base de données ne fonctionne plus (en utilisant la méthode ping de DBI), il se reconnectera.

Le processus de reconnexion peut être contrôlé par deux paramètres, "reconnect_attempts" et "reconnect_sleep". "reconnect_attempts" spécifie le nombre de tentatives de reconnexion que l'appender DBI effectue jusqu'à ce qu'il abandonne et échoue. "reconnect_sleep" est le temps entre les tentatives de reconnexion, mesuré en secondes. "reconnect_attempts" vaut par défaut 1, "reconnect_sleep" vaut 0.

Alternativement, utilisez "Apache::DBI" ou "Apache::DBI::Cache" et lisez CHANGING DBCONNECTIONS ci-dessus.

Notez que "Log::Log4perl::Appender::DBI" maintient une connexion ouverte pour chaque appender, ce qui peut être trop.

CHANGEMENT DES CONNEXIONS DBH (POOLING)

Si vous souhaitez obtenir votre dbh d'un endroit particulier, comme peut-être un pool, sous-classez et surchargez _init() et/ou create_statement(), par exemple

sub _init {
    ; #pas d'opération, pas de pooling à ce niveau
}
sub create_statement {
    my ($self, $stmt) = @_;

    $stmt || croak "Log4perl: sql non défini dans ".__PACKAGE__;

    return My::Connections->getConnection->prepare($stmt)
        || croak "Log4perl: DBI->prepare a échoué $DBI::errstr\n$stmt";
}
