NOM

Locale::gettext_dumb - Implémentation non locale de la traduction de messages Uniforum

SYNOPIS

use Locale::gettext_dumb qw(:locale_h :libintl_h);
# Normalement, vous ne voudrez pas inclure ce module directement mais plutôt comme ceci :
use Locale::Messages;

my $selected = Locale::Messages->select_package ('gettext_dumb');
gettext $msgid;
dgettext $domainname, $msgid;
dcgettext $domainname, $msgid, LC_MESSAGES;
ngettext $msgid, $msgid_plural, $count;
dngettext $domainname, $msgid, $msgid_plural, $count;
dcngettext $domainname, $msgid, $msgid_plural, $count, LC_MESSAGES;
pgettext $msgctxt, $msgid;
dpgettext $domainname, $msgctxt, $msgid;
dcpgettext $domainname, $msgctxt, $msgid, LC_MESSAGES;
npgettext $msgctxt, $msgid, $msgid_plural, $count;
dnpgettext $domainname, $msgctxt, $msgid, $msgid_plural, $count;
dcnpgettext $domainname, $msgctxt, $msgid, $msgid_plural, $count, LC_MESSAGES;

my $category = LC_CTYPE;

my $category = LC_MESSAGES;
my $category = LC_ALL;

DESCRIPTION

IMPORTANT ! Ce module est expérimental. Il peut ne pas fonctionner comme décrit !

Le module Locale::gettext_dumb fait exactement la même chose que Locale::gettext_xs(3pm) ou Locale::gettext_pp(3pm).

Alors que les deux autres modules utilisent POSIX::setlocale() pour déterminer la locale actuellement sélectionnée, ce backend ne vérifie que les variables d'environnement LANGUAGE, LANG, LC_ALL, LC_MESSAGES (dans cet ordre), lorsqu'il essaie de localiser un catalogue de messages (un fichier .mo).

Cette classe a été introduite dans libintl-perl 1.22.

UTILISATION

Ce module ne doit pas être utilisé pour des logiciels de bureau ou des scripts exécutés localement. Pourquoi ? Si vous utilisez un catalogue de messages par exemple en danois en UTF-8 (da_DA.UTF8) mais que la locale du système est réglée sur russe avec KOI8-R (ru_RU.KOI8-R), vous pouvez produire une sortie invalide, soit des séquences multi-octets invalides, soit du texte invalide, selon la perspective.

Cela se produira lorsque vous mélangez la sortie de Locale::gettext_pp avec une sortie dépendante de la locale du système d'exploitation, comme le contenu de la variable "$!", les fonctions de formatage de date et d'heure (localtime(), gmtime(), POSIX::strftime() etc.), le formatage des nombres avec printf() et ses semblables, et ainsi de suite.

Un scénario d'utilisation typique ressemble à ceci :

Vous avez une application serveur (par exemple une application web) qui est censée afficher un ensemble fixe de messages dans de nombreuses langues. Si vous voulez faire cela avec Locale::gettext_xs(3pm) ou Locale::gettext_pp(3pm), vous devez installer les données de locale pour toutes ces langues. Sinon, la traduction des messages ne fonctionnera pas.

Avec Locale::gettext_dumb(3pm), vous pouvez assouplir ces exigences et afficher des messages pour toutes les langues pour lesquelles vous avez des fichiers mo.

D'un autre côté, vous atteindrez bientôt des limites avec cette approche. Presque toute application nécessite plus qu'une simple traduction de messages pour la localisation. Vous voulez des dates et heures formatées, vous voulez afficher des nombres dans le format correct pour les langues sélectionnées, et vous pourriez vouloir afficher des messages d'erreur système ("$!").

En pratique, Locale::gettext_dumb(3pm) est toujours utile dans ces scénarios. Vos utilisateurs devront accepter le fait que la sortie présentée est dans différentes langues ou pour différentes locales, lorsque « leur » locale n'est pas installée sur votre système.

Il est plus dangereux de mélanger des sorties dans différents jeux de caractères, mais cela peut être facilement évité. Assurez-vous simplement que Locale::gettext_dump utilise UTF-8 (par exemple en réglant la variable d'environnement OUTPUT_CHARSET ou en appelant bind_textdomain_codeset()) et assurez-vous que la locale du système utilise également UTF-8, par exemple « en_US.UTF8 ». Si cela échoue, passez à une locale qui utilise un sous-ensemble d'UTF-8. En pratique, ce sera US-ASCII, le jeu de caractères utilisé par la locale par défaut « C » ou « POSIX ».

Votre application mélangera alors, dans une certaine mesure, des sorties pour différentes localisations ou langues. Mais cela est entièrement sous votre contrôle.

EXEMPLE

Voir ci-dessus ! Normalement, vous ne devriez pas utiliser ce module ! Cependant, supposons que vous ayez lu les avertissements. Dans une application web, vous feriez quelque chose comme ceci :

use Locale::TextDomain qw (com.example.yourapp);
use Locale::Messages qw (nl_putenv LC_ALL bindtextdomain
                         bind_textdomain_codeset);
use Locale::Util qw (web_set_locale);
use POSIX qw (setlocale);

# Essayez d'abord de passer à la locale demandée par l'utilisateur. Si vous
# la connaissez, vous pouvez essayer de la passer à setlocale comme ceci :
#
#   my $hardcoded_locale = 'fr_FR.UTF-8';
#   my $success = POSIX::setlocale (LC_ALL, $hardcoded_locale);
#
# Cependant, nous essayons de laisser libintl-perl faire un meilleur travail pour nous :
my $success = web_set_locale $ENV{HTTP_ACCEPT_LANGUAGE},
                             $ENV{HTTP_ACCEPT_CHARSET};
# Note : Si votre application force l'utilisation d'UTF-8 pour sa sortie
# vous devriez passer 'UTF-8' comme deuxième argument à web_set_locale
# au lieu de $ENV{HTTP_ACCEPT_CHARSET}.

if (!$success) {
    # Cela n'a pas fonctionné. Passez à l'interface dumb de
    # Locale::Messages.
    Locale::Messages->select_package ('gettext_dumb');

    # Et essayez de passer à une locale par défaut :
    if (!setlocale (LC_ALL, 'en_US.UTF-8')) {
        # Toujours pas de chance. Forcez au moins US-ASCII :
        setlocale (LC_ALL, 'C');
    }
    bind_textdomain_codeset 'com.example.yourapp', 'utf-8';
}

Si votre application force l'utilisation d'UTF-8, vous devriez ignorer la variable d'environnement
