LEXIQUES UNILATÉRAUX

Adapté d'une suggestion de Dan Muey

Il peut être courant (par exemple, dans votre lexique principal) que les clés et les valeurs du hachage coïncident. Comme ceci :

q{Hello, tell me your name}
  => q{Hello, tell me your name}

Il serait agréable de simplement écrire :

q{Hello, tell me your name} => ''

et que cela soit automatiquement développé dans la première forme. Parmi les avantages d'une telle représentation, cela conduirait à des fichiers plus petits, moins sujets aux fautes de frappe ou aux copier-coller erronés, et serait pratique pour quelqu'un qui le traduit, qui peut simplement copier le lexique principal et saisir la traduction au lieu d'avoir à supprimer la valeur d'abord.

Cela peut être réalisé en surchargeant "init" dans votre classe et en travaillant sur le lexique principal avec un code comme celui-ci :

package My::I18N;
...
sub init {
    my $lh = shift; # un nouveau handle
    $lh->SUPER::init();
    inflate_lexicon(\%My::I18N::en::Lexicon);
    return;
}
sub inflate_lexicon {
    my $lex = shift;
    while (my ($k, $v) = each %$lex) {
        $v = $k if !defined $v || $v eq '';
    }
}

Ici, nous supposons que "My::I18N::en" possède le lexique principal.

Il y a quelques inconvénients ici : l'économie de taille ne persistera pas à l'exécution après l'exécution de cet init(). Mais cela ne devrait pas être si critique, car si vous n'avez pas la place pour cela, vous n'aurez pas non plus la place pour une autre langue que la langue principale. Vous pourriez aussi le faire avec des ties, développant la valeur au moment de la recherche, ce qui devrait être plus coûteux en temps comme option.

PLACES DÉCIMALES DANS LE FORMATAGE DES NOMBRES

Après CPAN RT #36136 (https://rt.cpan.org/Ticket/Display.html?id=36136)

La documentation de Locale::Maketext indique que la méthode standard avec crochets "numf" est limitée et que vous devez la surcharger pour de meilleurs résultats. Elle suggère même l'utilisation de Number::Format.

Un tel défaut de la méthode standard "numf" est de ne pas pouvoir utiliser une certaine précision décimale. Par exemple,

$lh->maketext('pi est [numf,_1]', 355/113);

produit

pi est 3.14159292035398

Comme pi ≈ 355/116 n'est précis qu'à 6 décimales, vous voudrez dire :

$lh->maketext('pi est [numf,_1,6]', 355/113);

et obtenir "pi est 3.141592".

Une solution à cela pourrait utiliser "Number::Format" comme suit :

package Wuu;
use base qw(Locale::Maketext);
use Number::Format;
# peut être surchargé selon les conventions linguistiques
sub _numf_params {
    return (
        -thousands_sep  => '.',
        -decimal_point  => ',',
        -decimal_digits => 2,
    );
}
# construit un Number::Format
sub _numf_formatter {
    my ($lh, $scale) = @_;
    my @params = $lh->_numf_params;
    if ($scale) { # utilise une échelle explicite plutôt que la valeur par défaut
        push @params, (-decimal_digits => $scale);
    }
    return Number::Format->new(@params);
}
sub numf {
    my ($lh, $n, $scale) = @_;
    # récupère le formateur (mis en cache)
    my $nf = $lh->{__nf}{$scale} ||= $lh->_numf_formatter($scale);
    # formate le nombre lui-même
    return $nf->format_number($n);
}
package Wuu::pt;
use base qw(Wuu);

et ensuite

my $lh = Wuu->get_handle('pt');
$lh->maketext('A [numf,_1,3] km de distância', 1550.2222);

retournerait "A 1.550,222 km de distância".

Notez que les méthodes utilitaires standard de "Locale::Maketext" sont irrémédiablement limitées car elles ne pouvaient pas viser à faire tout ce qui pouvait en être attendu dans différentes langues, cultures et applications. Donc étendre "numf", "quant", et "sprintf" est naturel dès que vos besoins dépassent ce que font les standards.
