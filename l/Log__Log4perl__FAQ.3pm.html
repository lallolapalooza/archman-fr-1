NOM

Log::Log4perl::FAQ - Foire Aux Questions sur Log::Log4perl

DESCRIPTION

Cette FAQ présente une large gamme de tâches d'enregistrement courantes et comment les résoudre de la manière la plus élégante avec Log::Log4perl. La plupart du temps, il s'agira simplement de configurer intelligemment vos fichiers de configuration Log::Log4perl.

Pourquoi utiliser Log::Log4perl au lieu d'un autre module de journalisation sur CPAN ?

C'est une bonne question. Il existe des dizaines de modules de journalisation sur CPAN. En matière de journalisation, les gens pensent généralement : « Aha. Écrire des messages de débogage et d'erreur. Le débogage est inférieur à l'erreur. Facile. Je vais écrire le mien. » Écrire un module de journalisation est comme un rite de passage pour tout programmeur Perl, tout comme écrire son propre système de templating.

Bien sûr, après avoir maîtrisé les bases, il faut ajouter des fonctionnalités. Vous voudriez écrire un horodatage avec chaque message. Puis des horodatages avec des microsecondes. Ensuite, les messages doivent être écrits à la fois à l'écran et dans un fichier journal.

Et, à mesure que votre application grandit, vous pourriez vous demander : Pourquoi mon système de journalisation ne suit-il pas sa croissance ? Vous voudriez activer la journalisation dans des parties sélectionnées de l'application, et pas partout, car cela tue les performances. C'est à ce moment-là que les gens se tournent vers Log::Log4perl, car il gère tout cela.

Évitez ce changement coûteux.

Utilisez "Log::Log4perl" dès le début. Le mode ":easy" de "Log::Log4perl" prend en charge la journalisation facile dans des scripts simples :

use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init($DEBUG);
DEBUG "Un message de bas niveau";
ERROR "N'arrivera pas tant que le niveau ne sera pas augmenté à ERROR";

Et lorsque votre application se développe inévitablement, votre système de journalisation grandit avec elle sans que vous ayez à modifier aucun code.

S'il vous plaît, ne réinventez pas la journalisation. "Log::Log4perl" est là, il est facile à utiliser, il évolue et couvre de nombreux domaines auxquels vous n'avez pas encore pensé, mais que vous aborderez bientôt.

Quelle est la manière la plus simple d'utiliser Log4perl ?

Si vous voulez simplement profiter du confort de la journalisation, sans trop de surcharge, utilisez les Journalisation furtives. Si vous utilisez Log::Log4perl en mode ":easy" comme

use Log::Log4perl qw(:easy);

vous aurez les fonctions suivantes disponibles dans le package courant :

DEBUG("message");
INFO("message");
WARN("message");
ERROR("message");
FATAL("message");

Assurez-vous simplement que chaque package de votre code où vous les utilisez inclut d'abord "use Log::Log4perl qw(:easy)", et vous êtes prêt. La catégorie de chaque journalleur furtif sera équivalente au nom du package dans lequel il se trouve.

Ces journalleurs furtifs seront absolument silencieux jusqu'à ce que vous initialisiez Log::Log4perl dans votre programme principal avec soit

    # Définir tout comportement Log4perl
Log::Log4perl->init("foo.conf");

(en utilisant un fichier de configuration Log4perl complet) soit la méthode super-simple

    # Journaliser simplement vers STDERR
Log::Log4perl->easy_init($DEBUG);

ou la méthode de style paramétrique avec une complexité intermédiaire :

    # Ajouter à un fichier journal
Log::Log4perl->easy_init( { level   => $DEBUG,
                            file    => ">>test.log" } );

Pour plus d'informations, veuillez consulter "Stealth Loggers" dans Log::Log4perl.

Comment puis-je simplement journaliser tous mes messages d'ERREUR dans un fichier ?

Après avoir inclus le module "Log::Log4perl", initialisez simplement son comportement en passant une configuration à sa méthode "init" sous forme de référence de chaîne. Ensuite, obtenez une instance de journaliseur et écrivez un message avec sa méthode error() :

use Log::Log4perl qw(get_logger);
    # Définir la configuration
my $conf = q(
    log4perl.logger                    = ERROR, FileApp
    log4perl.appender.FileApp          = Log::Log4perl::Appender::File
    log4perl.appender.FileApp.filename = test.log
    log4perl.appender.FileApp.layout   = PatternLayout
    log4perl.appender.FileApp.layout.ConversionPattern = %d> %m%n
);
    # Initialiser le comportement de journalisation
Log::Log4perl->init( \$conf );
    # Obtenir une instance de journaliseur
my $logger = get_logger("Bar::Twix");
$logger->error("Oh mon dieu, une terrible erreur !");
$logger->warn("Oh mon dieu, un avertissement terrible !");

Cela ajoutera quelque chose comme

2002/10/29 20:11:55> Oh mon dieu, une terrible erreur !

au fichier journal "test.log". Comment tout cela fonctionne-t-il ?

Bien que la méthode init() de Log::Log4perl prenne généralement le nom d'un fichier de configuration comme paramètre d'entrée, comme dans

Log::Log4perl->init( "/path/mylog.conf" );

l'exemple ci-dessus montre comment passer une configuration sous forme de texte dans une référence scalaire.

La configuration telle qu'elle est présentée définit un journaliseur de la catégorie racine, auquel est attaché un appendice de type "Log::Log4perl::Appender::File". La ligne

log4perl.logger = ERROR, FileApp

ne liste pas de catégorie, définissant ainsi un journaliseur racine. Comparez cela avec

log4perl.logger.Bar.Twix = ERROR, FileApp

qui définirait un journaliseur pour la catégorie "Bar::Twix", montrant probablement un comportement différent. "FileApp" du côté droit de l'assignation est un nom de variable arbitrairement défini, qui n'est utilisé que pour référencer d'une manière ou d'une autre un appendice défini plus tard.

Les paramètres de l'appendice dans la configuration sont définis comme suit :

log4perl.appender.FileApp          = Log::Log4perl::Appender::File
log4perl.appender.FileApp.filename = test.log

Il sélectionne l'appendice de fichier de la hiérarchie "Log::Log4perl::Appender", qui ajoutera au fichier "test.log" s'il existe déjà. Si nous voulions écraser un fichier potentiellement existant, nous devrions explicitement définir le paramètre "mode" approprié de "Log::Log4perl::Appender::File" :

log4perl.appender.FileApp          = Log::Log4perl::Appender::File
log4perl.appender.FileApp.filename = test.log
log4perl.appender.FileApp.mode     = write

De plus, la configuration définit un format PatternLayout, ajoutant la date et l'heure actuelles joliment formatées, une flèche (>) et un espace avant les messages, suivis d'un retour à la ligne :

log4perl.appender.FileApp.layout   = PatternLayout
log4perl.appender.FileApp.layout.ConversionPattern = %d> %m%n

Obtenir une instance de journaliseur et réellement journaliser quelque chose se fait généralement dans une partie différente du système, comme la section d'initialisation de Log::Log4perl, mais dans cet exemple, cela est fait juste après l'initialisation pour des raisons de compacité :

    # Obtenir une instance de journaliseur
my $logger = get_logger("Bar::Twix");
$logger->error("Oh mon dieu, une terrible erreur !");

Cela récupère une instance du journaliseur de la catégorie "Bar::Twix", qui, comme toutes les autres catégories, hérite du comportement du journaliseur racine si aucun autre journaliseur n'est défini dans la section d'initialisation.

La méthode error() déclenche un message, que le journaliseur racine intercepte. Sa priorité est égale ou supérieure à la priorité du journaliseur racine (ERROR), ce qui amène le journaliseur racine à le transmettre à son appendice attaché. En revanche, le suivant

$logger->warn("Oh mon dieu, un avertissement terrible !");

ne passe pas, car le journaliseur racine a un réglage plus élevé (ERROR et au-dessus) que la priorité WARN du message.

Frequently Asked Questions

This document answers some frequently asked questions about Log::Log4perl.

If you find that something doesn't work, please let us know at log4perl-devel@lists.sourceforge.net -- we'll appreciate it. Have fun!

How can I include global (thread-specific) data in my log messages?

Say, you're writing a web application and want all your log messages to include the current client's IP address. Most certainly, you don't want to include it in each and every log message like in

$logger->debug( $r->connection->remote_ip,
                " Retrieving user data from DB" );

do you? Instead, you want to set it in a global data structure and have Log::Log4perl include it automatically via a PatternLayout setting in the configuration file:

log4perl.appender.FileApp.layout.ConversionPattern = %X{ip} %m%n

The conversion specifier %X{ip} references an entry under the key "ip" in the global "MDC" (mapped diagnostic context) table, which you've set once via

Log::Log4perl::MDC->put("ip", $r->connection->remote_ip);

at the start of the request handler. Note that this is a static (class) method, there's no logger object involved. You can use this method with as many key/value pairs as you like as long as you reference them under different names.

The mappings are stored in a global hash table within Log::Log4perl. Luckily, because the thread model in 5.8.0 doesn't share global variables between threads unless they're explicitly marked as such, there's no problem with multi-threaded environments.

For more details on the MDC, please refer to "Mapped Diagnostic Context (MDC)" in Log::Log4perl and Log::Log4perl::MDC.

My application is already logging to a file. How can I duplicate all messages to also go to the screen?

Assuming that you already have a Log4perl configuration file like

log4perl.logger                    = DEBUG, FileApp
log4perl.appender.FileApp          = Log::Log4perl::Appender::File
log4perl.appender.FileApp.filename = test.log
log4perl.appender.FileApp.layout   = PatternLayout
log4perl.appender.FileApp.layout.ConversionPattern = %d> %m%n

and log statements all over your code, it's very easy with Log4perl to have the same messages both printed to the logfile and the screen. No reason to change your code, of course, just add another appender to the configuration file and you're done:

log4perl.logger                    = DEBUG, FileApp, ScreenApp
log4perl.appender.FileApp          = Log::Log4perl::Appender::File
log4perl.appender.FileApp.filename = test.log
log4perl.appender.FileApp.layout   = PatternLayout
log4perl.appender.FileApp.layout.ConversionPattern = %d> %m%n
log4perl.appender.ScreenApp          = Log::Log4perl::Appender::Screen
log4perl.appender.ScreenApp.stderr   = 0
log4perl.appender.ScreenApp.layout   = PatternLayout
log4perl.appender.ScreenApp.layout.ConversionPattern = %d> %m%n

The configuration file above is assuming that both appenders are active in the same logger hierarchy, in this case the "root" category. But even if you've got file loggers defined in several parts of your system, belonging to different logger categories, each logging to different files, you can gobble up all logged messages by defining a root logger with a screen appender, which would duplicate messages from all your file loggers to the screen due to Log4perl's appender inheritance. Check

http://www.perl.com/pub/a/2002/09/11/log4perl.html

for details. Have fun!

How can I make sure my application logs a message when it dies unexpectedly?

Whenever you encounter a fatal error in your application, instead of saying something like

open FILE, "<blah" or die "Can't open blah -- bailing out!";

just use Log::Log4perl's fatal functions instead:

my $log = get_logger("Some::Package");
open FILE, "<blah" or $log->logdie("Can't open blah -- bailing out!");

This will both log the message with priority FATAL according to your current Log::Log4perl configuration and then call Perl's die() afterwards to terminate the program. It works the same with stealth loggers (see "Stealth Loggers" in Log::Log4perl), all you need to do is call

use Log::Log4perl qw(:easy);
open FILE, "<blah" or LOGDIE "Can't open blah -- bailing out!";

What can you do if you're using some library which doesn't use Log::Log4perl and calls die() internally if something goes wrong? Use a $SIG{__DIE__} pseudo signal handler

use Log::Log4perl qw(get_logger);
$SIG{__DIE__} = sub {
    if($^S) {
        # We're in an eval {} and don't want log
        # this message but catch it later
        return;
    }
    local $Log::Log4perl::caller_depth =
          $Log::Log4perl::caller_depth + 1;
    my $logger = get_logger("");
    $logger->fatal(@_);
    die @_; # Now terminate really
};

This will catch every die()-Exception of your application or the modules it uses. In case you want to It will fetch a root logger and pass on the die()-Message to it. If you make sure you've configured with a root logger like this:

Log::Log4perl->init(\q{
    log4perl.category         = FATAL, Logfile
    log4perl.appender.Logfile = Log::Log4perl::Appender::File
    log4perl.appender.Logfile.filename = fatal_errors.log
    log4perl.appender.Logfile.layout = \
               Log::Log4perl::Layout::PatternLayout
    log4perl.appender.Logfile.layout.ConversionPattern = %F{1}-%L (%M)> %m%n
});

then all die() messages will be routed to a file properly. The line

local $Log::Log4perl::caller_depth =
      $Log::Log4perl::caller_depth + 1;

in the pseudo signal handler above merits a more detailed explanation. With the setup above, if a module calls die() in one of its functions, the fatal message will be logged in the signal handler and not in the original function -- which will cause the %F, %L and %M placeholders in the pattern layout to be replaced by the filename, the line number and the function/method name of the signal handler, not the error-throwing module. To adjust this, Log::Log4perl has the $caller_depth variable, which defaults to 0, but can be set to positive integer values to offset the caller level. Increasing it by one will cause it to log the calling function's parameters, not the ones of the signal handler. See "Using Log::Log4perl from wrapper classes" in Log::Log4perl for more details.

How can I hook up the LWP library with Log::Log4perl?

Or, to put it more generally: How can you utilize a third-party library's embedded logging and debug statements in Log::Log4perl? How can you make them print to configurable appenders, turn them on and off, just as if they were regular Log::Log4perl logging statements?

The easiest solution is to map the third-party library logging statements to Log::Log4perl's stealth loggers via a typeglob assignment.

As an example, let's take LWP, one of the most popular Perl modules, which makes handling WWW requests and responses a breeze. Internally, LWP uses its own logging and debugging system, utilizing the following calls inside the LWP code (from the LWP::Debug man page):

    # Function tracing
LWP::Debug::trace('send()');
    # High-granular state in functions
LWP::Debug::debug('url ok');
    # Data going over the wire
LWP::Debug::conns("read $n bytes: $data");

First, let's assign Log::Log4perl priorities to these functions: I'd suggest that debug() messages have priority "INFO", trace() uses "DEBUG" and conns() also logs with "DEBUG" -- although your mileage may certainly vary.

Now, in order to transparently hook up LWP::Debug with Log::Log4perl, all we have to do is say

package LWP::Debug;
use Log::Log4perl qw(:easy);
*trace = *INFO;
*conns = *DEBUG;
*debug = *DEBUG;
package main;
# ... go on with your regular program ...

at the beginning of our program. In this way, every time the, say, "LWP::UserAgent" module calls LWP::Debug::trace(), it will implicitly call INFO(), which is the info() method of a stealth logger defined for the Log::Log4perl category "LWP::Debug". Is this cool or what?

Here's a complete program:

use LWP::UserAgent;
use HTTP::Request::Common;
use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init(
    { category => "LWP::Debug",
      level    => $DEBUG,
      layout   => "%r %p %M-%L %m%n",
    });
package LWP::Debug;
use Log::Log4perl qw(:easy);
*trace = *INFO;
*conns = *DEBUG;
*debug = *DEBUG;
package main;
my $ua = LWP::UserAgent->new();
my $resp = $ua->request(GET "http://amazon.com");
if($resp->is_success()) {
    print "Success: Received ",
          length($resp->content()), "\n";
} else {
    print "Error: ", $resp->code(), "\n";
}

Bien sûr, de cette manière, les instructions de journalisation et de débogage intégrées dans LWP peuvent être utilisées de la manière souhaitée par Log::Log4perl. Vous pouvez les envoyer à différents "appenders", les bloquer en fonction de la catégorie et de tout ce que Log::Log4perl a à offrir.

Le seul inconvénient de cette méthode : la gestion du comportement de journalisation par catégorie est toujours basée sur le package "LWP::Debug". Bien que les instructions de journalisation reflètent correctement le nom du package du module émetteur, les journaux discrets dans "LWP::Debug" sont tous de la catégorie "LWP::Debug". Cela implique que vous ne pouvez pas contrôler le comportement de journalisation en fonction du package qui *déclenche* une requête de journalisation (par exemple, LWP::UserAgent), mais uniquement en fonction du package qui *exécute* réellement l'instruction de journalisation, "LWP::Debug" dans ce cas.

Pour contourner cette énigme, nous devons écrire une fonction wrapper et la placer dans le package "LWP::Debug". Elle déterminera l'appelant et créera un logger lié à une catégorie portant le même nom que le package de l'appelant :

package LWP::Debug;
use Log::Log4perl qw(:levels get_logger);
sub l4p_wrapper {
    my($prio, @message) = @_;
    $Log::Log4perl::caller_depth += 2;
    get_logger(scalar caller(1))->log($prio, @message);
    $Log::Log4perl::caller_depth -= 2;
}
no warnings 'redefine';
*trace = sub { l4p_wrapper($INFO, @_); };
*debug = *conns = sub { l4p_wrapper($DEBUG, @_); };
package main;
# ... continuez avec votre programme principal ...

C'est moins performant que l'approche précédente, car chaque requête de journalisation demandera d'abord une référence à un logger, puis appellera le wrapper, qui à son tour appellera la fonction de journalisation appropriée.

Ce changement de hiérarchie doit être compensé en augmentant $Log::Log4perl::caller_depth de 2 avant d'appeler la fonction de journalisation et en la diminuant de 2 juste après. De plus, la fonction "l4p_wrapper" montrée ci-dessus appelle caller(1), qui détermine le nom du package *deux* niveaux plus bas dans la hiérarchie d'appel (et compense donc à la fois la fonction wrapper et la sous-routine anonyme qui l'appelle).

"no warnings 'redefine'" supprime un avertissement que Perl générerait sinon lors de la redéfinition des fonctions "LWP::Debug" : trace(), debug() et conns(). Si vous utilisez une version de Perl antérieure à 5.6.x, vous devez manipuler $^W à la place.

Pour vous faciliter la tâche lors de l'utilisation de LWP, Log::Log4perl 0.47 introduit "Log::Log4perl->infiltrate_lwp()" qui fait exactement ce qui précède.

Et si j'ai besoin de valeurs dynamiques dans un fichier de configuration Log4perl statique ?

Supposons que votre application utilise Log::Log4perl pour la journalisation et qu'elle est donc livrée avec un fichier de configuration Log4perl spécifiant le comportement de journalisation. Mais vous souhaitez également qu'elle accepte des paramètres en ligne de commande pour définir des valeurs comme le nom du fichier journal. Comment avoir à la fois un fichier de configuration Log4perl statique et une interface en ligne de commande dynamique ?

Depuis Log::Log4perl 0.28, chaque valeur dans le fichier de configuration peut être spécifiée comme un *hook Perl*. Donc, au lieu de dire

log4perl.appender.Logfile.filename = test.log

vous pourriez tout aussi bien avoir une sous-routine Perl qui livre la valeur dynamiquement :

log4perl.appender.Logfile.filename = sub { logfile(); };

étant donné que logfile() est une fonction valide dans votre package "main" retournant une chaîne contenant le chemin du fichier journal.

Ou, pensez à utiliser la valeur d'une variable d'environnement :

log4perl.appender.DBI.user = sub { $ENV{USERNAME} };

Lorsque "Log::Log4perl->init()" analyse le fichier de configuration, il remarquera l'affectation ci-dessus grâce à son motif "sub {...}" et la traitera d'une manière spéciale : il évaluera la sous-routine (qui peut contenir du code Perl arbitraire) et prendra sa valeur de retour comme côté droit de l'affectation.

Une application typique serait appelée comme suit en ligne de commande :

app                # le fichier journal est "test.log"
app -l mylog.txt   # le fichier journal est "mylog.txt"

Voici un exemple de code implémentant l'interface en ligne de commande ci-dessus :

use Log::Log4perl qw(get_logger);
use Getopt::Std;
getopt('l:', \our %OPTS);
my $conf = q(
log4perl.category.Bar.Twix         = WARN, Logfile
log4perl.appender.Logfile          = Log::Log4perl::Appender::File
log4perl.appender.Logfile.filename = sub { logfile(); };
log4perl.appender.Logfile.layout   = SimpleLayout
);
Log::Log4perl::init(\$conf);
my $logger = get_logger("Bar::Twix");
$logger->error("Blah");
###########################################
sub logfile {
###########################################
    if(exists $OPTS{l}) {
        return $OPTS{l};
    } else {
        return "test.log";
    }
}

Chaque hook Perl peut contenir du code perl arbitraire, assurez-vous simplement de qualifier entièrement les noms de variables éventuels (par exemple, %main::OPTS au lieu de %OPTS).

NOTE DE SÉCURITÉ : cette fonctionnalité signifie que du code Perl arbitraire peut être intégré dans le fichier de configuration. Dans le cas rare où les personnes ayant accès à votre fichier de configuration sont différentes de celles qui écrivent votre code et ne devraient pas avoir de droits d'exécution, vous pourriez vouloir appeler

$Log::Log4perl::Config->allow_code(0);

avant d'appeler init(). Cela empêchera Log::Log4perl d'exécuter *n'importe quel* code Perl dans le fichier de configuration (y compris le code pour les spécificateurs de conversion personnalisés (voir "Custom cspecs" dans Log::Log4perl::Layout::PatternLayout).

Comment puis-je faire rouler mes fichiers journaux automatiquement à minuit ?

Les applications qui s'exécutent longtemps ont tendance à produire des fichiers journaux de plus en plus volumineux. Cependant, à des fins de sauvegarde et de nettoyage, il est souvent souhaitable de déplacer le fichier journal actuel vers un emplacement différent de temps en temps et d'en créer un nouveau.

C'est une tâche non triviale, car elle doit être effectuée en synchronisation avec le système de journalisation afin de ne perdre aucun message pendant le processus.

Heureusement, l'appender "Log::Dispatch::FileRotate" de *Mark Pfeiffer* fonctionne bien avec Log::Log4perl pour faire rouler vos fichiers journaux de diverses manières.

Notez cependant que le fait que l'application gère la rotation d'un fichier journal n'est pas gratuit. Entre autres choses, cela nécessite de verrouiller le fichier journal à chaque écriture pour éviter les conditions de concurrence. Il y a de bonnes raisons d'utiliser des rotateurs externes comme "newsyslog" à la place. Voir l'entrée "How can I rotate a logfile with newsyslog?" dans la FAQ pour plus d'informations sur la façon de la configurer.

Lors de l'utilisation de "Log::Dispatch::FileRotate", tout ce que vous avez à faire est de le spécifier dans votre fichier de configuration Log::Log4perl et vos fichiers journaux seront automatiquement rotés.

Vous pouvez choisir entre rouler en fonction d'une taille maximale ("rouler si supérieur à 10 Mo") ou en fonction d'un modèle de date ("rouler tous les jours à minuit"). Dans les deux cas, "Log::Dispatch::FileRotate" vous permet de définir un nombre "max" de fichiers sauvegardés à conserver jusqu'à ce qu'il commence à écraser les plus anciens. Si vous définissez le paramètre "max" à 2 et que le nom de votre fichier journal est "test.log", "Log::Dispatch::FileRotate" déplacera "test.log" vers "test.log.1" lors du premier roulement. Lors du second roulement, il déplacera "test.log.1" vers "test.log.2" puis "test.log" vers "test.log.1". Lors du troisième roulement, il déplacera "test.log.1" vers "test.log.2" (jetant ainsi l'ancien "test.log.2") et "test.log" vers "test.log.1". Et ainsi de suite. De cette façon, il y aura toujours un maximum de 2 fichiers journaux sauvegardés.

Voici un exemple de fichier de configuration Log::Log4perl, définissant un roulement quotidien à minuit (modèle de date "yyyy-MM-dd"), conservant un maximum de 5 fichiers journaux sauvegardés :

log4perl.category         = WARN, Logfile
log4perl.appender.Logfile = Log::Dispatch::FileRotate
log4perl.appender.Logfile.filename    = test.log
log4perl.appender.Logfile.max         = 5
log4perl.appender.Logfile.DatePattern = yyyy-MM-dd
log4perl.appender.Logfile.TZ          = PST
log4perl.appender.Logfile.layout = \
    Log::Log4perl::Layout::PatternLayout
log4perl.appender.Logfile.layout.ConversionPattern = %d %m %n

Veuillez consulter la documentation de "Log::Dispatch::FileRotate" pour plus de détails. "Log::Dispatch::FileRotate" est disponible sur CPAN.

Quelle est la manière la plus simple de désactiver toute journalisation, même avec un fichier de configuration Log4perl détaillé ?

En plus des niveaux basés sur la catégorie et des seuils d'appender, Log::Log4perl prend en charge les seuils de journalisation à l'échelle du système. Il s'agit du niveau minimum que le système exigera de tout événement de journalisation pour qu'il soit transmis aux appenders configurés.

Par exemple, placer la ligne

log4perl.threshold = ERROR

n'importe où dans votre fichier de configuration limitera toute sortie vers n'importe quel appender aux événements de priorité ERROR ou supérieure (c'est-à-dire ERROR ou FATAL).

Cependant, afin de supprimer entièrement toute journalisation, vous devez utiliser une priorité supérieure à FATAL : c'est

simplement appelé "OFF", et il n'est jamais utilisé par aucun journal. Par définition, il est supérieur au niveau du journal le plus élevé défini.

Par conséquent, si vous conservez la ligne

log4perl.threshold = OFF

quelque part dans votre configuration Log::Log4perl, le système sera aussi silencieux qu'un cimetière. Si vous désactivez la ligne (par exemple, en la commentant), le système, lors du rechargement de la configuration, reprendra son fonctionnement normal, fournissant des messages de journalisation conformément au reste du fichier de configuration.

Comment puis-je enregistrer DEBUG et supérieur sur l'écran et INFO et supérieur dans un fichier ?

Vous avez besoin d'un journal avec deux expéditeurs (appenders) attachés :

log4perl.logger = DEBUG, Screen, File
log4perl.appender.Screen   = Log::Log4perl::Appender::Screen
log4perl.appender.Screen.layout = SimpleLayout
log4perl.appender.File   = Log::Log4perl::Appender::File
log4perl.appender.File.filename = test.log
log4perl.appender.File.layout = SimpleLayout
log4perl.appender.Screen.Threshold = INFO

Comme l'expéditeur de fichier n'est pas censé recevoir de messages avec une priorité inférieure à INFO, le paramètre "Threshold" de l'expéditeur les bloque, bien que le journal les transmette.

C'est une erreur courante de penser que vous pouvez définir deux journaux pour cela, mais cela ne fonctionnera pas à moins que ces deux journaux n'aient des catégories différentes. Si vous vouliez enregistrer tous les messages DEBUG et supérieurs du module Foo::Bar dans un fichier et tous les messages INFO et supérieurs du module Quack::Schmack sur l'écran, alors vous auriez pu définir deux journaux avec des niveaux différents "log4perl.logger.Foo.Bar" (niveau INFO) et "log4perl.logger.Quack.Schmack" (niveau DEBUG) et assigner l'expéditeur de fichier au premier et l'expéditeur d'écran au second. Mais ce que nous voulions accomplir, c'était de router tous les messages, indépendamment du module (ou de la catégorie) dont ils proviennent, vers les deux expéditeurs. La seule façon d'y parvenir est de définir le journal racine avec le niveau inférieur (DEBUG), d'y attacher les deux expéditeurs, et de bloquer les messages indésirables au niveau de l'expéditeur de fichier ("Threshold" réglé sur INFO).

Je continue d'obtenir des messages de journalisation en double ! Qu'est-ce qui ne va pas ?

Avoir plusieurs configurations pour des catégories liées dans le fichier de configuration Log4perl conduit parfois à un phénomène appelé "duplication de messages". Cela peut être très déroutant au début, mais si l'on y réfléchit correctement, il s'avère que Log4perl se comporte comme annoncé. Mais, ne désespérez pas, il existe bien sûr un certain nombre de façons d'éviter la duplication de messages dans vos journaux.

Voici un exemple de fichier de configuration Log4perl qui produit le phénomène :

log4perl.logger.Cat        = ERROR, Screen
log4perl.logger.Cat.Subcat = WARN, Screen
log4perl.appender.Screen   = Log::Log4perl::Appender::Screen
log4perl.appender.Screen.layout = SimpleLayout

Il définit deux journaux, un pour la catégorie "Cat" et un pour "Cat::Subcat", qui est évidemment une sous-catégorie de "Cat". Le journal parent a un réglage de priorité ERROR, l'enfant est réglé sur le niveau inférieur "WARN".

Maintenant, imaginez le code suivant dans votre programme :

my $logger = get_logger("Cat.Subcat");
$logger->warn("Warning!");

Que pensez-vous qu'il va se passer ? Un utilisateur inexpérimenté de Log4perl pourrait penser : "Eh bien, le message est envoyé avec le niveau WARN, donc le journal "Cat::Subcat" l'acceptera et le transmettra à l'expéditeur "Screen" attaché. Ensuite, le message remontera la hiérarchie des journaux, trouvera le journal "Cat", qui supprimera le message en raison de son réglage ERROR." Mais, de manière peut-être surprenante, ce que vous obtiendrez avec l'extrait de code ci-dessus, ce ne sont pas un mais deux messages de journalisation écrits à l'écran :

WARN - Warning!
WARN - Warning!

Que s'est-il passé ? Le coupable est que, une fois que le journal "Cat::Subcat" décide de se déclencher, il transmet le message *inconditionnellement* à tous les expéditeurs directement ou indirectement attachés. Le journal "Cat" ne sera jamais interrogé pour savoir s'il veut le message ou non -- le message sera simplement transmis à l'expéditeur attaché à "Cat".

Une façon d'empêcher le message de remonter la hiérarchie des journaux est de régler le drapeau "additivity" du journal subordonné à 0 :

log4perl.logger.Cat            = ERROR, Screen
log4perl.logger.Cat.Subcat     = WARN, Screen
log4perl.additivity.Cat.Subcat = 0
log4perl.appender.Screen   = Log::Log4perl::Appender::Screen
log4perl.appender.Screen.layout = SimpleLayout

Le message sera maintenant accepté par le journal "Cat::Subcat", transmis à son expéditeur, mais ensuite "Cat::Subcat" supprimera toute action supplémentaire. Bien que ce réglage évite les messages dupliqués comme vu précédemment, ce n'est souvent pas le comportement souhaité. Les messages qui remontent la hiérarchie sont une fonctionnalité utile de Log4perl.

Si vous définissez des expéditeurs *différents* pour les deux journaux, une autre option consiste à définir un seuil d'expéditeur pour l'expéditeur de niveau supérieur. Typiquement, il est réglé pour être égal au réglage du niveau du journal :

log4perl.logger.Cat           = ERROR, Screen1
log4perl.logger.Cat.Subcat    = WARN, Screen2
log4perl.appender.Screen1   = Log::Log4perl::Appender::Screen
log4perl.appender.Screen1.layout = SimpleLayout
log4perl.appender.Screen1.Threshold = ERROR
log4perl.appender.Screen2   = Log::Log4perl::Appender::Screen
log4perl.appender.Screen2.layout = SimpleLayout

Comme l'expéditeur "Screen1" bloque maintenant tout message avec une priorité inférieure à ERROR, même si le journal responsable le laisse passer, le message remontant la hiérarchie est bloqué à la dernière minute et *n'est pas* ajouté à "Screen1".

Jusqu'à présent, nous avons opéré dans les limites de la norme Logj, à laquelle Log4perl adhère. Cependant, si vous souhaitiez vraiment, vraiment utiliser un seul expéditeur et conserver la percolation des messages intacte sans avoir à gérer la duplication de messages, il existe une solution non standard pour vous :

log4perl.logger.Cat        = ERROR, Screen
log4perl.logger.Cat.Subcat = WARN, Screen
log4perl.appender.Screen   = Log::Log4perl::Appender::Screen
log4perl.appender.Screen.layout = SimpleLayout
log4perl.oneMessagePerAppender = 1

Le drapeau "oneMessagePerAppender" supprimera les messages dupliqués vers le même expéditeur. Encore une fois, c'est non standard. Mais super cool :).

Comment configurer Log::Log4perl pour m'envoyer un email si quelque chose se produit ?

Certains incidents nécessitent une action immédiate. Vous ne pouvez pas attendre que quelqu'un consulte les fichiers journaux, vous avez besoin d'être alerté sur votre bipeur immédiatement.

Le moyen le plus simple de le faire est d'utiliser le module "Log::Dispatch::Email::MailSend" comme expéditeur. Il est livré avec le bundle "Log::Dispatch" et vous permet de spécifier le destinataire et le sujet des e-mails sortants dans le fichier de configuration Log4perl :

log4perl.category = FATAL, Mailer
log4perl.appender.Mailer         = Log::Dispatch::Email::MailSend
log4perl.appender.Mailer.to      = drone@pageme.net
log4perl.appender.Mailer.subject = Something's broken!
log4perl.appender.Mailer.layout  = SimpleLayout

Le message de chaque incident de journalisation que cet expéditeur reçoit sera alors transmis à l'adresse e-mail donnée. Consultez la documentation de "Log::Dispatch::Email::MailSend" pour plus de détails. Et assurez-vous qu'il n'y a pas de déluge de messages e-mail envoyés par votre application, remplissant la boîte de réception du destinataire.

Il y a un bémol que vous devez connaître : la hiérarchie d'expéditeurs "Log::Dispatch::Email" active la mise en *tampon* par défaut. Cela signifie que l'expéditeur n'enverra pas les messages immédiatement mais attendra qu'un certain seuil soit atteint. Si vous préférez que vos alertes soient envoyées immédiatement, utilisez

log4perl.appender.Mailer.buffered = 0

pour désactiver la mise en tampon.

Comment puis-je explorer les références avant de les enregistrer ?

Si vous avez une référence vers une structure ou un objet imbriqué, vous ne voudrez probablement pas l'enregistrer comme HASH(0x81141d4) mais plutôt comme

$VAR1 = {
          'a' => 'b',
          'd' => 'e'
        };

en utilisant un module tel que Data::Dumper. Bien qu'il soit syntaxiquement correct de dire

$logger->debug(Data::Dumper::Dumper($ref));

cet appel impose un coût de performance considérable à votre application si le message est supprimé par Log::Log4perl, car Data::Dumper effectuera ses opérations coûteuses dans tous les cas, ne sachant pas que sa sortie ne sera pas désirée immédiatement.

Jusqu'à Log::Log4perl 0.28, il existe une meilleure façon : utilisez le filtrage de message comme suit :

$logger->debug( {filter => \&Data::Dumper::Dumper,
                 value  => $ref} );

et Log::Log4perl n'appellera la fonction de filtrage que lorsque le message sera effectivement écrit dans un appender. Assurez-vous simplement de passer l'ensemble sous forme de référence à un hash spécifiant une fonction de filtrage (telle qu'une référence de sous-routine) sous la clé "filter" et la valeur à passer à la fonction de filtrage sous "value". Lors de la journalisation, Log::Log4perl appellera la fonction de filtrage, passera la "value" comme argument et enregistrera la valeur renvoyée. Vous économisez ainsi de précieux cycles.

Comment puis-je collecter tous les messages FATAL dans un fichier journal supplémentaire ?

Supposons que vous ayez déployé Log4perl dans tout votre système et que vous ayez déjà activé la journalisation dans divers sous-systèmes. De plus, sans perturber toute autre configuration, comment puis-je collecter tous les messages FATAL de l'ensemble du système et les envoyer dans un fichier journal séparé ?

Si vous définissez un logger racine comme ceci :

log4perl.logger                  = FATAL, File
log4perl.appender.File           = Log::Log4perl::Appender::File
log4perl.appender.File.filename  = /tmp/fatal.txt
log4perl.appender.File.layout    = PatternLayout
log4perl.appender.File.layout.ConversionPattern= %d %m %n
    # !!! Quelque chose manque ...

vous serez surpris non seulement de recevoir tous les messages FATAL émis dans tout le système, mais aussi tout le reste — des centaines de millions de messages ERROR, WARNING, INFO et même DEBUG — se retrouveront dans votre fichier journal fatal.txt ! La raison en est que Log4perl (ou plutôt : Log4j) possède une fonctionnalité d'ajout d'appenders. Lorsqu'un logger inférieur décide de déclencher, le message est transmis à tous les appenders supérieurs, sans vérification de priorité avec ses propres loggers.

Mais il y a un moyen d'éviter cela : si votre appender définit un seuil minimum, seuls les messages de cette priorité ou supérieure seront enregistrés. Ajoutez donc simplement

log4perl.appender.File.Threshold = FATAL

à la configuration précédente et vous obtiendrez ce que vous vouliez au départ : un collecteur global de messages FATAL.

Comment puis-je regrouper plusieurs messages journaux en un seul ?

Aimeriez-vous compter les messages qui arrivent à votre appender et, une fois un seuil dépassé, imprimer un résumé ? Ainsi, quelque chose comme

$logger->error("Blah");
$logger->error("Blah");
$logger->error("Blah");

ne serait pas enregistré comme

Blah
Blah
Blah

mais comme

[3] Blah

Et si vous souhaitez différer la journalisation d'un message jusqu'à ce qu'il ait été émis plusieurs fois, vous pouvez le faire en créant un appender tamponné.

Définissons un nouvel appender comme suit :

package TallyAppender;
sub new {
    my($class, %options) = @_;
    my $self = { maxcount => 5,
                 %options
               };
    bless $self, $class;
    $self->{last_message}        = "";
    $self->{last_message_count}  = 0;
    return $self;
}

avec deux variables d'instance supplémentaires "last_message" et "last_message_count", qui stockent le contenu du message le plus récent et un compteur de son nombre d'occurrences. Il possède également un paramètre de configuration "maxcount", qui est de 5 par défaut dans l'exemple ci-dessus, mais peut être défini dans le fichier de configuration de Log4perl comme suit :

log4perl.logger = INFO, A
log4perl.appender.A=TallyAppender
log4perl.appender.A.maxcount = 3

La logique de comptage principale se trouve dans la méthode "log" de l'appender, qui est appelée chaque fois que Log4perl pense qu'un message doit être enregistré par notre appender :

sub log {
    my($self, %params) = @_;
        # Message changé ? Imprimer le tampon.
    if($self->{last_message} and
       $params{message} ne $self->{last_message}) {
        print "[$self->{last_message_count}]: " .
              "$self->{last_message}";
        $self->{last_message_count} = 1;
        $self->{last_message} = $params{message};
        return;
    }
    $self->{last_message_count}++;
    $self->{last_message} = $params{message};
        # Seuil dépassé ? Imprimer, réinitialiser le compteur
    if($self->{last_message_count} >=
       $self->{maxcount}) {
        print "[$self->{last_message_count}]: " .
              "$params{message}";
        $self->{last_message_count} = 0;
        $self->{last_message}       = "";
        return;
    }
}

Nous comparons essentiellement si le message dans $params{message} est identique à celui que nous avons stocké dans la variable d'instance "last_message". Si c'est le cas, nous incrémentons "last_message_count". Nous imprimons le message dans deux cas : si le nouveau message est différent de celui stocké, car nous devons alors imprimer l'ancien et stocker le nouveau. Ou, si le compteur dépasse le seuil défini par le paramètre de configuration "maxcount".

Note : l'appender reçoit toujours le message entièrement rendu et ne le compare qu'en bloc. Ainsi, s'il y a une date/horodatage dans le message, cela pourrait perturber votre logique. Vous pouvez y remédier en spécifiant %m %n comme layout et en ajoutant la date plus tard dans l'appender. Ou, rendez la comparaison intelligente pour ignorer la date.

À la fin, n'oubliez pas ce qui se passe si le programme se ferme. S'il reste des messages dans le tampon, ils devraient être imprimés à ce moment-là. C'est facile à faire dans la méthode DESTROY de l'appender, qui est appelée lors de la destruction de l'objet :

sub DESTROY {
    my($self) = @_;
    if($self->{last_message_count}) {
        print "[$self->{last_message_count}]: " .
              "$self->{last_message}";
        return;
    }
}

Cela garantira qu'aucun des messages mis en mémoire tampon ne sera perdu. Joyeuse mise en tampon !

Je veux enregistrer les messages ERROR et WARN dans des fichiers différents ! Comment puis-je faire cela ?

Supposez que vous vouliez que chaque déclaration de journalisation soit écrite dans un fichier distinct en fonction du niveau de priorité de la déclaration. Les messages de priorité "WARN" devraient aller dans "/tmp/app.warn", tandis que les événements de priorité "ERROR" devraient aller dans "/tmp/app.error".

Maintenant, si vous définissez deux appenders

AppWarn

et

AppError

et que vous les assignez tous les deux au logger racine, les messages qui montent depuis n'importe quel logger inférieur seront enregistrés par les deux appenders en raison de la fonctionnalité de propagation des messages de Log4perl. Si vous limitez leur exposition avec le mécanisme de seuil de l'appender et que vous définissez le seuil de "AppWarn" sur "FATAL", les messages ne seront enregistrés que par l'appender correspondant.

Pour synchroniser l'accès à un appender, vous pouvez utiliser un filtre personnalisé qui garantit qu'un seul thread écrit dans l'appender à la fois. Voici comment l'implémenter:

    use Log::Log4perl qw(:easy);
    Log::Log4perl::init( \ <<'EOT' );
        log4perl.logger             = INFO, A1
        log4perl.appender.A1        = Log::Log4perl::Appender::File
        log4perl.appender.A1.layout = \
            Log::Log4perl::Layout::PatternLayout
        log4perl.appender.A1.layout.ConversionPattern = %m%n
        log4perl.filter.M1 = Log::Log4perl::Filter::Mutex
        log4perl.filter.M1.MutexName = AppenderMutex
        log4perl.filter.M1.AcceptOnMatch = false
        log4perl.appender.A1.Filter = M1
EOT

Le filtre utilise un mutex nommé "AppenderMutex" pour garantir qu'un seul thread écrit dans l'appender à la fois. Le paramètre "AcceptOnMatch" est défini sur "false" pour supprimer le message lorsque le mutex est verrouillé.

Pour supprimer l'avertissement concernant les systèmes de journalisation non initialisés, vous pouvez ajouter la cible ":nowarn" à l'appel "use Log::Log4perl" du module:

use Log::Log4perl qw(get_logger :nowarn);

Cela garantira que Log::Log4perl ignore silencieusement les instructions de journalisation si aucune initialisation n'a eu lieu. Si vous utilisez l'API de Log4perl pour définir des loggers et des appenders, la même notification se produit si aucun appel à "add_appenders()" n'est effectué, c'est-à-dire si aucun appender n'est défini.

Comment synchroniser l'accès à un appendeur ?

Si vous utilisez la même instance d'un appendeur dans plusieurs processus, et que chaque processus transmet des messages à l'appendeur en parallèle, vous pourriez vous retrouver avec des entrées de log qui se chevauchent.

Les scénarios typiques incluent un appendeur de fichier que vous créez dans le programme principal, et qui sera ensuite partagé entre le processus parent et un processus enfant forké. Ou deux processus distincts, initialisant chacun un appendeur de fichier Log4perl sur le même fichier log.

Log::Log4perl ne synchronise pas l'accès au fichier log partagé par défaut. Selon le mécanisme de vidage du système d'exploitation, la taille du tampon et la taille de vos messages, il y a une faible probabilité de chevauchement.

La façon la plus simple d'empêcher les messages qui se chevauchent dans les fichiers logs écrits par plusieurs processus est de définir le drapeau "syswrite" de l'appendeur de fichier avec un mode d'écriture de fichier "append". Cela garantit que "Log::Log4perl::Appender::File" utilise syswrite() (qui est garanti de s'être exécuté sans interruption) au lieu de print() qui pourrait mettre le message en tampon ou être interrompu par le système d'exploitation pendant son écriture. Et en mode "append", le noyau du système d'exploitation s'assure que plusieurs processus partagent un marqueur de fin de fichier, garantissant que chaque processus écrit à la réelle fin du fichier. (La valeur de "append" pour le paramètre "mode" est le paramètre par défaut dans l'appendeur de fichier de Log4perl, vous n'avez donc pas besoin de le définir explicitement.)

  # Garantit les écritures atomiques
log4perl.category.Bar.Twix          = WARN, Logfile
log4perl.appender.Logfile           = Log::Log4perl::Appender::File
log4perl.appender.Logfile.mode      = append
log4perl.appender.Logfile.syswrite  = 1
log4perl.appender.Logfile.filename  = test.log
log4perl.appender.Logfile.layout    = SimpleLayout

Une autre façon garantie de séparer les messages avec n'importe quel type d'appendeur est d'insérer un appendeur composite Log::Log4perl::Appender::Synchronized entre Log::Log4perl et l'appendeur réel. Il s'assurera de laisser passer les messages par ce portail virtuel un par un seulement.

Voici un exemple de configuration pour synchroniser l'accès à un appendeur de fichier :

log4perl.category.Bar.Twix          = WARN, Syncer
log4perl.appender.Logfile           = Log::Log4perl::Appender::File
log4perl.appender.Logfile.autoflush = 1
log4perl.appender.Logfile.filename  = test.log
log4perl.appender.Logfile.layout    = SimpleLayout
log4perl.appender.Syncer            = Log::Log4perl::Appender::Synchronized
log4perl.appender.Syncer.appender   = Logfile

"Log::Log4perl::Appender::Synchronized" utilise le module "IPC::Shareable" et ses sémaphores, ce qui ralentira l'écriture des messages logs, mais garantit un accès séquentiel avec des vérifications atomiques. Consultez Log::Log4perl::Appender::Synchronized pour plus de détails.

Comment exécuter Log::Log4perl sous mod_perl ?

Dans les environnements persistants, il est important de suivre les règles énoncées dans la section "Initialiser une fois et une seule" de Log::Log4perl. Si vous ne l'avez pas encore lu, veuillez le faire dès maintenant. C'est très important.

Et peu importe si vous utilisez un gestionnaire de démarrage pour init() Log::Log4perl ou si vous utilisez la stratégie init_once() (ajoutée dans la version 0.42), dans les deux cas, vous aurez très probablement des écritures non synchronisées dans les fichiers logs.

Si Log::Log4perl est configuré avec un appendeur de fichier log, et qu'il est initialisé via le gestionnaire de démarrage Apache, le descripteur de fichier créé initialement sera partagé entre tous les processus Apache. Maintenant, avoir plusieurs appendeurs utilisant le même descripteur de fichier ou plusieurs appendeurs enregistrant sur le même fichier sans synchronisation, cela peut résulter en des messages qui se chevauchent. Parfois, c'est acceptable. Si ce n'est pas le cas, voici deux stratégies :

  • Utilisez l'appendeur Log::Log4perl::Appender::Synchronized pour vous connecter à vos appendeurs de fichiers. Voici l'écrit : http://log4perl.sourceforge.net/releases/Log-Log4perl/docs/html/Log/Log4perl/FAQ.html#23804
  • Utilisez un fichier log différent pour chaque processus comme dans 
    #log4perl.conf
...
log4perl.appender.A1.filename = sub { "mylog.$$.log" }

Mon programme utilise déjà warn() et die(). Comment puis-je passer à Log4perl ?

Si votre programme utilise déjà la fonction warn() de Perl pour afficher des messages d'erreur et que vous souhaitez les canaliser dans le monde Log4perl, définissez simplement un gestionnaire "__WARN__" où réside votre programme ou module :

use Log::Log4perl qw(:easy);
$SIG{__WARN__} = sub {
    local $Log::Log4perl::caller_depth =
        $Log::Log4perl::caller_depth + 1;
    WARN @_;
};

Pourquoi le définir "local" $Log::Log4perl::caller_depth ? Si vous laissez cela de côté, les spécificateurs de conversion de "PatternLayout" comme %M ou %F (qui affichent la fonction/méthode courante et le nom du fichier source) feront référence à l'endroit où réside le gestionnaire __WARN__, et non à l'environnement d'où la fonction warn() de Perl a été émise. Augmenter "caller_depth" compense ce décalage. Le rendre "local" garantit que le niveau est réinitialisé après la sortie du gestionnaire.

Une fois cela fait, si votre programme fait quelque chose comme

sub some_func {
    warn "Here's a warning";
}

vous obtiendrez (selon votre configuration Log::Log4perl) quelque chose comme

2004/02/19 20:41:02-main::some_func: Here's a warning at ./t line 25.

dans l'appendeur approprié, au lieu d'avoir un écran plein de messages sur STDERR. Cela fonctionne également avec le module "Carp" et ses fonctions carp() et cluck().

Si, par ailleurs, il est nécessaire de capturer die() et ses similaires, un gestionnaire "__DIE__" est approprié :

$SIG{__DIE__} = sub {
    if($^S) {
        # Nous sommes dans un eval {} et ne voulons pas logger
        # ce message mais le capturer plus tard
        return;
    }
    local $Log::Log4perl::caller_depth =
        $Log::Log4perl::caller_depth + 1;
    LOGDIE @_;
};

Cela appellera la fonction LOGDIE() de Log4perl, qui enregistrera une erreur fatale puis appellera die() en interne, provoquant la sortie du programme. Fonctionne de la même manière avec croak() de "Carp" et

confess() fonctions.

Certain module imprime des messages sur STDERR. Comment puis-je les rediriger vers Log::Log4perl ?

Si un module que vous utilisez n'utilise pas Log::Log4perl mais imprime plutôt des messages de journalisation sur STDERR, comme ceci :

########################################
package IgnorantModule;
########################################
sub some_method {
    print STDERR "Parbleu! An error!\n";
}
1;

il existe toujours un moyen de capturer ces messages et de les rediriger vers Log::Log4perl, sans même toucher au module. Ce dont vous avez besoin est un module de capture comme

########################################
package Trapper;
########################################
use Log::Log4perl qw(:easy);
sub TIEHANDLE {
    my $class = shift;
    bless [], $class;
}
sub PRINT {
    my $self = shift;
    $Log::Log4perl::caller_depth++;
    DEBUG @_;
    $Log::Log4perl::caller_depth--;
}
1;

et une commande "tie" dans le programme principal pour lier STDERR au module de capture, ainsi qu'une initialisation régulière de Log::Log4perl :

########################################
package main;
########################################
use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init(
    {level  => $DEBUG,
     file   => 'stdout',   # assurez-vous de ne pas utiliser stderr ici !
     layout => "%d %M: %m%n",
    });
tie *STDERR, "Trapper";

Assurez-vous de ne pas utiliser STDERR comme appender de fichier de Log::Log4perl ici (ce qui serait le défaut en mode ":easy"), car cela entraînerait une récursion infinie.

Maintenant, appeler

IgnorantModule::some_method();

résultera dans la sortie désirée :

2004/05/06 11:13:04 IgnorantModule::some_method: Parbleu! An error!

Pourquoi PAR (Perl Archive Toolkit) crée-t-il des exécutables qui ne trouvent ensuite pas leurs appenders Log::Log4perl ?

Si rien d'autre n'est spécifié, "Log::Log4perl" charge dynamiquement les classes d'appenders trouvées dans sa configuration. Si vous spécifiez :

#!/usr/bin/perl
# mytest.pl
use Log::Log4perl qw(get_logger);
my $conf = q(
  log4perl.category.Bar.Twix = WARN, Logfile
  log4perl.appender.Logfile  = Log::Log4perl::Appender::Screen
  log4perl.appender.Logfile.layout = SimpleLayout
);
Log::Log4perl::init(\$conf);
my $logger = get_logger("Bar::Twix");
$logger->error("Blah");

alors "Log::Log4perl::Appender::Screen" sera chargé pendant l'exécution du programme, pas lors de la compilation. Si vous faites compiler PAR le script ci-dessus en un exécutable binaire via :

pp -o mytest mytest.pl

et que vous exécutez ensuite "mytest" sur une machine sans Log::Log4perl installé, vous obtiendrez un message d'erreur tel que :

ERROR: can't load appenderclass 'Log::Log4perl::Appender::Screen'
Can't locate Log/Log4perl/Appender/Screen.pm in @INC ...

Pourquoi ? Au moment de la compilation, "pp" n'a pas réalisé que "Log::Log4perl::Appender::Screen" serait nécessaire plus tard et ne l'a pas inclus dans l'exécutable créé. Pour éviter cela, soit dites "use Log::Log4perl::Appender::Screen" explicitement dans le script, soit compilez-le avec :

pp -o mytest -M Log::Log4perl::Appender::Screen mytest.pl

pour vous assurer que la classe d'appender est incluse.

Comment puis-je accéder à un appender personnalisé défini dans la configuration ?

Tout appender défini dans le fichier de configuration ou quelque part dans le code peut être accédé ultérieurement via "Log::Log4perl->appender_by_name(\"nom_appender\")", qui renvoie une référence à l'objet appender.

Une fois que vous avez l'objet en main, il peut être interrogé ou modifié à votre guise. Par exemple, voyez l' IndentAppender personnalisé défini ci-dessous : après avoir appelé init() pour définir les paramètres de Log4perl, l'objet appender est récupéré pour appeler ses méthodes indent_more() et indent_less() pour contrôler l'indentation des messages :

package IndentAppender;
sub new {
    bless { indent => 0 }, $_[0];
}
sub indent_more  { $_[0]->{indent}++ }
sub indent_less  { $_[0]->{indent}-- }
sub log {
    my($self, %params) = @_;
    print " " x $self->{indent}, $params{message};
}
package main;
use Log::Log4perl qw(:easy);
my $conf = q(
log4perl.category          = DEBUG, Indented
log4perl.appender.Indented = IndentAppender
log4perl.appender.Indented.layout = Log::Log4perl::Layout::SimpleLayout
);
Log::Log4perl::init(\$conf);
my $appender = Log::Log4perl->appender_by_name("Indented");
DEBUG "No identation";
$appender->indent_more();
DEBUG "One more";
$appender->indent_more();
DEBUG "Two more";
$appender->indent_less();
DEBUG "One less";

Comme vous vous y attendez, cela imprimera :

DEBUG - No identation
 DEBUG - One more
  DEBUG - Two more
 DEBUG - One less

car l'appender même utilisé par Log4perl est modifié dynamiquement à l'exécution.

Je ne sais pas si Log::Log4perl est installé. Comment puis-je préparer mon script ?

Si votre script doit être préparé pour des environnements qui peuvent ou non avoir Log::Log4perl installé, il existe une astuce.

Si vous placez les blocs BEGIN suivants en haut du programme, vous pourrez utiliser les macros DEBUG(), INFO(), etc. en mode ":easy" de Log::Log4perl. Si Log::Log4perl est installé dans l'environnement cible, les règles normales de Log::Log4perl s'appliquent. Sinon, toutes les fonctions DEBUG(), INFO(), etc. sont "simulées" (stubbed), c'est-à-dire qu'elles deviennent des no-ops :

use warnings;
use strict;
BEGIN {
    eval { require Log::Log4perl; };
    if($@) {
        print "Log::Log4perl not installed - stubbing.\n";
        no strict qw(refs);
        *{"main::$_"} = sub { } for qw(DEBUG INFO WARN ERROR FATAL);
    } else {
        no warnings;
        print "Log::Log4perl installed - life is good.\n";
        require Log::Log4perl::Level;
        Log::Log4perl::Level->import(__PACKAGE__);
        Log::Log4perl->import(qw(:easy));
        Log::Log4perl->easy_init($main::DEBUG);
    }
}
    # Le script régulier commence ...
DEBUG "Hey now!";

Ce fragment va d'abord rechercher Log::Log4perl, et s'il ne le trouve pas, il aliasera DEBUG(), INFO(), etc. avec des sous-routines vides via des typeglobs. Si Log::Log4perl est disponible, ses constantes de niveau sont d'abord importées ($DEBUG, $INFO, etc.) puis easy_init() est appelé pour initialiser le système de journalisation.

Les appenders de fichier peuvent-ils créer des fichiers avec des permissions différentes ?

Généralement, lorsque "Log::Log4perl::Appender::File" crée un nouveau fichier, ses permissions sont définies sur "rw-r--r--". Pourquoi ? Parce que le umask de votre environnement est très probablement défini par défaut sur 0022, c'est le réglage standard.

Qu'est-ce qu'un umask, demandez-vous ? C'est un modèle qui est appliqué aux permissions de tous les fichiers nouvellement créés. Alors que des appels comme "open(FILE, \">foo\")" essaieront toujours de créer des fichiers en mode "rw-rw-rw-", le système appliquera le masque umask actuel pour déterminer le réglage final des permissions. Le umask est un masque de bits qui est inversé puis appliqué au réglage de permission demandé, en utilisant un ET bit à bit :

$request_permission &~ $umask

Ainsi, un réglage umask de 0000 (le 0 initial indique simplement une valeur octale) créera des fichiers en mode "rw-rw-rw-", un réglage de 0277 utilisera "r--------", et le 0022 standard utilisera "rw-r--r--".

Par exemple, si vous souhaitez que vos fichiers journaux soient créés avec des permissions "rw-r--rw-", utilisez un umask de 0020 avant d'appeler Log::Log4perl->init() :

use Log::Log4perl;
umask 0020;
    # Crée log.out en mode rw-r--rw
Log::Log4perl->init(\ q{
    log4perl.logger = WARN, File
    log4perl.appender.File = Log::Log4perl::Appender::File
    log4perl.appender.File.filename = log.out
    log4perl.appender.File.layout = SimpleLayout
});

Utiliser Log4perl dans un bloc END pose problème !

Il n'est pas facile d'arriver à cette erreur, mais si vous écrivez quelque chose comme :

END { Log::Log4perl::get_logger()->debug("Hey there."); }
use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init($DEBUG);

cela ne fonctionnera pas. La raison est que "Log::Log4perl" définit un bloc END qui nettoie tous les loggers. Et perl exécutera les blocs END dans l'ordre inverse de leur apparition lors de la phase de compilation, donc dans le scénario ci-dessus, le bloc END s'exécutera *après* que Log4perl ait nettoyé ses loggers.

Placer des blocs END utilisant Log4perl *après* une instruction "use Log::Log4perl" résout le problème :

use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init($DEBUG);
END { Log::Log4perl::get_logger()->debug("Hey there."); }

Dans ce scénario, le bloc END montré est exécuté *avant* que Log4perl ne nettoie et le message de débogage sera traité correctement.

Aide ! Mon appender lance un avertissement "Wide character in print" !

Cet avertissement s'affiche lorsque des chaînes Unicode sont imprimées sans précaution. L'avertissement disparaît si l'appendeur incriminé est configuré en mode utf-8 :

    # Soit dans le fichier de configuration log4perl :
log4perl.appender.Logfile.filename = test.log
log4perl.appender.Logfile.utf8     = 1
    # Ou, en mode facile :
Log::Log4perl->easy_init( {
  level => $DEBUG,
  file  => ":utf8> test.log"
} );

Si l'appendeur incriminé est un appendeur d'écran, définissez l'option "utf8" :

log4perl.appender.Screen.stderr = 1
log4perl.appender.Screen.utf8   = 1

Alternativement, "binmode" fait l'affaire :

  # Soit STDOUT ...
binmode(STDOUT, ":utf8);
  # ... soit STDERR.
binmode(STDERR, ":utf8);

Quelques détails à ce sujet : Les chaînes Perl sont soit des chaînes d'octets, soit des chaînes Unicode. "Mike" est une chaîne d'octets. "\x{30DE}\x{30A4}\x{30AF}" est une chaîne Unicode. Les chaînes Unicode sont marquées de manière spéciale et codées en interne en UTF-8.

Si vous imprimez une chaîne d'octets sur STDOUT, tout va bien, car STDOUT est par défaut en mode octet. Cependant, si vous imprimez une chaîne Unicode sur STDOUT sans précaution, "perl" tentera de transformer la chaîne Unicode en chaîne d'octets avant de l'imprimer. Cela peut poser problème si la chaîne Unicode contient des caractères 'larges' qui ne peuvent pas être représentés en Latin-1.

Par exemple, si vous créez une chaîne Unicode avec trois caractères Katakana japonais comme dans :

perl -le 'print "\x{30DE}\x{30A4}\x{30AF}"'

(prononcé par hasard Ma-i-ku, la prononciation japonaise de "Mike"), STDOUT est en mode octet et l'avertissement :

Wide character in print at ./script.pl line 14.

s'affiche. En configurant STDOUT en mode UTF-8 comme dans :

perl -le 'binmode(STDOUT, ":utf8"); print "\x{30DE}\x{30A4}\x{30AF}"'

la chaîne Unicode est imprimée silencieusement en UTF-8. Pour voir les caractères affichés, vous avez besoin d'un terminal UTF-8 avec une police incluant des caractères Katakana japonais.

Comment puis-je envoyer les erreurs à l'écran et les messages de débogage à un fichier ?

Supposons que vous vouliez conserver une sortie DEBUG détaillée dans un fichier et que seuls les messages de niveau ERROR et supérieurs soient imprimés à l'écran. Souvent, les développeurs créent quelque chose comme ceci :

 # Incorrect !!!
log4perl.logger = DEBUG, FileApp
log4perl.logger = ERROR, ScreenApp
 # Incorrect !!!

Cela ne fonctionnera pas. Les définitions de logger ne sont pas additives, et la seconde instruction écrasera la première. Les versions de Log4perl antérieures à 1.04 acceptaient cela silencieusement, laissant les utilisateurs perplexes car cela ne fonctionnait pas comme prévu. À partir de la version 1.04, cela lèvera une erreur *fatale* pour signaler le problème.

Ce que vous devez faire à la place, c'est ceci :

log4perl.logger                    = DEBUG, FileApp, ScreenApp
log4perl.appender.FileApp          = Log::Log4perl::Appender::File
log4perl.appender.FileApp.filename = test.log
log4perl.appender.FileApp.layout   = SimpleLayout
log4perl.appender.ScreenApp          = Log::Log4perl::Appender::Screen
log4perl.appender.ScreenApp.stderr   = 0
log4perl.appender.ScreenApp.layout   = SimpleLayout
   ### Limiter la sortie aux messages de niveau ERROR
log4perl.appender.ScreenApp.Threshold = ERROR
   ###

Notez que sans la définition de "Threshold" pour le deuxième appendeur, les deux appendeurs recevraient tous les messages de priorité DEBUG et supérieure. Avec le seuil défini sur ERROR, le deuxième appendeur filtrera les messages comme requis.

Où dois-je placer mes fichiers de log ?

Les fichiers de log peuvent être placés où vous le souhaitez, mais l'utilisateur effectif du processus appelant doit avoir les permissions d'écriture.

Si le fichier de log n'existe pas au démarrage du programme, l'appendeur de fichier de Log4perl créera le fichier. Pour cela, il a besoin des permissions d'écriture sur le répertoire où le nouveau fichier sera situé. Si le fichier de log existe déjà au démarrage du programme, le processus a simplement besoin des permissions d'écriture sur le fichier. Vous devez avoir les permissions d'écriture sur le répertoire du fichier si vous rencontrez des situations où le fichier de log est recréé, par exemple lors de la rotation des logs.

Si Log::Log4perl est utilisé par un serveur web (par exemple, dans un script CGI ou mod_perl), alors l'utilisateur du serveur (généralement "nobody" ou "www") doit avoir les permissions mentionnées ci-dessus.

Pour préparer votre serveur web à utiliser log4perl, nous recommandons :

webserver:~$ su -
webserver:~# mkdir /var/log/cgiapps
webserver:~# chown nobody:root /var/log/cgiapps/
webserver:~# chown nobody:root -R /var/log/cgiapps/
webserver:~# chmod 02755 -R /var/log/cgiapps/

Ensuite, configurez votre fichier /etc/log4perl.conf en incluant :

log4perl.appender.FileAppndr1.filename =
    /var/log/cgiapps/<app-name>.log

Comment puis-je faire tourner un fichier de log avec newsyslog ?

Voici quelques points à considérer lors de l'utilisation de l'utilitaire de rotation de fichiers populaire "newsyslog" (http://www.courtesan.com/newsyslog) avec l'appendeur de fichier de Log4perl dans des processus de longue durée.

Par exemple, avec une configuration newsyslog comme celle-ci :

# newsyslog.conf
/tmp/test.log 666  12  5  *  B

et avec un appel à :

# newsyslog -f /path/to/newsyslog.conf

"newsyslog" agira si "/tmp/test.log" dépasse la taille spécifiée de 5 Ko. Il déplacera le fichier de log actuel "/tmp/test.log" vers "/tmp/test.log.0" et créera un nouveau fichier "/tmp/test.log" vide avec les permissions spécifiées (c'est pourquoi "newsyslog" doit être exécuté en tant que root). Un fichier "/tmp/test.log.0" existant serait déplacé vers "/tmp/test.log.1", "/tmp/test.log.1" vers "/tmp/test.log.2", et ainsi de suite, pour chacun d'un maximum de 12 fichiers archivés configurés dans "newsyslog.conf".

Bien qu'un nouveau fichier ait été créé, du point de vue de l'appendeur Log4perl, cette situation est identique à celle décrite dans la FAQ précédente, intitulée "How can my file appender deal with disappearing log files".

Pour s'assurer que les messages de log sont écrits dans le nouveau fichier de log et non dans un fichier archivé ou perdus dans un endroit inconnu, l'appendeur doit être configuré pour gérer le cas de fichier disparu.

La situation devient intéressante lorsque "newsyslog" a l'option de compresser les fichiers archivés activée. Cela fait que le fichier original n'est pas simplement déplacé, mais disparaît. Si l'appendeur n'est pas configuré pour recréer le fichier dans ce cas, les messages de log seront perdus sans avertissement. Cela s'applique également au délai d'intervalle de "recreate_check_interval" secondes entre les vérifications du créateur.

Pour s'assurer qu'aucun message n'est perdu, une option est de définir l'intervalle sur :

log4perl.appender.Logfile.recreate_check_interval = 0

Cependant, cela est assez coûteux. Une meilleure option est de définir un gestionnaire de signaux :

log4perl.appender.Logfile.recreate = 1
log4perl.appender.Logfile.recreate_check_signal  = USR1
log4perl.appender.Logfile.recreate_pid_write = /tmp/myappid

En guise de service aux utilisateurs de "newsyslog", l'appendeur Log4perl écrit l'identifiant du processus actuel dans un fichier PID spécifié par l'option "recreate_pid_write". "newsyslog" doit être configuré comme suit :

# newsyslog.conf
configuration pour compresser les fichiers d'archives et # envoyer un signal à l'application activée par Log4perl /tmp/test.log 666 12 5 * B /tmp/myappid 30

pour envoyer le signal défini (30, qui est USR1 sur FreeBSD) au processus de l'application au moment de la rotation. Notez que le numéro de signal est différent sur Linux, où USR1 est désigné par 10. Consultez "man signal" pour plus de détails.

Comment un processus sous l'ID utilisateur A peut-il journaliser dans un fichier sous l'ID utilisateur B ?

Ce scénario se produit souvent dans les configurations où les processus s'exécutent sous différents identifiants d'utilisateur mais doivent écrire dans un fichier journal sous un identifiant d'utilisateur fixe, mais différent.

Avec un "appendeur" de fichier traditionnel, le fichier journal sera probablement créé sous l'identifiant d'un utilisateur et ajouté sous l'identifiant d'un autre utilisateur. Avec un "umask" typique de 0002, le fichier sera créé avec des permissions -rw-rw-r--. Si un utilisateur qui n'appartient pas au groupe du premier utilisateur ajoute ensuite au fichier journal, cela échouera en raison d'un problème de permissions.

Deux solutions potentielles viennent à l'esprit :

  • La création du fichier avec un "umask" de 0000 permettra à tous les utilisateurs d'ajouter au fichier journal. L'appendeur de fichier de Log4perl "Log::Log4perl::Appender::File" possède une option "umask" qui peut être définie pour prendre en charge cela : 
    log4perl.appender.File = Log::Log4perl::Appender::File
log4perl.appender.File.umask = sub { 0000 };

    De cette façon, le fichier journal sera créé avec des permissions -rw-rw-rw- et aura donc des permissions d'écriture universelles. Cela pourrait cependant ouvrir le fichier journal à des manipulations indésirables par des utilisateurs arbitraires.

  • L'exécution du processus sous un identifiant d'utilisateur effectif de "root" lui permettra d'écrire dans le fichier journal, peu importe qui a démarré le processus. Cependant, ce n'est pas une bonne idée, en raison de préoccupations de sécurité.

Heureusement, sous Unix, il existe le démon syslog qui s'exécute en tant que root et accepte les requêtes de journalisation des processus utilisateurs via une socket et les écrit dans des fichiers journaux comme configuré dans "/etc/syslog.conf".

En modifiant "/etc/syslog.conf" et en effectuant un HUP sur le démon syslog, vous pouvez configurer de nouveaux fichiers journaux :

# /etc/syslog.conf
...
user.* /some/path/file.log

En utilisant l'appendeur "Log::Dispatch::Syslog", qui est fourni avec la distribution "Log::Log4perl", vous pouvez alors envoyer des messages via syslog :

use Log::Log4perl qw(:easy);
Log::Log4perl->init(\<<EOT);
    log4perl.logger = DEBUG, app
    log4perl.appender.app=Log::Dispatch::Syslog
    log4perl.appender.app.Facility=user
    log4perl.appender.app.layout=SimpleLayout
EOT
    # Écrit dans /some/path/file.log
ERROR "Message!";

De cette façon, le démon syslog résoudra le problème de permissions.

Notez que bien qu'il soit possible d'utiliser syslog() sans Log4perl (syslog prend également en charge les niveaux de journalisation), les configurations syslog traditionnelles présentent un inconvénient important.

Sans la capacité de Log4perl d'activer la journalisation dans seulement certaines parties d'un système, les systèmes complexes déclencheront des événements de journalisation partout et ralentiront l'exécution au point de devenir inutilisables à des niveaux de débogage élevés.

Le contrôle à distance de la journalisation dans les parties hiérarchiques d'une application via les catégories de Log4perl est l'une de ses fonctionnalités les plus distinctives. Il permet d'activer des niveaux de débogage élevés dans des zones spécifiées sans impact notable sur les performances.

Je veux utiliser l'UTC au lieu de l'heure locale !

Si une mise en page définit une date, Log::Log4perl utilise l'heure locale pour la remplir. Si vous préférez l'UTC, définissez

log4perl.utcDateTimes = 1

dans votre configuration. Alternativement, vous pouvez définir

$Log::Log4perl::DateFormat::GMTIME = 1;

dans votre programme avant la première instruction de journalisation.

Log4perl peut-il intercepter les messages écrits dans un filehandle ?

Vous avez une fonction qui imprime dans un "filehandle". Vous souhaitez lier ce "filehandle" et transmettre tous les messages entrants à un logger Log4perl.

Premièrement, écrivons un paquet qui lie un "filehandle" et le transmet à un logger Log4perl :

package FileHandleLogger;
use Log::Log4perl qw(:levels get_logger);
sub TIEHANDLE {
   my($class, %options) = @_;
   my $self = {
       level    => $DEBUG,
       category => '',
       %options
   };
   $self->{logger} = get_logger($self->{category}),
   bless $self, $class;
}
sub PRINT {
    my($self, @rest) = @_;
    $Log::Log4perl::caller_depth++;
    $self->{logger}->log($self->{level}, @rest);
    $Log::Log4perl::caller_depth--;
}
sub PRINTF {
    my($self, $fmt, @rest) = @_;
    $Log::Log4perl::caller_depth++;
    $self->PRINT(sprintf($fmt, @rest));
    $Log::Log4perl::caller_depth--;
}
1;

Maintenant, si vous avez une fonction comme

sub function_printing_to_fh {
    my($fh) = @_;
    printf $fh "Hi there!\n";
}

qui prend un "filehandle" et y imprime quelque chose, elle peut être utilisée avec Log4perl :

use Log::Log4perl qw(:easy);
usa FileHandleLogger;
Log::Log4perl->easy_init($DEBUG);
tie *SOMEHANDLE, 'FileHandleLogger' or
    die "tie failed ($!)";
function_printing_to_fh(*SOMEHANDLE);
    # imprime "2007/03/22 21:43:30 Hi there!"

Si vous le souhaitez, vous pouvez même spécifier un niveau de journalisation ou une catégorie différent(e) :

tie *SOMEHANDLE, 'FileHandleLogger',
    level => $INFO, category => "Foo::Bar" or die "tie failed ($!)";

Je veux que les messages multilignes soient rendus ligne par ligne !

Avec le "PatternLayout" standard, si vous envoyez un message multiligne à un appendeur comme ceci :

use Log::Log4perl qw(:easy);
Log

il est rendu de cette façon :

2007/04/04 23:23:39 multi
line
message

Si vous voulez que chaque ligne soit rendue séparément selon la mise en page, utilisez "Log::Log4perl::Layout::PatternLayout::Multiline" :

use Log::Log4perl qw(:easy);
Log::Log4perl->init(\<<EOT);
  log4perl.category         = DEBUG, Screen
  log4perl.appender.Screen = Log::Log4perl::Appender::Screen
  log4perl.appender.Screen.layout = \\
    Log::Log4perl::Layout::PatternLayout::Multiline
  log4perl.appender.Screen.layout.ConversionPattern = %d %m %n
EOT
DEBUG "some\nmultiline\nmessage";

et vous obtiendrez

2007/04/04 23:23:39 some
2007/04/04 23:23:39 multiline
2007/04/04 23:23:39 message

à la place.

Je suis sur Windows et j'obtiens tous ces messages de 'redefinition' !

Si vous êtes sur Windows et que vous recevez des messages d'avertissement comme

Constant subroutine Log::Log4perl::_INTERNAL_DEBUG redefined at
  C:/Programme/Perl/lib/constant.pm line 103.
Subroutine import redefined at
  C:/Programme/Perl/site/lib/Log/Log4Perl.pm line 69.
Subroutine initialized redefined at
  C:/Programme/Perl/site/lib/Log/Log4Perl.pm line 207.

alors il y a de fortes chances que vous utilisiez 'Log::Log4Perl' (P majuscule incorrect) au lieu du correct 'Log::Log4perl'. Perl sous Windows ne gère pas bien cette erreur et affiche une série de messages d'avertissement confus. Mais maintenant vous le savez, utilisez simplement le nom de module correct et tout ira bien.

Log4perl se plaint qu'aucune initialisation n'a eu lieu lors de l'arrêt !

Si vous utilisez des commandes de journalisation Log4perl dans les méthodes DESTROY de vos objets, vous pourriez voir des messages confus comme

Log4perl: Seems like no initialization happened. Forgot to call init()?
Use of uninitialized value in subroutine entry at
/home/y/lib/perl5/site_perl/5.6.1/Log/Log4perl.pm line 134 during global
destruction. (in cleanup) Undefined subroutine &main:: called at
/home/y/lib/perl5/site_perl/5.6.1/Log/Log4perl.pm line 134 during global
destruction.

lorsque le programme s'arrête. Que se passe-t-il ?

Ce phénomène se produit si vous avez des références circulaires dans vos objets, que Perl ne peut pas nettoyer lorsqu'un objet sort de portée mais attend la destruction globale. À ce moment-là, cependant, Log4perl s'est déjà arrêté, vous ne pouvez donc plus l'utiliser.

Par exemple, voici une classe simple qui utilise un logger dans sa méthode DESTROY :

package A;
use Log::Log4perl qw(:easy);
sub new { bless {}, shift }
sub DESTROY { DEBUG "Waaah!"; }

Maintenant, si le programme principal crée un objet auto-référentiel, comme dans

package main;
use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init($DEBUG);
my $a = A->new();
$a->{selfref} = $a;

alors vous verrez le message d'erreur indiqué ci-dessus lors de la destruction globale. Comment aborder ce problème ?

Premièrement, vous devriez nettoyer vos références circulaires avant la destruction globale. Elles ne provoqueront pas seulement la destruction des objets dans un ordre difficile à prévoir, mais consommeront également de la mémoire jusqu'à l'arrêt du programme.

Ainsi, le programme ci-dessus pourrait facilement être corrigé en ajoutant

$a->{selfref} = undef;

à la fin ou dans un gestionnaire END. Si cela est difficile à faire, utilisez des références faibles :

package main;
use Scalar::Util qw(weaken);
use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init($DEBUG);
my $a = A->new();
$a->{selfref} = weaken $a;

Cela permet à Perl de nettoyer la référence circulaire lorsque l'objet sort de portée, et n'attend pas la destruction globale.

Comment puis-je accéder aux valeurs du tas POE depuis la mise en page de Log4perl ?

POE est un framework pour créer des applications multitâches s'exécutant dans un seul processus et un seul thread. Les équivalents de threads de POE sont les 'sessions', et comme elles s'exécutent quasi simultanément, vous ne pouvez pas utiliser les NDC/MDC globaux de Log4perl pour conserver des données spécifiques à la session.

Cependant, POE maintient déjà un magasin de données pour chaque session. Il est appelé 'heap' (tas) et est juste une table de hachage stockant des données spécifiques à la session par clé-valeur

Log::Log4perl::FAQ(3pm)

DESCRIPTION

This document answers some frequently asked questions about Log4perl.

I want to use my own custom logging levels.

You can't. Log4perl is using the standard log levels from Log::Log4perl::Level.

I want to log things from within POE sessions.

Log4perl can be configured to use POE session data. To access session-specific heap data from a Log4perl layout, define a custom cspec and reference it with the newly defined pattern in the layout:

use strict;
use POE;
use Log::Log4perl qw(:easy);
Log::Log4perl->init( \ q{
    log4perl.logger = DEBUG, Screen
    log4perl.appender.Screen = Log::Log4perl::Appender::Screen
    log4perl.appender.Screen.layout = PatternLayout
    log4perl.appender.Screen.layout.ConversionPattern = %U %m%n
    log4perl.PatternLayout.cspec.U = \
        sub { POE::Kernel->get_active_session->get_heap()->{ user } }
} );
for (qw( Huey Lewey Dewey )) {
    POE::Session->create(
        inline_states => {
            _start    => sub {
                $_[HEAP]->{user} = $_;
                POE::Kernel->yield('hello');
            },
            hello     => sub {
                DEBUG "I'm here now";
            }
        }
    );
}
POE::Kernel->run();
exit;

The code snippet above defines a new layout placeholder (called 'cspec' in Log4perl) %U which calls a subroutine, retrieves the active session, gets its heap and looks up the entry specified ('user').

Starting with Log::Log4perl 1.20, cspecs also support parameters in curly braces, so you can say

log4perl.appender.Screen.layout.ConversionPattern = %U{user} %U{id} %m%n
log4perl.PatternLayout.cspec.U = \
        sub { POE::Kernel->get_active_session-> \
              get_heap()->{ $_[0]->{curlies} } }

and print the POE session heap entries 'user' and 'id' with every logged message. For more details on cpecs, read the PatternLayout manual.

I want to print something unconditionally!

Sometimes it's a script that's supposed to log messages regardless if Log4perl has been initialized or not. Or there's a logging statement that's not going to be suppressed under any circumstances -- many people want to have the final word, make the executive decision, because it seems like the only logical choice.

But think about it: First off, if a messages is supposed to be printed, where is it supposed to end up at? STDOUT? STDERR? And are you sure you want to set in stone that this message needs to be printed, while someone else might find it annoying and wants to get rid of it?

The truth is, there's always going to be someone who wants to log a messages at all cost, but also another person who wants to suppress it with equal vigilance. There's no good way to serve these two conflicting desires, someone will always want to win at the cost of leaving the other party disappointed.

So, the best Log4perl offers is the ALWAYS level for a message that even fires if the system log level is set to $OFF:

use Log::Log4perl qw(:easy);
Log::Log4perl->easy_init( $OFF );
ALWAYS "This gets logged always. Well, almost always";

The logger won't fire, though, if Log4perl hasn't been initialized or if someone defines a custom log hurdle that's higher than $OFF.

Bottom line: Leave the setting of the logging level to the initial Perl script -- let their owners decided what they want, no matter how tempting it may be to decide it for them.

Why doesn't my END handler remove my log file on Win32?

If you have code like

use Log::Log4perl qw( :easy );
Log::Log4perl->easy_init( { level => $DEBUG, file => "my.log" } );
END { unlink "my.log" or die };

then you might be in for a surprise when you're running it on Windows, because the unlink() call in the END handler will complain that the file is still in use.

What happens in Perl if you have something like

END { print "first end in main\n"; }
use Module;
END { print "second end in main\n"; }

and

package Module;
END { print "end in module\n"; }
1;

is that you get

second end in main
end in module
first end in main

because perl stacks the END handlers in reverse order in which it encounters them in the compile phase.

Log4perl defines an END handler that cleans up left-over appenders (e.g. file appenders which still hold files open), because those appenders have circular references and therefore aren't cleaned up otherwise.

Now if you define an END handler after "use Log::Log4perl", it'll trigger before Log4perl gets a chance to clean up, which isn't a problem on Unix where you can delete a file even if some process has a handle to it open, but it's a problem on Win32, where the OS won't let you do that.

The solution is easy, just place the END handler before Log4perl gets loaded, like in

END { unlink "my.log" or die };
use Log::Log4perl qw( :easy );
Log::Log4perl->easy_init( { level => $DEBUG, file => "my.log" } );

which will call the END handlers in the intended order.
