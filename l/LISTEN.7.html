LISTEN(7) Documentation PostgreSQL 18.1 LISTEN(7)

NOM

LISTEN - écouter une notification

SYNTAXE

LISTEN canal

DESCRIPTION

LISTEN enregistre la session courante en tant qu'écouteur sur le canal de notification nommé canal. Si la session courante est déjà enregistrée en tant qu'écouteur pour ce canal de notification, rien n'est fait.

Chaque fois que la commande NOTIFY canal est invoquée, que ce soit par cette session ou une autre connectée à la même base de données, toutes les sessions écoutant actuellement ce canal de notification sont notifiées, et chacune notifie à son tour son application client connectée.

Une session peut être désenregistrée pour un canal de notification donné avec la commande UNLISTEN. Les enregistrements d'écoute de session sont automatiquement effacés lorsque la session se termine.

La méthode que doit utiliser une application cliente pour détecter les événements de notification dépend de l'interface de programmation d'application PostgreSQL qu'elle utilise. Avec la bibliothèque libpq, l'application émet LISTEN comme une commande SQL ordinaire, puis doit appeler périodiquement la fonction PQnotifies pour savoir si des événements de notification ont été reçus. D'autres interfaces comme libpgtcl fournissent des méthodes de plus haut niveau pour gérer les événements de notification ; en effet, avec libpgtcl, le programmeur d'application ne devrait même pas émettre LISTEN ou UNLISTEN directement. Voir la documentation de l'interface que vous utilisez pour plus de détails.

PARAMETRES

canal

Nom d'un canal de notification (n'importe quel identifiant).

NOTES

LISTEN prend effet lors de la validation de la transaction. Si LISTEN ou UNLISTEN est exécuté dans une transaction qui est ensuite annulée, l'ensemble des canaux de notification écoutés reste inchangé.

Une transaction qui a exécuté LISTEN ne peut pas être préparée pour le commit en deux phases.

Il existe une condition de concurrence lors de la configuration initiale d'une session d'écoute : si des transactions en cours de validation simultanée envoient des événements de notification, lesquels recevra exactement la nouvelle session d'écoute ? La réponse est que la session recevra tous les événements validés après un instant pendant l'étape de validation de la transaction. Mais cela est légèrement postérieur à tout état de la base de données que la transaction aurait pu observer dans ses requêtes. Cela conduit à la règle suivante pour l'utilisation de LISTEN : exécutez d'abord (et validez !) cette commande, puis dans une nouvelle transaction, inspectez l'état de la base de données tel que requis par la logique de l'application, puis fiez-vous aux notifications pour connaître les changements ultérieurs de l'état de la base de données. Les premières notifications reçues pourraient faire référence à des mises à jour déjà observées lors de l'inspection initiale de la base de données, mais ceci est généralement inoffensif.

NOTIFY(7) contient une discussion plus approfondie sur l'utilisation de LISTEN et NOTIFY.

EXEMPLES

Configurer et exécuter une séquence écouter/notifier depuis psql :

LISTEN virtual;
NOTIFY virtual;
Asynchronous notification "virtual" received from server process with PID 8448.

COMPATIBILITE

Il n'y a pas d'instruction LISTEN dans la norme SQL.

VOIR AUSSI
