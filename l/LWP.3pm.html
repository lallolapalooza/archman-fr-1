NOM

LWP - La bibliothèque du monde web pour Perl

SYNTAXE

use LWP;
print "Ceci est libwww-perl-$LWP::VERSION\n";

DESCRIPTION

La collection libwww-perl est un ensemble de modules Perl qui offre une interface de programmation d'application simple et cohérente pour le monde web. Le focus principal de la bibliothèque est de fournir des classes et des fonctions qui permettent d'écrire des clients WWW. La bibliothèque contient également des modules qui sont d'usage plus général et même des classes qui aident à implémenter de simples serveurs HTTP.

La plupart des modules de cette bibliothèque offrent une interface orientée objet. Les objets utilisateurs, les requêtes envoyées et les réponses reçues du serveur WWW sont représentés par des objets. Cela rend l'interface simple et puissante pour ces services. L'interface est facile à étendre et à personnaliser selon les besoins de l'utilisateur.

Les principales caractéristiques de la bibliothèque sont :

  • Elle inclut divers composants réutilisables (modules) qui peuvent être utilisés séparément ou ensemble.
  • Elle fournit un modèle orienté objet pour les communications de type HTTP. Dans ce cadre, nous supportons actuellement l'accès aux

COMMUNICATION DE TYPE HTTP

La bibliothèque libwww-perl est basée sur une communication de type HTTP. Cette section tente de décrire ce que cela signifie.

Commençons par cette citation d'un document de spécification HTTP :

•
Le protocole HTTP est basé sur un paradigme requête/réponse. Un client établit une connexion avec un serveur et envoie une requête au serveur sous la forme d'une méthode de requête, d'une URI et d'une version du protocole, suivis d'un message MIME contenant des en-têtes de requête, des informations client et un contenu éventuel. Le serveur répond avec une ligne de statut, incluant la version du message du protocole et un code de succès ou d'erreur, suivis d'un message MIME contenant des informations serveur, des informations d'entité et un contenu éventuel.

Ce que cela signifie pour libwww-perl, c'est que la communication se déroule toujours selon ces étapes : D'abord, un objet requête est créé et configuré. Cet objet est passé à un serveur et l'on obtient un objet réponse que l'on peut examiner. Une requête est toujours indépendante de toute requête précédente, c'est-à-dire que le service est sans état (stateless). Le même modèle simple est utilisé pour tout service auquel nous voulons accéder.

Par exemple, si nous voulons obtenir un document d'un serveur distant, nous envoyons une requête qui contient le nom du document et la réponse contiendra le document lui-même. Si nous accédons à un moteur de recherche, le contenu de la requête contiendra les paramètres de recherche et la réponse contiendra le résultat de la recherche. Si nous voulons envoyer un message e-mail à quelqu'un, nous envoyons un objet requête contenant notre message au serveur de messagerie et la réponse contiendra un accusé de réception indiquant que le message a été accepté et sera envoyé au(x) destinataire(s).

C'est aussi simple que ça !

L'Objet Requête

L'objet requête de libwww-perl a pour nom de classe HTTP::Request. Le fait que le nom de la classe utilise le préfixe "HTTP::" implique seulement que nous utilisons le modèle de communication HTTP. Cela ne limite pas le type de services auxquels nous pouvons tenter de passer cette requête. Par exemple, nous enverrions des HTTP::Requests aux serveurs FTP et gopher, ainsi qu'au système local.

Les principaux attributs des objets requête sont :

  • method est une courte chaîne indiquant le type de requête. Les méthodes les plus courantes sont GET, PUT, POST et HEAD.
  • uri est une chaîne qui désigne le protocole, le serveur et le nom du « document » auquel nous voulons accéder. L'uri peut également coder d'autres paramètres.
  • headers contient des informations supplémentaires sur la requête et peut être utilisé pour décrire le contenu. Les en-têtes sont un ensemble de paires clé/valeur.
  • content est une quantité quelconque de données.

L'Objet Réponse

L'objet réponse de libwww-perl a pour nom de classe HTTP::Response. Les principaux attributs des objets de cette classe sont :

  • code est une valeur numérique indiquant le résultat général de la requête.
  • message est une chaîne courte et lisible correspondant au code.
  • headers contient des informations supplémentaires sur la réponse et décrit le contenu.
  • content est une quantité quelconque de données.

Comme nous ne voulons pas gérer toutes les valeurs de code directement dans nos programmes, un objet réponse de libwww-perl a des méthodes que nous pouvons utiliser pour interroger quel type de réponse il s'agit. Les méthodes les plus courantes pour classer les réponses sont :

is_success()
La requête a été correctement reçue, comprise ou acceptée.
is_error()
La requête a échoué. Le serveur ou la ressource n'est pas disponible, l'accès à la ressource peut être refusé, ou il y a d'autres raisons d'échec.

L'Agent Utilisateur

Supposons que nous ayons créé un objet requête. Qu'en faisons-nous réellement pour obtenir une réponse ?

La réponse est que nous le passons à un objet agent utilisateur et celui-ci s'occupe de tout ce qu'il doit faire (comme la communication de bas niveau et la gestion des erreurs) et renvoie un objet réponse. L'agent utilisateur représente votre application sur le réseau et fournit une interface qui peut accepter des requêtes et renvoyer des réponses.

L'agent utilisateur est une couche d'interface entre votre code d'application et le réseau. À travers cette couche, vous pouvez accéder à divers serveurs sur le réseau.

Le nom de classe de l'agent utilisateur est LWP::UserAgent. Chaque application libwww-perl qui veut communiquer doit créer au moins un objet de cette classe. La principale méthode fournie par cet objet est request(). Cette méthode prend un objet HTTP::Request comme argument et renvoie (éventuellement) un objet HTTP::Response.

L'agent utilisateur a de nombreux autres attributs qui vous permettent de configurer la manière dont il communiquera avec le réseau et avec votre application.

  • timeout spécifie combien de temps nous donnons aux serveurs distants pour répondre avant que la bibliothèque ne se déconnecte et ne crée une réponse de time-out interne.
  • agent spécifie le nom que votre application utilise lorsqu'elle présente son identité sur le réseau.
  • from peut être configuré comme l'adresse e-mail de la personne responsable de l'exécution de l'application. S'il est configuré, alors cet e-mail sera envoyé aux serveurs avec chaque requête.
  • parse_head spécifie si nous devons initialiser les en-têtes de réponse à partir de la section <head> des documents HTML.
  • proxy et no_proxy spécifient si et quand passer par un serveur proxy. http://www.w3.org/History/1994/WWW/Proxies/

  • credentials fournit un moyen d'établir les noms d'utilisateur et mots de passe nécessaires pour accéder à certains services.

    • De nombreuses applications souhaitent un contrôle encore plus fin sur la façon dont elles interagissent avec le réseau et y parviennent en sous-classant LWP::UserAgent. La bibliothèque inclut une sous-classe, LWP::RobotUA, pour les applications de robots.

    Un Exemple

    Cet exemple montre comment l'agent de requête, une requête et une réponse sont représentés dans un vrai code Perl :

    # Créer un objet d'agent de requête
use LWP::UserAgent;
my $ua = LWP::UserAgent->new;
$ua->agent("MyApp/0.1 ");
# Créer une requête
my $req = HTTP::Request->new(POST => 'http://search.cpan.org/search');
$req->content_type('application/x-www-form-urlencoded');
$req->content('query=libwww-perl&mode=dist');
# Passer la requête à l'agent et obtenir une réponse
my $res = $ua->request($req);
# Vérifier le résultat de la réponse
if ($res->is_success) {
    print $res->content;
}
else {
    print $res->status_line, "\n";
}

    Le $ua est créé une fois au démarrage de l'application. De nouvelles requêtes doivent normalement être créées pour chaque requête envoyée.

    PRISE EN CHARGE DU RÉSEAU

    Cette section aborde les différents protocoles de communication et les méthodes HTTP qui peuvent être utilisées pour chacun.

    Pour toutes les requêtes, un en-tête « User-Agent » est ajouté et initialisé à partir de l'attribut "$ua->agent" avant de passer la requête au module réseau. De même, un en-tête « From » est initialisé à partir de l'attribut $ua->from.

    Pour toutes les réponses, la bibliothèque ajoute un en-tête appelé « Client-Date ». Cet en-tête contient l'heure à laquelle la réponse a été reçue par votre application. Le format et la signification de l'en-tête sont les mêmes que ceux de l'en-tête « Date » créé par le serveur. Vous pouvez également rencontrer d'autres en-têtes de type « Client-XXX ». Tous ces en-têtes sont générés en interne par la bibliothèque et ne sont pas reçus des serveurs.

    Requêtes HTTP

    Les requêtes HTTP sont simplement transmises à un serveur HTTP et c'est lui qui décide de la suite. Peu de serveurs implémentent d'autres méthodes que les habituelles « GET », « HEAD », « POST » et « PUT », mais les scripts CGI peuvent implémenter n'importe quelle méthode qu'ils souhaitent.

    Si le serveur n'est pas disponible, la bibliothèque générera une réponse d'erreur interne.

    La bibliothèque ajoute automatiquement un en-tête « Host » et un en-tête « Content-Length » à la requête HTTP avant de l'envoyer sur le réseau.

    Pour une requête GET, vous pourriez vouloir ajouter un en-tête « If-Modified-Since » ou « If-None-Match » pour rendre la requête conditionnelle.

    Pour une requête POST, vous devriez ajouter l'en-tête « Content-Type ». Lorsque vous essayez d'émuler la gestion des formulaires HTML, vous devriez normalement laisser la valeur de l'en-tête « Content-Type » comme « application/x-www-form-urlencoded ». Consultez lwpcook pour des exemples.

    L'implémentation de libwww-perl prend actuellement en charge les protocoles HTTP/1.1 et HTTP/1.0.

    La bibliothèque permet d'accéder à un serveur proxy via HTTP. Cela signifie que vous pouvez configurer la bibliothèque pour que toutes les requêtes passent par le module de protocole HTTP. Consultez LWP::UserAgent pour la documentation à ce sujet.

    Requêtes HTTPS

    Les requêtes HTTPS sont des requêtes HTTP sur une connexion réseau cryptée utilisant le protocole SSL développé par Netscape. Tout ce qui est mentionné pour les requêtes HTTP s'applique également aux requêtes HTTPS. De plus, la bibliothèque ajoute les en-têtes « Client-SSL-Cipher », « Client-SSL-Cert-Subject » et « Client-SSL-Cert-Issuer » à la réponse. Ces en-têtes indiquent la méthode de chiffrement utilisée et le nom du propriétaire du serveur.

    La requête peut contenir l'en-tête « If-SSL-Cert-Subject » pour rendre la requête conditionnelle sur le contenu du certificat du serveur. Si le sujet du certificat ne correspond pas, aucune requête n'est envoyée au serveur et une réponse d'erreur générée en interne est renvoyée. La valeur de l'en-tête « If-SSL-Cert-Subject » est interprétée comme une expression régulière Perl.

    Requêtes FTP

    La bibliothèque prend actuellement en charge les requêtes GET, HEAD et PUT. GET récupère un fichier ou une liste de répertoires à partir d'un serveur FTP. PUT stocke un fichier sur un serveur FTP.

    Vous pouvez spécifier un compte FTP pour les serveurs qui le demandent en plus du nom d'utilisateur et du mot de passe. Ceci est spécifié en incluant un en-tête « Account » dans la requête.

    Les noms d'utilisateur et mots de passe peuvent être spécifiés via une authentification basique ou codés dans l'URL. Les tentatives de connexion échouées renvoient une réponse « UNAUTHORIZED » avec « WWW-Authenticate: Basic » et peuvent être traitées comme une authentification basique pour HTTP.

    La bibliothèque prend en charge le mode de transfert FTP ASCII en spécifiant le paramètre « type=a » dans l'URL. Elle prend également en charge l'envoi de plages pour les transferts FTP en utilisant l'en-tête « Range ».

    Les listes de répertoires sont renvoyées par défaut sans être traitées (telles que renvoyées par le serveur FTP) avec le type de média signalé comme « text/ftp-dir-listing ». Le module File::Listing fournit des méthodes pour interpréter ces listes de répertoires.

    Le module FTP peut également convertir les listes de répertoires en HTML et cela peut être demandé via les mécanismes de négociation de contenu standards (ajoutez un en-tête « Accept: text/html » dans la requête si vous le souhaitez).

    Pour les récupérations de fichiers normales, le type de contenu « Content-Type » est déduit en fonction de l'extension du nom de fichier. Consultez LWP::MediaTypes pour plus d'informations.

    L'en-tête « If-Modified-Since » fonctionne pour les serveurs qui implémentent la commande « MDTM ». Il ne fonctionnera probablement pas pour les listes de répertoires.

    Exemple :

    $req = HTTP::Request->new(GET => 'ftp://me:passwd@ftp.some.where.com/');
$req->header(Accept => "text/html, */*;q=0.1");

    Requêtes de nouvelles

    L'accès au système de nouvelles USENET est implémenté via le protocole NNTP. Le nom du serveur de nouvelles est obtenu de la variable d'environnement NNTP_SERVER et est par défaut « news ». Il n'est pas possible de spécifier le nom d'hôte du serveur NNTP dans les URLs de nouvelles.

    La bibliothèque prend en charge GET et HEAD pour récupérer des articles de nouvelles via le protocole NNTP. Vous pouvez également publier des articles dans de nouveaux groupes de nouvelles en utilisant la méthode POST (surprise !).

    GET sur les nouveaux groupes de nouvelles n'est pas encore implémenté.

    Exemples :

    $req = HTTP::Request->new(GET => 'news:abc1234@a.sn.no');
$req = HTTP::Request->new(POST => 'news:comp.lang.perl.test');
$req->header(Subject => 'This is a test',
             From    => 'me@some.where.org');
$req->content(<<EOT);
This is the content of the message that we are sending to
the world.
EOT

    Requête Gopher

    La bibliothèque prend en charge les méthodes GET et HEAD pour les requêtes Gopher. Toutes les valeurs d'en-tête de requête sont ignorées. HEAD triche et renvoie une réponse sans communiquer avec le serveur.

    Les menus Gopher sont toujours convertis en HTML.

    L'en-tête « Content-Type » est généré à partir du type de document dans le chemin de l'URL lui-même (première lettre).

    Exemple :

    $req = HTTP::Request->new(GET => 'gopher://gopher.sn.no/');

    Requête de fichier

    La bibliothèque prend en charge les méthodes GET et HEAD pour les requêtes de fichiers. L'en-tête « If-Modified-Since » est pris en charge. Tous les autres en-têtes sont ignorés. Le composant *host* de l'URL de fichier doit être vide ou « localhost ». Toute autre valeur de *host* est traitée comme une erreur.

    Les répertoires sont toujours convertis en document HTML. Pour les fichiers normaux, les en-têtes « Content-Type » et « Content-Encoding » dans la réponse sont déduits en fonction de l'extension du nom de fichier.

    Exemple :

    $req = HTTP::Request->new(GET => 'file:/etc/passwd');

    Requête Mailto

    Vous pouvez envoyer (également appelé « POST ») des messages électroniques à l'aide de la bibliothèque. Tous les en-têtes spécifiés pour la requête sont transmis au système de messagerie. L'en-tête « To » est initialisé à partir de l'adresse e-mail dans l'URL.

    Exemple :

    $req = HTTP::Request->new(POST => 'mailto:libwww@perl.org');
$req->header(Subject => "subscribe");
$req->content("Please subscribe me to the libwww-perl mailing list!\n");

    Requêtes CPAN

    Les URLs avec le schéma « cpan: » sont redirigées vers un miroir CPAN approprié. Si vous avez votre propre miroir CPAN local, vous pourriez dire à LWP de l'utiliser pour les URLs « cpan: » au moyen d'une affectation comme :

    $LWP::Protocol::cpan::CPAN = "file:/local/CPAN/";

    Des miroirs CPAN appropriés peuvent également être choisis à partir de la configuration de CPAN.pm, donc si vous avez utilisé ce module, un miroir approprié devrait être choisi automatiquement. Si aucune de ces options ne s'applique, une redirection vers l'emplacement générique CPAN http est émise.

    Exemple de requête pour télécharger le dernier perl :

    $req = HTTP::Request->new(GET => "cpan:src/latest.tar.gz");

    ENVIRONNEMENT

    Les variables d'environnement suivantes sont utilisées par LWP :

    HOME
    Les fonctions LWP::MediaTypes rechercheront les fichiers .media.types et .mime.types relatifs à votre répertoire personnel.
    http_proxy
    ftp_proxy
    xxx_proxy
    no_proxy
    Ces variables d'environnement peuvent être définies pour activer la communication via un serveur proxy. Voir la description de la méthode "env_proxy" dans LWP::UserAgent.
    PERL_LWP_ENV_PROXY
    Si elle est définie sur une valeur VRAIE, alors LWP::UserAgent appellera par défaut "env_proxy" lors de l'initialisation. Cela permet à LWP de respecter les variables de proxy décrites ci-dessus.
    PERL_LWP_SSL_VERIFY_HOSTNAME
    Le réglage par défaut "verify_hostname" pour LWP::UserAgent. S'il n'est pas défini, la valeur par défaut sera 1. Définissez-le sur 0 pour désactiver la vérification du nom d'hôte (la valeur par défaut avant libwww-perl 5.840).
    PERL_LWP_SSL_CA_FILE
    PERL_LWP_SSL_CA_PATH
    Le fichier et/ou le répertoire où se trouvent les certificats d'autorité de certification approuvés. Voir LWP::UserAgent pour plus de détails.
    PERL_HTTP_URI_CLASS
    Utilisé pour décider quels objets URI instancier. La valeur par défaut est URI. Vous pourriez vouloir la définir sur URI::URL pour la compatibilité avec les anciennes versions.
