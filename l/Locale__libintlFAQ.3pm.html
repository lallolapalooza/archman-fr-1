QUESTIONS ET RÉPONSES

Pourquoi libintl-perl est-il si volumineux ? Pourquoi n'utilisez-vous pas Encode(3pm) pour la conversion des jeux de caractères au lieu de créer votre propre version ?

Encode(3pm) nécessite au moins Perl 5.7.x, tandis que libintl-perl doit fonctionner sur Perl 5.004. En interne, libintl-perl utilise Encode(3pm) s'il est disponible.

Pourquoi les fonctions gettext désactivent-elles toujours le flag utf-8 sur les chaînes qu'elles renvoient ?

Parce que les fonctions gettext ne savent pas si la chaîne est encodée en utf-8 ou non. Au lieu de faire des suppositions, il désactive plutôt le drapeau.

Puis-je définir le flag utf-8 sur les chaînes renvoyées par la famille de fonctions gettext ?

Oui, mais ce n'est pas recommandé. Si vous voulez absolument le faire, utilisez la fonction bind_textdomain_filter dans Locale::Messages pour cela.

Les chaînes renvoyées par gettext et ses similaires sont par défaut encodées dans le jeu de caractères préféré pour la locale de l'utilisateur, mais il n'existe aucun moyen portable de savoir s'il s'agit d'utf-8 ou non. Cela signifie que vous devez soit forcer utf-8 comme jeu de caractères de sortie (au moyen de bind_textdomain_codeset() et/ou de la variable d'environnement OUTPUT_CHARSET) et outrepasser la préférence de l'utilisateur, soit vous risquez de marquer des chaînes comme utf-8 alors qu'elles ne le sont pas réellement.

Le concept entier derrière ce flag utf-8 introduit dans Perl 5.6 est sérieusement défectueux, et le dilemme décrit ci-dessus en est une preuve. La meilleure chose que vous puissiez faire avec ce drapeau est de vous en débarrasser et de le désactiver. Votre code en bénéficiera et deviendra moins sujet aux erreurs, plus portable et plus rapide.

Pourquoi les caractères non-ASCII dans mon application Gtk2 s'affichent-il mal ?

La liaison Perl de Gtk2 a un défaut de conception. Elle attend que tous les messages d'interface utilisateur soient en UTF-8 et elle attend également que les messages soient marqués comme utf-8. La seule solution pour vous est de forcer tous vos fichiers po à être encodés en utf-8 (convertissez-les manuellement si nécessaire), et de forcer également ce jeu de caractères dans votre application, indépendamment des paramètres de locale de l'utilisateur. En supposant que votre textdomain est « org.bar.foo », vous devez coder le code suivant dans votre module principal ou votre script :

BEGIN {
    bind_textdomain_filter 'org.bar.foo', \&turn_utf_8_on;
    bind_textdomain_codeset 'org.bar.foo', 'utf-8';
}

Voir le fichier GTestRunner.pm de Test::Unit::GTestRunner(3pm) pour plus de détails.

Comment interfacer les définitions d'interface Glade2 avec libintl-perl ?

Gtk2::GladeXML(3pm) semble ignorer les appels à bind_textdomain(). Voir le fichier GTestRunner.pm de Test::Unit::GTestRunner(3pm) pour une solution possible.

Pourquoi Locale::TextDomain utilise-t-il un double underscore ? Je suis habitué à un seul underscore venant du C ou d'autres langages.

Les noms de fonctions constitués d'un seul caractère non alphanumérique rendent la fonction automatiquement globale en Perl. De plus, en Perl 6, l'opérateur de concaténation sera l'underscore au lieu du point.

Comment puis-je changer de langue ou forcer une langue spécifique indépendamment des paramètres utilisateur lus depuis l'environnement ?

La réponse simple est :

use POSIX qw (setlocale LC_ALL);

my $language = 'fr';
my $country = 'FR';
my $charset = 'iso-8859-1';
setlocale LC_ALL, "${language}_$country.$charset";

Malheureusement, cela échouera dans de nombreux cas. Le problème est que les identificateurs de locale ne sont pas standardisés et dépendent entièrement du système. Non seulement leur format général, mais aussi d'autres détails comme la sensibilité à la casse. Certains systèmes sont très indulgents sur le système - par exemple, normalisant les descriptions de jeux de caractères - d'autres très stricts. Pour être raisonnablement indépendant de la plateforme, vous devriez essayer une liste d'identificateurs de locale possibles pour vos paramètres souhaités. C'est à peu près ce que j'essaierais pour obtenir ce qui précède :

my @tries = qw (
     fr_FR.iso-8859-1 fr_FR.iso8859-1 fr_FR.iso88591
     fr_FR.ISO-8859-1 fr_FR.ISO8859-1 fr_FR.ISO88591
     fr.iso-8859-1 fr.iso8859-1 fr.iso88591
     fr.ISO-8859-1 fr.ISO8859-1 fr.ISO88591
     fr_FR
     French_France.iso-8859-1 French_France.iso8859-1 French_France.iso88591
     French_France.ISO-8859-1 French_France.ISO8859-1 French_France.ISO88591
     French.iso-8859-1 French.iso8859-1 French.iso88591
     French.ISO-8859-1 French.ISO8859-1 French.ISO88591
);
foreach my $try (@tries) {
     last if setlocale LC_ALL, $try;
}

Définissez Locale::Util(3pm) pour les fonctions qui vous aident avec cela.

Alternativement, vous pouvez forcer une langue spécifique en définissant les variables d'environnement LANGUAGE, LANG et OUTPUT_CHARSET, mais cela n'est garanti de fonctionner que si vous utilisez l'implémentation Perl pure de gettext (voir la documentation de select_package() dans Locale::Messages(3pm)). Vous feriez ce qui précède comme ceci :

use Locale::Messages qw (nl_putenv);
# LANGUAGE est une liste de langues séparées par des deux-points.
nl_putenv("LANGUAGE=fr_FR");
# Si LANGUAGE est défini, LANG doit être défini à la langue principale.
# Ce n'est pas nécessaire pour gettext, mais pour d'autres parties du système
# ça l'est.
nl_putenv("LANG=fr_FR");
# Forcer un jeu de caractères de sortie comme ceci :
nl_putenv("OUTPUT_CHARSET=iso-8859-1");
setlocale (LC_MESSAGES, 'C');

Ces variables d'environnement sont des extensions GNU, et elles sont également prises en compte par libintl-perl. Néanmoins, vous devriez toujours essayer de définir la locale avec setlocale pour la catégorie de rattrapage LC_ALL. Si vous ne le faites pas, la sortie de votre programme peut être désordonnée, mélangeant langues et jeux de caractères, si le système fonctionne dans une locale qui n'est pas compatible avec vos propres paramètres linguistiques.

N'oubliez pas que ces variables d'environnement ne sont pas garanties de fonctionner si vous utilisez une version XS de gettext. Pour forcer l'utilisation de l'implémentation Perl pure, faites ceci :

Locale::Messages->select_package ('gettext_pp');

Si vous pensez que c'est un cerveau mort, vous avez raison, mais je ne peux pas vous aider. En fait, il devrait y avoir une API plus flexible que setlocale, mais au moment de la rédaction, il n'y en a pas. D'ici là, la recommandation est la suivante :

1) Essayez de définir LC_ALL avec Locale::Util.
2) Si cela ne réussit pas, abandonnez ou ...
3) Réinitialisez LC_MESSAGES à C/POSIX.
4) Passez à Perl pur pour gettext.
5) Définissez les variables d'environnement LANGUAGE, LANG,
   et OUTPUT_CHARSET à vos valeurs souhaitées.
