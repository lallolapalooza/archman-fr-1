DESCRIPTIO

N

Ce module implémente une seule fonctionnalité qui n'intéresse que les modules perl avancés, à savoir les interruptions asynchrones (pensez aux « signaux UNIX », qui sont très similaires)

.

Parfois, les modules souhaitent exécuter du code de manière asynchrone (dans un autre thread, ou depuis un gestionnaire de signaux), puis signaler à l'interpréteur perl certains événements. Une méthode courante consiste à écrire des données dans un tube et à utiliser une boîte à outils de gestion d'événements pour surveiller les événements d'E/S. Une autre méthode consiste à envoyer un signal. Ces méthodes sont lentes et, dans le cas d'un tube, ne sont pas non plus asynchrones — elles n'interrompront pas un interpréteur perl en cours

d'exécution.

Ce module implémente des notifications asynchrones qui vous permettent de signaler du code perl en cours d'exécution depuis un autre thread, de manière asynchrone, et parfois même sans utiliser une seule

syscall.

SCÉNARIOS

D'UTILISATION
Gestion de signaux sans condition de
course
Il semble qu'il n'y ait aucun moyen de gérer les signaux sans condition de course en perl : pour attraper un signal, vous devez exécuter du code Perl, et entre l'entrée dans l'interpréteur la fonction « select » (ou d'autres fonctions bloquantes) et l'exécution de la syscall select, il y a une période de temps petite mais pertinente pendant laquelle les signaux seront mis en file d'attente, mais les gestionnaires de signaux perl ne seront pas exécutés et la syscall bloquante ne sera pas interrompue.

Vous pouvez utiliser ce module pour lier un signal à un rappel tout en activant simultanément un tube d'événements sur lequel vous pouvez appeler « select », éliminant complètement la condition de

course.

Cela peut être utilisé pour implémenter la gestion des signaux dans des boucles d'événements, par exemple AnyEvent, POE, IO::Async::Loop,

etc.
Les threads d'arrière-plan veulent un signalement
rapide
Supposiez que vous ayez besoin d'un minutage très précis et que vous puissiez économiser un cœur de CPU supplémentaire pour cela. Vous pouvez alors exécuter un thread supplémentaire qui signale votre interpréteur perl. Cela signifie que vous pouvez obtenir une source de minutage très précise pendant que votre code perl effectue des calculs intensifs, sans même utiliser de syscall pour communiquer entre vos threads.

Par exemple, le serveur de jeu deliantra utilise une variante de cette technique pour interrompre régulièrement les processus d'arrière-plan afin d'envoyer des mises à jour de carte aux clients

du jeu.

Ou EV::Loop::Async utilise un objet interrupt pour réveiller perl lorsque de nouveaux événements sont

arrivés.

COMMENT

L'UTILISER

Vous pouvez utiliser ce module en créant un objet « Async::Interrupt » pour chaque source d'événements de ce type. Cet objet stocke un rappel au niveau perl et/ou au niveau C qui est invoqué lorsque l' objet « Async::Interrupt » reçoit un signal. Il est exécuté à la prochaine fois où l'interpréteur perl est en cours d'exécution (c'est-à-dire qu'il interrompra un calcul, mais pas une fonction XS ou une syscall)

.

Vous pouvez signaler l' objet « Async::Interrupt » soit en appelant sa méthode « ->signal », ou, plus couramment, en appelant une fonction C. Il existe également la source de signaux intégrée (POSIX)

.

La « ->signal_func » renvoie l'adresse de la fonction C qui doit être appelée (plus un argument à utiliser pendant l'appel). La fonction de signalement prend également un argument entier dans la plage SIG_ATOMIC_MIN à SIG_ATOMIC_MAX (garantissant au moins 0..127)

.

Étant donné que ce type d'interruption est rapide, mais ne peut interrompre qu'un interpréteur en cours d'exécution, il existe une prise en charge facultative pour signaler un tube — cela signifie que vous pouvez également attendre que le tube devienne lisible (par exemple via EV ou AnyEvent). Cela entraîne bien sûr le surcoût d'un syscall « read » et « wr

it
e
».

Implémentation de la gestion de signaux sans condition de

course

Cet exemple utilise un seul tube d'événements pour tous les signaux, et un Async::Interrupt par signal. Ce code est en fait celui que le module AnyEvent utilise lui-même lorsque Async::Interrupt est

disponible.

D'abord, créez le tube d'événements et intégrez-le dans la boucle

d'événements

$SIGPIPE_W = AnyEvent->io (
   fh   => $SIGPIPE->fileno,
   poll => "r",
   cb   => \&_signal_check, # défini plus tard
)
;

Ensuite, pour chaque signal à intercepter, créez un objet Async::Interrupt. Le rappel définit simplement une variable globale, car nous ne sommes intéressés que par les signaux synchrones (c'est-à-dire lorsque la boucle d'événements interroge), ce qui explique pourquoi le vidange du tube n'est pas effectuée automatiquement

my $interrupt = new Async::Interrupt
   cb             => sub { undef $SIGNAL_RECEIVED{$signum} },
   signal         => $signum,
   pipe           => [$SIGPIPE->filenos],
   pipe_autodrain => 0,
;

Enfin, le rappel d'E/S pour le tube d'événements gère les signaux

: 
sub _signal_check {
   # vider d'abord le tube
   $SIGPIPE->drain;
   # deux boucles, juste pour être sûr
   while (%SIGNAL_RECEIVED) {
      for (keys %SIGNAL_RECEIVED) {
         delete $SIGNAL_RECEIVED{$_};
         warn "signal $_ received\n";
      }
   }
}
