Un objet ASYNC_WAIT_CTX représente une « session » asynchrone, c'est-à-dire un ensemble lié d'opérations cryptographiques. Par exemple, en termes SSL, cela correspondrait de manière un à un à une

connexion

SSL.

Le code applicatif doit créer un ASYNC_WAIT_CTX à l'aide de la fonction ASYNC_WAIT_CTX_new() avant d'appeler ASYNC_start_job() (voir ASYNC_START_JOB(3)). Lorsqu'une tâche est démarrée, elle est associée au ASYNC_WAIT_CTX pour la durée de cette tâche. Un ASYNC_WAIT_CTX ne doit être utilisé que pour un seul

ASYNC_JOB

à la fois, mais peut être réutilisé après qu'un ASYNC_JOB est terminé pour un ASYNC_JOB suivant. Lorsque la session est terminée (par exemple, la connexion SSL est fermée), le code applicatif effectue le nettoyage avec ASYNC_WAIT_CTX_free(). Les ASYNC_WAIT_CTX peuvent avoir des descripteurs de fichier d'« attente » qui leur sont associés. Appeler ASYNC_WAIT_CTX_get_all_fds() et passer un pointeur vers un ASYNC_WAIT_CTX dans le paramètre ctx renverra les descripteurs de fichier d'attente associés à cette tâche dans *fd. Le nombre de descripteurs de fichi

er renvoyés

sera stocké dans *numfds. Il est de la responsabilité de l'appelant de s'assurer qu'une mémoire suffisante a été allouée dans *fd pour recevoir tous les descripteurs de fichier. Appeler ASYNC_WAIT_CTX_get_all_fds() avec une valeur fd NULL ne renverra aucun descripteur de fichier mais remplira quand même *numfds. Par conséquent, le code applicatif est généralement censé appeler cette fonction deux fois : une fois pour obtenir le nombre de descripteurs de fichier, puis à nouveau lorsque suffisamment de mémoire a été allouée. Si un seul moteur asynchrone est utilisé, alors normalement cet appel ne renverra qu'un seul descripteur de fichier. Si plusieurs moteurs asynchrones sont utilisés, plus de descripteurs pourraient être renvoyés. La fonction ASYNC_WAIT_CTX_get_changed_fds() peut être utilisée pour détecter si des descripteurs de fichier ont changé depuis le dernier appel où ASYNC_start_job() a renvoyé ASYNC_PAUSE (ou depuis la création du ASYNC_WAIT_CTX si aucun résultat ASYNC_PAUSE n'a

été

reçu). Les paramètres numaddfds et numdelfds seront remplis avec le nombre de descripteurs de fichier ajoutés ou supprimés respectivement. *addfd et *delfd seront remplis avec la liste des descripteurs de fichier ajoutés et supprimés respectivement. De même que pour numaddfds and ASYNC_WAIT_CTX_get_all_fds(), l'un ou l'autre de ceux-ci peut être NULL, mais s'ils ne sont pas NULL, alors l'appelant est responsable de s'assurer qu'une mémoire suffisante est allouée. Les implémenteurs de code prenant en charge l'asynchrone (par exemple, les moteurs) sont encouragés à renvoyer un descripteur de fichier stable pour la durée de vie du ASYNC_WAIT_CTX afin de réduire le « churn » des

descripteurs

de fichier qui changent régulièrement - bien qu'aucune garantie à cet égard ne soit fournie aux applications. Les applications peuvent attendre que le descripteur de fichier soit prêt pour la « lecture » à l'aide d'un appel de fonction système tel que select ou poll (le

fait

d'être prêt pour la « lecture » indique que la tâche doit être reprise). Si aucun descripteur de fichier n'est mis à disposition, une application devra périodiquement « interroger » la tâche en essayant de la redémarrer pour voir si elle est prête à continuer. Le code prenant en charge l'asynchrone (par exemple, les moteurs) peut obtenir le ASYNC_WAIT_CTX actuel de la tâche via ASYNC_get_wait_ctx(3

)

et fournir un descripteur de fichier à utiliser pour l'attente en appelant ASYNC_WAIT_CTX_set_wait_fd(). Typiquement, cela serait fait par un moteur immédiatement avant d'appeler ASYNC_pause_job() et non par le code de l'utilisateur final. Une association existante avec un descripteur de fichier peut être obtenue à l'aide de ASYNC_WAIT_CTX_get_fd() et effacée à l'aide de ASYNC_WAIT_CTX_clear_fd(). Ces deux fonctions nécessitent une valeur key qui est unique au code prenant en charge l'asynchrone. Cela pourrait être n'importe quelle valeur unique, mais un bon candidat pourrait être le ENGINE * pour le moteur. Le paramètre custom_data peut être n'importe quelle valeur, et sera renvoyé lors d'un appel ultérieur à ASYNC_WAIT_CTX_get_fd(). La fonction ASYNC_WAIT_CTX_set_wait_fd() attend également un pointeur vers une routine de « nettoyage ». Celle-ci peut être NULL, mais si elle est fournie, elle sera automatiquement appelée lorsque le ASYNC_WAIT_CTX est libéré, et donne au moteur l'opportunité de fermer le descripteur de fichier ou toute autre ressource. Remarque : La routine de « nettoyage » n'est pas appelée si le descripteur de fichier est effacé directement par un appel à ASYNC_WAIT_CTX_clear_fd() . Un exemple d'ut

ilisation

typique pourrait être un moteur capable de gérer l'asynchrone. Le code utilisateur initierait des opérations cryptographiques. Le moteur initierait ces opérations de manière asynchrone puis appellerait ASYNC_WAIT_CTX_set_wait_fd() suivi de ASYNC_pause_job() pour rendre le contrôle au code utilisateur. Le code utilisateur peut alors effectuer d'autres tâches ou attendre que la tâche soit prête en appelant « select » ou une autre fonction similaire sur le descripteur de fichier d'attente. Le moteur peut signaler au code utilisateur que la tâche doit être reprise en rendant le descripteur de fichier d'attente « lisible ». Une fois repris, le moteur doit effacer le signal de réveil sur le descripteur

de

fichier d'attente. En plus d'un descripteur de fichier, le code utilisateur peut également être notifié via un rappel. Le rappel et les pointeurs de données sont stockés dans le ASYNC_WAIT_CTX avec un champ de statut supplémentaire qui peut être utilisé pour la notification des nouvelles tentatives d'un moteur. Cette méthode supplémentaire peut être utilisée lorsque l'utilisateur pense qu'un descripteur de fichier est trop coûteux en termes de cycles CPU ou dans un contexte où

un

descripteur de fichier n'est pas approprié. ASYNC_WAIT_CTX_set_callback() définit le rappel et l'argument du rappel. Le rappel sera appelé pour notifier le code utilisateur lorsque un moteur termine une opération cryptographique. Il est une exigence que la fonction de rappel soit courte et non bloquante car elle sera exécutée dans le contexte d'un

mécanisme

d'interrogation ou d'une interruption. ASYNC_WAIT_CTX_get_callback() renvoie le rappel défini dans

la

Un exemple d'utilisation de la méthode de rappel pourrait être le suivant. Le code utilisateur initierait des opérations cryptographiques, et le code du moteur dispatcherait cette opération au matériel, et si le dispatch est réussi, le code du moteur appellerait ASYNC_pause_job() pour rendre le contrôle au code utilisateur. Après cela, le code utilisateur peut effectuer d'autres tâches.
