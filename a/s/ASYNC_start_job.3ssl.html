DESCRIPTIO

N

OpenSSL implémente les capacités asynchrones à travers un ASYNC_JOB. Cela représente du code qui peut être démarré et qui s'exécute jusqu'à ce qu'un certain événement se produise. À ce moment-là, le code peut être mis en pause et le contrôle est rendu au code utilisateur jusqu'à ce qu'un événement ultérieur indique que la tâche peut être reprise. C'est une implémentation spécifique à OpenSSL du multitâche

coopératif.

La création d'un ASYNC_JOB est une opération relativement coûteuse. Par conséquent, pour des raisons d'efficacité, les tâches peuvent être créées à l'avance et réutilisées de nombreuses fois. Elles sont conservées dans un pool jusqu'à ce qu'elles soient nécessaires, auquel cas elles sont retirées du pool, utilisées, puis retournées au pool lorsque la tâche est terminée. Si l'application utilisateur est multi-thread, alors ASYNC_init_thread() peut être appelé pour chaque thread qui initiéra des tâches asynchrones. Avant que le code utilisateur ne se termine, les ressources par thread doivent être nettoyées. Cela se produira normalement automatiquement (voir OPENSSL_init_crypto(3)) mais peut être explicitement initié en utilisant ASYNC_cleanup_thread(). Aucune tâche asynchrone ne doit être en attente pour le thread lorsque ASYNC_cleanup_thread() est appelé. Ne pas s'assurer de cela entraînera des fuites de

mémoire.

L'argument max_size limite le nombre de ASYNC_JOBs qui seront conservés dans le pool. Si max_size est défini à 0, alors aucune limite supérieure n'est définie. Lorsqu'un ASYNC_JOB est nécessaire mais qu'il n'y en a aucun de disponible dans le pool, un sera automatiquement créé, tant que le total des ASYNC_JOBs gérés par le pool ne dépasse pas max_size. Lorsque le pool est initialisé pour la première fois, init_size ASYNC_JOBs seront créés immédiatement. Si ASYNC_init_thread() n'est pas appelé avant que le pool ne soit utilisé pour la première fois, alors il sera automatiquement appelé avec un max_size de 0 (pas de limite supérieure) et un init_size de 0 (aucun ASYNC_JOBs créé à l'avance)

.

Une tâche asynchrone est démarrée en appelant la fonction ASYNC_start_job(). Initialement *job devrait être NULL. ctx devrait pointer vers un objet ASYNC_WAIT_CTX créé à travers la fonction ASYNC_WAIT_CTX_new(3). ret devrait pointer vers un emplacement où la valeur de retour de la fonction asynchrone devrait être stockée à la fin de la tâche. func représente la fonction qui devrait être démarrée de manière asynchrone. Les données pointées par args et de taille size seront copiées puis passées comme argument à func lorsque la tâche démarre. ASYNC_start_job retournera l'une des valeurs suivantes

:
ASYNC_E
RR
Une erreur s'est produite en essayant de démarrer la tâche. Vérifiez la file d'erreurs OpenSSL (par exemple, voir ERR_print_errors(3)) pour plus de
détails.
ASYNC_NO_JO
BS
Il n'y a actuellement aucune tâche disponible dans le pool. Cet appel peut être réessayé plus
tard.
ASYNC_PAU
SE
La tâche a été démarrée avec succès mais a été « mise en pause » avant de se terminer (voir ASYNC_pause_job() ci-dessous). Un descripteur de la tâche est placé dans *job. D'autres travaux peuvent être effectués (si désiré) et la tâche redémarrée plus tard. Pour redémarrer une tâche, appelez ASYNC_start_job() à nouveau en passant le descripteur de tâche dans *job. Les paramètres func, args et size seront ignorés lors du redémarrage d'une tâche. Lors du redémarrage d'une tâche, ASYNC_start_job() doit être appelé depuis le même thread que celui depuis lequel la tâche a été initialement démarrée. ASYNC_WAIT_CTX est utilisé pour savoir quand une tâche est prête à être
redémarrée.
ASYNC_FINI
SH
La tâche est terminée. *job sera NULL et la valeur de retour de func sera placée dans *r
et
.

À un moment donné, il peut y avoir au maximum une tâche activement en cours d'exécution par thread (vous pouvez en avoir beaucoup en pause). ASYNC_get_current_job() peut être utilisé pour obtenir un pointeur vers l' ASYNC_JOB actuellement en cours d'exécution. Si aucune tâche n'est actuellement en cours d'exécution, alors cela retournera

NULL.

Si vous exécutez dans le contexte d'une tâche (c'est-à-dire que vous avez été appelé directement ou indirectement par la fonction « func » passée comme argument à ASYNC_start_job()) alors ASYNC_pause_job() retournera immédiatement le contrôle à l'application appelante avec ASYNC_PAUSE retourné de l'appel ASYNC_start_job(). Un appel ultérieur à ASYNC_start_job en passant le ASYNC_JOB pertinent dans le paramètre *job reprendra l'exécution à partir de l'appel ASYNC_pause_job(). Si ASYNC_pause_job() est appelé alors que vous n'êtes pas dans le contexte d'une tâche, aucune action n'est entreprise et ASYNC_pause_job() retourne

immédiatement.

ASYNC_get_wait_ctx() peut être utilisé pour obtenir un pointeur vers le ASYNC_WAIT_CTX pour la tâche (voir ASYNC_WAIT_CTX_new(3)). Les ASYNC_WAIT_CTXs contiennent deux façons différentes de notifier aux applications qu'une tâche est prête à être reprise. L'une est un descripteur de fichier « wait » (attente), et l'autre est un mécanisme de « callback »

.

Le descripteur de fichier « wait » associé à ASYNC_WAIT_CTX est utilisé par les applications pour attendre que le descripteur de fichier soit prêt pour la « lecture » en utilisant un appel de fonction système tel que select(2) ou poll(2) (être prêt pour la « lecture » indique que la tâche devrait être reprise). Si aucun descripteur de fichier n'est mis à disposition, une application devra périodiquement « interroger » la tâche en essayant de la redémarrer pour voir si elle est prête à

continuer.

Les ASYNC_WAIT_CTXs ont aussi un mécanisme de « callback » pour notifier les applications. Le callback est défini par une application, et il sera automatiquement appelé lorsque le moteur termine une opération de cryptographie, afin que l'application puisse reprendre le flux de travail mis en pause sans interroger. Un moteur pourrait être écrit pour vérifier si le callback a été défini. Si c'est le cas, il utiliserait le mécanisme de callback de préférence aux notifications par descripteur de fichier. Si un callback n'est pas défini, le moteur peut utiliser des notifications basées sur le descripteur de fichier. Veuillez noter que tous les moteurs ne peuvent pas prendre en charge le mécanisme de callback, donc le callback peut ne pas être utilisé même s'il a été défini. Voir ASYNC_WAIT_CTX_new() pour plus de

détails.

La fonction ASYNC_block_pause() empêchera la tâche actuellement active de se mettre en pause. Le blocage restera en place jusqu'à un appel ultérieur à ASYNC_unblock_pause(). Ces fonctions peuvent être imbriquées, par exemple si vous appelez ASYNC_block_pause() deux fois, alors vous devez appeler ASYNC_unblock_pause() deux fois afin de réactiver la mise en pause. Si ces fonctions sont appelées alors qu'il n'y a pas de tâche actuellement active, elles n'ont aucun effet. Cette fonctionnalité peut être utile pour éviter des scénarios d'interblocage. Par exemple, pendant l'exécution d'un ASYNC_JOB, une application acquiert un verrou. Elle appelle ensuite une fonction cryptographique qui invoque ASYNC_pause_job(). Cela retourne le contrôle au code qui a créé le ASYNC_JOB. Si ce code tente ensuite d'acquérir le même verrou avant de reprendre la tâche originale, un interblocage peut se produire. En appelant ASYNC_block_pause() immédiatement après avoir acquis le verrou et ASYNC_unblock_pause() immédiatement avant de le relâcher, cette situation ne peut pas se

produire.

Certaines plateformes ne peuvent pas prendre en charge les opérations asynchrones. La fonction ASYNC_is_capable() peut être utilisée pour détecter si la plateforme actuelle est capable de gérer les opérations asynchrones.ou

non.

Des fonctions d'allocation mémoire personnalisées sont prises en charge pour la plateforme POSIX. Les fonctions d'allocation mémoire personnalisées permettent des méthodes alternatives pour allouer la mémoire de pile, telles que mmap, ou l'utilisation de la mémoire de pile du fil d'exécution courant. L'utilisation d'un rappel ASYNC_stack_alloc_fn permet également la manipulation de la taille de la pile, qui vaut par défaut 32k. La taille de la pile peut être modifiée en allouant une pile d'une taille différente de la taille demandée, et en renvoyant la nouvelle taille de la pile dans le *num du

rap
pel.

RETOUR

ASYNC_init_thread renvoie 1 en cas de succès, sinon

0.

ASYNC_start_job renvoie l'une des valeurs suivantes : ASYNC_ERR, ASYNC_NO_JOBS, ASYNC_PAUSE ou ASYNC_FINISH comme décrit

ci-dessus.

ASYNC_pause_job renvoie 0 si une erreur s'est produite, sinon 1 en cas de succès. Si elle est appelée alors que l'on n'est pas dans le contexte d'un ASYNC_JOB, cela est considéré comme un succès et 1 est

renvoyé.

ASYNC_get_current_job renvoie un pointeur vers le ASYNC_JOB en cours d'exécution, ou NULL si l'on n'est pas dans le contexte d'un

job.

ASYNC_get_wait_ctx() renvoie un pointeur vers le ASYNC_WAIT_CTX du

job.

ASYNC_is_capable() renvoie 1 si la plateforme courante est capable d'asynchrone, sinon

0.

ASYNC_set_mem_functions renvoie 1 si les allocateurs de pile

personnalisés sont pris en charge par la plateforme cour
ante et qu'aucune allocation n'a encore eu lieu, sinon 0.

NOTE

S

Sur les plateformes Windows, l'en-tête <openssl/async.h> dépend de certains types habituellement rendus disponibles en incluant <windows.h>. Le développeur de l'application souhaitera probablement contrôler le moment où ce dernier est inclus, généralement comme l'un des premiers en-têtes inclus. Par conséquent, il est de la responsabilité du développeur de l'application d'inclure <windows.h> avant <openssl/

async
.h>.

EXEMPLE

S

L'exemple suivant montre comment utiliser la plupart des API asynchrones principales

: 
#ifdef _WIN32
# include <windows.h>
#endif
#include <stdio.h>
#include <unistd.h>
#include <openssl/async.h>
#include <openssl/crypto.h>
int unique = 0;
void cleanup(ASYNC_WAIT_CTX *ctx, const void *key, OSSL_ASYNC_FD r, void *vw)
{
    OSSL_ASYNC_FD *w = (OSSL_ASYNC_FD *)vw;
    close(r);
    close(*w);
    OPENSSL_free(w);
}
int jobfunc(void *arg)
{
    ASYNC_JOB *currjob;
    unsigned char *msg;
    int pipefds[2] = {0, 0};
    OSSL_ASYNC_FD *wptr;
    char buf = 'X';
    currjob = ASYNC_get_current_job();
    if (currjob != NULL) {
        printf("Executing within a job\n");
    } else {
        printf("Not executing within a job - should not happen\n");
        return 0;
    }
    msg = (unsigned char *)arg;
    printf("Passed in message is: %s\n", msg);
    /*
     * Create a way to inform the calling thread when this job is ready
     * to resume, in this example we're using file descriptors.
     * For offloading the task to an asynchronous ENGINE it's not necessary,
     * the ENGINE should handle that internally.
     */
    if (pipe(pipefds) != 0) {
        printf("Failed to create pipe\n");
        return 0;
    }
    wptr = OPENSSL_malloc(sizeof(OSSL_ASYNC_FD));
    if (wptr == NULL) {
        printf("Failed to malloc\n");
        return 0;
    }
    *wptr = pipefds[1];
    ASYNC_WAIT_CTX_set_wait_fd(ASYNC_get_wait_ctx(currjob), &unique,
                               pipefds[0], wptr, cleanup);
    /*
     * Normally some external event (like a network read being ready,
     * disk access being finished, or some hardware offload operation
     * completing) would cause this to happen at some
     * later point - but we do it here for demo purposes, i.e.
     * immediately signalling that the job is ready to be woken up after
     * we return to main via ASYNC_pause_job().
     */
    write(pipefds[1], &buf, 1);
    /*
     * Return control back to main just before calling a blocking
     * method. The main thread will wait until pipefds[0] is ready
     * for reading before returning control to this thread.
     */
    ASYNC_pause_job();
    /* Perform the blocking call (it won't block with this example code) */
    read(pipefds[0], &buf, 1);
    printf ("Resumed the job after a pause\n");
    return 1;
}
int main(void)
{
    ASYNC_JOB *job = NULL;
    ASYNC_WAIT_CTX *ctx = NULL;
    int ret;
    OSSL_ASYNC_FD waitfd;
    fd_set waitfdset;
    size_t numfds;
    unsigned char msg[13] = "Hello world!";
    printf("Starting...\n");
    ctx = ASYNC_WAIT_CTX_new();
    if (ctx == NULL) {
        printf("Failed to create ASYNC_WAIT_CTX\n");
        abort();
    }
    for (;;) {
        switch (ASYNC_start_job(&job, ctx, &ret, jobfunc, msg, sizeof(msg))) {
        case ASYNC_ERR:
        case ASYNC_NO_JOBS:
            printf("An error occurred\n");
            goto end;
        case ASYNC_PAUSE:
            printf("Job was paused\n");
            break;
        case ASYNC_FINISH:
            printf("Job finished with return value %d\n", ret);
            goto end;
        }
        /* Get the file descriptor we can use to wait for the job
         * to be ready to be woken up
         */
        printf("Waiting for the job to be woken up\n");
        if (!ASYNC_WAIT_CTX_get_all_fds(ctx, NULL, &numfds)
                || numfds > 1) {
            printf("Unexpected number of fds\n");
            abort();
        }
        ASYNC_WAIT_CTX_get_all_fds(ctx, &waitfd, &numfds);
        FD_ZERO(&waitfdset);
        FD_SET(waitfd, &waitfdset);
        /* Wait for the job to be ready for wakeup */
        select(waitfd + 1, &waitfdset, NULL, NULL, NULL);
    }
end:
    ASYNC_WAIT_CTX_free(ctx);
    printf("Finishing\n");
    return 0;
}
