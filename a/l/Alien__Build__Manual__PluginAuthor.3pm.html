Code pseudo Perl montrant comment les plugins sont appelés

: 
my $probe;
my $override = override();

if($override eq 'system') {

  $probe = probe();

  if($probe ne 'system') {
    die 'system tool or library not found';
  }

}

elsif($override eq 'default') {
  $probe = probe();

} else { # $override eq 'share'
  # notez que dans ce cas-ci, le
  # hook probe n'est jamais appelé
  $probe = 'share';
}

if($probe eq 'system') {
  gather_system();

} else { # $probe eq 'share'

  download();
  extract();
  patch();
  build();
  gather_share();

  # Vérifiez s'il existe un hook build_ffi
  if(defined &build_ffi) {
    patch_ffi();
    build_ffi();
    gather_ffi();
  }
}

# Par défaut, ceci renvoie simplement la valeur de $ENV{ALIEN_INSTALL_TYPE}
sub override {
  return $ENV{ALIEN_INSTALL_TYPE};
}

# Implémentation par défaut de download ; peut être
# remplacée en spécifiant un hook download
# différent. Voir Alien::Build::Plugin::Core::Download
# pour l'implémentation détaillée.
sub download {

  my $response = fetch();

  if($response->{type} eq 'html' || $response->{type} eq 'dir_listing') {
    # decode transformera un listage HTML (html) ou un listage de
    # répertoire FTP (dir_listing) en une liste régulière
    $response = decode($response);
  }

  if($response->{type} eq 'list') {

    # prefer filtrera les mauvaises entrées de la liste
    # et les triera de sorte que la première soit
    # celle que nous voulons
    $response = prefer($response);

    my $first_preferred = $res->{list}->[0];

    # prefer peut parfois inférer la version à partir du
    # nom de fichier.
    if(defined $first_preferred->{version}) {
      # pas un hook
      runtime_prop->{version} = $first_preferred->{version};
    }

    $response = fetch($first_preferred);

  }

  if($response->{type} eq 'file') {
    # pas un hook
    write_file_to_disk $response;
  }
}

DESCRIPTIO

N

Ce document explique comment écrire des plugins Alien::Build en utilisant la classe de base Alien::Build::

Plugin.

Écrire des

plugins

Les plugins utilisent Alien::Build::Plugin, qui définit la classe de base appropriée et vous fournit le constructeur de propriétés "has". "has" prend deux arguments, le nom de la propriété et la valeur par défaut. (Comme avec Moose et Moo, vous devriez utiliser une référence de code pour spécifier les valeurs par défaut non chaînes). Non définissez ceci comme classe de base de votre plugin directement

: 
use parent qw( Alien::Build::Plugin );  # incorrect
use Alien::Build::Plugin;               #
correct

La seule méthode que vous devez implémenter est "init". Depuis cette méthode, vous pouvez ajouter des hooks pour modifier le comportement de la recette alienfile. Voici un exemple très simple d'un hook probe, avec la logique de probe réelle supprimée

: 
sub init
{
  my($self, $meta) = @_;
  $meta->register_hook(
    probe => sub {
      my($build) = @_;
      if( ... )
      {
        return 'system';
      }
      else
      {
        return 'share';
      }
    },
  );
}

Les hooks reçoivent l'instance Alien::Build comme premier argument et, selon le hook, peuvent recevoir des arguments

supplémentaires
.

Modifier des

hooks

Vous pouvez aussi modifier des hooks en utilisant "before_hook", "around_hook" et "after_hook", de manière similaire aux modificateurs de Moose

: 
sub init
{
  my($self, $meta) = @_;

  $meta->before_hook(
    build => sub {
      my($build) = @_;
      $build->log('this runs before the build');
    },
  );

  $meta->after_hook(
    build => sub {
      my($build) = @_;
      $build->log('this runs after the build');
    },
  );

  $meta->around_hook(
    build => sub {
      my $orig = shift;

      # Les hooks around sont utiles pour définir des variables d'environnement
      local $ENV{CPPFLAGS} = '-I/foo/include';

      $orig->(@_);
    },
  );
}

Tester des

plugins

Vous pouvez et devriez écrire des tests pour votre plugin. La meilleure façon de le faire est d'utiliser Test::Alien::Build, qui vous permet d'écrire un alienfile en ligne dans votre test. Voici un exemple

: 
use Test::V0;
use Test::Alien::Build;

my $build = alienfile_ok q{
  use alienfile;
  plugin 'Build::MyPlugin' => (
    arg1
=> 'override for arg1', arg2 => [ 'something', 'else' ], ); ... }; # vous pouvez interroger $build, c'est une insta
nce de L<Alien::Build>. my $alien = alien_build_ok; # vous pouvez interroger $alien, c'est une instance de L<Alien::Base>.

Plugins

négociateurs

Un plugin négociateur n'implémente généralement rien par lui-même, mais choisit le meilleur plugin pour atteindre un objectif

particulier.

Le plugin « meilleur » peut dans certains cas varier selon la plateforme ou les outils disponibles. Par exemple, le négociateur de téléchargement pourrait choisir d'utiliser le plugin fetch qui repose sur la commande en ligne "curl", ou il pourrait choisir le plugin fetch qui repose sur le module Perl HTTP::Tiny selon la plateforme et ce qui est déjà installé. (Pour que l'un ou l'autre soit utile, ils doivent prendre en charge SSL)

.

Le plugin négociateur est par convention nommé quelque chose comme "Alien::Build::Plugin::*::Negotiate", mais est généralement invoqué sans le suffixe "::Negotiate". Par exemple

: 
plugin 'Download'; # est une abréviation pour Alien::Build::Plugin::Download::
Negotiator

Voici un exemple simple d'un négociateur qui choisit "curl" s'il est déjà installé et HTTP::Tiny sinon. (Le plugin de téléchargement réel est beaucoup plus intelligent et complexe que ceci, mais c'est un bon exemple simplifié)

. 
package Alien::Build::Plugin::Download::Negotiate;

use strict;
use warnings;
use Alien::Build::Plugin;
use File::Which qw( which );

sub init
{
  my($self, $meta) = @_;

  if(which('curl')) {
    $meta->apply_plugin('Fetch::Curl');
  } else {
    $meta->apply_plugin('Fetch::HTTPTiny');
  }
}

Hook

s

Le reste de ce document est une référence pour les hooks que vous pouvez enregistrer. En général, vous pouvez enregistrer n'importe que

l hook que vous voulez, mais certaines précautions doivent être prises car certains hooks ont un comportement par défaut qui sera r
emplacé lorsque vous enregistrez un hook. Les hooks sont présentés dans l'ordre alphabétique. L'ordre d'exécution est montré dans l
e diagramme de flux ci-dessus (si vous parcourez la version HTML de ce document), ou dans le code pseudo Perl de la section résumé.

HOOK

S

Hook

build 
$meta->register_hook( build => sub {
  my($build) = @_;
  ...
})
;

Cela effectue la construction principale du projet alienisé et l'installe dans l'espace de staging. Le répertoire courant est la racine de construction. Vous devez exécuter les outils nécessaires pour le projet et les installer dans "$build-"install_prop->{prefix}> ("%{.install

.pref
ix}").

Hook

build_ffi 
$meta->register_hook( build_ffi => sub {
  my($build) = @_;
  ...
})
;

C'est la même chose que build,

sauf qu'il ne se déclenche que
lors d'une construction FFI.

Hook

decode 
$meta->register_hook( decode => sub {
  my($build, $res) = @_;
  ...
}

Ce hook prend une référence de hachage de réponse du "fetch" hook ci-dessus avec un type de "html" ou "dir_listing" et la convertit en une référence de hachage de réponse de type "list". En somme, il prend une réponse de répertoire HTML ou FTP d'un hook fetch et la convertit en une liste de noms de fichiers et de liens qui peut être

utilisée par le hook prefer pour choisir le bon fichier à télécharger. Voir le ho
ok fetch pour la spécification des références de hachage d'entrée et de réponse.

check_digest

hook 
# implémenter le digest FOO-92 bien connu
$meta->register_hook( check_digest => sub {
  my($build, $file, $algorithm, $digest) = @_;
  if($algorithm ne 'FOO92') {
    return 0;
  }
  my $actual = foo92_hex_digest($file);
  if($actual eq $digest) {
    return 1;
  } else {
    die "Digest FOO92 does not match: got $actual, expected $digest";
  }
})
;

Ce hook doit vérifier que le $file donné (le format est le même que celui utilisé par le hook fetch) correspond au $digest donné en utilisant l' $algorithm donné. Si le plugin ne prend pas en charge l'algorithme donné, il doit retourner une valeur fausse. Si le d

igest ne correspond pas, il doit lever une exception. Si
le digest correspond, il doit retourner une valeur vraie.

clean_instal

l 
$meta->register_hook( clean_install => sub {
  my($build) = @_;
})
;

Ce hook vous permet de supprimer des fichiers de l'emplacement d'installation final avant que les fichiers ne soient installés par la couche d'installation (exemples : Alien::Build::MM, Alien::Build::MB ou App::af). Ce hook n'est pas appelé par défaut et doit être activé via l'interface de la couche d'installation (exemple : "clean_install" dans Alien::Build::MM)

.

Ce hook NE DOIT PAS supprimer le répertoire "_alien" ou son contenu de l'emplacement

d'installation.

L'implémentation par défaut supprime tous les fichiers SAUF le répertoire "_alien

" et son
contenu.

download

hook 
$meta->register_hook( download => sub {
  my($build) = @_;
  ...
})
;

Ce hook est utilisé pour télécharger la source depuis Internet. Soit sous forme d'archive (comme tar, zip, etc.), soit sous forme d'un répertoire de fichiers ("git clone", etc). Lorsque le hook est appelé, le répertoire de travail courant sera un nouveau répertoire vide, vous pouvez donc enregistrer le téléchargement dans le répertoire courant. Si vous enregistrez un seul fichier dans le répertoire, Alien::Build supposera qu'il s'agit d'une archive, qui sera traitée par le hook extract. Si vous enregistrez plusieurs fichiers, Alien::Build supposera que le répertoire courant est la racine de la source. Si aucun fichier n'est enregistré du tout, une exception avec un diagnostic approprié sera

levée.

Remarque : Si vous enregistrez ce hook, alors les hooks fetch, decode et prefer

NE SERONT PAS appelés, à moins que vous ne
les appeliez vous-même depuis ce hook.

extract

hook 
$meta->register_hook( extract => sub {
  my($build, $archive) = @_;
  ...
})
;

Ce hook est utilisé pour extraire une archive qui a déjà été téléchargée. Alien::Build a déjà des plugins pour les formats d'archives les plus courants, vous n'aurez donc probablement besoin de ceci que pour ajouter la prise en charge de nouveaux formats d'archives ou de formats inhabituels. Lorsque ce hook est appelé

, le répertoire de travail courant sera un nouveau répertoire vide, vous pouvez donc enregistrer le contenu de l'archive dans le répertoire courant. Si un seul répertoire est écrit dans le répertoire courant, Alien::Build supposera qu'il s'agit du répertoire racine du paquet. Si plusieurs fichiers et/ou répertoires so
nt présents, cela indiquera que le répertoire de travail courant est la racine du paquet. La logique gère généralement correctement le comportement par défaut pour tar (où les paquets sont généralement extraits dans un sous-répertoire) et pour zip (où les paquets sont généralement extraits dans le répertoire courant).

fetch

hook 
package Alien::Build::Plugin::MyPlugin;

use strict;
use warnings;
use Alien::Build::Plugin;
use Carp ();

has '+url' => sub { Carp::croak "url is required property" };

sub init
{
  my($self, $meta) = @_;

  $meta->register_hook( fetch => sub {
    my($build, $url, %options) = @_;
    ...
  }
}
1;

Utilisé pour récupérer une ressource. La première fois, il sera appelé sans argument (ou avec $url défini à "undef", la configuration utilisée pour trouver la ressource devrait donc être spécifiée par les propriétés du plugin. Lors des appels suivants, le premier argument sera une

URL.

Le hachage %options peut contenir ces options

:
http_heade
rs
En-têtes de requête HTTP, si un protocole approprié est utilisé. Les en-têtes sont fournis sous forme d'une référence de tableau de paires clé/valeur, ce qui permet d'avoir des clés d'en-tête dupliquées avec plusieurs valeurs.

Si un protocole non-HTTP est utilisé, ou si le plugin ne peut pas autrement envoyer d'en-têtes de requête HTTP, le plugin DEVRAIT émettre un avertissement en utilisant la méthode "$build->log", mais parce que cette option ne faisait pas part

ie de la spécification original
e, le plugin PEUT ne pas émettre cet av
ertissement tout en l'ignorant.

Notez que les versions d'Alien::Build antérieures à 2.39 ne passaient pas le hachage d'options au plugin

fetch.

Normalement, le premier fetch sera soit vers un fichier, soit vers un répertoire. S'il s'agit d'un fichier, le contenu doit être retourné sous forme d'une référence de hachage avec les clés suivantes

: 
# contenu du fichier stocké en Perl
return {
  type     => 'file',
  filename => $filename,
  content  => $content,
  version  => $version,  # optionnel, si connu
  protocol => $protocol, # AB 2.60 optionnel, mais recommandé
};

# contenu du fichier stocké dans le système de fichiers
return {
  type     => 'file',
  filename => $filename,
  path     => $path,     # chemin complet du système de fichiers vers le fichier
  version  => $version,  # optionnel, si connu
  tmp      => $tmp,      # optionnel
  protocol => $protocol, # AB 2.60 optionnel, mais recommandé
}
;

$tmp s'il est défini indiquera si le fichier est temporaire ou non, et peut être utilisé par Alien::Build pour enregistrer une copie dans certains cas. La valeur par défaut est vraie, Alien::Build suppose donc que le fichier ou le répertoire est temporaire si vous ne lui dites pas le contraire. La situation la plus courante où vous définiriez "tmp" à faux est lorsque le fichier est inclus dans la distribution Alien. Voir Alien::Build::Plugin::Fetch::Local par

exemple.

Si l'URL pointe vers un répertoire, vous devez le retourner soit sous forme d'une référence de hachage contenant une liste de fichiers

: 
return {
  type => 'list',
  list => [
    # filename : chaque nom de fichier ne doit être que la
    #   partie nom de fichier, sans chemin ni url.
    # url : chaque url doit être l'url complète
    #   nécessaire pour récupérer le fichier.
    # version : OPTIONNEL, peut être fourni par certains hooks fetch ou prefer
    { filename => $filename1, url => $url1, version => $version1 },
    { filename => $filename2, url => $url2, version => $version2 },
  ],
  protocol => $protocol, # AB 2.60 optionnel, mais recommandé
}
;

ou si la liste est au format HTML, sous forme d'une référence de hachage contenant les informations HTML

: 
return {
  type => 'html',
  charset  => $charset, # optionnel
  base     => $base,    # l'URL de base : utilisée pour calculer les URLs relatives
  content  => $content, # le contenu HTML
  protocol => $protocol, # optionnel, mais recommandé
}
;

ou un répertoire (généralement produit par des serveurs FTP) sous forme d'une référence de hachage

: 
return {
  type     => 'dir_listing',
  base     => $base,
  content  => $content,
  protocol => $protocol, # AB 2.60 optionnel, mais recommandé
}
;

[version 2.

60]

Pour toutes ces réponses, $protocol est optionnel, car il ne faisait pas partie de la spécification originale, cependant il est fortement recommandé d'inclure ce champ, car les futures versions d'Alien::Build l'utiliseront pour déterminer si un fichier a été téléchargé de manière sécurisée (c'est-à-dire via un protocole sécurisé comme SSL)

.

Certains plugins (comme les plugins decode) transforment un hachage de fichier d'un type à un autre, ils doivent maintenir le $protocol de l'ancienne vers la nouv

elle représentati
on du fichier.

gather_ffi

hook 
$meta->register_hook( gather_ffi => sub {
  my($build) = @_;
  $build->runtime_prop->{cflags}  = ...;
  $build->runtime_prop->{libs}    = ...;
  $build->runtime_prop->{version} = ...;
})
;

Ce hook est appelé pour une construction FFI afin de déterminer les propriétés nécessaires pour utiliser la bibliothèque ou l'outil. Ces

propriétés doivent être stockées dans le hachage runtime_prop comme montré ci-dessus. Les propriétés typiques nécessaires pour les bib
liothèques sont cflags et libs. Si possible, vous devriez également essayer de déterminer la version de la bibliothèque ou de l'outil.

gather_share

hook 
$meta->register_hook( gather_share => sub {
  my($build) = @_;
  $build->runtime_prop->{cflags}  = ...;
  $build->runtime_prop->{libs}    = ...;
  $build->runtime_prop->{version} = ...;
})
;

Ce hook est appelé pour une installation share afin de déterminer les propriétés nécessaires pour utiliser la bibliothèque ou l'outil. Ces

propriétés doivent être stockées dans le hachage runtime_prop comme montré ci-dessus. Les propriétés typiques nécessaires pour les bib
liothèques sont cflags et libs. Si possible, vous devriez également essayer de déterminer la version de la bibliothèque ou de l'outil.

gather_system

hook 
$meta->register_hook( gather_system => sub {
  my($build) = @_;
  $build->runtime_prop->{cflags}  = ...;
  $build->runtime_prop->{libs}    = ...;
  $build->runtime_prop->{version} = ...;
})
;

Ce hook est appelé pour une installation système afin de déterminer les propriétés nécessaires pour utiliser la bibliothèque ou l'outil. Ce

s propriétés doivent être stockées dans le hachage runtime_prop comme montré ci-dessus. Les propriétés typiques nécessaires pour les bi
bliothèques sont cflags et libs. Si possible, vous devriez également essayer de déterminer la version de la bibliothèque ou de l'outil.

override

hook 
$meta->register_hook( override => sub {
  my($build) = @_;
  return $ENV{ALIEN_INSTALL_TYPE} || '';
})
;

Cela vous permet de modifier la logique de surcharge. Elle doit retourner l'une des valeurs "share", "system", "default" ou ''. L'implémentation par défaut est montrée ci-dessus. Alien::Build::Plugin::Probe::Override et A

lien::Build::Plugin::Probe::OverrideCI sont des exemple
s de la manière dont vous pouvez utiliser ce hook.

patch

hook 
$meta->register_hook( patch => sub {
  my($build) = @_;
  ...
})
;

Ce hook est complètement optionnel. S'il est enregistré, il sera déclenché a

près l'extraction et avant la construction. Il vous permet d'appliquer des c
orrectifs ou d'apporter des modifications aux sources si elles sont nécessaires.

patch_ffi

hook 
$meta->register_hook( patch_ffi => sub {
  my($build) = @_;
  ...
})
;

Ce hook est exactement comme le hook

patch, sauf qu'il ne se déclenche
que lors d'une construction FFI.

prefer

hook 
$meta->register_hook( prefer => sub {
  my($build, $res) = @_;
  return {
    type => 'list',
    list => [sort @{ $res->{list} }],
  };
}

Ce hook trie les candidats à partir d'une liste générée soit par le hook "fetch" soit par le hook "decode". Il doit retourner une nouvelle référence de hachage de liste avec les candidats

triés du meilleur au pire. Il peut également
supprimer les candidats totalement inacceptables.

probe

hook 
$meta->register_hook( probe => sub {
  my($build) = @_;
  return 'system' if ...; # system install
  return 'share';         # otherwise
});

$meta->register_hook( probe => [ $command ] )
;

Ce hook doit retourner la chaîne "system" si le système d'exploitation fournit la bibliothèque ou l'outil. Il doit retourner "share" s

inon.

Vous pouvez également utiliser une commande qui retourne vrai lorsque l'outil ou la bibliothèque est disponible. Par exemple pour une utilisation avec "pkg-conf

ig" : 
$meta->register_hook( probe =>
  [ '%{pkgconf} --exists libfoo' ] )
;

Ou si vous aviez besoin d'une version minimale

: 
$meta->register_hook( probe =>
  [ '%{pkgconf} --atleast-version=1.00 libfoo' ] )
;

Notez que ce hook NE DOIT PAS collecter les propriétés du système, telles que cflags, libs, versions, etc., car le hook probe sera ignoré si la variable d'environnement "ALIEN_INSTALL_TYPE" est définie. La détection de ces propriétés devrait plutôt être effectuée par le hook

gather_system.

Plusieurs hooks probe peuvent être d

onnés. Ils seront utilisés en séque
nce, en s'arrêtant au premier q
ui détecte une installation système.
