NOM

package source - données de source locale ou distante utilisées pour construire un paquet basé sur ALPM.

DESCRIPTION

Les paquets basés sur ALPM peuvent être construits en utilisant zéro ou plusieurs sources locales et/ou distantes. En général, les sources de paquet sont indépendantes de l'architecture, mais peuvent être spécifiées de manière spécifique à l'architecture.

Dans les fichiers PKGBUILD , une source de paquet est définie en ajoutant une entrée au tableau source . Alternativement, un tableau nommé source, directement suivi d'un caractère de soulignement (« _ »), directement suivi d'une alpm-architecture (toutes sauf any) - peut être utilisé pour définir une source pour une architecture spécifique (par ex. source_aarch64).

Dans les fichiers SRCINFO , une source de paquet est définie en assignant une valeur au mot-clé source . Alternativement, un mot-clé spécifique à l'architecture nommé source, directement suivi d'un caractère de soulignement (« _ »), directement suivi d'une alpm-architecture (toutes sauf any) peut être utilisé (par ex. source_aarch64).

Locale

Les sources locales sont définies en utilisant des chemins de fichiers relatifs (par ex. my-file.txt).

Lorsqu'on ne spécifie pas d' hôte tout en utilisant le schéma file URI , il est possible d'utiliser des fichiers avec des chemins absolus sur l'hôte courant (par ex. file:///etc/passwd). Cependant, ceci est fortement déconseillé, car avec cette méthode les fichiers sources utilisés pour le packaging peuvent changer de manière arbitraire. Lors du packaging, il est plutôt conseillé de s'appuyer sur les chemins relatifs de fichiers situés au même endroit qu'un PKGBUILD. De cette façon, tous les fichiers sources locaux peuvent être suivis dans un système de contrôle de version (VCS).

Distante

Les sources distantes peuvent être récupérées en utilisant divers protocoles, tous définis à l'aide de chaînes URL [2] valides (par ex. https://example.com/project-1.0.0.tar.gz). En dehors des protocoles pour les sources distantes statiques (par ex. https), plusieurs protocoles VCS tels que bzr, fossil, git, hg et svn sont compris et peuvent être utilisés pour récupérer des versions spécifiques de sources distantes.

Par défaut, le nom de l'objet distant définit le nom final de la source locale (par ex. https://example.com/project-1.0.0.tar.gz correspond à project-1.0.0.tar.gz et git+https://example.org/repo#tag=1.0.0 à repo/ - voir renaming pour plus de détails).

Les protocoles VCS exposent des fonctionnalités optionnelles différentes pour récupérer du contenu distant spécifique. Cette fonctionnalité est accessible en utilisant des fragments d'URL dans l'URL source.

bzr

En utilisant bzr, il est possible de s'appuyer sur des identifiants de révision (voir bzr help revisionspec) en utilisant le fragment revision d'URL, par ex. :

•
bzr+https://example.org/trunk#revision=123

fossil

En utilisant fossil, il est possible de s'appuyer sur des identifiants de branche, de commit et de tag en utilisant les fragments branch, commit et tag d'URL, respectivement, par ex. :

  • fossil+https://example.org/repo#branch=my-branch
  • fossil+https://example.org/repo#commit=b5bb9d8014a0f9b1d61e21e796d78dccdf1352f23cd32812f4850b878ae4944c
  • fossil+https://example.org/repo#tag=1.0.0

git

En utilisant git, il est possible de s'appuyer sur des identifiants de branche, de commit et de tag en utilisant les fragments branch, commit et tag d'URL, respectivement, par ex. :

  • git+https://example.org/repo#branch=my-branch
  • git+https://example.org/repo#commit=f1d2d2f924e986ac86fdf7b36c94bcdf32beec15
  • git+https://example.org/repo#tag=1.0.0

hg

En utilisant hg, il est possible de s'appuyer sur des identifiants de branche, de révision et de tag en utilisant les fragments branch, revision et tag d'URL, respectivement, par ex. :

  • hg+https://example.org/repo#branch=my-branch
  • hg+https://example.org/repo#revision=f1d2d2f924e986ac86fdf7b36c94bcdf32beec15
  • hg+https://example.org/repo#tag=1.0.0

svn

En utilisant svn, il est possible de s'appuyer sur l'identifiant de révision en utilisant le fragment revision d'URL, par ex. :

•
svn+https://example.org/repo#revision=r123

Vérification de signature

La vérification de signature OpenPGP [3] est prise en charge lors de l'utilisation de certains types de sources de paquet. Pour qu'un logiciel de construction de paquet qui s'appuie sur un fichier PKGBUILD soit capable de vérifier une signature basée sur un certificat OpenPGP, il doit y avoir au moins une entrée dans son tableau validpgpkeys . De manière analogue, si un logiciel s'appuie sur un fichier SRCINFO , il doit avoir au moins une affectation de mot-clé validpgpkeys présente pour que la vérification de signature soit possible. Dans les deux cas, la vérification de signature OpenPGP [3] est tentée sur la base de certificats OpenPGP [4] qui correspondent aux empreintes OpenPGP [5] exposées dans validpgpkeys.

Une paire de sources locales ou distantes statiques, qui définissent un fichier et un fichier de signature détachée accompagnant (par ex. example-1.0.0.tar.gz avec example-1.0.0.tar.gz.sig, ou example-1.0.0.tar.gz avec example-1.0.0.tar.gz.asc, ou example-1.0.0.tar.gz avec example-1.0.0.tar.sign) sont une indication du besoin d'une vérification de signature OpenPGP.

Si des signatures OpenPGP sont disponibles dans une source distante basée sur git , le besoin (optionnel) de vérification de signature OpenPGP [3] des objets git peut être indiqué en utilisant le composant de requête signed d'URL (par ex. git+https://example.org/repo?signed#tag=1.0.0 pour vérifier un tag git spécifique, ou git+https://example.org/repo?signed#commit=f1d2d2f924e986ac86fdf7b36c94bcdf32beec15 pour vérifier un commit spécifique).

Si une vérification de signature OpenPGP [2] est demandée, le processus qui vérifie la source du paquet doit échouer si

  • un ou plusieurs certificats OpenPGP correspondant à une empreinte dans validpgpkeys ne sont pas disponibles,
  • le certificat OpenPGP utilisé pour la vérification de la source du paquet est révoqué au moment de la création de la signature,
  • le certificat OpenPGP utilisé pour la vérification de la source du paquet est expiré au moment de la création de la signature,
  • ou la source du paquet

    NAME

    alpm-package-source - alpm package source format

    DESCRIPTION

    This document describes the source files format for packages managed by pacman(8) and makepkg(8).

    Package build software typically reads a PKGBUILD file, which is a shell script that defines how a package is built. For certain build systems, a SRCINFO file may be generated from the PKGBUILD, containing package metadata in a machine-readable format.

    Both files define package metadata and package sources. Sources can be local files or remote URLs. Remote sources can be downloaded using protocols like HTTP(S), FTP, Git, Mercurial, etc.

    Sources

    The source array in PKGBUILD and SRCINFO files is used to list package sources. Sources can be local files or remote URLs. Sources are downloaded or accessed in the order they appear in the array.

    • Local files must be present in the build directory.
    • Remote URLs can use various protocols, including HTTP(S), FTP, Git, Mercurial, Subversion, etc. The appropriate helper program is used to download or access the source.

    • For VCS sources (e.g., Git), you can specify a branch, tag, or commit hash using URL parameters. For example: git+https://example.com/repo.git#tag=v1.0.0 or git+https://example.com/repo.git#branch=develop. A ?signed parameter can be appended to VCS URLs to request signature verification.

    OpenPGP signature verification

    For remote sources, OpenPGP signature verification can be enabled. This requires a detached signature file (e.g., source.tar.gz.sig) to be present alongside the source file, or for the source URL itself to indicate signature verification is required (e.g., VCS URLs with a ?signed parameter).

    The validpgpkeys array in PKGBUILD and SRCINFO files lists the fingerprints of OpenPGP keys that are trusted to sign the package sources. The signature will only be considered valid if it can be verified by one of the keys listed in validpgpkeys.

    If a source requires signature verification, but no detached signature is found or the signature is invalid, the build will fail. Note that this check cannot be performed for all source types, e.g. it is not possible for Git sources.

    If the signature check fails, the message will indicate that the source cannot be verified with any of the OpenPGP certificates pinned by fingerprint in validpgpkeys.

    Renaming

    In PKGBUILD and SRCINFO files, remote sources can be renamed. Using a target name, directly followed by ‘::’, directly followed by the remote source name (e.g. source-1.0.0.tar.gz::https://example.com/1.0.0.tar.gz or project::git+https://git.example.com/project.git).

    The renaming functionality differs between static protocols (e.g. https) and VCS protocols (e.g. git): In the former case the target name is a file and in the latter a directory (e.g. project-1.0.0.tar.gz::https://example.org/project-v1.0.0.tar.gz renames to the file project-1.0.0.tar.gz while other-name::git+https://example.org/repo#tag=v1.0.0 renames to the directory other-name/).

    Extraction

    By default, local and remote sources are automatically extracted by package build software such as makepkg, if (after renaming) the final source file name ending matches a known extension (e.g. .tar.gz).

    In PKGBUILD files a final source file name from the source array can be added to the noextract array to indicate that the automatic extraction should be prevented for the given file.

    In SRCINFO files a final source file name can be defined using the noextract keyword to indicate, that the automatic extraction should be prevented for the given file.

    EXAMPLES

    Sources locales et distantes statiques avec renommage

    pkgname=example
pkgver=0.1.0
pkgrel=1
pkgdesc="Un exemple de paquet"
arch=(x86_64)
url="https://example.org"
license=(GPL-3.0-or-later)
makedepends=(meson)
depends=(
  gcc-libs
  glibc
)
noextract=(custom-data.tar.gz)
source=(
  test.service
  custom-data.tar.gz{,.sig}
  $pkgname-$pkgver.tar.gz::https://download.example.org/$pkgname-v$pkgver.tar.gz
)
sha256sums=(
  b5bb9d8014a0f9b1d61e21e796d78dccdf1352f23cd32812f4850b878ae4944c
  7d865e959b2466918c9863afca942d0fb89d7c9ac0c99bafc3749504ded97730
  bf07a7fbb825fc0aae7bf4a1177b2b31fcf8a3feeaf7092761e18c859ee52a9c
  d18eca2e2e57e58a47e7dc15000d57f5180e7db9bb2a412ab2449637ab3ce3ff
)
validpgpkeys=(6d96270004515a0486bb7f76196a72b40c55a47f)
build() {
  meson setup --prefix /usr $pkgname-$pkgver build
  meson compile -C build
}
package(){
  meson install -C build --destdir "$pkgdir"
  install -vDm 644 test.service -t "$pkgname/usr/lib/systemd/system/"
  install -vDm 644 custom-data.tar.gz -t "$pkgname/usr/share/$pkgname/"
}

    Le PKGBUILD ci-dessus définit une configuration de source de paquet, dans laquelle la source distante est renommée et une source locale compressée n'est pas extraite mais utilisée telle quelle. De plus, la source locale custom-data.tar.gz est vérifiée à l'aide du fichier de signature détachée (supposé) custom-data.tar.gz.sig en utilisant la vérification de signature OpenPGP avec un certificat dont l'empreinte est 6d96270004515a0486bb7f76196a72b40c55a47f. Le fichier SRCINFO suivant est généré à partir du PKGBUILD:

    pkgbase = example
  pkgdesc = Un exemple de paquet
  pkgver = 0.1.0
  pkgrel = 1
  url = https://example.org

  makedepends = meson

  depends = glibc
  noextract = custom-data.tar.gz
  source = test.service
  source = custom-data.tar.gz
  source = custom-data.tar.gz.sig
  source = example-0.1.0.tar.gz::https://download.example.org/example-v0.1.0.tar.gz
  validpgpkeys = 6d96270004515a0486bb7f76196a72b40c55a47f
  sha256sums = b5bb9d8014a0f9b1d61e21e796d78dccdf1352f23cd32812f4850b878ae4944c
  sha256sums = 7d865e959b2466918c9863afca942d0fb89d7c9ac0c99bafc3749504ded97730
  sha256sums = bf07a7fbb825fc0aae7bf4a1177b2b31fcf8a3feeaf7092761e18c859ee52a9c
  sha256sums = d18eca2e2e57e58a47e7dc15000d57f5180e7db9bb2a412ab2449637ab3ce3ff
pkgname = example

    Sources locales et distantes VCS avec renommage

    pkgname=example-git
pkgver=0.1.0
pkgrel=1
pkgdesc="Un exemple de paquet"
arch=(x86_64)
url="https://example.org"
license=(GPL-3.0-or-later)
makedepends=(
  git
  meson
)
depends=(
  gcc-libs
  glibc
)
noextract=(custom-data.tar.gz)
source=(
  test.service
  custom-data.tar.gz{,.sig}
  $pkgname::git+https://git.example.org/repo?signed#tag=v$pkgver
)
sha256sums=(
  b5bb9d8014a0f9b1d61e21e796d78dccdf1352f23cd32812f4850b878ae4944c
  7d865e959b2466918c9863afca942d0fb89d7c9ac0c99bafc3749504ded97730
  bf07a7fbb825fc0aae7bf4a1177b2b31fcf8a3feeaf7092761e18c859ee52a9c
  1e717d3e52d72dde846f0028542d6ace456d7463fb7bc134ab9e812040758aad
)
validpgpkeys=(
  6d96270004515a0486bb7f76196a72b40c55a47f
  4cbd040533a2f43fc6691d773d510cda70f4126a
)
build() {
  meson setup --prefix /usr $pkgname build
  meson compile -C build
}
package(){
  meson install -C build --destdir "$pkgdir"
  install -vDm 644 test.service -t "$pkgname/usr/lib/systemd/system/"
  install -vDm 644 custom-data.tar.gz -t "$pkgname/usr/share/$pkgname/"
}

    Le PKGBUILD ci-dessus définit une configuration de source de paquet, dans laquelle la source distante basée sur git est renommée et une source locale compressée n'est pas extraite mais utilisée telle quelle. Pour la source locale custom-data.tar.gz, une vérification de signature OpenPGP est tentée en utilisant le fichier de signature détachée (supposé) custom-data.tar.gz.sig avec un certificat dont l'empreinte est 6d96270004515a0486bb7f76196a72b40c55a47f et un autre dont l'empreinte est 4cbd040533a2f43fc6691d773d510cda70f4126a. Pour la source distante basée sur git, une vérification de signature OpenPGP sur le tag sélectionné est tentée en utilisant soit un certificat dont l'empreinte est 6d96270004515a0486bb7f76196a72b40c55a47f, soit un autre dont l'empreinte est 4cbd040533a2f43fc6691d773d510cda70f4126a.

    Le fichier SRCINFO suivant est généré à partir du PKGBUILD:

  source = test.service
  source = custom-data.tar.gz
  source = custom-data.tar.gz.sig
  source = example-git::git+https://git.example.org/repo?signed#tag=v0.1.0
  validpgpkeys = 6d96270004515a0486bb7f76196a72b40c55a47f
  validpgpkeys = 4cbd040533a2f43fc6691d773d510cda70f4126a
  sha256sums = b5bb9d8014a0f9b1d61e21e796d78dccdf1352f23cd32812f4850b878ae4944c
  sha256sums = 7d865e959b2466918c9863afca942d0fb89d7c9ac0c99bafc3749504ded97730
