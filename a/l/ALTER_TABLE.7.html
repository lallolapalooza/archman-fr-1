DESCRIPTIO

N

ALTER TABLE modifie la définition d'une table existante. Plusieurs sous-formes sont décrites ci-dessous. Notez que le niveau de verrou requis peut différer pour chaque sous-forme. Un verrou ACCESS EXCLUSIVE est acquis sauf mention contraire explicite. Lorsque plusieurs sous-commandes sont fournies, le verrou acquis sera le plus strict requis par l'une quelconque des

sous-commandes.

ADD COLUMN [ IF NOT EXISTS

]
Cette forme ajoute une nouvelle colonne à la table, en utilisant la même syntaxe que CREATE TABLE. Si IF NOT EXISTS est spécifié et qu'une colonne existe déjà avec ce nom, aucune erreur n'est
levée.

DROP COLUMN [ IF EXISTS

]
Cette forme supprime une colonne d'une table. Les index et les contraintes de table impliquant la colonne seront également supprimés automatiquement. Les statistiques multivariées référençant la colonne supprimée seront également supprimées si la suppression de la colonne ferait que les statistiques ne contiennent des données que pour une seule colonne. Vous devrez indiquer CASCADE si quelque chose en dehors de la table dépend de la colonne, par exemple des références de clé étrangère ou des vues. Si IF EXISTS est spécifié et que la colonne n'existe pas, aucune erreur n'est levée. Dans ce cas, un avertissement est émis à la
place.

SET DATA

TYPE
Cette forme change le type d'une colonne d'une table. Les index et les contraintes simples de table impliquant la colonne seront automatiquement convertis pour utiliser le nouveau type de colonne en réanalysant l'expression fournie à l'origine. La clause COLLATE optionnelle spécifie une collation pour la nouvelle colonne ; si elle est omise, la collation est celle par défaut pour le nouveau type de colonne. La clause USING optionnelle spécifie comment calculer la nouvelle valeur de colonne à partir de l'ancienne ; si elle est omise, la conversion par défaut est la même qu'une conversion par affectation de l'ancien type de données vers le nouveau. Une clause USING doit être fournie s'il n'y a pas de conversion implicite ou par affectation de l'ancien vers le nouveau type.

Lorsque cette forme est utilisée, les statistiques de la colonne sont supprimées, donc il est recommandé d'exécuter ANALYZE sur la table par la suite. Pour une colonne générée virtuelle, ANALYZE n'est pas nécessaire car de telles

colonnes n'ont ja
mais de statistiques.

SET/DROP

DEFAULT
Ces formes définissent ou suppriment la valeur par défaut d'une colonne (où la suppression équivaut à définir la valeur par défaut à NULL). La nouvelle valeur par défaut ne s'appliquera que dans les INSERT ou UPDATE suivants ; elle ne fait pas changer les lignes déjà présentes dans la
table.

SET/DROP NOT

NULL
Ces formes changent si une colonne est marquée pour autoriser les valeurs NULL ou pour les rejeter.

SET NOT NULL ne peut être appliqué à une colonne que si aucun enregistrement de la table ne contient de valeur NULL pour cette colonne. Ordinairement, ceci est vérifié pendant ALTER TABLE en parcourant la table entière, sauf si NOT VALID est spécifié ; cependant, s'il existe une contrainte CHECK valide (et qui n'est pas supprimée dans la même commande) qui prouve qu'aucune valeur NULL ne peut exister, alors le parcours de la table est ignoré. Si une colonne a une contrainte not-null invalide, SET NOT NULL la

valide.

Si cette table est une partition, on ne peut pas effectuer DROP NOT NULL sur une colonne si elle est marquée NOT NULL dans la table parente. Pour supprimer la contrainte NOT NULL de toutes les partitions, effectuez DROP

NOT NULL sur la table parente. Même s'il n'y a pas de contrainte NOT NULL sur la table parente, une telle contrainte peut toujours être ajoutée à des partitions individuelles, si désiré ; c'est-à-dire que les enfants pe
uvent interdire les valeurs NULL même si le parent les autorise, mais pas l'inverse. Il est également possible de supprimer la contrainte NOT NULL de la table parente uniquement, ce qui ne la supprime pas des enfants.

Cette forme remplace l'expression d'une colonne générée. Les données existantes dans une colonne générée stockée sont réécrites et toutes les modifications futures appliqueront la nouvelle expression de génération.

Lorsque cette forme est utilisée sur une colonne générée stockée, ses statistiques sont supprimées, il est donc recommandé d'exécuter ANALYZE sur la table par la suite. Pour une colonne générée virtuelle, ANALYZE n'est pas nécessaire car de te

Cette forme définit ou réinitialise des options par attribut. Actuellement, les seules options par attribut définies sont n_distinct et n_distinct_inherited, qui remplacent les estimations du nombre de valeurs distinctes faites par les opérations ANALYZE ultérieures. n_distinct affecte les statistiques de la table elle-même, tandis que n_distinct_inherited affecte les statistiques collectées pour la table et ses enfants d'héritage, ainsi que les statistiques collectées pour les tables partitionnées. SET STORAGE { PLAIN | EXTERNAL | EXTENDED | MAIN | DEFAULT

}
Cette forme définit le mode de stockage d'une colonne. Cela contrôle si cette colonne est conservée en ligne ou dans une table TOAST secondaire, et si les données doivent être compressées ou non. PLAIN doit être utilisé pour les valeurs de longueur fixe telles que l'entier et est en ligne, non compressée. MAIN est pour les données en ligne, compressibles. EXTERNAL est pour les données externes, non compressées, et EXTENDED est pour les données externes, compressées. Écrire DEFAULT définit le mode de stockage sur le mode par défaut pour le type de données de la colonne. EXTENDED est le défaut pour la plupart des types de données qui prennent en charge le stockage non PLAIN. L'utilisation de EXTERNAL accélérera les opérations de sous-chaîne sur les valeurs text et bytea très grandes, au prix d'une augmentation de l'espace de stockage. Notez que ALTER TABLE ... SET STORAGE ne change rien en soi dans la table ; cela définit simplement la stratégie à suivre lors des futures mises à jour de la table. Consultez la section 66.2 pour plus
d'informations.

SET COMPRESSION compression_metho

d
Cette forme définit la méthode de compression d'une colonne, déterminant comment les valeurs insérées à l'avenir seront compressées (si le mode de stockage autorise la compression). Cela ne provoque pas la réécriture de la table, de sorte que les données existantes peuvent toujours être compressées avec d'autres méthodes de compression. Si la table est restaurée avec pg_restore, alors toutes les valeurs sont réécrites avec la méthode de compression configurée. Cependant, lorsque des données sont insérées depuis une autre relation (par exemple, par INSERT ... SELECT), les valeurs de la table source ne sont pas nécessairement détoasted, de sorte que toute donnée précédemment compressée peut conserver sa méthode de compression existante, plutôt que d'être recompressée avec la méthode de compression de la colonne cible. Les méthodes de compression prises en charge sont pglz et lz4. (lz4 n'est disponible que si --with-lz4 a été utilisé lors de la construction de PostgreSQL.) De plus, compression_method peut être default, qui sélectionne le comportement par défaut de consulter le paramètre default_toast_compression au moment de l'insertion des données pour déterminer la méthode à
utiliser.

ADD table_constraint [ NOT VALID

]
Cette forme ajoute une nouvelle contrainte à une table en utilisant la même syntaxe de contrainte que CREATE TABLE, plus l'option NOT VALID, qui n'est actuellement autorisée que pour les clés étrangères, les contraintes CHECK et les contraintes not-null.

Normalement, cette forme provoquera un parcours de la table pour vérifier que toutes les lignes existantes dans la table satisfont la nouvelle contrainte. Mais si l'option NOT VALID est utilisée, ce parcours potentiellement long est ignoré. La contrainte sera toujours appliquée aux insertions ou mises à jour ultérieures (c'est-à-dire qu'elles échoueront sauf s'il existe une ligne correspondante dans la table référencée, dans le cas des clés étrangères, ou qu'elles échoueront sauf si la nouvelle ligne correspond à la condition de vérification spécifiée). Mais la base de données n'assumera pas que la contrainte est vraie pour toutes les lignes de la table, tant qu'elle n'a pas été validée à l'aide de l'option VALIDATE CONSTRAINT. Consultez les Notes ci-dessous pour plus d'informations sur l'utilisation de l'option NOT

VALID.

Bien que la plupart des formes de ADD table_constraint nécessitent un verrou ACCESS EXCLUSIVE, ADD FOREIGN KEY ne nécessite qu'un verrou SHARE ROW EXCLUSIVE. Notez que ADD FOREIGN KEY acquiert également un verrou SHARE ROW EXCLUSIVE sur la table référencée, en plus du verrou sur la table sur laquelle la contrainte est

déclarée.

Cette forme ajoute une nouvelle contrainte PRIMARY KEY ou UNIQUE à une table sur la base d'un index unique existant. Toutes les colonnes de l'index seront incluses dans la contrainte.

L'index ne peut pas avoir de colonnes d'expression ni être un index partiel. De plus, il doit s'agir d'un index b-tree avec un ordre de tri par défaut. Ces restrictions garantissent que l'index est équivalent à celui qui serait construit par une commande ADD PRIMARY KEY ou ADD UNIQUE

régulière.

Si PRIMARY KEY est spécifié et que les colonnes de l'index ne sont pas déjà marquées NOT NULL, alors cette commande essaiera d'effectuer ALTER COLUMN SET NOT NULL sur chacune de ces colonnes. Cela nécessite un parcours complet de la table pour vérifier que la ou les colonnes ne contiennent pas de valeurs NULL. Dans tous les autres cas, il s'agit d'une opération

rapide.

Si un nom de contrainte est fourni, l'index sera renommé pour correspondre au nom de la contrainte. Sinon, la contrainte portera le même nom que

l'index.

Après l'exécution de cette commande, l'index est « possédé » par la contrainte, de la même manière que si l'index avait été construit par une commande ADD PRIMARY KEY ou ADD UNIQUE régulière. En particulier, supprimer la contrainte fera aussi disparaître

l'index.

Cette forme n'est actuellement pas prise en charge sur les tables

partitionnées.

expression.

DETACH PARTITION partition_name [ CONCURRENTLY | FINALIZE

]
Cette forme détache la partition spécifiée de la table cible. La partition détachée continue d'exister en tant que table autonome, mais n'a plus aucun lien avec la table dont elle a été détachée. Une fois toutes ces transactions terminées, la deuxième transaction acquiert SHARE UPDATE EXCLUSIVE sur la table partitionnée et ACCESS EXCLUSIVE sur la partition, et le processus de détachement se termine. Une contrainte CHECK qui duplique la contrainte de partition est ajoutée à la partition. CONCURRENTLY ne peut pas être exécuté dans un bloc de transaction et n'est pas autorisé si la table partitionnée contient une partition par

défaut.

Y qui a été annulée ou interrompue est terminée. Au plus une partition d

Lorsqu'une colonne est ajoutée avec ADD COLUMN et qu'un DEFAULT non volatile est spécifié, la valeur par défaut est évaluée au moment de l'énoncé et le résultat est stocké dans les métadonnées de la table, où il sera renvoyé lorsque des lignes existantes seront accessibles. La valeur ne sera appliquée que lorsque la table est réécrite, ce qui rend le ALTER TABLE très rapide même sur de grandes tables. Si aucune contrainte de colonne n'est spécifiée, NULL est utilisé comme DEFAULT. Dans aucun des deux cas, la réécriture de la table n'est

requise.

L'ajout d'une colonne avec un DEFAULT volatile (par ex., clock_timestamp()), une colonne générée stockée, une colonne d'identité, ou une colonne avec un type de domaine ayant des contraintes entraînera la réécriture de la table entière et de ses index. L'ajout d'une colonne générée virtuelle ne nécessite jamais de réécriturerite

.

Changer le type d'une colonne existante entraînera normalement la réécriture de l'ensemble de la table et de ses index. En tant qu'exception, lors du changement du type d'une colonne existante, si la clause USING ne modifie pas le contenu de la colonne et que l'ancien type est soit coercible binairement vers le nouveau type, soit un domaine non contraint sur le nouveau type, une réécriture de la table n'est pas nécessaire. Cependant, les index seront toujours reconstruits à moins que le système ne puisse vérifier que le nouvel index serait logiquement équivalent à l'existant. Par exemple, si la collation d'une colonne a été modifiée, une reconstruction de l'index est requise car le nouvel ordre de tri pourrait être différent. Cependant, en l'absence de changement de collation, une colonne peut être changée de text à varchar (ou vice versa) sans reconstruire les index car ces types de données trient de manière

identique.

La reconstruction des tables et/ou des index peut prendre un temps considérable pour une grande table et nécessitera temporairement jusqu'au double de l'espace

disque.

L'ajout d'une contrainte CHECK ou NOT NULL nécessite de parcourir la table pour vérifier que les lignes existantes respectent la contrainte, mais ne nécessite pas une réécriture de la table. Si une contrainte CHECK est ajoutée en tant que NOT ENFORCED, aucune vérification ne sera

effectuée.

De même, lors de l'attachement d'une nouvelle partition, celle-ci peut être parcourue pour vérifier que les lignes existantes respectent la contrainte de

partition.

La raison principale de fournir l'option de spécifier plusieurs modifications dans un seul ALTER TABLE est que plusieurs parcours ou réécritures de table peuvent ainsi être combinés en un seul passage sur la

table.

Parcourir une grande table pour vérifier de nouvelles contraintes de clé étrangère, de vérification ou de non-nullité peut prendre beaucoup de temps, et les autres mises à jour de la table sont bloquées jusqu'à ce que la commande ALTER TABLE ADD CONSTRAINT soit validée. Le but principal de l'option de contrainte NOT VALID est de réduire l'impact de l'ajout d'une contrainte sur les mises à jour concurrentes. Avec NOT VALID, la commande ADD CONSTRAINT ne parcourt pas la table et peut être validée immédiatement. Après cela, une commande VALIDATE CONSTRAINT peut être émise pour vérifier que les lignes existantes satisfont la contrainte. L'étape de validation n'a pas besoin de bloquer les mises à jour concurrentes, car elle sait que d'autres transactions feront respecter la contrainte pour les lignes qu'elles insèrent ou mettent à jour ; seules les lignes préexistantes doivent être vérifiées. Par conséquent, la validation n'acquiert qu'un verrou SHARE UPDATE EXCLUSIVE sur la table altérée. (Si la contrainte est une clé étrangère, un verrou ROW SHARE est également requis sur la table référencée par la contrainte.) En plus d'améliorer la concurrence, il peut être utile d'utiliser NOT VALID et VALIDATE CONSTRAINT dans les cas où la table est connue pour contenir des violations préexistantes. Une fois la contrainte en place, aucune nouvelle violation ne peut être insérée, et les problèmes existants peuvent être corrigés à loisir jusqu'à ce que VALIDATE CONSTRAINT finalement

réussisse.

La forme DROP COLUMN ne supprime pas physiquement la colonne, mais la rend simplement invisible aux opérations SQL. Les opérations d'insertion et de mise à jour ultérieures dans la table stockeront une valeur nulle pour la colonne. Ainsi, la suppression d'une colonne est rapide mais ne réduira pas immédiatement la taille sur disque de votre table, car l'espace occupé par la colonne supprimée n'est pas récupéré. L'espace sera récupéré au fil du temps à mesure que les lignes existantes sont mises à

jour.

Pour forcer la récupération immédiate de l'espace occupé par une colonne supprimée, vous pouvez exécuter l'une des formes de ALTER TABLE qui effectue une réécriture de l'ensemble de la table. Cela entraîne la reconstruction de chaque ligne avec la colonne supprimée remplacée par une valeur

nulle.

Les formes de réécriture de ALTER TABLE ne sont pas sûres pour MVCC. Après une réécriture de table, la table apparaîtra vide aux transactions concurrentes si elles utilisent un instantané pris avant que la réécriture n'ait eu lieu. Voir la section 13.6 pour plus de

détails.

L'option USING de SET DATA TYPE peut en fait spécifier toute expression impliquant les anciennes valeurs de la ligne ; c'est-à-dire qu'elle peut faire référence à d'autres colonnes ainsi qu'à celle qui est convertie. Cela permet d'effectuer des conversions très générales avec la syntaxe SET DATA TYPE. En raison de cette flexibilité, l'expression USING n'est pas appliquée à la valeur par défaut de la colonne (le cas échéant) ; le résultat pourrait ne pas être une expression constante comme requis pour une valeur par défaut. Cela signifie que lorsqu'il n'y a pas de conversion implicite ou d'affectation de l'ancien au nouveau type, SET DATA TYPE pourrait échouer à convertir la valeur par défaut même si une clause USING est fournie. Dans de tels cas, supprimez la valeur par défaut avec DROP DEFAULT, effectuez l'ALTER TYPE, puis utilisez SET DEFAULT pour ajouter une nouvelle valeur par défaut appropriée. Des considérations similaires s'appliquent aux index et aux contraintes impliquant la

colonne.

Si une table a des tables filles, il n'est pas permis d'ajouter, renommer ou changer le type d'une colonne dans la table parente sans faire de même pour les filles. Cela garantit que les filles ont toujours des colonnes correspondant à la parente. De même, une contrainte CHECK ne peut pas être renommée dans la parente sans également la renommer dans toutes les filles, afin que les contraintes CHECK correspondent également entre la parente et ses filles. (Cette restriction ne s'applique pas aux contraintes basées sur des index, cependant.) De plus, car la sélection depuis la parente sélectionne également depuis ses filles, une contrainte sur la parente ne peut pas être marquée valide à moins qu'elle ne soit également marquée valide pour ces filles. Dans tous ces cas, ALTER TABLE ONLY sera

rejeté.

Une opération DROP COLUMN récursive ne supprimera la colonne d'une table fille que si la fille n'hérite pas de cette colonne d'une autre parente et n'a jamais eu de définition indépendante de la colonne. Un DROP COLUMN non récursif (c'est-à-dire ALTER TABLE ONLY ... DROP COLUMN) ne supprime jamais de colonnes filles, mais les marque plutôt comme définies indépendamment plutôt qu'héritées. Une commande DROP COLUMN non récursive échouera pour une table partitionnée, car toutes les partitions d'une table doivent avoir les mêmes colonnes que la racine de partitionnement

.

Les actions pour les colonnes d'identité (ADD GENERATED, SET etc., DROP IDENTITY), ainsi que les actions CLUSTER, OWNER et TABLESPACE ne se propagent jamais aux tables filles ; c'est-à-dire qu'elles agissent toujours comme si ONLY avait été spécifié. Les actions affectant les états des triggers se propagent aux partitions des tables partitionnées (sauf si ONLY est spécifié), mais jamais aux filles de l'héritage traditionnel. L'ajout d'une contrainte ne se propage que pour les contraintes CHECK qui ne sont pas marquées NO

INHERIT.

Il n'est pas permis de modifier une partie d'une table de catalogue

système.

Consultez CREATE TABLE (CREATE_TABLE(7)) pour une description supplémentaire des paramètres valide

s. Le chapitre 5 contient des infor
mations supplémentaires sur l'héritage.

COMPATIBILIT

É

Les formes ADD [COLUMN], DROP [COLUMN], DROP IDENTITY, RESTART, SET DEFAULT, SET DATA TYPE (sans USING), SET GENERATED, et SET sequence_option sont conformes à la norme SQL. La forme ADD table_constraint est conforme à la norme SQL lorsque les clauses USING INDEX et NOT VALID sont omises et que le type de contrainte est l'un des suivants : CHECK, UNIQUE, PRIMARY KEY, ou REFERENCES. Les autres formes sont des extensions de PostgreSQL à la norme SQL. De plus, la possibilité de spécifier plus d'une manipulation dans une seule commande ALTER TABLE est une

extension.

ALTER TABLE DROP COLUMN peut être utilisé pour supprimer la seule colonne d'une table, laissan

t une table à zéro colonne. C'est une extension de
SQL, qui interdit les tables à zéro colonne.
