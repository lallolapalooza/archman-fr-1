Qu'est-ce qu'Alien, Alien::Base et Alien::Build

?

Alien est un espace de noms Perl pour définir des dépendances dans CPAN pour les bibliothèques et les outils qui ne sont pas « natifs » de CPAN. Pour une description de style manifeste du Pou

rquoi et du Comment, voir Alien. Alien::Base est une classe de base pour l'exécution d'Alien. Alien::Build est un outil pour sonder le système d'exploitation à la recherche de bibliothèques e
t d'outils existants, et pour télécharger, construire et installer des paquets. alienfile est un format de recette pour décrire comment sonder, télécharger, construire et installer un paquet.

Comment construire un paquet qui utilise un système de

construction

autocon

f

Utilisez le plugin autoconf (Alien::Build::Plugin::Build::Autoconf). Si votre paquet fournit un fichier « .pc » pkg-config, vous pouvez également utiliser le plugin PkgConfig (Alien::Build::Plugin::PkgConfig::Negotiate)

. 
use alienfile
plugin PkgConfig => 'libfoo';
share {
  start_url => 'http://example.org/dist';
  plugin Download => (
    version => qr/libfoo-([0-9\.])\.tar\.gz$/,
  );
  plugin Extract => 'tar.gz';
  plugin 'Build::Autoconf';
}
;

Si vous devez fournir des drapeaux personnalisés à configure, vous pouvez le faire aussi

: 
share {
  plugin 'Build::Autoconf';
  build [
    '%{configure} --disable-shared --enable-foo',
    '%{make}',
    '%{make} install',
  ];
}
;

Si votre paquet nécessite GNU Make, utilisez « %{gmake} » au lieu de « %{make} »

.

autoconf sans script

configure

Un certain nombre de projets Open Source utilisent autotools, mais ne fournissent pas le script « configure ». Lorsque vous alienisez ce type de paquet, vous avez quelques choix

:
construire configure en utilisant
autotools
L'alien Alien::Autotools est conçu pour fournir autotools pour construire de tels paquets à partir des sources. L'avantage est que c'est ainsi que les développeurs amont ont l'intention que leur paquet soit construit. L'inconvénient est que cela ajoute aussi plus de prérequis à votre Alien. Le côté positif est que si vous requérez cet Alien dans le bloc « share » (comme vous devriez le faire), alors ces prérequis ne seront tirés que lors d'une installation share lorsqu'ils sont nécessaires.

Veuillez consulter la documentation d'Alien::Au

totools pour les détails sur la façon
dont il peut être utilisé dans votre alienfile.
appliquer un patch au paquet localement avant la
construction
Vous pouvez utiliser la directive « patch » dans alienfile pour appliquer un patch au paquet alienisé localement avant la construction. Cela peut parfois être difficile car Autotools utilise des horodatages pour décider ce qui doit être reconstruit, et l'application d'un patch peut parfois le tromper en lui faisant penser que plus doit être reconstruit que ce qui l'est
réellement.
construire configure et l'archive
tarball
Vous pouvez aussi construire le script configure lors du développement de votre alien, générer l'archive
tarball et la fournir quelque part comme GitHub et l'utiliser comme source au lieu de la source originale.
Cela devrait généralement être un dernier recours si les deux autres méthodes s'avèrent trop difficiles.

de type

autoconf

Si vous voyez une erreur comme celle-ci

: 
Unknown option
"--with-pic".

C'est parce que le plugin autoconf utilise l'option « --with-pic » par défaut, puisqu'elle a du sens la plupart du temps, et autoconf ignore généralement les options qu'il ne reconnaît pas. Certains systèmes de construction de style autoconf échouent lorsqu'ils voient une option qu'ils ne reconnaissent pas. Vous pouvez désactiver ce comportement pour ces paquets

: 
plugin 'Build::Autoconf' => (
  with_pic => 0,
)
;

Une autre chose à propos du plugin autoconf est qu'il utilise « DESTDIR » pour faire une installation en deux étapes. Si vous voyez une erreur comme « nothing was installed into destdir », cela signifie que votre paquet ne prend pas en charge « DESTDIR ». Vous devriez plutôt utiliser le plugin MSYS et utiliser une séquence de commandes pour faire la construction comme ceci

: 
share {
  plugin 'Build::MSYS';
  build [
    # exécuter explicitement configure avec "sh" s'assurera que
    # cela fonctionne sur windows ainsi que sur UNIX.
    'sh configure --prefix=%{.install.prefix} --disable-shared',
    '%{make}',
    '%{make} install',
  ];
}
;

CMak

e

Il existe un alien Alien::cmake3 qui fournit « cmake » 3.x ou mieux (Il est préféré à l'ancien Alien::CMake). Bien qu'il soit recommandé que vous utilisiez le plugin « cmake » (Alien::Build::Plugin::Build::CMake) au lieu d'utiliser Alien::

cmake3. 
use alienfile;

share {
  plugin 'Build::CMake';
  build [
    # ceci est l'étape de construction par défaut, si vous n'en spécifiez pas une.
    [ '%{cmake}',
        @{ meta->prop->{plugin_build_cmake}->{args} },
        # ... mettez les arguments cmake supplémentaires ici ...
        '.'
    ],
    '%{make}',
    '%{make} install',
  ];
}
;

Makefiles

vanilla

Alien::Build fournit un helper (« %{make} ») pour le « make » utilisé par Perl et ExtUtils::MakeMaker (EUMM). Malheureusement, le « make » pris en charge par Perl et EUMM sur Windows (« nmake » et « dmake ») n'est pas largement pris en charge par la plupart des projets open source. (Heureusement, les perls et EUMM récents prennent maintenant en charge GNU Make sur windows)

.

Vous pouvez utiliser le plugin « make » (Alien::Build::Plugin::Build::Make) pour indiquer au système Alien::Build quel make le projet que vous alienisez

requiert. 
plugin 'Build::Make' => 'umake';
# umake rend %{make} soit GNU Make ou BSD Make sur Unix et GNU Make sur Windows.
build {
  build [
    # Vous pouvez utiliser le compilateur et les cflags de configuration Perl à l'aide de l'helper %{perl.config...}
    [ '%{make}', 'CC=%{perl.config.cc}', 'CFLAGS=%{perl.config.cccdlflags} %{perl.config.optimize}' ],
    [ '%{make}', 'install', 'PREFIX=%{.install.prefix}' ],
  ],
}
;

Certains projets open source nécessitent GNU Make, et vous pouvez le spécifier, et Alien::gmake sera tiré sur les plateformes qui ne l'ont pas

déjà. 
plugin 'Build::Make' => 'gmake';
.
.
.

Comment sonder un paquet qui utilise pkg-config

?

Utilisez le plugin « pkg-config » (Alien::Build::Plugin::PkgConfig::Negotiate)

: 
use alienfile;
plugin 'PkgConfig' => (
  pkg_name => 'libfoo',
)
;

Il sondera pour une version système de la bibliothèque. Il ajoutera aussi les propriétés appropriées « version » « cflags » et « libs » sur une installation « system » ou « sha

re
».

Comment spécifier une version minimale ou exacte requise pour les paquets qui utilisent pkg-config

?

Les différents plugins pkg-config prennent tous en charge les champs atleast_version, exact_version et maximum_version, qui ont la même signification que l' interface en ligne de commande « pkg-config »

: 
use alienfile;

plugin 'PkgConfig', pkg_name => 'foo', atleast_version => '1.2.
3';

o

u 
utiliseruse alienfile;

plugin 'Pk
gConfig', pkg_name => foo,
exact_version => '1.2.3';

Comment interroger un paquet qui utilise plusieurs fichiers .pc

?

Chaque plugin "PkgConfig" acceptera une référence de tableau au lieu d'une chaîne

: 
use alienfile;

plugin 'PkgConfig' => ( pkg_name => [ 'foo', 'bar', 'baz' ] )
;

Le premier "pkg_name" fourni sera utilisé par défaut une fois votre alien installé. Pour obtenir la configuration de "foo" et "bar", vous pouvez utiliser la méthode alt d'Alien::Base

: 
use Alien::libfoo;

$cflags = Alien::libfoo->cflags;               # drapeaux de compilati
on pour 'foo' $cflags = Alien::libfoo->alt('bar')->cflags ; # drapeaux de compilation pour
'bar' $cflags = Alien::libfoo->alt('baz')->cflags ; # drapeaux de compilation pour 'baz'

Comment créer un module Alien pour des paquets qui ne prennent pas en charge pkg-config

?

Paquets qui fournissent un script de

configuration

De nombreux paquets fournissent une commande que vous pouvez utiliser pour obtenir la version, les drapeaux de compilation et de liaison appropriés. Pour ces paquets, vous pouvez simplement utiliser les commandes dans votre alienfile. Quelque chose comme ceci

: 
use alienfile;

probe [ 'foo-config --version' ];

share {
  ...

  build [
    '%{make} PREFIX=%{.runtime.prefix}',
    '%{make} install PREFIX=%{.runtime.prefix}',
  ];
};

gather [
  [ 'foo-config', '--version', \'%{.runtime.version}' ],
  [ 'foo-config', '--cflags',  \'%{.runtime.cflags}'  ],
  [ 'foo-config', '--libs',    \'%{.runtime.libs}'    ],
]
;

Paquets qui nécessitent un test de

compilation

Certains paquets supposent simplement que vous savez que "-lfoo" fonctionnera. Pour ceux-ci, vous pouvez utiliser le plugin "cbuilder" (Alien::Build::Plugin::Probe::CBuilder)

. 
use alienfile;
plugin 'Probe::CBuilder' => (
  cflags => '-I/opt/libfoo/include',
  libs   => '-L/opt/libfoo/lib -lfoo',
);

share {
  ...
  gather sub {
    my($build) = @_;
    my $prefix = $build->runtime_prop->{prefix};
    $build->runtime_prop->{cflags} = "-I$prefix/include ";
    $build->runtime_prop->{libs}   = "-L$prefix/lib -lfoo ";
  };
}

Ce plugin compilera un petit programme avec ces drapeaux et testera qu'il fonctionne. (Il existe également des options pour fournir un programme capable d'effectuer des tests simples afin de s'assurer que la bibl

iothèque fonctionne). Si la détection fonctionne, il définira les drapeaux de compilation et de liaison. (Il existe également des options pour extraire la version du programme de test). Si vous effectuez une
installation en partage (share), vous devrez définir vous-même les drapeaux de compilation et de liaison à l'étape de collecte (gather), si vous n'utilisez pas un plugin de construction qui le fera pour vous.

Puis-je / Dois-je écrire un module Alien orienté outil

?

Certainement. L'intention initiale était de fournir des bibliothèques, mais les outils sont tout à fait faisables avec l'ensemble d'outils Alien::Build. Un bon exemple de la façon de faire cela est Alien::nasm. Vous voudrez utiliser le plugin 'Probe::CommandLine'

: 
use alienfile;

plugin 'Probe::CommandLine' => (
  command => 'gzip',
)
;

Comment tester mon paquet une fois qu'il est construit (avant qu'il ne soit installé)

?

Utilisez Test::Alien. Il possède

une documentation complète et
s'intègre bien avec Alien::Base.

Comment corriger (patcher) des paquets qui nécessitent des modifications

?

Si vous avez un fichier diff, vous pouvez utiliser patch

: 
use alienfile;

probe sub { 'share' }; # remplacer par une détection appropriée

share {
  ...
  patch [ '%{patch} -p1 < %{.install.patch}/mypatch.diff' ];
  build [ ... ] ;
}

..
.

Vous pouvez également appliquer un patch en Perl si c'est plus simple

: 
use alienfile;

probe sub { 'share' };

share {
  ...
  patch sub {
    my($build) = @_;
    # apporter des modifications aux sources avant la construction
  };
  build [ ... ];
}
;

Les drapeaux produits par un plugin sont incorrects

!

Parfois, les drapeaux de compilation ou de liaison que le plugin PkgConfig génère ne sont pas tout à fait corrects. (Souvent, c'est en fait parce qu'un mainteneur de paquet fournit un fichier ".pc" défectueux). (D'autres plugins peuvent également avoir des problèmes). Vous pourriez remplacer l'étape "gather" du plugin, mais une meilleure façon est de fournir un rappel de sous-routine à appeler après que l'étape de collecte est terminée. Vous pouvez le faire avec la directive "after" d'alienfile

: 
use alienfile;

plugin 'PkgConfig' => 'libfoo';

share {
  ...
  after 'gather' => sub {
    my($build) = @_;
    $build->runtime_prop->{libs}        .= " -lbar";        # libfoo nécessite aussi libbar
    $build->runtime_prop->{libs_static} .= " -lbar -lbaz";  # libfoo nécessite aussi libbaz en liaison statique
  };
}
;

Parfois, vous n'avez besoin de le faire que sur certaines plateformes. Vous pouvez ajuster la logique en fonction de $^O de manière

appropriée. 
use alienfile;

plugin 'PkgConfig' => 'libfoo';

share {
  ...
  after 'gather' => sub {
    my($build) = @_;
    if($^O eq 'MSWin32') {
      $build->runtime_prop->{libs} .= " -lpsapi";
    }
  };
}
;

Le "599 Internal Exception" indique une exception "interne" de HTTP::Tiny et n'est pas un vrai code de statut HTTP ou une erreur. Certains sites web autorisent une requête initiale depuis "http" mais redirigent ensuite vers "https". Si vous le pouvez, il est préférable de spécifier "https". Ne détecte pas le paquet système même s'il est

installé

Cela pourrait simplement être parce que l'alien nécessite un paquet plus récent que celui fourni par votre système

d'exploitation.

Cela pourrait aussi être parce que vous n'avez pas installé le paquet de développement. De nombreux fournisseurs Linux, en particulier, séparent les paquets en paquets d'exécution (runtime) et de développement. Sur les systèmes basés sur RPM, ces paquets de développement ont généralement le suffixe "-devel" (par exemple, exécution : "libffi" et développement : "libffi-devel"). Sur les systèmes basés sur Debian ces paquets de développement ont généralement le suffixe "-dev" (par exemple, exécution : "libffi" et développement : "libffi

-de
v").

La récupération réseau est

désactivée

Si vous obtenez une erreur comme celle-ci

Alien::Build> see see https://metacpan.org/pod/Alien::Build::Manual::FAQ#Network-fetch-is-turned-of

Cela est dû à ce que votre environnement est configuré pour ne pas installer les aliens qui nécessitent le réseau. Vous pouvez réactiver la récupération réseau en définissant "ALIEN_INSTALL_NETWORK" à vrai, ou en le supprimant. Cette variable d'environnement est conçue pour les environnem

ents qui ne souhaitent jamais installer d'aliens nécess

Je préférerais vraiment que vous ne téléchargiez pas de choses sur

Internet

L'idée d'Alien est de télécharger les paquets manquants et de les construire automatiquement pour faciliter l'installation. Certaines personnes pourraient ne pas aimer cela, ou pourraient même avoir des exigences de sécurité leur interdisant de télécharger des paquets au hasard sur Internet (attention, télécharger des choses au hasard depuis CPAN n'est peut-être pas plus sûr, alors assurez-vous d'auditer tout le logiciel open source que vous utilisez de manière appropriée). Une autre raison pour laquelle vous pourriez ne pas vouloir télécharger depuis Internet est si vous empaquetez un alien pour un fournisseur de système d'exploitation, qui voudra toujours utiliser la version système d'une bibliothèque. Dans cette situation, vous ne voulez pas qu'Alien::Build parte télécharger quelque chose depuis Internet parce que la sonde a échoué pour une raison

quelconque.

C'est facile à gérer, définissez simplement "ALIEN_INSTALL_TYPE" à "system" et une construction à partir du code source ne sera jamais tentée. Sur les systèmes qui ne fournissent pas de versions système de la bibliothèque ou de l'outil, vous obtiendrez une erreur, vous permettant d'installer la bibliothèque, et de réessayer l'installation de l'alien. Vous pouvez également définir la variable d'environnement sur certains aliens

seulement. 
% export ALIEN_INSTALL_TYPE=system  #
pour tout le monde % env ALIEN_INSTA
LL_TYPE=system cpanm -v Alien::libfoo
