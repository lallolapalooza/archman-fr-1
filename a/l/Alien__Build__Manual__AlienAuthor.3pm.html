Remarque : Veuillez lire l'intégralité du document avant de commencer à écrire votre propre alienfile. La section sur les bibliothèques dynamiques vs. statiques vous évitera probablement beaucoup de tracas si vous la lisez maintenant

Ce document est destiné à enseigner aux auteurs d'Alien comment construire leur propre distribution Alien en utilisant Alien::Build et Alien::Base. Une telle distribution Alien se compose de trois parties essentielles

:
Un
alienfile
C'est une recette pour 1) détecter une version déjà installée de la bibliothèque ou de l'outil que vous aliénisez, 2) télécharger et construire la bibliothèque ou l'outil que vous aliénisez et 3) rassembler les paramètres de configuration nécessaires à l'utilisation de cette bibliothèque ou de cet
outil.
Un installateur "Makefile.PL" ou "Build.PL" ou un "dist.ini" si vous utilisez Dist::
Zilla
C'est une fine couche entre votre recette alienfile et l'installateur Perl (soit ExtUtils::MakeMaker ou Module::Build)
.
Une classe Perl (fichier .pm) qui hérite de Alien::
Base
Pour la plupart des Aliens, cela n'a pas besoin
d'être personnalisé du tout, car Alien::B
ase fait généralement ce dont vous avez besoin.

Par exemple, si vous aliénisez une bibliothèque appelée libfoo, vous pourriez avoir ces fichiers

: 
Alien-Libfoo-1.00/Makefile.PL
Alien-Libfoo-1.00/alienfile
Alien-Libfoo-1.00/lib/Alien/Libfoo.
pm

Ce document se concentrera principalement sur la manière de construire un alienfile, mais nous couvrirons également brièvement la création d'un simple "Makefile.PL" ou "dist.ini" pour l'accompagner. Nous aborderons également le moment où vous pourriez vouloir étendre votre sous-classe pour ajouter des fonctionnalités non

standard.

Utilisation des

commandes

La plupart des bibliothèques et des outils logiciels sont livrés avec des instructions pour les installer sous la forme de commandes que vous êtes censé taper manuellement dans un shell. La façon la plus simple d'automatiser ces instructions est de simplement mettre les commandes dans votre alienfile. Par exemple, supposons que libfoo est construit avec autoconf et fournit un "pkg-config" fichier ".

pc".

Nous discuterons également des plugins plus tard. Pour les systèmes de construction courants comme autoconf ou CMake, il est généralement préférable d'utiliser le plugin approprié car ils géreront les cas particuliers mieux qu'un simple ensemble de commandes. Nous allons d'abord examiner les commandes car il est plus facile de comprendre les différentes phases avec des

commandes.

(À part, autoconf est une série d'outils et de macros utilisés pour configurer (généralement) une bibliothèque ou un outil C ou C++ en générant un certain nombre de Makefiles. C'est l'équivalent C d'ExtUtils::MakeMaker, si vous voulez. Fondamentalement, si les instructions de votre bibliothèque ou de votre outil commencent par './configure', c'est très probablement une bibliothèque ou un outil basé sur autoconf)

.

(À part 2, "pkg-config" est une façon standard de fournir les drapeaux du compilateur et de l'éditeur de liens nécessaires pour compiler et lier avec la bibliothèque. Si votre outil installe un fichier ".pc", généralement dans "$PREFIX/lib/pkgconfig", alors votre outil utilise "pkg-conf

ig").

Voici l'alienfile que vous pourriez avoir

: 
use alienfile;

probe [ 'pkg-config --exists libfoo' ];

share {

  start_url 'http://www.libfoo.org/src/libfoo-1.00.tar.gz';

  download [ 'wget %{.meta.start_url}' ];

  extract [ 'tar zxf %{.install.download}' ];

  build [
    [ './configure --prefix=%{.install.prefix} --disable-shared' ],
    [ '%{make}' ],
    [ '%{make} install' ],
  ];

};

gather [
  [ 'pkg-config --modversion libfoo', \'%{.runtime.version}' ],
  [ 'pkg-config --cflags     libfoo', \'%{.runtime.cflags}'  ],
  [ 'pkg-config --libs       libfoo', \'%{.runtime.libs}'    ],
]
;

Il se passe beaucoup de choses ici, alors décodons un peu. Un alienfile est juste du Perl avec un peu de sucre spécifique à Alien. La première

ligne 
use
alienfile;

importe le sucre dans l'alienfile. C'est aussi un indicateur pour le lecteur pour qu'il voie qu'il s'agit d'un alienfile et non d'un autre type de script

Perl.

La deuxième ligne est la directive probe

: 
probe [ 'pkg-config --exists libfoo' ]
;

est utilisée pour voir si la bibliothèque est déjà installée sur le système cible. Si "pkg-config" est dans le PATH, et si libfoo est installé, cela devrait se terminer avec un succès (0) et dire à Alien::Build d'utiliser la bibliothèque du système. Si soit "pkg-config" n'est pas dans le PATH, ou si libfoo n'est pas installé, alors cela se terminera avec un échec (!= 0) et indiquera à Alien::Build de télécharger et de construire à partir des

sources.

Vous pouvez fournir autant de directives probe que vous le souhaitez. C'est utile s'il existe différentes façons d'interroger le système. Alien::Build s'arrêtera à la première bibliothèque système trouvée avec succès. Disons que notre bibliothèque libfoo est livrée avec un fichier ".pc" pour une utilisation avec "pkg-config" et fournit également un programme "foo-config" pour trouver les mêmes valeurs. Vous pourriez alors spécifier cela dans votre

alienfile 
probe [ 'pkg-config --exists libfoo' ];
probe [ 'foo-config --version' ]
;

D'autres directives peuvent être spécifiées plusieurs fois s'il existe différentes méthodes qui peuvent être essayées pour les différentes

étapes.

Parfois, il est plus facile d'interroger une bibliothèque depuis Perl plutôt qu'avec une commande. Pour cela, vous pouvez utiliser une référence de code. Par exemple, une autre façon d'appeler "pkg-config" serait depuis Perl

: 
probe sub {
  my($build) = @_;  # $build est l'instance Alien::Build.
  system 'pkg-config --exists libfoo';
  $? == 0 ? 'system' : 'share';
}
;

Le code Perl devrait retourner 'system' si la bibliothèque est installée, et 'share' sinon. (Les autres directives devraient retourner une valeur vraie en cas de succès, et une valeur fausse en cas d'échec). Vous pouvez également lever une exception avec "die" pour indiquer un

échec.

La partie suivante de l'alienfile est le bloc "share", qui est utilisé pour regrouper les directives utilisées pour télécharger et installer la bibliothèque ou l'outil dans le cas où il n'est pas déjà

installé. 
share {
  start_url 'http://www.libfoo.org/src/libfoo-1.00.tar.gz';
  download [ 'wget %{.meta.start_url}' ];
  extract [ 'tar zxf %{.install.download}' ];
  build [
    [ './configure --prefix=%{.install.prefix} --disable-shared' ],
    [ '%{make}' ],
    [ '%{make} install' ],
  ];
}
;

Le start_url spécifie où trouver le paquet que vous aliénisez. Il devrait s'agir soit d'une archive tar (ou d'un fichier zip, ou autre), soit d'un index HTML. La directive download, comme vous pouvez l'imaginer, spécifie comment télécharger la bibliothèque ou l'outil. La directive extract spécifie comment extraire l'archive une fois qu'elle est téléchargée. Dans l'étape d'extraction, vous pouvez utiliser la variable "%{.install.download}" comme espace réservé pour l'archive qui a été téléchargée à l'étape de téléchargement. Cela est également accessible si vous utilisez une référence de code depuis l'instance Alien::Build

: 
share {
  ...
  requires 'Archive::Extract';
  extract sub {
    my($build) = @_;
    my $tarball = $build->install_prop->{download};
    my $ae = Archive::Extract->new( archive => $tarball );
    $ae->extract;
    1;
  }
  ...
}
;

La directive build spécifie comment construire la bibliothèque ou l'outil une fois qu'il a été téléchargé et extrait. Notez la variable spéciale "%{.install.prefix}" qui est l'emplacement où la bibliothèque devrait être installée. "%{make}" est un assistant qui sera remplacé par le "make" approprié, qui peut être appelé différemment sur certaines plateformes (sur Windows par exemple, il peut souvent être appelé "nmake" ou "dmake

").

La partie finale de l'alienfile contient une directive gather qui spécifie comment obtenir les détails sur la façon de compiler et de lier avec la bibliothèque. Pour cela, nous utilisons à nouveau la commande "pkg-config"

: 
gather [
  [ 'pkg-config --modversion libfoo', \'%{.runtime.version}' ],
  [ 'pkg-config --cflags     libfoo', \'%{.runtime.cflags}'  ],
  [ 'pkg-config --libs       libfoo', \'%{.runtime.libs}'    ],
];
La référence
scalaire

en tant que dernier élément de la liste de commandes indique à Alien::Build que la sortie de la commande doit être stockée dans la variable donnée. Les variables d'exécution (runtime) sont celles qui seront disponibles pour "Alien::Libfoo" une fois qu'il est installé. (Les propriétés d'installation, qui sont celles que nous avons vues jusqu'à présent, sont jetées une fois que la distribution Alien est installée. Vous

pouvez

également fournir un "sys" pour les directives qui doivent être utilisées lorsqu'une installation système est détectée. Normalement, vous n'avez besoin de le faire que si l'étape de collecte (gather) est différente entre les installations share et system. Par exemple,

ce 
qui précède est équivalent à :
build {
  ...

    [ 'pkg-config --modversion libfoo', \'%{.runtime.version}' ],
    [ 'pkg-config --cflags     libfoo', \'%{.runtime.cflags}'  ],
    [ 'pkg-config --libs       libfoo', \'%{.runtime.libs}'    ],
  ];
};

sys {
  gather [
    [ 'pkg-config --modversion libfoo', \'%{.runtime.version}' ],
    [ 'pkg-config --cflags     libfoo', \'%{.runtime.cflags}'  ],
    [ 'pkg-config --libs       libfoo', \'%{.runtime.libs}'    ],
  ];
};
(À ce propos, la
raison

pour laquelle il s'appelle "sys" et non "system" est pour qu'il ne rentre pas en conflit avec la fonction intégrée "system") ! Utilisatio

Le premier

est une bonne façon de montrer le chemin manuel complet que vous pouvez choisir, mais il y a beaucoup de répétition si vous créez de nombreux Aliens qui utilisent autoconf et "pkg-config" (ce qui est assez courant). alienfile vous permet d'utiliser des plugins. Voir Alien::Build::Plugin pour une liste de certaines catégories de plugins.

Pour

l'instant, je vais simplement vous montrer comment écrire l'alienfile pour libfoo ci-dessus en utilisant Alien::Build::Plugin::Build::Autoconf, Alien::Build::Plugin::PkgConfig::Negotiate, Alien::Build::Plugin::Download::Negotiate et Alien::Build::Plugin::Extract::Negotiate use

alienfile; 
plugin 'PkgConfig' => (
  pkg_name => 'libfoo',
);

share {
  start_url 'http://www.libfoo.org/src';
  plugin 'Download' => (
    filter => qr/^libfoo-[0-9\.]+\.tar\.gz$/,
    version => qr/^libfoo-([0-9\.]+)\.tar\.gz$/,
  );
  plugin 'Extract' => 'tar.gz';
  plugin 'Build::Autoconf';
  build [
    '%{configure} --disable-shared',
    '%{make}',
    '%{make} install',
  ];
};
Le premier plugin que nous utilisons est le plugin
de

négociation "pkg-config". Un plugin de négociation est un plugin qui ne fait pas le travail lui-même mais sélectionne le meilleur parmi un ensemble de plugins en fonction de votre plateforme et de votre environnement. (Dans le cas de Alien::Build::Plugin::PkgConfig::Negotiate, il peut choisir d'utiliser des outils en ligne de commande, une implémentation en Perl pur (PkgConfig) ou libpkgconf, selon ce qui est disponible). Lors de l'utilisation de plugins de négociation, vous pouvez omettre le suffixe "::Negotiate". Comme vous pouvez le voir, utiliser le plugin ici est un avantage car il est plus fiable que de simplement spécifier une commande qui pourrait ne pas être installée ! Ensuite,

nous

utilisons le plugin de négociation de téléchargement. C'est aussi mieux que la version ci-dessus, car encore une fois, "wget" pourrait ne pas être installé sur le système cible. De plus, vous pouvez spécifier une URL qui sera analysée pour en extraire les liens et utiliser

la

version la plus récente. Nous utilisons le plugin de négociation Extract pour utiliser soit des outils en ligne de commande, soit des bibliothèques Perl pour

extraire

l'archive une fois qu'elle est téléchargée. Enfin, nous utilisons le plugin Autoconf (Alien::Build::Plugin::Build::Autoconf). C'est beaucoup plus sophistiqué et plus fiable que dans l'exemple précédent, pour un certain nombre de raisons. Cette version fonctionnera même sur Windows, en supposant que la bibliothèque

les

bibliothèques dynamiques vs. statiques Si vous utilisez votre Alien pour construire un module XS, il est important que vous utilisiez des bibliothèques statiques si possible. Si vous avez un paquet qui refuse de construire une

bibliothèque

statique, alors vous pouvez utiliser Alien:: Role::Dino. En fait, laissez-moi revenir en arrière une minute. Pour une installation "share", il est préférable d'utiliser des bibliothèques statiques pour construire votre extension XS. C'est parce que si votre Alien est mis à jour vers une nouvelle version, cela peut casser vos modules XS existants. Pour une installation "system", les bibliothèques partagées

sont

généralement préférables car vous pouvez souvent obtenir des correctifs de sécurité sans avoir à reconstruire quoi que ce soit dans le monde de perl. Si vous avez regardé attentivement les sections « Utilisation de commandes » et « Utilisation de plugins » ci-dessus, vous avez peut-être remarqué que nous nous

sommes

efforcés autant que possible de dire à Autotools de construire uniquement des bibliothèques statiques en utilisant la commande "--disable-shared". Le plugin Autoconf fait aussi cela par défaut. Cependant, parfois vous aurez un paquet qui

construit 
les deux, ou peut-être que vous
voulez que les
bibliothèques

statiques et dynamiques fonctionnent à la fois avec XS et FFI. Dans ce cas, il y a le plugin Alien::Build::Plugin::Gather::IsolateDynamic. use alienfile; ... plugin 'Gather::IsolateDynamic'; Ce qu'il fait, c'est qu'il déplace les bibliothèques dynamiques (généralement .so sous Unix et .DLL sous Windows) à un endroit où elles peuvent être trouvées par FFI et où elles ne seront pas utilisées par le compilateur pour construire XS.

Cela

ne fait généralement aucun mal d'inclure ce plugin, donc si vous débutez, vous pourriez vouloir l'ajouter quand même. On pourrait dire qu'il aurait dû être le comportement par défaut depuis le début. Si vous avez déjà publié un Alien qui n'isole pas ses bibliothèques dynamiques, alors vous pourriez avoir des échecs avec d'anciens aliens mis à jour car le répertoire share n'est pas nettoyé par défaut (c'est peut-être un bug de conception dans la façon dont fon

ctionnent les répertoires share, mais c'e
st une caractéristique de longue date)

. Une solution de contournement pour

cela

est d'utiliser la propriété "clean_install" sur Alien::Build::MM, qui nettoiera le répertoire share lors de la mise à jour et vous évitera peut-être beaucoup de tracas. Une fois que vous avez un alienfile fonctionnel, vous pouvez écrire votre "Makefile

my $abmm = Alien::Build::MM->new;

WriteMakefile($abmm->mm_args(

  DISTNAME           => 'Alien-Libfoo',
  NAME               => 'Alien::Libfoo',
  VERSION_FROM       => 'lib/Alien/Libfoo.pm',
  CONFIGURE_REQUIRES => {

  },
  BUILD_REQUIRES => {
    'Alien::Build::MM' => 0,
  },

));

  $abmm->mm_postamble;
}

Configuration non

standard

Alien::Base prend en charge la plupart des éléments dont votre Alien aura besoin, comme les indicateurs du compilateur (cflags), les indicateurs de l'éditeur de liens (libs) et le répertoire des binaires (bin_dir). Votre bibliothèque ou outil peut avoir d'autres éléments de configuration qui ne sont pas pris en charge par défaut. Vous pouvez stocker les valeurs dans l'alienfile dans les propriétés d'exécution (runtime)

: 
gather [
  # standard:
  [ 'foo-config --version libfoo', \'%{.runtime.version}' ],
  [ 'foo-config --cflags  libfoo', \'%{.runtime.cflags}'  ],
  [ 'foo-config --libs    libfoo', \'%{.runtime.libs}'    ],
  # non-standard
  [ 'foo-config --bar-baz libfoo', \'%{.runtime.bar_baz}' ],
]
;

puis vous pouvez les exposer dans votre sous-classe d'Alien::Base

: 
package Alien::Libfoo;

use strict;
use warnings;
u
se parent qw( Alien::Base ); sub bar_baz { my($s
elf) = @_; $self->runtime_prop->{bar_baz}, }; 1;

Vous pouvez également écrire des tests spécifiquement pour FFI::Platypus, si votre alien va être utilisé pour écrire des liaisons FFI. (le test ci-dessous est l'équivalent FFI de l'exemple XS ci-dessus)

. 
use Test2::V0;
use Test::Alien;
use Alien::Libfoo;

alien_ok 'Alien::Libfoo';
ffi_ok { symbols => [ 'something' ] }, with_subtest {
  # $ffi is an instance of FFI::Platypus with the lib
  # set appropriately.
  my($ffi) = @_;
  my $something = $ffi->function( something => [] => 'int' );
  is $something->call(), 1, 'Foo::something() returns 1';
}
;

Si vous utilisez "ffi_ok", vous devez vous assurer que votre alien produit de manière fiable des bibliothèques dynamiques. Si ce n'est pas cohérent (si par exemple certaines plateformes ont tendance à ne pas fournir ou construire de bibliothèques dynamiques), vous pouvez vérifier que "dynamic_libs" ne retourne pas une liste

vide. 
...
alien_ok 'Alien::Libfoo';
SKIP: {
  skip "This test requires a dynamic library"
    unless Alien::Libfoo->dynamic_libs;
  ffi_ok { symbols [ 'something' ] }, with_subtest {
    ...
  };
}

Plus de détails sur les tests des modules Alien peuvent être trouvés dans la documentation de Test::

Alien.

Vous pouvez également exécuter les tests qui accompagnent le paquet que vous transformez en alien, en utilisant un bloc "test" dans votre alienfile. Gardez à l'esprit que certains paquets utilisent des outils de test ou ont d'autres prérequis qui ne seront pas disponibles sur les machines de vos utilisateurs lorsqu'ils tenteront d'installer votre alien. Vous ne voulez donc pas ajouter aveuglément un bloc test sans vérifier quels sont les prérequis. Pour les paquets de style Autoconf, vous testez généralement un paquet en utilisant la commande "make check"

: 
use alienfile;

plugin 'PkgConfig' => 'libfoo';

share {
  ... # standard build steps.
  test [ '%{make} check' ];
}
;
