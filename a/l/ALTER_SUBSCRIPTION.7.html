ALTER SUBSCRIPTION(7) Documentation PostgreSQL 18.1 ALTER SUBSCRIPTION(7)

NOM

ALTER_SUBSCRIPTION - modifie la définition d'une souscription

SYNOPSIS

ALTER SUBSCRIPTION name CONNECTION 'conninfo'
ALTER SUBSCRIPTION name SET PUBLICATION publication_name [, ...] [ WITH ( publication_option [= value] [, ... ] ) ]
ALTER SUBSCRIPTION name ADD PUBLICATION publication_name [, ...] [ WITH ( publication_option [= value] [, ... ] ) ]
ALTER SUBSCRIPTION name DROP PUBLICATION publication_name [, ...] [ WITH ( publication_option [= value] [, ... ] ) ]
ALTER SUBSCRIPTION name REFRESH PUBLICATION [ WITH ( refresh_option [= value] [, ... ] ) ]
ALTER SUBSCRIPTION name ENABLE
ALTER SUBSCRIPTION name DISABLE
ALTER SUBSCRIPTION name SET ( subscription_parameter [= value] [, ... ] )
ALTER SUBSCRIPTION name SKIP ( skip_option = value )
ALTER SUBSCRIPTION name OWNER TO { new_owner | CURRENT_ROLE | CURRENT_USER | SESSION_USER }
ALTER SUBSCRIPTION name RENAME TO new_name

DESCRIPTION

ALTER SUBSCRIPTION peut modifier la plupart des propriétés de la souscription qui peuvent être spécifiées dans CREATE SUBSCRIPTION (CREATE_SUBSCRIPTION(7)).

Vous devez être propriétaire de la souscription pour utiliser ALTER SUBSCRIPTION. Pour renommer une souscription ou en modifier le propriétaire, vous devez avoir la permission CREATE sur la base de données. De plus, pour modifier le propriétaire, vous devez pouvoir exécuter SET ROLE vers le nouveau rôle propriétaire. Si la souscription a password_required=false, seuls les superutilisateurs peuvent la modifier.

Lors du rafraîchissement d'une publication, nous supprimons les relations qui ne font plus partie de la publication et nous supprimons également les emplacements de synchronisation de table s'il y en a. Il est nécessaire de supprimer ces emplacements afin que les ressources allouées pour la souscription sur l'hôte distant soient libérées. Si, en raison d'une panie réseau ou d'une autre erreur, PostgreSQL ne peut pas supprimer les emplacements, une erreur sera signalée. Pour continuer dans cette situation, l'utilisateur doit soit réessayer l'opération, soit dissocier l'emplacement de la souscription et supprimer la souscription comme expliqué dans DROP SUBSCRIPTION (DROP_SUBSCRIPTION(7)).

Commandes ALTER SUBSCRIPTION ... REFRESH PUBLICATION, ALTER SUBSCRIPTION ... {SET|ADD|DROP} PUBLICATION ... avec l'option refresh définie à true, ALTER SUBSCRIPTION ... SET (failover = true|false) et ALTER SUBSCRIPTION ... SET (two_phase = false) ne peuvent pas être exécutées à l'intérieur d'un bloc de transaction.

Commandes ALTER SUBSCRIPTION ... REFRESH PUBLICATION et ALTER SUBSCRIPTION ... {SET|ADD|DROP} PUBLICATION ... avec l'option refresh définie à true ne peuvent pas non plus être exécutées lorsque la souscription a le commit à deux phases activé, sauf si copy_data est à false. Consultez la colonne subtwophasestate de pg_subscription pour connaître l'état réel à deux phases.

PARAMÈTRES

name

Le nom d'une souscription dont les propriétés doivent être modifiées.

CONNECTION 'conninfo'

Cette clause remplace la chaîne de connexion initialement définie par CREATE SUBSCRIPTION (CREATE_SUBSCRIPTION(7)). Voir cette page pour plus d'informations.

SET PUBLICATION publication_name
ADD PUBLICATION publication_name
DROP PUBLICATION publication_name

Ces formes modifient la liste des publications souscrites. SET remplace toute la liste des publications par une nouvelle liste, ADD ajoute des publications supplémentaires à la liste des publications, et DROP supprime les publications de la liste des publications. Nous permettons de spécifier des publications inexistantes dans les variantes ADD et SET afin que les utilisateurs puissent les ajouter ultérieurement. Voir CREATE SUBSCRIPTION (CREATE_SUBSCRIPTION(7)) pour plus d'informations. Par défaut, cette commande agit également comme REFRESH PUBLICATION.

publication_option spécifie des options supplémentaires pour cette opération. Les options prises en charge sont :

refresh (booléen)

Lorsqu'il est à false, la commande ne tentera pas de rafraîchir les informations de table. REFRESH PUBLICATION devrait alors être exécutée séparément. La valeur par défaut est true.

De plus, les options décrites sous REFRESH PUBLICATION peuvent être spécifiées pour contrôler l'opération de rafraîchissement implicite.

REFRESH PUBLICATION

Récupère les informations de table manquantes auprès de l'éditeur. Cela démarrera la réplication des tables qui ont été ajoutées aux publications souscrites depuis CREATE SUBSCRIPTION ou la dernière invocation de REFRESH PUBLICATION.

refresh_option spécifie des options supplémentaires pour l'opération de rafraîchissement. Les options prises en charge sont :

copy_data (booléen)

Indique s'il faut copier les données préexistantes dans les publications qui sont souscrites lorsque la réplication démarre. La valeur par défaut est true.

Les tables déjà souscrites ne sont pas copiées, même si la clause WHERE du filtre de lignes d'une table a été modifiée depuis.

Voir Notes pour les détails sur la manière dont copy_data = true peut interagir avec le paramètre origin.

Voir le paramètre binary de CREATE SUBSCRIPTION pour les détails sur la copie des données préexistantes au format binaire.

ENABLE

Active une souscription précédemment désactivée, en démarrant le travailleur de réplication logique à la fin de la transaction.

DISABLE

Désactive une souscription en cours d'exécution, en arrêtant le travailleur de réplication logique à la fin de la transaction.

SET ( subscription_parameter [= value] [, ... ] )

Cette clause modifie les paramètres initialement définis par CREATE SUBSCRIPTION (CREATE_SUBSCRIPTION(7)). Voir cette page pour plus d'informations. Les paramètres qui peuvent être modifiés sont slot_name, synchronous_commit, binary, streaming, disable_on_error, password_required, run_as_owner, origin, failover et two_phase. Seul un superutilisateur peut définir password_required = false.

Lors de la modification de slot_name, les valeurs des propriétés failover et two_phase de l'emplacement nommé peuvent différer des paramètres failover et two_phase correspondants spécifiés dans la souscription. Lors de la création de l'emplacement, assurez-vous que les propriétés failover et two_phase de l'emplacement correspondent à leurs paramètres correspondants de la souscription. Sinon, l'emplacement sur l'éditeur peut se comporter différemment de ce que ces options de souscription indiquent : par exemple, l'emplacement sur l'éditeur pourrait être synchronisé vers les serveurs de secours même lorsque l'option failover de la souscription est désactivée, ou il pourrait être désactivé pour la synchronisation même lorsque l'option failover de la souscription est activée.

Les paramètres failover et two_phase ne peuvent être modifiés que lorsque la souscription est désactivée.

Lors de la modification de two_phase de true à false, le processus backend signale une erreur si des transactions préparées effectuées par le travailleur de réplication logique (depuis que le paramètre two_phase était encore à true) sont trouvées. Vous pouvez résoudre les transactions préparées sur le nœud éditeur, ou les annuler manuellement sur le souscripteur, puis réessayer. Les transactions préparées par le travailleur de réplication logique correspondant à une souscription particulière ont le motif suivant : « pg_gid_%u_%u » (paramètres : oid de la souscription oid, identifiant de transaction distant xid). Pour résoudre de telles transactions manuellement, vous devez annuler toutes les transactions préparées avec les identifiants de souscription correspondants dans leurs noms. Les applications peuvent vérifier pg_prepared_xacts pour trouver les transactions préparées requises. Après que l'option two_phase a été changée de true à false, l'éditeur répliquera à nouveau les transactions lorsqu'elles seront validées.

SKIP ( skip_option = value )

Ignore l'application de toutes les modifications de la transaction distante. Si les données entrantes violent des contraintes, la réplication logique s'arrêtera jusqu'à ce que le problème soit résolu. En utilisant la commande ALTER SUBSCRIPTION ... SKIP , le travailleur de réplication logique ignore toutes les modifications de données dans la transaction. Cette option n'a aucun effet sur les transactions déjà préparées en activant two_phase sur le souscripteur. Après que le travailleur de réplication logique a ignoré avec succès la transaction ou a terminé une transaction, le LSN (stocké dans pg_subscription.subskiplsn) est effacé. Voir la section 29.7 pour les détails sur les conflits de réplication logique.

skip_option spécifie les options pour cette opération. L'option prise en charge est :

lsn (pg_lsn)

Indique le LSN de fin de la transaction distante dont les modifications doivent être ignorées par le travailleur de réplication logique. Le LSN de fin est le LSN à laquelle la transaction est soit validée, soit préparée. Le saut de sous-transactions individuelles n'est pas pris en charge. Régler sur NONE réinitialise le LSN.

new_owner

Le nom d'utilisateur du nouveau propriétaire de l'abonnement.

new_name

Le nouveau nom de l'abonnement.

Lorsqu'on spécifie un paramètre de type booléen, la partie value peut être omise, ce qui équivaut à spécifier TRUE.

EXEMPLES

Changer la publication souscrite par un abonnement en insert_only :

ALTER SUBSCRIPTION mysub SET PUBLICATION insert_only;

Désactiver (arrêter) l'abonnement :

ALTER SUBSCRIPTION mysub DISABLE;

COMPATIBILITÉ

ALTER SUBSCRIPTION est une extension PostgreSQL.
