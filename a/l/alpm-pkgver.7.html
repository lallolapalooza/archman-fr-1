Le format pkgver est un format de version, utilisé pour représenter les informations de version amont. Ce format est utilisé dans les scripts de construction ou les formats de fichiers pour la description ou la reproduction des données de

Comportement de

comparaison

Deux chaînes de version sont comparées en les divisant d'abord chacune en leurs segments et sous-segments basés sur l' algorithme de division des chaînes de version. Les segments et sous-segments des deux côtés sont ensuite comparés séquentiellement les uns aux autres. La comparaison se termine si un segment ou un sous-segment d'un côté est considéré comme plus récent ou plus ancien que celui de l'autre, ou s'il n'y a plus de segments et de sous-segments à comparer. Bien qu'il y ait quelques rares exceptions à cette règle générale, qui sont listées dans la section Comparaison pour les cas

particuliers.

Les règles générales de comparaison suivantes s'appliquent

  • Les chaînes ne contenant que des caractères numériques sont comparées comme des entiers. Ici, le plus grand nombre est considéré comme le plus récent (par ex. 2 >

NAME

alpm-pkgver — version comparison

DESCRIPTION

The alpm package manager uses a version comparison algorithm to determine whether one package version is newer or older than another. This comparison is performed by splitting version strings into segments, separated by delimiters such as dots (.), dashes (-), or underscores (_). Each segment is then further split into sub-segments consisting of alphanumeric characters. These sub-segments are compared lexicographically.

The comparison proceeds segment by segment. Within each segment, sub-segments are compared. Numerical sub-segments are treated as numbers, while alphanumeric sub-segments are compared lexicographically.

Special cases exist for handling differences in the number of segments or sub-segments, multiple consecutive delimiters, and trailing delimiters.

The primary algorithm used is inspired by the one found in rpmvercmp. The behavior concerning special cases can be surprising and is detailed below.

EXAMPLES

Basic comparison

Segments are compared sequentially. If the first differing segments or sub-segments are found, the comparison result is determined.

alpha0 < beta0

The sub-segments alpha and beta are compared by applying simple string ordering, which results in beta > alpha The comparison concludes with alpha0 < beta0. The last sub-segment is not considered.

alpha1 < alpha02

The first sub-segments alpha and alpha are equal. The second sub-segments 1 and 02 are compared and result in 1 < 2. The comparison concludes with alpha1 < alpha02.

1alpha0 < 2alpha0

The first sub-segments 1 and 2 are compared, resulting in 1 < 2. The comparison concludes with 1alpha0 < 2alpha0. The other sub-segments are not considered.

alpha1 < alpha.0

The characters in the first sub-segment alpha and the first segment alpha are equal. This leads to the special case of a subsequent sub-segment 1 and a new segment 0 being compared. In this special case, the new segment is always considered newer and the contents of the sub-segment are ignored. As a result, the comparison concludes with alpha1 < alpha.0. The second sub-segment (1) of alpha1 is not considered.

Comparison for special cases

The version comparison algorithm offers a few (arguably surprising) special cases, that require further expansion.

Multiple delimiters between segments

When looking at the delimiters between segments in two version strings, the amount of delimiters is deciding in whether one or the other version string is considered newer. If a version string has multiple consecutive delimiters between two segments and there are more delimiters present than in its counterpart version string at the same position, the first version string is always considered newer.

NOTE: The reason for this behavior is unclear and it is not certain whether it has been added intentionally.

Examples:

1...0 > 1.2

For 1...0 and 1.2, the first segments 1 and 1 are equal. The second segments 0 and 2 are not equal, but the segment in the first version string is preceded by three dots (...) while the other is only preceded by one dot (.). The comparison concludes with 1...0 > 1.2. The contents of the second segments are not considered.

Differing amounts of segments or sub-segments

Examples:

1 < 1.0
1 < 1.foo

The first segments 1 and 1 are equal. The first version string then ends while the second has another segment. An additional segment always leads to the version string to be considered newer than the one with no additional segment (this also applies to additional alphanumeric segments). The comparison concludes with 1 < 1.0 and 1 < 1.foo.

1.0 > 1.0foo.2

The first segments 1 and 1 are equal. The next sub-segments 0 and 0 are also equal. The first version string then ends, while the second has another sub-segment foo. As that sub-segment contains only alphabetic characters, it is considered older. This special case was historically introduced to catch alpha/beta releases that were often marked via a alpha suffix without delimiter such as 1.0.0alpha.1. However, this is no longer relevant with modern semantic versioning. As a result, the comparison concludes with 1.0 > 1.0foo.2. The last segment of 1.0foo.2 is not considered.

1.foo < 1.foo2

The first segments 1 and 1 are equal. The next sub-segments foo and foo are also equal. The first version string then ends, while the second has another sub-segment 2. As that sub-segment is numerical, it is considered newer. The comparison concludes with 1.foo < 1.foo2.

Version strings with trailing delimiters

Some version strings contain trailing delimiters. The original rpmvercmp implementation explicitly defines comparison on versions with trailing delimiters as undefined behaviour. vercmp adopted the algorithm, but never made any statements regarding such edge-cases. Hence, it is believed that the following rules are not intended behavior and may therefore be subject to change!

For the sake of completeness, the behavior has been analyzed, re-implemented and documented:

Examples:

1... == 1.

The first segments 1 and 1 are equal. Both version strings then end with an arbitrary amount of trailing delimiters. Counterintuitively, the amount of trailing delimiters does not matter in this case and they are always considered equal. The comparison concludes with 1... == 1..

1. > 1.foo.2

The first segments 1 and 1 are equal. The first version string then ends with a delimiter, while the second has another segment foo. For the second segment of the first version, imagine using an empty string. Because foo is alphabetical, it is automatically considered older, although it is not practically compared to another segment. This logic is a remnant of the special case that was historically introduced to catch alpha/beta releases, which were often marked via a alpha suffix such as 1.0.0alpha.1. The comparison concludes with 1. > 1.foo.2. The remaining segment of 1.foo.2 is not considered.

1. < 1.2
1. < 1.2foo

The first segments 1 and 1 are equal. The first version string then ends with a delimiter, while the second version has a segment/sub-segment 2. Because 2 is a numerical value, it is automatically considered newer, as it is not compared to an empty segment. The comparison concludes with 1. < 1.2 and 1. < 1.2foo.

1.alpha. < 1.alpha0

The next sub-segments alpha and alpha are also equal. The first version string then ends with a delimiter, while the second has a sub-segment 0. As 0 is numerical, it’s considered newer, as it is compared to an empty segment. The comparison concludes with 1.alpha. < 1.alpha0.
