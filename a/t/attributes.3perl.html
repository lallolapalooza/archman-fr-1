DESCRIPTIO

N

Les déclarations et définitions de sous-routines peuvent éventuellement avoir des listes d'attributs qui leur sont associées. (Les déclarations "my" de variables peuvent aussi en avoir, mais voir l'avertissement ci-dessous.) Perl traite ces déclarations en passant certaines informations sur le lieu d'appel et sur l'objet déclaré, avec la liste d'attributs, à ce module. En particulier, le premier exemple ci-dessus est équivalent à ce qui suit

: 
use attributes __PACKAGE__, \&foo,
'method';

Le deuxième exemple du synopsis fait quelque chose d'équivalent à ceci

: 
use attributes ();
my ($x,@y,%z);
attributes::->import(__PACKAGE__, \$x, 'Bent');
attributes::->import(__PACKAGE__, \@y, 'Bent');
attributes::->import(__PACKAGE__, \%z, 'Bent');
($x,@y,%z) =
1;

Oui, c'est beaucoup

d'expansion.

AVERTISSEMENT : les déclarations d'attributs pour les variables sont encore en cours d'évolution. La sémantique et les interfaces de telles déclarations pourraient changer dans des versions futures. Elles sont présentes à des fins d'expérimentation sur ce que la sémantique devrait être. Ne vous fiez pas à l'implémentation actuelle de cette

fonctionnalité.

Il n'y a actuellement que quelques attributs gérés par Perl lui-même (ou directement par ce module, selon la façon dont vous le voyez.) Cependant, des attributs spécifiques à un paquet sont permis par un mécanisme d'extension. (Voir « Gestion des attributs spécifiques au paquet » ci-dessous.

)

La définition des attributs de sous-routine se fait à la compilation. Les attributs de variables dans les déclarations "our" sont également appliqués à la compilation. Cependant, les variables "my" reçoivent leurs attributs à l'exécution. Cela signifie que vous devez atteindre le composant d'exécution de la variable "my" avant que ces attributs soient appliqués. Par exemple

: 
my $x : Bent = 42 if
0;

n'assignera ni 42 à $x ni n'appliquera l'attribut "Bent" à la

variable.

Une tentative de définir un attribut non reconnu est une erreur fatale. (L'erreur peut être interceptée, mais elle arrête quand même la compilation à l'intérieur de cet "eval".) Définir un attribut dont le nom est entièrement en lettres minuscules et qui n'est pas un attribut intégré (comme "foo") entraînera un avertissement avec -w ou "use warnings 're

served'".

Ce que fait

"import"

Dans la description, il est mentionné

que 
sub foo :
method;

est équivalent

à 
use attributes __PACKAGE__, \&foo,
'method';

Comme vous le savez peut-être, cela appelle la fonction "import" de "attributes" à la compilation avec ces paramètres : 'attributes', le nom du paquet de l'appelant, la référence vers le code et

'method'. 
attributes->import( __PACKAGE__, \&foo, 'method' )
;

Vous voulez donc savoir ce que "import" fait réellement

?

Tout d'abord, "import" obtient le type du troisième paramètre ('CODE' dans ce cas). "attributes.pm" vérifie s'il existe une sous-routine appelée "MODIFY_<reftype>_ATTRIBUTES" dans l'espace de noms de l'appelant (ici : 'main'). Dans ce cas, une sous-routine "MODIFY_CODE_ATTRIBUTES" est requise. Ensuite, cette méthode est appelée pour vérifier si vous avez utilisé un « mauvais attribut ». L'appel de sous-routine dans cet exemple ressemblerait

à 
MODIFY_CODE_ATTRIBUTES( 'main', \&foo, 'method' )
;

"MODIFY_<reftype>_ATTRIBUTES" doit retourner une liste de tous les « mauvais attributs ». S'il y a des mauvais attributs, "import" émet un message d'erreur

fatal.

(Voir « Gestion des at

tributs spécifiques au
paquet » ci-dessous.)

Attributs

intégrés

Voici les attributs intégrés pour les sous-routines

lval
ue
Indique que la sous-routine référencée est un lvalue valide et peut recevoir une assignation. La sous-routine doit retourner une valeur modifiable telle qu'une variable scalaire, comme décrit dans perlsub.

Ce module permet de définir cet attribut sur une sous-routine qui est déjà définie. Pour les sous-routines Perl (les XSUBs sont acceptables), cela peut ou non faire ce que vous voulez, selon le code à l'intérieur de la so

us-routine, avec des détails susceptibles de changer dans les futures versions de Perl. Vous pouvez rencontrer des problèmes avec le contexte lvalue qui n'est pas correctement propagé dans la sous-routine, ou peut-être mê
me des échecs d'assertion. Pour cette raison, un avertissement est émis si les avertissements sont activés. En d'autres termes, vous ne devriez le faire que si vous savez vraiment ce que vous faites. Vous avez été averti.
meth
od
Indique que la sous-routine référencée est une méthode. Une sous-routine ainsi marquée ne déclenchera pas l'avertissement « Ambiguous call resolved as CORE::%s
».
prototype(.
.)
L'attribut "prototype" est un moyen alternatif de spécifier un prototype sur une sous-routine. Le prototype désiré est entre les parenthèses.

Le prototype de l'attribut est assigné à la sous-routine immédiatement après le prototype de la sous-routine, ce qui signifie que si les deux sont déclarés en même temps, le prototype défini traditionnellement est ignoré. En d'autres termes, "sub foo($$) : prototype(@) {}" est indiscernable de "sub foo(@

){}".

Si les avertissements illegalproto sont activé

s, le prototype déclaré à l'intérieur
de cet attribut sera vérifié à la compilation.
con
st
Cet attribut expérimental, introduit dans Perl 5.22, ne s'applique qu'aux sous-routines anonymes. Il fait que la sous-routine est appelée dès que l'expression "sub" est évaluée. La valeur de retour est cap
turée et transformée en u
ne sous-routine constante.

Gestion des attributs spécifiques au paquet

NOM

attributes - attributs de sous-routine et de variable

SYNTAXIS

  use attributes;
  use attributes qw(get reftype);

  sub foo : Attr1 Attr2(arg1, arg2) ;
  my $bar : Attr3;

DESCRIPTION

ATTENTION : les mécanismes décrits ici sont encore expérimentaux. Ne vous fiez pas à l'implémentation actuelle. En particulier, il n'y a aucune disposition pour appliquer des attributs de package aux copies 'clonées' de sous-routines utilisées comme fermetures (closures). (Voir "Making References" dans perlref pour des informations sur les fermetures.) La gestion des attributs spécifiques aux packages peut changer de manière incompatible dans une future version.

Lorsqu'une liste d'attributs est présente dans une déclaration, une vérification est effectuée pour voir si un gestionnaire d'attribut 'modify' est présent dans le package approprié (ou son arbre d'héritage @ISA). De même, lorsque "attributes::get" est appelé sur une référence valide, une vérification est effectuée pour un gestionnaire d'attribut 'fetch' approprié. Voir "EXEMPLES" pour voir comment la détermination du "package approprié" fonctionne.

Les noms des gestionnaires sont basés sur le type sous-jacent de la variable déclarée ou de la référence passée. Parce que ces attributs sont associés à des déclarations de sous-routines ou de variables, cela ignore délibérément toute possibilité d'être béni (blessed) dans un package. Ainsi, une déclaration de sous-routine utilise "CODE" comme son type, et même une référence de hash bénie utilise "HASH" comme son type.

Les méthodes de classe invoquées pour modifier et récupérer sont les suivantes :

FETCH_type_ATTRIBUTES
Cette méthode est appelée avec deux arguments : le nom du package pertinent, et une référence vers une variable ou une sous-routine pour laquelle des attributs définis par le package sont désirés. La valeur de retour attendue est une liste d'attributs associés. Cette liste peut être vide.
MODIFY_type_ATTRIBUTES
Cette méthode est appelée avec deux arguments fixes, suivis de la liste des attributs de la déclaration pertinente. Les deux arguments fixes sont le nom du package pertinent et une référence vers la sous-routine ou la variable déclarée. La valeur de retour attendue est une liste d'attributs qui n'ont pas été reconnus par ce gestionnaire. Notez que cela permet à une classe dérivée de déléguer un appel à sa classe de base, puis d'examiner uniquement les attributs que la classe de base n'a pas déjà gérés pour elle.

L'appel à cette méthode est actuellement effectué *pendant* le traitement de la déclaration. En particulier, cela signifie qu'une référence de sous-routine sera probablement pour une sous-routine non définie, même si cette déclaration fait en fait partie de la définition.

Appeler attributes::get() depuis la portée d'une déclaration de package nulle "package ;" pour une référence de variable non bénie ne fournira aucun nom de package de départ pour la recherche de la méthode 'fetch'. Par conséquent, cette circonstance n'entraînera pas d'appel de méthode pour les attributs définis par le package. Une sous-routine nommée sait à quelle entrée de table de symboles elle appartient (ou appartenait à l'origine), et elle utilisera le package correspondant. Une sous-routine anonyme connaît le nom du package dans lequel elle a été compilée (sauf si elle a également été compilée avec une déclaration de package nulle), et utilisera donc ce nom de package.

Syntaxe des listes d'attributs

Une liste d'attributs est une séquence de spécifications d'attributs, séparées par un espace blanc ou un deux-points (avec un espace blanc optionnel). Chaque spécification d'attribut est un nom simple, éventuellement suivi d'une liste de paramètres entre parenthèses. Si une telle liste de paramètres est présente, elle est analysée comme pour les règles de l'opérateur q(). (Voir "Quote and Quote-like Operators" dans perlop.) La liste de paramètres est passée telle quelle, cependant, et non comme pour q().

Quelques exemples de listes d'attributs syntaxiquement valides :

switch(10,foo(7,3))  :  expensive
Ugly('\(") :Bad
_5x5
lvalue method

Quelques exemples de listes d'attributs syntaxiquement invalides (avec annotation) :

switch(10,foo()             # La chaîne () n'est pas équilibrée
Ugly('(')                   # La chaîne () n'est pas équilibrée
5x5                         # "5x5" n'est pas un identifiant valide
Y2::north                   # "Y2::north" n'est pas un identifiant simple
foo + bar                   # "+" n'est ni un deux-points ni un espace blanc

EXEMPLES

Voici quelques exemples de déclarations syntaxiquement valides, avec une annotation expliquant comment elles sont résolues en interne en invocations de "use attributes" par perl. Ces exemples sont principalement utiles pour voir comment le "package approprié" est trouvé pour les recherches de méthodes possibles pour les attributs définis par le package.

1.
Code : 
package Canine;
package Dog;
my Canine $spot : Watchful ;
Effet : 
use attributes ();
attributes::->import(Canine => \$spot, "Watchful");
2.
Code : 
package Felis;
my $cat : Nervous;
Effet : 
use attributes ();
attributes::->import(Felis => \$cat, "Nervous");
3.
Code : 
package X;
sub foo : lvalue ;
Effet : 
use attributes X => \&foo, "lvalue";
4.
Code : 
package X;
sub Y::x : lvalue { 1 }
Effet : 
use attributes Y => \&Y::x, "lvalue";
5.
Code : 
package X;
sub foo { 1 }
package Y;
BEGIN { *bar = \&X::foo; }
package Z;
sub Y::bar : lvalue ;
Effet : 
use attributes X => \&X::foo, "lvalue";

Ce dernier exemple est purement à des fins de complétude. Vous ne devriez pas essayer de manipuler les attributs de quelque chose dans un package qui n'est pas le vôtre.

PLUS D'EXEMPLES

1.
sub MODIFY_CODE_ATTRIBUTES {
   my ($class,$code,@attrs) = @_;
   my $allowed = 'MyAttribute';
   my @bad = grep { $_ ne $allowed } @attrs;
   return @bad;
}
sub foo : MyAttribute {
   print "foo\n";
}
Cet exemple s'exécute. Au moment de la compilation, "MODIFY_CODE_ATTRIBUTES" est appelé. Dans cette sous-routine, nous vérifions si un attribut est interdit et nous renvoyons une liste de ces "mauvais attributs".

Comme nous renvoyons une liste vide, tout va bien.
2.
sub MODIFY_CODE_ATTRIBUTES {
   my ($class,$code,@attrs) = @_;
   my $allowed = 'MyAttribute';
   my @bad = grep{ $_ ne $allowed }@attrs;
   return @bad;
}
sub foo : MyAttribute Test {
   print "foo\n";
}
Cet exemple est interrompu au moment de la compilation car nous utilisons l'attribut "Test" qui n'est pas autorisé. "MODIFY_CODE_ATTRIBUTES" renvoie une liste contenant un seul élément ('Test').
