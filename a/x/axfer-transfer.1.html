AXFER-TRANSFER(1) Manuel des commandes générales AXFER-TRANSFER(1)

NOM

axfer-transfer - transfert de trames de données audio pour les périphériques et nœuds sonores.

SYNTAXE

axfer transfer direction [ options-communes ] [ options-backend ] [ chemin-fichier ]

axfer transfer direction [ options-communes ] [ options-backend ] -I | --separate-channels chemin-fichier ...

direction = capture | lecture

options-communes = ( lire la section OPTIONS )

options-backend = ( lire la section OPTIONS )

chemins-fichiers = ( lire la section OPTIONS )

DESCRIPTION

La sous-commande transfer de axfer effectue la transmission de trames de données audio pour les périphériques disponibles dans les backends pris en charge. Ce programme est essentiellement conçu pour utiliser les API d'alsa-lib (backend libasound) afin de gérer les périphériques sonores pris en charge par le sous-système sonore Linux (ALSA).

OPTIONS

Direction

capture
Fonctionne pour la transmission de capture.
lecture
Fonctionne pour la transmission de lecture.

Chemin-fichier

Le chemin du fichier est traité comme un chemin relatif au répertoire de travail courant au moment de l'exécution s'il n'est pas un chemin complet depuis la racine.

L'entrée ou la sortie standard est utilisée si le chemin du fichier n'est pas spécifié ou s'il est indiqué comme '-'.

Pour la transmission de lecture, le format du conteneur du chemin-fichier donné est détecté automatiquement et les métadonnées sont utilisées pour les paramètres du format d'échantillon, des canaux, du débit, de la durée. Si rien n'est détecté, le contenu du chemin de fichier donné est traité comme des données brutes. Dans ce cas, les paramètres doivent être indiqués comme options.

Plusieurs chemins-fichiers sont autorisés avec l'option -I | --separate-channels. Dans ce cas, l'entrée et la sortie standard ne sont pas disponibles. Le même chemin-fichier n'est pas autorisé, sauf pour les chemins listés ci-dessous :
- /dev/null
- /dev/zero
- /dev/full
- /dev/random
- /dev/urandom

Indique le nombre de trames de données audio par seconde. Ceci est requis pour la transmission de capture ou la transmission de lecture avec des fichiers incluant des données audio brutes. Indique le type de fichier. Ceci est requis pour la transmission de capture. Les types disponibles sont listés ci-dessous :

MODÈLE D'ORDONNANCEMEN

T

Dans la conception du noyau ALSA PCM, le temps d'exécution du sous-flux PCM prend en charge deux modes ; réveil par période et sans réveil par période. Ces deux modes correspondent à différents modèles d'ordonnancement

.

Modèle d'ordonnancement basé sur

IRQ

Par défaut, le mode réveil par période est utilisé. Dans ce mode, les pilotes dans le noyau doivent faire fonctionner le matériel pour générer une notification périodique pour la transmission des trames de données audio. L'intervalle de notification est équivalent à la même quantité de trames de données audio qu'une période du tampon, par rapport au temps

réel.

Dans un gestionnaire assigné à la notification, une fonction auxiliaire du noyau ALSA PCM est appelée pour mettre à jour une position vers la tête de la transmission matérielle, puis la comparer avec une position vers la tête de l'opération de l'application pour déterminer le dépassement/sous-flux (XRUN) et réveiller les processus

bloqués.

À cette fin, l'IRQ matériel du contrôleur pour le bus audio série tel que Inter-IC sound est généralement utilisé. Dans ce cas, le contrôleur génère l'IRQ selon la transmission sur le bus audio série. Dans le gestionnaire assigné à l'IRQ, une transmission par accès direct au média (DMA) est demandée entre la mémoire hôte dédiée et la mémoire du

périphérique.

Si le matériel cible ne prend pas en charge ce type de mécanisme, la notification périodique doit être émulée par n'importe quel minuteur ; par exemple hrtimer, minuteur du noyau. Les plugins PCM externes générés par le SDK de plugins PCM dans alsa-lib devraient également émuler le comportement

ci-dessus.

Dans ce mode, les applications PCM sont programmées selon la manière typique des opérations d'E/S. Elles exécutent des appels système bloquants pour lire/écrire des trames de données audio dans le tampon du sous-flux PCM, ou des appels système bloquants pour attendre qu'une trame de données audio soit disponible. Dans axfer , c'est appelé modèle d'ordonnancement basé sur IRQ et c'est un comportement par défaut. Les utilisateurs peuvent configurer explicitement ce mode en utilisant l'option --sched-model avec la valeur

i
rq.

Modèle d'ordonnancement basé sur

minuteur

Le mode sans réveil par période est un mode optionnel du temps d'exécution du sous-flux PCM. Le mode suppose une caractéristique spécifique du matériel et l'assistance du pilote dans le noyau et des applications PCM. Dans ce mode, les pilotes dans le noyau ne font pas fonctionner le matériel pour générer une notification périodique pour la transmission des trames de données audio. Le matériel devrait continuer automatiquement la transmission des trames de données audio sans opération périodique des pilotes ; par exemple selon une transmission DMA auto-déclenchée, une chaîne de descripteurs

enregistrés.

Dans ce mode, rien ne réveille les processus bloqués, par conséquent les applications PCM devraient être programmées sans aucune opération bloquante. Pour cette raison, ce mode est activé lorsque les applications PCM configurent explicitement le paramètre matériel pour le temps d'exécution du sous-flux PCM, pour empêcher le désordre des applications existantes. De plus, rien ne maintient la synchronisation pour la transmission des trames de données audio, par conséquent les applications PCM devraient gérer volontairement un minuteur pour mettre en file d'attente les trames de données audio dans le tampon du sous-flux PCM pour l'écoulement du temps. En outre, au lieu du pilote, l'application PCM devrait appeler une fonction auxiliaire du noyau ALSA PCM pour mettre à jour une position vers la tête de la transmission matérielle et vérifier le

XRUN.

Dans axfer , c'est appelé modèle d'ordonnancement basé sur minuteur et est disponible tant que le matériel/pilote assiste le temps d'exécution sans réveil par période. Les utilisateurs devraient définir explicitement ce mode en utilisant l'option --sched-model avec la valeur ti

mer.

Dans le modèle d'ordonnancement, les applications PCM doivent prendre en compte l'espace disponible sur le tampon PCM avec l'écoulement du temps, généralement en cédant le CPU et en attendant une réordonnancement. Pour la cession, un délai d'attente est

calculé pour un nombre préférable de trames PCM à traiter. C'est pratique pour un type d'applications, comme les serveurs de son. Quand un thread d'E/S du serveur attend le délai d'attente, les autres threads peuvent traiter les trames de données audio po
ur les clients du serveur. De plus, avec l'utilisation du rembobinage/avance, les applications peuvent obtenir une faible latence entre la position de transmission et la position de traitement même si elles utilisent des tampons PCM de grande taille.

Avantages et

problèmes

Idéalement, le modèle d'ordonnancement basé sur minuteur a quelques avantages par rapport au modèle d'ordonnancement basé sur IRQ. Premièrement, aucun contexte d'interruption n'est exécuté pour le sous-flux PCM. Le sous-flux PCM n'est géré que dans un contexte de processus. Pas besoin de s'inquiéter des conditions de course entre les contextes IRQ et processus. Cela réduit certaines préoccupations pour certains développeurs de pilotes et d'applications. Deuxièmement, le temps CPU n'est pas utilisé pour les gestionnaires sur le contexte d'interruption. Le temps CPU peut être dédié aux autres tâches. C'est bon d'un point de vue de système à partage de temps. Troisièmement, le matériel n'est pas configuré pour générer des interruptions. C'est bon d'un point de vue de réduction de la consommation globale d'énergie

possiblement.

Dans l'un ou l'autre modèle d'ordonnancement, le matériel devrait permettre aux pilotes de lire le nombre de trames de données audio transférées entre la mémoire dédiée et la mémoire du périphérique pour

le bus audio série. Cependant, dans le modèle d'ordonnancement basé sur minuteur, la granularité fine et la précision de la valeur sont importantes. En fait, le matériel effectue la transmission entre
la mémoire dédiée et la mémoire du périphérique pour un petit lot de trames de données audio ou d'octets. Dans une vue des applications PCM, la granularité dans la transmission actuelle est requise pou
r décider du délai d'attente correct pour chaque opération d'E/S. En tant que noyau Linux v4.21, l'interface ALSA PCM entre le noyau et l'espace utilisateur n'a pas de fonctionnalité pour le signaler.

CONCEPTIO

N

Structure

modulaire

Ce programme se compose de trois modules ; xfer , mapper et container . Chaque module possède une couche d'abstraction pour permettre l'implémentation

réelle. 
           --------     ----------     -------------
périphérique <-> | xfer | <-> | mapper | <-> | container | <-> fichier
           --------     ----------     -------------
            libasound    single         wav
            libffado     multiple       au
                                        voc
raw

Le module xfer effectue la transmission réelle vers les périphériques et les nœuds. Le module peut avoir plusieurs arrière-plans de transmission. En tant qu'arrière-plan par défaut, l'arrière-plan libasound est utilisé pour effectuer la transmission via les API de alsa-lib. Le module permet à chaque arrière-plan d'analyser ses propres options de ligne de

commande.

Le module container effectue la lecture/l'écriture des trames de données audio via un descripteur pour le fichier/flux du conteneur multimédia ou des données brutes. Le module détecte automatiquement le type de conteneur multimédia et analyse les paramètres dans ses métadonnées de l'en-tête de données. Actuellement, trois types de conteneurs multimédias sont pris en charge ; Microsoft/IBM RIFF/Wave ( wav ), Sparc AU ( au ) et Creative Technology voice ( voc ). De plus, un conteneur spécial est préparé pour les données audio brutes ( raw )

.

Le module mapper gère la disposition et l'alignement du tampon pour la transmission des trames de données audio. Le module a deux implémentations ; single et multiple . L'arrière-plan single utilise un seul conteneur pour construire le tampon. L'arrière-plan multiple utilise plusieurs

conteneurs pour
le construire.

Prise en charge de la copie des trames de données

audio

Entre le module xfer et le module mapper, un pointeur vers un tampon incluant les trames de données audio est passé. Ce tampon a deux formes pour l'ordre entrelacé et non entrelacé. Pour le premier, le pointeur pointe vers un seul tampon. Pour le second, le pointeur pointe vers un tableau dont chaque élément pointe vers un tampon. Entre le module mapper et le module container, un pointeur vers un seul tampon est passé car les conteneurs multimédias pris en charge, y compris le type brut, stockent les trames de données audio dans l'ordre

entrelacé.

Lors du passage des trames de données audio entre les modules, axfer est programmé pour éviter la copie d'un tampon à un autre autant que possible. Par exemple, dans certains scénarios ci-dessous, aucune copie n'a lieu entre les

modules.


- xfer(mmap/interleaved), mapper(single), container(any)
- xfer(mmap/non-inter

leaved), mapper(multi
ple), containers(any)
