DESCRIPTIO

N

access() vérifie si le processus appelant peut accéder au fichier path. Si path est un lien symbolique, il est

déréférencé.

Le mode spécifie le(s) test(s) d'accessibilité à effectuer, et est soit la valeur F_OK, soit un masque constitué du OU bit à bit d'un ou plusieurs de R_OK, W_OK et X_OK. F_OK teste l'existence du fichier. R_OK, W_OK, et X_OK testent si le fichier existe et accorde respectivement les permissions de lecture, d'écriture et

d'exécution.

Le test est effectué en utilisant le UID réel et le GID réel du processus appelant, plutôt que les identifiants effectifs comme c'est fait lors de la tentative réelle d'une opération (par ex., open(2)) sur le fichier. De même, pour l'utilisateur root, le test utilise l'ensemble des capacités permises plutôt que l'ensemble des capacités effectives ; et pour les utilisateurs non root, le test utilise un ensemble vide de

capacités.

Cela permet aux programmes set-user-ID et aux programmes dotés de capacités de déterminer facilement l'autorité de l'utilisateur appelant. En d'autres termes, access() ne répond pas à la question « puis-je lire/écrire/exécuter ce fichier ? ». Il répond à une question légèrement différente : « (en supposant que je suis un binaire setuid) l' utilisateur qui m'a invoqué peut-il lire/écrire/exécuter ce fichier ? », ce qui donne aux programmes set-user-ID la possibilité d'empêcher les utilisateurs malveillants de les faire lire des fichiers que les utilisateurs ne devraient pas pouvoir

lire.

Si le processus appelant est privilégié (c.-à-d. si son UID réel est zéro), alors un test X_OK réussit pour un fichier régulier si la permission d'exécution est activée pour le propriétaire du fichier, le groupe ou les

autres.

NOTES Avertissement : l'utilisation de ces appels pour vérifier si un utilisateur est autorisé à, par exemple, ouvrir un fichier avant de le faire réellement à l'aide de open(2) crée une faille de sécurité, car l'utilisateur pourrait exploiter le court intervalle de temps entre la vérification et l'ouverture du fichier pour le manipuler. Pour cette raison, l'utilisation de cet appel système devrait être évitée. (Dans l'exemple décrit ci-dessus, une alternative plus sûre serait de basculer temporairement l'identifiant utilisateur effectif du processus vers l'identifiant

réel, puis d'appeler

open(2).) access() déréférence toujours les liens symboliques. Si vous devez vérifier les permissions sur un lien symbolique, utilisez faccessat() avec l

e drapeau

AT_SYMLINK_NOFOLLOW. Ces appels renvoient une erreur si l'un des types d'accès dans mode est refusé, même si certains des autres types d'accès

dans

mode sont autorisés. Un fichier n'est accessible que si les permissions sur chacun des répertoires dans le préfixe de chemin de path accordent l'accès de recherche (c'est-à-dire d'exécution). Si un répertoire est inaccessible, alors

l'appel

access() échoue, quelles que soient les permissions sur le fichier lui-même. Seuls les bits d'accès sont vérifiés, pas le type ou le contenu du fichier. Par conséquent, si un répertoire est trouvé comme étant inscriptible, cela signifie probablement que des fichiers peuvent être créés dans le répertoire, et non que le répertoire peut être écrit comme un fichier. De même, un fichier DOS peut être signalé comme exécutable,

mais l'appel

execve(2)

échouera
toujours.

Ces appels peuvent ne pas fonctionner correctement sur les systèmes de fichiers NFSv2 avec la correspondance UID activée, car la correspondance UID est effectuée sur le serveur et masquée au client, qui vérifie les permissions. (Les versions NFS 3 et supérieures effectuent la vérification sur le

serveur.) Des problèmes similaires peuvent survenir avec les montages FUSE.

ANOMALIES Parce que l'appel système faccessat() du noyau Linux ne prend pas en charge un argument flags, la fonction wrapper faccessat() fournie dans glibc 2.32 et antérieurs émule la fonctionnalité requise en utilisant une combinaison de l'appel système faccessat() et de fstatat(2). Cependant, cette émulation ne tient pas compte des ACL. À partir de glibc 2.33, la fonction wrapper évite cette anomalie en utilisant l'appel

système

faccessat2() lorsqu'il est fourni par le noyau sous-jacent. Dans Linux 2.4 (et antérieur), il y a une certaine étrangeté dans le traitement des tests X_OK pour le superutilisateur. Si toutes les catégories de permission d'exécution sont désactivées pour un fichier qui n'est pas un répertoire, alors le seul test access() qui renvoie -1 est lorsque mode est spécifié comme X_OK ; si R_OK ou W_OK est également spécifié dans mode,

alors

access() renvoie 0 pour de tels fichiers. Les premières versions de Linux 2.6 (jusqu'à et y compris Linux 2.6.3) se comportaient également de la même manière que Linux 2.4. Avant Linux 2.6.20, ces appels ignoraient l'effet du drapeau MS_NOEXEC s'il était utilisé pour mount(2) le système de fichiers sous-j

acent. Depuis Linux
2.6.20, le drapeau

MS_NOEXEC est

honoré.
