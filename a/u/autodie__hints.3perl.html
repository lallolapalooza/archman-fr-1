DESCRIPTIO

N

Introductio

n

Le pragma autodie est très intelligent lorsqu'il s'agit de travailler avec les fonctions intégrées de Perl. Le comportement de ces fonctions est fixe, et "autodie" sait exactement comment elles tentent de signaler un

échec.

Mais qu'en est-il des sous-routines définies par l'utilisateur dans les modules ? Si vous utilisez "autodie" sur une sous-routine définie par l'utilisateur, alors il suppose le comportement suivant pour démontrer un échec

:
  • Une valeur fausse, en contexte
    • scalaire
  • Une liste vide, en contexte
    • liste
  • Une liste contena
    • nt un seul undef,
en contexte liste

Toutes les autres valeurs de retour (y compris la liste contenant le seul zéro, et la liste contenant une seule chaîne vide) sont considérées comme des succès. Cependant, le code du monde réel n'est pas toujours aussi simple. Peut-être que le code avec lequel vous travaillez retourne une chaîne contenant le mot "FAIL" lors d'un échec, ou une liste de deux éléments contenant "(undef, "message d'erreur humain")". Pour faire fonctionner autodie avec ces sortes de sous-routines, nous avons l' interface d'indi

cations.

L'interface d'indications permet de fournir des indications à "autodie" sur la manière dont il doit détecter l'échec des sous-routines définies par l'utilisateur. Bien que ces puissent être fournies par l'utilisateur final de "autodie", elles sont idéalement écrites dans le module lui-même, ou dans un module auxiliaire ou une sous-classe de "autodie"

lui-
même.

Que sont les indications

?

Une indication est une sous-routine ou une valeur qui est comparée à la valeur de retour d'une sous-routine soumise à autodie. Si la correspondance retourne vrai, "autodie" considère que la sous-routine a

échoué.

Si l'indication fournie est une sous-routine, alors "autodie" passera la valeur de retour complète à cette sous-routine. Si l'indication est un objet regexp, alors "autodie" le fera correspondre à la valeur de retour. Si l'indication est undef, la valeur de retour doit être undef. Sur les versions de Perl 5.10 et plus récentes, toute autre valeur peut être fournie et elle sera appariée intelligemment à la valeur fournie. Cependant, les valeurs appariées intelligemment comme celles-ci sont

dépréciées.

Des indications peuvent être fournies pour les contextes scalaire et liste. Notez que une sous-routine soumise à autodie ne verra jamais un contexte void, car "autodie" a toujours besoin de capturer la valeur de retour pour l'examiner. Les sous-routines soumises à autodie appelées en contexte vo

id se comportent comme si elles étaient appelées en contexte scalai
re, mais leur valeur de retour est jetée après avoir été vérifiée.

Exemples

d'indications

Les indications peuvent consister en des références de sous-routines, des objets surchargeant l'appariement intelligent, des expressions régulières, et selon la version de Perl peut-être d'autres choses. Vous pouvez spécifier des indications différentes pour la manière dont l'échec doit être identifié dans les contextes scalaire et

liste.

Ces exemples s'appliquent pour une utilisation dans la sous-routine "AUTODIE_HINTS" et lors de l'appel de "autodie::hints->set_hi

nts_for()".

Les indications spécifiques au contexte les plus courantes sont

: 
# Les échecs scalaires retournent toujours undef :
    {  scalar => sub { !defined($_[0]) }  }
# Les échecs scalaires retournent toute valeur fausse [attente par défaut] :
    {  scalar => sub { ! $_[0] }  }
# Les échecs scalaires retournent toujours zéro explicitement :
    {  scalar => sub { defined($_[0]) && $_[0] eq '0' }  }
# Les échecs en liste retournent toujours une liste vide :
    {  list => sub { !@_ }  }
# Les échecs en liste retournent () ou (undef) [attente par défaut] :
    {  list => sub { ! @_ || @_ == 1 && !defined $_[0] }  }
# Les échecs en liste retournent () ou une seule valeur fausse :
    {  list => sub { ! @_ || @_ == 1 && !$_[0] }  }
# Les échecs en liste retournent (undef, "une certaine chaîne")
    {  list => sub { @_ == 2 && !defined $_[0] }  }
# foo() infructueux retourne 'FAIL' ou '_FAIL' en contexte scalaire,
#                    retourne (-1) en contexte liste...
autodie::hints->set_hints_for(
    \&foo,
    {
        scalar => qr/^ _? FAIL $/xms,
        list   => sub { @_ == 1 && $_[0] eq -1 },
    }
);
# foo() infructueux retourne 0 dans tous les contextes...
autodie::hints->set_hints_for(
    \&foo,
    {
        scalar => sub { defined($_[0]) && $_[0] == 0 },
        list   => sub { @_ == 1 && defined($_[0]) && $_[0] == 0 },
    }
)
;

Cette construction « dans tous les contextes » est très courante et peut être abrégée en utilisant la clé 'fail'. Cela définit à la fois les indications "scalar" et "list" à la même valeur

: 
# foo() infructueux retourne 0 dans tous les contextes...
autodie::hints->set_hints_for(
    \&foo,
    {
        fail => sub { @_ == 1 and defined $_[0] and $_[0] == 0 }
    }
);
# think_positive() infructueux retourne un nombre négatif en cas d'échec...
autodie::hints->set_hints_for(
    \&think_positive,
    {
        fail => sub { $_[0] < 0 }
    }
);
# my_system() infructueux retourne non-zéro en cas d'échec...
autodie::hints->set_hints_for(
    \&my_system,
    {
        fail => sub { $_[0] != 0 }
    }
)
;

Définir manuellement les indications depuis votre

programme

Si vous utilisez un module qui retourne quelque chose de spécial en cas d'échec, alors vous pouvez créer manuellement des indications pour chacune des sous-routines souhaitées. Une fois les indications spécifiées, elles sont disponibles pour tous les fichiers et modules chargés par la suite, ainsi vous pouvez déplacer ce travail dans un module et il fonctionnera

toujours. 
use Some::Module qw(foo bar);
use autodie::hints;
autodie::hints->set_hints_for(
        \&foo,
        {
                scalar => SCALAR_HINT,
                list   => LIST_HINT,
        }
);
autodie::hints->set_hints_for(
        \&bar,
        { fail => SOME_HINT, }
)
;

Il est possible de passer soit une référence de sous-routine (recommandée) soit un nom de sous-routine entièrement qualifié comme premier argument. Cela signifie que vous pouvez définir des indications sur des modules qui pourraient être chargés

: 
use autodie::hints;
autodie::hints->set_hints_for(
        'Some::Module:bar', { fail => SCALAR_HINT, }
)
;

Cette technique est la plus utile lorsque vous avez un projet qui utilise beaucoup de modules tiers. Vous pouvez définir toutes vos indications possibles en un seul endroit. Cela peut même être dans une sous-classe de autodie. Par exemple

: 
package my::autodie;
use parent qw(autodie);
use autodie::hints;
autodie::hints->set_hints_for(...);
1;

Vous pouvez maintenant "use my::autodie", qui fonctionnera exactement comme le "autodie" standard, mais sera maintenant conscient d

e toutes les indications
que vous avez définies.

Ajouter des indications à votre

module

"autodie" fournit une interface passive pour vous permettre de déclarer des indications pour votre module. Ces indications seront trouvées et utilisées par "autodie" s'il est chargé, mais sinon n'ont aucun effet (ou dépendances) sans autodie. Pour les définir, votre module doit déclarer qu'il fait le rôle "autodie::hints::provider". Cela peut être fait en écrivant votre propre méthode "DOES", en utilisant un système tel que "Class::DOES" pour gérer le gros du travail pour vous, ou en déclarant une %DOESpan> variable de paquet avec une clé "autodie::hints::provider" et une valeur vraie

correspondante.

Notez que la vérification d'un hash %DOES est un raccourci spécifique à "autodie". Les autres modules n'utilisent pas ce mécanisme pour vérifier les rôles, bien que vous puissiez utiliser le module "Class::DOES" depuis le CPAN pour

l'autoriser.

De plus, vous devez définir une sous-routine "AUTODIE_HINTS" qui renvoie une référence de hash contenant les indices pour vos sous-routines

: 
package Your::Module;
# Nous pouvons utiliser Class::DOES depuis le CPAN pour déclarer l'adhésion
# à un rôle.
use Class::DOES 'autodie::hints::provider' => 1;
# Alternativement, nous pouvons déclarer le rôle dans %DOES. Notez que
# ceci est une optimisation spécifique à autodie, bien que Class::DOES
# puisse être utilisé pour promouvoir ceci en une véritable déclaration de rôle.
our %DOES = ( 'autodie::hints::provider' => 1 );
# Enfin, nous devons définir les indices eux-mêmes.
sub AUTODIE_HINTS {
    return {
        foo => { scalar => HINTS, list => SOME_HINTS },
        bar => { scalar => HINTS, list => MORE_HINTS },
        baz => { fail => HINTS },
    }
}

Cela permet à votre code de définir des indices sans dépendre de "autodie" et "autodie::hints" étant chargés, ou même installés. De cette façon, votre code peut faire la bonne chose lorsque "autodie" est installé, mais n'a pas b

esoin d'en dépendr
e pour fonctionner.

Insister sur les

indices

Lorsqu'une sous-routine définie par l'utilisateur est enveloppée par "autodie", elle utilisera les indices s'ils sont disponibles, et sinon reviendra au comportement par défaut décrit dans l'introduction de ce document. Cela peut être problématique si nous nous attendons à ce qu'un indice existe, mais que (pour une raison quelconque) il n'a pas été

chargé.

Nous pouvons demander à autodie de exiger qu'un indice soit utilisé en préfixant un point d'exclamation au début du nom de la sous-routine. Un point d'exclamation seul indique que toutes les sous-routines après lui doivent avoir des indices

déclarés. 
# foo() et bar() doivent avoir leurs indices définis
use autodie qw( !foo !bar baz );
# Tout doit avoir des indices (recommandé).
use autodie qw( ! foo bar baz );
# bar() et baz() doivent avoir leurs indices définis
use autodie qw( foo ! bar baz );
# Activer autodie pour toutes les fonctions intégrées prises en charge par Perl,
# ainsi que pour foo(), bar() et baz(). Tout doit
# avoir des indices.
use autodie qw( ! :all foo bar baz )
;

Si des indices ne sont pas disponibles pour les sous-routines spécifiées, cela provoquera une erreur à la compilation. Insister sur les indices pour les fonctions intégrées de Perl (par ex., "open" et "close") est toujours

réussi.

Insister sur les indices est fortement

recomm
andé.
