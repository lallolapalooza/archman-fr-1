AUDITD-PLUGINS(5) Utilitaires d'administration système AUDITD-PLUGINS(5)

NOM

auditd-plugins - récepteurs d'événements en temps réel

DESCRIPTION

auditd peut multiplexer des événements d'audit en temps réel. Il prend des événements d'audit et les distribue à des programmes enfants qui souhaitent analyser les événements en temps réel. Lorsque le démon d'audit reçoit un SIGTERM ou SIGHUP, il transmet ce signal à ses processus enfants afin qu'ils puissent recharger la configuration ou se terminer.

Les programmes enfants installent un fichier de configuration dans un répertoire de plugins qui est par défaut /etc/audit/plugins.d. Ceci peut être contrôlé par une option de configuration d'auditd.conf, plugin_dir, si l'administrateur souhaite placer les plugins ailleurs. Mais auditd installera ses plugins à l'emplacement par défaut.

Le répertoire des plugins sera balayé et chaque plugin actif sera démarré. Si le plugin rencontre un problème et se termine, il sera démarré un maximum de max_restarts fois, comme spécifié dans auditd.conf.

Les fichiers de configuration doivent être des fichiers réguliers qui ne commencent pas par un caractère '.', contiennent au plus un caractère '.', et ont une extension '.conf'. Les fichiers qui ne respectent pas ces critères seront ignorés. Les options du fichier de configuration sont données une par ligne avec un signe égal entre le mot-clé et sa valeur. Les options disponibles sont les suivantes :

actif
Les options pour ceci sont yes ou no.
chemin
Ceci est le chemin absolu vers l'exécutable du plugin. Dans le cas des plugins internes, ce serait le nom du plugin.
type
Ceci indique au répartiteur comment le plugin doit être exécuté. Il n'y a qu'une seule option valide, toujours, ce qui signifie que le plugin est externe et doit toujours être exécuté. La valeur par défaut est toujours, car il n'y a plus de plugins intégrés.
arguments
Ceci vous permet de passer des arguments au programme enfant. Généralement, les plugins ne prennent pas d'arguments et ont leur propre fichier de configuration qui leur indique comment ils doivent être configurés. Pour l'instant, il y a une limite de 2 arguments.
format
Les options valides pour ceci sont binaire et chaîne. Binaire transmet les données exactement telles que le répartiteur d'événements les reçoit du démon d'audit. L'option chaîne indique au répartiteur de transformer complètement l'événement en une chaîne adaptée à l'analyse avec la bibliothèque d'analyse d'audit. La valeur par défaut est chaîne.

NOTE

auditd a une file d'attente interne pour stocker les événements pour les plugins. (Voir le paramètre q_depth dans auditd.conf.) Les plugins doivent surveiller et dépiler les événements aussi rapidement que possible et les mettre en file d'attente en interne s'ils ne peuvent pas être traités immédiatement. Si le plugin n'est pas en mesure de dépiler les enregistrements, la file d'attente interne d'auditd se remplira. À tout moment, en tant que root, vous pouvez exécuter ce qui suit pour vérifier les métriques d'auditd :

auditctl --signal cont ; sleep 1 ; cat /run/audit/auditd.state

Les plugins utilisant libauplugin peuvent récupérer leurs propres métriques de file d'attente avec auplugin_queue_depth, auplugin_queue_max_depth, et auplugin_queue_overflow. La fonction auplugin_register_stats_callback permet de signaler ces valeurs à partir d'un gestionnaire de signaux.

Si la file d'attente interne d'auditd se remplit, il ne peut pas dépiler les événements du tampon du noyau. Si le tampon du noyau se remplit, il examine la valeur de backlog_wait_time pour retarder tous les processus qui génèrent un événement afin de voir s'il y a finalement de la place pour ajouter l'événement. Cela sera probablement remarqué comme un ralentissement de divers processus sur la machine. Le sous-système d'audit du noyau peut être vérifié en exécutant :

auditctl -s

Lors de l'optimisation des performances du système d'audit, vous devriez vérifier les métriques du noyau et d'auditd et ajuster en conséquence.

NOTES POUR LES DÉVELOPPEURS

Lorsque le démon d'audit démarre votre plugin, vous s'exécuterez en tant que root. Si vous n'avez pas besoin de privilèges root, vous devriez changer d'UID/GID pour réduire les chances d'être une cible d'exploitation. Si vous avez besoin de conserver des capacités, l'utilisation de libcap-ng est le moyen le plus simple.

Votre environnement ne sera pas propre. Vous hériterez de nombreux attributs de l'auditd lui-même. Vous devrez ajuster votre masque de signaux, sigaction, umask, et vos variables d'environnement. Consultez la page de manuel d'auditd pour voir quels signaux auditd utilise. Les plugins sont censés gérer SIGTERM et SIGHUP. Vous hériterez également des limites de ressources de l'auditd. Notez que certaines de ces limites de ressources, telles que le nombre maximal de descripteurs ouverts, sont contrôlées par systemd. Vous héritez également de la valeur de nice de l'auditd. Vous pourriez vouloir l'ajuster pour vous assurer de suivre les événements d'audit entrants.

Auditd enverra les événements au plugin sur son entrée standard. Le plugin doit garder ce descripteur vide afin que les événements ne s'accumulent pas. Si vous effectuez un traitement important de chaque événement, vous devriez ajouter une file d'attente interne à votre conception afin de maintenir le flux des événements. La fonction auparse_feed est la méthode préférée pour examiner les événements complets si vous avez besoin d'analyser le contenu des événements.

FICHIERS

/etc/auditd/auditd.conf /etc/audit/plugins.d

VOIR AUSSI

auditd.conf(5), auditd(8), execve(2), auparse_feed(3).
