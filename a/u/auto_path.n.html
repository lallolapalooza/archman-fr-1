Les variables globales suivantes sont créées et gérées automatiquement par la bibliothèque Tcl. Sauf indication contraire ci-dessous, ces variables devraient normalement être considérées comme en lecture seule par le code propre à l'application et par les

Cette variable est initialisée au démarrage pour contenir, dans l'ordre : les répertoires listés dans la variable d'environnement TCLLIBPATH, le répertoire nommé par la variable globale tcl_library, le répertoire parent de tcl_library, [file dirname [file dirname [info nameofexecutable]]]/lib, les répertoires listés dans la variable tcl_pkgPath. Cette variable est maintenue par Tcl sous forme de tableau dont les éléments sont les variables d'environnement du processus. Lire un élément renverra la valeur de la variable d'environnement correspondante. Définir un élément du tableau modifiera la variable d'environnement correspondante ou en créera une nouvelle si elle n'existe pas déjà. Supprimer un élément de env supprimera la variable d'environnement correspondante. Les modifications du tableau env affecteront l'environnement passé aux processus enfants par des commandes comme exec. Si l'ensemble du tableau env est supprimé, alors Tcl cessera de surveiller les accès à env et ne mettra pas à jour les variables
d'environnement

Sous Windows, les variables d'environnement PATH et COMSPEC, quelle que soit leur casse, sont automatiquement converties en majuscules. Par exemple, la variable PATH pourrait être exportée par le système d'exploitation sous la forme « path », « Path », « PaTh », etc., obligeant autrement du code Tcl simple à prendre en charge de nombreux cas particuliers. Toutes les autres variables d'environnement héritées par Tcl restent inchangées. Définir une variable de tableau env à vide revient à la supprimer, car c'est le comportement du système d'exploitation Windows sous-jacent. Il convient de noter que s'appuyer sur une variable d'environnement existante et vide ne fonctionnera pas sous Windows et est déconseillé pour une utilisation multiplateforme

.

Cette variable contient la valeur de l'option de retour -errorcode définie par la dernière erreur survenue dans cet interpréteur. Cette valeur de liste représente des informations supplémentaires sur l'erreur sous une forme facile à traiter par des programmes. Le premier élément de la liste identifie une classe générale d'erreurs et détermine le format du reste de la liste. Les formats suivants pour les options de retour -errorcode sont utilisés par le noyau Tcl ; des applications individuelles peuvent définir des formats
supplémentaires

ARITH code
msg
Ce format est utilisé lorsqu'une erreur arithmétique se produit (par exemple, une tentative de diviser zéro par zéro dans la commande expr). Code identifie l'erreur précise et msg fournit une description lisible de l'erreur. Code sera soit DIVZERO (pour une tentative de division par zéro), DOMAIN (si un argument est en dehors du domaine d'une fonction, comme acos(-3)), IOVER
FLOW (pour un débordement d'entier), OVERFLOW (pour un débordement en virgu
le flottante), ou UNKNOWN (si la cause de l'erreur ne peut être déterminée).

La détection de ces erreurs dépend

en partie du matériel sous-jacent
et des bibliothèques système.

msg
Ce format est utilisé lorsqu'un processus enfant a été tué à cause d'un signal. L'élément pid sera l'identifiant du processus (en décimal). L'élément sigName sera le nom symbolique du signal qui a causé la terminaison du processus ; ce sera l'un des noms du fichier d'inclusion signal.h, comme SIGPIPE. L'élément msg sera un court message lisible décrivant le signal, comme « write on pipe with no readers » pour SIGPIP
E.

code

L'élément sigName sera le nom symbolique du signal qui a causé la suspension du processus ; ce sera l'un des noms du fichier d'inclusion signal.h, comme SIGTTIN. L'élément msg sera un court message lisible décrivant le signal, comme « background tty read » pour SIGTTI

L'élément errName contiendra le nom symbolique de l'erreur survenue, comme ENOENT ; ce sera l'une des valeurs définies dans le fichier d'inclusion errno.h. Indique une sorte de problème généré en relation avec Tcl lui-même, par exemple un échec de recherche d'un canal ou d'une variable.

Pour définir l'option de retour -errorcode, les applications doivent utiliser des procédures de bibliothèque telles que Tcl_SetObjErrorCode, Tcl_SetReturnOptions et Tcl_PosixError, ou elles peuvent invoquer l'option -errorcode de la commande return. Si aucune de ces méthodes de définition du code d'erreur n'a été utilisée, l'interpréteur Tcl réinitialisera la variable à NONE après la prochaine erreur.

errorInfo
Cette variable contient la valeur de l'option de retour -errorinfo définie par la dernière erreur survenue dans cet interpréteur. Cette valeur sous forme de chaîne contiendra une ou plusieurs lignes identifiant les commandes et procédures Tcl qui étaient en cours d'exécution au moment de la dernière erreur. Son contenu se présente sous la forme d'une trace de pile montrant les différentes commandes Tcl imbriquées qui avaient été invoquées au moment de l'erreur.
tcl_library
Cette variable contient le nom d'un répertoire contenant la bibliothèque système de scripts Tcl, tels que ceux utilisés pour le chargement automatique. La valeur de cette variable est renvoyée par la commande info library. Voir l'entrée de manuel library pour les détails des facilités fournies par la bibliothèque de scripts Tcl. Normalement, chaque application ou paquet aura sa propre bibliothèque de scripts spécifique à l'application en plus de la bibliothèque de scripts Tcl ; chaque application doit définir une variable globale portant un nom tel que $app_library (où app est le nom de l'application) pour contenir le nom de fichier réseau du répertoire de la bibliothèque de cette application. La valeur initiale de tcl_library est définie lors de la création d'un interpréteur en recherchant plusieurs répertoires différents jusqu'à ce qu'un répertoire contenant un script de démarrage Tcl approprié soit trouvé. Si la variable d'environnement TCL_LIBRARY existe, alors le répertoire qu'elle nomme est vérifié en premier. Si TCL_LIBRARY n'est pas définie ou ne fait pas référence à un répertoire approprié, Tcl vérifie alors plusieurs autres répertoires en fonction d'un emplacement par défaut compilé, de l'emplacement du binaire contenant l'application et du répertoire de travail actuel.
tcl_patchLevel
Lorsqu'un interpréteur est créé, Tcl initialise cette variable pour contenir une chaîne donnant le niveau de correctif actuel pour Tcl, tel que 8.4.16 pour Tcl 8.4 avec les seize premiers correctifs officiels, ou 8.5b3 pour la troisième version bêta de Tcl 8.5. La valeur de cette variable est renvoyée par la commande info patchlevel.
tcl_pkgPath
Cette variable contient une liste de répertoires indiquant où les paquets sont normalement installés. Elle n'est pas utilisée sous Windows. Elle contient généralement une ou deux entrées ; si elle en contient deux, la première est normalement un répertoire pour les paquets dépendant de la plateforme (par exemple, les binaires de bibliothèques partagées) et la seconde est normalement un répertoire pour les paquets indépendants de la plateforme (par exemple, les fichiers de script). Typiquement, un paquet est installé comme sous-répertoire de l'une des entrées de la variable tcl_pkgPath. Les répertoires de la variable tcl_pkgPath sont inclus par défaut dans la variable auto_path, de sorte qu'ils et leurs sous-répertoires immédiats sont automatiquement recherchés pour les paquets lors des commandes package require. Note : tcl_pkgPath n'est pas destinée à être modifiée par l'application. Sa valeur est ajoutée à auto_path au démarrage ; les changements apportés à tcl_pkgPath ne sont pas reflétés dans auto_path. Si vous souhaitez que Tcl recherche des répertoires supplémentaires pour les paquets, vous devez ajouter les noms de ces répertoires à auto_path, et non à tcl_pkgPath.
tcl_platform
Ceci est un tableau associatif dont les éléments contiennent des informations sur la plateforme sur laquelle l'application s'exécute, tels que le nom du système d'exploitation, son numéro de version actuel et le jeu d'instructions de la machine. Les éléments listés ci-dessous seront toujours définis, mais ils peuvent avoir des chaînes vides comme valeurs si Tcl n'a pas pu récupérer d'informations pertinentes. De plus, les extensions et les applications peuvent ajouter des valeurs supplémentaires au tableau. Les éléments prédéfinis sont :
byteOrder
L'ordre des octets natif de cette machine : soit littleEndian, soit bigEndian.
debug
Si cette variable existe, alors l'interpréteur a été compilé avec et lié à un runtime C activé pour le débogage. Cette variable n'existera que sous Windows, afin que les auteurs d'extensions puissent spécifier quel paquet charger en fonction de la bibliothèque d'exécution C utilisée. Ce n'est pas une indication que ce cœur contient des symboles.
engine
Le nom de l'implémentation du langage Tcl. Lorsque l'interpréteur est créé pour la première fois, il est toujours défini sur la chaîne Tcl.
machine
Le jeu d'instructions exécuté par cette machine, tel que intel, PPC, 68k, ou sun4m. Sur les machines UNIX, c'est la valeur renvoyée par uname -m.
os
Le nom du système d'exploitation exécuté sur cette machine, tel que Windows NT ou SunOS. Sur les machines UNIX, c'est la valeur renvoyée par uname -s.
osVersion
Le numéro de version du système d'exploitation exécuté sur cette machine. Sur les machines UNIX, c'est la valeur renvoyée par uname -r.
pathSeparator
Le caractère qui doit être utilisé pour diviser les variables d'environnement de type PATH en leur liste correspondante de noms de répertoires.
platform
Soit windows, soit unix. Ceci identifie l'environnement général de la machine.
pointerSize
Ceci donne la taille du pointeur natif de la machine en octets (strictement, c'est le même résultat que l'évaluation de sizeof(void*) en C.)
threaded
Si cette variable existe, alors l'interpréteur a été compilé avec les threads activés.
user
Ceci identifie l'utilisateur actuel en fonction des informations de connexion disponibles sur la plateforme. Cette valeur provient des appels système getuid() et getpwuid() sur Unix, et de la valeur de l'appel système GetUserName() sur Windows.
wordSize
Ceci donne la taille du mot natif de la machine en octets (strictement, c'est le même résultat que l'évaluation de sizeof(long) en C.)
tcl_precision
Cette variable contrôle le nombre de chiffres à générer lors de la conversion de valeurs à virgule flottante en chaînes. Elle est par défaut à 0. Les applications ne doivent pas modifier cette valeur ; elle est fournie pour la compatibilité avec le code hérité.
La valeur par défaut de 0 est spéciale, signifiant que Tcl doit convertir les nombres en utilisant le moins de chiffres possible tout en distinguant tout nombre à virgule flottante de ses voisins les plus proches. Elle diffère de l'utilisation d'une valeur arbitrairement élevée pour tcl_precision en ce sens qu'un nombre inexact comme 1.4 sera converti en 1.4 plutôt qu'en 1.3999999999999999, même si ce dernier est plus proche de la valeur exacte du nombre binaire.
Si tcl_precision n'est pas zéro, alors lorsque Tcl convertit un nombre à virgule flottante, il crée une représentation décimale d'au plus tcl_precision chiffres significatifs ; le résultat peut être plus court si le résultat plus court représente le nombre original exactement. Si aucun résultat d'au plus tcl_precision chiffres n'est une représentation exacte du nombre original, celui qui est le plus proche du nombre original est choisi. Si le nombre original se situe précisément entre deux représentations décimales également précises, celle qui a une valeur paire pour le chiffre le moins significatif est choisie ; par exemple, si tcl_precision est 3, alors 0.3125 sera converti en 0.312, et non en 0.313, tandis que 0.6875 sera converti en 0.688, et non en 0.687. Toute chaîne de zéros finaux restants est tronquée.
Une valeur de tcl_precision de 17 chiffres est "parfaite" pour le flottant IEEE en ce sens qu'elle permet aux valeurs en double précision d'être converties en chaînes puis reconverties en binaire sans perte d'information. Pour cette raison, vous la verrez souvent comme une valeur dans le code hérité qui doit s'exécuter sur des versions Tcl antérieures à 8.5. Elle n'est plus recommandée ; comme indiqué ci-dessus, une valeur zéro est la méthode préférée.
Tous les interpréteurs d'un thread partagent une seule valeur de tcl_precision : la modifier dans un interpréteur affectera également tous les autres interpréteurs. Les interpréteurs sécurisés ne sont pas autorisés à modifier la variable.
Les valeurs valides pour tcl_precision vont de 0 à 17.
tcl_rcFileName
Cette variable est utilisée lors de l'initialisation pour indiquer le nom d'un fichier de démarrage spécifique à l'utilisateur. Si elle est définie par l'initialisation spécifique à l'application, le code de démarrage Tcl vérifiera l'existence de ce fichier et le sourcera s'il existe. Par exemple, pour wish, la variable est définie sur ~/.wishrc pour Unix et ~/wishrc.tcl pour Windows.
tcl_traceCompile
La valeur de cette variable peut être définie pour contrôler la quantité d'informations de traçage affichées pendant la compilation du bytecode. Par défaut, tcl_traceCompile est zéro et aucune information n'est affichée. Définir tcl_traceCompile à 1 génère un résumé sur une ligne dans stdout chaque fois qu'une procédure ou une commande de haut niveau est compilée. La définir à 2 génère une liste détaillée dans stdout des instructions de bytecode émises lors de chaque compilation. Cette variable est utile pour traquer les problèmes présumés avec le compilateur Tcl.
Cette variable et cette fonctionnalité n'existent que si TCL_COMPILE_DEBUG a été défini lors de la compilation de Tcl.
tcl_traceEx
ec
La valeur de cette variable peut être définie pour contrôler la quantité d'informations de traçage affichée lors de l'exécution du code octet. Par défaut, tcl_traceExec vaut zéro et aucune information n'est affichée. En définissant tcl_traceExec à 1, on génère un traçage d'une ligne dans stdout à chaque appel d'une procédure Tcl. En la définissant à 2, on génère une ligne de sortie chaque fois qu'une commande Tcl est invoquée, contenant le nom de la commande et ses arguments. En la définissant à 3, on produit un traçage détaillé montrant le résultat de l'exécution de chaque instruction de code octet. Notez que lorsque tcl_traceExec vaut 2 ou 3, des commandes telles que set et incr, qui ont été entièrement remplacées par une séquence d'instructions de code octet, ne sont pas affichées. Défin
ir cette variable est utile pour traquer des problèmes
suspects avec le compilateur et l'interpréteur de code octet.
Cette variable et cette fonctionnalité n'existent que si TCL_COMPILE_DEBUG a été défini lors de la compilation de
Tcl.
tcl_wordcha
rs
La valeur de cette variable est une expression rationnelle qui peut être définie pour contrôler ce qui est considéré comme des caractères « mot », par exemple pour sélectionner un mot en double-cliquant dans du texte dans Tk. Elle dépend de la plateforme. Sur Windows, sa valeur par défaut est \S, signifiant tout sauf un caractère d'espace Unicode. Sinon, sa valeur par défaut est \w, qui correspond à tout caractère de mot Unicode (chiffre, lettre ou souligné)
.
tcl_nonwordch
ars
La valeur de cette variable est une expression rationnelle qui peut être définie pour contrôler ce qui est considéré comme des caractères « non-mot », par exemple pour sélectionner un mot en double-cliquant dans du texte dans Tk. Elle dépend de la plateforme. Sur Windows, sa valeur par défaut est \s, signifiant tout caractère d'espace Unicode. Sinon, sa valeur par défaut est \W, qui correspond à tout sauf un caractère de mot Unicode (chiffre, lettre ou souligné)
.
tcl_versi
on

Les changements de x représentent des changements majeurs avec des incompatibilités probables et les changements de y représentent de petites améliorations et des corrections de bogues qui conservent la compatibilité ascendante.
