AUDIT.RULES(7) Utilitaires d'administration système AUDIT.RULES(7)

NOM

audit.rules - un ensemble de règles chargées dans le système d'audit du noyau

DESCRIPTION

audit.rules est un fichier contenant des règles d'audit qui seront chargées par le script d'initialisation du démon d'audit chaque fois que le démon est démarré. Le programme auditctl est utilisé par les scripts d'initialisation pour effectuer cette opération. La syntaxe des règles est essentiellement la même que celle utilisée lors de la saisie d'une commande auditctl à l'invite du shell, sauf que vous n'avez pas besoin de saisir le nom de la commande auditctl car cela est implicite. Les règles d'audit se présentent en 3 variétés : contrôle, fichier et appel système.

Contrôle

Les commandes de contrôle impliquent généralement la configuration du système d'audit plutôt que de lui dire quoi surveiller. Ces commandes incluent généralement la suppression de toutes les règles, la définition de la taille de la file d'attente de rétroaction du noyau, la définition du mode d'échec, la définition de la limite de débit des événements, ou la demande à auditctl d'ignorer les erreurs de syntaxe dans les règles et de continuer le chargement. Généralement, ces règles se trouvent en haut du fichier de règles.

Système de fichiers

Les règles du système de fichiers sont parfois appelées « watches ». Ces règles sont utilisées pour auditer l'accès à des fichiers ou des répertoires particuliers qui pourraient vous intéresser. Si le chemin donné dans une règle de surveillance est un répertoire, la règle utilisée est récursive jusqu'au fond de l'arborescence des répertoires, à l'exclusion de tout répertoire qui pourrait être des points de montage. La syntaxe de ces règles de surveillance suit généralement ce format :

-a always,exit -F arch=b64 -F path=chemin-vers-fichier -F perm=permissions -F key=nom-clé

où les permissions sont l'une des suivantes :

r
- lecture du fichier
w
- écriture dans le fichier
x
- exécution du fichier
a
- changement d'attribut du fichier

Pour de meilleures performances, vous devriez fournir un champ arch dans la règle. Les permissions individuelles déclencheront la sélection des appels système qui utilisent ce type d'accès. Ne pas fournir l'architecture entraînera la sélection de tous les appels système, ce qui affectera les performances car tous les appels système seront évalués.

Des surveillance peuvent également être créées en utilisant le format obsolète -w, qui permet une compatibilité ascendante au détriment des performances système, comme expliqué. En utilisant les règles d'appels système comme montré ci-dessus, vous pouvez choisir entre path et dir, qui visent respectivement un inode spécifique ou une arborescence de répertoires. Il convient également de noter que la surveillance récursive des répertoires s'arrêtera s'il y a un point de montage sous le répertoire parent. Il existe une option pour rendre le sous-répertoire monté équivalent en utilisant une règle -q.

Appel système

Les règles d'appels système sont chargées dans un moteur de correspondance qui intercepte chaque appel système effectué par tous les programmes du système. Par conséquent, il est très important de n'utiliser les règles d'appels système que lorsque c'est nécessaire, car elles affectent les performances. Plus il y a de règles, plus l'impact sur les performances est important. Vous pouvez améliorer les performances, cependant, en combinant les appels système dans une seule règle chaque fois que possible.

Le noyau Linux dispose de 6 listes de correspondance de règles ou filtres, comme on les appelle parfois. Ce sont : task, exit, user, exclude, filesystem, et io_uring. La liste task est vérifiée uniquement lors des appels système fork ou clone. Elle est rarement utilisée en pratique.

Le filtre exit est l'endroit où toutes les demandes d'audit d'appels système et de système de fichiers sont évaluées.

Le filtre user est utilisé pour filtrer (supprimer) certains événements provenant de l'espace utilisateur. Par défaut, tout événement provenant de l'espace utilisateur est autorisé. Donc, s'il y a des événements que vous ne souhaitez pas voir, c'est un endroit où certains peuvent être supprimés. Consultez auditctl(8) pour connaître les champs valides.

Le filtre exclude est utilisé pour exclure certains événements de l'émission. Le type de message et un certain nombre de champs d'attributs du sujet peuvent être utilisés pour indiquer au noyau quels types de messages vous ne souhaitez pas enregistrer. Ce filtre peut supprimer l'événement dans son ensemble et n'est pas sélectif quant à tout autre attribut. Les filtres user et exit sont plus adaptés à l'audit sélectif d'événements. L'action est ignorée pour ce filtre, et est par défaut « never ».

Le filtre io_uring est utilisé pour surveiller les appels système sous-jacents effectués par les opérations io_uring.

Les règles d'appels système ont la forme générale suivante :

-a action,liste -S appel_système -F champ=valeur -k nom-clé

L'option -a indique au moteur de correspondance de règles du noyau que nous voulons ajouter une règle à la fin de la liste des règles. Mais nous devons spécifier sur quelle liste de règles elle va et quelle action entreprendre lorsqu'elle se déclenche. Les actions valides sont :

always
- crée toujours un événement
never
- ne crée jamais d'événement

L'action et la liste sont séparées par une virgule, mais sans espace entre les deux. Les listes valides sont : task, exit, user, exclude, filesystem et io_uring. Leur signification a été expliquée précédemment.

La prochaine étape dans la règle serait normalement l'option -S. Ce champ peut être soit le nom de l'appel système, soit son numéro. Pour la lisibilité, le nom est presque toujours utilisé. Vous pouvez spécifier plusieurs appels système dans une règle en spécifiant une autre option -S. Lorsqu'ils sont envoyés au noyau, tous les champs d'appels système sont mis dans un masque afin qu'une seule comparaison puisse déterminer si l'appel système est pertinent. Ainsi, l'ajout de plusieurs appels système dans une seule règle est très efficace. Lorsque vous spécifiez un nom d'appel système, auditctl recherche le nom et obtient son numéro d'appel système. Cela pose quelques problèmes sur les machines bi-architecture. Les numéros d'appels système 32 bits et 64 bits correspondent parfois, mais pas toujours. Pour résoudre ce problème, vous devriez généralement diviser la règle en deux, l'une spécifiant -F arch=b32 et l'autre spécifiant -F arch=b64. Cela doit être placé devant l'option -S afin qu'auditctl consulte la bonne table de recherche lors du retour du numéro.

Après la spécification de l'appel système, vous auriez normalement une ou plusieurs options -F qui affinent ce à quoi il faut correspondre. Plutôt que de lister tous les types de champs valides ici, le lecteur devrait consulter la page de manuel de auditctl qui contient une liste complète de chaque champ et de sa signification. Mais il vaut la peine de mentionner quelques points.

Le système d'audit considère les UID comme des nombres non signés. Le système d'audit utilise le nombre -1 pour indiquer qu'un loginuid n'est pas défini. Cela signifie que lorsqu'il est affiché, il ressemble à 4294967295. Mais lorsque vous écrivez des règles, vous pouvez utiliser soit « unset » (facile à retenir), soit -1, soit 4294967295. Ils sont tous équivalents. Si vous écrivez une règle pour essayer d'obtenir les utilisateurs valides du système, vous devez consulter /etc/login.defs pour voir où commencent les comptes utilisateur. Par exemple, si UID_MIN est 1000, vous devrez également prendre en compte que la représentation non signée de -1 est supérieure à 500. Vous aborderiez donc cela avec le fragment de règle suivant :

-F auid>=1000 -F auid!=unset

Ces vérifications individuelles sont « ANDées » et les deux doivent être vraies.

La dernière chose à savoir sur les règles d'appels système est que vous pouvez ajouter un champ clé, qui est une chaîne de texte libre que vous souhaitez insérer dans l'événement pour aider à identifier sa signification. Ceci est discuté plus en détail dans la section NOTES.

NOTES

Le but de l'audit est de pouvoir effectuer une investigation périodiquement ou chaque fois qu'un incident survient. Quelques étapes simples de planification préalable faciliteront ce travail. Le meilleur conseil est d'utiliser des clés dans les règles de surveillance et d'appels système pour donner un sens à la règle. Si des règles sont liées ou satisfont ensemble une exigence spécifique, donnez-leur un nom de clé commun. Vous pouvez l'utiliser pendant votre investigation pour sélectionner uniquement les résultats ayant une signification spécifique.

Lors d'une investigation, vous commenceriez normalement par la sortie principale de aureport pour avoir juste une idée de ce qui se passe sur le système. Ce rapport vous informe principalement sur les événements codés en dur par le système d'audit tels que les connexions/déconnexions, l'utilisation de l'authentification, les anomalies système, le nombre d'utilisateurs connectés à la machine et si SE Linux a détecté des AVC.
