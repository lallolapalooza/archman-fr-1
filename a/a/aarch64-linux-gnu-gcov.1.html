DESCRIPTIO

N

gcov est un programme de test de couverture. Utilisez-le en conjonction avec GCC pour analyser vos programmes afin de créer du code plus efficace et plus rapide et pour découvrir les parties non testées de votre programme. Vous pouvez utiliser gcov comme un outil de profilage pour aider à découvrir où vos efforts d'optimisation auront le meilleur effet sur votre code. Vous pouvez également utiliser gcov avec l'autre outil de profilage, gprof, pour évaluer quelles parties de votre code utilisent le plus grand temps de

calcul.

Les outils de profilage vous aident à analyser les performances de votre code. En utilisant un profileur tel que gcov ou gprof, vous pouvez obtenir certaines statistiques de performance de base, telles que

:
  • la fréquence d'exécution de chaque ligne de
    • code
  • quelles lignes de code sont réellement
    • exécutées
  • le temps de calcul
    • utilisé par chaq
ue section de code

Une fois que vous savez comment votre code fonctionne lorsqu'il est compilé, vous pouvez examiner chaque module pour voir quels modules devraient être optimisés. gcov vous aide à déterminer où travailler sur

l'optimisation.

Les développeurs de logiciels utilisent également le test de couverture en conjonction avec des suites de tests, pour s'assurer que le logiciel est réellement suffisamment bon pour une publication. Les suites de tests peuvent vérifier qu'un programme fonctionne comme prévu ; un programme de couverture teste pour voir dans quelle mesure le programme est exercé par la suite de tests. Les développeurs peuvent alors déterminer quels types de cas de test doivent être ajoutés aux suites de tests pour créer à la fois un meilleur test et un meilleur produit

final.

Vous devriez compiler votre code sans optimisation si vous prévoyez d'utiliser gcov car l'optimisation, en combinant certaines lignes de code en une fonction, peut ne pas vous donner autant d'informations que nécessaire pour rechercher les « points chauds » où le code utilise une grande quantité de temps de calcul. De même, parce que gcov accumule les statistiques par ligne (à la plus basse résolution), il fonctionne le mieux avec un style de programmation qui ne place qu'une seule instruction sur chaque ligne. Si vous utilisez des macros compliquées qui s'étendent en boucles ou en autres structures de contrôle, les statistiques sont moins utiles---elles ne rapportent que la ligne où l'appel de macro apparaît. Si vos macros complexes se comportent comme des fonctions, vous pouvez les remplacer par des fonctions en ligne pour résoudre ce

problème.

gcov crée un fichier journal appelé sourcefile.gcov qui indique combien de fois chaque ligne d'un fichier source sourcefile.c a été exécutée. Vous pouvez utiliser ces fichiers journaux avec gprof pour aider à régler finement la performance de vos programmes. gprof fournit des informations de chronométrage que vous pouvez utiliser avec les informations obtenues à partir de gcov

.

gcov ne fonctionne que sur du code compilé avec GCC. Il n'est pas com

patible avec aucun autre mécanisme de
profilage ou de test de couverture.

-d
--display-progress
Affiche la progression sur la sortie standard.
-f
--function-summaries
Produit des résumés pour chaque fonction en plus du résumé au niveau du fichier.
--include regex
Inclut les fonctions correspondant à regex. Cette option fait en sorte que gcov ne génère des rapports que pour les fonctions correspondant à l'expression régulière étendue regex. Cet indicateur peut être combiné avec --exclude. Si une fonction correspond à la fois aux inclusions et aux exclusions, la dernière inclusion/exclusion s'applique. Par défaut, gcov génère des rapports pour toutes les fonctions, mais si un --include est utilisé, seuls les fonctions correspondant à l'inclusion seront rapportées.
--exclude regex
Exclut les fonctions correspondant à regex. Cette option fait en sorte que gcov ne génère pas de rapports pour les fonctions correspondant à l'expression régulière étendue regex. Cet indicateur peut être combiné avec --include. Si une fonction correspond à la fois aux inclusions et aux exclusions, la dernière inclusion/exclusion s'applique. Par défaut, gcov génère des rapports pour toutes les fonctions, et si --exclude est utilisé, les fonctions correspondantes seront omises.
-h
--help
Affiche l'aide sur l'utilisation de gcov (sur la sortie standard) et quitte sans effectuer de traitement supplémentaire.
-j
--json-format
Produit le fichier gcov dans un format intermédiaire JSON facile à analyser qui ne nécessite pas le code source pour la génération. Le fichier JSON est compressé avec l'algorithme de compression gzip et les fichiers portent l'extension .gcov.json.gz.

La structure du JSON est la suivante :

{
  "current_working_directory": "foo/bar",
  "data_file": "a.out",
  "format_version": "2",
  "gcc_version": "11.1.1 20210510"
  "files": ["$file"]
}

Les champs de l'élément racine ont les sémantiques suivantes :

  • current_working_directory : répertoire de travail où une unité de compilation a été compilée
  • data_file : nom du fichier de données (GCDA)
  • format_version : version sémantique du format

    Changements dans la version 2 :

*
calls : des informations sur les appels de fonctions sont ajoutées
*
gcc_version : version du compilateur GCC

Chaque file a la forme suivante :

{
  "file": "a.c",
  "functions": ["$function"],
  "lines": ["$line"]
}

Les champs de l'élément file ont les sémantiques suivantes :

*
file_name : nom du fichier source

Chaque function a la forme suivante :

{
  "blocks": 2,
  "blocks_executed": 2,
  "demangled_name": "foo",
  "end_column": 1,
  "end_line": 4,
  "execution_count": 1,
  "name": "foo",
  "start_column": 5,
  "start_line": 1
}

Les champs de l'élément function ont les sémantiques suivantes :

  • blocks : nombre de blocs dans la fonction
  • blocks_executed : nombre de blocs exécutés de la fonction
  • demangled_name : nom démêlé de la fonction
  • end_column : colonne dans le fichier source où la fonction se termine
  • end_line : ligne dans le fichier source où la fonction se termine
  • execution_count : nombre d'exécutions de la fonction
  • name : nom de la fonction
  • start_column : colonne dans le fichier source où la fonction commence
  • start_line : ligne dans le fichier source où la fonction commence

Notez que les numéros de ligne et de colonne commencent à 1. Dans l'implémentation actuelle, start_line et start_column n'incluent aucun paramètre de modèle et le type de retour précédent, mais cela sera probablement corrigé à l'avenir.

Chaque line a la forme suivante :

{
  "block_ids": ["$block_id"],
  "branches": ["$branch"],
  "calls": ["$call"],
  "count": 2,
  "conditions": ["$condition"],
  "line_number": 15,
  "unexecuted_block": false,
  "function_name": "foo",
}

Les branches et les appels ne sont présents qu'avec l'option -b. Les champs de l'élément line ont les sémantiques suivantes :

  • block_ids : identifiants des blocs de base appartenant à la ligne
  • count : nombre d'exécutions de la ligne
  • line_number : numéro de ligne
  • unexecuted_block : indicateur si la ligne contient un bloc non exécuté (toutes les instructions de la ligne ne sont pas exécutées)
  • function_name : nom de la fonction à laquelle cette line appartient (pour une ligne avec des instructions intégrées, cela peut ne pas être défini)

Chaque branch a la forme suivante :

{
  "count": 11,
  "destination_block_id": 17,
  "fallthrough": true,
  "source_block_id": 13,
  "throw": false
}

Les champs de l'élément branch ont les sémantiques suivantes :

  • count : nombre d'exécutions de la branche
  • fallthrough : vrai si la branche est une branche de continuation
  • throw : vrai si la branche est une branche exceptionnelle
  • isource_block_id : ID du bloc de base où se produit cette branche
  • destination_block_id : ID du bloc de base vers lequel cette branche saute

Chaque call a la forme suivante :

{
  "destination_block_id": 1,
  "returned": 11,
  "source_block_id": 13
}

Les champs de l'élément call ont les sémantiques suivantes :

  • returned : nombre de fois qu'un appel de fonction est revenu (le nombre d'appels est égal à line::count)
  • isource_block_id : ID du bloc de base où se produit cet appel
  • destination_block_id : ID du bloc de base où l'exécution continue après le retour

Chaque condition a la forme suivante :

{
  "count": 4,
  "covered": 2,
  "not_covered_false": [],
  "not_covered_true": [0, 1],
}

Les champs de l'élément condition ont les sémantiques suivantes :

  • count : nombre de résultats de condition dans cette expression
  • covered : nombre de résultats de condition couverts dans cette expression
  • not_covered_true : termes, par index, non vus comme vrais dans cette expression
  • not_covered_false : termes, par index, non vus comme faux dans cette expression

Lors de l'utilisation de --preserve-paths, gcov utilise le chemin complet des fichiers source pour créer un nom de fichier de sortie. Cela peut entraîner des noms de fichiers longs qui peuvent dépasser les limites du système de fichiers. Cette option crée des noms de la forme fichier-source##md5.gcov, où le composant fichier-source est la dernière partie du nom de fichier et le composant md5 est calculé à partir du nom complet mangé qui aurait été utilisé autrement. L'option est une alternative à --preserve-paths sur les systèmes qui ont
une limite de système de fichiers.

gcov doit être exécuté avec le répertoire courant identique à celui que vous avez utilisé lors de l'invocation du compilateur. Sinon, il ne sera pas en mesure de localiser les fichiers source. gcov produit des fichiers appelés nom-mangé.gcov dans le répertoire courant. Ceux-ci contiennent les informations de couverture du fichier source auquel ils correspondent. Un fichier .gcov est produit pour chaque fichier source (ou d'en-tête) contenant du code, qui a été compilé pour produire les fichiers de données. La partie nom-mangé du nom du fichier de sortie est généralement simplement le nom du fichier source, mais peut être quelque chose de plus compliqué si les options -l ou -p sont fournies. Consultez ces options pour plus de

détails.

Si vous invoquez gcov avec plusieurs fichiers d'entrée, les contributions de chaque fichier d'entrée sont sommées. Typiquement, vous l'invoquerez avec la même liste de fichiers que pour le lien final de votre

exécutable.

Les fichiers .gcov contiennent les champs séparés par : ainsi que le code source du programme. Le format

est 
<nombre_d_exécution>:<numéro_de_ligne>:<texte_de_la_ligne_source
>

Des informations de bloc supplémentaires peuvent suivre chaque ligne, lorsque cela est demandé par une option de ligne de commande. Le nombre_d_exécution est - pour les lignes ne contenant pas de code. Les lignes non exécutées sont marquées ##### ou =====, selon qu'elles sont accessibles par des chemins non exceptionnels ou uniquement par des chemins exceptionnels tels que les gestionnaires d'exceptions C++, respectivement. Avec l'option -a, les blocs non exécutés sont marqués $$$$$ ou %%%%%, selon qu'un bloc de base est accessible via des chemins non exceptionnels ou exceptionnels. Les blocs de base exécutés ayant une instruction avec un nombre_d_exécution égal à zéro se terminent par le caractère * et sont colorés en magenta avec l'option -k. Cette fonctionnalité n'est pas prise en charge en

Ada.

Notez que GCC peut supprimer complètement les corps des fonctions qui ne sont pas nécessaires -- par exemple si elles sont en ligne partout. De telles fonctions sont marquées avec -, ce qui peut être trompeur. Utilisez les options -fkeep-inline-functions et -fkeep-static-functions pour conserver ces fonctions et permettre à gcov d'afficher correctement leur nombre_d_exécution

.

Certaines lignes d'information au début ont un numéro_de_ligne égal à zéro. Ces lignes d'en-tête sont de la

forme 
-:0:<étiquette>:
<valeur>

L'ordre et le nombre de ces lignes d'en-tête seront augmentés à mesure que le développement de gcov progresse --- ne comptez pas sur le fait qu'elles resteront inchangées. Utilisez l'étiquette pour localiser une ligne d'en-tête

particulière.

Les informations de bloc supplémentaires sont de la

forme 
<étiquette>
<information>

L' information est lisible par l'homme, mais conçue pour être suffisamment simple pour une analyse par machine

également.

Lors de l'impression des pourcentages, 0 % et 100 % ne sont imprimés que lorsque les valeurs sont exactement 0 % et 100 % respectivement. Les autres valeurs qui seraient conventionnellement arrondies à 0 % ou 100 % sont plutôt imprimées comme la valeur non limite la plus

proche.

Lors de l'utilisation de gcov, vous devez d'abord compiler votre programme avec une option GCC spéciale --coverage. Cela indique au compilateur de générer les informations supplémentaires nécessaires à gcov (essentiellement un graphe de flux du programme) et inclut également du code supplémentaire dans les fichiers objet pour générer les informations de profilage supplémentaires nécessaires à gcov. Ces fichiers supplémentaires sont placés dans le répertoire où se trouve le fichier

objet.

L'exécution du programme générera une sortie de profilage. Pour chaque fichier source compilé avec -fprofile-arcs, un fichier .gcda correspondant sera placé dans le répertoire du fichier

objet.

L'exécution de gcov avec les noms des fichiers source de votre programme comme arguments produira maintenant une liste du code avec la fréquence d'exécution de chaque ligne. Par exemple, si votre programme s'appelle tmp.cpp, voici ce que vous voyez lorsque vous utilisez la fonctionnalité de base gcov

$ g++ --coverage tmp.o

Pour chaque fonction, une ligne est imprimée indiquant combien de fois la fonction est appelée, combien de fois elle retourne et quel pourcentage des blocs de la fonction a été exécuté.

Pour chaque bloc de base, une ligne est imprimée après la dernière ligne du bloc de base décrivant la branche ou l'appel qui termine le bloc de base. Il peut y avoir plusieurs branches et appels listés pour une seule ligne source s'il y a plusieurs blocs de base qui se terminent sur cette ligne. Dans ce cas, les branches et les appels reçoivent chacun un numéro. Il n'y a pas de moyen simple de mapper ces branches et appels aux constructions sources. En général, cependant, la branche ou l'appel numéroté le plus bas correspondra à la construction la plus à gauche sur la ligne source.

Pour une branche, si elle a été exécutée au moins une fois, un pourcentage indiquant le nombre de fois où la branche a été prise divisé par le nombre de fois où la branche a été exécutée sera imprimé. Sinon, le message "jamais exécuté" est imprimé.

Pour un appel, s'il a été exécuté au moins une fois, un pourcentage indiquant le nombre de fois où l'appel est retourné divisé par le nombre de fois où l'appel a été exécuté sera imprimé. Ce sera généralement 100%, mais peut être inférieur pour les fonctions qui appellent "exit" ou "longjmp", et qui peuvent donc ne pas retourner à chaque fois qu'elles sont appelées.

Les comptes d'exécution sont cumulatifs. Si le programme exemple était exécuté à nouveau sans supprimer le fichier .gcda, le compte du nombre de fois où chaque ligne du code source

e était exécuté serait ajouté aux résultats de l'exécution précédente. Ceci est potentiellement utile de plusieurs manières. Utilisation de gcov avec l'optimisation GCC

Si vous prévoyez d'utiliser gcov pour vous aider à optimiser votre code, vous devez d'abord compiler votre programme avec une option spéciale de GCC : --coverage. En dehors de cela, vous pouvez utiliser toutes les autres options de GCC ; mais si vous voulez prouver que chaque ligne de votre programme a été exécutée, vous ne devez pas compiler avec l'optimisation en même temps. Sur certaines machines, l'optimiseur peut éliminer certaines lignes de code simples en les combinant avec d'autres lignes. Par exemple, un code comme celui-ci :

if (a != b)
  c = 1;
else
  c = 0;

peut être compilé en une seule instruction sur certaines machines. Dans ce cas, il n'y a aucun moyen pour gcov de calculer des comptes d'exécution séparés pour chaque ligne, car il n'y a pas de code séparé pour chaque ligne. Par conséquent, la sortie de gcov ressemble à ceci si vous avez compilé le programme avec l'optimisation :

100:   12:if (a != b)
100:   13:  c = 1;
100:   14:else
100:   15:  c = 0;

La sortie montre que ce bloc de code, combiné par l'optimisation, a été exécuté 100 fois. Dans un sens, ce résultat est correct, car il n'y avait qu'une seule instruction représentant ces quatre lignes. Cependant, la sortie n'indique pas combien de fois le résultat était 0 et combien de fois il était 1.

Les fonctions "inlineables" peuvent créer des comptes de lignes inattendus. Les comptes de lignes sont affichés pour le code source de la fonction "inlineable", mais ce qui est affiché dépend de l'endroit où la fonction est "inline" (insérée), ou si elle n'est pas "inline" du tout.

Si la fonction n'est pas "inline", le compilateur doit générer une copie hors ligne de la fonction, dans tout fichier objet qui en a besoin. Si fileA.o et fileB.o contiennent tous deux des corps hors ligne d'une fonction "inlineable" particulière, ils contiendront également des comptes de couverture pour cette fonction. Lorsque fileA.o et fileB.o sont liés ensemble, l'éditeur de liens sélectionnera, sur de nombreux systèmes, l'un de ces corps hors ligne pour tous les appels à cette fonction, et supprimera ou ignorera l'autre. Malheureusement, il ne supprimera pas les compteurs de couverture pour le corps de fonction inutilisé. Par conséquent, lors de l'instrumentation, toutes les utilisations de cette fonction, sauf une, afficheront des comptes nuls.

Si la fonction est "inline" à plusieurs endroits, la structure des blocs à chaque emplacement peut ne pas être la même. Par exemple, une condition pourrait maintenant être calculable au moment de la compilation dans certains cas. Parce que la couverture de toutes les utilisations de la fonction "inline" sera affichée pour les mêmes lignes sources, les comptes de lignes eux-mêmes pourraient sembler incohérents.

Les applications de longue durée peuvent utiliser les fonctions "__gcov_reset" et "__gcov_dump" pour limiter la collecte de profils à la région du programme d'intérêt. Appeler "__gcov_reset(void)" effacera tous les compteurs de profils d'exécution à zéro, et appeler "__gcov_dump(void)" provoquera le vidage des informations de profil collectées à ce moment-là dans les fichiers de sortie .gcda. Les applications instrumentées utilisent un destructeur statique de priorité 99 pour appeler la fonction "__gcov_dump". Ainsi, "__gcov_dump" est exécuté après tous les destructeurs statiques définis par l'utilisateur, ainsi que les gestionnaires enregistrés avec "atexit".

Si un exécutable charge un objet partagé dynamique via la fonctionnalité dlopen, -Wl,--dynamic-list-data est nécessaire pour vider toutes les données de profil.

La bibliothèque d'exécution de profilage signale diverses erreurs liées à la manipulation et à la sauvegarde du profil. Les erreurs sont imprimées dans la sortie d'erreur standard ou dans le fichier GCOV_ERROR_FILE, si la variable d'environnement est utilisée. Pour terminer immédiatement après une erreur, définissez la variable d'environnement GCOV_EXIT_AT_ERROR. Cela peut aider les utilisateurs à trouver les conflits de profil qui conduisent à un profil trompeur.
