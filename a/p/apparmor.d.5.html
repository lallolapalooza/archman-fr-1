NOM

apparmor.d - syntaxe des profils de sécurité pour AppArmor.

DESCRIPTION

Les profils AppArmor décrivent les droits d'accès obligatoires accordés à des programmes donnés et sont transmis au module d'application de la politique AppArmor à l'aide de apparmor_parser(8). Cette page manuel décrit le format des fichiers de configuration AppArmor ; voir apparmor(7) pour un aperçu d'AppArmor.

FORMAT

La politique AppArmor est écrite dans un langage déclaratif, dans lequel l'ordre des règles au sein d'une section ou d'un bloc donné n'a pas d'importance. La politique est par convention écrite de manière à être répartie dans plusieurs fichiers, mais ceci n'est pas une exigence. Elle pourrait tout aussi facilement être écrite dans un seul fichier. Le langage de la politique est compilé vers un format binaire indépendant de l'architecture qui est chargé dans le noyau pour l'application.

L'unité de base de confinement d'AppArmor est le profil. Il contient un ensemble de règles qui sont appliquées lorsque le profil est associé à un programme en cours d'exécution. Les règles au sein du profil fournissent une liste blanche des différentes permissions qui sont autorisées, ainsi que quelques autres règles spéciales.

Le texte dans la politique AppArmor est divisé en deux sections, le préambule et les définitions de profil. Le préambule doit apparaître au début du fichier et une fois que les définitions de profil commencent, plus aucune règle de préambule n'est autorisée (même dans les fichiers qui sont inclus dans le profil). Lorsque la politique AppArmor (ensemble de profils) est répartie sur plusieurs fichiers, chaque fichier peut avoir son propre préambule, qui peut être identique ou différent de celui des autres fichiers. Les fichiers inclus dans une section de profil ne peuvent pas avoir de section de préambule.

Ce qui suit est une description de type BNF des fichiers de configuration de la politique AppArmor ; voir ci-dessous pour un exemple de fichier de politique AppArmor. Les fichiers de configuration AppArmor sont orientés ligne ; # introduit un commentaire, similaire aux langages de script shell. L'exception à cette règle est que #include va inclure le contenu d'un fichier en ligne dans la politique ; ce comportement est modelé sur cpp(1).

RÈGLE_ALL =

'all'

Toutes les ressources et tous les programmes doivent avoir un chemin complet. Un profil peut contenir un nombre quelconque de sous-profils (alias profils enfants), limité uniquement par la mémoire du noyau. Les noms de sous-profils sont limités à 974 caractères. Les profils enfants peuvent être utilisés pour confiner une application d'une manière spéciale, ou lorsque vous souhaitez que l'enfant soit non confiné sur le système, mais confiné lorsqu'il est appelé depuis le parent. Les « hats » (chapeaux)

sont un profil enfant spécial
qui peut être utilisé avec l'appel

aa_change_hat(2) de l'API. Les applications écrites ou modifiées pour utiliser aa_change_hat(2) peuvent tirer parti des sous-profils pour s'exécuter sous différentes restrictions, en fonction de la logique du programme. Plusieurs applications prenant en charge aa_change_hat(2) existent, notamment un module Apache, mod_apparmor(5) ; un module PAM, pam_apparmor ; et une valve Tomcat, tomcat_apparmor. Les applications écrites ou modifiées pour utiliser change_profile(2) transitionnent de manière permanente vers le profil spécifié. libvirt est une telle

application.

En-tête de

profil

L'en-tête de profil se compose d'un nom requis qui est unique et de conditionnels d'attachement et de drapeaux de contrôle

optionnels.

No

m

Le nom du profil est son identifiant. C'est ce qui est affiché lors de l'introspection (ex. ps -Z), et il définit comment le profil est référencé par les règles de politique pour toute interaction de politique via ipc ou les changements de domaine. Il est recommandé que le nom soit court et signifiant pour l'application à laquelle il est appliqué, ex. firefo

x

pour le navigateur web firefox ou son rôle fonctionnel, ex. log_admin. Si le nom est le chemin absolu complet d'une application, ex. /usr/bin/firefo

x

et qu'un conditionnel d'attachement exec n'est pas spécifié, le nom est également utilisé comme conditionnel d'attachement exec du profil. Cet usage a cependant été déconseillé et est découragé car il entraîne des noms longs qui peuvent rendre les règles de profil difficiles à comprendre, et peuvent ne pas être entièrement affichés par certains outils

d'introspection.

Conditionnels

d'attachement

Les conditionnels d'attachement sont utilisés lors des changements de profil pour déterminer si un profil correspond à la transition de profil proposée. Les conditionnels d'attachement sont optionnels, leur application et leur moment sont déterminés par les conditions spécifiques

utilisées.

Lorsque des conditionnels d'attachement sont utilisés, les conditionnels d'attachement de tous les profils dans l'espace de noms seront évalués. Le profil avec l'ensemble d'attachements qui donnent la meilleure correspondance deviendra le nouveau profil après une opération de transition. Les attachements qui ne correspondent pas entraîneront que le profil ne sera pas disponible pour la

transition.

Si aucun conditionnel n'est spécifié, le profil ne sera utilisé que si une transition spécifie explicitement le nom du

profil.

Ce conditionnel n'est utilisé que lors d'une opération exec lorsque la règle exec correspondante spécifie un type de transition px ou cx (ou leurs dérivés). Le conditionnel d'attachement exec sera également utilisé par les tâches qui sont non confinées car elles utilisent une règle de transition pix . S'il n'y a aucune correspondance d'attachement, c'est à la règle exec de déterminer ce qui se passe (échec ou une option de repli). Note : voir le profil Nom pour des informations concernant l'utilisation du nom du profil comme conditionnel

d'attachement.

Si l'heuristique ne peut pas déterminer un gagnant entre plusieurs correspondances, l'exec sera

refusé.

Règles de lien

Les règles de lien permettent de spécifier la permission de former un lien dur comme une paire lien-cible. Si la condition de sous-ensemble est spécifiée, alors les permissions pour accéder au fichier lien doivent être un sous-ensemble des permissions du profil pour accéder au fichier cible. S'il existe une règle 'x' sur le nouveau lien, elle doit correspondre exactement au fichier original.

Par ex.

/file1  r,
/file2  rwk,
/link*  rw,
link subset /link* -> /**,

La règle de lien permet de lier /link à /file1 ou /file2 par nom, cependant, parce que le fichier /link a les permissions 'rw', il n'est pas autorisé à lier /file1 car cela accorderait un chemin d'accès à /file1 avec plus de permissions que les permissions 'r' spécifiées par le profil.

Un lien de /link vers /file2 serait autorisé car les permissions 'rw' de /link sont un sous-ensemble des permissions 'rwk' pour /file1.

La règle de lien est équivalente à spécifier la permission de lien 'l' comme permission en tête sans aucune autre permission d'accès au fichier. Lorsque c'est fait, les options de règle de lien peuvent être spécifiées.

La règle de lien suivante est équivalente à la règle de fichier avec la permission 'l'

link /foo -> bar,
l /foo -> /bar,

Les règles de fichier qui spécifient la permission 'l' et ne spécifient pas les permissions de lien étendues correspondent aux règles de lien comme suit.

/foo l,
l /foo,
link subset /foo -> /**,

Règles réseau

AppArmor prend en charge une médiation réseau simple et à gros grains. La règle réseau restreint toutes les opérations basées sur socket(2) . La médiation effectuée est une vérification à gros grains sur la possibilité de créer, lire ou écrire un socket d'un type et d'une famille donnés. Les règles réseau netlink(7) ne peuvent spécifier que les types 'dgram' et 'raw'.

Les règles réseau AppArmor sont accumulées afin que les permissions réseau accordées soient l'union de toutes les permissions des règles réseau listées.

Les règles réseau AppArmor sont larges et générales et deviennent plus restrictives à mesure que davantage d'informations sont spécifiées.

par ex.

network,               #autoriser l'accès à tous les réseaux
network tcp,           #autoriser l'accès à tcp
network inet tcp,      #autoriser l'accès à tcp uniquement pour les adresses inet4
network inet6 tcp,     #autoriser l'accès à tcp uniquement pour les adresses inet6
network netlink raw,   #autoriser l'accès à AF_NETLINK SOCK_RAW

Permissions réseau

Les permissions de règle réseau sont implicites lorsqu'une règle ne spécifie pas explicitement une liste d'accès. Par défaut, si une règle n'a pas de liste d'accès, toutes les permissions compatibles avec l'ensemble spécifié de conditionnels locaux et pairs sont implicites.

Les permissions create, bind, listen, shutdown, getattr, setattr, getopt et setopt sont des permissions de socket local. Elles ne s'appliquent qu'au socket local et ne peuvent pas être spécifiées dans des règles ayant un conditionnel pair. La permission accept s'applique à la combinaison d'un socket local et d'un socket pair. Les permissions connect, send et receive sont des permissions de socket pair.

Médiation de la famille inet/inet6

AppArmor prend en charge une médiation à grain fin des familles inet et inet6 en utilisant les conditionnels ip et port. Le conditionnel ip accepte à la fois IPv4 et IPv6 en utilisant la représentation habituelle de quatre octets séparés par '.' pour IPv4 et de huit groupes de quatre nombres hexadécimaux séparés par ':' pour IPv6. Les zéros de tête contigus peuvent être remplacés par '::' une fois. Sur un socket connecté, l'émetteur et le récepteur n'ont pas besoin d'être spécifiés dans les appels système recvfrom et sendto. Dans ce cas, et avec des sockets non liés, l'adresse IP est none, ou inconnue. Les adresses IP inconnues ou non liées sont représentées dans la politique par le mot-clé 'none'. Lorsque le conditionnel ip est omis, toutes les adresses IP seront autorisées : IPv4, IPv6 et none. Si INADDR_ANY ou in6addr_any est utilisé, le conditionnel ip peut être omis ou ils peuvent être représentés par :

network ip=::,         #autoriser in6addr_any
network ip=0.0.0.0;    #autoriser INADDR_ANY

Les règles réseau prennent en charge la spécification d'adresses IP locales et distantes, de ports et de plages de ports.

network ip=127.0.0.1 port=8080,
network peer=(ip=10.139.15.23 port=8081),
network ip=fd74:1820:b03a:b361::cf32 peer=(ip=fd74:1820:b03a:b361::a0f9),
network port=8080 peer=(port=8081),
network ip=127.0.0.1 port=8080 peer=(ip=10.139.15.23 port=8081),
network ip=127.0.0.1 port=8080-8084,

Règles de montage

AppArmor prend en charge la médiation de montage et permet de spécifier les types de systèmes de fichiers et les drapeaux de montage. La syntaxe des règles de montage dans AppArmor est basée sur la syntaxe de la commande mount(8) . Les règles de montage doivent contenir l'un des mots-clés mount, remount ou umount, mais toutes les conditions de montage sont facultatives. Les conditionnels facultatifs non spécifiés sont supposés correspondre à toutes les entrées (par ex, ne pas spécifier fstype signifie que tous les fstypes correspondent). En raison de la complexité de la commande mount et de la manière dont les options peuvent être spécifiées, AppArmor permet de spécifier les conditionnels de trois manières différentes :

1.
Si un conditionnel est spécifié avec '=', alors la règle n'accorde la permission qu'aux montages correspondant aux options exactement spécifiées. Par exemple, une politique AppArmor avec la règle suivante : 
mount options=ro /dev/foo -> /mnt/,

correspondrait à :

$ mount -o ro /dev/foo /mnt

mais pas à l'une ou l'autre de celles-ci :

$ mount -o ro,atime /dev/foo /mnt
$ mount -o rw /dev/foo /mnt
2.
Si un conditionnel est spécifié avec 'in', alors la règle accorde la permission aux montages correspondant à n'importe quelle combinaison des options spécifiées. Par exemple, si une politique AppArmor a la règle suivante : 
mount options in (ro,atime) /dev/foo -> /mnt/,

toutes ces commandes de montage correspondraient :

$ mount -o ro /dev/foo /mnt

Règles de files d'attente de messages

AppArmor prend en charge la médiation des files d'attente de messages POSIX et SYSV.

Les permissions de file d'attente de messages AppArmor sont implicites lorsqu'une règle ne spécifie pas explicitement une liste d'accès. Par défaut, toutes les permissions de file d'attente de messages sont implicites.

Les permissions de file d'attente de messages AppArmor deviennent plus restrictives à mesure que des informations supplémentaires sont spécifiées. La politique peut être spécifiée en déterminant son mode d'accès, son type, son étiquette et son nom de file d'attente de messages.

Concernant les modes d'accès, 'r' et 'read' sont utilisés pour lire les messages de la file d'attente. 'w' et 'write' sont utilisés pour écrire dans la file d'attente de messages. 'create' est utilisé pour créer la file d'attente de messages, et 'open' est utilisé pour obtenir l'identifiant de la file d'attente de messages lorsque la file est déjà créée. 'delete' est utilisé pour supprimer la file d'attente de messages. Les modes d'accès pour obtenir et définir les attributs de la file d'attente de messages sont 'setattr' et 'getattr'.

Le type de la politique peut être 'posix' ou 'sysv'. Ces informations sont pertinentes lorsque le nom de la file d'attente de messages n'est pas spécifié, et lorsqu'il est spécifié, il peut être déduit du nom de la file d'attente, car les noms de files d'attente de messages pour posix doivent commencer par '/', et les clés de files d'attente de messages pour SYSV doivent être un entier positif.

L'étiquette de la politique est l'étiquette attribuée à la file d'attente de messages lors de sa création.

Le nom de la file d'attente de messages peut être une chaîne commençant par '/' si le type est POSIX, ou un entier positif si le type est SYSV. Si le type n'est pas spécifié, il sera déduit du nom de la file d'attente.

Exemples de règles de files d'attente de messages AppArmor :

# Autoriser tout accès aux files d'attente de messages
mqueue,
# Autoriser explicitement tout accès aux files d'attente de messages,
mqueue (create, open, delete, read, write, getattr, setattr),
# Refuser explicitement l'utilisation des files d'attente de messages
deny mqueue,
# Autoriser tout accès pour une file d'attente POSIX de nom /bar
mqueue type=posix /bar,
# Autoriser la permission de création pour une file d'attente SYSV d'étiquette foo
mqueue create label=foo 123,

AppArmor prend en charge la médiation de ptrace(2). Les règles PTrace d'AppArmor sont accumulées de sorte que les permissions PTrace accordées soient l'union de toutes les permissions des règles PTrace listées.

Les permissions PTrace d'AppArmor sont implicites lorsqu'une règle ne spécifie pas explicitement une liste d'accès. Par défaut, toutes les permissions PTrace sont implicites.

ptrace (readby, tracedby) peer=unconfined,

Rlimit rules

AppArmor can set and control the resource limits associated with a profile as described in the setrlimit(2) man page.

The AppArmor rlimit controls allow setting of limits and restricting changes of them and these actions can be audited. Enforcement of the set limits is handled by the standard kernel enforcement mechanism for rlimits and will not result in an audited apparmor message if the limit is enforced.

If a profile does not have an rlimit rule associated with a given rlimit then the rlimit is left alone and regular access, including changing the limit, is allowed. However if the profile sets an rlimit then the current limit is checked and if greater than the limit specified in the rule it will be changed to the specified limit.

AppArmor rlimit rules control the hard limit of an application and ensure that if the hard limit is lowered that the soft limit does not exceed the hard limit value.

Eg.

set rlimit data <= 100M,
set rlimit nproc <= 10,
set rlimit nice <= 5,

Variables

AppArmor's policy language allows embedding variables into file rules to enable easier configuration for some common (and pervasive) setups. Variables may have multiple values assigned, but any variable assignments must be made before the start of the profile.

The parser will automatically expand variables to include all values that they have been assigned; it is an error to reference a variable without setting at least one value. You can use empty quotes ("") to explicitly add an empty value.

At the time of this writing, the following variables are defined in the provided AppArmor policy:

@{HOMEDIRS}
@{multiarch}
@{pid}
@{pids}
@{PROC}

@{apparmorfs}

@{XDG_DESKTOP_DIR}
@{XDG_DOWNLOAD_DIR}
@{XDG_TEMPLATES_DIR}
@{XDG_PUBLICSHARE_DIR}

@{XDG_PICTURES_DIR}

These are defined in files in /etc/apparmor.d/tunables and are used in many of the abstractions described later.

You may also add files in /etc/apparmor.d/tunables/home.d for site-specific customization of @{HOMEDIRS}, /etc/apparmor.d/tunables/multiarch.d for @{multiarch} and /etc/apparmor.d/tunables/xdg-user-dirs.d for @{XDG_*}.

The special @{profile_name} variable is set to the profile name and may be used in all policy.

Notes on variable expansion and the / character

It is important to note that how AppArmor performs variable expansion depends on the context where a variable is used. When a variable is expanded it can result in a string with multiple path characters next to each other, in a way that is not evident when looking at policy.

Eg.

Given the following variable definition and rule

@{HOME}=/home/*/ file rw @{HOME}/*,

The variable expansion results in a rule of

file rw /home/*//*.

When this occurs in a context where a path is expected, AppArmor will canonicalize the path by collapsing consecutive / characters into a single character. For the above example, this would be

file rw /home/*/*,

There is one exception to this rule, when the consecutive / characters are at the beginning of a path, this indicates a posix namespace and the characters will not be collapsed.

Eg.

@{HOME}=/home/*/ file rw /@{HOME}/*,

will result in an expansion of

file rw //home/*//*,

which is collapsed to

file rw //home/*/*,

Note: that the leading // in the above example is not collapsed to a single /. However the second // (that was also seen in the first example) is collapsed.

Alias rules

AppArmor also provides alias rules for remapping paths for site-specific layouts. They are an alternative form of path rewriting to using variables, and are done after variable resolution. Alias rules must occur within the preamble of the profile. System-wide aliases are found in /etc/apparmor.d/tunables/alias, which is included by /etc/apparmor.d/tunables/global. /etc/apparmor.d/tunables/global is typically included at the beginning of an AppArmor profile.

Globbing (AARE)

File resources and other parameters accepting an AARE may be specified with a globbing syntax similar to that used by popular shells, such as csh(1), bash(1), zsh(1).

*
can substitute for any number of characters, excepting '/'
**
can substitute for any number of characters, including '/'
?
can substitute for any single character excepting '/'
[abc]
will substitute for the single character a, b, or c
[a-c]
will substitute for the single character a, b, or c
[^a-c]
will substitute for any single character not matching a, b or c
{ab,cd}
will expand to one rule to match ab, one rule to match cd

Can also include variables.

@{variable}
will expand to all values assigned to the given variable.

When AppArmor looks up a directory the pathname being looked up will end with a slash (e.g., /var/tmp/); otherwise it will not end with a slash. Only rules that match a trailing slash will match directories. Some examples, none matching the /tmp/ directory itself, are:

/tmp/*
Files directly in /tmp.
/tmp/*/
Directories directly in /tmp.
/tmp/**
Files and directories anywhere underneath /tmp.
/tmp/**/
Directories anywhere underneath /tmp.

Rule Qualifiers

There are several rule qualifiers that can be applied to permission rules. Rule qualifiers can modify the rule and/or permissions within the rule.

priority
Specifies the priority of the rule. Currently the allowed range is -1000 to 1000 with the default priority of rule is 0. Rules with higher priority are given preferences and will completely override permissions of lower priority rules where they overlap. When rules partially overlap the permissions of the higher priority rule will completely override lower priority rules within in overlap. Within a given priority level rules that overlap will accumulate permissions in the standard apparmor fashion.
allow
Specifies that permissions requests that match the rule are allowed. This is the default value for rules and does not need to be specified. Conflicts with the deny qualifier.
audit
Specifies that permissions requests that match the rule should be recorded to the audit log.
deny
Specifies that permissions requests that match the rule should be denied without logging. Can be combined with 'audit' to enable logging. Conflicts with the allow qualifier.
owner
Specifies that the task must have the same euid/fsuid as the object being referenced by the permission check.

Qualifier Blocks

Rule Qualifiers can be applied to multiple rules at a time by grouping the rules into a rule block.

audit {
   /foo r,
   network,
}

#include mechanism

AppArmor provides an easy abstraction mechanism to group common access requirements; this abstraction is an extremely flexible way to grant site-specific rights and makes writing new AppArmor profiles very simple by assembling the needed building blocks for any given program.

The use of '#include' is modelled directly after cpp(1); its use will replace the '#include' statement with the specified file's contents. The leading '#' is optional, and the '#include' keyword can be followed by an option conditional 'if exists' that specifies profile compilation should continue if the specified file or directory is not found.

#include "/absolute/path" specifies that /absolute/path should be used. #include "relative/path" specifies that relative/path should be used, where the path is relative to the current working directory. #include <magic/path> is the most common usage; it will load magic/path relative to a directory specified to apparmor_parser(8). /etc/apparmor.d/ is the AppArmor default.

The supplied AppArmor profiles follow several conventions; the abstractions stored in /etc/apparmor.d/abstractions/ are some large clusters that are used in most profiles. What follows are short descriptions of how some of the abstractions are used.

abstractions/audio
Includes accesses to device files used for audio applications.
abstractions/authentication
Includes access to files and services typically necessary for services that perform user authentication.
abstractions/base
Includes files that should be readable and writable in all profiles.
abstractions/bash
Includes many files used by bash; useful for interactive shells and programs that call system(3).
abstractions/consoles
Includes read and write access to the device files controlling the virtual console, sshd(8), xterm(1), etc. This abstraction is needed for many programs that interact with users.
abstractions/fonts
Includes files necessary for font configuration and usage.

NAME

apparmor.d - AppArmor profile directory

DESCRIPTION

The apparmor.d directory is the root directory for AppArmor profiles. These profiles are used to confine applications to a specific set of system resources.

Profiles are organised in directories, and by default all profiles in the /etc/apparmor.d/ directory are loaded when AppArmor starts.

AppArmor supports using include files to break down complex profiles into smaller, more manageable pieces. These include files are often placed in subdirectories of /etc/apparmor.d/. Some common abstractions are included in the abstractions/ subdirectory.

Abstractions

Abstractions are include files that represent common sets of permissions. They are typically used to simplify AppArmor profiles by providing pre-defined rules for common tasks or application types.

abstractions/fonts
Inclut l'accès aux polices et aux bibliothèques de polices.
abstractions/gnome
Inclut l'accès en lecture et écriture aux fichiers de configuration GNOME, ainsi que l'accès en lecture aux bibliothèques GNOME.
abstractions/kde
Inclut l'accès en lecture et écriture aux fichiers de configuration KDE, ainsi que l'accès en lecture aux bibliothèques KDE.
abstractions/kerberosclient
Inclut les règles d'accès aux fichiers nécessaires pour les clients Kerberos courants.
abstractions/nameservice
Inclut des règles de fichiers pour autoriser les recherches DNS, LDAP, NIS, SMB, les bases de données de mots de passe utilisateurs et groupes, les services et les protocoles.
abstractions/perl
Inclut l'accès en lecture aux modules Perl.
abstractions/user-download
abstractions/user-mail
abstractions/user-manpages
abstractions/user-tmp
abstractions/user-write
Certains profils pour les programmes typiques "utilisateur" utiliseront ces fichiers d'inclusion pour décrire les droits des utilisateurs sur le système.
abstractions/wutmp
Inclut l'accès en écriture aux fichiers utilisés pour maintenir les bases de données wtmp(5) et utmp(5), utilisées avec les commandes w(1) et associées.
abstractions/X
Inclut l'accès en lecture aux bibliothèques, aux fichiers de configuration, aux fichiers d'authentification X et au socket X.

Certaines abstractions reposent sur des variables définies dans des fichiers du répertoire /etc/apparmor.d/tunables/. Ces variables sont actuellement @{HOME} et @{HOMEDIRS}. Les variables ne peuvent pas être définies dans la portée du profil ; elles ne peuvent être définies qu'avant le profil. Par conséquent, tout profil utilisant des abstractions devrait soit #include <tunables/global> soit s'assurer que @{HOME} et @{HOMEDIRS} sont définis avant le début de la définition du profil. Les utilitaires aa-autodep(8) et aa-genprof(8) émettront automatiquement #include <tunables/global> dans les profils générés.

Feature ABI

Le `feature abi` indique à AppArmor avec quel ensemble de fonctionnalités la politique a été développée. Ceci est important pour s'assurer que les noyaux avec un ensemble de fonctionnalités différent n'appliquent pas des fonctionnalités que la politique ne supporte pas, ce qui pourrait entraîner des échecs inattendus de l'application.

Lors de la compilation de la politique, l'ABI des fonctionnalités du noyau et l'ABI des fonctionnalités de la politique sont consultés pour construire une politique qui fonctionnera pour le noyau du système.

Si le noyau prend en charge une fonctionnalité non prise en charge par la politique, la politique sera construite de manière à ce que le noyau N'APPLIQUE PAS cette fonctionnalité.

Si la politique prend en charge une fonctionnalité non prise en charge par le noyau, la compilation peut dégrader la règle avec la fonctionnalité vers quelque chose que le noyau supporte, supprimer complètement la règle, ou échouer la compilation.

Si l'ABI de la politique est spécifié comme kernel, l'ABI du noyau en cours d'exécution sera utilisé. Ceci ne devrait jamais être utilisé dans une politique livrée car cela peut causer des problèmes sur le système lors de l'installation d'un nouveau noyau.

Compatibilité ABI avec AppArmor 2.x

AppArmor 3 reste compatible avec AppArmor 2.x en détectant quand un profil n'a pas d'ABI de fonctionnalités spécifié. Dans ce cas, la compilation de la politique appliquera soit l'ABI de fonctionnalités épinglé tel que spécifié par le fichier de configuration ou la ligne de commande, soit, si aucun des deux n'est appliqué, utilisera un ABI de fonctionnalités par défaut.

Il est important de noter que l'ABI de fonctionnalités par défaut ne prend pas en charge les nouvelles fonctionnalités ajoutées dans AppArmor 3 ou ultérieur.

Un exemple de profil AppArmor :

# quelle ABI de fonctionnalité la politique a été développée avec
abi <abi/3.0>,
# une définition de variable dans le préambule
@{HOME} = /home/*/ /root/
# un commentaire sur foo.
/usr/bin/foo {
  /bin/mount          ux,
  /dev/{,u}random     r,
  /etc/ld.so.cache    r,
  /etc/foo.conf       r,
  /etc/foo/*          r,
  /lib/ld-*.so*       rmix,
  /lib/lib*.so*       r,
  /proc/[0-9]**       r,
  /usr/lib/**         r,
  /tmp/foo.pid        wr,
  /tmp/foo.*          lrw,
  @{HOME}/.foo_file  rw,
  /usr/bin/baz        Cx -> baz,
  # un commentaire sur le chapeau (sous-profil) de foo, bar.
  ^bar {
    /lib/ld-*.so*       rmix,
    /usr/bin/bar        rmix,
    /var/spool/*        rwl,

KNOWN BUGS

  • Les options de montage prennent en charge la correspondance de motifs, mais les drapeaux de montage ne sont pas correctement intersectés avec les motifs spécifiés. Par exemple, 'mount options=**,' devrait être équivalent à 'mount,', mais ce n'est pas le cas. (LP : #965690)
  • Le type de système de fichiers (fstype) peut ne pas être comparé lorsque certains drapeaux de la commande mount sont utilisés. Spécifiquement, la correspondance de fstype ne fonctionne actuellement que lors de la création d'un nouveau montage et non lors d'un remount, bind, etc.
  • Les règles de montage avec plusieurs conditions 'options' ne sont pas appliquées comme documenté, mais fusionnées de telle sorte que 'options in (ro,nodev) options in (atime)' est équivalent à 'options in (ro,nodev,atime)'.
  • Lors de la spécification des options de montage avec la condition 'in', les valeurs positives et négatives correspondent lorsqu'une seule est spécifiée. Par exemple, 'rw' correspond lorsque 'ro' est spécifié et 'dev' correspond lorsque 'nodev' est spécifié, de sorte que 'options in (ro,nodev)' est équivalent à 'options in (rw,dev)'.
