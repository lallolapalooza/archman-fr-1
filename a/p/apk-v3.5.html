DESCRIPTIO

N

Un fichier .apk v3 contient le contenu d'un seul paquet, certaines métadonnées et certaines signatures. Le fichier .apk contient un arbre d'objets, représenté dans un format binaire personnalisé et se conformant globalement à un schéma prédéfini. Ce format de fichier est désigné à l'intérieur de apk(5) sous le no

m de
« adb ».

SCHÉMAS DE

FICHIERS

Un schéma est une représentation des éléments de données attendus dans un fichier adb. Les schémas forment un arbre, où les nœuds sont soit des schémas scalaires (qui sont des feuilles dans l'arbre), soit des schémas de tableau/objet, qui eux-mêmes ont des enfants. Par exemple, le schéma pour un objet paquet pourrait déclarer qu'il contient des champs qui eux-mêmes se conforment au schéma de tableau de chaînes, ou au schéma pkginfo, ou

similaire.

Les schémas eux-mêmes ne sont pas représentés dans le fichier adb d'aucune manière ; ils existent dans les parties de apk(1) qui lisent et écrivent de tels fichiers. Une description complète de tous les schémas d'apk serait longue, mais comme exemple, voici le schéma pour un fichier unique à l'intérieur d'un paquet

BLOC

S

Un fichier adb réel est composé d'une séquence de blocs typés ; un bloc commence également par un mot de tag de 32 bits en ordre little-endian, qui a deux bits de type et 30 bits de taille. Les deux bits de type sont

: x0 DB x1 IG x2 TA x3 ATA
0A
0S
0DA
0D
X

Le fichier adb doit commencer par un bloc ADB, puis éventuellement un ou plusieurs blocs SIG, puis un ou plusieurs blocs DATA. Le bloc ADB doit commencer par un nombre magique indiquant le schéma pour l'objet racine de l'ensemble du bloc ADB. Le bloc ADB contient également, en dehors de l'objet racine, certaines métadonnées décrivant la version du format adb

utilisé.

Le bloc SIG contient une ou plusieurs signatures du bloc ADB. Les signatures de la même version doivent être dans le même bloc SIG. Si dans le futur, une nouvelle version de signature est spécifiée, et que le paquet doit contenir pour des raisons de compatibilité deux versions différentes de signature pendant la période de transition, alors il doit y avoir deux blocs de signature, un pour chaque

version.

Contrairement au format v2, le nom de clé utilisé pour la signature n'est pas explicitement spécifié. À la place, un ID intrinsèque de la clé est utilisé pour la recherche, donc les vérificateurs doivent trouver la clé en se basant sur l'ID de la clé. Également contrairement au format v2, le bloc ADB n'est pas signé directement, mais il est d'abord haché par un hachage sécurisé (actuellement SHA512). Après cela, une petite charge utile avec ce hachage pré-calculé est signée par l'algorithme donné (généralement la charge utile est ensuite hachée à nouveau par le processus de signature avec un hachage sécurisé basé sur l' algorithme de signature)

.

Les blocs DATA sont utilisés pour stocker uniquement les données des fichiers du paquet ; toutes les métadonnées des fichiers, y compris les hachages de contenu, sont stockées dans le bloc ADB à la place. Le contenu des blocs DATA est donc protégé par les hachages donnés dans le bloc ADB, qui est lui-même protégé par la signature dans le bloc

SIG.
