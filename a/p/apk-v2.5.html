NOM

apk v2 - aperçu du format apk v2

DESCRIPTION

Un fichier .apk v2 contient le contenu d'un seul paquet, des métadonnées et des signatures. Le fichier .apk contient trois flux gzip concaténés, qui forment ensemble une seule archive tar. L'archive tar contient trois sections : les signatures, la section de contrôle et la section de données.

LES SIGNATURES

Les signatures sont une séquence de fichiers dont les noms commencent par ".SIGN.", qui doivent précéder toute autre donnée dans le tarball. Ces noms de fichiers ressemblent à ceci :

.SIGN.<algorithme>.<idclé>

où <algorithme> doit être l'un de DSA, RSA, RSA256, et RSA512 et <idclé> doit être le nom du fichier de la clé dans /etc/apk/keys (voir apk-keys(5)).

La signature peut être calculée soit sur les métadonnées (si les métadonnées contiennent un hachage de données pour les données), soit sur les métadonnées et les données ensemble (si les métadonnées ne contiennent pas de hachage de données).

Une seule signature d'une clé de confiance est suffisante, donc un apk peut être signé par plusieurs clés différentes si nécessaire, tant que les clients en font confiance à au moins une.

LA SECTION DE CONTRÔLE

Dans un fichier apk v2, les métadonnées du paquet sont stockées dans un seul fichier appelé PKGINFO. Ce fichier utilise un format clé-valeur, dans lequel les clés et les valeurs sont séparées par " = " et les lignes commençant par "#" sont des commentaires. Il existe de nombreuses clés autorisées et il n'y a pas de liste centralisée de clés connues ; la source de abuild(1) est la meilleure référence.

Une clé est importante pour comprendre le format v2 car elle affecte l'interprétation de la signature : s'il existe une clé "datahash" dans PKGINFO, sa valeur est le hachage sha256 de la partie données de l'apk. Les paquets sont censés avoir un datahash, mais les index ne le font pas.

La section de contrôle est également l'endroit où résident les scripts de crochet pré/post pour l'installation, la désinstallation et la mise à niveau, ainsi que les déclencheurs.

LA SECTION DE DONNÉES

La section de données est simplement une archive tar du contenu du paquet, telle que produite par le processus de construction. Ces fichiers sont post-traités par abuild-tar(1) et utilisent des en-têtes étendus pax pour inclure des sommes de contrôle par fichier dans un en-tête nommé APK-TOOLS.checksum.<hachage>.

EXEMPLE

À titre d'exemple, l'apk v2 de scdoc(1) lui-même contient ces fichiers dans cet ordre :

.SIGN.RSA.alpine-devel@lists.alpinelinux.org-6165ee59.rsa.pub
.PKGINFO
usr/
usr/bin/
usr/bin/scdoc
usr/share/
usr/share/pkgconfig/
usr/share/pkgconfig/scdoc.pc

Comme les fichiers apk v2 sont simplement des tarballs (divisés en plusieurs flux gzip), ils peuvent être inspectés et décompressés avec tar(1), bien qu'il faille être prudent lors de leur modification pour ne pas réordonner les sections ou invalider la signature. Il est préférable d'utiliser abuild(1) pour les modifier. Si vous souhaitez les décomposer en leurs flux gzip constituants, vous pouvez utiliser abuild-gzsplit(1).

NOTES

Seul le schéma de signature "RSA" (signifiant RSA + SHA1) est actuellement utilisé par abuild(1).

VOIR AUSSI

abuild(1), apk(8), apk-package(5), apk-v3(5)
