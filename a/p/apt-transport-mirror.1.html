Ce transport APT n'implémente pas à lui seul un protocole pour accéder à des dépôts locaux ou distants, mais récupère une liste de miroirs et redirige toutes les requêtes vers le ou les miroirs choisis dans cette apt-tran. La fonctionnalité de base est disponible depuis apt 0.7.24, mais elle était non documentée jusqu'à apt 1.6 qui contenait une refonte complète du transport et de ses fonctionnalités prises en charge. Notez qu'un transport n'est jamais appelé directement par un utilisateur, mais utilisé
l'utilisateur.

Si l'acquisition d'un fichier via un miroir échoue, la méthode s'assure qu'un autre miroir possible de la liste est automatiquement essayé jusqu'à ce que le fichier soit récupéré ou qu'aucun miroir ne reste dans la liste, gérant de manière transparente

les temps d'arrêt des serveurs et les problèmes similaires.

Les implications de sécurité du transport dépendent des considérations de sé

curité associées au transport utilisé pour récupérer la liste de miroirs et
des transports impliqués dans l'accès aux miroirs choisis par le transport.

S

Ce transport n'a actuellement aucune option de configuration. La sélection des miroirs est entièrement basée sur les miroirs offerts dans la liste de miroirs et les fichiers qu'APT doit acquérir. Format de la liste de

miroirs

Une liste de miroirs contient une ou plusieurs lignes, chacune spécifiant un URI pour un miroir. Les lignes vides et celles commençant par un caractère dièse (#) sont ignorées. Un URI commence toujours par un schéma URI qui définit le transport utilisé pour ce miroir. Si par exemple l'URI commence par http:, le transport responsable

est

apt-tra

nsport-
http(1)

qui peut avoir des exigences spécifiques pour le format de la partie restante

de l'URI.

Des métadonnées sur un miroir peuvent être données sur la même ligne, séparées de l'URI par une tabulation. Plusieurs éléments de métadonnées peuvent eux-mêmes être séparés par des tabulations ou des espaces. (Ceci est une fonctionnalité avancée disponible uniquement avec apt >= 1.6. Les versions antérieures d'apt échoueront à analyser les listes de miroirs utilisant cette fonctionnalité.

)

Depuis apt 1.6, l'utilisation de listes de miroirs compressées est également prise en charge. Notez que le nom de fichier de la liste de miroirs doit spécifier l'algorithme de compression utilisé ; il n'y a pas de détection automatique basée sur le contenu

du fichier.

Sélection des miroirs par métadonnées Comme spécifié dans le format, un miroir peut avoir des métadonnées supplémentaires attachées pour empêcher un miroir d'être sélectionné pour acquérir un fichier ne correspondant pas à ces métadonnées. De cette façon, la liste de miroirs peut par exemple contenir des miroirs partiels ne servant que certaines architectures, et APT choisira automatiquement un miroir différent pour les fichiers nécessitant une architecture non listée. Les limites prises en charge sont l'architecture (arch), le nom de code de la version (codename), le composant du dépôt auquel appartient le fichier (component), la langue à laquelle le fichier s'applique (lang), le nom de suite de la version (suite) et le type de fichier

(type).

Ordre de repli des

miroirs

Si aucune priorité n'est donnée pour un miroir via la clé de métadonnées priority, l'ordre dans lequel les miroirs sont contactés est aléatoire. Si un ensemble donné de miroirs doit

être essayé avant tout autre ensemble, une priorité peut être explicitement définie. Les miroirs avec le plus petit nombre sont essayés en premier. Les miroirs qui n'ont pas de pr
iorité explicite définie prennent par défaut le plus grand nombre possible et sont donc essayés en dernier. Le choix entre des miroirs avec la même priorité est à nouveau aléatoire.

Transports autorisés dans une liste de

miroirs

La disponibilité et le choix des transports dans une liste de miroirs sont limités par la manière dont le client APT accède à la liste de miroirs. Si un transport local comme file ou copy e

st utilisé, la liste de miroirs peut également inclure des sources locales, tandis qu'une liste de miroirs accessible via http ne le peut pas. De plus, une liste de miroirs ne peut pas con
tenir une liste de miroirs ou d'autres transports d'encapsulation (comme apt-transport-tor). Voir la documentation de ces transports pour savoir comment les utiliser avec la méthode mirror.

Notez que les versions d'apt antérieures à 1.6 ne prennent en charge aucun autre transport que

http.

Comme expliqué dans la définition du format, les versions d'apt antérieures à 1.6 ne prennent pas en charge ceci et échoueront à analyser la liste de miroirs. L'exemple de liste de miroirs est volontairement compliqué pour montr

er certains aspects de la sélection. La configuration suivante est supposée : Le premier miroir est un miroir local accessible via la méthode file, mais potentiellement incomplet. Le second miroir a une excellente connexion, ma
is est un miroir partiel en ce sens qu'il ne contient que des fichiers liés aux architectures amd64 et all. Les miroirs restants sont des miroirs moyens qui ne devraient être contactés que si les précédents n'ont pas fonctionné.

file:/srv/local/debian/mirror/ priority:1 type:index http://partial.example.org/mirror/ priority:2 arch:amd64 arch:all type:deb http://ftp.us.debian.org/debian/ type:deb http://ftp.de.debian.org/debian/ type:deb https://deb.debian.

org/debian/

Dans cette configuration avec cette liste de miroirs, le premier miroir sera utilisé pour télécharger tous les fichiers d'index en supposant que la liste de miroirs elle-même soit accessible via un transport local comme file. Si ce n'est pas le cas, si le miroir est autrement inaccessible ou s'il ne contient pas le fichier demandé, un autre miroir sera utilisé pour acquérir le fichier, choisi en fonction du type de fichier : Un fichier d'index sera servi par le dernier miroir de la liste, tandis qu'un paquet de l'architecture amd64 est servi par le second et ceux de par exemple l'architecture i386 par l'un des trois

derniers.
