NOM

apt-transport-https - Transport APT pour le téléchargement via le protocole HTTP Secure (HTTPS)

DESCRIPTION

Ce transport APT permet l'utilisation de dépôts accessibles via le protocole HTTP Secure (HTTPS), également appelé HTTP sur TLS. Il est disponible par défaut depuis apt 1.5 et était disponible avant cela dans le paquet apt-transport-https. Notez qu'un transport n'est jamais appelé directement par un utilisateur mais utilisé par les outils APT en fonction de la configuration de l'utilisateur.

HTTP est en soi un protocole de transport non chiffré (comparez avec apt-transport-http(1)), qui, comme indiqué par le S ajouté, est encapsulé dans une couche chiffrée connue sous le nom de Transport Layer Security (TLS) pour fournir un chiffrement de bout en bout. Un attaquant suffisamment capable peut toujours observer les partenaires de communication et une analyse plus approfondie de la communication chiffrée pourrait encore révéler des détails importants. Un aperçu des méthodes de transport alternatives disponibles est donné dans sources.list(5).

OPTIONS

Le protocole HTTPS est basé sur le protocole HTTP, donc toutes les options supportées par apt-transport-http(1) sont également disponibles via Acquire::https et utiliseront par défaut les mêmes valeurs que celles spécifiées pour Acquire::http. Ce manuel n'expliquera que les options uniques à https.

Crédentiels serveur

Par défaut, tous les certificats approuvés par le système (voir le paquet ca-certificates) sont utilisés pour la vérification du certificat serveur. Une autorité de certification (CA) alternative peut être configurée avec l'option Acquire::https::CAInfo et son option spécifique à l'hôte Acquire::https::CAInfo::hôte. L'option CAInfo spécifie un fichier composé de certificats CA (au format PEM) concaténés ensemble pour créer la chaîne que APT doit utiliser pour vérifier le chemin depuis votre certificat racine auto-signé. Si le serveur distant fournit la chaîne complète lors de l'échange, le fichier ne doit contenir que le certificat racine. Sinon, la chaîne complète est requise. Si vous avez besoin de supporter plusieurs autorités, la seule façon est de tout concaténer.

Une liste de révocation de certificats (CRL) personnalisée peut être configurée avec les options Acquire::https::CRLFile et Acquire::https::CRLFile::hôte. Comme avec l'option précédente, un fichier au format PEM doit être spécifié.

Désactivation de la sécurité

Lors de l'authentification du serveur, si la vérification du certificat échoue pour une raison quelconque (expiré, révoqué, homme du milieu, etc.), la connexion échoue. C'est évidemment ce que vous voulez dans tous les cas et ce que la valeur par défaut (true) de l'option Acquire::https::Verify-Peer et sa variante spécifique à l'hôte fournissent. Si vous savez exactement ce que vous faites, régler cette option sur « false » vous permet d'ignorer la vérification du certificat du pair et de faire réussir l'échange. Encore une fois, cette option est réservée au débogage ou aux tests, car elle supprime toute sécurité fournie par l'utilisation de HTTPS.

De même, l'option Acquire::https::Verify-Host et sa variante spécifique à l'hôte peuvent être utilisées pour désactiver une fonctionnalité de sécurité : le certificat fourni par le serveur inclut l'identité du serveur qui doit correspondre au nom DNS utilisé pour y accéder. Par défaut, comme demandé par la RFC 2818, le nom du miroir est vérifié par rapport à l'identité trouvée dans le certificat. Ce comportement par défaut est sûr et ne devrait pas être modifié, mais si vous savez que le serveur que vous utilisez a un nom DNS qui ne correspond pas à l'identité dans son certificat, vous pouvez régler l'option sur « false », ce qui empêchera la comparaison d'être effectuée.

Authentification du client

En plus de supporter l'authentification basée sur mot de passe (voir apt_auth.conf(5)), HTTPS supporte également l'authentification basée sur des certificats clients via Acquire::https::SSLCert et Acquire::https::SSLKey. Ceux-ci devraient être réglés respectivement sur le nom de fichier du certificat client X.509 et la clé privée associée (non chiffrée), tous deux au format PEM. En pratique, l'utilisation des variantes spécifiques à l'hôte des deux options est fortement recommandée.

EXEMPLES

Acquire::https {
	Proxy::example.org "DIRECT";
	Proxy "socks5h://apt:pass@127.0.0.1:9050";
	Proxy-Auto-Detect "/usr/local/bin/apt-https-proxy-auto-detect";
	No-Cache "true";
	Max-Age "3600";
	No-Store "true";
	Timeout "10";
	Dl-Limit "42";
	Pipeline-Depth "0";
	AllowRedirect "false";
	User-Agent "Mon APT-HTTPS";
	SendAccept "false";
	CAInfo "/chemin/vers/certs_ca.pem";
	CRLFile "/chemin/vers/toutes_les_crl.pem";
	Verify-Peer "true";
	Verify-Host::broken.example.org "false";
	SSLCert::example.org "/chemin/vers/cert_client.pem";
	SSLKey::example.org "/chemin/vers/cle_client.pem"
};
