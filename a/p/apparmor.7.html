NOM

AppArmor - amélioration du noyau pour confiner les programmes à un ensemble limité de ressources.

DESCRIPTION

AppArmor est une amélioration du noyau pour confiner les programmes à un ensemble limité de ressources. Le modèle de sécurité unique d'AppArmor consiste à lier les attributs de contrôle d'accès aux programmes plutôt qu'aux utilisateurs.

Le confinement AppArmor est assuré via des profils chargés dans le noyau via apparmor_parser(8), généralement via l'unité systemd apparmor.service, qui s'utilise comme suit :

# systemctl start apparmor
# systemctl reload apparmor

AppArmor peut fonctionner dans deux modes : enforcement (application) et complain (plainte ou apprentissage) :

  • enforcement - Les profils chargés en mode enforcement entraîneront l'application de la politique définie dans le profil ainsi que le signalement des tentatives de violation de politique à syslogd.
  • complain - Les profils chargés en mode "complain" n'appliqueront pas la politique. Au lieu de cela, ils signaleront les tentatives de violation de politique. Ce mode est pratique pour développer des profils. Pour gérer le mode complain pour des profils individuels, les utilitaires aa-complain(8) et aa-enforce(8) peuvent être utilisés. Ces utilitaires prennent un nom de programme comme argument.

Les profils sont traditionnellement stockés dans des fichiers dans /etc/apparmor.d/ sous des noms de fichiers suivant la convention de remplacement du / dans les chemins par . (sauf pour le / racine) afin que les profils soient plus faciles à gérer (par exemple, le profil /usr/sbin/nscd serait nommé usr.sbin.nscd).

Les profils sont appliqués à un processus au moment de l'exec(3) (comme vu à travers l'appel système execve(2)) : une fois qu'un profil est chargé pour un programme, ce programme sera confiné lors du prochain exec(3). Si un processus est déjà en cours d'exécution sous un profil, lorsque l'on remplace ce profil dans le noyau, le profil mis à jour est immédiatement appliqué à ce processus. D'autre part, un processus déjà en cours d'exécution sans confinement ne peut pas être confiné.

AppArmor prend en charge le système de fichiers securityfs du noyau Linux, et rend disponible la liste des profils actuellement chargés ; pour monter le système de fichiers :

# mount -tsecurityfs securityfs /sys/kernel/security
$ cat /sys/kernel/security/apparmor/profiles
/usr/bin/mutt
/usr/bin/gpg
   ...

Normalement, le script init montera securityfs s'il ne l'a pas déjà fait.

AppArmor restreint également les opérations privilégiées qu'un processus confiné peut exécuter, même si le processus s'exécute en tant que root. Un processus confiné ne peut pas appeler les appels système suivants :

create_module(2) delete_module(2) init_module(2) ioperm(2)
iopl(2) ptrace(2) reboot(2) setdomainname(2)
sethostname(2) swapoff(2) swapon(2) sysctl(2)

Mode Complain

Au lieu de refuser l'accès aux ressources pour lesquelles le profil n'a pas de règle, AppArmor peut "autoriser" l'accès et enregistrer un message pour l'opération qui le déclenche. C'est ce qu'on appelle le mode complain. Il est important de noter que les règles présentes dans le profil sont toujours appliquées, donc les règles d'autorisation continueront de supprimer ou de forcer les messages d'audit, et les règles de refus entraîneront toujours des refus et la suppression des messages de refus (voir Désactiver la mise en sourdine des audits de refus si cela pose problème).

Le mode complain peut être utilisé pour développer des profils de manière incrémentielle au fur et à mesure que l'on utilise une application. Les accès enregistrés peuvent être ajoutés au profil, puis l'application peut être davantage utilisée pour découvrir d'autres ajouts nécessaires. Comme AppArmor autorise les accès, l'application se comportera comme si AppArmor ne la confinait pas.

Attention le mode complain n'offre aucune sécurité, seulement de l'audit, tant qu'il est activé. Il ne doit pas être utilisé dans un environnement hostile, car les mauvais comportements pourraient être enregistrés et ajoutés au profil comme s'il s'agissait d'accès aux ressources que l'application devrait utiliser.

Note le mode complain peut être très verbeux avec des profils nouveaux ou vides, mais avec des profils développés, il peut ne rien enregistrer si le profil couvre bien le comportement de l'application. Voir Limitation du débit d'audit si le mode complain génère trop de messages de journal.

Pour mettre un profil et tous ses enfants ou profils chapeau qu'il pourrait contenir en mode complain, utilisez :

aa-complain /etc/apparmor.d/<l-application>

Pour définir manuellement un profil spécifique en mode complain, ajoutez le drapeau "complain", puis rechargez manuellement le profil :

profile foo flags=(complain) { ... }

Notez que le drapeau "complain" doit également être ajouté manuellement à tous les chapeaux ou profils enfants du profil, sinon ils continueront d'utiliser le mode précédent.

Pour activer le mode complain globalement, exécutez :

echo -n complain > /sys/module/apparmor/parameters/mode

ou pour le définir au démarrage, ajoutez :

apparmor.mode=complain

comme paramètre de démarrage du noyau.

Attention définir le mode complain globalement désactive toutes les protections de sécurité d'apparmor. Cela peut être utile lors du débogage ou du développement de profils, mais il est plus sûr de le définir sélectivement par profil.

ERREURS

Lorsqu'un processus confiné tente d'accéder à un fichier auquel il n'a pas la permission, le noyau signalera un message via l'audit, similaire à :

audit(1386511672.612:238): apparmor="DENIED" operation="exec" 
  parent=7589 profile="/tmp/sh" name="/bin/uname" pid=7605 
  comm="sh" requested_mask="x" denied_mask="x" fsuid=0 ouid=0
audit(1386511672.613:239): apparmor="DENIED" operation="open" 
  parent=7589 profile="/tmp/sh" name="/bin/uname" pid=7605 
  comm="sh" requested_mask="r" denied_mask="r" fsuid=0 ouid=0
audit(1386511772.804:246): apparmor="DENIED" operation="capable"
  parent=7246 profile="/tmp/sh" pid=7589 comm="sh" pid=7589 
  comm="sh" capability=2  capname="dac_override"

Les permissions demandées par le processus sont décrites dans operation= et denied_mask= (pour les fichiers - les capacités etc. utilisent un format de journal légèrement différent). Le nom et l'ID de processus du programme en cours d'exécution sont signalés, ainsi que le nom du profil incluant tout "chapeau" qui pourrait être actif, séparé par "//". ("Name" est entre guillemets, car le nom du processus est limité à 15 octets ; il est identique à celui rapporté via la comptabilité de processus Berkeley.)

Pour les processus confinés exécutés sous un profil qui a été chargé en mode complain, l'application n'aura pas lieu et les messages de journal signalés à l'audit seront de la forme :

audit(1386512577.017:275): apparmor="ALLOWED" operation="open"
  parent=8012 profile="/usr/bin/du" name="/etc/apparmor.d/tunables/"
  pid=8049 comm="du" requested_mask="r" denied_mask="r" fsuid=1000 ouid=0
audit(1386512577.017:276): apparmor="ALLOWED" operation="open"
  parent=8012 profile="/usr/bin/du" name="/etc/apparmor.d/tunables/"
  pid=8049 comm="du" requested_mask="r" denied_mask="r" fsuid=1000 ouid=0

Si le démon d'audit userland (auditd) n'est pas en cours d'exécution, le noyau enverra les événements d'audit à klogd ; klogd enverra les messages à syslog, qui enregistrera les messages avec la facilité KERN. Ainsi, les messages de REFUS et d'AUTORISATION peuvent aller soit dans /var/log/audit/audit.log, soit dans /var/log/messages, selon la configuration locale.

DÉBOGAGE

AppArmor fournit quelques facilités pour enregistrer plus d'informations, ce qui peut aider au débogage des profils.

Activer le mode debug

Lorsque le mode debug est activé, AppArmor enregistrera quelques messages supplémentaires dans dmesg (pas via le sous-système d'audit). Par exemple, les journaux indiqueront si le nettoyage de l'environnement a été appliqué.

Pour activer le mode debug, exécutez :

echo 1 > /sys/module/apparmor/parameters/debug

ou pour le définir au démarrage, ajoutez :

apparmor.debug=1

comme paramètre de démarrage du noyau.
