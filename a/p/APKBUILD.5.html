Par défaut, la fonction de séparation est la fin du nom du paquet après le dernier tiret. Ainsi, pour $pkgname-foo et libfoo la fonction de séparation est foo et libfoo respectivement. Un nom de fonction de séparation personnalisé peut être défini en utilisant foo:funcname. De manière similaire à la fonction package , la fonction de séparation doit déplacer les fichiers depuis $pkgdir (qui est le répertoire de travail courant par défaut) ou $srcdir vers $subpkgdir après avoir créé $subpkgdir.

Par défaut, arch détermine si un sous-paquet est considéré comme indépendant de l'architecture ou non. Cela peut être modifié en utilisant foo::noarch ou foo:funcname:all.

Lorsque plusieurs sous-paquets sont spécifiés, leurs fonctions de séparation sont exécutées dans l'ordre dans lequel elles apparaissent dans subpackages.

triggers

Spécifie un script de déclenchement utilisé par le paquet. Un script de déclenchement est un script shell qui est appelé chaque fois que des fichiers ou des répertoires surveillés sont modifiés. Vous pouvez spécifier les chemins à surveiller en utilisant la variable triggers comme suit : 
$pkgname.trigger=/usr/share/man:/usr/local/share/man

Cela exécutera le script de déclenchement du paquet chaque fois que des fichiers dans /usr/share/man ou /usr/local/share/man sont créés, modifiés ou supprimés.

options

La options variable vous permet de définir des paramètres pour le paquet au moment de la compilation. Il existe un certain nombre d'options valides que vous pouvez définir, et vous pouvez définir plusieurs options en écrivant un espace entre chacune d'elles. Des noms d'options personnalisés peuvent être utilisés lorsqu'ils contiennent exactement un :. Des options peuvent être définies pour un (sous)paquet spécifique en utilisant subpkgname::option (ou subpkgname:option pour les options personnalisées).

!archcheck

Spécifie que le paquet contient des binaires qui ne peuvent pas s'exécuter sur l'architecture cible. C'est principalement utilisé pour les paquets contenant du firmware, et ne devrait généralement jamais être nécessaire.

bigdocs

Spécifie que ce paquet a intentionnellement un sous-paquet -doc volumineux. Cela supprime ainsi un avertissement qui serait émis si le sous-paquet -doc dépasse un certain seuil de taille de paquet (actuellement 2 Mio).

charset.alias

Spécifie que le paquet fournit un fichier /usr/lib/charset.alias et qu'il devrait être installé sur le système de l'utilisateur. Ce n'est presque jamais le cas. N'utilisez pas cette option.

!check

Spécifie que le paquet n'exécutera pas de suite de tests. La raison pour laquelle la phase de vérification est désactivée devrait être notée dans un commentaire.

checkroot

Spécifie que la suite de tests de ce paquet sera exécutée dans fakeroot(8). C'est nécessaire pour certaines suites de tests qui échouent lorsqu'elles sont exécutées en tant que non-root.

!dbg

Spécifie que le paquet ne devrait pas être compilé avec un paquet d'informations de débogage. C'est la valeur par défaut sauf si DEFAULT_DBG est défini dans l'environnement ou abuild.conf(5). C'est typiquement utilisé sur des paquets qui ne génèrent pas d'informations de débogage (comme les paquets Python purs) ou des paquets qui ne supportent pas les paquets d'informations de débogage.

!fhs

Spécifie que le paquet viole la FHS et s'installe dans un emplacement tel que /usr/local, /opt, ou /srv.

ldpath-recursive

Spécifie que abuild(1) devrait utiliser l'argument --recursive de scanelf(1) lorsqu'il tente de trouver les dépendances de bibliothèques partagées (.so) du paquet.

lib64

Spécifie que le paquet installe des fichiers sous /lib64 ou /usr/lib64 et que le test pour ces répertoires devrait être ignoré. C'est déconseillé et ne devrait être utilisé que pour les paquets fournissant la compatibilité pour la GNU libc.

libtool

Spécifie que le paquet nécessite ses fichiers libtool (.la). Ils ne seront pas automatiquement supprimés par abuild(1).

net

Spécifie que le système de construction du paquet nécessite l'accès à un réseau. C'est déconseillé et un problème devrait être signalé auprès des auteurs du paquet.

!strip

Spécifie que strip(1) ne devrait pas être exécuté sur aucun des binaires du paquet. C'est automatiquement impliqué si le sous-paquet -dbg est activé, ou si vous utilisez DEFAULT_DBG.

suid

Spécifie que les binaires du paquet peuvent être installés avec set-uid. C'est un risque de sécurité et il est fortement recommandé d'utiliser des capacités ou la séparation des processus au lieu de set-uid lorsque c'est disponible.

setcap

Spécifie que les binaires du paquet peuvent être installés avec des capacités setcap(8) supplémentaires. Si cette option est activée, il est fortement recommandé de rendre ces binaires exécutables uniquement par root et les utilisateurs d'un groupe spécifique, pas par les autres.

textrels

Spécifie que les binaires du paquet sont connus pour contenir des relocalisations contre des segments de texte. Par défaut, abuild(1) refusera de créer un tel paquet car c'est un problème de sécurité.

toolchain

Spécifie que le paquet fait partie de l'ensemble de base de la chaîne d'outils et peut dépendre de paquets comme g++.

!tracedeps

Spécifie que abuild(1) ne devrait pas remplir automatiquement depends avec les dépendances de bibliothèques partagées (.so) ou de cibles de liens symboliques.

Variables automatiques

Les variables suivantes sont définies pour vous par abuild(1), mais peuvent être remplacées si nécessaire.

builddir

Spécifie le répertoire où le code source du paquet sera compilé. La valeur par défaut est $srcdir/$pkgname-$pkgver ce qui est approprié pour la plupart des distributions de sources. Si l'archive tarball source ne crée pas un répertoire $pkgname-$pkgver lorsqu'elle est décompressée, vous devez remplacer builddir.

pkgdir

Spécifie le répertoire où les fichiers compilés seront installés. Typiquement, vous appellerez `make DESTDIR="$pkgdir" install` ou similaire pour installer les fichiers. La valeur par défaut est $startdir/pkg et vous ne devriez pas modifier cette variable.

srcdir

Spécifie le répertoire où les fichiers spécifiés dans source sont téléchargés et décompressés. La valeur par défaut est $startdir/src et vous ne devriez pas avoir besoin de modifier cela.

startdir

Spécifie le répertoire où le fichier APKBUILD se trouve. Cela ne devrait généralement pas être utilisé.

subpkgdir

Spécifie le répertoire où les fichiers du sous-paquet devraient être placés. Cette variable n'est définie qu'à l'intérieur des fonctions de sous-paquet.

Fonctions

Les fonctions spécifiées ici peuvent être présentes dans n'importe quel fichier APKBUILD , mais à l'exception de package, ne sont pas strictement requises.

fetch

Cette fonction est appelée pour télécharger les fichiers distants dans source.

unpack

Cette fonction décompresse toutes les archives dans source vers srcdir.

prepare

Prépare les sources dans srcdir pour la compilation. La fonction par défaut prepare s'assure que les répertoires de compilation sont configurés correctement et applique tous les fichiers *.patch spécifiés dans source. Vous devez appeler default_prepare si vous écrivez une fonction prepare personnalisée.

build

Compile les sources dans builddir. Vous devez implémenter cette fonction vous-même. Si aucune compilation n'est requise, vous pouvez l'omettre.

check

Exécute la suite de tests du paquet. Cette fonction doit être implémentée sauf si !check a été spécifié dans options.

package

Installe le paquet dans pkgdir. Notez que pkgdir n'est pas créé pour vous ; si ce paquet n'installe aucun fichier (par exemple, un méta-paquet), vous devez utiliser `mkdir -p "$pkgdir"` pour sauter la phase de paquetisation.

Scripts d'installation

Un script d'installation est exécuté lorsqu'une action est effectuée sur un paquet par apk(8). Un script d'installation doit être écrit en shell et doit avoir une déclaration d'interpréteur #!/bin/sh comme première ligne. La variable install doit contenir les scripts d'installation nécessaires pour le paquet.

Le script d'installation sera exécuté à l'intérieur du système de fichiers racine où le paquet est en cours d'installation. Un argument unique sera passé aux scripts de rappel, qui est la version du paquet actuellement installé (ou désinstallé). Les scripts pre-upgrade et post-upgrade auront un deuxième argument supplémentaire, qui spécifie la version du paquet avant le processus de mise à niveau.

Les différentes actions pour lesquelles des scripts d'installation peuvent être spécifiés sont les suivantes :

$pkgname.pre-install

Exécuté avant que le paquet ne soit installé. Si ce script se termine avec une erreur (code de sortie non nul), apk(8) interrompra l'installation et le paquet ne sera pas installé. Ce script d'installation est typiquement utilisé pour créer les utilisateurs ou groupes nécessaires comme décrit dans pkggroups et pkgusers.

$pkgname.

post-install
Exécuté après l'installation du paquet. Si ce script se termine avec une erreur (code de sortie non nul), apk(8) marquera le paquet comme cassé. La commande `apk fix` essaiera de relancer le script post-install si cela se
produit.

$pkgname.

pre-upgrade
Exécuté avant la mise à niveau du paquet. Si ce script se termine avec une erreur (code de sortie non nul), apk(8) marquera le paquet comme
cassé.

$pkgname.

post-upgrade
Exécuté après la mise à niveau du paquet. Si ce script se termine avec une erreur (code de sortie non nul), apk(8) marquera le paquet comme cassé. La commande `apk fix` essaiera de relancer le script post-upgrade si cela se
produit.

$pkgname.

pre-deinstall
Exécuté avant la suppression du paquet du système. Si ce script se termine avec une erreur (code de sortie non nul), apk(8) ne supprimera pas le paquet du
système.

$pkgname.

qui est généralement bash(1).
