apt-secure - Prise en ch

arge de l'authentificati
on des archives pour APT

DESCRIPTIO

N

À partir de la version 0.6, APT contient du code qui effectue la vérification de la signature du fichier Release pour tous les dépôts. Cela garantit que des données telles que les paquets de l'archive ne peuvent pas être modifiées par des personnes qui n'ont pas accès à la clé de signature du fichier Release. À partir de la version 1.1 APT exige que les dépôts fournissent des informations d'authentification récentes pour une utilisation sans entrave du dépôt. Depuis la version 1.5, les changements dans les informations contenues dans le fichier Release concernant le dépôt doivent être confirmés avant qu'APT continue d'appliquer les mises à jour de ce

dépôt.

Remarque : Tous les interfaces de gestion de paquets basés sur APT comme apt-get(8), aptitude(8) et synaptic(8) prennent en charge cette fonctionnalité d'authentificatio

n, ce manuel utilise donc APT pour
les désigner tous, par simplicité.

CONFIGURATION

UTILISATEUR

Les clés doivent généralement être incluses dans leur fichier .sources correspondant en intégrant la clé blindée ASCII dans l'option Signed-By. Pour ce faire, remplacez la ligne vide par un point, puis indentez toutes les lignes de deux espaces. Voir sources.list(5) pour plus

d'informations.

Alternativement, les clés peuvent être placées dans /etc/apt/keyrings pour les clés locales, ou /usr/share/keyrings pour les clés gérées par des paquets, puis référencées par l'option Signed-By: /etc/apt/keyrings/example-archive-keyring.asc dans un fichier .sources ou en utilisant deb [signed-by=/etc/apt/keyrings/example-archive-keyring.asc] ... dans le format .list hérité. Cela peut être utile pour les versions d'APT antérieures à 2.4, qui ne prennent pas en charge les clés intégrées. Les clés blindées ASCII doivent utiliser l'extension .asc, et les clés non blindées l'extension .

gpg.

Pour générer des clés utilisables dans APT avec GnuPG, vous devrez utiliser la commande gpg --export-options export-minimal [--armor] --export. Les solutions antérieures impliquant --keyring fichier --import ne fonctionnent plus avec les versions récentes de GnuPG car elles utilisent un nouveau format interne ("GPG keybox database")

.

Notez qu'une installation par défaut contient déjà toutes les clés pour acquérir des paquets en toute sécurité depuis les dépôts par défaut, la gestion des clés n'est donc nécessaire que si des dépôts tiers sont ajoutés. Le paquet extrepo peut être utilisé pour gérer

facilement plusieur
s dépôts externes.

DÉPÔTS NON

SIGNÉS

Si une archive a un fichier Release non signé ou pas de fichier Release du tout, les versions actuelles d'APT refuseront par défaut de télécharger des données de celles-ci dans les opérations de mise à jour et même si le téléchargement est forcé, les interfaces comme apt-get(8) exigeront une confirmation explicite si une demande d'installation inclut un paquet d'une telle archive non

authentifiée.

Vous pouvez forcer tous les clients APT à émettre uniquement des avertissements en définissant l'option de configuration Acquire::AllowInsecureRepositories à true. Des dépôts individuels peuvent également être autorisés à être non sécurisés via l'option sources.list(5) allow-insecure=yes. Notez que les dépôts non sécurisés sont fortement déconseillés et que toutes les options pour forcer apt à continuer à les prendre en charge seront éventuellement supprimées. Les utilisateurs ont également l'option Trusted disponible pour désactiver même les avertissements, mais assurez-vous de comprendre les implications telles que détaillées dans sources.lis

t(5).

Un dépôt qui était précédemment authentifié mais qui perdrait cet état dans une opération de mise à jour lève une erreur dans tous les clients APT indépendamment de l'option pour autoriser ou interdire l'utilisation des dépôts non sécurisés. L'erreur peut être contournée en définissant également Acquire::AllowDowngradeToInsecureRepositories à true ou pour les dépôts individuels avec l'option sources.list(5) allow-downgrade-to-insecure=ye

s
.

DÉPÔTS

SIGNÉS

La chaîne de confiance d'une archive APT jusqu'à l'utilisateur final est composée de plusieurs étapes. apt-secure est la dernière étape de cette chaîne ; faire confiance à une archive ne signifie pas que vous lui faites confiance pour que ses paquets ne contiennent pas de code malveillant, mais signifie que vous faites confiance au mainteneur de l'archive. C'est la responsabilité du mainteneur de l'archive de s'assurer que l'intégrité de l'archive est

préservée.

apt-secure ne vérifie pas les signatures au niveau du paquet. Si vous avez besoin d'outils pour cela, vous devriez consulter debsig-verify et debsign (fournis respectivement dans les paquets debsig-verify et devscripts)

.

La chaîne de confiance dans Debian commence (par exemple) lorsqu'un mainteneur téléverse un nouveau paquet ou une nouvelle version d'un paquet vers l'archive Debian. Pour que cela devienne effectif, ce téléversement doit être signé par une clé contenue dans l'un des trousseaux de clés des mainteneurs de paquets Debian (disponibles dans le paquet debian-keyring). Les clés des mainteneurs sont signées par d'autres mainteneurs suivant des procédures préétablies pour garantir l'identité du détenteur de la clé. Des procédures similaires existent dans toutes les distributions basées sur

Debian.

Une fois le paquet téléversé vérifié et inclus dans l'archive, la signature du mainteneur est supprimée, et les sommes de contrôle du paquet sont calculées et placées dans le fichier Packages. Les sommes de contrôle de tous les fichiers Packages sont ensuite calculées et placées dans le fichier Release. Le fichier Release est ensuite signé par la clé de l'archive pour cette version de Debian, et distribué avec les paquets et les fichiers Packages sur les miroirs Debian. Les clés se trouvent dans le trousseau de clés de l'archive Debian disponible dans le paquet debian-archive-keyring

.

Les utilisateurs finaux peuvent vérifier la signature du fichier Release, en extraire une somme de contrôle d'un paquet et la comparer avec la somme de contrôle du paquet qu'ils ont téléchargé manuellement - ou s'en remettre à APT pour le faire automatiquement

.

Notez que cela est distinct de la vérification des signatures au cas par cas. Cela est conçu pour empêcher deux attaques possibles

:
•Attaques réseau de type "homme du milieu". Sans vérification de signature, des agents malveillants peuvent s'introduire dans le processus de téléchargement des paquets et fournir des logiciels malveillants soit en contrôlant un élément réseau (routeur, commutateur, etc.), soit en redirigeant le trafic vers un serveur pirate (via des attaques de falsification ARP ou DNS)
.
•Compromission du réseau de miroirs. Sans vérification de signature, un agent malveillant peut compromettre un hôte miroir et modifier les fichiers qu'il contient pour propager des logiciels malveillants à tous les utilisateurs téléchargeant des paquets depuis cet
hôte.

Cependant, cela ne se défend pas contre la compromission du serveur maître lui-même (qu

i signe les paquets) ni contre la compromission de la clé utilisée pour signer les fic
hiers Release. Dans tous les cas, ce mécanisme peut compléter une signature par paquet.

CHANGEMENTS

D'INFORMATIONS

Un fichier Release contient en plus des sommes de contrôle des fichiers du dépôt, des informations générales sur le dépôt comme l'origine, le nom de code ou le numéro de version de la

version.

Ces informations sont affichées à différents endroits, le propriétaire d'un dépôt devrait donc toujours s'assurer de leur exactitude. De plus, la configuration utilisateur comme apt_preferences(5) peut dépendre de ces informations et les utiliser. Depuis la version 1.5, l'utilisateur doit donc confirmer explicitement les changements pour

signaler qu'il est suffisamment préparé, par exemple pour la nouvelle version ma
jeure de la distribution livrée dans le dépôt (comme indiqué par le nom de code).

CONFIGURATION DU

DÉPÔT

Si vous souhaitez fournir des signatures d'archive dans une archive sous votre maintenance, vous devez

:
•Créer un fichier Release de premier niveau, s'il n'existe pas déjà. Vous pouvez le faire en exécutant apt-ftparchive release (fourni dans apt-utils)
.
•Le signer. Vous pouvez le faire en exécutant gpg --clearsign -o InRelease Release et gpg -abs -o Release.g
pg Release.
•Publier l'empreinte de la clé, afin que vos utilisateurs sachent quelle clé ils doivent importer pour authentifier les fichiers de l'archive. Il est préférable de fournir votre clé dans son propre trousseau paquet comme Debian le fait avec debian-archive-keyring pour pouvoir distribuer automatiquement plus tard les mises à jour et les transitions de
clés.
•Fournir des instructions sur la façon d'ajouter votre archive et votre clé. Si vos utilisateurs ne peuvent pas obtenir votre clé de manière sécurisée, la chaîne de confiance décrite ci-dessus est rompue. La manière dont vous pouvez aider les utilisateurs à ajouter votre clé dépend de votre archive et de votre public cible, allant du fait d'avoir votre paquet keyring inclus dans une autre archive que les utilisateurs ont déjà configurée (comme les dépôts par défaut de leur distribution) à l'utilisation de la toile de
confiance.

Chaque fois que le contenu de l'archive change (de nouveaux

paquets sont ajoutés ou supprimés), le mainteneur de l'archiv
e doit suivre les deux premières étapes décrites ci-dessus.
