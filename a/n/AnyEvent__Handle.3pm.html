Ceci est un module d'aide pour faciliter les E/S basées sur des événements sur des des handles de fichier basés sur des flux (sockets, tuyaux et autres objets de flux). Plus précisément, il ne fonctionne pas comme prévu sur les fichiers, les sockets basées sur des paquets ou des choses

Au minimum, vous devriez spécifier « fh » ou « connect », et le rappel « on_error »

AnyEvent::Handle gère deux files d'attente par descripteur, une pour l'écriture et une pour la

La file d'attente de lecture est plus complexe que la file d'attente d'écriture. Elle peut être utilisée de deux façons, la façon « simple », utilisant uniquement "on_read" et la façon « complexe », utilisant une file

d'attente.

Dans le cas simple, vous installez simplement un rappel "on_read" et chaque fois que de nouvelles données arrivent, il sera appelé. Vous pouvez alors retirer certaines données (s'il y en a assez) du tampon de lecture ("$handle->rbuf"). Ou vous pouvez laisser les données là si vous voulez accumuler plus (par ex. quand seul un message partiel a été reçu jusqu'à présent), ou changer la file d'attente de lecture avec par ex. "push_read"

.

Dans le cas plus complexe, vous voulez mettre en file d'attente plusieurs rappels. Dans ce cas, AnyEvent::Handle appellera le premier rappel en file d'attente chaque fois que de nouvelles données arrivent (aussi la première fois où il est mis en file d'attente) et le retirera lorsqu'il a fait son travail (voir "push_read", ci-dessous)

.

De cette façon, vous pouvez, par exemple, pousser trois lectures de lignes, suivies de la lecture d'un bloc de données, et AnyEvent::Handle les exécutera dans

l'ordre.

XML.

$handle->on_read (sub {
   # certaines données sont là, maintenant mettre en file d'attente la lecture de l'en-tête de longueur (4 octets)
   shift->unshift_read (chunk => 4, sub {
      # l'en-tête est arrivé, décoder
      my $len = unpack "N", $_[1];
      # maintenant lire la charge utile

         my $xml = $_[1];
         # traiter le xml
      });
   });
})
;

Pourquoi mon rappel "on_eof" n'est-il jamais appelé

Probablement parce que votre rappel "on_error" est appelé à la place : lorsque vous avez des requêtes en attente dans votre file de lecture, une EOF est considérée comme une erreur car vous attendiez clairement des données.

Pour éviter cela, assurez-vous d'avoir une file de lecture vide lorsque votre gestionnaire est censé être « inactif » (c'est-à-dire que les fermetures de connexion sont OK). Vous pouvez définir un gestionnaire "on_read" qui pousse simplement les premières requêtes de lecture dans la

Comment puis-je traiter des requêtes dans une boucle
?
La plupart des protocoles se composent d'une phase d'initialisation (l'authentification par exemple) suivie d'une phase de traitement des requêtes, où le serveur attend les requêtes et les traite, dans une boucle.

Il existe deux variantes importantes : la première (traditionnelle, meilleure) variante traite les requêtes jusqu'à ce que le serveur reçoive une commande QUIT, ce qui le fait d'abord fermer la connexion (hautement souhaitable pour un serveur TCP chargé). Le fait qu'un client abandonne la connexion est une erreur, ce qui signifie que cette variante peut détecter une fermeture de connexion

inattendue.

Pour gérer ce cas, assurez-vous toujours d'avoir une file de lecture non vide, en poussant le gestionnaire « début de requête de lecture » sur

celle-ci : 
# nous supposons qu'une requête commence par une seule ligne
my @start_request; @start_request = (line => sub {
   my ($hdl, $line) = @_;
   ... traiter la requête
   # pousser la lecture de la requête suivante, éventuellement depuis un rappel imbriqué
   $hdl->push_read (@start_request);
});
# authentification terminée, maintenant passer en boucle de traitement des requêtes
# maintenant pousser le premier @start_request
$hdl->push_read (@start_request)
;

En ayant toujours une "push_read" en attente, le gestionnaire attend toujours des données et lève l' erreur "EPIPE" lorsque la connexion est abandonnée de manière

inattendue.

La deuxième variante est un protocole où le client peut abandonner la connexion à tout moment. Pour TCP, cela signifie que la machine serveur peut manquer de sockets plus facilement, et en général, cela signifie que vous ne pouvez pas distinguer un échec de protocole/arrêt brutal du client d'une fermeture de connexion normale. Néanmoins, ce type de protocoles est courant (et parfois même la meilleure solution au

problème).

Avoir une requête de lecture en attente en permanence est possible si vous ignorez les erreurs "EPIPE", mais cela n'aide pas lorsque le client abandonne la connexion pendant une requête, ce qui serait toujours une

erreur.

Une meilleure solution est de pousser la lecture de la requête initiale dans un rappel "on_read". Cela évite une erreur, car lorsque le serveur n'attend pas de données (c'est-à-dire qu'il attend passivement la prochaine requête), une EOF ne lèvera pas d'erreur, mais entraînera simplement un rappel "on_eof". C'est aussi un peu plus lent et plus

simple : 
# authentification terminée, maintenant passer en boucle de traitement des requêtes
$hdl->on_read (sub {
   my ($hdl) = @_;
   # appelé chaque fois que nous recevons des données mais que la file de lecture est vide
   # simplement commencer à lire la requête
   $hdl->push_read (line => sub {
      my ($hdl, $line) = @_;
      ... traiter la requête
      # ne rien faire de spécial lorsque la requête a été traitée, juste
      # laisser la file de requêtes se vider.
});
});
J'obtiens des invocations de rappels différentes en mode TLS/Pourquoi ne puis-je pas mettre la lecture en

Contrairement, par exemple, à TCP, les connexions TLS ne se composent pas de deux canaux de communication indépendants, un pour chaque direction. Ou, autrement dit, les directions de lecture et d'écriture ne sont pas indépendantes l'une de l'autre : vous ne pouvez pas écrire de données si vous n'êtes pas également prêt à lire, et vice versa.

TLS.

Comment lire des données jusqu'à ce que l'autre côté ferme la connexion
?
Si vous voulez simplement lire vos données dans un scalaire perl, la façon la plus simple d'y parvenir est de définir un rappel "on_read" qui ne fait rien, de supprimer le rappel "on_eof" et dans le rappel "on_error", les données se trouveront dans "$_[0]{rbuf}" :

reçues.
