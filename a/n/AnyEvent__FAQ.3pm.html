Mon programme se termine avant de faire quoi que ce soit, que se passe-t-il

?

Les programmeurs nouveaux dans la programmation événementielle oublient souvent qu'ils peuvent en fait faire d'autres choses en « attendant » qu'un événement se produisent et oublient donc d'attendre réellement lorsqu'ils n'ont, en fait, rien d'autre à

faire.

Voici un exemple

: 
use AnyEvent;
my $timer = AnyEvent->timer (after => 5, cb => sub { say "hi" })
;

On pourrait s'attendre à ce que le programme imprime « hi » après 5 secondes et se termine probablement ensuite. Cependant, si vous exécutez cela, votre programme se terminera presque instantanément : la création du minuteur n'attend pas son échéance, à la place, la méthode « timer » retourne immédiatement et perl exécute le reste du programme. Mais il ne reste rien à exécuter, donc perl se

termine.

Pour forcer AnyEvent à attendre quelque chose, utilisez une condvar

: 
use AnyEvent;
my $quit_program = AnyEvent->condvar;
my $timer = AnyEvent->timer (after => 5, cb => sub { $quit_program->send });
$quit_program->
recv;

Ici, le programme ne se termine pas immédiatement, car il attend d'abord la condition « quit_program »

.

Dans la plupart des cas, votre programme principal devrait appeler directement la fonction « loop » de la bibliothèque d'événements

: 
use EV;
use
AnyEvent; .
.. EV::loop;

Pourquoi mon rappel « tcp_connect » n'est-il jamais appelé

?

Délicat : « tcp_connect » (et quelques autres fonctions dans AnyEvent::Socket) est extrêmement sensible au contexte de

l'appelant.

En contexte void, il fera simplement son travail et appellera éventuellement le rappel. Dans tout autre contexte, cependant, il retournera un objet « garde » spécial - lorsqu'il est détruit (par exemple lorsque vous ne le stockez pas mais le jetez), tcp_connect n'essaiera plus de se connecter ou d'appeler des

rappels.

Cela arrive souvent lorsque l'appel « tcp_connect » est à la fin d'une fonction

: 
sub do_connect {
   tcp_connect "www.example.com", 80, sub {
      ... code long
   };
}

C'est alors l'appelant qui décide s'il y a un contexte void ou non. On peut éviter ces cas en retournant explicitement rien

: 
sub do_connect {
   tcp_connect "www.
example.com", 80, sub { ... cod
e long }; () # retourner rien }

Pourquoi certains backends utilisent-ils beaucoup de CPU dans « AE::cv->recv »

?

Beaucoup de gens essaient ce simple programme, ou son équivalent

: 
use AnyEvent;
AnyEvent->condvar->
recv;

Ils sont alors choqués de voir que cela tourne essentiellement à vide avec le backend Perl, mais utilise 100% du CPU avec le backend EV, qui est censé être tellement

efficace.

La clé pour comprendre cela est de comprendre que le programme ci-dessus est en fait buggé : Rien n'appelle « ->send » sur la condvar, jamais. Pire, il n'y a aucun observateur d'événements. Fondamentalement, cela crée un interblocage : il n'y a aucun moyen de faire progresser les choses, ce programme ne fait rien d'utile, et cela ne changera pas dans le futur : c'est déjà un

ex-perroquet.

Certains backends réagissent à cela en se figeant, d'autres en tournant à vide, et d'autres font une boucle à 100% du

CPU.

Comme ce programme n'est pas utile (et se comporte comme documenté avec tous les backends, AnyEvent ne faisant aucune garantie sur le temps CPU), cela ne devrait pas être un gros problème : dès que votre programme implémente réellement quelque chose, l'utilisa

tion du CPU s
era normale.

Comment puis-je combiner des applications Win32::GUI avec AnyEvent

?

Eh bien, pas dans le même thread OS, c'est certain :) Ce que vous pouvez faire est de créer un autre ithread (ou fork) et d'exécuter AnyEvent dans ce thread, ou mieux encore, d'exécuter tout votre code GUI dans un deuxième

ithread.

Par exemple, vous pourriez charger Win32::GUI et AnyEvent::Util, puis créer un socketpair portable pour la communication GUI->

AnyEvent.

Puis fork/créer un nouvel ithread, et là-dedans, créer une fenêtre et envoyer le « $WINDOW->{-Handle} » à l'ithread AnyEvent pour qu'il puisse «

PostMessage ».

La communication de la GUI vers AnyEvent pourrait fonctionner en poussant des données dans une Thread::Queue et en écrivant un octet dans le socket. L'observateur AnyEvent de l'autre côté regardera alors la file

d'attente.

La communication d'AnyEvent vers la GUI peut aussi utiliser une Thread::Queue, mais pour réveiller le thread GUI, il utiliserait plutôt « Win32::GUI::PostMessage $WINDOW, 1030, 0, "" », et le thread GUI écouterait ces messages en utilisant « $WINDOW->Hook (1030 (), sub { ... })

»
.

Mon rappel meurt et..

.

Il ne doit pas le faire - une partie du contrat entre AnyEvent et le code utilisateur est que les rappels ne lèvent pas d'exceptions (et ne font pas des choses encore plus mauvaises, comme utiliser « last » en dehors d'une boucle :). Si votre rappel peut parfois mourir, vous devez utiliser « eval »

.

Si vous voulez retrouver un tel cas et que vous pouvez le reproduire, vous pouvez activer l'enveloppement (en appelant « AnyEvent::Debug::wrap » ou en définissant « PERL_ANYEVENT_DEBUG_WRAP=1 » avant de démarrer votre programme). Cela enveloppera chaque rapp

el dans un eval et rapportera toute exception av
ec une trace complète et des informations sur q
uel observateur est mort, où il a été créé, etc.
