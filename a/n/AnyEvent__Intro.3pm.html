Introduction à

AnyEvent

Ceci est un tutoriel qui vous présentera les fonctionnalités de

AnyEvent.

La première partie introduit le module principal AnyEvent (après vous avoir noyé un peu dans l'évangélisation), qui pourrait déjà fournir tout ce dont vous avez besoin : si vous n'êtes intéressé que par les capacités de gestion des événements d'AnyEvent, n'allez pas plus

loin.

La seconde partie se concentre sur la programmation réseau à l'aide de sockets

, pour laquelle AnyEvent offre beaucoup de support que vous pouvez utiliser, et
beaucoup de solutions de contournement autour des bizarreries de portabilité.

Qu'est-ce qu'AnyEvent

?

Si vous ne vous souciez pas des pourquoi et que vous voulez voir du code, sautez cette section

!

AnyEvent est avant tout un cadre (framework) pour faire de la programmation événementielle. Typiquement, de tels cadres sont tout ou rien : si vous utilisez un tel cadre, vous ne pouvez pas (facilement, ou même pas du tout) en utiliser un autre dans le même

programme.

AnyEvent est différent - c'est une fine couche d'abstraction au dessus d'autres boucles d'événements, tout comme DBI est une abstraction de nombreuses API de bases de données différentes. Son but principal est de déplacer le choix du cadre sous-jacent (la boucle d'événements) de l'auteur du module vers l'auteur du programme qui utilise le

module.

Cela signifie que vous pouvez écrire du code qui utilise des événements pour contrôler ce qu'il fait, sans forcer le reste du code du même programme à utiliser le même cadre sous-jacent que vous - c'est-à-dire que vous pouvez créer un module Perl basé sur les événements en utilisant AnyEvent, et les utilisateurs de ce module peuvent toujours choisir entre utiliser Gtk2, Tk, Event (ou s'exécuter dans Irssi ou rxvt-unicode) ou toute autre boucle d'événements supportée. AnyEvent fournit même sa propre implémentation de boucle d'événements en perl pur, donc votre code fonctionne quelles que soient les autres modules qui sont ou ne sont pas installés. Ce dernier point est important, car AnyEvent n'a aucune dépendance dure vers d'autres modules, ce qui le rend facile à installer, par exemple quand vous manquez d'un compilateur C. Quel que soit l'environnement, AnyEvent s'en

arrangera.

Une limitation typique des modules Perl existants tels que Net::IRC est qu'ils viennent avec leur propre boucle d'événements : dans Net::IRC, un programme qui l'utilise doit démarrer la boucle d'événements de Net::IRC. Cela signifie que l'on ne peut pas intégrer ce module dans une interface graphique Gtk2 par exemple, car ce module, lui aussi, force l'utilisation de sa propre boucle d'événements (à savoir Glib)

.

Un autre exemple est LWP : il ne fournit aucune interface événementielle du tout. C'est une bibliothèque cliente HTTP (et FTP etc.) purement bloquante, ce qui signifie généralement que vous devez soit lancer un autre processus, soit faire un fork pour une requête HTTP, soit utiliser des threads (par exemple Coro::LWP), si vous voulez faire autre chose pendant que vous attendez la fin de la

requête.

La motivation derrière ces conceptions est souvent qu'un module ne veut pas dépendre d'un module XS compliqué (Net::IRC), ou qu'il ne veut pas forcer l'utilisateur à utiliser une boucle d'événements spécifique (LWP), de peur de limiter sévèrement l'utilité du module : si votre module requiert Glib, il ne s'exécutera pas dans un programme

Tk.

AnyEvent résout ce dilemme, en ne forçant pas les auteurs de modules à l'une ou l'autre des options

:
- écrire leur propre boucle d'événements (car il garantit la disponibilité d'une boucle d'événements partout - même sur windows sans modules supplémentaires installés)
.
- choisir une boucle d'événements spécifique (car AnyEvent fonctionne avec la plupart des boucles d'événements disponibles pour
Perl).

Si l'auteur du module utilise AnyEvent pour tous ses besoins en événements (événements IO, minuteries, signaux, ...), alors tous les autres modules peuvent simplement utiliser son module et n'ont pas à choisir une boucle d'événements ou à s'adapter à sa boucle d'événements. Le choix de la boucle d'événements est finalement fait par l'auteur du programme qui utilise tous les modules et écrit le programme principal. Et même là, il n'a pas à choisir, il peut simplement laisser AnyEvent choisir la boucle d'événements la plus efficace disponible sur le

système.

ale du module AnyEvent.

Introduction à la Programmation Basée sur les

Événements

Alors, qu'est-ce que la programmation utilisant des événements ? Cela signifie tout simplement qu'au lieu que votre code attende activement quelque chose, comme l'utilisateur qui entre quelque chose sur STDIN

: 
$| = 1; print "enter your name> ";
my $name = <STDIN>
;

Vous dites plutôt à votre cadre d'événements de vous notifier dans le cas où des données sont disponibles sur STDIN, en utilisant un mécanisme de rappel (callback)

: 
use AnyEvent;
$| = 1; print "enter your name> ";
my $name;
my $wait_for_input = AnyEvent->io (
   fh   => \*STDIN, # which file handle to check
   poll => "r",     # which event to wait for ("r"ead data)
   cb   => sub {    # what callback to execute
      $name = <STDIN>; # read it
   }
);
# do something else
here

Cela a l'air plus compliqué, et c'est sûrement le cas, mais l'avantage d'utiliser des événements est que votre programme peut faire autre chose au lieu d'attendre la saisie (note de côté : combiner AnyEvent avec un paquet de threads tel que Coro peut recouvrer beaucoup de la simplicité, obtenant ainsi efficacement le meilleur des deux mondes)

.

L'attente telle que faite dans le premier exemple est aussi appelée "bloquer" le processus car vous "bloquez"/empêchez votre processus d'exécuter quoi que ce soit d'autre pendant ce

temps.

Le second exemple évite le blocage en n'enregistrant qu'un intérêt pour un événement de lecture, ce qui est rapide et ne bloque pas votre processus. Le rappel ne sera appelé que lorsque des données sont disponibles et peuvent être lues sans

bloquer.

L'"intérêt" est représenté par un objet retourné par "AnyEvent->io" appelé un objet "observateur" (watcher) - ainsi nommé parce qu'il "surveille" votre descripteur de fichier (ou d'autres sources d'événements) pour l'événement qui vous intéresse

.

Dans l'exemple ci-dessus, nous créons un observateur d'E/S en appelant la méthode "AnyEvent->io". Un manque d'intérêt supplémentaire pour un événement est exprimé en oubliant simplement son observateur, par exemple en mettant à "undef" la seule variable dans laquelle il est stocké. AnyEvent nettoiera automatiquement l'observateur s'il n'est plus utilisé, un peu comme Perl ferme vos descripteurs de fichier si vous ne les utilisez plus nulle

part.

Une petite note sur les

rappels

Un problème courant qui frappe les gens est celui du passage de paramètres aux rappels. Les programmeurs habitués à des langages tels que C ou C++ sont souvent habitués à un style où l'on passe l'adresse d'une fonction (une référence de fonction) et une valeur de données, par ex.

: 
sub callback {
   my ($arg) = @_;
   $arg->method;
}
my $arg = ...;
call_me_back_later \&callback,
$arg;

C'est lourd, car l'endroit où le comportement est spécifié (lorsque le rappel est enregistré) est souvent loin de l'endroit où le comportement est implémenté. Cela n'utilise pas non plus la syntaxe Perl pour invoquer le code. Il y a aussi une pénalité d'abstraction à payer car on doit nommer le rappel, ce qui est souvent inutile et mène à des noms sans sens ou

dupliqués.

En Perl, on peut spécifier le comportement de manière beaucoup plus directe en utilisant les fermetures (closures). Les fermetures sont des blocs de code qui prennent une référence au(x) scope(s) englobant(s) lorsqu'ils sont créés. Cela signifie que les variables lexicales dans le scope lorsqu'une fermeture est créée peuvent être utilisées à l'intérieur de la fermeture

: 
my $arg = ...;
call_me_back_later sub { $arg->method }
;

Dans la plupart des cas, les fermetures sont plus rapides, utilisent moins de ressources et résultent en un code beaucoup plus clair que l'approche traditionnelle. Plus rapides, car le passage de paramètres et leur stockage dans des variables locales en Perl est relativement lent. Moins de ressources, car les fermetures prennent des références à des variables existantes sans avoir à en créer de nouvelles, et code plus clair car il est immédiatement évident que le second exemple appelle la méthode "method" lorsque le rappel est

invoqué.

En dehors de cela, l'argument le plus fort pour utiliser des fermetures avec AnyEvent est qu'AnyEvent ne permet pas de passer des paramètres au rappel, donc les fermetures sont le seul moyen d'y parvenir dans la plupart des cas :

->

Un petit indice pour attraper les

erreurs

AnyEvent ne vérifie pas les paramètres que vous passez, au moins pas par défaut. Pour activer la vérification, lancez simplement votre programme avec "AE_STRICT=1" dans l'environnement, ou mettez "use AnyEvent::Strict" près du haut de votre programme

: 
AE_STRICT=1 perl
myprogram

Vous pouvez trouver plus d'informations à ce sujetest et des aides au débogage supplémentaires plus tard dans cette

introduction.

Variables de

condition

Retour à l'exemple du watcher d'E/S : le code n'est pas encore un programme entièrement fonctionnel et ne fonctionnera pas tel quel. La raison est que votre rappel ne sera pas invoqué de nulle part ; vous devez d'abord exécuter la boucle d'événements. De plus, les programmes basés sur les événements doivent aussi parfois se bloquer, par exemple quand il n'y a rien à faire et que tout attend l'arrivée de nouveaux

événements.

Dans AnyEvent, cela se fait à l'aide de variables de condition. On les appelle « variables de condition » parce qu'elles représentent une condition qui est initialement fausse et qui doit être

remplie.

Vous pouvez aussi les appeler « points de fusion », « points de synchronisation », « ports de rendez-vous » ou même des rappels et bien d'autres choses (et on les appelle souvent ainsi dans d'autres frameworks). L'important est que vous pouvez les créer librement et attendre ensuite qu'elles deviennent

vraies.

Les variables de condition ont deux côtés - un côté est le « producteur » de la condition (quel que soit le code qui détecte et signale la condition), l'autre côté est le « consommateur » (le code qui attend cette condition)

.

Dans notre exemple de la section précédente, le producteur est le rappel d'événements et il n'y a pas encore de consommateur - changeons cela tout de suite

: 
use AnyEvent;
$| = 1; print "enter your name> ";
my $name;
my $name_ready = AnyEvent->condvar;
my $wait_for_input = AnyEvent->io (
   fh   => \*STDIN,
   poll => "r",
   cb   => sub {
      $name = <STDIN>;
      $name_ready->send;
   }
);
# do something else here
# now wait until the name is available:
$name_ready->recv;
undef $wait_for_input; # watcher no longer needed
print "your name is
$name\n";

Ce programme crée une condvar AnyEvent en appelant la méthode "AnyEvent->condvar". Il crée ensuite un watcher comme d'habitude, mais à l'intérieur du rappel il "send"s la variable de condition $name_ready, ce qui fait que quiconque attend dessus

continue.

Le « quiconque » dans ce cas est le code qui suit, qui appelle "$name_ready->recv" : le producteur appelle "send", le consommateur appelle "recv"

.

S'il n'y a pas encore de $name disponible, alors l'appel à "$name_ready->recv" bloquera votre programme jusqu'à ce que la condition devienne

vraie.

Comme les noms "send" et "recv" l'impliquent, vous pouvez en fait envoyer et recevoir des données avec cela, par exemple, le code ci-dessus pourrait aussi être écrit comme ceci, sans variable supplémentaire pour stocker le nom

: 
use AnyEvent;
$| = 1; print "enter your name> ";
my $name_ready = AnyEvent->condvar;
my $wait_for_input = AnyEvent->io (
   fh => \*STDIN, poll => "r",
   cb => sub { $name_ready->send (scalar <STDIN>) }
);
# do something else here
# now wait and fetch the name
my $name = $name_ready->recv;
undef $wait_for_input; # watcher no longer needed
print "your name is
$name\n";

Vous pouvez passer un nombre quelconque d'arguments à "send", et chaque appel subséquent à "recv" les

retou
rnera.

La « boucle principale

»

La plupart des frameworks basés sur les événements ont quelque chose appelé une « boucle principale » ou « fonction d'exécution de la boucle d'événements » ou quelque chose de

similaire.

Tout comme dans "recv" AnyEvent, ces fonctions doivent être appelées éventuellement pour que votre boucle d'événements ait la chance de chercher réellement les événements qui vous

intéressent.

Par exemple, dans un programme Gtk2, l'exemple ci-dessus pourrait aussi être écrit comme ceci

: 
use Gtk2 -init;
use AnyEvent;
############################################
# create a window and some label
my $window = new Gtk2::Window "toplevel";
$window->add (my $label = new Gtk2::Label "soon replaced by name");
$window->show_all;
############################################
# do our AnyEvent stuff
$| = 1; print "enter your name> ";
my $wait_for_input = AnyEvent->io (
   fh => \*STDIN, poll => "r",
   cb => sub {
      # set the label
      $label->set_text (scalar <STDIN>);
      print "enter another name> ";
   }
);
############################################
# Now enter Gtk2's event loop
main
Gtk2;

Aucune variable de condition nulle part en vue - à la place, nous lisons simplement une ligne depuis STDIN et remplaçons le texte dans le label. En fait, puisque personne "undef"s $wait_for_input, vous pouvez entrer plusieurs

lignes.

Au lieu d'attendre une variable de condition, le programme entre dans la boucle principale Gtk2 en appelant "Gtk2->main", qui bloquera le programme et attendra l'arrivée

d'événements.

Cela montre aussi qu'AnyEvent est assez flexible - vous n'avez rien eu à faire pour faire utiliser Gtk2 (en fait Glib) par le watcher AnyEvent - cela a simplement

fonctionné.

Il faut admettre que l'exemple est un peu idiot - qui voudrait lire des noms depuis l'entrée standard dans une application Gtk+ ? Mais imaginez qu'au lieu de faire cela, vous fassiez une requête HTTP en arrière-plan et affichiez ses résultats. En fait, avec la programmation basée sur les événements, vous pouvez faire de nombreuses requêtes HTTP en parallèle dans votre programme et quand même fournir un retour à l'utilisateur et rester

interactif.

Et dans la partie suivante, vous verrez comment faire exactement cela - en implémentant une requête HTTP, par nous-mêmes, avec les modules utilitaires fournis avec

AnyEvent.

Avant cela, cependant, regardons brièvement comment vous écririez votre programme en utilisant uniquement AnyEvent, sans jamais appeler la fonction run de la boucle d'événements d'un autre

framework.

Dans l'exemple utilisant des variables de condition, nous les avons utilisées pour commencer à attendre les événements, et en fait, les variables de condition sont la solution

: 
my $quit_program = AnyEvent->condvar;
# create AnyEvent watchers (or not) here
$quit_program->
recv;

Si l'un de vos rappels de watcher décide de quitter (cela est souvent appelé un « unloop » dans d'autres frameworks), il peut simplement appeler "$quit_program->send". Bien sûr, ils pourraient aussi décider de ne pas le faire et appeler "exit" à la place, ou ils pourraient décider de ne jamais quitter (par exemple dans un programme daemon à longue durée de vie)

.

Si vous n'avez pas besoin d'une fonctionnalité de sortie propre et que vous voulez simplement exécuter la boucle d'événements, vous pouvez faire ceci

: 
AnyEvent->condvar->
recv;

Et c'est, en fait, le plus proche de

l'idée d'une fonction d'exécution de
boucle principale qu'AnyEvent offre.

Minuteries et autres sources

d'événements

Jusqu'ici, nous n'avons utilisé que des watchers d'E/S. Ceux-ci sont utiles principalement pour savoir si un socket a des données à lire, ou de l'espace pour écrire plus de données. Sur des systèmes d'exploitation sains, cela fonctionne aussi pour les fenêtres de console/terminaux (généralement sur l'entrée standard), les lignes sérielles, toutes sortes d'autres appareils, essentiellement presque tout ce qui a un descripteur de fichier mais qui n'est pas un fichier lui-même. (Comme d'habitude, « sains » exclut windows - sur cette plateforme vous auriez besoin de fonctions différentes pour tout cela, compliquant énormément le code - pensez « socket seulement » sur windows)

.

Cependant, l'E/S n'est pas tout - la deuxième source d'événements la plus importante est l'horloge. Par exemple, lors d'une requête HTTP, vous pourriez vouloir expirer si le serveur ne répond pas dans un certain délai

prédéfini.

Dans AnyEvent, les watchers d'événements de minuterie sont créés en appelant la méthode "AnyEvent->timer"

: 
use AnyEvent;
my $cv = AnyEvent->condvar;
my $wait_one_and_a_half_seconds = AnyEvent->timer (
   after => 1.5,  # after how many seconds to invoke the cb?
   cb    => sub { # the callback to invoke
      $cv->send;
   },
);
# can do something else here
# now wait till our time has come
$cv->
recv;

Contrairement aux watchers d'E/S, les minuteries ne s'intéressent qu'au nombre de secondes qu'elles doivent attendre. Quand (au moins) ce laps de temps s'est écoulé, AnyEvent invoquera votre

rappel.

Contrairement aux watchers d'E/S, qui appelleront votre rappel autant de fois qu'il y a de données disponibles, les minuteries sont normalement à usage unique : après avoir « tiré » une fois et invoqué votre rappel, elles sont mortes et ne font plus

rien.

Pour obtenir une minuterie répétitive, comme une minuterie qui se déclenche environ une fois par seconde, vous pouvez spécifier un paramètre "interval"

: 
my $once_per_second = AnyEvent->timer (
   after => 0,    # first invoke ASAP
   interval => 1, # then invoke every second
   cb    => sub { # the callback to invoke
      $cv->send;
   },
)
;

Sources plus

ésotériques

AnyEvent a aussi quelques autres sources d'événements plus ésotériques que vous pouvez exploiter : les watchers de signal, de processus enfant et

d'inactivité.

Les watchers de signal peuvent être utilisés pour attendre des « événements de signal », ce qui signifie que votre processus a reçu un signal (comme "SIGTERM" ou "SIGUSR

1").

Les watchers de processus enfant attendent la sortie d'un processus enfant. Ils sont utiles lorsque vous fork un processus séparé et avez besoin de savoir quand il se termine, mais que vous ne voulez pas attendre cela en

bloquant.

Les watchers d'inactivité invoquent leur rappel lorsque la boucle d'événements a traité tous les événements en attente, a interrogé pour de nouveaux événements et n'en a trouvé aucun, c'est-à-dire lorsque votre processus est autrement inactif. Ils sont utiles si vous voulez faire un traitement de données non trivial qui peut être fait quand votre programme n'a rien de mieux à

faire.

Tous ces types de watchers sont décrits en détail dans la page de manuel principale

d'AnyEvent.

Parfois, vous avez aussi besoin de savoir quelle est l'heure actuelle : "AnyEvent->now" retourne l'heure que la boîte à outils d'événements utilise pour planifier les minuteries relatives, et c'est généralement ce que vous voulez. Elle est souvent mise en cache (ce qui signifie qu'elle peut être un peu obsolète). Dans ce cas, vous pouvez utiliser la méthode plus coûteuse "AnyEvent->time" qui demandera à votre système d'e

xploitation l'heure actue
lle, ce qui est plus lent
, mais aussi plus à jour.

   my ($handle, $line) = @_;

   if ($line =~ /^...-/) {
      # if yes, then unshift another line read
      $handle->unshift_read (line => $read_response);
   } else {
      # otherwise we are done
      # free callback
      undef $read_response;

      print "we are don reading: $response\n";
   }
};
$handle->push_read (line => $read_response)
;

Pour inventer un exemple tordu, imaginez que vous cherchez un nombre pair de caractères suivi d'un deux-points (":"). Imaginez aussi qu'AnyEvent::Handle n'a pas de type de lecture "regex" qui pourrait être utilisé, donc vous devriez le faire

manuellement.

Pour implémenter un gestionnaire de lecture pour cela, vous devriez "push_read" (ou "unshift_read") une seule référence de

code.

Cette référence de code sera alors appelée chaque fois qu'il y a des données (nouvelles) disponibles dans le tampon de lecture, et elle doit soit manger/consommer avec succès certaines de ces données (et retourner vrai), soit retourner faux pour indiquer qu'elle souhaite être rappelée à

nouveau.

Si la référence de code retourne vrai, elle sera alors retirée de la file d'attente de lecture (car elle a analysé/consommé ce qu'elle était censée consommer), sinon elle reste en tête de

celle-ci.

L'exemple ci-dessus pourrait être codé comme ceci

: 
$handle->push_read (sub {
   my ($handle) = @_;
   # check for even number of characters + ":"
   # and remove the data if a match is found.
   # if not, return false (actually nothing)
   $handle->{rbuf} =~ s/^( (?:..)* ) ://x
      or return;
   # we got some data in $1, passe-le à qui le souhaite
   $finish->($1);
   # et retourne vrai pour indiquer que nous avons terminé
   1
}
)
;

Aides au

débogage

Maintenant que vous avez vu comment utiliser AnyEvent, voici ce qu'il faut utiliser lorsque vous ne l'utilisez pas correctement, ou simplement que vous rencontrez un bug quelque part et que vous souhaitez le déboguer

:
Activer la vérification stricte des arguments pendant le
développement
AnyEvent ne fait pas, par défaut, de vérification des arguments. Cela peut conduire à des résultats étranges et inattendus, surtout si vous essayez simplement de vous familiariser avec AnyEvent.

AnyEvent prend en charge un mode spécial "strict" - désactivé par défaut - qui effectue une vérification très stricte des arguments, au prix d'un ralentissement de votre programme. Pendant le développement, cependant, ce mode est très utile car il détecte rapidement les erreurs les plus

courantes.

Vous pouvez activer ce mode strict soit en définissant une variable d'environnement "AE_STRICT" avec une valeur vraie dans votre

environnement : 
AE_STRICT=1 perl
myprog

Ou vous pouvez écrire "use AnyEvent::Strict" dans votre programme, ce qui a le même effet (ne faites pas cela en production,

cependant)
.
Augmenter la verbosité, configurer la
journalisation
AnyEvent, par défaut, ne journalise que les messages critiques. Si quelque chose ne fonctionne pas, il y a peut-être eu un avertissement à ce sujet que vous n'avez pas vu parce qu'il a été supprimé.

Pendant le développement, il est donc recommandé d'augmenter le niveau de journalisation au moins au niveau warn (5)

: 
AE_VERBOSE=5 perl
myprog

D'autres niveaux qui pourraient être utiles sont debug (8) ou même trace (9)

.

La journalisation d'AnyEvent est assez

polyvalente - la page man An
yEvent::Log contient tous les détails.
Encapsulation des watchers, traçage, le
shell
Pour encore plus de débogage, vous pouvez activer l'encapsulation des watchers : 
AE_DEBUG_WRAP=2 perl
myprog

Cela aura pour effet d'envelopper chaque watcher dans un objet spécial qui stocke une trace de pile de la date de sa création, stocke une trace de pile lorsqu'une exception se produit pendant l'exécution du watcher, et stocke beaucoup d'autres informations. Si cela ralentit trop votre programme, alors "AE_DEBUG_WRAP=1" évite les traces de pile

coûteuses.

stockées :

Où aller à partir d'ici

?

Cette introduction aurait dû expliquer les concepts clés de AnyEvent - les watchers d'événements et les variables de condition, AnyEvent::Socket - les utilitaires réseau de base, et AnyEvent::Handle - un beau wrapper autour de

sockets.

Vous pourriez soit commencer à coder des choses tout de suite, regarder ces pages man pour les détails minutieux, ou parcourir CPAN pour d'autres modules AnyEvent (tels que AnyEvent::IRC ou AnyEvent::HTTP) pour voir plus d'exemples de code (ou simplement pour les utiliser)

.

Si vous avez besoin d'un protocole qui n'a pas d'implémentation utilisant AnyEvent, rappelez-vous que vous pouvez mélanger AnyEvent avec un autre framework d'événements, tel que POE, afin que vous puissiez toujours utiliser AnyEvent pour vos propres tâches plus les modules d'un autre framework d'événements pour combler les

lacunes.

Et enfin, vous pourriez aussi regarder Coro, en particulier Coro::AnyEvent, pour voir comment vous pouvez transformer la programmation basée sur les événements du style callback vers le style impératif habituel (aussi appelé "inversion de contrôle" - AnyEvent appelle vous, mais Coro vous permet d'appeler

AnyEv
ent).
