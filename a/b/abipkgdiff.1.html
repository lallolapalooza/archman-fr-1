abipkgdiff - comparer les ABI des fichiers ELF dans des paquets

logiciels binaires.

L'ABI des binaires contenus dans le second ensemble de paquets est comparée à l'ABI des binaires contenus dans le premier ensemble de

paquets. binaires. suppression.

Cet outil utilise la bibliothèque libabigail pour analyser le binaire ainsi que ses informations de débogage associées. Voici son mode de fonctionnement

général. analysé.

Libabigail dispose ensuite de capacités pour générer des

représentations textuelles des corpus d'ABI, les co
mparer, analyser leurs changements et les rapporter.

    Cette option doit être utilisée avec les options --devel-pkg1 et --devel-pkg2. Avec cette option, les types qui ne sont *PAS* définis dans les en-têtes sont entièrement supprimés de la représentation interne construite par Libabigail pour représenter l'ABI. Ils n'ont donc pas besoin d'être filtrés du rapport final de changement d'ABI car ils ne sont même pas présents dans la représentation de Libabigail.

    Cette option rend potentiellement la consommation de mémoire de Libabigail moindre. Elle est principalement destinée à optimiser la consommation de mémoire de l'outil sur des binaires avec beaucoup de types publiquement définis et exportés.

    La sortie typique de abipkgdiff et abidiff lors de la comparaison de deux binaires, que nous appellerons rapport d'impact complet, ressemble à ceci :

$ abidiff libtest-v0.so libtest-v1.so
Résumé des changements de fonctions : 0 Supprimées, 1 Modifiée, 0 Ajoutées fonction
Résumé des changements de variables : 0 Supprimées, 0 Modifiées, 0 Ajoutées variable
1 fonction présentant des changements de sous-type indirects :
  [C]'function void fn(C&)' at test-v1.cc:13:1 présente des changements de sous-type indirects :
    le paramètre 1 de type 'C&' présente des changements de sous-type :
      dans le type référencé 'struct C' at test-v1.cc:7:1 :
        la taille du type n'a pas changé
        1 changement de membre de données :
         le type de 'leaf* C::m0' a changé :
           dans le type pointé 'struct leaf' at test-v1.cc:1:1 :
             la taille du type a changé de 32 à 64 bits
             1 insertion de membre de données :
               'char leaf::m1', à l'offset 32 (en bits) at test-v1.cc:4:1
$

Donc, dans cet exemple, le rapport émet des informations sur la façon dont l'insertion de membre de données dans « struct leaf » est accessible depuis la fonction « void fn(C&) ». En d'autres termes, le rapport montre non seulement le changement de membre de données sur « struct leaf », mais il montre également l'impact de ce changement sur la fonction « void fn(C&) ».

Dans le jargon d'abidiff (et d'abipkgdiff), le changement sur « struct leaf » est appelé un changement de feuille. Ainsi, les options --leaf-changes-only et --impacted-interfaces affichent, eh bien, uniquement le changement de feuille. Et cela se présente ainsi :

$ abidiff -l libtest-v0.so libtest-v1.so
'struct leaf' a changé :
  la taille du type a changé de 32 à 64 bits
  1 insertion de membre de données :
    'char leaf::m1', à l'offset 32 (en bits) at test-v1.cc:4:1
  une interface impactée :
    function void fn(C&)
$

Notez comment le rapport se termine en affichant la liste des interfaces impactées par le changement de feuille. C'est l'effet de l'option supplémentaire --impacted-interfaces.

Maintenant, si vous ne voulez pas voir cette liste d'interfaces impactées, vous pouvez simplement éviter d'utiliser l'option --impacted-interface. Vous pouvez en apprendre davantage sur cette option ci-dessous, en tout cas.

Veuillez noter que lors de la comparaison de deux paquets du noyau Linux, c'est ce rapport des changements de feuilles qui est émis par défaut. Le rapport normal dit rapport d'impact complet peut être émis avec l'option --full-impact qui est documentée plus loin ci-dessous.

  • --linux-kernel-abi-whitelist | -w <chemin-vers-liste-blanche>

    Lors de la comparaison de deux paquets RPM du noyau Linux, cette option pointe vers la liste blanche des noms de symboles ELF de fonctions et de variables qui doivent être comparés pour les changements d'ABI. Cette liste blanche est appelée une « liste blanche ABI du noyau Linux ».

    Toute autre fonction ou variable dont les symboles ELF ne sont pas présents dans cette liste blanche ne sera pas prise en compte par le processus de comparaison d'ABI.

    Si cette option n'est pas fournie — donc si aucune liste blanche n'est fournie — alors l'ABI de toutes les fonctions et variables globales publiquement définies et exportées par les binaires du noyau Linux est comparée.

    Veuillez noter que si un paquet de liste blanche est donné en paramètre, cette option le gère correctement, comme si l'option --wp avait été utilisée.
