Paquet: tcl

Licences: TCL

tclvars(n) Commandes intégrées de Tcl tclvars(n)

NOM

argc, argv, argv0, auto_path, env, errorCode, errorInfo, tcl_interactive, tcl_library, tcl_nonwordchars, tcl_patchLevel, tcl_pkgPath, tcl_platform, tcl_precision, tcl_rcFileName, tcl_traceCompile, tcl_traceExec, tcl_wordchars, tcl_version - Variables utilisées par Tcl

DESCRIPTION

Les variables globales suivantes sont créées et gérées automatiquement par la bibliothèque Tcl. Sauf indication contraire ci-dessous, ces variables doivent normalement être considérées comme en lecture seule par le code spécifique à l'application et par les utilisateurs.

auto_path
Si défini, il doit contenir une liste Tcl valide donnant les répertoires à rechercher lors des opérations de chargement automatique (y compris pour les fichiers d'index de paquets lors de l'utilisation du gestionnaire par défaut package unknown ). Cette variable est initialisée au démarrage pour contenir, dans l'ordre : les répertoires listés dans la TCLLIBPATH variable d'environnement, le répertoire nommé par la tcl_library variable globale, le répertoire parent de tcl_library, [file dirname [file dirname [info nameofexecutable]]]/lib, les répertoires listés dans la tcl_pkgPath variable. Les emplacements supplémentaires où rechercher des fichiers et des index de paquets doivent normalement être ajoutés à cette variable en utilisant lappend.

Des variables supplémentaires relatives à la gestion des paquets existent. Plus de détails sont listés dans la VARIABLES section de la page man library .

env
Cette variable est maintenue par Tcl sous forme de tableau dont les éléments sont les variables d'environnement du processus. La lecture d'un élément renverra la valeur de la variable d'environnement correspondante. La définition d'un élément du tableau modifiera la variable d'environnement correspondante ou en créera une nouvelle si elle n'existe pas déjà. La suppression d'un élément de env supprimera la variable d'environnement correspondante. Les modifications du tableau env affecteront l'environnement passé aux processus enfants par des commandes comme exec. Si le tableau env entier est supprimé, Tcl cessera de surveiller les accès à env et ne mettra pas à jour les variables d'environnement.

Sous Windows, les variables d'environnement PATH et COMSPEC, quelle que soit leur capitalisation, sont automatiquement converties en majuscules. Par exemple, la variable PATH peut être exportée par le système d'exploitation sous la forme « path », « Path », « PaTh », etc., obligeant du code Tcl par ailleurs simple à prendre en charge de nombreux cas particuliers. Toutes les autres variables d'environnement héritées par Tcl restent inchangées. Définir une variable du tableau env à vide revient à la supprimer, car telle est le comportement du système d'exploitation Windows sous-jacent. Il convient de noter que s'appuyer sur une variable d'environnement existante mais vide ne fonctionnera pas sous Windows et est déconseillé pour un usage multiplateforme.

Les éléments suivants de env sont spécifiques à Tcl :

env(HOME)
Cette variable d'environnement, si définie, indique l'emplacement du répertoire considéré comme le répertoire personnel de l'utilisateur courant, et vers lequel un appel à cd sans arguments ou avec seulement « ~ » comme argument changera de répertoire. La plupart des plateformes définissent correctement cette valeur par défaut ; elle n'a normalement pas besoin d'être définie par le code utilisateur.
env(TCL_LIBRARY)
Si définie, elle spécifie l'emplacement du répertoire contenant les scripts de bibliothèque (la valeur de cette variable sera assignée à la tcl_library variable et donc renvoyée par la commande info library). Si cette variable n'est pas définie, une valeur par défaut est utilisée.

Notez que cette variable d'environnement ne doit normalement pas être définie.

env(TCLLIBPATH)
Si définie, elle doit contenir une liste Tcl valide donnant les répertoires à rechercher lors des opérations de chargement automatique. Les répertoires doivent être spécifiés au format Tcl, en utilisant « / » comme séparateur de chemin, quelle que soit la plateforme. Cette variable n'est utilisée que lors de l'initialisation de la auto_path variable.
env(TCL_TZ), env(TZ)
Ces variables spécifient le fuseau horaire par défaut utilisé pour l'analyse et le formatage des heures et des dates dans la clock commande. Sur de nombreuses plateformes, la variable d'environnement TZ est configurée par le système d'exploitation.
env(LC_ALL), env(LC_MESSAGES), env(LANG)
Ces variables d'environnement sont utilisées par le paquet msgcat pour déterminer la locale à utiliser pour formater les messages.
env(TCL_INTERP_DEBUG_FRAME)
Si elle existe, elle a le même effet que d'exécuter interp debug {} -frame 1 comme toute première commande de chaque nouvel interpréteur Tcl.
errorCode
Cette variable contient la valeur de l'option de retour -errorcode définie par la dernière erreur survenue dans cet interpréteur. Cette valeur de liste représente des informations supplémentaires sur l'erreur sous une forme facile à traiter par des programmes. Le premier élément de la liste identifie une classe générale d'erreurs et détermine le format du reste de la liste. Les formats suivants pour les options de retour -errorcode sont utilisés par le noyau Tcl ; des applications individuelles peuvent définir des formats supplémentaires.
ARITH code msg
Ce format est utilisé lorsqu'une erreur arithmétique se produit (par exemple, une tentative de diviser zéro par zéro dans la expr commande). Code identifie l'erreur précise et msg fournit une description lisible de l'erreur. Code sera soit DIVZERO (pour une tentative de division par zéro), DOMAIN (si un argument est en dehors du domaine d'une fonction, comme acos(-3)), IOVERFLOW (pour un débordement d'entier), OVERFLOW (pour un débordement en virgule flottante), ou UNKNOWN (si la cause de l'erreur ne peut être déterminée).

La détection de ces erreurs dépend en partie du matériel sous-jacent et des bibliothèques système.

CHILDKILLED pid sigName msg
Ce format est utilisé lorsqu'un processus enfant a été tué à cause d'un signal. L'élément pid sera l'identifiant du processus (en décimal). L'élément sigName sera le nom symbolique du signal qui a causé la terminaison du processus ; il s'agira de l'un des noms du fichier d'inclusion signal.h, comme SIGPIPE. L'élément msg sera un court message lisible décrivant le signal, comme « write on pipe with no readers » pour SIGPIPE.
CHILDSTATUS pid code
Ce format est utilisé lorsqu'un processus enfant s'est terminé avec un code de sortie non nul. L'élément pid sera l'identifiant du processus (en décimal) et l'élément code sera le code de sortie renvoyé par le processus (également en décimal).
CHILDSUSP pid sigName msg
Ce format est utilisé lorsqu'un processus enfant a été suspendu à cause d'un signal. L'élément pid sera l'identifiant du processus, en décimal. L'élément sigName sera le nom symbolique du signal qui a causé la suspension du processus ; il s'agira de l'un des noms du fichier d'inclusion signal.h, comme SIGTTIN. L'élément msg sera un court message lisible décrivant le signal, comme « background tty read » pour SIGTTIN.
NONE
Ce format est utilisé pour les erreurs pour lesquelles aucune information supplémentaire n'est disponible en dehors du message renvoyé avec l'erreur. Dans ces cas, l'option de retour -errorcode consistera en une liste contenant un seul élément dont le contenu est NONE.
POSIX errName msg
Si le premier élément est POSIX, alors l'erreur s'est produite lors d'un appel au noyau POSIX. L'élément errName contiendra le nom symbolique de l'erreur survenue, comme ENOENT; il s'agira de l'une des valeurs définies dans le fichier d'inclusion errno.h. L'élément msg serae un message lisible par l'humain correspondant à errName, tel que « no such file or directory » pour le cas ENOENT .
TCL ...
Indique un type de problème généré en relation avec Tcl lui-même, par ex. un échec lors de la recherche d'un canal ou d'une variable.

Pour définir l'option de retour -errorcode , les applications devraient utiliser des procédures de bibliothèque telles que Tcl_SetObjErrorCode, Tcl_SetReturnOptions, et Tcl_PosixError, ou elles peuvent invoquer l'option -errorcode de la commande return . Si aucune de ces méthodes pour définir le code d'erreur n'a été utilisée, l'interpréteur Tcl réinitialisera la variable à NONE après la prochaine erreur.

errorInfo
Cette variable contient la valeur de l'option de retour -errorinfo définie par l'erreur la plus récente survenue dans cet interpréteur. Cette valeur de chaîne contiendra une ou plusieurs lignes identifiant les commandes et procédures Tcl qui étaient en cours d'exécution lorsque l'erreur la plus récente est survenue. Son contenu prend la forme d'une trace de pile montrant les différentes commandes Tcl imbriquées qui avaient été invoquées au moment de l'erreur.
tcl_library
Cette variable contient le nom d'un répertoire contenant la bibliothèque système de scripts Tcl, tels que ceux utilisés pour le chargement automatique. La valeur de cette variable est retournée par la info library commande. Voir l'entrée de manuel library pour les détails des fonctionnalités fournies par la bibliothèque de scripts Tcl. Normalement, chaque application ou package aura sa propre bibliothèque de scripts spécifique à l'application en plus de la bibliothèque de scripts Tcl ; chaque application devrait définir une variable globale avec un nom comme $app_library (où app est le nom de l'application) pour contenir le nom de fichier réseau du répertoire de bibliothèque de cette application. La valeur initiale de tcl_library est définie lorsqu'un interpréteur est créé en recherchant plusieurs répertoires différents jusqu'à en trouver un qui contient un script de démarrage Tcl approprié. Si la variable d'environnement TCL_LIBRARY existe, alors le répertoire qu'elle nomme est vérifié en premier. Si TCL_LIBRARY n'est pas définie ou ne référence pas un répertoire approprié, alors Tcl vérifie plusieurs autres répertoires basés sur un emplacement par défaut compilé, l'emplacement du binaire contenant l'application, et le répertoire de travail courant.
tcl_patchLevel
Lorsqu'un interpréteur est créé, Tcl initialise cette variable pour contenir une chaîne donnant le niveau de patch courant pour Tcl, tel que 8.4.16 pour Tcl 8.4 avec les seize premiers patches officiels, ou 8.5b3 pour la troisième version bêta de Tcl 8.5. La valeur de cette variable est retournée par la info patchlevel commande.
tcl_pkgPath
Cette variable contient une liste de répertoires indiquant où les packages sont normalement installés. Elle n'est pas utilisée sur Windows. Elle contient typiquement une ou deux entrées ; si elle contient deux entrées, la première est normalement un répertoire pour les packages dépendants de la plateforme (par ex., les binaires de bibliothèque partagée) et la seconde est normalement un répertoire pour les packages indépendants de la plateforme (par ex., les fichiers de script). Typiquement, un package est installé en tant que sous-répertoire de l'une des entrées de la variable tcl_pkgPath . Les répertoires dans la variable tcl_pkgPath sont inclus par défaut dans la variable auto_path , donc eux et leurs sous-répertoires immédiats sont automatiquement recherchés pour les packages lors des commandes package require . Note : tcl_pkgPath n'est pas destiné à être modifié par l'application. Sa valeur est ajoutée à auto_path au démarrage ; les modifications de tcl_pkgPath ne sont pas répercutées dans auto_path. Si vous voulez que Tcl recherche des répertoires supplémentaires pour les packages, vous devriez ajouter les noms de ces répertoires à auto_path, pas à tcl_pkgPath.
tcl_platform
C'est un tableau associatif dont les éléments contiennent des informations sur la plateforme sur laquelle l'application s'exécute, telles que le nom du système d'exploitation, son numéro de version courant, et le jeu d'instructions de la machine. Les éléments listés ci-dessous seront toujours définis, mais ils peuvent avoir des chaînes vides comme valeurs si Tcl n'a pas pu récupérer d'informations pertinentes. De plus, les extensions et les applications peuvent ajouter des valeurs supplémentaires au tableau. Les éléments prédéfinis sont :
byteOrder
L'ordre d'octets natif de cette machine : soit littleEndian ou bigEndian.
debug
Si cette variable existe, alors l'interpréteur a été compilé avec et lié à une bibliothèque d'exécution C activée pour le débogage. Cette variable n'existera que sur Windows, afin que les auteurs d'extensions puissent spécifier quel package charger en fonction de la bibliothèque d'exécution C utilisée. Ceci n'est pas une indication que ce noyau contient des symboles.
engine
Le nom de l'implémentation du langage Tcl. Lorsque l'interpréteur est créé pour la première fois, ceci est toujours défini à la chaîne Tcl.
machine
Le jeu d'instructions exécuté par cette machine, tel que intel, PPC, 68k, ou sun4m. Sur les machines UNIX, c'est la valeur retournée par uname -m.
os
Le nom du système d'exploitation s'exécutant sur cette machine, tel que Windows NT ou SunOS. Sur les machines UNIX, c'est la valeur retournée par uname -s.
osVersion
Le numéro de version du système d'exploitation s'exécutant sur cette machine. Sur les machines UNIX, c'est la valeur retournée par uname -r.
pathSeparator
Le caractère qui devrait être utilisé pour diviser les variables d'environnement de type PATH en leur liste correspondante de noms de répertoires.
platform
Soit windows, ou unix. Ceci identifie l'environnement d'exploitation général de la machine.
pointerSize
Ceci donne la taille du pointeur de la machine native en octets (strictement, c'est le même que le résultat de l'évaluation de sizeof(void*) en C.)
threaded
Si cette variable existe, alors l'interpréteur a été compilé avec les threads activés.
user
Ceci identifie l'utilisateur courant basé sur les informations de connexion disponibles sur la plateforme. Cette valeur provient des appels système getuid() et getpwuid() sur Unix, et de la valeur de l'appel système GetUserName() sur Windows.
wordSize
Ceci donne la taille du mot de la machine native en octets (strictement, c'est le même que le résultat de l'évaluation de sizeof(long) en C.)
tcl_precision
Cette variable contrôle le nombre de chiffres à générer lors de la conversion des valeurs en virgule flottante en chaînes. Sa valeur par défaut est 0. Les applications ne devraient pas changer cette valeur ; elle est fournie pour la compatibilité avec le code hérité.
La valeur par défaut de 0 est spéciale, signifiant que Tcl devrait convertir les nombres en utilisant aussi peu de chiffres que possible tout en distinguant toujours tout nombre en virgule flottante de ses voisins les plus proches. Elle diffère de l'utilisation d'une valeur arbitrairement élevée pour tcl_precision en ce que un nombre inexact comme 1.4 sera converti en 1.4 plutôt qu'en 1.3999999999999999 bien que ce dernier soit plus proche de la valeur exacte du nombre binaire.
Si tcl_precision n'est pas zéro, alors lorsque Tcl convertit un nombre en virgule flottante, il crée une représentation décimale d'au plus tcl_precision chiffres significatifs ; le résultat peut être plus court si le résultat plus court représente le nombre original exactement. Si aucun résultat d'au plus tcl_precision chiffres n'est une représentation exacte du nombre original, celui qui est le plus proche du nombre original est choisi. Si le nombre original se trouve précisément entre deux représentations décimales également précises, alors celui avec une valeur paire pour le chiffre le moins significatif est choisi ; par exemple, si tcl_precision est 3, alors 0.3125 sera converti en 0.312, pas en 0.313, tandis que 0.6875 sera converti en 0.688, pas en 0.687. Toute chaîne de zéros finaux restante est supprimée.
Une tcl_precision valeur de 17 chiffres est « parfaite » pour les virgules flottantes IEEE en ce qu'elle permet aux valeurs en double précision d'être converties en chaînes et en retour en binaire sans perte d'information. Pour cette raison, vous le verrez souvent comme une valeur dans le code hérité qui doit s'exécuter sur des versions de Tcl antérieures à 8.5. Ce n'est plus recommandé ; comme noté ci-dessus, une valeur zéro est la méthode préférée.
Tous les interpréteurs dans un thread partagent une seule tcl_precision valeur : la changer dans un interpréteur affectera tous les autres interpréteurs également. Les interpréteurs sûrs ne sont pas autorisés à modifier la variable.
Les valeurs valides pour tcl_precision vont de 0 à 17.
tcl_rcFileName
Cette variable est utilisée lors de l'initialisation pour indiquer le nom d'un fichier de démarrage spécifique à l'utilisateur. Si elle est définie par une initialisation spécifique à l'application, alors le code de démarrage de Tcl vérifiera l'existence de ce fichier et source s'il existe. Par exemple, pour wish la variable est définie à ~/.wishrc pour Unix et ~/wishrc.tcl pour Windows.
tcl_traceCompile
La valeur de cette variable peut être définie pour contrôler la quantité d'informations de traçage affichées lors de la compilation en code octet. Par défaut, tcl_traceCompile est zéro et aucune information n'est affichée. Définir tcl_traceCompile à 1 génère un résumé d'une ligne dans stdout chaque fois qu'une procédure ou une commande de niveau supérieur est compilée. Le définir à 2 génère une liste détaillée dans stdout des instructions de code octet émises lors de chaque compilation. Cette variable est utile pour traquer des problèmes suspects avec le compilateur Tcl.
Cette variable et cette fonctionnalité n'existent que si TCL_COMPILE_DEBUG a été défini lors de la compilation de Tcl.
tcl_traceExec
La valeur de cette variable peut être définie pour contrôler la quantité d'informations de traçage affichées lors de l'exécution du bytecode. Par défaut, tcl_traceExec est zéro et aucune information n'est affichée. Définir tcl_traceExec à 1 génère une trace d'une ligne sur stdout à chaque appel d'une procédure Tcl. La définir à 2 génère une ligne de sortie chaque fois qu'une commande Tcl est invoquée, contenant le nom de la commande et ses arguments. La définir à 3 produit une trace détaillée montrant le résultat de l'exécution de chaque instruction de bytecode. Notez que lorsque tcl_traceExec est 2 ou 3, les commandes telles que set et incr qui ont été entièrement remplacées par une séquence d'instructions de bytecode ne sont pas affichées. La définition de cette variable est utile pour traquer des problèmes suspects avec le compilateur et l'interpréteur de bytecode.
Cette variable et cette fonctionnalité n'existent que si TCL_COMPILE_DEBUG a été défini lors de la compilation de Tcl.
tcl_wordchars
La valeur de cette variable est une expression régulière qui peut être définie pour contrôler quels caractères sont considérés comme des caractères de « mot », par exemple pour sélectionner un mot par double-clic dans le texte Tk. Elle dépend de la plateforme. Sous Windows, elle vaut par défaut \S, ce qui signifie tout sauf un caractère d'espacement Unicode. Sinon, elle vaut par défaut \w, qui est tout caractère de mot Unicode (chiffre, lettre ou soulignement).
tcl_nonwordchars
La valeur de cette variable est une expression régulière qui peut être définie pour contrôler quels caractères sont considérés comme des caractères « non-mot », par exemple pour sélectionner un mot par double-clic dans le texte Tk. Elle dépend de la plateforme. Sous Windows, elle vaut par défaut \s, ce qui signifie tout caractère d'espacement Unicode. Sinon, elle vaut par défaut \W, qui est tout sauf un caractère de mot Unicode (chiffre, lettre ou soulignement).
tcl_version
Lorsqu'un interpréteur est créé, Tcl initialise cette variable pour contenir le numéro de version de cette version de Tcl sous la forme x.y. Les changements à x représentent des changements majeurs avec des incompatibilités probables et les changements à y représentent de petites améliorations et corrections de bugs qui conservent la compatibilité descendante. La valeur de cette variable est retournée par la commande info tclversion.

AUTRES VARIABLES GLOBALES

Les variables suivantes sont garanties d'exister uniquement dans les exécutables tclsh et wish ; la bibliothèque Tcl ne les définit pas elle-même mais de nombreux environnements Tcl le font.

argc
Le nombre d'arguments pour tclsh ou wish.
argv
Liste Tcl des arguments pour tclsh ou wish.
argv0
Le script que tclsh ou wish a commencé à exécuter (s'il a été spécifié) ou sinon le nom par lequel tclsh ou wish a été invoqué.
tcl_interactive
Contient 1 si tclsh ou wish s'exécute de manière interactive (aucun script n'a été spécifié et l'entrée standard est un périphérique de type terminal), 0 sinon.

EXEMPLES

Pour ajouter un répertoire à la collection d'emplacements recherchés par package require, par exemple, en raison de certains packages spécifiques à l'application utilisés, la variable auto_path doit être mise à jour :

lappend ::auto_path [file join [pwd] "theLibDir"]

Une manière simple, bien que peu robuste, de gérer les arguments de ligne de commande de la forme « -foo 1 -bar 2 » est de les charger dans un tableau après avoir chargé les paramètres par défaut :

array set arguments {-foo 0 -bar 0 -grill 0}
array set arguments $::argv
puts "foo is $arguments(-foo)"
puts "bar is $arguments(-bar)"
puts "grill is $arguments(-grill)"

La variable globale argv0 peut être utilisée (en conjonction avec la commande info script) pour déterminer si le script actuel est exécuté comme script principal ou chargé comme bibliothèque. Ceci est utile car cela permet à un seul script d'être utilisé à la fois comme bibliothèque et comme démonstration de cette bibliothèque :

if {$::argv0 eq [info script]} {
    # exécution en tant que : tclsh example.tcl
} else {
    package provide Example 1.0
}
