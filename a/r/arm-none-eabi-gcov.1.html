DESCRIPTION

gcov est un programme de couverture de test. Utilisez-le en conjonction avec GCC pour analyser vos programmes afin de créer un code plus efficace et plus rapide, et pour découvrir les parties non testées de votre programme. Vous pouvez utiliser gcov comme un outil de profilage pour découvrir où vos efforts d'optimisation auront le plus d'impact sur votre code. Vous pouvez également utiliser gcov avec l'autre outil de profilage, gprof, pour évaluer quelles parties de votre code consomment le plus de temps de calcul.

Les outils de profilage vous aident à analyser les performances de votre code. En utilisant un profileur tel que gcov ou gprof, vous pouvez obtenir des statistiques de performance de base, telles que :

  • la fréquence d'exécution de chaque ligne de code
  • quelles lignes de code sont effectivement exécutées
  • combien de temps de calcul chaque section de code utilise

Une fois que vous connaissez ces informations sur le fonctionnement de votre code une fois compilé, vous pouvez examiner chaque module pour voir lesquels devraient être optimisés. gcov vous aide à déterminer où concentrer vos efforts d'optimisation.

Les développeurs de logiciels utilisent également le test de couverture en conjonction avec des suites de tests, pour s'assurer que le logiciel est suffisamment bon pour une publication. Les suites de tests peuvent vérifier qu'un programme fonctionne comme prévu ; un programme de couverture vérifie quelle partie du programme est exercée par la suite de tests. Les développeurs peuvent alors déterminer quels types de cas de test doivent être ajoutés aux suites de tests pour créer à la fois de meilleurs tests et un meilleur produit final.

Vous devriez compiler votre code sans optimisation si vous prévoyez d'utiliser gcov, car l'optimisation, en combinant certaines lignes de code en une seule fonction, peut ne pas vous fournir autant d'informations que nécessaire pour rechercher les « points chauds » où le code consomme beaucoup de temps de calcul. De même, comme gcov accumule les statistiques ligne par ligne (à la plus faible résolution), il fonctionne mieux avec un style de programmation qui place une seule instruction par ligne. Si vous utilisez des macros complexes qui se développent en boucles ou en autres structures de contrôle, les statistiques sont moins utiles — elles ne rapportent que la ligne où apparaît l'appel de macro. Si vos macros complexes se comportent comme des fonctions, vous pouvez les remplacer par des fonctions en ligne pour résoudre ce problème.

gcov crée un fichier journal appelé sourcefile.gcov qui indique combien de fois chaque ligne d'un fichier source sourcefile.c a été exécutée. Vous pouvez utiliser ces fichiers journaux en conjonction avec gprof pour affiner les performances de vos programmes. gprof fournit des informations de temps que vous pouvez utiliser avec les informations que vous obtenez de gcov.

gcov ne fonctionne qu'avec le code compilé par GCC. Il n'est pas compatible avec tout autre mécanisme de profilage ou de couverture de test.

OPTIONS

-a
--all-blocks
Écrit les comptes d'exécution individuels pour chaque bloc de base. Normalement, gcov n'affiche les comptes d'exécution que pour les blocs principaux d'une ligne. Avec cette option, vous pouvez déterminer si des blocs au sein d'une même ligne ne sont pas exécutés.
-b
--branch-probabilities
Écrit les fréquences des branches dans le fichier de sortie, et affiche les informations récapitulatives des branches sur la sortie standard. Cette option vous permet de voir combien de fois chaque branche de votre programme a été prise. Les branches inconditionnelles ne seront pas affichées, à moins que l'option -u ne soit donnée.
-c
--branch-counts
Écrit les fréquences des branches sous forme de nombre de branches prises, plutôt que de pourcentage de branches prises.
-g
--conditions
Écrit la couverture des conditions dans le fichier de sortie, et affiche les informations récapitulatives des conditions sur la sortie standard. Cette option vous permet de voir si les conditions de votre programme ont au moins une fois eu un effet indépendant sur le résultat de l'expression booléenne (couverture des conditions/décisions modifiées). Cela nécessite de compiler la source avec -fcondition-coverage.
-d
--display-progress
Affiche la progression sur la sortie standard.
-f
--function-summaries
Affiche des résumés pour chaque fonction en plus du résumé au niveau du fichier.
-h
--help
Affiche l'aide sur l'utilisation de gcov (sur la sortie standard), et quitte sans effectuer de traitement supplémentaire.
-j
--json-format
Produit le fichier gcov dans un format intermédiaire JSON facile à analyser, qui ne nécessite pas de code source pour sa génération. Le fichier JSON est compressé avec l'algorithme de compression gzip et les fichiers ont l'extension .gcov.json.gz.

gcov doit être exécuté avec le répertoire courant identique à celui lorsque vous avez invoqué le compilateur. Sinon, il ne pourra pas localiser les fichiers source. gcov produit des fichiers appelés nommangé.gcov dans le répertoire courant. Ceux-ci contiennent les informations de couverture du fichier source auquel ils correspondent. Un fichier .gcov est produit pour chaque fichier source (ou d'en-tête) contenant du code, qui a été compilé pour produire les fichiers de données. La partie nommangé du nom du fichier de sortie est généralement simplement le nom du fichier source, mais peut être quelque chose de plus compliqué si les options -l ou -p sont données. Reportez-vous à ces options pour plus de

détails.

Si vous invoquez gcov avec plusieurs fichiers d'entrée, les contributions de chaque fichier d'entrée sont sommées. Typiquement, vous l'invoqueriez avec la même liste de fichiers que le lien final de votre

exécutable.

Les fichiers .gcov contiennent les champs séparés par : ainsi que le code source du programme. Le format

est 
<execution_count>:<line_number>:<source line
text>

Des informations de bloc supplémentaires peuvent suivre chaque ligne, lorsque cela est demandé par une option de ligne de commande. Le execution_count est - pour les lignes ne contenant pas de code. Les lignes non exécutées sont marquées ##### ou =====, selon qu'elles sont accessibles par des chemins non exceptionnels ou uniquement par des chemins exceptionnels tels que les gestionnaires d'exceptions C++, respectivement. Avec l' option -a, les blocs non exécutés sont marqués $$$$$ ou %%%%%, selon qu'un bloc de base est accessible via des chemins non exceptionnels ou exceptionnels. Les blocs de base exécutés ayant une instruction avec un execution_count zéro se terminent par le caractère * et sont coloriés en magenta avec l' option -k. Cette fonctionnalité n'est pas prise en charge en

Ada.

Notez que GCC peut supprimer complètement les corps des fonctions qui ne sont pas nécessaires -- par exemple s'ils sont en ligne partout. De telles fonctions sont marquées avec -, ce qui peut être déroutant. Utilisez l'option -fkeep-inline-options et -fkeep-static-functions pour conserver ces fonctions et permettre à gcov d'afficher correctement leur execution_count.

Certaines lignes d'informations au début ont un line_number de zéro. Ces lignes de préambule sont de la forme

-:0:<tag>:<value>

L'ordre et le nombre de ces lignes de préambule seront augmentés au fur et à mesure du développement de gcov --- ne vous fiez pas à leur conservation inchangée. Utilisez tag pour localiser une ligne de préambule particulière.

Les informations supplémentaires sur les blocs sont de la forme

<tag> <information>

L'information est lisible par l'homme, mais conçue pour être suffisamment simple pour un traitement automatique.

Lors de l'impression des pourcentages, 0% et 100% ne sont imprimés que lorsque les valeurs sont exactement 0% et 100% respectivement. D'autres valeurs qui seraient conventionnellement arrondies à 0% ou 100% sont alors imprimées comme la valeur non limite la plus proche.

Lors de l'utilisation de gcov, vous devez d'abord compiler votre programme avec une option spéciale de GCC --coverage. Cela indique au compilateur de générer les informations supplémentaires nécessaires à gcov (principalement un graphe de flux du programme) et inclut également du code supplémentaire dans les fichiers objet pour générer les informations de profilage supplémentaires nécessaires à gcov. Ces fichiers supplémentaires sont placés dans le répertoire où se trouve le fichier objet.

L'exécution du programme générera une sortie de profilage. Pour chaque fichier source compilé avec -fprofile-arcs, un fichier .gcda accompagnant sera placé dans le répertoire du fichier objet.

L'exécution de gcov avec les noms de fichiers source de votre programme comme arguments produira maintenant une liste du code avec la fréquence d'exécution pour chaque ligne. Par exemple, si votre programme est appelé tmp.cpp, voici ce que vous voyez lorsque vous utilisez la fonctionnalité de base de gcov:

$ g++ --coverage tmp.cpp -c
$ g++ --coverage tmp.o
$ a.out
$ gcov tmp.cpp -m

Après chaque bloc, les comptes de branchement et d'appel du bloc seront affichés, si l'option -b est donnée.

Pour chaque fonction, une ligne est affichée indiquant combien de fois la fonction est appelée, combien de fois elle retourne et quel pourcentage des blocs de la fonction a été exécuté.

Pour chaque bloc de base, une ligne est affichée après la dernière ligne du bloc de base décrivant le branchement ou l'appel qui termine le bloc de base. Il peut y avoir plusieurs branchements et appels listés pour une seule ligne source s'il y a plusieurs blocs de base qui se terminent sur cette ligne. Dans ce cas, les branchements et appels reçoivent chacun un numéro. Il n'y a pas de moyen simple de faire correspondre ces branchements et appels aux constructions sources. En général, cependant, le branchement ou l'appel de plus petit numéro correspondra à la construction la plus à gauche sur la ligne source.

Pour un branchement, s'il a été exécuté au moins une fois, un pourcentage indiquant le nombre de fois où le branchement a été pris divisé par le nombre de fois où le branchement a été exécuté sera affiché. Sinon, le message "never executed" (jamais exécuté) sera affiché.

Pour un appel, s'il a été exécuté au moins une fois, un pourcentage indiquant le nombre de fois où l'appel a retourné divisé par le nombre de fois où l'appel a été exécuté sera affiché. Ce sera généralement 100%, mais peut être inférieur pour les fonctions qui appellent "exit" ou "longjmp", et qui peuvent donc ne pas retourner à chaque fois qu'elles sont appelées.

Les comptes d'exécution sont cumulatifs. Si le programme exemple était réexécuté sans supprimer le fichier .gcda, le compte du nombre de fois où chaque ligne de la source a été exécutée serait ajouté aux résultats de la (ou des) exécution(s) précédente(s). Ceci est potentiellement utile de plusieurs manières. Par exemple, il pourrait être utilisé pour accumuler des données sur un certain nombre d'exécutions de programmes dans le cadre d'une suite de vérification de tests, ou pour fournir des informations plus précises à long terme sur un grand nombre d'exécutions de programmes.

Les données des fichiers .gcda sont sauvegardées juste avant que le programme ne se termine. Pour chaque

fichier source compilé avec -fprofile-arcs, le code de profilage tente d'abord de lire un fichier .gcda existant ; si le fichier ne correspond pas à l'exécutable (nombre différent de comptages de blocs de base), il ignore le contenu du fichier. Il ajoute ensuite les nouveaux comptages d'exécution et écrit enfin les données dans le

fichier.

Utilisation de gcov avec l'optimisation de

GCC

Si vous prévoyez d'utiliser gcov pour aider à optimiser votre code, vous devez d'abord compiler votre programme avec une option GCC spéciale --coverage. En dehors de cela, vous pouvez utiliser n'importe quelles autres options GCC ; mais si vous voulez prouver que chaque ligne de votre programme a été exécutée, vous ne devriez pas compiler avec l'optimisation en même temps. Sur certaines machines, l'optimiseur peut éliminer certaines lignes de code simples en les combinant avec d'autres lignes. Par exemple, du code comme ceci

: 
if (a != b)
  c = 1;
else
  c =
0;

peut être compilé en une seule instruction sur certaines machines. Dans ce cas, il n'y a aucun moyen pour gcov de calculer des comptages d'exécution séparés pour chaque ligne car il n'y a pas de code séparé pour chaque ligne. Par conséquent, la sortie de gcov ressemble à ceci si vous avez compilé le programme avec l'optimisation

: 
100:   12:if (a != b)
100:   13:  c = 1;
100:   14:else
100:   15:  c =
0;

La sortie montre que ce bloc de code, combiné par l'optimisation, s'est exécuté 100 fois. En un sens, ce résultat est correct, car il n'y avait qu'une seule instruction représentant ces quatre lignes. Cependant, la sortie n'indique pas combien de fois le résultat était 0 et combien de fois le résultat était

1.

Les fonctions inlinables peuvent créer des comptages de lignes inattendus. Les comptages de lignes sont affichés pour le code source de la fonction inlinable, mais ce qui est affiché dépend de l'endroit où la fonction est inlinée, ou si elle n'est pas inlinée du

tout.

Si la fonction n'est pas inlinée, le compilateur doit émettre une copie hors ligne de la fonction, dans tout fichier objet qui en a besoin. Si fileA.o et fileB.o contiennent tous deux des corps hors ligne d'une fonction inlinable particulière, ils contiendront également tous deux des comptages de couverture pour cette fonction. Lorsque fileA.o et fileB.o sont liés ensemble, l'éditeur de liens sélectionnera, sur de nombreux systèmes, l'un de ces corps hors ligne pour tous les appels à cette fonction, et supprimera ou ignorera l'autre. Malheureusement, il ne supprimera pas les compteurs de couverture du corps de fonction inutilisé. Ainsi, lorsqu'il est instrumenté, tous les usages de cette fonction à l'exception d'un seul afficheront des comptages à

zéro.

Si la fonction est inlinée à plusieurs endroits, la structure de blocs à chaque emplacement pourrait ne pas être la même. Par exemple, une condition pourrait désormais être calculable à la compilation dans certains cas. Étant donné que la couverture de tous les usages de la fonction en ligne sera affichée pour les mêmes lignes sources, les comptages de lignes eux-mêmes pourraient sembler

incohérents.

Les applications à longue durée d'exécution peuvent utiliser les fonctionnalités "__gcov_reset" et "__gcov_dump" pour restreindre la collecte de profil à la région du programme d'intérêt. Appeler "__gcov_reset(void)" effacera tous les compteurs de profil d'exécution à zéro, et appeler "__gcov_dump(void)" fera en sorte que les informations de profil collectées à ce moment-là soient écrites dans les fichiers de sortie .gcda. Les applications instrumentées utilisent un destructeur statique avec la priorité 99 pour invoquer la fonction "__gcov_dump". Ainsi "__gcov_dump" est exécutée après tous les destructeurs statiques définis par l'utilisateur, ainsi que les gestionnaires enregistrés avec "atexit"

.

Si un exécutable charge un objet partagé dynamique via la fonctionnalité dlopen, -Wl,--dynamic-list-data est nécessaire pour écrire toutes les données de

profil.

La bibliothèque d'exécution de profilage signale diverses erreurs liées à la manipulation du profil et à l'enregistrement du profil. Les erreurs sont imprimées dans la sortie d'erreur standard ou dans le fichier GCOV_ERROR_FILE, si la variable d'environnement est utilisée. Afin de se terminer immédiatement après qu'une erreur se produit, définissez la variable d'environnement GCOV_EXIT_AT_ERROR. Cela peut aider les utilisateu

rs à trouver des confl
its de profil qui conduis
ent à un profil trompeur.
