DESCRIPTIO

N

Ce module de protocole noyau implémente le protocole de résolution d'adresses (Address Resolution Protocol) défini dans la RFC 826. Il est utilisé pour convertir entre les adresses matérielles de couche 2 et les adresses de protocole IPv4 sur les réseaux directement connectés. L'utilisateur n'interagit normalement pas directement avec ce module, sauf pour le configurer ; il fournit plutôt un service pour d'autres protocoles dans le

noyau.

Un processus utilisateur peut recevoir des paquets ARP en utilisant des sockets packet(7). Il existe également un mécanisme pour gérer le cache ARP dans l'espace utilisateur en utilisant des sockets netlink(7). La table ARP peut également être contrôlée via ioctl(2) sur n'importe quelle socket AF_INET

.

Le module ARP maintient un cache de correspondances entre les adresses matérielles et les adresses de protocole. Le cache a une taille limitée, de sorte que les entrées anciennes et moins fréquemment utilisées sont récupérées par le ramasse-miettes (garbage-collected). Les entrées marquées comme permanentes ne sont jamais supprimées par le ramasse-miettes. Le cache peut être manipulé directement à l'aide d'ioctls et son comportement peut être réglé via les interfaces /proc décrites

ci-dessous.

Lorsqu'il n'y a pas de retour positif pour une correspondance existante pendant un certain temps (voir les interfaces /proc ci-dessous), une entrée de cache de voisin est considérée comme obsolète (stale). Un retour positif peut être obtenu depuis une couche supérieure ; par exemple, depuis un accusé de réception (ACK) TCP réussi. D'autres protocoles peuvent signaler une progression en utilisant le drapeau MSG_CONFIRM de sendmsg(2). Quand il n'y a pas de progression, ARP tente de sonder à nouveau. Il essaie d'abord de demander à un démon arp local app_solicit fois une adresse MAC mise à jour. Si cela échoue et qu'une ancienne adresse MAC est connée, une sonde unicast est envoyée ucast_solicit fois. Si cela échoue aussi, une nouvelle requête ARP sera diffusée sur le réseau. Les requêtes ne sont envoyées que lorsqu'il y a des données en attente

d'envoi.

Linux ajoutera automatiquement une entrée proxy arp non permanente lorsqu'il reçoit une requête pour une adresse vers laquelle il fait de la redirection et que le proxy arp est activé sur l'interface de réception. Lorsqu'il existe une route de rejet pour la cible, aucune entrée proxy arp n'est

ajoutée.

Ioctl

s

Trois ioctls sont disponibles sur toutes les sockets AF_INET. Ils prennent un pointeur vers une struct arpreq comme

argument. 


struct arpreq {
    struct sockaddr arp_pa;      /* adresse de protocole */
    struct sockaddr arp_ha;      /* adresse matérielle */
    int             arp_flags;   /* drapeaux */
    struct sockaddr arp_netmask; /* masque réseau de l'adresse de protocole */
    char            arp_dev[16];
}
;

SIOCSARP, SIOCDARP et SIOCGARP définissent, suppriment et récupèrent respectivement une correspondance ARP. La définition et la suppression de correspondances ARP sont des opérations privilégiées et ne peuvent être effectuées que par un processus possédant la capacité CAP_NET_ADMIN ou un UID effectif de

0.

Interfaces

/proc

ARP prend en charge une gamme d' interfaces /proc pour configurer des paramètres de manière globale ou par interface. Les interfaces peuvent être accessibles en lisant ou en écrivant les fichiers /proc/sys/net/ipv4/neigh/*/*. Chaque interface du système a son propre répertoire dans /proc/sys/net/ipv4/neigh/. Le paramètre du répertoire "default" est utilisé pour tous les périphériques nouvellement créés. Sauf indication contraire, les interfaces liées au temps sont spécifiées en

secondes.

VERSION

S

La structure struct arpreq a changé dans Linux 2.0 pour inclure le membre arp_dev et les numéros d'ioctl ont changé en même temps. La prise en charge des anciens ioctl a été abandonnée dans Linux 2.

2.

La prise en charge des entrées ARP de proxy pour les réseaux (masque de sous-réseau différent de 0xffffffff) a été abandonnée dans Linux 2.2. Elle est remplacée par la configuration automatique de l'ARP de proxy par le noyau pour tous les hôtes accessibles sur les autres interfaces (lorsque le routage et l'ARP de proxy sont activés pour l'interface)

.

Les interfaces neigh/* n'existaient

pas avant
Linux 2.2.

BUG

S

Certains réglages de minuterie sont spécifiés en jiffies, ce qui dépend de l'architecture et de la version du noyau ; voir time(

7).

Il n'existe aucun moyen de signaler un retour positif depuis l'espace utilisateur. Cela signifie que les protocoles orientés connexion implémentés dans l'espace utilisateur généreront un trafic ARP excessif, car ndisc sondera régulièrement l'adresse MAC. Le même problème s'applique à certains protocoles du noyau (par ex., NFS sur UDP)

.
