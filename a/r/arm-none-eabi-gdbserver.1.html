DESCRIPTIO

N

gdbserver est un programme qui vous permet d'exécuter GDB sur une machine différente de celle qui exécute le programme en cours de

débogage.

Utilisation (côté serveur (cible))

:

Tout d'abord, vous devez placer une copie du programme que vous souhaitez déboguer sur le système cible. Le programme peut être dépouillé de ses symboles pour économiser de l'espace si nécessaire, car gdbserver ne se soucie pas des symboles. Toute la gestion des symboles est prise en charge par GDB exécuté sur le système

hôte.

Pour utiliser le serveur, connectez-vous au système cible et exécutez le programme gdbserver. Vous devez lui indiquer (a) comment communiquer avec GDB, (b) le nom de votre programme et (c) ses arguments. La syntaxe générale est

: 
cible> gdbserver <comm> <programme> [<args> ...
]

Par exemple, en utilisant un port série, vous pourriez dire

: 
cible> gdbserver /dev/com1 emacs foo.
txt

Cela indique à gdbserver de déboguer emacs avec l'argument foo.txt et de communiquer avec GDB via /dev/com1. gdbserver attend maintenant patiemment que l'hôte GDB communique avec

lui.

Pour utiliser une connexion TCP, vous pourriez dire

: 
cible> gdbserver host:2345 emacs foo.
txt

Cela dit à peu près la même chose que l'exemple précédent, sauf que nous allons communiquer avec le GDB "hôte" via TCP. L'argument "host:2345" signifie que nous attendons une connexion TCP en provenance de "host" vers le port TCP local 2345. (Actuellement, la partie "host" est ignorée.) Vous pouvez choisir le numéro de port de votre choix à condition qu'il n'entre pas en conflit avec les ports TCP existants sur le système cible. Ce même numéro de port doit être utilisé dans la commande "target remote" du GDB hôte, qui sera décrite sous peu. Notez que si vous choisissez un numéro de port qui entre en conflit avec un autre service, gdbserver affichera un message d'erreur et se

terminera.

gdbserver peut également s'attacher à des programmes en cours d'exécution. Cela s'effectue via l'argument --attach. La syntaxe est

: 
cible> gdbserver --attach <comm>
<pid>

pid est l'identifiant de processus d'un processus en cours d'exécution. Il n'est pas nécessaire d'indiquer à gdbserver un binaire pour le processus en cours

d'exécution.

Pour démarrer "gdbserver" sans fournir de commande initiale à exécuter ni d'identifiant de processus auquel s'attacher, utilisez l'option de ligne de commande --multi. Dans ce cas, vous devez vous connecter en utilisant "target extended-remote" pour démarrer le programme que vous souhaitez

déboguer. 
cible> gdbserver --multi
<comm>

Utilisation (côté hôte)

:

Vous avez besoin d'une copie non dépouillée du programme cible sur votre système hôte, car GDB doit examiner ses tables de symboles et autres. Démarrez GDB comme vous le feriez normalement, avec le programme cible comme premier argument. (Vous devrez peut-être utiliser l'option --baud si la ligne série fonctionne à une vitesse autre que 9600 bauds.) C'est-à-dire "gdb PROGRAMME-CIBLE", ou "gdb --baud BAUDS PROGRAMME-CIBLE". Après cela, la seule nouvelle commande que vous ayez besoin de connaître est "target remote" (ou "target extended-remote"). Son argument est soit un nom de périphérique (généralement un périphérique série, comme /dev/ttyb), soit un descripteur "HÔTE:PORT". Par exemple

: 
(gdb) target remote
/dev/ttyb

communique avec le serveur via la ligne série /dev/ttyb, et

: 
(gdb) target remote la-cible:
2345

communique via une connexion TCP avec le port 2345 sur l'hôte `la-cible', où vous avez précédemment démarré gdbserver avec le même numéro de port. Notez que pour les connexions TCP, vous devez démarrer gdbserver avant d'utiliser la commande `target remote', sinon vous pourriez obtenir une erreur ressemblant à `Connection

refused'.

gdbserver peut également déboguer plusieurs inférieurs à la fois, comme décrit dans le manuel de GDB au nœud "Inferiors Connections and Programs" -- commande shell "info -f gdb -n 'Inferiors Connections and Programs'". Dans ce cas, utilisez la variante de commande GDB "extended-rem

ote" : 
(gdb) target extended-remote la-cible:
2345

L'option gdbserver --multi peut être utili

sée ou non
dans ce cas.

OPTION

S

Il existe trois modes différents pour invoquer gdbserv

er :
  • Déboguer un programme spécifique désigné par son nom de programme : 
    gdbserver <comm> <prog> [<args>
    ...]

    Le paramètre comm spécifie comment le serveur doit communiquer avec GDB ; il s'agit soit d'un nom de périphérique (pour utiliser une ligne série), soit d'un numéro de port TCP (":1234"), soit de "-" ou "stdio" pour utiliser stdin/stdout de "gdbserver". Spécifiez le nom du programme à déboguer dans prog. Tous les arguments restants seront transmis au programme verbatim. Lorsque le programme se termine, GDB fermera la connexion et "gdbserver"

    se term
    • inera.
  • Déboguer un programme spécifique en spécifiant l'identifiant de processus d'un programme en cours d'exécution : 
    gdbserver --attach <comm>
    <pid>

    Le paramètre comm est tel que décrit ci-dessus. Fournissez l'identifiant de processus d'un programme en cours d'exécution dans pid ; GDB fera le reste. Comme avec le mode précédent, lorsque le processus pid se termine, GDB fermera la connexion et "gdbserver"

    se term
    • inera.
  • Mode multi-processus -- déboguer plus d'un programme/processus : 
    gdbserver --multi
    <comm>

    Dans ce mode, GDB peut indiquer à gdbserver quelles commandes exécuter. Contrairement aux 2 autres modes, GDB ne ferme

    ra pas la connexion lorsqu'un processus déb

plusieurs processus dans la même session.

Indique à "gdbserver" d'afficher des informations d'état supplémentaires sur le processus de débogage. Cette option est destinée au développement de "gdbserver" et aux rapports de bogue destinés aux développeurs.

Chaque option est le nom d'un composant pour lequel le débogage doit être activé. La liste des options possibles est all, threads, event-loop, remote. L'option spéciale all active tous les composants. cible> gdbserver --debug=all,
-event-loop
