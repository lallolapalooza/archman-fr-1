DESCRIPTIO

N

ld combine un certain nombre de fichiers objet et d'archives, relocalise leurs données et résout les références de symboles. Habituellement, la dernière étape de la compilation d'un programme consiste à exécuter ld

.

ld accepte les fichiers écrits dans le Langage de Commande de l'Éditeur de Liens, une sur-ensemble de la syntaxe du Langage de Commande de l'Éditeur de Liens d'AT&T, afin de fournir un contrôle explicite et total sur le processus de

liaison.

Cette page de manuel ne décrit pas le langage de commande ; voir l'entrée ld dans "info" pour tous les détails sur le langage de commande et sur les autres aspects de l'éditeur de liens

GNU.

Cette version de ld utilise les bibliothèques BFD à usage général pour manipuler les fichiers objet. Cela permet à ld de lire, combiner et écrire des fichiers objet dans de nombreux formats différents---par exemple COFF ou "a.out". Différents formats peuvent être liés ensemble pour produire n'importe quel type de fichier objet

disponible.

En plus de sa flexibilité, l'éditeur de liens GNU est plus utile que les autres éditeurs de liens pour fournir des informations de diagnostic. Beaucoup d'éditeurs de liens abandonnent l'exécution immédiatement lorsqu'ils rencontrent une erreur ; chaque fois que c'est possible, ld continue l'exécution, vous permettant d'identifier d'autres erreurs (ou, dans certains cas, d'obtenir un fichier de sortie malgré l'erreur)

.

L'éditeur de liens GNU ld est conçu pour couvrir un large éventail de situations et pour être aussi compatible que possible avec

les autres éditeurs de liens. En conséquence, vous
avez de nombreux choix pour contrôler son comportement.

OPTION

S

L'éditeur de liens prend en charge une pléthore d'options de ligne de commande, mais en pratique, peu d'entre elles sont utilisées dans un contexte particulier. Par exemple, une utilisation fréquente de ld est de lier des fichiers objet Unix standard sur un système Unix standard et pris en charge. Sur un tel système, pour lier un fichier "hello.

o" : 
ld -o <sortie> /lib/crt0.o hello.o
-lc

Cela indique à ld de produire un fichier appelé sortie comme résultat de la liaison du fichier "/lib/crt0.o" avec "hello.o" et la bibliothèque "libc.a", qui proviendra des répertoires de recherche standard. (Voir la discussion de l'option -l ci-dessous.

)

Certaines des options de ligne de commande pour ld peuvent être spécifiées à n'importe quel point de la ligne de commande. Cependant, les options qui se réfèrent à des fichiers, telles que -l ou -T, provoquent la lecture du fichier au point où l'option apparaît dans la ligne de commande, par rapport aux fichiers objet et aux autres options de fichier. Répéter des options non-fichiers avec un argument différent n'aura soit aucun effet supplémentaire, soit annulera les occurrences précédentes (celles situées plus à gauche sur la ligne de commande) de cette option. Les options qui peuvent être significativement spécifiées plus d'une fois sont notées dans les descriptions

ci-dessous.

Les arguments non-options sont des fichiers objet ou des archives qui doivent être liés ensemble. Ils peuvent suivre, précéder ou être mélangés avec les options de ligne de commande, sauf qu'un argument de fichier objet ne peut pas être placé entre une option et son

argument.

Habituellement, l'éditeur de liens est invoqué avec au moins un fichier objet, mais vous pouvez spécifier d'autres formes de fichiers d'entrée binaires en utilisant -l, -R et le langage de commande des scripts. Si aucun fichier d'entrée binaire n'est spécifié du tout, l'éditeur de liens ne produit aucune sortie et émet le message No input f

iles.

Si l'éditeur de liens ne peut pas reconnaître le format d'un fichier objet, il supposera qu'il s'agit d'un script de l'éditeur de liens. Un script spécifié de cette manière augmente le script principal de l'éditeur de liens utilisé pour la liaison (soit le script par défaut de l'éditeur de liens, soit celui spécifié en utilisant -T). Cette fonctionnalité permet à l'éditeur de liens de lier avec un fichier qui semble être un objet ou une archive, mais qui définit en fait simplement certaines valeurs de symboles, ou utilise "INPUT" ou "GROUP" pour charger d'autres objets. Spécifier un script de cette manière augmente simplement le script principal de l'éditeur de liens, avec les commandes supplémentaires placées après le script principal ; utilisez l'option -T pour remplacer entièrement le script par défaut de l'éditeur de liens, mais notez l'effet de la commande "INSERT"

.

Pour les options dont les noms sont d'une seule lettre, les arguments de l'option doivent soit suivre la lettre de l'option sans espace blanc intermédiaire, soit être donnés comme des arguments séparés immédiatement après l'option qui les

requiert.

Pour les options dont les noms sont de plusieurs lettres, un seul tiret ou deux peuvent précéder le nom de l'option ; par exemple, -trace-symbol et --trace-symbol sont équivalents. Notez---il y a une exception à cette règle. Les options à lettres multiples qui commencent par un 'o' minuscule ne peuvent être précédées que par deux tirets. Cela est fait pour réduire la confusion avec l'option -o. Ainsi, par exemple, -omagic définit le nom du fichier de sortie à magic alors que --omagic définit l'indicateur NMAGIC sur la

sortie.

Les arguments des options à lettres multiples doivent soit être séparés du nom de l'option par un signe égal, soit être donnés comme des arguments séparés immédiatement après l'option qui les requiert. Par exemple, --trace-symbol foo et --trace-symbol=foo sont équivalents. Les abréviations uniques des noms des options à lettres multiples sont

acceptées.

Notez---si l'éditeur de liens est invoqué indirectement, via un pilote de compilateur (par exemple gcc), alors toutes les options de ligne de commande de l'éditeur de liens doivent être préfixées par -Wl, (ou ce qui est approprié pour le pilote de compilateur particulier) comme ceci

: 
gcc -Wl,--start-group foo.o bar.o -Wl,
--end-group

C'est important, car sinon le programme pilote de compilateur peut silencieusement abandonner les options de l'éditeur de liens, entraînant une mauvaise liaison. De la confusion peut également survenir lors du passage d'options nécessitant des valeurs via un pilote, car l'utilisation d'un espace entre l'option et l'argument agit comme un séparateur et fait que le pilote ne passe que l'option à l'éditeur de liens et l'argument au compilateur. Dans ce cas, il est plus simple d'utiliser les formes jointes des options à une seule et à plusieurs lettres, telles que

: 
gcc foo.o bar.o -Wl,-eENTRY -Wl,-Map=a.

L'utilisation de 'auto-import' fonctionnera généralement "comme par magie" - mais parfois vous pouvez voir ce message :

"la variable '<var>' ne peut pas être auto-importée. Veuillez lire la documentation de "--enable-auto-import" de ld pour plus de détails."

Ce message se produit lorsque certaines (sous-)expressions accèdent à une adresse donnée ultimement par la somme de deux constantes (les tables d'importation Win32 n'en autorisent qu'une). Les cas où cela peut se produire incluent les accès aux champs membres de variables struct importées d'une DLL, ainsi que l'utilisation d'un indice constant dans une variable tableau importée d'une DLL. Tout tableau multi-mots (tableaux, structures, long long, etc.) peut déclencher cette condition d'erreur. Cependant, quel que soit le type de données exact de la variable exportée fautive, ld la détectera toujours, émettra l'avertissement et s'arrêtera.

Il existe plusieurs façons de résoudre cette difficulté, quel que soit le type de données de la variable exportée :

Une façon est d'utiliser l'option --enable-runtime-pseudo-reloc. Cela laisse la tâche d'ajuster les références dans votre code client à l'environnement d'exécution, donc cette méthode ne fonctionne que lorsque l'environnement d'exécution prend en charge cette fonctionnalité.

Une deuxième solution consiste à forcer l'une des 'constantes' à être une variable - c'est-à-dire inconnue et non optimisable au moment de la compilation. Pour les tableaux, il y a deux possibilités : a) rendre l'indexé (l'adresse du tableau) une variable, ou b) rendre l'indice 'constant' une variable. Ainsi :

extern type extern_array[];
extern_array[1] -->
   { volatile type *t=extern_array; t[1] }

ou

extern type extern_array[];
extern_array[1] -->
   { volatile int t=1; extern_array[t] }

Pour les structures (et la plupart des autres types de données multi-mots), la seule option est de rendre la structure elle-même (ou le long long, ou le...) variable :

extern struct s extern_struct;
extern_struct.field -->
   { volatile struct s *t=&extern_struct; t->field }

ou

extern long long extern_ll;
extern_ll -->
  { volatile long long * local_ll=&extern_ll; *local_ll }

Une troisième méthode pour gérer cette difficulté est d'abandonner 'auto-import' pour le symbole fautif et de le marquer avec "__declspec(dllimport)". Cependant, en pratique, cela nécessite d'utiliser des #defines au moment de la compilation pour indiquer si vous construisez une DLL, si vous construisez du code client qui se liera à la DLL, ou si vous construisez/liez simplement à une bibliothèque statique. --omagic

ENVIRONNEMENT

Vous pouvez modifier le comportement de ld avec les variables d'environnement "GNUTARGET", "LDEMULATION" et "COLLECT_NO_DEMANGLE".

"GNUTARGET" détermine le format objet des fichiers d'entrée si vous n'utilisez pas -b (ou son synonyme --format). Sa valeur doit être l'un des noms BFD pour un format d'entrée. S'il n'y a pas de "GNUTARGET" dans l'environnement, ld utilise le format naturel de la cible. Si "GNUTARGET" est défini sur "default", BFD tente de découvrir le format d'entrée en examinant les fichiers binaires d'entrée; cette méthode réussit souvent, mais il y a des ambiguïtés potentielles, car il n'y a pas de méthode pour garantir que le nombre magique utilisé pour spécifier les formats de fichier objet soit unique. Cependant, la procédure de configuration de BFD sur chaque système place le format conventionnel pour ce système en premier dans la liste de recherche, de sorte que les ambiguïtés sont résolues en faveur de la convention.

"LDEMULATION" détermine l'émulation par défaut si vous n'utilisez pas l'option -m. L'émulation peut affecter divers aspects du comportement de l'éditeur de liens, en particulier le script d'édition de liens par défaut. Vous pouvez lister les émulations disponibles avec les options --verbose ou -V. Si l'option -m n'est pas utilisée et que la variable d'environnement "LDEMULATION" n'est pas définie, l'émulation par défaut dépend de la manière dont l'éditeur de liens a été configuré.

Normalement, l'éditeur de liens désémantisera les symboles par défaut. Cependant, si "COLLECT_NO_DEMANGLE" est défini dans l'environnement, alors il ne désémantisera pas les symboles par défaut. Cette variable d'environnement est utilisée de manière similaire par le programme wrapper de l'éditeur de liens "gcc". Le défaut peut être outrepassé par les options --demangle et --no-demangle.
