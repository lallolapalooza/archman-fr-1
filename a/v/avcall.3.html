DESCRIPTIO

N

Cet ensemble de macros construit une liste d'arguments pour une fonction C et appelle la fonction avec celle-ci. Il réduit considérablement la quantité de code de « colle » nécessaire pour les analyseurs, les débogueurs, les interprètes intégrés, les extensions C aux programmes d'application et d'autres situations où des collections de fonctions doivent être appelées avec des listes d'arguments fournis de

l'extérieur.

Les conventions d'appel de fonctions diffèrent considérablement d'une machine à l'autre et avcall tente de fournir un certain degré d'isolation vis-à-vis de ces dépendances

d'architecture.

L'interface est comme stdarg(3) à l'envers. Toutes les macros renvoient 0 en cas de succès, < 0 en cas d'échec (par ex., débordement de la liste d'arguments ou type non pris en charge)

.

NOTE

S

(1) Les fonctions dont la première déclaration est au style Kernighan & Ritchie (c'est-à-dire sans liste d'arguments typée) DOIVENT utiliser les promotions d'expressions C K&R par défaut (char et short vers int, float vers double) qu'elles soient compilées par un compilateur K&R ou ANSI, car les vrais types des arguments peuvent ne pas être connus au point d'appel. De telles fonctions convertissent généralement leurs arguments vers les types déclarés à l'entrée de la fonction. (En fait, la seule façon de passer un vrai char, short ou float en C K&R est par un cast explicite : func((char)c,(float)f) ). De même, certains compilateurs K&R (comme Sun cc sur sparc) renvoient en fait un float comme un

double.

Par conséquent, pour les arguments de fonctions déclarées au style K&R, vous devriez utiliser av_int() et av_double() plutôt que av_char(), av_short() ou av_float(). Si vous utilisez un compilateur K&R, les fichiers d'en-tête avcall peuvent être capables de détecter cela et de définir av_float(), etc, de manière appropriée, mais avec un compilateur ANSI il n'y a aucun moyen pour avcall de savoir comment une fonction a été déclarée, donc vous devez corriger les types des arguments

vous-même.

(2) Les arguments de type explicites des macros av_struct() et av_ptr() sont typiquement utilisés pour calculer la taille, l'alignement et les conventions de passage. Cela peut ne pas être suffisant pour certaines machines avec un traitement inhabituel des structures et des pointeurs : dans ce cas, des macros supplémentaires av_start_type() et av_type() peuvent être

définies.

(3) Les macros av_start_longlong(), av_start_ulonglong(), av_longlong() et av_ulonglong() ne fonctionnent que si le compilateur C dispose d'un type long long 64-bit integer

fonctionnel.

(4) Les types de structure utilisés dans av_start_struct() et av_struct() ne doivent contenir que des champs int, long, long long ou pointeur (signés ou non). Les types de structu

re contenant des champs char, short, float, double (signés
ou non) ou d'autres structures ne sont pas pris en charge.

BOGUE

S

Les implémentations actuelles ont été testées sur une sélection de cas courants mais il y a probablement encore de nombreux

bogues.

Il y a généralement des limites intégrées sur la taille de la liste d'arguments, qui peuvent également inclure la taille de toute argument de

structure.

La décision de savoir si une structure doit être renvoyée dans des registres ou en mémoire ne considère que la taille et l'alignement de la structure. C'est imprécis : par exemple, gcc sur m68k-next renvoie struct { char a,b,c; } dans des registres et struct { char a[3]; } en mémoire, bien que les deux

types aient la même tai
lle et le même alignement.

NON-BOGUE

S

Toutes les informations sont passées dans les registres du CPU et la pile. Le paquet avcall est donc sûr pour

les environneme
nts multithread.

PORTAGE

D'AVCALL

Les ports, les corrections de bogues et les suggestions sont les bienvenus. Les macros nécessaires pour pousser les arguments sont assez sales, mais il semble possible de porter avcall sur une gamme de machines. Les ports vers des machines non standard ou non 32 bits sont particulièrement bienvenus afin que nous puissions trier l'interface avant qu'il ne soit trop

tard.

Des informations sur les conventions de passage d'arguments peuvent être trouvées dans les sources de gcc, fichier gcc-2.6.3/config/cpu/cpu.h, section "Stack layout; function entry, exit and calling.

"

Une partie de ce code sale est généralement gérée par une routine de colle au niveau C ou assembleur qui pousse réellement les arguments, appelle la fonction et déballe toute valeur de retour. Elle est appelée avcall_call(). Une version assembleur précompilée est également disponible pour les personnes sans gcc. La routine devrait idéalement avoir des drapeaux pour les conventions de passage des autrescompilateurs

.

Beaucoup des routines actuelles gaspillent beaucoup d'espace de pile

et font généralement des choses étranges aux trames de pile - un
peu plus de code assembleur aiderait probablement beaucoup ici.
