gcovest un programme de test de couverture. Utilisez-le en conjonction avec GCC pour analyser vos programmes afin de créer du code plus efficace et plus rapide et pour découvrir les parties non testées de votre programme. Vous pouvez utilisergcov comme un outil de profilage pour aider à découvrir où vos efforts d'optimisation auront le plus d'effet sur votre code. Vous pouvez également utiliser
gcoven conjonction avec l'autre outil de profilage,gprof
, pour évaluer quelles parties de votre code utilisent le plus grand temps de calcul.Les outils de profilage vous aident à analyser les performances de votre code. En utilisant un profileur tel quegcov ou
gprof, vous pouvez obtenir certaines statistiques de performance de base, telles que :la fréquence d'exécution de chaque ligne de code
quelles lignes de code sont réellement exécutéesle temps de calcul utilisé par chaque section de codeUne fois que vous savez comment votre code fonctionne lorsqu'il est compilé, vous pouvez examiner chaque module pour voir quels modules devraient être optimisés. gcov vous aide à déterminer où travailler sur l'optimisation.
Les développeurs de logiciels utilisent également le test de couverture en conjonction avec des suites de tests, pour s'assurer que le logiciel est réellement suffisamment bon pour une publication. Les suites de tests peuvent vérifier qu'un programme fonctionne comme prévu ; un programme de couverture teste pour voir dans quelle mesure le programme est exercé par la suite de tests. Les développeurs peuvent alors déterminer quels types de cas de test doivent être ajoutés aux suites de tests pour créer à la fois de meilleurs tests et un meilleur produit final.Vous devriez compiler votre code sans optimisation si vous prévoyez d'utilisergcov
car l'optimisation, en combinant certaines lignes de code en une fonction, peut ne pas vous donner autant d'informations que vous en avez besoin pour rechercher les « points chauds » où le code utilise beaucoup de temps de calcul. De même, parce quegcovaccumule les statistiques par ligne (à la plus faible résolution), il fonctionne le mieux avec un style de programmation qui place une seule instruction sur chaque ligne. Si vous utilisez des macros compliquées qui s'étendent en boucles ou en autres structures de contrôle, les statistiques sont moins utiles---elles ne rapportent que la ligne où l'appel de macro apparaît. Si vos macros complexes se comportent comme des fonctions, vous pouvez les remplacer par des fonctions en ligne pour résoudre ce problème.

-d
--display-progress
Affiche la progression sur la sortie standard.
-f
--function-summaries
Produit des résumés pour chaque fonction en plus du résumé au niveau du fichier.
--include regex
Inclut les fonctions correspondant à regex. Cette option fait que gcov ne rapporte que sur les fonctions qui correspondent à l'expression régulière étendue regex. Ce drapeau peut être combiné avec --exclude. Si une fonction correspond à la fois aux inclusions et aux exclusions, la dernière inclusion/exclusion s'applique. Par défaut gcov rapporte sur toutes les fonctions, mais si un --include est utilisé, seules les fonctions correspondant à l'inclusion seront rapportées.
--exclude regex
Exclut les fonctions correspondant à regex. Cette option fait que gcov ne rapporte pas sur les fonctions qui correspondent à l'expression régulière étendue regex. Ce drapeau peut être combiné avec --include. Si une fonction correspond à la fois aux inclusions et aux exclusions, la dernière inclusion/exclusion s'applique. Par défaut gcov rapporte sur toutes les fonctions, et si --exclude est utilisé, les fonctions qui y correspondent seront omises.
-h
--help
Affiche l'aide sur l'utilisation de gcov (sur la sortie standard) et se termine sans effectuer aucun traitement supplémentaire.
-j
--json-format
Produit le fichier gcov dans un format intermédiaire JSON facile à analyser qui ne nécessite pas le code source pour sa génération. Le fichier JSON est compressé avec l'algorithme de compression gzip et les fichiers ont l'extension .gcov.json.gz .

La structure du JSON est la suivante :

{
  "current_working_directory": "foo/bar",
  "data_file": "a.out",
  "format_version": "2",
  "gcc_version": "11.1.1 20210510"
  "files": ["$file"]
}

Les champs de l'élément racine ont la sémantique suivante :

  • current_working_directory: répertoire de travail dans lequel l'unité de compilation a été compilée
  • data_file: nom du fichier de données (GCDA)
  • format_version: version sémantique du format

    Changements dans la version 2:

*
calls: des informations sur les appels de fonctions sont ajoutées
*
gcc_version: version du compilateur GCC

Chaque file a la forme suivante :

{
  "file": "a.c",
  "functions": ["$function"],
  "lines": ["$line"]
}

Les champs de l'élément file ont la sémantique suivante :

*
file_name: nom du fichier source

Chaque function a la forme suivante :

{
  "blocks": 2,
  "blocks_executed": 2,
  "demangled_name": "foo",
  "end_column": 1,
  "end_line": 4,
  "execution_count": 1,
  "name": "foo",
  "start_column": 5,
  "start_line": 1
}

Les champs de l'élément function ont la sémantique suivante :

  • blocks: nombre de blocs dans la fonction
  • blocks_executed: nombre de blocs exécutés de la fonction
  • demangled_name: nom dé-manglé de la fonction
  • end_column: colonne dans le fichier source où la fonction se termine
  • end_line: ligne dans le fichier source où la fonction se termine
  • execution_count: nombre d'exécutions de la fonction
  • name: nom de la fonction
  • start_column: colonne dans le fichier source où la fonction commence
  • start_line: ligne dans le fichier source où la fonction commence

Notez que les numéros de ligne et de colonne commencent à 1. Dans l'implémentation actuelle, start_line et start_column n'incluent pas les paramètres de gabarit ni le type de retour initial, mais cela sera probablement corrigé à l'avenir.

Chaque line a la forme suivante :

{
  "block_ids": ["$block_id"],
  "branches": ["$branch"],
  "calls": ["$call"],
  "count": 2,
  "conditions": ["$condition"],
  "line_number": 15,
  "unexecuted_block": false,
  "function_name": "foo",
}

Les branches et les appels ne sont présents qu'avec l'option -b . Les champs de l'élément line ont la sémantique suivante :

  • block_ids: identifiants des blocs de base appartenant à la ligne
  • count: nombre d'exécutions de la ligne
  • line_number: numéro de ligne
  • unexecuted_block: indique si la ligne contient un bloc non exécuté (toutes les instructions de la ligne ne sont pas exécutées)
  • function_name: nom de la fonction à laquelle cette line appartient (pour une ligne avec des instructions inlinées, peut ne pas être défini)

Chaque branch a la forme suivante :

{
  "count": 11,
  "destination_block_id": 17,
  "fallthrough": true,
  "source_block_id": 13,
  "throw": false
}

Les champs de l'élément branch ont la sémantique suivante :

  • count: nombre d'exécutions de la branche
  • fallthrough: vrai lorsque la branche est une branche de passage direct
  • throw: vrai lorsque la branche est une branche exceptionnelle
  • isource_block_id: identifiant du bloc de base où cette branche se produit
  • destination_block_id: identifiant du bloc de base vers lequel cette branche saute

Chaque call a la forme suivante :

{
  "destination_block_id": 1,
  "returned": 11,
  "source_block_id": 13
}

Les champs de l'élément call ont la sémantique suivante :

  • returned: nombre de fois où un appel de fonction est retourné (le nombre d'appels est égal à line::count)
  • isource_block_id: identifiant du bloc de base où cet appel se produit
  • destination_block_id: identifiant du bloc de base où cet appel se poursuit après le retour

Chaque condition a la forme suivante :

{
  "count": 4,
  "covered": 2,
  "not_covered_false": [],
  "not_covered_true": [0, 1],
}

Les champs de l'élément condition ont la sémantique suivante :

  • count: nombre de résultats de condition dans cette expression
  • covered: nombre de résultats de condition couverts dans cette expression
  • not_covered_true: termes, par index, non vus comme vrais dans cette expression
  • not_covered_false: termes, par index, non vus comme faux dans cette expression

--hash-filenames
Lors de l'utilisation de --preserve-paths, gcov utilise le chemin complet des fichiers source pour créer un nom de fichier de sortie. Cela peut entraîner des noms de fichiers longs qui peuvent dépasser les limites du système de fichiers. Cette option crée des noms de la forme source-file##md5.gcov, où le composant source-file est la partie finale du nom de fichier et le composant md5 est calculé à partir du nom complet qui aurait été utilisé autrement. L'option est une alternative à --preserve-paths sur les systèmes qui ont une limite de système de fichiers.

gcov doit être exécuté avec le répertoire courant identique à celui dans lequel vous avez appelé le compilateur. Sinon, il ne pourra pas localiser les fichiers source. gcov produit des fichiers nommés mangledname.gcov dans le répertoire courant. Ceux-ci contiennent les informations de couverture du fichier source auquel ils correspondent. Un fichier .gcov est produit pour chaque fichier source (ou d'en-tête) contenant du code, qui a été compilé pour produire les fichiers de données. La partie mangledname du nom du fichier de sortie est généralement simplement le nom du fichier source, mais peut être quelque chose de plus compliqué si les options -l ou -p sont données. Se référer à ces options pour les détails.

Si vous invoquez gcov avec plusieurs fichiers d'entrée, les contributions de chaque fichier d'entrée sont additionnées. Typiquement, vous l'invoqueriez avec la même liste de fichiers que le lien final de votre exécutable.

Les fichiers .gcov contiennent des champs séparés par des : ainsi que le code source du programme. Le format est

<nombre_executions>:<numero_ligne>:<texte_ligne_source>

Des informations supplémentaires sur les blocs peuvent succéder à chaque ligne, lorsque demandées par une option de ligne de commande. Le nombre_executions est - pour les lignes ne contenant pas de code. Les lignes non exécutées sont marquées ##### ou =====, selon qu'elles sont atteignables par des chemins non exceptionnels ou seulement par des chemins exceptionnels tels que les gestionnaires d'exceptions C++, respectivement. Avec l'option -a, les blocs non exécutés sont marqués $$$$$ ou %%%%%, selon qu'un bloc de base est atteignable via des chemins non exceptionnels ou exceptionnels. Les blocs de base exécutés ayant une instruction avec un nombre_executions de zéro se terminent par le caractère * et sont colorés en magenta avec l'option -k. Cette fonctionnalité n'est pas prise en charge dans Ada.

Notez que GCC peut supprimer complètement les corps des fonctions qui ne sont pas nécessaires - par exemple si elles sont inline partout. Ces fonctions sont marquées avec -, ce qui peut être déroutant. Utilisez les options -fkeep-inline-functions et -fkeep-static-functions pour conserver ces fonctions et permettre à gcov d'afficher correctement leur nombre_executions.

Certaines lignes d'information au début ont un numero_ligne de zéro. Ces lignes d'en-tête sont de la forme

-:0:<tag>:<valeur>

L'ordre et le nombre de ces lignes d'en-tête seront augmentés au fur et à mesure que le développement de gcov progresse --- ne comptez pas sur leur conservation inchangée. Utilisez tag pour localiser une ligne d'en-tête particulière.

Les informations supplémentaires sur les blocs sont de la forme

<tag> <information>

L'information est lisible par l'homme, mais conçue pour être suffisamment simple pour être également analysée par machine.

Lors de l'affichage des pourcentages, 0% et 100% ne sont affichés que lorsque les valeurs sont exactement 0% et 100% respectivement. Les autres valeurs qui seraient conventionnellement arrondies à 0% ou 100% sont au lieu de cela affichées comme la valeur non limite la plus proche.

Lorsque vous utilisez gcov, vous devez d'abord compiler votre programme avec une option spéciale de GCC --coverage. Cela indique au compilateur de générer des informations supplémentaires nécessaires à gcov (essentiellement un graphe de flot du programme) et inclut également du code supplémentaire dans les fichiers objet pour générer les informations de profilage supplémentaires nécessaires à gcov. Ces fichiers supplémentaires sont placés dans le répertoire où se trouve le fichier objet.

L'exécution du programme générera une sortie de profilage. Pour chaque fichier source compilé avec -fprofile-arcs, un fichier .gcda accompagnateur sera placé dans le répertoire du fichier objet.

L'exécution de gcov avec les noms de fichiers source de votre programme comme arguments produira maintenant un listing du code avec la fréquence d'exécution pour chaque ligne. Par exemple, si votre programme s'appelle tmp.cpp, voici ce que vous voyez lorsque vous utilisez la fonctionnalité de base de gcov:

$ g++ --coverage tmp.cpp -c
$ g++ --coverage tmp.o
$ a.out
$ gcov tmp.cpp -m
Fichier 'tmp.cpp'
Lignes exécutées : 92.86% sur 14

Les compteurs d'exécution sont cumulatifs. Si le programme d'exemple était exécuté à nouveau sans supprimer le fichier .gcda [[67]], le compteur pour le nombre de fois où chaque ligne du source a été exécutée sera ajouté aux résultats de la ou des exécutions précédentes. C'est potentiellement utile de plusieurs manières. Par exemple, cela pourrait être utilisé pour accumuler des données sur plusieurs exécutions du programme dans le cadre d'une suite de vérification de tests, ou pour fournir des informations à long terme plus précises sur un grand nombre d'exécutions du programme.

Les données dans les .gcda fichiers sont enregistrées juste avant la sortie du programme. Pour chaque fichier source compilé avec -fprofile-arcs, le code de profilage essaie d'abord de lire un .gcda fichier existant ; si le fichier ne correspond pas à l'exécutable (nombre différent de comptages de blocs de base), il ignorera le contenu du fichier. Il ajoute ensuite les nouveaux comptages d'exécution et écrit enfin les données dans le fichier.

Utilisation de gcov avec l'optimisation de GCC

Si vous prévoyez d'utiliser gcov pour aider à optimiser votre code, vous devez d'abord compiler votre programme avec une option GCC spéciale --coverage. En dehors de cela, vous pouvez utiliser n'importe quelles autres options GCC ; mais si vous voulez prouver que chaque ligne de votre programme a été exécutée, vous ne devriez pas compiler avec l'optimisation en même temps. Sur certaines machines, l'optimiseur peut éliminer certaines lignes de code simples en les combinant avec d'autres lignes. Par exemple, du code comme ceci :

if (a != b)
  c = 1;
else
  c = 0;

peut être compilé en une seule instruction sur certaines machines. Dans ce cas, il n'y a aucun moyen pour gcov de calculer des comptages d'exécution séparés pour chaque ligne car il n'y a pas de code séparé pour chaque ligne. Par conséquent, la sortie gcov ressemble à ceci si vous avez compilé le programme avec l'optimisation :

100:   12:if (a != b)
100:   13:  c = 1;
100:   14:else
100:   15:  c = 0;

La sortie montre que ce bloc de code, combiné par l'optimisation, s'est exécuté 100 fois. En un sens, ce résultat est correct, car il n'y avait qu'une seule instruction représentant toutes ces quatre lignes. Cependant, la sortie n'indique pas combien de fois le résultat était 0 et combien de fois le résultat était 1.

Les fonctions enlinéables peuvent créer des comptages de lignes inattendus. Les comptages de lignes sont affichés pour le code source de la fonction enlinéable, mais ce qui est affiché dépend de l'endroit où la fonction est inlinée, ou si elle n'est pas inlinée du tout.

Si la fonction n'est pas inlinée, le compilateur doit émettre une copie hors ligne de la fonction, dans tout fichier objet qui en a besoin. Si fileA.o et fileB.o contiennent tous deux des corps hors ligne d'une fonction enlinéable particulière, ils contiendront aussi tous deux des comptages de couverture pour cette fonction. Quand fileA.o et fileB.o sont liés ensemble, l'éditeur de liens sélectionnera, sur de nombreux systèmes, l'un de ces corps hors ligne pour tous les appels à cette fonction, et supprimera ou ignorera l'autre. Malheureusement, il ne supprimera pas les compteurs de couverture pour le corps de fonction inutilisé. Par conséquent, lorsque l'instrumentation est activée, toutes les utilisations de cette fonction sauf une montreront des comptages à zéro.

Si la fonction est inlinée à plusieurs endroits, la structure de blocs à chaque emplacement pourrait ne pas être la même. Par exemple, une condition pourrait maintenant être calculable à la compilation dans certaines instances. Parce que la couverture de toutes les utilisations de la fonction enlinée sera affichée pour les mêmes lignes de source, les comptages de lignes eux-mêmes pourraient sembler incohérents.

Les applications à longue durée d'exécution peuvent utiliser les fonctionnalités "__gcov_reset" et "__gcov_dump" pour restreindre la collecte de profil à la région du programme d'intérêt. Appeler "__gcov_reset(void)" effacera tous les compteurs de profil d'exécution à zéro, et appeler "__gcov_dump(void)" fera en sorte que le profil collecté à ce moment soit vidé dans les fichiers de sortie .gcda . Les applications instrumentées utilisent un destructeur statique avec la priorité 99 pour invoquer la fonction "__gcov_dump" . Ainsi "__gcov_dump" est exécuté après tous les destructeurs statiques définis par l'utilisateur, ainsi que les gestionnaires enregistrés avec "atexit".

Si un exécutable charge un objet partagé dynamique via la fonctionnalité dlopen, l'option -Wl,--dynamic-list-data est nécessaire pour vider toutes les données de profil.

La bibliothèque d'exécution de profilage signale diverses erreurs liées à la manipulation du profil et à l'enregistrement du profil. Les erreurs sont imprimées dans la sortie d'erreur standard ou dans le fichier GCOV_ERROR_FILE , si la variable d'environnement est utilisée. Afin de se terminer immédiatement après qu'une erreur se produise, définissez la variable d'environnement GCOV_EXIT_AT_ERROR . Cela peut aider les utilisateurs à trouver des conflits de profil qui conduisent à un profil trompeur.
