DESCRIPTIO

N

ld combine un certain nombre de fichiers objets et d'archives, relocalise leurs données et résout les références de symboles. Habituellement, la dernière étape de la compilation d'un programme consiste à exécuter ld

.

ld accepte les fichiers de langage de commande de liaison écrits dans un sur-ensemble de la syntaxe du langage de commande de l'éditeur de liens d'AT&T, afin de fournir un contrôle explicite et total sur le processus de

liaison.

Cette page manuel ne décrit pas le langage de commande ; voir l'entrée ld dans "info" pour tous les détails sur le langage de commande et sur les autres aspects de l'éditeur de liens

GNU.

Cette version de ld utilise les bibliothèques BFD à usage général pour manipuler les fichiers objets. Cela permet à ld de lire, combiner et écrire des fichiers objets dans de nombreux formats différents---par exemple COFF ou "a.out". Différents formats peuvent être liés ensemble pour produire n'importe quel type de fichier objet

disponible.

En dehors de sa flexibilité, l'éditeur de liens GNU est plus utile que les autres éditeurs de liens pour fournir des informations de diagnostic. Beaucoup d'éditeurs de liens abandonnent l'exécution immédiatement lorsqu'ils rencontrent une erreur ; chaque fois que c'est possible, ld continue l'exécution, vous permettant d'identifier d'autres erreurs (ou, dans certains cas, d'obtenir un fichier de sortie malgré l'erreur)

.

L'éditeur de liens GNU ld est conçu pour couvrir un large éventail de situations et pour être aussi compatible que possible avec

les autres éditeurs de liens. En conséquence, vous av
ez de nombreux choix pour contrôler son comportement.

OPTION

S

L'éditeur de liens prend en charge une pléthore d'options de ligne de commande, mais en pratique, peu d'entre elles sont utilisées dans un contexte particulier. Par exemple, une utilisation fréquente de ld est de lier des fichiers objets Unix standard sur un système Unix standard et pris en charge. Sur un tel système, pour lier un fichier "hello.

o" : 
ld -o <sortie> /lib/crt0.o hello.o
-lc

Cela indique à ld de produire un fichier appelé sortie comme résultat de la liaison du fichier "/lib/crt0.o" avec "hello.o" et la bibliothèque "libc.a", qui proviendra des répertoires de recherche standard. (Voir la discussion de l'option -l ci-dessous.

)

Certaines des options de ligne de commande de ld peuvent être spécifiées à n'importe quel point de la ligne de commande. Cependant, les options qui se réfèrent à des fichiers, telles que -l ou -T, provoquent la lecture du fichier au point où l'option apparaît dans la ligne de commande, par rapport aux fichiers objets et aux autres options de fichier. La répétition d'options non-fichiers avec un argument différent n'aura soit aucun effet supplémentaire, soit remplacera les occurrences précédentes (celles plus à gauche dans la ligne de commande) de cette option. Les options qui peuvent être significativement spécifiées plus d'une fois sont notées dans les descriptions

ci-dessous.

Les arguments non-options sont des fichiers objets ou des archives qui doivent être liés ensemble. Ils peuvent suivre, précéder ou être mélangés avec les options de ligne de commande, sauf qu'un argument de fichier objet ne peut pas être placé entre une option et son

argument.

Habituellement, l'éditeur de liens est invoqué avec au moins un fichier objet, mais vous pouvez spécifier d'autres formes de fichiers d'entrée binaires en utilisant -l, -R et le langage de commande de script. Si aucun fichier d'entrée binaire n'est spécifié du tout, l'éditeur de liens ne produit aucune sortie et émet le message No input f

iles.

Si l'éditeur de liens ne peut pas reconnaître le format d'un fichier objet, il supposera qu'il s'agit d'un script de liaison. Un script spécifié de cette manière augmente le script de liaison principal utilisé pour la liaison (soit le script de liaison par défaut, soit celui spécifié en utilisant -T). Cette fonctionnalité permet à l'éditeur de liens de lier un fichier qui semble être un objet ou une archive, mais qui définit en fait simplement certaines valeurs de symboles, ou utilise "INPUT" ou "GROUP" pour charger d'autres objets. Spécifier un script de cette manière augmente simplement le script de liaison principal, avec les commandes supplémentaires placées après le script principal ; utilisez l'option -T pour remplacer entièrement le script de liaison par défaut, mais notez l'effet de la commande "INSERT"

.

Pour les options dont les noms sont une seule lettre, les arguments de l'option doivent soit suivre la lettre de l'option sans espace intermédiaire, soit être donnés comme arguments séparés immédiatement après l'option qui les

requiert.

Pour les options dont les noms sont de plusieurs lettres, soit un seul tiret soit deux peuvent précéder le nom de l'option ; par exemple, -trace-symbol et --trace-symbol sont équivalents. Notez---il y a une exception à cette règle. Les options à plusieurs lettres qui commencent par un 'o' minuscule ne peuvent être précédées que par deux tirets. Cela est fait pour réduire la confusion avec l'option -o. Ainsi, par exemple -omagic définit le nom du fichier de sortie à magic alors que --omagic définit le drapeau NMAGIC sur la

sortie.

Les arguments des options à plusieurs lettres doivent soit être séparés du nom de l'option par un signe égal, soit être donnés comme arguments séparés immédiatement après l'option qui les requiert. Par exemple, --trace-symbol foo et --trace-symbol=foo sont équivalents. Les abréviations uniques des noms des options à plusieurs lettres sont

acceptées.

Notez---si l'éditeur de liens est invoqué indirectement, via un pilote de compilateur (par ex. gcc), alors toutes les options de ligne de commande de l'éditeur de liens doivent être préfixées par -Wl, (ou ce qui est approprié pour le pilote de compilateur particulier) comme ceci

: 
gcc -Wl,--start-group foo.o bar.o -Wl,
--end-group

C'est important, car sinon le programme pilote de compilateur peut silencieusement abandonner les options de l'éditeur de liens, entraînant une mauvaise liaison. Une confusion peut également survenir lors du passage d'options nécessitant des valeurs via un pilote, car l'utilisation d'un espace entre l'option et l'argument agit comme un séparateur et fait que le pilote ne transmet que l'option à l'éditeur de liens et l'argument au compilateur. Dans ce cas, il est le plus simple d'utiliser les formes jointes des options à une et à plusieurs lettres, telles que

: 
gcc foo.o bar.o -Wl,-eENTRY -Wl,-Map=a.

--section-ordering-file=script
Cette option est utilisée pour augmenter le script de linkeur actuel avec une mappage supplémentaire des sections d'entrée vers les sections de sortie. Ce fichier doit utiliser la même syntaxe pour "SECTIONS" que celle utilisée dans les scripts de linkeur normaux, mais il ne doit rien faire d'autre que de placer les sections d'entrée dans les sections de sortie. @pxref{SECTIONS}

Une seconde contrainte sur le script d'ordonnancement des sections est qu'il ne peut référencer que les sections de sortie qui sont déjà définies par le script de linkeur actuellement utilisé. (C'est-à-dire le script de linkeur par défaut ou un script spécifié sur la ligne de commande). L'avantage du script d'ordonnancement des sections est cependant que les sections d'entrée sont mappées au début des sections de sortie, de sorte qu'elles peuvent garantir l'ordonnancement des sections dans la section de sortie. Par exemple, imaginez que le script de linkeur par défaut ressemble à ceci :

SECTIONS {
  .text : { *(.text.hot) ; *(.text .text.*) }
  .data : { *(.data.big) ; *(.data .data.*) }
  }

Ensuite, si un fichier d'ordonnancement de sections comme celui-ci est utilisé :

.text : { *(.text.first) ; *(.text.z*) }
.data : { foo.o(.data.first) ; *(.data.small) }

Cela serait équivalent à un script de linkeur comme celui-ci :

SECTIONS {
  .text : { *(.text.first) ; *(.text.z*) ; *(.text.hot) ; *(.text .text.*) }
  .data : { foo.o(.data.first) ; *(.data.small) ; *(.data.big) ; *(.data .data.*) }
  }

L'avantage du fichier d'ordonnancement de sections est qu'il peut être utilisé pour ordonner les sections qui importent à l'utilisateur sans avoir à se soucier des autres sections, des régions mémoire, ou de quoi que ce soit d'autre.

--warn-common
Avertit lorsqu'un symbole commun est combiné avec un autre symbole commun ou avec une définition de symbole. Les éditeurs de liens Unix autorisent cette pratique quelque peu laxiste, mais les éditeurs de liens sur certains autres systèmes d'exploitation ne le font pas. Cette option vous permet de détecter des problèmes potentiels liés à la combinaison de symboles globaux. Malheureusement, certaines bibliothèques C utilisent cette pratique, vous pouvez donc recevoir des avertissements concernant des symboles dans les bibliothèques ainsi que dans vos programmes.

Il existe trois types de symboles globaux, illustrés ici par des exemples C :

int i = 1;
Une définition, qui va dans la section de données initialisées du fichier de sortie.
extern int i;
Une référence indéfinie, qui n'alloue pas d'espace. Il doit y avoir soit une définition, soit un symbole commun pour la variable quelque part.
int i;
Un symbole commun. S'il n'y a que des symboles communs (un ou plusieurs) pour une variable, elle va dans la zone de données non initialisées du fichier de sortie. L'éditeur de liens fusionne plusieurs symboles communs pour la même variable en un seul symbole. S'ils sont de tailles différentes, il choisit la plus grande taille. L'éditeur de liens transforme un symbole commun en une déclaration, s'il existe une définition de la même variable.

L'option --warn-common peut générer cinq types d'avertissements. Chaque avertissement se compose d'une paire de lignes : la première décrit le symbole qui vient d'être rencontré, et la seconde décrit le symbole précédent rencontré avec le même nom. Un ou les deux symboles seront des symboles communs.

1.
Transformation d'un symbole commun en une référence, car il existe déjà une définition du symbole. 
<fichier>(<section>): avertissement : commun de `<symbole>'
   écrasé par la définition
<fichier>(<section>): avertissement : défini ici
2.
Transformation d'un symbole commun en une référence, car une définition ultérieure du symbole est rencontrée. C'est la même chose que le cas précédent, sauf que les symboles sont rencontrés dans un ordre différent. 
<fichier>(<section>): avertissement : définition de `<symbole>'
   écrasant un commun
<fichier>(<section>): avertissement : le commun est ici
3.
Fusion d'un symbole commun avec un symbole commun précédent de même taille. 
<fichier>(<section>): avertissement : multiples communs
   de `<symbole>'
<fichier>(<section>): avertissement : le commun précédent est ici
4.
Fusion d'un symbole commun avec un symbole commun précédent plus grand. 
<fichier>(<section>): avertissement : commun de `<symbole>'
   écrasé par un commun plus grand
<fichier>(<section>): avertissement : le commun plus grand est ici
5.
Fusion d'un symbole commun avec un symbole commun précédent plus petit. C'est la même chose que le cas précédent, sauf que les symboles sont rencontrés dans un ordre différent. 
<fichier>(<section>): avertissement : commun de `<symbole>'
   écrasant un commun plus petit
<fichier>(<section>): avertissement : le commun plus petit est ici

--warn-execstack
--warn-execstack-objects
--no-warn-execstack
Sur les plateformes ELF, l'éditeur de liens peut générer des messages d'avertissement s'il est invité à créer un fichier de sortie contenant une pile exécutable. Il existe trois états possibles :
1.
Ne génère aucun avertissement.
2.
Génère toujours des avertissements, même si la pile exécutable est demandée via l'option de ligne de commande -z execstack.
3.
Génère uniquement un avertissement si un fichier objet demande une pile exécutable, mais pas si l'option -z execstack est utilisée.

L'état par défaut dépend de la manière dont l'éditeur de liens a été configuré lors de sa construction. L'option --no-warn-execstack place toujours l'éditeur de liens dans l'état sans avertissement. L'option --warn-execstack place l'éditeur de liens dans l'état d'avertissement toujours. L'option --warn-execstack-objects place l'éditeur de liens dans l'état d'avertissement uniquement pour les fichiers objets.

Remarque : les fichiers d'entrée au format ELF peuvent spécifier qu'ils nécessitent une pile exécutable en ayant une section .note.GNU-stack avec le bit exécutable défini dans ses drapeaux de section. Ils peuvent spécifier qu'ils n'ont pas besoin d'une pile exécutable en ayant la même section, mais sans le bit d'exécution défini. Si un fichier d'entrée n'a pas de section .note.GNU-stack, le comportement par défaut est spécifique à la cible. Pour certaines cibles, l'absence d'une telle section implique qu'une pile exécutable *est* requise. C'est souvent un problème pour les fichiers assembleur faits à la main.

Avertit si plusieurs valeurs de pointeur global sont nécessaires dans le fichier de sortie. Ceci n'a de sens que pour certains processeurs
ssors, tels que l'Alpha. Plus précisément, certains processeurs placent les constantes de grande valeur dans une section spéciale. --wrap=symbole
Utiliser une fonction enveloppe pour symbole. Toute référence indéfinie à symbole sera résolue en "__wrap_symbole". Toute référence indéfinie à "__real_symbole" sera résolue en symbole.

Ceci peut être utilisé pour fournir une enveloppe à une fonction système. La fonction enveloppe doit être appelée "__wrap_symbole". Si elle souhaite appeler la fonction système, elle doit appeler "__real_symbole".

Voici un exemple trivial :

void *
__wrap_malloc (size_t c)
{
  printf ("malloc appelé avec %zu\n", c);
  return __real_malloc (c);
}

Si vous liez un autre code avec ce fichier en utilisant --wrap malloc, alors tous les appels à "malloc" appelleront la fonction "__wrap_malloc" à la place. L'appel à "__real_malloc" dans "__wrap_malloc" appellera la vraie fonction "malloc".

Vous pourriez vouloir fournir une fonction "__real_malloc" également, afin que les liaisons sans l'option --wrap réussissent. Si vous le faites, vous ne devez pas mettre la définition de "__real_malloc" dans le même fichier que "__wrap_malloc" ; si vous le faites, l'assembleur peut résoudre l'appel avant que l'éditeur de liens ait la chance de le lier à "malloc".

Seules les références indéfinies sont remplacées par l'éditeur de liens. Ainsi, les références internes à une unité de traduction à symbole ne sont pas résolues en "__wrap_symbole". Dans l'exemple suivant, l'appel à "f" dans "g" n'est pas résolu en "__wrap_f".

int
f (void)
{
  return 123;
}

int
g (void)
{
  return f();
}

--compress-debug-sections=none
--compress-debug-sections=zlib

--compress-debug-sections=zlib-gabi
--compress-debug-sections=zstd
Sur les plateformes ELF, ces options contrôlent la compression des sections de débogage DWARF à l'aide de zlib.

--compress-debug-sections=none ne compresse pas les sections de débogage DWARF. --compress-debug-sections=zlib-gnu compresse les sections de débogage DWARF et les renomme pour commencer par .zdebug au lieu de .debug. --compress-debug-sections=zlib-gabi compresse également les sections de débogage DWARF, mais au lieu de les renommer, il définit l'indicateur SHF_COMPRESSED dans les en-têtes des sections.

L'option --compress-debug-sections=zlib est un alias pour --compress-debug-sections=zlib-gabi.

--compress-debug-sections=zstd compresse les sections de débogage DWARF en utilisant zstd.

--reduce-memory-overheads
Cette option réduit les besoins en mémoire à l'exécution de ld, au détriment de la vitesse de liaison. Ce message survient lorsque certaines (sous-)expressions accèdent à une adresse donnée finalement par la somme de deux constantes (les tables d'importation Win32 n'en permettent qu'une). Les cas où cela peut survenir incluent les accès aux champs de membre de variables de structure importées depuis une DLL, ainsi que l'utilisation d'un index constant dans une variable de tableau importée depuis une DLL. N'importe quelle variable multi-mots (tableaux, structures, long long, etc.) peut déclencher cette condition d'erreur. terminera.

:

Une façon est d'utiliser l'option --enable-runtime-pseudo-reloc. Cela laisse la tâche d'ajuster les références dans votre code client pour l'environnement d'exécution, donc cette méthode ne fonctionne que lorsque l'environnement d'exécution supporte cette

fonctionnalité.

Une deuxième solution est de forcer l'une des 'constantes' à être une variable -- c'est-à-dire, inconnue et non optimisable à la compilation. Pour les tableaux, il y a deux possibilités : a) rendre l'indexé (l'adresse du tableau) une variable, ou b) rendre l'index 'constant' une variable.

}

DESCRIPTION

This manual page describes the options for avr-ld, the GNU linker. It is part of the GNU Binutils package.

avr-ld combines various objects files into a single executable file, resolving symbols and performing relocation.

The GNU linker can be told to emulate different linkers. This is done using the -m option.

The default emulation is determined when the linker is configured. You can obtain a list of available emulations using the -V or --version options.

OPTIONS

The long and short forms of options are, where they differ, unambiguously shown. Options that are not valid for all targets are noted.

-b value
--format=value

Set the input-file object code format to value. value can be any of the BFD formats. See the BFD documentation for a list of supported formats.

This option can be used multiple times. If it is used more than once, the linker will accept object files in any of the specified formats.

If no -b option is specified, the linker will attempt to guess the input file format from the contents of the file.

When used with the a.out format, -b can be followed by a list of target specific options, which are

insn32
If insn32 is used, then the linker only uses 32-bit instruction encodings. By default or if --no-insn32 is used, all instruction encodings are used, including 16-bit ones where possible.
--ignore-branch-isa
--no-ignore-branch-isa
These options control branch relocation checks for invalid ISA mode transitions. If --ignore-branch-isa is used, then the linker accepts any branch relocations and any ISA mode transition required is lost in relocation calculation, except for some cases of "BAL" instructions which meet relaxation conditions and are converted to equivalent "JALX" instructions as the associated relocation is calculated. By default or if --no-ignore-branch-isa is used a check is made causing the loss of an ISA mode transition to produce an error.
--compact-branches
--no-compact-branches
These options control the generation of compact instructions by the linker in the PLT entries for MIPS R6.
-N
--omagic
Mark the output as "OMAGIC" (0407) in the a.out header to indicate that the text segment is not to be write-protected and shared. Since the text and data sections are both readable and writable, the data section is allocated immediately contiguous after the text segment. This is the oldest format for PDP11 executable programs and is the default for ld on PDP11 Unix systems from the beginning through 2.11BSD.
-n
--nmagic
Mark the output as "NMAGIC" (0410) in the a.out header to indicate that when the output file is executed, the text portion will be read-only and shareable among all processes executing the same file. This involves moving the data areas up to the first possible 8K byte page boundary following the end of the text. This option creates a pure executable format.
-z
--imagic
Mark the output as "IMAGIC" (0411) in the a.out header to indicate that when the output file is executed, the program text and data areas will be loaded into separate address spaces using the split instruction and data space feature of the memory management unit in larger models of the PDP11. This doubles the address space available to the program. The text segment is again pure, write-protected, and shareable. The only difference in the output format between this option and the others, besides the magic number, is that both the text and data sections start at location 0. The -z option selected this format in 2.11BSD. This option creates a separate executable format.
--no-omagic
Equivalent to --nmagic for pdp11-aout.

ENVIRONMENT

You can change the behaviour of ld with the environment variables "GNUTARGET", "LDEMULATION" and "COLLECT_NO_DEMANGLE".

"GNUTARGET" determines the input-file object format if you don't use -b (or its synonym --format). Its value should be one of the BFD names for an input format. If there is no "GNUTARGET" in the environment, ld uses the natural format of the target. If "GNUTARGET" is set to "default" then BFD attempts to discover the input format by examining binary input files; this method often succeeds, but there are potential ambiguities, since there is no method of ensuring that the magic number used to specify object-file formats is unique. However, the configuration procedure for BFD on each system places the conventional format for that system first in the search-list, so ambiguities are resolved in favor of convention.

"LDEMULATION" determines the default emulation if you don't use the -m option. The emulation can affect various aspects of linker behaviour, particularly the default linker script. You can list the available emulations with the --verbose or -V options. If the -m option is not used, and the "LDEMULATION" environment variable is not defined, the default emulation depends upon how the linker was configured.

Normally, the linker will default to demangling symbols. However, if "COLLECT_NO_DEMANGLE" is set in the environment, then it will default to not demangling symbols. This environment variable is used in a similar fashion by the "gcc" linker wrapper program. The default may be overridden by the --demangle and --no-demangle options.
