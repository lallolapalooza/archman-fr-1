APERÇU DE LA GESTION DE

L'ÉTAT

Étant donné que HTTP est un protocole sans état, chaque clic ultérieur sur un site web est traité comme une nouvelle requête par le serveur Web. Le serveur n'établit pas de lien entre une visite et une précédente, ainsi toutes les informations d'état des requêtes précédentes sont perdues. Cela rend impossible la création d'applications telles que des paniers d'achat ou des sites web nécessitant une authentification des utilisateurs. Les gens ont donc dû faire quelque chose face à cette situation désespérée dans laquelle HTTP nous

plaçait.

Pour nous sauver, interviennent des technologies telles que les cookies HTTP et les QUERY_STRINGs qui nous aident à conserver la session de l'utilisateur pendant une certaine période. Puisque les cookies HTTP et les QUERY_STRINGs seuls ne peuvent pas nous emmener très loin (RFC 2965, Section 5, « Limitations d'implémentation »), plusieurs autres bibliothèques ont été développées pour étendre leurs capacités et promettre une solution plus fiable. CGI::Session en fait

partie.

Avant de discuter de cette bibliothèque, examinons quelques solutions

alternatives.

COOKI

E

Un cookie est un fragment d'information textuelle qu'un serveur web a le droit de placer sur le disque dur de l'utilisateur, en supposant que l'agent utilisateur (comme Internet Explorer, Mozilla, etc.) soit compatible avec la spécification. Une fois le cookie placé, les agents utilisateurs doivent renvoyer ces cookies au serveur dans le cadre de la requête HTTP. De cette façon, l'application serveur (CGI, par exemple) aura un moyen de relier les requêtes précédentes provenant du même agent utilisateur, surmontant ainsi l'absence d'état

d'HTTP.

Bien que les cookies HTTP semblent être une solution prometteuse pour l'absence d'état d'HTTP, ils comportent certaines limitations, telles qu'un nombre limité de cookies par domaine et par agent utilisateur, ainsi qu'une taille limitée pour chaque cookie. Les agents utilisateurs doivent stocker au moins 300 cookies à la fois, 20 cookies par domaine et permettre 4096 octets de stockage pour chaque cookie. Ils soulèvent également plusieurs préoccupations de confidentialité et de sécurité, dont les listes peuvent être trouvées dans les sections 6 - « Confidentialité » et 7 - « Considérations de sécurité » de la RFC

296
5.

QUERY

STRING

Une chaîne de requête (query string) est une chaîne ajoutée à l'URL après un point d'interrogation (?) telle que

: http://my.dot.com/login.cgi?user=sherzodr;password=top-secret

Comme vous l'avez probablement deviné, cela peut aussi vous aider à transmettre des informations d'état d'un clic à un autre,

mais à votre avis, à quel point est-ce sécurisé, étant donné que ces URL ont tendance à être mises en cache par la plupart
des agents utilisateurs et également enregistrées dans le journal d'accès du serveur, auquel tout le monde peut avoir accès.

CHAMPS

CACHÉS

Un champ caché est une autre alternative aux chaînes de requête et il existe en deux variantes : les champs cachés utilisés dans les méthodes POST et ceux utilisés dans les GET. Ceux utilisés dans les méthodes GET se transformeront en véritables chaînes de requête une fois soumis, donc tous les inconvénients des QUERY_STRINGs s'appliquent. Bien que les requêtes POST n'aient pas les limitations de leur cousine GET, les pages qui les contiennent sont mises en cache par le navigateur Web et sont disponibles dans le code source de la page (évidemment). Elles deviennent également difficiles à gérer lorsque l'on a une grande quantité d'informations d'état à suivre (par exemple, un panier d'achat ou un moteur de recherche avancé)

.

Les chaînes de requête et les champs cachés sont égalem

ent facilement perdus en fermant le navigateur ou
en cliquant sur le bouton « Retour » du navigateur.

GESTION DE SESSION CÔTÉ

SERVEUR

Cette technique est construite sur les technologies mentionnées ci-dessus plus un dispositif de stockage côté serveur, qui enregistre les données d'état côté serveur. Chaque session a un identifiant unique associé aux données sur le serveur. Cet identifiant est également associé à l'agent utilisateur soit sous la forme d'un cookie HTTP, d'une QUERY_STRING, d'un champ caché ou de toute combinaison des éléments ci-dessus. Cela est nécessaire pour établir la connexion avec le client et ses

données.

Avantages

:
  • Nous n'avons plus besoin de dépendre des contraintes de l'agent utilisateur concernant la taille des
    • cookies.
  • Les données sensibles n'ont plus besoin de circuler sur le réseau à chaque requête (ce qui est le cas avec les chaînes de requête, les cookies et les champs cachés). La seule chose qui circule est l'identifiant unique généré pour la session (5767393932698093d0b75ef614376314, par exemple), qui ne devrait avoir aucun sens pour les
    • tiers.
  • L'utilisateur n'aura pas de données sensibles stockées sur son ordinateur dans un fichier non sécurisé (ce qui est le cas d'un fichier cookie)
    • .
  • Il est possible de gérer des structures de données très grandes et même complexes de manière transparente (ce que les cookies HTTP
    • ne gère
nt pas).

C'est de cela qu'il s'agit avec CGI::Ses

sion - implémenter la gestion de ses
sion côté serveur. C'est maintenant le
bon moment pour se mettre à l'œuvre.

STYLE DE

PROGRAMMATION

Le système de gestion de session côté serveur peut sembler terriblement compliqué si vous n'avez jamais eu à le gérer. Heureusement, avec CGI::Session, toute la complexité est gérée de manière transparente par la bibliothèque. Cette section du manuel peut être considérée comme un tutoriel d'introduction à la fois à la logique derrière la gestion de session et au style de programmation de CGI::

Session.

Toutes les applications utilisant la gestion de session côté serveur reposent sur le schéma d'opération suivant, quelle que soit la manière dont le système est implémenté

:
1
.
Vérifier si l'utilisateur a un cookie de session déposé sur son ordinateur lors d'une requête
précédente
2
.
Si le cookie n'existe pas, créer un nouvel identifiant de session et le déposer sous forme de cookie sur l'ordinateur de
l'utilisateur.
3
.
Si le cookie de session existe, lire l'ID de session depuis le cookie et charger toutes les données de session précédemment enregistrées depuis le stockage côté serveur. Si la session avait une date d'expiration définie, il est utile de redéposer le même cookie sur l'ordinateur de l'utilisateur afin que son temps d'expiration soit réinitialisé pour être relatif au moment de la dernière activité de
l'utilisateur.
4
.
Stocker dans la session toutes les données
nécessaires que vous souhaitez rendre
disponibles pour la prochaine requête HTTP.

CGI::Session gérera toutes les étapes ci-dessus. Tout ce que vous avez à faire est de choisir ce que vous voulez stocker dans la

session.

POUR

COMMENCER

Pour rendre la fonctionnalité de CGI::Session disponible dans votre programme, faites l'une ou l'autre des actions suivantes quelque part en haut de votre fichier de programme

: 
use CGI::Session;
# ou
require CGI::
Session;

Chaque fois que vous êtes prêt à créer une nouvelle session dans votre application, faites ce qui suit

: 
$session = CGI::Session->new () or die CGI::Session->
errstr;

La ligne ci-dessus essaiera d'abord de réinitialiser une session existante en consultant les cookies et les paramètres QUERY_STRING nécessaires. Si cela échoue, elle créera une session entièrement nouvelle avec un ID unique, normalement appelé session ID, SID en abrégé, et accessible via la méthode objet id()

.

Nous n'avons pas vérifié les cookies de session ci-dessus, n'est-ce pas ? Non, nous ne l'avons pas fait, mais CGI::Session l'a fait. Il a cherché un cookie appelé « CGISESSID », et s'il l'a trouvé, il a essayé de charger la session existante depuis le stockage côté serveur (un fichier dans notre cas). Si le cookie n'existait pas, il a cherché un paramètre QUERY_STRING appelé « CGISESSID ». Si toutes les tentatives de récupération de l'ID de session ont échoué, il a créé une nouvelle

session.

REMARQUE : Pour que la syntaxe ci-dessus fonctionne comme prévu, votre application doit avoir un accès en écriture au dossier TEMPDIR de votre ordinateur, qui est généralement /tmp sous UNIX. Si ce n'est pas le cas, ou si vous souhaitez stocker les fichiers de session de cette application dans un autre endroit, vous pouvez passer le troisième argument comme ceci

: 
$session = CGI::Session->new(undef, undef, {Directory=>'../tmp/sessions'})
;

Désormais, il stockera toutes les nouvelles sessions créées dans (et essaiera d'initialiser les sessions demandées depuis) ce dossier. Ne vous inquiétez pas si la hiérarchie de répertoires que vous voulez utiliser n'existe pas déjà. Elle sera créée pour vous. Pour des détails sur la manière dont les données de session sont stockées, consultez CGI::Session::Driver::file, qui est le pilote par défaut utilisé dans notre exemple

ci-dessus.

Il y a une petite, mais très importante chose que votre application doit faire après avoir créé l'objet CGI::Session comme ci-dessus. Elle doit déposer l'ID de session sous la forme d'un Hcookie HTTP sur l'ordinateur de l'utilisateur. CGI::Session utilisera ce cookie pour identifier l'utilisateur lors de sa prochaine requête et pourra charger les données de session précédemment

stockées.

Pour vous assurer que CGI::Session pourra lire votre cookie lors de la prochaine requête, vous devez consulter sa méthode name() pour le nom suggéré du cookie

: 
$cookie = $query->cookie( -name   => $session->name,
                          -value  => $session->id );
print $query->header( -cookie=>$cookie )
;

name() retourne "CGISESSID" par défaut. Si vous préférez un nom de cookie différent, vous pouvez le changer tout aussi facilement, mais vous devez le faire avant la création de l'objet CGI::Session

: 
CGI::Session->name("SID");
$session = CGI::Session->new()
;

La création du cookie n'était pas trop difficile, n'est-ce pas ? Mais il existe un moyen encore plus simple d'envoyer un cookie en utilisant CGI::Session

: 
print $session->header()
;

Ce qui précède créera le cookie en utilisant CGI::Cookie et retournera les en-têtes http appropriés en utilisant la méthode CGI de CGI.pm. Tous les arguments de CGI::Session seront passés à CGI::head

er().

Bien sûr, cette méthode de n'initialisation ne fonctionnera que si le client accepte les cookies. Sinon, vous devrez passer l'identifiant de session dans chaque URL de votre application en tant que QUERY_STRING. Pour que CGI::Session le détecte, le nom du paramètre doit être le même que celui retourné par name()

: 
printf ("<a href=\"$ENV{SCRIPT_NAME}?%s=%s\">click me</a>", $session->name, $session->id)
;

Si vous avez déjà un identifiant de session à initialiser, vous pouvez le passer en tant qu'unique argument, ou en tant que second argument de la syntaxe multi-arguments

: 
$session = CGI::Session->new( $sid );
$session = CGI::Session->new( "serializer:freezethaw", $sid );
$session = CGI::Session->new( "driver:mysql", $sid, {Handle=>$dbh} )
;

Par défaut, CGI::Session utilise le CGI standard pour analyser les requêtes et les cookies. Si vous préférez utiliser un objet différent mais compatible, vous pouvez passer cet objet à la place de $sid

: 
$cgi     = CGI::Simple->new();
$session = CGI::Session->new( $cgi );
$session = CGI::Session->new( "driver:db_file;serializer:storable", $cgi);
#
etc

STOCKAGE DES

DONNÉES

CGI::Session offre la méthode param(), qui se comporte exactement comme la méthode param() de CGI.pm avec une syntaxe identique. param() est utilisée pour stocker des données dans la session ainsi que pour accéder aux données déjà

stockées.

Imaginez qu'un client a soumis un formulaire de connexion sur votre site Web. Vous, en tant que bon hôte, souhaitiez vous souvenir du nom de l'invité, afin de pouvoir a) le saluer en conséquence lorsqu'il visite à nouveau votre site, ou b) être utile en remplissant la partie nom d'utilisateur de son formulaire de connexion, afin que le client puisse passer directement au champ mot de passe sans avoir à retaper son nom

d'utilisateur. 
my $name = $cgi->param('username');
$session->param('username', $name)
;

Notez que nous récupérons la valeur username du champ en utilisant la méthode param() de CGI.pm (ou d'une autre bibliothèque compatible) et que nous la stockons dans la session en utilisant la méthode param() de CGI::Session. param()

méthode.

Si vous avez trop de choses à transférer dans la session, vous risquez de vous retrouver à taper ce code encore et encore. Je l'ai fait, et croyez-moi, cela devient très ennuyant très vite, et est aussi sujet aux erreurs. Nous avons donc introduit la méthode pratique suivante

: 
$session->save_param(['name'])
;

Si vous souhaitez stocker plusieurs champs de formulaire, incluez-les tous dans la seconde liste

: 
$session->save_param(['name', 'email'])
;

Si vous souhaitez stocker tous les paramètres QUERY_STRING disponibles, vous pouvez omettre les arguments

: 
$session->save_param()
;

Voir save_param() pour plus de

détails.

Lors du stockage de données dans la session, vous n'êtes pas limité aux chaînes de caractères. Vous pouvez stocker des tableaux, des hachages et même la plupart des objets. Vous devrez les passer en tant que références (sauf les objets)

.

Par exemple, pour récupérer toutes les valeurs sélectionnées d'une liste défilante et les stocker dans la session

: 
my @fruits = $cgi->param('fruits');
$session->param('fruits', \@fruits)
;

Pour les paramètres à valeurs multiples, save_param() fera également ce qu'il faut. Ainsi, ce qui précède est équivalent à

: 
$session->save_param($cgi, ['fruits'])
;

Toutes les mises à jour des données de session effectuées avec les méthodes ci-dessus ne seront pas répercutées dans le magasin de données tant que votre application ne se termine pas, ou tant que $session ne sort pas de sa portée. Si, pour une raison quelconque, vous devez valider les modifications dans le magasin de données avant la fin de votre application, vous devez appeler la méthode flush()

: 
$session->flush()
;

J'ai écrit beaucoup de code et n'ai jamais ressenti le besoin d'utiliser la méthode flush(), car CGI::Session appelle cette méthode à la fin de chaque requête. Il y a cependant des occasions où l'on peut imaginer qu'il faille appeler flus

h(
).

ACCÈS AUX DONNÉES

STOCKÉES

Il n'y a aucun intérêt à stocker des données si vous ne pouvez pas y accéder. Vous pouvez accéder aux données de session stockées en utilisant la même méthode param() que vous avez utilisée pour les stocker. Vous souvenez-vous du champ Nom d'utilisateur de la section précédente que nous avons stocké dans la session ? Lisons-le pour pouvoir remplir partiellement le formulaire de connexion pour l'utilisateur

: 
$name = $session->param("name");
printf "<input type=\"text\" name=\"name\" value=\"%s\" />",
$name;

Pour récupérer le tableau @fruits précédemment stocké, n'oubliez pas de le dé-référencer

: 
@fruits = @{ $session->param('fruits') }
;

Très fréquemment, vous vous retrouverez à devoir créer des formulaires pré-remplis et pré-sélectionnés, comme des boutons radio, des cases à cocher et des menus déroulants, en fonction des préférences ou des actions précédentes de l'utilisateur. Avec les champs de texte et les zones de texte, ce n'est pas un gros problème - vous pouvez simplement récupérer un paramètre unique depuis la session et coder en dur la valeur dans le champ de texte. Mais comment feriez-vous lorsque vous avez un groupe de boutons radio, de cases à cocher et de listes défilantes ? À cette fin, CGI::Session fournit la méthode load_param(), qui charge les paramètres de session donnés dans un objet CGI (en supposant qu'ils ont été précédemment enregistrés avec save_param() ou une méthode alternative)

: 
$session->load_param($cgi, ["fruits"])
;

Maintenant, lorsque vous dites

: 
print $cgi->checkbox_group(fruits=>['apple', 'banana', 'apricot'])
;

détails.

Les cases à cocher générées seront pré-remplies en utilisant les informations précédemment

enregistrées.

En supposant que l'objet de session a stocké les paramètres "first_name" et "email" tout en étant associé à HTML::Template, vous pouvez maintenant accéder à ces valeurs depuis votre fichier "some.tmpl"

: 
Hello <a href="mailto:<TMPL_VAR email>"> <TMPL_VAR first_name> </a>

EFFACEMENT DES DONNÉES DE

SESSION

Vous stockez des données de session, vous accédez aux données de session et à un moment donné vous voudrez effacer certaines données de session, si ce n'est pas toutes. À cette fin, CGI::Session fournit la méthode clear() qui prend éventuellement un argument sous forme de référence à un tableau indiquant quels paramètres de session doivent être supprimés de l'objet de session

: 
$session->clear(["~logged-in", "email"])
;

La ligne ci-dessus supprime les paramètres de session "~logged-in" et "email" de la session. Et la prochaine fois que vous dites

: 
$email = $session->param("email")
;

elle retourne undef. Si vous omettez l'argument de clear(), sachez que tous les paramètres de session que vous avez jamais stockés dans l'objet de session seront supprimés. Notez que cela ne supprime pas la session elle- même. La session reste ouverte et accessible. Seuls les paramètres que vous y avez stockés sont

supprimés.

Voir clear() pour

les dé
tails.

SESSION

S'il y a un début, il y a une fin. Si la session a pu être créée, il devrait être possible de la supprimer définitivement du disque

$session->delete()

L'appel à delete() ci-dessus supprime définitivement la session du disque. Ne le confondez pas avec clear(), qui ne fait qu'effacer certains paramètres de session mais garde la session

EXPIRATIO

N

CGI::Session offre des moyens limités d'expirer les sessions. Expirer une session revient à la supprimer via delete(), mais la suppression a lieu automatiquement. Pour faire expirer une session, vous devez indiquer à la bibliothèque combien de temps la session sera valide après le dernier accès. Lorsque ce temps est atteint, CGI::Session refuse de récupérer la session. Il supprime la session et en retourne une toute nouvelle. Pour attribuer un délai d'expiration à une session, utilisez expire()

: 
$session->expire(3600);     # expire after 3600 seconds
$session->expire('+1h');    # expire after 1 hour
$session->expire('+15m');   # expire after 15 minutes
$session->expire('+1M');    # expire after a month and so
on.

Lorsqu'une session est définie pour expirer à un moment donné dans le futur, mais que la session n'a pas été demandée à ce moment-là ou après, elle restera sur le disque. Lorsqu'une session expirée est demandée, CGI::Session supprimera les données du disque et initialisera une toute nouvelle

session.

Voir expire() pour les

détails.

Avant CGI::Session 4.x, il n'y avait aucun moyen d'intercepter les requêtes vers des sessions expirées. CGI::Session 4.x a introduit un nouveau type de constructeur, load(), qui est identique dans son usage à new(), mais qui n'est pas autorisé à créer des sessions. Il ne peut que les charger. Si la session s'avère expirée, ou si la session n'existe pas, il retournera un objet CGI::Session vide. Et si la session est expirée, en plus d'être vide, son statut sera également défini comme expiré. Vous pouvez vérifier ces conditions en utilisant les méthodes empty() et is_expired(). Si la session a été chargée avec succès, l'objet retourné par load() est une session aussi bonne que celle retournée par new()

: 
$session = CGI::Session->load() or die CGI::Session->errstr;
if ( $session->is_expired ) {
    die "Votre session a expiré. Veuillez actualiser votre navigateur pour redémarrer votre session";
}
if ( $session->is_empty ) {
    $session = $session->new();
}

L'exemple ci-dessus mérite votre attention. Rappelez-vous, toutes les sessions expirées sont des sessions vides, mais toutes les sessions vides ne sont pas des sessions expirées. En suivant cette règle, nous devons vérifier avec is_expired() avant de vérifier avec is_empty(). Il y a une autre chose à propos de l'exemple ci-dessus. Remarquez comment il crée une nouvelle session lorsqu'une session inexistante a été demandée ? En appelant new() en tant que méthode d'objet ! L'avantage de cela est que lorsque vous appelez new() sur un objet session, un nouvel objet sera créé en utilisant la même configuration que l'objet

précédent.

Par exemple

: 
$session = CGI::Session->load("driver:mysql;serializer:storable", undef, {Handle=>$dbh});
if ( $session->is_expired ) {
    die "Votre session a expiré. Veuillez actualiser votre navigateur pour redémarrer votre session";
}
if ( $session->is_empty ) {
    $session = $session->new();
}

L'objet $session initial était configuré avec mysql comme pilote, storable comme sérialiseur et $dbh comme gestionnaire de base de données. Appeler new() sur cet objet retournera un objet de la même configuration. Ainsi l'objet $session retourné par new() dans l'exemple ci-dessus utilisera mysql comme pilote, storable comme sérialiseur et $dbh comme gestionnaire de base de

données.

Voir is_expired(), is_empty(), load() pour les

détails.

Parfois, il est tout à fait logique d'expirer un certain paramètre de session, plutôt que toute la session. Je fais généralement cela sur mes sites avec authentification, où après que l'utilisateur s'est connecté avec succès, je définis son paramètre de session "_logged_in" à vrai, et j'attribue un compteur d'expiration sur ce drapeau à quelque chose comme 30 minutes. Cela signifie qu'après 30 minutes d'inactivité, CGI::Session effacera le drapeau "_logged_in", indiquant que l'utilisateur doit se reconnecter. J'admets que le même effet peut être obtenu en simplement expirant() la session elle-même, mais en faisant cela nous perdrons les autres paramètres de session, tels que le panier d'achat de l'utilisateur, les préférences de session et ainsi de

suite.

Cette fonctionnalité peut également être utilisée pour simuler une authentification en couches, par exemple, vous pouvez conserver l'accès de l'utilisateur à ses informations de profil personnel pendant 60 minutes après une connexion réussie, mais faire expirer son accès à ses informations de carte de crédit après 5 minutes d'inactivité. Pour obtenir cet effet, nous utiliserons à nouveau la méthode expire()

: 
$session->expire(_profile_access, '1h');
$session->expire(_cc_access, '5m')
;

Avec la syntaxe ci-dessus, la personne aura toujours accès à ses informations personnelles même après 5 heures d'inactivité. Mais lorsqu'il essaie d'accéder ou de mettre à jour ses informations de carte de crédit, un écran "veuillez vous reconnecter" peut lui être

affiché.

Voir expire() pour les

détails.

STOCKAG

E

La sécurité de la bibliothèque dépend à bien des égards de l'implémentation. Après avoir utilisé cette bibliothèque, vous n'avez plus à envoyer toutes les informations au cookie de l'utilisateur, sauf l'identifiant de session. Mais, vous devez toujours stocker les données côté serveur. Ainsi, un autre ensemble de questions surgit : une personne malveillante peut-elle accéder aux données de session sur votre serveur, même si elle le fait, peut-elle comprendre les données du fichier de session, et même si elle le peut, peut-elle réutiliser les informations contre la personne qui a créé cette session ? Comme vous le voyez, la réponse dépend de vous, celui qui

l'implémente.
  • Première règle empirique, ne stockez pas les mots de passe des utilisateurs ou d'autres données sensibles dans la session, s'il vous plaît. Si vous devez le faire, utilisez un chiffrement à sens unique, comme md5 ou SHA-1-1. D'après ma propre expérience, je peux vous assurer que dans les applications Web alimentées par des sessions correctement implémentées, il n'y a jamais besoin de
    • cela.
  • La configuration par défaut du pilote utilise la classe Data::Dumper pour sérialiser les données afin de pouvoir les sauvegarder sur le disque. Le résultat de Data::Dumper est une structure de données lisible par l'homme, qui, si elle est ouverte, peut être interprétée facilement. Si vous configurez votre objet session pour utiliser soit Storable soit FreezeThaw comme sérialiseur, cela rendrait plus difficile pour les méchants de comprendre les données de session. Mais n'utilisez pas cela comme seule précaution. Puisque des doigts malveillants peuvent taper un programme rapide utilisant Storable ou FreezeThaw pour déchiffrer les fichiers de session très
    • facilement.
  • Ne permettez à personne de mettre à jour le contenu des fichiers de session. Si vous utilisez le sérialiseur par défaut, la chaîne de données sérialisées doit être évaluée par eval() pour faire revivre la structure de données originale. Bien sûr, nous utilisons Safe pour le faire en toute sécurité, mais votre prudence ne fait pas de mal non
    • plus.
  • Ne gardez pas les sessions ouvertes très longtemps. Cela augmentera la possibilité qu'un méchant puisse avoir l'identifiant de session valide de quelqu'un à un moment donné (acquis d'une manière ou d'une autre). Pour cela, utilisez la méthode expire() pour définir un compteur d'expiration. Plus les informa
    • tions sur votre site Web sont sensi

configurée pour expirer rapidement.

IDENTIFIANTS DE

SESSION

Les identifiants de session ne sont pas faciles à deviner (sauf si vous utilisez le générateur d'ID incrémental) ! La configuration par défaut de CGI::Session utilise Digest::MD5 pour générer un identifiant aléatoire de 32 caractères. Bien que cette chaîne ne puisse pas être devinée aussi facilement par d'autres, s'ils la découvrent d'une manière ou d'une autre, peuvent-ils utiliser cet identifiant contre l'autre personne

?

Considérez le scénario où vous donnez à quelqu'un, soit par e-mail soit par messagerie instantanée, un lien vers un site Web où vous êtes actuellement connecté. L'URL que vous donnez à cette personne contient un identifiant de session en tant que partie d'une chaîne de requête. Si le site initialisait la session uniquement à l'aide du paramètre de chaîne de requête, après avoir cliqué sur ce lien, cette personne apparaît maintenant sur ce site comme vous, et pourrait avoir accès instantanément à toutes vos données

privées.

Même si vous utilisez uniquement les cookies comme transporteurs d'identifiants de session, ce n'est pas si difficile de planter un cookie dans le fichier de cookie avec le même identifiant et de tromper le navigateur web pour qu'il envoie cet identifiant de session particulier au serveur. Ainsi, la clé de la sécurité est de vérifier si la personne qui nous demande de récupérer des données de session est bien la personne qui a initialement créé les données de

session.

Une façon d'aider à cela est de vérifier également que l'adresse IP à partir de laquelle la session est utilisée est toujours la même. Cependant, cela s'avère ne pas être pratique dans les cas courants car certains grands FAI (comme AOL) utilisent des proxys qui font que chaque requête provenant du même utilisateur provient d'une adresse IP

différente.

Si vous avez une application où vous êtes sûr que les adresses IP de vos utilisateurs sont constantes pendant une session, vous pouvez envisager d'activer une option pour effectuer cette vérification

: 
use CGI::Session
'-ip_match';

Pour la rétrocompatibilité, vous pouvez également y parvenir en définissant $CGI::Session::IP_MATCH à une valeur vraie. Cela garantit qu'avant d'initialiser une session précédemment stockée, il vérifie si l'adre

sse IP stockée dans la session correspond à l'adresse IP de l'utili
sateur demandant cette session. Dans ce cas, la bibliothèque retourn
e la session, sinon elle échoue avec un message d'erreur approprié.
