DESCRIPTIO

N

Les groupes de contrôle, généralement appelés cgroups, sont une fonctionnalité du noyau Linux qui permet d'organiser les processus en groupes hiérarchiques dont l'utilisation de divers types de ressources peut ensuite être limitée et surveillée. L'interface cgroup du noyau est fournie par un pseudo-système de fichiers appelé cgroupfs. Le regroupement est implémenté dans le code noyau des cgroups, tandis que le suivi et les limites des ressources sont implémentés dans un ensemble de sous-systèmes par type de ressource (mémoire, CPU, etc.)

.

Terminologi

e

Un cgroup est un ensemble de processus qui sont liés à un ensemble de limites ou de paramètres définis via le système de fichiers des

cgroups.

Un sous-système est un composant du noyau qui modifie le comportement des processus dans un cgroup. Divers sous-systèmes ont été implémentés, rendant possible des actions telles que la limitation de la quantité de temps CPU et de mémoire disponibles pour un cgroup, la comptabilisation du temps CPU utilisé par un cgroup, et la suspension et la reprise de l'exécution des processus dans un cgroup. Les sous-systèmes sont parfois aussi appelés contrôleurs de ressources (ou simplement contrôleurs)

.

Les cgroups d'un contrôleur sont organisés dans une hiérarchie. Cette hiérarchie est définie en créant, supprimant et renommant des sous-répertoires dans le système de fichiers des cgroups. À chaque niveau de la hiérarchie, des attributs (par exemple, des limites) peuvent être définis. Les limites, le contrôle et la comptabilisatio

n fournis par les cgroups ont généralement un effet sur toute la sous-hiérarchie située sous le cgroup où les attributs sont définis. Ainsi, pa
r exemple, les limites placées sur un cgroup à un niveau supérieur de la hiérarchie ne peuvent pas être dépassées par les cgroups descendants.

Cgroups version 1 et version

2

La première version de l'implémentation des cgroups a été publiée dans Linux 2.6.24. Au fil du temps, divers contrôleurs de cgroups ont été ajoutés pour permettre la gestion de divers types de ressources. Cependant, le développement de ces contrôleurs a été largement non coordonné, avec pour résultat de nombreuses incohérences entre les contrôleurs et une gestion des hiérarchies de cgroups devenue plutôt complexe. Une description plus détaillée de ces problèmes peut être trouvée dans le fichier source du noyau Documentation/admin-guide/cgroup-v2.rst (ou Documentation/cgroup-v2.txt dans Linux 4.17 et les versions antérieures)

.

En raison des problèmes de l'implémentation initiale des cgroups (cgroups version 1), à partir de Linux 3.10, un travail a commencé sur une nouvelle implémentation orthogonale pour remédier à ces problèmes. Initialement marquée comme expérimentale et cachée derrière l'option de montage -o __DEVEL__sane_behavior, la nouvelle version (cgroups version 2) a finalement été rendue officielle avec la publication de Linux 4.5. Les différences entre les deux versions sont décrites dans le texte ci-dessous. Le fichier cgroup.sane_behavior, présent dans cgroups v1, est un vestige de cette option de montage. Le fichier rapporte toujours "0" et n'est conservé que pour des raisons de compatibilité

ascendante.

Bien que cgroups v2 soit destiné à remplacer cgroups v1, l'ancien système continue d'exister (et pour des raisons de compatibilité, il est peu probable qu'il soit supprimé). Actuellement,

cgroups v2 n'implémente qu'un sous-ensemble des contrôleurs disponibles dans cgroups v1. Les deux systèmes sont implémentés de telle sorte que les contrôleurs v1 et v2 peuvent être montés
sur le même système. Ainsi, par exemple, il est possible d'utiliser les contrôleurs pris en charge sous la version 2, tout en utilisant les contrôleurs de la version 1 là où la version 2 ne
les prend pas encore en charge. La seule restriction ici est qu'un contrôleur ne peut pas être utilisé simultanément dans une hiérarchie de cgroups v1 et dans la hiérarchie de cgroups v2.

CGROUPS VERSION

1

Sous cgroups v1, chaque contrôleur peut être monté sur un système de fichiers cgroup distinct qui fournit sa propre organisation hiérarchique des processus sur le système. Il est également possible de monter plusieurs (voire tous) contrôleurs de cgroups v1 sur le même système de fichiers cgroup, ce qui signifie que les contrôleurs montés ensemble gèrent la même organisation hiérarchique des

processus.

Pour chaque hiérarchie montée, l'arborescence des répertoires reflète la hiérarchie des groupes de contrôle. Chaque groupe de contrôle est représenté par un répertoire, chacun de ses groupes de contrôle enfants étant représenté par un sous-répertoire. Par exemple, /user/joe/1.session représente le groupe de contrôle 1.session, qui est un enfant du cgroup joe, qui est un enfant de /user. Sous chaque répertoire de cgroup se trouve un ensemble de fichiers qui peuvent être lus ou écrits, reflétant les limites de ressources et quelques propriétés générales des

cgroups.

Tâches (threads) et

processus

Dans cgroups v1, une distinction est faite entre processus et tâches. Dans cette vue, un processus peut être composé de plusieurs tâches (plus communément appelées threads d'un point de vue espace utilisateur, et appelées ainsi dans le reste de cette page man). Dans cgroups v1, il est possible de manipuler indépendamment l'appartenance aux cgroups des threads d'un

processus.

La capacité de cgroups v1 à répartir les threads entre différents cgroups a causé des problèmes dans certains cas. Par exemple, cela n'avait pas de sens pour le contrôleur mémoire, car tous les threads d'un processus partagent un espace d'adressage unique. En raison de ces problèmes, la capacité de manipuler indépendamment l'appartenance aux cgroup

s des threads d'un processus a été supprimée dans l'implémentation initiale de cgroups v2, puis
restaurée sous une forme plus limitée (voir la discussion sur le « mode thread » ci-dessous).

Montage des contrôleurs

v1

L'utilisation des cgroups nécessite un noyau compilé avec l'option CONFIG_CGROUP. De plus, chacun des contrôleurs v1 a une option de configuration associée qui doit être définie afin d'utiliser ce

contrôleur.

Afin d'utiliser un contrôleur v1, il doit être monté sur un système de fichiers cgroup. L'endroit habituel pour de tels montages est sous un système de fichiers tmpfs(5) monté sur /sys/fs/cgroup. Ainsi, on pourrait monter le contrôleur cpu comme suit

: 


mount -t cgroup -o cpu none /sys/fs/cgroup/cp
u

Il est possible de monter plusieurs contrôleurs sur la même hiérarchie. Par exemple, ici les contrôleurs cpu et cpuacct sont montés ensemble sur une seule hiérarchie

: 


mount -t cgroup -o cpu,cpuacct none /sys/fs/cgroup/cpu,
cpuacct

Monter des contrôleurs ensemble a pour effet qu'un processus est dans le même cgroup pour tous les contrôleurs montés ensemble. Monter séparément les contrôleurs permet à un processus d'être dans le cgroup /foo1 pour un contrôleur tout en étant dans /foo2/foo3 pour un

autre.

Il est possible de monter tous les contrôleurs v1 sur la même hiérarchie

: 


mount -t cgroup -o all cgroup
/sys/fs/cgroup

(On peut obtenir le même résultat en omettant -o all, car c'est la valeur par défaut si aucun contrôleur n'est explicitement spécifié.

)

Il n'est pas possible de monter le même contrôleur sur plusieurs hiérarchies de cgroups. Par exemple, il n'est pas possible de monter à la fois les contrôleurs cpu et cpuacct sur une hiérarchie, et de monter le contrôleur cpu seul sur une autre hiérarchie. Il est possible de créer plusieurs montages avec exactement le même ensemble de contrôleurs montés ensemble. Cependant, dans ce cas, le résultat n'est que plusieurs points de montage fournissant une vue de la même

hiérarchie.

Notez que sur de nombreux systèmes, les contrôleurs v1 sont automatiquement montés sous /sys/fs/cgroup ; en particulier, systemd(1) crée automa

tiquement de t
els montages.

Démontage des contrôleurs

v1

Un système de fichiers cgroup monté peut être démonté à l'aide de la commande umount(8), comme dans l'exemple suivant

: 


umount /sys/fs/cgroup/pid
s

Mais notez bien : un système de fichiers cgroup n'est démonté que s'il n'est pas occupé, c'est-à-dire s'il n'a pas de cgroups enfants. Si ce n'est pas le cas, alors le seul effet de umount(8) est de rendre le montage invisible. Ainsi, pour s'assurer que le montagent est réellement supprimé, il faut d'abord supprimer tous les cgroup

s enfants, ce qui à son tour ne peut être fait qu'après que tous les
processus membres ont été déplacés de ces cgroups vers le cgroup racine.

Création de cgroups et déplacement de

processus

Un système de fichiers cgroup contient initialement un seul cgroup racine, '/', auquel tous les processus appartiennent. Un nouveau cgroup est créé en créant un répertoire dans le système de fichiers cgroup

: 


mkdir /sys/fs/cgroup/cpu/cg
1

Cela crée un nouveau cgroup

vide.

Un processus peut être déplacé vers ce cgroup en écrivant son PID dans le fichier cgroup.procs du cgroup

: 


echo $$ > /sys/fs/cgroup/cpu/cg1/cgroup.
procs

Un seul PID à la fois devrait être écrit dans ce

fichier.

Écrire la valeur 0 dans un fichier cgroup.procs provoque le déplacement du processus qui écrit vers le cgroup

correspondant.

Lors de l'écriture d'un PID dans cgroup.procs, tous les threads du processus sont déplacés vers le nouveau cgroup en une seule

fois.

Au sein d'une hiérarchie, un processus peut être membre d'un seul cgroup. Écrire le PID d'un processus dans un fichier cgroup.procs le retire automatiquement du cgroup dont il était auparavant

membre.

Le fichier cgroup.procs peut être lu pour obtenir une liste des processus qui sont membres d'un cgroup. La liste de PIDs retournée n'est pas garantie d'être dans l'ordre. Elle n'est pas non plus garantie d'être exempte de doublons. (Par exemple, un PID peut être recyclé pendant la lecture de la liste.

)

Dans les cgroups v1, un thread individuel peut être déplacé vers un autre cgroup en écrivant son identifiant de thread (c'est-à-dire l'identifiant de thread du noyau renvoyé par clone(2) et gettid(2)) dans le fichier tasks d'un répertoire de cgroup. Ce fichier peut être lu

pour découvrir l'ensemble des threa
ds qui sont membres du cgroup.

Suppression de

cgroups

Pour supprimer un cgroup, il ne doit d'abord avoir aucun cgroup enfant et ne contenir aucun processus (no

n zombie). Tant que c'est le cas, on peut simplement supprimer le chemin du répertoire correspondant. Not
ez que les fichiers dans un répertoire de cgroup ne peuvent pas et n'ont pas besoin d'être supprimés.

Notification de libération des cgroups

v1

Deux fichiers peuvent être utilisés pour déterminer si le noyau fournit des notifications lorsqu'un cgroup devient vide. Un cgroup est considéré comme vide lorsqu'il ne contient aucun cgroup enfant et aucun processus

membre.

Un fichier spécial dans le répertoire racine de chaque hiérarchie de cgroup, release_agent, peut être utilisé pour enregistrer le chemin d'accès d'un programme qui peut être invoqué lorsqu'un cgroup dans la hiérarchie devient vide. Le chemin d'accès du cgroup nouvellement vide (par rapport au point de montage du cgroup) est fourni comme unique argument de ligne de commande lorsque le programme release_agent est invoqué. Le programme release_agent peut supprimer le répertoire du cgroup, ou peut-être le remplir à nouveau

avec

un processus. La valeur par défaut du fichier release_agent est vide, ce qui signifie qu'aucun agent

de

libération n'est invoqué. Le contenu du fichier release_agent peut également être spécifié via une option de montage lorsque

le 


système de fichiers cgroup est monté

Si ce fichier contient la valeur 0, alors le programme release_agent n'est pas invoqué. S'il contient la valeur 1, le programme release_agent est invoqué. La valeur par défaut de ce fichier dans le cgroup racine est 0. Au

moment où un nouveau cgroup est créé, la valeur de ce fichier
est héritée du fichier correspondant dans le cgroup parent.

Règle des cgroups v2 « pas de processus internes

»

Les cgroups v2 imposent une règle dite « pas de processus internes ». En gros, cette règle signifie qu'à l'exception du cgroup racine, les processus ne peuvent résider que dans des nœuds feuilles (cgroups qui ne contiennent pas eux-mêmes de cgroups enfants). Cela évite la nécessité de décider comment répartir les ressources entre les processus qui sont membres du cgroup A et les processus des cgroups enfants de

A.

Par exemple, si le cgroup /cg1/cg2 existe, alors un processus peut résider dans /cg1/cg2, mais pas dans /cg1. Cela sert à éviter une ambiguïté des cgroups v1 concernant la délégation des ressources entre les processus dans /cg1 et ses cgroups enfants. L'approche recommandée dans les cgroups v2 est de créer un sous-répertoire appelé leaf pour tout cgroup non feuille qui doit contenir des processus, mais pas de cgroups enfants. Ainsi, les processus qui auparavant seraient allés dans /cg1 iraient maintenant dans /cg1/leaf. Cela a l'avantage de rendre explicite la relation entre les processus dans /cg1/leaf et les autres enfants de /cg1

La règle « pas de processus internes » est en fait plus subtile que ce qui est indiqué ci-dessus. Plus précisément, la règle est qu'un cgroup (non racine) ne peut pas à la fois (1) avoir des processus membres et (2) distribuer des ressources aux cgroups enfants — c'est-à-dire avoir un fichier cgroup.subtree_control non vide. PRIVILÉGIÉ

Dans le contexte des cgroups, la délégation signifie confier la gestion d'un sous-arbre de la hiérarchie des cgroups à un utilisateur non privilégié. Délégation Cgroups v2 : nsdelegate et espaces de noms cgroup

À partir de Linux 4.13, il existe un deuxième moyen d'effectuer la délégation de cgroup dans la hiérarchie cgroups v2. Ceci est fait en montant ou en remontant le système de fichiers cgroup v2 avec l'option de montage nsdelegate. Par exemple, si le système de fichiers cgroup v2 a déjà été monté, nous pouvons le remonter avec l'option nsdelegate comme suit :


mount -t cgroup2 -o remount,nsdelegate \
                 none /sys/fs/cgroup/unified

L'effet de cette option de montage est de faire des espaces de noms cgroup des frontières de délégation automatiques. Plus précisément, les restrictions suivantes s'appliquent aux processus à l'intérieur de l'espace de noms cgroup :

•
Les écritures dans les fichiers d'interface du contrôleur dans le répertoire racine de l'espace de noms échoueront avec l'erreur EPERM. Les processus à l'intérieur de l'espace de noms cgroup peuvent toujours écrire dans les fichiers délégables dans le répertoire racine de l'espace de noms cgroup tels que cgroup.procs et cgroup.subtree_control, et peuvent créer une sous-hiérarchie sous le répertoire racine.
•
Les tentatives de migration de processus à travers la frontière de l'espace de noms sont refusées (avec l'erreur ENOENT). Les processus à l'intérieur de l'espace de noms cgroup peuvent toujours (sous réserve des règles de confinement décrites ci-dessous) déplacer des processus entre les cgroups à l'intérieur de la sous-hiérarchie sous la racine de l'espace de noms.

La capacité de définir les espaces de noms cgroup comme frontières de délégation rend les espaces de noms cgroup plus utiles. Pour comprendre pourquoi, supposons que nous ayons déjà une hiérarchie de cgroup qui a été déléguée à un utilisateur non privilégié, cecilia, en utilisant la technique de délégation plus ancienne décrite ci-dessus. Supposons en outre que cecilia souhaitait déléguer davantage une sous-hiérarchie sous la hiérarchie déléguée existante. (Par exemple, la hiérarchie déléguée pourrait être associée à un conteneur non privilégié exécuté par cecilia.) Même si un espace de noms cgroup était utilisé, étant donné que les deux hiérarchies appartiennent à l'utilisateur non privilégié cecilia, les actions illégitimes suivantes pourraient être effectuées :

•
Un processus de la hiérarchie inférieure pourrait modifier les paramètres du contrôleur de ressources dans le répertoire racine de cette hiérarchie. (Ces paramètres du contrôleur de ressources sont destinés à permettre le contrôle depuis le cgroup parent ; un processus à l'intérieur du cgroup enfant ne devrait pas être autorisé à les modifier.)
•
Un processus à l'intérieur de la hiérarchie inférieure pourrait déplacer des processus à l'intérieur et à l'extérieur de la hiérarchie inférieure si les cgroups de la hiérarchie supérieure étaient d'une manière ou d'une autre visibles.

L'utilisation de l'option de montage nsdelegate empêche ces deux possibilités.

L'option de montage nsdelegate n'a d'effet que lorsqu'elle est effectuée dans l'espace de noms de montage initial ; dans d'autres espaces de noms de montage, l'option est silencieusement ignorée.

Note : sur certains systèmes, systemd(1) monte automatiquement le système de fichiers cgroup v2. Afin d'expérimenter l'opération nsdelegate, il peut être utile de démarrer le noyau avec les options de ligne de commande suivantes :


cgroup_no_v1=all systemd.legacy_systemd_cgroup_controller

Ces options amènent le noyau à démarrer avec les contrôleurs cgroups v1 désactivés (ce qui signifie que les contrôleurs sont disponibles dans la hiérarchie v2), et indiquent à systemd(1) de ne pas monter et d'utiliser la hiérarchie cgroup v2, afin que la hiérarchie v2 puisse être montée manuellement avec les options souhaitées après le démarrage.

Règles de confinement de délégation de cgroup

Certaines règles de confinement de délégation garantissent que le délégataire peut déplacer des processus entre les cgroups au sein du sous-arbre délégué, mais ne peut pas déplacer des processus de l'extérieur du sous-arbre délégué vers le sous-arbre ou vice versa. Un processus non privilégié (c'est-à-dire le délégataire) peut écrire le PID d'un processus "cible" dans un fichier cgroup.procs uniquement si toutes les conditions suivantes sont remplies :

•
L'écrivain a l'autorisation d'écrire sur le fichier cgroup.procs dans le cgroup de destination.
•
L'écrivain a l'autorisation d'écrire sur le fichier cgroup.procs dans l'ancêtre commun le plus proche des cgroups source et destination. Notez que dans certains cas, l'ancêtre commun le plus proche peut être le cgroup source ou destination lui-même. Cette exigence n'est pas appliquée pour les hiérarchies cgroups v1, avec la conséquence que le confinement en v1 est moins strict qu'en v2. (Par exemple, en cgroups v1, l'utilisateur qui possède deux sous-hiérarchies déléguées distinctes peut déplacer un processus entre les hiérarchies.)
•
Si le système de fichiers cgroup v2 a été monté avec l'option nsdelegate, l'écrivain doit pouvoir voir les cgroups source et destination depuis son espace de noms cgroup.
•
En cgroups v1 : l'UID effectif de l'écrivain (c'est-à-dire le délégataire) correspond à l'ID utilisateur réel ou à l'ID utilisateur sauvegardé du processus cible. Avant Linux 4.11, cette exigence s'appliquait également aux cgroups v2 (C'était une exigence historique héritée des cgroups v1 qui a été jugée inutile par la suite, car les autres règles suffisent pour le confinement dans les cgroups v2.)

Note : une conséquence de ces règles de confinement de délégation est que le délégataire non privilégié ne peut pas placer le premier processus dans le sous-arbre délégué ; au lieu de cela, le délégant doit placer le premier processus (un processus appartenant au délégataire) dans le sous-arbre délégué.

MODE THREAD CGROUPS VERSION 2

Parmi les restrictions imposées par cgroups v2 qui n'étaient pas présentes dans cgroups v1 figurent les suivantes :

•
Pas de contrôle au niveau des threads : tous les threads d'un processus doivent être dans le même cgroup.
•
Pas de processus internes : un cgroup ne peut pas avoir de processus membres et exercer des contrôleurs sur des cgroups enfants.

Ces deux restrictions ont été ajoutées car l'absence de ces restrictions avait causé des problèmes dans cgroups v1. En particulier, la capacité de cgroups v1 à permettre une granularité au niveau des threads pour l'appartenance aux cgroups n'avait aucun sens pour certains contrôleurs. (Un exemple notable était le contrôleur memory : comme les threads partagent un espace d'adressage, il n'avait aucun sens de diviser les threads entre différents cgroups memory.)

Nonobstant la décision de conception initiale dans cgroups v2, il existait des cas d'utilisation pour certains contrôleurs, notamment le contrôleur cpu, pour lesquels la granularité au niveau des threads du contrôle était significative et utile. Pour répondre à de tels cas d'utilisation, Linux 4.14 a ajouté le mode thread pour cgroups v2.

Le mode thread permet les choses suivantes :

•
La création de sous-arbres filetés dans lesquels les threads d'un processus peuvent être répartis entre les cgroups à l'intérieur de l'arbre. (Un sous-arbre filé peut contenir plusieurs processus multithreadés.)
•
Le concept de contrôleurs filetés, qui peuvent distribuer les ressources entre les cgroups d'un sous-arbre filé.
•
Un assouplissement de la règle "pas de processus internes", de sorte que, dans un sous-arbre filé, un cgroup peut à la fois contenir des threads membres et exercer un contrôle des ressources sur les cgroups enfants.

Avec l'ajout du mode thread, chaque cgroup non racine contient maintenant un nouveau fichier, cgroup.type, qui expose, et dans certaines circonstances peut être utilisé pour changer, le "type" d'un cgroup. Ce fichier contient l'une des valeurs de type suivantes :

domain
Ceci est un cgroup v2 normal qui fournit un contrôle au niveau du processus. Si un processus est membre de ce cgroup, alors tous les threads du processus sont (par définition) dans le même cgroup. C'est le type de cgroup par défaut, et il offre le même comportement que celui fourni pour les cgroups dans l'implémentation initiale de cgroups v2.
threaded
Ce cgroup est membre d'un sous-arbre filé. Des threads peuvent être ajoutés à ce cgroup, et des contrôleurs peuvent être activés pour le cgroup.
domain threaded
Ceci est un cgroup de domaine qui sert de racine à un sous-arbre filé. Ce type de cgroup est également connu sous le nom de "racine filée".
domain invalid
Ceci est un cgroup à l'intérieur d'un sous-arbre filé qui est dans un état "invalide". Les processus ne peuvent pas être ajoutés au cgroup, et les contrôleurs ne peuvent pas être activés pour le cgroup. La seule chose qui peut être faite avec ce cgroup (autre que sa suppression) est de le convertir en un cgroup threaded en écrivant la chaîne "threaded" dans le fichier cgroup.type.
La raison d'être de ce type "intermédiaire" lors de la création d'un sous-arbre filé (plutôt que le noyau ne convertisse simplement immédiatement tous les cgroups sous la racine filée en type threaded) est de permettre d'éventuelles extensions futures au modèle de mode thread.

Contrôleurs filetés versus contrôleurs de domaine

Avec l'ajout du mode threads, cgroups v2 distingue désormais deux types de contrôleurs de ressources :

•
Contrôleurs filetés : ces contrôleurs prennent en charge la granularité des threads pour le contrôle des ressources et peuvent être activés à l'intérieur des sous-arbres filetés, avec pour résultat que les fichiers d'interface du contrôleur correspondants apparaissent à l'intérieur des cgroups du sous-arbre filé. En date de Linux 4.19, les contrôleurs suivants sont filetés : cpu, perf_event, et pids.
•
Contrôleurs de domaine : ces contrôleurs ne prennent en charge que la granularité des processus pour le contrôle des ressources. Du point de vue d'un contrôleur de domaine, tous les threads d'un processus sont toujours dans le même cgroup. Les contrôleurs de domaine ne peuvent pas être activés à l'intérieur d'un sous-arbre filé.

•
Le type du cgroup parent, y, devient domain threaded. Le cgroup parent est la racine d'un sous-arbre à fils (également connu sous le nom de « threaded root

Nous écrivons la chaîne "threaded" dans chacun des cgroups domain invalid sous y, afin de les convertir en type threaded. En conséquence de cette étape, tous les fils sous la racine à fils ont maintenant le type threaded et le sous-arbre à fils est désormais pleinement utilisable. La nécessité d'écrire "threaded" dans chacun de ces cgroups est quelque peu fastidieuse, m

Utilisation d'un sous-arbre à

fils

Au sein d'un sous-arbre à fils, les contrôleurs à fils peuvent être activés dans chaque sous-groupe dont le type a été changé en threaded ; lors de cette opération, les fichiers d'interface du correspondant apparaissent dans les enfants de ce

cgroup.

Un processus peut être déplacé dans un sous-arbre à fils en écrivant son PID dans le fichier cgroup.procs dans l'un des cgroups à l'intérieur de l'arbre. Cela a pour effet de faire de tous les fils du processus des membres du cgroup correspondant et de faire du processus un membre du sous-arbre à fils. Les fils du processus peuvent ensuite être répartis dans le sous-arbre à fils en écrivant leurs identifiants de fil (voir gettid(2)) dans les fichiers cgroup.threads dans différents cgroups à l'intérieur du sous-arbre. Les fils d'un processus doivent tous résider dans le même sous-arbre à

fils.

Comme pour l'écriture dans cgroup.procs, certaines règles de confinement s'appliquent lors de l'écriture dans le fichier cgroup.threads

:
•
L'écrivain doit avoir la permission d'écriture sur le fichier cgroup.threads dans le cgroup de
destination.
•
L'écrivain doit avoir la permission d'écriture sur le fichier cgroup.procs dans l'ancêtre commun des cgroups source et destination. (Dans certains cas, l'ancêtre commun peut être le cgroup source ou destination lui-même.
)
•
Les cgroups source et destination doivent être dans le même sous-arbre à fils. (En dehors d'un sous-arbre à fils, une tentative de déplacer un fil en écrivant son identifiant de fil dans le fichier cgroup.threads dans un cgroup domain différent échoue avec l'erreur EOPNOT
SUP
P.)

Le fichier cgroup.threads est présent dans chaque cgroup (y compris les cgroups domain) et peut être lu afin de découvrir l'ensemble des fils présents dans le cgroup. L'ensemble des identifiants de fil obtenu lors de la lecture de ce fichier n'est pas garanti d'être trié ou exempt de

doublons.

Le fichier cgroup.procs dans la racine à fils affiche les PID de tous les processus qui sont membres du sous-arbre à fils. Les fichiers cgroup.procs dans les autres cgroups du sous-arbre ne sont pas

lisibles.

Les contrôleurs de domaine ne peuvent pas être activés dans un sous-arbre à fils ; aucun fichier d'interface de contrôleur n'apparaît à l'intérieur des cgroups situés sous la racine à fils. Du point de vue d'un contrôleur de domaine, les sous-arbres à fils sont invisibles : un processus multi-fils à l'intérieur d'un sous-arbre à fils apparaît à un contrôleur de domaine comme un processus qui réside dans le cgroup racine à

fils.

Au sein d'un sous-arbre à fils, la règle « pas de processus internes

» ne s'applique pas : un cgroup peut à la fois contenir des processus
membres (ou fils) et exercer des contrôleurs sur les cgroups enfants.

Règles pour l'écriture dans cgroup.type et la création de sous-arbres à

fils

Un certain nombre de règles s'appliquent lors de l'écriture dans le fichier cgroup.type

:
•
Seule la chaîne "threaded" peut être écrite. En d'autres termes, la seule transition explicite possible est de convertir un cgroup domain en type threade
d.
•
L'effet de l'écriture de "threaded" dépend de la valeur actuelle dans cgroup.type,
comme
suit :
•
domain ou domain threaded : commencer la création d'un sous-arbre à fils (dont la racine est le parent de ce cgroup) via la première des voies décrites ci-dessus

•
domain invalid : convertir ce cgroup (qui se trouve dans un sous-arbre à fils) en état utilisable (c'est-à-dire threade

•
threaded : aucun effet (une « no-op

•
Nous ne pouvons pas écrire dans un fichier cgroup.type si le type du parent est domain invalid. En d'autres termes, les cgroups d'un sous-arbre à fils doivent être convertis en état threaded de manière de
scendante

Il existe également certaines contraintes qui doivent être satisfaites afin de créer un sous-arbre à fils enraciné au cgroup x

•
Il ne peut pas y avoir de processus membres dans les cgroups descendants de x. (Le cgroup x peut lui-même avoir des processus membres.

•
Aucun contrôleur de domaine ne peut être activé dans le fichier cgroup.subtree_control de x

Le type de cgroup « domain threaded

Selon les voies décrites ci-dessus, le type d'un cgroup peut changer en domain threaded dans l'un des cas suivants

•
La chaîne "threaded" est écrite dans un cgroup
enfant.
•
Un contrôleur à fils est activé à l

Un cgroup domain threaded, x, peut revenir au type domain si les conditions ci-dessus ne sont plus remplies — c'est-à-dire si tous les cgroups enfants threaded de x sont supprimés et soit x n'a plus de contrôleurs à fils activés, soit n'a plus de processus

•
Tous les descendants domain invalid de x qui ne sont pas dans des sous-arbres à fils de niveau inférieur reviennent au type domai
n.
•
Les cgroups racines dans tous les sous-arbres à fils de niveau inférieur reviennent au type domain
thr

Exceptions pour le cgroup

racine

Le cgroup racine de la hiérarchie v2 est traité de manière exceptionnelle : il peut être le parent à la fois de cgroups domain et threaded. Si la chaîne "threaded" est écrite dans le fichier cgroup.type de l'un des enfants du cgroup racine,

alors
•
Le type de ce cgroup devient threade
d.
•
Le type de tous les descendants de ce cgroup qui ne font pas partie de sous-arbres à fils de niveau inférieur change en domain i
nva
lid.

Notez que dans ce cas, il n'y a pas de cgroup dont le type devient domain threaded. (Notionnellement, le cgroup racine peut être considéré comme la racine à fils pour le cgroup dont le type a été changé en threade

d.)

Le but de ce traitement exceptionnel du cgroup racine est de permettre à un cgroup à fils qui utilise le contrôleur cpu d'être placé aussi haut que possible dans la hiérarchie, af

in de minimiser le (petit) coût de
parcours de la hiérarchie des cgroups.

Le contrôleur « cpu » des cgroups v2 et les fils temps

réel

À partir de Linux 4.19, le contrôleur cpu des cgroups v2 ne prend pas en charge le contrôle des fils temps réel (plus précisément les fils planifiés selon l'une des politiques SCHED_FIFO, SCHED_RR, décrites SCHED_DEADLINE ; voir sched(7)). Par conséquent, le contrôleur cpu ne peut être activé dans le cgroup racine que si tous les fils temps réel se trouvent dans le cgroup racine. (S'il y a des fils temps réel dans des cgroups non racines, alors un write(2) de la chaîne «+cpu» au fichier cgroup.subtree_control échoue avec l'erreur EINVA

L.)

Sur certains systèmes, systemd(1) place certains threads temps réel dans des cgroups non racine dans la hiérarchie v2. Sur de tels systèmes, ces threads doivent d'abord être déplacés vers le cgroup racine avant que le contrôleur cpu

puisse ê
