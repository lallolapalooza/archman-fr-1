DESCRIPTIO

N

CGI::Cookie est une interface pour les cookies HTTP/1.1, un mécanisme qui permet aux serveurs Web de stocker des informations persistantes du côté navigateur de la connexion. Bien que CGI::Cookie soit destiné à être utilisé en conjonction avec CGI.pm (et est en fait utilisé par lui en interne), vous pouvez utiliser ce module

indépendamment.

Pour des informations complètes sur les cookies,

voir https://tools.ietf.org/html/rfc626
5

UTILISATION DE CGI::

Cookie

CGI::Cookie est orienté objet. Chaque objet cookie a un nom et une valeur. Le nom est n'importe quelle valeur scalaire. La valeur est n'importe quelle valeur scalaire ou tableau (les tableaux associatifs sont également autorisés). Les cookies ont aussi plusieurs attributs facultatifs, notamment

:
1. date
d'expiration
La date d'expiration indique au navigateur combien de temps conserver le cookie. Si le cookie spécifie une date d'expiration dans le futur, le navigateur stockera les informations du cookie dans un fichier disque et les renverra au serveur à chaque fois que l'utilisateur se reconnecte (jusqu'à ce que la date d'expiration soit atteinte). Si le cookie spécifie une date d'expiration dans le passé, le navigateur supprimera le cookie du fichier disque. Si la date d'expiration n'est pas spécifiée, le cookie ne persistera que jusqu'à ce que l'utilisateur quitte le
navigateur.
2.
domaine
Il s'agit d'un nom de domaine partiel ou complet pour lequel le cookie est valide. Le navigateur renverra le cookie à tout hôte correspondant au nom de domaine partiel. Par exemple, si vous spécifiez un nom de domaine ".capricorn.com", le navigateur renverra le cookie aux serveurs Web s'exécutant sur n'importe laquelle des machines "www.capricorn.com", "ftp.capricorn.com", "feckless.capricorn.com", etc. Les noms de domaine doivent contenir au moins deux points pour empêcher les tentatives de correspondance avec des domaines de premier niveau comme ".edu". Si aucun domaine n'est spécifié, le navigateur ne renverra le cookie qu'aux serveurs sur l'hôte d'où le cookie
provient.
3.
chemin
Si vous fournissez un attribut de chemin de cookie, le navigateur le vérifiera par rapport à l'URL de votre script avant de renvoyer le cookie. Par exemple, si vous spécifiez le chemin "/cgi-bin", le cookie sera renvoyé à chacun des scripts "/cgi-bin/tally.pl", "/cgi-bin/order.pl", et "/cgi-bin/customer_service/complain.pl", mais pas au script "/cgi-private/site_admin.pl". Par défaut, le chemin est défini sur "/", afin que tous les scripts de votre site reçoivent le
cookie.
4. indicateur
secure
Si l'attribut "secure" est défini, le cookie ne sera envoyé à votre script que si la requête CGI s'effectue sur un canal sécurisé, tel que
SSL.
5. indicateur
httponly
Si l'attribut "httponly" est défini, le cookie ne sera accessible que par le biais de requêtes HTTP. Ce cookie sera inaccessible via JavaScript (pour prévenir les attaques XSS).

Cette fonctionnalité est prise en charge par presque tous les navigateurs

modernes.

CRÉATION DE NOUVEAUX

COOKIES 
my $c = CGI::Cookie->new(-name    =>  'foo',
                     -value   =>  'bar',
                     -expires =>  '+3M',
                   '-max-age' =>  '+3M',
                     -domain  =>  '.capricorn.com',
                     -path    =>  '/cgi-bin/database',
                     -secure  =>  1,
                     -samesite=>  "Lax",
                     -priority=>  "High",
                    )
;

Créez des cookies à partir de zéro avec la méthode new. Les paramètres -name et -value sont requis. Le nom doit être une valeur scalaire. La valeur peut être un scalaire, une référence de tableau, ou une référence de hachage. (À un certain moment dans le futur, les cookies prendront en charge l'un des protocoles de sérialisation d'objets Perl pour une pleine généralité)

.

-expires accepte n'importe lequel des formats de date relatifs ou absolus reconnus par CGI.pm, par exemple "+3M" pour trois mois dans le futur. Voir la documentation de CGI.pm pour plus de

détails.

-max-age accepte les mêmes formats de données que -expires, mais définit une valeur relative au lieu d'une valeur absolue comme -expires. Ceci est destiné à être plus sécurisé car une horloge pourrait être modifiée pour falsifier une heure absolue. En pratique, en 2011, "-max-age" ne bénéficie toujours pas de la prise en charge généralisée dont "-expires" bénéficie. Vous pouvez définir les deux, et les navigateurs qui prennent en charge "-max-age" devraient ignorer l'en-tête "Expires". L'inconvénient de cette approche est la bande passante utilisée pour envoyer un en-tête supplémentaire pour chaque

cookie.

-domain pointe vers un nom de domaine ou vers un nom d'hôte complètement qualifié. S'il n'est pas spécifié, le cookie ne sera renvoyé qu'au serveur Web qui l'a

créé.

-path pointe vers une URL partielle sur le serveur actuel. Le cookie sera renvoyé à toutes les URLs commençant par le chemin spécifié. S'il n'est pas spécifié, il vaut par défaut '/', ce qui renvoie le cookie à toutes les pages de votre

site.

-secure si défini à une valeur vraie, indique au navigateur de renvoyer le cookie uniquement lorsqu'un protocole cryptographique est

utilisé.

-httponly si défini à une valeur vraie, le cookie ne sera pas accessible via

JavaScript.

-samesite peut être "Lax", "Strict", ou "None" et fait partie des normes en évolution pour les cookies. Veuillez vous référer à la documentation actuelle à ce

sujet.

Pour la compatibilité avec Apache::Cookie, vous pouvez éventuellement passer un objet de requête mod_perl comme premier argument à new(). Il sera simplement ignoré

: 
my $c = CGI::Cookie->new($r,
                        -name    =>  'foo',
                        -value   =>  ['bar','baz']
)
;
