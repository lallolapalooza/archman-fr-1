DESCRIPTIO

N

CGI.pm est une solution stable, complète et mature pour le traitement et la préparation des requêtes et des réponses HTTP. Ses fonctionnalités principales incluent le traitement des soumissions de formulaires, le téléversement de fichiers, la lecture et l'écriture des cookies, la génération et la manipulation des chaînes de requête, ainsi que le traitement et la préparation des en-têtes

HTTP.

CGI.pm performe très bien dans un environnement CGI.pm standard et inclut également un support intégré pour mod_perl et mod_perl2 ainsi que

FastCGI.

Il a l'avantage d'avoir été développé et affiné pendant 20 ans avec les contributions de dizaines de contributeurs et d'être déployé sur des milliers de sites web. CGI.pm était inclus dans la distribution perl de perl v5.4 à v5.20, mais il a maintenant été retiré du cœur de perl.

Style de

programmation

Il existe deux styles de programmation avec CGI.pm, un style orienté objet (OO) et un style orienté fonction. Il est recommandé d'utiliser le style OO car CGI.pm créera un objet interne par défaut lorsque les fonctions sont appelées de manière procédurale et vous n'aurez pas à vous soucier des conflits de noms de méthodes avec les fonctions intégrées de

perl.

Dans le style orienté objet, vous créez un ou plusieurs objets CGI puis utilisez des méthodes d'objet pour créer les différents éléments de la page. Chaque objet CGI commence avec la liste des paramètres nommés qui ont été passés à votre script CGI par le serveur. Vous pouvez modifier les objets, les sauvegarder dans un fichier ou une base de données et les recréer. Comme chaque objet correspond à l'« état » du script CGI, et comme la liste de paramètres de chaque objet est indépendante des autres, cela vous permet de sauvegarder l'état du script et de le restaurer plus

tard.

Par exemple, en utilisant le style orienté objet

: 
#!/usr/bin/env perl
use strict;
use warnings;
use CGI;                             # load CGI routines
my $q = CGI->new;                    # create new CGI object
print $q->header;                    # create the HTTP
header

Dans le style orienté fonction, il y a un objet CGI par défaut avec lequel vous n'interagissez que rarement directement. À la place, vous appelez simplement des fonctions pour récupérer les paramètres CGI, gérer les cookies, etc. L'exemple suivant est identique au précédent en termes de sortie, mais utilise l'interface orientée fonction. Les principales différences sont que nous devons maintenant importer un ensemble de fonctions dans notre espace de noms (généralement les fonctions « standard »), et que nous n'avons pas besoin de créer l'objet

CGI. 
#!/usr/bin/env perl
use strict;
use warnings;
use CGI qw/:standard/;           # load standard CGI routines
print header();                  # create the HTTP
header

Les exemples de ce document utilisent principalement le style orienté objet. Voir COMMENT IMPORTER LES FONCTIONS pour des informations importantes sur la programmation orientée fonction dans CGI.

Appeler les routines de CGI.

pm

La plupart des routines de CGI.pm acceptent plusieurs arguments, parfois jusqu'à 20 arguments optionnels ! Pour simplifier cette interface, toutes les routines utilisent un style d'appel par argument nommé qui ressemble à ceci

: 
print $q->header(
    -type    => 'image/gif',
    -expires => '+3d',
)
;

Chaque nom d'argument est précédé d'un tiret. Ni la casse ni l'ordre n'importent dans la liste d'arguments : -type, -Type et -TYPE sont tous acceptables. En fait, seul le premier argument doit commencer par un tiret. Si un tiret est présent dans le premier argument, CGI.pm suppose des tirets pour les

suivants.

Plusieurs routines sont couramment appelées avec un seul argument. Dans le cas de ces routines, vous pouvez fournir l'argument unique sans nom d'argument. header() est justement l'une de ces routines. Dans ce cas, l'argument unique est le type de

document. 
print $q->header('text/html')
;

Les autres routines de ce type sont documentées

ci-dessous.

Parfois, les arguments nommés attendent un scalaire, parfois une référence à un tableau, et parfois une référence à un hachage. Souvent, vous pouvez passer n'importe quel type d'argument et la routine fera ce qui est le plus approprié. Par exemple, la routine param() est utilisée pour définir un paramètre CGI avec une valeur simple ou une valeur multi-valuée. Les deux cas sont montrés ci-dessous

: 
$q->param(
    -name  => 'veggie',
    -value => 'tomato',
);
$q->param(
    -name  => 'veggie',
    -value => [ qw/tomato tomahto potato potahto/ ],
)
;

De nombreuses routines feront quelque chose d'utile avec un argument nommé qu'elles ne reconnaissent pas. Par exemple, vous pouvez produire des champs d'en-tête HTTP non standard en les fournissant comme arguments nommés

: 
print $q->header(
    -type            => 'text/html',
    -cost            => 'Three smackers',
    -annoyance_level => 'high',
    -complaints_to   => 'bit bucket',
)
;

Cela produira l'en-tête HTTP non standard suivant

: 
HTTP/1.0 200 OK
Cost: Three smackers
Annoyance-level: high
Complaints-to: bit bucket
Content-type:
text/html

Cela écrira l'état actuel du formulaire dans le gestionnaire de fichier fourni. Vous pouvez le relire en fournissant un gestionnaire de fichier à la méthode new(). Notez que le gestionnaire de fichier peut être un fichier, un pipe, ou quoi que ce soit

Le format du fichier enregistré est

: 
NAME1=VALUE1
NAME1=VALUE1'
NAME2=VALUE2
NAME3=VALUE3
=

Le nom et la valeur sont tous deux échappés pour une utilisation dans une URL. Les paramètres CGI à valeurs multiples sont représentés par des noms répétés. Un enregistrement de session est délimité par un seul symbole =. Vous pouvez écrire plusieurs enregistrements et les relire avec plusieurs appels à new. Vous pouvez faire cela sur plusieurs sessions en ouvrant le fichier en mode ajout, ce qui vous permet de créer des livres d'or primitifs, ou de conserver un historique des requêtes des utilisateurs. Voici un court exemple de création de plusieurs enregistrements de session

: 
use strict;
use warnings;
use CGI;
open (my $out_fh,'>>','test.out') || die "Can't open test.out: $!";
my $records = 5;
for ( 0 .. $records ) {
    my $q = CGI->new;
    $q->param( -name => 'counter',-value => $_ );
    $q->save( $out_fh );
}
close( $out_fh );
# reopen for reading
open (my $in_fh,'<','test.out') || die "Can't open test.out: $!";
while (!eof($in_fh)) {
    my $q = CGI->new($in_fh);
    print $q->param('counter'),"\n";
}

if ( my $error = $q->cgi_error ) {

    exit 0;
}

Pour utiliser l'interface orientée fonction, vous devez spécifier quelles routines de CGI.pm ou quels ensembles de routines importer dans l'espace de noms de votre script. Il y a une petite surcharge associée à cette importation, mais elle n'est pas très

Les méthodes listées seront importées dans le package courant ; vous pouvez les appeler directement sans avoir à créer d'abord un objet CGI. Cet exemple montre comment importer les méthodes param() et header(), puis les utiliser directement

: 
use strict;
use warnings;
use CGI qw/ param header /;
print header('text/plain');

GÉNÉRATION DE DOCUMENTS

DYNAMIQUES

La plupart des fonctions de CGI.pm traitent de la création de documents à la volée. Généralement, vous produirez d'abord l'en-tête HTTP, suivi du document lui-même. CGI.pm fournit des fonctions pour générer des en-têtes HTTP de divers

types.

Chacune de ces fonctions produit un fragment HTTP que vous pouvez imprimer directement pour qu'il soit traité par le navigateur, l'ajouter à une chaîne, ou l'enregistrer dans un fichier pour une utilisation

ultérieure.

Création d'un en-tête http

standard

Normalement, la première chose que vous ferez dans n'importe quel script CGI est d'imprimer un en-tête HTTP. Cela indique au navigateur le type de document à attendre, et donne d'autres informations facultatives, telles que la langue, la date d'expiration, et s'il faut mettre le document en cache. L'en-tête peut aussi être manipuléed pour des buts spéciaux, tels que le push de serveur et les pages à paiement à la

vue. 
use strict;
use warnings;
use CGI;
my $cgi = CGI->new;
print $cgi->header;
    -ou-
print $cgi->header('image/gif');
    -ou-
print $cgi->header('text/html','204 No response');
    -ou-
print $cgi->header(
    -type       => 'image/gif',
    -nph        => 1,
    -status     => '402 Payment required',
    -expires    => '+3d',
    -cookie     => $cookie,
    -charset    => 'utf-8',
    -attachment => 'foo.gif',
    -Cost       => '$2.00'
)
;

header() renvoie l'en-tête Content-type:. Vous pouvez fournir votre propre type MIME si vous le souhaitez, sinon il est par défaut text/html. Un second paramètre facultatif spécifie le code de statut et un message lisible par l'homme. Par exemple, vous pouvez spécifier 204, "No response" pour créer un script qui indique au navigateur de ne rien faire du tout. Notez que la RFC 2616 attend que la phrase lisible par l'homme soit présente en plus du code de statut

numérique.

Le dernier exemple montre le style d'arguments nommés pour passer des arguments aux méthodes CGI en utilisant des paramètres nommés. Les paramètres reconnus sont -type, -status, -expires, et -cookie. Tout autre paramètre nommé verra ses tirets initiaux supprimés et sera converti en champ d'en-tête, vous permettant de spécifier n'importe quel en-tête HTTP que vous désirez. Les tirets bas internes seront convertis en tirets

: 
print $cgi->header( -Content_length => 3002 )
;

La plupart des navigateurs ne mettent pas en cache la sortie des scripts CGI. Chaque fois que le navigateur recharge la page, le script est invoqué à nouveau. Vous pouvez changer ce comportement avec le paramètre -expires. Quand vous spécifiez un intervalle d'expiration absolu ou relatif avec ce paramètre, certains navigateurs et serveurs proxy mettront en cache la sortie du script jusqu'à la date d'expiration indiquée. Les formes suivantes sont toutes valides pour le champ -expires

: 
+30s                                  30 secondes à partir de maintenant
+10m                                  dix minutes à partir de maintenant
+1h                                   une heure à partir de maintenant
-1d                                   hier (c'est-à-dire "Dès que possible !")
now                                   immédiatement
+3M                                   dans trois mois
+10y                                  dans dix ans
Thursday, 25-Apr-2018 00:40:33 GMT    à l'heure et à la date
indiquées

Le paramètre -cookie génère un en-tête qui indique au navigateur de fournir un "cookie magique" lors de toutes les transactions ultérieures avec votre script. Certains cookies ont un format spécial qui inclut des attributs intéressants tels que le temps d'expiration. Utilisez la méthode cookie() pour créer et récupérer les cookies de

session.

Le paramètre -nph, s'il est défini à une valeur vraie, émettra les en-têtes corrects pour fonctionner avec un script NPH (no-parse-header). C'est important à utiliser avec certains serveurs qui attendent que tous leurs scripts soient

NPH.

Le paramètre -charset peut être utilisé pour contrôler le jeu de caractères envoyé au navigateur. S'il n'est pas fourni, la valeur par défaut est ISO-8859-1. En effetet de bord, cela définit aussi la méthode charset(). Notez que la valeur par défaut étant ISO-8859-1 peut ne pas avoir de sens pour tous les types de contenu, par exemple

:

1

défaut.

Le paramètre -attachment peut être utilisé pour transformer la page en pièce jointe. Au lieu d'afficher la page, certains navigateurs demanderont à l'utilisateur de l'enregistrer sur disque. La valeur de l'argument est le nom suggéré pour le fichier enregistré. Pour que cela fonctionne, vous devrez peut-être définir le -type à "application/octet-stream"

Le paramètre -p3p ajoutera une balise P3P à l'en-tête sortant. Le paramètre peut être une référence de tableau ou une chaîne délimitée par des espaces de balises P3P. Par exemple

Principes de

base

Lorsque le formulaire est traité, vous pouvez récupérer un descripteur de fichier compatible IO::File pour un champ de téléversement de fichier comme ceci

: 
use autodie;
# undef peut être renvoyé si ce n'est pas un descripteur de fichier valide
if ( my $io_handle = $q->upload('field_name') ) {
    open ( my $out_file,'>>','/usr/local/web/users/feedback' );
    while ( my $bytesread = $io_handle->read($buffer,1024) ) {
        print $out_file $buffer;
    }
}

Dans un contexte de liste, upload() renverra un tableau de descripteurs de fichier. Cela permet de traiter des formulaires qui utilisent le même nom pour plusieurs champs de

téléversement.

Si vous souhaitez obtenir le nom de fichier saisi pour le fichier, vous pouvez simplement appeler param()

: 
my $filename = $q->param('field_name')
;

Différents navigateurs renverront des choses légèrement différentes pour le nom. Certains navigateurs renvoient uniquement le nom de fichier. D'autres renvoient le chemin complet vers le fichier, en utilisant les conventions de chemin de la machine de l'utilisateur. Quoi qu'il en soit, le nom renvoyé est toujours le nom du fichier sur la machine de l'utilisateur, et n'a aucun rapport avec le nom du fichier temporaire que CGI.pm crée lors du spooling de téléversement (voir ci-dessous)

.

Lorsqu'un fichier est téléversé, le navigateur envoie généralement avec lui certaines informations dans les en-têtes Content-Type (type MIME) et Content-Disposition (nom de fichier). Pour récupérer ces informations, appelez uploadInfo(). Elle renvoie une référence vers un tableau associatif contenant tous les en-têtes du

document. 
my $filehandle = $q->upload( 'uploaded_file' );
my $type       = $q->uploadInfo( $filehandle )->{'Content-Type'};
if ( $type ne 'text/html' ) {
    die "HTML FILES ONLY!";
}

Notez que vous devez utiliser ->upload ou ->param pour obtenir le descripteur de fichier à passer à uploadInfo, car en interne il est représenté comme un objet File::Temp (ce qui est ce qui sera renvoyé par ->upload ou ->param). Lorsque vous utilisez ->Vars, vous obtiendrez le nom de fichier littéral plutôt que l'objet File::Temp, qui ne renverra rien lorsqu'il sera passé à uploadInfo. N'utilisez donc pas ->

Vars.

Lors du téléversement de plusieurs fichiers, appelez ->param() dans un contexte de liste pour récupérer une liste de descripteurs de fichier que vous pouvez utiliser lors de l'appel de ->

uploadInfo. 
my @filehandles = $q->param('uploaded_file');
for my $fh (@filehandles) {
  my $info = $q->uploadInfo($fh);
  ...
}

Si vous utilisez une machine qui reconnaît les modes de données "text" et "binary", assurez-vous de comprendre quand et comment les utiliser (voir le livre Camel). Sinon, vous pourriez constater que les fichiers binaires sont corrompus lors des téléversements de

fichiers.

Accès direct aux fichiers

temporaires

Lors du traitement d'un fichier téléversé, CGI.pm crée un fichier temporaire sur votre disque dur et vous passe un descripteur de fichier vers ce fichier. Une fois que vous avez terminé avec le descripteur de fichier, CGI.pm supprime (unlink) le fichier temporaire. Si nécessaire, vous pouvez accéder directement au fichier temporaire. Vous pouvez accéder au fichier temporaire d'un téléversement de fichier en passant le descripteur de fichier à la méthode tmpFileName()

: 
my $filehandle  = $q->upload( 'uploaded_file' );
my $tmpfilename = $q->tmpFileName( $filehandle )
;

Comme pour ->uploadInfo, il est préférable d'utiliser la référence renvoyée par ->upload ou ->param, bien que contrairement à ->uploadInfo, les noms de fichier simples fonctionnent aussi si possible pour la rétrocompatibilité

.

Le fichier temporaire sera supprimé automatiquement lorsque votre programme se termine, à moins que vous ne le renommiez manuellement ou que vous ne définissiez $CGI::UNLINK_TMP_FILES à 0. Sur certains systèmes d'exploitation (comme Windows NT), vous devrez fermer le descripteur de fichier du fichier temporaire avant que votre programme ne se termine. Sinon, la tentative de suppression du fichier temporaire

échouera.

Changements dans la gestion des fichiers temporaires (v4.

05+)

La gestion des fichiers temporaires de CGI.pm a été significativement refactorisée, cette logique est maintenant entièrement déléguée à File::Temp (qui est enveloppé dans un objet de compatibilité, CGI::File::Temp - N'UTILISEZ PAS CE PAQUETAGE DIRECTEMENT). Par conséquent, la variable PRIVATE_TEMPFILES a été supprimée, ainsi que la routine private_tempfiles dépréciée et la suppression complète du paquetage CGITempFile. Le $CGITempFile::TMPDIRECTORY n'est plus utilisé pour définir le répertoire temporaire, consultez la documentation perldoc de File::Temp si vous souhaitez remplacer les paramètres par défaut de ce paquetage (la variable d'environnement TMPDIR est toujours disponible sur certaines plateformes). Pour les plateformes Windows, l'ordre des répertoires temporaires reste comme avant : TEMP > TMP > WINDIR ( > TMPDIR ) donc si vous avez l'un de ces paramètres utilisés dans des scripts existants, ils devraient toujours

fonctionner.

Le paquetage Fh existe toujours mais ne fait rien, la classe CGI::File::Temp est une sous-classe à la fois de File::Temp et du paquetage vide Fh, donc si vous avez du code qui vérifie que le descripteur de fichier est un Fh, cela devrait toujours

fonctionner.

Lorsque vous obtenez le descripteur de fichier interne, vous recevrez un objet File::Temp, cela devrait être transparent car File::Temp est un IO::Handle et un IO::Seekable, ce qui signifie qu'il se comporte comme auparavant. Si vous faites quelque chose d'inhabituel concernant les fichiers temporaires, vous devriez tester votre code avant de déployer cette mise à jour et consulter la documentation de File::Temp pour plus

d'informations.

interrompus

Il y a occasionnellement des problèmes liés à l'analyse du fichier téléversé. Cela se produit généralement lorsque l'utilisateur appuie sur "Stop" avant que le téléversement ne soit terminé. Dans ce cas, CGI.pm renverra undef pour le nom du fichier téléversé et définira cgi_error() à la chaîne "400 Bad request (malformed multipart POST)". Ce message d'erreur est conçu pour que vous puissiez l'incorporer dans un code de statut à envoyer au navigateur. Exemple

Barres de progression pour les téléversements de fichiers et éviter les fichiers

temporaires

CGI.pm vous donne un accès de bas niveau à la gestion des téléversements de fichiers via un crochet (hook) de téléversement de fichier. Vous pouvez utiliser cette fonctionnalité pour désactiver complètement le stockage des fichiers temporaires des téléversements de fichiers, ou potentiellement écrire votre propre indicateur de progression de téléversement de

C'est très similaire à la fonctionnalité UPLOAD_HOOK disponible dans Apache::Request, à l'exception que le premier argument de la fonction de rappel est un objet Apache::Upload, ici c'est le nom de fichier

distant. 
my $q = CGI->new( \&hook [,$data [,$use_tempfile]] );

    my ( $filename, $buffer, $bytes_read, $data ) = @_;
    print "Read $bytes_read bytes of $filename\n";
}

Le champ $data est facultatif ; il vous permet de passer des informations de configuration (par exemple un descripteur de base de données) à votre fonction de rappel de

crochet.

ÉVITER LES ATTAQUES PAR DÉNI DE

SERVICE

Un problème potentiel de CGI.pm est que, par défaut, il tente de traiter les envois de formulaires POST quelle que soit leur taille. Un pirate malicieux pourrait attaquer votre site en envoyant à un script CGI un POST énorme de plusieurs gigaoctets. CGI.pm tentera de lire l'intégralité du POST dans une variable, augmentant énormément de taille jusqu'à ce qu'il manque de mémoire. Pendant que le script tente d'allouer la mémoire, le système peut ralentir considérablement. C'est une forme d'attaque par déni de

service.

Une autre attaque possible consiste à forcer CGI.pm à accepter un téléversement de fichier énorme. CGI.pm acceptera le téléversement et le stockera dans un répertoire temporaire même si votre script ne s'attend pas à recevoir un fichier téléversé. CGI.pm supprimera automatiquement le fichier lorsqu'il se terminera, mais entre-temps, l'utilisateur distant peut avoir rempli l'espace disque du serveur, causant des problèmes à d'autres

programmes.

La meilleure façon d'éviter les attaques par déni de service est de limiter la quantité de mémoire, de temps CPU et d'espace disque que les scripts CGI peuvent utiliser. Certains serveurs Web sont livrés avec des fonctionnalités intégrées pour accomplir cela. Dans d'autres cas, vous pouvez utiliser les commandes du shell limit ou ulimit pour établir des plafonds sur l'utilisation des ressources par les

CGI.

CGI.pm dispose également de protections intégrées simples contre les attaques par déni de service, mais vous devez les activer avant de pouvoir les utiliser. Elles prennent la forme de deux variables globales dans l'espace de noms CGI

:
$CGI::POST_MAX
Si défini à un entier non négatif, cette variable établit un plafond sur la taille des envois POST, en octets. Si CGI.pm détecte un POST supérieur au plafond, il quittera immédiatement avec un message d'erreur. Cette valeur affectera aussi bien les POST ordinaires que les POST multipart, ce qui signifie qu'elle limite également la taille maximale des téléversements de fichiers. Vous devriez la définir à une valeur raisonnablement élevée, comme 10
mégaoctets.
$CGI::DISABLE_UPLOADS
Si défini à une valeur non nulle, cela désactivera complèt
ement les téléversements de fichiers. Les autres val
eurs de formulaire seront traitées comme d'habitude. s="Pp">Pour utiliser ces variables, définissez la variable en haut du script, juste après l'instruction "use"

COMPATIBILITÉ AVEC CGI-LIB.

Pour faciliter la conversion des programmes existants qui utilisent cgi-lib.pl, la routine de compatibilité "ReadParse" est fournie. La conversion est simple

:

ANCIENNE

VERSION 
require "cgi-lib.pl";
&
print "The value of the antique is $in{antique}.
\n";

NOUVELLE

VERSION 
use CGI;
CGI::ReadParse();
print "The value of the antique is $in{antique}.
\n";

La routine ReadParse() de CGI.pm crée une variable liée nommée %in, qui peut être accédée pour obtenir les variables de la requête. Comme ReadParse, vous pouvez également fournir votre propre variable. Les fonctionnalités rarement utilisées de ReadParse, telles que la création de @in et $in, ne sont pas prises en

charge.

Une fois que vous avez utilisé ReadParse, vous pouvez récupérer l'objet requête lui-même de cette manière

: 
my $q = $in{CGI}
;

Cela vous permet de commencer à utiliser les fonctionnalités plus intéressantes de CGI.pm sans réécrire vos anciens scripts à partir de

zéro.

Une façon encore plus simple de mélanger les appels cgi-lib avec les appels CGI.pm est d'importer à la fois les ":cgi-lib" et ":standard"

: 
use CGI qw(:cgi-lib :standard);
&
print "The price of your purchase is $in{price}.\n";
print textfield(-name=>'price', -default=>'$1.99')
;
