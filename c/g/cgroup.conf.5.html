NOM

cgroup.conf - Fichier de configuration Slurm pour le support cgroup

DESCRIPTION

cgroup.conf est un fichier ASCII qui définit les paramètres utilisés par les plugins Slurm liés aux cgroups Linux. Le fichier est toujours situé dans le même répertoire que slurm.conf.

Les noms de paramètres ne sont pas sensibles à la casse. Tout texte suivant un "#" dans le fichier de configuration est traité comme un commentaire jusqu'à la fin de cette ligne. Les modifications apportées au fichier de configuration prennent effet lors du redémarrage des démons Slurm, de la réception du signal SIGHUP par les démons, ou de l'exécution de la commande "scontrol reconfigure", sauf indication contraire.

Pour des informations générales sur les cgroups Slurm, consultez le guide Cgroups sur https://slurm.schedmd.com/cgroups.html.

Les paramètres cgroup.conf suivants sont définis pour contrôler le comportement général des plugins cgroup de Slurm.

CgroupMountpoint=CHEMIN
Uniquement destiné au développement et aux tests. Spécifie le CHEMIN sous lequel les contrôleurs de cgroup doivent être montés. Le CHEMIN par défaut est /sys/fs/cgroup.
CgroupPlugin=<cgroup/v1|cgroup/v2|autodetect|disabled>
Spécifie le plugin à utiliser lors de l'interaction avec le sous-système cgroup. Les valeurs prises en charge sont "disabled", pour désactiver complètement toute interaction avec les cgroups, "cgroup/v1" qui prend en charge l'interface héritée de cgroup v1, "cgroup/v2" pour l'architecture unifiée cgroup2, et "autodetect" qui tente de déterminer la version de cgroup que votre système fournit. "autodetect" est utile pour avoir une configuration unique dans les clusters où les nœuds peuvent avoir différentes versions de cgroup. La valeur par défaut est "autodetect" sous Linux, sinon la valeur par défaut est "disabled".

NOTE : le plugin cgroup/v1 est déprécié et aucune nouvelle fonctionnalité n'y sera ajoutée. Il est recommandé de passer à cgroup/v2 dès que possible.

CgroupSlice=NOM_DE_SLICE
Démarre slurmd et le scope slurmstepd dans le slice spécifié. Si vous démarrez slurmd avec systemd, vous devriez également ajouter la propriété Slice= dans la section [Service] du fichier slurmd.service. La modification de ce paramètre nécessite l'arrêt de tous les scopes slurmstepd sur le nœud et le redémarrage de slurmd. Ne s'applique qu'à cgroup v2. La valeur par défaut est system.slice.
SystemdTimeout=<nombre>
Sur les systèmes lents comme les machines virtuelles ou lorsque systemd est occupé, il peut s'écouler beaucoup de temps pour initialiser et préparer le scope pour slurmd lors du démarrage. Slurm attendra un maximum de ce temps (en millisecondes) pour que le scope soit prêt avant d'échouer. Ne s'applique qu'à cgroup/v2. La valeur par défaut est 1000 ms.
IgnoreSystemd=<oui|non>
Uniquement pour cgroup/v2 et pour le développement et les tests. Cela évitera tout appel à dbus et tout contact avec systemd, et préparera à la place toute la hiérarchie cgroup manuellement. Cette option est dangereuse sur les systèmes avec systemd car le cgroup peut être modifié par systemd et causer des problèmes aux jobs.
IgnoreSystemdOnFailure=<oui|non>
Uniquement pour cgroup/v2 et pour le développement et les tests. Il a une fonctionnalité similaire à IgnoreSystemd mais uniquement dans le cas où un appel dbus ne réussit pas.
EnableControllers=<oui|non>
Uniquement pour cgroup/v2 et généralement pour le développement, les tests, lors de l'exécution sur des noyaux anciens et/ou des anciennes versions de systemd (par exemple, RHEL8, systemd < 244) où tous les contrôleurs ne sont pas activés dans l'arbre cgroup. Avec ce paramètre, slurmd récupère les contrôleurs disponibles depuis le fichier cgroup.controllers de la racine (CgroupMountPoint, par défaut /sys/fs/cgroup/cgroup.controllers) et les rend disponibles à tous les niveaux de l'arbre cgroup jusqu'à ce qu'il atteigne la feuille cgroup de Slurm.
EnableExtraControllers=<tous|contrôleur1[,contrôleur2,...]>
Cela activera des contrôleurs supplémentaires non utilisés nativement par Slurm dans le sous-arbre cgroup du job. S'il est combiné avec EnableControllers, il les activera à tous les niveaux de l'arbre cgroup à partir du cgroup racine de l'OS. Les contrôleurs qui peuvent être activés sont io, pids, rdma, hugetlb et misc ou tous. S'ils n'existent pas dans le système, une erreur est enregistrée. Uniquement pour cgroup/v2.

TACHE/PLUGINS_CGROUP

Les paramètres cgroup.conf suivants sont définis pour contrôler le comportement de ce plugin particulier :

AllowedRAMSpace=<nombre>
Limite la RAM du job/étape à ce pourcentage de la mémoire allouée. Le pourcentage fourni peut être exprimé en nombre à virgule flottante, par exemple 101,5. Définit la limite douce de mémoire cgroup à la taille de mémoire allouée, puis définit la limite dure de mémoire du job/étape à (AllowedRAMSpace/100) * mémoire allouée. Si le job/étape dépasse la limite dure, cela peut déclencher des événements de mémoire insuffisante (OOM), y compris oom-kill, qui seront enregistrés dans le tampon circulaire du journal du noyau (dmesg sous Linux). La définition de AllowedRAMSpace au-dessus de 100 peut provoquer des événements OOM système car elle permet au job/étape d'allouer plus de mémoire que celle configurée pour les nœuds. Il est suggéré de réduire la mémoire disponible configurée pour les nœuds afin d'éviter les événements OOM système. La définition de AllowedRAMSpace en dessous de 100 entraînera pour les jobs une réception de moins de mémoire que ce qui a été alloué et la limite douce de mémoire sera définie à la même valeur que la limite dure. Voir également ConstrainRAMSpace. La valeur par défaut est 100.
AllowedSwapSpace=<nombre>
Limite l'espace swap cgroup du job à ce pourcentage de la mémoire allouée. La valeur par défaut est 0, ce qui signifie que RAM+Swap sera limité à AllowedRAMSpace. Le pourcentage fourni peut être exprimé en nombre à virgule flottante, par exemple 50,5. Si la limite est dépassée, les étapes du job seront tuées et un message d'avertissement sera écrit sur la sortie d'erreur standard. Voir également ConstrainSwapSpace. NOTE : Définir AllowedSwapSpace à 0 n'empêche pas le noyau Linux d'utiliser l'espace swap. Pour contrôler comment le noyau utilise l'espace swap, voir MemorySwappiness.
ConstrainCores=<oui|non>
Si configuré sur "oui", contraindre les cœurs autorisés au sous-ensemble des ressources allouées. Cette fonctionnalité utilise le sous-système cpuset. En raison d'un bogue corrigé dans la version 1.11.5 de HWLOC, le plugin task/affinity peut être requis en plus de task/cgroup pour que cela fonctionne correctement. La valeur par défaut est "non".
ConstrainDevices=<oui|non>
Si configuré sur "oui", contraindre les périphériques autorisés du job en fonction des ressources GRES allouées. Il utilise le sous-système devices pour cela. La valeur par défaut est "non".
ConstrainRAMSpace=<oui|non>
Si configuré sur "oui", contraindre l'utilisation de la RAM du job en définissant la limite douce de mémoire à la mémoire allouée et la limite dure à la mémoire allouée * AllowedRAMSpace. La valeur par défaut est "no".

"no", auquel cas la limite de RAM du job sera définie sur sa limite d'espace d'échange si ConstrainSwapSpace est défini à "yes". CR_*_Memory doit être défini dans slurm.conf pour que ce paramètre ait un effet. Voir aussi AllowedSwapSpace, AllowedRAMSpace et ConstrainSwapSpace.

NOTE: Lors de l'utilisation de ConstrainRAMSpace, si la mémoire combinée utilisée par tous les processus d'une étape dépasse la limite, le noyau déclenchera un événement OOM, tuant un ou plusieurs des processus de l'étape. L'état de l'étape sera marqué comme OOM, mais l'étape elle-même continuera de s'exécuter et d'autres processus de l'étape peuvent également continuer à s'exécuter. Cela diffère du comportement de OverMemoryKill, où toute l'étape sera tuée/annulée.

NOTE: Lorsqu'il est activé, ConstrainRAMSpace peut entraîner une baisse notable du débit des jobs par nœud. Les sites ayant des exigences de haut débit doivent soigneusement peser le compromis entre le débit par nœud et les problèmes potentiels pouvant découler d'une utilisation non contrainte de la mémoire sur le nœud. Voir https://slurm.schedmd.com/high_throughput.html pour une discussion plus approfondie.

ConstrainSwapSpace=<yes|no>
Si configuré à "yes", contraint l'utilisation de l'espace d'échange du job. La valeur par défaut est "no". Notez que lorsque défini à "yes" et que ConstrainRAMSpace est défini à "no", AllowedRAMSpace est automatiquement défini à 100% afin de limiter la quantité RAM+Swap à 100% de la demande du job plus le pourcentage d'espace d'échange autorisé. Cette quantité est donc définie à la fois comme limite de RAM et de RAM+Swap. Cela signifie que dans ce cas particulier, ConstrainRAMSpace est automatiquement activé avec la même limite que celle utilisée pour contraindre l'espace d'échange. CR_*_Memory doit être défini dans slurm.conf pour que ce paramètre ait un effet. Voir aussi AllowedSwapSpace.
MaxRAMPercent=PERCENT
Définit une borne supérieure en pourcentage de la RAM totale (RealMemory configuré du nœud) pour la contrainte de RAM d'un job. C'est la contrainte de mémoire qui sera appliquée aux jobs pour lesquels Slurm n'a pas explicitement alloué de mémoire (c'est-à-dire que le plugin de sélection de Slurm n'est pas configuré pour gérer les allocations de mémoire). Le PERCENT peut être un nombre flottant arbitraire. La valeur par défaut est 100.
MaxSwapPercent=PERCENT
Définit une borne supérieure (en pourcentage de la RAM totale, RealMemory configuré du nœud) pour la quantité de RAM+Swap qui peut être utilisée pour un job. C'est la limite d'échange qui sera appliquée aux jobs sur les systèmes où la mémoire n'est pas explicitement allouée aux jobs. Le PERCENT peut être un nombre flottant arbitraire entre 0 et 100. La valeur par défaut est 100.
MemorySwappiness=<number>
Uniquement pour cgroup/v1. Configure la priorité du noyau pour échanger les pages anonymes (telles que les données de programme) par rapport aux pages de cache de fichiers pour le cgroup du job. Les valeurs valides sont comprises entre 0 et 100 inclus. Une valeur de 0 empêche le noyau d'échanger les données de programme. Une valeur de 100 donne une priorité égale à l'échange des pages de cache de fichiers ou des pages anonymes. Si non défini, la valeur de swappiness par défaut du noyau sera utilisée. ConstrainSwapSpace doit être défini à yes pour que ce paramètre soit appliqué.
MinRAMSpace=<number>
Définit une borne inférieure (en Mo) pour les limites de mémoire définies par AllowedRAMSpace et AllowedSwapSpace. Cela empêche de créer accidentellement un cgroup de mémoire avec une limite si basse que slurmstepd est immédiatement tué par manque de RAM. Si cela se produit, le nettoyage ne sera pas effectué et des fichiers temporaires, des sockets et des répertoires peuvent rester sur le nœud. La limite par défaut est 30M.

PLUGIN PROCTRACK/CGROUP

Les paramètres cgroup.conf suivants sont définis pour contrôler le comportement de ce plugin particulier :

SignalChildrenProcesses=<yes|no>
Si configuré à "yes", envoie des signaux (pour annuler, suspendre, reprendre, etc.) à tous les processus enfants d'un job/étape. Sinon, n'envoie des signaux qu'au processus parent d'un job/étape. Le paramètre par défaut est "no".

NOTES SPÉCIFIQUES À LA DISTRIBUTION

Debian et ses dérivés (par ex. Ubuntu) excluent généralement les cgroups memory et memsw (swap) par défaut. Pour les inclure, ajoutez les paramètres suivants à la ligne de commande du noyau : cgroup_enable=memory swapaccount=1

Cela peut généralement être placé dans /etc/default/grub à l'intérieur de la variable GRUB_CMDLINE_LINUX . Une commande telle que update-grub doit être exécutée après la mise à jour du fichier.

EXEMPLE

/etc/slurm/cgroup.conf:
Ce fichier cgroup.conf d'exemple montre une configuration qui active les mécanismes d'application des cgroups les plus couramment utilisés.
###
# Slurm cgroup support configuration file.
###
ConstrainCores=yes
ConstrainDevices=yes
ConstrainRAMSpace=yes
ConstrainSwapSpace=yes
/etc/slurm/slurm.conf:
Voici les entrées requises dans slurm.conf pour activer les mécanismes d'application des cgroups. Assurez-vous que les définitions de nœuds dans votre slurm.conf correspondent étroitement à la configuration montrée par "slurmd -C". Soit MemSpecLimit doit être défini, soit RealMemory doit être défini avec une valeur inférieure à la quantité réelle de mémoire d'un nœud pour garantir que tous les processus système/non-job auront suffisamment de mémoire en tout temps. Les sites devraient également configurer pam_slurm_adopt pour s'assurer que les utilisateurs ne peuvent pas échapper aux cgroups via ssh.
###
# Slurm configuration entries for cgroups
###
ProctrackType=proctrack/cgroup
TaskPlugin=task/cgroup,task/affinity
JobAcctGatherType=jobacct_gather/cgroup #optional for gathering metrics
PrologFlags=Contain                     #X11 flag is also suggested
