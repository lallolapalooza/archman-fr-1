Pourquoi ce tutoriel

?

L'une des parties puissantes de RRDtool est sa capacité à effectuer toutes sortes de calculs sur les données récupérées depuis ses bases de données. Cependant, les nombreuses options et la syntaxe de RRDtool le rendent difficile à comprendre pour l'utilisateur moyen.

Les manuels expliquent bien ce que font ces options ; cependant, ils n'expliquent pas (et ne devraient pas expliquer) en détail pourquoi elles sont utiles. Comme pour mon tutoriel RRDtool : si vous voulez un document simple dans un langage simple, vous devriez lir
e ce tutoriel. Si vous êtes satisfait de la documentation officielle, vous trouverez peut-être ce document trop simple ou même ennuyeux. Si vous choisissez de lire ce tutoriel, je m'attends également à ce que vous ayez lu et entièrement compris mon autre tutoriel.

Qu'est-ce qu'un CDEF

?

Lorsque vous récupérez des données depuis un RRD, vous utilisez un "DEF" pour travailler avec ces données. Considérez-le comme une variable qui change

au fil du temps (où le temps est l'axe des x). La valeur de cette variable est ce qui se trouve dans la base de données à ce moment précis et vous ne po
uvez effectuer aucune modification dessus. C'est à cela que servent les CDEF : ils prennent des valeurs issues de DEF et effectuent des calculs dessus.

Syntax

e 
DEF:var_name_1=some.rrd:ds_name:CF
CDEF:var_name_2=RPN_expressio
n

Vous définissez d'abord "var_name_1" comme étant les données collectées depuis la source de données "ds_name" trouvée dans le RRD "some.rrd" avec la fonction de consolidation

"CF".

Supposons que le compteur SNMP ifInOctets soit enregistré dans mrtg.rrd comme le DS "in". Alors le DEF suivant définit une variable pour la moyenne de cette source de données

: 
DEF:inbytes=mrtg.rrd:in:
AVERAGE

Disons que vous voulez afficher des bits par seconde (au lieu de octets par seconde comme stocké dans la base de données). Vous devez définir un calcul (d'où "CDEF") sur la variable "inbytes" et utiliser cette variable (inbits) à la place de l'originale

: 
CDEF:inbits=inbytes,8,
*

Cela indique à RRDtool de multiplier inbytes par huit pour obtenir inbits. J'expliquerai plus tard comment cela fonctionne. Dans les fonctions de graphique ou d'impression, vous pouvez maintenant utiliser inbits là où vous utiliseriez inbits

sinon.

Notez que le nom de variable utilisé dans le CDEF (inbits) ne doit pas être le même que le nom de variable dans le DEF (inbytes)

!

RPN est l'abréviation de Reverse Polish Notation (notation polonaise inversée). Cela fonctionne comme suit. Vous placez les variables ou les nombres sur une pile. À la fin, il devrait rester exactement un nombre : le résultat de la série d'opérations. S'il ne reste pas exactement un nombre, RRDtool se plaindra

signifie.

Now look at an expression that contains a

multiplication:

First in normal math: "let result = a+b*c". In this case you can't choose the order yourself, you have to start with the multiplication and then add a to it. You may alter the position of b and c, you must not alter the position of a and

b.

You have to take this in consideration when converting this expression into RPN. Read it as: "Add the outcome of b*c to a" and then it is easy to write the RPN expression: "result=a,b,c,*,+" Another expression that would return the same: "result=b,c,*,a,

+"

In normal math, you may encounter something like "a*(b+c)" and this can also be converted into RPN. The parenthesis just tell you to first add b and c, and then multiply a with the result. Again, now it is easy to write it in RPN: "result=a,b,c,+,*". Note that this is very similar to one of the expressions in the previous paragraph, only the multiplication and the addition changed

places.

When you have problems with RPN or when RRDtool is complaining, it's usually a good thing to write down the

stack on a piece of paper and see what happens. Have the manual ready and pretend to be RRDtool. Just do
all the math by hand to see what happens, I'm sure this will solve most, if not all, problems you encounter.

Some special

numbers

The unknown

value

Sometimes collecting your data will fail. This can be very common, especially when querying over busy links. RRDtool can be configured to allow for one (or even more) unknown value(s) and calculate the missing update. You can, for instance, query your device every minute. This is creating one so called PDP or primary data point per minute. If you defined your RRD to contain an RRA that stores 5-minute values, you need five of those PDPs to create one CDP (consolidated data point). These PDPs can become unknown in two

cases:
1
.
The updates are too far apart. This is tuned using the "heartbeat"
setting.
2
.
The update was set to unknown on purpose by i
nserting no value (using the template op
tion) or by using "U" as the value to insert.

When a CDP is calculated, another mechanism determines if this CDP is valid or not. If there are too many PDPs unknown, the CDP is unknown as well. This is determined by the xff factor. Please note that one unknown counter update can result in two unknown PDPs! If you only allow for one unknown PDP per CDP, this makes the CDP go

unknown!

Suppose the counter increments with one per second and you retrieve it every

minute: 
counter value    resulting rate
10'000
10'060            1; (10'060-10'000)/60 == 1
10'120            1; (10'120-10'060)/60 == 1
unknown           unknown; you don't know the last value
10'240            unknown; you don't know the previous value
10'300            1; (10'300-10'240)/60 ==
1

If the CDP was to be calculated from the last five updates, it would get two unknown PDPs and three known PDPs. If xff would have been set to 0.5 which by the way is a commonly used factor, the CDP would have a known value of 1. If xff would have been set to 0.2 then the resulting CDP would be

unknown.

You have to decide the proper values for heartbeat, number

of PDPs per CDP and the xff factor. As you can see from
the previous text they define the behavior of your RRA.

Working with unknown data in your

database

As you have read in the previous chapter, entries in an RRA can be set to the unknown value. If you do calculations with this type of value, the result has to be unknown too. This means that an expression such as "result=a,b,+" will be unknown if either a or b is unknown. It would be wrong to just ignore the unknown value and return the value of the other parameter. By doing so, you would assume "unknown" means "zero" and this is not

true.

There has been a case where somebody was collecting data for over a year. A new piece of equipment was installed, a new RRD was created and the scripts were changed to add a counter from the old database and a counter from the new database. The result was disappointing, a large part of the statistics seemed to have vanished mysteriously ... They of course didn't, values from the old database (known values) were added to values from the new database (unknown values) and the result was

unknown.

In this case, it is fairly reasonable to use a CDEF that alters unknown data into zero. The counters of the device were unknown (after all, it wasn't installed yet!) but you know that the data rate through the device had to be zero (because of the same reason: it was not installed)

.

There are some ex

amples below that
make this change.

Infinit

y

Infinite data is another form of a special number. It cannot be graphed because by definition you would never reach the infinite value. You can think of positive and negative infinity depending on the position relative to

zero.

RRDtool is capable of representing (-not- graphing!) infinity by stopping at its current maximum (for positive infinity) or minimum (for negative infinity) without knowing this maximum (minimum)

.

Infinity in RRDtool is mostly used to draw an AREA without knowing its vertical dimensions. You can think of it as

drawing an AREA with an infinite height and displaying only the part that is visible in the current graph. Th
is is probably a good way to approximate infinity and it sure allows for some neat tricks. See below for examples.

Working with unknown data and

infinity

Sometimes you would like to discard unknown data and pretend it is zero (or any othe

r value for that matter) and sometimes you would like to pretend that known data is
unknown (to discard known-to-be-wrong data). This is why CDEFs have support for unkno
wn data. There are also examples available that show unknown data by using infinity.

Some

examples

Example: using a recently created

RRD

You are keeping statistics on your router for over a year now. Recently you installed an extra router and you would like to show the combined throughput for these two

devices.

If you just add up the counters from router.rrd and router2.rrd, you will add known data (from router.rrd) to unknown data (from router2.rrd) for the bigger part of your stats. You could solve this in a few

ways:
  • While creating the new database, fill it with zeros from the start to now. You have to make the database start at or before the least recent time in the other
    • database.
  • Alternatively, you cou
    • ld use CDEF and alter
unknown data to zero.

Both methods have their pros and cons. The first method is troublesome and if you want to do that you have to figure it out yourself. It is not possible to create a database filled with zeros, you have to put them in manually. Implementing the second method is described

next:

What we want is: "if the value is unknown, replace it with zero". This could be written in pseudo-code as: if (value is unknown) then (zero) else (value). When reading the rrdgraph manual you notice the "UN" function that returns zero or one. You also notice the "IF" function that takes zero or one as

input.

First look at the "IF" function. It takes three values from the stack, the first value is the decision point, the second value is returned to the stack if the evaluation is "true" and if not, the third value is returned to the stack. We want the "UN" function to decide what happens so we combine those two functions in one

CDEF.

Lets write down the two possible paths for the "IF"

function: 
if true  return a
if false return
b

In RPN: "result=x,a,b,IF" where "x" is either true or

false.

Now we have to fill in "x", this should be the "(value is unknown)" part and this is in RPN: "result=value,

UN"

We now combine them: "result=value,UN,a,b,IF" and when we fill in the appropriate things for "a" and "b" we're

finished:

"CDEF:result=value,UN,0,value,

IF"

You may want to read Steve Rader's RPN guide if you have difficulties with the way I explained this last

example.

If you want to check this RPN expression, just mimic RRDtool

behavior: 
For any known value, the expression evaluates as follows:
CDEF:result=value,UN,0,value,IF  (value,UN) is not true so it becomes 0
CDEF:result=0,0,value,IF         "IF" will return the 3rd value
CDEF:result=value                The known value is returned
For the unknown value, this happens:
CDEF:result=value,UN,0,value,IF  (value,UN) is true so it becomes 1
CDEF:result=1,0,value,IF         "IF" sees 1 and returns the 2nd value
CDEF:result=0                    Zero is
returned

Of course, if you would like to see another value instead of zero, you can use that other

value.

Eventually, when all unknown data is removed f

rom the RRD, you may want to remove this ru
le so that unknown data is properly displayed.

Example: better handling of unknown data, by using

time

The above example has one drawback. If you do log unknown data in your database after installing your new equipment, it will also be translated into zero and therefore you won't see that there was a problem. This is not good and what you really want to do

is:
  • If there is unknown data, look at the time that this sample was
    • taken.
  • If the unknown value is before time xxx, make it
    • zero.
  • If it is after ti
    • me xxx, leave it
as unknown data.

This is doable: you can compare the time that the sample was taken à une heure connue. En supposant que vous ayez commencé à surveiller votre appareil le vendredi 17 septembre 1999 à 00:35:57 MET DST. Traduisez cette heure en secondes depuis le 1970-01-01 et cela donne 937'521'357. Si vous traitez des valeurs inconnues reçues après cette heure, vous souhaitez les laisser inconnues et si elles ont été « reçues » avant cette heure, vous souhaitez les traduire en zéro (de sorte que vous puissiez effectivement les ignorer tout en les ajoutant aux compteurs de vos autres routeurs).

Traduire le vendredi 17 septembre 1999 à 00:35:57 MET DST en 937'521'357 peut se faire, par exemple, en utilisant la commande date de GNU :

date -d "19990917 00:35:57" +%s

Vous pouvez aussi exporter la base de données et voir où les données commencent à être connues. Il existe plusieurs autres façons de faire cela, choisissez-en une.

Maintenant, nous devons créer la logique qui nous permet de traiter les valeurs inconnues différemment selon le moment où l'échantillon a été pris. C'est un processus en trois étapes :

1.
Si l'horodatage de la valeur est postérieur à 937'521'357, laissez-le tel quel.
2.
Si la valeur est une valeur connue, laissez-la telle quelle.
3.
Changez la valeur inconnue en zéro.

Regardons la première partie :

if (true) return the original value

Nous réécrivons ceci :

if (true) return "a"
if (false) return "b"

Nous devons calculer true ou false à partir de l'étape 1. Il existe une fonction disponible qui renvoie l'horodatage de l'échantillon courant. Elle s'appelle, ô surprise, "TIME". Cette heure doit être comparée à un nombre constant, nous avons besoin de "GT". La sortie de "GT" est true ou false et c'est une bonne entrée pour "IF". Nous voulons "if (time > 937521357) then (return a) else (return b)".

Ce processus a déjà été décrit en détail dans le chapitre précédent, faisons-le rapidement :

if (x) then a else b
   où x représente "time>937521357"
   où a représente la valeur originale
   où b représente le résultat de l'exemple précédent
time>937521357       --> TIME,937521357,GT
if (x) then a else b --> x,a,b,IF
substituer x         --> TIME,937521357,GT,a,b,IF
substituer a         --> TIME,937521357,GT,value,b,IF
substituer b         --> TIME,937521357,GT,value,value,UN,0,value,IF,IF

Nous aboutissons à : "CDEF:result=TIME,937521357,GT,value,value,UN,0,value,IF,IF"

Cela semble très complexe, cependant, comme vous pouvez le voir, ce n'a pas été trop difficile à trouver.

Exemple : Faire semblant que les données bizarres n'existent pas

Supposons que vous ayez un problème qui se manifeste par d'énormes pics dans votre graphique. Vous savez que cela arrive et pourquoi, alors vous décidez de contourner le problème. Peut-être utilisez-vous votre réseau pour faire une sauvegarde la nuit et en faisant cela vous obtenez presque 10 Mo/s tandis que le reste de votre activité réseau ne produit pas de chiffres supérieurs à 100 ko/s.

Il y a deux options :

1.
Si le nombre dépasse 100 ko/s, il est incorrect et vous voulez le masquer en le changeant en inconnu.
2.
Vous ne voulez pas que le graphique montre plus de 100 ko/s.

Code pseudo : if (number > 100) then unknown else number ou Code pseudo : if (number > 100) then 100 else number.

Le deuxième « problème » peut aussi être résolu en utilisant l'option rigide de RRDtool graph, cependant cela n'a pas le même résultat. Dans cet exemple, vous pouvez vous retrouver avec un graphique qui fait une mise à l'échelle automatique. De plus, si vous utilisez les nombres pour afficher les maxima, ils seront fixés à 100 ko/s.

Nous utilisons "IF" et "GT" à nouveau. "if (x) then (y) else (z)" s'écrit "CDEF:result=x,y,z,IF" ; maintenant remplissez x, y et z. Pour x, vous mettez "number greater than 100kb/s" devenant "number,100000,GT" (kilo est 1'000 et b/s est ce que nous mesurons !). La partie "z" est "number" dans les deux cas et la partie "y" est soit "UNKN" pour inconnu ou "100000" pour 100 ko/s.

Les deux expressions CDEF seraient :

CDEF:result=number,100000,GT,UNKN,number,IF
CDEF:result=number,100000,GT,100000,number,IF

Exemple : travailler sur une certaine période

Si vous voulez un graphique qui s'étale sur quelques semaines, mais que vous ne voudriez voir les données de certains routeurs que pour une semaine, vous devez « cacher » le reste de la période. Ne me demandez pas quand cela serait utile, c'est juste là pour l'exemple :)

Nous devons comparer l'horodatage à une date de début et une date de fin. Comparer n'est pas difficile :

TIME,begintime,GE
TIME,endtime,LE

Ces deux parties du CDEF produisent soit 0 pour faux soit 1 pour vrai. Nous pouvons maintenant vérifier si les deux sont à 0 (ou 1) en utilisant quelques instructions IF mais, comme Wataru Satoh l'a fait remarquer, nous pouvons utiliser les fonctions "*" ou "+" comme ET logique et OU logique.

Pour "*", le résultat sera zéro (faux) si l'un des deux opérandes est zéro. Pour "+", le résultat ne sera faux (0) que lorsque deux opérandes faux (0) seront additionnés. Attention : *tout* nombre différent de 0 sera considéré comme « vrai ». Cela signifie que, par exemple, "-1,1,+" (qui devrait être « true or true ») deviendra FALSE ... En d'autres termes, utilisez "+" seulement si vous savez avec certitude que vous n'avez que des nombres positifs (ou zéro).

Compilons le CDEF complet :

DEF:ds0=router1.rrd:AVERAGE
CDEF:ds0modified=TIME,begintime,GT,TIME,endtime,LE,*,ds0,UNKN,IF

Cela renverra la valeur de ds0 si les deux comparaisons renvoient vrai. Vous pourriez aussi faire l'inverse :

DEF:ds0=router1.rrd:AVERAGE
CDEF:ds0modified=TIME,begintime,LT,TIME,endtime,GT,+,UNKN,ds0,IF

Cela renverra un UNKNOWN si l'une des comparaisons renvoie vrai.

Exemple : Vous soupçonnez avoir des problèmes et voulez voir les données inconnues.

Supposons que vous additionniez le nombre d'utilisateurs actifs sur plusieurs serveurs terminaux. Si l'un d'eux ne donne pas de réponse (ou une réponse incorrecte) vous obtenez "NaN" dans la base de données ("Not a Number") et NaN est évalué comme Inconnu.

Dans ce cas, vous aimeriez être alerté et la somme des valeurs restantes n'a aucune valeur pour vous.

Ce serait quelque chose comme :

DEF:users1=location1.rrd:onlineTS1:LAST
DEF:users2=location1.rrd:onlineTS2:LAST
DEF:users3=location2.rrd:onlineTS1:LAST
DEF:users4=location2.rrd:onlineTS2:LAST
CDEF:allusers=users1,users2,users3,users4,+,+,+

Si vous tracez maintenant allusers, des données inconnues dans l'un de users1..users4 apparaîtront comme un trou dans votre graphique. Vous voulez modifier cela pour montrer une ligne rouge vif, pas un trou.

Définissez un CDEF supplémentaire qui est inconnu si tout est en ordre et infini s'il y a une valeur inconnue :

CDEF:wrongdata=allusers,UN,INF,UNKN,IF

"allusers,UN" sera évalué soit à true soit à false, c'est la partie (x) de la fonction "IF" et elle vérifie si allusers est inconnu. La partie (y) de la fonction "IF" est fixée à "INF" (qui signifie infini) et la partie (z) de la fonction renvoie "UNKN".

La logique est : if (allusers == unknown) then return INF else return UNKN.

Vous pouvez maintenant utiliser AREA pour afficher ce "wrongdata" en rouge vif. S'il est inconnu (parce que allusers est connu) alors l'AREA rouge n'apparaîtra pas. Si la valeur est INF (parce que allusers est inconnu) alors l'AREA rouge sera rempli sur le graphique à ce moment particulier.

AREA:allusers#0000FF:combined user count
AREA:wrongdata#FF0000:unknown data

Même exemple utile avec des données empilées (STACK) :

Si vous utilisez stack dans l'exemple précédent (comme je le ferais) alors vous n'additionnez pas les valeurs. Par conséquent, il n'y a pas de relation entre les quatre valeurs et vous n'obtenez pas une seule valeur à tester. Supposons que users3 soit inconnu à un moment donné : users1 est tracé, users2 est empilé au-dessus de users1, users3 est inconnu et donc rien ne se passe, users4 est empilé au-dessus de users2. Ajoutez quand même les CDEF supplémentaires et utilisez-les pour superposer le graphique « normal » :

DEF:users1=location1.rrd:onlineTS1:LAST
DEF:users2=location1.rrd:onlineTS2:LAST
DEF:users3=location2.rrd:onlineTS1:LAST
DEF:users4=location2.rrd:onlineTS2:LAST
CDEF:allusers=users1,users2,users3,users4,+,+,+
CDEF:wrongdata=allusers,UN,INF,UNKN,IF
AREA:users1#0000FF:users at ts1
STACK:users2#00FF00:users at ts2
STACK:users3#00FFFF:users at ts3
STACK:users4#FFFF00:users at ts4
AREA:wrongdata#FF0000:unknown data

S'il y a des données inconnues dans l'un de users1..users4, l'AREA "wrongdata" sera dessiné et parce qu'il commence à l'axe X et a une hauteur infinie, il écrasera efficacement les parties empilées (STACK).

Vous pourriez combiner les deux lignes CDEF en une seule (nous n'utilisons pas "allusers") si vous le souhaitez. Mais il y a de bonnes raisons d'écrire deux CDEFS :

  • Cela améliore la lisibilité du script.
  • Cela peut être utilisé à l'intérieur de GPRINT pour afficher le nombre total d'utilisateurs.

Si vous choisissez de les combiner, vous pouvez substituer "allusers" dans le second CDEF par la partie après le signe égal de la première ligne :

CDEF:wrongdata=users1,users2,users3,users4,+,+,+,UN,INF,UNKN,IF

Si vous le faites, vous ne pourrez pas utiliser les GPRINT suivants :

COMMENT:"Total number of users seen"
GPRINT:allusers:MAX:"Maximum: %6.0lf"
GPRINT:allusers:MIN:"Minimum: %6.0lf"
GPRINT:allusers:AVERAGE:"Average: %6.0lf"
GPRINT:allusers:LAST:"Current: %6.0lf\n"

Ces deux CDEF sont construits à partir de plusieurs fonctions. Il est utile de les décomposer pour voir ce qu'ils font. En commençant par le premier CDEF, nous obtiendrions

: 
idat1,UN --> a
0        --> b
idat1    --> c
if (a) then (b) else
(c)

Le résultat est donc "0" si la condition "idat1" égale "UN" est vraie. Sinon, la valeur originale de "idat1" est remise sur la pile. Appelons cette réponse "d". Le processus est répété pour les cinq prochains éléments de la pile, il est fait de la même manière et renverra la réponse "h". La pile résultante est donc "d,h". L'expression a été simplifiée en "d,h,+,8,*" et il est maintenant facile de voir que nous ajoutons "d" et "h", et multiplions le résultat par

huit.

Le résultat final est que nous avons ajouté "idat1" et "idat2" et dans le proc

essus nous avons effectivement ignoré les valeurs inconnues. Le résultat est
multiplié par huit, très probablement pour convertir des octets/s en bits/s.

Démonstration

d'infini 
rrdtool graph example.png --title="INF demo" \
   DEF:val1=some.rrd:ds0:AVERAGE \
   DEF:val2=some.rrd:ds1:AVERAGE \
   DEF:val3=some.rrd:ds2:AVERAGE \
   DEF:val4=other.rrd:ds0:AVERAGE \
   CDEF:background=val4,POP,TIME,7200,%,3600,LE,INF,UNKN,IF \
   CDEF:wipeout=val1,val2,val3,val4,+,+,+,UN,INF,UNKN,IF \
   AREA:background#F0F0F0 \
   AREA:val1#0000FF:Value1 \
   STACK:val2#00C000:Value2 \
   STACK:val3#FFFF00:Value3 \
   STACK:val4#FFC000:Value4 \
   AREA:whipeout#FF0000:
Unknown

Cette démonstration montre deux façons d'utiliser l'infini. C'est un peu délicat de voir ce qui se passe dans le CDEF

"background". 
"val4,POP,TIME,7200,%,3600,LE,INF,UNKN,
IF"

Ce RPN prend la valeur de "val4" comme entrée puis la retire immédiatement de la pile en utilisant "POP". La pile est maintenant vide mais comme effet secondaire nous connaissons maintenant l'heure à laquelle cet échantillon a été pris. Cette heure est mise sur la pile par la fonction

"TIME".

"TIME,7200,%" prend le modulo du temps et 7'200 (qui est deux heures). La valeur résultante sur la pile sera un nombre dans la plage de 0 à

7199.

Pour ceux qui ne connaissent pas la fonction modulo : c'est le reste après une division entière. Si vous divisez 16 par 3, la réponse serait 5 et le reste serait 1. Donc, "16,3,%" renvoie

1.

Nous avons le résultat de "TIME,7200,%" sur la pile, appelons ceci "a". Le début du RPN est devenu "a,3600,LE" et cela vérifie si "a" est inférieur ou égal à "3600". C'est vrai la moitié du temps. Nous devons maintenant traiter le reste du RPN et ce n'est qu'une simple fonction "IF" qui renvoie soit "INF" soit "UNKN" selon l'heure. Ceci est renvoyé à la variable

"background".

Le second CDEF a été discuté plus tôt dans ce document, nous ne le ferons pas

ici.

Maintenant vous pouvez dessiner les différentes couches. Commencez par le fond qui est soit inconnu (rien à voir) soit infini (toute la partie positive du graphique est remplie)

.

Ensuite vous dessinez les données par-dessus ce fond, elles recouvriront le fond. Supposons que l'une des val1..val4 soit inconnue, dans ce cas vous n'aurez que trois barres empilées les unes sur les autres. Vous ne voulez pas voir cela car les données ne sont valides que lorsque les quatre variables sont valides. C'est pourquoi vous utilisez le second CDEF, il recouvrira les données avec une AREA pour que les données ne soient plus

visibles.

Si vos données peuvent aussi avoir des valeurs négatives, vous devez aussi recouvrir l'autre moitié

de votre graphique. Cela peut être fait d'une manière relativement simple : ce dont vous avez besoin
est la variable "wipeout" et placez un signe négatif devant elle : "CDEF:wipeout2=wipeout,-1,*"
