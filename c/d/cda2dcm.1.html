NOM

cda2dcm - Encapsule un fichier CDA dans un fichier au format DICOM

SYNOPSIS

cda2dcm [options] cdafile-in dcmfile-out

DESCRIPTION

L'utilitaire cda2dcm lit un fichier CDA (cdafile-in), le convertit en une instance SOP de stockage CDA encapsulé DICOM et stocke les données converties dans un fichier de sortie (dcmfile-out).

PARAMÈTRES

cdafile-in   Nom du fichier d'entrée CDA à encapsuler
dcmfile-out  Nom du fichier de sortie DICOM ("-" pour la sortie standard)

OPTIONS

options générales

  -h   --help
         affiche ce texte d'aide et quitte
       --version
         affiche les informations de version et quitte
       --arguments
         affiche les arguments de la ligne de commande étendus
  -q   --quiet
         mode silencieux, n'affiche ni les avertissements ni les erreurs
  -v   --verbose
         mode verbeux, affiche les détails du traitement
  -d   --debug
         mode débogage, affiche les informations de débogage
  -ll  --log-level  [l]evel: constante de chaîne
         (fatal, error, warn, info, debug, trace)
         utilise le niveau l pour le journal
  -lc  --log-config  [f]ilename: chaîne
         utilise le fichier de configuration f pour le journal

options du document DICOM

titre du document :
  +t   --title  [t]itle: chaîne (par défaut : vide)
         titre du document
  +cn  --concept-name  [CSD] [CV] [CM]: chaîne (par défaut : vide)
         représentation codée du titre du document définie par le
         schéma de codage CSD, la valeur du code CV et la signification du code CM
données du patient :
  +pn  --patient-name  [n]ame: chaîne
         nom du patient en syntaxe PN DICOM
  +pi  --patient-id  [i]d: chaîne
         identifiant du patient
  +pb  --patient-birthdate  [d]ate: chaîne (AAAAMMJJ)
         date de naissance du patient
  +ps  --patient-sex  [s]ex: chaîne (M, F ou O)
         sexe du patient
étude et série :
  +sg  --generate
         génère de nouveaux UID d'étude et de série (par défaut)
  +st  --study-from  [f]ilename: chaîne
         lit les données du patient/de l'étude à partir d'un fichier DICOM
  +se  --series-from  [f]ilename: chaîne
         lit les données du patient/de l'étude/de la série à partir d'un fichier DICOM
numéro d'instance :
  +i1  --instance-one
         utilise le numéro d'instance 1 (par défaut, pas avec +se)
  +ii  --instance-inc
         incrémente le numéro d'instance (uniquement avec +se)
  +is  --instance-set [i]nstance number: entier
         utilise le numéro d'instance i
annotation intégrée (burned-in) :
  +an  --annotation-yes
         le document contient des données d'identification du patient (par défaut)
  -an  --annotation-no
         le document ne contient pas de données d'identification du patient
remplacement des données du fichier CDA :
  -ov  --no-override
         les données du patient et du document CDA doivent correspondre à l'étude,
         à la série ou aux informations saisies manuellement (par défaut)
  +ov  --override
         les données obtenues à partir du fichier CDA seront écrasées
         par les informations de l'étude, de la série ou saisies manuellement

options de traitement

autres options de traitement :
  -k   --key  [k]ey: gggg,eeee="str", chemin ou nom de dictionnaire="str"
         ajoute un attribut supplémentaire

options de sortie

format du fichier de sortie :
  +F   --write-file
         écrit le format fichier (par défaut)
  -F   --write-dataset
         écrit le jeu de données sans méta-informations de fichier
encodage de la longueur de groupe :
  +g=  --group-length-recalc
         recalcule les longueurs de groupe si elles sont présentes (par défaut)
  +g   --group-length-create
         écrit toujours avec les éléments de longueur de groupe
  -g   --group-length-remove
         écrit toujours sans les éléments de longueur de groupe
encodage de la longueur dans les séquences et les éléments :
  +e   --length-explicit
         écrit avec des longueurs explicites (par défaut)
  -e   --length-undefined
         écrit avec des longueurs indéfinies
remplissage de fin de jeu de données (pas avec --write-dataset) :
  -p   --padding-off
         pas de remplissage (implicite si --write-dataset)
  +p   --padding-create  [f]ile-pad [i]tem-pad: entier
         aligne le fichier sur un multiple de f octets
         et les éléments sur un multiple de i octets

NOTES

Sources des attributs

L'application peut recevoir des entrées supplémentaires pour remplir les attributs obligatoires (et facultatifs) du nouveau fichier DICOM, tels que les informations sur le patient, l'étude et la série :

  • L'option --key peut être utilisée pour ajouter d'autres attributs au fichier de sortie DICOM.
  • Il est également possible de spécifier des séquences, des éléments et des attributs imbriqués en utilisant l'option --key . Dans ces cas, une notation de « chemin » spéciale doit être utilisée. Les détails sur cette notation de chemin se trouvent dans la documentation de dcmodify.
  • L'option --key peut être présente plusieurs fois.
  • La partie de la valeur (après le '=') peut être absente, ce qui a pour effet de définir l'attribut avec une longueur nulle.
  • Veuillez noter que l'option --key est appliquée à toute fin, juste avant l'enregistrement du fichier DICOM, il n'y a donc aucun contrôle de valeur.

JOURNALISATION

Le niveau de sortie de journalisation des différentes outils en ligne de commande et des bibliothèques sous-jacentes peut être spécifié par l'utilisateur. Par défaut, seules les erreurs et les avertissements sont écrits sur le flux d'erreur standard. En utilisant l'option --verbose les messages informatifs tels que les détails du traitement sont également rapportés. L'option --debug peut être utilisée pour obtenir plus de détails sur l'activité interne, par exemple à des fins de débogage. D'autres niveaux de journalisation peuvent être sélectionnés à l'aide de l'option --log-level. En mode --quiet seules les erreurs fatales sont rapportées. En cas d'événements d'erreur très graves, l'application se terminera généralement. Pour plus de détails sur les différents niveaux de journalisation, voir la documentation du module « oflog ».

Si la sortie de journalisation doit être écrite dans un fichier (avec rotation du journal de fichier en option), dans le syslog (Unix) ou le journal des événements (Windows), l'option --log-config peut être utilisée. Ce fichier de configuration permet également de diriger uniquement certains messages vers un flux de sortie particulier et de filtrer certains messages en fonction du module ou de l'application où ils sont générés. Un exemple de fichier de configuration est fourni dans <etcdir>/logger.cfg.

LIGNE DE COMMANDE

Tous les outils en ligne de commande utilisent la notation suivante pour les paramètres : les crochets enclos des valeurs facultatives (0-1), les trois points de suspension indiquent que plusieurs valeurs sont autorisées (1-n), une combinaison des deux signifie de 0 à n valeurs.

Les options de la ligne de commande se distinguent des paramètres par un signe '+' ou '-' en tête, respectivement. Habituellement, l'ordre et la position des options de la ligne de commande sont arbitraires (c'est-à-dire qu'elles peuvent apparaître n'importe où). Cependant, si des options sont mutuellement exclusives, la plus à droite est utilisée. Ce comportement est conforme aux règles d'évaluation standard des shells Unix courants.

De plus, un ou plusieurs fichiers de commande peuvent être spécifiés en utilisant un signe '@' comme préfixe du nom de fichier (par exemple @command.txt). Un tel argument de commande est remplacé par le contenu du fichier texte correspondant (plusieurs espaces blancs sont traités comme un seul séparateur s'ils n'apparaissent pas entre deux guillemets) avant toute autre évaluation. Veuillez noter qu'un fichier de commande ne peut pas contenir un autre fichier de commande. Cette approche simple mais efficace permet de résumer des combinaisons courantes d'options/de paramètres et évite des lignes de commande longues et déroutantes (un exemple est fourni dans le fichier <datadir>/dumppat.txt).

CODES DE SORTIE

L'utilitaire cda2dcm utilise les codes de sortie suivants lors de sa terminaison. Cela permet à l'utilisateur de vérifier la raison pour laquelle l'application s'est terminée.

général

EXITCODE_NO_ERROR                 0
EXITCODE_COMMANDLINE_SYNTAX_ERROR 1
EXITCODE_MEMORY_EXHAUSTED         4

erreurs de fichier d'entrée

EXITCODE_CANNOT_READ_INPUT_FILE   20
EXITCODE_NO_INPUT_FILES           21
EXITCODE_INVALID_INPUT_FILE       22

erreurs de fichier de sortie

EXITCODE_CANNOT_WRITE_OUTPUT_FILE 40

ENVIRONNEMENT

L'utilitaire cda2dcm tentera de charger les dictionnaires de données DICOM spécifiés dans la variable DCMDICTPATH . Par défaut, c'est-à-dire si la variable DCMDICTPATH n'est pas définie, le fichier <datadir>/dicom.dic sera chargé, sauf si le dictionnaire est intégré à l'application (par défaut sous Windows).

Le comportement par défaut doit être préféré et la variable DCMDICTPATH ne doit être utilisée que lorsque des dictionnaires de données alternatifs sont nécessaires. La variable DCMDICTPATH a le même format que la variable PATH du shell Unix, un deux-points (":") séparant les entrées. Sur les systèmes Windows, un point-virgule (";") est utilisé comme séparateur. Le code du dictionnaire de données tentera de charger chaque fichier spécifié dans la variable DCMDICTPATH . C'est une erreur si aucun dictionnaire de données ne peut être chargé.
