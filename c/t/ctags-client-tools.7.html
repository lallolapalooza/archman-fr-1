PSEUDO-TAG

S

Les pseudo-tags, stockés dans un fichier de tags, indiquent comment ctags a généré le fichier de tags : si le fichier de tags est trié ou non, quelle version du format de fichier de tags est utilisée, le nom du générateur de tags, et ainsi de suite. Le terme opposé de pseudo-tags est regular-tags. Un regular-tag correspond à un objet de langage dans un fichier d'entrée. Un pseudo-tag correspond au fichier de tags lui-même. Les outils clients peuvent utiliser les pseudo-tags comme référence pour traiter les

regular-tags.

Un pseudo-tag est stocké dans un fichier de tags dans le même format que les regular-tags tel que décrit dans tags(5), sauf que les noms de pseudo-tags sont préfixés par "!_". Pour des informations générales sur les pseudo-tags, voir "TAG FILE INFORMATION" dans tags(5)

.

Un exemple de pseudo-tag

:

Universal C
tags /Derived fro
m Exuberant Ctags/

motif.

Universal Ctags étend le schéma de nommage des pseudo-tags classiques disponibles dans Exuberant Ctags pour émettre des informations spécifiques à un langage sous forme de pseudo-tags

Universal ctags peut exécuter plusieurs parseurs. Cela signifie qu'un parseur, qui supporte plusieurs parseurs (parseurs invités ou sous-parseurs), peut émettre des tags pour différents

langages.

Parseurs

invités

Un parseur peut exécuter des parseurs invités sur les zones d'un fichier

source.

Considérez le texte suivant comme un fichier source ("input.html")

        <script>class MyObjec
t {}</script> <style type="text/cs

UTILISATION DE READTAGS

Consultez readtags(1) pour savoir comment utiliser readtags. Cette section est consacrée à la discussion de certains sujets notables pour les outils clients.

Construction d'expressions de filtre/tri

Certaines séquences d'échappement dans les expressions sont reconnues par readtags. Par exemple, lors de la recherche d'un tag correspondant à a\?b, si vous utilisez une expression de filtre comme '(eq? $name "a\?b")', comme \? est traduit en un simple ? par readtags, cela recherche en fait a?b.

Un autre problème est le suivant : si les outils clients communiquent avec readtags non pas directement via un sous-processus, mais via un shell, alors si un guillemet simple apparaît dans les expressions de filtre (qui sont également entourées de guillemets simples), cela termine l'expression, produisant des expressions cassées, et peut même entraîner une injection de shell involontaire. Les guillemets simples peuvent être échappés en utilisant '"'"'.

Ainsi, les outils clients doivent :

  • Remplacer \ par \\
  • Remplacer ' par '"'"', s'ils communiquent avec readtags via un shell.

à l'intérieur des expressions. Si l'expression contient également des chaînes de caractères, " dans les chaînes doit être remplacé par \".

Une autre chose à noter est que les champs manquants sont représentés par #f, et l'application d'opérateurs de chaîne à ceux-ci produira une erreur. Vous devez toujours vérifier si un champ est manquant avant d'appliquer des opérateurs de chaîne. Voir la section « Filtrage » dans readtags(1) pour savoir comment faire cela. Exécutez « readtags -H filter » pour voir quels opérateurs acceptent des arguments de chaîne.

Construction d'expressions de filtre/tri en utilisant les langages Lisp

Les outils clients écrits en Lisp pourraient construire l'expression en utilisant des listes. prin1 (dans les Lisps de style Common Lisp) et write (dans les Lisps de style Scheme) peuvent traduire la liste en une chaîne qui peut être utilisée directement. Par exemple, en EmacsLisp :

(let ((name "hi"))
  (prin1 `(eq? $name ,name)))
=> "(eq\\? $name "hi")"

Le « ? » est échappé, et readtags peut le gérer.

Les séquences d'échappement produites par write dans les Lisps de style Scheme sont exactement celles prises en charge par readtags, donc toute expression readtags valide peut être utilisée. Les Lisps de style Common Lisp peuvent produire des séquences d'échappement non reconnues par readtags, comme \#, donc les symboles contenant « # » ne peuvent pas être utilisés. Readtags fournit des alias pour ces Lisps, ils devraient donc :

  • Utiliser true pour #t.
  • Utiliser false pour #f.
  • Utiliser nil ou () pour ().
  • Utiliser (string->regexp "PATTERN") pour #/PATTERN/. Utiliser (string->regexp "PATTERN" :case-fold true) pour #/PATTERN/i. Notez que string->regexp n'exige pas l'échappement de « / » dans le motif.

Notez que si l'outil client communique avec readtags via un shell, alors dans la chaîne produite, ' doit toujours être remplacé par '"'"' pour éviter les expressions cassées et l'injection de shell.

Analyser la sortie de readtags

Dans la sortie de readtags, des tabulations peuvent apparaître dans toutes les valeurs de champs (par exemple, le nom du tag lui-même pourrait contenir des tabulations), ce qui rend difficile la division de la ligne en champs. Les outils clients devraient utiliser l'option -E, qui conserve les séquences d'échappement dans le fichier de tags, de sorte que le seul champ pouvant contenir des tabulations est le champ motif.

Le champ motif peut :

  • Utiliser un numéro de ligne. Cela ressemblera à nombre;" (par exemple, 10;").
  • Utiliser un motif de recherche. Cela ressemblera à /motif/;" ou ?motif?;". Notez que le motif de recherche peut contenir des tabulations.
  • Combiner les deux, comme nombre;/motif/;" ou nombre;?motif?;".

Ces règles s'appliquent aux fichiers de tags utilisant le format étendu, qui est le format par défaut. Le format hérité (c'est-à-dire --format=1) n'inclut pas les points-virgules. Il est ancien et peu utilisé, nous n'en discuterons donc pas ici.

Les outils clients peuvent diviser la ligne en utilisant les étapes suivantes :

  • Trouver les deux premiers tabulations dans la ligne, pour obtenir le nom et le champ d'entrée.
  • À partir de la 2ème tabulation :
  • Si un / suit, alors le délimiteur du motif est /.
  • Si un ? suit, alors le délimiteur du motif est ?.
  • Si un nombre suit, alors :
  • Si un ;/ suit le nombre, alors le délimiteur est /.
  • Si un ;? suit le nombre, alors le délimiteur est ?.
  • Si un ;" suit le nombre, alors le champ utilise uniquement le numéro de ligne, et il n'y a pas de délimiteur de motif (car il n'y a pas de motif regex). Dans ce cas, le champ motif se termine à la 3ème tabulation.
  • Après le délimiteur d'ouverture, trouver le prochain délimiteur de motif non échappé, et c'est le délimiteur de fermeture. Il sera suivi de ;" puis d'une tabulation. C'est la fin du champ motif. Par « délimiteur de motif non échappé », nous entendons un nombre pair (y compris 0) de barres obliques inverses avant lui.
  • À partir d'ici, divisez le reste de la ligne en champs par des tabulations.

Ensuite, les séquences d'échappement dans les champs autres que le champ motif doivent être traduites. Voir « Proposition » dans tags(5) pour connaître toutes les séquences d'échappement.

Utiliser le champ motif

Le champ motif spécifie comment trouver un tag dans son fichier source. Le code qui génère ce champ semble avoir une longue histoire, il y a donc quelques pièges et il est un peu difficile à gérer. Un outil client pourrait simplement exiger le champ ligne : et sauter à la ligne qu'il spécifie, pour éviter d'utiliser le champ motif. Mais quoi qu'il en soit, nous discuterons ici de la manière d'en tirer le meilleur parti.

Vous devriez prendre les mots ici uniquement comme des suggestions, et non comme des normes. Un outil client pourrait certainement développer des moyens meilleurs (ou plus simples) d'utiliser le champ motif.

De la dernière section, nous savons que le champ motif peut contenir un numéro de ligne et un motif de recherche. Lorsqu'il ne contient que le numéro de ligne, sa manipulation est facile : vous sautez simplement à cette ligne.

Le motif de recherche ressemble à une commande EX, mais comme nous le verrons plus tard, ce n'est en fait pas une commande valide, donc un travail manuel est requis pour le traiter.

Le motif de recherche peut ressembler à /motif/, appelé « motif de recherche avant », ou ?motif?, appelé « motif de recherche arrière ». L'utilisation d'un motif de recherche signifie que même si le fichier source est mis à jour, tant que la partie contenant le tag ne change pas, nous pourrions toujours localiser correctement le tag en recherchant.

Lorsque le champ motif ne contient que le motif de recherche, vous le recherchez simplement. La direction de recherche (avant/arrière) n'a pas d'importance, car elle est décidée uniquement par l'activation ou non de l'option -B, et non par le contexte réel. Vous pouvez toujours commencer la recherche depuis, disons, le début du fichier.

Lorsque le motif de recherche et le numéro de ligne sont tous deux présents, vous pouvez tirer parti du numéro de ligne, en allant d'abord à la ligne, puis en recherchant l'occurrence la plus proche du motif. Une façon de faire cela est de rechercher le motif à la fois vers l'avant et vers l'arrière, et lorsqu'il y a une occurrence des deux côtés, de choisir celle qui est la plus proche.

L'avantage est que lorsqu'il y a plusieurs lignes identiques dans le fichier source (par exemple, le bloc COMMON en Fortran), cela peut nous aider à trouver la bonne ligne, même après la mise à jour du fichier source et le décalage de la position du tag de quelques lignes.

Parlons maintenant de la manière de rechercher le motif. Après avoir supprimé les / ou ? autour de celui-ci, le motif ressemble à un motif regex. Ce devrait être un motif regex, comme requis pour être une commande EX valide, mais ce n'en est en fait pas une, comme vous le verrez ci-dessous.

Il peut commencer par un ^, ce qui signifie que le motif commence au début d'une ligne. Il peut également se terminer par un non échappé $, ce qui signifie que le motif se termine à la fin d'une ligne. Gardons cette information et supprimons-la également.
