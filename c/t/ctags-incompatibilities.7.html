Cette page décrit les changements majeurs incompatibles introduits dans Universal Ctags, dérivé d'Exuberant

Ctags.

préchargement)

Universal Ctags ne charge pas ~/.ctags au démarrage. Les chemins des fichiers de préchar

gement ont changé. Voir la sec

commande

spécifié

standard.

$ ctags -o -

L'ordre d'application des motifs et des extensions dans --langma

Lors de l'application des correspondances pour un nom de fichier source donné, Exuberant Ctags teste les motifs de nom de fichier APRÈS les extensions de fichier (e-map-order). Universal Ctags fait différemment ; il teste les motifs de nom de fichier AVANT les extensions de fichier (u-map-ord

er).

Ce changement incompatibilité est introduit pour gérer la situation suivante

:
  • build.xml en tant que fichier
    • source,
  • Le parseur Ant déclare qu'il gère un motif de nom de fichier build.xml,
    • et
  • Le parseur XML déclare qu'il gère une extension de fichier .

Quel parseur doit être utilisé pour analyser build.xml ? L'hypothèse de Universal Ctags est que l'utilisateur peut vouloir utiliser le parseur Ant ; le motif de nom de fichier qu'il déclare est plus spécifique que l'extension de fichier déclarée par le parseur XML. Cependant, e-map-order choisit le parseur

XML.

Universal Ctags utilise donc l'ordre u-map-order même s'il introduit une incompatibilité

Même dans Exuberant Ctags, --file-tags n'est pas documenté dans sa page man. Au lieu de spécifier --file-tags ou --file-tags=yes, utilisez --extras=+f ou --extras=+{inpu

Au lieu de spécifier --file-tags=no, utilisez --extras=-f ou --extras=-{inpu

Universal Ctags introduit l'extra F/fileScope comme remplacement pour l'option --file

Au lieu de spécifier --file-tags ou --file-tags=yes, utilisez --extras=+F ou --extras=+{file

Au lieu de spécifier --file-tags=no, utilisez --extras=-F ou --extras=-{

Obsolescence de l'option --<LA

NG>-kinds

Certaines options ont <LANG> comme partie paramétrée dans leur nom, comme --foo-<LANG>=... ou --<LANG>-foo=.... La plupart de ces options dans Exuberant Ctags ont la première forme, --foo-<LANG>=.... L'exception est --<LANG>-k

inds.

Universal Ctags utilise la première forme pour toutes les options <LANG> paramétrées. Utilisez --kinds-<LANG> au lieu de --<LANG>-kinds dans Universal Ctags. --<LANG>-kinds fonctionne toujours mais sera supprimé à

l'avenir.

La première forme peut être

plus conviviale pour les mot
eurs de complétion de shell.

Interdiction de définir un kind avec file comme

nom

Le nom de kind file est réservé. Son utilisation comme partie d'une spécification de kind dans l'option --regex-<LANG>

est maintenan
t interdite.

Interdiction de définir un kind avec 'F' comme

lettre

La lettre de kind 'F' est réservée. Son utilisation comme partie d'une spécification de kind dans l'option --regex-<LANG>

est maintenan
t interdite.

Interdiction d'utiliser autre chose qu'un caractère alphabétique comme lettre de

kind

Exuberant Ctags accepte un caractère autre qu'un caractère alphabétique comme lettre de kind dans l'option --regex-<LANG>=... Universal Ct

ags n'accepte qu'un c
aractère alphabétique.

Caractères acceptables comme parties d'un nom de

kind

Exuberant Ctags accepte n'importe quel caractère comme partie d'un nom de kind défini avec --regex-<LANG>=/regex/remplacement/spécification-de-kind/

.

Universal Ctags n'accepte qu'un caractère alphabétique comme première lettre d'un nom de kind. Universal Ctags n'accepte que des caractères alphabétiques ou numériques pour les lettres

restantes.

Un exemple

: 
--regex-Foo=/ab
stract +class +
([a-z]+)/\1/a,a
bstract class/i

Universal Ctags rejette cela car le nom de kind, abstract class, contient un caractère

d'espacement.

Cette exigence vise à faire en sorte

que la sortie de Universal Ctags re
specte le format du fichier de tags.

Une combinaison de lettre de kind et de nom de

kind

Dans Universal Ctags, la combinaison d'une lettre de kind et d'un nom dedoit être unique dans un

langage.

Vous ne pouvez pas définir plus d'un type en réutilisant une lettre de type avec des noms de type différents. Vous ne pouvez pas définir plus d'un type en réutilisant un nom de type avec des lettres de type

différentes.

Un exemple

: 
--regex-Foo=/abstract +clas
s +([a-z]+)/\1/a,abstractCl
ass/i --regex-Foo=/attribute
+([a-z]+)/\1/a,attribute/i

Universal Ctags rejette ceci car la lettre de type, 'a', est utilisée deux fois pour définir un type abstractClass et attri

but
e.

Utilisation de caractères numériques dans la partie nom du tagfield

tag

Le format de fichier tags version 2, le format de sortie par défaut d' Exuberant Ctags, n'accepte que des caractères alphabétiques dans la partie nom du tagfield

tag.

Universal Ctags introduit une exception à cette spécification ; il peut utiliser des caractères numériques en plus des caractères alphabétiques en tant que lettres autres que la lettre initiale de la partie

nom.

Les types heading1, heading2, et heading3 dans le parse

ur HTML sont
des exemples.

Troncature du motif pour les lignes d'entrée

longues

Pour éviter de générer des fichiers tags trop volumineux, un champ motif est tronqué, par défaut, lorsque sa taille dépasse 96 octets. Une limite différente peut être spécifiée avec --pattern-length-limit=N. Spécifier 0 comme N résulte en aucune troncatur

e, comme le fait
Exuberant Ctags.

Lettres et noms de

types

Une lettre de type 'F' et un nom de type file sont réservés dans la partie principale. Un parseur ne peut pas avoir un type en conflit avec ces éléments réservés. Certains changements incompatibles sont introduits pour suivre la règle

ci-dessus.
  • Le type file de Cobol est renommé en fileDesc car le nom de type file est
    • réservé.
  • Le 'F' de Ruby (singletonMethod) est changé en 'S'
    • .
  • Le 'F' de SQL (field) est changé en 'E
