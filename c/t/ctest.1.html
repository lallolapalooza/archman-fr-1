LABEL

MATCHING

Tests may have labels attached to them. Tests may be included or excluded from a test run by filtering on the labels. Each individual filter is a regular expression applied to the labels attached to a

test.

When -L is used, in order for a test to be included in a test run, each regular expression must match at least one label. Using more than one -L option means "match all of

these".

The -LE option works just like -L, but excludes tests rather than including them. A test is excluded if each regular expression matches at least one

label.

If a test has no labels attached to it, then -L will never include that test, and -LE will never exclude that test. As an example of tests with labels, consider five tests, with the following

labels:
  • test1 has labels tuesday and producti
    • on
  • test2 has labels tuesday and te
    • st
  • test3 has labels wednesday and producti
    • on
  • test4 has label wednesd
    • ay
  • test5 has labels friday and t
    • e
s
t

Running ctest with -L tuesday -L test will select test2, which has both labels. Running CTest with -L test will select test2 and test5, because both of them have a label that matches that regular

expression.

Because the matching works with regular expressions, take note that running CTest with -L es will match all five tests. To select the tuesday and wednesday tests together, use a single regular expression that matches either of them, like -L "tu

e|w
ed".

SUMMARY

CTest prints timing summary information for each LABEL and subproject associated with the tests run. The label time summary will not include labels that are mapped to

subprojects.

When the PROCESSORS <#prop_test:PROCESSORS> test property is set, CTest will display a weighted test timing result in label and subproject summaries. The time is reported with sec * proc instead of just sec

The weighted time summary reported for each label or subproject j is computed

ALLOCATION DE

RESSOURCES

CTest fournit un mécanisme permettant aux tests de spécifier les ressources dont ils ont besoin de manière fine, et aux utilisateurs de spécifier les ressources disponibles sur la machine d'exécution. Cela permet à CTest de suivre en interne quelles ressources sont utilisées et lesquelles sont libres, en planifiant les tests de manière à ce qu'ils ne tentent pas de réclamer des ressources qui ne sont pas

disponibles.

Lorsque la fonctionnalité d'allocation de ressources est utilisée, CTest ne sursouscrit pas les ressources. Par exemple, si une ressource a 8 emplacements, CTest n'exécutera pas de tests qui utilisent collectivement plus de 8 emplacements à la fois. Cela a pour effet de limiter le nombre de tests pouvant s'exécuter à un moment donné, même si un argument -j élevé est utilisé, si ces tests utilisent tous des emplacements de la même ressource. De plus, cela signifie qu'un test unique utilisant plus d'une ressource qu'il n'y en a de disponible sur une machine ne s'exécutera pas du tout (et sera signalé comme Non exécu

té).

Un cas d'utilisation courant de cette fonctionnalité est pour les tests nécessitant l'utilisation d'un GPU. Plusieurs tests peuvent allouer de la mémoire à partir d'un GPU simultanément, mais si trop de tests tentent de le faire à la fois, certains d'entre eux échoueront à allouer, entraînant un test en échec, alors que le test aurait réussi s'il avait eu la mémoire dont il avait besoin. En utilisant la fonctionnalité d'allocation de ressources, chaque test peut spécifier la quantité de mémoire dont il a besoin d'un GPU, permettant à CTest de planifier les tests de manière à ce que l'exécution simultanée de plusieurs de ces tests n'épuise pas le pool de mémoire du

GPU.

Veuillez noter que CTest n'a aucun concept de ce qu'est un GPU ou de la quantité de mémoire qu'il possède. Il n'a aucun moyen de communiquer avec un GPU pour récupérer ces informations ou effectuer une quelconque gestion de la mémoire, bien que le projet puisse définir un test qui fournit des détails sur la machine de test (voir Fichier de spécification de ressources généré dynamiquement)

.

CTest suit une liste de types de ressources abstraits, chacun ayant un certain nombre d'emplacements disponibles pour que les tests les utilisent. Chaque test spécifie le nombre d'emplacements dont il a besoin d'une ressource donnée, et CTest les planifie alors de manière à ce que le nombre total d'emplacements utilisés ne dépasse pas la capacité listée. Lorsqu'un test est exécuté et que des emplacements d'une ressource sont alloués à ce test, les tests peuvent supposer qu'ils ont l'utilisation exclusive de ces emplacements pendant la durée du processus du

test.

La fonctionnalité d'allocation de ressources de CTest se compose d'au moins deux entrées

:
  • Le fichier de spécification de ressources, décrit ci-dessous, qui décrit les ressources disponibles sur le
    • système.
  • La propriété RESOURCE_GROUPS <#prop_test:RESOURCE_G
    • ROUPS> des tests,
qui décrit les ressourc
es requises par le test.

Lorsque CTest exécute un test, les ressources allouées à ce test sont transmises sous la forme d'un ensemble de variables d'environnement comme décrit ci-dessous. L'utilisation de ces informations pour décider à quelle ressource se connecter est laissée à l'auteur du

test.

La propriété RESOURCE_GROUPS indique à CTest quelles ressources un test s'attend à utiliser, regroupées d'une manière significative pour le test. Le test lui-même doit lire les variables d'environnement pour déterminer quelles ressources ont été allouées à chaque groupe. Par exemple, chaque groupe peut correspondre à un processus que le test créera lors de son

exécution.

Notez que même si un test spécifie une propriété RESOURCE_GROUPS, il est toujours possible que ce test s'exécute sans aucune allocation de ressources (et sans les variables d'environnement correspondantes) si l'utilisateur ne passe pas de fichier de spécification de ressources. Le passage de ce fichier, soit via l'argument de ligne de commande --resource-spec-file, soit via l'argument RESOURCE_SPEC_FILE de ctest_test() <#command:ctest_test>, est ce qui active la fonctionnalité d'allocation de ressources. Les tests doivent vérifier la variable d'environnement CTEST_RESOURCE_GROUP_COUNT pour savoir si l'allocation de ressources est activée ou non. Cette variable sera toujours (et uniquement) définie si l'allocation de ressources est activée. Si l'allocation de ressources n'est pas activée, alors la variable CTEST_RESOURCE_GROUP_COUNT n'existera pas, même si elle existe pour le processus ctest parent. Si un test doit absolument avoir une allocation de ressources, il peut retourner un code de sortie indiquant un échec ou utiliser les propriétés SKIP_RETURN_CODE <#prop_test:SKIP_RETURN_CODE> ou SKIP_REGULAR_EXPRESSION <#prop_test:SKIP_REGULAR_EXPRESSION> pour indiquer un test

ignoré.
