Nom

ctags - Générer des fichiers de tags pour le code source

SYNOPSIS

ctags [<options>] [<fichier_source(s)>]
etags [<options>] [<fichier_source(s)>]

DESCRIPTION

Les programmes ctags et etags (voir l'option -e) (ci-après collectivement désignés sous le nom de ctags, sauf indication contraire) génèrent un index (ou fichier "de tags") pour une variété d'"objets de langage" trouvés dans les fichiers source(s). Ce fichier de tags permet à ces éléments d'être rapidement et facilement localisés par un éditeur de texte ou d'autres utilitaires (outils clients). Un tag désigne un objet de langage pour lequel une entrée d'index est disponible (ou, alternativement, l'entrée d'index créée pour cet objet).

Alternativement, ctags peut générer un fichier de références croisées qui liste, sous forme lisible par l'homme, des informations sur les divers objets de langage trouvés dans un ensemble de fichiers sources.

Les fichiers d'index de tags sont supportés par de nombreux éditeurs, qui permettent à l'utilisateur de localiser l'objet associé à un nom apparaissant dans un fichier source et de sauter vers le fichier et la ligne qui définissent le nom. Voir le manuel de votre éditeur préféré concernant l'utilisation de la commande ctags et des fichiers d'index de tags dans l'éditeur.

ctags est capable de générer différents types de tags pour chacun des nombreux langages différents. Pour une liste complète des langages supportés, les noms par lesquels ils sont reconnus, et les types de tags qui sont générés pour chacun, voir les options --list-languages et --list-kinds-full.

Cette page de manuel décrit Universal Ctags, une implémentation de ctags dérivée de Exuberant Ctags. Les principaux changements incompatibles entre Universal Ctags et Exuberant Ctags sont énumérés dans ctags-incompatibilities(7).

L'un des avantages d'Exuberant Ctags est qu'il permet à un utilisateur de définir un nouveau parseur depuis la ligne de commande. L'extension de cette capacité est l'une des principales caractéristiques d'Universal Ctags. ctags-optlib(7) décrit comment cette capacité est étendue.

Les nouvelles fonctionnalités expérimentales introduites ne sont pas expliquées ici. Si vous êtes intéressé par ces fonctionnalités et les internes de ctags, visitez https://docs.ctags.io/.

INTERFACE DE LIGNE DE COMMANDE

Malgré la richesse des options disponibles, les paramètres par défaut sont définis de manière à ce que ctags soit le plus souvent exécuté sans aucune option (par ex. "ctags *", ou "ctags -R"), ce qui créera un fichier de tags dans le répertoire courant pour tous les fichiers sources reconnus. Les options décrites ci-dessous sont fournies uniquement pour permettre une personnalisation afin de répondre à des besoins spécifiques.

Notez que les espaces séparant les options à une seule lettre de leurs paramètres sont facultatifs.

Notez également que les paramètres booléens des options sous forme longue (celles commençant par -- et qui prennent un paramètre [=(oui|non)]) peuvent être omis, auquel cas =oui est implicite. (par ex. --sort est équivalent à --sort=oui). Notez en outre que =1, =on et =true sont considérés comme des synonymes de =oui, et que =0, =off et =false sont considérés comme des synonymes de =non.

Certaines options sont soit ignorées, soit utiles uniquement lorsqu'elles sont utilisées en mode etags (voir l'option -e). Ces options seront notées.

<options> doit précéder les <fichiers_source(s)> suivant la convention POSIX standard.

Les options acceptant des noms de langages les accepteront en majuscules ou minuscules. Voir l'option --list-languages pour une liste complète des noms de langages intégrés.

Lettres et noms

Certaines options acceptent des indicateurs à une seule lettre comme paramètres (par ex. l'option --kinds-<LANG>). Spécifier uniquement des lettres aide un utilisateur à créer rapidement une ligne de commande complexe. Cependant, une ligne de commande incluant des séquences d'indicateurs à une seule lettre devient difficile à comprendre.

Universal Ctags accepte des indicateurs de nom long en plus de ces indicateurs à une seule lettre. Les indicateurs de nom long et à une seule lettre peuvent être mélangés dans un paramètre d'option en entourant chaque nom long d'accolades. Ainsi, à titre d'exemple, les trois notations suivantes pour l'option --kinds-C ont la même signification :

--kinds-C=+pLl
--kinds-C=+{prototype}{label}{local}
--kinds-C=+{prototype}L{local}

Notez que les accolades peuvent être des métacaractères dans votre interpréteur de commandes. Mettez des guillemets simples dans un tel cas.

Les options --list-... affichent les indicateurs à une seule lettre et les indicateurs de nom long associés.

Options de liste

Universal Ctags introduit de nombreuses options --list-... qui fournissent les données internes d'Universal Ctags (Voir "Listing Options"). Les utilisateurs et les outils clients peuvent utiliser ces données. Les options --with-list-header et --machinable ajustent la sortie de la plupart des options --list-....

Le réglage par défaut (--with-list-header=oui et --machinable=non) est pour une utilisation interactive depuis un terminal. L'en-tête qui explique la signification des colonnes est simplement ajouté à la sortie, et chaque colonne est alignée dans toutes les lignes. La ligne d'en-tête commence par un caractère dièse ('#').

Pour le scripting dans un outil client, --with-list-header=non et --machinable=oui peuvent être utiles. L'en-tête n'est pas ajouté à la sortie, et chaque colonne est séparée par des tabulations.

Notez que l'ordre des colonnes changera dans les futures versions. Cependant, les libellés dans l'en-tête ne changeront pas. Ainsi, en parcourant l'en-tête, un outil client peut trouver l'index de la colonne cible.

OPTIONS

ctags a plus d'options que celles listées ici. Les options commençant par un caractère de soulignement, telles que --_echo=<msg>, ne sont pas listées ici. Elles sont expérimentales ou à des fins de débogage.

Contrôle la manière dont les noms de fichiers sont associés aux langues (voir l'option --list-maps). --map-<LANG>=[+|-]<extension>
|<motif>
Cette option fournit un moyen de contrôler les correspondances des noms de fichiers aux langues de manière plus fine que l'option --langmap.

Dans ctags, plus d'une langue peut correspondre à un motif de nom de fichier <motif> ou à une <extension> de fichier (correspondance N:1). Pendant que ctags examine successivement chaque nom de fichier source, il essaie de déterminer la langue du fichier en appliquant les tests décrits dans « Détermination de la langue d'un fichier ».

Si une langue a été identifiée, le fichier est ouvert puis l'analyseur de langage approprié est appelé pour opérer sur le fichier actuellement ouvert. L'analyseur analyse le fichier et ajoute une entrée au fichier de balises pour chaque objet de langage qu'il est écrit pour gérer. Notes pour l'analyseur C/C++

Cette implémentation de ctags n'impose aucune exigence de formatage au code C, contrairement aux implémentations héritées. Les implémentations plus anciennes de ctags avaient tendance à s'appuyer sur certaines hypothèses de formatage afin de l'aider à résoudre les dilemmes de codage causés par les conditions prédéfinies.

En général, ctags essaie d'être intelligent à propos des directives prédéfinies conditionnelles. Si une directive prédéfinie conditionnelle est rencontrée dans une instruction qui définit une balise, ctags ne suit qu'une seule branche de cette conditionnelle (sauf dans le cas spécial de #if 0, où il ne suit qu'une seule branche). La raison en est qu'omettre de suivre une seule branche peut entraîner une syntaxe ambiguë, comme dans l'exemple suivant :

#else
union {

        long b;
}

NOM

ctags - générer des tables d'index pour les programmes source

SYNTAXE

ctags [option...] [fichier...]

DESCRIPTION

Cet utilitaire analyse les fichiers source spécifiés et crée une table d'index contenant des informations sur les objets de programmation tels que les fonctions, les variables, les macros, les classes, etc. Cette table d'index peut ensuite être utilisée par divers outils, tels que les éditeurs de texte, pour faciliter la navigation et la compréhension du code source.

Le format des fichiers de table est spécifié dans tags(5).

Les options sont regroupées en catégories ci-dessous. Les options commençant par un ¬ sont des options d'activation ou de désactivation. Par exemple, ¬option désactive une option qui est activée par défaut, et ¬option désactive une option qui est désactivée par défaut.

Vous pouvez spécifier options dans des fichiers d'options (voir la section FILES ci-dessous).

Indique si les chemins des balises doivent être relatifs au répertoire du fichier de balises. La valeur par défaut est yes.
--format-tag=format
Définit le format des lignes du fichier de balises. Les champs disponibles sont : name, address, kind, file, signature, language, role, parent, context.
--sort-empty[={yes,no}
Indique si les balises vides doivent être triées. La valeur par défaut est no.

DETAILS

Lorsque vous utilisez l'option --excmd=extended, ctags utilise des expressions régulières pour localiser les balises. Si vous avez un fichier source contenant une définition locale de paramètre qui a le même nom qu'une variable globale, et que le modèle de recherche pour les deux est identique, il est possible que le modèle de recherche trouve la déclaration de paramètre local avant de trouver la définition réelle de la variable globale, car les lignes (et donc leurs modèles de recherche) sont identiques.

Cela peut être évité en utilisant l'option --excmd=simple.

CHANGEMENTS INCOMPATIBLES

Voir ctags-incompatibilités(7) pour les incompatibilités entre Universal Ctags et Exuberant Ctags.

Cette section décrit les incompatibilités majeures au sein des versions d'Universal Ctags.

Unification de la lettre de type pour les types inconnus
Certains analyseurs utilisaient différentes lettres de type pour les types inconnus. EmacsLisp utilisait u. Go utilisait u. Julian utilisait x. Lisp utilisait u. Lua utilisait X. et Python utilisait x. Ils ont été unifiés en Y lors du développement de la version 5.9.x.

BOGUES

ctags a plus d'options que ls(1).

ctags suppose que le fichier d'entrée est écrit dans la grammaire correcte. Sinon, le résultat de ctags est indéfini. En d'autres termes, il possède une fonctionnalité "garbage in, garbage out" (GIGO).

Lors de l'analyse d'une définition de méthode C++ (par exemple, className::function), ctags ne peut pas déterminer si le spécificateur de portée est un nom de classe ou un spécificateur d'espace de noms et le liste toujours comme un nom de classe dans la partie portée des champs d'extension. De plus, si une fonction C++ est définie en dehors de la déclaration de classe (le cas le plus courant), la spécification d'accès (c'est-à-dire public, protected ou private) et les informations d'implémentation (par exemple, virtuelle, virtuelle pure) contenues dans la déclaration de la fonction ne sont pas connues lorsque la balise est générée pour la définition de la fonction. Elles seront cependant disponibles pour les prototypes (par exemple, --kinds-c++=+p).

Aucune balise qualifiée n'est générée pour les objets de langage hérités dans une classe.

VARIABLES D'ENVIRONNEMENT

TMPDIR
Sur les hôtes de type Unix où mkstemp(3) est disponible, la valeur de cette variable spécifie le répertoire dans lequel placer les fichiers temporaires. Cela peut être utile si la taille d'un fichier temporaire devient trop grande pour tenir dans la partition contenant le répertoire temporaire par défaut défini lors de la compilation.

ctags crée des fichiers temporaires uniquement si (1) un fichier de balises de style Emacs est généré, (2) le fichier de balises est envoyé vers la sortie standard, ou (3) le programme a été compilé pour utiliser un algorithme de tri interne pour trier les fichiers de balises au lieu de l'utilitaire sort(1) du système d'exploitation. Si l'utilitaire sort(1) du système d'exploitation est utilisé, il observera généralement également cette variable.

Notez que si ctags est setuid, la valeur de TMPDIR sera ignorée.

Chargement des fichiers d'options

$XDG_CONFIG_HOME/ctags/*.ctags, ou $HOME/.config/ctags/*.ctags si $XDG_CONFIG_HOME n'est pas défini

$HOME/.ctags.d/*.ctags

$HOMEDRIVE$HOMEPATH/ctags.d/*.ctags (uniquement sur MS Windows)

.ctags.d/*.ctags

ctags.d/*.ctags

Si l'un de ces fichiers de configuration existe, chacun contiendra un ensemble d'options par défaut qui seront lues dans l'ordre indiqué au démarrage de ctags, mais avant que toute option de ligne de commande ne soit lue. Cela permet de définir des valeurs par défaut personnelles ou au niveau du projet.

Il est possible de compiler ctags pour lire un fichier de configuration supplémentaire avant tous ceux mentionnés ci-dessus, ce qui sera indiqué si la sortie produite par l'option --version liste la fonctionnalité custom-conf.

Les options apparaissant sur la ligne de commande remplaceront les options spécifiées dans ces fichiers. Seules les options seront lues à partir de ces fichiers.

Notez que les fichiers d'options sont lus en mode ligne, où les espaces sont significatifs (car l'encadrement par guillemets du shell n'est pas possible), mais les espaces au début d'une ligne sont ignorés. Chaque ligne du fichier est lue comme un paramètre de ligne de commande (comme si elle était encadrée par des guillemets simples). Par conséquent, utilisez des retours à la ligne pour indiquer des arguments de ligne de commande séparés.

Une ligne commençant par '#' est traitée comme un commentaire.

Les fichiers *.ctags dans un répertoire sont chargés dans l'ordre alphabétique.

Liste par défaut du chemin optlib

$XDG_CONFIG_HOME/ctags, ou $HOME/.config/ctags si $XDG_CONFIG_HOME n'est pas défini

$HOME/.ctags.d

$HOMEDRIVE$HOMEPATH/ctags.d (uniquement sur MS Windows)

Ces répertoires font partie de la liste du chemin optlib par défaut. Voir "Options de fichiers d'options" pour la liste du chemin optlib.

Si vous avez un ensemble d'options que vous souhaitez activer conditionnellement, créez un répertoire dans le chemin de la liste du chemin optlib, et placez les options dans des fichiers portant l'extension .ctags sous le répertoire. --options=<nom_du_répertoire> sert à activer les options.

Par exemple, imaginez que vous ayez des options à activer uniquement lors de l'analyse de l'arborescence source du noyau Linux. Dans ce cas, créez le répertoire $HOME/.ctags.d/linux, placez les options dans $HOME/.ctags.d/linux/my.ctags. Si vous avez beaucoup d'options, vous pouvez les diviser en plusieurs fichiers comme $HOME/.ctags.d/linux/device-driver.ctags et $HOME/.ctags.d/linux/network-stack.ctags. Dans tous les cas, vous pouvez activer les options dans le(s) fichier(s) .ctags sous le répertoire en ajoutant --options=linux à votre ligne de commande ctags.
