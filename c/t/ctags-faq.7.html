DESCRIPTION

Quelle est la différence entre Universal Ctags et Exuberant Ctags ?

Universal Ctags est un fork non officiel d'Exuberant Ctags. Les différences sont résumées dans la page man ctags-incompatibilities(7).

La plus notable est qu'Universal Ctags ne lit pas le fichier ~/.ctags . À la place, il lit les fichiers *.ctags situés dans le répertoire ~/.ctags.d .

Comment éviter de devoir spécifier mes options préférées à chaque fois ?

Soit en définissant la variable d'environnement CTAGS avec vos options personnalisées, soit en les plaçant dans un fichier ~/.ctags.d/anyname.ctags dans votre répertoire personnel.

Que sont ces étranges fragments de texte commençant par ;" qui suivent de nombreuses lignes du fichier de tags ?

Ce sont des drapeaux d'extension. Ils sont ajoutés afin de fournir des informations supplémentaires sur le tag qui peuvent être utilisées par l'éditeur afin de gérer les tags de manière plus intelligente. Ils sont ajoutés à la partie commande EX de la ligne de tag d'une manière qui assure la compatibilité ascendante avec les implémentations existantes de l'éditeur Vi. Le point-virgule est un séparateur de commande EX et le guillemet double commence un commentaire EX. Ainsi, les drapeaux d'extension apparaissent comme un commentaire EX et doivent être ignorés par l'éditeur lorsqu'il traite la commande EX.

Certains éditeurs non-vi, cependant, n'implémentent que le strict minimum de commandes EX afin de traiter la commande de recherche ou le numéro de ligne dans le troisième champ du fichier de tags. Si vous rencontrez ce problème, utilisez l'option --format=1 pour générer un fichier de tags sans ces extensions (rappelez-vous que vous pouvez définir la variable d'environnement CTAGS avec n'importe quels arguments par défaut que vous souhaitez fournir). Demandez ensuite au fournisseur de votre éditeur d'implémenter la gestion de cette fonctionnalité des commandes EX.

Pourquoi ne puis-je pas me rendre à class::member?

Parce que, par défaut, ctags ne génère des tags que pour les identifiants séparés trouvés dans les fichiers source. Si vous spécifiez l'option --extra=+q , alors ctags générera aussi un second tag qualifié par la classe pour chaque membre de classe (donnée et fonction/méthode) sous la forme class::member pour C++, et sous la forme class.method pour Eiffel et Java.

Pourquoi atterris-je sur la mauvaise ligne lorsque je me rends à un tag ?

Par défaut, ctags encode le numéro de ligne dans le fichier où les tags de macro (#define) sont trouvés. Cela a été fait pour rester compatible avec la version UNIX originale de ctags. Si vous modifiez le fichier contenant le tag sans reconstruire le fichier de tags, l'emplacement du tag dans le fichier de tags peut ne plus correspondre à l'emplacement actuel.

Afin d'éviter ce problème, vous pouvez spécifier l'option --excmd=p, ce qui fait que ctags utilise un motif de recherche pour localiser les tags de macro. Je n'ai jamais découvert pourquoi l'original UNIX ctags utilisait exclusivement des numéros de ligne pour les tags de macro, mais j'ai jusqu'à présent résisté à changer le comportement par défaut d'Exuberant (et d'Universal) Ctags pour se comporter différemment.

Comment faire pour me rendre au tag que je veux au lieu du mauvais portant le même nom ?

Un fichier de tags est simplement une liste de noms de tags et de l'endroit où les trouver. S'il y a des entrées en double, vous vous retrouvez souvent sur le mauvais parce que le fichier de tags est trié et votre éditeur localise le premier dans le fichier de tags.

Le Vi standard ne fournit aucune fonctionnalité pour modifier ce comportement. Cependant, Vim a de bonnes fonctionnalités pour minimiser ce problème, principalement en examinant toutes les correspondances et en choisissant la meilleure selon les circonstances. Vim fournit également des commandes qui permettent la sélection du tag correspondant désiré.

Comment localiser toutes les références à une fonction ou une variable spécifique ?

Il existe déjà plusieurs paquets disponibles qui fournissent cette fonctionnalité. À savoir : le système de tags de code source GLOBAL, GNU id-utils, cscope et cflow. Au moment de la rédaction, ils se trouvent aux emplacements suivants :

  • GLOBAL : http://www.gnu.org/software/global
  • id-utils : http://www.gnu.org/software/idutils/idutils.html
  • cscope : http://cscope.sourceforge.net
  • cflow : <ftp://www.ibiblio.org/pub/Linux/devel/lang/c>

Pourquoi l'ajout de tags à un fichier de tags est-il si long ?

Parfois, dans une tentative de construire un fichier de tags global pour tous les fichiers source d'une grande arborescence de source de nombreux répertoires, quelqu'un essaiera de lancer ctags en mode ajout (-a) sur chaque répertoire de la hiérarchie. Chaque fois que ctags est invoqué, son comportement par défaut est de trier le fichier de tags une fois que les tags de cette exécution ont été ajoutés. À mesure que le fichier de tags cumulé grandit, le temps de tri augmente arithmétiquement.

La meilleure façon d'éviter ce problème (et la plus efficace) est de faire usage de l'option --recurse (ou -R) de ctags en exécutant la commande suivante à la racine de la hiérarchie de répertoires (exécutant ainsi ctags une seule fois) :

ctags -R

Si vous insistez vraiment pour lancer ctags séparément sur chaque répertoire, vous pouvez éviter la passe de tri à chaque fois en spécifiant l'option --sort=no. Une fois que le fichier de tags est complètement construit, utilisez la commande sort pour trier manuellement le fichier de tags final, ou laissez la dernière invocation de ctags trier le fichier.

Comment devrais-je configurer les fichiers de tags pour une hiérarchie de répertoires à plusieurs niveaux ?

Il y a quelques façons d'aborder cela :

1.
Un fichier de tags local dans chaque répertoire contenant uniquement les tags pour les fichiers source de ce répertoire.
2.
Un seul grand fichierobal tag file present in the root directory of your hierarchy, containing all tags present in all source files in the hierarchy.
3.
A local tag file in each directory containing only the tags for source files in that directory, in addition
to one single global tag file present in the root directory of your hierarchy, containing all non-static tags present in all source files in the hierarchy.
4
.
A local tag file in each directory of the hierarchy, each one containing all tags present in source files in
that directory and all non-static tags in every directory below it (note that this implies also having one big tag file in the root directory of the hierarchy).

Yes, Unicode file names are supported on unix-like platforms
    (Linux, macOS, Cygwin, etc.). However, on MS Windows, you need to use Windows 10 version 1903 or
    later to use Unicode file names. (This is an experimental feature, though.)
    On older versions on Windows, Universal Ctags only support file names
    represented in the current code page. If you still want to use Unicode file
    names on them, use Cygwin or MSYS2 version of Universal Ctags as a
    
workaround.
