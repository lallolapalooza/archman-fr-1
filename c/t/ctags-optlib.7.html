Exuberant Ctags, l'ancêtre de Universal Ctags, a fourni un moyen de définir un nouvel analyseur depuis la ligne de commande. Universal Ctags étend et affine cette fonctionnalité. L'analyseur optlib est le nom de ce type d'analyseur dans Universal Ctags. "opt" indique qu'un analyseur est défini par une combinaison d'options de ligne de commande. "lib" indique qu'un analyseur optlib peut être plus qu'une configuration personnelle ad

hoc.

Cette page manuelle est destinée aux personnes qui souhaitent définir un analyseur optlib. Les lecteurs doivent d'abord lire ctags(1) d'Universal

Ctags.

La conception des options et des notations pour définir un analyseur dans Exuberant Ctags peut se concentrer sur la réduction du nombre de frappes de l'utilisateur. Réduire le nombre de frappes est important pour les utilisateurs qui souhaitent définir (ou personnaliser) un analyseur

rapidement.

D'un autre côté, la conception dans Universal Ctags se concentre sur la maintenabilité. La notation d'Universal Ctags est plus redondante que celle d'Exuberant Ctags ; le kind nouvellement introduit doit être déclaré explicitement, les noms (longs) sont préférés aux indicateurs d'une lettre spécifiant les kinds, et les règles de nommage sont plus

strictes.

Cette page manuelle n'explique que les options et les indicateurs stables. Universal Ctags introduit également des options et des indicateurs expérimentaux dont les noms commencent par _. Pour la documentation de ces options et indicateurs, visitez le site web d'Universal Ctags à l'adresse https://ctag

s.io/.

Stocker une définition d'analyseur dans un

fichier

Bien qu'il soit possible de définir un analyseur depuis la ligne de commande, vous ne souhaitez pas taper la même ligne de commande chaque fois que vous avez besoin de l'analyseur. Vous pouvez stocker les options de définition d'un analyseur dans un

fichier.

ctags charge les fichiers (fichiers de préchargement) listés dans la section « FILES » de ctags(1) au démarrage du programme. Vous pouvez y placer la définition de votre analyseur dont vous avez généralement

besoin.

--options=<chemin>, --options-maybe=<chemin>, et --optlib-dir=[+]<répertoire> servent à charger des fichiers optlib dont vous avez occasionnellement besoin. Voir la section « Option File Options » de ctags(1) pour ces

options.

Comme expliqué dans la section « FILES » de ctags(1), les options de définition d'un analyseur sont listées ligne par ligne dans un fichier optlib. Les espaces en début de ligne sont ignorés. Une ligne commençant par '#' est traitée comme un commentaire. Il n'est pas nécessaire d'échapper les métacaractères du

shell.

Utilisez .ctags comme extension de fichier pour un fichier optlib. Vous pouvez définir plusieurs analyseurs dans un fichier optlib, mais il est préférable de créer un fichier pour chaque définition

d'analyseur.

--langdef=<no
m>
Définit une nouvelle langue définie par l'utilisateur, <nom>, à analyser avec des expressions régulières. Une fois défini, <nom> peut être utilisé dans d'autres options prenant des noms de langues.

<nom> doit être composé de caractères alphanumériques, de '#' ou de '+' ('[a-zA-Z0-9#+]+'). Les caractères graphiques autres que '#' et '+' sont interdits (ou réservés). Certains d'entre eux ([-=:{.]) sont interdits car ils peuvent déconcerter l'analyseur de ligne de commande de ctags. Les autres sont simplement réservés pour l'extension future de

ctags.

all est une exception. all comme <nom> n'est pas acceptable. C'est un mot réservé. Voir la description de l'option --kinds-(<LANG>|all)=[+|-](<kinds>|*) dans ctags(1) pour savoir comment le mot réservé est

utilisé.

NONE est une autre exception. NONE comme <nom> n'est pas

acceptable.

Les noms des analyseurs intégrés sont en majuscules. Quand ctags évalue une option dans une ligne de commande et choisit un analyseur, ctags utilise les noms des analyseurs de manière insensible à la casse. Par conséquent, donner un nom commençant par une lettre minuscule ne vous aide pas à éviter le conflit de noms d'analyseur. Cependant, dans un fichier de tags, ctags imprime les noms des analyseurs de manière sensible à la casse ; il imprime un nom d'analyseur tel que spécifié dans l'option --langdef=<nom>. Par conséquent, nous vous recommandons de donner un nom commençant par une lettre minuscule à votre analyseur optlib privé

. Avec cette convention, les gens peuvent savoir si une entrée de tag dans un fichi
er de tags provient d'un analyseur intégré ou d'un analyseur optlib privé.
--kinddef-<LANG>=<lettre>,<nom>,
<description>
Définit un kind pour <LANG>. Ne confondez pas cela avec --kinds-<LANG>.

<lettre> doit être un caractère alphabétique ('[a-zA-EG-Z]') autre que "F". "F" est réservé pour représenter un fichier depuis Exuberant

Ctags.

<nom> doit commencer par un caractère alphabétique, et le reste doit être alphanumérique ('[a-zA-Z][a-zA-Z0-9]*'). N'utilisez pas "file" comme <nom>. Il est réservé pour représenter un fichier depuis Exuberant

Ctags.

Notez que l'utilisation d'un chiffre dans un <nom> viole la version 2 du format de fichier de tags bien que ctags l'accepte. Pour plus de détails, voir

tags(5).

<description> peut être composée de n'importe quels caractères ASCII imprimables. L'exception est { et \. { est réservé pour ajouter des indicateurs à cette option à l'avenir. Mettez donc \ avant { pour inclure { dans une description. Pour inclure \ lui-même dans une description, mettez \ avant \

--regex-<LANG>=/<line_pattern>/<name_pattern>/<kind-spec>/[<flags>

Définit une expression régulière sur une seule ligne.

La paire /<line_pattern>/<name_pattern>/ définit un motif de remplacement d'expression régulière, similaire dans le style aux commandes de substitution sed, s/regexp/replacement/, avec lesquelles générer des tags à partir des fichiers sources associés au langage nommé, <LANG>, (insensible à la casse ; soit un langage intégré ou défini par l'utilisateur)

.

L'expression régulière, <line_pattern>, définit une expression régulière étendue (approximativement celle utilisée par egrep(1)), qui est utilisée pour localiser une ligne source unique contenant un tag et peut spécifier des caractères de tabulation en utilisant \t

.

Lorsqu'une ligne correspondante est trouvée, un tag sera généré pour le nom défini par <name_pattern>, qui contiendra généralement les références arrière spéciales \1 à \9 pour faire référence aux groupes de sous-expressions correspondants dans <line_patt

ern>.

Les caractères de séparation '/' montrés dans le paramètre de l'option peuvent en fait être remplacés par n'importe quel caractère. Notez que le caractère de séparation utilisé devra être échappé avec une barre oblique inverse ('\') partout où il est utilisé dans le paramètre en tant que quelque chose d'autre qu'un séparateur. L'expression régulière définie par cette option est ajoutée à la liste actuelle des expressions régulières pour le langage spécifié, sauf si le paramètre est omis, auquel cas la liste actuelle est

effacée.

Sauf si modifié par <flags>, <line_pattern> est interprété comme une expression régulière étendue POSIX. Le <name_pattern> devrait s'étendre pour toutes les lignes correspondantes à une chaîne de caractères non vide, ou un message d'avertissement sera rapporté, sauf si le drapeau regex {placeholder} est

spécifié.

Un spécificateur de kind (<kind-spec>) pour les tags correspondant à l'expression régulière peut suivre <name_pattern>, ce qui déterminera quel type de tag est rapporté dans le champ d'extension kind (voir tags(5)

).

plète.

La forme à une lettre sous la forme de <letter>. Elle fait simplement référence à un kind <letter> défini avec --kinddef-<LANG>. Cette forme est recommandée dans Universal

Ctags.

La forme complète de <kind-spec> est sous la forme de <letter>,<name>,<description>. Soit le kind <name> et/ou le <description> peuvent être omis. Voir la description de l'option --kinddef-<LANG>=<letter>,<name>,<description> à propos des

éléments.

La forme complète n'est prise en charge que pour maintenir la compatibilité avec Exuberant Ctags qui n'a pas l'option --kinddef-<LANG>. La prise en charge de cette forme sera retirée de Universal Ctags à

l'avenir.

Spécifie quoi faire avec la pile de portée interne.

Un analyseur programmé avec --regex-<LANG> a une pile (pile de portée) interne. Vous pouvez l'utiliser pour suivre les informations de portée. L' indicateur scope=... sert à manipuler et utiliser la pile de

portée.

Si {scope=push} est spécifié, une balise capturée avec --regex-<LANG> est poussée sur la pile. {scope=push} implique {scope=r

ef}.

Vous pouvez remplir le champ de portée (scope:) de la balise capturée avec {scope=ref}. Si l'indicateur {scope=ref} est donné, ctags attache la balise du sommet à la balise capturée avec --regex-<LANG> comme valeur pour le champ scope

:.

ctags retire la balise du sommet de la pile lorsque --regex-<LANG> avec {scope=pop} correspond à la ligne

d'entrée.

Spécifier {scope=clear} supprime toutes les balises dans la portée. Spécifier {scope=set} supprime toutes les balises dans la portée, puis pousse la balise capturée comme {scope=push} le

fait.

{scope=replace} fait les trois choses séquentiellement. D'abord il fait la même chose que {scope=pop}, puis remplit le champ scope: de la balise capturée avec --regex-<LANG>, et pousse la balise sur la pile de portée comme si {scope=push} était donné en dernier. Vous ne pouvez pas spécifier une autre action de portée avec {scope=repl

ace}.

Vous ne voulez pas spécifier {scope=pop}{scope=push} comme alternative à {scope=replace}; {scope=pop}{scope=push} remplit le champ scope: de la balise capturée avec --regex-<LANG> d'abord, puis retire la balise du sommet de la pile, et pousse enfin la balise capturée sur la pile de portée. Le moment du remplissage du champ end est différent entre {scope=replace} et {scope=pop}{scop

e=push}.

Dans certains cas, vous pouvez vouloir utiliser --regex-<LANG> uniquement pour ses effets de bord : l'utiliser uniquement pour manipuler la pile mais pas pour capturer une balise. Dans un tel cas, rendez le composant <name_pattern> de l'option --regex-<LANG> vide tout en spécifiant {placeholder} comme indicateur de regex. Par exemple, une balise non nommée peut être placée sur la pile en donnant l'indicateur de regex "{scope=push}{place

holder}".

Vous vous demandez peut-être ce qui se passe si un motif de regex avec l'indicateur {scope=ref} correspond à une ligne d'entrée mais la pile est vide, ou une balise non nommée est au sommet. Si le motif de regex contient un indicateur {scope=ref} et que la pile est vide, l' indicateur {scope=ref} est ignoré et rien n'est attaché au champ scope

Si le sommet de la pile contient une balise non nommée, ctags cherche plus profondément dans la pile pour trouver la balise nommée la plus haute. Si elle atteint le bas de la pile sans trouver de balise nommée, l' indicateur {scope=ref} est ignoré et rien n'est attaché au champ scope
