DESCRIPTIO

N

Ccache est un cache de compilateur. Il accélère la recompilation en mettant en cache le résultat des compilations précédentes et en détectant quand la même compilation est effectuée à

nouveau.

Ccache a été soigneusement écrit pour produire toujours exactement la même sortie du compilateur que celle que vous obtiendriez sans le cache. La seule façon dont vous devriez pouvoir dire que vous utilisez ccache est la vitesse. Les exceptions actuellement connues à cet objectif sont listées sous AVERTISSEMENTS. Si vous découvrez un cas non documenté où ccache m

odifie la sortie de votre compil
ateur, veuillez nous en informer.

D'EXÉCUTION

Il existe deux façons différentes d'utiliser ccache pour mettre en cache une compilation

1.Préfixez votre commande de compilation par ccache. Cette méthode est la plus pratique si vous voulez simplement essayer ccache ou l'utiliser pour des projets spécifiques. Exemple :

cp ccache /usr/local/bin/g

Et ainsi de suite. Cela fonctionnera tant que le répertoire contenant les liens symboliques ou les copies de ccache précède le répertoire contenant le compilateur (généralement /usr/bin) dans PATH

Options

supplémentaires

Lorsqu'il est exécuté en tant que compilateur, ccache prend généralement les mêmes options de ligne de commande que le compilateur que vous utilisez. La seule exception à cela est l'option --ccache-skip. Cette option peut être utilisée pour dire à ccache d'éviter d'interpréter l'option suivante de quelque manière que ce soit et de la transmettre au compilateur telle

quelle.

Remarque

--ccache-skip indique actuellement à ccache de ne pas interpréter l'
option suivante comme une option de compila

teur spéciale — l'option sera tout de m
ême incluse dans le hachage du mode direct.

La raison pour laquelle cela peut être important est que ccache a besoin d'analyser la ligne de commande et de déterminer ce qui est un nom de fichier d'entrée et ce qui est une option de compilateur, car il a besoin du nom de fichier d'entrée pour déterminer le nom du fichier objet résultant (entre autres choses). L'heuristique que ccache utilise lors de l'analyse de la ligne de commande est que tout argument qui existe en tant que fichier est traité comme un nom de fichier d'entrée. En utilisant --ccache-skip, vous pouvez forcer une option à ne pas être traitée comme un nom de fichier d'entrée et à être transmise au compilateur comme option de ligne de commande à la

place.

Un autre cas où --ccache-skip peut être utile est si ccache interprète une option de manière spéciale alors qu'il ne devrait pas, car l'option a une autre signification pour votre compilateur que ce que ccache

pense.

Syntaxe des valeurs de

Toutes les valeurs de configuration prennent en charge l'expansion des variables d'environnement. La syntaxe est similaire à la syntaxe du shell POSIX : $VAR ou ${VAR}. Les deux variantes seront développées en la valeur de la variable d'environnement VAR

Les fichiers de configuration sont dans un format simple « clé = valeur », une option par ligne. Les lignes commençant par une dièse sont des commentaires. Les lignes vides sont ignorées, tout comme les espaces entourant les clés et les valeurs. Exemple

Certaines options de configuration sont des valeurs booléennes (c'est-à-dire des valeurs de vérité). Dans un fichier de configuration, de telles valeurs doivent être définies sur la chaîne true ou false. Pour les variables d'environnement correspondantes, la sémantique est un peu différente

Cette option spécifie si ccache doit réécrire les chemins relatifs dans la sortie textuelle du compilateur (erreur standard et sortie standard) en chemins absolus. base_dir (CCACHE_BASEDIR

Cette option est une liste de chemins de répertoires absolus. Le séparateur de liste est le point-virgule sur les systèmes Windows et les deux-points sur les autres systèmes. Si elle est définie, ccache réécrira les chemins absolus en chemins relatifs au répertoire de travail courant, mais uniquement les chemins absolus qui commencent par l'un des chemins base_dir. Les résultats du cache peuvent alors être partagés pour des compilations dans différents répertoires même si le projet utilise des chemins absolus dans la ligne de commande du compilateur. Voir également la discussion sous COMPILATION DANS DIFFÉRENTS RÉPERTOIRES. Si elle est définie à la chaîne vide (qui est la valeur par défaut), aucune réécriture n'est effectuée.

Un chemin typique à utiliser comme base_dir est votre répertoire personnel ou un autre répertoire qui est parent de vos répertoires de projet. N'utilisez pas / comme répertoire de base car cela ferait que ccache réécrirait également les chemins vers les fichiers d'en-tête système, ce qui est généralement contre-productif

.

Par exemple, supposons que le répertoire de travail courant d'Alice est /home/alice/project1/build et qu'elle compile comme ceci

GESTION DE LA TAILLE DU

CACHE

Par défaut, ccache a une limite de 5 Go pour la taille totale des fichiers du cache et aucune limite sur le nombre de fichiers. Vous pouvez définir des limites différentes en utilisant les options de ligne de commande -M/--max-size et -F/--max-files. Utilisez l'option -s/--show-stats pour voir la taille du cache et les limites actuellement configurées (en plus de diverses autres statistiques)

Le nettoyage peut être déclenché de deux manières différentes : automatique et

manuelle.

Nettoyage

automatique

Après qu'un nouveau résultat de compilation a été écrit dans le cache local, ccache déclenchera un nettoyage automatique si max_size ou max_files est dépassé. Le nettoyage supprime les entrées du cache dans un ordre approximatif LRU (moins récemment utilisé) basé sur l'heure de modification (mtime) des fichiers dans le cache. Pour cette raison, ccache met à jour le mtime des fichiers du cache lus lors d'un succès de cache pour les marquer comme récemment

utilisés.

Pour des raisons de performance, seules les entrées d'un sous-ensemble du cache sont prises en compte lorsqu'un nettoyage automatique est déclenché. Cela signifie qu'il n'y a pas de garantie que les entrées les plus anciennes de l'ensemble du cache soient évincées à chaque nettoyage individuel, mais avec le temps, l'ensemble du cache aura un comportement d'« éjection LRU approximative

»
.

Nettoyage

manuel

Vous pouvez exécuter ccache -c/--cleanup pour forcer le nettoyage de l'ensemble du cache. Cela recalculera les informations de taille du cache et s'assurera également que la taille du cache ne dépasse pas max_size et max_files

UTILISATION DE CCACHE AVEC D'AUTRES ENVELOPPES DE

COMPILATEUR

La façon recommandée de combiner ccache avec une autre enveloppe de compilateur (comme « distcc ») est de laisser ccache exécuter l'enveloppe de compilateur. C'est accompli en définissant prefix_command, par exemple en définissant environnementale CCACHE_PREFIX au nom de l'enveloppe (par exemple, distcc). Ccache préfixera alors la ligne de commande avec la commande spécifiée lors de l'exécution du compilateur. Pour spécifier plusieurs commandes de préfixe, définissez prefix_command sur une liste de commandes séparées par des deux-points.

À moins que vous ne définissiez compiler_check sur une commande appropriée (voir la description de cette option de configuration), il n'est pas recommandé d'utiliser la forme ccache anotherwrapper compiler args comme commande de compilation. Il n'est pas non plus recommandé d'utiliser la technique de mascarade pour l'autre enveloppe de compilateur. La raison est que, par défaut, ccache hachera dans les deux cas le mtime et la taille de l'autre enveloppe au lieu du vrai compilateur, ce qui signifie que :

•Les mises à niveau du compilateur ne seront pas détectées correctement.
•Les résultats mis en cache ne seront pas partagés entre les compilations avec et sans l'autre enveloppe.

Autre détail mineur : si prefix_command est utilisé, ccache n'invoquera pas l'autre enveloppe lors de l'exécution du préprocesseur, ce qui améliore les performances. Vous pouvez utiliser prefix_command_cpp si vous souhaitez également invoquer l'autre enveloppe lors du prétraitement (normalement en ajoutant -E).

DÉPANNAGE

Général

Un conseil général pour obtenir des informations sur ce que fait ccache est d'activer la journalisation de débogage en définissant l'option de configuration debug (ou la variable d'environnement CCACHE_DEBUG) ; voir DÉBOGAGE DU CACHE pour plus d'informations. Une autre façon de suivre ce qui se passe est de vérifier la sortie de ccache -s.

Performance

Ccache a été écrit pour être performant dès le départ, mais parfois vous devrez peut-être ajuster la façon dont vous utilisez le compilateur et ccache afin d'améliorer les performances.

Comme ccache fonctionne mieux lorsque les entrées/sorties sont rapides, placez le répertoire de cache sur un périphérique de stockage rapide si possible. Avoir beaucoup de mémoire libre afin que les fichiers dans le répertoire de cache restent dans le cache disque est également préférable.

Un bon moyen de surveiller l'efficacité de ccache est d'exécuter ccache -s avant et après votre compilation, puis de comparer les compteurs statistiques. Voici quelques problèmes courants et ce qui peut être fait pour augmenter le taux de réussite :

•Si le compteur des succès de cache précompilés a été incrémenté au lieu de celui des succès de cache directs, ccache est revenu au mode préprocesseur, qui est généralement plus lent. Quelques raisons possibles sont :
•Le code source a été modifié de telle manière que la sortie du préprocesseur n'est pas affectée.
•Les arguments du compilateur qui sont hachés en mode direct mais pas en mode préprocesseur ont changé (-I, -include, -D, etc.) et ils n'ont pas affecté la sortie du préprocesseur.
•L'option de compilateur -Xpreprocessor ou -Wp,* (sauf -Wp,-MD,<path>, -Wp,-MMD,<path> et -Wp,-D<define>) est utilisée.
•C'était la première compilation avec une nouvelle valeur du répertoire de base.
•Une modification ou un changement d'état d'un des fichiers d'en-tête est trop récent. Voir GESTION DES FICHIERS SOURCE NOUVELLEMENT CRÉÉS.
•La macro préprocesseur __TIME__ est (potentiellement) utilisée. Ccache désactive le mode direct si __TIME__ est présent dans le code source. Ceci est fait par mesure de sécurité car la chaîne indique qu'une macro __TIME__ *peut* affecter la sortie. (Pour en être sûr, ccache devrait exécuter le préprocesseur, mais le seul but du mode direct est d'éviter cela.) Si vous savez que __TIME__ n'est pas utilisé en pratique, ou si vous ne vous souciez pas que ccache produise des objets où __TIME__ est développé en quelque chose du passé, vous pouvez définir sloppiness sur time_macros.
•La macro préprocesseur __DATE__ est (potentiellement) utilisée et la date a changé. Ceci est similaire à la façon dont __TIME__ est géré. Si __DATE__ est présent dans le code source, ccache hache la date actuelle afin de pouvoir produire le bon fichier objet si la macro __DATE__ affecte la sortie. Si vous savez que __DATE__ n'est pas utilisé en pratique, ou si vous ne vous souciez pas que ccache produise des objets où __DATE__ est développé en quelque chose du passé, vous pouvez définir sloppiness sur time_macros.
•La macro préprocesseur __TIMESTAMP__ est (potentiellement) utilisée et l'heure de modification du fichier source a changé. Ceci est similaire à la façon dont __TIME__ est géré. Si __TIMESTAMP__ est présent dans le code source, ccache hache la représentation textuelle de l'heure de modification du fichier source afin de pouvoir produire le bon fichier objet si la macro __TIMESTAMP__ affecte la sortie. Si vous savez que __TIMESTAMP__ n'est pas utilisé en pratique, ou si vous ne vous souciez pas que ccache produise des objets où __TIMESTAMP__ est développé en quelque chose du passé, vous pouvez définir sloppiness sur time_macros.
•Le chemin du fichier d'entrée a changé. Ccache inclut le chemin du fichier d'entrée dans le hachage du mode direct afin de pouvoir tenir compte des fichiers d'inclusion relatifs et de produire un fichier objet correct si le code source inclut une macro __FILE__.
•Si un compteur de succès de cache n'a pas été incrémenté même si le même code a été compilé et mis en cache auparavant, ccache a soit détecté que quelque chose a changé de toute façon, soit un nettoyage a été effectué (explicitement ou implicitement lorsqu'une limite de cache a été atteinte). Certaines choses peut-être peu évidentes qui peuvent entraîner une absence de succès de cache sont l'utilisation des macros __TIME__, __DATE__ ou __TIMESTAMP__, ou l'utilisation de code généré automatiquement contenant une horodatage, un compteur de compilation ou d'autres informations volatiles.
•Si « Plusieurs fichiers source » a été incrémenté, c'est une indication que le compilateur a été invoqué sur plusieurs fichiers source à la fois. Ccache ne prend pas cela en charge. Compilez les fichiers source séparément si possible.
•Si « Option de compilateur non prise en charge » a été incrémentée, activez la journalisation de débogage et vérifiez quelle option de compilateur a été rejetée.
•Si « Échec du prétraitement » a été incrémenté, une raison possible est que des en-têtes précompilés sont utilisés. Voir EN-TÊTES PRÉCOMPILÉS pour remédier à cela.
•Si « Impossible d'utiliser l'en-tête précompilé » a été incrémenté, voir EN-TÊTES PRÉCOMPILÉS.
•Si « Impossible d'utiliser les modules » a été incrémenté, voir MODULES C++.

Fichiers objets corrompus

Il convient de noter que ccache est susceptible aux problèmes de stockage généraux. Si un mauvais fichier objet s'infiltre dans le cache pour une raison quelconque, il restera bien sûr mauvais. Quelques raisons possibles pour des fichiers objets erronés sont du matériel défectueux (disque dur, contrôleur de disque, mémoire, etc.), des pilotes ou des systèmes de fichiers bogués, une mauvaise prefix_command ou une enveloppe de compilateur défectueuse. Si cela se produit, le moyen le plus simple de le corriger est le suivant :

1.Compilez de manière à ce que le mauvais fichier objet se retrouve dans l'arborescence de compilation.
2.Supprimez le mauvais fichier objet de l'arborescence de compilation.
3.Recompilez avec CCACHE_RECACHE défini.

Une alternative est de vider tout le cache avec ccache -C si vous ne craignez pas de perdre d'autres résultats mis en cache.

Il n'y a aucun problème signalé concernant ccache produisant des fichiers objets cassés de manière reproductible. Cela ne signifie pas que cela ne peut pas arriver, donc si vous trouvez un cas répétable, veuillez le signaler.
