NOM

CPAN::Meta::History::Meta_1_3 - Spécification des métadonnées version 1.3 pour META.yml

PRÉFACE

Ceci est une copie historique de la spécification version 1.3 pour les fichiers META.yml , copyright Ken Williams et sous licence selon les mêmes conditions que Perl lui-même.

Modifications par rapport à l'original :

  • Diverses corrections d'orthographe
  • Inclusion de la liste des licences valides issue de Module::Build 0.2805 plutôt qu'un lien vers le module, avec des mises à mineures du texte et des liens pour refléter les versions à l'époque de la publication.
  • Correction de certains liens morts pour pointer vers des ressources actives.

SYNOPSIS

--- #YAML:1.0
name: Module-Build
abstract: Build and install Perl modules
version: 0.20
author:
  - Ken Williams <kwilliams@cpan.org>
license: perl
distribution_type: module
requires:
  Config: 0
  Cwd: 0
  Data::Dumper: 0
  ExtUtils::Install: 0
  File::Basename: 0
  File::Compare: 0
  File::Copy: 0
  File::Find: 0
  File::Path: 0
  File::Spec: 0
  IO::File: 0
  perl: 5.005_03
recommends:
  Archive::Tar: 1.00
  ExtUtils::Install: 0.3
  ExtUtils::ParseXS: 2.02
  Pod::Text: 0
  YAML: 0.35
build_requires:
  Test: 0
urls:
  license: http://dev.perl.org/licenses/
meta-spec:
  version: 1.3
  url: http://module-build.sourceforge.net/META-spec-v1.3.html
generated_by: Module::Build version 0.20

DESCRIPTION

Ce document décrit la version 1.3 de la spécification META.yml

. Le fichier META.yml décrit des propriétés importantes des distributions Perl contribuées, comme celles que l'on trouve sur CPAN. Il est généralement créé par des outils comme Module::Build, Module::Install et ExtUtils::MakeMaker.

Les champs du fichier META.yml sont destinés à être utiles pour les personnes qui maintiennent des collections de modules (comme CPAN), pour celles qui écrivent des outils d'installation (comme CPAN.pm ou CPANPLUS), ou simplement pour celles qui veulent connaître certaines informations sur une distribution avant de la télécharger et de commencer à l'installer.

Note : La dernière version stable de cette spécification peut toujours être trouvée à l'adresse http://module-build.sourceforge.net/META-spec-current.html, et la dernière version de développement (qui peut inclure des choses qui ne figureront pas dans la version stable) peut toujours être trouvée à http://module-build.sourceforge.net/META-spec-blead.html.

FORMAT

Les fichiers META.yml sont écrits au format YAML (voir http://www.yaml.org/).

Voir les liens suivants pour comprendre pourquoi nous avons choisi YAML plutôt que, par exemple, XML ou Data::Dumper :

  • Plans de conception de Module::Build http://www.nntp.perl.org/group/perl.makemaker/2002/04/msg407.html
  • Pas convaincu par YAML http://www.nntp.perl.org/group/perl.module-authors/2003/11/msg1353.html
  • Préoccupations concernant META http://www.nntp.perl.org/group/perl.module-authors/2003/11/msg1385.html

TERMINOLOGIE

distribution
C'est l'objet principal décrit par la spécification META.yml . Dans le contexte de ce document, cela fait généralement référence à une collection de modules, de scripts et/ou de documents qui sont distribués ensemble pour que d'autres développeurs puissent les utiliser. Des exemples de distributions sont "Class-Container", "libwww-perl"ou "DBI".
module
Cela fait référence à une bibliothèque de code réutilisable, généralement contenue dans un seul fichier. Actuellement, nous parlons principalement de modules perl, mais cette spécification devrait être suffisamment ouverte pour s'appliquer à d'autres langages également (ex. python, ruby). Des exemples de modules sont "Class::Container", "LWP::Simple"ou "DBD::File".

EN-TÊTE

La première ligne d'un fichier META.yml devrait être un en-tête de document YAML valide comme "--- #YAML:1.0".

CHAMPS

Le reste du fichier META.yml est une grande table de correspondance YAML dont les clés sont décrites ici.

meta-spec

Exemple :

meta-spec:
  version: 1.3
  url: http://module-build.sourceforge.net/META-spec-v1.3.html

(Spec 1.1) [requis] {URL} Ce champ indique l'emplacement de la version de la spécification META.yml utilisée.

name

Exemple :

name: Module-Build

(Spec 1.0) [requis] {string} Le nom de la distribution, souvent créé en prenant le « module principal » de la distribution et en remplaçant "::" par "-". Parfois, il est complètement différent, comme dans le cas de la distribution libwww-perl (voir http://search.cpan.org/dist/libwww-perl/).

version

Exemple :

version: 0.20

(Spec 1.0) [requis] {version} La version de la distribution à laquelle le fichier META.yml fait référence.

abstract

Exemple :

abstract: Build and install Perl modules.

(Spec 1.1) [requis] {string} Une courte description du but de la distribution.

author

Exemple :

author:
  - Ken Williams <kwilliams@cpan.org>

(Spec 1.1) [requis] {liste de chaînes} Une séquence YAML indiquant le ou les auteurs de la distribution. La forme préférée est nom-de-l'auteur <adresse-email>.

license

Exemple :

license: perl

(Spec 1.0) [requis] {string} La licence sous laquelle cette distribution peut être utilisée et redistribuée.

Doit être l'une des licences suivantes :

apache
La distribution est sous licence Apache Software License version 1.1 (http://opensource.org/licenses/Apache-1.1).
artistic
La distribution est sous licence Artistic License version 1, telle que spécifiée par le fichier Artistic de la distribution perl standard (http://opensource.org/licenses/Artistic-Perl-1.0).
bsd
La distribution est sous licence BSD 3-Clause License (http://opensource.org/licenses/BSD-3-Clause).
gpl
La distribution est distribuée selon les termes de la GNU General Public License version 2 (http://opensource.org/licenses/GPL-2.0).
lgpl
La distribution est distribuée selon les termes de la GNU Lesser General Public License version 2 (http://opensource.org/licenses/LGPL-2.1).
mit
La distribution est sous licence MIT License (http://opensource.org/licenses/MIT).
mozilla
La distribution est sous licence Mozilla PLicence Publique. (http://opensource.org/licenses/MPL-1.0 ou http://opensource.org/licenses/MPL-1.1)
open_source
La distribution est sous licence selon une autre licence approuvée par l'Open Source Initiative listée sur http://www.opensource.org/licenses/.
perl
La distribution peut être copiée et redistribuée selon les mêmes termes que perl lui-même (c'est de loin l'option de licence la plus courante pour les modules sur CPAN). Il s'agit d'une double licence, dans laquelle l'utilisateur peut choisir entre la licence GPL version 1 ou la licence Artistic version 1.
restrictive
La distribution ne peut pas être redistribuée sans la permission spéciale de l'auteur et/ou du détenteur des droits d'auteur.
unrestricted
La distribution est sous une licence qui n'est pas approuvée par www.opensource.org http://www.opensource.org/ mais qui permet la distribution sans restrictions.

distribution_type

Exemple :

distribution_type: module

(Spec 1.0) [optionnel] {string} Quel type de contenu est contenu dans cette distribution. La plupart des choses sur CPAN sont des "module"s (ce qui peut aussi signifier une collection de modules), mais certaines choses sont des "script"s.

Malheureusement, ce champ est essentiellement sans signification, car de nombreuses distributions sont des hybrides de plusieurs types de choses, ou quelque chose de nouveau, ou subjectivement différentes dans leur focus selon ceux qui les utilisent. Des outils comme Module::Build et MakeMaker cesseront probablement de générer ce champ.

requires

Exemple :

requires:
  Data::Dumper: 0
  File::Find: 1.03

(Spec 1.0) [optionnel] {map} Un mapping YAML indiquant les modules Perl dont cette distribution a besoin pour un fonctionnement correct. Les clés sont les noms des modules, et les valeurs sont des spécifications de version comme décrit dans "SPÉCIFICATIONS DE VERSION".

recommends

Exemple :

recommends:
  Data::Dumper: 0
  File::Find: 1.03

(Spec 1.0) [optionnel] {map} Un mapping YAML indiquant les modules Perl que cette distribution recommande pour un fonctionnement amélioré. Les clés sont les noms des modules, et les valeurs sont des spécifications de version comme décrit dans "SPÉCIFICATIONS DE VERSION".

ALTERNATIVE : Il peut être souhaitable de présenter à l'utilisateur quelles fonctionnalités dépendent de quels modules afin qu'il puisse prendre une décision éclairée concernant les modules recommandés à installer.

Exemple :

optional_features:
- foo:
    description: Provides the ability to blah.
    requires:
      Data::Dumper: 0
      File::Find: 1.03
- bar:
    description: This feature is not available on this platform.
    excludes_os: MSWin32

(Spec 1.1) [optionnel] {map} Une séquence YAML de noms pour des fonctionnalités optionnelles qui sont disponibles lorsque leurs exigences sont satisfaites. Pour chaque fonctionnalité, une description est fournie avec n'importe lequel de "requires", "build_requires", "conflicts", "requires_packages", "requires_os", et "excludes_os" qui ont le même sens dans ce sous-contexte que décrit ailleurs dans ce document.

build_requires

Exemple :

build_requires:
  Data::Dumper: 0
  File::Find: 1.03

(Spec 1.0) [optionnel] {map} Un mapping YAML indiquant les modules Perl requis pour la construction et/ou les tests de cette distribution. Les clés sont les noms des modules, et les valeurs sont des spécifications de version comme décrit dans "SPÉCIFICATIONS DE VERSION". Ces dépendances ne sont pas requises après l'installation du module.

conflicts

Exemple :

conflicts:
  Data::Dumper: 0
  File::Find: 1.03

(Spec 1.0) [optionnel] {map} Un mapping YAML indiquant les modules Perl qui ne peuvent pas être installés tant que cette distribution est installée. C'est une situation assez rare. Les clés pour "conflicts" sont les noms des modules, et les valeurs sont des spécifications de version comme décrit dans "SPÉCIFICATIONS DE VERSION".

dynamic_config

Exemple :

dynamic_config: 0

(Spec 1.0) [optionnel] {boolean} Un indicateur booléen indiquant si un Build.PL ou Makefile.PL (ou similaire) doit être exécuté lors de la construction de cette distribution, ou si elle peut être construite, testée et installée uniquement en consultant son fichier de métadonnées. La raison principale de définir ceci à une valeur vraie est que votre module effectue une configuration dynamique (poser des questions, détecter l'environnement, etc.) dans le cadre de son processus de construction/installation.

Actuellement, Module::Build ne fait rien avec cet indicateur - c'est probablement aux outils de niveau supérieur comme CPAN de faire quelque chose d'utile avec. Cela peut potentiellement apporter beaucoup d'améliorations en termes de sécurité, d'empaquetage et de commodité.

Si ce champ est omis, il vaut par défaut 1 (vrai).

private

(Obsolète) (Spec 1.0) [optionnel] {map} Ce champ a été renommé en "no_index". Voir ci-dessous.

provides

Exemple :

provides:
  Foo::Bar:
    file: lib/Foo/Bar.pm
    version: 0.27_02
  Foo::Bar::Blah:
    file: lib/Foo/Bar/Blah.pm
  Foo::Bar::Baz:
    file: lib/Foo/Bar/Baz.pm
    version: 0.3

(Spec 1.1) [optionnel] {map} Un mapping YAML qui décrit tous les paquets fournis par cette distribution. Ces informations peuvent être (et, dans certains cas, sont) utilisées par des mécanismes de distribution et d'automatisation comme PAUSE, CPAN et search.cpan.org pour construire des index indiquant dans quelle distribution divers paquets peuvent être trouvés.

Lorsque vous utilisez des outils comme Module::Build qui peuvent générer le mapping "provides" pour votre distribution automatiquement, assurez-vous d'examiner ce qu'il génère pour vous assurer que cela a du sens - les indexeurs feront généralement confiance au champ "provides" s'il est présent, plutôt que de parcourir les fichiers de la distribution eux-mêmes pour déterminer les paquets et les versions. C'est une bonne chose, car cela signifie que vous pouvez utiliser le champ "provides" pour dire aux indexeurs précisément ce que vous voulez indexer au sujet de votre distribution, plutôt que de compter sur eux pour essentiellement deviner ce que vous voulez indexer.

no_index

Exemple :

no_index:
  file:
  - My/Module.pm
  directory:
  - My/Private
  package:
  - My::Module::Stuff
  namespace:
  - My::Module::Stuff

(Spec 1.1) [optionnel] {map} Un mapping YAML qui décrit tous les fichiers, répertoires, paquets et espaces de noms qui sont privés (c'est-à-dire des artefacts d'implémentation) qui n'intéressent pas les outils de recherche et d'indexation. C'est utile lorsque aucun champ "provides" n'est présent.

Par exemple, http://search.cpan.org/ exclut les éléments listés dans "no_index" lors de la recherche de POD, ce qui signifie que les fichiers dans ces répertoires ne seront pas convertis en HTML et rendus publics - ce qui est utile si vous avez des PODs d'exemple ou de test que vous ne voulez pas que le moteur de recherche parcoure.

file

(Spec 1.1) [optionnel] Exclut tout ou partie des fichiers listés.

directory

(Spec 1.1) [optionnel] Exclut tout ce qui se trouve sous le(s) répertoire(s) listé(s).

[Note : les éditions précédentes de la spécification avaient "dir" au lieu de "directory", mais je pense que MakeMaker et divers utilisateurs ont commencé à utiliser "directory", donc par déférence nous sommes passés à celui-ci.]

package

(Spec 1.1) [optionnel] Exclut le ou les paquets listés.

namespace

(Spec 1.1) [optionnel] Exclut tout ce qui se trouve sous le ou les espaces de noms listés, mais pas l'espace de noms listé lui-même.

keywords

Exemple :

keywords:
  - make
  - build
  - install

(Spec 1.1) [optionnel] {list} Une séquence de mots-clés/phrases qui décrivent cette distribution.

resources

Exemple :

resources:
  license: http://dev.perl.org/licenses/
  homepage: http://sourceforge.net/projects/module-build
  bugtracker: http://rt.cpan.org/NoAuth/Bugs.html?Dist=Module-Build
  repository: http://sourceforge.net/cvs/?group_id=45731
  MailingList: http://lists.sourceforge.net/lists/listinfo/module-build-general

(Spec 1.1) [optionnel] {map} Un mapping de toutes les ressources URL liées à cette distribution. Les clés entièrement en minuscules, comme "homepage", "license", et "bugtracker", sont réservées par cette spécification, car elles ont des significations "officielles" définies ici dans cette spécification. Si vous souhaitez ajouter vos propres entrées "spéciales" (comme l'entrée "MailingList" ci-dessus), utilisez au moins une lettre majuscule.

L'ensemble actuel des clés officielles est :

homepage
Le site web officiel de ce projet.
license
Une URL pour un énoncé officiel de la licence de cette distribution.
bugtracker
Une URL pour un suivi de bogues (par ex. une file Bugzilla ou RT) pour ce projet.

generated_by

Exemple:

generated_by: Module::Build version 0.20

(Spec 1.0) [required] {string} Indique l'outil qui a été utilisé pour créer ce META.yml fichier. Il est de bonne pratique d'inclure à la fois le nom de l'outil et sa version, mais ce champ est essentiellement opaque, du moins pour le moment. Si META.yml a été généré à la main, il est suggéré que l'auteur soit spécifié ici.

[Note : Mon meta_stats.pl script que j'utilise pour recueillir des statistiques concernant META.yml l'utilisation préfère la forme listée ci-dessus, c'est-à-dire qu'il divise sur /\s+version\s+/ en prenant le premier champ comme le nom de l'outil qui a généré le fichier et le deuxième champ comme la version de cet outil. RWS]

SPÉCIFICATIONS DE VERSION

Certains champs nécessitent une spécification de version (ex. "requires", "recommends", "build_requires", etc.) pour indiquer la ou les version(s) particulière(s) d'un autre module qui peut être requis en tant que prérequis. Cette section détaille les formats de spécification de version qui sont actuellement pris en charge.

Le format le plus simple pour une spécification de version est simplement le numéro de version lui-même, par ex. 2.4. Cela signifie que au moins la version 2.4 doit être présente. Pour indiquer que n'importe quelle version d'un prérequis convient, même si le prérequis ne définit pas de version du tout, utilisez la version 0.

Vous pouvez également utiliser les opérateurs < (inférieur à), <= (inférieur ou égal), > (supérieur à), >= (supérieur ou égal), == (égal), et != (différent). Par exemple, la spécification < 2.0 signifie que n'importe quelle version du prérequis inférieure à 2.0 convient.

Pour des situations plus compliquées, les spécifications de version peuvent être combinées par ET (AND) à l'aide de virgules. La spécification >= 1.2, != 1.5, < 2.0 indique une version qui doit être au moins 1.2, inférieure à 2.0, et différente de 1.5.
