Les métadonnées de distribution décrivent des propriétés importantes des distributions Perl. Les outils de construction de distribution comme Module::Build, Module::Install, ExtUtils::MakeMaker ou Dist::Zilla doivent créer un fichier de métadonnées conformément à cette spécification et l'inclure avec la distribution pour l'utilisation par les outils

automatisés qui indexent, examinent, empaquent ou installent les distributions Perl.

CHAMPS REQUIS

abstract

Exemple :

abstract => 'Build and install Perl modules'

(Spec 1.2) [requis] {String}

Ceci est une courte description du but de la distribution.

author

Exemple :

author => [ 'Ken Williams <kwilliams@cpan.org>' ]

(Spec 1.2) [requis] {Liste d'une ou plusieurs Strings}

Cette Liste indique la ou les personnes à contacter concernant la distribution. La forme préférée de la chaîne de contact est :

contact-name <email-address>

Ce champ fournit une liste de contacts générale indépendante des autres champs structurés fournis dans le champ "resources", tels que "bugtracker". Le ou les destinataires peuvent être contactés pour n'importe quel but, y compris mais sans s'y limiter les problèmes (de sécurité) liés à la distribution, les questions sur la distribution ou les bugs dans la distribution.

L'auteur original d'une distribution est généralement le contact listé dans ce champ. Les co-mainteneurs, les mainteneurs successeurs ou les listes de diffusion consacrées à la distribution peuvent également être listés en plus de ou à la place de l'auteur original.

dynamic_config

Exemple :

dynamic_config => 1

(Spec 2) [requis] {Boolean}

Un drapeau booléen indiquant si un Build.PL ou Makefile.PL (ou similaire) doit être exécuté pour déterminer les prérequis.

Ce champ devrait être défini à une valeur vraie si la distribution effectue une configuration dynamique (poser des questions, sonder l'environnement, etc.) dans le cadre de sa configuration. Ce champ devrait être défini à une valeur fausse pour indiquer que les prérequis inclus dans les métadonnées peuvent être considérés comme finaux et valides pour une analyse statique.

Note : lorsque ce champ est vrai, les prérequis post-configuration ne sont pas garantis d'avoir un quelconque rapport avec ceux énoncés dans les métadonnées, et s'y fier est une erreur. Voir aussi "Prerequisites for dynamically configured distributions" dans les notes des implémenteurs.

Ce champ indique explicitement ne pas indiquer si l'installation peut être effectuée sans risque sans utiliser un fichier Makefile ou Build, car il peut y avoir des fichiers spéciaux à installer ou des cibles d'installation personnalisées (par ex. pour les modules à double vie qui existent sur CPAN ainsi que dans le cœur de Perl). Ce champ définit uniquement si les prérequis sont exactement tels que donnés dans les métadonnées.

generated_by

Exemple :

generated_by => 'Module::Build version 0.36'

(Spec 1.0) [requis] {String}

Ce champ indique l'outil qui a été utilisé pour créer ces métadonnées. Il n'y a pas de sémantique définie pour ce champ, mais il est traditionnel d'utiliser une chaîne de la forme "Generating::Package version 1.23" ou le nom de l'auteur, si le fichier a été généré à la main.

meta-spec

Exemple :

'meta-spec' => {
  version => '2',
  url     => 'http://search.cpan.org/perldoc?CPAN::Meta::Spec',
}

(Spec 1.2) [requis] {Map}

Ce champ indique la version de la CPAN Meta Spec qui devrait être utilisée pour interpréter les métadonnées. Les consommateurs doivent vérifier cette clé dès que possible et interrompre tout traitement ultérieur des métadonnées si la version de meta-spec n'est pas prise en charge par le consommateur.

Les clés suivantes sont valides, mais seule "version" est requise.

version
Cette sous-clé donne l'entier Version de la CPAN Meta Spec contre laquelle le document a été généré.
url
Ceci est une URL du document de spécification des métadonnées correspondant à la version donnée. Ceci est strictement destiné à la lecture par un humain et ne devrait pas influencer l'interprétation du document.

Pour la version 2 de la spec, l'une ou l'autre de ces options est recommandée :

  • "https://metacpan.org/pod/CPAN::Meta::Spec"
  • "http://search.cpan.org/perldoc?CPAN::Meta::Spec"

name

Exemple :

name => 'Module-Build'

(Spec 1.0) [requis] {String}

Ce champ est le nom de la distribution. Il est souvent créé en prenant le "paquet principal" dans la distribution et en changeant "::" en "-", mais le nom peut être complètement non lié aux paquets de la distribution. Par exemple, LWP::UserAgent est distribué dans le cadre de la distribution nommée "libwww-perl".

release_status

Exemple :

release_status => 'stable'

(Spec 2) [requis] {String}

Ce champ fournit le statut de publication de cette distribution. Si le champ "version" contient un caractère de soulignement alors "release_status" ne doit pas être "stable."

Le champ "release_status" doit avoir l'une des valeurs suivantes :

stable
Cela indique une publication ordinaire, "finale", qui devrait être indexée par PAUSE ou d'autres indexeurs.
testing
Cela indique une publication "bêta" qui est substantiellement complète, mais qui présente un risque accru de bugs et nécessite des tests supplémentaires. La distribution ne devrait pas être installée par-dessus une version stable sans une demande explicite ou une autre confirmation d'un utilisateur. Ce statut de publication peut également être utilisé pour les versions "release candidate" d'une distribution.
unstable
Cela indique une publication "alpha" qui est en développement actif, mais qui a été publiée pour des retours précoces ou des tests et peut manquer de fonctionnalités ou avoir des bugs sérieux. La distribution ne devrait pas être installée par-dessus une version stable sans une demande explicite ou une autre confirmation d'un utilisateur.

Les consommateurs peuvent utiliser ce champ pour déterminer comment indexer la distribution pour CPAN ou d'autres dépôts en plus de ou en remplacement des heuristiques basées sur le numéro de version ou le nom de fichier.

version

Exemple :

version => '0.36'

(Spec 1.0) [requis] {Version}

Ce champ donne la version de la distribution à laquelle la structure de métadonnées se réfère.

CHAMPS FACULTATIFS

description

Exemple :

description =>  "Module::Build is a system for "
  . "building, testing, and installing Perl modules. "
  . "It is meant to ... blah blah blah ...",

(Spec 2) [facultatif] {String}

Une description plus longue et plus complète du but ou de l'utilisation prévue de la distribution que celle fournie par la clé "abstract" .

keywords

Exemple :

keywords => [ qw/ toolchain cpan dual-life / ]

(Spec 1.1) [facultatif] {Liste de zéro ou plusieurs Strings}

Une Liste de mots-clés qui décrivent cette distribution. Les mots-clés ne doivent pas inclure d'espaces.

no_index

Exemple :

no_index => {
  file      => [ 'My/Module.pm' ],
  directory => [ 'My/Private' ],
  package   => [ 'My::Module::Secret' ],
  namespace => [ 'My::Module::Sample' ],
}

(Spec 1.2) [facultatif] {Map}

Cette Map décrit tous les fichiers, répertoires, paquets et espaces de noms qui sont privés à l'empaquetage ou à l'implémentation de la distribution et devraient être ignorés par les outils d'indexation ou de recherche. Notez que ceci est une liste d'exclusions, et la spec ne définit pas ce qu'il faut inclure - voir "Indexing distributions a la PAUSE" dans les notes des implémenteurs pour plus d'informations.

Les sous-clés valides sont les suivantes :

file
Une List de chemins relatifs verso fichiers. Les chemins doivent être spécifiés avec les conventions unix.
directory
Une Liste de chemins relatifs vers des répertoires. Les chemins doivent être spécifiés avec les conventions unix.

[ Note : les éditions précédentes de la spécification utilisaient "dir" au lieu de "directory" ]

package
Une Liste de noms de paquets.
namespace
Une Liste de namespaces de paquets, où tout ce qui se trouve en dessous du namespace doit être ignoré, mais pas le namespace lui-même.

Dans l'exemple ci-dessus pour "no_index", "My::Module::Sample::Foo" serait ignoré, mais "My::Module::Sample" ne le serait pas.

optional_features

Exemple :

optional_features => {
  sqlite => {
    description => 'Provides SQLite support',
    prereqs => {
      runtime => {
        requires => {
          'DBD::SQLite' => '1.25'
        }
      }
    }
  }
}

(Spec 2) [optionnel] {Map}

Cette Map décrit des fonctionnalités optionnelles avec des prérequis incrémentaux. Chaque clé de la Map "optional_features" est une String utilisée pour identifier la fonctionnalité et chaque valeur est une Map avec des informations supplémentaires sur la fonctionnalité. Les sous-clés valides incluent :

description
C'est une String décrivant la fonctionnalité. Chaque fonctionnalité optionnelle devrait fournir une description
prereqs
Cette entrée est requise et a la même structure que celle de la clé "prereqs" . Elle fournit une liste de requirements de paquets qui doivent être satisfaits pour que la fonctionnalité soit prise en charge ou activée.

Il y a une restriction cruciale : les prérequis d'une fonctionnalité optionnelle ne doivent pas inclure des prérequis de phase "configure" .

Les consommateurs ne doivent pas inclure les fonctionnalités optionnelles comme prérequis sans instruction explicite des utilisateurs (que ce soit via une invite interactive, un paramètre de fonction ou une valeur de configuration, etc.).

Si une fonctionnalité optionnelle est utilisée par un consommateur pour ajouter des prérequis supplémentaires, le consommateur devrait fusionner les prérequis de la fonctionnalité optionnelle avec ceux donnés par la clé "prereqs" en utilisant la même sémantique. Voir « Fusion et résolution des prérequis » pour plus de détails sur la fusion des prérequis.

Suggestion pour éviter son utilisation : Parce qu'il n'y a actuellement aucun moyen pour une distribution de spécifier une dépendance à une fonctionnalité optionnelle d'une autre dépendance, l'utilisation de "optional_feature" est découragée. À la place, créez une distribution séparée et installable qui garantit que la fonctionnalité désirée est disponible. Par exemple, si "Foo::Bar" a une fonctionnalité "Baz" , publiez une distribution "Foo-Bar-Baz" séparée qui satisfait les requirements pour la fonctionnalité.

prereqs

Exemple :

prereqs => {
  runtime => {
    requires => {
      'perl'          => '5.006',
      'File::Spec'    => '0.86',
      'JSON'          => '2.16',
    },
    recommends => {
      'JSON::XS'      => '2.26',
    },
    suggests => {
      'Archive::Tar'  => '0',
    },
  },
  build => {
    requires => {
      'Alien::SDL'    => '1.00',
    },
  },
  test => {
    recommends => {
      'Test::Deep'    => '0.10',
    },
  }
}

(Spec 2) [optionnel] {Map}

C'est une Map qui décrit tous les prérequis de la distribution. Les clés sont des phases d'activité, telles que "configure", "build", "test" ou "runtime". Les valeurs sont des Maps dans lesquelles les clés nomment le type de relation de prérequis tel que "requires", "recommends", ou "suggests" et la valeur fournit un ensemble de relations de prérequis. L'ensemble des relations doit être spécifié comme une Map de noms de paquets vers des plages de versions.

La définition complète de ce champ est donnée dans la section « Spécification des prérequis ».

provides

Exemple :

provides => {
  'Foo::Bar' => {
    file    => 'lib/Foo/Bar.pm',
    version => '0.27_02',
  },
  'Foo::Bar::Blah' => {
    file    => 'lib/Foo/Bar/Blah.pm',
  },
  'Foo::Bar::Baz' => {
    file    => 'lib/Foo/Bar/Baz.pm',
    version => '0.3',
  },
}

(Spec 1.2) [optionnel] {Map}

Cela décrit tous les paquets fournis par cette distribution. Ces informations sont utilisées par les mécanismes de distribution et d'automatisation comme PAUSE, CPAN, metacpan.org et search.cpan.org pour construire des index indiquant dans quelle distribution divers paquets peuvent être trouvés.

Les clés de "provides" sont des noms de paquets qui peuvent être trouvés dans la distribution. Si une clé de nom de paquet est fournie, elle doit avoir une Map avec les sous-clés valides suivantes :

file
Ce champ est requis. Il doit contenir un chemin de fichier relatif de style Unix depuis la racine du répertoire de la distribution vers un fichier qui contient ou génère le paquet. Il peut être donné comme "META.yml" ou "META.json" pour revendiquer un paquet pour l'indexation sans avoir besoin d'un "*.pm".
version
S'il existe, ce champ doit contenir une Version String pour le paquet. Si le paquet n'a pas de $VERSION", ce champ doit être omis.

resources

Exemple :

resources => {
  license     => [ 'http://dev.perl.org/licenses/' ],
  homepage    => 'http://sourceforge.net/projects/module-build',
  bugtracker  => {
    web    => 'http://rt.cpan.org/Public/Dist/Display.html?Name=CPAN-Meta',
    mailto => 'meta-bugs@example.com',
  },
  repository  => {
    url  => 'git://github.com/dagolden/cpan-meta.git',
    web  => 'http://github.com/dagolden/cpan-meta',
    type => 'git',
  },
  x_twitter   => 'http://twitter.com/cpan_linked/',
}

(Spec 2) [optionnel] {Map}

Ce champ décrit des ressources liées à cette distribution.

Les sous-clés valides incluent :

homepage
Le site web officiel de ce projet.
license
Une Liste de URL's qui se rapportent à la licence de cette distribution. Comme pour le champ de premier niveau "license" , la documentation de la distribution devrait être consultée pour clarifier l'interprétation des licences multiples fournies ici.
bugtracker
Cette entrée décrit le système de suivi des bugs pour cette distribution. C'est une Map avec les clés valides suivantes : 
web    - une URL pointant vers une interface web pour le suivi des bugs
mailto - une adresse e-mail à laquelle les bugs peuvent être envoyés
repository
Cette entrée décrit le dépôt de contrôle des sources pour cette distribution. C'est une Map avec les clés valides suivantes : 
url  - une URL pointant vers le dépôt lui-même
web  - une URL pointant vers une interface web pour le dépôt
type - une chaîne en minuscules indiquant le VCS utilisé

Parce qu'une url comme "http://myrepo.example.com/" est ambiguë quant au type, les producteurs devraient fournir un "type" chaque fois qu'une clé "url" est donnée. Le champ "type" devrait être le nom du programme le plus couramment utilisé pour travailler avec le dépôt, par ex. "git", "svn", "cvs", "darcs", "bzr" ou "hg".

NUMÉROS DE VERSION

Formats de version

Cette section définit le type Version, utilisé par plusieurs champs dans la Spécification CPAN Meta.

Les numéros de version doivent être traités comme des chaînes, pas comme des nombres. Par exemple, 1.200 ne doit pas être sérialisé comme 1.2. La comparaison de versions devrait être déléguée au module perl version, version 0.80 ou plus récente.

Sauf indication contraire, venuméros de version doivent apparaître dans l'un des deux formats suivants : Versions décimales Les versions décimales sont des « nombres décimaux » réguliers, avec certaines limitations.

Elles
doivent être non négatives et doivent commencer et se terminer par un chiffre. Un seul
underscore peut
être inclus, mais doit se trouver entre deux chiffres. Elles ne doivent pas utiliser la notation exponentielle (« 1.23e-2 »). version => '1.234' # OK version => '1.23_04' # OK version => '1.23_04_05' # Illégal version => '1.' # Illégal version => '.1' # Illégal Versions à entiers séparés par des points Les versions à entiers séparés par des points (également connues sous le nom de versions à décimales séparées par des points) se composent d'entiers positifs séparés par des points (c'est-à-dire des « points », des « périodes » ou des « points décimaux »). Elles sont de format équivalent aux « v-strings » de Perl, avec quelques restrictions supplémentaires sur la forme. Elles doivent être données sous la forme « normale », qui commence par le caractère « v » et contient au moins trois composantes entières. Pour conserver une correspondance un à un avec les versions décimales, toutes les composantes après la première devraient 
être limitées à la pl
age de 0 à 999. La c
omposante finale peut

Comparer les numéros de version

Le module version fournit la méthode la plus fiable pour comparer les numéros de version, quelles que soient les formes dans lesquelles ils peuvent être fournis ou exister au sein des modules. Étant donné deux chaînes contenant des numéros de version, $v1 et $v2, elles doivent être converties en objets "version" avant d'utiliser les opérateurs de comparaison ordinaires. Par exemple :

use version;
if ( version->new($v1) <=> version->new($v2) ) {
  print "Versions are not equal\n";
}

Si la seule comparaison nécessaire est de savoir si un module installé est d'une version suffisamment élevée, un test direct peut être effectué en utilisant la forme chaîne de "eval" et de la fonction "use" . Par exemple, pour le module $mod et la prérequis de version $prereq:

if ( eval "use $mod $prereq (); 1" ) {
  print "Module $mod version is OK.\n";
}

Cependant, si les valeurs de $mod et $prereq n'ont pas été assainies, cela présente des implications de sécurité.

Prérequis pour les distributions à configuration dynamique

Lorsque "dynamic_config" est vrai, il est erroné de présumer que les prérequis donnés dans les métadonnées de la distribution auront un quelconque rapport avec les prérequis réels de la distribution.

En pratique, cependant, on peut généralement s'attendre à ce que de tels prérequis soient l'une des deux choses suivantes :

  • Les prérequis minimaux pour la distribution, auxquels la configuration dynamique n'ajoutera que des éléments
  • Ce que la distribution était configurée avec sur la machine du publieur au moment de la publication

Le second cas donne souvent des résultats identiques au premier, bien que ce ne soit le cas que par accident.

En tant que tel, les consommateurs peuvent utiliser ces données pour une analyse informative, mais les présenter à l'utilisateur comme canoniques ou s'y fier en tant que tel est invariablement la plus grande des folies.

Indexer les distributions à la manière de PAUSE

Bien que no_index vous dise ce qui doit être ignoré lors de l'indexation, cette spécification n'a pas d'opinion sur la manière dont vous devriez obtenir votre liste initiale de candidats à éventuellement indexer. Pour les distributions « normales », vous pourriez envisager de simplement indexer le contenu de lib/, mais il existe de nombreuses curiosités fascinantes sur CPAN et de nombreuses distributions de l'époque où il était normal de mettre le fichier .pm principal à la racine de l'archive de la distribution - PAUSE indexe donc actuellement tous les fichiers .pm et .PL qui ne sont pas soit (a) spécifiquement exclus par no_index, soit (b) dans les répertoires "inc", "xt"ou "t" , ou des répertoires d'« erreur » courants tels que "perl5".

Ou : Si vous essayez d'être semblable à PAUSE, assurez-vous de sauter "inc", "xt" et "t" ainsi que tout ce qui est marqué comme no_index.

Rappelez-vous également : Si le fichier META contient un champ provides, vous ne devriez rien indexer en premier lieu - utilisez-le simplement.

HISTORIQUE

Ken Williams a écrit la spécification originale de CPAN Meta (aussi connue sous le nom de « spécification META.yml ») en 2003 et l'a maintenue à travers plusieurs révisions avec les contributions de divers membres de la communauté. En 2005, Randy Sims l'a redessinée de HTML en POD pour la version 1.2. Ken a continué à maintenir la spécification jusqu'à la version 1.4.

À la fin de 2009, David Golden a organisé le processus de révision de la proposition de la version 2. David et Ricardo Signes ont rédigé la spécification finale de la version 2 en avril 2010 sur la base de la spécification 1.4 et des correctifs contribués pendant le processus de proposition.
