close(n)

Paquet: tcl

Licences: TCL

close(n) Commandes intégrées Tcl close(n)

NOM

close - Ferme un canal ouvert

SYNOPSIS

close channelId ?r(ead)|w(rite)?

DESCRIPTION

Ferme ou semi-ferme le canal donné par channelId.

ChannelId doit être un identifiant pour un canal ouvert tel qu'un canal standard Tcl (stdin, stdout, ou stderr), la valeur de retour d'une invocation de open ou socket, ou le résultat d'une commande de création de canal fournie par une extension Tcl.

La forme à un seul argument est une simple « fermeture complète » : toute sortie mise en tampon est vidée vers le périphérique de sortie du canal, toute entrée mise en tampon est rejetée, le fichier ou le périphérique sous-jacent est fermé, et channelId devient indisponible pour utilisation.

Si le canal est bloquant, la commande ne retourne pas tant que toute la sortie n'est pas vidée. Si le canal est non bloquant et qu'il y a de la sortie non vidée, le canal reste ouvert et la commande retourne immédiatement ; la sortie sera vidée en arrière-plan et le canal sera fermé lorsque tout le vidage sera terminé.

Si channelId est un canal bloquant pour un pipeline de commandes, alors close attend la fin des processus enfants.

Si le canal est partagé entre des interpréteurs, alors close rend channelId indisponible dans l'interpréteur appelant mais n'a aucun autre effet tant que tous les interpréteurs partageant le canal n'ont pas fermé le canal. Lorsque le dernier interpréteur dans lequel le canal est enregistré invoque close, les actions de nettoyage décrites ci-dessus se produisent. Voir la commande interp pour une description du partage de canaux.

Les canaux sont automatiquement fermés lorsqu'un interpréteur est détruit et lorsque le processus se termine. À partir de 8.6 (TIP#398), les canaux non bloquants ne sont plus basculés en mode bloquant lors de la sortie ; cela garantit une sortie rapide même lorsque le pair ou un canal de communication est bloqué. Pour garantir un vidage correct des canaux non bloquants bloqués à la sortie, il faut maintenant soit (a) les rebasculer activement en mode bloquant, soit (b) utiliser la variable d'environnement TCL_FLUSH_NONBLOCKING_ON_EXIT, qui, lorsqu'elle est définie et non égale à « 0 », restaure le comportement précédent.

La commande retourne une chaîne vide et peut générer une erreur si une erreur se produit lors du vidage de la sortie. Si une commande dans un pipeline de commandes créé avec open retourne une erreur, close génère une erreur (similaire à la commande exec.)

La forme à deux arguments est une « semi-fermeture » : étant donné un canal bidirectionnel comme une socket ou un pipeline de commandes et une direction (éventuellement abrégée), elle ne ferme que le sous-flux allant dans cette direction. Cela signifie un shutdown() sur une socket et un close() d'une extrémité d'un tuyau pour un pipeline de commandes. Ensuite, la structure de données du canal au niveau Tcl est conservée ou libérée en fonction de si l'autre direction est toujours ouverte.

Une fermeture à un argument sur un canal bidirectionnel déjà semi-fermé est définie pour simplement « terminer le travail ». Une semi-fermeture sur une moitié déjà fermée, ou sur un canal unidirectionnel du mauvais côté, lève une erreur.

Dans le cas d'un pipeline de commandes, la charge de la récupération des enfants incombe au dernier close ou semi-close, qui est ainsi autorisé à signaler une erreur de sortie anormale.

Actuellement, seules les sockets et les pipelines de commandes prennent en charge la semi-fermeture. Une extension future permettra aux canaux réfléchis et empilés de le faire.

EXEMPLE

Ceci illustre comment vous pouvez utiliser Tcl pour garantir que les fichiers soient fermés même en cas d'erreurs en combinant catch, close et return :

proc withOpenFile {filename channelVar script} {
    upvar 1 $channelVar chan
    set chan [open $filename]
    catch {
        uplevel 1 $script
    } result options
    close $chan
    return -options $options $result
}
