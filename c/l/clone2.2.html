Le signal de terminaison de l'enfant

Lorsque le processus enfant se termine, un signal peut être envoyé au parent. Le signal de terminaison est spécifié dans l'octet de poids faible de flags (clone()) ou dans cl_args.exit_signal (clone3()). Si ce signal est spécifié comme autre chose que SIGCHLD, alors le processus parent doit spécifier les options __WALL ou __WCLONE lors de l'attente de l'enfant avec wait(2). Si aucun signal (c'est-à-dire zéro) n'est spécifié, alors le processus parent n'est pas signalé lorsque l'enfant se termine.

Le tableau set_tid

Par défaut, le noyau choisit le PID séquentiel suivant pour le nouveau processus dans chacun des espaces de noms PID où il est présent. Lors de la création d'un processus avec clone3(), le tableau set_tid (disponible depuis Linux 5.5) peut être utilisé pour sélectionner des PID spécifiques pour le processus dans certains ou tous les espaces de noms PID où il est présent. Si le PID du processus nouvellement créé doit être défini uniquement pour l'espace de noms PID actuel ou pour le nouvel espace de noms PID créé (si flags contient CLONE_NEWPID), alors le premier élément du tableau set_tid doit être le PID souhaité et set_tid_size doit être égal à 1.

Si le PID du processus nouvellement créé doit avoir une certaine valeur dans plusieurs espaces de noms PID, alors le tableau set_tid peut avoir plusieurs entrées. La première entrée définit le PID dans l'espace de noms PID le plus imbriqué et chacune des entrées suivantes contient le PID dans l'espace de noms PID ancêtre correspondant. Le nombre d'espaces de noms PID dans lesquels un PID doit être défini est défini par set_tid_size, qui ne peut pas être supérieur au nombre d'espaces de noms PID actuellement imbriqués.

Pour créer un processus avec les PID suivants dans une hiérarchie d'espaces de noms PID :

Niveau de l'espace de noms PID PID demandé Notes
0 31496 Espace de noms PID le plus externe
1 42
2 7 Espace de noms PID le plus interne

Définissez le tableau à :


set_tid[0] = 7;
set_tid[1] = 42;
set_tid[2] = 31496;
set_tid_size = 3;

Si seuls les PID dans les deux espaces de noms PID les plus internes doivent être spécifiés, définissez le tableau à :


set_tid[0] = 7;
set_tid[1] = 42;
set_tid_size = 2;

Le PID dans les espaces de noms PID en dehors des deux espaces de noms PID les plus internes est sélectionné de la même manière que tout autre PID est sélectionné.

La fonctionnalité set_tid nécessite CAP_SYS_ADMIN ou (depuis Linux 5.9) CAP_CHECKPOINT_RESTORE dans tous les espaces de noms utilisateur propriétaires des espaces de noms PID cibles.

Les appelants ne peuvent choisir un PID supérieur à 1 dans un espace de noms PID donné que si un processus init (c'est-à-dire un processus avec PID 1) existe déjà dans cet espace de noms. Sinon, l'entrée PID pour cet espace de noms PID doit être 1.

Le masque flags

Les deux appels clone() et clone3() permettent un masque de bits flags qui modifie leur comportement et permet à l'appelant de spécifier ce qui est partagé entre le processus appelant et le processus enfant. Ce masque de bits — l'argument flags de clone() ou le champ cl_args.flags passé à clone3() — est désigné comme le masque flags dans le reste de cette page.

Le masque flags est spécifié comme une opération OU bit à bit de zéro ou plusieurs des constantes listées ci-dessous. Sauf indication contraire, ces indicateurs sont disponibles (et ont le même effet) dans clone() et clone3().

CLONE_CHILD_CLEARTID (depuis Linux 2.5.49)
Efface (zéro) l'ID du thread enfant à l'emplacement pointé par child_tid (clone()) ou cl_args.child_tid (clone3()) dans la mémoire de l'enfant lorsque l'enfant se termine, et effectue un réveil sur le futex à cette adresse. L'adresse impliquée peut être modifiée par l'appel système set_tid_address(2). Ceci est utilisé par les bibliothèques de threading.
CLONE_CHILD_SETTID (depuis Linux 2.5.49)
Stocke l'ID du thread enfant à l'emplacement pointé par child_tid (clone()) ou cl_args.child_tid (clone3()) dans la mémoire de l'enfant. L'opération de stockage s'achève avant que l'appel clone ne renvoie le contrôle à l'espace utilisateur dans le processus enfant. (Notez que l'opération de stockage peut ne pas s'être achevée avant que l'appel clone ne renvoie dans le processus parent, ce qui est pertinent si l'indicateur CLONE_VM est également utilisé.)
CLONE_CLEAR_SIGHAND (depuis Linux 5.5)
Par défaut, les dispositions des signaux dans le thread enfant sont les mêmes que dans le parent. Si cet indicateur est spécifié, alors tous les signaux qui sont gérés dans le parent (et non définis sur SIG_IGN) sont réinitialisés à leurs dispositions par défaut (SIG_DFL) dans l'enfant.
Spécifier cet indicateur conjointement avec CLONE_SIGHAND est absurde et interdit.
CLONE_DETACHED (historique)
Pendant un certain temps (durant la série de développement Linux 2.5), il y a eu un indicateur CLONE_DETACHED, qui empêchait le parent de recevoir un signal lorsque l'enfant se terminait. Finalement, l'effet de cet indicateur a été absorbé par l'indicateur CLONE_THREAD et au moment où Linux 2.6.0 est sorti, cet indicateur n'avait aucun effet. Depuis Linux 2.6.2, la nécessité de donner cet indicateur conjointement avec CLONE_THREAD a disparu.
Cet indicateur est toujours défini, mais il est généralement ignoré lors de l'appel à clone(). Cependant, voir la description de CLONE_PIDFD pour certaines exceptions.
CLONE_FILES (depuis Linux 2.0)
Si CLONE_FILES est défini, le processus appelant et le processus enfant partagent la même table de descripteurs de fichiers. Tout descripteur de fichier créé par le processus appelant ou par le processus enfant est également valide dans l'autre processus. De même, si l'un des processus ferme un descripteur de fichier, ou modifie ses indicateurs associés (en utilisant l'opération fcntl(2) F_SETFD), l'autre processus est également affecté. Si un processus partageant une table de descripteurs de fichiers appelle execve(2), sa table de descripteurs de fichiers est dupliquée (non partagée).
Si CLONE_FILES n'est pas défini, le processus enfant hérite d'une copie de tous les descripteurs de fichiers ouverts dans le processus appelant au moment de l'appel clone. Les opérations ultérieures qui ouvrent ou ferment des descripteurs de fichiers, ou modifient les indicateurs de descripteurs de fichiers, effectuées par le processus appelant ou l'enfant n'affectent pas l'autre processus. Notez cependant que les descripteurs de fichiers dupliqués dans l'enfant font référence aux mêmes descriptions de fichiers ouvertes que les descripteurs de fichiers correspondants dans le processus appelant, et partagent donc les décalages de fichiers et les indicateurs d'état de fichiers (voir open(2)).
CLONE_FS (depuis Linux 2.0)
Si CLONE_FS est défini, l'appelant et le processus enfant partagent les mêmes informations du système de fichiers. Cela inclut la racine du système de fichiers, le répertoire de travail courant et l'umask. Tout appel à chroot(2), chdir(2), ou umask(2) effectué par le processus appelant ou l'enfant affecte également l'autre processus.
Si CLONE_FS n'est pas défini, le processus enfant travaille sur une copie des informations du système de fichiers du processus appelant au moment de l'appel clone. Les appels à chroot(2), chdir(2), ou umask(2) effectués plus tard par l'un des processus n'affectent pas l'autre processus.
CLONE_INTO_CGROUP (depuis Linux 5.7)
Par défaut, un processus enfant est placé dans le même cgroup de version 2 que son parent. L'indicateur CLONE_INTO_CGROUP permet au processus enfant d'être créé dans un cgroup de version 2 différent. (Notez que CLONE_INTO_CGROUP n'a d'effet que pour les cgroups de version 2.)
Afin de placer le processus enfant dans un cgroup différent, l'appelant spécifie CLONE_INTO_CGROUP dans cl_args.flags et passe un descripteur de fichier qui fait référence à un cgroup de version 2 dans le champ cl_args.cgroup. (Ce descripteur de fichier peut être obtenu en ouvrant un répertoire de cgroup v2 en utilisant soit le drapeau O_RDONLY, soit le drapeau O_PATH.) Notez que toutes les restrictions habituelles (décrites dans cgroups(7)) sur le placement d'un processus dans un cgroup de version 2 s'appliquent.
Parmi les cas d'utilisation possibles pour CLONE_INTO_CGROUP figurent les suivants :
•
Lancer un processus dans un cgroup différent de celui du parent permet à un gestionnaire de services de lancer directement de nouveaux services dans des cgroups dédiés. Cela élimine le "jitter" de comptabilité qui serait causé si le processus enfant était d'abord créé dans le même cgroup que le parent, puis déplacé vers le cgroup cible. De plus, lancer le processus enfant directement dans un cgroup cible est nettement moins coûteux que de déplacer le processus enfant vers le cgroup cible après sa création.
•
L'indicateur CLONE_INTO_CGROUP permet également la création de processus gelés en les lançant dans un cgroup gelé. (Voir cgroups(7) pour une description du contrôleur freezer.)
•
Pour les applications multi-threads (ou même les implémentations de threads qui utilisent les cgroups pour limiter les threads individuels), il est possible d'établir une disposition fixe des cgroups avant de lancer chaque thread directement dans son cgroup cible.
CLONE_IO (depuis Linux 2.6.25)
Si CLONE_IO est défini, le nouveau processus partage un contexte d'E/S avec le processus appelant. Si cet indicateur n'est pas défini, alors (comme avec fork(2)), le nouveau processus a son propre contexte d'E/S.
Le contexte d'E/S est la portée des E/S du planificateur de disque
ulateur (c'est-à-dire ce que l'ordonnanceur d'E/S utilise pour modéliser l'ordonnancement des E/S d'un processus). Si des processus partagent le même contexte d'E/S, ils sont traités comme un seul par l'ordonnanceur d'E/S. En conséquence, ils se partagent le temps disque. Pour certains ordonnanceurs d'E/S, si deux processus partagent un contexte d'E/S, ils seront autorisés à entrelacer leurs accès au disque. Si plusieurs fils d'exécution effectuent des E/S pour le compte du même processus (aio_read(3) , par exemple), ils devraient utiliser CLONE_IO pour obtenir de meilleures performances d'E/S. CLONE_SIGHAND (depuis Linux 2.0)
Si CLONE_SIGHAND est défini, le processus appelant et le processus enfant partagent la même table de gestionnaires de signaux. Si le processus appelant ou le processus enfant appelle sigaction(2) pour changer le comportement associé à un signal, le comportement est modifié dans l'autre processus également. Cependant, le processus appelant et les processus enfants ont toujours des masques de signaux et des ensembles de signaux en attente distincts. Ainsi, l'un d'eux peut bloquer ou débloquer des signaux en utilisant sigprocmask(2) sans affecter l'autre processus.
Si CLONE_SIGHAND n'est pas défini, le processus enfant hérite d'une copie des gestionnaires de signaux du processus appelant au moment de l'appel clone. Les appels à sigaction(2) effectués plus tard par l'un des processus n'ont aucun effet sur l'autre processus.
Depuis Linux 2.6.0, le masque flags doit également inclure CLONE_VM si CLONE_SIGHAND est spécifié.
CLONE_STOPPED (depuis Linux 2.6.0)
Si CLONE_STOPPED est défini, alors l'enfant est initialement arrêté (comme s'il lui avait été envoyé un signal SIGSTOP ), et doit être repris en lui envoyant un signal SIGCONT .
Ce drapeau a été déprécié à partir de Linux 2.6.25, et a été supprimé complètement dans Linux 2.6.38. Depuis lors, le noyau l'ignore silencieusement sans erreur. À partir de Linux 4.6, le même bit a été réutilisé pour le drapeau CLONE_NEWCGROUP .
CLONE_SYSVSEM (depuis Linux 2.5.10)
Si CLONE_SYSVSEM est défini, alors l'enfant et le processus appelant partagent une seule liste de valeurs d'ajustement de sémaphore System V (semadj) (voir semop(2)). Dans ce cas, la liste partagée accumule les valeurs semadj de tous les processus partageant la liste, et les ajustements de sémaphore ne sont effectués que lorsque le dernier processus partageant la liste se termine (ou cesse de partager la liste en utilisant unshare(2)). Si ce drapeau n'est pas défini, alors l'enfant a une liste semadj séparée qui est initialement vide.
CLONE_THREAD (depuis Linux 2.4.0)
Si CLONE_THREAD est défini, l'enfant est placé dans le même groupe de threads que le processus appelant. Pour rendre le reste de la discussion sur CLONE_THREAD plus lisible, le terme « thread » est utilisé pour désigner les processus au sein d'un groupe de threads.
Les groupes de threads étaient une fonctionnalité ajoutée dans Linux 2.4 pour prendre en charge la notion POSIX de threads partageant un seul PID. En interne, ce PID partagé est le soi-disant identifiant de groupe de threads (TGID) pour le groupe de threads. Depuis Linux 2.4, les appels à getpid(2) retournent le TGID de l'appelant.
Les threads au sein d'un groupe peuvent être distingués par leurs identifiants de threads (TID) uniques (à l'échelle du système). Le TID d'un nouveau thread est disponible en tant que résultat de fonction retourné à l'appelant, et un thread peut obtenir son propre TID en utilisant gettid(2).
Lorsqu'un appel clone est effectué sans spécifier CLONE_THREAD, alors le thread résultant est placé dans un nouveau groupe de threads dont le TGID est le même que le TID du thread. Ce thread est le leader du nouveau groupe de threads.
Un nouveau thread créé avec CLONE_THREAD a le même processus parent que le processus qui a fait l'appel clone (c'est-à-dire, comme CLONE_PARENT), de sorte que les appels à getppid(2) retournent la même valeur pour tous les threads d'un groupe de threads. Lorsqu'un thread CLONE_THREAD se termine, le thread qui l'a créé ne reçoit pas de signal SIGCHLD (ou autre signal de terminaison) ; et le statut d'un tel thread ne peut pas non plus être obtenu en utilisant wait(2). (Le thread est dit détaché.)
Après que tous les threads d'un groupe de threads se sont terminés, le processus parent du groupe de threads reçoit un signal SIGCHLD (ou autre signal de terminaison).
Si l'un des threads d'un groupe de threads effectue un execve(2), alors tous les threads autres que le leader du groupe de threads sont terminés, et le nouveau programme est exécuté dans le leader du groupe de threads.
Si l'un des threads d'un groupe de threads crée un enfant en utilisant fork(2), alors n'importe quel thread du groupe peut wait(2) pour cet enfant.
Depuis Linux 2.5.35, le masque flags doit également inclure CLONE_SIGHAND si CLONE_THREAD est spécifié (et notez que, depuis Linux 2.6.0, CLONE_SIGHAND requiert également CLONE_VM pour être inclus).
Les dispositions et actions de signal sont à l'échelle du processus : si un signal non géré est délivré à un thread, alors il affectera (terminera, arrêtera, reprendra, sera ignoré dans) tous les membres du groupe de threads.
Chaque thread a son propre masque de signaux, défini par sigprocmask(2).
Un signal peut être dirigé vers le processus ou vers un thread. Un signal dirigé vers le processus est ciblé sur un groupe de threads (c'est-à-dire, un TGID), et est délivré à un thread arbitrairement sélectionné parmi ceux qui ne bloquent pas le signal. Un signal peut être dirigé vers le processus parce qu'il a été généré par le noyau pour des raisons autres qu'une exception matérielle, ou parce qu'il a été envoyé en utilisant kill(2) ou sigqueue(3). Un signal dirigé vers un thread est ciblé sur (c'est-à-dire délivré à) un thread spécifique. Un signal peut être dirigé vers un thread parce qu'il a été envoyé en utilisant tgkill(2) ou pthread_sigqueue(3), ou parce que le thread a exécuté une instruction de langage machine qui a déclenché une exception matérielle (par exemple, un accès mémoire invalide déclenchant SIGSEGV ou une exception en virgule flottante déclenchant SIGFPE).
Un appel à sigpending(2) retourne un ensemble de signaux qui est l'union des signaux dirigés vers le processus en attente et des signaux en attente pour le thread appelant.
Si un signal dirigé vers le processus est délivré à un groupe de threads, et que le groupe de threads a installé un gestionnaire pour le signal, alors le gestionnaire est invoqué dans exactement un membre arbitrairement sélectionné du groupe de threads qui n'a pas bloqué le signal. Si plusieurs threads dans un groupe attendent d'accepter le même signal en utilisant sigwaitinfo(2), le noyau sélectionnera arbitrairement l'un de ces threads pour recevoir le signal.
CLONE_UNTRACED (depuis Linux 2.5.46)
Si CLONE_UNTRACED est spécifié, alors un processus de traçage ne peut pas forcer CLONE_PTRACE sur ce processus enfant.
CLONE_VFORK (depuis Linux 2.2)
Si CLONE_VFORK est défini, l'exécution du processus appelant est suspendue jusqu'à ce que l'enfant libère ses ressources de mémoire virtuelle via un appel à execve(2) ou _exit(2) (comme avec vfork(2)).
Si CLONE_VFORK n'est pas défini, alors à la fois le processus appelant et l'enfant sont ordonnables après l'appel, et une application ne doit pas compter sur un ordre d'exécution particulier.
CLONE_VM (depuis Linux 2.0)
Si CLONE_VM est défini, le processus appelant et le processus enfant s'exécutent dans le même espace mémoire. En particulier, les écritures mémoire effectuées par le processus appelant ou par le processus enfant sont également visibles dans l'autre processus. De plus, tout mappage ou démappage mémoire effectué avec mmap(2) ou munmap(2) par l'enfant ou le processus appelant affecte également l'autre processus.
Si CLONE_VM n'est pas défini, le processus enfant s'exécute dans une copie séparée de l'espace mémoire du processus appelant au moment de l'appel clone. Les écritures mémoire ou les mappages/démappages de fichiers effectués par l'un des processus n'affectent pas l'autre, comme avec fork(2).
Si le drapeau CLONE_VM est spécifié et que le drapeau CLONE_VFORK n'est pas spécifié, alors toute pile de signaux alternative qui a été établie par sigaltstack(2) est effacée dans le processus enfant.

VALEUR RETOURNÉE

En cas de succès, l'identifiant de thread du processus enfant est retourné dans le thread d'exécution de l'appelant. En cas d'échec, -1 est retourné dans le contexte de l'appelant, aucun processus enfant n'est créé, et errno est défini pour indiquer l'erreur.

VERSIONS

La fonction wrapper clone() de glibc apporte quelques modifications à la mémoire pointée par stack (modifications nécessaires pour configurer correctement la pile pour l'enfant) avant d'appeler l'appel système clone(). Ainsi, dans les cas où clone() est utilisé pour créer récursivement des enfants, n'utilisez pas le tampon utilisé pour la pile du parent comme pile de l'enfant.

Sur i386, clone() ne doit pas être appelé via vsyscall, mais directement via int $0x80.

Différences entre la bibliothèque C et le noyau

L'appel système brut clone() correspond plus étroitement à fork(2) en ce sens que l'exécution dans l'enfant continue à partir du point de l'appel. En tant que tel, les arguments fn et arg de la fonction wrapper clone() sont omis.

Contrairement à la fonction wrapper de glibc, l'appel système brut clone() accepte NULL comme argument stack (et clone3() autorise de même cl_args.stack à être NULL). Dans ce cas, l'enfant utilise une copie de la pile du parent. (Les sémantiques de copie sur écriture garantissent que l'enfant obtient des copies séparées des pages de pile lorsque l'un des processus modifie la pile.) Dans ce cas, pour un fonctionnement correct, l'option CLONE_VM ne doit pas être spécifiée. (Si l'enfant partage la mémoire du parent en raison de l'utilisation de l'option CLONE_VM, aucune duplication par copie sur écriture ne se produit et le chaos est susceptible d'en résulter.)

L'ordre des arguments diffère également dans l'appel système brut, et il existe des variations dans les arguments entre les architectures, comme détaillé dans les paragraphes suivants.

L'interface de l'appel système brut sur x86-64 et certaines autres architectures (y compris sh, tile et alpha) est :


long clone(unsigned long flags, void *stack,
           int *parent_tid, int *child_tid,
           unsigned long tls);

Sur x86-32, et plusieurs autres architectures courantes (y compris score, ARM, ARM 64, PA-RISC, arc, Power PC, xtensa et MIPS), l'ordre des deux derniers arguments est inversé :


long clone(unsigned long flags, void *stack,
          int *parent_tid, unsigned long tls,
          int *child_tid);

Sur les architectures cris et s390, l'ordre des deux premiers arguments est inversé :


long clone(void *stack, unsigned long flags,
           int *parent_tid, int *child_tid,
           unsigned long tls);

NAME

clone, clone3 - create a child process

SYNOPSIS

#include <sched.h>

int clone(int (*fn)(void *), void *stack, int flags, void *arg);

#define _GNU_SOURCE             /* See feature_test_macros(7) */
#include <sys/types.h>
#include <linux/sched.h>

int clone3(struct clone_args *args);

DESCRIPTION

The clone() system call creates a new process. The new process (child) is a copy of the calling process (parent) except that it has a unique process ID. The child process is created by calling the function specified by fn.

The arguments are:

fn
A pointer to the function that the child process should execute. This function is called with the single argument arg. The return value of fn is used as the exit status of the child process. If fn is NULL, the child process inherits the parent's execution flow from the point where clone() was called.
stack
This argument specifies the location and size of the stack for the new child process. The stack is created in a separate memory region. The stack grows downward in memory (towards lower addresses). Therefore, stack should point to the *top* of the memory region allocated for the child's stack. The size of the stack is determined by the size of the memory region provided.
flags
A bit mask that specifies how the child process should be created. The most important flags are:
CLONE_VM
If this flag is set, the child shares the same memory space as the parent. Any changes made by the child to the memory of the parent (e.g., writing to memory, mapping or unmapping memory) are visible to the parent, and vice versa. This flag is typically used when creating threads.
CLONE_FS
If this flag is set, the child shares the same file system information as the parent (i.e., the root directory, current working directory, and umask). Otherwise, the child inherits a copy of the parent's file system information. This flag is often used in conjunction with CLONE_VM.
CLONE_FILES
If this flag is set, the child shares the same open file descriptors as the parent. Otherwise, the child inherits a copy of the parent's file descriptor table. The file offset, file status flags, and signal handling flags are shared. This flag is often used in conjunction with CLONE_VM.
CLONE_SIGHAND
If this flag is set, the child shares the same signal handlers as the parent. This flag must be used with CLONE_VM. This flag is used to create threads.
CLONE_THREAD
If this flag is set, the child is created as a thread, sharing the same memory space, file descriptor table, and signal handlers as the parent. The child will be in the same thread group as the parent. The child's thread ID will be the same as the parent's thread ID. This flag is used to create threads. This flag implies CLONE_VM, CLONE_FS, and CLONE_SIGHAND.
CLONE_PARENT
If this flag is set, the child has the same parent process as the calling process. Otherwise, the child's parent is the process that called clone(). This flag is often used in conjunction with CLONE_THREAD to create threads.
CLONE_NEWNS
Create the child in a new set of network namespaces.
CLONE_NEWUTS
Create the child in a new UTS (UNIX Timesharing System) namespace. This allows the child to have its own host name and domain name.
CLONE_NEWIPC
Create the child in a new IPC namespace.
CLONE_NEWPID
Create the child in a new PID namespace.
CLONE_NEWNET
Create the child in a new network namespace.
CLONE_NEWUSER
Create the child in a new user namespace.
CLONE_NEWCGROUP
Create the child in a new cgroup namespace.
SIGCHLD
If this signal is specified, the child sends SIGCHLD to the parent when it terminates. This is the default behavior for fork(). If CLONE_THREAD is used, then SIGCHLD is not sent to the parent. Instead, the parent receives a signal specified by the parent_tid argument.

The clone() system call returns the process ID of the child process in the parent, and 0 in the child. If an error occurs, clone() returns -1 in the parent, and the child process is not created.

The clone3() system call is a newer interface for creating processes that is more flexible and extensible than clone(). It takes a pointer to a struct clone_args which specifies the flags and other arguments for the new process.

The struct clone_args contains the following fields:

unsigned flags;
unsigned size;
pid_t *pid;
pid_t *child_tid;
pid_t *parent_tid;
void *exit_signal;
void *stack;
unsigned stack_size;
void *exec_stack;
unsigned exec_size;
long *tls;
unsigned setbounds;
unsigned *lbs;
unsigned *ub;
unsigned pd; /* process data */
unsigned flags_set;
unsigned /* reserved */ ;

The clone3() system call returns the process ID of the child process in the parent, and 0 in the child. If an error occurs, clone3() returns -1 in the parent, and the child process is not created.

blackfin, m68k, and sparc

The argument-passing conventions on blackfin, m68k, and sparc are different from the descriptions above. For details, see the kernel (and glibc) source.

HISTORY

clone3()
Linux 5.3.

Linux 2.4 and earlier

In the Linux 2.4.x series, CLONE_THREAD generally does not make the parent of the new thread the same as the parent of the calling process. However, from Linux 2.4.7 to Linux 2.4.18 the CLONE_THREAD flag implied the CLONE_PARENT flag (as in Linux 2.6.0 and later).

ia64

On ia64, a different interface is used:


int __clone2(typeof(int (void *)) *fn,
             void *stack_base, size_t stack_size,
             int flags, void *arg, ...
          /* pid_t *parent_tid, struct user_desc *tls,
             pid_t *child_tid */ );

The prototype shown above is for the glibc wrapper function; for the system call itself, the prototype can be described as follows (it is identical to the clone() prototype on microblaze):


long clone2(unsigned long flags, void *stack_base,
            int stack_size, /* Size of stack */
            int *parent_tid, int *child_tid,
            unsigned long tls);

__clone2() operates in the same way as clone(), except that stack_base points to the lowest address of the child's stack area, and stack_size specifies the size of the stack pointed to by stack_base.

NOTES

One use of these system calls is to implement threads: multiple flows of control in a program that run concurrently in a shared address space.

The kcmp(2) system call can be used to test whether two processes share various resources such as a file descriptor table, System V semaphore undo operations, or a virtual address space.

Handlers registered using pthread_atfork(3) are not executed during a clone call.

BUGS

GNU C library versions 2.3.4 up to and including 2.24 contained a wrapper function for getpid(2) that performed caching of PIDs. This caching relied on support in the glibc wrapper for clone(), but limitations in the implementation meant that the cache was not up to date in some circumstances. In particular, if a signal was delivered to the child immediately after the clone() call, then a call to getpid(2) in a handler for the signal could return the PID of the calling process ("the parent"), if the clone wrapper had not yet had a chance to update the PID cache in the child. (This discussion ignores the case where the child was created using CLONE_THREAD, when getpid(2) should return the same value in the child and in the process that called clone(), since the caller and the child are in the same thread group. The stale-cache problem also does not occur if the flags argument includes CLONE_VM.) To get the truth, it was sometimes necessary to use code such as the following:


#include <syscall.h>
pid_t mypid;
mypid = syscall(SYS_getpid);

Because of the stale-cache problem, as well as other problems noted in getpid(2), the PID caching feature was removed in glibc 2.25.

EXAMPLES

The following program demonstrates the use of clone() to create a child process that executes in a separate UTS namespace. The child changes the hostname in its UTS namespace. Both parent and child then display the system hostname, making it possible to see that the hostname differs in the UTS namespaces of the parent and child. For an example of the use of this program, see setns(2).

Within the sample program, we allocate the memory that is to be used for the child's stack using mmap(2) rather than malloc(3) for the following reasons:

•
mmap(2) allocates a block of memory that starts on a page boundary and is a multiple of the page size. This is useful if we want to establish a guard page (a page with protection PROT_NONE) at the end of the stack using mprotect(2).
•
We can specify the MAP_STACK flag to request a mapping that is suitable for a stack. For the moment, this flag is a no-op on Linux, but it exists and has effect on some other systems, so we should include it for portability.

Program source

#define _GNU_SOURCE
#include <err.h>
#include <sched.h>
#include <signal.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/types.h>
#include <sys/utsname.h>
#include <sys/wait.h>
#include <unistd.h>

static int              /* Start function for cloned child */
childFunc(void *arg)
{
    struct utsname uts;

    /* Change hostname in UTS namespace of child.  */
    if (sethostname(arg, strlen(arg)) == -1)
        err(EXIT_FAILURE, "sethostname");

    /* Retrieve and display hostname.  */
    if (uname(&uts) == -1)
        err(EXIT_FAILURE, "uname");
    printf("uts.nodename in child:  %s\n", uts.nodename);

    /* Keep the namespace open for a while, by sleeping.
       This allows some experimentation--for example, another
       process might join the namespace.  */
    sleep(200);

    return 0;           /* Child terminates now */
}

#define STACK_SIZE (1024 * 1024)    /* Stack size for cloned child */

int
main(int argc, char *argv[])
{
    char            *stack;         /* Start of stack buffer */
    char            *stackTop;      /* End of stack buffer */
    pid_t           pid;
    struct utsname  uts;

    if (argc < 2) {
        fprintf(stderr, "Usage: %s <child-hostname>\n", argv[0]);
        exit(EXIT_SUCCESS);
    }

    /* Allocate memory to be used for the stack of the child.  */
    stack = mmap(NULL, STACK_SIZE, PROT_READ | PROT_WRITE,
                 MAP_PRIVATE | MAP_ANONYMOUS | MAP_STACK, -1, 0);
    if (stack == MAP_FAILED)
        err(EXIT_FAILURE, "mmap");

    stackTop = stack + STACK_SIZE;  /* Assume stack grows downward */

    /* Create child that has its own UTS namespace;
       child commences execution in childFunc().  */
    pid = clone(childFunc, stackTop, CLONE_NEWUTS | SIGCHLD, argv[1]);
    if (pid == -1)
        err(EXIT_FAILURE, "clone");

    /* The stack memory is no longer needed by the parent */
    if (munmap(stack, STACK_SIZE))
        err(EXIT_FAILURE, "munmap");

    printf("clone() returned %jd\n", (intmax_t) pid);

    /* Parent falls through to here */
    sleep(1);           /* Give child time to change its hostname */

    /* Display hostname in parent's UTS namespace.  This will be
       different from hostname in child's UTS namespace.  */
    if (uname(&uts) == -1)
        err(EXIT_FAILURE, "uname");
    printf("uts.nodename in parent: %s\n", uts.nodename);

    if (waitpid(pid, NULL, 0) == -1)    /* Wait for child */
        err(EXIT_FAILURE, "waitpid");

    printf("child has terminated\n");

    exit(EXIT_SUCCESS);
}
