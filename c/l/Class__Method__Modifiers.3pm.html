RÉSUM

É 
package Child;
use parent 'MyParent';
use Class::Method::Modifiers;
sub new_method { }
before 'old_method' => sub {
    carp "old_method is deprecated, use new_method";
};
around 'other_method' => sub {
    my $orig = shift;
    my $ret = $orig->(@_);
    return $ret =~ /\d/ ? $ret : lc $ret;
};
after 'private', 'protected' => sub {
    debug "finished calling a dangerous method";
};
use Class::Method::Modifiers qw(fresh);
fresh 'not_in_hierarchy' => sub {
    warn "freshly added method\n";
}
;

DESCRIPTIO

N

Les modificateurs de méthode sont une fonctionnalité pratique issue du monde du CLOS (Common Lisp Object System)

.

Dans sa forme la plus basique, un modificateur de méthode n'est rien d'autre qu'une méthode qui appelle "$self->SUPER::foo(@_)". Pour ma part, j'ai du mal à me souvenir de cette invocation exacte, alors mes classes font rarement une redistribution vers leurs classes de base. Très mauvais

!

"Class::Method::Modifiers" fournit trois modificateurs : "before", "around", et "after". "before" et "after" s'exécutent juste avant et après la méthode qu'ils modifient, mais ne peuvent pas vraiment affecter cette méthode originale. "around" s'exécute à la place de la méthode originale, avec un crochet pour appeler facilement cette méthode originale. Voir la section "MODIFIERS" pour plus de détails sur le fonctionnement des modificateurs

particuliers.

Un avantage évident de l'utilisation de "Class::Method::Modifiers" est que vous pouvez définir plusieurs modificateurs dans un seul espace de noms. Ces modificateurs distincts n'ont pas besoin de se connaître les uns les autres. Cela rend la conception descendante facile. Ayez une classe de base qui fournit les méthodes squelette de chaque opération, et laissez les plugins modifier ces méthodes pour développer les détails

spécifiques.

Les classes parentes n'ont pas besoin de connaître "Class::Method::Modifiers". Cela signifie que vous devriez pouvoir modifier des méthodes dans n'importe quelle sous-classe. Voir Term::VT102::ZeroBased pour un exemple de sous-classe avec "Class::Method::Mo

difiers".

En bref, "Class::Method::Modifiers" résout le problème de s'assurer que vous appelez "$self->SUPER::foo(@_)", et fournit une interface plus propre pour

cela.

Depuis la version 1.00, "Class::Method::Modifiers" est plus rapide dans certains cas que Moose. Voir benchmark/method_modifiers.pl dans la distribution

Moose.

"Class::Method::Modifiers" fournit également un type de "modificateur" supplémentaire, "fresh" ; voi

r ci-de
ssous.

MODIFICATEUR

S

Tous les modificateurs vous permettent de modifier une ou plusieurs méthodes à la fois. Les noms de plusieurs méthodes peuvent être fournis sous forme de liste ou de référence de tableau. Exemples

: 
before 'method' => sub { ... };
before 'method1', 'method2' => sub { ... };
before [ 'method1', 'method2' ] => sub { ... }
;

before method(s) => sub { ... }

;

"before" est appelé avant la méthode qu'il modifie. Sa valeur de retour est totalement ignorée. Il reçoit le même @_ que la méthode qu'il modifie aurait reçu. Vous pouvez modifier le @_ que la méthode originale recevra en modifiant $_[0] et compagnie (ou en modifiant quoi que ce soit à

l'intérieur d'une référence
). C'est une fonctionnalité !

after method(s) => sub { ... }

;

"after" est appelé après la méthode qu'il modifie. Sa valeur de retour est totalement ignorée. Il reçoit le même @_ que la méthode qu'il modifie a reçu, en grande partie. La méthode originale peut modifier @_ (comme en modifiant $_[0] ou des références) et "after" verra la version modifiée. Si vous n'aimez pas ce comportement, spécifiez à la fois un "before" et "after", et copiez le @_ pendant "before" pour que "after" puiss

e l'uti
liser.

around method(s) => sub { ... }

;

"around" est appelé à la place de la méthode qu'il modifie. La méthode que vous surchargez est passée en tant que premier argument (appelé $orig par convention). Attention aux valeurs de retour contextuelles de $orig

.

Vous pouvez utiliser "around" pour

:
Passer un @_ différent à
$orig 
around 'method' => sub {
    my $orig = shift;
    my $self = shift;
    $orig->($self, reverse
@_);
};
Modifier la valeur de retour de
$orig 
around 'method' => sub {
    my $orig = shift;
    ucfirst $orig->(@_)
;
};
Éviter d'appeler $orig -- conditionnellem
ent 
around 'method' => sub {
my $orig = shift;
return $orig->(@_) i
f time() % 2; retur
n "no dice, captain"; };

fresh method(s) => sub { ... }

;

(Disponible depuis la version 2.

00)

Contrairement aux autres modificateurs, celui-ci ne modifie pas une méthode existante. Ordinairement, "fresh" installe simplement le coderef comme méthode dans la classe appropriée ; mais si la hiérarchie de classes contient déjà une méthode du même nom, une exception est levée. L'idée de ce "modificateur" est d'augmenter la sécurité lors de la sous-classification. Supposons que vous écriviez une sous-classe d'une classe Some::Base et que vous ajoutiez une nouvelle méthode

: 
package My::Subclass;
use base 'Some::Base';
sub foo { ...
}

Si une version ultérieure de Some::Base ajoute également une nouvelle méthode nommée "foo", votre méthode masquera cette méthode. Alternativement, vous pouvez utiliser "fresh" pour installer la méthode supplémentaire dans votre sous-classe

: 
package My::Subclass;
use base 'Some::Base';
use Class::Method::Modifiers 'fresh';
fresh 'foo' => sub { ... }
;

Maintenant, mettre à niveau Some::Base vers une version avec une méthode "foo" conflictuelle provoquera le déclenchement d'une exception ; voir cette erreur vous donnera l'opportunité de corriger le problème (peut-être en choisissant un nom de méthode différent dans votre sous-classe ou similaire)

.

Créer des méthodes fraîches avec "install_modifier" (voir ci-dessous) fournit un moyen d'obtenir des avantages de sécurité similaires lors de l'ajout de monkeypatches locaux à des classes existantes ; voir http://aaroncrane.co.uk/talks/monkey_patching_subclassing/

.

Pour des raisons de compatibilité d'API, cette fonction n'est exportée que lorsque vous la demandez spécifiquement, ou pour ":al

l
".

install_modifier $package, $type, @names, sub { ...

}

"install_modifier" est comme "before", "after", "around", et "fresh" mais il vous permet aussi de sélectionner dynamiquement le type de modificateur ('before', 'after', 'around', 'fresh') et le paquet dans lequel les modificateurs de méthode sont installés. Ce niveau expert fonction est exportée que lorsque vous le demandez spécifiquement, ou pour ":a

l
l"
.

NOTE

S

Les trois modificateurs normaux ; "before", "after", et "around" ; sont exportés dans votre espace de noms par défaut. Vous pouvez "use Class::Method::Modifiers ()" pour éviter de modifier votre espace de noms. Je pourrais emprunter d'autres fonctionnalités à Moose, à savoir "super", "override", "inner", "augment", et quoi que ce soit que les gens de Moose inventent

ensuite.

Notez que la syntaxe et la sémantique de ces modificateurs sont directement empruntées à Moose (les implémentations, cependant, ne le sont pas)

.

Class::Trigger partage quelques similitudes avec "Class::Method::Modifiers", et ils ont même un certain chevauchement de but -- les deux peuvent être utilisés pour implémenter des applications hautement pluggables. La différence est que Class::Trigger fournit un mécanisme pour permettre facilement aux classes parentes d'invoquer des hooks définis par d'autres code. "Class::Method::Modifiers" fournit un moyen sûr de redéfinir/augmenter des méthodes, et la classe parente n'a pas besoin de le

savoir.

:lvalue

MÉTHODES

Lors de l'ajout de "before" ou "after" modificateurs, la méthode enveloppe sera une méthode lvalue si la sous-routine enveloppée l'est, et l'affectation à la méthode se propagera à la méthode enveloppée comme prévu. Pour "around" modificateurs, c'est la sous-routine du mo

dificateur qui déterm
ine si la méthode envelopp
e est une méthode lvalue.

AVERTISSEMEN

TS

Il est erroné de modifier une méthode qui n'existe pas dans la hiérarchie d'héritage de votre classe. Si cela se produit, une exception sera levée lorsque le modificateur est

défini.

Cela ne fonctionne pas encore bien avec "caller". Il y a quelques "TODO" tests pour cela. N'espérez pas trop cependant

!

L'application de modificateurs aux méthodes lvalue de tableau n'est pas entièrement prise en charge. Tenter d'affecter à une méthode lvalue de tableau à laquelle un "after" modificateur est appliqué entraînera une erreur. Les méthodes lvalue de tabl

eau ne sont pas bien prises en charge par per
l en général, et devraient être évitées.

CHANGEMENTS MAJEURS DE

VERSION

Ce module a été passé à 1.00 après une réimplémentation complète, pour indiquer une rupture de la compatibilité ascendante. Le modificateur "guard" a été supprimé, et les internes sont complètement

différents.

La nouvelle version est plusieurs fois plus rapide avec la moitié du code. Elle est maintenant même plus rapide que

Moose.

Tout code qui utilisait simplement des modificateurs ne devrait pas changer de comportement, sauf pour devenir plus correct. Et, bien sûr, plus rapide.
