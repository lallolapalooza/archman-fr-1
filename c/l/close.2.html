DESCRIPTIO

N

close() ferme un descripteur de fichier, de sorte qu'il ne pointe plus vers aucun fichier et peut être réutilisé. Tous les verrous d'enregistrement (voir fcntl(2)) détenus sur le fichier auquel il était associé, et appartenant au processus, sont supprimés, quel que soit le descripteur de fichier utilisé pour obtenir le verrou. Cela a des conséquences fâcheuses et il faut être particulièrement prudent lors de l'utilisation des verrous d'enregistrement consultatifs. Voir fcntl(2) pour une discussion des risques et des conséquences, ainsi que pour les verrous de description de fichier ouverte (probablement préférables)

.

Si fd est le dernier descripteur de fichier pointant vers la description de fichier ouverte sous-jacente (voir open(2)), les ressources associées à la description de fichier ouverte sont libérées ; si le descripteur de fichier était la dernière référence vers un fichier qui a été supprimé à l'aide de unlink(2), le fich

ier est
effacé.

AVERTISSEMEN

TS

Une fermeture réussie ne garantit pas que les données ont été enregistrées avec succès sur le disque, car le noyau utilise le cache de tampons pour différer les écritures. En général, les systèmes de fichiers ne vident pas les tampons lors de la fermeture d'un fichier. Si vous devez être sûr que les données sont physiquement stockées sur le disque sous-jacent, utilisez fsync(2). (Cela dépendra du matériel du disque à ce stade.

)

Processus multithreadés et

close()

Il est probablement imprudent de fermer des descripteurs de fichier alors qu'ils peuvent être utilisés par des appels système dans d'autres threads du même processus. Comme un descripteur de fichier peut être réutilisé, il existe certaines conditions de concurrence obscures qui peuvent causer des effets de bord

indésirables.

De plus, considérez le scénario suivant où deux threads effectuent des opérations sur le même descripteur de fichier

:
(1
)
Un thread est bloqué dans un appel système d'entrée/sortie sur le descripteur de fichier. Par exemple, il essaie d' écrire (write(2)) dans un tube déjà plein, ou essaie de lire (read(2)) depuis un socket de flux qui n'a actuellement aucune donnée
disponible.
(2
)
Un autre thread
ferme le descrip
teur de fichier.

Le comportement dans cette situation varie selon les systèmes. Sur certains systèmes, lorsque le descripteur de fichier est fermé, l'appel système bloquant retourne immédiatement avec une

erreur.

Sur Linux (et peut-être certains autres systèmes), le comportement est différent : l'appel système d'entrée/sortie bloquant détient une référence vers la description de fichier ouverte sous-jacente, et cette référence maintient la description ouverte jusqu'à ce que l'appel système d'entrée/sortie se termine. (Voir open(2) pour une discussion des descriptions de fichier ouverte.) Ainsi, l'appel système bloquant dans le premier thread peut se terminer avec succès après le close() dans le

second
thread.

Gestion des codes de retour d'erreur de

close()

Un programmeur prudent vérifiera la valeur de retour de close(), car il est tout à fait possible que des erreurs sur une opération write(2) précédente ne soient rapportées que lors du close() final qui libère la description de fichier ouverte. Ne pas vérifier la valeur de retour lors de la fermeture d'un fichier peut entraîner une perte silencieuse de données. Cela peut particulièrement être observé avec NFS et avec les quotas de

disque.

Notez cependant qu'un code de retour d'échec ne doit être utilisé qu'à des fins de diagnostic (c'est-à-dire un avertissement à l'application qu'il peut y avoir encore des entrées/sorties en attente ou qu'il y a eu des entrées/sorties en échec) ou à des fins correctives (par exemple, réécrire le fichier une fois de plus ou créer une sauvegarde)

.

Réessayer close() après un code de retour d'échec est la mauvaise chose à faire, car cela peut causer la fermeture d'un descripteur de fichier réutilisé par un autre thread. Cela peut se produire car le noyau Linux libère toujours le descripteur de fichier tôt dans l'opération de fermeture, le libérant pour réutilisation ; les étapes qui peuvent retourner une erreur, comme le vidage des données vers le système de fichiers ou le périphérique, n'ont lieu que plus tard dans l'opération de

fermeture.

De nombreuses autres implémentations ferment également toujours le descripteur de fichier (sauf dans le cas de EBADF, signifiant que le descripteur de fichier était invalide) même si elles rapportent ensuite une erreur lors du retour de close(). POSIX.1-2008 était muet sur ce

point.

Un programmeur prudent qui veut connaître les erreurs d'entrée/sortie peut faire précéder close() d'un appel à fsync(

2).

L'erreur EINTR est un cas quelque peu spécial. Concernant l'erreur EINTR, POSIX.1-2008 disait

:
Si close() est interrompu par un signal qui doit être intercepté, il doit renvoyer -1 avec errno défini à EINTR et l'état de fd est
indéfini.

Cela permet le comportement qui se produit sur Linux et de nombreuses autres implémentations, où, comme pour d'autres erreurs qui peuvent être rapportées par close(), le descripteur de fichier est garanti d'être fermé. Cependant, cela permet aussi une autre possibilité : que l'implémentation renvoie une erreur EINTR et garde le descripteur de fichier ouvert. (Selon sa documentation, le close() de HP-UX fait cela.) L'appelant doit alors à nouveau utiliser close() pour fermer le descripteur de fichier, afin d'éviter les fuites de descripteurs de fichier. Cette divergence dans les comportements d'implémentation constitue un obstacle difficile pour les applications portables, car sur de nombreuses implémentations, close() ne doit pas être rappelé après une erreur EINTR, et sur au moins une, close() doit être

rappelé.

POSIX.1-2024 a standardisé le comportement de HP

-UX, rendant Linux et de nombreuses autres
implémentations non conformes. Il n'y a pas
de plan pour changer le comportement sur Linux.
