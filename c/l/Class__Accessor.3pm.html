NOM

Class::Accessor - Génération automatisée d'accesseurs

SYNOPSIS

package Foo;
use base qw(Class::Accessor);
Foo->follow_best_practice;
Foo->mk_accessors(qw(name role salary));
# ou si vous préférez une interface de type Moose...
package Foo;
use Class::Accessor "antlers";
has name => ( is => "rw", isa => "Str" );
has role => ( is => "rw", isa => "Str" );
has salary => ( is => "rw", isa => "Num" );
# Pendant ce temps, dans un bout de code à côté !
# Class::Accessor fournit new().
my $mp = Foo->new({ name => "Marty", role => "JAPH" });
my $job = $mp->role;  # récupère $mp->{role}
$mp->salary(400000);  # définit $mp->{salary} = 400000 # J'aimerais bien
# comme my @info = @{$mp}{qw(name role)}
my @info = $mp->get(qw(name role));
# $mp->{salary} = 400000
$mp->set('salary', 400000);

DESCRIPTION

Ce module génère automatiquement des accesseurs/mutateurs pour votre classe.

La plupart du temps, écrire des accesseurs est un exercice de copier-coller. Vous vous retrouvez généralement avec une série de méthodes comme ceci :

  sub name {
      my $self = shift;
      if(@_) {
          $self->{name} = $_[0];
      }
      return $self->{name};
  }
  sub salary {
      my $self = shift;
      if(@_) {
          $self->{salary} = $_[0];
      }
      return $self->{salary};
  }
# etc...

Une pour chaque donnée de votre objet. Bien que certaines seront uniques, effectuant des vérifications de valeurs et des astuces de stockage spéciales, la plupart seront simplement des exercices de répétition. Non seulement c'est un Mauvais Style d'avoir un tas de code répétitif, mais ce n'est tout simplement pas paresseux, ce qui est la vraie tragédie.

Si vous faites de votre module une sous-classe de Class::Accessor et déclarez vos champs d'accesseurs avec mk_accessors() alors vous vous retrouverez avec un ensemble d'accesseurs générés automatiquement qui peuvent même être personnalisés !

La configuration de base est très simple :

package Foo;
use base qw(Class::Accessor);
Foo->mk_accessors( qw(far bar car) );

Terminé. Foo a maintenant des accesseurs simples far(), bar() et car() définis.

Alternativement, si vous souhaitez suivre les directives best practice de Damian, vous pouvez utiliser :

package Foo;
use base qw(Class::Accessor);
Foo->follow_best_practice;
Foo->mk_accessors( qw(far bar car) );

Note : vous devez appeler "follow_best_practice" avant d'appeler "mk_accessors".

De type Moose

À la demande populaire, nous avons maintenant une interface simple de type Moose. Vous pouvez maintenant faire :

package Foo;
use Class::Accessor "antlers";
has far => ( is => "rw" );
has bar => ( is => "rw" );
has car => ( is => "rw" );

Actuellement, seul l'attribut "is" est pris en charge.

CONSTRUCTEUR

Class::Accessor fournit un constructeur de base, "new". Il génère un objet basé sur un hash et peut être appelé soit comme méthode de classe, soit comme méthode d'objet.

new

my $obj = Foo->new;
my $obj = $other_obj->new;
my $obj = Foo->new(\%fields);
my $obj = $other_obj->new(\%fields);

Il prend un hash optionnel %fields qui est utilisé pour initialiser l'objet (pratique si vous utilisez des accesseurs en lecture seule). Les champs du hash correspondent aux noms de vos accesseurs, donc...

package Foo;
use base qw(Class::Accessor);
Foo->mk_accessors('foo');
my $obj = Foo->new({ foo => 42 });
print $obj->foo;    # 42

cependant %fields peut contenir n'importe quoi, new() les mettra tous dans votre objet.

CRÉATION D'ACCESSEURS

follow_best_practice

Dans son livre Perl Best Practices, Damian recommande des méthodes get et set séparées avec les préfixes set_ et get_ pour rendre explicite ce que vous comptez faire. Si vous souhaitez créer ces méthodes d'accesseur au lieu des méthodes par défaut, appelez :

__PACKAGE__->follow_best_practice

avant que vous n'appeliez l'une des méthodes de création d'accesseurs.

accessor_name_for / mutator_name_for

Vous pouvez avoir vos propres idées de fous pour les noms des accesseurs, vous pouvez donc les réaliser en surchargeant "accessor_name_for" et "mutator_name_for" dans votre sous-classe. (J'ai copié cette idée de Class::DBI.)

mk_accessors

__PACKAGE__->mk_accessors(@fields);

Cela crée des méthodes accesseur/mutateur pour chaque champ nommé donné dans @fields. Pour chaque champ dans @fields il générera deux accesseurs. L'un appelé "field()" et l'autre appelé "_field_accessor()". Par exemple :

# Génère foo(), _foo_accessor(), bar() et _bar_accessor().
__PACKAGE__->mk_accessors(qw(foo bar));

Voir « Overriding autogenerated accessors » dans CAVEATS AND TRICKS pour plus de détails.

mk_ro_accessors

__PACKAGE__->mk_ro_accessors(@read_only_fields);

Identique à mk_accessors() sauf qu'il générera des accesseurs en lecture seule (c'est-à-dire de véritables accesseurs). Si vous essayez de définir une valeur avec ces accesseurs, il lèvera une exception. Il n'utilise que get() et non set().

package Foo;
use base qw(Class::Accessor);
Foo->mk_ro_accessors(qw(foo bar));
# Supposons que nous ayons un objet $foo de la classe Foo...
print $foo->foo;  # ok, affiche la valeur de $foo->{foo}
$foo->foo(42);    # BOOM !  Méchant vous.

mk_wo_accessors

__PACKAGE__->mk_wo_accessors(@write_only_fields);

Identique à mk_accessors() sauf qu'il générera des accesseurs en écriture seule (c'est-à-dire des mutateurs). Si vous essayez de lire une valeur avec ces accesseurs, il lèvera une exception. Il n'utilise que set() et non get().

NOTE Je ne suis pas entièrement sûr de l'utilité de cela, mais je suis sûr que quelqu'un en aura besoin. Si vous avez trouvé une utilisation, faites-le moi savoir. Pour l'instant, c'est ici pour l'orthogonalité et parce que c'est facile à implémenter.

package Foo;
use base qw(Class::Accessor);
Foo->mk_wo_accessors(qw(foo bar));
# Supposons que nous ayons un objet $foo de la classe Foo...
$foo->foo(42);      # OK.  Définit $self->{foo} = 42
print $foo->foo;    # BOOM !  Impossible de lire depuis cet accesseur.

Moose !

Si vous préférez une interface de type Moose pour créer des accesseurs, vous pouvez utiliser "has" en important ce module comme ceci :

use Class::Accessor "antlers";

ou

use Class::Accessor "moose-like";

Ensuite, vous pouvez déclarer des accesseurs comme ceci :

has alpha => ( is => "rw", isa => "Str" );
has beta  => ( is => "ro", isa => "Str" );
has gamma => ( is => "wo", isa => "Str" );

Actuellement, seul l'attribut "is" est pris en charge. Et notre "is" prend également en charge la valeur « wo » pour créer un accesseur en écriture seule.

Si vous utilisez l'interface de type Moose, vous devriez utiliser "extends" plutôt que de modifier votre @ISA directement. Fondamentalement, remplacez

@ISA = qw/Foo Bar/;

par

extends(qw/Foo Bar/);

DÉTAILS

Un accesseur généré par Class::Accessor ressemble à quelque chose comme ceci :

# Votre foo peut varier.
sub foo {
    my($self) = shift;
    if(@_) {    # définir
        return $self->set('foo', @_);
    }
    else {
        return $self->get('foo');
    }
}

Très simple. Tout ce qu'il fait, c'est déterminer si vous voulez définir une valeur ou obtenir une valeur et appelle la méthode appropriée. Class::Accessor fournit des méthodes get() et set() par défaut que votre classe peut redéfinir. Elles sont détaillées plus tard.

Modifier le comportement de l'accesseur

Plutôt que de modifier réellement l'accesseur lui-même, il est beaucoup plus judicieux de simplement redéfinir les deux méthodes clés que l'accesseur appelle. À savoir set() et get().

Si vous -vraiment- le souhaitez, vous pouvez redéfinir make_accessor().

set

$obj->set($key, $value);
$obj->set($key, @values);

set() définit comment, généralement, on stocke des données dans l'objet.

redéfinissez cette méthode pour changer la façon dont les données sont stockées par vos accesseurs.

get

$value  = $obj->get($key);
@values = $obj->get(@keys);

get() définit comment les données sont récupérées depuis vos objets.

redéfinissez cette méthode pour changer la façon dont elles sont récupérées.

make_accessor

$accessor = __PACKAGE__->make_accessor($field);

Génère une référence de sous-programme qui agit comme un accesseur pour le champ donné $field. Elle appelle get() et set().

Si vous souhaitez changer le comportement de vos accesseurs, essayez de redéfinir get() et set() avant de commencer à bidouiller make_accessor().

make_ro_accessor

$read_only_accessor = __PACKAGE__->make_ro_accessor($field);

Génère une référence de sous-programme qui agit comme un accesseur en lecture seule pour le champ donné $field. Elle appelle uniquement get().

Redéfinissez get() pour changer le comportement de vos accesseurs.

make_wo_accessor

$write_only_accessor = __PACKAGE__->make_wo_accessor($field);

Génère une référence de sous-programme qui agit comme un accesseur en écriture seule (mutateur) pour le champ donné $field. Elle appelle uniquement set().

Redéfinissez set() pour changer le comportement de vos accesseurs.

EXCEPTIONS

Si quelque chose se passe mal, Class::Accessor émettra un avertissement ou mourra en appelant Carp::carp ou Carp::croak. Si cela ne vous convient pas, vous pouvez redéfinir _carp() et _croak() dans votre sous-classe et faire tout ce que vous voulez d'autre.

EFFICACITÉ

Class::Accessor n'utilise pas de chargeur automatique (autoloader), il est donc beaucoup plus rapide que vous ne le penseriez. Ses méthodes générées n'entraînent aucune pénalité particulière par rapport à celles que vous écririez vous-même.

            Rate    Acc   Fast Faster Direct

Direct 2860979/s   977%   399%   295%     --

Class::Accessor::Fast est plus rapide que les méthodes écrites par un programmeur moyen (où "moyen" est basé sur le code d'exemple de Schwern).

Class::Accessor est plus lent que la moyenne, mais plus flexible.

Class::Accessor::Fuzzer est encore plus rapide que Class::Accessor::Fast. Il utilise un tableau en interne, pas un hachage. Cela peut être une bonne ou une mauvaise caractéristique selon votre point de vue.

L'accès direct au hachage est, bien sûr, beaucoup plus rapide que tout cela, mais il ne fournit aucune encapsulation.

Bien sûr, ce n'est pas aussi simple que de dire "Class::Accessor est plus lent que la moyenne". Ce sont des mesures de performance pour un accesseur simple. Si vos accesseurs effectuent un travail compliqué quelconque (comme parler à une base de données ou écrire dans un fichier), le temps passé à faire ce travail noiera rapidement le temps passé juste à appeler l'accesseur. Dans ce cas, Class::Accessor et ceux que vous écrivez seront à peu près à la même vitesse.

EXEMPLES

Voici un exemple de génération d'un accesseur pour chaque champ public de votre classe.

package Altoids;
use base qw(Class::Accessor Class::Fields);
use fields qw(curiously strong mints);
Altoids->mk_accessors( Altoids->show_fields('Public') );
sub new {
    my $proto = shift;
    my $class = ref $proto || $proto;
    return fields::new($class);
}
my Altoids $tin = Altoids->new;
$tin->curiously('Curiouser and curiouser');
print $tin->{curiously};    # prints 'Curiouser and curiouser'
# Subclassing works, too.
package Mint::Snuff;
use base qw(Altoids);
my Mint::Snuff $pouch = Mint::Snuff->new;
$pouch->strong('Blow your head off!');
print $pouch->{strong};     # prints 'Blow your head off!'

Voici un exemple simple de modification du comportement de vos accesseurs.

package Foo;
use base qw(Class::Accessor);
Foo->mk_accessors(qw(this that up down));
sub get {
    my $self = shift;
    # Note every time someone gets some data.
    print STDERR "Getting @_\n";
    $self->SUPER::get(@_);
}
sub set {
    my ($self, $key) = splice(@_, 0, 2);
    # Note every time someone sets some data.
    print STDERR "Setting $key to @_\n";
    $self->SUPER::set($key, @_);
}

AVERTISSEMENTS ET ASTUCES

Class::Accessor doit faire un peu de magie interne pour faire son travail rapidement et efficacement. À cause de cela, il y a quelques astuces et pièges qu'il faut connaître.

Hé, rien n'est parfait.

Ne créez pas de champ appelé DESTROY

C'est mauvais. Puisque DESTROY est une méthode magique, il serait mauvais pour nous de définir un accesseur en utilisant ce nom. Class::Accessor émettra un avertissement si vous essayez de l'utiliser avec un champ nommé "DESTROY".

Redéfinir les accesseurs générés automatiquement

Vous pouvez vouloir redéfinir l'accesseur généré automatiquement avec le vôtre, tout en faisant appeler à votre accesseur personnalisé celui par défaut. Par exemple, peut-être que vous voulez avoir un accesseur qui vérifie sa saisie. Normalement, on s'attendrait à ce que cela fonctionne :

package Foo;
use base qw(Class::Accessor);
Foo->mk_accessors(qw(email this that whatever));
# Only accept addresses which look valid.
sub email {
    my($self) = shift;
    my($email) = @_;
    if( @_ ) {  # Setting
        require Email::Valid;
        unless( Email::Valid->address($email) ) {
            carp("$email doesn't look like a valid address.");
            return;
        }
    }
    return $self->SUPER::email(@_);
}

Il y a un problème subtil dans le dernier exemple, et il est dans cette ligne :

return $self->SUPER::email(@_);

Si nous regardons comment Foo a été défini, il a appelé mk_accessors() qui a inséré email() directement dans l'espace de noms de Foo. Il n'y a *pas* de SUPER::email() vers qui déléguer ! Deux façons de contourner cela... la première est de faire une classe de base "pure" pour Foo. Cette classe pure générera les accesseurs et fournira la super-classe nécessaire pour que Foo les utilise :

package Pure::Organic::Foo;
use base qw(Class::Accessor);
Pure::Organic::Foo->mk_accessors(qw(email this that whatever));
package Foo;
use base qw(Pure::Organic::Foo);

Et maintenant Foo::email() peut redéfinir le Pure::Organic::Foo::email() généré et l'utiliser comme SUPER::email().

C'est probablement la solution la plus évidente pour tout le monde sauf moi. À la place, ce qui a d'abord eu du sens pour moi était que mk_accessors() définisse un alias de email(), _email_accessor(). En utilisant cette solution, Foo::email() serait écrit avec :

return $self->_email_accessor(@_);

au lieu de l'attendu SUPER::email().
