DESCRIPTIO

N

Ces appels système créent un nouveau processus (« fils »), d'une manière similaire à fork(

2).

Contrairement à fork(2), ces appels système offrent un contrôle plus précis sur les parties du contexte d'exécution qui sont partagées entre le processus appelant et le processus fils. Par exemple, à l'aide de ces appels système, l'appelant peut contrôler si les deux processus partagent ou non l'espace d'adressage virtuel, la table des descripteurs de fichiers et la table des gestionnaires de signaux. Ces appels système permettent également de placer le nouveau processus fils dans des namespaces(7) s

éparés.

Notez que dans cette page manuelle, « processus appelant » correspond normalement à « processus parent ». Mais voir les descriptions de CLONE_PARENT et CLONE_THREAD ci-

dessous.

page.

La fonction wrapper

clone()

Lorsque le processus fils est créé avec la fonction wrapper clone(), il commence son exécution en appelant la fonction pointée par l'argument fn. (Cela diffère de fork(2), où l'exécution continue dans le fils à partir du point de l'appel fork(2).) L'argument arg est passé comme argument de la fonction fn

.

Lorsque la fonction fn(arg) retourne, le processus fils se termine. L'entier retourné par fn est le code de sortie du processus fils. Le processus fils peut également se terminer explicitement en appelant exit(2) ou après avoir reçu un signal

fatal.

L'argument stack spécifie l'emplacement de la pile utilisée par le processus fils. Puisque le processus fils et le processus appelant peuvent partager la mémoire, il n'est pas possible pour le processus fils de s'exécuter sur la même pile que le processus appelant. Le processus appelant doit donc configurer l'espace mémoire pour la pile du fils et passer un pointeur vers cet espace à clone(). Les piles croissent vers le bas sur tous les processeurs qui exécutent Linux (sauf les processeurs HP PA), donc stack pointe généralement vers l'adresse la plus haute de l'espace mémoire configuré pour la pile du fils. Notez que clone() ne fournit pas de moyen par lequel l'appelant peut informer le noyau de la taille de la zone de

pile.

Les arguments restants de clone() sont dis

cutés ci-
dessous.

clone3(

)

L'appel système clone3() fournit un ensemble supérieur à la fonctionnalité de l'interface plus ancienne clone(). Il fournit également un certain nombre d'améliorations de l'API, notamment : de l'espace pour des bits de drapeaux supplémentaires ; une meilleure séparation dans l'utilisation des différents arguments ; et la capacité de spécifier la taille de la zone de pile du

fils.

Comme pour fork(2), clone3() retourne à la fois dans le parent et dans le fils. Il retourne 0 dans le processus fils et retourne le PID du fils dans le

parent.

L'argument cl_args de clone3() est une structure de la forme suivante

:

    u64 flags;        /* Masque de bits des drapeaux */

                         dans la mémoire du parent (pid_t *) */
    u64 exit_signal;  /* Signal à délivrer au parent lors de la
                         terminaison de l'enfant */
    u64 stack;        /* Pointeur vers l'octet le plus bas de la pile */
    u64 stack_size;   /* Taille de la pile */
    u64 tls;          /* Emplacement du nouveau TLS */
    u64 set_tid;      /* Pointeur vers un tableau pid_t
                         (depuis Linux 5.5) */
    u64 set_tid_size; /* Nombre d'éléments dans set_tid
                         (depuis Linux 5.5) */

                         de l'enfant (depuis Linux 5.7) */

L'argument size fourni à clone3() doit être initialisé à la taille de cette structure. (L'existence de l'argument size permet des extensions futures de la structure clone_args .

La pile du processus fils est spécifiée via cl_args.stack, qui pointe vers l'octet le plus bas de la zone de pile, et cl_args.stack_size, qui spécifie la taille de la pile en octets. Dans le cas où le drapeau CLONE_VM (voir ci-dessous) est spécifié, une pile doit être explicitement allouée et spécifiée. Sinon, ces deux champs peuvent être spécifiés comme NULL et 0, ce qui fait que le fils utilise la même zone de pile que le parent (dans son propre espace d'adressage virtuel)

.

Les champs restants de l'argument cl_args sont discu

tés ci

Le signal de fin de processus enfant

Lorsque le processus enfant se termine, un signal peut être envoyé au parent. Le signal de fin est spécifié dans l'octet de poids faible de flags (clone()) ou dans cl_args.exit_signal (clone3()). Si ce signal est autre que SIGCHLD, le processus parent doit spécifier les options __WALL ou __WCLONE lors de l'attente de l'enfant avec wait(2). Si aucun signal (c'est-à-dire zéro) n'est spécifié, le processus parent n'est pas signalé lorsque l'enfant se termine.

Le tableau set_tid

Par défaut, le noyau choisit le prochain PID séquentiel pour le nouveau processus dans chacun des espaces de noms PID où il est présent. Lors de la création d'un processus avec clone3(), le tableau set_tid (disponible depuis Linux 5.5) peut être utilisé pour sélectionner des PID spécifiques pour le processus dans certains ou dans tous les espaces de noms PID où il est présent. Si le PID du processus nouvellement créé doit être défini uniquement pour l'espace de noms PID actuel ou dans le nouvel espace de noms PID créé (si flags contient CLONE_NEWPID), alors le premier élément du tableau set_tid doit être le PID désiré et set_tid_size doit être 1.

Si le PID du processus nouvellement créé doit avoir une certaine valeur dans plusieurs espaces de noms PID, alors le tableau set_tid peut avoir plusieurs entrées. La première entrée définit le PID dans l'espace de noms PID le plus imbriqué et chacune des entrées suivantes contient le PID dans l'espace de noms PID parent correspondant. Le nombre d'espaces de noms PID dans lesquels un PID doit être défini est défini par set_tid_size, qui ne peut pas être plus grand que le nombre d'espaces de noms PID actuellement imbriqués.

Pour créer un processus avec les PID suivants dans une hiérarchie d'espaces de noms PID :

Niveau NS PID PID demandé Notes
0 31496 Espace de noms PID le plus externe
1 42
2 7 Espace de noms PID le plus interne

Définissez le tableau à :


set_tid[0] = 7;
set_tid[1] = 42;
set_tid[2] = 31496;
set_tid_size = 3;

Si seuls les PID dans les deux espaces de noms PID les plus internes doivent être spécifiés, définissez le tableau à :


set_tid[0] = 7;
set_tid[1] = 42;
set_tid_size = 2;

Le PID dans les espaces de noms PID en dehors des deux espaces de noms PID les plus internes est sélectionné de la même manière que tout autre PID.

La fonctionnalité set_tid nécessite CAP_SYS_ADMIN ou (depuis Linux 5.9) CAP_CHECKPOINT_RESTORE dans tous les espaces de noms utilisateur propriétaires des espaces de noms PID cibles.

Les appelants ne peuvent choisir un PID supérieur à 1 dans un espace de noms PID donné que si un processus init (c'est-à-dire un processus avec PID 1) existe déjà dans cet espace de noms. Sinon, l'entrée PID pour cet espace de noms PID doit être 1.

Le masque flags

clone() et clone3() permettent tous deux un masque de bits flags qui modifie leur comportement et permet à l'appelant de spécifier ce qui est partagé entre le processus appelant et le processus enfant. Ce masque de bits — l'argument flags de clone() ou le champ cl_args.flags passé à clone3() — est désigné comme le masque flags dans le reste de cette page.

Le masque flags est spécifié comme un OU bit à bit de zéro ou plusieurs des constantes listées ci-dessous. Sauf indication contraire, ces drapeaux sont disponibles (et ont le même effet) dans clone() et clone3().

CLONE_CHILD_CLEARTID (depuis Linux 2.5.49)
Efface (met à zéro) l'identifiant de thread enfant à l'emplacement pointé par child_tid (clone()) ou cl_args.child_tid (clone3()) dans la mémoire de l'enfant lorsque l'enfant se termine, et effectue un réveil sur le futex à cette adresse. L'adresse concernée peut être modifiée par l'appel système set_tid_address(2). Ceci est utilisé par les bibliothèques de threading.
CLONE_CHILD_SETTID (depuis Linux 2.5.49)
Stocke l'identifiant de thread enfant à l'emplacement pointé par child_tid (clone()) ou cl_args.child_tid (clone3()) dans la mémoire de l'enfant. L'opération de stockage s'achève avant que l'appel clone ne retourne le contrôle à l'espace utilisateur dans le processus enfant. (Notez que l'opération de stockage peut ne pas s'être achevée avant que l'appel clone ne retourne dans le processus parent, ce qui est pertinent si le drapeau CLONE_VM est également utilisé.)
CLONE_CLEAR_SIGHAND (depuis Linux 5.5)
Par défaut, les dispositions de signaux dans le thread enfant sont les mêmes que dans le parent. Si ce drapeau est spécifié, tous les signaux qui sont gérés dans le parent (et non définis sur SIG_IGN) sont réinitialisés à leurs dispositions par défaut (SIG_DFL) dans l'enfant.
Spécifier ce drapeau avec CLONE_SIGHAND n'a pas de sens et est interdit.
CLONE_DETACHED (historique)
Pendant un certain temps (durant la série de développement Linux 2.5), il y avait un drapeau CLONE_DETACHED, qui empêchait le parent de recevoir un signal lorsque l'enfant se terminait. Finalement, l'effet de ce drapeau a été intégré sous le drapeau CLONE_THREAD et au moment de la sortie de Linux 2.6.0, ce drapeau n'avait aucun effet. Depuis Linux 2.6.2, la nécessité de donner ce drapeau avec CLONE_THREAD a disparu.
Ce drapeau est toujours défini, mais il est généralement ignoré lors de l'appel à clone(). Cependant, voir la description de CLONE_PIDFD pour certaines exceptions.
CLONE_FILES (depuis Linux 2.0)
Si CLONE_FILES est défini, le processus appelant et le processus enfant partagent le même tableau de descripteurs de fichiers. Tout descripteur de fichier créé par le processus appelant ou par le processus enfant est également valide dans l'autre processus. De même, si l'un des processus ferme un descripteur de fichier, ou modifie ses drapeaux associés (en utilisant l'opération fcntl(2) F_SETFD), l'autre processus est également affecté. Si un processus partageant un tableau de descripteurs de fichiers appelle execve(2), son tableau de descripteurs de fichiers est dupliqué (non partagé).
Si CLONE_FILES n'est pas défini, le processus enfant hérite d'une copie de tous les descripteurs de fichiers ouverts dans le processus appelant au moment de l'appel clone. Les opérations ultérieures qui ouvrent ou ferment des descripteurs de fichiers, ou modifient les drapeaux des descripteurs de fichiers, effectuées par le processus appelant ou par le processus enfant n'affectent pas l'autre processus. Notez cependant que les descripteurs de fichiers dupliqués dans l'enfant font référence aux mêmes descriptions de fichiers ouverts que les descripteurs de fichiers correspondants dans le processus appelant, et partagent donc les décalages de fichiers et les drapeaux d'état de fichiers (voir open(2)).
CLONE_FS (depuis Linux 2.0)
Si CLONE_FS est défini, l'appelant et le processus enfant partagent les mêmes informations du système de fichiers. Cela inclut la racine du système de fichiers, le répertoire de travail actuel et l'umask. Tout appel à chroot(2), chdir(2), ou umask(2) effectué par le processus appelant ou par le processus enfant affecte également l'autre processus.
Si CLONE_FS n'est pas défini, le processus enfant travaille sur une copie des informations du système de fichiers du processus appelant au moment de l'appel clone. Les appels à chroot(2), chdir(2), ou umask(2) effectués ultérieurement par l'un des processus n'affectent pas l'autre processus.
CLONE_INTO_CGROUP (depuis Linux 5.7)
Par défaut, un processus enfant est placé dans le même cgroup de version 2 que son parent. Le drapeau CLONE_INTO_CGROUP permet au processus enfant d'être créé dans un cgroup de version 2 différent. (Notez que CLONE_INTO_CGROUP n'a d'effet que pour les cgroups de version 2.)
Afin de placer le processus enfant dans un cgroup différent, l'appelant spécifie CLONE_INTO_CGROUP dans cl_args.flags et passe un descripteur de fichier qui fait référence à un cgroup de version 2 dans le champ cl_args.cgroup. (Ce descripteur de fichier peut être obtenu en ouvrant un répertoire cgroup v2 en utilisant soit le drapeau O_RDONLY, soit le drapeau O_PATH.) Notez que toutes les restrictions habituelles (décrites dans cgroups(7)) concernant le placement d'un processus dans un cgroup de version 2 s'appliquent.
Parmi les cas d'utilisation possibles pour CLONE_INTO_CGROUP figurent les suivants :
•
Lancer un processus dans un cgroup différent de celui du parent permet à un gestionnaire de services de lancer directement de nouveaux services dans des cgroups dédiés. Cela élimine la gigue comptable qui serait causée si le processus enfant était d'abord créé dans le même cgroup que le parent, puis déplacé dans le cgroup cible. De plus, lancer le processus enfant directement dans un cgroup cible est significativement moins coûteux que de déplacer le processus enfant dans le cgroup cible après sa création.
•
Le drapeau CLONE_INTO_CGROUP permet également la création de processus gelés en les lançant dans un cgroup gelé. (Voir cgroups(7) pour une description du contrôleur freezer.)
•
Pour les applications multithreads (ou même les implémentations de threads qui utilisent les cgroups pour limiter les threads individuels), il est possible d'établir une disposition fixe des cgroups avant de lancer chaque thread directement dans son cgroup cible.

Si CLONE_IO est défini, alors le nouveau processus partage un contexte d'E/S avec le processus appelant. Si t
cet drapeau n'est pas défini, alors (comme avec fork(2)) le nouveau processus possède son propre contexte d'E/S.
Le contexte d'E/S est le domaine d'E/S du planificateur de disque (c'est-à-dire ce que le planificateur d'E/S utilise pour modéliser la planification des E/S d'un processus). Si des processus partagent le même contexte d'E/S, ils sont traités comme un seul par le planificateur d'E/S. En conséquence, ils se partagent le temps disque. Pour certains planificateurs d'E/S, si deux processus partagent un contexte d'E/S, ils seront autorisés à entrelacer leurs accès au disque. Si plusieurs fils d'exécution effectuent des E/S au nom du même processus (aio_read(3), par exemple), ils devraient employer CLONE_IO pour obtenir de meilleures performances

Les groupes de threads étaient une fonctionnalité ajoutée dans Linux 2.4 pour prendre en charge la notion POSIX de threads consistant en un ensemble de threads partageant un seul PID. Un signal peut être dirigé vers le processus ou vers un thread. Un signal dirigé vers le processus est ciblé sur un groupe de threads (c'est-à-dire, un TGID), et est délivré à un thread sélectionné arbitrairement parmi ceux qui ne bloquent pas le signal. E).

Les versions 2.3.4 à 2.24 incluses de la bibliothèque C GNU contenaient une fonction wrapper pour getpid(2) qui effectuait la mise en cache des PID. Cette mise en cache reposait sur le support dans le wrapper glibc pour clone(), mais des limitations dans l'implémentation signifiaient que le cache n'était pas à jour dans certaines circonstances. En particulier, si un signal était livré à l'enfant immédiatement après l'appel clone(), un appel à getpid(2) dans un gestionnaire de ce signal pouvait renvoyer le PID du processus appelant (« le parent »), si le wrapper clone n'avait pas encore eu l'occasion de mettre à jour le cache de PID dans l'enfant. (Cette discussion ignore le cas où l'enfant a été créé avec CLONE_THREAD, où getpid(2) devrait renvoyer la même valeur dans l'enfant et dans le processus qui a appelé clone(), puisque l'appelant et l'enfant sont dans le même groupe de threads. Le problème du cache obsolète ne se produit pas non plus si l'argument flags inclut CLONE_VM.) Pour obtenir la valeur exacte, il était parfois nécessaire d'utiliser du code tel que le suivant

mypid = syscall(SYS_getpid)

:
•
mmap(2) alloue un bloc de mémoire qui commence sur une limite de page et dont la taille est un multiple de la taille de page. C'est utile si nous voulons établir une page de garde (une page avec la protection PROT_NONE) à la fin de la pile avec mprotect
(2).
•
Nous pouvons spécifier le drapeau MAP_STACK pour demander une correspondance adaptée à une pile. Pour le moment, ce drapeau est sans effet sur Linux,
mais il existe et a un effet sur certains autres systè
mes, nous devrions donc l'inclure pour la portabilité.

static int              /* Fonction de départ pour l'enfant cloné */
childFunc(void *arg)
{
    struct utsname uts;
    /* Change le nom d'hôte dans l'espace de noms UTS de l'enfant.  */
    if (sethostname(arg, strlen(arg)) == -1)
        err(EXIT_FAILURE, "sethostname");
    /* Récupère et affiche le nom d'hôte.  */
    if (uname(&uts) == -1)
        err(EXIT_FAILURE, "uname");
    printf("uts.nodename in child:  %s\n", uts.nodename);
    /* Garde l'espace de noms ouvert un certain temps, en dormant.
       Cela permet certaines expérimentations--par exemple, un autre
       processus pourrait rejoindre l'espace de noms.  */
    sleep(200);
    return 0;           /* L'enfant se termine maintenant */
}
#define STACK_SIZE (1024 * 1024)    /* Taille de la pile pour l'enfant cloné */
int
main(int argc, char *argv[])
{
    char            *stack;         /* Début du tampon de pile */
    char            *stackTop;      /* Fin du tampon de pile */
    pid_t           pid;
    struct utsname  uts;
    if (argc < 2) {
        fprintf(stderr, "Usage: %s <child-hostname>\n", argv[0]);
        exit(EXIT_SUCCESS);
    }
    /* Alloue la mémoire à utiliser pour la pile de l'enfant.  */
    stack = mmap(NULL, STACK_SIZE, PROT_READ | PROT_WRITE,
                 MAP_PRIVATE | MAP_ANONYMOUS | MAP_STACK, -1, 0);
    if (stack == MAP_FAILED)
        err(EXIT_FAILURE, "mmap");
    stackTop = stack + STACK_SIZE;  /* Supposer que la pile croît vers le bas */
    /* Crée un enfant qui a son propre espace de noms UTS ;
       l'enfant commence l'exécution dans childFunc().  */
    pid = clone(childFunc, stackTop, CLONE_NEWUTS | SIGCHLD, argv[1]);
    if (pid == -1)
        err(EXIT_FAILURE, "clone");
    if (munmap(stack, STACK_SIZE))
        err(EXIT_FAILURE, "munmap");
    printf("clone() returned %jd\n", (intmax_t) pid);
    /* Le parent continue ici */
    sleep(1;           /* Donne à l'enfant le temps de changer son nom d'hôte */
    /* Affiche le nom d'hôte dans l'espace de noms UTS du parent.  Cela sera
       différent du nom d'hôte dans l'espace de noms UTS de l'enfant.  */
    if (uname(&uts) == -1)
        err(EXIT_FAILURE, "uname");
    printf("uts.nodename in parent: %s\n", uts.nodename);
    if (waitpid(pid, NULL, 0) == -1)    /* Attend l'enfant */
        err(EXIT_FAILURE, "waitpid");
    printf("child has terminated\n");
    exit(EXIT_SUCCESS)
;
}
