DESCRIPTIO

N

Ces appels système créent un nouveau processus (« fils »), d'une manière similaire à fork(

2).

Contrairement à fork(2), ces appels système offrent un contrôle plus précis sur les parties du contexte d'exécution qui sont partagées entre le processus appelant et le processus fils. Par exemple, à l'aide de ces appels système, l'appelant peut contrôler si les deux processus partagent ou non l'espace d'adressage virtuel, la table des descripteurs de fichiers et la table des gestionnaires de signaux. Ces appels système permettent également de placer le nouveau processus fils dans des namespaces(7) s

éparés.

Notez que dans cette page manuelle, « processus appelant » correspond normalement au « processus parent ». Mais voir les descriptions de CLONE_PARENT et CLONE_THREAD ci-

dessous.

La fonction wrapper

clone()

Lorsque le processus fils est créé avec la fonction wrapper clone(), il commence son exécution en appelant la fonction pointée par l'argument fn. (Cela diffère de fork(2), où l'exécution continue dans le fils à partir du point de l'appel fork(2).) L'argument arg est passé comme argument de la fonction fn

.

Lorsque la fonction fn(arg) retourne, le processus fils se termine. L'entier retourné par fn est le code de sortie du processus fils. Le processus fils peut également se terminer explicitement en appelant exit(2) ou après avoir reçu un signal

fatal.

L'argument stack spécifie l'emplacement de la pile utilisée par le processus fils. Puisque le processus fils et le processus appelant peuvent partager la mémoire, il n'est pas possible pour le processus fils de s'exécuter sur la même pile que le processus appelant. Le processus appelant doit donc mettre en place un espace mémoire pour la pile du fils et passer un pointeur vers cet espace à clone(). Les piles croissent vers le bas sur tous les processeurs qui exécutent Linux (sauf les processeurs HP PA), donc stack pointe généralement vers l'adresse la plus haute de l'espace mémoire mis en place pour la pile du fils. Notez que clone() ne fournit aucun moyen par lequel l'appelant peut informer le noyau de la taille de la zone de

pile.

Les arguments restants de clone() sont dis

cutés ci-
dessous.

clone3(

)

L'appel système clone3() fournit un ensemble supérieur de la fonctionnalité de l'interface plus ancienne clone(). Il fournit également un certain nombre d'améliorations de l'API, notamment : de l'espace pour des bits de drapeaux supplémentaires ; une meilleure séparation dans l'utilisation des différents arguments ; et la capacité à spécifier la taille de la zone de pile du

fils.

Comme pour fork(2), clone3() retourne à la fois dans le parent et dans le fils. Il retourne 0 dans le processus fils et retourne le PID du fils dans le

parent.

Sinon, ces deux champs peuvent être spécifiés comme NULL et 0, ce qui fait que le fils utilise la même zone de pile que le parent (dans son propre espace d'adressage virtuel)

Les groupes de threads étaient une fonctionnalité ajoutée dans Linux 2.4 pour prendre en charge la notion POSIX de threads consistant en un ensemble de threads partageant un PID unique. En interne, ce PID partagé est le soi-disant identifiant de groupe de threads (TGID) du groupe de threads. Depuis Linux 2.4, les appels à getpid(2) retournent le TGID de

Les threads au sein d'un groupe peuvent être distingués par leurs identifiants de threads (TID) uniques (à l'échelle du système). Le TID d'un nouveau thread est disponible en tant que résultat de fonction retourné à l'appelant, et un thread peut obtenir son propre TID en utilisant gettid(
2).
Lorsqu'un appel clone est effectué sans spécifier CLONE_THREAD, alors le thread résultant est placé dans un nouveau groupe de threads dont le TGID est le même que le TID du thread. Ce thread est le leader du nouveau groupe de
threads.
Un nouveau thread créé avec CLONE_THREAD a le même processus parent que le processus qui a fait l'appel clone (c'est-à-dire, comme CLONE_PARENT), de sorte que les appels à getppid(2) retournent la même valeur pour tous les threads d'un groupe de threads. Lorsqu'un thread CLONE_THREAD se termine, le thread qui l'a créé ne reçoit pas de signal SIGCHLD (ou autre signal de terminaison) ; et le statut d'un tel thread ne peut pas non plus être obtenu en utilisant wait(2). (Le thread est dit détach
é.)
Après que tous les threads d'un groupe de threads se sont terminés, le processus parent du groupe de threads reçoit un signal SIGCHLD (ou autre signal de terminaison)
.
Si l'un des threads d'un groupe de threads effectue un execve(2), alors tous les threads autres que le leader du groupe de threads sont terminés, et le nouveau programme est exécuté dans le leader du groupe de
threads.
Si l'un des threads d'un groupe de threads crée un enfant en utilisant fork(2), alors n'importe quel thread du groupe peut attendre (wait(2)) cet
enfant.
Depuis Linux 2.5.35, le masque flags doit également inclure CLONE_SIGHAND si CLONE_THREAD est spécifié (et notez que, depuis Linux 2.6.0, CLONE_SIGHAND requiert également CLONE_VM pour être inclus)
.
Les dispositions et actions des signaux s'appliquent à l'ensemble du processus : si un signal non géré est délivré à un thread, alors il affectera (terminera, arrêtera, reprendra, sera ignoré par) tous les membres du groupe de
threads.
Chaque thread a son propre masque de signaux, tel que défini par sigprocmas
k(2).
Un signal peut être dirigé vers le processus ou vers un thread. Un signal dirigé vers le processus est ciblé sur un groupe de threads (c'est-à-dire, un TGID), et est délivré à un thread choisi arbitrairement parmi ceux qui ne bloquent pas le signal. Un signal peut être dirigé vers le processus parce qu'il a été généré par le noyau pour des raisons autres qu'une exception matérielle, ou parce qu'il a été envoyé en utilisant kill(2) ou sigqueue(3). Un signal dirigé vers un thread est ciblé sur (c'est-à-dire, délivré à) un thread spécifique. Un signal peut être dirigé vers un thread parce qu'il a été envoyé en utilisant tgkill(2) ou pthread_sigqueue(3), ou parce que le thread a exécuté une instruction de langage machine qui a déclenché une exception matérielle (par exemple, un accès mémoire invalide déclenchant SIGSEGV ou une exception en virgule flottante déclenchant SIGFP
E).
Un appel à sigpending(2) retourne un ensemble de signaux qui est l'union des signaux dirigés vers le processus en attente et des signaux en attente pour le thread
appelant.
Si un signal dirigé vers le processus est délivré à un groupe de threads, et que le groupe de threads a installé un gestionnaire pour le signal, alors le gestionnaire est invoqué dans exactement un membre du groupe de threads, choisi arbitrairement, qui n'a pas bloqué le signal. Si plusieurs threads dans un groupe attendent d'accepter le même signal en utilisant sigwaitinfo(2), le noyau choisira arbitraire
ment l'un de ces threads
pour recevoir le signal.

C Différences bibliothèque

C/noyau

L'appel système brut clone() correspond plus étroitement à fork(2) en ce que l'exécution dans l'enfant continue à partir du point de l'appel. En tant que tel, les arguments fn et arg de la fonction wrapper clone() sont

omis.

Contrairement à l'emballage glibc, l'appel système brut clone() accepte NULL comme argument stack (et clone3() permet également cl_args.stack d'être NULL). Dans ce cas, l'enfant utilise une copie de la pile du parent. (La sémantique copy-on-write garantit que l'enfant obtient des copies séparées des pages de pile lorsque l'un des processus modifie la pile.) Dans ce cas, pour un fonctionnement correct, l'option CLONE_VM ne devrait pas être spécifiée. (Si l'enfant partage la mémoire du parent en raison de l'utilisation du drapeau CLONE_VM, alors aucune duplication copy-on-write ne se produit et le chaos est probable.

)

L'ordre des arguments diffère également dans l'appel système brut, et il y a des variations dans les arguments selon les architectures, comme détaillé dans les paragraphes

suivants.

L'interface d'appel système brut sur x86-64 et certaines autres architectures (y compris sh, tile et alpha) est

: 


long clone(unsigned long flags, void *stack,
           int *parent_tid, int *child_tid,
           unsigned long tls)
;

Sur x86-32 et plusieurs autres architectures courantes (y compris score, ARM, ARM 64, PA-RISC, arc, Power PC, xtensa et MIPS), l'ordre des deux derniers arguments est inversé

: 


long clone(unsigned long flags, void *stack,
          int *parent_tid, unsigned long tls,
          int *child_tid)
;

Sur les architectures cris et s390, l'ordre des deux premiers arguments est inversé

: 


long clone(void *stack, unsigned long flags,
           int *parent_tid, int *child_tid,
           unsigned long tls)
;

Sur l'architecture microblaze, un argument supplémentaire est fourni

: 


long clone(unsigned long flags, void *stack,
           int stack_size,         /* Taille de la pile */
           int *parent_tid, int *child_tid,
           unsigned long tls);

blackfin, m68k et sparc

Les conventions de passage d'arguments sur les architectures blackfin, m68k et sparc sont différentes de celles décrites ci-dessus. Pour plus de détails, consultez le code source du noyau (et de glibc).

Linux 2.4 et antérieur

Dans la série Linux 2.4.x, CLONE_THREAD ne fait généralement pas du parent du nouveau thread le même que le parent du processus appelant. Cependant, de Linux 2.4.7 à Linux 2.4.18, le drapeau CLONE_THREAD impliquait le drapeau CLONE_PARENT (comme dans Linux 2.6.0 et versions ultérieures).

ia64

Sur ia64, une interface différente est utilisée :


int __clone2(typeof(int (void *)) *fn,
             void *stack_base, size_t stack_size,
             int flags, void *arg, ...
          /* pid_t *parent_tid, struct user_desc *tls,
             pid_t *child_tid */ );

Le prototype ci-dessus est pour la fonction wrapper de glibc ; pour l'appel système lui-même, le prototype peut être décrit comme suit (il est identique au prototype clone() sur microblaze) :


long clone2(unsigned long flags, void *stack_base,
            int stack_size,         /* Taille de la pile */
            int *parent_tid, int *child_tid,
            unsigned long tls);

__clone2() fonctionne de la même manière que clone(), sauf que stack_base pointe vers l'adresse la plus basse de la zone de pile de l'enfant, et stack_size spécifie la taille de la pile pointée par stack_base.

NOTES

Une utilisation de ces appels système est de mettre en œuvre des threads : plusieurs flux de contrôle dans un programme qui s'exécutent concurremment dans un espace d'adressage partagé.

L'appel système kcmp(2) peut être utilisé pour tester si deux processus partagent diverses ressources telles qu'une table de descripteurs de fichiers, des opérations d'annulation de sémaphores System V, ou un espace d'adressage virtuel.

Les gestionnaires enregistrés à l'aide de pthread_atfork(3) ne sont pas exécutés pendant un appel clone.

BOGUES

Les versions de la bibliothèque C GNU 2.3.4 jusqu'à 2.24 incluse contiennent une fonction wrapper pour getpid(2) qui effectuait une mise en cache des PID. Cette mise en cache reposait sur le support dans le wrapper glibc pour clone(), mais des limitations dans l'implémentation signifiaient que le cache n'était pas à jour dans certaines circonstances. En particulier, si un signal était délivré à l'enfant immédiatement après l'appel clone(), alors un appel à getpid(2) dans un gestionnaire du signal pouvait retourner le PID du processus appelant ("le parent"), si le wrapper clone n'avait pas encore eu la possibilité de mettre à jour le cache PID dans l'enfant. (Cette discussion ignore le cas où l'enfant a été créé en utilisant CLONE_THREAD, lorsque getpid(2) *devrait* retourner la même valeur dans l'enfant et dans le processus qui a appelé clone(), puisque l'appelant et l'enfant sont dans le même groupe de threads. Le problème du cache obsolète ne se produit pas non plus si l'argument flags inclut CLONE_VM.) Pour obtenir la vérité, il était parfois nécessaire d'utiliser un code tel que le suivant :


#include <syscall.h>
pid_t mypid;
mypid = syscall(SYS_getpid);

En raison du problème de cache obsolète, ainsi que d'autres problèmes mentionnés dans getpid(2), la fonctionnalité de mise en cache des PID a été supprimée dans glibc 2.25.

EXEMPLES

Le programme suivant démontre l'utilisation de clone() pour créer un processus enfant qui s'exécute dans un espace de noms UTS distinct. L'enfant modifie le nom d'hôte dans son espace de noms UTS. Le parent et l'enfant affichent ensuite le nom d'hôte du système, ce qui permet de constater que le nom d'hôte diffère dans les espaces de noms UTS du parent et de l'enfant. Pour un exemple d'utilisation de ce programme, voir setns(2).

Dans le programme exemple, nous allouons la mémoire qui sera utilisée pour la pile de l'enfant à l'aide de mmap(2) plutôt que de malloc(3) pour les raisons suivantes :

•
mmap(2) alloue un bloc de mémoire qui commence à la limite d'une page et est un multiple de la taille de page. Ceci est utile si nous voulons établir une page de garde (une page avec la protection PROT_NONE) à la fin de la pile en utilisant mprotect(2).
•
Nous pouvons spécifier le drapeau MAP_STACK pour demander un mapping adapté à une pile. Pour le moment, ce drapeau est un no-op sous Linux, mais il existe et a un effet sur certains autres systèmes, nous devrions donc l'inclure pour la portabilité.

Source du programme

#define _GNU_SOURCE
#include <err.h>
#include <sched.h>
#include <signal.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/types.h>
#include <sys/utsname.h>
#include <sys/wait.h>
#include <unistd.h>
static int              /* Fonction de démarrage pour l'enfant cloné */
childFunc(void *arg)
{
    struct utsname uts;
    /* Changer le nom d'hôte dans l'espace de noms UTS de l'enfant.  */
    if (sethostname(arg, strlen(arg)) == -1)
        err(EXIT_FAILURE, "sethostname");
    /* Récupérer et afficher le nom d'hôte.  */
    if (uname(&uts) == -1)
        err(EXIT_FAILURE, "uname");
    printf("uts.nodename dans l'enfant : %s\n", uts.nodename);
    /* Garder l'espace de noms ouvert pendant un moment, en dormant.
       Ceci permet quelques expérimentations--par exemple, un autre
       processus pourrait rejoindre l'espace de noms.  */
    sleep(200);
    return 0;           /* L'enfant se termine maintenant */
}
#define STACK_SIZE (1024 * 1024)    /* Taille de pile pour l'enfant cloné */
int
main(int argc, char *argv[])
{
    char            *stack;         /* Début du tampon de pile */
    char            *stackTop;      /* Fin du tampon de pile */
    pid_t           pid;
    struct utsname  uts;
    if (argc < 2) {
        fprintf(stderr, "Usage: %s <nom-hote-enfant>\n", argv[0]);
        exit(EXIT_SUCCESS);
    }
    /* Allouer de la mémoire à utiliser pour la pile de l'enfant.  */
    stack = mmap(NULL, STACK_SIZE, PROT_READ | PROT_WRITE,
                 MAP_PRIVATE | MAP_ANONYMOUS | MAP_STACK, -1, 0);
    if (stack == MAP_FAILED)
        err(EXIT_FAILURE, "mmap");
    stackTop = stack + STACK_SIZE;  /* Supposer que la pile grandit vers le bas */
    /* Créer un enfant qui a son propre espace de noms UTS ;
       l'enfant commence son exécution dans childFunc().  */
    pid = clone(childFunc, stackTop, CLONE_NEWUTS | SIGCHLD, argv[1]);
    if (pid == -1)
        err(EXIT_FAILURE, "clone");
    if (munmap(stack, STACK_SIZE))
        err(EXIT_FAILURE, "munmap");
    printf("clone() a retourné %jd\n", (intmax_t) pid);
    /* Le parent continue ici */
    sleep(1);           /* Donner à l'enfant le temps de changer son nom d'hôte */
    /* Afficher le nom d'hôte dans l'espace de noms UTS du parent.  Ceci sera
       différent du nom d'hôte dans l'espace de noms UTS de l'enfant.  */
    if (uname(&uts) == -1)
        err(EXIT_FAILURE, "uname");
    printf("uts.nodename dans le parent : %s\n", uts.nodename);
    if (waitpid(pid, NULL, 0) == -1)    /* Attendre l'enfant */
        err(EXIT_FAILURE, "waitpid");
    printf("l'enfant s'est terminé\n");
    exit(EXIT_SUCCESS);
}

NOM

clone3 - création d'un nouveau processus avec des options de contrôle plus fines

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <sys/wait.h>
#include <linux/sched.h>

pid_t clone3(struct clone_args *args, size_t size);

DESCRIPTION

La fonction clone3() est une alternative plus récente et plus flexible à clone(2) pour la création de nouveaux processus (threads). Elle permet un contrôle plus fin sur les ressources partagées entre le processus appelant et le nouveau processus.

La structure clone_args est définie comme suit :

struct clone_args {
    __u64 flags;             // Indicateurs pour le clonage
    __u64 parent_tid;        // Indicateur pour le tid parent
    __u64 child_tid;         // Indicateur pour le tid enfant
    __u64 exit_signal;       // Signal à envoyer au parent lors de la sortie
    __u64 stack;             // Pointeur vers la pile du nouveau processus
    __u64 stack_size;        // Taille de la pile
    __u64 tls;               // Pointeur vers le descripteur de segment TLS
    __u64 setfields;         // Champs définis dans clone_args
    __u64 setval;            // Valeur pour les champs définis
    __u64 __unused3;
    __u64 __unused4;
};

Les drapeaux (flags) spécifient les ressources qui seront partagées ou isolées entre le processus parent et le nouveau processus. Ils incluent, entre autres :

  • CLONE_VM : Partager l'espace d'adressage mémoire.
  • CLONE_FS : Partager le système de fichiers (répertoire courant, etc.).
  • CLONE_FILES : Partager les descripteurs de fichiers.
  • CLONE_SIGHAND : Partager les gestionnaires de signaux.
  • CLONE_THREAD : Créer un thread dans le même groupe de threads.
  • CLONE_NEWNS : Créer un nouveau namespace de montage.
  • CLONE_NEWUTS : Créer un nouveau namespace UTS (nom d'hôte).
  • CLONE_NEWIPC : Créer un nouveau namespace IPC.
  • CLONE_NEWPID : Créer un nouveau namespace PID.
  • CLONE_NEWNET : Créer un nouveau namespace réseau.
  • CLONE_NEWUSER : Créer un nouveau namespace utilisateur.

Le champ stack pointe vers la pile du nouveau processus. Si CLONE_VM est spécifié, le processus enfant doit fournir sa propre pile. Sinon, le processus enfant partage la pile du processus parent.

Le champ exit_signal spécifie le signal à envoyer au processus parent lorsque le processus enfant se termine. S'il est défini à 0, aucun signal n'est envoyé.

Les champs parent_tid et child_tid sont utilisés pour la notification du tid (thread identifier) du parent et de l'enfant. Ils sont rarement utilisés directement.

Le champ tls est utilisé pour configurer le segment TLS (Thread-Local Storage).

Le champ setfields et setval permettent de définir des valeurs spécifiques pour certains champs de la structure.

La fonction clone3() crée un nouveau processus qui est une copie du processus appelant, sauf indication contraire par les drapeaux spécifiés dans args->flags. Le nouveau processus hérite des informations de contexte spécifiées par les drapeaux. Le processus enfant commence son exécution à partir de l'adresse spécifiée par args->stack (qui pointe généralement vers le début de la pile, où le code de retour de la fonction sera stocké).

VALEUR DE RETOUR

En cas de succès, clone3() retourne le pid (process identifier) du nouveau processus au processus parent, et 0 au nouveau processus enfant.

En cas d'échec, clone3() retourne -1 et définit errno pour indiquer l'erreur.

ERREURS

Les erreurs possibles sont nombreuses et dépendent des drapeaux utilisés. Certaines erreurs courantes incluent :

  • EINVAL : args est NULL, size est incorrect, ou les drapeaux sont invalides.
  • ENOMEM : Pas assez de mémoire pour créer le nouveau processus.
  • EPERM : Privilèges insuffisants pour certaines opérations (par exemple, la création de nouveaux namespaces sans les permissions nécessaires).
  • EFAULT : Un pointeur dans args est invalide.

VERSIONS

La fonction clone3() a été introduite dans le noyau Linux version 5.3.

NORMES

Aucune.

HISTORIQUE

La fonction clone3() a été introduite pour remplacer et améliorer la fonction clone(2), offrant un contrôle plus fin sur le partage des ressources et l'isolation des namespaces.

NOTES

L'utilisation de clone3() est généralement réservée aux programmes système et aux conteneurs. L'utilisation incorrecte peut entraîner des comportements inattendus ou des problèmes de sécurité.

Il est important de fournir une pile valide pour le nouveau processus, surtout si CLONE_VM est utilisé. La pile doit être suffisamment grande pour contenir les données nécessaires à l'exécution du code enfant.

La gestion des signaux et des erreurs doit être soigneusement considérée lors de l'utilisation de cette fonction.

BOGUES

Aucun bogues connus.

EXEMPLES

Un exemple simple de création d'un thread léger utilisant clone3() :

#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <sched.h>
#include <sys/wait.h>
#include <unistd.h>

#define STACK_SIZE (1024 * 1024)

int thread_func(void* arg) {
    printf("Je suis le thread enfant, PID: %ld\n", (long)getpid());
    return 0;
}

int main() {
    char *stack;
    char *stack_top;
    struct clone_args args = {0};

    stack = malloc(STACK_SIZE);
    if (stack == NULL) {
        perror("malloc");
        exit(EXIT_FAILURE);
    }
    stack_top = stack + STACK_SIZE; // La pile grandit vers les adresses basses

    args.flags = CLONE_VM | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD;
    args.stack = (unsigned long)stack_top;
    args.exit_signal = SIGCHLD; // Envoyer SIGCHLD au parent à la sortie

    pid_t pid = clone3(&args, sizeof(args));

    if (pid == -1) {
        perror("clone3");
        free(stack);
        exit(EXIT_FAILURE);
    }

    if (pid == 0) {
        // Code exécuté par le thread enfant
        thread_func(NULL);
        exit(EXIT_SUCCESS);
    } else {
        // Code exécuté par le thread parent
        printf("Je suis le thread parent, PID: %ld, mon enfant est : %d\n", (long)getpid(), pid);
        waitpid(pid, NULL, 0); // Attendre que l'enfant se termine
        printf("Le thread enfant s'est terminé.\n");
        free(stack);
    }

    return 0;
}
