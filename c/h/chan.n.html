Cette commande fournit plusieurs opérations pour lire depuis, écrire vers et autrement manipuler des canaux ouverts (tels que ceux créés avec les commandes open et socket, ou les canaux nommés par défaut stdin, stdout ou stderr qui correspondent respectivement aux flux d'entrée, de sortie et d'erreur standard du processus). Option indique quoi faire avec le canal ; toute abréviation unique de option est acceptable. Les options valides sont

:
chan blocked channel
Id
Cette commande teste si la dernière opération d'entrée sur le canal appelé channelId a échoué parce qu'elle aurait autrement causé le blocage du processus, et renvoie 1 si c'était le cas. Elle renvoie 0 sinon. Notez que cela ne renvoie 1 que lorsque le canal a été configuré pour être non bloquant ; tous les canaux Tcl ont le mode bloquant activé par
défaut.
chan close channelId ?directio
n?
Ferme et détruit le canal appelé channelId. Notez que cela supprime tous les file-events enregistrés sur le canal. Si l'argument direction (qui doit être read ou write ou toute abréviation unique de ceux-ci) est présent, le canal ne sera que semi-fermé, de sorte qu'il peut passer d'lecture-écriture à écriture seule ou lecture seule respectivement. Si un canal en lecture seule est fermé pour la lecture, c'est comme si le canal était entièrement fermé, et respectivement similaire pour les canaux en écriture seule. Sans l'argument direction, le canal est fermé pour la lecture et l'écriture (mais seulement si ces directions sont actuellement ouvertes
). C'est une erreur de fermer un canal en lecture seule pou
r l'écriture, ou un canal en écriture seule pour la lecture.

Dans le cadre de la fermeture du canal, toute la sortie tamponnée est vidée vers le périphérique de sortie du canal (seulement si le canal cesse d'être inscriptible), toute l'entrée tamponnée est ignorée (seulement si le canal cesse d'être lisible), la ressource système sous-jacente est fermée et channelId devient indisponible pour une utilisation future (tous deux seulement si le canal est entièrement fermé)

.

Si le canal est bloquant et que le canal cesse d'être inscriptible, la commande ne retourne pas tant que toute la sortie n'a pas été vidée. Si le canal est non bloquant et qu'il y a de la sortie non vidée, le canal reste ouvert et la commande retourne immédiatement ; la sortie sera vidée en arrière-plan et le canal sera fermé lorsque tout le vidage sera

terminé.

Si channelId est un canal bloquant pour un pipeline de commandes, alors chan close attend que les processus enfants se

terminent.

Si le canal est partagé entre interpréteurs, alors chan close rend channelId indisponible dans l'interpréteur appelant mais n'a aucun autre effet tant que tous les interpréteurs partageant n'ont pas fermé le canal. Lorsque le dernier interpréteur dans lequel le canal est enregistré invoque chan close (ou close), les actions de nettoyage décrites ci-dessus se produisent. Avec la fermeture semi-fermée, la semi-fermeture du canal ne s'applique qu'à la vue du canal de l'interpréteur actuel jusqu'à ce que tous les canaux l'aient fermé dans cette direction (ou complètement). Voir la commande interp pour une description du partage de

canaux.

Les canaux sont automatiquement entièrement fermés lorsqu'un interpréteur est détruit et lorsque le processus se termine. Les canaux sont basculés en mode bloquant, pour s'assurer que toute la sortie est correctement vidée avant que le processus ne se

termine.

La commande retourne une chaîne vide, et peut générer une erreur si une erreur se produit lors du vidage de la sortie. Si une commande dans un pipeline de commandes créé avec open retourne une erreur, chan close génère une erreur (similaire à la commande exec)

.

Notez que les fermetures semi-fermées des sockets et des pipelines de commandes peuvent avoir des effe

ts secondaires importants car elles résultent d'un shutdown() ou close() de la ressource système sous
-jacente, ce qui peut changer la façon dont d'autres processus ou systèmes répondent au programme Tcl.

L'option -blocking détermine si les opérations d'E/S sur le canal peuvent causer le blocage indéfini du processus. La valeur de l'option doit être une valeur booléenne appropriée. Les canaux sont normalement en mode bloquant ; si un canal est placé en mode non bloquant, cela affectera le fonctionnement des commandes chan gets, chan read, chan puts, chan flush, et chan close ; voir la documentation de ces commandes pour les détails. Pour que le mode non bloquant fonctionne correctement, l'application doit utiliser la boucle d'événements Tcl (par exemple en appelant Tcl_DoOneEvent ou en invoquant la commande vwait)
.
-buffering newVal

Si newValue est full, alors le système d'E/S tamponnera la sortie jusqu'à ce que son tampon interne soit plein ou jusqu'à ce que la commande chan flush soit invoquée. Si newValue est line, alors le système d'E/S videra automatiquement la sortie du canal chaque fois qu'un caractère de nouvelle ligne est produit. Si newValue est none, le système d'E/S videra automatiquement après chaque opération d'écriture. La valeur par défaut pour -buffering est full sauf pour les canaux qui se connectent à des périphériques de type terminal ; pour ces canaux, le réglage initial est line. De plus, stdin et stdout sont initialement définis à line, et stderr est défini à non

-encoding na

Cette option est utilisée pour spécifier l'encodage du canal comme l'un des encodages nommés retournés par encoding names ou la valeur spéciale binary, de sorte que les données puissent être converties vers et depuis Unicode pour une utilisation dans Tcl. Par exemple, pour que Tcl lise des caractères d'un fichier japonais en shiftjis et traite et affiche correctement le contenu, l'encodage serait défini à shiftjis. Par la suite, lors de la lecture depuis le canal, les octets du fichier japonais seraient convertis en Unicode au fur et à mesure de leur lecture. L'écri
ture est également prise en charge - lorsque des chaînes Tcl sont écrites sur le
canal, elles seront automatiquement converties vers l'encodage spécifié en sortie.

Si un fichier contient des données purement binaires (par exemple, une image JPEG), l'encodage du canal devrait être configuré à binary. Tcl n'attribuera alors aucune interprétation aux données du fichier et lira ou écrira simplement des octets bruts. La commande binary de Tcl peut être utilisée pour manipuler ces données orientées octets. Il est généralement préférable de définir l'option -translation à binary lorsque vous souhaitez transférer des données binaires, car cela désactive également les autres interprétations automatiques des octets dans le

flux.

chan copy inputChan outputChan ?-size size? ?-command callbac
k?
Copie les données du canal inputChan, qui doit avoir été ouvert pour la lecture, vers le canal outputChan, qui doit avoir été ouvert pour l'écriture. La commande chan copy exploite la mise en tampon dans le système d'E/S Tcl pour éviter des copies supplémentaires et pour éviter de mettre en ta
mpon trop de données en mémoire principale lors de la copie de fichi
ers volumineux vers des destinations lentes comme les sockets réseau.

La commande chan copy transfère les données depuis inputChan jusqu'à la fin du fichier ou jusqu'à ce que size octets ou caractères aient été transférés ; size est en octets si les deux canaux utilisent le même encodage, et en caractères sinon. Si aucun argument -size n'est donné, la copie se poursuit jusqu'à la fin du fichier. Toutes les données lues depuis inputChan sont copiées vers outputChan. Sans l'option -command, chan copy se bloque jusqu'à ce que la copie soit terminée et renvoie le nombre d'octets ou de caractères (en utilisant les mêmes règles que pour l'option -size) écrits sur outputChan

.

L'argument -command fait fonctionner chan copy en arrière-plan. Dans ce cas, il renvoie immédiatement et le callback est invoqué plus tard lorsque la copie est terminée. Le callback est appelé avec un ou deux arguments supplémentaires qui indiquent combien d'octets ont été écrits sur outputChan. Si une erreur s'est produite lors de la copie en arrière-plan, le deuxième argument est la chaîne d'erreur associée à l'erreur. Avec une copie en arrière-plan, il n'est pas nécessaire de mettre inputChan ou outputChan en mode non bloquant ; la commande chan copy s'en charge automatiquement. Cependant, il est nécessaire d'entrer dans la boucle d'événements en utilisant la commande vwait ou en utilisant

Tk.

Vous n'êtes pas autorisé à effectuer d'autres opérations d'E/S avec inputChan ou outputChan pendant une copie en arrière-plan chan copy. Si inputChan ou outputChan se ferme pendant que la copie est en cours, la copie en cours est arrêtée et le callback de commande n'est pas appelé. Si inputChan est fermé, toutes les données déjà mises en file d'attente pour outputChan sont

écrites.

Notez que inputChan peut devenir lisible pendant une copie en arrière-plan. Vous devriez désactiver tous les gestionnaires chan event ou fileevent pendant une copie en arrière-plan afin que ces gestionnaires n'interfèrent pas avec la copie. Toute tentative d'E/S par un gestionnaire chan event ou fileevent obtiendra une erreur « channel busy »

.

Chan copy traduit les séquences de fin de ligne dans inputChan et outputChan selon l'option -translation pour ces canaux (voir chan configure ci-dessus). Les traductions signifient que le nombre d'octets lus depuis inputChan peut être différent du nombre d'octets écrits sur outputChan. Seul le nombre d'octets écrits sur outputChan est rapporté, soit comme la valeur de retour d'un chan copy synchrone, soit comme l'argument du callback pour un chan copy asyn

chrone.

Chan copy respecte les encodages et les traductions de caractères configurés pour les canaux. Cela signifie que les caractères entrants sont convertis d'abord en UTF-8 interne, puis dans l'encodage du canal sur lequel chan copy écrit (voir chan configure ci-dessus pour plus de détails sur les options -encoding et -translation). Aucune conversion n'est effectuée si les deux canaux sont définis sur l'encodage binary et ont des traductions correspondantes. Si seul le canal de sortie est défini sur l'encodage binary, le système écrira la représentation UTF-8 interne des caractères entrants. Si seul le canal d'entrée est défini sur l'encodage binary, le système supposera que les octets entrants sont des caractères UTF-8 valides et les convertira selon l'encodage

de sortie. Le comportement du système pour les octets qui ne s
ont pas des caractères UTF-8 valides est indéfini dans ce cas.
chan create mode
cmdPrefix
Cette sous-commande crée un nouveau canal au niveau du script en utilisant le préfixe de commande cmdPrefix comme gestionnaire. Un tel canal est appelé un canal réfléchi. Le préfixe de commande spécifié, cmdPrefix, doit être une liste non vide et doit fournir l'API décrite dans la page de manuel refchan. Le descripteur du nouveau canal est renvoyé comme résultat de la commande chan create, et le canal est ouvert. Utilisez soit close soit chan close pour su
pprimer
le canal.

L'argument mode spécifie si le nouveau canal est ouvert pour la lecture, l'écriture, ou les deux. Il doit être une liste contenant l'une des chaînes «read » ou «write ». La liste doit avoir au moins un élément, car un canal sur lequel on ne peut ni écrire ni lire n'a pas de sens. La commande gestionnaire pour le nouveau canal doit prendre en charge le mode choisi, sinon une erreur est

levée.

Le préfixe de commande est exécuté dans l'espace de noms global, au sommet de la pile d'appels, après l'ajout des arguments comme décrit dans la page refchanb> de la page de manuel. La résolution de la commande se fait au moment de l'appel. Renommer la commande, ou la détruire signifie que le prochain appel d'une méthode de traitement peut échouer, ce qui fera échouer également la commande de canal qui invoque le traitement. Selon la sous-commande invoquée, le message d'erreur peut ne pas être capable d'expliquer la raison de cet

échec.

Chaque canal créé avec cette sous-commande sait dans quel interpréteur il a été créé, et n'exécute sa commande de traitement que dans cet interpréteur, même si le canal a été partagé avec et/ou déplacé vers un autre interpréteur. Chaque canal réfléchi sait aussi dans quel thread il a été créé, et n'exécute sa commande de traitement que dans ce thread, même si le canal a été déplacé vers un autre thread. À cette fin, toutes les invocations du traitement sont transférées au thread original en lui postant des événements spéciaux. Cela signifie que le thread original (c'est-à-dire le thread qui a exécuté la commande chan create) doit avoir une boucle d'événements active, c'est-à-dire qu'il doit être capable de traiter de tels événements. Sinon, le thread qui les envoie va bloquer indéfiniment. Un interblocage peut

survenir.

Notez que cela permet la création d'un canal dont les deux extrémités vivent dans deux threads différents, fournissant un pont orienté flux entre ces threads. En d'autres termes, nous pouvons fournir un moyen de communication en flux régulier entre les threads au lieu de devoir envoyer des

commandes.

Lorsqu'un thread ou un interpréteur est supprimé, tous les canaux créés avec cette sous-commande et utilisant ce thread/interpréteur comme base de calcul sont également supprimés, dans tous les interpréteurs avec lesquels ils ont été partagés ou vers lesquels ils ont été déplacés, et dans le thread vers lequel ils ont été transférés. Bien que cela retire le tapis sous les autres threads et/ou interpréteurs, cela ne peut être évité. Tenter d'utiliser un tel canal provoquera la génération d'une erreur standard concernant des identifiants de canal

inconnus.

Cette sous-commande est sûre et rendue accessible aux interpréteurs sûrs. Bien qu'elle organise l'exécution de code Tcl ar

bitraire, le système s'assure également que le c
ode est toujours exécuté dans l'interpréteur sûr.

Arrange pour que le script Tcl script soit installé comme un gestionnaire d'événements fichier à appeler chaque fois que le canal appelé channelId entre dans l'état décrit par event (qui doit être soit readable (lisible) ou writable (inscriptible)) ; un seul tel gestionnaire peut être installé par événement par canal à la fois. Si script est la chaîne vide, le gestionnaire actuel est supprimé (cela se produit aussi si le canal est fermé ou l'interpréteur supprimé). Si script est omis, le script actuellement installé est renvoyé (ou une chaîne vide si un tel gestionnaire n'est pas installé). Le rappel n'est effectué que si la boucle d'événements est en cours de service (par exemple via vwait ou upda
te
).

Un gestionnaire d'événements fichier est une liaison entre un canal et un script, de sorte que le script est évalué chaque fois que le canal devient lisible ou inscriptible. Les gestionnaires d'événements fichier sont le plus couramment utilisés pour permettre la réception de données d'un autre processus sur une base pilotée par les événements, afin que le récepteur puisse continuer à interagir avec l'utilisateur ou avec d'autres canaux en attendant que les données arrivent. Si une application invoque chan gets ou chan read sur un canal bloquant alors qu'aucune donnée d'entrée n'est disponible, le processus se bloquera ; jusqu'à ce que les données d'entrée arrivent, il ne pourra pas servir d'autres événements, il semblera donc à l'utilisateur qu'il « fige ». Avec chan event, le processus peut savoir quand des données sont présentes et n'invoquer chan gets ou chan read que lorsqu'ils ne se bloqueront

pas.

Un canal est considéré comme lisible s'il y a des données non lues disponibles sur le périphérique sous-jacent. Un canal est aussi considéré comme lisible s'il y a des données non lues dans un tampon d'entrée, sauf dans le cas spécial où la tentative la plus récente de lecture depuis le canal était un appel chan gets qui n'a pas pu trouver une ligne complète dans le tampon d'entrée. Cette fonctionnalité permet de lire un fichier ligne par ligne en mode non bloquant à l'aide des événements. Un canal est aussi considéré comme lisible si une condition de fin de fichier ou d'erreur est présente sur le fichier ou le périphérique sous-jacent. Il est important pour script de vérifier ces conditions et de les traiter de manière appropriée ; par exemple, s'il n'y a pas de vérification spéciale pour la fin de fichier, une boucle infinie peut survenir où script ne lit aucune donnée, retourne, et est immédiatement invoqué à

nouveau.

Un canal est considéré comme inscriptible si au moins un octet de données peut être écrit sur le fichier ou le périphérique sous-jacent sans bloquer, ou si une condition d'erreur est présente sur le fichier ou le périphérique sous-jacent. Notez que les sockets clients ouverts en mode asynchrone deviennent inscriptibles lorsqu'ils deviennent connectés ou si la connexion

échoue.

L'E/S pilotée par les événements fonctionne au mieux pour les canaux qui ont été placés en mode non bloquant avec la commande chan configure. En mode bloquant, une commande chan puts peut bloquer si vous lui donnez plus de données que le fichier ou le périphérique sous-jacent ne peut accepter, et une commande chan gets ou chan read bloquera si vous tentez de lire plus de données que ce qui est prêt ; aucun événement ne sera traité pendant que les commandes bloquent. En mode non bloquant chan puts, chan read, et chan gets ne bloquent

jamais.

Le script pour un événement fichier est exécuté au niveau global (hors du contexte de toute procédure Tcl) dans l'interpréteur dans lequel la commande chan event a été invoquée. Si une erreur se produit pendant l'exécution du script, la commande enregistrée avec interp bgerror est utilisée pour signaler l'erreur. De plus, le gestionnaire d'événements fichier est supprim

é s'il renvoie une erreur ; cela est fait pour prévenir l
es boucles infinies dues à des gestionnaires défectueux.

NAME


chan - Reading and writing Tcl values to and from channels






SYNOPSIS


chan puts ?-nonewline? ?channelId? string
chan gets ?channelId?
chan read ?channelId? ?numChars?
chan flush ?channelId?
chan eof ?channelId?
chan blocked ?channelId?
chan configure ?channelId? ?optionName? ?optionValue?...
chan event ?channelId? ?mask? ?script?
chan copy ?sourceId? ?destId? ?numBytes?
chan close ?channelId? ?option?







DESCRIPTION


The chan command provides access to Tcl's channel
    mechanism, which is used for input and output operations. The command is
    broken into several subcommands, each performing a specific operation on
    one or more channels.


The operations are:



    
chan puts ?-nonewline? ?channelId? string

    
Writes the string to the channel specified by channelId. If
        channelId is omitted, it defaults to the standard output channel.
        If the -nonewline option is given, then a newline character is
        not appended to the output. This is useful for writing prompt strings
        that are followed by user input on the same line.

    
chan gets ?channelId?

    
Reads a line of text from the channel specified by channelId. If
        channelId is omitted, it defaults to the standard input channel.
        A line is considered to be all characters up to the next newline
        character, inclusive. The newline character is read from the channel but
        not included in the returned string. If the end of the file is reached
        before any characters are read, then an empty string is returned. If
        end-of-file is reached after reading some characters but before reading a
        newline, the remaining characters are returned. If the channel is
        non-blocking and no full line is available, then chan gets will
        return an error. Otherwise, chan gets will block until a full line
        is available or end-of-file is reached.

    
chan read ?channelId? ?numChars?

    
Reads up to numChars characters from the channel specified by
        channelId. If channelId is omitted, it defaults to the
        standard input channel. If numChars is omitted, then all
        remaining characters in the channel are read until end-of-file. If the
        channel is non-blocking and not enough characters are available, then
        chan read will return an error. Otherwise, chan read will
        block until the requested number of characters are available or
        end-of-file is reached.

    
chan flush ?channelId?

    
Flushes any buffered output to the channel specified by channelId.
        If channelId is omitted, it defaults to the standard output
        channel.

    
chan eof ?channelId?

    
Returns 1 if end-of-file has been reached on the channel specified
        by channelId, and 0 otherwise. If channelId is
        omitted, it defaults to the standard input channel.

    
chan blocked ?channelId?

    
Returns 1 if the channel specified by channelId is currently
        in a non-blocking state and the last I/O operation would have blocked,
        and 0 otherwise. If channelId is omitted, it defaults to
        the standard input channel.

    
chan configure ?channelId? ?optionName? ?optionValue?...

    
This command is used to query and modify the options associated with a
        channel. If only channelId is specified, then all options and their
        values are returned as a list. If optionName is specified, then
        only the value of that option is returned. If optionName and
        optionValue are specified, then the option is set to the new
        value. The available options depend on the type of channel. Common
        options include:





    
-blocking boolean

    
If boolean is -true, then I/O operations on the channel
        will block until the operation can be completed. If boolean is
        -false, then operations will not block. Instead, if an operation
        cannot be completed immediately, it will return an error and the
        chan blocked command will return 1.

    
-buffering bufferType

    
Controls how output to the channel is buffered. Possible values for
        bufferType are none, line, and full.
        none means output is written immediately. line means
        output is written when a newline character is encountered or when the
        channel is flushed or closed. full means output is written
        only when the buffer is full. The default buffering depends on the type
        of channel.

    
-encoding encodingName

    
Specifies the character encoding used for the channel. See the encoding
        manual entry for a list of supported encodings.

    
-translation mode

    
Specifies how end-of-line characters are translated between the Tcl
        internal representation (newline, `\n`) and the external representation
        for the channel. Possible values for mode are auto,
        binary, cr, lf, and crlf. auto is
        the default for most text channels and translates `\n` to the system's
        native end-of-line sequence on output, and translates the system's
        native end-of-line sequence to `\n` on input. binary performs no
        translation. cr translates `\n` to `\r` on output and `\r` to
        `\n` on input. lf translates `\n` to `\n` on output and `\n` to
        `\n` on input (i.e., no translation). crlf translates `\n` to
        `\r\n` on output and `\r\n` to `\n` on input.





    
chan event ?channelId? ?mask? ?script?

    
Registers or unregisters a script to be executed when a specific event
        occurs on the channel. The mask is a comma-separated list of
        event types: readable, writable, or exception. If
        script is an empty string, then the event is unregistered. If all
        arguments are omitted, then all registered events and scripts are returned
        as a list of (channelId eventType script) triplets. See also
        fileevent.

    
chan copy ?sourceId? ?destId? ?numBytes?

    
Copies data from the sourceId channel to the destId channel.
        If numBytes is omitted, then data is copied until end-of-file is
        reached on the source channel. Returns the number of bytes copied. This
        command is useful for efficiently copying data between channels, for
        example, when creating a server that forwards data from one client to
        another.

    
chan close ?channelId? ?option?

    
Closes the channel specified by channelId. If channelId
        is omitted, it defaults to the standard output channel. If the -error
        option is specified, the channel is closed even if there are pending
        output errors. By default, chan close will block until all
        buffered output has been written. If the channel is not already open,
        an error is raised.








EXAMPLES


# A simple server that echoes back anything it receives
proc log {message} {
    chan puts stdout $message
}
# This is called whenever a new client connects to the server
proc connect {chan host port} {
    set clientName [format <%s:%d> $host $port]
    log "connection from $clientName"
    chan configure $chan -blocking 0 -buffering line
    chan event $chan readable [list echoLine $chan $clientName]
}
# This is called whenever either at least one byte of input
# data is available, or the channel was closed by the client.
proc echoLine {chan clientName} {
    chan gets $chan line
    if {[chan eof $chan]} {
        log "finishing connection from $clientName"
        chan close $chan
    } elseif {![chan blocked $chan]} {
        # Didn't block waiting for end-of-line
        log "$clientName - $line"
        chan puts $chan $line
    }
}
# Create the server socket and enter the event-loop to wait
# for incoming connections...
socket -server connect 12345
vwait forever

DESCRIPTION

La commande chan donne accès au mécanisme de canaux de Tcl, qui est utilisé pour les opérations d'entrée et de sortie. La commande est divisée en plusieurs sous-commandes, chacune effectuant une opération spécifique sur un ou plusieurs canaux.

Les opérations sont :

chan puts ?-nonewline? ?channelId? string
Écrit la chaîne dans le canal spécifié par channelId. Si channelId est omis, il prend la sortie standard comme valeur par défaut. Si l'option -nonewline est donnée, alors un caractère de nouvelle ligne n'est pas ajouté à la sortie. Ceci est utile pour écrire des chaînes d'invite qui sont suivies par l'entrée de l'utilisateur sur la même ligne.
chan gets ?channelId?
Lit une ligne de texte depuis le canal spécifié par channelId. Si channelId est omis, il prend l'entrée standard comme valeur par défaut. Une ligne est considérée comme tous les caractères jusqu'à la prochaine nouvelle ligne incluse. Le caractère de nouvelle ligne est lu depuis le canal mais n'est pas inclus dans la chaîne retournée. Si la fin du fichier est atteinte avant que des caractères ne soient lus, une chaîne vide est retournée. Si la fin du fichier est atteinte après la lecture de certains caractères mais avant la lecture d'une nouvelle ligne, les caractères restants sont retournés. Si le canal est en mode non bloquant et qu'aucune ligne complète n'est disponible, alors chan gets retournera une erreur. Sinon, chan gets bloquera jusqu'à ce qu'une ligne complète soit disponible ou que la fin du fichier soit atteinte.
chan read ?channelId? ?numChars?
Lit jusqu'à numChars caractères depuis le canal spécifié par channelId. Si channelId est omis, il prend l'entrée standard comme valeur par défaut. Si numChars est omis, alors tous les caractères restants dans le canal sont lus jusqu'à la fin du fichier. Si le canal est en mode non bloquant et que pas assez de caractères sont disponibles, alors chan read retournera une erreur. Sinon, chan read bloquera jusqu'à ce que le nombre de caractères demandé soit disponible ou que la fin du fichier soit atteinte.
chan flush ?channelId?
Vide tout tampon de sortie vers le canal spécifié par channelId. Si channelId est omis, il prend la sortie standard comme valeur par défaut.
chan eof ?channelId?
Retourne 1 si la fin du fichier a été atteinte sur le canal spécifié par channelId, et 0 sinon. Si channelId est omis, il prend l'entrée standard comme valeur par défaut.
chan blocked ?channelId?
Retourne 1 si le canal spécifié par channelId est actuellement dans un état non bloquant et que la dernière opération d'E/S aurait bloqué, et 0 sinon. Si channelId est omis, il prend l'entrée standard comme valeur par défaut.
chan configure ?channelId? ?optionName? ?optionValue?...
Cette commande est utilisée pour interroger et modifier les options associées à un canal. Si seul channelId est spécifié, alors toutes les options et leurs valeurs sont retournées sous forme de liste. Si optionName est spécifié, alors seule la valeur de cette option est retournée. Si optionName et optionValue sont spécifiés, alors l'option est définie à la nouvelle valeur. Les options disponibles dépendent du type de canal. Les options courantes incluent :
-blocking booléen
Si booléen est -vrai, alors les opérations d'E/S sur le canal bloqueront jusqu'à ce que l'opération puisse être complétée. Si booléen est -faux, alors les opérations ne bloqueront pas. Au lieu de cela, si une opération ne peut pas être complétée immédiatement, elle retournera une erreur et la commande chan blocked retournera 1.
-buffering typeTampon
Contrôle la façon dont la sortie vers le canal est mise en tampon. Les valeurs possibles pour typeTampon sont none, line, et full. none signifie que la sortie est écrite immédiatement. line signifie que la sortie est écrite lorsqu'un caractère de nouvelle ligne est rencontré ou lorsque le canal est vidé ou fermé. full signifie que la sortie est écrite seulement lorsque le tampon est plein. Le tampon par défaut dépend du type de canal.
-encoding nomEncodage
Spécifie l'encodage de caractères utilisé pour le canal. Voir l'entrée de manuel encoding pour une liste des encodages supportés.
-translation mode
Spécifie comment les caractères de fin de ligne sont traduits entre la représentation interne de Tcl (nouvelle ligne, `\n`) et la représentation externe pour le canal. Les valeurs possibles pour mode sont auto, binary, cr, lf, et crlf. auto est la valeur par défaut pour la plupart des canaux de texte et traduit `\n` en la séquence de fin de ligne native du système en sortie, et traduit la séquence de fin de ligne native du système en `\n` en entrée. binary n'effectue aucune traduction. cr traduit `\n` en `\r` en sortie et `\r` en `\n` en entrée. lf traduit `\n` en `\n` en sortie et `\n` en `\n` en entrée (c'est-à-dire aucune traduction). crlf traduit `\n` en `\r\n` en sortie et `\r\n` en `\n` en entrée.
chan event ?channelId? ?mask? ?script?
Enregistre ou désenregistre un script à exécuter lorsqu'un événement spécifique se produit sur le canal. Le masque est une liste d'événements séparés par des virgules : readable, writable, ou exception. Si script est une chaîne vide, alors l'événement est désenregistré. Si tous les arguments sont omis, alors tous les événements et scripts enregistrés sont retournés sous forme de liste de triplets (channelId eventType script). Voir aussi fileevent.
chan copy ?sourceId? ?destId? ?numBytes?
Copie des données du canal sourceId vers le canal destId. Si numBytes est omis, alors les données sont copiées jusqu'à ce que la fin du fichier soit atteinte sur le canal source. Retourne le nombre d'octets copiés. Cette commande est utile pour copier efficacement des données entre canaux, par exemple, lors de la création d'un serveur qui transfère des données d'un client à un autre.
chan close ?channelId? ?option?
Ferme le canal spécifié par channelId. Si channelId est omis, il prend la sortie standard comme valeur par défaut. Si l'option -error est spécifiée, le canal est fermé même s'il y a des erreurs de sortie en attente. Par défaut, chan close bloquera jusqu'à ce que toute sortie tamponnée ait été écrite. Si le canal n'est pas déjà ouvert, une erreur est levée.

EXEMPLES

# Un serveur simple qui renvoie tout ce qu'il reçoit
proc log {message} {
    chan puts stdout $message
}
# Ceci est appelé chaque fois qu'un nouveau client se connecte au serveur
proc connect {chan host port} {
    set clientName [format <%s:%d> $host $port]
    log "connexion depuis $clientName"
    chan configure $chan -blocking 0 -buffering line
    chan event $chan readable [list echoLine $chan $clientName]
}
# Ceci est appelé chaque fois qu'au moins un octet de données d'entrée
# est disponible, ou que le canal a été fermé par le client.
proc echoLine {chan clientName} {
    chan gets $chan line
    if {[chan eof $chan]} {
        log "fin de connexion depuis $clientName"
        chan close $chan
    } elseif {![chan blocked $chan]} {
        # N'a pas bloqué en attendant la fin de ligne
        log "$clientName - $line"
        chan puts $chan $line
    }
}
# Créer le socket serveur et entrer dans la boucle d'événements pour attendre
# les connexions entrantes...
socket -server connect 12345
vwait forever
