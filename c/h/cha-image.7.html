Images inline

Sur les terminaux qui supportent les images, Chawan peut afficher divers formats d'images bitmap.

Activation des images

Il y a en fait deux options pour les images dans la configuration :

  • buffer.images : cela active le téléchargement des images, même si elles ne peuvent pas être affichées.
  • display.image-mode : définit la méthode d'affichage des images inline. Par défaut, c'est "auto", mais elle peut aussi être définie manuellement sur "sixel" ou "kitty".

Dans la plupart des cas, tout ce que vous avez à faire est de régler "buffer.images" sur true :

# dans ~/.chawan/config.toml (ou ~/.config/chawan/config.toml)
[buffer]
images = true

Avec le mode d'image par défaut, Chawan trouvera la meilleure méthode d'affichage d'image supportée par votre terminal. Cependant, si votre terminal ne parvient pas à indiquer à Chawan qu'il peut afficher des sixels, vous pourriez également devoir régler "display.image-mode" de manière appropriée. Voir ci-dessous pour une discussion plus approfondie de la configuration des sixels.

Formats de sortie

Les formats de sortie supportés sont :

  • Le format DEC Sixel
  • Le protocole graphique du terminal Kitty

Le premier est supporté car il est universellement adopté ; le second car il est techniquement supérieur à toutes les alternatives existantes.

Le support pour d'autres protocoles (iTerm, MLTerm, etc.) n'est pas prévu. (À ma connaissance, tous les terminaux capables d'afficher des images supportent au moins l'un des deux ci-dessus de toute façon.)

Le support pour les hacks tels que w3mimgdisplay, ueberzug, etc. n'est pas prévu.

Sixel

Sixel est le format d'image le plus largement supporté. Voir https://arewesixelyet.com pour trouver un terminal qui le supporte.

Mises en garde connues et détails d'implémentation :

  • XTerm nécessite une configuration étendue pour un support optimal des sixels. En particulier, vous voudrez définir les attributs decTerminalID, numColorRegisters et maxGraphicSize. Voir man xterm pour les détails.
  • Nous supposons que les registres de couleurs privés sont supportés. Sur les terminaux où ce n'est pas le cas (par exemple, SyncTERM ou terminaux matériels), les couleurs seront mélangées avec plusieurs images à l'écran.
  • Nous envoyons XTSMGRAPHICS pour récupérer le nombre de registres de couleurs ; en cas d'échec, nous revenons à 256. Vous pouvez outrepasser le nombre de registres de couleurs en utilisant la valeur de configuration display.sixel-colors.
  • Pour un affichage sixel des plus efficaces, vous voudrez une hauteur de cellule qui soit un multiple de 6. Sinon, les images devront être recodées plusieurs fois lors du défilement.
  • Normalement, l'encodage Sixel se déroule en deux passes. Sur les ordinateurs lents, vous pouvez essayer de régler display.sixel-colors = 2, ce qui sautera la première passe (mais affichera également tout en monochrome).
  • La transparence est supportée, mais elle paraît étrange car nous approximons un canal alpha 8 bits avec le canal alpha 1 bit de Sixel. De plus, certains terminaux ne l'émulent pas correctement - en cas de doute, essayez XTerm (qui le fait).

Kitty

Sur les terminaux qui le supportent, le protocole de Kitty est préféré à Sixel. Son principal avantage est que les images n'ont pas besoin d'être renvoyées chaque fois qu'elles se déplacent à l'écran (c'est-à-dire lors du défilement), mais le transfert initial devrait également être plus rapide (car la compression PNG a tendance à surpasser le RLE de Sixel).

Contrairement à Sixel, le protocole Kitty supporte pleinement la transparence.

Formats d'entrée

Actuellement, les formats d'entrée supportés sont :

  • BMP, PNG, JPEG, GIF (via stb_image)
  • WebP (via JebP)
  • SVG (via NanoSVG)

D'autres formats pourraient être ajoutés à l'avenir, à condition qu'il existe une implémentation raisonnablement petite, de préférence dans le domaine public. (Je ne veux pas dépendre de bibliothèques externes de décodage d'images, mais quelque chose comme stbi est acceptable à intégrer.)

Système de modules de codec

Toutes les implémentations de codecs d'images sont spécifiées par le schéma d'URL "img-codec+nom:", où "nom" est le sous-type MIME. par exemple, pour image/png, c'est "img-codec+png:". (Cela signifie en effet que seuls les types MIME "image" peuvent être utilisés.)

Comme tous les schémas, ceux-ci sont définis (et peuvent être outrepassés) dans le fichier urimethodmap, et sont implémentés sous forme de programmes CGI locaux. Ces programmes prennent une image encodée en entrée standard et rejettent les données RGBA décodées en sortie standard - lors de l'encodage, inversement.

Cela signifie qu'il est possible pour les utilisateurs de définir des décodeurs d'images pour leurs formats préférés, ou même d'outrepasser ceux intégrés. (Si vous finissez par faire cela pour une raison quelconque, veuillez m'envoyer un e-mail afin que je puisse l'ajouter au répertoire bonus.)

Un codec peut avoir une ou les deux instructions "decode" et "encode" ; celles-ci sont définies dans le nom du chemin. Ainsi, "img-codec+png:decode" est appelé pour décoder les PNG, et "img-codec+png:encode" pour les encoder.

Les en-têtes sont utilisés pour transférer des métadonnées (comme les dimensions de l'image), à la fois depuis le navigateur (entrée) et vers le navigateur (sortie). Une description détaillée des interfaces décodeur et encodeur suit.

décodage

Lorsque le chemin est égal à "decode", un script CGI de codec doit prendre un flux binaire d'une image encodée sur son entrée standard et imprimer le flux binaire équivalent de valeurs RGBA 8 bits (par composant) en grande boutiste sur la sortie standard.

En-têtes d'entrée :

•
Cha-Image-Info-Only: 1

Ceci indique au décodeur d'image de n'envoyer que les métadonnées de l'image (c'est-à-dire la taille). Techniquement, le décodeur est libre de décoder réellement l'image, mais le navigateur ignorera toute sortie après les en-têtes.

En-têtes de sortie :

•
Cha-Image-Dimensions: {largeur}x{hauteur}

La taille de l'image décodée. par exemple, pour 123x456, 123 est la largeur et 456 est la hauteur.

encodage

Lorsque le chemin est égal à "encode", un script CGI de codec doit prendre un flux binaire de valeurs RGBA 8 bits (par composant) en grande boutiste sur son entrée standard et imprimer l'image encodée équivalente sur sa sortie standard.

En-têtes d'entrée :

•
Cha-Image-Dimensions: {largeur}x{hauteur}

Spécifie les dimensions de l'image RGBA d'entrée. Cela signifie que {largeur} * {hauteur} * 4 == {taille des données reçues en entrée standard}.

Le format est le même que ci-dessus ; en fait, la conception est telle que vous pourriez directement rediriger la sortie de decode vers encode (et vice versa).

•
Cha-Image-Quality: {nombre}

La qualité d'encodage demandée, allant de 1 à 100 inclusivement (c'est-à-dire 1..100). Il appartient à l'encodeur d'interpréter ce nombre.

(L'encodeur JPEG stb_image utilise ceci.)

En-têtes de sortie :

Actuellement, aucun en-tête de sortie n'est défini pour les encodeurs.

Ignorer les copies avec mmap

L'implémentation naïve du système ci-dessus devrait copier la sortie au moins deux fois lorsqu'une image est redimensionnée. Pour éviter ces copies, stdin et/ou stdout est (actuellement) un fichier dans le répertoire tmp pour :

  • stdin de décodage, lorsque l'image est déjà téléchargée
  • stdout de décodage, toujours
  • stdin d'encodage, toujours

Cela permet de mapper stdin/stdout avec mmap au lieu de les traiter par flux avec read et write. En faisant cela, gardez à l'esprit les points suivants :

  • Lors de la lecture, vous devez vérifier votre position initiale dans le fichier avec lseek.
  • Lors de l'écriture, vos en-têtes font partie de la sortie. Au minimum, vous devez placer une nouvelle ligne au début du fichier.
  • Ceci est un détail d'implémentation, et pourrait changer à tout moment à l'avenir (par exemple, si nous ajoutons un "no cach
e files” mode). Vérifiez toujours S_ISREG pour vous assurer que vous traitez réellement avec un fichier. (Utilisez recvDataLoopOrMmap et maybeMmapForSend de io/dynstream.nim pour gérer cela automatiquement.)
