DESCRIPTIO

N

L'utilitaire chmod doit changer un ou tous les bits de mode de fichier du fichier nommé par chaque opérande fichier de la manière spécifiée par l'opérande mode

.

Il est défini par l'implémentation si et comment l'utilitaire chmod affecte tout mécanisme de contrôle d'accès alternatif ou supplémentaire (voir le volume Définitions de base de POSIX.1‐2017, Section 4.5, Autorisations d'accès aux fichiers) utilisé pour le fichier

spécifié.

Seul un processus dont l'identifiant utilisateur effectif correspond à l'identifiant utilisateur du fichier, ou un processus disposant des privilèges appropriés, doit être autorisé à changer les bits de mode de fichier d'un

fichier.

Après avoir changé avec succès les bits de mode de fichier d'un fichier, l'utilitaire chmod doit marquer pour mise à jour l'horoda

tage du dernier changem
ent d'état du fichier.

DESCRIPTION

ÉTENDUE

L'opérande mode doit être soit une expression symbolic_mode soit un entier octal non négatif. La forme symbolic_mode est décrite par la grammaire plus loin dans cette

section.

Chaque clause doit spécifier une opération à effectuer sur les bits de mode de fichier actuels de chaque fichier. Les opérations doivent être effectuées sur chaque fichier dans l'ordre dans lequel les clauses sont

spécifiées.

Les symboles who u, g, et o doivent spécifier respectivement les parties utilisateur, groupe, et autre des bits de mode de fichier. Un who composé du symbole a doit être équivalent à ugo

.

Les symboles perm r, w, et x représentent respectivement les portions lecture, écriture, et exécution/recherche des bits de mode de fichier. Le symbole perm s doit représenter les bits set-user-ID-on-execution (quand who contient ou implique u) et set-group-ID-on-execution (quand who contient ou implique g)

.

Le symbole perm X doit représenter la portion exécution/recherche des bits de mode de fichier si le fichier est un répertoire ou si les bits de mode de fichier actuels (non modifiés) ont au moins un des bits d'exécution (S_IXUSR, S_IXGRP, ou S_IXOTH) défini. Il doit être ignoré si le fichier n'est pas un répertoire et qu'aucun des bits d'exécution n'est défini dans les bits de mode de fichier

actuels.

Les symboles permcopy u, g, et o doivent représenter les permissions actuelles associées respectivement aux parties utilisateur, groupe, et autre des bits de mode de fichier. Pour le reste de cette section, perm fait référence aux non-terminaux perm et permcopy dans la

grammaire.

Si plusieurs actionlist sont groupées avec une seule wholist dans la grammaire, chaque actionlist doit être appliqué dans l'ordre spécifié avec cette wholist. Les symboles op doivent représenter l'opération effectuée, comme suit

Grammaire pour

chmod

La grammaire et les conventions lexicales dans cette section décrivent la syntaxe pour l'opérande symbolic_mode. Les conventions générales pour ce style de grammaire sont décrites dans la Section 1.3, Conventions de grammaire. Un symbolic_mode valide peut être représenté comme le symbole non terminal symbolic_mode dans la grammaire. Cette syntaxe formelle prendra précédence sur la description de syntaxe textuelle

précédente.

Le traitement lexical est entièrement basé sur des caractères simples. Les implémentations n'ont pas besoin de permettre des caractères <blank> à l'intérieur de l'unique argument en cours de

traitement.

UTILISATION PAR LES

APPLICATIONS

Certaines implémentations de l'utilitaire chmod changent le mode d'un répertoire avant les fichiers du répertoire lorsqu'elles effectuent un changement récursif (option -R) ; d'autres changent le mode du répertoire après les fichiers du répertoire. Si une application essaie de retirer la permission de lecture ou de recherche pour une hiérarchie de fichiers, la tentative de retrait échoue si le répertoire est changé en premier ; d'un autre côté, essayer de réactiver les permissions pour une hiérarchie restreinte échoue si les répertoires sont changés en dernier. Les utilisateurs ne devraient pas essayer de rendre une hiérarchie inaccessible pour

eux-mêmes.

Certaines implémentations de chmod n'ont jamais utilisé le umask du processus lors du changement de modes ; les systèmes conformes à ce volume de POSIX.1‐2017 le font lorsque le who n'est pas spécifié. Notez la différence entre

JUSTIFICATIO

N

La fonctionnalité de chmod est décrite substantiellement par des références à des concepts définis dans le volume Interfaces Système de POSIX.1‐2017. De cette façon, il y a moins de duplication d'effort requise pour décrire les interactions des permissions. Cependant, le comportement de cet utilitaire n'est pas décrit en termes de la fonction chmod() du volume Interfaces Système de POSIX.1‐2017 parce que cette spécification requiert certains effets de bord sur des mécanismes alternatifs de contrôle d'accès aux fichiers qui pourraient ne pas être appropriés, dépendant de l'implémentation

.

Les implémentations qui supportent le verrouillage obligatoire de fichiers et d'enregistrements tel que spécifié par le standard /usr/group de 1984 utilisaient historiquement la combinaison du bit set-group-ID défini et du bit d'exécution du groupe effacé pour indiquer le verrouillage obligatoire. Cette condition est habituellement définie ou effacée avec le mode symbolique symbole perm l au lieu des symboles perm s et x afin que le mode de verrouillage obligatoire ne soit pas changé sans indication explicite que c'était ce que l'utilisateur avait l'intention de faire. Par conséquent, les détails sur la manière dont l'implémentation traite ces conditions doivent être définis dans la documentation. Ce volume de POSIX.1‐2017 ne requiert pas le verrouillage obligatoire (ni le volume Interfaces Système de POSIX.1‐2017), mais le permet comme une extension. Cependant, ce volume de POSIX.1‐2017 requiert que les utilitaires ls et chmod fonctionnent de manière cohérente dans ce domaine. Si ls -l fichier indique que le bit set-group-ID est défini, chmod g-s fichier doit l'effacer (en supposant que les privilèges appropriés existent pour changer les modes)

.

Les versions System V et BSD utilisent des codes de statut de sortie différents. Certaines implémentations utilisaient le statut de sortie comme un compte du nombre d'erreurs survenues ; cette pratique est inutilisable car il peut dépasser la plage des valeurs de statut de sortie valides. Ce problème est évité ici en

spécifiant

uniquement 0 et >0 comme valeurs de sortie. Le volume des Interfaces système de POSIX.1‐2017 indique que des restrictions définies par l'implémentation peuvent faire que les bits S_ISUID et S_ISGID sont ignorés. Ce volume de POSIX. 1‐2017 permet à l' utilitaire chmod de choisir de modifier ces bits avant d'appeler chmod() (ou une fonction fournissant des capacités équivalentes) pour les fichiers non réguliers. Entre autres, cela permet aux implémentations qui utilisent

les

bits s et-user-ID et set-group-ID sur les répertoires pour activer des fonctionnalités étendues de gérer cesextensions de manière intelligente. Le symbole X a été adopté à partir des systèmes basés sur BSD car il fournit une fonctionnalité couramment souhaitée lors de modifications récursives ( option -R).
