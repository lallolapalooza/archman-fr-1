CHECKMK(1) CHECKMK(1)

NOM

checkmk - Script Awk pour générer des tests unitaires C destinés à être utilisés avec le framework de tests unitaires Check.

SYNOPSIS

checkmk [ clean_mode=1 ] [ fichier-entrée ]

DESCRIPTION

Génère des fichiers source en langage C contenant des tests unitaires destinés à être utilisés avec le framework de tests unitaires Check. Le but de ce script est d'automatiser une partie du code standard que l'on doit écrire lors de la création d'une suite de tests avec Check : plus précisément, l'instanciation d'un SRunner, de Suite(s) et de TCase(s), ainsi que la création des relations entre ces objets et les fonctions de test.

Cet outil est destiné à être utilisé par ceux qui sont familiarisés avec le framework de tests unitaires Check. On supposera une connaissance de ce framework tout au long de ce manuel.

Le framework Check, ainsi que des informations à son sujet, est disponible à l'adresse https://libcheck.github.io/check/ <URL :https://libcheck.github.io/check/>.

L'argument fichier-entrée de checkmk utilise une syntaxe simple, semblable à celle du préprocesseur C, pour déclarer des fonctions de test et pour décrire leurs relations avec les Suites et les TCases dans Check. checkmk utilise ensuite ces informations pour écrire automatiquement une fonction main() contenant toutes les déclarations nécessaires, ainsi que tout le code requis pour exécuter les suites de tests. La sortie finale en langage C est imprimée sur la sortie standardde checkmk.

Des moyens sont prévus pour insérer du code utilisateur dans la fonction main() générée, afin de permettre l'utilisation de la journalisation, de fixtures de test ou de codes de sortie spécialisés.

Bien qu'il soit possible d'omettre l'argument fichier-entrée de checkmk et de fournir le fichier d'entrée sur l' entrée standardde checkmk, il est généralement recommandé de le fournir en tant qu'argument. Cela permet à checkmk de connaître le nom du fichier, de placer des références à celui-ci dans les commentaires initiaux de la sortie en langage C, et d'insérer des directives #line en C tout au long du code, afin de faciliter le débogage des problèmes en orientant l'utilisateur vers le fichier d'entrée original.

OPTIONS

La seule option officiellement prise en charge est la spécification d'une valeur vraie (utilisant la définition d'Awk pour « vrai ») pour la variable clean_mode. Cela empêche checkmk de placer les directives #line appropriées dans le code source, ce que certains pourraient considérer comme un encombrement inutile.

L'auteur déconseille l'utilisation de cette option, car elle amènera les compilateurs C et les outils de débogage à référencer des lignes dans la sortie générée automatiquement, plutôt que les fichiers d'entrée originaux de checkmk. Cela encouragerait les utilisateurs à modifier les fichiers de sortie au lieu des fichiers d'entrée originaux, rendrait difficile pour les éditeurs intelligents ou les IDE d'ouvrir le bon fichier à modifier, et pourrait entraîner l'écrasement des corrections lors de la régénération des fichiers de sortie.

Les directives #line sont automatiquement supprimées lorsque le fichier d'entrée est fourni sur l'entrée standard au lieu d'être passé en argument de la ligne de commande.

EXEMPLE SIMPLE

Dans sa forme la plus simple, un fichier d'entrée peut être simplement un prologue et une fonction de test. Tout ce qui apparaît avant la première fonction de test fait partie du prologue et sera copié tel quel dans la sortie. La fonction de test est commencée par une ligne de la forme :

#test nom_test

Où nom_test est le nom de votre fonction de test. Cela sera utilisé pour nommer une fonction C, il doit donc s'agir d'un identifiant C valide.

Voici un petit exemple complet :

--------------------------------------------------
/* Un exemple de test complet */
#include <stdio.h>
#test the_test
    int nc;
    const char msg[] = "\n\n    Hello, world!\n";
    nc = printf("%s", msg);
    ck_assert(nc == (sizeof(msg) - 1)); /* pour le NUL terminant. */
--------------------------------------------------

Si vous placez ce qui précède dans un fichier nommé basic_complete.ts et que vous le traitez avec la commande suivante :

$ checkmk basic_complete.ts > basic_complete.c

basic_complete.c contiendra une sortie similaire à :

--------------------------------------------------
/*
 * NE PAS MODIFIER CE FICHIER. Généré par checkmk.
 * Modifier le fichier source original "in" à la place.
 */
#include <check.h>
/* Un exemple de test complet */
#include <stdio.h>
START_TEST(the_test)
{
    int nc;
    const char msg[] = "\n\n    Hello, world!\n";
    nc = printf("%s", msg);
    ck_assert(nc == (sizeof(msg) - 1)); /* pour le NUL terminant. */
}
END_TEST
int main(void)
{
    Suite *s1 = suite_create("Core");
    TCase *tc1_1 = tcase_create("Core");
    SRunner *sr = srunner_create(s1);
    int nf;
    suite_add_tcase(s1, tc1_1);
    tcase_add_test(tc1_1, the_test);
    srunner_run_all(sr, CK_ENV);
    nf = srunner_ntests_failed(sr);
    srunner_free(sr);
    return nf == 0 ? 0 : 1;
}
--------------------------------------------------

En usage réel, basic_complete.c contiendrait également des directives #line.

RÉSUMÉ DES DIRECTIVES

Voici un résumé complet de toutes les directives de style préprocesseur C comprises par checkmk. Voir ci-dessous pour plus de détails.

# test nom_test
# test-signal(signal) nom_test
# test-exit(code_sortie) nom_test
# test-loop(début, fin) nom_test
# test-loop-signal(signal, début, fin) nom_test
# test-loop-exit(code_sortie, début, fin) nom_test
# suite NomSuiteDeTest
# tcase NomCasDeTest
# main-pre
# main-post

Toutes les directives ne sont pas sensibles à la casse. Des espaces peuvent apparaître au début de la ligne avant le #, entre le # et la directive, entre la directive et n'importe quel argument, et à la fin de la ligne.

DIRECTIVES DE DÉFINITION DE TESTS

Voici une explication plus détaillée des directives qui peuvent être utilisées pour définir des fonctions de test et leurs conteneurs.

FONCTIONS DE TEST

# test nom_test
# test-signal(signal) nom_test
# test-exit(code_sortie) nom_test
# test-loop(début, fin) nom_test
# test-loop-signal(signal, début, fin) nom_test
# test-loop-exit(code_sortie, début, fin) nom_test

Ce sont les directives les plus fondamentales pour créer un modèle destiné à l'entrée de checkmk. Ce sont les seules directives requises : il doit y avoir au moins une directive #test* dans le modèle, sinon checkmk échouera avec un message d'erreur. Les directives #test* peuvent être spécifiées plusieurs fois, chacune commençant la définition d'une nouvelle fonction de test.

L'argument nom_test sera utilisé comme nom d'une fonction de test dans la sortie en langage C, il doit donc s'agir d'un identifiant C valide. C'est-à-dire qu'il doit commencer par un caractère alphabétique ou le souligné (_), suivi de caractères alphanumériques et/ou de soulignés optionnels.

Les noms de caractères universels (introduits en C99) sont également autorisés, sous la forme \uXXXX ou \UXXXXXXXX, où les X représentent des chiffres hexadécimaux.

C'est une erreur de spécifier le même nom_test dans plus d'une directive #test*, qu'elles soient associées à des cas de test ou des suites de test différents ou non.

Voir IDENTIFIANTS CHECKMK pour la liste des identifiants qui devraient être évités comme noms de fonctions de test.

SUITES DE TEST

# suite NomSuiteDeTest

Cette directive spécifie le nom de la suite de test (objetSuite dans le framework de test Check) à laquelle tous les futurs cas de test (et leurs fonctions de test) seront ajoutés.

Le NomSuiteDeTest est une chaîne de texte, et peut contenir n'importe quel type de caractères (à l'exception du caractère NUL ASCII et du saut de ligne, qui terminerait la directive). Tout espace blanc initial ou final sera omis du nom de la suite de test.

Commencer une nouvelle suite de test commence également un nouveau cas de test, dont le nom est identique à celui de la nouvelle suite de test. Ce nom de cas de test peut être remplacé par une directive #tcase ultérieure.

Notez qu'un objet Suite ne sera en fait pas défini par chcheckmk dans la sortie C, sauf s'il est suivi à un moment donné par une directive #test (sans #suite intermédiaire). Ce n'est pas une erreur pour un #suite de ne pas avoir de #test associés ; le #suite (et les #tcase associés) ne produira simplement aucune action de la part de checkmk (et serait donc inutile).

C'est une erreur pour une directive #suite de spécifier plusieurs fois la même suite (sensible à la casse), sauf si les utilisations précédentes n'ont pas été instanciées par la présence d'au moins une directive #test associée.

Si vous ne spécifiez pas de directive #suite avant la première directive #test, checkmk effectue l'équivalent d'une directive #suite implicite, avec la chaîne "Core" comme valeur pour TestSuiteName (ce qui implique également un objet de test case "Core"). C'est démontré ci-dessus dans EXEMPLE DE BASE.

CAS DE TEST

# tcase TestCaseName

Cette directive spécifie le nom du cas de test (TCase objet dans le framework de test Check) auquel toutes les futures fonctions de test seront ajoutées.

Le #tcase fonctionne de manière très similaire à #suite. Le TestCaseName est une chaîne de texte, et peut contenir des caractères arbitraires ; et un objet TCase ne sera pas réellement défini à moins qu'il ne soit suivi d'une directive #test associée.

C'est une erreur pour une directive #tcase de spécifier plusieurs fois le même cas de test (sensible à la casse), sauf si les utilisations précédentes n'ont pas été instanciées par la présence d'au moins une directive #test associée.

Voir aussi la directive #suite, décrite ci-dessus.

CODE UTILISATEUR DANS MAIN()

Le C main() est automatiquement généré par checkmk, définissant les SRunner's, Suite's, etTCase's nécessaires aux directives de définition de test spécifiées par l'utilisateur.

Pour la plupart des situations, ce main() entièrement automatisé est tout à fait adapté en l'état. Cependant, il y a des situations où l'on pourrait souhaiter ajouter du code personnalisé au main(). Par exemple, si l'utilisateur souhaite :

•
changer la valeur du délai d'attente du test via tcase_set_timeout(),
•
spécifier le "no-fork-mode" de Check via srunner_set_fork_status(),
•
mettre en place des fixtures de test pour certains cas de test, via tcase_add_checked_fixture() outcase_add_unchecked_fixture(),
•
mettre en place la journalisation des tests pour le lanceur de suite, via srunner_set_log() ousrunner_set_xml(), ou
•
effectuer une finalisation personnalisée après l'exécution des suites de test.

À ces fins, les directives #main-pre et #main-post ont été fournies.

PROLOGUE DE MAIN()

# main-pre

Le texte suivant cette directive sera placé tel quel dans le corps de la fonction main() générée, juste après checkmk's déclarations de variables locales, et avant que tout test n'ait été exécuté (en fait, avant même que les relations entre les tests, les cas de test et les suites de test n'aient été établies, bien que ce fait ne devrait pas faire beaucoup de différence). Puisque checkmk vient tout juste de finir de faire ses déclarations, il est permis, même selon les directives strictes de l'ISO C 1990, de faire des déclarations de variables personnalisées ici.

Contrairement aux directives décrites précédemment, #main-pre peut être spécifié au plus une fois. Il ne peut pas être précédé de la directive #main-post, et aucune directive #suite, #tcase ou #test ne peut apparaître après lui.

#main-pre est un bon endroit pour ajuster les paramètres ou mettre en place des fixtures de test. Bien sûr, pour ce faire, vous devez connaître les noms que checkmk a utilisés pour instancier les SRunner's, Suite's, etTCase's.

IDENTIFIANTS CHECKMK

Les pointeurs vers les Suite's sont déclarés en utilisant le motif sX, où X est un nombre qui commence à 1, et est incrémenté pour chaque directive #suite suivante. s1 existe toujours, et contient la fonction de test déclarée par la première directive #test. Si cette directive n'était pas précédée d'un #suite, elle recevra le nom "Core".

Les pointeurs vers les TCase's sont déclarés en utilisant le motif tcX_Y, où X correspond au nombre utilisé pour le nom de la Suite qui contiendra ce TCase; et Y est un nombre qui commence à 1 pour chaque nouvelle Suite, et est incrémenté pour chaque TCase dans cette Suite.

Un pointeur vers un SRunner est déclaré en utilisant l'identifiant sr ; il y a aussi un entier nommé nf qui contient le nombre d'échecs de test (après que les tests ont été exécutés).

Pour des raisons évidentes, l'utilisateur ne doit pas tenter de déclarer des identifiants locaux dans main(), ou définir des macros ou des fonctions de test, dont les noms pourraient entrer en conflit avec les noms de variables locales utilisés par checkmk. Pour résumer, ces noms sont :

sX

tcX_Y

sr

nf.

EPILOGUE DE MAIN()

# main-post

Bien qu'il ne soit pas aussi utile, checkmk fournit également une directive #main-post pour insérer du code personnalisé à la fin de main(), après que les tests ont été exécutés. Cela pourrait être utilisé pour nettoyer les ressources qui ont été allouées dans le prologue, ou pour imprimer des informations sur les tests échoués, ou pour fournir un code de statut de sortie personnalisé.

Notez que, si vous utilisez cette directive, checkmk ne fournira pas de statement return : vous devrez en fournir un vous-même.

La directive #main-post ne peut pas être suivie par d'autres directives reconnues par checkmk.

EXEMPLE COMPLET

Maintenant que vous avez lu les descriptions détaillées des différentes directives, voyons-les toutes en action avec ce modèle assez complet.

--------------------------------------------------
#include "mempool.h"  /* définit MEMPOOLSZ, prototypages pour
                         mempool_init() et mempool_free() */
void *mempool;
void mp_setup(void)
{
    mempool = mempool_init(MEMPOOLSZ);
    ck_assert_msg(mempool != NULL, "Couldn't allocate mempool.");
}
void mp_teardown(void)
{
    mempool_free(mempool);
}
/* end of prologue */
#suite Mempool
#tcase MP Init
#test mempool_init_zero_test
    mempool = mempool_init(0);
    ck_assert_msg(mempool == NULL, "Allocated a zero-sized mempool!");
    ck_assert_msg(mempool_error(), "Didn't get an error for zero alloc.");
/* "MP Util" TCase utilise une fixture vérifiée. */
#tcase MP Util
#test mempool_copy_test
    void *cp = mempool_copy(mempool);
    ck_assert_msg(cp != NULL, "Couldn't perform mempool copy.");
    ck_assert_msg(cp != mempool, "Copy returned original pointer!");
#test mempool_size_test
    ck_assert(mempool_getsize(mempool) == MEMPOOLSZ);
#main-pre
    tcase_add_checked_fixture(tc1_2, mp_setup, mp_teardown);
    srunner_set_log(sr, "mplog.txt");
#main-post
    if (nf != 0) {
      printf("Hey, something's wrong! %d whole tests failed!\n", nf);
    }
    return 0; /* Harness checks for output, always return success
                 regardless. */
--------------------------------------------------

    checkmk(1)

    NOM
    checkmk - commande pour interroger et administrer Checkmk.

    SYNTAXE
    checkmk [OPTIONS] COMMANDE [ARGUMENTS...]

    DESCRIPTION
    La commande checkmk est l'interface principale pour interagir avec le système Checkmk. Elle permet d'effectuer diverses opérations telles que la vérification de l'état des hôtes et des services, la gestion des agents, la modification de la configuration et bien plus encore.

    OPTIONS

    • -h, --help : Affiche l'aide et quitte.
    • -V, --version : Affiche les informations sur la version et quitte.
    • -v, --verbose : Augmente la verbosité de la sortie.
    • -c FICHIER, --config=FICHIER : Spécifie un fichier de configuration différent.

    COMMANDES

    • check : Vérifie l'état des hôtes et des services.
    • discover : Découvre de nouveaux services sur un hôte.
    • activate-changes : Active les changements de configuration.
    • show-config : Affiche la configuration actuelle.
    • restart : Redémarre le moteur de Checkmk.
    • stop : Arrête le moteur de Checkmk.
    • start : Démarre le moteur de Checkmk.
    • status : Affiche le statut du moteur de Checkmk.
    • puppet-local : Exécute une commande locale pour l'intégration Puppet.
    • agent-registration : Gère l'enregistrement des agents.
    • push-agent-configs : Pousse les configurations des agents.
    • rotate-logs : Effectue une rotation des fichiers journaux.
    • rrdcached-purge : Nettoie le cache RRD.
    • clean-notify-archive : Nettoie l'archive des notifications.
    • mk-livestatus : Interface vers le module Livestatus.

    EXEMPLES 

    # Vérifier l'état de tous les hôtes et services
checkmk check

# Découvrir de nouveaux services sur l'hôte "webserver"
checkmk discover webserver

# Activer les changements de configuration en attente
checkmk activate-changes

# Afficher la configuration actuelle
checkmk show-config

# Redémarrer le moteur de Checkmk
checkmk restart

    STATUT DE SORTIE
    Retourne 0 si la commande réussit, une valeur non nulle en cas d'erreur.

    FICHIERS

    • /etc/checkmk/main.mk : Fichier de configuration principal.
    • /opt/checkmk/site/bin/checkmk : Script de la commande.

    VOIR AUSSI

    • checkmk-agent(1)
    • La documentation officielle de Checkmk.

    CODE UTILISATEUR DANS MAIN()
    Le code utilisateur spécifique à la fonction main() peut être placé ici. Cela est utile pour des extensions personnalisées ou des intégrations spécifiques.

    EXEMPLE COMPLET
    Voici un exemple plus complet montrant comment vérifier l'état d'un hôte spécifique, activer les changements et redémarrer le service Checkmk : 

    # Vérifier l'hôte "dbserver"
checkmk check dbserver

# Activer les changements de configuration
checkmk activate-changes

# Redémarrer le service Checkmk
checkmk restart
