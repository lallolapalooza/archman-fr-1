chown(2) Manuel des appels système chown(2)

NOM

chown, fchown, lchown, fchownat - changer le propriétaire d'un fichier

BIBLIOTHÈQUE

Bibliothèque C standard (libc,-lc)

SYNOPSIS

#include <unistd.h>
int chown(const char *path, uid_t owner, gid_t group);
int fchown(int fd, uid_t owner, gid_t group);
int lchown(const char *path, uid_t owner, gid_t group);
#include <fcntl.h>           /* Définition des constantes AT_* */
#include <unistd.h>
int fchownat(int dirfd, const char *path,
             uid_t owner, gid_t group, int flags);
Exigences des macros de test de fonctionnalités pour glibc (voir feature_test_macros(7)) :

fchown(), lchown() :

    /* Depuis glibc 2.12 : */ _POSIX_C_SOURCE >= 200809L
        || _XOPEN_SOURCE >= 500
        || /* glibc <= 2.19 : */ _BSD_SOURCE

fchownat() :

    Depuis glibc 2.10 :
        _POSIX_C_SOURCE >= 200809L
    Avant glibc 2.10 :
        _ATFILE_SOURCE

DESCRIPTION

Ces appels système changent le propriétaire et le groupe d'un fichier. Les appels système chown(), fchown() et lchown() ne diffèrent que par la manière dont le fichier est spécifié :

•
chown() change le propriétaire du fichier spécifié par path, qui est référencé s'il s'agit d'un lien symbolique.
•
fchown() change le propriétaire du fichier auquel fait référence le descripteur de fichier ouvert fd.
•
lchown() est comme chown(), mais ne référence pas les liens symboliques.

Seul un processus privilégié (Linux : un processus possédant la capacité CAP_CHOWN ) peut changer le propriétaire d'un fichier. Le propriétaire d'un fichier peut changer le groupe du fichier pour n'importe quel groupe dont ce propriétaire est membre. Un processus privilégié (Linux : avec CAP_CHOWN) peut changer le groupe arbitrairement.

Si owner ou group est spécifié comme -1, alors cet identifiant n'est pas modifié.

Lorsque le propriétaire ou le groupe d'un fichier exécutable est changé par un utilisateur non privilégié, les bits de mode S_ISUID et S_ISGID sont effacés. POSIX ne spécifie pas si cela devrait également se produire lorsque root effectue le chown() ; le comportement de Linux dépend de la version du noyau, et depuis Linux 2.2.13, root est traité comme les autres utilisateurs. Dans le cas d'un fichier non exécutable par le groupe (c'est-à-dire un fichier pour lequel le bit S_IXGRP n'est pas défini), le bit S_ISGID indique le verrouillage obligatoire et n'est pas effacé par un chown().

Lorsque le propriétaire ou le groupe d'un fichier exécutable est changé (par n'importe quel utilisateur), tous les ensembles de capacités du fichier sont effacés.

fchownat()

L'appel système fchownat() fonctionne exactement de la même manière que chown(), à l'exception des différences décrites ici.

Si path est relatif, alors il est interprété relativement au répertoire auquel fait référence le descripteur de fichier dirfd (plutôt que relativement au répertoire de travail courant du processus appelant, comme c'est le cas pour chown() avec un chemin relatif).

Si path est relatif et dirfd est la valeur spéciale AT_FDCWD, alors path est interprété relativement au répertoire de travail courant du processus appelant (comme chown()).

Si path est absolu, alors dirfd est ignoré.

L'argument flags est un masque de bits créé en combinant par OU logique 0 ou plusieurs des valeurs suivantes :

AT_EMPTY_PATH (depuis Linux 2.6.39)
Si path est une chaîne vide, opérer sur le fichier auquel fait référence dirfd (qui peut avoir été obtenu à l'aide de l'indicateur open(2) O_PATH ). Dans ce cas, dirfd peut faire référence à n'importe quel type de fichier, pas seulement à un répertoire. Si dirfd est AT_FDCWD, l'appel opère sur le répertoire de travail courant. Cet indicateur est spécifique à Linux ; définissez _GNU_SOURCE pour obtenir sa définition.
AT_SYMLINK_NOFOLLOW
Si path est un lien symbolique, ne le référence pas : opérer à la place sur le lien lui-même, comme lchown(). (Par défaut, fchownat() référence les liens symboliques, comme chown().)

Voir openat(2) pour une explication de la nécessité de fchownat().

VALEUR RENVOYÉE

En cas de succès, zéro est renvoyé. En cas d'erreur, -1 est renvoyé et errno est défini pour indiquer l'erreur.

ERREURS

Selon le système de fichiers, des erreurs autres que celles listées ci-dessous peuvent être renvoyées.

Les erreurs plus générales pour chown() sont listées ci-dessous.

EACCES
La permission de recherche est refusée sur un composant du préfixe du chemin. (Voir aussi path_resolution(7).)
EBADF
(fchown()) fd n'est pas un descripteur de fichier ouvert valide.
EBADF
(fchownat()) path est relatif mais dirfd n'est ni AT_FDCWD ni un descripteur de fichier valide.
EFAULT
path pointe en dehors de votre espace d'adressage accessible.
EINVAL
(fchownat()) Indicateur invalide spécifié dans flags.
EIO
(fchown()) Une erreur d'E/S de bas niveau s'est produite lors de la modification de l'inode.
ELOOP
Trop de liens symboliques ont été rencontrés lors de la résolution de path.
ENAMETOOLONG
path est trop long.
ENOENT
Le fichier n'existe pas.
ENOMEM
Mémoire noyau insuffisante disponible.
ENOTDIR
Un composant du préfixe du chemin n'est pas un répertoire.
ENOTDIR
(fchownat()) path est relatif et dirfd est un descripteur de fichier faisant référence à un fichier autre qu'un répertoire.
EPERM
Le processus appelant n'avait pas les permissions requises (voir ci-dessus) pour changer le propriétaire et/ou le groupe.
EPERM
Le fichier est marqué immuable ou en ajout uniquement. (Voir FS_IOC_SETFLAGS(2const).)
EROFS
Le fichier nommé réside sur un système de fichiers en lecture seule.

VERSIONS

La version 4.4BSD ne peut être utilisée que par le superutilisateur (c'est-à-dire, les utilisateurs ordinaires ne peuvent pas céder leurs fichiers).

BIBLIOTHQUE

SYNTAXE

#include <unistd.h>

int chown(const char *pathname, uid_t owner, gid_t group);

#include <unistd.h>

int chown32(const char *pathname, int32_t owner, int32_t group);
int fchown32(int fd, int32_t owner, int32_t group);
int lchown32(const char *pathname, int32_t owner, int32_t group);

Utiliser `_FILE_OFFSET_BITS` pour obtenir les prototypes ci-dessus.

Utiliser `_GNU_SOURCE` pour obtenir les prototypes des fonctions suivantes :

#include <fcntl.h>
#include <sys/types.h>

int chownat(int dirfd, const char *pathname, uid_t owner, gid_t group, int flags);
int fchownat(int dirfd, const char *pathname, uid_t owner, gid_t group, int flags);

DESCRIPTION

Ces appels système modifient le propriétaire (UID) et/ou le groupe (GID) d'un fichier. Le propriétaire et le groupe sont spécifiés par les arguments owner et group respectivement. Si un argument est spécifié comme -1, alors le propriétaire ou le groupe correspondant n'est pas modifié.

Seul le superutilisateur (root) peut changer la propriété d'un fichier. Un processus non privilégié peut changer le propriétaire d'un fichier seulement s'il est le propriétaire du fichier, et le nouveau propriétaire est soit le propriétaire actuel, soit -1, et le nouveau groupe est soit le GID effectif du processus, soit un GID supplémentaire du processus, soit -1.

L'appel système chown() s'applique au fichier pointé par le chemin pathname. S'il s'agit d'un lien symbolique, il est traité comme tout autre fichier ordinaire et ce n'est pas le fichier vers lequel il pointe qui est modifié.

L'appel système fchown() s'applique au fichier ouvert dont le descripteur est fd.

L'appel système lchown() est similaire à chown(), mais il est appliqué au lien symbolique lui-même, et non au fichier vers lequel il pointe.

Les appels système chown32(), fchown32() et lchown32() ont été introduits pour prendre en charge les identifiants d'utilisateur et de groupe 32 bits sur les systèmes plus anciens où ces identifiants ne pouvaient pas dépasser 16 bits. Les fonctions wrapper de glibc (voir plus bas) traitent ces différences automatiquement.

L'appel système chownat() et fchownat() sont analogues à chown() et fchown() respectivement, mais avec les spécificités suivantes :

  • S'il s'agit de pathname relatif, il est interprété par rapport au descripteur de fichier dirfd (un descripteur de fichier pointant vers un répertoire) plutôt que par rapport au répertoire de travail actuel. S'il est spécifié comme AT_FDCWD dans dirfd, alors pathname est interprété par rapport au répertoire de travail actuel, comme d'habitude.
  • Les appels chownat() et fchownat() peuvent modifier la propriété des fichiers dans des répertoires spécifiés par dirfd sans avoir besoin d'accéder au répertoire de travail actuel.
  • Les appels chownat() et fchownat() peuvent fonctionner sur des fichiers référencés par des descripteurs de fichier créés avec l'indicateur O_PATH.

L'argument flags peut être 0 ou une combinaison de valeurs suivantes :

AT_EMPTY_PATH
Si pathname est une chaîne vide, alors dirfd est utilisé pour faire référence au fichier. Si dirfd n'est pas AT_FDCWD, alors il doit pointer vers le fichier dont la propriété doit être modifiée.
AT_NO_AUTOMOUNT
Ne pas déclencher de montage automatique si pathname traverse un point de montage.
AT_SYMLINK_NOFOLLOW
Si pathname pointe vers un lien symbolique, ne pas le suivre. C'est l'équivalent de lchown(). Sans cet indicateur, chownat() suit les liens symboliques, comme chown().

Le comportement de chown(), fchown() et lchown() concernant les GID lorsqu'un fichier est créé dépend de la manière dont le système de fichiers est monté et des options de montage utilisées. Ces options sont :

  • -o grpid (ou -o bsdgroups) : Le GID du nouveau fichier est le même que celui du répertoire parent.
  • -o ngrpid (ou -o sysvgroups) : Le GID du nouveau fichier est le GID effectif du processus créant le fichier, à moins que le bit set-group-ID ne soit activé sur le répertoire parent, auquel cas le GID du nouveau fichier est le même que celui du répertoire parent.

La plupart des systèmes de fichiers Linux, y compris ext2, ext3, ext4 et XFS, prennent en charge ces options. Les systèmes de fichiers qui ne prennent pas en charge ces options de montage se comportent comme s'ils avaient été montés avec -o ngrpid.

Lorsque vous créez un nouveau fichier (par exemple, par open(2) ou mkdir(2)), son propriétaire est défini sur le UID du système de fichiers du processus créant. Le groupe du fichier dépend d'une série de facteurs, notamment le type de système de fichiers, les options utilisées pour monter le système de fichiers et si le bit de mode set-group-ID est activé sur le répertoire parent.

Si le système de fichiers prend en charge les options de montage -o grpid (ou, de manière synonyme, -o bsdgroups) et -o ngrpid (ou, de manière synonyme, -o sysvgroups) de mount(8), alors les règles sont les suivantes :

•
Si le système de fichiers est monté avec -o grpid, alors le groupe d'un nouveau fichier est le même que celui du répertoire parent.
•
Si le système de fichiers est monté avec -o ngrpid et que le bit set-group-ID est désactivé sur le répertoire parent, alors le groupe d'un nouveau fichier est le même que le GID du système de fichiers du processus.
•
Si le système de fichiers est monté avec -o ngrpid et que le bit set-group-ID est activé sur le répertoire parent, alors le groupe d'un nouveau fichier est le même que celui du répertoire parent.

En date de Linux 4.12, les options de montage -o grpid et -o ngrpid sont prises en charge par ext2, ext3, ext4 et XFS. Les systèmes de fichiers qui ne prennent pas en charge ces options de montage suivent les règles de -o ngrpid.

Notes glibc

Sur les noyaux plus anciens où fchownat() n'est pas disponible, la fonction wrapper de glibc se rabat sur l'utilisation de chown() et lchown(). Lorsque path est relatif, glibc construit un nom de chemin basé sur le lien symbolique dans /proc/self/fd qui correspond à l'argument dirfd.

NFS

Les sémantiques de chown() sont délibérément violées sur les systèmes de fichiers NFS sur lesquels le mappage UID est activé. De plus, les sémantiques de tous les appels système qui accèdent au contenu du fichier sont violées, car chown() peut entraîner une révocation immédiate de l'accès sur des fichiers déjà ouverts. La mise en cache côté client peut entraîner un délai entre le moment où la propriété a été modifiée pour permettre l'accès à un utilisateur et le moment où le fichier peut effectivement être accédé par l'utilisateur sur d'autres clients.

Détails historiques

Les appels système Linux d'origine chown(), fchown() et lchown() ne prenaient en charge que les identifiants utilisateur et groupe 16 bits. Par la suite, Linux 2.4 a ajouté chown32(), fchown32() et lchown32(), prenant en charge les identifiants 32 bits. Les fonctions wrapper chown(), fchown() et lchown() de glibc traitent transparencement les variations entre les versions du noyau.

Avant Linux 2.1.81 (sauf 2.1.46), chown() ne suivait pas les liens symboliques. Depuis Linux 2.1.81, chown() suit les liens symboliques, et il existe un nouvel appel système lchown() qui ne suit pas les liens symboliques. Depuis Linux 2.1.86, ce nouvel appel (qui a les mêmes sémantiques que l'ancien chown()) a le même numéro d'appel système, et chown() a reçu le numéro nouvellement introduit.

EXEMPLES

Le programme suivant modifie la propriété du fichier nommé dans son deuxième argument de ligne de commande à la valeur spécifiée dans son premier argument de ligne de commande. Le nouveau propriétaire peut être spécifié soit comme un identifiant utilisateur numérique, soit comme un nom d'utilisateur (qui est converti en un identifiant utilisateur en utilisant getpwnam(3) pour effectuer une recherche dans le fichier de mots de passe du système).

Source du programme

#include <pwd.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/types.h>
#include <unistd.h>
int
main(int argc, char *argv[])
{
    char           *endptr;
    uid_t          uid;
    struct passwd  *pwd;
    if (argc != 3 || argv[1][0] == '\0') {
        fprintf(stderr, "%s <proprietaire> <fichier>\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    uid = strtol(argv[1], &endptr, 10);  /* Permettre une chaîne numérique */
    if (*endptr != '\0') {         /* N'était pas une chaîne purement numérique */
        pwd = getpwnam(argv[1]);   /* Essayer d'obtenir l'UID pour le nom d'utilisateur */
        if (pwd == NULL) {
            perror("getpwnam");
            exit(EXIT_FAILURE);
        }
        uid = pwd->pw_uid;
    }
    if (chown(argv[2], uid, -1) == -1) {
        perror("chown");
        exit(EXIT_FAILURE);
    }
    exit(EXIT_SUCCESS);
}
