Prise en charge des CGI locaux dans Chawan

Chawan prend en charge l'invocation de scripts CGI placés dans un répertoire spécifié dans l'option de configuration external.cgi-dir. Par défaut, cela est défini sur $CHA_DIR/cgi-bin (c'est-à-dire ~/.chawan/cgi-bin ou ~/.config/chawan/cgi-bin, selon l'emplacement de config.toml) et /usr/local/libexec/chawan/cgi-bin.

Un script CGI dans l'un de ces répertoires peut être exécuté en visitant l'URL cgi-bin:nom-du-script. $PATH_INFO et $QUERY_STRING sont définis comme d'habitude, c'est-à-dire cgi-bin:nom-du-script/abcd?defgh=ijkl définira $PATH_INFO sur /abcd, et $QUERY_STRING sur defgh=ijkl.

Notes supplémentaires sur le traitement des chemins CGI :

  • L'URL doit être opaque, vous ne devez donc pas ajouter de double slash après le schéma. Par exemple , cgi-bin://nom-du-script NE fonctionnera PAS, seulement cgi-bin:nom-du-script.
  • Les chemins commençant par /cgi-bin/ ou /$LIB/ sont automatiquement dépouillés de ce segment. Ainsi, par exemple, cgi-bin:/cgi-bin/nom-du-script devient cgi-bin:nom-du-script.
  • Si external.w3m-cgi-compat est vrai, les URL de type file: sont converties en URL cgi-bin: si le nom de chemin commence par /cgi-bin/, /$LIB/, ou le chemin d'un script CGI local. Remarque : ceci n'est pas sûr, veuillez ne pas l'utiliser sauf nécessité absolue.
  • Les chemins absolus sont acceptés comme par exemple cgi-bin:/chemin/vers/repertoire-cgi/nom-du-script. Notez cependant que cela ne fonctionne que si /chemin/vers/repertoire-cgi a déjà été spécifié comme répertoire CGI dans external.cgi-dir.

En-têtes

Les scripts CGI locaux peuvent envoyer certains en-têtes que Chawan interprétera spécialement (et ne transmettra donc pas par exemple à l'API fetch, etc.) :

  • Status : Interprété comme le code d'état HTTP.
  • Cha-Control : En-tête spécial, voir ci-dessous.

Ces en-têtes doivent être envoyés avant tout autre en-tête normal. Les en-têtes reçus après un en-tête normal ou un en-tête Cha-Control: ControlDone seront traités comme des en-têtes normaux.

La valeur de l'en-tête Cha-Control est analysée comme suit :

Cha-Control-Value = Commande *Parametre
Commande = ALPHA *ALPHA
Parametre = SPACE *CHAR

En d'autres termes, il s'agit de Commande [Param1] [Param2] ....

Les commandes actuellement disponibles sont :

  • Connected : Ne prend aucun paramètre. Doit être le premier en-tête rapporté ; cela signifie que la connexion au serveur a été établie avec succès, mais qu'aucune donnée n'a encore été reçue. Lorsqu'un autre en-tête est envoyé en premier, Chawan agira comme si un en-tête Cha-Control: Connected avait été implicitement envoyé avant celui-ci.
  • ConnectionError : Doit être le premier en-tête rapporté. Le paramètre 1 est le code d'erreur, voir ci-dessous. Si des paramètres suivants sont donnés, ils sont concaténés pour former un message d'erreur personnalisé.

Remarque : des messages d'erreur courts mais descriptifs sont préférés, les messages qui ne tiennent pas à l'écran sont actuellement tronqués.

•
ControlDone : Indique qu'aucun autre en-tête spécial ne sera envoyé ; cela signifie que les en-têtes Cha-Control et Status envoyés après cela doivent être interprétés comme des en-têtes normaux (et donc par exemple être disponibles pour le code JS appelant le script en utilisant l'API fetch).

AVERTISSEMENT : cet en-tête doit être envoyé avant tout en-tête non codé en dur qui prend des entrées externes. Par exemple, un client HTTP devrait envoyer Cha-Control: ControlDone avant de renvoyer les en-têtes récupérés.

Vous trouverez ci-dessous une liste des codes d'erreur et de leurs contreparties en texte. Les scripts CGI peuvent utiliser l'un ou l'autre (mais pas les deux) dans un en-tête ConnectionError.

  • 1 InternalError : Une erreur interne a empêché le script de récupérer la ressource demandée. Les scripts CGI peuvent également l'utiliser pour signaler qu'ils n'ont aucune information sur ce qui s'est mal passé.
  • 2 InvalidMethod : Le client a demandé des données en utilisant une méthode non prise en charge par ce protocole.
  • 3 InvalidURL : L'URL de la requête n'a pas pu être interprétée comme une URL valide pour ce format.
  • 4 FileNotFound : Aucun fichier n'a été trouvé à l'adresse demandée, la requête est donc dénuée de sens. Remarque : ceci ne doit être utilisé que par des protocoles qui ne reposent pas sur une architecture client-serveur, par exemple l'accès aux fichiers locaux, les bases de données locales ou les mécanismes de récupération de fichiers peer-to-peer. Un serveur répondant par « fichier non trouvé » N'EST PAS une erreur de connexion, et est mieux représenté par une réponse avec un code d'état 404.
  • 5 ConnectionRefused : Le serveur a refusé d'établir une connexion.
  • 6 ProxyRefusedToConnect : Le proxy a refusé d'établir une connexion.
  • 7 FailedToResolveHost : Le nom d'hôte n'a pas pu être résolu.
  • 8 FailedToResolveProxy : Le proxy n'a pas pu être résolu.
  • 9 ProxyAuthFail : Le proxy a refusé le nom d'utilisateur/mot de passe fourni.
  • 10 InvalidResponse : La réponse du serveur dévie tellement de la spécification qu'elle ne peut pas être traitée de manière significative.
  • 11 ProxyInvalidResponse : La réponse du proxy dévie tellement de la spécification qu'elle ne peut pas être traitée de manière significative.

Variables d'environnement

Chawan définit les variables d'environnement suivantes :

  • SERVER_SOFTWARE="Chawan"
  • SERVER_PROTOCOL="HTTP/1.0"
  • SERVER_NAME="localhost"
  • SERVER_PORT="80"
  • REMOTE_HOST="localhost"
  • REMOTE_ADDR="127.0.0.1"
  • GATEWAY_INTERFACE="CGI/1.1"
  • SCRIPT_NAME="/cgi-bin/nom-du-script" si appelé avec un chemin relatif, et "/chemin/vers/script/nom-du-script" si appelé avec un chemin absolu.
  • SCRIPT_FILENAME="/chemin/vers/script/nom-du-script"
  • QUERY_STRING= la chaîne de requête (c'est-à-dire URL.search). Cette variable est encodée en pourcentage.
  • PATH_INFO= tout ce qui suit le nom du chemin du script, par exemple , pour cgi-bin:nom-du-script/abcd/efgh "/abcd/efgh". Cette variable N'EST PAS encodée en pourcentage.
  • REQUEST_URI="$SCRIPT_NAME/$PATH_INFO?$QUERY_STRING
  • REQUEST_METHOD= méthode HTTP utilisée pour faire la requête, par exemple GET ou POST
  • REQUEST_HEADERS= Une liste de tous les en-têtes de cette requête, séparés par des sauts de ligne.
  • CHA_LIBEXEC_DIR= Le répertoire libexec que Chawan a été configuré pour utiliser lors de la compilation. Voir la section des outils ci-dessous pour plus de détails sur l'utilité de ceci.
  • CONTENT_TYPE= pour les requêtes POST, l'en-tête Content-Type. Non défini pour les autres types de requêtes (par exemple GET).
  • CONTENT_LENGTH= la longueur du contenu, si $CONTENT_TYPE a été défini.
  • ALL_PROXY= si un proxy a été défini, l'URL du proxy. AVERTISSEMENT : pour des raisons de sécurité, ceci doit être respecté lors de l'établissement de connexions externes. Si un script CGI ne prend pas en charge les proxys, il ne doit jamais établir de connexions externes lorsque la variable ALL_PROXY est définie, mais plutôt renvoyer un message d'erreur.
  • HTTP_COOKIE= si défini, l'en-tête Cookie.
  • HTTP_REFERER=

  • CHA_TMP_DIR= répertoire utilisé pour stocker les fichiers temporaires.
  • CHA_DIR= emplacement du fichier de configuration.

    Si example://username:password@example.org:1234/path/name.html?example est l'URL d'origine, alors :

    • MAPPED_URI_SCHEME= le schéma de l'URL d'origine, dans ce cas example.
    • MAPPED_URI_USERNAME= la partie nom d'utilisateur, dans ce cas username. Si aucun nom d'utilisateur n'a été spécifié, la variable est définie comme chaîne vide.
    • MAPPED_URI_PASSWORD= la partie mot de passe, dans ce cas password. Si aucun mot de passe n'a été spécifié, la variable est définie comme chaîne vide.
    • MAPPED_URI_HOST= la partie hôte, dans ce cas host.org Si aucun hôte n'a été spécifié, la variable est définie comme chaîne vide. (Un exemple d'URL sans hôte : about:blank, ici blank est le nom du chemin.)
    • MAPPED_URI_PORT= le port, dans ce cas 1234. Si aucun port n'a été spécifié, la variable est définie comme chaîne vide. (Dans ce cas, le script CGI est censé utiliser le port par défaut du schéma, s'il y en a un.)
    • MAPPED_URI_PATH= le nom du chemin, dans ce cas /path/name.html?example. Si aucun chemin n'a été spécifié, la variable est définie comme chaîne vide. Le nom du chemin est encodé en pourcentage.
    • MAPPED_URI_QUERY= la chaîne de requête, dans ce cas example. Contrairement à JavaScript, aucun point d'interrogation n'est ajouté au début de la chaîne. La chaîne de requête est également encodée en pourcentage.

    La partie fragment est volontairement omise.

    Corps de la requête

    Si le corps de la requête n'est pas vide, il est transmis en flux au programme via l'entrée standard.

    Notez qu'il peut s'agir d'une requête application/x-www-form-urlencoded ou d'une requête multipart/form-data ; CONTENT_TYPE stocke des informations sur le type de requête et, dans le cas d'une requête multipart, la frontière également.

    Outils

    Chawan fournit certains binaires d'assistance qui peuvent être utiles pour les scripts CGI. Ceux-ci peuvent être accessibles de manière portable en exécutant "$CHA_LIBEXEC_DIR"/[program].

    Actuellement, les outils suivants sont disponibles :

    • urldec: décode en pourcentage les chaînes passées sur l'entrée standard.
    • urlenc: encode en pourcentage les chaînes passées sur l'entrée standard, en prenant un jeu d'encodage en pourcentage comme premier paramètre.

    Dépannage

    Notez que la sortie d'erreur standard est redirigée vers la console du navigateur (par défaut, M-cM-c). Cela facilite le débogage d'un script CGI défaillant, mais peut aussi ralentir le navigateur en cas de journalisation excessive. Si ce n'est pas le comportement désiré, enveloppez votre script dans un script shell qui redirige stderr vers /dev/null.

    Mon script renvoie un message d'erreur « Failed to execute script ».

    Cela signifie que l'appel execl au script a échoué. Assurez-vous que le bit exécutable de votre script CGI est défini, c'est-à-dire exécutez chmod +x /path/to/cgi/script.

    Mon script renvoie un message d'erreur « invalid CGI path ».

    Assurez-vous que vous n'avez pas inclus de barres obliques initiales. Rappel : cgi-bin://script-name ne fonctionne pas, utilisez cgi-bin:script-name.

    Mon script renvoie un message d'erreur « CGI file not found ».

    Vérifiez à nouveau que votre script CGI se trouve à l'emplacement correct. Assurez-vous également que vous n'appelez pas accidentellement le script avec un chemin absolu via cgi-bin:/script-name (au lieu de la forme correcte cgi-bin:script-name).

    Il est également possible que external.cgi-dir ne soit pas réellement défini sur le répertoire où se trouve votre script. Notez que par défaut, cela dépend du chemin du binaire, donc par exemple si votre binaire se trouve dans ~/src/chawan/target/release/bin/cha, mais que vous mettez votre script CGI dans /usr/local/libexec/chawan/cgi-bin, alors cela ne fonctionnera pas.

    Mon script renvoie un message d'erreur « failed to set up CGI script ».

    Cela signifie que soit pipe soit fork a échoué. Peut-être que vous manquez de mémoire ?
