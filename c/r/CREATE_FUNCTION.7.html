DESCRIPTIO

N

CREATE FUNCTION définit une nouvelle fonction. CREATE OR REPLACE FUNCTION créera soit une nouvelle fonction, soit remplacera une définition existante. Pour pouvoir définir une fonction, l'utilisateur doit disposer du privilège USAGE sur le

langage.

Si un nom de schéma est inclus, la fonction est créée dans le schéma spécifié. Sinon, elle est créée dans le schéma courant. Le nom de la nouvelle fonction ne doit correspondre à aucune fonction ou procédure existante ayant les mêmes types d'arguments d'entrée dans le même schéma. Cependant, les fonctions et procédures de types d'arguments différents peuvent partager un nom (on appelle cela le surchargement)

.

Pour remplacer la définition actuelle d'une fonction existante, utilisez CREATE OR REPLACE FUNCTION. Il n'est pas possible de changer le nom ou les types d'arguments d'une fonction de cette manière (si vous essayiez, vous créeriez en réalité une nouvelle fonction distincte). De plus, CREATE OR REPLACE FUNCTION ne vous permettra pas de changer le type de retour d'une fonction existante. Pour ce faire, vous devez supprimer et recréer la fonction. (Lors de l'utilisation de paramètres OUT, cela signifie que vous ne pouvez pas changer les types des paramètres OUT autres qu'en supprimant la fonction.

)

Lorsque CREATE OR REPLACE FUNCTION est utilisé pour remplacer une fonction existante, la propriété et les permissions de la fonction ne changent pas. Toutes les autres propriétés de la fonction reçoivent les valeurs spécifiées ou implicites dans la commande. Vous devez être le propriétaire de la fonction pour la remplacer (ce qui inclut le fait d'être membre du rôle propriétaire)

.

Si vous supprimez puis recréez une fonction, la nouvelle fonction n'est pas la même entité que l'ancienne ; vous devrez supprimer les règles, vues, déclencheurs, etc. existants qui font référence à l'ancienne fonction. Utilisez CREATE OR REPLACE FUNCTION pour changer une définition de fonction sans casser les objets qui font référence à la fonction. De plus, ALTER FUNCTION peut être utilisé pour changer la plupart des propriétés auxiliaires d'une fonction

existante.

L'utilisateur qui crée la fonction en devient le

propriétaire.

Pour pouvoir créer une fonction, vous devez disposer du privilège USAGE sur les types d'arguments et le type de

retour.

l'écriture de fonctions.

IMMUTABLE
STABLE
VOLATIL

E
Ces attributs informent l'optimiseur de requêtes du comportement de la fonction. Au plus un choix peut être spécifié. Si aucun de ceux-ci n'apparaît, VOLATILE est l'hypothèse par défaut.

IMMUTABLE indique que la fonction ne peut pas modifier la base de données et retourne toujours le même résultat pour les mêmes valeurs d'arguments ; c'est-à-dire qu'elle ne fait pas de recherches dans la base de données ni n'utilise autrement d'informations non directement présentes dans sa liste d'arguments. Si cette option est donnée, tout appel de la fonction avec des arguments entièrement constants peut être immédiatement remplacé par la valeur de la

fonction.

STABLE indique que la fonction ne peut pas modifier la base de données, et qu'au sein d'un même balayage de table, elle retournera toujours le même résultat pour les mêmes valeurs d'arguments, mais que son résultat pourrait changer entre des instructions SQL. C'est le choix approprié pour les fonctions dont les résultats dépendent de recherches dans la base de données, de variables de paramètres (telles que le fuseau horaire actuel), etc. (C'est inapproprié pour les déclencheurs AFTER qui souhaitent interroger les lignes modifiées par la transactionmmand.) Also note that the current_timestamp family of functions qualify as stable, since their values do not change within a

transaction.

VOLATILE indique que la valeur de la fonction peut changer même au sein d'un seul balayage de table, de sorte qu'aucune optimisation ne peut être effectuée. Relativement peu de fonctions de base de données sont volatiles en ce sens ; quelques exemples sont random(), currval(), timeofday(). Mais notez que toute fonction qui a des effets de bord doit être classée comme volatile, même si son résultat est tout à fait prévisible, afin d'empêcher que les appels ne soient optimisés ; un exemple est setval()

.

LEAKPROO

F
LEAKPROOF indique que la fonction n'a pas d'effets de bord. Elle ne révèle aucune information sur ses arguments autres que par sa valeur de retour. Par exemple, une fonction qui lance un message d'erreur pour certaines valeurs d'arguments mais pas pour d'autres, ou qui inclut les valeurs des arguments dans un message d'erreur, n'est pas étanche. Cela affecte la manière dont le système exécute les requêtes contre des vues créées avec l'option security_barrier ou des tables avec la sécurité au niveau des lignes activée. Le système fera respecter les conditions des politiques de sécurité et des vues de barrière de sécurité avant toute condition fournie par l'utilisateur à partir de la requête elle-même qui contient des fonctions non étanches, afin d'éviter l'exposition involontaire de données. Les fonctions et les opérateurs marqués comme étanches sont considérés comme dignes de confiance et peuvent être exécutés avant les conditions des politiques de sécurité et des vues de barrière de sécurité. De plus, les fonctions qui ne prennent pas d'arguments ou auxquelles aucun argument de la vue de barrière de sécurité ou de la table n'est passé n'ont pas besoin d'être marquées comme étanches pour être exécutées avant les conditions de sécurité. Voir CREATE VIEW (CREATE_VIEW(7)) et la section 39.5. Cette option ne peut être définie que par le superutilisateur
.

CALLED ON NULL INPUT (par défaut) indique que la fonction sera appelée normalement lorsque certains de ses arguments sont nuls. Il est alors de la responsabilité de l'auteur de la fonction de vérifier les valeurs nulles si nécessaire et de répondre de manière appropriée.

RETURNS NULL ON NULL INPUT ou STRICT indique que la fonction renvoie toujours null lorsque l'un de ses arguments est null. Si ce paramètre est spécifié, la fonction n'est pas exécutée lorsqu'il y a des arguments nuls ; à la place, un résultat null est supposé

PARALLE

L
PARALLEL UNSAFE indique que la fonction ne peut pas être exécutée en mode parallèle ; la présence d'une telle fonction dans une instruction SQL force un plan d'exécution séquentiel. C'est le défaut. PARALLEL RESTRICTED indique que la fonction peut être exécutée en mode parallèle, mais seulement dans le processus leader du groupe parallèle. PARALLEL SAFE indique que la fonction peut être exécutée en toute sécurité en mode parallèle sans restriction, y compris dans les processus de travail parallèles.

Les fonctions doivent être étiquetées comme non sûres pour le parallélisme si elles modifient l'état de la base de données, changent l'état de la transaction (autrement qu'en utilisant une sous-transaction pour la récupération d'erreur), accèdent aux séquences (par exemple, en appelant currval) ou apportent des modifications persistantes aux paramètres. Elles doivent être étiquetées comme restreintes pour le parallélisme si elles accèdent à des tables temporaires, à l'état de la connexion c

lient, à des curseurs, à des instructions préparées, ou à un état local divers du backend que le système ne peut pas synchroniser en mode parallèle (par exemple, setseed ne peut pas être exécuté autrement que par le leader car un changement fait par un autre processus ne serait pas reflété dans le leader). En général, si une fonction est étiquetée comme sûre alors qu'elle est restreinte ou non sûre, ou si elle est étiquetée comme restreinte alors qu'elle est en fait non sûre, elle peut lan
cer des erreurs ou produire de mauvais résultats lorsqu'elle est utilisée dans une requête parallèle. Les fonctions en langage C pourraient en théorie présenter un comportement totalement indéfini si elles sont mal étiquetées, car il n'y a aucun moyen pour le système de se protéger contre du code C arbitraire, mais dans la plupart des cas le résultat ne sera pas pire que pour n'importe quelle autre fonction. En cas de doute, les fonctions doivent être étiquetées comme UNSAFE, qui est le défaut.

SURCHARG

E

PostgreSQL permet la surcharge de fonctions ; c'est-à-dire, le même nom peut être utilisé pour plusieurs fonctions différentes à condition qu'elles aient des types d'arguments d'entrée distincts. Que vous l'utilisiez ou non, cette capacité entraîne des précautions de sécurité lors de l'appel de fonctions dans des bases de données où certains utilisateurs se méfient d'autres utilisateurs ; voir la section 10.

3.

Deux fonctions sont considérées comme identiques si elles ont les mêmes noms et les mêmes types d'arguments d'entrée, en ignorant les paramètres OUT. Ainsi, par exemple, ces déclarations entrent en conflit

: 
CREATE FUNCTION foo(int) ...
CREATE FUNCTION foo(int, out text) .
.
.

Les fonctions qui ont des listes de types d'arguments différentes ne seront pas considérées comme entrant en conflit au moment de la création, mais si des valeurs par défaut sont fournies, elles pourraient entrer en conflit lors de l'utilisation. Par exemple,

considérez 
CREATE FUNCTION foo(int) ...
CREATE FUNCTION foo(int, int default 42) .
.
.

Un appel foo(10) échouera en raiso

n de l'ambiguïté concernant la
fonction qui devrait être appelée.

NOTE

S

La syntaxe complète de type SQL est autorisée pour déclarer les arguments et la valeur de retour d'une fonction. Cependant, les modificateurs de type entre parenthèses (par exemple, le champ de précision pour le type numeric) sont ignorés par CREATE FUNCTION. Ainsi, par exemple, CREATE FUNCTION foo (varchar(10)) ... est exactement la même chose que CREATE FUNCTION foo (varchar) ...

.

Lors du remplacement d'une fonction existante avec CREATE OR REPLACE FUNCTION, il y a des restrictions sur le changement des noms de paramètres. Vous ne pouvez pas changer le nom déjà attribué à un paramètre d'entrée (bien que vous puissiez ajouter des noms à des paramètres qui n'en avaient pas auparavant). S'il y a plus d'un paramètre de sortie, vous ne pouvez pas changer les noms des paramètres de sortie, car cela changerait les noms de colonnes du type composite anonyme qui décrit le résultat de la fonction. Ces restrictions sont mises en place pour garantir que les appels existants de la fonction ne cessent pas de fonctionner lorsqu'elle est

remplacée.

Si une fonction est déclarée STRICT avec un argument VARIADIC, le test de sévérité vérifie que le tableau variadique dans son ensemble est non nul. La fonction sera

toujours appelée si le tabl
eau a des éléments nuls.

ÉCRIRE EN TOUTE SÉCURITÉ DES FONCTIONS SECURITY

DEFINER

Étant donné qu'une fonction SECURITY DEFINER est exécutée avec les privilèges du propriétaire de la fonction, il faut veiller à ce que la fonction ne puisse pas être mal utilisée. Pour des raisons de sécurité, search_path doit être défini de manière à exclure tout schéma accessible en écriture par des utilisateurs non fiables. Cela empêche les utilisateurs malveillants de créer des objets (par exemple des tables, des fonctions et des opérateurs) qui masquent les objets destinés à être utilisés par la fonction. Particulièrement important à cet égard est le schéma des tables temporaires, qui est recherché en premier par défaut et est normalement accessible en écriture par n'importe qui. Un arrangement sûr peut être obtenu en forçant le schéma temporaire à être recherché en dernier. Pour ce faire, écrivez pg_temp comme dernière entrée dans search_path. Cette fonction illustre une utilisation sûre

: 
CREATE FUNCTION check_password(uname TEXT, pass TEXT)
RETURNS BOOLEAN AS $$
DECLARE passed BOOLEAN;
BEGIN
        SELECT  (pwd
= $2) INTO passed FROM pwds WHERE username = $1; RETURN passed; END; $$ LANGUAGE plpgsql SEC
URITY DEFINER -- Définit un search_path sûr : schéma(s) de confiance, puis 'pg_temp'. SET search_path = admin, pg_temp;

L'intention de cette fonction est d'accéder à une table admin.pwds. Mais sans la clause SET, ou avec une clause SET mentionnant uniquement admin, la fonction pourrait être détournée en créant une table temporaire nommée

pwds.

Si la fonction security definer a l'intention de créer des rôles, et si elle s'exécute en tant que non-superutilisateur, createrole_self_grant devrait également être défini à une valeur connue à l'aide de la clause

SET.

Un autre point à garder à l'esprit est que par défaut, le privilège d'exécution est accordé à PUBLIC pour les fonctions nouvellement créées (voir la section 5.8 pour plus d'informations). Souvent, vous souhaiterez restreindre l'utilisation d'une fonction security definer à certains utilisateurs seulement. Pour ce faire, vous devez révoquer les privilèges PUBLIC par défaut puis accorder sélectivement le privilège d'exécution. Pour éviter une période où la nouvelle fonction est accessible à tous, créez-la et définissez les privilèges au sein d'une seule transaction. Par exemple

: 
BEGIN;
CREATE FUNCTION check_password(uname TEXT, pass TEXT)
... SECURITY DEFINER; REVOKE ALL ON FUNCTION check_password
(uname TEXT, pass TEXT) FROM PUBLIC; GRANT EXECUTE ON FUNCT
ION check_password(uname TEXT, pass TEXT) TO admins; COMMIT;

É

Une commande CREATE FUNCTION est définie dans la norme SQL. L'implémentation de PostgreSQL peut être utilisée de manière compatible mais comporte de nombreuses extensions. Inversement, la norme SQL spécifie un certain nombre de fonctionnalités optionnelles qui ne sont pas implémentées dans

PostgreSQL.

Les points de compatibilité importants sont les suivants

:
•OR REPLACE est une extension
PostgreSQL.
•Pour la compatibilité avec certains autres systèmes de bases de données, argmode peut être écrit avant ou après argname. Mais seule la première manière est conforme à la
norme.
•Pour les valeurs par défaut des paramètres, la norme SQL spécifie uniquement la syntaxe avec le mot-clé DEFAULT. La syntaxe avec = est utilisée dans T-SQL et
Firebird.
•Le modificateur SETOF est une extension
PostgreSQL.
•Seul SQL est normalisé comme
langage.
•Tous les autres attributs, à l'exception de CALLED ON NULL INPUT et RETURNS NULL ON NULL INPUT, ne sont pas

Les fonctions LANGUAGE SQL simples peuvent être écrites d'une manière à la fois conforme à la norme et portable
