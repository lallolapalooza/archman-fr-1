CRON(8) Administration système CRON(8)

NOM

crond - démon pour exécuter les commandes planifiées

SYNTAXE

crond [-c | -h | -i | -n | -p | -P | -s | -m<commandecourriel>]
crond -x [ext,sch,proc,pars,load,misc,test,bit]
crond -V

DESCRIPTION

Cron est lancé depuis /etc/rc.d/init.d ou /etc/init.d lorsque des scripts sysvinit classiques sont utilisés. Si systemd est activé, alors un fichier d'unité est installé dans /lib/systemd/system/crond.service et le démon est démarré par la commande systemctl start crond.service. Il retourne immédiatement, donc il n'est pas nécessaire de le démarrer avec le paramètre '&'.

Cron recherche dans /var/spool/cron les fichiers crontab qui sont nommés d'après les comptes dans /etc/passwd ; les crontabs trouvés sont chargés en mémoire. Cron recherche également /etc/anacrontab et tous les fichiers dans le répertoire /etc/cron.d, qui ont un format différent (voir crontab(5)). Cron examine toutes les crontabs stockées et vérifie chaque tâche pour voir si elle doit être exécutée dans la minute courante. Lors de l'exécution des commandes, toute sortie est envoyée par courrier au propriétaire de la crontab (ou à l'utilisateur spécifié dans la variable d'environnement MAILTO de la crontab, si elle existe). Toute sortie de tâche peut également être envoyée à syslog en utilisant l'option -s.

Il existe deux méthodes pour vérifier les changements dans les crontabs. La première méthode consiste à vérifier le timestamp (heure de modification) d'un fichier. La seconde méthode utilise le support inotify. L'utilisation d'inotify est enregistrée dans le journal /var/log/cron après le démarrage du démon. Le support inotify vérifie les changements dans toutes les crontabs et n'accède au disque dur que lorsqu'un changement est détecté.

Lorsqu'on utilise l'option de timestamp, Cron vérifie les timestamps de ses crontabs chaque minute pour détecter tout changement et recharge les crontabs qui ont changé. Il n'est pas nécessaire de redémarrer Cron après la modification de certaines crontabs. L'option de timestamp est également utilisée lorsque inotify ne peut pas être initialisé.

Cron vérifie ces fichiers et répertoires :

/etc/crontab
crontab système. De nos jours, le fichier est vide par défaut. Initialement, il était généralement utilisé pour exécuter des tâches quotidiennes, hebdomadaires, mensuelles. Par défaut, ces tâches sont maintenant exécutées via anacron qui lit le fichier de configuration /etc/anacrontab. Voir anacrontab(5) pour plus de détails.
/etc/cron.d/
répertoire contenant les cronjobs système stockés pour différents utilisateurs.
/var/spool/cron
répertoire contenant les crontabs utilisateur créées par la commande crontab.

Notez que la commande crontab(1) met à jour le timestamp du répertoire de spool à chaque modification d'une crontab.

Heure d'été et autres changements d'heure

Les changements d'heure locaux de moins de trois heures, tels que ceux causés par les changements d'heure d'été, sont traités de manière spéciale. Cela s'applique uniquement aux tâches qui s'exécutent à une heure spécifique et aux tâches qui s'exécutent avec une granularité supérieure à une heure. Les tâches qui s'exécutent plus fréquemment sont planifiées normalement.

Si l'heure a été ajustée d'une heure en avant, les tâches qui se seraient exécutées dans l'intervalle qui a été sauté seront exécutées immédiatement. Inversement, si l'heure a été ajustée en arrière, l'exécution de la même tâche deux fois est évitée.

Les changements d'heure de plus de 3 heures sont considérés comme des corrections de l'horloge ou du fuseau horaire, et la nouvelle heure est utilisée immédiatement.

Il est possible d'utiliser différents fuseaux horaires pour les crontabs. Voir crontab(5) pour plus d'informations.

Contrôle d'accès PAM

Cron prend en charge le contrôle d'accès avec PAM si le système dispose de PAM installé. Pour plus d'informations, voir pam(8). Un fichier de configuration PAM pour crond est installé dans /etc/pam.d/crond. Le démon charge l'environnement PAM à partir du module pam_env. Ceci peut être outrepassé en définissant des paramètres spécifiques dans le fichier crontab approprié.

OPTIONS

-h
Affiche un message d'aide et quitte.
-i
Désactive le support inotify.
-m
Cette option permet de spécifier une commande shell pour l'envoi de la sortie de courrier de Cron au lieu d'utiliser sendmail(8). Cette commande doit accepter un message de courrier entièrement formaté (avec des en-têtes) sur l'entrée standard et l'envoyer comme un message de courrier aux destinataires spécifiés dans les en-têtes de courrier. Spécifier la chaîne off (c'est-à-dire, crond -m off) désactivera l'envoi de courrier.
-n
Indique au démon de s'exécuter au premier plan. Ceci peut être utile lors de son démarrage depuis init. Avec cette option, il est nécessaire de modifier le paramètre pam. Le fichier /etc/pam.d/crond ne doit pas activer le module pam_loginuid.so.
-f
identique à -n, cohérent avec d'autres implémentations de crond.
-p
Permet à Cron d'accepter toutes les crontabs définies par l'utilisateur.
-P
Ne pas définir PATH. PATH est plutôt hérité de l'environnement.
-c
Cette option active le support de clustering, tel que décrit ci-dessous.
-s
Cette option dirigera Cron pour envoyer la sortie de la tâche au journal système en utilisant syslog(3). Ceci est utile si votre système n'a pas sendmail(8) installé ou si le courrier est désactivé.
-x
Cette option permet de définir les indicateurs de débogage.
-V
Affiche la version et quitte.

SIGNAL

Lorsqu'il reçoit SIGHUP, le démon Cron ferme et rouvre son fichier journal. Ceci s'avère utile dans les scripts qui font la rotation et l'archivage des fichiers journaux. Naturellement, ceci n'est pas pertinent si Cron a été compilé pour utiliser syslog(3).

SUPPORT DE CLUSTERING

Dans cette version de Cron, il est possible d'utiliser un /var/spool/cron partagé monté en réseau sur un cluster d'hôtes et de spécifier qu'un seul des hôtes doit exécuter les tâches crontab de ce répertoire à la fois. Ceci est réalisé en démarrant Cron avec l'option -c, et en faisant en sorte que le fichier /var/spool/cron/.cron.hostname contienne une seule ligne, qui représente le nom d'hôte de l'hôte du cluster qui doit exécuter les tâches. Si ce fichier n'existe pas, ou si le nom d'hôte qu'il contient ne correspond pas à celui renvoyé par gethostname(2), alors toutes les crontabs de ce répertoire sont ignorées. Ceci n'a aucun effet sur les tâches cron spécifiées dans le fichier /etc/crontab ou dans les fichiers du répertoire /etc/cron.d. Ces fichiers sont toujours exécutés et considérés comme spécifiques à l'hôte.

Plutôt que de modifier directement /var/spool/cron/.cron.hostname, utilisez l'option -n de crontab(1) pour spécifier l'hôte.

Vous devriez vous assurer que tous les hôtes d'un cluster, et le serveur de fichiers depuis lequel ils montent le répertoire crontab partagé, ont des horloges étroitement synchronisées, par exemple en utilisant ntpd(8), sinon les résultats seront très imprévisibles.

L'utilisation du partage de cluster désactive automatiquement le support inotify, car inotify ne peut pas être utilisé avec des systèmes de fichiers partagés montés en réseau.

ATTENTION

Toutes les fichiers crontab doivent être des fichiers réguliers ou des liens symboliques vers des fichiers réguliers, ils ne doivent pas être exécutables ou inscriptibles par quelqu'un d'autre que le propriétaire.
