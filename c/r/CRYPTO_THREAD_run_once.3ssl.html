DESCRIPTIO

N

OpenSSL peut être utilisé en toute sécurité dans des applications multi-threadées à condition que la prise en charge de l'API de threading du système d'exploitation sous-jacent soit intégrée. Actuellement, OpenSSL prend en charge les API pthread et Windows. OpenSSL peut également être compilé sans aucune prise en charge multi-thread, par exemple sur des plateformes qui ne fournissent aucune prise en charge du threading ou qui fournissent une API de threading qui n'est pas encore prise en charge par

OpenSSL.

Les fonctions multi-thread suivantes sont fournies

:
  • CRYPTO_THREAD_run_once() peut être utilisé pour effectuer une initialisation unique. Le argument once doit être un pointeur vers un objet statique de type CRYPTO_ONCE qui a été initialisé statiquement à la valeur CRYPTO_ONCE_STATIC_INIT. L' argument init est un pointeur vers une fonction qui effectue l'initialisation souhaitée exactement une fois. En particulier, cela peut être utilisé pour allouer des verrous de manière thread-safe, qui peuvent ensuite être utilisés avec les fonctions de verrouillage
    • ci-dessous.
  • CRYPTO_THREAD_lock_new() alloue, initialise et retourne un nouveau verrou de
    • lecture/écriture.
  • CRYPTO_THREAD_read_lock() verrouille le verrou fourni pour la
    • lecture.
  • CRYPTO_THREAD_write_lock() verrouille le verrou fourni pour
    • l'écriture.
  • CRYPTO_THREAD_unlock() déverrouille le verrou précédemment v
    • errouillé.
  • CRYPTO_THREAD_lock_free() libère le verrou fourni. Si l' argument est NULL, rien n'est
    • fait.
  • CRYPTO_atomic_add() ajoute atomiquement amount à *val et retourne le résultat de l'opération dans *ret. lock sera verrouillé, sauf si les opérations atomiques sont prises en charge sur la plateforme spécifique. En raison de cela, si une variable est modifiée par CRYPTO_atomic_add() alors CRYPTO_atomic_add() doit être la seule façon dont la variable est modifiée. Si les opérations atomiques ne sont pas prises en charge et que lock est NULL, alors la fonction
    • échouera.
  • CRYPTO_atomic_add64() ajoute atomiquement op à *val et retourne le résultat de l'opération dans *ret. lock sera verrouillé, sauf si les opérations atomiques sont prises en charge sur la plateforme spécifique. En raison de cela, si une variable est modifiée par CRYPTO_atomic_add64() alors CRYPTO_atomic_add64() doit être la seule façon dont la variable est modifiée. Si les opérations atomiques ne sont pas prises en charge et que lock est NULL, alors la fonction
    • échouera.
  • CRYPTO_atomic_and() effectue un ET bit à bit atomique de op et *val et stocke le résultat dans *val. Elle retourne également le résultat de l'opération dans *ret. lock sera verrouillé, sauf si les opérations atomiques sont prises en charge sur la plateforme spécifique. En raison de cela, si une variable est modifiée par CRYPTO_atomic_and() ou lue par CRYPTO_atomic_load() alors CRYPTO_atomic_and() doit être la seule façon dont la variable est modifiée. Si les opérations atomiques ne sont pas prises en charge et que lock est NULL, alors la fonction
    • échouera.
  • CRYPTO_atomic_or() effectue un OU bit à bit atomique de op et *val et stocke le résultat dans *val. Elle retourne également le résultat de l'opération dans *ret. lock sera verrouillé, sauf si les opérations atomiques sont prises en charge sur la plateforme spécifique. En raison de cela, si une variable est modifiée par CRYPTO_atomic_or() ou lue par CRYPTO_atomic_load() alors CRYPTO_atomic_or() doit être la seule façon dont la variable est modifiée. Si les opérations atomiques ne sont pas prises en charge et que lock est NULL, alors la fonction
    • échouera.
  • CRYPTO_atomic_load() charge atomiquement le contenu de *val dans *ret. lock sera verrouillé, sauf si les opérations atomiques sont prises en charge sur la plateforme spécifique. En raison de cela, si une variable est modifiée par CRYPTO_atomic_or() ou lue par CRYPTO_atomic_load() alors CRYPTO_atomic_load() doit être la seule façon dont la variable est lue. Si les opérations atomiques ne sont pas prises en charge et que lock est NULL, alors la fonction
    • échouera.
  • CRYPTO_atomic_store() stocke atomiquement le contenu de val dans *dst. lock sera verrouillé, sauf si les opérations atomiques sont prises en charge sur la plateforme
    • spécifique.
  • CRYPTO_atomic_load_int() fonctionne de manière identique à CRYPTO_atomic_load() mais opère sur une valeur int au lieu d'une valeur uint64_t
    • .
  • OSSL_set_max_threads() définit le nombre maximum de threads à utiliser par le pool de threads. Si l'argument est 0, le poolage de threads est désactivé. OpenSSL ne créera aucun thread et les threads existants dans le pool de threads seront arrêtés. Le nombre maximum de threads est une limite, pas une cible. Les threads ne seront pas créés sauf si (et tant qu'il y a) une demande. Le poolage de threads est désactivé par défaut. Pour activer le threading, vous devez appeler OSSL_set_max_threads() explicitement. En aucun cas cela n'est fait pour
    • vous.
  • OSSL_get_thread_support_flags() détermine avec quelles fonctionnalités de pool de threads OpenSSL est compilé et est capable de prendre en charge dans l'environnement d'exécution actuel. OSSL_THREAD_SUPPORT_FLAG_THREAD_POOL indique que les fonctionnalités de base du pool de threads sont disponibles, et OSSL_THREAD_SUPPORT_FLAG_DEFAULT_SPAWN indique que le modèle de pool de threads par défaut est disponible. Le modèle de pool de
    • threads par défaut est actuellement le seul modèle disponible,
par conséquent ces deux indicateurs doivent être définis pour
que les fonctionnalités de pool de threads soient utilisées.

RETOURNÉES

CRYPTO_THREAD_run_once() retourne 1 en cas de succès, ou 0 en cas

d'erreur.

CRYPTO_THREAD_lock_new() retourne le verrou alloué, ou NULL en cas

d'erreur.

CRYPTO_THREAD_lock_free() ne retourne aucune

valeur.

OSSL_set_max_threads() retourne 1 en cas de succès et 0 en cas d'échec. Retourne un échec si le poolage de threads géré par OpenSSL n'est pas pris en charge (par exemple, s'il n'est pas pris en charge sur la plateforme actuelle, ou parce qu'OpenSSL n'est pas compilé avec la prise en charge nécessaire)

.

OSSL_get_max_threads() retourne le nombre maximum de threads actuellement autorisés à être utilisés par le pool de threads. Si le poolage de threads est désactivé ou non disponible, retourne

0.

OSSL_get_thread_support_flags() retourne zéro ou plusieurs valeurs OSSL_THREAD_SUPPORT_FLAG

.

Les autres fonctions ret

ournent 1 en cas de succè
s, ou 0 en cas d'erreur.

REMARQUE

S

Sur les plateformes Windows, les types et fonctions CRYPTO_THREAD_* dans l'en-tête <openssl/crypto.h> dépendent de certains des types habituellement rendus disponibles en incluant <windows.h>. Le développeur d'application aura probablement besoin de contrôler quand ce dernier est inclus, généralement comme l'un des premiers en-têtes inclus. Par conséquent, il est défini comme la responsabilité du développeur d'application d'inclure <windows.h> avant <openssl/crypto.h> lorsque l'utilisation des

types et fonctions CRYP
TO_THREAD_* est requise.

EXEMPLE

S

Vous pouvez vérifier si OpenSSL a été configuré avec le support des threads

: 
#include <openssl/opensslconf.h>
#if defined(OPENSSL_THREADS)
    /* support des threads activé */
#else
    /* pas de support des threads */
#endif

Cet exemple initialise et utilise un verrou de manière

sûre. 
#ifdef _WIN32
# include <windows.h>
#endif
#include <openssl/crypto.h>
static CRYPTO_ONCE once = CRYPTO_ONCE_STATIC_INIT;
static CRYPTO_RWLOCK *lock;
static void myinit(void)
{
    lock = CRYPTO_THREAD_lock_new();
}
static int mylock(void)
{
    if (!CRYPTO_THREAD_run_once(&once, void init) || lock == NULL)
        return 0;
    return CRYPTO_THREAD_write_lock(lock);
}
static int myunlock(void)
{
    return CRYPTO_THREAD_unlock(lock);
}
int serialized(void)
{
    int ret = 0;
    if (!mylock()) {
       /* Ne pas déverrouiller à moins que le verrou n'ait été acquis avec succès. */
       return 0;
    }
    /* Votre code ici, ne pas retourner sans libérer le verrou ! */
    ret = ... ;
    myunlock();
    return ret;
}

La finalisation des verrous est un sujet avancé, non couvert dans cet exemple. Cela ne peut être fait qu'à la sortie du processus ou lorsqu

'une bibliothèque chargée dynamiquement n'est plus utilisée et est déchargée. La solution la plus simple est de simplement « fuiter » le
verrou dans les applications et de ne pas charger/décharger à plusieurs reprises des bibliothèques partagées qui allouent des verrous.
