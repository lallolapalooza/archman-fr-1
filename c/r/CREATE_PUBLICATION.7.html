SYNOPSI

S 
CREATE PUBLICATION name
    [ FOR ALL TABLES
      | FOR publication_object [, ... ] ]
    [ WITH ( publication_parameter [= value] [, ... ] ) ]
où publication_object est l'une des formes suivantes :
    TABLE [ ONLY ] table_name [ * ] [ ( column_name [, ... ] ) ] [ WHERE ( expression ) ] [, ... ]
    TABLES IN SCHEMA { schema_name | CURRENT_SCHEMA } [, ...
]

DESCRIPTIO

N

CREATE PUBLICATION ajoute une nouvelle publication à la base de données courante. Le nom de la publication doit être distinct de celui de toute publication existante dans la base de données

courante.

Une publication est essentiellement un groupe de tables dont les changements de données sont

destinés à être répliqués par réplication logique. Voir la section 29.1 pour des détails sur
la façon dont les publications s'intègrent dans la configuration de la réplication logique.

PARAMÈTRE

S

nam

e
Le nom de la nouvelle
publication.

FOR

TABLE
Spécifie une liste de tables à ajouter à la publication. Si ONLY est spécifié avant le nom de la table, seule cette table est ajoutée à la publication. Si ONLY n'est pas spécifié, la table et toutes ses tables descendantes (le cas échéant) sont ajoutées. En option, * peut être spécifié après le nom de la table pour indiquer explicitement que les tables descendantes sont incluses. Cela ne s'applique pas cependant aux tables partitionnées. Les partitions d'une table partitionnée sont toujours implicitement considérées comme faisant partie de la publication, elles ne sont donc jamais ajoutées explicitement à la publication.

Si la clause WHERE facultative est spécifiée, elle définit une expression de filtre de lignes. Les lignes pour lesquelles l'expression évalue à false ou null ne seront pas publiées. Notez que des parenthèses sont requises autour de l'expression. Cela n'a aucun effet sur les commandes

TRUNCATE.

Lorsqu'une liste de colonnes est spécifiée, seules les colonnes nommées sont répliquées. La liste de colonnes peut également contenir des colonnes générées stockées. Si la liste de colonnes est omise, la publication répliquera par défaut toutes les colonnes non générées (y compris celles ajoutées à l'avenir). Les colonnes générées stockées peuvent également être répliquées si publish_generated_columns est défini à stored. Spécifier une liste de colonnes n'a aucun effet sur les commandes TRUNCATE. Voir la section 29.5 pour des détails sur les listes de

colonnes.

Seules les tables de base persistantes et les tables partitionnées peuvent faire partie d'une publication. Les tables temporaires, les tables non journalisées, les tables étrangères, les vues matérialisées et les vues ordinaires ne peuvent pas faire partie d'une

publication.

Spécifier une liste de colonnes lorsque la publication publie également FOR TABLES IN SCHEMA n'est pas pris en

charge.

Lorsqu'une table partitionnée est ajoutée à une publication, toutes ses partitions existantes et futures son

t implicitement considérées comme faisant partie de la publication. Ainsi, même les opérations effectué
es directement sur une partition sont également publiées via les publications dont ses ancêtres font partie.

FOR ALL

TABLES
Marque la publication comme celle qui réplique les changements pour toutes les tables de la base de données, y compris les tables créées dans le
futur.

FOR TABLES IN

SCHEMA
Marque la publication comme celle qui réplique les changements pour toutes les tables de la liste de schémas spécifiée, y compris les tables créées dans le futur.

Spécifier un schéma lorsque la publication publie également une table avec une liste de colonnes n'est pas pris en

charge.

Seules les tables de base persistantes et les tables partitionnées présentes dans le schéma seront incluses comme partie de la publication. Les tables temporaires, les tables non journalisées, les tables étrangères, les vues matérialisées et les vues ordinaires du schéma ne feront pas partie de la

publication.

Lorsqu'une table partitionnée est publiée via une publication au niveau du schéma, toutes ses partitions existantes et futures sont

implicitement considérées comme faisant partie de la publication, qu'elles proviennent ou non du schéma de la publication. Ainsi, même
les opérations effectuées directement sur une partition sont également publiées via les publications dont ses ancêtres font partie.

WITH ( publication_parameter [= value] [, ... ]

)
Cette clause spécifie des paramètres facultatifs pour une publication. Les paramètres suivants sont pris en charge :

publish

(string)
Ce paramètre détermine quelles opérations DML seront publiées par la nouvelle publication aux abonnés. La valeur est une liste d'opérations séparées par des virgules. Les opérations autorisées sont insert, update, delete et truncate. Par défaut, toutes les actions sont publiées, la valeur par défaut de cette option est donc 'insert, update, delete, truncate'.

Ce paramètre n'affecte que les opérations DML. En particulier, la synchronisatio

n initiale des données (voir la section 29.9.1) pour la réplication logique ne ti
ent pas compte de ce paramètre lors de la copie des données de table existantes.

publish_generated_columns

(enum)
Spécifie si les colonnes générées présentes dans les tables associées à la publication doivent être répliquées. Les valeurs possibles sont none et stored.

La valeur par défaut est none, ce qui signifie que les colonnes générées présentes dans les tables associées à la publication ne seront pas

répliquées.

Si défini à stored, les colonnes générées stockées présentes dans les tables associées à la publication seront

répliquées.

Note
Si l'abonné provient d'une version antérieure à 18, la synchronisation initiale de la table ne copiera pas les colonnes générées, même si le paramètre publish_generated_columns est stored dans le publieur.
Voir la section 29.6 pour plus de détails sur la réplication logique des colonnes
générées.

publish_via_partition_root

(boolean)
Ce paramètre détermine si les changements dans une table partitionnée (ou sur ses partitions) contenue dans la publication seront publiés en utilisant l'identité et le schéma de la table partitionnée plutôt que ceux des partitions individuelles qui sont réellement modifiées ; cette dernière option est la valeur par défaut. Activer cela permet de répliquer les changements vers une table non partitionnée ou une table partitionnée constituée d'un ensemble différent de partitions.

Il peut arriver qu'un abonnement combine plusieurs publications. Si une table partitionnée est publiée par l'une des publications abonnées qui définissent publish_via_partition_root = true, les changements sur cette table partitionnée (ou sur ses partitions) seront publiés en utilisant l'identité et le schéma de cette table partitionnée plutôt que ceux des partitions

individuelles.

Ce paramètre affecte également la façon dont les filtres de lignes et les listes de colonnes sont choisis pour les partitions ; voir ci-dessous pour plus de

détails.

Si cela est activé, les opér

ations TRUNCATE effectuées
directement sur les partit
ions ne sont pas répliquées.

Lors de la spécification d'un paramètre de type boolean, la partie value peut être omise, ce

qui équivaut à
spécifier TRUE.

NOTE

S

Si FOR TABLE, FOR ALL TABLES ou FOR TABLES IN SCHEMA ne sont pas spécifiés, la publication commence avec un ensemble vide de tables. C'est utile si des tables ou des schémas doivent être ajoutés plus

tard.

La création d'une publication ne démarre pas la réplication. Elle définit seulement une logique de groupement et de filtrage pour les futurs

abonnés.

Pour créer une publication, l'utilisateur appelant doit avoir le privilège CREATE pour la base de données courante. (Bien sûr, les superutilisateurs contournent cette vérification.

)

Pour ajouter une table à une publication, l'utilisateur appelant doit avoir les droits de propriété sur la table. Les FOR ALL TABLES et FOR TABLES IN SCHEMA exigent que l'utilisateur appelant soit un superutilisateur

.

Les tables ajoutées à une publication qui publie UPDATE et/ou DELETE doivent avoir une REPLICA IDENTITY définie. Sinon, ces opérations seront interdites sur ces

tables.

Toute liste de colonnes doit inclure les colonnes REPLICA IDENTITY afin que les opérations UPDATE ou DELETE soient publiées. Il n'y a aucune restriction de liste de colonnes si la publication ne publie que des opérations INSERT

.

Une expression de filtre de lignes (c'est-à-dire la clause WHERE) ne doit contenir que des colonnes couvertes par la REPLICA IDENTITY, afin que les opérations UPDATE et DELETE soient publiées. Pour la publication d'opérations INSERT, n'importe quelle colonne peut être utilisée dans l'expression WHERE. Le filtre de lignes autorise des expressions simples qui n'ont pas de fonctions définies par l'utilisateur, d'opérateurs définis par l'utilisateur, de types définis par l'utilisateur, de collations définies par l'utilisateur, de fonctions intégrées non immuables, ni de références aux colonnes

système.

Les colonnes générées qui font partie de la REPLICA IDENTITY doivent êtreed explicitement soit en les listant dans la liste de colonnes, soit en activant l'option publish_generated_columns, afin que UPDATE et les opérations DELETE soient

publiées.

Le filtre de ligne sur une table devient redondant si FOR TABLES IN SCHEMA est spécifié et que la table appartient au schéma

concerné.

Pour les tables partitionnées publiées, le filtre de ligne de chaque partition est pris depuis la table partitionnée publiée si le paramètre de publication publish_via_partition_root vaut true, ou depuis la partition elle-même s'il vaut false (par défaut). Voir la section 29.4 pour plus de détails sur les filtres de ligne. De même, pour les tables partitionnées publiées, la liste de colonnes de chaque partition est prise depuis la table partitionnée publiée si le paramètre de publication publish_via_partition_root vaut true, ou depuis la partition elle-même s'il vaut

false.

Pour une commande INSERT ... ON CONFLICT, la publication publiera l'opération résultant de la commande. Selon le résultat, elle peut être publiée comme INSERT ou UPDATE, ou elle peut ne pas être publiée du

tout.

Pour une commande MERGE, la publication publiera une opération INSERT, UPDATE ou DELETE pour chaque ligne insérée, mise à jour ou

supprimée.

ATTACHer une table dans un arbre de partition dont la racine est publiée à l'aide d'une publication avec publish_via_partition_root défini à true n'a pas pour effet de répliquer le contenu existant de la

table.

Les commandes COPY ... FROM sont publiées comme des opérations

INSERT.

Les opérations DDL ne sont pas

publiées.
