SYNOPSI

S

DESCRIPTIO

N

CREATE VIEW définit une vue d'une requête. La vue n'est pas matérialisée physiquement. À la place, la requête est exécutée à chaque fois que la vue est référencée dans une

requête.

CREATE OR REPLACE VIEW est similaire, mais si une vue du même nom existe déjà, elle est remplacée. La nouvelle requête doit générer les mêmes colonnes que celles générées par la requête de la vue existante (c'est-à-dire les mêmes noms de colonnes dans le même ordre et avec les mêmes types de données), mais elle peut ajouter des colonnes supplémentaires à la fin de la liste. Les calculs donnant naissance aux colonnes de sortie peuvent être complètement

différents.

Si un nom de schéma est donné (par exemple, CREATE VIEW myschema.myview ...) alors la vue est créée dans le schéma spécifié. Sinon, elle est créée dans le

schéma courant. Les vues temporaires existent dans un schéma spécial, donc un nom de schéma ne peut pas être donné lors de la création d'une vue temporaire
. Le nom de la vue doit être distinct du nom de toute autre relation (table, séquence, index, vue, vue matérialisée ou table distante) dans le même schéma.

PARAMÈTRE

S

TEMPORARY ou

TEMP
Si spécifié, la vue est créée en tant que vue temporaire. Les vues temporaires sont automatiquement supprimées à la fin de la session courante. Les relations permanentes existantes portant le même nom ne sont pas visibles par la session courante tant que la vue temporaire existe, à moins qu'elles ne soient référencées avec des noms qualifiés par le schéma.

Si l'une des tables référencées par la vue est te

mporaire, la vue est créée en tant que vue t
emporaire (que TEMPORARY soit spécifié ou non).

WITH [ CASCADED | LOCAL ] CHECK

OPTION
Cette option contrôle le comportement des vues automatiquement mises à jour. Lorsque cette option est spécifiée, les INSERT, UPDATE et MERGE sur la vue seront vérifiés pour s'assurer que les nouvelles lignes satisfont la condition définissant la vue (c'est-à-dire que les nouvelles lignes sont vérifiées pour s'assurer qu'elles sont visibles à travers la vue). Si ce n'est pas le cas, la mise à jour sera rejetée. Si CHECK OPTION n'est pas spécifié, les INSERT, UPDATE et MERGE sur la vue sont autorisés à créer des lignes qui ne sont pas visibles à travers la vue. Les options de vérification suivantes sont prises en charge :

LOCA

L
Les nouvelles lignes ne sont vérifiées que par rapport aux conditions définies directement dans la vue elle-même. Les conditions définies sur les vues de base sous-jacentes ne sont pas vérifiées (sauf si elles spécifient elles-mêmes CHECK OPTION)
.

CASCADE

D
Les nouvelles lignes sont vérifiées par rapport aux conditions de la vue et de toutes les vues de base sous-jacentes. Si CHECK OPTION est spécifié, et que ni LOCAL ni CASCADED n'est spécifié, alors CASCADED est
supposé.

CHECK OPTION ne peut pas être utilisé avec les vues

RECURSIVE.

Notez que CHECK OPTION n'est pris en charge que sur les vues qui sont automatiquement mises à jour et qui n'ont ni déclencheurs INSTEAD OF ni règles INSTEAD. Si une vue automatiquement mise à jour est définie au-dessus d'une vue de base ayant des déclencheurs INSTEAD OF, alors l'option LOCAL CHECK OPTION peut être utilisée pour vérifier les conditions sur la vue automatiquement mise à jour, mais les conditions sur la vue de base ayant des déclencheurs INSTEAD OF ne seront pas vérifiées (une option de vérification en cascade ne se propagera pas jusqu'à une vue mise à jour par déclencheur, et toute option de vérification définie directement sur une vue mise à jour par déclencheur sera ignorée). Si la vue ou l'une de ses relations de base a une règle INSTEAD qui fait que la INSERT ou la UPDATE est réécrite, alors toutes les options de vérification seront ignorées dans la requête réécrite, y compris toute vérification provenant des vues automatiquement mises à jour définies au-dessus de la relation ayant la règle INSTEAD. MERGE n'est pas pris en charge si la

NOTE

S

Utilisez l'instruction DROP VIEW pour supprimer des

vues.

Veillez à ce que les noms et les types des colonnes de la vue soient assignés comme vous le souhaitez. Par exemple

: 
CREATE VIEW vi
sta AS SELECT
'Hello World';

est de mauvais style car le nom de colonne vaut par défaut ?column? ; de plus, le type de données de la colonne vaut par défaut text, ce qui n'est peut-être pas ce que vous vouliez. Un meilleur style pour un littéral de chaîne dans le résultat d'une vue serait quelque chose comme

: 
CREATE VIEW vista A
S SELECT text 'Hel
lo World' AS hello;

Par défaut, l'accès aux relations de base sous-jacentes référencées dans la vue est déterminé par les permissions du propriétaire de la vue. Dans certains cas, cela peut être utilisé pour fournir un accès sécurisé mais restreint aux tables sous-jacentes. Cependant, toutes les vues ne sont pas sécurisées contre la falsification ; voir la section 39.5 pour les

détails.

Si la vue a la propriété security_invoker définie à true, l'accès aux relations de base sous-jacentes est déterminé par les permissions de l'utilisateur exécutant la requête, plutôt que par celles du propriétaire de la vue. Ainsi, l'utilisateur d'une vue security invoker doit avoir les permissions pertinentes sur la vue et ses relations de base

sous-jacentes.

Si l'une des relations de base sous-jacentes est une vue security invoker, elle sera traitée comme si elle avait été accédée directement depuis la requête originale. Ainsi, une vue security invoker vérifiera toujours ses relations de base sous-jacentes en utilisant les permissions de l'utilisateur courant, même si elle est accédée depuis une vue sans la propriété security_invoker

.

Si l'une des relations de base sous-jacentes a la sécurité au niveau des lignes activée, alors par défaut, les politiques de sécurité au niveau des lignes du propriétaire de la vue sont appliquées, et l'accès à toute relation supplémentaire référencée par ces politiques est déterminé par les permissions du propriétaire de la vue. Cependant, si la vue a security_invoker défini à true, alors les politiques et les permissions de l'utilisateur appelant sont utilisées à la place, comme si les relations de base avaient été référencées directement depuis la requête utilisant la

vue.

Les fonctions appelées dans la vue sont traitées comme si elles avaient été appelées directement depuis la requête utilisant la vue. Par conséquent, l'utilisateur d'une vue doit avoir les permissions pour appeler toutes les fonctions utilisées par la vue. Les fonctions dans la vue sont exécutées avec les privilèges de l'utilisateur exécutant la requête ou du propriétaire de la fonction, selon que les fonctions sont définies comme SECURITY INVOKER ou SECURITY DEFINER. Ainsi, par exemple, appeler CURRENT_USER directement dans une vue retournera toujours l'utilisateur appelant, et non le propriétaire de la vue. Cela n'est pas affecté par le réglage security_invoker de la vue, et donc une vue avec security_invoker défini à false n'est pas équivalente à une fonction SECURITY DEFINER et ces concepts ne doivent pas être confondus

.

L'utilisateur qui crée ou remplace une vue doit disposer des privilèges USAGE sur tout schéma référencé dans la requête de la vue, afin de rechercher les objets référencés dans ces schémas. Notez cependant que cette recherche n'a lieu que lorsque la vue est créée ou remplacée. Par conséquent, l'utilisateur de la vue n'a besoin que du privilège USAGE sur le schéma contenant la vue, et non sur les schémas référencés dans la requête de la vue, même pour une vue avec security_invoker

.

Lorsque CREATE OR REPLACE VIEW est utilisé sur une vue existante, seule la règle SELECT définissant la vue, ainsi que les paramètres WITH ( ... ) et son CHECK OPTION sont modifiés. Les autres propriétés de la vue, y compris la propriété, les permissions et les règles non-SELECT, restent inchangées. Vous devez être propriétaire de la vue pour la remplacer (ce qui inclut le fait d'être membre du rôle propriétaire)

.

Vues mises à

jour

Les vues simples sont automatiquement mises à jour : le système permettra INSERT, UPDATE, DELETE, et MERGE d'être utilisés sur la vue de la même manière que sur une table normale. Une vue est automatiquement mise à jour si elle satisfait toutes les conditions suivantes

:
•La vue doit avoir exactement une entrée dans sa liste FROM, qui doit être une table ou une autre vue mise à
jour.
•La définition de la vue ne doit pas contenir de clauses WITH, DISTINCT, GROUP BY, HAVING, LIMIT ou OFFSET au niveau
supérieur.
•La définition de la vue ne doit pas contenir d'opérations d'ensemble (UNION, INTERSECT ou EXCEPT) au niveau
supérieur.
•La liste de sélection de la vue ne doit contenir aucun agrégat, fonction de fenêtre ou fonction renvoyant un
ensemble.

Une vue automatiquement mise à jour peut contenir un mélange de colonnes mises à jour et non mises à jour. Une colonne est mise à jour si elle est une référence simple à une colonne mise à jour de la relation de base sous-jacente ; sinon la colonne est en lecture seule, et une erreur sera levée si un INSERT, UPDATE, ou MERGE tente d'affecter une valeur à

celle-ci.

Si la vue est automatiquement mise à jour, le système convertira tout INSERT, UPDATE, DELETE, ou MERGE sur la vue en l'instruction correspondante sur la relation de base sous-jacente. Les instructions INSERT ayant une clause ON CONFLICT UPDATE sont entièrement prises en

charge.

Si une vue automatiquement mise à jour contient une condition WHERE, la condition restreint les lignes de la relation de base qui peuvent être modifiées par UPDATE, DELETE, et MERGE sur la vue. Cependant, un UPDATE ou MERGE peut modifier une ligne de sorte qu'elle ne satisfasse plus la condition WHERE, et n'est donc plus visible à travers la vue. De même, une commande INSERT ou MERGE peut potentiellement insérer des lignes de relation de base qui ne satisfont pas la condition WHERE et ne sont donc pas visibles à travers la vue (ON CONFLICT UPDATE peut de même affecter une ligne existante non visible à travers la vue). Le CHECK OPTION peut être utilisé pour empêcher INSERT, UPDATE, et MERGE de créer de telles lignes qui ne sont pas visibles à travers la

vue.

Si une vue automatiquement mise à jour est marquée avec la propriété security_barrier, alors toutes les conditions WHERE de la vue (et toute condition utilisant des opérateurs marqués comme LEAKPROOF) seront toujours évaluées avant toute condition ajoutée par un utilisateur de la vue. Voir la section 39.5 pour plus de détails. Notez que, en raison de cela, les lignes qui ne sont finalement pas retournées (car elles ne passent pas les conditions WHERE de l'utilisateur) peuvent quand même être verrouillées. EXPLAIN peut être utilisé pour voir quelles conditions sont appliquées au niveau de la relation (et ne verrouillent donc pas les lignes) et quelles ne le sont

pas.

Une vue plus complexe qui ne satisfait pas toutes ces conditions est en lecture seule par défaut : le système ne permettra pas un INSERT, UPDATE, DELETE, ou MERGE sur la vue. Vous pouvez obtenir l'effet d'une vue mise à jour en créant des déclencheurs INSTEAD OF sur la vue, qui doivent convertir les insertions, etc. tentées sur la vue en actions appropriées sur d'autres tables. Pour plus d'informations, voir CREATE TRIGGER (CREATE_TRIGGER(7)). Une autre possibilité est de créer des règles (voir CREATE RULE (CREATE_RULE(7))), mais en pratique les déclencheurs sont plus faciles à comprendre et à utiliser correctement. Notez également que MERGE n'est pas pris en charge sur les relations avec des

règles.

Notez que l'utilisateur effectuant l'insertion, la mise à jour ou la suppression sur la vue doit disposer du privilège d'insertion, de mise à jour ou de suppression corresp

ondant sur la vue. De plus, par défaut, le propriétaire de la vue doit disposer des privilèges pertinents sur les relations de base sous-jacentes, alors que l'utilisateu
r effectuant la mise à jour n'a besoin d'aucune permission sur les relations de base sous-jacentes (voir la section 39.5). Cependant, si la vue a security_invoker défini
à true, l'utilisateur effectuant la mise à jour, plutôt que le propriétaire de la vue, doit disposer des privilèges pertinents sur les relations de base sous-jacentes.

EXEMPLE

S

Créer une vue contenant tous les films de comédie

: 
CREATE VIEW comedies AS
SELECT * FROM films
WHERE kind = 'Comedy';

Cela créera une vue contenant les colonnes qui se trouvent dans la table film au moment de la création de la vue. Bien que * ait été utilisé pour créer la vue, les colonnes ajoutées plus tard à la table ne feront pas partie de la

vue.

Créer une vue avec LOCAL CHECK OPTION

: 
CREATE VIEW universal_comedies AS
    SEL
ECT * FROM comedies WHERE classifi
cation = 'U' WITH LOCAL CHECK OPTION;

Cela créera une vue basée sur la vue comedies, montrant uniquement les films avec kind = 'Comedy' et classification = 'U'. Toute tentative de INSERT ou UPDATE d'une ligne dans la vue sera rejetée si la nouvelle ligne n'a pas classification = 'U', mais le kind du film ne sera pas

vérifié.

Créer une vue avec CASCADED CHECK OPTION

: 
CREATE VIEW pg_comedies AS
    SELECT *
FROM comedies WHERE classificatio
n = 'PG' WITH CASCADED CHECK OPTION;

Cela créera une vue qui vérifie à la fois le kind et la classification des nouvelles

lignes.

Créer une vue avec un mélange de colonnes mises à jour et non mises à jour

: 
CREATE VIEW comedies AS
    SELECT f.*,
           country_code_to_name(f.country_code)
AS country, (SELECT avg(r.rating) FROM user_ratings r
WHERE r.film_id = f.id) AS avg_rating FROM films f WHERE f.kind = 'Comedy';

Cette vue prendra en charge INSERT, UPDATE et DELETE. Toutes les colonnes de la table films seront mises à jour, alors que les colonnes calculées country et avg_rating seront en lecture

seule.

Créer une vue récursive contenant les nombres de 1 à 100

: 
CREATE RECURSIVE VIEW public.nums_1_100
(n) AS VALUES (1) UNION ALL SE
LECT n+1 FROM nums_1_100 WHERE n < 100;

Remarquez que bien que le nom de la vue récursive soit qualifié par le schéma dans ce CREATE, sa référence interne à elle-même n'est pas qualifiée par le schéma. Cela est dû

au fait que le nom de la CTE créée implicitemen
t ne peut pas être qualifié par le schéma.
