CREATE_POLICY - définit une nou

velle politique de sécurité au n
iveau des lignes pour une table

SYNOPSI

S 
CREATE POLICY nom ON nom_table
    [ AS { PERMISSIVE | RESTRICTIVE } ]
    [ FOR { ALL | SELECT | INSERT | UPDATE | DELETE } ]
    [ TO { nom_rôle | PUBLIC | CURRENT_ROLE | CURRENT_USER | SESSION_USER } [, ...] ]
    [ USING ( expression_using ) ]
    [ WITH CHECK ( expression_check )
]

DESCRIPTIO

N

La commande CREATE POLICY définit une nouvelle politique de sécurité au niveau des lignes pour une table. Notez que la sécurité au niveau des lignes doit être activée sur la table (à l'aide de ALTER TABLE ... ENABLE ROW LEVEL SECURITY) pour que les politiques créées soient

appliquées.

Une politique accorde la permission de sélectionner, d'insérer, de mettre à jour ou de supprimer les lignes qui correspondent à l'expression de politique pertinente. Les lignes existantes de la table sont vérifiées par rapport à l'expression spécifiée dans USING, tandis que les nouvelles lignes qui seraient créées via INSERT ou UPDATE sont vérifiées par rapport à l'expression spécifiée dans WITH CHECK. Lorsqu'une expression USING renvoie true pour une ligne donnée, cette ligne est visible pour l'utilisateur, tandis que si false ou null est renvoyé, la ligne n'est pas visible. Lorsqu'une expression WITH CHECK renvoie true pour une ligne, cette ligne est insérée ou mise à jour, tandis que si false ou null est renvoyé, une erreur se

produit.

Pour les instructions INSERT, UPDATE et MERGE, les expressions WITH CHECK sont appliquées après le déclenchement des déclencheurs BEFORE et avant toute modification réelle des données. Ainsi, un déclencheur BEFORE ROW peut modifier les données à insérer, affectant le résultat de la vérification de la politique de sécurité. Les expressions WITH CHECK sont appliquées avant toute autre

contrainte.

Les noms de politique sont propres à chaque table. Par conséquent, un même nom de politique peut être utilisé pour de nombreuses tables différentes et avoir une définition pour chaque table qui lui est

appropriée.

Les politiques peuvent être appliquées à des commandes spécifiques ou à des rôles spécifiques. Par défaut, les politiques nouvellement créées s'appliquent à toutes les commandes et à tous les rôles, sauf indication contraire. Plusieurs politiques peuvent s'appliquer à une seule commande ; voir ci-dessous pour plus de détails. Le tableau 300 résume comment les différents types de politiques s'appliquent à des commandes

spécifiques.

Pour les politiques qui peuvent avoir à la fois des expressions USING et WITH CHECK (ALL et UPDATE), si aucune expression WITH CHECK n'est définie, l'expression USING sera utilisée à la fois pour déterminer quelles lignes sont visibles (cas USING normal) et quelles nouvelles lignes seront autorisées à être ajoutées (cas WITH CHECK)

.

Si la sécurité au niveau des lignes est activée pour une table, mais qu

'aucune politique applicable n'existe, une politique « refus par défaut
» est supposée, de sorte qu'aucune ligne ne sera visible ni modifiable.

PARAMÈTRE

S

no

m
Le nom de la politique à créer. Il doit être distinct du nom de toute autre politique pour la
table.

nom_tabl

e
Le nom (éventuellement qualifié par le schéma) de la table à laquelle la politique
s'applique.

PERMISSIV

E
Spécifie que la politique doit être créée comme une politique permissive. Toutes les politiques permissives applicables à une requête donnée seront combinées à l'aide de l'opérateur booléen « OR ». En créant des politiques permissives, les administrateurs peuvent ajouter à l'ensemble des enregistrements qui peuvent être accessibles. Les politiques sont permissives par
défaut.

RESTRICTIV

E
Spécifie que la politique doit être créée comme une politique restrictive. Toutes les politives restrictives applicables à une requête donnée seront combinées à l'aide de l'opérateur booléen « AND ». En créant des politiques restrictives, les administrateurs peuvent réduire l'ensemble des enregistrements qui peuvent être accessibles, car toutes les politiques restrictives doivent être satisfaites pour chaque enregistrement.

Notez qu'il doit y avoir au moins une politique permissive pour accorder l'accès aux enregistrements avant que les politiques restrictives puissent être utilisées effica

cement pour réduire cet accès. S'il n'existe que des politiques restrictives, aucun enregistrement ne sera accessible. Lorsqu'un mélange de politiques permissives et res
trictives est présent, un enregistrement n'est accessible que si au moins l'une des politiques permissives est satisfaite, en plus de toutes les politiques restrictives.

command

e
La commande à laquelle la politique s'applique. Les options valides sont ALL, SELECT, INSERT, UPDATE et DELETE. ALL est la valeur par défaut. Voir ci-dessous pour les spécificités concernant leur
application.

nom_rôl

e
Le ou les rôles auxquels la politique doit être appliquée. La valeur par défaut est PUBLIC, ce qui appliquera la politique à tous les
rôles.

expression_usin

g
Toute expression conditionnelle SQL (renvoyant un booléen). L'expression conditionnelle ne peut contenir aucune fonction d'agrégation ou de fenêtre. Cette expression sera ajoutée aux requêtes qui font référence à la table si la sécurité au niveau des lignes est activée. Les lignes pour lesquelles l'expression renvoie true seront visibles. Toutes les lignes pour lesquelles l'expression renvoie false ou null ne seront pas visibles pour l'utilisateur (dans un SELECT) et ne seront pas disponibles pour modification (dans un UPDATE ou DELETE). Ces lignes sont silencieusement supprimées ; aucune erreur n'est
signalée.

expression_chec

k
Toute expression conditionnelle SQL (renvoyant un booléen). L'expression conditionnelle ne peut contenir aucune fonction d'agrégation ou de fenêtre. Cette expression sera utilisée dans les requêtes INSERT et UPDATE sur la table si la sécurité au niveau des lignes est activée. Seules les lignes pour lesquelles l'expression est évaluée à true seront autorisées. Une erreur sera levée si l'expression est évaluée à false ou null pour l'un des enregistrements insérés ou l'un des enregistrements résultant de la mise à jour. Notez que l' expression_check est évaluée par rapport aux nouveaux contenus proposés de la ligne, et non aux contenus
d'origine.

Politiques par

commande

AL

L
Utiliser ALL pour une politique signifie qu'elle s'appliquera à toutes les commandes, quel que soit le type de commande. Si une politique ALL existe et que des politiques plus spécifiques existent, alors à la fois la politique ALL et la politique (ou les politiques) plus spécifique(s) seront appliquées. De plus, les politiques ALL seront appliquées à la fois au côté sélection d'une requête et au côté modification, en utilisant l'expression USING pour les deux cas si seule une expression USING a été définie.

À titre d'exemple, si un UPDATE est émis, la politique ALL sera applicable à la fois à ce que l'UPDATE sera capable de sélectionner comme lignes à mettre à jour (en appliquant l'expression USING), et aux lignes mises à jour résultantes, pour vérifier si elles sont autorisées à être ajoutées à la table (en appliquant l'expression WITH CHECK si elle est définie, et l'expression USING sinon). Si une commande INSERT ou UPDATE tente d'ajouter à la table des lignes qui ne satisfont pas l'expres

sion WITH CHECK de la politique ALL, l
'ensemble de la commande sera annulé.

SELEC

T
Utiliser SELECT pour une politique signifie qu'elle s'appliquera aux requêtes SELECT et chaque fois que des permissions SELECT sont requises sur la relation pour laquelle la politique est définie. Le résultat est que seuls les enregistrements de la relation qui satisfont la politique SELECT seront renvoyés lors d'une requête SELECT, et que les requêtes qui nécessitent des permissions SELECT, comme UPDATE, ne verront également que les enregistrements autorisés par la politique SELECT. Une politique SELECT ne peut pas avoir d'expression WITH CHECK, car elle ne s'applique que dans les cas où des enregistrements sont récupérés depuis la
relation.

INSER

T
Utiliser INSERT pour une politique signifie qu'elle s'appliquera aux commandes INSERT et aux commandes MERGE contenant des actions INSERT. Les lignes insérées qui ne satisfont pas cette politique entraîneront une erreur de violation de politique, et l'ensemble de la commande INSERT sera annulé. Une politique INSERT ne peut pas avoir d'expression USING, car elle ne s'applique que dans les cas où des enregistrements sont ajoutés à la relation.

Notez que INSERT avec ON CONFLICT DO UPDATE ne vérifie l

es expressions WITH CHECK des politiques INSERT que pour
les lignes ajoutées à la relation par le chemin INSERT.

UPDAT

E
Utiliser UPDATE pour une politique signifie qu'elle s'appliquera aux commandes UPDATE, SELECT FOR UPDATE et SELECT FOR SHARE, ainsi qu'aux clauses auxiliaires ON CONFLICT DO UPDATE des commandes INSERT. Les commandes MERGE contenant des actions UPDATE sont également affectées. Étant donné que UPDATE consiste à récupérer un enregistrement existant et à le remplacer par un nouvel enregistrement modifié, les politiques UPDATE acceptent à la fois une expression USING et une expression WITH CHECK. L'expression USING détermine quels enregistrements la commande UPDATE verra pour opérer, tandis que l'expression WITH CHECK définit quelles lignes modifiées sont autorisées à être stockées dans la relation.

Toutes les lignes dont les valeurs mises à jour ne satisfont passs l'expression WITH CHECK provoquera une erreur et que la commande entière sera interrompue. Si seule une clause USING est spécifiée, alors cette clause sera utilisée à la fois pour les cas USING et WITH

CHECK.

Typiquement, une commande UPDATE a aussi besoin de lire des données depuis des colonnes dans la relation mise à jour (par exemple, dans une clause WHERE ou une clause RETURNING, ou dans une expression à droite de la clause SET). Dans ce cas, les droits SELECT sont aussi requis sur la relation mise à jour, et les politiques SELECT ou ALL appropriées seront appliquées en plus des politiques UPDATE. Ainsi, l'utilisateur doit avoir accès à la ou aux lignes mises à jour via une politique SELECT ou ALL en plus d'avoir la permission de mettre à jour la ou les lignes via une politique UPDATE ou

ALL.

Lorsqu'une commande INSERT a une clause auxiliaire ON CONFLICT DO UPDATE, si le chemin UPDATE est emprunté, la ligne à mettre à jour est d'abord vérifiée par rapport aux expressions USING de toute politique UPDATE, puis la nouvelle ligne mise à jour est vérifiée par rapport aux expressions WITH CHECK. Notez cependant que, contrairement à une commande UPDATE autonome, si la ligne existante ne passe pas les expressions USING, une erreur sera lancée (le chemin UPDATE ne sera jamais évité si

lencieu
sement).

DELET

E
Utiliser DELETE pour une politique signifie qu'elle s'appliquera aux commandes DELETE. Seules les lignes qui passent cette politique seront vues par une commande DELETE. Il peut y avoir des lignes visibles via un SELECT qui ne sont pas disponibles pour la suppression, si elles ne passent pas l'expression USING pour la politique DELETE.

Dans la plupart des cas, une commande DELETE a aussi besoin de lire des données depuis des colonnes dans la relation à partir de laquelle elle supprime (par exemple, dans une clause WHERE ou une clause RETURNING). Dans ce cas, les droits SELECT sont aussi requis sur la relation, et les politiques SELECT ou ALL appropriées seront appliquées en plus des politiques DELETE. Ainsi, l'utilisateur doit avoir accès à la ou aux lignes supprimées via une politique SELECT ou ALL en plus d'avoir la permission de supprimer la ou les lignes via une politique DELETE ou

ALL.

Une politique DELETE ne peut pas avoir d'expression WITH CHECK, car elle

ne s'applique que dans les cas où des enregistrements sont supprimés d
e la relation, de sorte qu'il n'y a pas de nouvelle ligne à vérifier.

Application de politiques

multiples

Lorsque plusieurs politiques de types de commande différents s'appliquent à la même commande (par exemple,
des politiques SELECT et UPDATE appliquées à une commande UPDATE), alors l'utilisateur doit avoir les deux types de permissions (par exemple, la permission de sélectionner des lignes dans la relation ainsi que la permission de les mettre à jour). Ainsi, les expressions pour un type de politique sont combinées avec les expressions pour l'autre type de politique à l'aide de l'opérateur

AND.

Lorsque plusieurs politiques du même type de commande s'appliquent à la même commande, alors il doit y avoir au moins une politique PERMISSIVE accordant l'accès à la relation, et toutes les politiques RESTRICTIVE doivent passer. Ainsi, toutes les expressions des politiques PERMISSIVE sont combinées à l'aide de OR, toutes les expressions des politiques RESTRICTIVE sont combinées à l'aide de AND, et les résultats sont combinés à l'aide de AND. S'il n'y a pas de politiques PERMISSIVE, l'accès est

refusé.

Notez que, pour les besoins de la combinaison de politiques multiples, les politiques ALL sont traitées comme ayant le même type que l'autre type de politique qui est

appliqué.

Par exemple, dans une commande UPDATE nécessitant à la fois les permissions SELECT et UPDATE, s'il y a plusieurs politiques applicables de chaque type, elles seront combinées comme suit

NOTE

S

Vous devez être le propriétaire d'une table pour créer ou modifier des politiques pour

celle-ci.

Bien que les politiques soient appliquées pour les requêtes explicites contre les tables de la base de données, elles ne sont pas appliquées lorsque le système effectue des vérifications d'intégrité référentielle internes ou valide des contraintes. Cela signifie qu'il existe des moyens indirects de déterminer qu'une valeur donnée existe. Un exemple est la tentative d'insérer une valeur en double dans une colonne qui est une clé primaire ou qui a une contrainte unique. Si l'insertion échoue, l'utilisateur peut en déduire que la valeur existe déjà. (Cet exemple suppose que l'utilisateur est autorisé par la politique à insérer des enregistrements qu'il n'est pas autorisé à voir.) Un autre exemple est le cas où un utilisateur est autorisé à insérer dans une table qui en référence une autre, autrement cachée. L'existence peut être déterminée par l'utilisateur en insérant des valeurs dans la table de référence, où le succès indiquerait que la valeur existe dans la table référencée. Ces problèmes peuvent être résolus en élaborant soigneusement des politiques pour empêcher les utilisateurs d'insérer, de supprimer ou de mettre à jour des enregistrements du tout qui pourraient indiquer une valeur qu'ils ne sont pas autrement en mesure de voir, ou en utilisant des valeurs générées (par exemple, des clés de substitution) au lieu de clés avec des significations

externes.

Généralement, le système appliquera les conditions de filtrage imposées à l'aide de politiques de sécurité avant les qualifications qui apparaissent dans les requêtes des utilisateurs, afin d'éviter l'exposition involontaire des données protégées à des fonctions définies par l'utilisateur qui pourraient ne pas être dignes de confiance. Cependant, les fonctions et opérateurs marqués par le système (ou l'administrateur système) comme LEAKPROOF peuvent être évalués avant les expressions de politique, car ils sont supposés être dignes de

confiance.

Puisque les expressions de politique sont ajoutées directement à la requête de l'utilisateur, elles seront exécutées avec les droits de l'utilisateur qui exécute la requête globale. Par conséquent, les utilisateurs qui utilisent une politique donnée doivent pouvoir accéder à toutes les tables ou fonctions référencées dans l'expression, sinon ils recevront simplement une erreur de permission refusée lors de la tentative d'interroger la table qui a la sécurité au niveau des lignes activée. Cela ne change pas le fonctionnement des vues, cependant. Comme pour les requêtes et vues normales, les vérifications de permission et les politiques pour les tables référencées par une vue utiliseront les droits du propriétaire de la vue et toutes les politiques qui s'appliquent au propriétaire de la vue, sauf si la vue est définie en utilisant l'option security_invoker (voir CREATE VI

EW).

Il n'existe pas de politique distincte pour MERGE. À la place, les politiques définies pour SELECT, INSERT, UPDATE et DELETE sont appliquées lors de l'exécution de MERGE, en fonction des actions qui sont

effectuées.

Des discussions supplémentaires et des exemples pratiques peuvent être trouvés dans la Section

5.
9.
