DESCRIPTIO

N

CREATE TYPE enregistre un nouveau type de données pour utilisation dans la base de données courante. L'utilisateur qui définit un type en devient le

propriétaire.

Si un nom de schéma est fourni, le type est créé dans le schéma spécifié. Sinon, il est créé dans le schéma courant. Le nom du type doit être distinct de celui de tout type ou domaine existant dans le même schéma. (Comme les tables ont des types de données associés, le nom du type doit également être distinct de celui de toute table existante dans le même schéma.

)

Il existe cinq formes de CREATE TYPE, comme le montre le synopsis de syntaxe ci-dessus. Elles créent respectivement un type composite, un type énuméré, un type plage, un type de base ou un type coquille. Les quatre premiers sont discutés tour à tour ci-dessous. Un type coquille est simplement un emplacement réservé pour un type à définir plus tard ; il est créé en émettant CREATE TYPE sans aucun paramètre autre que le nom du type. Les types coquilles sont nécessaires comme références anticipées lors de la création de types plage et de types de base, comme discuté dans ces

sections.

Types

composites

La première forme de CREATE TYPE crée un type composite. Le type composite est spécifié par une liste de noms d'attributs et de types de données. La collation d'un attribut peut également être spécifiée, si son type de données est triable. Un type composite est essentiellement le même que le type de ligne d'une table, mais utiliser CREATE TYPE évite la nécessité de créer une table réelle lorsque tout ce que l'on souhaite est de définir un type. Un type composite autonome est utile, par exemple, comme argument ou type de retour d'une

fonction.

Pour pouvoir créer un type composite

, vous devez avoir le privilège U
SAGE sur tous les types d'attributs.

Types

énumérés

La deuxième forme de CREATE TYPE crée un type énuméré (enum), comme décrit dans la section 8.7. Les types enum prennent une liste de libellés entre guillemets, chacun devant faire moins de NAMEDATALEN octets de long (64 octets dans une compilation standard de PostgreSQL). (Il est possible de créer un type énuméré avec zéro libellé, mais un tel type ne peut pas être utilisé pour stocker des valeurs avant qu'au moins un libellé n'ait été ajouté à l'aide de ALTER

TYP
E.)

Types

plage

La troisième forme de CREATE TYPE crée un nouveau type plage, comme décrit dans la section 8.

17.

Le sous_type d'un type plage peut être de n'importe quel type ayant une classe opérateur b-tree associée (pour déterminer l'ordre des valeurs pour le type plage). Normalement, la classe opérateur b-tree par défaut du sous_type est utilisée pour déterminer l'ordre ; pour utiliser une classe opérateur non par défaut, spécifiez son nom avec subtype_opclass. Si le sous_type est triable et que vous souhaitez utiliser une collation non par défaut dans l'ordre de la plage, spécifiez la collation souhaitée avec l'option collation

.

La fonction canonique facultative doit prendre un argument de type plage en cours de définition et renvoyer une valeur du même type. Elle est utilisée pour convertir les valeurs de plage en une forme canonique, le cas échéant. Voir la section 8.17.8 pour plus d'informations. La création d'une fonction canonique est un peu délicate, car elle doit être définie avant que le type plage puisse être déclaré. Pour ce faire, vous devez d'abord créer un type coquille, qui est un type de réservation qui n'a aucune propriété autre qu'un nom et un propriétaire. Cela se fait en émettant la commande CREATE TYPE nom, sans paramètres supplémentaires. Ensuite, la fonction peut être déclarée en utilisant le type coquille comme argument et résultat, et enfin le type plage peut être déclaré en utilisant le même nom. Cela remplace automatiquement l'entrée du type coquille par un type plage

valide.

La fonction subtype_diff facultative doit prendre deux valeurs de type sous_type comme argument et renvoyer une valeur double précision représentant la différence entre les deux valeurs données. Bien que facultative, sa fourniture permet une bien plus grande efficacité des index GiST sur les colonnes de type plage. Voir la section 8.17.8 pour plus

d'informations.

Le paramètre multirange_type_name facultatif spécifie le nom du type multirange correspondant. S'il n'est pas spécifié, ce nom est choisi automatiquement comme suit. Si le nom du type plage contient la sous-chaîne range, le

nom du type multirange est formé en remplaçant la sous-chaîne range par multirange dans le nom du type pla
ge. Sinon, le nom du type multirange est formé en ajoutant le suffixe _multirange au nom du type plage.

Types de

base

La quatrième forme de CREATE TYPE crée un nouveau type de base (type scalaire). Pour créer un nouveau type de base, vous devez être un superutilisateur. (Cette restriction est imposée car une définition de type erronée pourrait déstabiliser ou même faire planter le serveur.

)

Les paramètres peuvent apparaître dans n'importe quel ordre, pas seulement celui illustré ci-dessus, et la plupart sont facultatifs. Vous devez enregistrer deux fonctions ou plus (à l'aide de CREATE FUNCTION) avant de définir le type. Les fonctions de support input_function et output_function sont requises, tandis que les fonctions receive_function, send_function, type_modifier_input_function, type_modifier_output_function, analyze_function et subscript_function sont facultatives. Généralement, ces fonctions doivent être codées en C ou dans un autre langage de bas

niveau.

La fonction input_function convertit la représentation textuelle externe du type en la représentation interne utilisée par les opérateurs et les fonctions définis pour le type. La fonction output_function effectue la transformation inverse. La fonction d'entrée peut être déclarée comme prenant un argument de type cstring, ou comme prenant trois arguments de types cstring, oid, integer. Le premier argument est le texte d'entrée sous forme de chaîne C, le deuxième argument est l'OID propre au type (sauf pour les types de tableau, qui reçoivent à la place l'OID de leur type élément), et le troisième est le typmod de la colonne de destination, si connu (-1 sera passé sinon). La fonction d'entrée doit renvoyer une valeur du type de données lui-même. Habituellement, une fonction d'entrée devrait être déclarée STRICT ; si ce n'est pas le cas, elle sera appelée avec un premier paramètre NULL lors de la lecture d'une valeur d'entrée NULL. La fonction doit quand même renvoyer NULL dans ce cas, sauf si elle lève une erreur. (Ce cas vise principalement à prendre en charge les fonctions d'entrée de domaine, qui pourraient avoir besoin de rejeter les entrées NULL.) La fonction de sortie doit être déclarée comme prenant un argument du nouveau type de données. La fonction de sortie doit renvoyer le type cstring. Les fonctions de sortie ne sont pas invoquées pour les valeurs

NULL.

La fonction receive_function facultative convertit la représentation binaire externe du type en la représentation interne. Si cette fonction n'est pas fournie, le type ne peut pas participer à l'entrée binaire. La représentation binaire devrait être choisie pour être peu coûteuse à convertir en forme interne, tout en étant raisonnablement portable. (Par exemple, les types de données entiers standard utilisent l'ordre des octets réseau comme représentation binaire externe, tandis que la représentation interne est dans l'ordre natif de la machine.) La fonction de réception devrait effectuer une vérification adéquate pour s'assurer que la valeur est valide. La fonction de réception peut être déclarée comme prenant un argument de type internal, ou comme prenant trois arguments de types internal, oid, integer. Le premier argument est un pointeur vers un tampon StringInfo contenanteive octets ; les arguments optionnels sont les mêmes que pour la fonction d'entrée de texte. La fonction de réception doit renvoyer une valeur du type de données lui-même. Habituellement, une fonction de réception doit être déclarée STRICT ; si ce n'est pas le cas, elle sera appelée avec un premier paramètre NULL lors de la lecture d'une valeur d'entrée NULL. La fonction doit quand même renvoyer NULL dans ce cas, sauf si elle lève une erreur. (Ce cas vise principalement à prendre en charge les fonctions de réception de domaine, qui pourraient avoir besoin de rejeter les entrées NULL.) De même, l'optionnel send_function convertit de la représentation interne vers la représentation binaire externe. Si cette fonction n'est pas fournie, le type ne peut pas participer à la sortie binaire. La fonction d'envoi doit être déclarée pour prendre un argument du nouveau type de données. La fonction d'envoi doit renvoyer le type bytea. Les fonctions d'envoi ne sont pas invoquées pour les valeurs

NULL.

Vous devriez à ce stade vous demander comment les fonctions d'entrée et de sortie peuvent être déclarées pour avoir des résultats ou des arguments du nouveau type, alors qu'elles doivent être créées avant que le nouveau type puisse être créé. La réponse est que le type devrait d'abord être défini comme un type coquille, qui est un type de substitution qui n'a aucune propriété à part un nom et un propriétaire. Cela se fait en émettant la commande CREATE TYPE name, sans paramètres supplémentaires. Ensuite, les fonctions d'E/S en C peuvent être définies en faisant référence au type coquille. Enfin, CREATE TYPE avec une définition complète remplace l'entrée de coquille par une définition de type complète et valide, après quoi le nouveau type peut être utilisé

normalement.

L'optionnel type_modifier_input_function et type_modifier_output_function sont nécessaires si le type prend en charge des modificateurs, c'est-à-dire des contraintes optionnelles attachées à une déclaration de type, comme char(5) ou numeric(30,2). PostgreSQL permet aux types définis par l'utilisateur de prendre un ou plusieurs constantes simples ou identifiants comme modificateurs. Cependant, ces informations doivent pouvoir être regroupées en une seule valeur entière non négative pour le stockage dans les catalogues système. Le type_modifier_input_function reçoit le ou les modificateurs déclarés sous la forme d'un tableau de cstring. Il doit vérifier la validité des valeurs (en lançant une erreur si elles sont incorrectes) et, si elles sont correctes, renvoyer une seule valeur entière non négative qui sera stockée dans la colonne « typmod ». Les modificateurs de type seront rejetés si le type n'a pas de type_modifier_input_function. Le type_modifier_output_function convertit la valeur entière interne typmod en la forme correcte pour l'affichage à l'utilisateur. Il doit renvoyer une valeur cstring qui est la chaîne exacte à ajouter au nom du type ; par exemple, la fonction de numeric pourrait renvoyer (30,2). Il est permis d'omettre le type_modifier_output_function, auquel cas le format d'affichage par défaut est simplement la valeur entière typmod stockée entourée de

parenthèses.

L'optionnel analyze_function effectue la collecte de statistiques spécifiques au type pour les colonnes du type de données. Par défaut, ANALYZE essaiera de recueillir des statistiques en utilisant les opérateurs « égal » et « inférieur à » du type, s'il existe une classe d'opérateur b-tree par défaut pour le type. Pour les types non scalaires, ce comportement est probablement inapproprié, il peut donc être remplacé en spécifiant une fonction d'analyse personnalisée. La fonction d'analyse doit être déclarée pour prendre un seul argument de type internal et renvoyer un résultat booléen. L'API détaillée des fonctions d'analyse se trouve dans src/include/commands/vacuum.

h.

L'optionnel subscript_function permet au type de données d'être indexé dans les commandes SQL. Spécifier cette fonction ne fait pas considérer le type comme un type de tableau « véritable » ; par exemple, il ne sera pas un candidat pour le type de résultat des constructions ARRAY[]. Mais si l'indexation d'une valeur du type est une notation naturelle pour en extraire des données, alors un subscript_function peut être écrit pour définir ce que cela signifie. La fonction d'indexation doit être déclarée pour prendre un seul argument de type internal et renvoyer un résultat internal, qui est un pointeur vers une structure de méthodes (fonctions) qui implémentent l'indexation. L'API détaillée des fonctions d'indexation se trouve dans src/include/nodes/subscripting.h. Il peut également être utile de lire l'implémentation des tableaux dans src/backend/utils/adt/arraysubs.c, ou le code plus simple dans contrib/hstore/hstore_subs.c. Des informations supplémentaires apparaissent dans Types de tableau

ci-dessous.

Bien que les détails de la représentation interne du nouveau type soient uniquement connus des fonctions d'E/S et des autres fonctions que vous créez pour travailler avec le type, il existe plusieurs propriétés de la représentation interne qui doivent être déclarées à PostgreSQL. La plus importante est internallength. Les types de données de base peuvent être de longueur fixe, auquel cas internallength est un entier positif, ou de longueur variable, indiqué en définissant internallength à VARIABLE. (En interne, cela est représenté par typlen défini à -1.) La représentation interne de tous les types de longueur variable doit commencer par un entier de 4 octets donnant la longueur totale de cette valeur du type. (Notez que le champ de longueur est souvent encodé, comme décrit dans la section 66.2 ; il est imprudent d'y accéder directement.

)

L'indicateur optionnel PASSEDBYVALUE indique que les valeurs de ce type de données sont passées par valeur plutôt que par référence. Les types passés par valeur doivent être de longueur fixe, et leur représentation interne ne peut pas être plus grande que la taille du type Datum (4 octets sur certaines machines, 8 octets sur d'autres)

.

Le paramètre alignment spécifie l'alignement de stockage requis pour le type de données. Les valeurs autorisées équivalent à un alignement sur des limites de 1, 2, 4 ou 8 octets. Notez que les types de longueur variable doivent avoir un alignement d'au moins 4, car ils contiennent nécessairement un int4 comme premier

composant.

Le paramètre storage permet de sélectionner des stratégies de stockage pour les types de données de longueur variable. (Seul plain est autorisé pour les types de longueur fixe.) plain spécifie que les données du type seront toujours stockées en ligne et non compressées. extended spécifie que le système essaiera d'abord de compresser une valeur de données longue, et déplacera la valeur hors de la ligne principale de la table si elle est encore trop longue. external permet le déplacement de la valeur hors de la table principale, mais le système n'essaiera pas de la compresser. main permet la compression, mais décourage le déplacement de la valeur hors de la table principale. (Les éléments de données avec cette stratégie de stockage pourraient quand même être déplacés hors de la table principale s'il n'y a aucun autre moyen de faire tenir une ligne, mais ils seront conservés dans la table principale de préférence aux éléments extended et external.

)

Toutes les valeurs storage autres que plain impliquent que les fonctions du type de données peuvent gérer des valeurs qui ont été toastées, comme décrit dans la section 66.2 et la section 36.13.1. L'autre valeur spécifique donnée détermine simplement la stratégie de stockage TOAST par défaut pour les colonnes d'un type de données toastable ; les utilisateurs peuvent choisir d'autres stratégies pour des colonnes individuelles en utilisant ALTER TABLE SET

STORAGE.

Le paramètre like_type fournit une méthode alternative pour spécifier les propriétés de représentation de base d'un type de données : les copier depuis un type existant. Les valeurs de internallength, passedbyvalue, alignment et storage sont copiées depuis le type nommé. (Il est possible, bien que généralement indésirable, de remplacer certaines de ces valeurs en les spécifiant avec la clause LIKE.) Spécifier la représentation de cette manière est particulièrement utile lorsque l'implémentation de bas niveau du nouveau type « profite » d'un type existant d'une certaine

manière.

Les paramètres category et preferred peuvent être utilisés pour aider à contrôler quel cast implicite sera appliqué dans les situations ambiguës. Chaque type de données appartient à une catégorie nommée par un seul caractère ASCII, et chaque type est soit « préféré » soit non au sein de sa catégorie. L'analyseur préférera le cast vers les types préférés (mais seulement depuis d'autres types de la même catégorie) lorsque cette règle est utile pour résoudre des fonctions ou opérateurs surchargés. Pour plus de détails, voir le chapitre 10. Pour les types qui n'ont pas de casts implicites vers ou depuis d'autres types, il suffit de laisser ces réglages aux valeurs par défaut. Cependant, pour un groupe de types liés qui ont des casts implicites, il est souvent utile de les marquer tous comme appartenant à une catégorie et de sélectionner un ou deux des types « les plus généraux » comme étant préférés au sein de la catégorie. Le paramètre category est particulièrement utile lors de l'ajout d'un type défini par l'utilisateur à une catégorie intégrée existante, comme les types numériques ou les types de chaînes. Cependant, il est également possible de créer de nouvelles catégories de types entièrement définies par l'utilisateur. Sélectionnez n'importe quel caractère ASCII autre qu'une lettre majuscule pour nommer une telle

catégorie.

Une valeur par défaut peut être spécifiée, au cas où un utilisateur voudrait que les colonnes du type de données aient une valeur par défaut autre que la valeur nulle. Spécifiez la valeur par défaut avec le mot-clé DEFAULT. (Une telle valeur par défaut peut être remplacée par une clause DEFAULT explicite attachée à une colonne particulière.

)

Pour indiquer qu'un type est un type de tableau de longueur fixe, spécifiez le type des éléments du tableau avec le mot-clé ELEMENT. Par exemple, pour définir un tableau d'entiers de 4 octets (int4), spécifiez ELEMENT = int4. Pour plus de détails, voir Types de tableau

ci-dessous.

Pour indiquer le délimiteur à utiliser entre les valeurs dans la représentation externe des tableaux de ce type, delimiter peut être défini sur un caractère spécifique. Le délimiteur par défaut est la virgule (,). Notez que le délimiteur est associé au type des éléments du tableau, pas au type de tableau

lui-même.

Si le paramètre booléen optionnel collatable est vrai, les définitions de colonnes et les expressions du type peuvent porter des informations de collation via l'utilisation de la clause COLLATE. Il appartient aux impl

émentations des fonctions opérant sur le type d'utiliser réellement les informations de colla
tion ; cela ne se produit pas automatiquement simplement en marquant le type comme collatable.

Types de

tableau

Chaque fois qu'un type défini par l'utilisateur est créé, PostgreSQL crée automatiquement un type de tableau associé, dont le nom consiste en le nom du type d'élément préfixé d'un souligné, et tronqué si nécessaire pour rester inférieur à NAMEDATALEN octets. (Si le nom ainsi généré entre en collision avec un nom de type existant, le processus est répété jusqu'à ce qu'un nom sans collision soit trouvé.) Ce type de tableau créé implicitement est de longueur variable et utilise les fonctions d'entrée et de sortie intégrées array_in et array_out. De plus, c'est ce type que le système utilise pour des constructions telles que ARRAY[] sur le type défini par l'utilisateur. Le type de tableau suit tout changement du propriétaire ou du schéma de son type d'élément, et est supprimé si le type d'élément

l'est.

Vous pourriez raisonnablement vous demander pourquoi il existe une option ELEMENT, si le système crée automatiquement le bon type de tableau. Le cas principal où il est utile d'utiliser ELEMENT est lorsque vous créez un type de longueur fixe qui est accidentellement un tableau d'un certain nombre de choses identiques en interne, et que vous voulez permettre l'accès direct à ces choses par indexation, en plus de toutes les opérations que vous prévoyez de fournir pour le type dans son ensemble. Par exemple, tyun point est représenté simplement par deux nombres en virgule flottante, auxquels on peut accéder via point[0] et point[1]. Notez que cette fonctionnalité ne fonctionne que pour les types de longueur fixe dont la forme interne est exactement une séquence de champs identiques de longueur fixe. Pour des raisons historiques (c'est-à-dire que c'est clairement faux, mais il est bien trop tard pour le changer), l'indexation des types de tableau de longueur fixe commence à zéro, plutôt qu'à un comme pour les tableaux de longueur

variable.

Spécifier l'option SUBSCRIPT permet d'indexer un type de données, même si le système ne le considère pas autrement comme un type tableau. Le comportement décrit ci-dessus pour les tableaux de longueur fixe est en fait implémenté par la fonction de gestion SUBSCRIPT raw_array_subscript_handler, qui est utilisée automatiquement si vous spécifiez ELEMENT pour un type de longueur fixe sans écrire également SUBSCRIPT

.

Lorsque vous spécifiez une fonction SUBSCRIPT personnalisée, il n'est pas nécessaire de spécifier ELEMENT, sauf si la fonction de gestion SUBSCRIPT a besoin de consulter typelem pour savoir quoi renvoyer. Sachez que spécifier ELEMENT fait supposer au système que le nouveau type contient, ou dépend physiquement d'une manière ou d'un

e autre, le type élément ; ainsi, par exemple, la mo
dification des propriétés du type élément ne sera pas
autorisée s'il existe des colonnes du type dépendant.

NOTE

S

Étant donné qu'il n'y a aucune restriction sur l'utilisation d'un type de données une fois qu'il a été créé, créer un type de base ou un type plage équivaut à accorder la permission d'exécution publique sur les fonctions mentionnées dans la définition du type. Cela n'est généralement pas un problème pour les types de fonctions utiles dans une définition de type. Mais vous pourriez vouloir réfléchir à deux fois avant de concevoir un type d'une manière qui nécessiterait l'utilisation d'informations « secrètes » lors de sa conversion vers ou depuis la forme

externe.

Avant la version 8.3 de PostgreSQL, le nom d'un type de tableau généré était toujours exactement le nom du type élément avec un caractère de soulignement (_) préfixé. (Les noms de type étaient donc limités en longueur à un caractère de moins que les autres noms.) Bien que ce soit encore généralement le cas, le nom du type de tableau peut varier de cela en cas de noms de longueur maximale ou de collisions avec des noms de type utilisateur qui commencent par un soulignement. Écrire du code qui dépend de cette convention est donc déconseillé. Utilisez plutôt pg_type.typarray pour localiser le type de tableau associé à un type

donné.

Il peut être conseillé d'éviter d'utiliser des noms de type et de table qui commencent par un soulignement. Bien que le serveur modifie les noms de type de tableau générés pour éviter les collisions avec les noms fournis par l'utilisateur, il y a toujours un risque de confusion, en particulier avec les anciens logiciels clients qui peuvent supposer que les noms de type commençant par des soulignements représentent toujours des

tableaux.

Avant la version 8.2 de PostgreSQL, la syntaxe de création de type shell CREATE TYPE name n'existait pas. La manière de créer un nouveau type de base était de créer d'abord sa fonction d'entrée. Dans cette approche, PostgreSQL verra d'abord le nom du nouveau type de données comme type de retour de la fonction d'entrée. Le type shell est créé implicitement dans cette situation, et il peut ensuite être référencé dans les définitions des autres fonctions d'E/S. Cette approche fonctionne toujours, mais est déconseillée et pourrait être interdite dans une future version. De plus, pour éviter d'encombrer accidentellement les catalogues avec des types shell à la suite de simples fautes de frappe dans les définitions de fonctions, un type shell ne sera créé de cette manière que si la fonction d'entrée est écrite en

C.

Dans la version 16 et ultérieures de PostgreSQL, il est souhaitable que les fonctions d'entrée des types de base renvoient des erreurs « douces » en utilisant le nouveau mécanisme errsave()/ereturn(), plutôt que de lever des exceptions ereport() comme dans les versions précédentes. Voir

src/backend/utils/fmgr/READ
ME pour plus d'informations.

EXEMPLE

S

Cet exemple crée un type composite et l'utilise dans une définition de fonction

: 
CREATE TYPE compfoo AS (f1 int, f2 text);
CREATE
FUNCTION getfoo() RETURNS SETOF compfoo AS $$
SELECT fooid, fooname FROM foo $$ LANGUAGE SQL;

Cet exemple crée un type énuméré et l'utilise dans une définition de table

: 
CREATE TYPE bug_status AS ENUM ('new', 'open', 'closed');
CREATE TABLE bug (
    id serial,
    description text,
    status bug_status
)
;

Cet exemple crée un type plage

: 
CREATE TYPE float8_range A
S RANGE (subtype = float8,
subtype_diff = float8mi);

Cet exemple crée le type de données de base box puis utilise le type dans une définition de table

: 
CREATE TYPE box;
CREATE FUNCTION my_box_in_function(cstring) RETURNS box AS ... ;
CREATE FUNCTION my_box_out_function(box) RETURNS cstring AS ... ;
CREATE TYPE box (
    INTERNALLENGTH = 16,
    INPUT = my_box_in_function,
    OUTPUT = my_box_out_function
);
CREATE TABLE myboxes (
    id integer,
    description box
)
;

Si la structure interne de box était un tableau de quatre éléments float4, nous pourrions plutôt utiliser

: 
CREATE TYPE box (
    INTERNALLENGTH = 16,
    INPUT = my_box_in_function,
    OUTPUT = my_box_out_function,
    ELEMENT = float4
)
;

ce qui permettrait d'accéder aux nombres composant une valeur box par indexation. Sinon, le type se comporte de la même manière

qu'avant.

Cet exemple crée un type d'objet volumineux et l'utilise dans une définition de table

: 
CREATE TYPE bigobj (
    INPUT = lo_filein, OUTPUT = lo_fileout,
    INTERNALLENGTH = VARIABLE
);
CREATE TABLE big_objs (
    id integer,
    obj bigobj
)
;

PostgreSQL.
