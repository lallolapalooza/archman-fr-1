SYNOPSI

S 
CREATE CAST (source_type AS target_type)
    WITH FUNCTION function_name [ (argument_type [, ...]) ]
    [ AS ASSIGNMENT | AS IMPLICIT ]
CREATE CAST (source_type AS target_type)
    WITHOUT FUNCTION
    [ AS ASSIGNMENT | AS IMPLICIT ]
CREATE CAST (source_type AS target_type)
    WITH INOUT
[ AS ASSIGNMENT
| AS IMPLICIT ]

DESCRIPTIO

N

CREATE CAST définit une nouvelle conversion. Une conversion spécifie comment effectuer une transformation entre deux types de données. Par

exemple, 
SELECT CA
ST(42 AS
float8);

convertit la constante entière 42 en type float8 en invoquant une fonction spécifiée précédemment, dans ce cas float8(int4). (Si aucune conversion appropriée n'a été définie, la transformation échoue.

)

Deux types peuvent être coercibles binaires, ce qui signifie que la transformation peut être effectuée « gratuitement » sans invoquer aucune fonction. Cela requiert que les valeurs correspondantes utilisent la même représentation interne. Par exemple, les types text et varchar sont coercibles binaires dans les deux sens. La coercibilité binaire n'est pas nécessairement une relation symétrique. Par exemple, la conversion de xml vers text peut être effectuée pour rien dans l'implémentation actuelle, mais la direction inverse requiert une fonction qui effectue au moins une vérification syntaxique. (Deux types qui sont coercibles binaires dans les deux sens sont aussi appelés compatibles binaires.

)

Vous pouvez définir une conversion comme une conversion E/S en utilisant la syntaxe WITH INOUT. Une conversion E/S est effectuée en invoquant la fonction de sortie du type de données source, et en passant la chaîne résultante à la fonction d'entrée du type de données cible. Dans beaucoup de cas courants, cette fonctionnalité évite la nécessité d'écrire une fonction de conversion séparée. Une conversion E/S agit de la même manière qu'une conversion basée sur une fonction régulière ; seule l' implémentation est

différente.

Par défaut, une conversion ne peut être invoquée que par une requête de conversion explicite, c'est-à-dire une construction explicite CAST(x AS typename) ou x::typename

.

Si la conversion est marquée AS ASSIGNMENT, elle peut être invoquée implicitement lors de l'affectation d'une valeur à une colonne du type de données cible. Par exemple, en supposant que foo.f1 est une colonne de type text, alors

: 
INSERT INTO
foo (f1) V
ALUES (42);

sera autorisé si la conversion du type integer au type text est marquée AS ASSIGNMENT, sinon non. (Nous utilisons généralement le terme conversion d'affectation pour décrire ce type de conversion.

)

Si la conversion est marquée AS IMPLICIT, elle peut être invoquée implicitement dans n'importe quel contexte, qu'il s'agisse d'une affectation ou de manière interne dans une expression. (Nous utilisons généralement le terme conversion implicite pour décrire ce type de conversion.) Par exemple, considérez cette requête

: 
SELEC
T 2 +
4.0;

L'analyseur marque initialement les constantes comme étant de type integer et numeric respectivement. Il n'y a pas d'opérateur integer + numeric dans les catalogues système, mais il y a un opérateur numeric + numeric. La requête réussira donc si une conversion de integer vers numeric est disponible et est marquée AS IMPLICIT — ce qui est en fait le cas. L'analyseur appliquera la conversion implicite et résoudra la requête comme si elle avait été

écrite 
SELECT CAST
( 2 AS nume
ric ) + 4.0;

Maintenant, les catalogues fournissent aussi une conversion de numeric vers integer. Si cette conversion était marquée AS IMPLICIT — ce qui n'est pas le cas — alors l' analyseur ferait face au choix entre l'interprétation ci-dessus et l'alternative de convertir la constante numeric en integer et d'appliquer l' opérateur integer + integer. N'ayant aucune connaissance du choix à préférer, il abandonnerait et déclarerait la requête ambiguë. Le fait que seule une des deux conversions soit implicite est la manière dont nous enseignons à l'analyseur de préférer la résolution d'une expression mixte numeric-et-integer comme numeric ; il n'y a pas de connaissance intégrée à ce

sujet.

Il est sage d'être prudent quant au marquage des conversions comme implicites. Une abondance excessive de chemins de conversion implicite peut causer à PostgreSQL de choisir des interprétations surprenantes des commandes, ou de ne pas pouvoir résoudre les commandes du tout car il y a plusieurs interprétations possibles. Une bonne règle empirique est de rendre une conversion invoquable implicitement uniquement pour les transformations préservant l'information entre des types de la même catégorie générale de types. Par exemple, la conversion de int2 vers int4 peut raisonnablement être implicite, mais la conversion de float8 vers int4 devrait probablement être uniquement d'affectation. Les conversions entre catégories de types, comme text vers int4, sont préférablement rendues explicites

uniquement.

Note

Parfois, il est nécessaire pour des raisons d'utilisabilité ou de conformité aux normes de fournir plusieurs conversions implicites parmi un ensemble de types, résultant en une ambiguïté qui ne peut être évitée comme ci-dessus. L'analyseur a une heuristique de repli basée sur les catégories de types et les types préférés qui peut aider à fournir le comportement désiré dans de tels cas. Voir CREATE TYPE(CREATE_TYPE(7)) pour

plus d'inf
ormations.

Pour pouvoir créer une conversion, vous devez être propriétaire du type de données source ou cible et avoir le pri

vilège USAGE sur l'autre type. Pour créer une conversion coercible binaire, vous devez être superutilisateur. (Cet
te restriction est imposée car une conversion coercible binaire erronée peut facilement faire planter le serveur.)

PARAMÈTRE

S

source_typ

e
Le nom du type de données source de la
conversion.

target_typ

e
Le nom du type de données cible de la
conversion.

function_name[(argument_type [, ...])

]
La fonction utilisée pour effectuer la conversion. Le nom de la fonction peut être qualifiée par un schéma. Si ce n'est pas le cas, la fonction sera recherchée dans le chemin de recherche des schémas. Le type de données de résultat de la fonction doit correspondre au type cible de la conversion. Ses arguments sont discutés ci-dessous. Si aucune liste d'arguments n'est spécifiée, le nom de la fonction doit être unique dans son
schéma.

WITHOUT

FUNCTION
Indique que le type source est coercible binairement vers le type cible, donc aucune fonction n'est requise pour effectuer la
conversion.

WITH

INOUT
Indique que la conversion est une conversion E/S, effectuée en invoquant la fonction de sortie du type de données source, et en passant la chaîne résultante à la fonction d'entrée du type de données
cible.

AS

ASSIGNMENT
Indique que la conversion peut être invoquée implicitement dans les contextes
d'affectation.

AS

IMPLICIT
Indique que la conversion peut être invoquée implicitement dans n'importe quel
contexte.

Les fonctions d'implémentation de conversion peuvent avoir de un à trois arguments. Le type du premier argument doit être identique au type source de la conversion ou en être coercible binairement. Le deuxième argument, s'il est présent, doit être de type integer ; il reçoit le modificateur de type associé au type de destination, ou -1 s'il n'y en a pas. Le troisième argument, s'il est présent, doit être de type boolean ; il reçoit true si la conversion est une conversion explicite, false sinon. (Bizarrement, le standard SQL exige des comportements différents pour les conversions explicites et implicites dans certains cas. Cet argument est fourni pour les fonctions qui doivent implémenter de telles conversions. Il n'est pas recommandé de concevoir vos propres types de données de manière à ce que cela soit important.

)

Le type de retour d'une fonction de conversion doit être identique au type cible de la conversion ou en être coercible

binairement.

Ordinairement, une conversion doit avoir des types de données source et cible différents. Cependant, il est permis de déclarer une conversion avec des types source et cible identiques si elle a une fonction d'implémentation de conversion avec plus d'un argument. Ceci est utilisé pour représenter les fonctions de coercition de longueur spécifiques aux types dans les catalogues système. La fonction nommée est utilisée pour coercer une valeur du type vers la valeur de modificateur de type donnée par son deuxième

argument.

Quand une conversion a des types source et cible différents et une fonction qui prend plus d'un argument, elle supporte la conversion d'un type vers un autre et l'application d'une coercition de longueur en une seule étape. Quand une telle entrée n'est pas disponible, la coercition vers un type qui utilise un modificateur de type implique deux étapes de conversion, une pour convertir entre les types de données et une seconde pour appliquer le

modificateur.

Une conversion vers ou depuis un type de domaine n'a actuel

lement aucun effet. La conversion vers ou depuis un domain
e utilise les conversions associées à son type sous-jacent.

NOTE

S

Utilisez DROP CAST pour supprimer les conversions définies par

l'utilisateur.

Rappelez-vous que si vous voulez pouvoir convertir les types dans les deux sens, vous devez déclarer les conversions dans les deux sens

explicitement.

Il n'est généralement pas nécessaire pour créer des conversions entre types définis par l'utilisateur et les types de chaînes standard (text, varchar et char(n), ainsi que les types définis par l'utilisateur qui sont définis dans la catégorie des chaînes). PostgreSQL fournit des conversions automatiques d'E/S pour cela. Les conversions automatiques vers les types de chaînes sont traitées comme des conversions d'affectation, tandis que les conversions automatiques depuis les types de chaînes ne sont explicites que. Vous pouvez remplacer ce comportement en déclarant votre propre conversion pour remplacer une conversion automatique, mais généralement la seule raison de le faire est si vous souhaitez que la conversion soit plus facilement invocable que le réglage standard uniquement-affectation ou uniquement-explicite. Une autre raison possible est que vous voulez que la conversion se comporte différemment de la fonction d'E/S du type ; mais c'est suffisamment surprenant pour que vous devriez réfléchir à deux fois pour savoir si c'est une bonne idée. (Un petit nombre de types intégrés ont en effet des comportements différents pour les conversions, principalement en raison des exigences de la norme SQL.

)

Bien que non requis, il est recommandé que vous continuiez à suivre cette ancienne convention de nommer les fonctions d'implémentation de conversion d'après le type de données cible. Beaucoup d'utilisateurs sont habitués à pouvoir convertir des types de données en utilisant une notation de style fonction, c'est-à-dire nomtype(x). Cette notation n'est en fait rien de plus ni de moins qu'un appel de la fonction d'implémentation de conversion ; elle n'est pas traitée spécialement comme une conversion. Si vos fonctions de conversion ne sont pas nommées pour prendre en charge cette convention, vous surprendrez les utilisateurs. Puisque PostgreSQL permet la surcharge du même nom de fonction avec différents types d'arguments, il n'y a aucune difficulté à avoir plusieurs fonctions de conversion depuis différents types qui utilisent toutes le nom du type

cible.

Note

En fait, le paragraphe précédent est une simplification excessive : il y a deux cas dans lesquels une construction d'appel de fonction sera traitée comme une requête de conversion sans l'avoir associée à une fonction réelle. Si un appel de fonction nom(x) ne correspond pas exactement à une fonction existante, mais que nom est le nom d'un type de données et que pg_cast fournit une conversion coercible binaire vers ce type depuis le type de x, alors l'appel sera interprété comme une conversion coercible binaire. Cette exception est faite pour que les conversions coercibles binaires puissent être invoquées en utilisant la syntaxe fonctionnelle, même si elles ne possèdent aucune fonction. D

e même, s'il n'y a pas d'entrée pg_cast mais que la conversion serait vers ou depuis un type de chaîne, l'appel sera interprété
comme une conversion d'E/S. Cette exception permet aux conversions d'E/S d'être invoquées en utilisant la syntaxe fonctionnelle.

Note

Il y a aussi une exception à l'exception : les conversions d'E/S depuis les types composites vers les types de chaînes ne peuvent pas

être invoquées en utilisant la syntaxe fonctionnelle, mais doivent être écrites en syntaxe de conversion explicite (soit CAST, soit
la notation ::). Cette exception a été ajoutée parce qu'après l'introduction des conversions d'E/S automatiquement fournies, il a ét
é trouvé trop facile d'invoquer accidentellement une telle conversion lorsqu'une fonction ou une référence de colonne était destinée.

EXEMPLE

S

Pour créer une conversion d'affectation depuis le type bigint vers le type int4 en utilisant la fonction int4(bigint)

: 
CREATE CAST (bigint AS
int4) WITH FUNCTION int4
(bigint) AS ASSIGNMENT;

(Cette conversion

est déjà prédéfinie
dans le système.)
