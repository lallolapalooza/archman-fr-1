SYNOPSI

DESCRIPTIO

N

CREATE SUBSCRIPTION ajoute une nouvelle souscription de réplication logique. L'utilisateur qui crée la souscription en devient le propriétaire. Le nom de la souscription doit être distinct du nom de toute souscription existante dans la base de données

courante.

Une souscription représente une connexion de réplication vers le diffuseur (publisher). Ainsi, en plus d'ajouter des définitions dans les catalogues locaux, cette commande crée normalement un emplacement de réplication sur le

diffuseur.

Un travailleur de réplication logique sera démarré pour répliquer les données de la nouvelle souscription au moment du commit de la transaction dans laquelle cette commande est exécutée, à moins que la souscription ne soit initialement

désactivée.

Pour pouvoir créer une souscription, vous devez disposer des privilèges du rôle pg_create_subscription, ainsi que des privilèges CREATE sur la base de données

courante.

Des informations supplémentaires sur les souscription

s et la réplication logique dans son ensemble sont
disponibles à la section 29.2 et au chapitre 29.

Cette clause spécifie des paramètres optionnels pour une souscription.

Les paramètres suivants contrôlent ce qui se passe lors de la création de la souscription

:

connect

(booléen)
Indique si la commande CREATE SUBSCRIPTION doit se connecter au diffuseur ou non. La valeur par défaut est true. Définir cette valeur à false forcera les valeurs de create_slot, enabled et copy_data à false. (Vous ne pouvez pas combiner la définition de connect à false avec la définition de create_slot, enabled ou copy_data à true.)

Comme aucune connexion n'est établie lorsque cette option est false, aucune table n'est souscrite. Pour initier

la réplication, vous devez créer manuellement l'emplacement de réplication, activer le basculement (failover)
si nécessaire, activer la souscription et actualiser la souscription. Voir la section 29.2.3 pour des exemples.

create_slot

(booléen)
Indique si la commande doit créer l'emplacement de réplication sur le diffuseur. La valeur par défaut est true.

Si défini à false, il vous incombe de créer l'

emplacement du diffuseur d'une autre mani
ère. Voir la section 29.2.3 pour des exemples.

enabled

(booléen)
Indique si la souscription doit être activement en réplication ou si elle doit simplement être configurée mais pas encore démarrée. La valeur par défaut est
true.

slot_name

(chaîne)
Nom de l'emplacement de réplication du diffuseur à utiliser. La valeur par défaut est d'utiliser le nom de la souscription comme nom d'emplacement.

Définir slot_name à NONE signifie qu'aucun emplacement de réplication ne sera associé à la souscription. De telles souscriptions doivent également avoir enabled et create_slot définis à false. Utilisez ceci lorsque vous créerez l'emplacement de réplication ultérieurement manuellement. Voir la section 29.2.3 pour des

exemples.

Lorsque vous définissez slot_name à un nom valide et create_slot à false, la valeur de la propriété failover de l'emplacement nommé peut différer du paramètre failover correspondant spécifié dans la souscription. Assurez-vous toujours que la propr

iété failover de l'emplacement correspond au paramètre correspondant de la souscription et vice versa. Sinon, l'emplacement sur le diffuseur peut se comporter différemment de ce que indiquent ces options de souscription : par exemple, l'emplacemen
t sur le diffuseur pourrait être synchronisé vers les serveurs de secours même si l'option failover de la souscription est désactivée, ou pourrait être désactivé pour la synchronisation même si l'option failover de la souscription est activée.

Les paramètres suivants contrôlent le comportement de réplication de la souscription après sa création

:

binary

(booléen)
Indique si la souscription demandera au diffuseur d'envoyer les données au format binaire (par opposition au texte). La valeur par défaut est false. Toute copie de synchronisation initiale de table (voir copy_data) utilise également le même format. Le format binaire peut être plus rapide que le format texte, mais il est moins portable entre les architectures de machines et les versions de PostgreSQL. Le format binaire est très spécifique aux types de données ; par exemple, il ne permettra pas de copier depuis une colonne smallint vers une colonne integer, même si cela fonctionnerait très bien en format texte. Même lorsque cette option est activée, seuls les types de données disposant de fonctions d'envoi et de réception binaires seront transférés en binaire. Notez que la synchronisation initiale nécessite que tous les types de données aient des fonctions d'envoi et de réception binaires, sinon la synchronisation échouera (voir CREATE TYPE (CREATE_TYPE(7)) pour plus d'informations sur les fonctions d'envoi/réception).

Lors d'une réplication entre versions, il est possible que le diffuseur ait une fonction d'envoi binaire pour un type de données donné, mais que l'abonné manque d'une fonction de réception binaire pour ce type. Dans un tel cas, le transfert de données échouera et l'option binary ne pourra pas être

utilisée.

Si le diffuseur est une version de PostgreSQL antérieur

e à 16, alors toute synchronisation initiale de tab
le utilisera le format texte même si binary = true.

copy_data

(booléen)
Indique s'il faut copier les données préexistantes dans les publications auxquelles on s'abonne lorsque la réplication démarre. La valeur par défaut est true.

Si les publications contiennent des clauses WHERE, cela affectera les données copiées. Voir les Notes pour plus de

détails.

Voir les Notes pour plus de détails su

r la façon dont copy_data = true pe

streaming

(énumération)
Indique s'il faut activer le streaming des transactions en cours pour cette souscription. La valeur par défaut est parallel, ce qui signifie que les changements entrants sont directement appliqués via l'un des travailleurs d'application parallèles, si disponibles. Si aucun travailleur d'application parallèle n'est disponible pour gérer les transactions en streaming, les changements sont écrits dans des fichiers temporaires et appliqués après le commit de la transaction. Notez que si une erreur se produit dans un travailleur d'application parallèle, le LSN de fin de la transaction distante peut ne pas être signalé dans le journal du serveur.

Attention
Il existe un risque d'interblocage lorsque les schémas du diffuseur et de l'abonné diffèrent, bien que de tels cas soient rares. Le travailleur d'application est équipé pour réessayer automatiquement ces transactions.
Si défini à on, les changements entrants sont écrits dans des fichiers temporaires puis appliqués uniquement après le commit de la transaction sur le diffuseur et sa réception par l'abonné.

Si défini à off, toutes les transactions son

synchronous_commit

(énumération)
La valeur de ce paramètre remplace le paramètre synchronous_commit au sein des processus de travail d'application de cette souscription. La valeur par défaut est off.

Il est sûr d'utiliser off pour la réplication logique : si l'abonné perd des transactions en raison d'une synchronisation manquante, les données seront renvoyées depuis le

diffuseur.

Un réglage différent peut être approprié lors d'une réplication logique synchrone. Les travailleurs de réplication logique signalent les positions d'écriture et de vidage au diffuseur, et lors de l'utilisation de la réplication synchrone, le diffuseur attendra le vidage effectif. Cela signifie que définir synchronous_commit à off pour l'abonné lorsque la souscription est utilisée pour la réplication synchrone pourrait augmenter la latence pour COMMIT sur le diffuseur. Dans ce scénario, il peut être av

antageux de définir synchr
onous_commit à local ou plus.

two_phase

(booléen)
Indique si l'engagement en deux phases (two-phase commit) est activé pour cette souscription. La valeur par défaut est false.

Lorsque l'engagement en deux phases est activé, les transactions préparées sont envoyées à l'abonné au moment du PREPARE TRANSACTION, et sont traitées comme des transactions en deux phases sur l'abonné également. Sinon, les transactions préparées ne sont envoyées à l'abonné qu'une fois committées, puis traitées immédiatement par

l'abonné.

L'implémentation de l'engagement en deux phases nécessite que la réplication ait terminé avec succès la phase de synchronisation initiale des tables. Ainsi, même lorsque two_phase est activé pour une souscriptionption, l'état interne en deux phases reste temporairement « en attente

» jusqu'à la fin de la phase d'initialisation. Voir la colonne subtwop
hasestate de pg_subscription pour connaître l'état réel en deux phases.

disable_on_error

(boolean)
Indique si l'abonnement doit être automatiquement désactivé si des erreurs sont détectées par les processus d'abonnement lors de la réplication des données depuis le publieur. La valeur par défaut est
false.

password_required

(boolean)
Si défini à true, les connexions au publieur effectuées à la suite de cet abonnement doivent utiliser une authentification par mot de passe et le mot de passe doit être spécifié dans la chaîne de connexion. Ce paramètre est ignoré lorsque l'abonnement appartient à un superutilisateur. La valeur par défaut est true. Seuls les superutilisateurs peuvent définir cette valeur à
false.

run_as_owner

(boolean)
Si true, toutes les actions de réplication sont effectuées en tant que propriétaire de l'abonnement. Si false, les processus de réplication effectueront les actions sur chaque table en tant que propriétaire de cette table. Cette dernière configuration est généralement beaucoup plus sécurisée ; pour plus de détails, voir la section 29.11. La valeur par défaut est
false.

origin

(string)
Indique si l'abonnement demandera au publieur de n'envoyer que les modifications qui n'ont pas d'origine ou d'envoyer les modifications quelle que soit leur origine. Définir origin à none signifie que l'abonnement demandera au publieur de n'envoyer que les modifications qui n'ont pas d'origine. Définir origin à any signifie que le publieur envoie les modifications quelle que soit leur origine. La valeur par défaut est any.

NOTE

S

Voir la section 29.11 pour plus de détails sur la configuration du contrôle d'accès entre l'abonnement et l'instance de

publication.

Lors de la création d'un emplacement de réplication (comportement par défaut), CREATE SUBSCRIPTION ne peut pas être exécuté à l'intérieur d'un bloc de

transaction.

La création d'un abonnement qui se connecte au même cluster de bases de données (par exemple, pour répliquer entre des bases de données du même cluster ou pour répliquer au sein de la même base de données) ne réussira que si l'emplacement de réplication n'est pas créé dans le cadre de la même commande. Sinon, l'appel CREATE SUBSCRIPTION restera bloqué. Pour que cela fonctionne, créez l'emplacement de réplication séparément (en utilisant la fonction pg_create_logical_replication_slot avec le nom de plugin pgoutput) et créez l'abonnement en utilisant le paramètre create_slot = false. Voir la section 29.2.3 pour des exemples. Ceci est une restriction d'implémentation qui pourrait être levée dans une version

future.

Si une table de la publication comporte une clause WHERE, les lignes pour lesquelles l' expression est évaluée à false ou NULL ne seront pas publiées. Si l'abonnement a plusieurs publications dans lesquelles la même table a été publiée avec des clauses WHERE différentes, une ligne sera publiée si l'une des expressions (se référant à cette opération de publication) est satisfaite. Dans le cas de clauses WHERE différentes, si l'une des publications n'a pas de clause WHERE (se référant à cette opération de publication) ou si la publication est déclarée comme FOR ALL TABLES ou FOR TABLES IN SCHEMA, les lignes sont toujours publiées quelle que soit la définition des autres expressions. Si l'abonné est une version de PostgreSQL antérieure à 15, tout filtrage de lignes est ignoré pendant la phase de synchronisation initiale des données. Dans ce cas, l'utilisateur peut envisager de supprimer toute donnée initialement copiée qui serait incompatible avec le filtrage ultérieur. Parce que la synchronisation initiale des données ne tient pas compte du paramètre publish de la publication lors de la copie des données de table existantes, certaines lignes peuvent être copiées qui ne seraient pas répliquées en utilisant DML. Voir la section 29.2.2 pour des

exemples.

Les abonnements ayant plusieurs publications dans lesquelles la même table a été publiée avec des listes de colonnes différentes ne sont pas pris en

charge.

Nous permettons de spécifier des publications inexistantes afin que les utilisateurs puissent les ajouter ultérieurement. Cela signifie que pg_subscription peut contenir des publications

inexistantes.

Lors de l'utilisation d'une combinaison de paramètres d'abonnement de copy_data = true et origin = NONE, les données de table de la synchronisation initiale sont copiées directement depuis le publieur, ce qui signifie que la connaissance de la véritable origine de ces données n'est pas possible. Si le publieur a également des abonnements, les données de table copiées peuvent provenir de plus loin en amont. Ce scénario est détecté et un AVERTISSEMENT est journalisé pour l'utilisateur, mais l'avertissement n'est qu'une indication d'un problème potentiel ; il appartient à l'utilisateur de faire les vérifications nécessaires pour s'assurer que les origines des données copiées sont réellement celles souhaitées ou

non.

Pour trouver quelles tables pourraient potentiellement inclure des origines non locales (en raison d'autres abonnements créés sur le publieur), essayez cette requête SQL

: 
# substituez <pub-names> ci-dessous par le(s) nom(s) de vos publications à interroger
SELECT DISTINCT PT.schemaname, PT.tablename
FROM
pg_publication_tables PT JOIN pg_class C ON (C.relname = PT.tablename) JOIN pg_namespace N ON (N.nspname = PT.schemaname),
pg_subscription_rel PS WHERE C.relnamespace = N.oid AND (PS.srrelid = C.oid OR C.oid IN (SELECT relid FROM pg_partitio
n_ancestors(PS.srrelid) UNION SELECT relid FROM pg_partition_tree(PS.srrelid))) AND PT.pubname IN (<pub-names>);
