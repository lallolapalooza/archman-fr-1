DESCRIPTIO

N

Cryptsetup est un utilitaire pour configurer et gérer le chiffrement de disque complet sur les périphériques de stockage. Il peut chiffrer des périphériques de bloc (tels que des disques durs ou des partitions) et des conteneurs (images de disque stockées en tant que fichiers)

.

Lorsque vous déverrouillez un volume chiffré, cryptsetup crée un nouveau mappage de périphérique que les applications peuvent accéder comme n'importe quel périphérique de stockage normal. Le travail réel de chiffrement et de déchiffrement est effectué de manière transparente par le pilote dm-crypt du device-mapper du

noyau.

Cryptsetup fonctionne avec deux types de volumes principaux : les volumes chiffrés simples (plain) et les volumes LUKS (Linux Unified Key Setup). Les volumes simples fournissent un chiffrement de base, tandis que les volumes LUKS incluent un en-tête de métadonnées qui permet des fonctionnalités avancées comme plusieurs emplacements de clés (keyslots) et la gestion des clés. De plus, LUKS peut être utilisé pour gérer le chiffrement matériel sur les disques de stockage compatibles

OPAL.

Cryptsetup fournit également une prise en charge limitée des volumes créés par d'autres systèmes de chiffrement, y compris loop-AES, TrueCrypt, VeraCrypt, BitLocker et FileVault2

.

Pour plus d'informations sur une action cryptsetup spécifique, voir cryptsetup-<action>(8), où <action> est le nom de l'action

cryptsetup.

Les périphériques cryptsetup peuvent être activés au démarrage via crypttab(5), qui fait partie de systemd(1) ou d'autres scripts

d'initiali
sation système.

MODE SIMPLE

(PLAIN)

Le chiffrement simple dm-crypt chiffre le périphérique secteur par secteur avec un seul hachage non salé de la phrase de passe. Aucune vérification n'est effectuée et aucune métadonnée n'est utilisée. Il n'y a pas d'opération de formatage. Lorsque le périphérique brut est mappé (ouvert), les opérations habituelles sur le périphérique peuvent être utilisées sur le périphérique mappé, y compris la création de système de fichiers. Les périphériques mappés résident généralement dans /dev/mapper/<nom>

.

EXTENSION

LUKS

LUKS, le Linux Unified Key Setup, est un standard pour le chiffrement de disque. Il ajoute un en-tête standardisé au début du périphérique, une zone d'emplacements de clés directement derrière l'en-tête et la zone de données principales derrière celle-ci. L'ensemble complet est appelé un « conteneur LUKS ». Le périphérique sur lequel réside un conteneur LUKS est appelé un « périphérique LUKS ». Pour la plupart des usages, les deux termes peuvent être utilisés de manière interchangeable

.

LUKS peut gérer plusieurs phrases de passe qui peuvent être révoquées ou modifiées individuellement. Chaque phrase de passe utilise un emplacement de clé individuel contenant une clé de volume pour le chiffrement des données. Les emplacements de clés peuvent être effacés de manière sécurisée du support persistant grâce à l'utilisation de bandes anti-forensiques. Les phrases de passe sont protégées contre les attaques par force brute par la fonction de dérivation de clé basée sur le mot de passe (PBKDF). Une phrase de passe stockée dans un fichier est appelée un fichier de clé. La seule différence entre une phrase de passe et un fichier de clé est qu'un fichier de clé peut contenir des données binaires. Les deux sont traités de la même

manière.

La version 1 de LUKS (ou LUKS1) est le format de métadonnées d'origine, tandis que LUKS2 est une nouvelle version qui permet des extensions supplémentaires comme différents algorithmes PBKDF ou le chiffrement authentifié. Vous pouvez formater le périphérique avec une version LUKS spécifique avec --type luks1 ou --type luks2 dans la commande luksFormat. Normalement, vous n'avez pas besoin de spécifier de version car elle est reconnue automatiquement. Le format par défaut est

LUKS2.

Le paramètre <périphérique> peut également être spécifié par un UUID LUKS au format UUID=<uuid>

.

L'en-tête LUKS peut être détaché des données (stocké séparément). Pour spécifier un en-tête détaché, le paramètre --header peut être utilisé dans toutes les commandes LUKS et a toujours la priorité sur le paramètre positionnel <périphéri

que>.

EXTENSION TCRYPT (COMPATIBLE AVEC TRUECRYPT ET

VERACRYPT)

Cryptsetup prend en charge le mappage de partitions chiffrées TrueCrypt, tcplay ou VeraCrypt en utilisant une API native du noyau Linux. Le formatage des en-têtes et la modification des en-têtes TCRYPT ne sont pas pris en charge ; cryptsetup ne modifie jamais l'en-tête TCRYPT sur le

périphérique.

L'extension TCRYPT nécessite que l'API crypto noyau/espace utilisateur soit disponible. Si vous configurez le noyau vous-même, activez « User-space interface for symmetric key cipher algorithms » dans la section « Cryptographic API » (option .config CRYPTO_USER_API_SKCIPHER)

.

Comme l'en-tête TCRYPT est chiffré, vous devez toujours fournir une phrase de passe valide et des fichiers de

clé.

Cryptsetup devrait reconnaître toutes les variantes d'en-tête, à l'exception des chaînes de chiffrement héritées utilisant le mode de chiffrement LRW avec un bloc de chiffrement de 64 bits (à savoir, Blowfish en mode LRW n'est pas reconnu ; c'est une limitation de l'API crypto du noyau)

.

VeraCrypt est une extension de TrueCrypt avec un nombre d'itérations augmenté, de sorte que le déverrouillage peut prendre beaucoup de

temps.

Pour ouvrir un périphérique VeraCrypt avec une valeur Personal Iteration Multiplier (PIM) personnalisée, utilisez soit l'option --veracrypt-pim PIM pour spécifier directement le PIM en ligne de commande, soit --veracrypt-query-pim pour être invité à saisir le

PIM.

La valeur PIM affecte le nombre d'itérations appliquées lors de la dérivation de clé. Veuillez consulter PIM https://veracrypt.io/en/Personal%20Iterations%20Multiplier%20(PIM).html pour des informations plus

détaillées.

Si vous devez désactiver la prise en charge des périphériques VeraCrypt, utilisez l'option --disable-veracrypt

.

L'activation avec tcryptOpen n'est prise en charge que pour les chaînes de chiffrement utilisant les modes de chiffrement LRW ou

XTS.

La commande tcryptDump devrait fonctionner pour tous les périphériques TCRYPT reconnus et ne nécessite pas les privilèges de superutilisateur

.

Pour mapper le périphérique système (le périphérique avec le chargeur de démarrage où se trouve l'intégralité du système chiffré), utilisez l'option --tcrypt-system. Veuillez lire les informations spécifiques dans la section de l'option --tcrypt-system de cryptsetup-tcryptOpen(8), car le mappage d'un périphérique chiffré système est

délicat.

Pour utiliser un en-tête caché (et mapper le périphérique caché, s'il est disponible), utilisez l'option --tcrypt-hidden

.

Pour utiliser explicitement l'en-tête de sauvegarde (secondaire), utilisez l'option --tcrypt-backup

.

Il n'y a aucune protection pour un volume caché si le volume externe est monté. La raison est que s'il y avait une protection, elle nécessiterait certaines métadonnées décrivant ce qu'il faut protéger dans le volume externe, et le volume caché deviendrait

détectable.

EXTENSION BITLK (COMPATIBLE AVEC BITLOCKER DE

WINDOWS)

Cryptsetup prend en charge le mappage de partitions chiffrées BitLocker et BitLocker to Go en utilisant une API native du noyau Linux. Le formatage des en-têtes et la modification des en-têtes BITLK ne sont pas prises en charge ; cryptsetup ne modifie jamais l'en-tête BITLK sur le

périphérique.

L'extension BITLK nécessite que l'API crypto noyau/espace utilisateur soit disponible (pour plus de détails, voir la section TCRYPT)

.

Cryptsetup devrait reconnaître toutes les variantes d'en-tête BITLK, à l'exception de l'en-tête hérité utilisé dans les systèmes Windows Vista et des périphériques BitLocker partiellement déchiffrés. L'activation des périphériques hérités chiffrés en mode CBC nécessite au moins une version du noyau Linux 5.3, et pour les périphériques utilisant l'Elephant diffuser, le noyau 5.

6.

La commande bitlkDump devrait fonctionner pour tous les périphériques BITLK reconnus et ne nécessite pas les privilèges de superutilisateur

.

Pour le déverrouillage avec open, un mot de passe, une phrase de passe de récupération ou une clé de démarrage doivent être

fournis.

De plus, le déverrouillage à l'aide de la clé du volume est pris en charge. Vous devez fournir la clé de chiffrement du volume complet (FVEK) de BitLocker à l'aide de l'option --volume-key-file. La clé doit être déchiffrée et sans l'en-tête (seulement 128/256/512 bits de données de clé selon le chiffrement et le mode utilisés)

.

Les autres méthodes de déverrouillage (TPM, SmartCard) ne sont pas prises en

charge.

EXTENSION FVAULT2 (COMPATIBLE AVEC FILEVAULT2 D'APPLE

MACOS)

Cryptsetup prend en charge le mappage de FileVault2 (chiffrement complet du disque FileVault2) d'Apple pour le système d'exploitation macOS système utilisant une API native du noyau

Linux.

Cryptsetup ne prend en charge que FileVault2 basé sur Core Storage et le système de fichiers HFS+ (introduit dans Mac OS X 10.7 Lion). Il ne prend PAS en charge la nouvelle version de FileVault basée sur le système de fichiers APFS utilisé dans les versions récentes de

macOS.

La mise en forme de l'en-tête et les modifications de l'en-tête FVAULT2 ne sont pas prises en charge ; cryptsetup ne modifie jamais l'en-tête FVAULT2 sur le

périphérique.

L'extension FVAULT2 nécessite la disponibilité de l'API crypto espace utilisateur/noyau (pour plus de détails, voir la section TCRYPT) et un pilote de noyau pour le système de fichiers HFS+ (hfsplus)

.

Cryptsetup devrait reconnaître la configuration de base pour les périphériques

portables.

La commande fvault2Dump devrait fonctionner pour tous les périphériques FVAULT2 reconnus et ne nécessite pas de privilèges de superutilisateur

.

Pour déverrouiller avec la commande open, un mot de passe doit être fourni. Les autres méthodes de déverrouillage ne sont pas prises en

charge.

SED (SELF ENCRYPTING DRIVE) OPAL

EXTENSION

Cryptsetup prend en charge l'utilisation du chiffrement matériel natif sur les périphériques qui fournissent une interface OPAL, à la fois imbriquée avec dm-crypt et autonome. Les phrases de passe, les jetons et les métadonnées sont stockés à l'aide du format d'en-tête LUKS2 et sont donc compatibles avec tout logiciel ou système utilisant LUKS2 (par ex., les jetons)

.

La prise en charge d'OPAL nécessite au moins le noyau v6.4. Le redimensionnement des périphériques n'est pas pris en

charge.

L'option --hw-opal peut être spécifiée pour OPAL + dm-crypt, et --hw-opal-only peut être spécifiée pour utiliser uniquement OPAL, sans couche

dm-crypt.

L'ouverture, la fermeture et l'enregistrement des jetons fonctionnent de la même manière qu'avec LUKS2 et dm-crypt. Les nouveaux paramètres ne sont nécessaires que lors du formatage ; les métadonnées LUKS2 garantiront que la bonne configuration est effectuée lors de l'ouverture ou de la

fermeture.

Si aucune étiquette de sous-système n'est spécifiée, elle sera automatiquement définie sur HW-OPAL afin qu'il soit immédiatement apparent qu'un périphérique utilise

OPAL.

FORMA

T

luksFormat --type luks2 --hw-opal <périphérique> [<fichier de clé>

Spécifiez en plus --hw-opal-only au lieu de --hw-opal pour éviter la couche dm-crypt. En plus de la phrase de passe habituel

le, un mot de passe administrateur devra être spécifié lors du formatage de la première partition du périphérique, et devra
être fourni à nouveau lors du formatage de toute autre partition jusqu'à ce qu'une réinitialisation d'usine soit effectuée.

MODE PLAIN OU LUKS

?

À moins que vous ne compreniez bien les fondements cryptographiques, utilisez LUKS. En mode plain, il

existe un certain nombre d'erreurs utilisateur possibles qui diminuent massivement la sécurité. Bien
que LUKS ne puisse pas toutes les corriger, il peut en atténuer l'impact pour beaucoup d'entre elles.

AVERTISSEMEN

TS

De nombreuses informations utiles sur les risques de l'utilisation du stockage chiffré, sur la gestion des problèmes et sur les aspects de sécurité peuvent être trouvées dans la FAQ de Cryptsetup. Lisez-la. Néanmoins, certains risques méritent d'être mentionnés

ici.

Sauvegarde : Les supports de stockage meurent. Le chiffrement n'a aucune influence là-dessus. La sauvegarde est obligatoire pour les données chiffrées également, si les données ont une quelconque valeur. Voir la FAQ de Cryptsetup pour des conseils sur la façon de sauvegarder un volume

chiffré.

Encodage de caractères : Si vous saisissez une phrase de passe avec des symboles spéciaux, la phrase de passe peut changer en fonction de l'encodage de caractères. Les paramètres du clavier peuvent également être modifiés, ce qui peut rendre la saisie à l'aveugle difficile ou impossible. Par exemple, le passage d'une variante ASCII 8 bits à UTF-8 peut entraîner un encodage binaire différent et donc une phrase de passe différente vue par cryptsetup, même si ce que vous voyez sur le terminal est exactement le même. Il est donc fortement recommandé de sélectionner les caractères de la phrase de passe uniquement parmi l'ASCII 7 bits, car l'encodage pour l'ASCII 7 bits reste le même pour toutes les variantes ASCII et

UTF-8.

En-tête LUKS : Si l'en-tête d'un volume LUKS est endommagé, toutes les données sont définitivement perdues à moins que vous n'ayez une sauvegarde de l'en-tête. Si un emplacement de clé est endommagé, il ne peut être restauré qu'à partir d'une sauvegarde d'en-tête ou si un autre emplacement de clé actif avec une phrase de passe connue n'est pas endommagé. Ce risque est le résultat d'un compromis entre sécurité et sûreté, car LUKS est conçu pour un effacement rapide et sécurisé en écrasant simplement la zone d'en-tête et d'emplacement de

clé.

Partitions précédemment utilisées : Si une partition a été utilisée précédemment, c'est une très bonne idée d'effacer les signatures de système de fichiers, les données, etc., avant de créer un conteneur LUKS ou dm-crypt plain. Pour une suppression rapide des signatures de système de fichiers, utilisez wipefs(8) avec l'option --all. Notez que cela ne supprime pas les données ; cela invalide uniquement les signatures de format connues. Pour un effacem

ent complet, écrasez toute la partition avant de créer un conteneur. Si vous
ne savez pas comment faire, la FAQ de cryptsetup décrit plusieurs options.

DESCRIPTION

The cryptsetup utility is a convenient device manager for setting up an encrypted partition or file using Kernel Crypto API. It supports all the features of the dm-crypt kernel module and provides a simple interface for creating, unlocking, and managing encrypted volumes.

The tool supports various encryption formats, but primarily works with the Linux Unified Key Setup (LUKS) format.

This man page covers details for LUKS specific features and configuration options, especially those that may differ from the generic device mapper target options.

LUKS FEATURES

Multiple passphrases and key slots

LUKS allows for multiple passphrases (up to 8 for LUKS1, 32 for LUKS2) to be stored in the header. Each passphrase decrypts a specific "keyslot" which contains the actual encryption key. This feature is useful for sharing access to an encrypted volume or for creating backup passphrases.

Key derivation and hashing

LUKS uses a Password-Based Key Derivation Function (PBKDF) to derive the master encryption key from the user's passphrase. This process involves hashing the passphrase multiple times with a salt to increase resistance against brute-force attacks and to mitigate the risk of using low-entropy passphrases.

LUKS1 uses PBKDF2, while LUKS2 supports both PBKDF2 and Argon2 (a more modern, memory-hard PBKDF). The PBKDF parameters (e.g., iteration count, memory usage) can be adjusted to balance security and performance.

Header backup and restore

The LUKS header contains all the metadata necessary to access the encrypted volume, including the key slots and PBKDF settings. cryptsetup provides options to back up and restore the LUKS header to prevent data loss in case of header corruption.

Keyfile support

In addition to passphrases, LUKS supports using key files for authentication. These key files can be stored on external media or within the system, providing an alternative or supplementary method for unlocking encrypted volumes.

Device encryption parameters

When creating a LUKS volume (luksFormat), cryptsetup allows you to specify various encryption parameters, including:

  • Cipher: The encryption algorithm (e.g., AES, Serpent).
  • Mode: The block cipher mode of operation (e.g., XTS, CBC). XTS is the recommended mode for disk encryption.
  • Key size: The length of the encryption key in bits.
  • Hash: The hashing algorithm used for passphrase derivation (e.g., SHA256, SHA512).

The available options depend on the underlying kernel crypto API support and the compiled cryptographic libraries.

Cipher and hash selection details

The choice of cipher and mode is crucial for security and performance. XTS mode is generally preferred for full disk encryption as it's designed specifically for this purpose and avoids some of the weaknesses of other modes like CBC when used with random access storage.

The hashing algorithm used in PBKDF (e.g., SHA256, SHA512) affects the security of passphrase protection. Stronger hashes offer better resistance to brute-force attacks.

Key management

LUKS provides robust key management capabilities. Multiple key slots allow for flexible access control and recovery scenarios. When adding or changing passphrases, cryptsetup uses PBKDF benchmarking to determine appropriate costs (iteration counts) based on the system's performance. These costs can be manually overridden if necessary, but caution is advised.

The --iter-time option allows users to specify the desired time (in seconds) for passphrase processing. A higher value increases security for low-entropy passphrases but also increases the time taken to open the volume. For high-entropy passphrases, excessively high iteration counts offer diminishing security returns.

From stdin: LUKS will read passphrases from stdin up to the first newline character or the compiled-in maximum key file length. If --keyfile-size is given, it is ignored.

From key file: The complete keyfile is read up to the compiled-in maximum size. Newline characters do not terminate the input. The --keyfile-size option can be used to limit what is read.

LUKS uses Password-Based Key Derivation Function (PBKDF) to protect against brute-force attacks and to give some protection to low-entropy passphrases (see cryptsetup FAQ). LUKS1 supports the PBKDF2 algorithm only, while LUKS2 also supports memory-hard Argon2. PBKDFs are configured with costs: how long the iteration should run (CPU cost or iteration count), how much memory is used (memory cost), and how many parallel processes are used (parallel cost). PBKDF2 supports only iteration count. Cryptsetup uses PBKDF benchmarking to calculate optimal costs based on the computer where the new passphrase is being initialized. If needed, these costs can also be overwritten. Note that there are some hardcoded limits, for details see MINIMAL AND MAXIMAL PBKDF COSTS section in --pbkdf option description.

Whenever a passphrase is added to a LUKS header (luksAddKey, luksFormat), the user may specify how much time the passphrase processing should consume. The time is used to determine the iteration count for PBKDF2, and higher times will offer better protection for low-entropy passphrases, but the open command will take longer to complete. For passphrases that have entropy higher than the used key length, higher iteration times will not increase security.

The default setting of one or two seconds is sufficient for most practical cases. The only exception is a low-entropy passphrase used on a device with a slow CPU, as this will result in a low iteration count. On a slow device, it may be advisable to increase the iteration time using the --iter-time option to obtain a higher iteration count. This does slow down all later luksOpen operations accordingly.

Incoherent behavior for invalid passphrases/keys

LUKS checks for a valid passphrase when a keyslot is decrypted.

The behavior of plain dm-crypt is different. It will always unlock the device with the passphrase given. If the given passphrase is wrong, the device mapped by plain dm-crypt will use the wrong encryption key, and the data will be unreadable.

Supported ciphers, modes, hashes and key sizes

The available combinations of ciphers, modes, hashes and key sizes depend on kernel support. See /proc/crypto for a list of available options. You might need to load additional kernel crypto modules to get more options.

Cryptsetup processes many operations outside of the kernel, so the configured cryptographic library must also support selected algorithms. Some algorithms may be missing as cryptsetup can be compiled with various cryptographic backends (libraries).

Notes on passphrases

Mathematics can’t be bribed. Make sure you keep your passphrases safe. There are a few nice tricks for constructing a fallback when suddenly, out of the blue, your brain refuses to cooperate. These fallbacks need LUKS, as it’s only possible with LUKS to have multiple passphrases. Still, if your attacker model does not prevent it, storing your passphrase in a sealed envelope somewhere may be a good idea as well.

Notes on Random Number Generators

Random Number Generators (RNGs) used in cryptsetup are always the kernel RNGs without any modifications or additions to the data stream produced.

There are two types of randomness that cryptsetup/LUKS needs. One type is used for salts, the AF splitter and for wiping deleted keyslots. The second type is used for the volume key.

With recent kernels (Linux kernel 5.6), you do not need to worry about selecting RNG (/dev/random or /dev/urandom). In a low-entropy situation (embedded system), initialization of the kernel RNG can take a very long time, but this happens before cryptsetup can even be started. Use cryptsetup --help to show the compiled-in default random number generator. See urandom(4) for more information.

Authenticated disk encryption (EXPERIMENTAL)

Normal disk encryption modes are length-preserving (the plaintext sector is the same size as a ciphertext sector) and can provide only confidentiality protection, not cryptographically sound data integrity protection.

Authenticated modes require additional space per-sector for the authentication tag and use Authenticated Encryption with Additional Data (AEAD) algorithms.

If you configure a LUKS2 device with data integrity protection, there will be an underlying dm-integrity device, which provides additional per-sector metadata space and data journal protection to ensure atomicity of data and metadata updates. Because there must be additional space for metadata and journal, the available space for the device will be smaller than for length-preserving modes.

The dm-crypt device then resides on top of such a dm-integrity device. All activation and deactivation of this device stack is performed by cryptsetup; there is no difference in using luksOpen for integrity-protected devices. If you want to format a LUKS2 device with data integrity protection, use --integrity option (see cryptsetup-luksFormat(8)).

Albeit Linux kernel 5.7 added TRIM support for standalone dm-integrity devices, cryptsetup(8) can’t offer support for discards (TRIM) in authenticated encryption mode, because the underlying dm-crypt kernel module does not support this functionality when dm-integrity is used as auth tag space allocator (see --allow-discards in cryptsetup-open(8)).

Some integrity modes require two independent keys (a key for encryption and authentication). Both these keys are stored in one LUKS keyslot.

Support for authenticated modes is experimental, and only some modes are available now. Note that very few authenticated encryption algorithms are suitable for disk encryption. You also cannot use CRC32 or other non-cryptographic checksums (other than the special integrity mode "none"). If, for some reason, you want to have integrity control without using authentication mode, then you should separately configure dm-integrity independently of LUKS2.

Notes on loopback device use

Cryptsetup is usually used directly on a block device (disk partition or LVM volume). However, if the device argument is a file, cryptsetup tries to allocate a loopback device and map it into this file. Of course, you can always map a file to a loop device manually. See the cryptsetup FAQ for an example.

When device mapping is active, you can see the loop backing file in the status command output. Also see losetup(8).

LUKS2 header locking

The LUKS2 on-disk metadata is updated in several steps, and to achieve a proper atomic update, there is a locking mechanism. For an image in a file, the code uses the flock(2) system call. For a block device, lock is performed over a special file stored in a locking directory (by default /run/cryptsetup). The locking directory should be created with the proper security context by the distribution during the boot-up phase. Only LUKS2 uses locks; other formats do not use this mechanism.

LUKS on-disk format specification

For LUKS on-disk metadata specification, see LUKS1 https://gitlab.com/cryptsetup/cryptsetup/wikis/Specification and LUKS2 https://gitlab.com/cryptsetup/LUKS2-docs.
