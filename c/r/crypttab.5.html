DESCRIPTIO

Le fichier /etc/crypttab décrit les périphériques de blocs chiffrés qui sont configurés lors du démarrage du

système.

Les lignes vides et les lignes commençant par le caractère "#" sont ignorées. Chacune des lignes restantes décrit un périphérique de bloc chiffré. Les champs sont délimités par des

espaces.

Chaque ligne est de la

forme 
nom-volume périphérique-chiffré fichier-clé optio
n
s

Les deux premiers champs sont obligatoires, les deux restants sont

facultatifs.

La configuration des périphériques de blocs chiffrés à l'aide de ce fichier prend en charge quatre modes de chiffrement : LUKS, TrueCrypt, BitLocker et plain (non chiffré). Voir cryptsetup(8) pour plus d'informations sur chaque mode. Quand aucun mode n'est spécifié dans le champ des options et que le périphérique de bloc contient une signature LUKS, il est ouvert comme un périphérique LUKS ; sinon, il est supposé être au format dm-crypt brut (mode plain)

.

Les quatre champs de /etc/crypttab sont définis comme suit

:
1.Le premier champ contient le nom du volume résultant contenant les données déchiffrées ; son périphérique de bloc est configuré sous
/dev/mapper/.
2.Le deuxième champ contient le chemin vers le périphérique de bloc ou le fichier sous-jacent, ou une spécification d'un périphérique de bloc via "UUID=" suivi de
l'UUID.
3.Le troisième champ spécifie un chemin absolu vers un fichier contenant la clé de chiffrement. En option, le chemin peut être suivi de ":" et d'une spécification de périphérique de style /etc/fstab (par exemple commençant par "LABEL=" ou similaire) ; auquel cas le chemin est pris relativement à la racine du système de fichiers du périphérique spécifié. Si le champ est absent ou vaut "none" ou "-", un fichier nommé d'après le volume à déverrouiller (c'est-à-dire la première colonne de la ligne), avec le suffixe .key, est automatiquement chargé depuis les répertoires /etc/cryptsetup-keys.d/ et /run/cryptsetup-keys.d/, s'ils existent. Sinon, le mot de passe doit être saisi manuellement lors du démarrage du système. Pour le chiffrement de la partition d'échange (swap), /dev/urandom peut être utilisé comme fichier clé, résultant en une clé aléatoire.

Si le chemin du fichier clé spécifié fait référence à un socket de flux AF_UNIX dans le système de fichiers, la clé est acquise en se connectant au socket et en la lisant depuis la connexion. Cela permet l'imp

lémentation d'un service pour fournir les informations de clé de manière dyna
mique, au moment où elles sont nécessaires. Pour les détails, voir ci-dessous.
4.Le quatrième champ, s'il est présent, est une
liste d'options délimitée par des virgules. Les o
ptions prises en charge sont listées ci-dessous.

ACQUISITION DE LA

CLÉ

Six mécanismes différents pour acquérir la clé de déchiffrement ou la phrase de passe déverrouillant le volume chiffré sont pris en charge. Plus précisément

:
1.Primordialement, l'utilisateur peut être interrogé de manière interactive lors de l'activation du volume (c'est-à-dire généralement au démarrage), en lui demandant de saisir les phrases de passe
nécessaires.
2.La clé (non chiffrée) peut être lue depuis un fichier sur le disque, éventuellement sur un support amovible. Le troisième champ de chaque ligne encode l'emplacement, pour les détails voir
ci-dessus.
3.La clé (non chiffrée) peut être demandée à un autre service, en spécifiant un socket de système de fichiers AF_UNIX à la place d'un fichier clé dans le troisième champ. Pour les détails, voir ci-dessus et
ci-dessous.
4.La clé peut être acquise via un jeton de sécurité matériel ou une carte à puce compatible PKCS#11. Dans ce cas, une clé enregistrée utilisée dans le processus de déverrouillage est stockée sur le disque/support amovible, acquise via AF_UNIX, ou stockée dans l'en-tête de métadonnées de jeton JSON LUKS2. Pour RSA, la clé enregistrée est une clé de volume chiffrée. La clé de volume chiffrée est ensuite déchiffrée par le jeton PKCS#11 avec une clé privée RSA stockée dessus, et utilisée pour déverrouiller le volume chiffré. Pour la cryptographie à courbe elliptique (EC), la clé enregistrée est la clé publique générée lors du processus d'inscription. La clé publique est ensuite utilisée pour dériver un secret partagé avec une clé privée stockée dans le jeton PKCS#11. Le secret partagé dérivé est ensuite utilisé pour déverrouiller le volume. Utilisez l'option pkcs11-uri= décrite ci-dessous pour utiliser ce
mécanisme.
5.De même, la clé peut être acquise via un jeton de sécurité matériel compatible FIDO2 (qui doit implémenter l'extension "hmac-secret"). Dans ce cas, une clé générée aléatoirement lors de l'inscription est stockée sur le disque/support amovible, acquise via AF_UNIX, ou stockée dans l'en-tête de métadonnées de jeton JSON LUKS2. La clé aléatoire est hachée via une fonction de hachage à clé (HMAC) sur le jeton FIDO2, en utilisant une clé secrète stockée sur le jeton qui ne le quitte jamais. La valeur de hachage résultante est ensuite utilisée comme clé pour déverrouiller le volume chiffré. Utilisez l'option fido2-device= décrite ci-dessous pour utiliser ce
mécanisme.
6.De même, la clé peut être acquise via une puce de sécurité TPM2. Dans ce cas, une clé générée aléatoirement (lors de l'inscription) — chiffrée par une clé asymétrique dérivée de la clé de graine de la puce TPM2 — est stockée sur le disque/support amovible, acquise via AF_UNIX, ou stockée dans l'en-tête de métadonnées de jeton JSON LUKS2. Utilisez l'option tpm2-device= décrite ci-dessous pour utiliser ce
mécanisme.

Pour les cinq derniers mécanismes, la source du matériau de clé utilisé pour déverrouiller le volume est principalement configurée dans le troisième champ de chaque ligne de /etc/crypttab, mais peut aussi être configurée dans /etc/cryptsetup-keys.d/ et /run/cryptsetup-keys.d/ (voir ci-dessus) ou dans l'en-tête de métadonnées de jeton JSON LUKS2 (dans le cas des trois derniers). Utilisez l'outil systemd-cryptenroll(1) pour inscrire les périphéri

ques PKCS#11, FIDO2 et TPM
2 dans les volumes LUKS2.

Marque ce périphérique cryptsetup comme nécessitant le réseau. Il sera démarré après que le réseau soit disponible, de manière similaire aux unités systemd.mount(5) marquées avec _netdev. nofai

l
Cet appareil ne sera pas une dépendance forte de cryptsetup.target. Il sera toujours tiré et démarré, mais le système n'attendra pas que l'appareil apparaisse et soit déverrouillé, et le démarrage n'échouera pas si cela échoue. Si un fichier de clé et/ou un en-tête sont spécifiés, les dépendances sur leurs répertoires respectifs ne seront pas non plus fatales, de sorte que le démontage de ces répertoires ne provoquera pas la désactivation de l'unité cryptset générée.

champ.

Ajouté dans la version 186.

password-echo=yes|no|masked

Contrôle si les mots de passe ou les PIN de jeton de sécurité sont affichés ou non lorsqu'ils sont lus depuis la console. Prend une valeur booléenne ou la chaîne spéciale « masked ». La valeur par défaut est password-echo=masked.

Si activé, les caractères tapés sont affichés littéralement. Si désactivé, les caractères tapés ne sont affichés sous aucune forme, l'utilisateur n'aura aucun retour d'information sur son entrée. Si défini sur « masked », un astérisque (« * ») est affiché pour chaque caractère tapé. Quel que soit le mode choisi, si l'utilisateur appuie sur la touche tabulation (« ⇥ ») à tout moment, ou sur la touche retour arrière (« ⌫ ») avant que d'autres données n'aient été entrées, l'affichage est désactivé.

Ajouté dans la version 249.

password-cache=yes|no|read-only

Contrôle si un cache doit être utilisé pour les mots de passe ou les PIN de jeton de sécurité. Prend une valeur booléenne ou la chaîne spéciale « read-only ». La valeur par défaut est « yes ».

Si défini sur « read-only », le keyring du noyau est vérifié pour un mot de passe/PIN avant d'en demander un interactivement. Si défini sur « yes », en plus de la vérification du keyring, tout mot de passe/PIN entré interactivement est mis en cache dans le keyring avec un délai d'expiration de 2,5 minutes avant d'être purgé.

Notez que cette option n'est pas autorisée pour les jetons de sécurité PKCS#11. La raison est que les jetons de sécurité PKCS#11 sont généralement configurés pour se verrouiller après avoir reçu un PIN invalide plusieurs fois, l'utilisation du cache pourrait donc verrouiller involontairement le jeton.

Ajouté dans la version 257.

pkcs11-uri=

Prend soit la valeur spéciale « auto », soit un URI PKCS#11 RFC7512[2] pointant vers une clé privée qui est utilisée pour déchiffrer la clé chiffrée spécifiée dans la troisième colonne de la ligne. Ceci est utile pour déverrouiller des volumes chiffrés via des jetons de sécurité compatibles PKCS#11 ou des cartes à puce. Voir ci-dessous pour un exemple de configuration de ce mécanisme pour déverrouiller un volume LUKS2 avec un jeton de sécurité YubiKey.

Si spécifié comme « auto », le volume doit être de type LUKS2 et doit contenir des métadonnées de jeton de sécurité PKCS#11 dans sa section de jeton LUKS2 JSON. En ce mode, l'URI et la clé chiffrée sont automatiquement lus à partir de l'en-tête de jeton LUKS2 JSON. Utilisez systemd-cryptenroll(1) comme outil simple pour enregistrer des jetons de sécurité PKCS#11 ou des cartes à puce d'une manière compatible avec « auto ». En ce mode, la troisième colonne de la ligne doit rester vide (c'est-à-dire spécifiée comme « - »).

L'URI spécifié peut faire référence directement à une clé privée stockée sur un jeton ou alternativement juste à un slot ou à un jeton, auquel cas une recherche d'une clé privée appropriée sera effectuée. Dans ce cas, si plusieurs objets appropriés sont trouvés, le jeton est refusé. Le fichier clé configuré dans la troisième colonne de la ligne est utilisé tel quel (c'est-à-dire sous forme binaire, non traité). La clé déchiffrée résultante (pour RSA) ou le secret partagé dérivé (pour ECC) est ensuite encodé en Base64 avant d'être utilisé pour déverrouiller le volume LUKS.

Utilisez systemd-cryptenroll --pkcs11-token-uri=list pour lister tous les jetons de sécurité PKCS#11 appropriés actuellement branchés, avec leurs URIs.

Notez que de nombreux jetons de sécurité plus récents qui peuvent être utilisés comme jetons de sécurité PKCS#11 implémentent également la norme FIDO2 plus récente et plus simple. Envisagez d'utiliser fido2-device= (décrit ci-dessous) pour l'enregistrer via FIDO2 à la place. Notez qu'un jeton de sécurité enregistré via PKCS#11 ne peut pas être utilisé pour déverrouiller le volume via FIDO2, à moins qu'il ne soit également enregistré via FIDO2, et vice versa.

Ajouté dans la version 245.

fido2-device=

Prend soit la valeur spéciale « auto », soit le chemin vers un nœud de périphérique « hidraw » (par exemple /dev/hidraw1) faisant référence à un jeton de sécurité FIDO2 qui implémente l'extension « hmac-secret » (la plupart des jetons de sécurité matériels actuels le font). Voir ci-dessous pour un exemple de configuration de ce mécanisme pour déverrouiller un volume chiffré avec un jeton de sécurité FIDO2.

Si spécifié comme « auto », le périphérique de jeton FIDO2 est automatiquement découvert lorsqu'il est branché.

Le déverrouillage de volume FIDO2 nécessite un identifiant client (CID) configuré via fido2-cid= (voir ci-dessous) et une clé pour passer à la fonctionnalité HMAC du jeton de sécurité (configurée dans la troisième colonne de la ligne) pour fonctionner. Si non configuré et que le volume est de type LUKS2, le CID et la clé sont lus à partir des métadonnées de jeton LUKS2 JSON à la place. Utilisez systemd-cryptenroll(1) comme outil simple pour enregistrer des jetons de sécurité FIDO2 pour les volumes LUKS2.

Utilisez systemd-cryptenroll --fido2-device=list pour lister tous les jetons de sécurité FIDO2 appropriés actuellement branchés, avec leurs nœuds de périphérique.

Cette option implémente le mécanisme suivant : la clé configurée est hachée via la fonction de hachage clé HMAC que le périphérique FIDO2 implémente, indexée par une clé secrète intégrée au périphérique. La valeur de hachage résultante est encodée en Base64 et utilisée pour déverrouiller le volume LUKS2. Comme il ne devrait pas être possible d'extraire le secret du jeton matériel, il ne devrait pas être possible de récupérer la clé hachée étant donné la clé configurée — sans posséder le jeton matériel.

Notez que de nombreux jetons de sécurité qui implémentent FIDO2 implémentent également PKCS#11, approprié pour déverrouiller des volumes via l'option pkcs11-uri= décrite ci-dessus. Généralement, la norme FIDO2 plus récente et plus simple est préférable.

Ajouté dans la version 257.

tpm2-device=

Prend soit la valeur spéciale « auto », soit le chemin vers un nœud de périphérique (par exemple /dev/tpmrm0) faisant référence à une puce de sécurité TPM2. Voir ci-dessous pour un exemple de configuration de ce mécanisme pour déverrouiller un volume chiffré avec une puce TPM2.

Utilisez tpm2-pcrs= (voir ci-dessous) pour configurer l'ensemble des PCR TPM2 pour lier le déverrouillage du volume. Utilisez systemd-cryptenroll(1) comme outil simple pour enregistrer les puces de sécurité TPM2 dans les volumes LUKS2.

Si spécifié comme « auto », le périphérique TPM2 est automatiquement découvert. Utilisez systemd-cryptenroll --tpm2-device=list pour lister tous les périphériques TPM2 appropriés actuellement disponibles, avec leurs nœuds de périphérique.

Cette option implémente le mécanisme suivant : lors de l'enregistrement d'un périphérique TPM2 via systemd-cryptenroll sur un volume LUKS2, une clé aléatoire déverrouillant le volume est générée sur l'hôte et chargée dans la puce TPM2 où elle est chiffrée avec une paire de clés « primaire » asymétrique dérivée de la clé « seed » interne du TPM2. Ni la clé seed ni la clé primaire ne sont autorisées à quitter la puce TPM2 — cependant, la clé maintenant chiffrée peut l'être. Elle est sauvegardée dans l'en-tête de jeton LUKS2 du volume. Lors du déverrouillage du volume chiffré, la paire de clés primaire est générée à nouveau sur la puce TPM2 (ce qui fonctionne tant que la clé seed de la puce est correctement maintenue par la puce TPM2), qui est ensuite utilisée pour déchiffrer (sur la puce TPM2) la clé chiffrée à partir de l'en-tête de jeton LUKS2 du volume enregistré là pendant l'enregistrement. La clé déchiffrée résultante est ensuite utilisée pour déverrouiller le volume. Lorsque la clé aléatoire est chiffrée, les valeurs actuelles des PCR sélectionnés (voir ci-dessous) sont incluses dans l'opération, de sorte qu'un état PCR différent entraîne des clés chiffrées différentes et que la clé déchiffrée ne peut être récupérée que si le même état PCR est reproduit.

Ajouté dans la version 248.

tpm2-pcrs=

Prend une liste d'index de PCR TPM2 (« Platform Configuration Register ») séparée par des « + » (par exemple « 0+7+15 ») pour lier le déverrouillage du volume TPM2. Cette option n'est utile que lorsque TPM2 enrollment metadata n'est pas déjà disponible dans l'en-tête de jeton JSON LUKS2, de la même manière que systemd-cryptenroll l'écrit. Si non utilisé (et si aucun métadonnée dans l'en-tête de jeton JSON LUKS2 ne le définit), la valeur par défaut est une liste contenant une seule entrée : PCR 7. Attribuez une chaîne vide pour encoder une politique qui lie la clé à aucun PCR, rendant la clé accessible aux programmes locaux quel que soit l'état actuel des PCR.

FICHIERS DE CLÉS

AF_UNIX

Si le chemin du fichier de clé (tel que spécifié dans la troisième colonne des entrées /etc/crypttab, voir ci-dessus) fait référence à un socket de flux AF_UNIX dans le système de fichiers, la clé est acquise en se connectant au socket et en lisant la clé depuis la connexion. La connexion est établie depuis un nom de socket AF_UNIX dans l'espace de noms abstrait, voir unix(7) pour plus de détails. Le nom de socket source est choisi selon le format suivant

: 
NUL ALÉATOIRE /cryptsetup/ VOLU
M
E

En d'autres termes : un octet NUL (comme requis pour les sockets d'espace de noms abstrait), suivi d'une chaîne aléatoire (composée uniquement de caractères alphanumériques), suivie de la chaîne littérale « /cryptsetup/ », suivie du nom du volume pour lequel acquérir la clé. Par exemple, pour le volume « myvol »

: 
\0d7067f78d9827418/cryptsetup/myv
o
l

Les services écoutant sur le socket de flux AF_UNIX peuvent interroger le nom du socket source avec getpeername(2), et l'utiliser pour déterminer quelle clé envoyer, permettant à un seul socket d'écoute de servir des clés pour plusieurs volumes. Si la logique PKCS#11 est utilisée (voir ci-dessus), le nom source du socket est choisi de manière similaire, sauf que la chaîne littérale « /cryptsetup-pkcs11/ » est utilisée. Et de même pour FIDO

2 (« /cryptsetup-fido2-salt/ ») et TPM2 (« /cryptsetup-tpm2/ »). Un composant de chemin différent est utilisé pour que les services fournissant le matériel de clé sachent
que la clé secrète n'a pas été demandée directement, mais plutôt une clé chiffrée qui sera déchiffrée via la logique PKCS#11/FIDO2/TPM2 pour acquérir la clé secrète finale.

Exemple 4. Exemple de déverrouillage d'un volume TPM2

La logique TPM2 permet d'utiliser n'importe quelle puce TPM2 prise en charge par le noyau Linux pour déverrouiller un volume chiffré. Voici un exemple de configuration d'une puce TPM2 à cet effet pour un volume LUKS2, en utilisant systemd-cryptenroll(1) :

# SPDX-License-Identifier: MIT-0
# Enregistrer la puce de sécurité TPM2 dans le volume LUKS2, et la lier uniquement au PCR 7
# Remplacez /dev/sdXn par la partition à utiliser (par exemple /dev/sda1).
sudo systemd-cryptenroll --tpm2-device=auto --tpm2-pcrs=7 /dev/sdXn
# Test : Exécutons systemd-cryptsetup pour tester si cela a fonctionné.
sudo systemd-cryptsetup attach mytest /dev/sdXn none tpm2-device=auto
# Si cela a fonctionné, ajoutons maintenant la même ligne de manière persistante dans /etc/crypttab,
# pour l'avenir. Nous ne voulons pas utiliser le nom (instable) /dev/sdX, alors trouvons
# un lien stable :
udevadm info -q symlink -r /dev/sdXn
# Ajoutons maintenant la ligne en utilisant le lien symbolique by-uuid à /etc/crypttab :
sudo bash -c 'echo "mytest /dev/disk/by-uuid/... none tpm2-device=auto" >>/etc/crypttab'
# Et vérifions maintenant que le déverrouillage automatique fonctionne :
sudo systemd-cryptsetup detach mytest
sudo systemctl daemon-reload
sudo systemctl start cryptsetup.target
systemctl is-active systemd-cryptsetup@mytest.service
# Une fois que nous avons le périphérique qui sera déverrouillé automatiquement, nous pouvons l'utiliser.
# Habituellement, nous créerions un système de fichiers et l'ajouterions à /etc/fstab :
sudo mkfs.ext4 /dev/mapper/mytest
# Ceci affiche un 'UUID du système de fichiers', que nous pouvons utiliser comme nom stable :
sudo bash -c 'echo "/dev/disk/by-uuid/... /var/mytest ext4 defaults,x-systemd.mkdir 0 2" >>/etc/fstab'
# Et vérifions maintenant que le montage fonctionne :
sudo systemctl daemon-reload
