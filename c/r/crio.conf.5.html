DESCRIPTIO

N

Le fichier de configuration de CRI-O spécifie toutes les options de configuration disponibles et les indicateurs de ligne de commande pour le daemon crio(8) OCI Kubernetes Container Runtime ⟨./crio.8.md⟩, mais dans un format TOML qui peut être plus facilement modifié et

versionné.

CRI-O prend en charge le rechargement partiel de la configuration pendant l'exécution, ce qui peut être fait en envoyant SIGHUP au processus en cours d'exécution. Les options actuellement prises en charge dans crio.conf sont explicitement marquées avec « This option supports live configuration reload »

.

Le fichier containers-registries.conf(5) peut également être rechargé en envoyant SIGHUP au processus

crio.

Le crio.conf par déf

aut est situé dans
/etc/crio/crio.conf.

FORMA

T

Le format TOML ⟨https://github.com/toml-lang/toml⟩ est utilisé comme encodage du fichier de configuration. Chaque option et sous-table listée ici est imbriquée sous une table globale « crio ». Aucune option nue n'est utilisée. Le format de TOML peut être simplifié ainsi

: 
[table]
option = valeur
[table.s
ous_table1] option = valeur [ta
ble.sous_table2] option = valeur

TABLE

CRIO

CRI-O lit ses valeurs de stockage par défaut à partir du fichier containers-storage.conf(5) situé dans /etc/containers/storage.conf. Modifiez cette configuration de stockage si vous souhaitez changer les valeurs par défaut du système. Si vous souhaitez modifier le stockage uniquement pour CRI-O, vous pouvez modifier les options de configuration du stockage

ici.

root="/var/lib/containers/storage" Chemin vers le « répertoire racine ». CRI-O y stocke toutes ses données, y compris les images de

conteneurs.

runroot="/run/containers/storage" Chemin vers le « répertoire d'exécution ». CRI-O y stocke tout son

état.

storage_driver="overlay" Pilote de stockage utilisé pour gérer le stockage des images et des conteneurs. Veuillez consulter containers-storage.conf(5) pour voir tous les pilotes de stockage

disponibles.

storage_option=[] Liste pour passer des options au pilote de stockage. Veuillez consulter containers-storage.conf(5) pour voir toutes les options de stockage

disponibles.

log_dir="/var/log/crio/pods" Le répertoire de journalisation par défaut où tous les journaux seront écrits, sauf indication contraire directe du kubelet. Le répertoire de journalisation spécifié doit être un répertoire

absolu.

version_file="/run/crio/version" Emplacement où CRI-O dépose le fichier de version temporaire. Il est utilisé pour vérifier si crio wipe doit effacer les conteneurs, ce qui devrait toujours se produire lors du redémarrage d'un

nœud

version_file_persist="" Emplacement où CRI-O dépose le fichier de version persistant. Il est utilisé pour vérifier si crio wipe doit effacer les images, ce qui ne devrait se produire que lorsque CRI-O a été mis à

niveau

imagestore="" Stocke les images nouvellement tirées dans le chemin spécifié, plutôt que le chemin fourni par

--root.

internal_wipe=true Cette option est actuellement OBSOLÈTE et sera supprimée à l'avenir. Indique si CRI-O doit effacer les conteneurs après un redémarrage et les images après une mise à niveau lorsque le serveur démarre. Si défini à false, il faut exécuter crio wipe pour effacer les conteneurs et les images dans ces

situations.

internal_repair=true InternalRepair indique si CRI-O doit vérifier si le stockage des conteneurs et des images a été corrompu après un redémarrage soudain. Si c'est le cas, CRI-O tente également de réparer le

stockage.

clean_shutdown_file="/var/lib/crio/clean.shutdown" Emplacement où CRI-O dépose le fichier d'arrêt propre. Il est utilisé pour vérifi

er si crio a eu le temps de synchroniser avant de s'arrêter. S'i
l est introuvable, crio wipe effacera le répertoire de stockage.

hooks_dir=["chemin", ...] Chaque *.json fichier dans le chemin configure un hook pour les conteneurs CRI-O. Pour plus de détails sur la syntaxe des fichiers JSON et la sémantique de l'injection de hooks, voir oci-hooks(5). CRI-O prend actuellement en charge les schémas de hooks 1.0.0 et 0.1.0, bien que le schéma 0.1.0 soit

Les chemins listés plus loin dans le tableau ont une priorité plus élevée (oci-hooks(5) discute de la priorité des répertoires)

Pour les conditions d'annotation, CRI-O utilise les annotations Kubernetes, qui sont un sous-ensemble des annotations passées à l'exécution OCI. Par exemple, io.kubernetes.cri-o.Volumes fait partie des annotations de configuration de l'exécution OCI, mais ne fait pas partie des annotations Kubernetes correspondantes pour les

hooks.

Pour les conditions de montage par liaison, seuls les montages explicitement demandés par la configuration Kubernetes sont pris en compte. Les montages par liaison que CRI-O insère par défaut (par ex. /dev/shm) ne sont pas pris en

compte.

.

default_mounts_file="" Chemin vers le fichier spécifiant les montages par défaut pour chaque conteneur. Le format de la configuration est /SRC:/DST, un montage par ligne. Notez que CRI-O lit ses montages par défaut depuis les deux fichiers suivants

: 
1) `/etc/containers/mounts.conf` (c'est-à-dire, default_mounts_file) : C'est le fichier de remplacement, où les utilisateurs peuvent soit ajouter leurs propres montages par défaut, soit remplacer les montages par défaut fournis avec le paquet.
2) `/usr/share/containers/mounts.conf` : C'est le fichier par défaut lu pour les montages. Si vous voulez que CRI-O lise depuis un fichier de montages différent et spécifique, vous pouvez modifier default_mounts_file. Notez que, si cela est fait, CRI-O n'ajoutera que les montages qu'il trouve dans ce
fichier.

place.

log_filter="" Filtre les messages de journal par l'expression régulière fournie. Cette option prend en charge le rechargement de la configuration en direct. Par exemple, 'request:.*' filtre toutes les requêtes

gRPC.

log_level="info" Modifie la verbosité des journaux en fonction du niveau auquel elle est définie. Les options sont fatal, panic, error, warn, info, debug et trace. Cette option prend en charge le rechargement de la configuration en

direct.

log_size_max=-1 Taille maximale autorisée pour le fichier de journal du conteneur. Les nombres négatifs indiquent qu'aucune limite de taille n'est imposée. Si elle est positive, elle doit être >= 8192 pour correspondre/dépasser le tampon de lecture de conmon. Le fichier est tronqué et rouvert afin que la limite ne soit jamais dépassée. Cette option est obsolète. L'option Kubelet --container-log-max-size devrait être utilisée à la

place.

log_to_journald=false Indique si la sortie du conteneur doit être journalisée dans journald en plus du fichier de journal

Kubernetes.

container_exits_dir="/run/crio/exits" Chemin vers le répertoire dans lequel les fichiers de sortie des conteneurs sont écrits par

conmon.

container_attach_socket_dir="/run/crio" Chemin vers le répertoire pour les sockets d'attachement des

conteneurs.

bind_mount_prefix="" Un préfixe à utiliser pour la source des montages par liaison. Cette option serait utile lorsque CRI-O est exécuté dans un conteneur et que le répertoire / de l'hôte est monté comme /host dans le conteneur. Ensuite, si CRI-O est exécuté avec l'option --bind-mount-prefix=/host, CRI-O ajouterait le répertoire /host à tous les montages par liaison qu'il transmet à CRI. Si Kubernetes demandait à ce que /var/lib/foobar soit monté par liaison dans le conteneur, alors CRI-O monterait par liaison /host/var/lib/foobar. Comme CRI-O lui-même est exécuté dans un conteneur avec / ou l'hôte monté sur /host, le conteneur finirait par avoir /var/lib/foobar de l'hôte monté dans le conteneur plutôt que /var/lib/foobar du conteneur

CRI-O.

read_only=false Si défini à true, tous les conteneurs s'exécuteront en mode lecture

seule.

uid_mappings="" Les mappages UID pour l'espace de noms d'utilisateurs de chaque conteneur. Une plage est spécifiée sous la forme containerUID:HostUID:Size. Les plages multiples doivent être séparées par une virgule. Cette option est obsolète et sera remplacée par la prise en charge native des espaces de noms d'utilisateurs Kubernetes à

l'avenir.

minimum_mappable_uid=-1 Le UID hôte le plus bas qui peut être spécifié dans les mappages fournis, soit comme partie d'un uid_mappings ou comme partie d'une requête reçue via CRI, pour un pod qui sera exécuté avec un UID autre que 0. Cette option est obsolète et sera remplacée par la prise en charge des espaces de noms d'utilisateurs Kubernetes (KEP-127) à

l'avenir.

gid_mappings="" Les mappages GID pour l'espace de noms d'utilisateurs de chaque conteneur. Une plage est spécifiée sous la forme containerGID:HostGID:Size. Les plages multiples doivent être séparées par une virgule. Cette option est obsolète et sera remplacée par la prise en charge des espaces de noms d'utilisateurs Kubernetes (KEP-127) à

l'avenir.

minimum_mappable_gid=-1 Le GID hôte le plus bas qui peut être spécifié dans les mappages fournis, soit comme partie d'un gid_mappings ou comme partie d'une requête reçue via CRI, pour un pod qui sera exécuté avec un UID autre que 0. Cette option est obsolète et sera remplacée par la prise en charge des espaces de noms d'utilisateurs Kubernetes (KEP-127) à

l'avenir.

ctr_stop_timeout=30 Le délai minimal en secondes à attendre avant d'émettre un délai d'attente concernant la terminaison appropriée du

conteneur.

drop_infra_ctr=true Détermine si nous supprimons le conteneur infra lorsqu'un pod n'a pas d'espace de noms PID privé et n'utilise pas un exécuteur de séparation noyau (comme kata). Nécessite manage_ns_lifecycle à

true.

infra_ctr_cpuset="" Détermine l'ensemble de CPU pour exécuter les conteneurs infra. Si non spécifié, CRI-O utilisera tous les CPU en ligne pour exécuter les conteneurs infra. Vous pouvez spécifier les CPU au format de liste de CPU Linux. Pour obtenir une meilleure isolation pour les pods garantis, définissez ce paramètre à la même valeur que reserved-cpus de

kubelet.

shared_cpuset="" Détermine l'ensemble de CPU qui est autorisé à être partagé entre les conteneurs garantis, indépendamment de, et en plus de, l'exclusivité de leurs CPU. Ce champ est facultatif et ne serait pas utilisé s'il n'est pas spécifié. Vous pouvez spécifier les CPU au format de liste de CPU

namespaces_dir="/run" Le répertoire où l'état des espaces de noms gérés est suivi. Utilisé uniquement lorsque manage_ns_lifecycle est

CRIO.RUNTIME.WORKLOADS

TABLE

La table "crio.runtime.workloads" définit une liste de workloads - une manière de personnaliser le comportement d'un pod et d'un conteneur. Un workload est choisi pour un pod selon que l' activation_annotation du workload est une annotation sur le

pod.

activation_annotation="" activation_annotation est l'annotation du pod qui active ces paramètres de

workload.

annotation_prefix="" annotation_prefix est la manière dont un pod peut remplacer une ressource spécifique pour un conteneur. L'annotation complète doit être de la forme $annotation_prefix.$resource/$ctr

name = $value.

allowed_annotations=[] allowed_annotations est une tranche d' annotations expérimentales que ce workload est autorisé à traiter. Les valeurs actuellement reconnues sont : "io.kubernetes.cri-o.userns-mode" pour configurer un espace de noms utilisateur pour le pod. "io.kubernetes.cri-o.cgroup2-mount-hierarchy-rw" pour monter les cgroups en écriture lorsque défini à "true". "io.kubernetes.cri-o.Devices" pour configurer les périphériques du pod. "io.kubernetes.cri-o.ShmSize" pour configurer la taille de /dev/shm. "io.kubernetes.cri-o.UnifiedCgroup.$CTR_NAME" pour configurer le bloc unifié cgroup v2 d'un conteneur. "io.containers.trace-syscall" pour tracer les appels système via le hook seccomp

BPF OCI. "io.kubernetes.cri-o.seccompNotifierAction" pour activer la fonctionnalité de notification seccomp. "io.kubernetes.cri-o.umask" pour définir l'umask du processus d'initialisation du conteneur. "io.kubernetes.cri.rdt-class" pour définir la classe RDT d'un conteneur "seccomp-profile.kubernetes.cri-o.io" pour définir le profil seccomp pour :
- un conteneur spécifique en utilisant : "seccomp-profile.kubernetes.cri-o.io/" - un pod entier en utilisant : "seccomp-profile.kubernetes.cri-o.io/POD" Notez que l'annotation fonctionne sur les conteneurs ainsi que sur les images. "io.kubernetes.cri-o.DisableFIPS" pour désactiver le mode FIPS pour un pod dans un cluster Kubernetes avec FIPS activé.

Utilisation de la fonctionnalité de notification seccomp

:

Cette fonctionnalité peut vous aider à déboguer les problèmes liés à seccomp, par exemple si les appels système bloqués (erreurs permission denied) ont un impact négatif sur le

workload.

Pour pouvoir utiliser cette fonctionnalité, configurez un exécution qui a l'annotation "io.kubernetes.cri-o.seccompNotifierAction" dans le tableau allowed_annotations

.

Elle nécessite également au moins runc 1.1.0 ou crun 0.19 qui prennent en charge la fonctionnalité de

notification.

Si tout est configuré, CRI-O modifiera les profils seccomp choisis pour les conteneurs si l'annotation "io.kubernetes.cri-o.seccompNotifierAction" est définie sur le sandbox du Pod. CRI-O sera alors notifié si un conteneur utilise un appel système bloqué et terminera alors le workload après un délai d'attente de 5 secondes si la valeur de "io.kubernetes.cri-o.seccompNotifierAction=stop"

.

Cela signifie également que plusieurs appels système peuvent être capturés pendant cette période, le délai d'attente étant réinitialisé une fois qu'un nouvel appel système a été

découvert.

Cela signifie également que le "restartPolicy" du Pod doit être défini à "Never", sinon le kubelet redémarrera le conteneur

immédiatement.

Veuillez noter que CRI-O ne peut pas être notifié si un

appel système est bloqué en fonction du defaultAction de sec
comp, ce qui est une limitation générale de l'exécution.

Si "enforcing", une extraction d'image échouera si un nom court est utilisé,
