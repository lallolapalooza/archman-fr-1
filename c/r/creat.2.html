O_DIRECT (depuis Linux 2.4.10)
Tenter de minimiser les effets du cache sur les entrées/sorties vers et depuis ce fichier. En général cela dégradera les performances, mais c'est utile dans des situations spéciales, comme lorsque les applications gèrent leur propre cache. Les entrées/sorties de fichier sont faites directement vers/depuis les tampons de l'espace utilisateur. L'indicateur O_DIRECT seul fait un effort pour transférer les données de manière synchrone, mais ne donne pas les garanties de l'indicateur O_SYNC selon lesquelles les données et les métadonnées nécessaires sont transférées. Pour garantir des entrées/sorties synchrones, O_SYNC doit être utilisé en plus de O_DIRECT. Voir les NOTES ci-dessous pour plus de détails.
Une interface sémantiquement similaire (mais obsolète) pour les périphériques blocs est décrite dans raw(8).
O_DIRECTORY
Si path n'est pas un répertoire, faire échouer open(). Cet indicateur a été ajouté dans Linux 2.1.126, pour éviter les problèmes de déni de service si opendir(3) est appelé sur un FIFO ou un périphérique bande.
O_DSYNC
Les opérations d'écriture sur le fichier se termineront selon les exigences d'intégrité des données des entrées/sorties synchrones data integrity completion.
Au moment où write(2) (et similaire) retourne, les données de sortie ont été transférées vers le matériel sous-jacent, avec toutes les métadonnées de fichier qui seraient nécessaires pour récupérer ces données (c'est-à-dire comme si chaque write(2) était suivi d'un appel à fdatasync(2)). Voir VERSIONS.
O_EXCL
S'assurer que cet appel crée le fichier : si cet indicateur est spécifié en conjonction avec O_CREAT, et que path existe déjà, alors open() échoue avec l'erreur EEXIST.
Lorsque ces deux indicateurs sont spécifiés, les liens symboliques ne sont pas suivis : si path est un lien symbolique, alors open() échoue peu importe où le lien symbolique pointe.
En général, le comportement de O_EXCL est indéfini s'il est utilisé sans O_CREAT. Il y a une exception : sur Linux 2.6 et ultérieur, O_EXCL peut être utilisé sans O_CREAT si path fait référence à un périphérique bloc. Si le périphérique bloc est utilisé par le système (par ex., monté), open() échoue avec l'erreur EBUSY.
Sur NFS, O_EXCL n'est pris en charge que lors de l'utilisation de NFSv3 ou ultérieur sur un noyau 2.6 ou ultérieur. Dans les environnements NFS où la prise en charge de O_EXCL n'est pas fournie, les programmes qui s'y reposent pour effectuer des tâches de verrouillage contiendront une condition de course. Les programmes portables qui souhaitent effectuer un verrouillage atomique de fichier à l'aide d'un fichier de verrouillage, et doivent éviter de dépendre de la prise en charge NFS pour O_EXCL, peuvent créer un fichier unique sur le même système de fichiers (par ex., en incorporant le nom d'hôte et le PID), et utiliser link(2) pour créer un lien vers le fichier de verrouillage. Si link(2) retourne 0, le verrouillage est réussi. Sinon, utiliser stat(2) sur le fichier unique pour vérifier si son nombre de liens est passé à 2, auquel cas le verrouillage est également réussi.
O_LARGEFILE
(LFS) Permettre l'ouverture de fichiers dont les tailles ne peuvent pas être représentées dans un off_t (mais peuvent être représentées dans un off64_t). La macro _LARGEFILE64_SOURCE doit être définie (avant d'inclure n'importe quels fichiers d'en-tête) afin d'obtenir cette définition. Définir la macro de test de fonctionnalité _FILE_OFFSET_BITS à 64 (plutôt que d'utiliser O_LARGEFILE) est la méthode préférée pour accéder aux fichiers volumineux sur les systèmes 32 bits (voir feature_test_macros(7)).
O_NOATIME (depuis Linux 2.6.8)
Ne pas mettre à jour l'heure du dernier accès au fichier (st_atime dans l'inode) lorsque le fichier est luavec read(2).
Cet indicateur ne peut être utilisé que si l'une des conditions suivantes est vraie :
•
L'UID effectif du processus correspond à l'UID propriétaire du fichier.
•
Le processus appelant possède la capacité CAP_FOWNER dans son espace de noms d'utilisateur et l'UID propriétaire du fichier a un mappage dans l'espace de noms.
Cet indicateur est destiné à être utilisé par les programmes d'indexation ou de sauvegarde, où son utilisation peut réduire considérablement la quantité d'activité disque. Cet indicateur peut ne pas être efficace sur tous les systèmes de fichiers. Un exemple est NFS, où le serveur maintient l'heure d'accès.
O_NOCTTY
Si path fait référence à un périphérique terminal—voir tty(4)—il ne deviendra pas le terminal de contrôle du processus même si le processus n'en a pas.
O_NOFOLLOW
Si le composant final (c'est-à-dire le nom de base) de path est un lien symbolique, alors l'ouverture échoue, avec l'erreur ELOOP. Les liens symboliques dans les composants précédents du chemin seront toujours suivis. (Notez que l'erreur ELOOP qui peut survenir dans ce cas est indistinguable du cas où une ouverture échoue parce qu'il y a trop de liens symboliques trouvés lors de la résolution des composants dans le préfixe de chemin du nom de chemin.)
Cet indicateur est une extension FreeBSD, qui a été ajoutée dans Linux 2.1.126, et a ensuite été standardisée dans POSIX.1-2008.
Voir aussi O_PATH ci-dessous.
O_NONBLOCK ou O_NDELAY
Lorsque c'est possible, le fichier est ouvert en mode non bloquant. Ni open() ni aucune opération d'entrée/sortie ultérieure sur le descripteur de fichier qui est retourné ne feront attendre le processus appelant.
Notez que le réglage de cet indicateur n'a aucun effet sur l'opération de poll(2), select(2), epoll(7), et similaire, puisque ces interfaces informent simplement l'appelant de savoir si un descripteur de fichier est « prêt », ce qui signifie qu'une opération d'entrée/sortie effectuée sur le descripteur de fichier avec l'indicateur O_NONBLOCK à zéro ne bloquerait pas.
Notez que cet indicateur n'a aucun effet pour les fichiers réguliers et les périphériques blocs ; c'est-à-dire que les opérations d'entrée/sortie bloqueront (brièvement) lorsque l'activité du périphérique est requise, que O_NONBLOCK soit défini ou non. Puisque la sémantique de O_NONBLOCK pourrait éventuellement être implémentée, les applications ne devraient pas dépendre du comportement bloquant lorsqu'elles spécifient cet indicateur pour les fichiers réguliers et les périphériques blocs.
Pour le traitement des FIFO (tubes nommés), voir aussi fifo(7). Pour une discussion de l'effet de O_NONBLOCK en conjonction avec les verrous de fichier obligatoires et les baux de fichier, voir fcntl(2).
O_PATH (depuis Linux 2.6.39)
Obtenir un descripteur de fichier qui peut être utilisé à deux fins : indiquer un emplacement dans l'arborescence du système de fichiers et effectuer des opérations qui agissent purement au niveau du descripteur de fichier. Le fichier lui-même n'est pas ouvert, et d'autres opérations de fichier (par ex., read(2), write(2), fchmod(2), fchown(2), fgetxattr(2), ioctl(2), mmap(2)) échouent avec l'erreur EBADF.
Les opérations suivantes peuvent être effectuées sur le descripteur de fichier résultant :
•
close(2).
•
fchdir(2), si le descripteur de fichier fait référence à un répertoire (depuis Linux 3.5).
•
fstat(2) (depuis Linux 3.6).
•
fstatfs(2) (depuis Linux 3.12).
•
Dupliquer le descripteur de fichier (dup(2), fcntl(2) F_DUPFD, etc.).
•
Obtenir et définir les indicateurs du descripteur de fichier (fcntl(2) F_GETFD et F_SETFD).
•
Récupérer les indicateurs d'état d'ouverture de fichier en utilisant l'opération fcntl(2) F_GETFL : les indicateurs retournés incluront le bit O_PATH.
•
Passer le descripteur de fichier comme argument dirfd de openat() et des autres appels système "*at()". Cela inclut linkat(2) avec AT_EMPTY_PATH (ou via procfs en utilisant AT_SYMLINK_FOLLOW) même si le fichier n'est pas un répertoire.
•
Passer le descripteur de fichier à un autre processus via un socket de domaine UNIX (voir SCM_RIGHTS dans unix(7)).
Lorsque O_PATH est spécifié dans flags, les bits de drapeau autres que O_CLOEXEC, O_DIRECTORY, et O_NOFOLLOW sont ignorés.
Ouvrir un fichier ou un répertoire avec le drapeau O_PATH ne nécessite aucune permission sur l'objet lui-même (mais nécessite la permission d'exécution sur les répertoires du préfixe du chemin). Selon l'opération suivante, une vérification des permissions de fichier appropriées peut être effectuée (par exemple, fchdir(2) nécessite la permission d'exécution sur le répertoire référencé par son argument descripteur de fichier). Par contraste, obtenir une référence à un objet de système de fichiers en l'ouvrant avec le drapeau O_RDONLY nécessite que l'appelant ait la permission de lecture sur l'objet, même lorsque l'opération suivante (par exemple, fchdir(2), fstat(2)) ne nécessite pas la permission de lecture sur l'objet.
Si path est un lien symbolique et que le drapeau O_NOFOLLOW est également spécifié, alors l'appel retourne un descripteur de fichier référencant le lien symbolique. Ce descripteur de fichier peut être utilisé comme l'argument dirfd dans les appels à fchownat(2), fstatat(2), linkat(2), et readlinkat(2) avec un chemin vide pour faire opérer les appels sur le lien symbolique.
Si path fait référence à un point de montage automatique qui n'a pas encore été déclenché, de sorte qu'aucun autre système de fichiers n'y est monté, alors l'appel retourne un descripteur de fichier référencant le répertoire de montage automatique sans déclencher un montage. fstatfs(2) peut ensuite être utilisé pour déterminer s'il s'agit, en fait, d'un point de montage automatique non déclenché (.f_type == AUTOFS_SUPER_MAGIC).
Une utilisation de O_PATH pour les fichiers réguliers est de fournir l'équivalent de la fonctionnalité O_EXEC de POSIX.1. Cela nous permet d'ouvrir un fichier pour lequel nous avons la permission d'exécution mais pas la permission de lecture, puis d'exécuter ce fichier, avec des étapes quelque chose comme ce qui suit :

char buf[PATH_MAX];
fd = open("some_prog", O_PATH);
snprintf(buf, PATH_MAX, "/proc/self/fd/%d", fd);
execl(buf, "some_prog", (char *) NULL);

Un descripteur de fichier O_PATH peut également être passé comme argument de fexecve(3).
O_SYNC
Les opécriture sur le fichier se compléteront selon les exigences de l'intégrité des données d'E/S synchronisées fichier (par contraste avec l'intégrité des données d'E/S synchronisées données fournie par O_DSYNC.)
Au moment où write(2) (ou similaire) retourne, les données de sortie et les métadonnées de fichier associées ont été transférées vers le matériel sous-jacent (c'est-à-dire, comme si chaque write(2) était suivi d'un appel à fsync(2)). Voir VERSIONS.
O_TMPFILE (depuis Linux 3.11)
Crée un fichier temporaire régulier non nommé. L'argument path spécifie un répertoire ; un inode non nommé sera créé dans le système de fichiers de ce répertoire. Tout ce qui est écrit dans le fichier résultant sera perdu lorsque le dernier descripteur de fichier est fermé, à moins que le fichier ne reçoive un nom.
O_TMPFILE doit être spécifié avec l'un de O_RDWR ou O_WRONLY et, optionnellement, O_EXCL. Si O_EXCL n'est pas spécifié, alors linkat(2) peut être utilisé pour lier le fichier temporaire dans le système de fichiers, le rendant permanent, en utilisant du code comme le suivant :

char path[PATH_MAX];
fd = open("/path/to/dir", O_TMPFILE | O_RDWR,
                        S_IRUSR | S_IWUSR);
/* File I/O on 'fd'...  */
linkat(fd, "", AT_FDCWD, "/path/for/file", AT_EMPTY_PATH);
/* If the caller doesn't have the CAP_DAC_READ_SEARCH
   capability (needed to use AT_EMPTY_PATH with linkat(2)),
   and there is a proc(5) filesystem mounted, then the
   linkat(2) call above can be replaced with:
snprintf(path, PATH_MAX,  "/proc/self/fd/%d", fd);
linkat(AT_FDCWD, path, AT_FDCWD, "/path/for/file",
                        AT_SYMLINK_FOLLOW);
*/

Dans ce cas, l'argument open() mode détermine le mode de permission du fichier, comme avec O_CREAT.
Spécifier O_EXCL en conjonction avec O_TMPFILE empêche un fichier temporaire d'être lié dans le système de fichiers de la manière ci-dessus. (Notez que la signification de O_EXCL dans ce cas est différente de la signification de O_EXCL autrement.)
Il y a deux principaux cas d'utilisation pour O_TMPFILE:
•
Fonctionnalité améliorée de tmpfile(3) : création sans course de fichiers temporaires qui (1) sont automatiquement supprimés à la fermeture ; (2) ne peuvent jamais être atteints via aucun chemin ; (3) ne sont pas sujets aux attaques par liens symboliques ; et (4) ne nécessitent pas que l'appelant conçoive des noms uniques.
•
Création d'un fichier qui est initialement invisible, qui est ensuite rempli de données et ajusté pour avoir des attributs de système de fichiers appropriés (fchown(2), fchmod(2), fsetxattr(2), etc.) avant d'être lié atomiquement dans le système de fichiers dans un état complètement formé (en utilisant linkat(2) comme décrit ci-dessus).
O_TMPFILE nécessite le support par le système de fichiers sous-jacent ; seuls un sous-ensemble des systèmes de fichiers Linux fournissent ce support. Dans l'implémentation initiale, le support était fourni dans les systèmes de fichiers ext2, ext3, ext4, UDF, Minix, et tmpfs. Le support pour d'autres systèmes de fichiers a été ajouté par la suite comme suit : XFS (Linux 3.15) ; Btrfs (Linux 3.16) ; F2FS (Linux 3.16) ; et ubifs (Linux 4.9)
O_TRUNC
Si le fichier existe déjà et est un fichier régulier et que le mode d'accès permet l'écriture (c'est-à-dire, est O_RDWR ou O_WRONLY) il sera tronqué à une longueur de 0. Si le fichier est un FIFO ou un fichier de terminal, le drapeau O_TRUNC est ignoré. Sinon, l'effet de O_TRUNC est indéfini.

creat()

Un appel à creat() est équivalent à appeler open() avec flags égal à O_CREAT|O_WRONLY|O_TRUNC.

openat()

L'appel système openat() opère exactement de la même manière que open(), sauf pour les différences décrites ici.

L'argument dirfd est utilisé en conjonction avec l'argument path comme suit :

•
Si le chemin donné dans path est absolu, alors dirfd est ignoré.
•
Si le chemin donné dans path est relatif et que dirfd est la valeur spéciale AT_FDCWD, alors path est interprété relativement au répertoire de travail courant du processus appelant (comme open()).
•
Si le chemin donné dans path est relatif, alors il est interprété relativement au répertoire référencé par le descripteur de fichier dirfd (plutôt que relativement au répertoire de travail courant du processus appelant, comme le fait open() pour un chemin relatif). Dans ce cas, dirfd doit être un répertoire qui a été ouvert pour la lecture (O_RDONLY) ou en utilisant le drapeau O_PATH .

Si le chemin donné dans path est relatif, et que dirfd n'est pas un descripteur de fichier valide, une erreur (EBADF) résulte. (Spécifier un numéro de descripteur de fichier invalide dans dirfd peut être utilisé comme un moyen pour s'assurer que path est absolu.)

openat2(2)

L'appel système openat2(2) est une extension de openat(), et fournit un ensemble supérieur des fonctionnalités de openat(). Il est documenté séparément, dans openat2(2).

VALEUR RETOURNÉE

En cas de succès, open(), openat(), et creat() retournent le nouveau descripteur de fichier (un entier non négatif). En cas d'erreur, -1 est retourné et errno est défini pour indiquer l'erreur.

Pour plus de détails, voir les descriptions de /proc/sys/fs/protected_fifos et /proc/sys/fs/protected_regular dans proc_sys_fs(5).

VERSIONS

L'effet (non défini) de O_RDONLY | O_TRUNC varie selon les implémentations. Sur de nombreux systèmes, le fichier est effectivement tronqué.

I/O synchronisé

L'option "synchronized I/O" de POSIX.1-2008 spécifie différentes variantes d'I/O synchronisé, et spécifie les indicateurs open() O_SYNC, O_DSYNC et O_RSYNC pour contrôler le comportement. Indépendamment du fait qu'une implémentation prenne en charge cette option, elle doit au moins prendre en charge l'utilisation de O_SYNC pour les fichiers réguliers.

Linux implémente O_SYNC et O_DSYNC, mais pas O_RSYNC. De manière quelque peu incorrecte, glibc définit O_RSYNC pour avoir la même valeur que O_SYNC. (O_RSYNC est défini dans le fichier d'en-tête Linux <asm/fcntl.h> sur HP PA-RISC, mais il n'est pas utilisé.)

O_SYNC fournit une complétion d'intégrité de fichier d'I/O synchronisé, ce qui signifie que les opérations d'écriture videront les données et toutes les mises à jour de métadonnées vers le matériel sous-jacent. O_DSYNC fournit une complétion d'intégrité de données d'I/O synchronisé, ce qui signifie que les opérations d'écriture videront les données vers le matériel sous-jacent, mais ne videront que les mises à jour de métadonnées nécessaires pour permettre à une opération de lecture ultérieure de se terminer avec succès. La complétion d'intégrité des données peut réduire le nombre d'opérations disque requises pour les applications qui n'ont pas besoin des garanties de complétion d'intégrité de fichier.

Pour comprendre la différence entre les deux types de complétion, considérez deux éléments de métadonnées de fichier : l'horodatage de la dernière modification du fichier (st_mtime) et la longueur du fichier. Toutes les opérations d'écriture mettront à jour l'horodatage de la dernière modification du fichier, mais seules les écritures qui ajoutent des données à la fin du fichier modifieront la longueur du fichier. L'horodatage de la dernière modification n'est pas nécessaire pour garantir qu'une lecture se termine avec succès, mais la longueur du fichier l'est. Ainsi, O_DSYNC ne garantirait que le vidage des mises à jour de la métadonnée de longueur de fichier (tandis que O_SYNC viderait également toujours la métadonnée d'horodatage de dernière modification).

Avant Linux 2.6.33, Linux n'implémentait que l'indicateur O_SYNC pour open(). Cependant, lorsque cet indicateur était spécifié, la plupart des systèmes de fichiers fournissaient en fait l'équivalent d'une complétion d'intégrité des données d'I/O synchronisé (c'est-à-dire que O_SYNC était en fait implémenté comme l'équivalent de O_DSYNC).

Depuis Linux 2.6.33, une prise en charge correcte de O_SYNC est fournie. Cependant, pour assurer la compatibilité binaire ascendante, O_DSYNC a été défini avec la même valeur que l'ancien O_SYNC, et O_SYNC a été défini comme une nouvelle valeur d'indicateur (à deux bits) qui inclut la valeur de l'indicateur O_DSYNC. Cela garantit que les applications compilées avec de nouveaux en-têtes obtiennent au moins les sémantiques O_DSYNC avant Linux 2.6.33.

NOTES

Sous Linux, l'indicateur O_NONBLOCK est parfois utilisé dans les cas où l'on souhaite ouvrir un fichier sans nécessairement avoir l'intention de le lire ou de l'écrire. Par exemple, cela peut être utilisé pour ouvrir un périphérique afin d'obtenir un descripteur de fichier à utiliser avec ioctl(2).

Notez que open() peut ouvrir des fichiers spéciaux de périphérique, mais creat() ne peut pas les créer ; utilisez plutôt mknod(2) .

Si le fichier est nouvellement créé, ses champs st_atime, st_ctime, st_mtime (respectivement, heure du dernier accès, heure du dernier changement de statut et heure de la dernière modification ; voir stat(2)) sont définis à l'heure actuelle, et il en va de même pour les champs st_ctime et st_mtime du répertoire parent. Sinon, si le fichier est modifié à cause de l'indicateur O_TRUNC , ses champs st_ctime et st_mtime sont définis à l'heure actuelle.

Les fichiers du répertoire /proc/pid/fd montrent les descripteurs de fichiers ouverts du processus dont le PID est pid. Les fichiers du répertoire /proc/pid/fdinfo montrent encore plus d'informations sur ces descripteurs de fichiers. Voir proc(5) pour plus de détails sur ces deux répertoires.

Le fichier d'en-tête Linux <asm/fcntl.h> ne définit pas O_ASYNC; le synonyme (dérivé de BSD) FASYNC est défini à la place.

Descriptions de fichiers ouverts

Le terme description de fichier ouvert est celui utilisé par POSIX pour désigner les entrées dans la table globale des fichiers ouverts. Dans d'autres contextes, cet objet est également appelé « objet de fichier ouvert », « poignée de fichier », « entrée de table de fichiers ouverts » ou—dans le jargon des développeurs du noyau—une struct file.

Lorsqu'un descripteur de fichier est dupliqué (avec dup(2) ou similaire), le duplicata fait référence à la même description de fichier ouvert que le descripteur de fichier original, et les deux descripteurs de fichier partagent par conséquent le décalage de fichier et les indicateurs d'état du fichier. Un tel partage peut également se produire entre processus : un processus enfant créé via fork(2) hérite de duplicatas des descripteurs de fichier de son parent, et ces duplicatas font référence aux mêmes descriptions de fichiers ouverts.

Chaque open() d'un fichier crée une nouvelle description de fichier ouvert ; ainsi, il peut y avoir plusieurs descriptions de fichiers ouverts correspondant à un même inœud de fichier.

Sur Linux, on peut utiliser l'opération kcmp(2) KCMP_FILE pour tester si deux descripteurs de fichier (dans le même processus ou dans deux processus différents) font référence à la même description de fichier ouvert.

NFS

Il y a de nombreuses imperfections dans le protocole sous-jacent à NFS, affectant entre autres O_SYNC et O_NDELAY.

Sur les systèmes de fichiers NFS avec la correspondance d'UID activée, open() peut renvoyer un descripteur de fichier mais, par exemple, les requêtes read(2) sont refusées avec EACCES. Cela est dû au fait que le client effectue open()

en vérifiant les permissions, mais que la correspondance d'UID est effectuée par le serveur lors des requêtes de lecture et d'écriture.

FIFO Ouvrir l'extrémité en lecture ou en écriture d'un FIFO bloque jusqu'à ce que l'autre extrémité soit également ouverte (par un autre processus ou thread). Voir fifo(7)

pour plus de détails.

Mode d'accès au fichier Contrairement aux autres valeurs qui peuvent être spécifiées dansflags , les valeurs de mode d'accès O_RDONLY, O_WRONLYet O_RDWR ne spécifient pas des bits individuels. Elles définissent plutôt les deux bits de poids faible de flagset sont définies respectivement comme 0, 1 et 2. En d'autres termes, la combinaison O_RDONLY | O_WRONLY est une erreur logique et n'a certainement pas la même signification que O_RDWR.

Linux réserve le mode d'accès spécial et non standard 3 (binaire 11) dans flags pour signifier : vérifier les permissions de lecture et d'écriture sur le fichier et renvoyer un descripteur de fichier qui ne peut pas être utilisé pour la lecture ou l'écriture. Ce mode d'accès non standard est utilisé par certains pilotes Linux pour renvoyer un descripteur de fichier qui doit être utilisé uniquement pour des opérations ioctl(2) spécifiques au périphérique.

Justification de openat() et des autres API utilisant des descripteurs de fichier de répertoire

openat() et les autres appels système et fonctions de bibliothèque qui prennent un argument de descripteur de fichier de répertoire (c'est-à-dire execveat(2), faccessat(2), fanotify_mark(2), fchmodat(2), fchownat(2), fspick(2), fstatat(2), futimesat(2), linkat(2), mkdirat(2), mknodat(2), mount_setattr(2), move_mount(2), name_to_handle_at(2), open_tree(2), openat2(2), readlinkat(2), renameat(2), renameat2(2), statx(2), symlinkat(2), unlinkat(2), utimensat(2), mkfifoat(3)et scandirat(3)) résolvent deux problèmes des anciennes interfaces qui les précédaient. Ici, l'explication est en termes de l'appel openat(), mais la justification est analogue pour les autres interfaces.

Premièrement, openat() permet à une application d'éviter les conditions de course qui pourraient survenir lors de l'utilisation de open() pour ouvrir des fichiers dans des répertoires autres que le répertoire de travail courant. Ces conditions de course résultent du fait qu'une composante du préfixe de répertoire donné à open() pourrait être modifiée en parallèle de l'appel à open(). Supposons, par exemple, que nous souhaitions créer le fichier dir1/dir2/xxx.dep si le fichier dir1/dir2/xxx existe. Le problème est qu'entre la vérification de l'existence et l'étape de création du fichier, dir1 ou dir2 (qui pourraient être des liens symboliques) pourraient être modifiés pour pointer vers un emplacement différent. De telles courses peuvent être évitées en ouvrant un descripteur de fichier pour le répertoire cible, puis en spécifiant ce descripteur de fichier comme argument dirfd de (disons) fstatat(2) et openat(). L'utilisation du descripteur de fichier dirfd présente également d'autres avantages :

•
le descripteur de fichier est une référence stable au répertoire, même si le répertoire est renommé ; et
•
le descripteur de fichier ouvert empêche le système de fichiers sous-jacent d'être démonté, tout comme lorsqu'un processus a un répertoire de travail courant sur un système de fichiers.

Deuxièmement, openat() permet l'implémentation d'un « répertoire de travail courant » par thread, via un ou plusieurs descripteurs de fichier maintenus par l'application. (Cette fonctionnalité peut aussi être obtenue par des astuces basées sur l'utilisation de /proc/self/fd/dirfd, mais de manière moins efficace.)

L'argument dirfd pour ces API peut être obtenu en utilisant open() ou openat() pour ouvrir un répertoire (avec soit l'indicateur O_RDONLY soit O_PATH ). Alternativement, un tel descripteur de fichier peut être obtenu en appliquant dirfd(3) à un flux de répertoire créé avec opendir(3).

Lorsque ces API reçoivent un argument dirfd de AT_FDCWD ou que le chemin d'accès spécifié est absolu, elles traitent leur argument de chemin d'accès de la même manière que les API conventionnelles correspondantes. Cependant, dans ce cas, plusieurs des API ont un argument flags qui donne accès à des fonctionnalités non disponibles avec les API conventionnelles correspondantes.

O_DIRECT

L'indicateur O_DIRECT peut imposer des restrictions d'alignement sur la longueur et l'adresse des tampons en espace utilisateur et le décalage de fichier des E/S. Sous Linux, les restrictions d'alignement varient selon le système de fichiers et la version du noyau et peuvent être totalement absentes. Le traitement des E/S O_DIRECT mal alignées varie également ; elles peuvent soit échouer avec EINVAL soit revenir à des E/S avec tampon.

Depuis Linux 6.1, la prise en charge de O_DIRECT et les restrictions d'alignement pour un fichier peuvent être interrogées en utilisant statx(2), avec l'indicateur STATX_DIOALIGN . La prise en charge de STATX_DIOALIGN varie selon le système de fichiers ; voir statx(2).

Certains systèmes de fichiers fournissent leurs propres interfaces pour interroger les restrictions d'alignement O_DIRECT , par exemple l'opération XFS_IOC_DIOINFO dans xfsctl(3). STATX_DIOALIGN devrait être utilisé à la place lorsqu'il est disponible.

Si rien de ce qui précède n'est disponible, alors la prise en charge des E/S directes et l'Les restrictions d'alignement ne peuvent être déduites que des caractéristiques connues du système de fichiers, du fichier individuel, du(des) périphérique(s) de stockage sous-jacent(s) et de la version du noyau. Dans Linux 2.4, la plupart des systèmes de fichiers basés sur des périphériques blocs exigent que l'offset du fichier ainsi que la longueur et l'adresse mémoire de tous les segments d'E/S soient des multiples de la taille de bloc du système de fichiers (typiquement 4096 octets). Dans Linux 2.6.0, cela a été assoupli à la taille de bloc logique du périphérique bloc (typiquement 512 octets). La taille de bloc logique d'un périphérique bloc peut être déterminée à l'aide de l' ioctl(2) BLKSSZGET opération ou depuis le shell en utilisant la commande :


blockdev --getss

O_DIRECT Les E/S ne devraient jamais être exécutées de manière concurrente avec l' fork(2) appel système, si le tampon mémoire est une correspondance privée (c'est-à-dire, toute correspondance créée avec le mmap(2) drapeau MAP_PRIVATE ; cela inclut la mémoire allouée sur le tas et les tampons alloués statiquement). Toutes ces E/S, qu'elles soient soumises via une interface d'E/S asynchrone ou depuis un autre thread dans le processus, devraient être complétées avant que fork(2) ne soit appelé. Le fait de ne pas le faire peut entraîner une corruption de données et un comportement indéfini dans les processus parent et enfant. Cette restriction ne s'applique pas lorsque le tampon mémoire pour les O_DIRECT E/S a été créé en utilisant shmat(2) ou mmap(2) avec le drapeau MAP_SHARED . Cette restriction ne s'applique pas non plus lorsque le tampon mémoire a été conseillé comme MADV_DONTFORK avec madvise(2), garantissant qu'il ne sera pas disponible pour l'enfant après fork(2).

Le O_DIRECT drapeau a été introduit dans SGI IRIX, où il a des restrictions d'alignement similaires à celles de Linux 2.4. IRIX a aussi un fcntl(2) appel pour interroger les alignements et les tailles appropriés. FreeBSD 4.x a introduit un drapeau du même nom, mais sans restrictions d'alignement.

O_DIRECT La prise en charge a été ajoutée dans Linux 2.4.10. Les anciens noyaux Linux ignorent simplement ce drapeau. Certains systèmes de fichiers peuvent ne pas implémenter le drapeau, auquel cas open() échoue avec l'erreur EINVAL s'il est utilisé.

Les applications devraient éviter de mélanger O_DIRECT et l'E/S normale vers le même fichier, et en particulier vers des régions de octets qui se chevauchent dans le même fichier. Même lorsque le système de fichiers gère correctement les problèmes de cohérence dans cette situation, le débit d'E/S global sera probablement plus lent que l'utilisation de l'un ou l'autre mode seul. De même, les applications devraient éviter de mélanger mmap(2) de fichiers avec l'E/S directe vers les mêmes fichiers.

Le comportement de O_DIRECT avec NFS différera des systèmes de fichiers locaux. Les anciens noyaux, ou les noyaux configurés de certaines manières, peuvent ne pas prendre en charge cette combinaison. Le protocole NFS ne prend pas en charge le passage du drapeau au serveur, donc O_DIRECT l'E/S contournera le cache de pages uniquement sur le client ; le serveur peut toujours mettre en cache l'E/S. Le client demande au serveur de rendre l'E/S synchrone pour préserver la sémantique synchrone de O_DIRECT. Certains serveurs se comporteront mal dans ces circonstances, surtout si la taille de l'E/S est petite. Certains serveurs peuvent également être configurés pour mentir aux clients sur le fait que l'E/S a atteint le stockage stable ; cela évitera la pénalité de performance au prix d'un certain risque pour l'intégrité des données en cas de panne de courant du serveur. Le client NFS de Linux n'impose aucune restriction d'alignement sur O_DIRECT l'E/S.

En résumé, O_DIRECT est un outil potentiellement puissant qui devrait être utilisé avec prudence. Il est recommandé que les applications traitent l'utilisation de O_DIRECT comme une option de performance qui est désactivée par défaut.

BUGS

Actuellement, il n'est pas possible d'activer l'E/S pilotée par signal en spécifiant O_ASYNC lors de l'appel à open() ; utilisez fcntl(2) pour activer ce drapeau.

On doit vérifier deux codes d'erreur différents, EISDIR et ENOENT, lorsqu'on essaie de déterminer si le noyau prend en charge la O_TMPFILE fonctionnalité.
