Les champs clés de l'index sont spécifiés sous forme de noms de colonnes ou, alternativement, sous forme d'expressions écrites entre parenthèses. Plusieurs champs peuvent être spécifiés si la méthode d'index prend en charge

Un champ d'index peut être une expression calculée à partir des valeurs d'une ou de plusieurs colonnes de la ligne de la table. Cette fonctionnalité peut être utilisée pour obtenir un accès rapide aux données basé sur une transformation des données de base. Par exemple, un index calculé sur upper(col) permettrait à la clause WHERE upper(col) = 'JIM' d'utiliser un

index.

PostgreSQL fournit les méthodes d'index B-tree, hash, GiST, SP-GiST, GIN et BRIN. Les utilisateurs peuvent également définir leurs propres méthodes d'index, mais c'est assez

compliqué.

Lorsque la clause WHERE est présente, un index partiel est créé. Un index partiel est un index qui ne contient des entrées que pour une partie d'une table, généralement une partie qui est plus utile à indexer que le reste de la table. Par exemple, si vous avez une table qui contient à la fois des commandes facturées et non facturées, où les commandes non facturées ne représentent qu'une petite fraction de la table totale mais constituent une section souvent utilisée, vous pouvez améliorer les performances en créant un index sur cette seule portion. Une autre application possible est d'utiliser WHERE avec UNIQUE pour imposer l'unicité sur un sous-ensemble d'une table. Voir la section 11.8 pour plus de

détails.

L'expression utilisée dans la clause WHERE ne peut faire référence qu'aux colonnes de la table sous-jacente, mais elle peut utiliser toutes les colonnes, pas seulement celles qui sont indexées. Actuellement, les sous-requêtes et les expressions d'agrégation sont également interdites dans WHERE. Les mêmes restrictions s'appliquent aux champs d'index qui sont des

expressions.

Toutes les fonctions et opérateurs utilisés dans une définition d'index doivent être « immuables », c'est-à-dire que leurs résultats ne doivent dépendre que de leurs arguments et jamais d'une influence externe (comme le contenu d'une autre table ou l'heure actuelle). Cette restriction garantit que le comportement de l'index est bien défini. Pour utiliser une fonction définie par l'utilisateur dans une expression d'index ou une clause WHERE, n'oubliez pas de marquer la fonction comme immuable lors de sa

création.

La clause facultative INCLUDE spécifie une liste de colonnes qui seront incluses dans l'index en tant que colonnes non clés. Une colonne non clé ne peut pas être utilisée dans une qualification de recherche de balayage d'index, et elle est ignorée pour les besoins de toute contrainte d'unicité ou d'exclusion imposée par l'index. Cependant, un balayage d'index seul peut renvoyer le contenu des colonnes non clés sans avoir à visiter la table de l'index, car elles sont disponibles directement à partir de l'entrée d'index. Ainsi, l'ajout de colonnes non clés permet d'utiliser les balayages d'index seul pour des requêtes qui autrement ne pourraient pas les utiliser.

Il est sage d'être prudent quant à l'ajout de colonnes non clés à un index, en particulier les colonnes larges. Si un tuple d'index dépasse la taille maximale autorisée pour le type d'index, l'insertion de données échouera. Paramètres de stockage de l'index

La clause WITH facultative spécifie des paramètres de stockage pour l'index. Chaque méthode d'indexage possède son propre ensemble de paramètres de stockage autorisés.

Les méthodes d'indexage B-tree, hash, GiST et SP-GiST acceptent toutes ce paramètre :

fillfactor (integer)

Contrôle à quel point la méthode d'indexage essaiera de remplir les pages d'index. Pour les B-arbres, les pages feuilles sont remplies à ce pourcentage lors de la construction initiale de l'index, ainsi que lors de l'extension de l'index à droite (ajout de nouvelles valeurs de clé maximales). Si les pages deviennent ensuite complètement pleines, elles seront scindées, entraînant une fragmentation de la structure de l'index sur disque. Les B-arbres utilisent un fillfactor par défaut de 90, mais toute valeur entière de 10 à 100 peut être sélectionnée.

Les index B-tree sur les tables où de nombreuses insertions et/ou mises à jour sont anticipées peuvent bénéficier de réglages de fillfactor plus bas au CREATE INDEX moment (après le chargement en masse dans la table). Des valeurs dans la plage de 50 à 90 peuvent utilement « lisser » le taux de scissions de pages pendant la première vie du B-arbre (abaisser le fillfactor comme cela peut même réduire le nombre absolu de scissions de pages, bien que cet effet dépende fortement de la charge de travail). La technique de suppression d'index B-tree de bas en haut décrite dans la section 65.1.4.2 dépend de l'espace « supplémentaire » disponible sur les pages pour stocker des « versions » de tuples supplémentaires, et peut donc être affectée par le fillfactor (bien que l'effet ne soit généralement pas significatif).

Dans d'autres cas spécifiques, il peut être utile d'augmenter le fillfactor à 100 au CREATE INDEX moment afin de maximiser l'utilisation de l'espace. Vous ne devriez envisager cela que si vous êtes absolument certain que la table est statique (c'est-à-dire qu'elle ne sera jamais affectée par des insertions ou des mises à jour). Un réglage de fillfactor de 100 risque sinon de nuire aux performances : même quelques mises à jour ou insertions provoqueront une soudaine avalanche de scissions de pages.

Les autres méthodes d'indexage utilisent le fillfactor de manière différente mais grossièrement analogue ; le fillfactor par défaut varie selon les méthodes.

Les index B-tree acceptent en outre ce paramètre :

deduplicate_items (boolean)

Contrôle l'utilisation de la technique de déduplication B-tree décrite dans la section 65.1.4.3. Défini à ON ou OFF pour activer ou désactiver l'optimisation. (D'autres orthographes de ON et OFF sont autorisées comme décrit dans la section 19.1.) La valeur par défaut est ON.

Note
Désactiver deduplicate_items via ALTER INDEX empêche les insertions futures de déclencher la déduplication, mais ne fait pas en soi que les tuples de liste de publication existants utilisent la représentation standard de tuple.

Les index GiST acceptent en outre ce paramètre :

buffering (enum)

Contrôle si la technique de construction avec tampon décrite dans la section 65.2.4.1 est utilisée pour construire l'index. Avec OFF, le tamponnage est désactivé, avec ON il est activé, et avec AUTO il est initialement désactivé, mais est activé à la volée une fois que la taille de l'index atteint effective_cache_size. La valeur par défaut est AUTO. Notez que si une construction triée est possible, elle sera utilisée à la place de la construction avec tampon sauf si buffering=ON est spécifié.

Les index GIN acceptent ces paramètres :

fastupdate (boolean)

Contrôle l'utilisation de la technique de mise à jour rapide décrite dans la section 65.4.4.1. ON active la mise à jour rapide, OFF la désactive. La valeur par défaut est ON.

Note
Désactiver fastupdate via ALTER INDEX empêche les insertions futures d'entrer dans la liste des entrées d'index en attente, mais ne vide pas en soi les entrées existantes. Vous voudrez peut-être VACUUM la table ou appeler la fonction gin_clean_pending_list par la suite pour vous assurer que la liste en attente est vidée.

gin_pending_list_limit (integer)

Remplace le réglage global de gin_pending_list_limit pour cet index. Cette valeur est spécifiée en kilo-octets.

Les index BRIN acceptent ces paramètres :

pages_per_range (integer)

Définit le nombre de blocs de table qui composent une plage de blocs pour chaque entrée d'un index BRIN (voir la section 65.5.1 pour plus de détails). La valeur par défaut est 128.

autosummarize (boolean)

Définit si une exécution de résumé est mise en file d'attente pour la plage de pages précédente chaque fois qu'une insertion est détectée sur la suivante (voir la section 65.5.1.1 pour plus de détails). La valeur par défaut est off.

Construction d'index de manière concurrente

La création d'un index peut interférer avec le fonctionnement régulier d'une base de données. Normalement, PostgreSQL verrouille la table à indexer contre les écritures et effectue toute la construction de l'index avec un seul balayage de la table. D'autres transactions peuvent toujours lire la table, mais si elles essaient d'insérer, de mettre à jour ou de supprimer des lignes dans la table, elles seront bloquées jusqu'à la fin de la construction de l'index. Cela pourrait avoir un effet grave si le système est une base de données de production active. Les tables très volumineuses peuvent prendre de nombreuses heures pour être indexées, et même pour les tables plus petites, une construction d'index peut exclure les écrivains pendant des périodes inacceptablement longues pour un système de production.

PostgreSQL prend en charge la construction d'index sans exclure les écritures. Cette méthode est invoquée en spécifiant l'option CONCURRENTLY de CREATE INDEX. Lorsque cette option est utilisée, PostgreSQL doit effectuer deux balayages de la table, et en plus il doit attendre que toutes les transactions existantes qui pourraient potentiellement modifier ou utiliser l'index se terminent. Ainsi, cette méthode nécessite plus de travail total qu'une construction d'index standard et prend significativement plus de temps pour se terminer. Cependant, puisqu'elle permet aux opérations normales de continuer pendant la construction de l'index, cette méthode est utile pour ajouter de nouveaux index dans un environnement de production. Bien sûr, la charge CPU et E/S supplémentaire imposée par la création de l'index pourrait ralentir d'autres opérations.

Dans une construction d'index concurrente, l'index est en réalité enregistré comme un index « invalide » dans les catalogues système dans une transaction, puis deux balayages de table ont lieu dans deux autres transactions. Avant chaque balayage de table, la construction de l'index doit attendre que les transactions existantes qui ont modifié la table se terminent. Après le second balayage, la construction de l'index doit attendre que toutes les transactions ayant un instantané (voir le chapitre 13) antérieur au second balayage se terminent, y compris les transactions utilisées par n'importe quelle phase des constructions d'index concurrentes sur d'autres tables, si les index concernés sont partiels ou ont des colonnes qui ne sont pas de simples références de colonnes. Enfin, l'index peut être marqué « valide » et prêt à l'emploi, et la CREATE INDEX commande se termine. Même alors, cependant, l'index peut ne pas être immédiatement utilisable pour les requêtes : dans le pire des cas, il ne peut pas être utilisé tant qu'il existe des transactions antérieures au début de la construction de l'index.

Si un problème survient lors du balayage de la table, comme un interblocage ou une violation d'unicité dans un index unique, la CREATE INDEX commande échouera mais laissera derrière elle un index « invalide ». Cet index sera ignoré à des fins de requête car il pourrait être incomplet ; cependant, il consommera toujours du surcoût de mise à jour. La commande psql \d signalera un tel index comme INVALID :

postgres=# \d tab
       Table "public.tab"
 Column |  Type   | Collation | Nullable | Default
--------+---------+-----------+----------+---------
 col    | integer |           |          |
Indexes:
    "idx" btree (col) INVALID

La méthode de récupération recommandée dans de tels cas est de supprimer l'index et de réessayer d'exécuter CREATE INDEX CONCURRENTLY. (Une autre possibilité est de reconstruire l'index avec REINDEX INDEX CONCURRENTLY).

Un autre avertissement lors de la construction concurrente d'un index unique est que la contrainte d'unicité est déjà appliquée contre les autres transactions lorsque le second balayage de table commence. Cela signifie que des violations de contrainte pourraient être signalées dans d'autres requêtes avant que l'index ne devienne disponible pour l'utilisation, ou même dans des cas où la construction de l'index échoue finalement. De plus, si un échec survient lors du second balayage, l'index « invalide » continue d'appliquer sa contrainte d'unicité par la suite.

Les constructions concurrentes d'index sur expressions et d'index partiels sont prises en charge. Les erreurs survenant lors de l'évaluation de ces expressions pourraient provoquer un comportement similaire à celui décrit ci-dessus pour les violations de contrainte d'unicité.

Les constructions d'index régulières permettent à d'autres constructions d'index régulières sur la même table de se produire simultanément, mais une seule construction d'index concurrente peut avoir lieu à la fois sur une table. Dans les deux cas, la modification du schéma de la table n'est pas autorisée pendant la construction de l'index. Une autre différence est qu'une commande CREATE INDEX régulière peut être exécutée dans un bloc de transaction, mais CREATE INDEX CONCURRENTLY ne peut pas.

Les constructions concurrentes pour les index sur les tables partitionnées ne sont actuellement pas prises en charge. Cependant, vous pouvez construire concurremment l'index sur chaque partition individuellement puis enfin créer l'index partitionné de manière non concurrente afin de réduire le temps pendant lequel les écritures sur la table partitionnée seront bloquées. Dans ce cas, la construction de l'index partitionné est une opération sur les métadonnées uniquement.

Voir le chapitre 11 pour des informations sur les moments où les index peuvent être utilisés, quand ils ne le sont pas, et dans quelles situations particulières ils peuvent être utiles.

Actuellement, seules les méthodes d'indexage B-tree, GiST, GIN et BRIN prennent en charge les index à colonnes de clé multiples. Le fait qu'il puisse y avoir plusieurs colonnes de clé est indépendant du fait que des colonnes INCLUDE puissent être ajoutées à l'index. Les index peuvent avoir jusqu'à 32 colonnes, y compris les colonnes INCLUDE. (Cette limite peut être modifiée lors de la construction de PostgreSQL.) Seul B-tree prend actuellement en charge les index uniques.

Une classe d'opérateurs avec paramètres facultatifs peut être spécifiée pour chaque colonne d'un index. La classe d'opérateurs identifie les opérateurs à utiliser par l'index pour cette colonne. Par exemple, un index B-tree sur des entiers de quatre octets utiliserait la classe int4_ops ; cette classe d'opérateurs inclut des fonctions de comparaison pour les entiers de quatre octets. En pratique, la classe d'opérateurs par défaut du type de données de la colonne est généralement suffisante. Le principal intérêt des classes d'opérateurs est que pour certains types de données, il pourrait y avoir plus d'un ordre significatif. Par exemple, nous pourrions vouloir trier un type de données de nombres complexes soit par valeur absolue, soit par partie réelle. Nous pourrions faire cela en définissant deux classes d'opérateurs pour le type de données puis en sélectionnant la classe appropriée lors de la création d'un index. Plus d'informations sur des classes d'opérateurs se trouve dans la section 11.10 et dans la section 36.

Lorsque CREATE INDEX est invoqué sur une table partitionnée, le comportement par défaut est de récurser sur toutes les partitions afin de s'assurer qu'elles ont toutes des index correspondants. Chaque partition est d'abord vérifiée pour déterminer si un index équivalent existe déjà, et le cas échéant, cet index sera attaché en tant qu'index de partition à l'index en cours de création, qui deviendra son index parent. Si aucun index correspondant n'existe, un nouvel index sera créé et automatiquement attaché ; le nom du nouvel index dans chaque partition sera déterminé comme si aucun nom d'index n'av été spécifié dans la commande. Si l'option ONLY est spécifiée, aucune récursion n'est effectuée et l'index est marqué invalide. (ALTER INDEX ... Pour les méthodes d'index qui prennent en charge les balayages ordonnés (actuellement, seul B-tree), les clauses facultatives ASC, DESC, NULLS FIRST et/ou NULLS LAST peuvent être spécifiées pour modifier l'ordre de tri de l'index. Étant donné qu'un index ordonné peut être balayé dans les deux sens, il n'est généralement pas utile de créer un index sur une seule colonne en DESC — cet ordre de tri est déjà disponible avec un index régulier.
