DESCRIPTIO

N

CREATE TABLE créera une nouvelle table, initialement vide, dans la base de données courante. La table appartiendra à l'utilisateur qui émet la

commande.

Si un nom de schéma est donné (par exemple, CREATE TABLE myschema.mytable ...) alors la table est créée dans le schéma spécifié. Sinon, elle est créée dans le schéma courant. Les tables temporaires existent dans un schéma spécial, donc un nom de schéma ne peut pas être donné lors de la création d'une table temporaire. Le nom de la table doit être distinct du nom de toute autre relation (table, séquence, index, vue, vue matérialisée ou table distante) dans le même

schéma.

CREATE TABLE crée également automatiquement un type de données qui représente le type composite correspondant à une ligne de la table. Par conséquent, les tables ne peuvent pas porter le même nom qu'un type de données existant dans le même

schéma.

Les clauses de contrainte facultatives spécifient des contraintes (tests) que les nouvelles lignes ou les lignes mises à jour doivent satisfaire pour qu'une opération d'insertion ou de mise à jour réussisse. Une contrainte est un objet SQL qui aide à définir l'ensemble des valeurs valides dans la table de diverses

manières.

Il existe deux façons de définir des contraintes : les contraintes de table et les contraintes de colonne. Une contrainte de colonne est définie comme partie d'une définition de colonne. Une définition de contrainte de table n'est pas liée à une colonne particulière et peut englober plus d'une colonne. Chaque contrainte de colonne peut aussi être écrite comme une contrainte de table ; une contrainte de colonne n'est qu'une commodité de notation à utiliser lorsque la contrainte n'affecte qu'une

colonne.

Pour pouvoir créer une table, vous devez avoir le

privilège USAGE sur tous les types de colonne
s ou sur le type de la clause OF, respectivement.

TEMPORARY ou

TEMP
Si spécifié, la table est créée comme table temporaire. Les tables temporaires sont automatiquement supprimées à la fin d'une session ou, de manière facultative, à la fin de la transaction en cours (voir ON COMMIT ci-dessous). Le chemin de recherche (search_path) par défaut inclut d'abord le schéma temporaire et donc les tables permanentes existantes portant le même nom ne sont pas choisies pour les nouveaux plans tant que la table temporaire existe, sauf si elles sont référencées avec des noms qualifiés par schéma. Tout index créé sur une table temporaire est également automatiquement temporaire.

Le démon autovacuum ne peut pas accéder et donc ne peut pas exécuter vacuum ou analyze sur les tables temporaires. Pour cette raison, des opérations vacuum et analyze appropriées doivent être effectuées via des commandes SQL de session. Par exemple, si une table temporaire va être utilisée dans des requêtes complexes, il est judicieux d'exécuter ANALYZE sur la table temporaire après qu'elle a été

remplie.

UNLOGGE

Si spécifié, la table est créée comme table non journalisée (unlogged). Les données écrites dans les tables non journalisées ne sont pas écrites dans le journal d'anticipation (voir Chapitre 28), ce qui les rend considérablement plus rapides que les tables ordinaires. Cependant, elles ne sont pas résistantes aux pannes : une table non journalisée est automatiquement tronquée après un crash ou une fermeture non propre. Le contenu d'une table non journalisée n'est également pas répliqué vers les serveurs de secours. Tout index créé sur une table non journalisée est également automatiquement non journalisé.

Si cela est spécifié, toute séquence créée en même temps que la table non journalisée (pour les colonnes identity ou serial) est également créée comme non

journalisée.

La clause COLLATE affecte une collation à la colonne (qui doit être d'un type de données pouvant être collationné). Si elle n'est pas spécifiée, la collation par défaut du type de données de la colonne est

STORAGE { PLAIN | EXTERNAL | EXTENDED | MAIN | DEFAULT

}
Cette forme définit le mode de stockage pour la colonne. Elle contrôle si cette colonne est stockée en ligne ou dans une table TOAST secondaire, et si les données doivent être compressées ou non. PLAIN doit être utilisé pour les valeurs de longueur fixe telles que les entiers et est stocké en ligne, non compressé. MAIN est pour les données en ligne, compressibles. EXTERNAL est pour les données externes, non compressées, et EXTENDED est pour les données externes, compressées. Écrire DEFAULT définit le mode de stockage sur le mode par défaut pour le type de données de la colonne. EXTENDED est la valeur par défaut pour la plupart des types de données qui prennent en charge le stockage non PLAIN. L'utilisation de EXTERNAL rendra les opérations de substring plus rapides sur les très grandes valeurs text et bytea, au prix d'un espace de stockage accru. Consultez la Section 66.2 pour plus
d'informations.

COMPRESSION compression_metho

La clause COMPRESSION définit la méthode de compression pour la colonne. La compression n'est prise en charge que pour les types de données à largeur variable, et n'est utilisée que lorsque le mode de stockage de la colonne est main ou extended. (Voir ALTER TABLE (ALTER_TABLE(7)) pour des informations sur les modes de stockage des colonnes.) Définir cette propriété pour une table partitionnée n'a pas d'effet direct, car ces tables n'ont pas de stockage propre, mais la valeur configurée sera héritée par les partitions nouvellement créées. Les méthodes de compression prises en charge sont pglz et lz4. (lz4 n'est disponible que si --with-lz4 a été utilisé lors de la construction de PostgreSQL.) De plus, compression_method peut être default pour spécifier explicitement le comportement par défaut, qui consiste à consulter le paramètre default_toast_compression au moment de l'insertion des données pour déterminer la méthode à
utiliser.

INHERITS ( parent_table [, ... ]

)
La clause facultative INHERITS spécifie une liste de tables dont la nouvelle table hérite automatiquement de toutes les colonnes. Les tables parentes peuvent être des tables simples ou des tables étrangères.

L'utilisation de INHERITS crée une relation persistante entre la nouvelle table fille et sa ou ses tables parentes. Les modifications de schéma du ou des parents se propagent normalement également aux filles, et par défaut les données de la table fille sont incluses dans les balayages du ou des

parents.

Si le même nom de colonne existe dans plus d'une table parente, une erreur est signalée sauf si les types de données des colonnes correspondent dans chacune des tables parentes. S'il n'y a pas de conflit, les colonnes en double sont fusionnées pour former une seule colonne dans la nouvelle table. Si la liste de noms de colonnes de la nouvelle table contient un nom de colonne qui est également hérité, le type de données doit également correspondre à la ou aux colonnes héritées, et les définitions de colonnes sont fusionnées en une seule. Si la nouvelle table spécifie explicitement une valeur par défaut pour la colonne, cette valeur par défaut remplace toutes les valeurs par défaut provenant des déclarations héritées de la colonne. Sinon, tous les parents qui spécifient des valeurs par défaut pour la colonne doivent spécifier la même valeur par défaut, sinon une erreur sera

signalée.

Les contraintes CHECK sont fusionnées essentiellement de la même manière que les colonnes : si plusieurs tables parentes et/ou la définition de la nouvelle table contiennent des contraintes CHECK de même nom, ces contraintes doivent toutes avoir la même expression de vérification, sinon une erreur sera signalée. Les contraintes ayant le même nom et la même expression seront fusionnées en une seule copie. Une contrainte marquée NO INHERIT dans un parent ne sera pas considérée. Notez qu'une contrainte CHECK sans nom dans la nouvelle table ne sera jamais fusionnée, car un nom unique sera toujours choisi pour

elle.

Les paramètres STORAGE des colonnes sont également copiés depuis les tables

parentes.

Si une colonne dans la table parente est une colonne d'identité,

cette propriété n'est pas héritée. Une colonne dans la table f

PARTITION BY { RANGE | LIST | HASH } ( { column_name | ( expression ) } [ opclass ] [, ...]

)
La clause facultative PARTITION BY spécifie une stratégie de partitionnement de la table. La table ainsi créée est appelée table partitionnée. La liste entre parenthèses de colonnes ou d'expressions forme la clé de partitionnement de la table. Lors de l'utilisation du partitionnement par plage ou par hachage, la clé de partitionnement peut inclure plusieurs colonnes ou expressions (jusqu'à 32, mais cette limite peut être modifiée lors de la construction de PostgreSQL), mais pour le partitionnement par liste, la clé de partitionnement doit se composer d'une seule colonne ou expression.

Le partitionnement par plage et par liste nécessite une classe d'opérateurs btree, tandis que le partitionnement par hachage nécessite une classe d'opérateurs de hachage. Si aucune classe d'opérateurs n'est spécifiée explicitement, la classe d'opérateurs par défaut du type approprié sera utilisée ; s'il n'existe pas de classe d'opérateurs par défaut, une erreur sera levée. Lorsque le partitionnement par hachage est utilisé, la classe d'opérateurs utilisée doit implémenter la fonction de support 2 (voir la Section 36.16.3 pour les détails)

.

Une table partitionnée est divisée en sous-tables (appelées partitions), qui sont créées à l'aide de commandes CREATE TABLE séparées. La table partitionnée est elle-même vide. Une ligne de données insérée dans la table est acheminée vers une partition en fonction de la valeur des colonnes ou des expressions de la clé de partitionnement. Si aucune partition existante ne correspond aux valeurs de la nouvelle ligne, une erreur sera

signalée.

Consultez la Section 5.12 po

ur plus de discussions sur le
partitionnement des tables.

PARTITION OF parent_table { FOR VALUES partition_bound_spec | DEFAULT

}
Crée la table comme partition de la table parente spécifiée. La table peut être créée soit comme partition pour des valeurs spécifiques en utilisant FOR VALUES, soit comme partition par défaut en utilisant DEFAULT. Tous les index, contraintes et déclencheurs au niveau des lignes définis par l'utilisateur qui existent dans la table parente sont clonés sur la nouvelle partition.

Le partition_bound_spec doit correspondre à la méthode de partitionnement et à la clé de partitionnement de la table parente, et ne doit pas se chevaucher avec une partition existante de ce parent. La forme avec IN est utilisée pour le partitionnement par liste, la forme avec FROM et TO est utilisée pour le partitionnement par plage, et la forme avec WITH est utilisée pour le partitionnement par

hachage.

partition_bound_expr est toute expression sans variable (les sous-requêtes, les fonctions de fenêtre, les fonctions d'agrégation et les fonctions renvoyant des ensembles ne sont pas autorisées). Son type de données doit correspondre au type de données de la colonne de clé de partitionnement correspondante. L'expression est évaluée une fois au moment de la création de la table, elle peut donc même contenir des expressions volatiles telles que CURRENT_TIMESTAMP

.

Lors de la création d'une partition par liste, NULL peut être spécifié pour indiquer que la partition autorise la colonne de clé de partitionnement à être nulle. Cependant, il ne peut pas y avoir plus d'une telle partition par liste pour une table parente donnée. NULL ne peut pas être spécifié pour les partitions par

plage.

Lors de la création d'une partition par plage, la borne inférieure spécifiée avec FROM est une borne incluse, tandis que la borne supérieure spécifiée avec TO est une borne exclue. C'est-à-dire que les valeurs spécifiées dans la liste FROM sont des valeurs valides des colonnes de clé de partitionnement correspondantes pour cette partition, tandis que celles de la liste TO ne le sont pas. Notez que cette instruction doit être comprise selon les règles de comparaison ligne par ligne (Section 9.25.5). Par exemple, étant donné PARTITION BY RANGE (x,y), une borne de partition FROM (1, 2) TO (3, 4) autorise x=1 avec tout y>=2, x=2 avec tout y non nul, et x=3 avec tout

y<4.

Les valeurs spéciales MINVALUE et MAXVALUE peuvent être utilisées lors de la création d'une partition par plage pour indiquer qu'il n'y a pas de borne inférieure ou supérieure sur la valeur de la colonne. Par exemple, une partition définie avec FROM (MINVALUE) TO (10) autorise toutes les valeurs inférieures à 10, et une partition définie avec FROM (10) TO (MAXVALUE) autorise toutes les valeurs supérieures ou égales à

10.

Lors de la création d'une partition par plage impliquant plus d'une colonne, il peut également être judicieux d'utiliser MAXVALUE comme partie de la borne inférieure, et MINVALUE comme partie de la borne supérieure. Par exemple, une partition définie avec FROM (0, MAXVALUE) TO (10, MAXVALUE) autorise toutes les lignes où la première colonne de clé de partitionnement est supérieure à 0 et inférieure ou égale à 10. De même, une partition définie avec FROM ('a', MINVALUE) TO ('b', MINVALUE) autorise toutes les lignes où la première colonne de clé de partitionnement commence par « a »

.

Notez que si MINVALUE ou MAXVALUE est utilisé pour une colonne d'une borne de partitionnement, la même valeur doit être utilisée pour toutes les colonnes suivantes. Par exemple, (10, MINVALUE, 0) n'est pas une borne valide ; vous devriez écrire (10, MINVALUE, MINVALUE)

.

Notez également que certains types d'éléments, comme timestamp, ont la notion d'« infini », qui est simplement une autre valeur pouvant être stockée. Cela diffère de MINVALUE et MAXVALUE, qui ne sont pas de vraies valeurs pouvant être stockées, mais plutôt des moyens d'exprimer que la valeur est illimitée. MAXVALUE peut être considéré comme supérieur à toute autre valeur, y compris « l'infini », et MINVALUE comme inférieur à toute autre valeur, y compris « l'infini négatif ». Ainsi, la plage FROM ('infinity') TO (MAXVALUE) n'est pas une plage vide ; elle autorise précisément une valeur à être stockée — « l'infini »

.

Si DEFAULT est spécifié, la table sera créée comme partition par défaut de la table parente. Cette option n'est pas disponible pour les tables partitionnées par hachage. Une valeur de clé de partitionnement qui ne rentre dans aucune autre partition du parent donné sera acheminée vers la partition par

défaut.

Lorsqu'une table a une partition DEFAULT existante et qu'une nouvelle partition y est ajoutée, la partition par défaut doit être balayée pour vérifier qu'elle ne contient pas de lignes qui appartiennent proprement à la nouvelle partition. Si la partition par défaut contient un grand nombre de lignes, cela peut être lent. Le balayage sera ignoré si la partition par défaut est une table étrangère ou si elle a une contrainte qui prouve qu'elle ne peut pas contenir de lignes qui devraient être placées dans la nouvelle

partition.

Lors de la création d'une partition par hachage, un module et un reste doivent être spécifiés. Le module doit être un entier positif, et le reste doit être un entier non négatif inférieur au module. Typiquement, lors de la configuration initiale d'une table partitionnée par hachage, vous devriez choisir un module égal au nombre de partitions et attribuer à chaque table le même module et un reste différent (voir les exemples, ci-dessous). Cependant, il n'est pas requis que chaque partition ait le même module, seulement que chaque module qui apparaît entre les partitions d'une table partitionnée par hachage est un facteur du prochain plus grand module. Cela permet d'augmenter le nombre de partitions de manière incrémentielle sans avoir à déplacer toutes les données d'un seul coup. Par exemple, supposez que vous ayez une table partitionnée par hachage avec 8 partitions, chacune ayant un module de 8, mais que vous constatiez qu'il est nécessaire d'augmenter le nombre de partitions à 16. Vous pouvez détacher l'une des partitions de module 8, créer deux nouvelles partitions de module 16 couvrant la même portion de l'espace des clés (l'une avec un reste égal au reste de la partition détachée, et l'autre avec un reste égal à cette valeur plus 8), et les remplir à nouveau avec des données. Vous pouvez ensuite répéter cette opération — peut-être à un moment ultérieur — pour chaque partition de module 8 jusqu'à ce qu'il n'en reste aucune. Bien que cela puisse encore impliquer un grand déplacement de données à chaque étape, c'est toujours préférable à devoir créer une table entièrement nouvelle et déplacer toutes les données d'un seul

coup.

Une partition doit avoir les mêmes noms de colonnes et types que la table partitionnée à laquelle elle appartient. Les modifications des noms ou des types de colonnes d'une table partitionnée se propageront automatiquement à toutes les partitions. Les contraintes CHECK seront héritées automatiquement par chaque partition, mais une partition individuelle peut spécifier des contraintes CHECK supplémentaires ; les contraintes supplémentaires portant le même nom et la même condition que celles de la table parente seront fusionnées avec la contrainte parente. Les valeurs par défaut peuvent être spécifiées séparément pour chaque partition. Mais notez que la valeur par défaut d'une partition n'est pas appliquée lors de l'insertion d'un tuple via une table

partitionnée.

Les lignes insérées dans une table partitionnée seront automatiquement acheminées vers la partition correcte. Si aucune partition appropriée n'existe, une erreur se

produira.

Les opérations telles que TRUNCATE qui affectent normalement une table et tous ses enfants d'héritage se propageront à toutes les partitions, mais peuvent également être effectuées sur une partition

individuelle.

Notez que la création d'une partition à l'aide de PARTITION OF nécessite de prendre un verrou ACCESS EXCLUSIVE sur la table parente partitionnée. De même, la suppression d'une partition avec DROP TABLE nécessite de prendre un verrou ACCESS EXCLUSIVE sur la table parente. Il est possible d'utiliser ALTER TABLE ATTACH/DETACH PARTITION pour effectuer ces opérations avec un verrou plus faible,

réduisant ainsi les interférences avec les opé
rations concurrentes sur la table partitionnée.

LIKE source_table [ like_option ...

]
La clause LIKE spécifie une table à partir de laquelle la nouvelle table copie automatiquement tous les noms de colonnes, leurs types de données et leurs contraintes NOT NULL.

Contrairement à INHERITS, la nouvelle table et la table d'origine sont complètement découplées une fois la création terminée. Les modifications apportées à la table d'origine ne seront pas appliquées à la nouvelle table, et il n'est pas possible d'inclure les données de la nouvelle table dans les balayages de la table

d'origine.

Contrairement également à INHERITS, les colonnes et contraintes copiées par LIKE ne sont pas fusionnées avec les colonnes et contraintes de même nom. Si le même nom est spécifié explicitement ou dans une autre clause LIKE, une erreur est

signalée.

Les clauses like_option facultatives spécifient quelles propriétés supplémentaires de la table d'origine copier. Spécifier INCLUDING copie la propriété, spécifier EXCLUDING omet la propriété. EXCLUDING est la valeur par défaut. Si plusieurs spécifications sont faites pour le même type d'objet, la dernière est utilisée. Les options disponibles sont

:

INCLUDING

Les commentaires des colonnes, contraintes et index copiés seront copiés. Le comportement par défaut est d'exclure les commentaires, ce qui fait que les colonnes et contraintes copiées dans la nouvelle table n'ont pas de
commentaires.

INCLUDING

COMPRESSION
La méthode de compression des colonnes sera copiée. Le comportement par défaut est d'exclure les méthodes de compression, ce qui fait que les colonnes ont la méthode de compression par
défaut.

INCLUDING

CONSTRAINTS
Les contraintes CHECK seront copiées. Aucune distinction n'est faite entre les contraintes de colonne et les contraintes de table. Les contraintes NOT NULL sont toujours copiées vers la nouvelle

INCLUDING

DEFAULTS

La contrainte UNIQUE spécifie qu'un groupe d'une ou plusieurs colonnes d'une table ne peut contenir que des valeurs uniques. Le comportement d'une contrainte de table UNIQUE est le même que celui d'une contrainte de colonne UNIQUE, avec la capacité supplémentaire de s'étendre sur plusieurs colonnes. La contrainte impose donc que deux lignes quelconques doivent différer dans au moins l'une de ces colonnes.

Si l'option WITHOUT OVERLAPS est spécifiée pour la dernière colonne, alors cette colonne est vérifiée pour les chevauchements au lieu de l'égalité. Dans ce cas, les autres colonnes de la contrainte permettront les doublants à condition que les doublants ne se chevauchent pas dans la colonne WITHOUT OVERLAPS. (C'est parfois appelé une clé temporelle, si la colonne est une plage de dates ou d'horodatages, mais PostgreSQL permet des plages sur n'importe quel type de base.) En effet, une telle contrainte est appliquée avec une contrainte EXCLUDE plutôt qu'une contrainte UNIQUE. Ainsi, par exemple, UNIQUE (id, valid_at WITHOUT OVERLAPS) se comporte comme EXCLUDE USING GIST (id WITH =, valid_at WITH &&). La colonne WITHOUT OVERLAPS doit avoir un type plage ou multirange. Les plages/multiranges vides ne sont pas autorisées. Les colonnes non WITHOUT OVERLAPS de la contrainte peuvent être de n'importe quel type pouvant être comparé pour l'égalité dans un index GiST. Par défaut, seuls les types plage sont pris en charge, mais vous pouvez utiliser d'autres types en ajoutant l'extension btree_gist (qui est la façon prévue d'utiliser cette fonctionnalité)

.

Pour les besoins d'une contrainte UNIQUE, les valeurs NULL ne sont pas considérées comme égales, sauf si NULLS NOT DISTINCT est

spécifié.

COMPATIBILIT

É

La commande CREATE TABLE est conforme à la norme SQL, à l'exception des cas listés

ci-dessous.

Tables

temporaires

Bien que la syntaxe de CREATE TEMPORARY TABLE ressemble à celle de la norme SQL, l'effet n'est pas le même. Dans la norme, les tables temporaires ne sont définies qu'une seule fois et existent automatiquement (avec un contenu vide au départ) dans chaque session qui en a besoin. PostgreSQL exige en revanche que chaque session émette sa propre commande CREATE TEMPORARY TABLE pour chaque table temporaire à utiliser. Cela permet à différentes sessions d'utiliser le même nom de table temporaire à des fins différentes, alors que l'approche de la norme contraint toutes les instances d'un nom de table temporaire donné à avoir la même structure de

table.

La définition du comportement des tables temporaires dans la norme est largement ignorée. Le comportement de PostgreSQL sur ce point est similaire à celui de plusieurs autres bases de données

SQL.

La norme SQL distingue également les tables temporaires globales et locales, où une table temporaire locale a un ensemble de contenu distinct pour chaque module SQL au sein de chaque session, bien que sa définition reste partagée entre les sessions. Comme PostgreSQL ne prend pas en charge les modules SQL, cette distinction n'est pas pertinente dans

PostgreSQL.

Par souci de compatibilité, PostgreSQL acceptera les mots-clés GLOBAL et LOCAL dans une déclaration de table temporaire, mais ils n'ont actuellement aucun effet. L'utilisation de ces mots-clés est déconseillée, car les versions futures de PostgreSQL pourraient adopter une interprétation de leur signification plus conforme à la

norme.

La clause ON COMMIT pour les tables temporaires ressemble également à la norme SQL, mais présente certaines différences.

Si la clause ON COMMIT est omise, SQL spécifie que le comportement par défaut est ON COMMIT DELETE ROWS. Cependant, l
e comportement par défaut dans PostgreSQL est ON COMMIT PRESERVE ROWS. L'option ON COMMIT DROP n'existe pas dans SQL.

Contraintes d'unicité non

différables

Lorsqu'une contrainte UNIQUE ou PRIMARY KEY n'est pas différable, PostgreSQL vérifie l'unicité immédiatement chaque fois qu'une ligne est insérée ou modifiée. La norme SQL indique que l'unicité ne

doit être appliquée qu'à la fin de l'instruction ; cela fait une différence lorsque, par exemple, une seule commande met à jour plusieurs valeurs de clé. Pour obtenir un comportement conforme
à la norme, déclarez la contrainte comme DEFERRABLE mais non différée (c'est-à-dire INITIALLY IMMEDIATE). Notez que cela peut être nettement plus lent qu'une vérification d'unicité immédiate.
