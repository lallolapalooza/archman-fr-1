NOM

crsh - Outil d'administration de cluster

VERSION

Cette documentation concerne la version : 4.16

SYNOPSIS

crsh [-a '<commande>'] [-K <secondes>] [-q] [-c '<nom_fichier>'] [-x <colonnes>] [-C '<nom_fichier>'] [--debug [[...] || <ENTIER>]] [-d] [-e '<[utilisateur@]<hôte>[:port]>'] [--fillscreen] [-f '<police>'] [-h] [-L '[tag]'] [-H] [-o '<CHAINE>'] [-p <port>] [-Q] [-y <lignes>] [-s] [-r '<nom_fichier>'] [-t '<CHAINE>'] [-g] [-T '<titre>'] [-u] [-?] [-A] [-l '<nom_utilisateur>'] [-v]

CONNEXES

Voir également les pages man individuelles pour chacune de ces utilitaires

ccon - Utiliser 'console' comme méthode de communication
csftp - Utiliser 'sftp' comme méthode de communication
cssh - Utiliser 'ssh' comme méthode de communication
ctel - Utiliser 'telnet' comme méthode de communication

DESCRIPTION

La commande ouvre une console d'administration et un xterm vers tous les hôtes spécifiés. Tout texte tapé dans la console d'administration est répliqué dans toutes les fenêtres. Toutes les fenêtres peuvent également être utilisées directement.

Cet outil est destiné (mais pas limité) à l'administration de clusters où la même configuration ou les mêmes commandes doivent être exécutées sur chaque nœud du cluster. L'exécution de ces commandes simultanément via cet outil garantit que tous les nœuds restent synchronisés.

Les connexions sont ouvertes en utilisant rsh, qui doit être correctement installé et configuré.

Une prudence particulière doit être prise lors de la modification de fichiers, car les lignes ne sont pas nécessairement dans le même ordre ; supposer que la ligne 5 est identique sur tous les serveurs et la modifier est dangereux. Il est préférable de rechercher la ligne spécifique à modifier et de vérifier que tous les terminaux sont conformes aux attentes avant de valider les modifications.

Notes supplémentaires

Veuillez également consulter "BOGUES CONNUS".

  • La ligne pointillée sur n'importe quel sous-menu est détachable, c'est-à-dire cliquez dessus et le sous-menu se transforme en sa propre fenêtre.
  • Décochez un nom d'hôte dans le sous-menu Hôtes pour déconnecter l'hôte de la fenêtre de contrôle du cluster, de sorte que tout texte tapé dans la console ne soit pas envoyé à cet hôte. Le re-sélectionner le reconnectera.
  • Si les barres de menus de votre gestionnaire de fenêtres sont masquées par les fenêtres du terminal, consultez les options "screen_reserve_XXXXX" dans le fichier $HOME/.clusterssh/config (voir "FICHIERS").
  • Si les terminaux se chevauchent trop, consultez les options "terminal_reserve_XXXXX" dans le fichier $HOME/.clusterssh/config (voir "FICHIERS").
  • Lors de l'utilisation de ClusterSSH sur un grand nombre de systèmes pour se connecter à un seul système à l'aide d'un utilitaire SSH (par exemple, vous émettez une commande pour copier un fichier à l'aide de scp depuis les ordinateurs distants vers un seul hôte) et lorsque ces connexions nécessitent une authentification (c'est-à-dire que vous allez vous authentifier avec un mot de passe), le démon sshd à cet endroit peut refuser les connexions après que la limite "MaxStartups" dans sshd_config soit dépassée. (Si cette valeur n'est pas définie, elle est par défaut à 10). Il s'agit d'un comportement attendu ; sshd utilise ce mécanisme pour prévenir les attaques par déni de service provenant de sources non authentifiées. Veuillez régler sshd_config et recharger le démon SSH, ou envisagez d'utiliser le mécanisme ~/.ssh/authorized_keys pour l'authentification si vous rencontrez ce problème.
  • Si les fenêtres clientes ne parviennent pas à s'ouvrir, essayez d'exécuter :

    "crsh -e {nom d'hôte unique}"

    Cela testera les mécanismes utilisés pour ouvrir des fenêtres vers les hôtes. Cela pourrait être dû soit à l'option de terminal "-xrm" qui active "AllowSendEvents" (certains terminaux ne nécessitent pas cette option, d'autres terminaux ont une autre méthode pour l'activer - voir la documentation de votre terminal) soit à la configuration de "rsh".
