DESCRIPTIO

N

CREATE STATISTICS créera un nouvel objet de statistiques étendues suivant des données concernant la table, la table externe ou la vue matérialisée spécifiée. L'objet de statistiques sera créé dans la base de données actuelle et appartiendra à l'utilisateur émettant la

commande.

La commande CREATE STATISTICS possède deux formes de base. La première forme permet de collecter des statistiques univariées pour une expression unique, offrant des avantages similaires à ceux d'un index sur expression sans la surcharge de la maintenance d'index. Cette forme ne permet pas de spécifier le type de statistiques, car les différents types de statistiques ne concernent que les statistiques multivariées. La deuxième forme de la commande permet de collecter des statistiques multivariées sur plusieurs colonnes et/ou expressions, en spécifiant éventuellement les types de statistiques à inclure. Cette forme entraînera également automatiquement la collecte de statistiques univariées sur toutes les expressions incluses dans la

liste.

Si un nom de schéma est donné (par exemple, CREATE STATISTICS myschema.mystat ...), alors l'objet de statis

tiques est créé dans le schéma spécifié. Sinon, il est créé dans le schéma actuel. Si fourni, le nom de
l'objet de statistiques doit être distinct du nom de tout autre objet de statistiques dans le même schéma.

PARAMÈTRE

S

IF NOT

EXISTS
Ne pas lever d'erreur si un objet de statistiques portant le même nom existe déjà. Un avis est émis dans ce cas. Notez que seul le nom de l'objet de statistiques est pris en compte ici, et non les détails de sa définition. Le nom des statistiques est requis lorsque IF NOT EXISTS est
spécifié.

statistics_nam

e
Le nom (éventuellement qualifié par le schéma) de l'objet de statistiques à créer. Si le nom est omis, PostgreSQL choisit un nom approprié basé sur le nom de la table parent et le(s) nom(s) de colonne et/ou d'expression défini(s)
.

statistics_kin

d
Un type de statistiques multivariées à calculer dans cet objet de statistiques. Les types actuellement pris en charge sont ndistinct, qui active les statistiques n-distinctes, dependencies, qui active les statistiques de dépendance fonctionnelle, et mcv, qui active les listes de valeurs les plus courantes. Si cette clause est omise, tous les types de statistiques pris en charge sont inclus dans l'objet de statistiques. Les statistiques d'expression univariées sont construites automatiquement si la définition des statistiques inclut des expressions complexes plutôt que de simples références de colonnes. Pour plus d'informations, voir la section 14.2.2 et la section 69.
2.

column_nam

e
Le nom d'une colonne de table à couvrir par les statistiques calculées. Cela n'est autorisé que lors de la construction de statistiques multivariées. Au moins deux noms de colonnes ou expressions doivent être spécifiés, et leur ordre n'est pas
significatif.

expressio

n
Une expression à couvrir par les statistiques calculées. Cela peut être utilisé pour construire des statistiques univariées sur une expression unique, ou comme partie d'une liste de plusieurs noms de colonnes et/ou d'expressions pour construire des statistiques multivariées. Dans ce dernier cas, des statistiques univariées séparées sont construites automatiquement pour chaque expression de la
liste.

table_nam

e
Le nom (éventuellement qualifié par le schéma) de la table contenant la ou les colonnes sur lesquelles les statistiques sont calculées ; voir ANALYZE(7) pour une explication du tra
itement de l'héritag
e et des partitions.

NOTE

S

Vous devez être le propriétaire d'une table pour créer un objet de statistiques la lisant. Une fois créé, cependant, la propriété de l'objet de statistiques est indépendante de la ou des tables

sous-jacentes.

Les statistiques d'expression sont par expression et sont similaires à la création d'un index sur l'expression, sauf qu'elles évitent la surcharge de la maintenance d'index. Les statistiques d'expression sont construites automatiquement pour chaque expression dans la définition de l'objet de

statistiques.

Les statistiques étendues ne sont actuellement pas utilisées par le planificate

ur pour les estimations de sélectivité faites pour les jointures de tables. Cett
e limitation sera probablement supprimée dans une future version de PostgreSQL.

EXEMPLE

S

Créer la table t1 avec deux colonnes fonctionnellement dépendantes, c'est-à-dire que la connaissance d'une valeur dans la première colonne est suffisante pour déterminer la valeur dans l'autre colonne. Puis construire des statistiques de dépendance fonctionnelle sur ces colonnes

: 
CREATE TABLE t1 (
    a   int,
    b   int
);
INSERT INTO t1 SELECT i/100, i/500
                 FROM generate_series(1,1000000) s(i);
ANALYZE t1;
-- le nombre de lignes correspondantes sera fortement sous-estimé :
EXPLAIN ANALYZE SELECT * FROM t1 WHERE (a = 1) AND (b = 0);
CREATE STATISTICS s1 (dependencies) ON a, b FROM t1;
ANALYZE t1;
-- maintenant l'estimation du nombre de lignes est plus précise :
EXPLAIN ANALYZE SELECT * FROM t1 WHERE (a = 1) AND (b =
0)
;

Sans statistiques de dépendance fonctionnelle, le planificateur supposerait que les deux conditions WHERE sont indépendantes et multiplierait leurs sélectivités pour obtenir une estimation du nombre de lignes beaucoup trop faible. Avec de telles statistiques, le planificateur reconnaît que les conditions WHERE sont redondantes et ne sous-estime pas le nombre de

lignes.

Créer la table t2 avec deux colonnes parfaitement corrélées (contenant des données identiques), et une liste MCV sur ces colonnes

: 
CREATE TABLE t2 (
    a   int,
    b   int
);
INSERT INTO t2 SELECT mod(i,100), mod(i,100)
                 FROM generate_series(1,1000000) s(i);
CREATE STATISTICS s2 (mcv) ON a, b FROM t2;
ANALYZE t2;
-- combinaison valide (trouvée dans MCV)
EXPLAIN ANALYZE SELECT * FROM t2 WHERE (a = 1) AND (b = 1);
-- combinaison invalide (non trouvée dans MCV)
EXPLAIN ANALYZE SELECT * FROM t2 WHERE (a = 1) AND (b =
2)
;

La liste MCV donne au planificateur des informations plus détaillées sur les valeurs spécifiques qui apparaissent couramment dans la table, ainsi qu'une borne supérieure sur les sélectivités des combinaisons de valeurs qui n'apparaissent pas dans la table, lui permettant de générer de meilleures estimations dans les deux

cas.

Créer la table t3 avec une seule colonne timestamp, et exécuter des requêtes utilisant des expressions sur cette colonne. Sans statistiques étendues, le planificateur n'a aucune information sur la distribution des données pour les expressions et utilise des estimations par défaut. Le planificateur ne réalise pas non plus que la valeur de la date tronquée au mois est entièrement déterminée par la valeur de la date tronquée au jour. Puis construire des statistiques d'expression et ndistinct sur ces deux expressions

: 
CREATE TABLE t3 (
    a   timestamp
);
INSERT INTO t3 SELECT i FROM generate_series('2020-01-01'::timestamp,
                                             '2020-12-31'::timestamp,
                                             '1 minute'::interval) s(i);
ANALYZE t3;
-- le nombre de lignes correspondantes sera fortement sous-estimé :
EXPLAIN ANALYZE SELECT * FROM t3
  WHERE date_trunc('month', a) = '2020-01-01'::timestamp;
EXPLAIN ANALYZE SE
LECT * FROM t3 WHERE date_trunc('day', a) BETWEEN '2020-01-01'::timestamp AND '2020-06-30'::timestamp; EXPLAIN ANALYZE SELECT date_trunc('month', a), date_trunc('day', a) FROM t3 GROUP BY 1, 2; -- construire des statistiques ndistinct sur la paire d'expressions (les -- statistiques par expression sont construites automatiquement) CREATE STATISTICS s3 (ndistinct) ON date_trunc('month', a), date_trunc('
day', a) FROM t3; ANALYZE t3; -- maintenant les estimations du nombre de lignes sont plus précises : EXPLAIN ANALYZE SELECT * FROM t3 WHERE date_trunc('month', a) = '2020-01-01'::timestamp; EXPLAIN ANALYZE SELECT * FROM t3 WHERE date_trunc('day', a) BETWEEN '2020-01-01'::timestamp AND '2020-06-30'::timestamp; EXPLAIN ANALYZE SELECT date_trunc('month', a), date_trunc('day', a) FROM t3 GROUP BY 1, 2;

Sans statistiques d'expression et ndistinct, le planificateur n'a aucune information sur le nombre de valeurs distinctes pour les expressions et doit se fier aux estimations par défaut. Les conditions d'égalité et de plage sont supposées avoir une sélectivité de 0,5 %, et le nombre de valeurs distinctes dans l'expression est supposé être le même que pour la colonne (c'est-à-dire unique). Cela entraîne une sous-estimation significative du nombre de lignes dans les deux premières requêtes. De plus, le planificateur n'a aucune informationation sur la relation entre les expressions, il suppose donc que les deux conditions WHERE et GROUP BY sont indépendantes, et multiplie leurs sélectivités pour obtenir une surestimation importante du n

ombre de groupes dans la requête d'agrégation. Ce problème est aggravé par le manque de statistiques précises pour les expressions, contraignant le planificateur à utiliser une estimation ndistinct par défa
ut pour l'expression, dérivée du ndistinct de la colonne. Avec de telles statistiques, le planificateur reconnaît que les conditions sont corrélées et parvient à des estimations beaucoup plus précises.
