DESCRIPTIO

N

Les fonctions crypt, crypt_r, crypt_rn et crypt_ra « hachent » de manière irréversible la phrase pour son stockage dans la base de données de mots de passe du système ( shadow(5)) en utilisant une « méthode de hachage » cryptographique. Le résultat de cette opération est appelé une « phrase secrète hachée » ou simplement un « hachage ». Les méthodes de hachage sont décrites danscrypt(5). Le param

ètre

setting contrôle la méthode de hachage à utiliser et fournit également divers paramètres à la méthode choisie, le plus important étant un « sel » aléatoire qui garantit qu'aucun hachage stocké n'est identique à un autre, même si les chaînes phrase sont

identiques.

L'argument data de crypt_r est une structure de type struct crypt_data. Elle contient au moins ces champs

: 
struct crypt_data {
    char output[CRYPT_OUTPUT_SIZE];
    char setting[CRYPT_OUTPUT_SIZE];
    char input[CRYPT_MAX_PASSPHRASE_SIZE];
    char initialized;
}
;

Après un retour réussi de crypt_r, la phrase secrète hachée sera stockée dans output. Les applications sont encouragées, mais pas obligées, d'utiliser les champs input et setting pour stocker les chaînes qu'elles passeront en tant que phrase d'entrée et paramètre à crypt_r. Cela facilitera l'effacement de toutes les données sensibles lorsqu'elles ne seront plus

nécessaires.

Le champ initialized doit être défini à zéro avant la première fois où un objet struct crypt_data est utilisé dans un appel à crypt_r(). Nous recommandons de mettre l'ensemble de l'objet à zéro, et pas seulement initialized et pas seulement les champs documentés, avant la première utilisation. (Bien sûr, faites-le avant de stocker quoi que ce soit dans setting et input

.)

L'argument data de crypt_rn doit également pointer vers un objet struct crypt_data, et size doit être la taille de cet objet, convertie en int. Lorsqu'il est utilisé avec crypt_rn, l'ensemble de l'objet data (à l'exception des champs input et setting) doit être mis à zéro avant sa première utilisation ; ce n'est pas seulement une recommandation, comme pour crypt_r. Sinon, les champs de l'objet ont les mêmes usages que pour crypt_r

.

Lors du premier appel à crypt_ra, data doit être l'adresse d'une variable void * initialisée à NULL, et size doit être l'adresse d'une variable int initialisée à zéro. crypt_ra allouera et initialisera un objet struct crypt_data, en utilisant malloc(3), et écrira son adresse et sa taille dans les variables pointées par data et size. Celles-ci peuvent être réutilisées lors d'appels ultérieurs. Une fois que l'application a terminé le hachage des phrases secrètes, elle doit désallouer l'objet struct crypt_data en utilisant free

(3
).

VALEURS DE

RETOUR

En cas de réussite, crypt, crypt_r, crypt_rn et crypt_ra renvoient un pointeur vers une chaîne qui encode à la fois la phrase secrète hachée et les paramètres utilisés pour l'encoder. Cette chaîne est directement utilisable comme setting dans d'autres appels à crypt, crypt_r, crypt_rn et crypt_ra, et comme préfixe dans les appels à crypt_gensalt, crypt_gensalt_rn et crypt_gensalt_ra. Elle sera entièrement en ASCII imprimable et ne contiendra ni espaces ni les caractères «: », «; », «* », «! » ou «\ ». Voir crypt(5) pour plus de détails sur le format des phrases secrètes

hachées.

crypt place son résultat dans une zone de stockage statique, qui sera écrasée par les appels ultérieurs à crypt. Il n'est pas sûr d'appeler crypt depuis plusieurs threads simultanément. Il n'est pas non plus recommandé d'utiliser le pointeur renvoyé comme argument pour un autre appel à crypt, car certaines implémentations, y compris les versions antérieures de libxcrypt, peuvent écraser le tampon de sortie statique sous-jacent avant de calculer le

hachage.

crypt_r, crypt_rn et crypt_ra placent leur résultat dans le champ output de leur argument data. Il est sûr de les appeler depuis plusieurs threads simultanément, à condition qu'un objet data distinct soit utilisé pour chaque thread. Il n'est pas non plus recommandé d'utiliser le pointeur renvoyé comme argument pour un autre appel à crypt_r, crypt_rn et crypt_ra en utilisant le même data pour les appels ultérieurs, car certaines implémentations, y compris les versions antérieures de libxcrypt, peuvent écraser le champ output de l'argument data passé avant de calculer le hachage. Appeler crypt_ra avec les paramètres phrase et/ou setting situés dans un objet data passé qui est plus petit que la taille de struct crypt_data n'est pas recommandé, car certaines implémentations, y compris les versions antérieures de libxcrypt, peuvent ne pas préserver les littéraux passés, si l'objet data doit être

modifié.

En cas d'erreur, crypt_r, crypt_rn et crypt_ra écrivent un hachage invalide dans le champ output de leur argument data, et crypt écrit un hachage invalide dans sa zone de stockage statique. Cette chaîne sera plus courte que 13 caractères, commencera par un «* » et ne sera pas égale à setting

.

En cas d'erreur, crypt_rn et crypt_ra renvoient un pointeur nul. crypt_r et crypt peuvent également renvoyer un pointeur nul, ou renvoyer un pointeur vers l'hachage invalide, selon la configuration de libcrypt. NAME

crypt, crypt_r, crypt_rn, crypt_ra — password hashing

LIBRARY

libcrypt

SYNOPSIS

#include <crypt.h>

char *crypt(const char *key, const char *salt);

intcrypt_r(const char *key, const char *salt, char *buffer);

intcrypt_rn(const char *key, const char *setting, char *buffer, size_t size);

intcrypt_ra(const char *key, const char *setting, char **buffer, size_t *size);

DESCRIPTION

The crypt family of functions compute a cryptographic hash of a password. The hash is based on the string key (the password) and a salt value. The result is intended to be stored in the password database.

The crypt function is the traditional interface. It takes a password key and a salt string salt. The salt string typically consists of a method identifier followed by a salt value, e.g., "$6$rounds=4096$Somesaltstring$somehash". If salt begins with a '$', it indicates a specific hashing method. If it does not begin with '$', the DES-based method is assumed. The function returns a pointer to a static buffer containing the hashed password.

The crypt_r function is the reentrant version of crypt. It takes the password key, the salt string salt, and a pointer to a buffer buffer in which the hashed password will be stored. It returns 0 on success, and -1 on error.

The crypt_rn function is a more flexible interface. It takes the password key, a setting string, a buffer buffer where the hashed password is to be stored, and the maximum size of the buffer. The setting string specifies the hashing method and any parameters, e.g., "$6$rounds=4096$". It is recommended to use the salt generated by crypt_gensalt(3) as the setting string.

The crypt_ra function is similar to crypt_rn, but it allocates the buffer dynamically. It takes the password key, the setting string, and pointers to a buffer pointer buffer and a size variable size. The function allocates memory for the hash result using malloc(3), stores the pointer to it in buffer, and stores the size of the allocated buffer in size. The caller is responsible for freeing the allocated memory using free(3).

All four functions may use a salt string that also specifies the hashing method to use. For example, the salt string "$6$rounds=4096$Somesaltstring$" specifies that the SHA-512 crypt hashing method should be used, with 4096 rounds, and "Somesaltstring" as the salt. If the salt string does not start with '$', the traditional DES crypt method is used, and the first two characters of the salt are used as the salt value.

The crypt function returns a pointer to a static buffer. This buffer is not thread-safe and may be overwritten by subsequent calls to crypt in the same thread or other threads. For thread-safe operations, use crypt_r, crypt_rn, or crypt_ra.

All four functions compute the hash based on the provided password and salt. The output is a string that represents the hashed password. The exact format of the output string depends on the hashing method used.

(Compatibility note: Old applications may assume that crypt cannot return a null pointer. This implementation may return a null pointer on error in some cases, although it generally sets errno and returns an invalid hash. Be aware of potential incompatibilcrypt cannot return a null pointer. See PORTABILITY NOTES below.)

All four functions set errno when they fail. When the functions succeed, the value of errno is unspecified and must not be relied upon.

ERRORS

EINVAL
setting is invalid, or requests a hashing method that is not supported.
ERANGE
phrase is too long (more than CRYPT_MAX_PASSPHRASE_SIZE characters; some hashing methods may have lower limits).
crypt_rn only: size is too small for the hashing method requested by setting.
ENOMEM
Failed to allocate internal scratch memory.
crypt_ra only: failed to allocate memory for data.
ENOSYS or EOPNOTSUPP
Hashing passphrases is not supported at all on this installation, or the hashing method requested by setting is not supported. These error codes are not used by this version of libcrypt, but may be encountered on other systems.

PORTABILITY NOTES

crypt is included in POSIX, but crypt_r, crypt_rn, and crypt_ra are not part of any standard.

POSIX does not specify any hashing methods, and does not require hashed passphrases to be portable between systems. In practice, hashed passphrases are portable as long as both systems support the hashing method that was used. However, the set of supported hashing methods varies considerably from system to system.

The behavior of crypt on errors isn't well standardized. Some implementations simply can't fail (except by crashing the program), others return a null pointer or a fixed string. Most implementations don't set errno, but some do. POSIX specifies returning a null pointer and setting errno, but it defines only one possible error, ENOSYS, in the case where crypt is not supported at all. Some older applications are not prepared to handle null pointers returned by crypt. The behavior described above for this implementation, setting errno and returning an invalid hash different from setting, is chosen to make these applications fail closed when an error occurs.

Due to historical restrictions on the export of cryptographic software from the USA, crypt is an optional POSIX component. Applications should therefore be prepared for crypt not to be available, or to always fail (setting errno to ENOSYS) at runtime.

POSIX specifies that crypt is declared in <unistd.h>, but only if the macro _XOPEN_CRYPT is defined and has a value greater than or equal to zero. Since libcrypt does not provide <unistd.h>, it declares crypt, crypt_r, crypt_rn, and crypt_ra in <crypt.h> instead.

On a minority of systems (notably recent versions of Solaris), crypt uses a thread-specific static storage buffer, which makes it safe to call from multiple threads simultaneously, but does not prevent each call within a thread from overwriting the results of the previous one.

BUGS

Some implementations of crypt, upon error, return an invalid hash that is stored in a read-only location or only initialized once, which means that it is only safe to erase the buffer pointed to by the crypt return value if an error did not occur.

struct crypt_data may be quite large (32kB in this implementation of libcrypt; over 128kB in some other implementations). This is large enough that it may be unwise to allocate it on the stack.

Some recently designed hashing methods need even more scratch memory, but the crypt_r interface makes it impossible to change the size of struct crypt_data without breaking binary compatibility. The crypt_rn interface could accommodate larger allocations for specific hashing methods, but the caller of crypt_rn has no way of knowing how much memory to allocate. crypt_ra does the allocation itself, but can only make a single call to malloc(3).

HISTORY

A rotor-based crypt function appeared in Version 6 AT&T UNIX. The “traditional” DES-based crypt first appeared in Version 7 AT&T UNIX.

crypt_r originates with the GNU C Library. There's also a crypt_r function on HP-UX and MKS Toolkit, but the prototypes and semantics differ.

crypt_rn and crypt_ra originate with the Openwall project.
