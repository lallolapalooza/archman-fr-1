DESCRIPTIO

N

CREATE DOMAIN crée un nouveau domaine. Un domaine est essentiellement un type de données avec des contraintes facultatives (restrictions sur l'ensemble des valeurs autorisées). L'utilisateur qui définit un domaine en devient le

propriétaire.

Si un nom de schéma est donné (par exemple, CREATE DOMAIN myschema.mydomain ...), le domaine est créé dans le schéma spécifié. Sinon, il est créé dans le schéma courant. Le nom du domaine doit être unique parmi les types et domaines existant dans son

schéma.

Les domaines sont utiles pour abstraire les contraintes courantes sur les champs dans un emplacement unique afin de faciliter la maintenance. Par exemple, plusieurs tables peuvent contenir des colonnes d'adresse courriel, toutes nécessitant la même contrainte CHECK pour vérifier la syntaxe de l'adresse. Définissez un domaine plutôt que de configurer la contrainte de chaque table individuellement

.

Pour pouvoir créer un domaine, v

ous devez avoir le privilège US
AGE sur le type sous-jacent.

data_typ

Une collation facultative pour le domaine. Si aucune collation n'est spécifiée, le domaine a le même comportement de collation que son type de données sous-jacent. Le type sous-jacent doit être triable si COLLATE est
spécifié.

DEFAULT expressio

n
La clause DEFAULT spécifie une valeur par défaut pour les colonnes du type de données du domaine. La valeur est toute expression sans variable (mais les sous-requêtes ne sont pas autorisées). Le type de données de l'expression par défaut doit correspondre au type de données du domaine. Si aucune valeur par défaut n'est spécifiée, la valeur par défaut est la valeur nulle.

L'expression par défaut sera utilisée dans toute opération d'insertion qui ne spécifie pas de valeur pour la colonne. Si un

e valeur par défaut est définie pour une colonne particulière, elle remplace toute valeur par défaut associée au domaine
. À son tour, la valeur par défaut du domaine remplace toute valeur par défaut associée au type de données sous-jacent.

nom.

CHECK (expression

)
Les clauses CHECK spécifient des contraintes d'intégrité ou des tests que les valeurs du domaine doivent satisfaire. Chaque contrainte doit être une expression produisant un résultat booléen. Elle doit utiliser le mot clé VALUE pour faire référence à la valeur testée. Les expressions s'évaluant à TRUE ou UNKNOWN réussissent. Si l'expression produit un résultat FALSE, une erreur est signalée et la valeur ne peut pas être convertie en le type du domaine.

Actuellement, les expressions CHECK ne peuvent pas contenir de sous-requêtes ni faire référence à des variables autres que

VALUE.

Lorsqu'un domaine a plusieurs contraintes CHECK, elles seront

testées dans l'ordre alphabétique par nom. (Les versions d
e PostgreSQL antérieures à 9.5 ne respectaient aucun ordre
de déclenchement particulier pour les contraintes CHECK.)

NOTE

S

Les contraintes de domaine, en particulier NOT NULL, sont vérifiées lors de la conversion d'une valeur en le type du domaine. Il est possible qu'une colonne qui est nominativement de type domaine lise comme nulle malgré l'existence d'une telle contrainte. Par exemple, cela peut se produire dans une requête de jointure externe, si la colonne du domaine se trouve côté nullable de la jointure externe. Un exemple plus subtil

est 
INSERT INTO tab (domcol) VALUES ((SELECT domcol FROM tab WHERE false)
)
;

Le sous-SELECT scalaire vide produira une valeur nulle qui est considérée comme étant de type domaine, donc aucune vérification de contrainte supplémentaire ne lui est appliquée, et l'insertion

réussira.

Il est très difficile d'éviter ces problèmes, en raison de l'hypothèse générale du SQL selon laquelle une valeur nulle est une valeur valide pour chaque type de données. La meilleure pratique consiste donc à concevoir les contraintes d'un domaine de manière à autoriser une valeur nulle, puis à appliquer des contraintes NOT NULL aux colonnes de type domaine au besoin, plutôt que directement au type du

domaine.

PostgreSQL suppose que les conditions des contraintes CHECK sont immuables, c'est-à-dire qu'elles donneront toujours le même résultat pour la même valeur d'entrée. Cette hypothèse justifie le fait d'examiner les contraintes CHECK uniquement lorsqu'une valeur est convertie pour la première fois en un type de domaine, et pas à d'autres moments. (C'est essentiellement la même chose que le traitement des contraintes CHECK de table, comme décrit dans la section 5.5.1.

)

Un exemple courant de violation de cette hypothèse consiste à référencer une fonction définie par l'utilisateur dans une expression CHECK, puis à changer le comportement de cette fonction. PostgreSQL n'interdit pas cela, mais il ne remarquera pas s'il existe des valeurs stockées de type domaine qui violent désormais la contrainte CHECK. Cela provoquerait l'échec d'une sauvegarde et d'une restauration ultérieures de la base de données. La manière recommandée de gérer un tel changement est de supprimer la contrainte (à l'aide de ALTER DOMAIN), d'ajuster la définition de la fonction, puis de réajouter la contrainte, la revérifiant ainsi par rapport aux données

stockées.

C'est également une bonne pratique de s'

assurer que les expressions CHECK d
e domaine ne provoqueront pas d'erreurs.
