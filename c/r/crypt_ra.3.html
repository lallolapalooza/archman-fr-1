CRYPT(3) Manuel des fonctions de bibliothèque CRYPT(3)

NOM

crypt, crypt_r, crypt_rn, crypt_ra — hachage de phrases de passe

BIBLIOTHÈQUE

Bibliothèque Crypt (libcrypt, -lcrypt)

SYNOPSIS

#include <crypt.h>

char *
crypt(const char *phrase, const char *setting);

char *
crypt_r(const char *phrase, const char *setting, struct crypt_data *data);

char *
crypt_rn(const char *phrase, const char *setting, struct crypt_data *data, int size);

char *
crypt_ra(const char *phrase, const char *setting, void **data, int *size);

DESCRIPTION

Les fonctions crypt, crypt_r, crypt_rnet crypt_ra « hachent » de manière irréversible la phrase pour son stockage dans la base de données de mots de passe du système (shadow(5)) en utilisant une « méthode de hachage » cryptographique. Le résultat de cette opération est appelé une « phrase de passe hachée » ou simplement un « hachage ». Les méthodes de hachage sont décrites dans crypt(5).

setting contrôle la méthode de hachage à utiliser et fournit également divers paramètres à la méthode choisie, le plus important étant un « sel » aléatoire qui garantit qu'aucun des hachages stockés n'est identique, même si les chaînes phrase sont identiques.

L'argument data de crypt_r est une structure de type struct crypt_data. Elle contient au moins les champs suivants :

struct crypt_data {
    char output[CRYPT_OUTPUT_SIZE];
    char setting[CRYPT_OUTPUT_SIZE];
    char input[CRYPT_MAX_PASSPHRASE_SIZE];
    char initialized;
};

Après un retour réussi de crypt_r, la phrase de passe hachée sera stockée dans output. Il est recommandé, mais non obligatoire, que les applications utilisent les champs input et setting pour stocker les chaînes qu'elles passeront en tant que phrase d'entrée et paramètre de configuration à crypt_r. Cela facilitera l'effacement de toutes les données sensibles lorsqu'elles ne seront plus nécessaires.

Le champ initialized doit être défini à zéro avant la première utilisation d'un objet struct crypt_data dans un appel à crypt_r(). Nous recommandons de mettre l'objet entier à zéro, et pas seulement initialized ni seulement les champs documentés, avant la première utilisation. (Bien sûr, faites-le avant de stocker quoi que ce soit dans setting et input.)

L'argument data de crypt_rn doit également pointer vers un objet struct crypt_data , et size doit être la taille de cet objet, convertie en int. Lorsqu'il est utilisé avec crypt_rn, l'objet data entier (à l'exception des champs input et setting ) doit être mis à zéro avant sa première utilisation ; il ne s'agit pas seulement d'une recommandation, comme pour crypt_r. Sinon, les champs de l'objet ont les mêmes usages que pour crypt_r.

Lors du premier appel à crypt_ra, data doit être l'adresse d'une variable void * initialisée à NULL, et size doit être l'adresse d'une variable int initialisée à zéro. crypt_ra allouera et initialisera un objet struct crypt_data en utilisant malloc(3), et écrira son adresse et sa taille dans les variables pointées par data et size. Celles-ci peuvent être réutilisées lors d'appels ultérieurs. Lorsque l'application a terminé le hachage des phrases de passe, elle doit désallouer l'objet struct crypt_data en utilisant free(3).

VALEURS RENVOYÉES

En cas de réussite, crypt, crypt_r, crypt_rnet crypt_ra renvoient un pointeur vers une chaîne qui encode à la fois la phrase de passe hachée et les paramètres utilisés pour l'encoder. Cette chaîne peut être utilisée directement comme setting dans d'autres appels à crypt, crypt_r, crypt_rnet crypt_ra, et comme prefix dans les appels à crypt_gensalt, crypt_gensalt_rnet crypt_gensalt_ra. Elle sera entièrement en ASCII imprimable et ne contiendra ni espaces ni les caractères «:», «;», «*», «!» ou «\». Voir crypt(5) pour plus de détails sur le format des phrases de passe hachées.

crypt place son résultat dans une zone de stockage statique, qui sera écrasée par les appels ultérieurs à crypt. Il n'est pas sûr d'appeler crypt depuis plusieurs threads simultanément. Il n'est pas non plus recommandé d'utiliser le pointeur renvoyé comme argument pour un autre appel à crypt, car certaines implémentations, y compris les versions antérieures de libxcrypt, peuvent écraser le tampon de sortie statique sous-jacent avant de calculer le hachage.

crypt_r, crypt_rnet crypt_ra placent leur résultat dans le champ output de leur argument data . Il est sûr de les appeler depuis plusieurs threads simultanément, à condition d'utiliser un objet data distinct pour chaque thread. Il n'est pas non plus recommandé d'utiliser le pointeur renvoyé comme argument pour un autre appel à crypt_r, crypt_rnet crypt_ra en utilisant le même objet data pour les appels ultérieurs, car certaines implémentations, y compris les versions antérieures de libxcrypt, peuvent écraser le champ output de l'argument data passé avant de calculer le hachage. Il n'est pas recommandé d'appeler crypt_ra avec les paramètres phrase et/ou setting situés à l'intérieur d'un objet data passé dont la taille est inférieure à celle de struct crypt_data , car certaines implémentations, y compris les versions antérieures de libxcrypt, peuvent ne pas préserver les littéraux passés si l'objet data doit être modifié.

En cas d'erreur, crypt_r, crypt_rnet crypt_ra écrivent un hachage invalide dans le champ output de leur argument data , et crypt écrit un hachage invalide dans sa zone de stockage statique. Cette chaîne sera plus courte que 13 caractères, commencera par «*» et ne sera pas égale à setting.

En cas d'erreur, crypt_rn et crypt_ra renvoient un pointeur nul. crypt_r et crypt peuvent également renvoyer un pointeur nul, ou renvoyer un pointeur vers le hachage invalide, selon la configuration de libcrypt. (L'option de renvoyer le hachage invalide est pour la compatibilitity with old applications that assume that crypt cannot return a null pointer. See PORTABILITY NOTES below.)

All four functions set errno when they fail. When the functions succeed, the value of errno is unspecified and must not be relied upon.

ERREURS

EINVAL
setting est invalide, ou demande une méthode de hachage qui n'est pas prise en charge.
ERANGE
phrase est trop longue (plus de CRYPT_MAX_PASSPHRASE_SIZE caractères ; certaines méthodes de hachage peuvent avoir des limites inférieures).
crypt_rn uniquement : size est trop petit pour la méthode de hachage demandée par setting.
ENOMEM
Échec de l'allocation de la mémoire de travail interne.
crypt_ra uniquement : échec de l'allocation de la mémoire pour data.
ENOSYS ou EOPNOTSUPP
Le hachage des phrases de passe n'est pas du tout pris en charge sur cette installation, ou la méthode de hachage demandée par setting n'est pas prise en charge. Ces codes d'erreur ne sont pas utilisés par cette version de libcrypt, mais peuvent être rencontrés sur d'autres systèmes.

NOTES DE PORTABILITÉ

crypt est inclus dans POSIX, mais crypt_r, crypt_rn, et crypt_ra ne font partie d'aucun standard.

POSIX ne spécifie aucune méthode de hachage et ne requiert pas que les phrases de passe hachées soient portables entre les systèmes. En pratique, les phrases de passe hachées sont portables tant que les deux systèmes prennent en charge la méthode de hachage utilisée. Cependant, l'ensemble des méthodes de hachage prises en charge varie considérablement d'un système à l'autre.

Le comportement de crypt en cas d'erreur n'est pas bien standardisé. Certaines implémentations ne peuvent tout simplement pas échouer (sauf en faisant planter le programme), d'autres retournent un pointeur nul ou une chaîne fixe. La plupart des implémentations ne définissent pas errno, mais certaines le font. POSIX spécifie de retourner un pointeur nul et de définir errno, mais il ne définit qu'une seule erreur possible, ENOSYS, dans le cas où crypt n'est pas du tout pris en charge. Certaines anciennes applications ne sont pas préparées à gérer les pointeurs nuls retournés par crypt. Le comportement décrit ci-dessus pour cette implémentation, définir errno et retourner un hachage invalide différent de setting, est choisi pour faire échouer ces applications en mode sûr (fail closed) lorsqu'une erreur se produit.

En raison de restrictions historiques sur l'exportation de logiciels cryptographiques depuis les États-Unis, crypt est un composant POSIX optionnel. Les applications doivent donc être préparées pour le cas où crypt ne serait pas disponible, ou échouerait toujours (en définissant errno à ENOSYS) à l'exécution.

POSIX spécifie que crypt est déclaré dans <unistd.h>, mais seulement si la macro _XOPEN_CRYPT est définie et a une valeur supérieure ou égale à zéro. Puisque libcrypt ne fournit pas <unistd.h>, il déclare crypt, crypt_r, crypt_rn, et crypt_ra dans <crypt.h> à la place.

Sur une minorité de systèmes (notamment les versions récentes de Solaris), crypt utilise un tampon de stockage statique spécifique au thread, ce qui le rend sûr à appeler depuis plusieurs threads simultanément, mais n'empêche pas chaque appel au sein d'un thread d'écraser les résultats du précédent.

BUGS

Certaines implémentations de crypt, en cas d'erreur, retournent un hachage invalide stocké dans un emplacement en lecture seule ou seulement initialisé une fois, ce qui signifie qu'il n'est sûr d'effacer le tampon pointé par la crypt valeur de retour que si une erreur ne s'est pas produite.

struct crypt_data peut être assez grand (32kB dans cette implémentation de libcrypt ; plus de 128kB dans certaines autres implémentations). C'est assez grand pour qu'il puisse être imprudent de l'allouer sur la pile.

Certaines méthodes de hachage conçues récemment ont besoin de encore plus de mémoire de travail, mais l' crypt_r interface rend impossible de changer la taille de struct crypt_data sans casser la compatibilité binaire. L' crypt_rn interface pourrait accommoder des allocations plus grandes pour des méthodes de hachage spécifiques, mais l'appelant de crypt_rn n'a aucun moyen de savoir combien de mémoire allouer. crypt_ra fait l'allocation lui-même, mais ne peut faire qu'un seul appel à malloc(3).

ATTRIBUTS

HISTORIQUE

Une fonction crypt basée sur un rotor est apparue dans Version 6 AT&T UNIX. La fonction crypt « traditionnelle » basée sur DES est apparue pour la première fois dans Version 7 AT&T UNIX.

crypt_r provient de la GNU C Library. Il existe aussi une fonction crypt_r sur HP-UX et MKS Toolkit, mais les prototypes et la sémantique diffèrent.

crypt_rn et crypt_ra proviennent du projet Openwall.
