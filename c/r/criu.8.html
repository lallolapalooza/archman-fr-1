criu - point de contrôle/restauration en espace

utilisateur



SYNOPSI

S

DESCRIPTIO

N

criu est un outil pour la prise de points de contrôle et la restauration d'applications en cours d'exécution. Il le fait en enregistrant leur état sous forme d'une collection de fichiers (voir la commande dump) et en créant des processus équivalents à partir de ces fichiers (voir la commande restore). L'opération de restauration peut être effectuée ultérieurement, sur un système différent, ou les

deux.

--external type[id]:valeu

r
Dumper une instance d'une ressource externe. La syntaxe générique est type de ressource, suivi de l' id de la ressource (encadré par desuare brackets), and optional value (prepended by a literal colon). The following resource types are currently supported: mnt, dev, file, tty, unix. Syntax depends on type. Note to restore external resources, either --external or --inherit-fd is used, depending on resource
type.

--external mnt[mountpoint]:nam

e
Dump an external bind mount referenced by mountpoint, saving it to image under the identifier name

--external mnt[]:flag

s
Dump all external bind mounts, autodetecting those. Optional flags can contain m to also dump external master mounts, s to also dump external shared mounts (default behavior is to abort dumping if such mounts are found). If flags are not provided, colon is
optional.

--external dev[major/minor]:nam

e
Allow to dump a mount namespace having a real block device mounted. A block device is identified by its major and minor numbers, and criu saves its information to image under the identifier name

--external file[mnt_id:inode

Dump an external file, i.e. an opened file that is can not be resolved from the current mount namespace, which can not be dumped without using this option. The file is identified by mnt_id (a field obtained from /proc/pid/fdinfo/N) and inode (as returned by stat(2))

Dump an external TTY, identified by st_rdev and st_dev fields returned by stat(

--external unix[id

Tell criu that one end of a pair of UNIX sockets (created by socketpair(2)) with the given id is OK to be

--external net[inode]:nam

e
Mark a network namespace as external and do not include it in the checkpoint. The label name can be used with --inherit-fd during restore to specify a file descriptor to a preconfigured network

--cgroup-props spe

c
Specify controllers and their properties to be saved into the image file. criu predefines specifications for common controllers, but since the kernel can add new controllers and modify their properties, there should be a way to specify ones matched the kernel.

spec argument describes the controller and properties specification in a simplified YAML

form: 
"c1":
 - "strategy": "merge"
 - "prope
rties": ["a", "b"] "c2": - "strategy":
"replace" - "properties": ["c", "d"]

where c1 and c2 are controllers names, and a, b, c, d are their

properties.

Note the format: double quotes, spaces and new lines are required. The strategy specifies what to do if a controller specified already exists as a built-in one: criu can either merge or replace s

uch.

For example, the command line for the above example should look like

this: 
--cgroup-props "\"c1\":\n - \"strategy\"
: \"merge\"\n - \"properties\": [\"a\", \
"b\"]\n \"c2\":\n - \"strategy\": \"repla
ce\"\n - \"properties\": [\"c\", \"d\"]"

Instead of trying to mount cgroups in CRIU, provide a path to a directory with already created cgroup yard. Useful if you don’t want to grant CAP_SYS_ADMIN to CRIU. For every cgroup mount there should be exactly one directory. If there is only one controller in this mount, the dir’s name should be just the name of the controller. If there are multiple controllers comounted, the directory name should have them be separated by a comma.

--allow-uprobe

s
Autorise le dump lorsqu'un vma de uprobes est présent. Lorsqu'il est utilisé lors du dump, cette option est également requise lors du restore. 
Un vma de uprobes est automatiquement créé par le noyau une fois qu'un
  uprobe est déclenché. Ce mapping n'est pas supprimé même un
e fois que le uprobe est effacé. Ainsi, même si un processus avait des uprobes attachés et qu'ils ont été supprimés au moment où
le processus est dumpé, cette option est toujours requise car criu n'a aucun moyen de savoir s'il y a des uprobes actifs ou non. 
Lorsque vous utilisez cette option lors du restore, assurez-vous que
  les uprobes (s'il y en a) a
ctifs sur les processus dumpés sont toujours actifs. Sinon, lorsque l'exécution atteint un empl
acement avec un uprobe dans l'un des processus restaurés, un SIGTRAP sera envoyé à ce processus. 
À titre d'exemple, disons qu'un uprobe est défini sur la fonction foo
  dans l'exécutable du processus p_bar. Chaque fois que l'exécution dans
  p_bar atteint la
fonction foo, le uprobe est déclenché. Si le uprobe a été déclenché au moins une fois, le noyau aura créé le vma de uprobes. Pour dumper p_bar, cette option
est nécessaire. Après le dump, disons que le uprobe est supprimé. Maintenant, lors du restore avec cette option, une fois que l'exécution atteint la foncti
on foo, un SIGTRAP sera envoyé au p_bar restauré. Sauf s'il a un gestionnaire de signal installé pour SIGTRAP, il sera terminé et un core dump sera effectué.

FICHIERS DE

CONFIGURATION

Criu prend en charge l'utilisation de fichiers de configuration pour éviter la nécessité d'écrire chaque option sur la ligne de commande, ce qui est utile surtout avec une utilisation répétée des mêmes options. Un fichier de configuration spécifique peut être passé avec l'option "--config file". Si aucun fichier n'est passé, les fichiers de configuration par défaut /etc/criu/default.conf et $HOME/.criu/default.conf sont analysés (s'ils sont présents sur le système). Si la variable d'environnement CRIU_CONFIG_FILE est définie, elle sera également

analysée.

Les options passées à CRIU via CLI, RPC ou fichier de configuration sont évaluées dans l'ordre suivant

:
•apply_config(/etc/criu/default.
conf)
•apply_config($HOME/.criu/default.
conf)
•apply_config(CRIU_CONFIG_FILE
)
•apply_config(--config file
)
•apply_config(CLI) ou apply_config(RPC
)
•apply_config(fichier de configuration RPC) (uniquement pour le mode
RPC)

L'analyse du fichier de configuration par défaut peut être désactivée avec "--no-default-config" si nécessaire. Les fichiers de configuration analysés sont fusionnés avec les options de la ligne de commande, ce qui permet de remplacer les options

booléennes.



Syntaxe du fichier de

configuration

Les commentaires sont pris en charge en utilisant le signe '#'. Le reste de la ligne est ignoré. Les options sont les mêmes que les options de la ligne de commande sans le préfixe '--', utilisez une option par ligne (avec l'argument correspondant si applicable, séparés par des espaces). Si nécessaire, l'argument peut être fourni entre guillemets doubles (cela ne devrait être nécessaire que si l'argument contient des espaces). Si ce type d'argument contient également un guillemet double littéral, il peut être échappé en utilisant le signe '\'. L'utilisation de commandes est interdite et toutes les autres séquences d'échappement sont interprétées

littéralement.

Exemple de fichier de configuration pour illustrer la syntaxe

: 
$ cat ~/.criu/default.conf
tcp-established
work-dir "/
home/USERNAME/criu/my \"work\" directory" #this is a
comment no-restore-sibling # this is another comment



Configuration fichiers en mode

RPC

Non seulement criu évalue les fichiers de configuration en mode CLI, il évalue aussi les fichiers de configuration en mode RPC. Tout comme en mode CLI, les valeurs du fichier de configuration sont évaluées en premier. Cela signifie que toute option définie via RPC écrasera le paramètre du fichier de configuration. L'utilisateur peut ainsi modifier le comportement par défaut de criu mais il n'est pas possible de modifier les paramètres qui sont explicitement définis par le client

RPC.

Le client RPC peut cependant spécifier un fichier de configuration supplémentaire qui sera évalué après les options RPC (voir ci-dessus pour l'ordre d'évaluation des options). Le client RPC peut spécifier ce fichier de configuration supplémentaire via "req.opts.config_file = /path/to/file". Les valeurs issues de ce fichier de configuration écraseront tous les autres paramètres de fichier de configuration ou options RPC. Cela peut entraîner un comportement indésirable de criu et ne doit être utilisé qu'avec

prudence.



NON-ROO

T

criu peut être utilisé en tant que non-root avec soit la capacité CAP_SYS_ADMIN soit la capacité CAP_CHECKPOINT_RESTORE introduite dans le noyau Linux 5.9. CAP_CHECKPOINT_RESTORE est le minimum

requis.

criu a également besoin soit de CAP_SYS_PTRACE soit d'une valeur de 0 dans /proc/sys/kernel/yama/ptrace_scope (voir ptrace(2)) pour pouvoir interrompre le processus pour le

dump.

Exécuter criu en tant que non-root comporte de nombreuses limitations et selon le processus à checkpointer et restaurer, cela peut ne pas être

possible.

En plus de CAP_CHECKPOINT_RESTORE, il est possible de donner criu des capacités supplémentaires pour activer des fonctionnalités supplémentaires en mode

non-root.

Actuellement criu peut bénéficier des capacités supplémentaires suivantes

:
•CAP_NET_ADMI
N
•CAP_SYS_CHROO
T
•CAP_SETUI
D
•CAP_SYS_RESOURC
E

Notez que pour certaines opérations, disposer d'une capacité dans un namespace autre que le namespace init (c'est-à-dire le namespace par défaut/root) n'est pas suffisant. Par exemple, pour lire les liens symboliques dans proc/[pid]/map_files CRIU nécessite CAP_CHECKPOINT_RESTORE dans le namespace init ; disposer de CAP_CHECKPOINT_RESTORE tout en s'exécutant dans un autre user namespace (par ex. dans un conteneur) ne permet pas à CRIU de lire les liens symboliques dans /proc/[pid]

/map_files.

Sans accès à /proc/[pid]/map_files, le checkpoint/restore de processus ayant mappé des fichiers supprimés peut ne pas être

possible.

Indépendamment des capacités, il est toujours nécessaire d'utiliser "--unprivileged" pour accepter les limitations de criu en mode

non-root.
