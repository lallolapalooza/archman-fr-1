Paquet: postgresql

CREATE RULE(7) Documentation PostgreSQL 18.1 CREATE RULE(7)

NOM

CREATE_RULE - définit une nouvelle règle de réécriture

SYNOPSIS

CREATE [ OR REPLACE ] RULE nom AS ON événement
    TO nom_table [ WHERE condition ]
    DO [ ALSO | INSTEAD ] { NOTHING | commande | ( commande ; commande ... ) }
où événement peut être l'un des suivants :
    SELECT | INSERT | UPDATE | DELETE

DESCRIPTION

CREATE RULE définit une nouvelle règle s'appliquant à une table ou vue spécifiée. CREATE OR REPLACE RULE crée soit une nouvelle règle, soit remplace une règle existante portant le même nom pour la même table.

Le système de règles de PostgreSQL permet de définir une action alternative à effectuer lors des insertions, mises à jour ou suppressions dans les tables de la base de données. En gros, une règle provoque l'exécution de commandes supplémentaires lorsqu'une commande donnée sur une table donnée est exécutée. Alternativement, une règle INSTEAD peut remplacer une commande donnée par une autre, ou empêcher qu'une commande ne soit exécutée du tout. Les règles servent aussi à implémenter les vues SQL. Il est important de comprendre qu'une règle est en réalité un mécanisme de transformation de commande, ou macro-commande. La transformation se produit avant que l'exécution de la commande ne commence. Si vous voulez réellement une opération qui se déclenche indépendamment pour chaque ligne physique, vous voulez probablement utiliser un déclencheur (trigger) plutôt qu'une règle. Plus d'informations sur le système de règles se trouvent au chapitre 39.

Actuellement, les règles ON SELECT ne peuvent être attachées qu'aux vues. Une telle règle doit être nommée "_RETURN", doit être une règle INSTEAD inconditionnelle, et doit avoir une action qui consiste en une seule commande SELECT . Cette commande définit le contenu visible de la vue. (La vue elle-même est essentiellement une table factice sans stockage.) Il vaut mieux considérer une telle règle comme un détail d'implémentation. Bien qu'une vue puisse être redéfinie via CREATE OR REPLACE RULE "_RETURN" AS ..., il est de meilleur style d'utiliser CREATE OR REPLACE VIEW.

Vous pouvez créer l'illusion d'une vue modifiable en définissant des règles ON INSERT, ON UPDATE et ON DELETE (ou tout sous-ensemble de celles- ci suffisant pour vos besoins) pour remplacer les actions de mise à jour sur la vue par des mises à jour appropriées sur d'autres tables. Si vous voulez prendre en charge INSERT RETURNING et ainsi de suite, assurez-vous de placer une clause RETURNING appropriée dans chacune de ces règles.

Il y a un piège si vous essayez d'utiliser des règles conditionnelles pour des mises à jour de vues complexes : il doit y avoir une règle INSTEAD inconditionnelle pour chaque action que vous souhaitez autoriser sur la vue. Si la règle est conditionnelle, ou n'est pas INSTEAD, le système rejettera toujours les tentatives d'effectuer l'action de mise à jour, car il pense qu'il pourrait finir par essayer d'effectuer l'action sur la table factice de la vue dans certains cas. Si vous voulez gérer tous les cas utiles dans des règles conditionnelles, ajoutez une règle inconditionnelle DO INSTEAD NOTHING pour que le système comprenne qu'il ne sera jamais appelé à mettre à jour la table factice. Ensuite, rendez les règles conditionnelles non-INSTEAD ; dans les cas où elles s'appliquent, elles s'ajoutent à l'action par défaut INSTEAD NOTHING. (Cette méthode ne fonctionne actuellement pas pour prendre en charge les requêtes RETURNING, cependant.)


Note

Une vue suffisamment simple pour être automatiquement modifiable (voir CREATE VIEW (CREATE_VIEW(7))) ne nécessite pas de règle créée par l'utilisateur pour être modifiable. Bien que vous puissiez créer une règle explicite quand même, la transformation de mise à jour automatique sera généralement plus performante qu'une règle explicite.

Une autre alternative à considérer est d'utiliser des déclencheurs INSTEAD OF (voir CREATE TRIGGER (CREATE_TRIGGER(7))) à la place des règles.

PARAMÈTRES

nom

Le nom d'une règle à créer. Il doit être distinct du nom de toute autre règle pour la même table. Plusieurs règles sur la même table et le même type d'événement sont appliquées dans l'ordre alphabétique des noms.

événement

L'événement est l'un de SELECT, INSERT, UPDATE ou DELETE. Notez qu'un INSERT contenant une clause ON CONFLICT ne peut pas être utilisé sur des tables qui ont des règles INSERT ou UPDATE. Envisagez plutôt d'utiliser une vue modifiable.

nom_table

Le nom (éventuellement qualifié par un schéma) de la table ou de la vue à laquelle la règle s'applique.

condition

Toute expression conditionnelle SQL (renvoyant un booléen). L'expression de condition ne peut pas faire référence à des tables autres que NEW et OLD, et ne peut pas contenir de fonctions d'agrégation.

INSTEAD

INSTEAD indique que les commandes doivent être exécutées à la place de la commande originale.

ALSO

ALSO indique que les commandes doivent être exécutées en plus de la commande originale.

Si ni ALSO ni INSTEAD n'est spécifié, ALSO est la valeur par défaut.

commande

La ou les commandes qui composent l'action de la règle. Les commandes valides sont SELECT, INSERT, UPDATE, DELETE, ou NOTIFY.

Dans condition et commande, les noms de tables spéciaux NEW et OLD peuvent être utilisés pour faire référence aux valeurs dans la table référencée. NEW est valide dans les règles ON INSERT et ON UPDATE pour faire référence à la nouvelle ligne en cours d'insertion ou de mise à jour. OLD est valide dans les règles ON UPDATE et ON DELETE pour faire référence à la ligne existante en cours de mise à jour ou de suppression.

NOTES

Vous devez être le propriétaire d'une table pour créer ou modifier des règles pour celle-ci.

Dans une règle pour INSERT, UPDATE ou DELETE sur une vue, vous pouvez ajouter une clause RETURNING qui émet les colonnes de la vue. Cette clause sera utilisée pour calculer les sorties si la règle est déclenchée par une commande INSERT RETURNING, UPDATE RETURNING, ou DELETE RETURNING respectivement. Lorsque la règle est déclenchée par une commande sans RETURNING, la clause RETURNING de la règle sera ignorée. L'implémentation actuelle n'autorise que les règles INSTEAD inconditionnelles à contenir RETURNING ; de plus, il peut y avoir au plus une clause RETURNING parmi toutes les règles pour le même événement. (Cela garantit qu'il n'y a qu'une seule clause RETURNING candidate à utiliser pour calculer les résultats.) Les requêtes RETURNING sur la vue seront rejetées s'il n'y a pas de clause RETURNING dans aucune règle disponible.

Il est très important de veiller à éviter les règles circulaires. Par exemple, bien que chacune des deux définitions de règles suivantes soit acceptée par PostgreSQL, la commande SELECT ferait que PostgreSQL signalerait une erreur à cause de l'expansion récursive d'une règle :

CREATE RULE "_RETURN" AS
    ON SELECT TO t1
    DO INSTEAD
        SELECT * FROM t2;
CREATE RULE "_RETURN" AS
    ON SELECT TO t2
    DO INSTEAD
        SELECT * FROM t1;
SELECT * FROM t1;

Actuellement, si une action de règle contient une commande NOTIFY , la commande NOTIFY sera exécutée inconditionnellement, c'est-à-dire que le NOTIFY sera émis même s'il n'y a aucune ligne à laquelle la règle devrait s'appliquer. Par exemple, dans :

CREATE RULE notify_me AS ON UPDATE TO mytable DO ALSO NOTIFY mytable;
UPDATE mytable SET name = 'foo' WHERE id = 42;

un NOTIFY sera envoyé pendant le UPDATE, qu'il y ait ou non des lignes correspondant à la condition id = 42. Ceci est une restriction d'implémentation qui pourrait être corrigée dans de futures versions.

COMPATIBILITÉ

CREATE RULE est une extension du langage PostgreSQL, tout comme le système complet de réécriture des requêtes.

VOIR AUSSI

ALTER RULE (ALTER_RULE(7)), DROP RULE (DROP_RULE(7))
