CREATE TRIGGER(7) Documentation PostgreSQL 18.1 CREATE TRIGGER(7)

NOM

CREATE_TRIGGER - définit un nouveau déclencheur

SYNOPSIS

CREATE [ OR REPLACE ] [ CONSTRAINT ] TRIGGER nom { BEFORE | AFTER | INSTEAD OF } { événement [ OR ... ] }
    ON nom_table
    [ FROM nom_table_référencée ]
    [ NOT DEFERRABLE | [ DEFERRABLE ] [ INITIALLY IMMEDIATE | INITIALLY DEFERRED ] ]
    [ REFERENCING { { OLD | NEW } TABLE [ AS ] nom_relation_transition } [ ... ] ]
    [ FOR [ EACH ] { ROW | STATEMENT } ]
    [ WHEN ( condition ) ]
    EXECUTE { FUNCTION | PROCEDURE } nom_fonction ( arguments )
où événement peut être l'un des suivants :
    INSERT
    UPDATE [ OF nom_colonne [, ... ] ]
    DELETE
    TRUNCATE

DESCRIPTION

CREATE TRIGGER crée un nouveau déclencheur. CREATE OR REPLACE TRIGGER crée soit un nouveau déclencheur, soit remplace un déclencheur existant. Le déclencheur sera associé à la table, vue ou table étrangère spécifiée et exécutera la fonction spécifiée nom_fonction lorsque certaines opérations sont effectuées sur cette table.

Pour remplacer la définition actuelle d'un déclencheur existant, utilisez CREATE OR REPLACE TRIGGER, en spécifiant le nom du déclencheur existant et sa table parente. Toutes les autres propriétés sont remplacées.

Le déclencheur peut être spécifié pour se déclencher avant que l'opération ne soit tentée sur une ligne (avant la vérification des contraintes et avant que le INSERT, UPDATE, ou DELETE ne soit tenté) ; ou après que l'opération a été terminée (après la vérification des contraintes et après que le INSERT, UPDATE, ou DELETE a été terminé) ; ou à la place de l'opération (dans le cas des insertions, mises à jour ou suppressions sur une vue). Si le déclencheur se déclenche avant ou à la place de l'événement, le déclencheur peut ignorer l'opération pour la ligne en cours, ou modifier la ligne en cours d'insertion (pour les opérations INSERT et UPDATE uniquement). Si le déclencheur se déclenche après l'événement, toutes les modifications, y compris les effets des autres déclencheurs, sont « visibles » pour le déclencheur.

Un déclencheur marqué FOR EACH ROW est appelé une fois pour chaque ligne que l'opération modifie. Par exemple, un DELETE qui affecte 10 lignes entraînera l'appel de tous les déclencheurs ON DELETE sur la relation cible 10 fois séparément, une fois pour chaque ligne supprimée. En revanche, un déclencheur marqué FOR EACH STATEMENT ne s'exécute qu'une seule fois pour une opération donnée, peu importe le nombre de lignes qu'elle modifie (en particulier, une opération qui modifie zéro ligne entraînera toujours l'exécution de tous les déclencheurs FOR EACH STATEMENT applicables).

Les déclencheurs spécifiés pour se déclencher INSTEAD OF l'événement du déclencheur doivent être marqués FOR EACH ROW et ne peuvent être définis que sur des vues. Les déclencheurs BEFORE et AFTER sur une vue doivent être marqués FOR EACH STATEMENT.

De plus, des déclencheurs peuvent être définis pour se déclencher pour TRUNCATE, bien que uniquement FOR EACH STATEMENT.

Le tableau suivant résume les types de déclencheurs qui peuvent être utilisés sur les tables, les vues et les tables étrangères :

Quand Événement Niveau ligne Niveau instruction
BEFORE INSERT/UPDATE/DELETE Tables et tables étrangères Tables, vues et tables étrangères
TRUNCATE — Tables et tables étrangères
AFTER INSERT/UPDATE/DELETE Tables et tables étrangères Tables, vues et tables étrangères
TRUNCATE — Tables et tables étrangères
INSTEAD OF INSERT/UPDATE/DELETE Vues —
TRUNCATE — —

De plus, une définition de déclencheur peut spécifier une condition booléenne WHEN, qui sera testée pour déterminer si le déclencheur doit se déclencher. Dans les déclencheurs de niveau ligne, la condition WHEN peut examiner les anciennes et/ou les nouvelles valeurs des colonnes de la ligne. Les déclencheurs de niveau instruction peuvent également avoir des conditions WHEN, bien que cette fonctionnalité ne soit pas très utile pour eux puisque la condition ne peut faire référence à aucune valeur de la table.

Si plusieurs déclencheurs du même type sont définis pour le même événement, ils seront déclenchés dans l'ordre alphabétique par nom.

Lorsque l'option CONSTRAINT est spécifiée, cette commande crée un déclencheur de contrainte. C'est la même chose qu'un déclencheur régulier, sauf que le moment du déclenchement du déclencheur peut être ajusté à l'aide de SET CONSTRAINTS. Les déclencheurs de contrainte doivent être des déclencheurs AFTER ROW sur des tables ordinaires (pas des tables étrangères). Ils peuvent être déclenchés soit à la fin de l'instruction provoquant l'événement déclencheur, soit à la fin de la transaction contenant ; dans ce dernier cas, on dit qu'ils sont différés. Le déclenchement d'un déclencheur différé en attente peut aussi être forcé à se produire immédiatement à l'aide de SET CONSTRAINTS. Les déclencheurs de contrainte sont censés lever une exception lorsque les contraintes qu'ils implémentent sont violées.

L'option REFERENCING permet la collecte de relations de transition, qui sont des ensembles de lignes incluant toutes les lignes insérées, supprimées ou modifiées par l'instruction SQL en cours. Cette fonctionnalité permet au déclencheur de voir une vue globale de ce que l'instruction a fait, et pas seulement une ligne à la fois. Cette option n'est autorisée que pour un déclencheur AFTER sur une table ordinaire (pas une table étrangère). Le déclencheur ne doit pas être un déclencheur de contrainte. De plus, si le déclencheur est un déclencheur UPDATE, il ne doit pas spécifier une liste de nom_colonne lors de l'utilisation de cette option. OLD TABLE ne peut être spécifié qu'une seule fois, et seulement pour un déclencheur qui peut se déclencher sur UPDATE ou DELETE ; il crée une relation de transition contenant les images d'avant de toutes les lignes mises à jour ou supprimées par l'instruction. De même, NEW TABLE ne peut être spécifié qu'une seule fois, et seulement pour un déclencheur qui peut se déclencher sur UPDATE ou INSERT ; il crée une relation de transition contenant les images d'après de toutes les lignes mises à jour ou insérées par l'instruction.

SELECT ne modifie aucune ligne, vous ne pouvez donc pas créer de déclencheurs SELECT . Les règles et les vues peuvent fournir des solutions réalisables à des problèmes qui semblent nécessiter des déclencheurs SELECT .

Consultez le chapitre 37 pour plus d'informations sur les déclencheurs.

PARAMÈTRES

nom

Le nom à donner au nouveau déclencheur. Il doit être distinct du nom de tout autre déclencheur pour la même table. Le nom ne peut pas être qualifié par un schéma — le déclencheur hérite du schéma de sa table. Pour un déclencheur de contrainte, c'est aussi le nom à utiliser lors de la modification du comportement du déclencheur à l'aide de SET CONSTRAINTS.

BEFORE
AFTER
INSTEAD OF

Détermine si la fonction est appelée avant, après, ou à la place de l'événement. Un déclencheur de contrainte ne peut être spécifié que comme AFTER.

événement

L'un de INSERT, UPDATE, DELETE ou TRUNCATE ; cela spécifie l'événement qui déclenchera le déclencheur. Plusieurs événements peuvent être spécifiés en utilisant OR, sauf lorsque des relations de transition sont demandées.

Pour les événements UPDATE, il est possible de spécifier une liste de colonnes en utilisant cette syntaxe :

UPDATE OF nom_colonne1 [, nom_colonne2 ... ]

Le déclencheur ne se déclenchera que si au moins une des colonnes listées est mentionnée comme cible de la commande UPDATE ou si l'une des colonnes listées est une colonne générée qui dépend d'une colonne qui est la cible de la commande UPDATE.

Les événements INSTEAD OF UPDATE ne permettent pas une liste de colonnes. Une liste de colonnes ne peut pas non plus être spécifiée lors de la demande de relations de transition.

nom_table

Le nom (éventuellement qualifié par un schéma) de la table, vue ou table étrangère à laquelle le déclencheur est destiné.

nom_table_référencée

Le nom (éventuellement qualifié par un schéma) d'une autre table référencée par la contrainte. Cette option est utilisée pour les contraintes de clé étrangère et n'est pas recommandée pour un usage général. Elle ne peut être spécifiée que pour les déclencheurs de contrainte.

DEFERRABLE
NOT DEFERRABLETABLE
INITIALLY IMMEDIATE
INITIALLY DEFERRED

Le moment par défaut de déclenchement du trigger. Voir la documentation de CREATE TABLE (CREATE_TABLE(7)) pour les détails de ces options de contrainte. Cela ne peut être spécifié que pour les triggers de contrainte.

REFERENCING

Ce mot-clé est immédiatement suivi de la déclaration d'un ou deux noms de relation qui donnent accès aux relations de transition de la déclaration déclenchante.

OLD TABLE
NEW TABLE

Cette clause indique si le nom de relation suivant correspond à la relation de transition de l'image avant (before-image) ou à la relation de transition de l'image après (after-image).

transition_relation_name

Le nom (non qualifié) à utiliser dans le trigger pour cette relation de transition.

FOR EACH ROW
FOR EACH STATEMENT

Cela spécifie si la fonction trigger doit être exécutée une fois pour chaque ligne affectée par l'événement déclencheur, ou seulement une fois par instruction SQL. Si aucune des deux options n'est spécifiée, FOR EACH STATEMENT est la valeur par défaut. Les triggers de contrainte ne peuvent être spécifiés que FOR EACH ROW.

condition

Une expression booléenne qui détermine si la fonction trigger sera effectivement exécutée. Si WHEN est spécifié, la fonction ne sera appelée que si la condition renvoie true. Dans les triggers FOR EACH ROW, la condition WHEN peut faire référence aux colonnes des valeurs de ligne old et/ou new en écrivant OLD.column_name ou NEW.column_name respectivement. Bien entendu, les triggers INSERT ne peuvent pas faire référence à OLD et les triggers DELETE ne peuvent pas faire référence à NEW.

Les triggers INSTEAD OF ne prennent pas en charge les conditions WHEN.

Actuellement, les expressions WHEN ne peuvent pas contenir de sous-requêtes.

Notez que pour les triggers de contrainte, l'évaluation de la condition WHEN n'est pas différée, mais se produit immédiatement après que l'opération de mise à jour de la ligne a été effectuée. Si la condition n'évalue pas à true, le trigger n'est pas mis en file pour une exécution différée.

function_name

Une fonction fournie par l'utilisateur, déclarée comme ne prenant aucun argument et renvoyant le type trigger, qui est exécutée lorsque le trigger se déclenche.

Dans la syntaxe de CREATE TRIGGER, les mots-clés FUNCTION et PROCEDURE sont équivalents, mais la fonction référencée doit dans tous les cas être une fonction, et non une procédure. L'utilisation du mot-clé PROCEDURE ici est historique et déconseillée.

arguments

Une liste facultative d'arguments séparés par des virgules à fournir à la fonction lorsque le trigger est exécuté. Les arguments sont des constantes de chaîne littérales. Des noms simples et des constantes numériques peuvent aussi être écrits ici, mais ils seront tous convertis en chaînes. Veuillez vérifier la description du langage d'implémentation de la fonction trigger pour savoir comment ces arguments peuvent être accessibles dans la fonction ; cela peut être différent des arguments de fonction normaux.

NOTES

Pour créer ou remplacer un trigger sur une table, l'utilisateur doit avoir le privilège TRIGGER sur la table. L'utilisateur doit également avoir le privilège EXECUTE sur la fonction trigger.

Utilisez DROP TRIGGER pour supprimer un trigger.

La création d'un trigger au niveau des lignes sur une table partitionnée entraînera la création d'un trigger « clone » identique sur chacune de ses partitions existantes ; et toute partition créée ou attachée ultérieurement aura également un trigger identique. S'il existe déjà un trigger portant un nom en conflit sur une partition fille, une erreur se produit, sauf si CREATE OR REPLACE TRIGGER est utilisé, auquel cas ce trigger est remplacé par un trigger clone. Lorsqu'une partition est détachée de sa parente, ses triggers clones sont supprimés.

Un trigger spécifique à une colonne (un trigger défini à l'aide de la syntaxe UPDATE OF column_name ) se déclenchera lorsque l'une de ses colonnes est listée comme cible dans la liste SET de la commande UPDATE . Il est possible que la valeur d'une colonne change même si le trigger ne se déclenche pas, car les modifications apportées au contenu de la ligne par les triggers BEFORE UPDATE ne sont pas prises en compte. Inversement, une commande telle que UPDATE ... SET x = x ... déclenchera un trigger sur la colonne x, même si la valeur de la colonne n'a pas changé.

Dans un trigger BEFORE, la condition WHEN est évaluée juste avant que la fonction soit ou serait exécutée, donc l'utilisation de WHEN n'est pas matériellement différente du test de la même condition au début de la fonction trigger. Notez en particulier que la ligne NEW vue par la condition est la valeur actuelle, éventuellement modifiée par des triggers antérieurs. De plus, la condition WHEN d'un trigger BEFORE n'est pas autorisée à examiner les colonnes système de la ligne NEW (comme ctid), car celles-ci n'auront pas encore été définies.

Dans un trigger AFTER, la condition WHEN est évaluée juste après que la mise à jour de la ligne se produit, et elle détermine si un événement est mis en file pour déclencher le trigger à la fin de l'instruction. Ainsi, lorsque la condition WHEN d'un trigger AFTER ne renvoie pas true, il n'est pas nécessaire de mettre un événement en file ni de récupérer à nouveau la ligne à la fin de l'instruction. Cela peut entraîner des accélérations significatives dans les instructions qui modifient de nombreuses lignes, si le trigger ne doit être déclenché que pour quelques-unes des lignes.

Dans certains cas, une seule commande SQL peut déclencher plus d'un type de trigger. Par exemple, un INSERT avec une clause ON CONFLICT DO UPDATE peut provoquer à la fois des opérations d'insertion et de mise à jour, il déclenchera donc les deux types de triggers selon les besoins. Les relations de transition fournies aux triggers sont spécifiques à leur type d'événement ; ainsi un trigger INSERT ne verra que les lignes insérées, tandis qu'un trigger UPDATE ne verra que les lignes mises à jour.

Les mises à jour ou suppressions de lignes causées par des actions d'application de clé étrangère, telles que ON UPDATE CASCADE ou ON DELETE SET NULL, sont traitées comme faisant partie de la commande SQL qui les a causées (notez que ces actions ne sont jamais différées). Les triggers pertinents sur la table affectée seront déclenchés, ce qui fournit un autre moyen par lequel une commande SQL peut déclencher des triggers qui ne correspondent pas directement à son type. Dans les cas simples, les triggers qui demandent des relations de transition verront tous les changements causés dans leur table par une seule commande SQL originale comme une seule relation de transition. Cependant, il existe des cas où la présence d'un trigger AFTER ROW qui demande des relations de transition entraînera la division des actions d'application de clé étrangère déclenchées par une seule commande SQL en plusieurs étapes, chacune avec sa ou ses propres relations de transition. Dans de tels cas, tous les triggers au niveau des instructions présents seront déclenchés une fois par création d'un ensemble de relations de transition, garantissant que les triggers voient chaque ligne affectée dans une relation de transition une et une seule fois.

Les triggers au niveau des instructions sur une vue ne sont déclenchés que si l'action sur la vue est gérée par un trigger INSTEAD OF au niveau des lignes. Si l'action est gérée par une règle INSTEAD, alors quelles que soient les instructions émises par la règle, elles sont exécutées à la place de l'instruction originale nommant la vue, de sorte que les triggers qui seront déclenchés sont ceux sur les tables nommées dans les instructions de remplacement. De même, si la vue est automatiquement mise à jour, l'action est gérée en réécrivant automatiquement l'instruction en une action sur la table de base de la vue, de sorte que les triggers au niveau des instructions de la table de base sont ceux qui sont déclenchés.

La modification d'une table partitionnée ou d'une table ayant des enfants d'héritage déclenche les triggers au niveau des instructions attachés à la table explicitement nommée, mais pas les triggers au niveau des instructions de ses partitions ou tables filles. En revanche, les triggers au niveau des lignes sont déclenchés sur les lignes des partitions ou tables filles affectées, même si elles ne sont pas explicitement nommées dans la requête. Si un trigger au niveau des instructions a été défini avec des relations de transition nommées par une clause REFERENCING, alors les images avant et après des lignes sont visibles depuis toutes les partitions ou tables filles affectées. Dans le cas des enfants d'héritage, les images de ligne ne comprennent que les colonnes présentes dans la table à laquelle le trigger est attaché.

Actuellement, les triggers au niveau des lignes avec des relations de transition ne peuvent pas être définis sur des partitions ou des tables filles d'héritage. De plus, les triggers sur des tables partitionnées ne peuvent pas être INSTEAD OF.

Actuellement, l'option OR REPLACE n'est pas prise en charge pour les triggers de contrainte.

Remplacer un trigger existant dans une transaction qui a déjà effectué des actions de mise à jour sur la table du trigger n'est pas recommandé. Les décisions de déclenchement du trigger, ou les portions de décisions de déclenchement, qui ont déjà été prises ne seront pas réexaminées, les effets pourraient donc être surprenants.

Il existe quelques fonctions trigger intégrées qui peuvent être utilisées pour résoudre des problèmes courants sans avoir à écrire votre propre code de trigger ; voir la Section 9.29.

EXEMPLES

Exécuter la fonction check_account_update chaque fois qu'une ligne de la table accounts est sur le point d'être mise à jour :

CREATE TRIGGER check_update
    BEFORE UPDATE ON accounts
    FOR EACH ROW
    EXECUTE FUNCTION check_account_update();

Modifier cette définition de trigger pour n'exécuter la fonction que si la colonne balance est spécifiée comme cible dans la commande UPDATE :

CREATE OR REPLACE TRIGGER check_update
    BEFORE UPDATE OF balance ON accounts
    FOR EACH ROW
    EXECUTE FUNCTION check_account_update();

Cette forme n'exécute la fonction que si la colonne balance a en fait changé de valeur :

CREATE TRIGGER check_update
    BEFORE UPDATE ON accounts
    FOR EACH ROW
    WHEN (OLD.balance IS DISTINCT FROM NEW.balance)
    EXECUTE FUNCTION check_account_update();

Appeler une fonction pour journaliser les mises à jour des comptes, mais seulement si quelque chose a changé :

CREATE TRIGGER log_update
    AFTER UPDATE ON accounts
    FOR EACH ROW
    WHEN (OLD.* IS DISTINCT FROM NEW.*)
    EXECUTE FUNCTION log_account_update();

Exécuter la fonction view_insert_row pour chaque ligne afin d'insérer des lignes dans les tables sous-jacentes à une vue :

CREATE TRIGGER view_insert
    INSTEAD OF INSERT ON my_view
    FOR EACH ROW
    EXECUTE FUNCTION view_insert_row();

Exécuter la fonction check_transfer_balances_to_zero pour chaque instruction afin de confirmer que les lignes de transfert se compensent à un net de zéro :

CREATE TRIGGER transfer_insert
    AFTER INSERT ON transfer
    REFERENCING NEW TABLE AS inserted
    FOR EACH STATEMENT
    EXECUTE FUNCTION check_transfer_balances_to_zero();

Exécuter la fonction check_matching_pairs pour chaque ligne afin de confirmer que les modifications sont faites sur des paires assorties en même temps (par la même instruction) :

CREATE TRIGGER paired_items_update
    AFTER UPDATE ON paired_items
    REFERENCING NEW TABLE AS newtab OLD TABLE AS oldtab
    FOR EACH ROW
    EXECUTE FUNCTION check_matching_pairs();

La Section 37.4 contient un exemple complet de fonction triggerion écrit en C.

COMPATIBILITÉ

L'instruction CREATE TRIGGER dans PostgreSQL implémente un sous-ensemble du standard SQL. Les fonctionnalités suivantes sont actuellement manquantes :

•Bien que les noms de tables de transition pour les déclencheurs AFTER soient spécifiés à l'aide de la clause REFERENCING de la manière standard, les variables de ligne utilisées dans les déclencheurs FOR EACH ROW ne peuvent pas être spécifiées dans une clause REFERENCING. Elles sont disponibles d'une manière qui dépend du langage dans lequel la fonction du déclencheur est écrite, mais qui est fixe pour un langage donné. Certains langages se comportent effectivement comme s'il existait une clause REFERENCING contenant OLD ROW AS OLD NEW ROW AS NEW.
•Le standard permet l'utilisation de tables de transition avec des déclencheurs UPDATE spécifiques à une colonne, mais alors l'ensemble des lignes qui devraient être visibles dans les tables de transition dépend de la liste de colonnes du déclencheur. Ceci n'est actuellement pas implémenté par PostgreSQL.
•PostgreSQL n'autorise que l'exécution d'une fonction définie par l'utilisateur pour l'action déclenchée. Le standard autorise l'exécution de plusieurs autres commandes SQL, telles que CREATE TABLE, comme action déclenchée. Cette limitation n'est pas difficile à contourner en créant une fonction définie par l'utilisateur qui exécute les commandes souhaitées.

SQL spécifie que plusieurs déclencheurs doivent être déclenchés dans l'ordre de leur création. PostgreSQL utilise l'ordre du nom, qui a été jugé plus pratique.

SQL spécifie que les déclencheurs BEFORE DELETE sur les suppressions en cascade se déclenchent après l'achèvement du DELETE en cascade. Le comportement de PostgreSQL est que BEFORE DELETE se déclenche toujours avant l'action de suppression, même en cascade. C'est considéré comme plus cohérent. Il y a aussi un comportement non standard si les déclencheurs BEFORE modifient des lignes ou empêchent les mises à jour pendant une mise à jour causée par une action référentielle. Cela peut conduire à des violations de contraintes ou à des données stockées qui ne respectent pas la contrainte référentielle.

La possibilité de spécifier plusieurs actions pour un seul déclencheur en utilisant OR est une extension de PostgreSQL au standard SQL.

La possibilité de déclencher des déclencheurs pour TRUNCATE est une extension de PostgreSQL au standard SQL, tout comme la possibilité de définir des déclencheurs au niveau des instructions sur des vues.

CREATE CONSTRAINT TRIGGER est une extension de PostgreSQL au standard SQL. L'option OR REPLACE l'est aussi.
