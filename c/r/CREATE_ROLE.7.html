DESCRIPTIO

N

CREATE ROLE ajoute un nouveau rôle à un cluster de bases de données PostgreSQL. Un rôle est une entité qui peut être propriétaire d'objets de base de données et posséder des privilèges de base de données ; un rôle peut être considéré comme un « utilisateur », un « groupe », ou les deux, selon son utilisation. Consultez le chapitre 21 et le chapitre 20 pour obtenir des informations sur la gestion des utilisateurs et l'authentification. Vous devez disposer du privilège CREATEROLE ou être un superutilisateur de base de données pour utiliser cette

commande.

Notez que les rôles sont définis au niveau du cluster de bases de données, et sont donc valides dans toutes les bases de données du

cluster.

Lors de la création d'un rôle, il est possible d'affecter immédiatement le rôle nouvellement créé comme membre d'un rôle existant, et aussi d'affecter des rôles existants comme membres du rôle nouvellement créé. Les règles déterminant les options d'appartenance initiales activées sont décrites ci-dessous dans les clauses IN ROLE, ROLE et ADMIN. La commande GRANT(7) offre un contrôle fin des options lors de la création de l'apparte

nance, et la possibilité de modifier ces
options après la création du nouveau rôle.

PARAMÈTRE

S

no

m
Le nom du nouveau
rôle.

SUPERUSER
NOSUPERUSE

R
Ces clauses déterminent si le nouveau rôle est un « superutilisateur », qui peut contourner toutes les restrictions d'accès au sein de la base de données. Le statut de superutilisateur est dangereux et ne doit être utilisé que lorsque c'est réellement nécessaire. Vous devez vous-même être un superutilisateur pour créer un nouveau superutilisateur. Si non spécifié, NOSUPERUSER est la valeur par
défaut.

CREATEDB
NOCREATED

B
Ces clauses définissent la capacité d'un rôle à créer des bases de données. Si CREATEDB est spécifié, le rôle en cours de définition sera autorisé à créer de nouvelles bases de données. La spécification de NOCREATEDB refusera à un rôle la capacité de créer des bases de données. Si non spécifié, NOCREATEDB est la valeur par défaut. Seuls les rôles superutilisateurs ou les rôles disposant de CREATEDB peuvent spécifier
CREATEDB.

CREATEROLE
NOCREATEROL

E
Ces clauses déterminent si un rôle sera autorisé à créer, modifier, supprimer, commenter et changer l'étiquette de sécurité d'autres rôles. Consultez la création de rôles pour plus de détails sur les capacités conférées par ce privilège. Si non spécifié, NOCREATEROLE est la valeur par
défaut.

INHERIT
NOINHERI

T
Cela affecte le statut d'héritage d'appartenance lorsque ce rôle est ajouté comme membre d'un autre rôle, à la fois dans cette commande et dans les commandes futures. Plus précisément, cela contrôle le statut d'héritage des appartenance ajoutées avec cette commande en utilisant la clause IN ROLE, et dans les commandes ultérieures en utilisant la clause ROLE. C'est également utilisé comme statut d'héritage par défaut lors de l'ajout de ce rôle comme membre à l'aide de la commande GRANT. Si non spécifié, INHERIT est la valeur par défaut.

Dans les versions de PostgreSQL antérieures à la 16, l'hérita

ge était un attribut au niveau du rôle qui contrôlait toutes
les vérifications d'appartenance à l'exécution pour ce rôle.

LOGIN
NOLOGI

N
Ces clauses déterminent si un rôle est autorisé à se connecter ; c'est-à-dire si le rôle peut être donné comme nom d'autorisation de session initial lors de la connexion d'un client. Un rôle possédant l'attribut LOGIN peut être considéré comme un utilisateur. Les rôles sans cet attribut sont utiles pour gérer les privilèges de base de données, mais ne sont pas des utilisateurs au sens habituel du terme. Si non spécifié, NOLOGIN est la valeur par défaut, sauf lorsque CREATE ROLE est invoqué via son orthographe alternative CREATE U
SER.

REPLICATION
NOREPLICATIO

N
Ces clauses déterminent si un rôle est un rôle de réplication. Un rôle doit posséder cet attribut (ou être un superutilisateur) pour pouvoir se connecter au serveur en mode réplication (réplication physique ou logique) et pour pouvoir créer ou supprimer des emplacements de réplication. Un rôle possédant l'attribut REPLICATION est un rôle très privilégié et ne doit être utilisé que sur des rôles réellement utilisés pour la réplication. Si non spécifié, NOREPLICATION est la valeur par défaut. Seuls les rôles superutilisateurs ou les rôles disposant de REPLICATION peuvent spécifier
REPLICATION.

BYPASSRLS
NOBYPASSRL

S
Ces clauses déterminent si un rôle contourne toutes les politiques de sécurité au niveau des lignes (RLS). NOBYPASSRLS est la valeur par défaut. Seuls les rôles superutilisateurs ou les rôles disposant de BYPASSRLS peuvent spécifier BYPASSRLS.

Notez que pg_dump définira row_security à OFF par défaut, pour s'assurer que tout le contenu d'une table est sauve

gardé. Si l'utilisateur exécutant pg_dump ne dispose pas des permissions appropriées, une erreur sera renvoyée. C
ependant, les superutilisateurs et le propriétaire de la table en cours de sauvegarde contournent toujours la RLS.

CONNECTION LIMIT nb_connexion

s
Si le rôle peut se connecter, cela spécifie le nombre de connexions simultanées que le rôle peut établir. -1 (la valeur par défaut) signifie aucune limite. Notez que seules les connexions normales sont comptées dans cette limite. Ni les transactions préparées ni les connexions des processus d'arrière-plan ne sont comptées dans cette
limite.

[ ENCRYPTED ] PASSWORD 'mot_de_passe'
PASSWORD

NULL
Définit le mot de passe du rôle. (Un mot de passe n'est utile que pour les rôles possédant l'attribut LOGIN, mais vous pouvez néanmoins en définir un pour les rôles qui ne l'ont pas.) Si vous ne prévoyez pas d'utiliser l'authentification par mot de passe, vous pouvez omettre cette option. Si aucun mot de passe n'est spécifié, le mot de passe sera défini à null et l'authentification par mot de passe échouera toujours pour cet utilisateur. Un mot de passe null peut éventuellement être écrit explicitement comme PASSWORD NULL.

Note
Spécifier une chaîne vide définira également le mot de passe à null, mais ce n'était pas le cas avant la version 10 de PostgreSQL. Dans les versions précédentes, une chaîne vide pouvait être utilisée ou non, selon la méthode d'authentification et la version exacte, et libpq refusait de l'utiliser dans tous les cas. Pour éviter l'ambiguïté, il convient d'éviter de spécifier une chaîne
vide. Le mot de passe est toujours stocké chiffré dans les catalogues système. Le mot-clé ENCRYPTED n'a aucun effet, mais est accepté pour des raisons de compatibilité ascendante. La méthode de chiffrement est déterminée par le paramètre de configuration password_encryption. Si la chaîne de mot de passe présentée est déjà au format chiffré MD5 ou SCRAM, elle est telle quelle quel que soit password_encryption (puisque le système ne peut pas déchiffrer la chaîne de mot de passe chiffrée spécifiée pour la chiffrer dans un format différent). Cela permet le rechargement des mots de passe chiffrés lors de la sauvegarde/restauration.

Avertissement
La prise en charge des mots de passe chiffrés MD5 est obsolète et sera su
pprimée dans une future version de PostgreSQL. Consultez la section 20.5
pour plus de détails sur la migration vers un autre type de mot de passe.

VALID UNTIL 'horodatage

'
La clause VALID UNTIL définit une date et une heure après lesquelles le mot de passe du rôle n'est plus valide. Si cette clause est omise, le mot de passe sera valide pour
toujours.

IN ROLE nom_rôl

e
La clause IN ROLE fait que le nouveau rôle est automatiquement ajouté comme membre des rôles existants spécifiés. La nouvelle appartenance aura l'option SET activée et l'option ADMIN désactivée. L'option INHERIT sera activée sauf si l'option NOINHERIT est
spécifiée.

ROLE nom_rôl

e
La clause ROLE fait qu'un ou plusieurs rôles existants spécifiés sont automatiquement ajoutés comme membres, avec l'option SET activée. Cela rend en fait le nouveau rôle un « groupe ». Les rôles nommés dans cette clause avec l'attribut INHERIT au niveau du rôle auront l'option INHERIT activée dans la nouvelle appartenance. Les nouvelles appartenance auront l'option ADMIN
désactivée.

ADMIN nom_rôl

e
La clause ADMIN a le même effet que ROLE, mais les rôles nommés sont ajoutés comme membres du nouveau rôle avec ADMIN activé, leur donnant le droit d'accorder l'appartenance au nouveau rôle à
d'autres.

d

is est acceptée pour des raiso

NOTE

S

Utilisez ALTER ROLE pour modifier les attributs d'un rôle, et DROP ROLE pour supprimer un rôle. Tous les attributs spécifiés par CREATE Le rôle peut être modifié par des commandes ALTER ROLE ulté

rieures.

La manière recommandée d'ajouter et de retirer des membres de rôles utilisés comme groupes est d'utiliser GRANT et REVOKE

.

La clause VALID UNTIL définit une date d'expiration pour le mot de passe uniquement, pas pour le rôle en lui-même. En particulier, la date d'expiration n'est pas appliquée lors de la connexion avec une méthode d'authentification non basée sur le mot de

passe.

Les attributs de rôle définis ici ne sont pas héritables, c'est-à-dire qu'être membre d'un rôle ayant, par exemple, CREATEDB n'autorisera pas le membre à créer de nouvelles bases de données même si l'attribution de membre a l'option INHERIT. Bien entendu, si l'attribution de membre a l'option SET, le rôle membre pourrait SET ROLE sur le rôle createdb puis créer une nouvelle base de

données.

Les attributions de membre créées par les clauses IN ROLE, ROLE et ADMIN ont le rôle exécutant cette commande comme

octroyant.

L'attribut INHERIT est la valeur par défaut pour des raisons de compatibilité ascendante : dans les versions précédentes de PostgreSQL, les utilisateurs avaient toujours accès à tous les privilèges des groupes dont ils étaient membres. Cependant, NOINHERIT fournit une correspondance plus étroite avec la sémantique spécifiée dans le standard

SQL.

PostgreSQL inclut un programme createuser(1) qui a les mêmes fonctionnalités que CREATE ROLE (en fait, il appelle cette commande) mais qui peut être exécuté depuis le shell de

commandes.

L'option CONNECTION LIMIT n'est appliquée qu'approximativement ; si deux nouvelles sessions démarrent à peu près en même temps alors qu'il ne reste qu'un « créneau » de connexion pour le rôle, il est possible que les deux échouent. De plus, la limite n'est jamais appliquée pour les superutilisateurs

.

Une prudence doit être exercée lors de la spécification d'un mot de passe non chiffré avec cette commande. Le mot de passe sera transmis au serveur en clair, et il pourrait aussi être enregistré dans l'historique des commandes du client ou le journal du serveur. La commande createuser(1), cependant, transmet le mot de passe chiffré. De plus, psql(1) contient une commande \password qui peut être utilisée pour chan

ger le mot de passe de
manière sûre plus tard.

COMPATIBILIT

É

L'instruction CREATE ROLE est dans le standard SQL, mais le standard ne requiert que la

syntaxe 
CREATE ROLE nom [ WITH ADMIN nom_r
ôle
]

Les administrateurs initiaux multiples, et toutes les autres options de CREATE ROLE, sont des extensions

PostgreSQL.

Le standard SQL définit les concepts d'utilisateurs et de rôles, mais il les considère comme des concepts distincts et laisse à chaque implémentation de base de données le soin de spécifier toutes les commandes définissant les utilisateurs. Dans PostgreSQL, nous avons choisi d'unifier les utilisateurs et les rôles en un seul type d'entité. Les rôles ont donc beaucoup plus d'attributs optionnels que dans le

standard.

Le comportement spécifié par le standard SQL est le plus fidèlement approché en créant des utilisateurs standard SQL comme des rôles PostgreSQL avec l' option NOINHERIT, et des rôles standard SQL comme des rôles PostgreSQL avec l' option

INHERIT.

La clause USER a le même comportement que ROLE mais a été dépréciée

: 
USER nom_rôle [, ..
.
]

La clause IN GROUP a le même comportement que IN ROLE mais a été dépréciée

: 
IN GROUP nom_rô
le [
, .
..]
