CREATE DATABASE(7) Documentation PostgreSQL 18.1 CREATE DATABASE(7)

NOM

CREATE_DATABASE - crée une nouvelle base de données

SYNOPSIS

CREATE DATABASE name
    [ WITH ] [ OWNER [=] user_name ]
           [ TEMPLATE [=] template ]
           [ ENCODING [=] encoding ]
           [ STRATEGY [=] strategy ]
           [ LOCALE [=] locale ]
           [ LC_COLLATE [=] lc_collate ]
           [ LC_CTYPE [=] lc_ctype ]
           [ BUILTIN_LOCALE [=] builtin_locale ]
           [ ICU_LOCALE [=] icu_locale ]
           [ ICU_RULES [=] icu_rules ]
           [ LOCALE_PROVIDER [=] locale_provider ]
           [ COLLATION_VERSION = collation_version ]
           [ TABLESPACE [=] tablespace_name ]
           [ ALLOW_CONNECTIONS [=] allowconn ]
           [ CONNECTION LIMIT [=] connlimit ]
           [ IS_TEMPLATE [=] istemplate ]
           [ OID [=] oid ]

DESCRIPTION

CREATE DATABASE crée une nouvelle base de données PostgreSQL.

Pour créer une base de données, vous devez être superutilisateur ou posséder le privilège spécial CREATEDB. Voir CREATE ROLE (CREATE_ROLE(7)).

Par défaut, la nouvelle base de données sera créée en clonant la base de données système standard template1. Un modèle différent peut être spécifié en écrivant TEMPLATE name. En particulier, en écrivant TEMPLATE template0, vous pouvez créer une base de données vierge (une base où aucun objet défini par l'utilisateur n'existe et où les objets système n'ont pas été modifiés) contenant uniquement les objets standards prédéfinis par votre version de PostgreSQL. C'est utile si vous souhaitez éviter de copier des objets locaux à l'installation qui pourraient avoir été ajoutés à template1.

PARAMÈTRES

name

Le nom de la base de données à créer.

user_name

Le nom du rôle de l'utilisateur qui sera propriétaire de la nouvelle base de données, ou DEFAULT pour utiliser la valeur par défaut (à savoir l'utilisateur qui exécute la commande). Pour créer une base de données appartenant à un autre rôle, vous devez pouvoir exécuter SET ROLE vers ce rôle.

template

Le nom du modèle à partir duquel créer la nouvelle base de données, ou DEFAULT pour utiliser le modèle par défaut (template1).

encoding

Encodage de jeu de caractères à utiliser dans la nouvelle base de données. Spécifiez une chaîne constante (par ex. 'SQL_ASCII'), ou un numéro d'encodage entier, ou DEFAULT pour utiliser l'encodage par défaut (à savoir l'encodage de la base de données modèle). Les jeux de caractères pris en charge par le serveur PostgreSQL sont décrits dans la section 23.3.1. Voir ci-dessous pour des restrictions supplémentaires.

strategy

Stratégie à utiliser pour créer la nouvelle base de données. Si la stratégie WAL_LOG est utilisée, la base de données sera copiée bloc par bloc et chaque bloc sera écrit séparément dans le journal d'anticipation (write-ahead log). C'est la stratégie la plus efficace lorsque la base de données modèle est petite, et c'est donc la valeur par défaut. L'ancienne stratégie FILE_COPY est également disponible. Cette stratégie écrit un petit enregistrement dans le journal d'anticipation pour chaque espace de tablespace utilisé par la base de données cible. Chaque tel enregistrement représente la copie d'un répertoire entier vers un nouvel emplacement au niveau du système de fichiers. Bien que cela réduise considérablement le volume du journal d'anticipation, en particulier si la base de données modèle est grande, cela force également le système à effectuer un point de contrôle (checkpoint) à la fois avant et après la création de la nouvelle base de données. Dans certaines situations, cela peut avoir un impact négatif perceptible sur les performances globales du système. La stratégie FILE_COPY est affectée par le paramètre file_copy_method.

locale

Définit l'ordre de collation par défaut et la classification des caractères dans la nouvelle base de données. La collation affecte l'ordre de tri appliqué aux chaînes, par ex. dans les requêtes avec ORDER BY, ainsi que l'ordre utilisé dans les index sur les colonnes de texte. La classification des caractères affecte la catégorisation des caractères, par ex. minuscule, majuscule et chiffre. Définit également les aspects associés de l'environnement du système d'exploitation, LC_COLLATE et LC_CTYPE. La valeur par défaut est le même réglage que celui de la base de données modèle. Voir la section 23.2.2.3.1 et la section 23.2.2.3.2 pour plus de détails.

Peut être remplacé en définissant lc_collate, lc_ctype, builtin_locale, ou icu_locale individuellement.

Si locale_provider est builtin, alors locale ou builtin_locale doit être spécifié et défini à C, C.UTF-8 ou PG_UNICODE_FAST.


Astuce
Les autres paramètres de localisation lc_messages, lc_monetary, lc_numeric et lc_time ne sont pas fixes par base de données et ne sont pas définis par cette commande. Si vous voulez en faire les valeurs par défaut pour une base de données spécifique, vous pouvez utiliser ALTER DATABASE ... SET.

lc_collate

Définit LC_COLLATE dans l'environnement du système d'exploitation du serveur de bases de données. La valeur par défaut est celle de locale si spécifié, sinon le même réglage que celui de la base de données modèle. Voir ci-dessous pour des restrictions supplémentaires.

Si locale_provider est libc, définit également l'ordre de collation par défaut à utiliser dans la nouvelle base de données, en remplaçant le réglage locale.

lc_ctype

Définit LC_CTYPE dans l'environnement du système d'exploitation du serveur de bases de données. La valeur par défaut est celle de locale si spécifié, sinon le même réglage que celui de la base de données modèle. Voir ci-dessous pour des restrictions supplémentaires.

Si locale_provider est libc, définit également la classification des caractères par défaut à utiliser dans la nouvelle base de données, en remplaçant le réglage locale.

builtin_locale

Spécifie la localisation du fournisseur builtin pour l'ordre de collation par défaut et la classification des caractères de la base de données, en remplaçant le réglage locale. Le fournisseur de localisation doit être builtin. La valeur par défaut est celle de locale si spécifié ; sinon le même réglage que celui de la base de données modèle.

Les localisations disponibles pour le fournisseur builtin sont C, C.UTF-8 et PG_UNICODE_FAST.

icu_locale

Spécifie la localisation ICU (voir la section 23.2.2.3.2) pour l'ordre de collation par défaut et la classification des caractères de la base de données, en remplaçant le réglage locale. Le fournisseur de localisation doit être ICU. La valeur par défaut est celle de locale si spécifié ; sinon le même réglage que celui de la base de données modèle.

icu_rules

Spécifie des règles de collation supplémentaires pour personnaliser le comportement de la collation par défaut de cette base de données. Ceci n'est pris en charge que pour ICU. Voir la section 23.2.3.4 pour plus de détails.

locale_provider

Spécifie le fournisseur à utiliser pour la collation par défaut dans cette base de données. Les valeurs possibles sont builtin, icu (si le serveur a été compilé avec la prise en charge d'ICU) ou libc. Par défaut, le fournisseur est le même que celui du template. Voir la section 23.1.4 pour plus de détails.

collation_version

Spécifie la chaîne de version de collation à stocker avec la base de données. Normalement, cela doit être omis, ce qui fera que la version sera calculée à partir de la version réelle de la collation de la base de données telle que fournie par le système d'exploitation. Cette option est destinée à être utilisée par pg_upgrade pour copier la version depuis une installation existante.

Voir aussi ALTER DATABASE (ALTER_DATABASE(7)) pour savoir comment gérer les incompatibilités de version de collation des bases de données.

tablespace_name

Le nom de l'espace de tablespace qui sera associé avec la nouvelle base de données, ou DEFAULT pour utiliser l'espace de tablespace de la base de données modèle. Cet espace de tablespace sera l'espace de tablespace par défaut utilisé pour les objets créés dans cette base de données. Voir CREATE TABLESPACE (CREATE_TABLESPACE(7)) pour plus d'informations.

allowconn

Si false, alors personne ne peut se connecter à cette base de données. La valeur par défaut est true, ce qui autorise les connexions (sauf si restreintes par d'autres mécanismes, comme GRANT/REVOKE CONNECT).

connlimit

Combien de connexions simultanées peuvent être établies avec cette base de données. -1 (la valeur par défaut) signifie sans limite.

istemplate

Si true, alors cette base de données peut être clonée par n'importe quel utilisateur possédant les privilèges CREATEDB ; si false (la valeur par défaut), alors seuls les superutilisateurs ou le propriétaire de la base de données peuvent la cloner.

oid

L'identifiant d'objet à utiliser pour la nouvelle base de données. Si ce paramètre n'est pas spécifié, PostgreSQL choisira automatiquement un OID approprié. Ce paramètre est principalement destiné à un usage interne par pg_upgrade, et seul pg_upgrade peut spécifier une valeur inférieure à 16384.

Les paramètres optionnels peuvent être écrits dans n'importe quel ordre, et pas seulement dans l'ordreustrated above.

NOTES

CREATE DATABASE ne peut pas être exécuté à l'intérieur d'un bloc de transaction.

Les erreurs du type « could not initialize database directory » sont très probablement liées à des permissions insuffisantes sur le répertoire de données, un disque plein ou d'autres problèmes de système de fichiers.

Utilisez DROP DATABASE pour supprimer une base de données.

Le programme createdb(1) est un programme wrapper autour de cette commande, fourni pour plus de commodité.

Les paramètres de configuration au niveau de la base de données (définis via ALTER DATABASE) et les permissions au niveau de la base de données (définies via GRANT) ne sont pas copiés depuis la base de données modèle.

Bien qu'il soit possible de copier une base de données autre que template1 en spécifiant son nom comme modèle, ceci n'est pas (encore) destiné à être une fonctionnalité «COPY DATABASE» à usage général. La limitation principale est qu'aucune autre session ne peut être connectée à la base de données modèle pendant qu'elle est copiée. CREATE DATABASE échouera si une autre connexion existe au moment où il démarre ; sinon, les nouvelles connexions à la base de données modèle sont bloquées jusqu'à ce que CREATE DATABASE se termine. Voir la section 22.3 pour plus d'informations.

L'encodage de jeu de caractères spécifié pour la nouvelle base de données doit être compatible avec les paramètres de locale choisis (LC_COLLATE et LC_CTYPE). Si la locale est C (ou équivalemment POSIX), alors tous les encodages sont autorisés, mais pour les autres paramètres de locale, il n'y a qu'un seul encodage qui fonctionnera correctement. (Sur Windows, cependant, l'encodage UTF-8 peut être utilisé avec n'importe quelle locale.) CREATE DATABASE permettra aux superutilisateurs de spécifier l'encodage SQL_ASCII quel que soit le paramétrage de la locale, mais ce choix est déprécié et peut entraîner un dysfonctionnement des fonctions de chaînes de caractères si des données non compatibles avec l'encodage de la locale sont stockées dans la base de données.

L'encodage et les paramètres de locale doivent correspondre à ceux de la base de données modèle, sauf lorsque template0 est utilisé comme modèle. Cela est dû au fait que d'autres bases de données peuvent contenir des données qui ne correspondent pas à l'encodage spécifié, ou peuvent contenir des index dont l'ordre de tri est affecté par LC_COLLATE et LC_CTYPE. Copier de telles données entraînerait une base de données corrompue selon les nouveaux paramètres. template0, cependant, est connu pour ne contenir aucune donnée ou index qui serait affecté.

Il n'existe actuellement aucune option pour utiliser une locale de base de données avec des comparaisons non déterministes (voir CREATE COLLATION pour une explication). Si cela est nécessaire, des collations par colonne devraient être utilisées.

L'option CONNECTION LIMIT n'est appliquée qu'approximativement ; si deux nouvelles sessions démarrent à peu près en même temps alors qu'il ne reste qu'un « emplacement » de connexion pour la base de données, il est possible que les deux échouent. De plus, la limite n'est pas appliquée aux superutilisateurs ou aux processus de travail d'arrière-plan.

EXAMPLES

Pour créer une nouvelle base de données :

CREATE DATABASE lusiadas;

Pour créer une base de données sales appartenant à l'utilisateur salesapp avec un tablespace par défaut de salesspace :

CREATE DATABASE sales OWNER salesapp TABLESPACE salesspace;

Pour créer une base de données music avec une locale différente :

CREATE DATABASE music
    LOCALE 'sv_SE.utf8'
    TEMPLATE template0;

Dans cet exemple, la clause TEMPLATE template0 est requise si la locale spécifiée est différente de celle de template1. (Si ce n'est pas le cas, alors spécifier la locale explicitement est redondant.)

Pour créer une base de données music2 avec une locale différente et un encodage de jeu de caractères différent :

CREATE DATABASE music2
    LOCALE 'sv_SE.iso885915'
    ENCODING LATIN9
    TEMPLATE template0;

Les paramètres de locale et d'encodage spécifiés doivent correspondre, sinon une erreur sera signalée.

Notez que les noms de locale sont spécifiques au système d'exploitation, de sorte que les commandes ci-dessus pourraient ne pas fonctionner de la même manière partout.

COMPATIBILITY

Il n'y a pas de déclaration CREATE DATABASE dans le standard SQL. Les bases de données sont équivalentes aux catalogues, dont la création est définie par l'implémentation.
