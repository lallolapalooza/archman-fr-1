FICHIERS D'ENTRÉE

Chaque fichier d'entrée doit être l'un des suivants : un fichier texte contenant un programme source en langage C, un fichier objet au format produit par c99 -c, ou une bibliothèque de fichiers objets, au format produit en archivage de zéro ou plusieurs fichiers objets, à l'aide de ar. Les implémentations peuvent fournir des utilitaires supplémentaires qui produisent des fichiers dans ces formats. Les formats de fichiers d'entrée supplémentaires sont définis par l'implémentation.

VARIABLES D'ENVIRONNEMENT

Les variables d'environnement suivantes affecteront l'exécution de c99 :

LANG
Fournit une valeur par défaut pour les variables d'internationalisation qui sont non définies ou vides. (Voir le volume des Définitions de base de POSIX.1‐2017, Section 8.2, Variables d'internationalisation pour la précédence des variables d'internationalisation utilisées pour déterminer les valeurs des catégories de locale.)
LC_ALL
Si défini avec une chaîne de caractères non vide, remplace les valeurs de toutes les autres variables d'internationalisation.
LC_CTYPE
Détermine la locale pour l'interprétation des séquences d'octets de données textuelles en tant que caractères (par exemple, caractères mono-octet par opposition à multi-octets dans les arguments et les fichiers d'entrée).
LC_MESSAGES

Détermine la locale qui doit être utilisée pour affecter le format et le contenu des messages de diagnostic écrits sur la sortie d'erreur standard.
NLSPATH
Détermine l'emplacement des catalogues de messages pour le traitement de LC_MESSAGES.
TMPDIR
Fournit un nom de chemin qui doit remplacer le répertoire par défaut pour les fichiers temporaires, le cas échéant. Sur les systèmes conformes XSI, fournit un nom de chemin qui doit remplacer le répertoire par défaut pour les fichiers temporaires, le cas échéant.

ÉVÉNEMENTS ASYNCHRONES

Par défaut.

STDOUT

Si plusieurs opérandes pathname se terminant par .c (ou éventuellement d'autres suffixes non spécifiés) sont donnés, pour chaque fichier de ce type :

"%s:\n", <pathname>

peut être écrit. Ces messages, s'ils sont écrits, doivent précéder le traitement de chaque fichier d'entrée ; ils ne doivent pas être écrits sur la sortie standard s'ils sont écrits sur la sortie d'erreur standard, comme décrit dans la section STDERR.

Si l'option -E est spécifiée, la sortie standard sera un fichier texte représentant les résultats de l'étape de préprocesseur du langage ; elle peut contenir des informations supplémentaires appropriées pour les passes de compilation ultérieures.

STDERR

La sortie d'erreur standard ne sera utilisée que pour les messages de diagnostic. Si plusieurs opérandes pathname se terminant par .c (ou éventuellement d'autres suffixes non spécifiés) sont donnés, pour chaque fichier de ce type :

"%s:\n", <pathname>

peut être écrit pour permettre l'identification des messages de diagnostic et d'avertissement avec le fichier d'entrée approprié. Ces messages, s'ils sont écrits, doivent précéder le traitement de chaque fichier d'entrée ; ils ne doivent pas être écrits sur la sortie d'erreur standard s'ils sont écrits sur la sortie standard, comme décrit dans la section STDOUT.

Cet utilitaire peut produire des messages d'avertissement concernant certaines conditions qui ne justifient pas un code de retour d'erreur (non nul).

FICHIERS DE SORTIE

Des fichiers objets ou des fichiers exécutables, ou les deux, sont produits dans des formats non spécifiés. Si le nom de chemin d'un fichier objet ou d'un fichier exécutable à créer par c99 aboutit à une entrée de répertoire existante pour un fichier qui n'est pas un fichier régulier, il est non spécifié si c99 tentera de créer le fichier ou émettra un diagnostic et se terminera avec un statut de sortie non nul.

DESCRIPTION ÉTENDUE

Bibliothèques Standard

L'utilitaire c99 reconnaîtra les options -l suivantes pour les bibliothèques standard :

-l c
Cette option rendra disponibles toutes les interfaces référencées dans le volume des Interfaces Système de POSIX.1‐2017, à l'exception possible des interfaces listées comme résidant dans <aio.h>, <arpa/inet.h>, <complex.h>, <fenv.h>, <math.h>, <mqueue.h>, <netdb.h>, <net/if.h>, <netinet/in.h>, <pthread.h>, <sched.h>, <semaphore.h>, <spawn.h>, <sys/socket.h>, pthread_kill(), et pthread_sigmask() dans <signal.h>, <trace.h>, les interfaces marquées comme facultatives dans <sys/mman.h>, les interfaces marquées comme ADV (Informations Consultatives) dans <fcntl.h>, et les interfaces commençant par le préfixe clock_ ou timer_ dans <time.h>. Cette option ne sera pas requise pour provoquer une recherche dans cette bibliothèque.
-l l
Cette option rendra disponibles toutes les interfaces requises par la sortie en langage C de lex qui ne sont pas rendues disponibles par l'option -l c.
-l pthread
Cette option rendra disponibles toutes les interfaces référencées dans <pthread.h> et pthread_kill() et pthread_sigmask() référencées dans <signal.h>. Une implémentation peut rechercher cette bibliothèque en l'absence de cette option.
-l m
Cette option rendra disponibles toutes les interfaces référencées dans <math.h>, <complex.h>, et <fenv.h>. Une implémentation peut rechercher cette bibliothèque en l'absence de cette option.
-l rt
Cette option rendra disponibles toutes les interfaces référencées dans <aio.h>, <mqueue.h>, <sched.h>, <semaphore.h>, et <spawn.h>, les interfaces marquées comme facultatives dans <sys/mman.h>, les interfaces marquées comme ADV (Informations Consultatives) dans <fcntl.h>, et les interfaces commençant par les préfixes clock_ et timer_ dans <time.h>. Une implémentation peut rechercher cette bibliothèque en l'absence de cette option.
-l trace
Cette option rendra disponibles toutes les interfaces référencées dans <trace.h>. Une implémentation peut rechercher cette bibliothèque en l'absence de cette option.
-l xnet
Cette option rendra disponibles toutes les interfaces référencées dans <arpa/inet.h>, <netdb.h>, <net/if.h>, <netinet/in.h>, et <sys/socket.h>. Une implémentation peut rechercher cette bibliothèque en l'absence de cette option.
-l y
Cette option rendra disponibles toutes les interfaces requises par la sortie en langage C de yacc qui ne sont pas rendues disponibles par l'option -l c.

En l'absence d'options qui interdisent l'invocation de l'éditeur de liens, telles que -c ou -E, l'utilitaire c99 provoquera l'envoi de l'équivalent d'une option -l c à l'éditeur de liens après le dernier opérande pathname ou option -l, provoquant sa recherche après le chargement de tous les autres fichiers objets et bibliothèques.

Il est non spécifié si les bibliothèques libc.a, libl.a, libm.a, libpthread.a, librt.a, libtrace.a, libxnet.a, ou liby.a existent en tant que fichiers réguliers. L'implémentation peut accepter comme arguments d'option -l des noms d'objets qui n'existent pas en tant que fichiers réguliers.

Symboles Externes

Le compilateur C et l'éditeur de liens doivent supporter la signification des symboles externes jusqu'à une longueur d'au moins 31 octets ; l'action prise lors de la rencontre de symboles dépassant la longueur maximale des symboles définie par l'implémentation est non spécifiée.

Le compilateur et l'éditeur de liens doivent supporter un minimum de 511 symboles externes par fichier source ou objet, et un minimum de 4095 symboles externes au total. Un message de diagnostic doit être écrit sur la sortie standard si la limite définie par l'implémentation est dépassée ; d'autres actions sont non spécifiées.

Recherche d'En-têtes

Si un fichier portant le même nom que l'un des en-têtes standard définis dans le volume des Définitions de base de POSIX.1‐2017, Chapitre 13, Headers, non fourni dans le cadre de l'implémentation, est placé dans l'un des emplacements habituels qui sont recherchés par défaut pour les en-têtes, les résultats sont non spécifiés.

CONSÉQUENCES DES

ERREURS

Lorsque c99 rencontre une erreur de compilation qui empêche la création d'un fichier objet, il doit écrire un message de diagnostic sur l'erreur standard et continuer à compiler les autres opérandes de code source, mais il ne doit pas effectuer la phase de liaison et il doit retourner un code de sortie non nul. Si l'édition de liens échoue, un message de diagnostic doit être écrit sur l'erreur standard et c99 se termine avec un code de sortie non nul. Une application conforme doit se fier au code de sortie de c99, plutôt qu'à l'existence ou au mode du fichier

exécutable.

UTILISATION PAR LES

APPLICATIONS

Étant donné que l' utilitaire c99 crée généralement des fichiers dans le répertoire courant pendant le processus de compilation, il est généralement nécessaire d'exécuter le utilitaire c99 dans un répertoire où un fichier peut être

créé.

Sur les systèmes fournissant la conformité POSIX (voir le volume des définitions de base de POSIX.1‐2017, Chapitre 2, Conformité), c99 n'est requis qu'avec l'option de développement en langage C ; les systèmes conformes à XSI fournissent toujours c99

.

Certaines implémentations historiques ont créé des fichiers .o lorsque -c n'est pas spécifié et que plus d'un fichier source est fourni. Puisque ce domaine n'est pas spécifié, l'application ne peut pas compter sur la création de fichiers .o mais elle doit aussi être préparée à la suppression, à la fin de l'édition de liaison, de fichiers .o liés qui existent

déjà.

Il existe une implication possible selon laquelle, si un utilisateur fournit des versions des fonctions standard (avant qu'elles ne soient rencontrées par une liaison implicite avec -l c ou explicite avec -l m), ces versions seraient utilisées à la place des versions standard. Il existe diverses raisons pour lesquelles cela pourrait ne pas être vrai (fonctions définies en tant que macros, manipulations pour un espace de noms propre, etc.), de sorte que l'existence de fichiers nommés de la même manière que les bibliothèques standard dans les répertoires -L est explicitement déclarée produire un comportement non

spécifié.

Toutes les fonctions spécifiées dans le volume des interfaces système de POSIX.1‐2017 peuvent être rendues visibles par les implémentations lorsque la bibliothèque standard C est recherchée. Les applications conformes doivent demander explicitement la recherche des autres bibliothèques standard lorsque des fonctions rendues visibles par ces bibliothèques sont

utilisées.

Dans la norme ISO C, la correspondance entre les caractères physiques de la source et le jeu de caractères source C est définie par l'implémentation. Les implémentations peuvent supprimer les caractères d'espacement avant le <newline> terminant une ligne (physique) en tant que partie de cette correspondance et, en conséquence, un ou plusieurs caractères d'espacement (et aucun autre caractère) entre un caractère <backslash> et le caractère <newline> qui termine la ligne produit des résultats définis par l'implémentation. Les applications portables ne devraient pas utiliser de tels

constructions.

JUSTIFICATIO

N

L' utilitaire c99 est basé sur l' utilitaire c89 initialement introduit dans la norme ISO POSIX‐2:

1993.

Certaines des modifications par rapport à c89 incluent la capacité à entremêler les options et les opérandes (ce que de nombreuses implémentations de c89 autorisaient bien que cela ne soit pas spécifié), la description de -l comme option au lieu d'opérande, et la modification du contenu de la section des bibliothèques standard pour prendre en compte les nouveaux en-têtes et options ; par exemple, <spawn.h> ajouté à la description de -l rt, et -l trace ajouté pour l'option de

traçage.

POSIX.1‐2008 spécifie que l' utilitaire c99 doit être capable d'utiliser des fichiers réguliers pour les fichiers *.o et pour les fichiers a.out. Les implémentations sont libres d'écraser les fichiers existants d'autres types lorsqu'elles tentent de créer des fichiers objets et des fichiers exécutables, mais ne sont pas tenues de le faire. Si autre chose qu'un fichier régulier est spécifié et que son utilisation échoue pour une raison quelconque, c99 est tenu d'émettre un message de diagnostic et de se terminer avec un code de sortie non nul. Mais pour certains types de fichiers, le problème peut ne pas être remarqué pendant longtemps. Par exemple, si un FIFO nommé a.out existe dans le répertoire courant, c99 peut tenter d'ouvrir a.out et se bloquera dans l'appel open() jusqu'à ce qu'un autre processus ouvre le FIFO en lecture. Ensuite, c99 peut écrire la majeure partie de a.out dans le FIFO et échouer lorsqu'il tente de se déplacer (seek) en arrière près du début du fichier pour insérer un horodatage (les FIFO ne sont pas des fichiers avec déplacement possible). L' utilitaire c99 est également autorisé à émettre un diagnostic immédiatement s'il rencontre un fichier a.out ou *.o qui n'est pas un fichier régulier. Pour une utilisation portable, les applications doivent s'assurer que tout a.out, argument d'option -o, ou fichiers *.o correspondant à des fichiers *.c n'entrent pas en conflit avec des noms déjà utilisés qui ne sont pas des fichiers réguliers ou des liens symboliques pointant vers des fichiers

réguliers.

Sur de nombreux systèmes, les applications multi-threadées s'exécutent dans un environnement de programmation distinct de celui utilisé par les applications mono-threadées. Cet environnement de programmation multi-threadé (en plus de nécessiter la spécification de -l pthread au moment de la liaison) peut nécessiter des drapeaux supplémentaires à définir lorsque les en-têtes sont traités à la compilation (-D_REENTRANT étant courant). Cet environnement de programmation est orthogonal aux environnements de programmation de taille de type discutés ci-dessus et listés dans le Tableau 4-4, Environnements de programmation : Tailles de types. Cette version de la norme ajoute des appels à l'utilitaire getconf pour fournir les drapeaux du compilateur C et les drapeaux de l'éditeur de liaison/chargeur nécessaires pour prendre en charge les applications multi-threadées. Notez que sur un système où les applications mono-threadées sont un cas particulier d'une application multi-threadée, ces deux appels getconf peuvent retourner des chaînes NULL ; sur d'autres implémentations, ces deux chaînes peuvent être

non-NULL.

Le comité de normalisation du C a inventé les trigraphes (par exemple, "??!" pour représenter '|') afin de résoudre les problèmes de portabilité des caractères dans les environnements de développement basés sur des variantes nationales du jeu de caractères standard 7 bits ISO/IEC 646:1991. Cependant, ces environnements étaient déjà obsolètes lorsque la première norme ISO C a été publiée, et en pratique les trigraphes n'ont pas été utilisés pour leur but prévu, et sont généralement destinés à conserver leur signification originale en K&R C. Par exemple, en pratique, une chaîne de caractères source en langage C comme "What??!" est généralement destinée à se terminer par deux caractères <question-mark> et un <exclamation-mark>, et non par '|'

.

Lorsque l' option -E est utilisée, l'exécution de certaines directives de préprocesseur #pragma peut simplement entraîner la copie de la directive dans la sortie en tant qu

e partie des informations supplémentaires autorisées utilis
ées par les passes de compilation suivantes (voir STDOUT).
