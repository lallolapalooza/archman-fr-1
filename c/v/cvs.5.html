cvs(5) Manuel des formats de fichiers cvs(5)

NOM

cvs - Fichiers de support du système de versions concurrentes

REMARQUE

Cette documentation n'est peut-être plus à jour. Veuillez consulter le Cederqvist (Manuel de CVS) comme spécifié dans cvs(1).

SYNOPSIS

$CVSROOT/CVSROOT/commitinfo,v
$CVSROOT/CVSROOT/cvsignore,v
$CVSROOT/CVSROOT/cvswrappers,v
$CVSROOT/CVSROOT/editinfo,v
$CVSROOT/CVSROOT/history
$CVSROOT/CVSROOT/loginfo,v
$CVSROOT/CVSROOT/modules,v
$CVSROOT/CVSROOT/rcsinfo,v
$CVSROOT/CVSROOT/taginfo,v

DESCRIPTION

cvs est un système qui fournit le contrôle de source pour des collections hiérarchiques de répertoires source. Les commandes et les procédures pour utiliser cvs sont décrites dans cvs(1).

cvs gère les dépôts de source, les répertoires contenant les copies maîtres des fichiers sous contrôle de révision, en copiant des révisions particulières des fichiers vers (et les modifications en retour depuis) les répertoires de travailprivés des développeurs. En termes de structure de fichiers, chaque dépôt de source individuel est un sous-répertoire direct de $CVSROOT.

Les fichiers décrits ici sont des fichiers de support ; ils n'ont pas à exister pour que cvs fonctionne, mais ils vous permettent de rendre les opérations de cvs plus flexibles.

Vous pouvez utiliser le fichier « modules » pour définir des noms symboliques pour des collections de sources maintenues avec cvs. S'il n'existe pas de fichier « modules », les développeurs doivent spécifier des noms de chemins complets (absolus, ou relatifs à $CVSROOT) pour les fichiers qu'ils souhaitent gérer avec les commandes cvs.

Vous pouvez utiliser le fichier « commitinfo » pour définir des programmes à exécuter chaque fois que «cvs commit» est sur le point de s'exécuter. Ces programmes sont utilisés pour la vérification « pré-commit » afin de vérifier que les fichiers modifiés, ajoutés et supprimés sont réellement prêts à être validés. Certaines utilisations de cette vérification pourraient consister à désactiver une partie (ou la totalité) du dépôt de source pour une personne ou un groupe particulier. Ou peut-être à vérifier que les fichiers modifiés sont conformes aux normes de pratique de codage du site.

Vous pouvez utiliser le fichier « cvswrappers » pour enregistrer les commandes wrapper de cvs à utiliser lors de la validation et de la récupération de fichiers depuis le dépôt. Les wrappers permettent de traiter le fichier ou le répertoire lors de l'entrée et de la sortie de CVS. Les utilisations prévues sont nombreuses, une utilisation possible serait de reformater un fichier C avant que le fichier ne soit validé, afin que tout le code du dépôt ait le même aspect.

Vous pouvez utiliser le fichier « loginfo » pour définir des programmes à exécuter après chaque commit, qui écrit une entrée de journal pour les changements dans le dépôt. Ces programmes de journalisation pourraient être utilisés pour ajouter le message de journal à un fichier. Ou envoyer le message de journal par courrier électronique à un groupe de développeurs. Ou peut-être publier le message de journal dans un groupe de discussion particulier.

Vous pouvez utiliser le fichier « taginfo » pour définir des programmes à exécuter après chaque opération tagourtag . Ces programmes pourraient être utilisés pour ajouter un message à un fichier listant le nouveau nom de tag et le programmeur qui l'a créé, ou envoyer un courrier à un groupe de développeurs, ou peut-être publier un message dans un groupe de discussion particulier.

Vous pouvez utiliser le fichier « rcsinfo » pour définir des formulaires pour les messages de journal.

Vous pouvez utiliser le fichier « editinfo » pour définir un programme à exécuter pour l'édition/la validation des entrées de journal de «cvs commit». C'est surtout utile lorsqu'il est utilisé avec une spécification de formulaire « rcsinfo », car il peut vérifier que les champs appropriés du formulaire ont été remplis par l'utilisateur qui valide le changement.

Vous pouvez utiliser le fichier « cvsignore » pour spécifier la liste par défaut des fichiers à ignorer lors de update.

Vous pouvez utiliser le fichier « history » pour enregistrer les commandes cvs qui affectent le dépôt. La création de ce fichier active la journalisation de l'historique.

FICHIERS

modules
Le fichier « modules » enregistre vos définitions de noms pour des collections de code source. cvs utilisera ces définitions si vous utilisez cvs pour valider un fichier avec le bon format vers «$CVSROOT/CVSROOT/modules,v».

Le fichier « modules » peut contenir des lignes vides et des commentaires (lignes commençant par «#») ainsi que des définitions de modules. Les lignes longues peuvent être poursuivies sur la ligne suivante en spécifiant une barre oblique inverse (« \ ») comme dernier caractère de la ligne.

Une définition de module est une ligne unique du fichier « modules », dans l'un des deux formats. Dans les deux cas, mname représente le nom symbolique du module, et le reste de la ligne est sa définition.

mname -a aliases...
Cela représente la façon la plus simple de définir un module mname. Le «-a» indique que la définition est un simple alias : cvs traitera toute utilisation de mname (en tant qu'argument de commande) comme si la liste de noms aliases avait été spécifiée à la place. aliases peut contenir soit d'autres noms de modules, soit des chemins. Lorsque vous utilisez des chemins dans aliases, «cvs checkout» crée tous les répertoires intermédiaires dans le répertoire de travail, comme si le chemin avait été spécifié explicitement dans les arguments cvs.

mname [ options ] dir [ files... ] [ &module... ]

Dans le cas le plus simple, cette forme de définition de module se réduit à «mname dir». Cela définit tous les fichiers du répertoire dir comme module mname. dir est un chemin relatif (depuis $CVSROOT) vers un répertoire de source dans l'un des dépôts de source. Dans ce cas, lors du checkout, un répertoire unique appelé mname est créé comme répertoire de travail ; aucun niveau de répertoire intermédiaire n'est utilisé par défaut, même si dir était un chemin impliquant plusieurs niveaux de répertoires.

En spécifiant explicitement les files dans la définition de module après dir, vous pouvez sélectionner des fichiers particuliers du répertoire dir. La définition d'exemple pour modules est un exemple d'un module défini avec un seul fichier d'un répertoire particulier. Voici un autre exemple :

m4test  unsupported/gnu/m4 foreach.m4 forloop.m4

Avec cette définition, exécuter «cvs checkout m4test» créera un répertoire de travail unique « m4test » contenant les deux fichiers listés, qui proviennent tous deux d'un répertoire commun à plusieurs niveaux de profondeur dans le dépôt de source cvs.

Une définition de module peut faire référence à d'autres modules en incluant «&module» dans sa définition. checkout crée un sous-répertoire pour chaque modulede ce type, dans votre répertoire de travail.
Nouveau dans cvs 1.3 ; évitez cette fonctionnalité si vous partagez des définitions de modules avec des versions plus anciennes de cvs.

Enfin, vous pouvez utiliser une ou plusieurs des options suivantes dans les définitions de modules :

«-d name», pour nommer le répertoire de travail autrement que par le nom du module.
Nouveau dans cvs 1.3 ; évitez cette fonctionnalité si vous partagez des définitions de modules avec des versions plus anciennes de cvs.

«-i prog» vous permet de spécifier un programme prog à exécuter chaque fois que des fichiers d'un module sont validés. prog s'exécute avec un seul argument, le chemin complet du répertoire affecté dans un dépôt de source. Les fichiers « commitinfo », « loginfo » et « editinfo » fournissent d'autres moyens d'appeler un programme lors d'un commit.

«-o prog» vous permet de spécifier un programme prog à exécuter chaque fois que des fichiers d'un module sont récupérés. prog s'exécute avec un seul argument, le nom du module.

«-e prog» vous permet de spécifier un programme prog à exécuter chaque fois que des fichiers d'un module sont exportés. prog s'exécute avec un seul argument, le nom du module.

«-t prog» vous permet de spécifier un programme prog à exécuter chaque fois que des fichiers d'un module sont étiquetés. prog s'exécute avec deux arguments : le nom du module et le tag symbolique spécifié à rtag.

«-u prog» vous permet de spécifier un programme prog à exécuter chaque fois que «cvs update» est exécuté depuis le répertoire de premier niveau du module récupéré. prog s'exécute avec un seul argument, le chemin complet vers le dépôt de source pour ce module.

commitinfo, loginfo, rcsinfo, editinfo
Ces fichiers spécifient tous des programmes à appeler à différents points du processus `cvs commit'. Ils ont une structure commune. Chaque ligne est une paire de champs : une expression régulière, séparée par des espaces d'un nom de fichier ou d'un modèle de ligne de commande. Chaque fois que l'une des expressions régulières correspond à un nom de répertoire dans le dépôt, le reste de la ligne est utilisé. Si la ligne commence par le caractère # , la ligne entière est considérée comme un commentaire et est ignorée. Les espaces entre les champs sont également ignorés.

Pour `loginfo', le reste de la ligne est un modèle de ligne de commande à exécuter. Les modèles peuvent inclure non seulement un nom de programme, mais aussi toute liste d'arguments que vous souhaitez. Si vous écrivez `%s' quelque part dans la liste d'arguments, cvs fournit, à cet endroit, la liste des fichiers affectés par le commit. La première entrée de la liste est le chemin relatif dans le dépôt source où la modification est effectuée. Les arguments restants listent les fichiers qui sont modifiés, ajoutés ou supprimés par cette invocation de commit .

Pour `taginfo', le reste de la ligne est un modèle de ligne de commande à exécuter. Les arguments passés à la commande sont, dans l'ordre, le tagname , operation (c'est-à-dire add pour `tag', mov pour `tag -F', et del pour `tag -d'), repository , et les suivants sont des paires de filename revision . Un code de sortie non nul du programme filtre entraînera l'abandon du tag.

Pour `commitinfo', le reste de la ligne est un modèle de ligne de commande à exécuter. Le modèle peut inclure non seulement un nom de programme, mais aussi toute liste d'arguments que vous souhaitez. Le chemin complet vers le dépôt source actuel est ajouté au modèle, suivi des noms de fichiers impliqués dans le commit (fichiers ajoutés, supprimés et modifiés).

Pour `rcsinfo', le reste de la ligne est le chemin complet vers un fichier qui doit être chargé dans le modèle de message de log.

Pour `editinfo', le reste de la ligne est un modèle de ligne de commande à exécuter. Le modèle peut inclure non seulement un nom de programme, mais aussi toute liste d'arguments que vous souhaitez. Le chemin complet vers le fichier de modèle de message de log actuel est ajouté au modèle.

Vous pouvez utiliser l'une des deux chaînes spéciales suivantes au lieu d'une expression régulière : `ALL' spécifie un modèle de ligne de commande qui doit toujours être exécuté, et `DEFAULT' spécifie un modèle de ligne de commande à utiliser si aucune expression régulière ne correspond.

Le fichier `commitinfo' contient des commandes à exécuter avant toute autre activité de commit , afin de vous permettre de vérifier les conditions qui doivent être satisfaites avant que le commit ne puisse se poursuivre. Le reste du commit ne s'exécutera que si toutes les commandes sélectionnées de ce fichier se terminent avec le code de sortie 0.

Le fichier `rcsinfo' vous permet de spécifier des modèles de log pour la session de journalisation de commit ; vous pouvez l'utiliser pour fournir un formulaire à éditer lors du remplissage du log de commit. Le champ après l'expression régulière, dans ce fichier, contient des noms de fichiers (de fichiers contenant les formulaires de journalisation) plutôt que des modèles de commandes.

Le fichier `editinfo' vous permet d'exécuter un script avant le début du commit, mais après que les informations de log ont été enregistrées. Ces scripts d'« édition » peuvent vérifier les informations enregistrées dans le fichier de log. Si le script d'édition se termine avec un code de sortie non nul, le commit est abandonné.

Le fichier `loginfo' contient des commandes à exécuter à la fin d'un commit. Le texte spécifié comme message de log de commit est transmis via un pipe à la commande ; les utilisations typiques incluent l'envoi de courrier, le dépôt d'un article dans un newsgroup, ou l'ajout à un fichier central.

cvsignore, .cvsignore
La liste par défaut des fichiers (ou motifs de noms de fichiers de sh(1)) à ignorer lors d'uncvs update'. Au démarrage, cvs charge la liste par défaut compilée de motifs de noms de fichiers (voir cvs(1)). Ensuite, la liste par dépôt incluse dans $CVSROOT/CVSROOT/cvsignore est chargée, si elle existe. Ensuite, la liste par utilisateur est chargée depuis `$HOME/.cvsignore'. Enfin, lorsque cvs parcourt vos répertoires, il chargera tous les fichiers `.cvsignore' par répertoire lorsqu'il en trouve un. Ces fichiers par répertoire ne sont valables que pour exactement le répertoire qui les contient, et non pour les sous-répertoires.
history
Créez ce fichier dans $CVSROOT/CVSROOT pour activer la journalisation de l'historique (voir la description de `cvs history').
