NOM

coredumpctl - Récupérer et traiter les vidages de mémoire (core dumps) sauvegardés et leurs métadonnées

SYNTAXE

coredumpctl [OPTIONS...] {COMMANDE} [PID|COMM|EXE|CORRESPONDANCE...]

DESCRIPTION

coredumpctl est un outil qui peut être utilisé pour récupérer et traiter les vidages de mémoire (core dumps) et leurs métadonnées qui ont été sauvegardés par systemd-coredump(8).

COMMANDES

Les commandes suivantes sont comprises :

list

Lister les vidages de mémoire capturés dans le journal correspondant aux caractéristiques spécifiées. Si aucune commande n'est spécifiée, c'est la commande par défaut.

La sortie est conçue pour être lisible par l'homme et contient un tableau avec les colonnes suivantes :

TIME

L'horodatage du crash, tel que rapporté par le noyau.

Ajouté dans la version 233.

PID

L'identifiant du processus qui a crashé.

Ajouté dans la version 233.

UID, GID

Les identifiants d'utilisateur et de groupe du processus qui a crashé.

Ajouté dans la version 233.

SIGNAL

Le signal qui a causé le crash du processus, le cas échéant.

Ajouté dans la version 233.

COREFILE

Informations indiquant si le vidage de mémoire a été sauvegardé et s'il est toujours accessible : « none » signifie que le vidage n'a pas été sauvegardé, « - » signifie qu'il n'était pas disponible (par exemple parce que le processus n'a pas été terminé par un signal), « present » signifie que le fichier de vidage est accessible par l'utilisateur actuel, « journal » signifie que le vidage a été stocké dans le « journal », « truncated » est identique à l'un des deux précédents, mais le vidage était trop volumineux et n'a pas été sauvegardé dans son intégralité, « error » signifie que le fichier de vidage est inaccessible, très probablement en raison d'autorisations insuffisantes, et « missing » signifie que le vidage a été sauvegardé dans un fichier, mais que ce fichier a depuis été supprimé.

Ajouté dans la version 233.

EXE

Le chemin complet de l'exécutable. Pour les backtraces de scripts, il s'agit du nom de l'interpréteur.

Ajouté dans la version 233.

Il convient de noter que différentes restrictions s'appliquent aux données enregistrées dans le journal et aux fichiers de vidage de mémoire sauvegardés dans /var/lib/systemd/coredump ; voir l'aperçu dans systemd-coredump(8). Ainsi, il peut très bien arriver qu'un vidage de mémoire particulier soit toujours répertorié dans le journal, alors que son fichier de vidage de mémoire correspondant a déjà été supprimé.

Ajouté dans la version 215.

info

Afficher des informations détaillées sur le dernier vidage de mémoire ou sur les vidages de mémoire correspondant aux caractéristiques spécifiées, capturés dans le journal.

Ajouté dans la version 215.

dump

Extraire le dernier vidage de mémoire correspondant aux caractéristiques spécifiées. Le vidage de mémoire sera écrit sur la sortie standard, sauf si un fichier de sortie est spécifié avec --output=.

Ajouté dans la version 215.

debug

Invoquer un débogueur sur le dernier vidage de mémoire correspondant aux caractéristiques spécifiées. Par défaut, gdb(1) sera utilisé. Ceci peut être modifié en utilisant l'option --debugger= ou la variable d'environnement $SYSTEMD_DEBUGGER. Utilisez l'option --debugger-arguments= pour passer des arguments de ligne de commande supplémentaires au débogueur.

Ajouté dans la version 239.

OPTIONS

Les options suivantes sont comprises :

-h, --help

Imprimer un court texte d'aide et quitter.

--version

Imprimer une courte chaîne de version et quitter.

--no-pager

Ne pas rediriger la sortie vers un paginator.

--no-legend

Ne pas imprimer la légende, c'est-à-dire les en-têtes de colonne et le pied de page avec les indices.

--json=MODE

Affiche la sortie au format JSON. Attend l'une des valeurs : « short » (pour la sortie la plus courte possible sans espaces superflus ni sauts de ligne), « pretty » (pour une version formatée de la même chose, avec indentation et sauts de ligne) ou « off » (pour désactiver la sortie JSON, par défaut).

-1

Afficher uniquement les informations du vidage de mémoire le plus récent, au lieu de lister tous les vidages de mémoire connus. Équivalent à --reverse -n 1.

Ajouté dans la version 215.

-n INT

Afficher au maximum le nombre d'entrées spécifié. Le paramètre spécifié doit être un entier supérieur ou égal à 1.

Ajouté dans la version 248.

-S, --since

N'imprimer que les entrées depuis la date spécifiée.

Ajouté dans la version 233.

-U, --until

N'imprimer que les entrées jusqu'à la date spécifiée.

Ajouté dans la version 233.

-r, --reverse

Inverser la sortie de sorte que les entrées les plus récentes soient affichées en premier.

Ajouté dans la version 233.

-F CHAMP, --field=CHAMP

Imprimer toutes les valeurs possibles que le champ spécifié prend dans les entrées de vidage de mémoire correspondantes du journal.

Ajouté dans la version 215.

-o FICHIER, --output=FICHIER

Écrire le vidage dans FICHIER.

Ajouté dans la version 215.

--debugger=DEBOGUEUR

Utiliser le débogueur donné pour la commande debug. S'il n'est pas donné et que $SYSTEMD_DEBUGGER est non défini, alors gdb(1) sera utilisé.

Ajouté dans la version 239.

-A ARGUMENTS, --debugger-arguments=ARGUMENTS

Passer les ARGUMENTS donnés comme arguments de ligne de commande supplémentaires au débogueur. Mettre entre guillemets si ARGUMENTS contient des espaces. (Voir les Exemples.)

Ajouté dans la version 248.

--file=GLOB

Prend un glob de fichier comme argument. S'il est spécifié, coredumpctl opérera sur les fichiers journaux spécifiés correspondant à GLOB au lieu des chemins par défaut du journal d'exécution et du système. Peut être spécifié plusieurs fois, auquel cas les fichiers seront entrelacés de manière appropriée.

Ajouté dans la version 246.

-D REP, --directory=REP

Utiliser les fichiers journaux dans le REP spécifié.

Ajouté dans la version 225.

--root=RACINE

Utiliser le répertoire racine RACINE lors de la recherche des vidages de mémoire.

Ajouté dans la version 252.

--image=image

Prend un chemin vers un fichier image disque ou un nœud de périphérique bloc. S'il est spécifié, toutes les opérations sont appliquées au système de fichiers dans l'image disque indiquée. Cette option est similaire à --root=, mais opère sur les systèmes de fichiers stockés dans des images disque ou des périphériques bloc. L'image disque doit contenir soit un seul système de fichiers, soit un ensemble de systèmes de fichiers dans une table de partitions GPT, conformément à la Spécification des partitions détectables[1]. Pour plus d'informations sur les images disque prises en charge, voir le commutateur du même nom dans systemd-nspawn(1).

Ajouté dans la version 252.

--image-policy=politique

Prend une chaîne de politique d'image comme argument, conformément à systemd.image-policy(7). La politique est appliquée lors de l'opération sur l'image disque spécifiée via --image=, voir ci-dessus. Si elle n'est pas spécifiée, elle utilise par défaut la politique « * », c'est-à-dire que tous les systèmes de fichiers reconnus dans l'image sont utilisés.

-q, --quiet

Supprime les messages d'information concernant le manque d'accès aux fichiers journaux et les vidages de mémoire potentiels en cours de traitement.

Ajouté dans la version 233.

--all

Examiner tous les fichiers journaux disponibles dans /var/log/journal/ (à l'exclusion des espaces de noms de journaux) au lieu des seuls journaux locaux.

Ajouté dans la version 250.

EXEMPLE

S

Exemple 1. Lister tous les core dumps d'un

programme 
$ coredumpctl list /usr/lib64/firefox/firefox
TIME       PID  UID  GID SIG     COREFILE EXE
SIZE Tue ... 8018 1000 1000 SIGSEGV missing /usr/lib64/firefox/firefox - Wed ... 251609 1000 1000 SIGTRAP m
issing /usr/lib64/firefox/firefox - Fri ... 552351 1000 1000 SIGSEGV present /usr/lib64/firefox/firefox 28.7M

Le journal contient trois entrées concernant /usr/lib64/firefox/firefox, et seule la dernière entrée dispose encore d'un fichier core (sur le stockage externe du disque)

.

Notez que coredumpctl a besoin d'accéder aux fichiers du journal pour récupérer les entrées pertinentes. Ainsi, un utilisateur non privilégié ne verra normalement que les informations sur les programmes plantés de cet

utilisateur.

Exemple 2. Invoquer gdb sur le dernier core

dump 
$ core
dumpctl
debug

Exemple 3. Utiliser gdb pour afficher les informations complètes des registres du dernier core

dump 
$ coredumpctl debug --deb
ugger-arguments="-batch
-ex 'info all-registers'"
