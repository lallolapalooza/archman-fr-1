coin_multithreading_support - Support multithreadé dans Coin

Le support de Coin pour l'utilisation de plusieurs threads dans les programmes applicatifs et la bibliothèque Coin elle-même, se compose de deux fonctionnalités principales :

•
Coin fournit des classes d'abstraction pour la gestion des threads, indépendantes de la plateforme. Ce sont des classes que le programmeur applicatif peut utiliser librement dans son code pour lancer de nouveaux threads, contrôler leur exécution, travailler avec des mutex et effectuer d'autres tâches liées à la gestion de plusieurs threads.

Les classes en question sont SbThread, SbMutex, SbStorage, SbBarrier, SbCondVar, SbFifo, SbThreadAutoLock, SbRWMutex et SbTypedStorage. Consultez leur documentation respective pour des informations détaillées.

Les classes masquent entièrement l'implémentation spécifique au système, qui est soit basée sur les API natives Win32 (sur Microsoft Windows), soit sur les threads POSIX (sur les systèmes UNIX et similaires).

•
L'autre aspect de notre support multithreadé est que Coin peut être spécialement configuré de manière à ce que les parcours de rendu du graphe de scène soient effectués de manière thread-safe. Cela signifie par exemple qu'il est possible de faire en sorte que Coin rende la scène en parallèle sur plusieurs processeurs pour plusieurs pipelines de rendu, afin de mieux exploiter de tels systèmes haut de gamme (comme les environnements CAVE, par exemple).

Les parcours de rendu thread-safe sont désactivés par défaut, car ils impliquent un léger surcoût qui rendrait le rendu (très) légèrement plus lent dans les invocations mono-threadées.

Pour obtenir une bibliothèque Coin compilée avec le rendu thread-safe, il faut activement reconfigurer Coin et construire une version locale spéciale. Pour les constructions basées sur configure (systèmes UNIX et similaires, ou avec Cygwin sur Microsoft Windows), cela se fait avec l'option "--enable-threadsafe" passée à Autoconf configure. Pour modifier la configuration et reconstruire avec Visual Studio, vous devrez changer la directive de préprocesseur COIN_THREADSAFE pour qu'elle soit définie dans le fichier src/setup.h situé dans le même dossier que celui où vous avez trouvé votre fichier solution.

Il y a quelques restrictions et autres points qu'il est important de garder à l'esprit :

  • Nous ne fournissons pas encore de support pour intégrer le support de rendu multithreadé dans les bindings GUI SoQt / SoWin / etc, et nous ne fournissons pas non plus de bindings contre des bibliothèques spécifiques gérant le rendu multi-pipeline. Cela signifie que le programmeur applicatif devra posséder une certaine expertise et faire des efforts pour pouvoir utiliser le rendu multi-pipeline avec Coin.
  • Les parcours de rendu sont actuellement la seule opération que nous supportons publiquement comme étant thread-safe. Il y a d'autres aspects de Coin que nous savons être thread-safe, comme la plupart des autres parcours d'actions au-delà du simple rendu, mais nous ne faisons aucune garantie à cet égard.
  • Soyez prudent lorsque vous utilisez un thread distinct pour modifier les structures Coin par rapport à celui utilisé pour le thread d'événements GUI de l'application.

Nous sommes conscients d'au moins des problèmes avec Qt3 (et donc SoQt), où vous ne devriez pas modifier le graphe de scène de quelque manière que ce soit dans un thread distinct du thread Qt principal. En effet, cela déclenche des opérations où Qt3 n'est pas thread-safe. Pour Qt4, nous n'avons pas eu connaissance de tels problèmes.
