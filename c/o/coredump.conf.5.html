DESCRIPTIO

N

Ces fichiers configurent le comportement de systemd-coredump(8), un gestionnaire de core dumps invoqué par le noyau. Que systemd-coredump soit utilisé est déterminé par le réglage kernel.core_pattern sysctl(8) du noyau. Voir les pages systemd-coredump(8) et core(5) pour

les dé
tails.

RÉPERTOIRES DE CONFIGURATION ET

PRÉCÉDENCE

La configuration par défaut est définie lors de la compilation ; une configuration n'est donc nécessaire que lorsqu'il faut s'écarter de ces valeurs par défaut. Le fichier de configuration principal est chargé depuis l'un des répertories listés par ordre de priorité ; seul le premier fichier trouvé est utilisé : /etc/systemd/, /run/systemd/, /usr/local/lib/systemd/ [1], /usr/lib/systemd/. La version du fichier fournie par le fournisseur contient des entrées commentées montrant les valeurs par défaut, à titre de guide pour l'administrateur. Des surcharges locales peuvent également être créées en créant des drop-ins, comme décrit ci-dessous. Le fichier de configuration principal peut également être modifié à cette fin (ou une copie dans /etc/ s'il est livré sous /usr/), cependant l'utilisation de drop-ins pour la configuration locale est recommandée plutôt que la modification du fichier de configuration

principal.

En plus du fichier de configuration principal, des extraits de configuration drop-in sont lus depuis /usr/lib/systemd/*.conf.d/, /usr/local/lib/systemd/*.conf.d/ et /etc/systemd/*.conf.d/. Ces drop-ins ont une priorité plus élevée et remplacent le fichier de configuration principal. Les fichiers dans les sous-répertoires de configuration *.conf.d/ sont triés par leur nom de fichier dans l'ordre lexicographique, quel que soit le sous-répertoire dans lequel ils se trouvent. Lorsque plusieurs fichiers spécifient la même option, pour les options qui n'acceptent qu'une seule valeur, l'entrée du fichier trié en dernier prend la priorité, et pour les options qui acceptent une liste de valeurs, les entrées sont collectées telles qu'elles apparaissent dans les fichiers

triés.

Lorsque les paquets doivent personnaliser la configuration, ils peuvent installer des drop-ins sous /usr/. Les fichiers dans /etc/ sont réservés à l'administrateur local, qui peut utiliser cette logique pour remplacer les fichiers de configuration installés par les paquets du fournisseur. Des drop-ins doivent être utilisés pour remplacer les drop-ins de paquets, car le fichier de configuration principal a une priorité plus faible. Il est recommandé de préfixer tous les noms de fichiers dans ces sous-répertoires d'un nombre à deux chiffres et d'un tiret, pour simplifier le tri. Cela définit également un concept de priorités de drop-ins pour permettre aux fournisseurs de systèmes d'exploitation de livrer des drop-ins dans une plage spécifique inférieure à celle utilisée par les utilisateurs. Cela devrait réduire le risque que les drop-ins de paquets remplacent accidentellement des drop-ins définis par les utilisateurs. Il est recommandé d'utiliser la plage 10-40 pour les drop-ins dans /usr/ et la plage 60-90 pour les drop-ins dans /etc/ et /run/, afin de s'assurer que les drop-ins locaux et transitoires prennent la priorité sur les drop-ins livrés par le fournisseur du système

d'exploitation.

Pour désactiver un fichier de configuration fourni par le fournisseur, la méthode recomm

andée est de placer un lien symbolique vers /dev/null dans le répertoire de configuration
dans /etc/, avec le même nom de fichier que le fichier de configuration du fournisseur.

OPTION

S

Toutes les options sont configurées dans la section [Coredump]

:

Storage

=
Contrôle où stocker les cores. L'une des valeurs "none", "external" et "journal". Avec "none", les core dumps peuvent être journalisés (y compris la trace d'appels si possible), mais pas stockés de manière permanente. Avec "external" (par défaut), les cores seront stockés dans /var/lib/systemd/coredump/. Avec "journal", les cores seront stockés dans le journal et tournés selon les schémas de rotation normaux du journal.

Lorsque les cores sont stockés dans le journal, ils peuvent être compressés selon les paramètres de compression du journal, voir journald.conf(5). Lorsque les cores sont stockés en externe, ils seront compressés par défaut, voir

ci-dessous.

Notez que pour traiter un coredump (c'est-à-dire extraire une trace d'appels), le core doit d'abord être écrit sur le disque. Ainsi, sauf si ProcessSizeMax= est défini à 0 (voir ci-dessous), le core sera écrit dans /var/lib/systemd/coredump/ dans tous les cas (sous un nom de fichier temporaire, ou même dans un fichier déjà délié), Storage= ne contrôle donc que s'il faut le laisser là même après son

traitement.

Compress

=
Contrôle la compression pour le stockage externe. Prend un argument booléen, dont la valeur par défaut est "yes".

ProcessSizeMax

=
La taille maximale en octets d'un core qui sera traité. Les core dumps dépassant cette taille peuvent être stockés, mais la trace d'appels ne sera pas générée. Comme les autres tailles dans ce même fichier de configuration, les suffixes usuels sur la base de 1024 sont autorisés (B, K, M, G, T, P et E). Valeur par défaut : 1G sur les systèmes 32 bits, 32G sur les systèmes 64 bits.

Définir Storage=none et ProcessSizeMax=0 désactive tout traitement des coredumps à l'exception d'une entrée de

journal.

ns la ver
sion 215.

EnterNamespace

=
Pour les processus appartenant à un espace de noms PID, contrôle si systemd-coredump(8) doit tenter de traiter les core dumps sur l'hôte, en utilisant les informations de débogage de la hiérarchie du système de fichiers (c'est-à-dire l'espace de noms de montage) du processus qui a planté. L'accès à la hiérarchie du système de fichiers du processus peut être nécessaire pour générer une trace d'appels entièrement symbolisée. Si défini à "yes", systemd-coredump obtiendra l'arbre des montages depuis l'espace de noms de montage du processus qui a planté et essaiera de générer la trace d'appels dans le contexte de l'hôte en utilisant les informations de débogage des binaires et bibliothèques contenus dans la hiérarchie du processus qui a planté. Valeur par défaut : "no", c'est-à-dire aucune tentative n'est faite pour acquérir des informations de débogage externes depuis l'espace de noms de montage du processus, afin de maximiser la sécurité. Cette option n'a aucun effet sur les processus qui font partie de l'espace de noms PID de l'hôte.

Notez que le coredump du processus dans l'espace de noms est toujours enregistré dans /var/lib/systemd/coredump/ sur l'hôte même si EnterNamespace= est défini à "no" (sous réserve de Storage

=).

Notez que EnterNamespace= n'a un effet que si un core dump est généré par un conteneur dont l'unité n'a pas CoredumpReceive=

activé.

Notez qu'il est généralement préférable de laisser les conteneurs et autres bac à sable basés sur les espaces de noms traiter leurs propres coredumps, si possible, pour une meilleure sécurité. Cela peut être activé sur l'unité du conteneur via le paramètre CoredumpReceive=, voir systemd.resource-control(5) pour les

détails.

ExternalSizeMax=, JournalSizeMax

=
La taille maximale (compressée ou non compressée) en octets d'un coredump à enregistrer dans des fichiers séparés sur le disque (par défaut : 1G sur les systèmes 32 bits, 32G sur les systèmes 64 bits) ou dans le journal (par défaut : 767M). Notez que le service journal applique une limite stricte de 767M sur les enregistrements de journal et ignorera les enregistrements plus grands soumis. Par conséquent, JournalSizeMax= peut être abaissé par rapport à la valeur par défaut, mais pas augmenté. Les suffixes d'unité sont autorisés tout comme dans ProcessSizeMax=.

ExternalSizeMax=infinity définit la taille du core à

illimitée.

ns la ver
sion 215.

MaxUse=, KeepFree

=
Applique des limites sur l'espace disque, spécifié en octets, occupé par les core dumps stockés en externe. Les suffixes d'unité sont autorisés tout comme dans ProcessSizeMax=. MaxUse= s'assure que les anciens core dumps sont supprimés dès que l'espace disque total occupé par les core dumps dépasse cette limite (valeur par défaut : 10 % de la taille totale du disque). KeepFree= contrôle combien d'espace disque garder au moins libre (valeur par défaut : 15 % de la taille totale du disque). Notez que l'espace disque utilisé par les core dumps peut temporairement dépasser ces limites pendant le traitement des core dumps. Notez que les anciens core dumps sont égalementvidé en fonction du temps via systemd-tmpfiles(8). Définissez l'une ou l'autre valeur à 0 pour désactiver le nettoyage basé sur la taille.
