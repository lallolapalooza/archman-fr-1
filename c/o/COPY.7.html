DESCRIPTIO

N

COPY déplace des données entre les tables PostgreSQL et les fichiers du système de fichiers standard. COPY TO copie le contenu d'une table vers un fichier, tandis que COPY FROM copie des données d'un fichier vers une table (en ajoutant les données à ce qui se trouve déjà dans la table). COPY TO peut également copier les résultats d'une requête SE

LECT.

Si une liste de colonnes est spécifiée, COPY TO ne copie que les données des colonnes spécifiées dans le fichier. Pour COPY FROM, chaque champ du fichier est inséré, dans l'ordre, dans la colonne spécifiée. Les colonnes de table non spécifiées dans la liste de colonnes de COPY FROM recevront leurs valeurs par

défaut.

COPY avec un nom de fichier indique au serveur PostgreSQL de lire directement depuis ou d'écrire vers un fichier. Le fichier doit être accessible par l'utilisateur PostgreSQL (l'identifiant utilisateur sous le quel le serveur s'exécute) et le nom doit être spécifié du point de vue du serveur. Lorsque PROGRAM est spécifié, le serveur exécute la commande donnée et lit depuis la sortie standard du programme, ou écrit vers l'entrée standard du programme. La commande doit être spécifiée du point de vue du serveur et être exécutable par l'utilisateur PostgreSQL. Lorsque STDIN ou STDOUT est spécifié, les données sont transmises via la connexion entre le client et le

serveur.

Chaque processus serveur exécutant COPY signalera sa progression dans la vue pg_stat_progress_copy. Voir la section 27.4.3 pour plus de

détails.

Par défaut, COPY échouera s'il rencontre une erreur pendant le traitement. Pour les cas d'utilisation où une tentative au mieux pour

charger l'intégralité du fichier est souhaitée, la clause ON_ER
ROR peut être utilisée pour spécifier un autre comportement.

NOTE

S

COPY TO peut être utilisé avec des tables simples et des vues matérialisées peuplées. Par exemple, COPY table TO copie les mêmes lignes que SELECT * FROM ONLY table. Cependant, il ne prend pas directement en charge d'autres types de relations, comme les tables partitionnées, les tables filles d'héritage ou les vues. Pour copier toutes les lignes de telles relations, utilisez COPY (SELECT * FROM table)

TO.

COPY FROM peut être utilisé avec des tables simples, étrangères ou partitionnées, ou avec des vues ayant des déclencheurs INSTEAD OF

INSERT.

Vous devez avoir le privilège select sur la table dont les valeurs sont lues par COPY TO, et le privilège insert sur la table dans laquelle les valeurs sont insérées par COPY FROM. Il suffit d'avoir les privilèges de colonne sur la ou les colonnes listées dans la

commande.

Si la sécurité au niveau des lignes est activée pour la table, les politiques SELECT pertinentes s'appliqueront aux instructions COPY table TO. Actuellement, COPY FROM n'est pas pris en charge pour les tables avec sécurité au niveau des lignes. Utilisez des instructions INSERT équivalentes à la

place.

Les fichiers nommés dans une commande COPY sont lus ou écrits directement par le serveur, et non par l'application client. Par conséquent, ils doivent se trouver sur la machine du serveur de base de données ou y être accessibles, et non sur le client. Ils doivent être accessibles et lisibles ou inscriptibles par l'utilisateur PostgreSQL (l'identifiant utilisateur sous lequel le serveur s'exécute), et non par le client. De même, la commande spécifiée avec PROGRAM est exécutée directement par le serveur, et non par l'application client, et doit être exécutable par l'utilisateur PostgreSQL. COPY nommant un fichier ou une commande n'est autorisé que pour les superutilisateurs de la base de données ou les utilisateurs à qui l'un des rôles pg_read_server_files, pg_write_server_files ou pg_execute_server_program est accordé, car cela permet de lire ou d'écrire n'importe quel fichier ou d'exécuter un programme auquel le serveur a les privilèges

d'accès.

Ne confondez pas COPY avec l'instruction psql \copy. \copy invoque COPY FROM STDIN ou COPY TO STDOUT, puis récupère/enregistre les données dans un fichier accessible au client psql. Ainsi, l'accessibilité des fichiers et les droits d'accès dépendent du client plutôt que du serveur lorsque \copy est

utilisé.

Il est recommandé que le nom de fichier utilisé dans COPY soit toujours spécifié comme un chemin absolu. Cela est imposé par le serveur dans le cas de COPY TO, mais pour COPY FROM vous avez la possibilité de lire depuis un fichier spécifié par un chemin relatif. Le chemin sera interprété relativement au répertoire de travail du processus serveur (normalement le répertoire de données du cluster), et non au répertoire de travail du

client.

L'exécution d'une commande avec PROGRAM peut être restreinte par les mécanismes de contrôle d'accès du système d'exploitation, tels que

SELinux.

COPY FROM invoquera tous les déclencheurs et vérifiera les contraintes sur la table de destination. Cependant, il n'invoquera pas les

règles.

Pour les colonnes d'identité, la commande COPY FROM écrira toujours les valeurs de colonne fournies dans les données d'entrée, comme l' option OVERRIDING SYSTEM VALUE de

INSERT.

L'entrée et la sortie de COPY sont affectées par DateStyle. Pour assurer la portabilité vers d'autres installations PostgreSQL qui pourraient utiliser des paramètres DateStyle non par défaut, DateStyle devrait être défini sur ISO avant d'utiliser COPY TO. C'est aussi une bonne idée d'éviter de dumper des données avec IntervalStyle défini sur sql_standard, car les valeurs d'intervalle négatives pourraient être mal interprétées par un serveur ayant un paramètre différent pour IntervalStyle

.

Les données d'entrée sont interprétées selon l'option ENCODING ou l'encodage client actuel, et les données de sortie sont encodées en ENCODING ou l'encodage client actuel, même si les données ne passent pas par le client mais sont lues depuis ou écrites dans un fichier directement par le

serveur.

La commande COPY FROM insère physiquement les lignes d'entrée dans la table au fur et à mesure de son avancement. Si la commande échoue, ces lignes sont laissées dans un état supprimé ; ces lignes ne seront pas visibles, mais occuperont toujours de l'espace disque. Cela peut représenter une quantité considérable d'espace disque gaspillé si l'échec s'est produit bien avancé dans une grande opération de copie. VACUUM devrait être utilisé pour récupérer l'espace

gaspillé.

FORCE_NULL et FORCE_NOT_NULL peuvent être utilisés simultanément sur la mê

me colonne. Cela résulte en la conversion des chaînes nulles entre guillemets
en valeurs nulles et des chaînes nulles sans guillemets en chaînes vides.

Format

texte

Lorsque le format texte est utilisé, les données lues ou écrites sont un fichier texte avec une ligne par ligne de table. Les colonnes dans une ligne sont séparées par le caractère délimiteur. Les valeurs des colonnes elles-mêmes sont des chaînes générées par la fonction de sortie, ou acceptables par la fonction d'entrée, du type de données de chaque attribut. La chaîne nulle spécifiée est utilisée à la place des colonnes qui sont nulles. COPY FROM lèvera une erreur si une ligne du fichier d'entrée contient plus ou moins de colonnes que

prévu.

La fin des données peut être représentée par une ligne contenant uniquement le point-virgule arrière (\.). Un marqueur de fin de données n'est pas nécessaire lors de la lecture depuis un fichier, car la fin de fichier convient parfaitement ; dans ce contexte, cette disposition n'existe que pour la compatibilité ascendante. Cependant, psql utilise \. pour terminer une opération COPY FROM STDIN (c'est-à-dire la lecture de données COPY en ligne dans un script SQL). Dans ce contexte, la règle est nécessaire pour pouvoir terminer l'opération avant la fin du

script.

Les caractères de barre oblique inverse (\) peuvent être utilisés dans les données COPY pour échapper des caractères de données qui pourraient autrement être pris comme délimiteurs de ligne ou de colonne. En particulier, les caractères suivants doivent être précédés d'une barre oblique inverse s'ils apparaissent dans une valeur de colonne : la barre oblique inverse elle-même, le saut de ligne, le retour de chariot et le caractère délimiteur

actuel.

La chaîne nulle spécifiée est envoyée par COPY TO sans ajouter de barres oblique inverse ; inversement, COPY FROM compare l'entrée à la chaîne nulle avant de supprimer les barres oblique inverse. Par conséquent, une chaîne nulle telle que \N ne peut pas être confondue avec la valeur de donnée réelle \N (qui serait représentée comme \\N)

.

Tout autre caractère avec barre oblique inverse qui n'est pas mentionné dans le tableau ci-dessus sera considéré comme représentant lui-même. Cependant, faites attention à ne pas ajouter de barres oblique inverse inutrily, car cela pourrait accidentellement produire une chaîne correspondant au marqueur de fin de données (\.) ou à la chaîne nulle (\N par défaut). Ces chaînes seront reconnues avant tout autre traitement des barres obliques

Il est fortement recommandé que les applications générant des données COPY convertissent les retours à la ligne et les retours chariot des données en les séquences \n et \r respectivement. Actuellement, il est possible de représenter un retour chariot de données par une barre oblique inverse et un retour chariot, et de représenter un retour à la ligne de données par une barre oblique inverse et un retour à la ligne. Cependant, ces représentations pourraient ne pas être acceptées dans les futures versions. Elles sont également très vulnérables à la corruption si le fichier COPY est transféré entre différentes machines (par exemple, de Unix vers Windows ou inversement)

.

Toutes les séquences de barres obliques inversées sont interprétées après la conversion d'encodage. Les octets spécifiés avec les séquences de barres obliques inversées octales et hexadécimales doivent former des caractères valides dans l'encodage de la base de

données.

COPY TO terminera chaque ligne avec un retour à la ligne de style Unix (“\n”). Les serveurs fonctionnant sur Microsoft Windows produisent à la place un retour chariot/retour à la ligne (“\r\n”), mais seulement pour COPY vers un fichier serveur ; par cohérence entre les plateformes, COPY TO STDOUT envoie toujours “\n” quel que soit le plateforme du serveur. COPY FROM peut gérer les lignes se terminant par des retours à la ligne, des retours chariot, ou des retours chariot/retours à la ligne. Pour réduire le risque d'erreur dû à des retours à la ligne ou des retours chariot sans barre oblique inverse qui étaient destinés à être des données, COPY FROM se plaindra si les fins de ligne

dans l'entrée ne sont
pas toutes identiques.

Format

CSV

Cette option de format est utilisée pour importer et exporter le format de fichier Valeurs Séparées par des Virgules (CSV) utilisé par de nombreux autres programmes, tels que les tableurs. Au lieu des règles d'échappement utilisées par le format texte standard de PostgreSQL, il produit et reconnaît le mécanisme d'échappement CSV

commun.

Les valeurs dans chaque enregistrement sont séparées par le caractère DELIMITER. Si la valeur contient le caractère délimiteur, le caractère QUOTE, la chaîne NULL, un retour chariot ou un caractère de saut de ligne, alors la valeur entière est préfixée et suffixée par le caractère QUOTE, et toute occurrence dans la valeur d'un caractère QUOTE ou du caractère ESCAPE est précédée du caractère d'échappement. Vous pouvez également utiliser FORCE_QUOTE pour forcer les guillemets lors de la sortie de valeurs non-NULL dans des colonnes

spécifiques.

Le format CSV n'a pas de moyen standard de distinguer une valeur NULL d'une chaîne vide. PostgreSQL COPY gère cela par le biais des guillemets. Un NULL est produit comme la chaîne paramètre NULL et n'est pas entouré de guillemets, tandis qu'une valeur non-NULL correspondant à la chaîne paramètre NULL est entourée de guillemets. Par exemple, avec les paramètres par défaut, un NULL est écrit comme une chaîne vide sans guillemets, tandis qu'une valeur de données chaîne vide est écrite avec des guillemets doubles (""). La lecture des valeurs suit des règles similaires. Vous pouvez utiliser FORCE_NOT_NULL pour empêcher les comparaisons d'entrée NULL pour des colonnes spécifiques. Vous pouvez également utiliser FORCE_NULL pour convertir les valeurs de données de chaîne nulle entourées de guillemets en

NULL.

Parce que la barre oblique inverse n'est pas un caractère spécial dans le format CSV, le marqueur de fin de données utilisé en mode texte (\.) n'est normalement pas traité comme spécial lors de la lecture de données CSV. Une exception est que psql terminera une opération COPY FROM STDIN (c'est-à-dire la lecture de données COPY en ligne dans un script SQL) à une ligne contenant uniquement \., que ce soit en mode texte ou CSV

.

Note

Les versions de PostgreSQL antérieures à la v18 reconnaissaient toujours \. non entouré de guillemets comme un marqueur de fin de données, même lors de la lecture depuis un fichier séparé. Pour compatibilité avec les versions plus anciennes, COPY TO entourera \. de guillemets lorsqu'il est

seul sur une ligne, même si
ce n'est plus nécessaire.

Note

Au format CSV, tous les caractères sont significatifs. Une valeur entourée de guillemets entourée d'espaces blancs, ou de tout autre caractère que DELIMITER, inclura ces

caractères. Cela peut causer des erreurs si vous importez des données depuis un système qui remplit les lignes CSV d'espaces blancs jusqu'à une certaine largeur fixe. Si une
telle situation survient, vous pourriez avoir besoin de prétraiter le fichier CSV pour supprimer les espaces blancs de fin, avant d'importer les données dans PostgreSQL.

Note

Le format CSV reconnaîtra et produira à la fois des fichiers CSV avec des valeurs entourées

de guillemets contenant des retours chariot et des retours à la ligne intégrés. Ainsi, les fichi
ers ne sont pas strictement une ligne par ligne de table comme les fichiers au format texte.

Note

De nombreux programmes produisent des fichiers CSV étranges et parfois pervers, de sorte que le format de fichier est plus une convention qu'un standard. Ainsi, vous pourriez rencontrer certains fichiers qui ne peuvent pas être importés à l'aide de ce mécanisme, et COPY pourrait produire des fichie

Format

Binaire

L'option de format binaire fait que toutes les données sont stockées/lues au format binaire plutôt que sous forme de texte. C'est un peu plus rapide que les formats texte et CSV, mais un fichier au format binaire est moins portable entre les architectures de machines et les versions de PostgreSQL. De plus, le format binaire est très spécifique au type de données ; par exemple, il ne fonctionnera pas de produire des données binaires à partir d'une colonne smallint et de les lire dans une colonne integer, même si cela fonctionnerait très bien au format

texte.

Le format de fichier binaire se compose d'un en-tête de fichier, de zéro ou plusieurs tuples contenant les données de ligne, et d'un pied de fichier. Les en-têtes et les données sont dans l'ordre d'octets

réseau.

Note

Les versions de PostgreSQL antéri

eures à 7.4 utilisaient un format
de fichier binaire différent.

En-tête de fichier

L'en-tête de fichier se compose de 15 octets de champs fixes, suivis d'une zone d'extension d'en-tête de longueur variable. Les champs fixes sont

:

e

(La signature est conçue pour permettre l'identification facile des fichiers qui ont été altérés par un transfert non transparent aux 8 bits. Cette signature sera modifiée par des filtres de traduction de fin de ligne, des octets zéro supprimés, des bits de poids fort supprimés, ou des changements de parité.
)

Champ de

drapeaux
Masque de bits d'entier sur 32 bits pour indiquer des aspects importants du format de fichier. Les bits sont numérotés de 0 (LSB) à 31 (MSB). Notez que ce champ est stocké dans l'ordre d'octets réseau (l'octet de poids significatif en premier), comme le sont tous les champs d'entiers utilisés dans le format de fichier. Les bits 16–31 sont réservés pour indiquer des problèmes critiques de format de fichier ; un lecteur doit interrompre s'il trouve un bit inattendu défini dans cette plage. Entier sur 32 bits, longueur en octets du reste de l'en-tête, n'incluant pas lui-même. Actuellement, ceci est zéro, et le premier tuple suit immédiatement. La zone d'extension d'en-tête est conçue pour contenir une séquence de blocs auto-identifiants. Le champ de drapeaux n'est pas destiné à indiquer aux lecteurs ce qui se trouve dans la zone d'extension. La conception spécifique du contenu de l'extension d'en-tête est laissée pour une version

Cette conception permet à la fois des ajouts d'en-tête rétrocompatibles (ajouter des blocs d'extension d'en-tête, ou

Tuples

Chaque tuple commence par un entier sur 16 bits donnant le nombre de champs dans le tuple. (Actuellement, tous les tuples d'une table auront le même nombre, mais cela pourrait ne pas toujours être le cas.) Ensuite, répété pour chaque champ dans le tuple, il y a un mot de longueur sur 32 bits suivi d'autant d'octets de données de champ. (Le mot de longueur n'inclut pas lui-même, et peut être zéro.) Comme cas spécial, -1 indique une valeur de champ NULL. Aucun octet de valeur ne suit dans le cas

NULL.

Il n'y a pas d'alignement de remplissage ni aucune autre donnée supplémentaire entre les

champs.

Actuellement, toutes les valeurs de données dans un fichier au format binaire sont supposées être au format binaire (code de format un). On anticipe qu'une future extension pourrait ajouter un champ d'en-tête permettant de spécifier des codes de format par

colonne.

Pour déterminer le format binaire approprié pour les données de tuple réelles, vous devriez consulter la source de PostgreSQL, en particulier les fonctions *send et *recv pour chaque type de données de colonne (généralement, ces fonctions se trouvent dans le répertoire src/backend/utils/adt/ de la distribution source)

.

Si les OIDs sont inclus dans le fichier, le champ OID suit immédiatement le mot du nombre de c

hamps. C'est un champ normal sauf qu'il n'est pas inclus dans le nombre de champs. Notez que le
s colonnes système oid ne sont pas prises en charge dans les versions actuelles de PostgreSQL.

Le pied de fichier se compose d'un mot entier sur 16 bits contenant -1. Celui-ci est facilement distinguable du mot du nombre de champs d'un

tuple.
