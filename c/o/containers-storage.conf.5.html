:

TABLE

STORAGE

La table storage prend en charge les options suivantes

:

driver=""
Pilote de stockage de conteneurs Copy On Write (COW). Les pilotes valides sont "overlay", "vfs", "btrfs" et "zfs". Certains pilotes (par exemple "zfs" et "btrfs") peuvent ne pas fonctionner si votre noyau ne prend pas en charge le système de fichiers. Ce champ est requis pour garantir un fonctionnement correct. Les pilotes valides en mode sans racine (rootless) sont "btrfs", "overlay" et "vfs". Les utilisateurs sans racine utilisent par défaut le pilote défini dans la configuration système lorsque c'est possible. Lorsque la configuration système utilise un pilote sans racine non pris en charge, les utilisateurs sans racine utilisent par défaut "overlay" s'il est disponible, sinon

"vfs".

graphroot=""
Répertoire du graphe de stockage des conteneurs (par défaut : "/var/lib/containers/storage") Répertoire par défaut pour stocker tout le contenu inscriptible créé par les programmes de stockage de conteneurs. Le chemin graphroot sans racine prend en charge les substitutions de variables d'environnement (c.-à-d. $HOME/containers/storage). Lors du changement de l'emplacement de graphroot sur un système SELINUX, assurez-vous que l'étiquetage corresponde aux étiquettes des emplacements par défaut avec les commandes suivantes

: 
# semanage fcontext -a -e /var/lib/containers/storage /NEWSTORAGEPATH
# restorecon -R -v
/NEWSTORAGEPATH

En mode sans racine, vous

définiriez 
# semanage fcontext -a -e $HOME/.local/share/containers NEWSTORAGEPATH
$ restorecon -R -v
/NEWSTORAGEPATH

rootless_storage_path="$HOME/.local/share/containers/storage"
Chemin de stockage pour les utilisateurs sans racine. Par défaut, le graphroot pour les utilisateurs sans racine est défini sur $XDG_DATA_HOME/containers/storage, si XDG_DATA_HOME est défini. Sinon $HOME/.local/share/containers/storage est utilisé. Ce champ peut être utilisé si les administrateurs doivent changer l'emplacement de stockage pour tous les utilisateurs. Le chemin de stockage sans racine prend en charge les substitutions de variables d'environnement (c.-à-d. $HOME/containers/storage

)

Un cas d'utilisation courant de ce champ est de fournir un répertoire de stockage local lorsque les répertoires personnels des utilisateurs sont montés via NFS (podman ne prend pas en charge le stockage de conteneurs sur NFS)

.

imagestore=""
Le chemin de stockage des images (par défaut, on suppose qu'il est le même que graphroot). Chemin de l'imagestore, qui est différent de graphroot. Par défaut, les images dans la bibliothèque de stockage sont stockées dans le graphroot. Si imagestore est fourni, les images nouvellement extraites seront stockées dans l'emplacement imagestore. Tout autre stockage continue d'être stocké dans le graphroot. Lors de l'utilisation du pilote overlay, les images précédemment stockées dans le graphroot restent accessibles. En interne, la bibliothèque de stockage monte graphroot en tant que additionalImageStore pour permettre ce

comportement.

Un cas d'utilisation courant du champ imagestore est pour les utilisateurs qui doivent diviser les systèmes de fichiers dans différentes partitions. La partition imagestore stocke les images et la partition graphroot stocke le contenu des conteneurs créé à partir des

images.

Imagestore, s'il est défini, doit être différent de graphroot

.

runroot=""
Répertoire d'exécution du stockage des conteneurs (par défaut : "/run/containers/storage") Répertoire par défaut pour stocker tout le contenu temporaire inscriptible créé par les programmes de stockage de conteneurs. Le chemin runroot sans racine prend en charge les substitutions de variables d'environnement (c.-à-d. $HOME/containers/storage

)

driver_priority=[]
Liste de priorité des pilotes de stockage qui seront testés les uns après les autres pour choisir le pilote de stockage s'il n'est pas défini. Le premier pilote de stockage de cette liste qui peut être utilisé sera choisi comme nouveau, et tous les suivants ne seront pas essayés. Si tous les pilotes de cette liste ne sont pas viables, alors tous les pilotes connus seront essayés et le premier fonctionnel sera choisi. Par défaut, le pilote de stockage est défini via l'option driver. S'il n'est pas défini, le meilleur pilote sera choisi en fonction de la plateforme actuelle. Cette option vous permet de remplacer cette liste de priorité interne par une liste personnalisée pour préférer certains pilotes. Définir cette option n'a d'effet que si le stockage local n'a pas encore été initialisé et que le nom du pilote n'est pas

défini.

transient_store =

"false"|"true"

Le mode de stockage transitoire fait que toutes les métadonnées des conteneurs sont enregistrées dans un stockage temporaire (c.-à-d. runroot ci-dessus). C'est plus rapide, mais ne persiste pas après un redémarrage. Une collecte de déchets supplémentaire doit également être effectuée au démarrage, donc cette option doit rester désactivée dans la plupart des configurations. (par défaut :

false)

TABLE OPTIONS

STORAGE

La table storage.options prend en charge les options suivantes

:

additionalimagestores=[]
Chemins vers des magasins d'images de conteneurs supplémentaires. Généralement, ceux-ci sont en lecture seule et stockés sur des partages réseau

distants.

root-auto-userns-user=""
Root-auto-userns-user est un nom d'utilisateur qui peut être utilisé pour rechercher une ou plusieurs plages UID/GID dans les fichiers /etc/subuid et /etc/subgid. Ces plages seront réparties entre les conteneurs configurés pour créer automatiquement un espace de noms utilisateur. Les conteneurs configurés pour créer automatiquement un espace de noms utilisateur peuvent toujours se chevaucher avec les conteneurs ayant une correspondance explicite définie. Ce paramètre est ignoré lors de l'exécution en mode sans

racine.

auto-userns-min-size=1024
Auto-userns-min-size est la taille minimale d'un espace de noms utilisateur créé automatiquement

.

auto-userns-max-size=65536
Auto-userns-max-size est la taille maximale d'un espace de noms utilisateur créé automatiquement

.

disable-volatile=true
Si disable-volatile est défini, alors l'

optimisation de montage "volatile"
est désactivée pour tous les conteneurs.

Chemin vers un dépôt ostree qui pourrait avoir

convert_images="false"|"true"
Si défini à "true", containers/storage convertira les images qui ne sont
pas déjà au format zstd:chunked en ce format avant le traitement
afin de tirer parti de la déduplication locale et des liens physiques.
C'est une opération coûteuse, donc elle n'est pas activée par défaut.
C'est un "booléen sous forme de chaîne" : "false"|"true" (ne peut pas être un booléen TOML

natif)

insecure_allow_unpredictable_image_contents="false"|"true"
Cela ne devrait presque jamais être défini.
Cela permet des extractions partielles d'imagessans garantir que les « tirages partiels »
et les tirages non partiels aboutissent tous deux à des contenus d'image cohérents. Cela
permet de tirer des images estargz et des premières versions d'images zstd:chunked ; sinon, ces
couches utilisent toujours le chemin traditionnel de tirage non partiel. Cette option

doit

être activée extrêmement rarement, uniquement si toutes les images qui pourraient ÉVENTUELLEMENT être
tirées sur ce système sont garanties (par exemple à l'aide d'une politique de signature) provenir d'un système
de construction réputé ne jamais attaquer l'intégrité des images. Si cette

vérification

de cohérence était désactivée, des images malveillantes pourraient être construites de manière
à contourner d'autres mécanismes d'audit, de sorte que la présence de la plupart des autres mécanismes
d'audit ne remplace pas la nécessité mentionnée ci-dessus pour que toutes les images proviennent d'un
système de construction de confiance.

En
