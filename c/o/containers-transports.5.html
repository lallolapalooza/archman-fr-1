NOM

containers-transports - description des transports supportés pour la copie et le stockage des images de conteneurs

DESCRIPTION

Les outils qui utilisent la bibliothèque containers/image, y compris skopeo(1), buildah(1), podman(1), partagent tous une syntaxe commune pour référencer les images de conteneurs dans divers emplacements. La forme générale de la syntaxe est transport:détails, où les détails dépendent du transport spécifié, qui sont documentés ci-dessous.

La sémantique des noms d'image dépend finalement de l'environnement où ils sont évalués. Par exemple : s'ils sont évalués sur un serveur distant, les noms d'image peuvent faire référence à des chemins sur ce serveur ; les chemins relatifs sont relatifs au répertoire courant du consommateur d'image.

containers-storage:[[spécificateur-de-stockage]]{id-image|référence-docker[@id-image]}

Une image située dans un stockage local de conteneurs. Le format de référence-docker est décrit en détail dans le transport docker.

Le spécificateur-de-stockage permet de référencer des emplacements de stockage sur le système de fichiers et a le format [[driver@]root[+run-root][:options]] où le driver optionnel fait référence au pilote de stockage (par exemple, overlay ou btrfs) et où root est un chemin absolu vers le répertoire racine du stockage. Le run-root optionnel peut être utilisé pour spécifier le répertoire d'exécution du stockage où tout le contenu temporaire inscriptible est stocké. Les options optionnelles sont une liste d'options spécifiques au pilote séparées par des virgules. Veuillez vous référer à containers-storage.conf(5) pour plus d'informations sur les pilotes et les options supportés.

dir:chemin

Un répertoire local existant chemin stockant le manifeste, les fichiers tar des couches et les signatures sous forme de fichiers individuels. Ceci est un format non standardisé, principalement utile pour le débogage ou l'inspection non invasive de conteneurs.

docker://référence-docker

Une image dans un registre implémentant l'"API HTTP V2 du Registre Docker". Par défaut, utilise l'état d'autorisation dans $XDG_RUNTIME_DIR/containers/auth.json, qui est défini en utilisant podman-login(1). Si l'état d'autorisation n'y est pas trouvé, $HOME/.docker/config.json est vérifié, qui est défini en utilisant docker-login(1). Le fichier containers-registries.conf(5) permet en outre de configurer divers paramètres d'un registre.

Notez qu'une référence-docker a le format suivant : nom[:étiquette | @digest]. Bien que le transport docker ne supporte pas à la fois une étiquette et un digest en même temps, certains formats comme containers-storage le font. Les digests peuvent également être utilisés dans une destination d'image tant que le manifeste correspond au digest fourni.

Le transport docker supporte l'envoi d'images sans étiquette ni digest vers un registre lorsque le nom de l'image est suffixé par @@unknown-digest@@. Le format de référence nom@@unknown-digest@@ ne peut pas être utilisé avec une référence qui a une étiquette ou un digest. Le digest des images peut être exploré avec skopeo-inspect(1).

Si nom ne contient pas de barre oblique, il est traité comme docker.io/library/nom. Sinon, le composant avant la première barre oblique est vérifié s'il est reconnu comme un nom d'hôte ⟨c'est-à-dire s'il contient un `.` ou un `:`, ou si le composant est exactement `localhost`⟩. Si le premier composant du nom n'est pas reconnu comme un nom d'hôte [:port], nom est traité comme docker.io/nom.

docker-archive:chemin[:{référence-docker|@index-source}]

Une image est stockée dans le fichier formaté par docker-save(1).

À moins qu'un outil ne documente explicitement le contraire, une écriture vers une destination docker-archive: écrase complètement chemin, le remplaçant par l'unique image fournie.

Le chemin peut faire référence à un flux, par exemple docker-archive:/dev/stdin.

référence-docker ne doit pas contenir de digest. Alternativement, pour lire des archives, @index-source est un index basé sur zéro dans le manifeste de l'archive (pour accéder aux images non étiquetées). Si ni référence-docker ni @_index_source_ n'est spécifié lors de la lecture d'une archive, l'archive doit contenir exactement une image.

docker-daemon:référence-docker|algo:digest

Une image stockée dans le stockage interne du démon Docker. L'image doit être spécifiée comme une référence-docker ou sous la forme alternative algo:digest lorsqu'elle est utilisée comme source d'image. Le format algo:digest fait référence à l'ID de l'image rapporté par docker-inspect(1).

oci:chemin[:{référence|@index-source}]

Une image dans une structure de répertoire conforme à la "Spécification de mise en page des images Open Container" à chemin.

La valeur chemin se termine au premier caractère : ; tout autre caractère : n'est pas un séparateur, mais fait partie de référence. La référence est utilisée pour définir, ou faire correspondre, l'annotation org.opencontainers.image.ref.name dans l'index de niveau supérieur. Pour lire des images, @index-source est un index basé sur zéro dans le manifeste (pour accéder aux images non étiquetées). Si ni la référence ni @_index_source_ ne sont spécifiés lors de la lecture d'une image, le chemin doit contenir exactement une image.

oci-archive:chemin[:référence]

Une image dans une archive tar(1) dont le contenu est conforme à la "Spécification de mise en page des images Open Container" à chemin.

À moins qu'un outil ne documente explicitement le contraire, une écriture vers une destination oci-archive: écrase complètement chemin, le remplaçant par l'unique image fournie.

La valeur chemin se termine au premier caractère : ; tout autre caractère : n'est pas un séparateur, mais fait partie de référence. La référence est utilisée pour définir, ou faire correspondre, l'annotation org.opencontainers.image.ref.name dans l'index de niveau supérieur. Si référence n'est pas spécifiée lors de la lecture d'une archive, l'archive doit contenir exactement une image.

sif:chemin

Une image utilisant le format d'image Singularity à chemin.

Seule la lecture des images est supportée, et tous les scripts ne peuvent pas être représentés dans le format OCI.

EXEMPLES

Les exemples suivants montrent comment certains des transports de conteneurs peuvent être utilisés. Les exemples utilisent skopeo-copy(1) pour copier des images de conteneurs.

Copier une image d'un registre à un autre :

$ skopeo copy docker://docker.io/library/alpine:latest docker://localhost:5000/alpine:latest

Copier une image d'un démon Docker en cours d'exécution vers un répertoire dans la disposition OCI :

$ mkdir alpine-oci
$ skopeo copy docker-daemon:alpine:latest oci:alpine-oci
$ tree alpine-oci
test-oci/
├── blobs
│   └── sha256
│       ├── 83ef92b73cf4595aa7fe214ec6747228283d585f373d8f6bc08d66bebab531b7
│       ├── 9a6259e911dcd0a53535a25a9760ad8f2eded3528e0ad5604c4488624795cecc
│       └── ff8df268d29ccbe81cdf0a173076dcfbbea4bb2b6df1dd26766a73cb7b4ae6f7
├── index.json
└── oci-layout
2 répertoires, 5 fichiers

Copier une image d'un registre vers le stockage local :

$ skopeo copy docker://docker.io/library/alpine:latest containers-storage:alpine:latest
