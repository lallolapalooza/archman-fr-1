Variables de condition.

Les variables de condition sont utiles lorsque plusieurs threads souhaitent accéder à une structure de données partagée qui est protégée par un mutex (un verrou d'exclusion mutuelle).

Une variable de condition est un canal de communication. Du côté du récepteur, un ou plusieurs threads peuvent indiquer qu'ils souhaitent attendre qu'une certaine propriété devienne vraie. Du côté de l'émetteur, un thread peut signaler que cette propriété est devenue vraie, ce qui provoque le réveil d'un (ou de plusieurs) threads en attente.

Par exemple, dans l'implémentation d'une structure de données de type file d'attente, si un thread qui souhaite extraire un élément constate que la file est actuellement vide, alors ce thread attend que la file devienne non vide. Un thread qui insère un élément dans la file signale que la file est devenue non vide. Une variable de condition est utilisée à cette fin. Ce canal de communication transmet l'information selon laquelle la propriété « la file est non vide » est vraie, ou plus précisément, peut être vraie. (Nous expliquons ci-dessous pourquoi le récepteur d'un signal ne peut pas être certain que la propriété est satisfaite.)

Pour continuer l'exemple de la file d'attente, en supposant que la file a une capacité maximale fixe, un thread qui souhaite insérer un élément peut constater que la file est pleine. Alors, ce thread doit attendre que la file ne soit plus pleine, et un thread qui extrait un élément de la file signale que la file n'est plus pleine. Une autre variable de condition est utilisée à cette fin.

En bref, une variable de condition c est utilisée pour transmettre l'information selon laquelle une certaine propriété P concernant une structure de données partagée D, protégée par un mutex m , peut être vraie.

Les variables de condition offrent une alternative efficace à l'attente active (busy-waiting). Lorsqu'on souhaite attendre que la propriété P soit vraie, au lieu d'écrire une boucle d'attente active :

     Mutex.lock m;
     while not P do
       Mutex.unlock m; Mutex.lock m
     done;
     <mettre à jour la structure de données>;
     Mutex.unlock m
on utilise Condition.wait dans le corps de la boucle, comme suit : 
     Mutex.lock m;
     while not P do
       Condition.wait c m
     done;
     <mettre à jour la structure de données>;
     Mutex.unlock m
La boucle d'attente active est inefficace car le thread en attente consomme du temps de traitement et crée une contention du mutex m . Appeler Condition.wait permet au thread en attente de être suspendu, de sorte qu'il ne consomme aucune ressource de calcul pendant l'attente.

Avec une variable de condition c , exactement un mutex m est associé. Cette association est implicite : le mutex m n'est pas explicitement passé en argument à Condition.create . Il appartient au programmeur de savoir, pour chaque variable de condition c , quel est le mutex associé m .

Avec un mutex m , plusieurs variables de condition peuvent être associées. Dans l'exemple de la file d'attente à capacité bornée, une variable de condition est utilisée pour indiquer que la file est non vide, et une autre variable de condition est utilisée pour indiquer que la file n'est pas pleine.

Avec une variable de condition c , exactement une propriété logique P devrait être associée. Des exemples de telles propriétés incluent « la file est non vide » et « la file n'est pas pleine ». Il appartient au programmeur de garder la trace, pour chaque variable de condition, de la propriété P correspondante. Un signal est envoyé sur la variable de condition c comme indication que la propriété P est vraie, ou peut être vraie. Cependant, du côté du récepteur, un thread qui est réveillé ne peut pas supposer que P est vraie ; après qu'un appel à Condition.wait se termine, on doit explicitement tester si P est vraie. Il y a plusieurs raisons à cela. Une raison est qu'entre le moment où le signal est envoyé et le moment où un thread en attente reçoit le signal et est planifié, la propriété P peut être falsifiée par un autre thread qui est capable d'acquérir le mutex m et d'altérer la structure de données D. Une autre raison est que des réveils spuriux peuvent survenir : un thread en attente peut être réveillé même si aucun signal n'a été envoyé.

Voici un exemple complet, où un mutex protège une file d'attente non bornée séquentielle, et où une variable de condition est utilisée pour signaler que la file est non vide.

     type 'a safe_queue =
       { queue : 'a Queue.t; mutex : Mutex.t; nonempty : Condition.t }
     let create () =
       { queue = Queue.create(); mutex = Mutex.create();
         nonempty = Condition.create() }
     let add v q =
       Mutex.lock q.mutex;
       let was_empty = Queue.is_empty q.queue in
       Queue.add v q.queue;
       if was_empty then Condition.broadcast q.nonempty;
       Mutex.unlock q.mutex
     let take q =
       Mutex.lock q.mutex;
       while Queue.is_empty q.queue do Condition.wait q.nonempty q.mutex done;
       let v = Queue.take q.queue in (* ne peut pas échouer car la file est non vide *)
       Mutex.unlock q.mutex;
       v
Parce que l'appel à Condition.broadcast a lieu à l'intérieur de la section critique, la propriété suivante est vérifiée chaque fois que le mutex est déverrouillé : si la file est non vide, alors aucun thread n'est en attente, ou, en d'autres termes, si un certain thread est en attente, alors la file doit être vide. C'est une propriété souhaitable : si un thread qui tente d'exécuter une opération take pouvait rester suspendu même si la file est non vide, ce serait une situation problématique, connue sous le nom d'interblocage (deadlock).

type t

Le type des variables de condition.

val create : unit -> t

create() crée et retourne une nouvelle variable de condition. Cette variable de condition devrait être associée (dans l'esprit du programmeur) à un certain mutex m et à une certaine propriété P de la structure de données qui est protégée par le mutex m .

val wait : t -> Mutex.t -> unit

L'appel wait c m n'est autorisé que si m est le mutex associé à la variable de condition c , et seulement si m est actuellement verrouillé. Cet appel déverrouille atomiquement le mutex m et suspend le thread courant sur la variable de condition c . Ce thread peut ensuite être réveillé après que la variable de condition c a été signalée via Condition.signal ou Condition.broadcast ; cependant, il peut aussi être réveillé sans raison. Le mutex m est verrouillé à nouveau avant que wait ne retourne. On ne peut pas supposer que la propriété P associée à la variable de condition c est satisfaite quand wait retourne ; on doit explicitement tester si P est satisfaite après avoir appelé wait .

val signal : t -> unit

signal c réveille un des threads en attente sur la variable de condition c , s'il y en a un. S'il n'y en a aucun, cet appel n'a aucun effet.

Il est recommandé d'appeler signal c à l'intérieur d'une section critique, c'est-à-dire pendant que le mutex m associé à c est verrouillé.

val broadcast : t -> unit

broadcast c réveille tous les threads en attente sur la variable de condition c . S'il n'y en a aucun, cet appel n'a aucun effet.

Il est recommandé d'appeler broadcast c à l'intérieur d'une section critique, c'est-à-dire pendant que le mutex m associé à c est verrouillé.
