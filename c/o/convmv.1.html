NOM

convmv - convertit les noms de fichiers d'un encodage à un autre

SYNTAXE

convmv [options] FICHIER(S) ... RÉPERTOIRE(S)

OPTIONS

-f ENCODAGE
spécifie l'encodage actuel du ou des noms de fichiers à convertir
-t ENCODAGE
spécifie l'encodage vers lequel le ou les noms de fichiers doivent être convertis
-i
mode interactif (demande y/n pour chaque action)
-r
parcourt récursivement les répertoires
--nfc
les fichiers cibles seront en forme normale C pour UTF-8 (Linux etc.)
--nfd
les fichiers cibles seront en forme normale D pour UTF-8 (OS X etc.).
--qfrom , --qto
soyez plus discret quant au "from" ou "to" d'un renommage (si cela perturbe votre terminal par exemple). Ceci ne fera rien d'autre que remplacer tout caractère non-ASCII (octet par octet) par ? et tout caractère de contrôle par * lors de l'affichage, cela n'affecte pas l'opération de renommage elle-même.
--exec commande
exécute la commande donnée. Vous devez mettre la commande entre guillemets et #1 sera substitué par l'ancien nom de fichier, #2 par le nouveau. En utilisant cette option, les cibles des liens symboliques resteront intactes. Gardez à l'esprit que #1 et #2 seront déjà échappés par convmv, vous ne devez pas ajouter de guillemets supplémentaires autour d'eux.

Exemple :

convmv -f latin1 -t utf-8 -r --exec "echo #1 doit être renommé en #2" chemin/vers/fichiers

--list
liste tous les encodages disponibles. Pour obtenir la prise en charge de plus d'encodages chinois ou japonais, installez les paquets Perl HanExtra ou JIS2K Encode. L'installation du paquet Perl IMAPUTF7 peut également être utile si vous avez besoin de cet encodage.
--lowmem
maintient une faible empreinte mémoire en ne créant pas de table de hachage de tous les fichiers. Cela désactive la vérification si les cibles des liens symboliques sont dans le sous-arbre. Les pointeurs de cibles de liens symboliques seront convertis sans distinction. Si vous convertissez plusieurs centaines de milliers ou des millions de fichiers, l'utilisation de la mémoire de convmv peut devenir très élevée. Cette option vous aidera dans ce cas.
--nosmart
par défaut, convmv détecte si un nom de fichier est déjà encodé en UTF-8 et ignorera ce fichier si une conversion d'un jeu de caractères vers UTF-8 doit être effectuée. "--nosmart" forcera également la conversion vers UTF-8 pour de tels fichiers, ce qui pourrait résulter en un "UTF-8 doublement encodé" (voir la section ci-dessous).
--fixdouble
en utilisant l'option "--fixdouble", convmv ne convertit que les fichiers qui resteront encodés en UTF-8 après la conversion. C'est utile pour corriger les fichiers UTF-8 doublement encodés. Tous les fichiers qui ne sont pas UTF-8 ou qui ne résulteront pas en UTF-8 après conversion ne seront pas touchés. Voir également le chapitre "Comment annuler le double encodage UTF-8..." ci-dessous.
--notest
Nécessaire pour renommer réellement les fichiers. Par défaut, convmv affichera simplement ce qu'il compte faire.
--parsable
Ceci est une option avancée qui sera utile aux personnes souhaitant écrire une interface graphique (et peut-être à d'autres). Elle fera afficher à convmv ce qu'il ferait d'une manière facilement analysable. La première colonne contient l'action ou une sorte d'information, la deuxième colonne contient principalement le fichier à modifier et, le cas échéant, la troisième colonne contient la valeur modifiée. Chaque colonne est séparée par \0\n (barre nulle nouvelle ligne). Chaque ligne (une action) est séparée par \0\0\n (barre nulle barre nulle nouvelle ligne).
--run-parsable
Cette option peut être utilisée pour exécuter aveuglément la sortie d'une exécution précédente de --parsable. De cette façon, il est possible de renommer une énorme quantité de fichiers en un minimum de temps.
--no-preserve-mtimes
modifier les noms de fichiers met généralement à jour le mtime du répertoire parent. Depuis la version 2, convmv réinitialise par défaut le mtime à la valeur précédente. Si votre système de fichiers prend en charge la résolution infra-secondaire, la partie infra-seconde de l'atime et du mtime sera perdue car Perl ne la prend pas encore en charge. Avec cette option, vous pouvez désactiver la préservation des mtimes.
--replace
si le fichier vers lequel le renommage doit être effectué existe déjà, il sera écrasé si le contenu de l'autre fichier est égal.
--unescape
cette option supprimera ces laids séquences hexadécimales % des noms de fichiers et les transformera en caractères 8 bits (espérons-le) plus jolis. Après --unescape, vous pourriez vouloir faire une conversion de jeu de caractères. Ces séquences comme %20 etc. sont parfois produites lors du téléchargement via http ou ftp.
--upper , --lower
transforme les noms de fichiers en majuscules ou minuscules. Lorsque le fichier n'est pas encodé en ASCII, convmv attend un jeu de caractères spécifié via le commutateur -f.
--map=mapping-supplémentaire
applique des mappages de caractères personnalisés, actuellement supportés :

ntfs-sfm(-undo), ntfs-sfu(-undo) pour le mappage des caractères ntfs illégaux pour les clients cifs Linux ou Macintosh (voir KB Microsoft 117258 également l'option de montage mapchars de mount.cifs sur Linux).

ntfs-pretty(-undo) pour le mappage des caractères ntfs illégaux vers leurs versions japonaises jolies et légales.

Voir la fonction map_get_newname() comment ajouter facilement vos propres mappages si nécessaire. Faites-moi savoir si vous pensez que convmv manque d'un mappage utile ici.

--dotlessi
gère le problème du 'i' sans point / 'I' avec point. Une version en minuscule de "I" sera également sans point tandis qu'une version en majuscule de "i" aura également un point. Ceci est un problème pour le turc et l'azéri.

Soit dit en passant : le point en exposant de la lettre i a été ajouté au Moyen Âge pour distinguer la lettre (dans les manuscrits) des traits verticaux adjacents dans des lettres comme u, m et n. J est une forme variant de i qui a émergé à cette époque et est ensuite devenue une lettre distincte.

--caseful-sz
laisse convmv convertir la ligature sz (U+00DF) en sa version majuscule (U+1E9E) et vice versa. Depuis 2017, la plupart des tables de mappage de cas des systèmes de fichiers ne traitent pas ces deux points de code comme équivalents de casse. Par conséquent, par défaut, convmv les traite comme sans casse pour l'instant (sauf si cette option est utilisée).
--help
affiche un bref résumé des options disponibles
--dump-options
affiche une liste de toutes les options disponibles

DESCRIPTION

convmv est conçu pour aider à convertir un nom de fichier unique, une arborescence de répertoires et les fichiers qu'elle contient, ou un système de fichiers entier, vers un encodage différent. Il ne fait que convertir les noms de fichiers, pas le contenu des fichiers. Une caractéristique spéciale de convmv est qu'il prend également en charge les liens symboliques, et convertit le pointeur de cible du lien symbolique au cas où la cible du lien symbolique serait également convertie.

Tout cela est très utile lorsque l'on souhaite passer des anciens locales 8 bits aux locales UTF-8. Il est également possible de convertir des répertoires en UTF-8 qui sont déjà partiellement encodés en UTF-8. convmv est capable de détecter si certains fichiers sont encodés en UTF-8 et les ignorera par défaut. Pour désactiver cette intelligence, utilisez le commutateur "--nosmart".

Problèmes de système de fichiers

Presque tous les systèmes de fichiers POSIX ne se soucient pas de la manière dont les noms de fichiers sont encodés, voici quelques exceptions :

HFS+ sur OS X / Darwin

Linux et (la plupart ?) des autres systèmes d'exploitation de type Unix utilisent la forme normale C (NFC) pour son encodage UTF-8 par défaut, mais n'appliquent pas cela. HF

HFS+ sur Macintosh OS applique la forme de normalisation D (NFD), où quelques caractères sont encodés différemment. Sur OS X, il n'est pas possible de créer des noms de fichiers UTF-8 en NFC car cela est empêché au niveau du système de fichiers. Sur HFS+, les noms de fichiers sont stockés en interne en UTF-16 et lorsqu'ils sont reconvertis en UTF-8 (car les systèmes d'exploitation basés sur Unix ne peuvent pas gérer UTF-16 directement), le NFD est créé quelle qu'en soit la raison. Voir http://developer.apple.com/qa/qa2001/qa1173.html pour plus de détails. Je pense que c'était une très mauvaise idée et que cela casse beaucoup de choses sous OS X qui s'attendent à un système POSIX normal conforme. Partout ailleurs, convmv est capable de convertir des fichiers de NFC vers NFD ou vice versa, ce qui rend l'interopérabilité avec de tels systèmes beaucoup plus

facile.

APFS sur

macOS

Apple, avec l'introduction d'APFS dans macOS 10.3, a abandonné l'imposition du NFD à l'espace utilisateur. Mais une fois que vous avez imposé le NFD, il n'y a pas de retour en arrière facile sans casser les applications existantes. Ils ont donc dû rendre APFS insensible à la normalisation, ce qui signifie qu'un fichier peut être créé en NFC ou en NFD dans le système de fichiers et qu'il peut être accessible avec les deux formes également. Sous le capot, ils stockent des hachages de la forme normalisée du nom de fichier pour fournir l'insensibilité à la normalisation. Cela semble être une bonne idée ? Voyons : Si vous faites un readdir sur un répertoire, vous obtiendrez les fichiers dans la forme de normalisation qui a été utilisée lors de leur création. Si vous faites un stat sur un fichier en forme NFC ou NFD, vous obtiendrez la forme de normalisation que vous avez utilisée dans l'appel stat. Les applications en espace utilisateur ne peuvent donc pas s'attendre à ce qu'un fichier qui peut être stat'é et accessible avec succès fasse également partie des listages de répertoires, car la forme de normalisation retournée est falsifiée pour correspondre à ce que l'utilisateur a demandé. Théoriquement, l'espace utilisateur devra aussi normaliser les chaînes tout le temps. C'est le même problème que pour l'insensibilité à la casse des noms de fichiers précédemment, qui casse encore beaucoup d'applications en espace utilisateur. Seulement, cette dernière était beaucoup plus évidente à repérer et à implémenter que cette chose. Tant pis, et merci pour tous les

poissons.

JF

S

Si les gens montent des partitions JFS avec iocharset=utf8, il y a un problème similaire, car JFS est conçu pour stocker les noms de fichiers en interne en UTF-16 aussi ; c'est parce que le JFS de Linux est en réalité JFS2, qui était une réécriture de JFS pour OS/2. Les partitions JFS devraient toujours être montées avec iocharset=iso8859-1, ce qui est également la valeur par défaut avec les noyaux 2.6.6 récents. Si cela n'est pas fait, JFS ne se comporte pas comme un système de fichiers POSIX et il pourrait arriver que certains fichiers ne puissent pas être créés du tout, par exemple des noms de fichiers avec un encodage ISO-8859-1. Seulement lorsque l'interopération avec OS/2 est nécessaire, iocharset devrait être défini selon la table de caractères de votre locale

utilisée.

NFS

4

Contrairement aux autres systèmes de fichiers POSIX, RFC3530 (NFS 4) mandate UTF-8 mais dit aussi : « Le profil nfs4_cs_prep ne spécifie pas de forme de normalisation. Une révision ultérieure de cette spécification peut spécifier une forme de normalisation particulière. » En d'autres termes, si vous voulez utiliser NFS4, vous pourriez trouver les fonctionnalités de conversion et de normalisation de convmv très

utiles.

FAT/VFAT et

NTFS

NTFS et VFAT (pour les noms de fichiers longs) utilisent UTF-16 en interne pour stocker les n

oms de fichiers. Vous ne devriez pas avoir besoin de convertir les noms de fichiers si vous
montez l'un de ces systèmes de fichiers. Utilisez plutôt des options de montage appropriées !

Comment annuler des noms de fichiers doublement encodés en UTF-8 (ou

autre)

Parfois, il pourrait arriver que vous ayez « doublement encodé » certains noms de fichiers, par exemple les noms de fichiers étaient déjà encodés en UTF-8 et vous avez accidentellement fait une autre conversion depuis un certain jeu de caractères vers UTF-8. Vous pouvez simplement annuler cela en convertissant dans l'autre sens. Le jeu de caractères source doit être UTF-8 et le jeu de caractères cible doit être le jeu de caractères source que vous avez accidentellement utilisé précédemment. Si vous utilisez l'option "--fixdouble", convmv s'assurera que seuls les fichiers qui seront toujours encodés en UTF-8 après la conversion seront traités et il laissera les fichiers non-UTF-8 intacts. Vous devriez vérifier pour obtenir les résultats corrects en effectuant la conversion sans "--notest" avant, aussi l'option "--qfrom" pourrait être utile, car les noms de fichiers utf-8 doublement encodés pourraient bousiller votre terminal s'ils sont imprimés - ils contiennent souvent des séquences de contrôle qui font des choses amusantes avec votre fenêtre de terminal. Si vous n'êtes pas sûr du jeu de caractères depuis lequel la conversion a été accidentellement faite, utiliser "--qfrom" est une bonne façon de débusquer l'encodage

requis sans détruire définit
ivement les noms de fichiers.

Comment réparer des fichiers

Samba

Quand dans smb.conf (de Samba 2.x) la variable "character set" n'a pas été définie correctement, les fichiers créés depuis des clients Win* sont créés dans la page de code du client, par exemple cp850 pour les langues européennes occidentales. En conséquence de cela, les fichiers qui contiennent des caractères non-ASCII sont bousillés si vous les faites "ls" sur le serveur Unix. Si vous changez la variable "character set" après coup à iso8859-1, les fichiers nouvellement créés sont corrects, mais les anciens fichiers sont toujours bousillés dans l'encodage Windows. Dans ce cas, convmv peut aussi être utilisé pour convertir les anciens fichiers partagés par Samba de cp850 vers

iso8859-1.

Au fait : Samba 3.x finalement mappe vers des noms de fichiers

UTF-8 par défaut, donc aussi quand vous migrez de Samba 2 vers
Samba 3 vous pourriez avoir à convertir vos noms de fichiers.

Problèmes d'interopérabilité de

Netatalk

Quand Netatalk est basculé vers UTF-8, ce qui est pris en charge dans la version 2, il ne suffit PAS de renommer les noms de fichiers. Il faut faire plus. Voir http://netatalk.sourceforge.net/2.0/htmldocs/upgrade.html#volumes-and-

filenames et l'utilitaire unicon
v de Netatalk pour plus de détails.

Doveco

t

Certaines versions de Dovecot utilisent UTF-8 pour les dossiers Maildir, d'autres utilisent I

MAP-UTF-7 aussi appelé mUTF7 ou UTF-7 modifié. Dans certains scénarios de migration, les admi
nistrateurs pourraient avoir à convertir les noms de dossiers, ce qui peut être fait avec con
vmv. Assurez-vous d'installer le paquet Perl IMAPUTF7 pour utiliser cet encodage avec convmv.
