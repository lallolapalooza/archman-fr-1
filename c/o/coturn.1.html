TURN REST

API

Dans WebRTC, le navigateur obtient les informations de connexion TURN depuis le serveur web. Ces informations sont sensibles - car elles contiennent les identifiants TURN nécessaires. Comme ces identifiants sont transmis sur les réseaux publics, nous avons une faille de sécurité

potentielle.

Si nous devons transmettre des informations précieuses sur le réseau public, alors ces informations doivent avoir une durée de vie limitée. Ainsi, la personne qui obtient ces informations sans autorisation ne pourra causer que des dégâts

limités.

C'est ainsi qu'est apparue l'idée de l'API REST TURN - des identifiants TURN à durée limitée. Ce mécanisme de sécurité est basé sur le mécanisme d'identifiants à long terme. L'idée principale de l'API REST est que le serveur web fournit les identifiants au client, mais que ces identifiants ne peuvent être utilisés que pendant une durée limitée par une application qui doit créer une connexion à un serveur

TURN.

Le mécanisme d'identifiants à long terme "classique" (LTCM) est décrit ici

:

http://tools.ietf.org/html/rfc5389#section-10.

2

http://tools.ietf.org/html/rfc5389#section-15.

4

Pour l'authentification, chaque utilisateur doit connaître deux choses : le nom d'utilisateur et le mot de passe. De plus, l'utilisateur doit fournir la valeur ORIGIN, afin que le serveur puisse déterminer le realm à utiliser pour l'utilisateur. Les valeurs nonce et realm sont fournies par le serveur TURN. Mais le LTCM ne dit rien sur la nature et la persistance du nom d'utilisateur et du mot de passe ; et c'est ce que l'API REST

utilise.

Dans l'API REST TURN, il n'y a pas de mots de passe persistants pour les utilisateurs. Un utilisateur a juste le nom d'utilisateur. Le mot de passe est toujours temporaire, et il est généré par le serveur web à la demande, lorsque l'utilisateur accède à la page WebRTC. Et, en fait, seul un nom d'utilisateur de session temporaire et unique est fourni à

l'utilisateur.

L'utilisateur temporaire est généré comme suit

:

temporary-username="timestamp" + ":" +

"username"

où username est le nom d'utilisateur persistant, et le format du timestamp est simplement le nombre de secondes depuis 1970 - la même valeur que celle renvoyée par la fonction time(NULL)

.

Le mot de passe temporaire est obtenu comme la fonction HMAC-SHA1 sur le nom d'utilisateur temporaire, avec le secret partagé comme clé HMAC, puis le résultat est encodé

:

temporary-password = base64_encode(hmac-sha1(shared-secret, temporary-username)

)

Le serveur TURN et le serveur web connaissent tous deux le même secret partagé. La manière dont le secret partagé est distribué parmi les entités concernées est laissée aux détails du déploiement WebRTC - cela dépasse le cadre de l'API REST

TURN.

Ainsi, un timestamp est utilisé pour le calcul du mot de passe temporaire, et ce timestamp peut être récupéré depuis le nom d'utilisateur temporaire. Cette information est précieuse, mais seulement temporaire, tant que le timestamp n'est pas expiré. Sans la connaissance du secret partagé, un nouveau mot de passe temporaire ne peut être

généré.

Tout cela est formellement décrit dans le document TURN REST API de Justin Uberti, qui peut être obtenu en suivant le lien "TURN REST API" dans la page du projet TURN Server https://github.com/coturn/coturn/

.

Une fois que le nom d'utilisateur et le mot de passe temporaires sont obtenus par l'application cliente (navigateur), le reste n'est que le mécanisme d'identifiants à long terme "classique". Pour les développeurs, nous allons le décrire étape par étape ci-dessous

:
  • un nouveau client TURN envoie une commande de requête au serveur TURN. De manière facultative, il y ajoute le champ
    • ORIGIN.
  • le serveur TURN voit qu'il s'agit d'un nouveau client et que le message n'est pas
    • authentifié.
  • le serveur TURN génère une chaîne nonce aléatoire et renvoie l'erreur 401 au client, avec le nonce et le realm inclus. Si le champ ORIGIN était présent dans la requête du client, il peut influencer la valeur du realm que le serveur choisit pour le
    • client.
  • le client voit l'erreur 401 et extrait deux valeurs de la réponse d'erreur : le nonce et le
    • realm.
  • le client utilise le nom d'utilisateur, le realm et le mot de passe pour produire une
    • clé
: 
         key = MD5(username ":" realm ":" SASLprep(password))
(SASLprep est décrit ici : http://tools.ietf.org/html/rfc4013)
  • le client forme une nouvelle requête, y ajoute le nom d'utilisateur, le realm et le nonce. Ensuite, le client calcule et ajoute le champ d'intégrité à la requête. C'est la partie la plus délicate du processus, et elle est décrite à la fin de la section 15.4 : http://tools.ietf.org/html/rfc5389#section-15.
    • 4
  • le client ajoute, de manière facultative, le champ d'empreinte (fingerprint). Cela peut également être une procédure délicate, décrite dans la section 15.5 du même document. WebRTC utilise généralement des messages TURN avec
    • empreinte.
  • le serveur TURN reçoit la requête et lit le nom
    • d'utilisateur.
  • ensuite, le serveur TURN vérifie que le nonce et le realm dans la requête sont
    • valides.
  • ensuite, le serveur TURN calcule la
    • clé.
  • ensuite, le serveur TURN calcule le champ
    • d'intégrité.
  • ensuite, le serveur TURN compare le champ
    • d'intégrité calculé avec celui reçu - ils
doivent être identiques. Si les champs d'in
tégrité diffèrent, la requête est rejetée.

Dans les communications suivantes, le client peut suivre exactement la même séquence, mais pour optimiser, le client, ayant déjà les informations sur le realm et le nonce, pré-calcule généralement la chaîne d'intégrité pour chaque requête, de sorte que la réponse d'erreur 401 devient inutile. Le serveur TURN peut utiliser l'option--stale-nonce" pour une sécurité supplémentaire : après un certain temps, le nonce expire et le client obtiendra une réponse d'erreur 438 avec un nouveau nonce, et le client devra commencer à utiliser le nouveau

nonce.

Dans les communications suivantes, le serveur et le client supposeront toujours le même mot de passe - le mot de passe original devient un paramètre de session et n'expire jamais. Ainsi, le mot de passe ne change pas tant que la session est valide et non expirée. Donc, si la session est correctement maintenue, elle peut durer indéfiniment, même si le mot de passe de l'utilisateur a déjà été modifié (dans la base de données). La session utilise simplement l'ancien mot de passe. Une fois la session déconnectée, le client devra utiliser le nouveau mot de passe pour se reconnecter (si le mot de passe a été modifié)

.

Un exemple où un nouveau secret partagé est généré toutes les heures par la machine du serveur TURN puis fourni au serveur web, à distance, est fourni dans le script examples/scripts/restapi/shared_secret_maintainer.pl

.

Une chose très importante est que le nonce doit

être totalement aléatoire et doit être différent
pour différents clients et différentes sessions.

base de données des utilisateurs et pour la base de données de statut et de statistiques. Par exemple, vous pouvez utiliser MySQL com
me base de données des utilisateurs, et vous pouvez utiliser Redis pour les statistiques. Ou vous pouvez utiliser Redis pour les deux.

Ainsi, nous avons 6 choix pour la gestion des utilisateurs, et 2 choix pour la gestion des statistiques. Ces deux sont totalement indépendants. Donc, vous avez au total 6*2=12 façons de gérer les informations persistantes, choisissez celle qui vous convient le

mieux.

Vous n'avez pas à gérer les informations de la base de données "manuellement" - le programme turnadmin peut tout gérer pour vous. Pour PostgreSQL et MySQL, vous devrez simplement créer une base de données vide avec le script SQL schema.sql. Avec Redis, vous n'avez même pas à faire cela - exécutez simplement turnadmin et il configurera les utilisateurs pour vous (voir les manuels de turnadmin). Si vous utilisez SQLite, alors le turnserver ou turnadmin initialisera la base de données vide pour vous, au démarrage. Le processus d'installation du serveur TURN crée une base d

e données SQLite vide et initialisée dans l'emplacement par défaut (/va
r/db/turndb ou /usr/local/var/db/turndb ou /var/lib/turn/turndb, selon

le système). ==============================
