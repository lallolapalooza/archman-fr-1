containers-auth.json(5) Manuel des formats de fichier containers-auth.json(5)

NOM

containers-auth.json - syntaxe du fichier d'authentification de registre

DESCRIPTION

Un fichier au format JSON contrôlant l'authentification auprès des registres d'images de conteneurs. Le fichier principal (lecture/écriture) est stocké dans ${XDG_RUNTIME_DIR}/containers/auth.json sous Linux ; sous Windows et macOS, dans $HOME/.config/containers/auth.json.

Lors de la recherche des identifiants pour un registre, les fichiers suivants seront lus en séquence jusqu'à ce que l'identifiant valide soit trouvé : d'abord le fichier principal (lecture/écriture), ou l'override explicite à l'aide d'une option de l'application appelante. Si les identifiants ne sont pas présents, la recherche continue dans ${XDG_CONFIG_HOME}/containers/auth.json (habituellement ~/.config/containers/auth.json), $HOME/.docker/config.json, $HOME/.dockercfg.

À l'exception du fichier principal (lecture/écriture), les autres fichiers sont en lecture seule à moins que l'utilisateur, via une option de l'application appelante, ne pointe explicitement vers celui-ci comme override.

FORMAT

Le fichier auth.json stocke, ou référence, des identifiants qui permettent à l'utilisateur de s'authentifier auprès des registres d'images de conteneurs. Il est principalement géré par une commande login d'un outil de conteneur tel que podman login, buildah login ou skopeo login.

Chaque entrée contient un seul nom d'hôte (par exemple, docker.io) ou un espace de noms (par exemple, quay.io/user/image) comme clé, et des identifiants sous la forme d'une chaîne encodée en base64 comme valeur de auth. La chaîne encodée en base64 contient une concaténation du nom d'utilisateur, d'un deux-points et du mot de passe.

Lors de la vérification des identifiants disponibles, le dépôt pertinent est mis en correspondance avec les clés disponibles dans son ordre hiérarchique, allant du plus spécifique au moins spécifique. Par exemple, un pull d'image pour my-registry.local/namespace/user/image:latest entraînera une recherche dans auth.json dans l'ordre suivant :

  • my-registry.local/namespace/user/image
  • my-registry.local/namespace/user
  • my-registry.local/namespace
  • my-registry.local

De cette façon, il est possible de configurer plusieurs identifiants pour un seul registre qui peuvent être distingués par leur chemin.

L'exemple suivant montre les valeurs trouvées dans auth.json après que l'utilisateur se soit connecté à ses comptes sur quay.io et docker.io :

{
	"auths": {
		"docker.io": {
			"auth": "erfi7sYi89234xJUqaqxgmzcnQ2rRFWM5aJX0EC="
		},
		"quay.io": {
			"auth": "juQAqGmz5eR1ipzx8Evn6KGdw8fEa1w5MWczmgY="
		}
	}
}

Cet exemple montre comment utiliser plusieurs chemins pour un seul registre, tout en conservant un fallback pour my-registry.local :

{
	"auths": {
		"my-registry.local/foo/bar/image": {
			"auth": "…"
		},
		"my-registry.local/foo": {
			"auth": "…"
		},
		"my-registry.local": {
			"auth": "…"
		},
	}
}

Une entrée peut être supprimée en utilisant une commande logout d'un outil de conteneur tel que podman logout ou buildah logout.

De plus, des gestionnaires d'identifiants (credential helpers) peuvent être configurés pour des registres spécifiques, et le logiciel de gestion d'identifiants peut être utilisé pour gérer les identifiants plus sûrement que de ne stocker que des identifiants encodés en base64 dans auth.json.

Lorsque le gestionnaire d'identifiants est utilisé sur une plateforme Linux, le fichier auth.json contiendra des clés spécifiant le domaine du registre, et des valeurs spécifiant le suffixe du programme à utiliser (c'est-à-dire tout ce qui suit docker-credential-). Par exemple :

{
    "auths": {
        "localhost:5001": {}
    },
    "credHelpers": {
		"registry.example.com": "secretservice"
	}
}

Pour plus d'informations sur les gestionnaires d'identifiants, veuillez consulter le projet GitHub docker-credential-helpers ⟨https://github.com/docker/docker-credential-helpers/releases⟩.
