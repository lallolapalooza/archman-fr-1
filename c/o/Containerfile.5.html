NOM

Containerfile(Dockerfile) - automatise les étapes de création d'une image de conteneur

INTRODUCTION

Le Containerfile est un fichier de configuration qui automatise les étapes de création d'une image de conteneur. Il est similaire à un Makefile. Les moteurs de conteneurs (Podman, Buildah, Docker) lisent les instructions du Containerfile pour automatiser les étapes qui seraient autrement effectuées manuellement pour créer une image. Pour construire une image, créez un fichier nommé Containerfile.

Le Containerfile décrit les étapes prises pour assembler l'image. Une fois le Containerfile créé, appelez la commande buildah build, podman build, docker build en utilisant le chemin du répertoire de contexte qui contient le Containerfile comme argument. Podman et Buildah utilisent par défaut Containerfile et reviendront à Dockerfilesi nécessaire. Docker ne cherchera que Dockerfile dans le répertoire de contexte.

Dockerfile est un nom alternatif pour le même objet. Containerfile et Dockerfile prennent en charge la même syntaxe.

Montages RUN

--mount=type=TYPE,TYPE-SPECIFIC-OPTION[,...]

Attache un montage de système de fichiers au conteneur

Les types de montage actuellement pris en charge sont bind, cache, secret et tmpfs.

   ex.
   mount=type=bind,source=/path/on/host,destination=/path/in/container,relabel=shared
   mount=type=tmpfs,tmpfs-size=512M,destination=/path/in/container
   mount=type=secret,id=mysecret cat /run/secrets/mysecret
   Options courantes :
      · src, source : spécification de la source du montage pour bind et volume. Obligatoire pour bind. Si `from` est spécifié, `src` est le sous-chemin dans le champ `from`.
      · dst, destination, target : spécification de la destination du montage.
      · ro, read-only : true (par défaut) ou false.
   Options spécifiques à bind :
      · bind-propagation : shared, slave, private, rshared, rslave, ou rprivate (par défaut). Voir aussi mount(2).
      . bind-nonrecursive : ne pas configurer un montage bind récursif. Par défaut, il est récursif.
      · from : nom de l'étape ou de l'image pour la racine de la source. Par défaut, le contexte de construction.
      · relabel=shared, z : Relabélise le contenu de src avec une étiquette partagée.
      . relabel=private, Z : Relabélise le contenu de src avec une étiquette privée.
      Les systèmes de libellés comme SELinux exigent des libellés appropriés sur le contenu monté en bind dans un conteneur. Sans libellé, le système de sécurité peut empêcher les processus s'exécutant à l'intérieur du conteneur d'utiliser le contenu. Par défaut, les moteurs de conteneurs ne changent pas les libellés définis par l'OS. L'indicateur relabel indique au moteur de relabéliser les objets de fichiers sur le montage partagé.
      Les options relabel=shared et z indiquent au moteur que deux conteneurs ou plus partageront le contenu du montage. Le moteur libelle le contenu avec un libellé de contenu partagé.
      Les options relabel=private et Z indiquent au moteur de libeller le contenu avec un libellé privé non partagé. Seul le conteneur actuel peut utiliser un montage privé.
      Le relabélisation parcourt le système de fichiers sous le montage et change le libellé de chaque fichier ; si le montage a des milliers d'inodes, ce processus prend du temps, retardant le démarrage du conteneur.
      · rw, read-write : permet les écritures sur le montage.
   Options spécifiques à tmpfs :
      · tmpfs-size : Taille du montage tmpfs en octets. Illimitée par défaut sous Linux.
      · tmpfs-mode : Mode de fichier du tmpfs en octal. (ex. 700 ou 0700.) Par défaut 1777 sous Linux.
      · tmpcopyup : Le chemin masqué par le montage tmpfs est copié récursivement vers le tmpfs lui-même.
Options spécifiques à cache :
      · id : Crée un répertoire de cache séparé pour un id particulier.
      · mode : Mode de fichier pour le nouveau répertoire de cache en octal. Par défaut 0755.
      · ro, readonly : cache en lecture seule si défini.
      · uid : uid pour le répertoire de cache.
      · gid : gid pour le répertoire de cache.
      · from : nom de l'étape pour la racine de la source. Par défaut, le répertoire de cache de l'hôte.
      · rw, read-write : permet les écritures sur le montage.

. ONBUILD --
ONBUILD [INSTRUCTION] L'instruction
ONBUILD ajoute une instruction de déclenchement à une image. Le
déclencheur est exécuté à un moment ultérieur, lorsque l'image est utilisée comme base pour
une autre construction. Les moteurs de conteneurs exécutent le déclencheur dans le contexte de la construction en aval,
comme si le déclencheur existait immédiatement après l'instruction FROM dans le
Containerfile en

aval.

Vous pouvez enregistrer n'importe quelle instruction de construction comme déclencheur. Un déclencheur est utile si
vous définissez une image à utiliser comme base pour construire d'autres images. Par
exemple, si vous définissez un environnement de construction d'application ou un démon
personnalisé avec une configuration spécifique à

l'utilisateur.

Considérez une image destinée à être un constructeur d'applications python réutilisable. Elle doit
ajouter le code source de l'application à un répertoire particulier, et pourrait avoir besoin d'un script de construction
appelé après cela. Vous ne pouvez pas simplement appeler ADD et RUN maintenant, car
vous n'avez pas encore accès au code source de l'application, et il est différent
pour chaque construction

d'application.

-- Fournir aux développeurs d'applications un Containerfile de base à copier-coller
est inefficace, source d'erreurs et
difficile à mettre à jour car il se mélange au code spécifique à l'application.
La solution est d'utiliser ONBUILD pour enregistrer des instructions à l'avance, afin de
les exécuter plus tard, lors de la prochaine étape de construction.
