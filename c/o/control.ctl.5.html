control.ctl - Spécifier

le traitement des mess
ages de contrôle Usenet

DESCRIPTIO

N

Le fichier pathetc/control.ctl est utilisé pour déterminer quelle action est entreprise lorsqu'un message de contrôle est reçu. Il est lu par controlchan, qui est normalement invoqué en tant que programme de canal par innd. Quand control.ctl est modifié, controlchan le remarque automatiquement et le

recharge.

Si un fichier control.ctl.local existe dans pathetc, il est lu par controlchan après control.ctl (le comportement résultant est comme si le contenu de control.ctl.local se trouvait à la fin de control.ctl). Ce fichier local est formaté comme control.ctl et est destiné à contenir des personnalisations locales. Il est également automatiquement rechargé lorsqu'il est

modifié.

Les lignes vides et les lignes commençant par un signe dièse ("#") sont ignorées. Toutes les autres lignes doivent se composer de quatre champs séparés par des deux-points

: 
<type>:<from>:<newsgroups>:
<action>

Les lignes sont appariées dans l'ordre et la dernière ligne correspondante du fichier sera utilisée, sauf pour les messages checkgroups qui sont traités différemment (chaque ligne correspondante est utilisée)

.

Le premier champ, <type>, est le type de message de contrôle pour lequel cette ligne est valide. Il doit être soit le nom d'un message de contrôle soit le mot "all" pour indiquer qu'il s'applique à tous les messages de contrôle. De plus, les types spéciaux suivants sont compris

:
/encodin
g/
Ce type spécifie l'encodage des messages de contrôle newgroup et checkgroups afin que les nouvelles descriptions puissent être décodées correctement. 
/encoding/:*:cn.*:
gb18030

signifie qu'une description pour un groupe de discussion dans la hiérarchie chinoise cn.* sera décodée comme si elle était encodée en GB18030, sauf si un jeu de caractères est spécifié dans le message de contrôle (dans un tel cas, le jeu de caractères mentionné dans le message est utilisé). Cependant, il est possible de remplacer le jeu de caractères mentionné si "=force" est ajouté après l'encodage. Par

exemple, 
/encoding/:*:scout.forum.chinese:
big5=force

signifie que la description de scout.forum.chinese sera toujours décodée comme si elle était encodée en Big5, quel que soit le jeu de caractères du message de contrôle

correspondant.

La valeur par défaut quand aucun encodage n'est mentionné (ou quand l'encodage spécifié est inconnu) est "CP125

2".

La dernière ligne correspondante pour un nom de groupe de discussion donné dans control.ctl s

era uti
lisée.
/localencodi
ng/
Quand ce type est utilisé, la ligne ne consiste qu'en deux champs. La valeur par défaut quand ce type n'apparaît pas dans control.ctl (ou quand le jeu de caractères spécifié est inconnu) est équivalente à : 
/localencoding/:
utf-8

Cela signifie que les nouvelles descriptions dans le fichier newsgroups seront écrites en utilisant UTF-8. Et controlchan essaiera de lire les descriptions existantes, afin de voir si elles doivent être mises à jour, comme si elles étaient encodées en

UTF-8.

La dernière ligne correspondante dans control.ctl s

era uti
lisée.
/maxdocheckgrou
ps/
Ce type spécifie le nombre maximum de changements qui peuvent être faits en une fois par un checkgroups avant d'abandonner et d'envoyer les changements par courriel à l'administrateur si aucun fichier journal n'a été spécifié. La valeur par défaut est 10. 
/maxdocheckgroups/:*:*:10
/maxdocheckgroups/:*:fr.
*:20

Une telle configuration signifie qu'un checkgroups contenant 15 changements pour la hiérarchie française fr.* (newgroups à ajouter, supprimer ou changer le statut) sera automatiquement honoré alors qu'un checkgroups contenant 15 changements pour france.* n'aura que les changements requis envoyés par courriel ou

journalisés.

l sera
util
isée.

Le deuxième champ, <from>, est un motif de style shell qui correspond à l'adresse e-mail de la personne qui publie le message (avec l'adresse d'abord convertie en minuscules). L'appariement est fait avec des règles équivalentes à celles de l'instruction case du shell ; voir sh(1) pour plus de

détails.

Si le message de contrôle est un newgroup ou rmgroup, le troisième champ, <newsgroups>, est un motif de style shell correspondant au groupe de discussion affecté par le message de contrôle (en particulier "?" correspond exactement à un caractère, "*" correspond à zéro ou plusieurs caractères et "|" permet de faire correspondre plusieurs motifs sur la même ligne -- par exemple "comp.*|humanities.*" correspond à tous les groupes de discussion dont le nom commence par "comp." ou "humanities."). Si le message de contrôle est un checkgroups, le troisième champ est un motif de style shell correspondant aux groupes de discussion qui doivent être traités pour la vérification. Si le message de contrôle est d'un autre type, le troisième champ est

ignoré.

Le quatrième champ, <action>, spécifie quelle action entreprendre avec les messages de contrôle qui correspondent à cette ligne. Les actions suivantes sont comprises

:
do
it
L'action demandée par le message de contrôle doit être effectuée. Cela signifie que le changement sera effectué silencieusement. Pour les messages checkgroups, en fonction de la valeur de /maxdocheckgroups/, les commandes shell qui doivent être exécutées peuvent être envoyées par courriel à l'administrateur de news (l'argument pour --with-news-master donné au moment de la configuration, "usenet" par défaut) au lieu d'être effectuées.

Si vous voulez toujours être notifié des actions effectuées, utilisez "doit=mail" à la pla

ce (voir ci
-dessous).
doit=fich
ier
L'action est effectuée comme dans doit, et de plus une entrée de journal est écrite dans le fichier journal spécifié fichier. Si fichier est le mot "mail", l'entré de journal est envoyée par courriel à l'administrateur de news à la place. Une chaîne vide est équivalente à /dev/null et indique de ne rien journaliser.

Si fichier commence par une barre oblique, il est pris comme le nom de fichier absolu à utiliser pour le fichier journal. Sinon, le nom de fichier est formé en préfixant pathlog et une barre oblique, et en suffixant ".log". En d'autres termes, une action de "doit=newgroup" journalisera dans pathlog/ne

wgroup
.log.
abando
nner
Aucune action n'est entreprise et le message est ignoré. Pour les messages checkgroups, cela signifie que les groupes de discussion mentionnés seront considérés comme inexistants dans le checkgroups pour son traitement ultérieur. 
checkgroups:*:comp.*:doit
checkgroups:*:*binaries*:
drop

supprimera par exemple tous les groupes de discussion dont le nom contient "binaries" dans la hiérarchie comp.*, même si de tels groupes sont mentionnés dans le checkgroups. (Dans cet exemple, la suppression est effectuée par l'action doit car abandonner ne fait rien par

lui-même.
)
verify
-*
Si l'action commence par la chaîne "verify-", comme dans : 
verify-news.announce.
newgroups

alors la vérification PGP du message de contrôle sera effectuée et l'identifiant utilisateur de la clé du signataire authentifié sera vérifié par rapport à l'identité attendue définie par le reste de la chaîne ("news.announce.newgroups" dans l'exemple ci-dessus). Cette vérification est faite via pgpverify ; voir pgpverify(1) pour plus de

détails.

Si aucune journalisation n'est spécifiée (avec =fichier comme mentionné ci-dessous), la journalisation sera faite de la même manière qu'avec doit comme décrit

c
i-dessus.
verify-*=courr
iel
La vérification PGP est effectuée comme pour l'action verify-* décrite ci-dessus, et la notification des messages de contrôle newgroup et rmgroup réussis et la sortie des messages checkgroups seront envoyées par courriel à l'administrateur de news. (Dans le cas des messages checkgroups, cela signifie que le script shell qui doit être exécuté sera envoyé par courriel à l'administrateur. Le sujet du courriel contiendra des informations sur le fait que le script a déjà été exécuté, en fonction de la valeur de /maxdocheckgr
oups/.)
verify-*=fich
ier
La vérification PGP est effectuée comme pour l'action verify-* décrite ci-dessus, et une entrée de journal est écrite dans le fichier spécifié comme décrit dans doit=fichier ci-dessus. (Dans le cas des messages checkgroups, cela signifie que la sortie du script shell du message checkgroups sera écrite dans ce fichier. La ligne initiale du journal contiendra des informations indiquant si le script a déjà été exécuté, en fonction de la valeur de /maxdocheckgr
oups/.)
lo
g
Un message de journal d'une seule ligne est envoyé sur la sortie d'erreur standard. innd dirige normalement cela vers pathlog/errl
og.
log=fich
ier
Une entrée de journal est écrite dans le fichier journal spécifié, qui est interprété comme dans doit=fichier décrit
ci-dessus.
ma
il
Un message de courriel est envoyé
à l'administrateur de news sans p
rendre aucune autre action.

L'une des différences entre une action doit ou verify et une action mail pour un message de contrôle checkgroups réside dans le courriel qui est envoyé ; doit ou verify enverra à l'administrateur de news un script shell (qui peut avoir déjà été exécuté) pour créer, supprimer ou modifier des groupes de discussion afin de correspondre au message checkgroups, alors que mail enverra simplement les lignes pertinentes du checkgroups pour un traitement manuel par l'administrateur de

news.

L'utilisation de l'action verify pour le traitement des messages newgroup, rmgroup et checkgroups est FORTEMENT recommandée. L'abus des messages de contrôle est répandu, et l'authentification par signature PGP est actuellement la seule manière fiable de s'assurer qu'un message de contrôle provient bien de celui qui prétend l'être. La plupart des grandes hiérarchies émettent désormais des messages de contrôle authentifiés par

PGP.

Afin d'utiliser les actions verify, l'anneau de clés PGP de l'utilisateur news doit être rempli avec les clés PGP des mainteneurs de hiérarchie dont vous souhaitez honorer les messages de contrôle. Pour plus de détails sur les messages de contrôle authentifiés par PGP et l'URL pour télécharger les clés PGP des grandes hiérarchies, voir pgpverify

(1).

Les messages de contrôle de type cancel sont traités en interne par innd et ne peuvent être affectés par

aucun des mécanis
mes décrits ici.

EXEMPLE

S

Avec les trois lignes suivantes dans control.c

tl : 
newgroup:*:*:drop
newgroup:group-admin@isc.org:comp.*:verify-news.announce.newgroups
newgroup:kre@munnari.oz.au:aus.*:
mail

un newgroup provenant de "group-admin@isc.org" sera honoré s'il concerne un groupe de discussion dans la hiérarchie comp.* et s'il possède une signature valide correspondant à la clé PGP avec un identifiant utilisateur de "news.announce.newgroups". Si un newgroup prétendant provenir de "kre@munnari.oz.au" pour un groupe de discussion dans la hiérarchie aus.* est reçu, il sera également honoré. Tous les autres messages newgroup seront

ignorés.

De plus, si un fichier control.ctl.local existe et contient

: 
newgroup:*:comp.lang.*:
drop

alors un article de contrôle newgroup pour comp.lang.awk ne sera pas honoré même s'il provient de "group-admin@isc.org" avec une signature

valide.

En ce qui concerne checkgroups, supposons que votre serveur news contienne ces groupes pour foo.*, tous étant non modérés (statut "y" dans le fichier active)

: 
foo.bar1
foo.bar2.first
foo.bar2.second
foo.bar2.third
foo.bar3
foo.bar3.first
foo.bar3.second
foo.
bar5

et que vous receviez le checkgroups suivant de <foo@bar.com> pour foo.*

: 
foo.bar1          Un groupe de discussion valide.
foo.bar3.first    Un seul groupe de discussion dans foo.bar3.*.
foo.bar4          Un groupe de discussion que vous voulez.
foo.bar5          Un groupe de discussion que vous ne voulez pas.
foo.bar5.first    Un autre groupe de discussion que vous ne voulez
pas.

avec les entrées control.ctl suivantes

: 
/maxdocheckgroups/:*:foo.*:2
checkgroups:foo@bar.com:foo.*:verify-key-foo
checkgroups:foo@bar.com:foo.bar2.*:doit
checkgroups:foo@bar.com:foo.bar3.*:mail
checkgroups:foo@bar.com:foo.bar4|foo.bar4.*:doit
checkgroups:foo@bar.com:foo.bar5|foo.bar5.*:
drop

Ensuite, comme control.ctl est traité de bas en haut, voici ce qui se passe

:
1
.
Les groupes de discussion foo.bar5 et foo.bar5.first sont marqués comme indésirables. Mais rien n'est encore fait : d'autres entrées control.ctl doivent être traitées avec une action réelle et un ensemble de groupes de discussion contenant foo.bar5 et foo.bar5.
first.
2
.
Le groupe de discussion foo.bar4 est créé silencieusement sur le serveur news, avec la description "A newsgroup you want." ajoutée au fichier newsgroups. En l'absence de valeurs d'encodage (que ce soit dans le message checkgroups ou dans /encoding/ et /localencoding), la valeur par défaut est de décoder la phrase en CP1242 et de la ré-encoder en UTF-8.

Si "doit=mail" avait été utilisé, un courriel aurait été envoyé à l'admin

istrateur de news pour l'informer que f
oo.bar4 a été créé avec succès.
3
.
Le groupe de discussion foo.bar3.second n'est plus présent. Un courriel est envoyé à l'administrateur de news avec un script shell à exécuter. Lorsqu'il est exécuté manuellement, foo.bar3.second sera supprimé.

Notez que les descriptions sont traitées différemment et ont déjà été mises à jo

ur sans aucune intervention manuelle (foo.bar3.first a désormais la description
"Only one newsgroup in foo.bar3.*." et foo.bar3.second n'a plus de description).
4
.
Les groupes de discussion foo.bar2.first, foo.bar2.second et foo.bar2.third ne sont plus présents. Cependant, comme le nombre maximum de modifications qui pourraient être faites à la fois par un checkgroups avant d'interrompre et d'envoyer les modifications à l'administrateur de news est de 2, ces groupes de discussion ne sont pas supprimés. Un courriel est envoyé avec un script shell à exécuter manuellement afin de supprimer ces groupes du serveur news.

Notez que leurs descriptions sont supprimées du fichier newsgroups, ainsi que toute autre description possible pour les groupes de discussion obsolètes dans foo.

bar2.
*.
5
.
L'entrée restante est exécutée si la vérification PGP du message checkgroups réussit. Sinon, rien n'est fait (en particulier, foo.bar5 reste sur le serveur news).

Si la signature PGP est vérifiée, foo.bar3 et foo.bar5 sont supprimés du serveur news. Cette entrée agit sur les groupes de discussion marqués comme supprimés dans sa portée et les groupes de discussion non déjà traités par les entrées control.ctl précédentes (comme foo.bar3 car seuls foo.bar3.* ont été vérifiés précédemment)

.

Notez que si vous aviez voulu conserver foo.bar3 ou foo.bar5, vous auriez pu les ajouter au fichier localgroups dans pat

h
e
tc
