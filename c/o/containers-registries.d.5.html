DESCRIPTIO

N

Le répertoire de configuration des registres contient la configuration pour divers registres (serveurs stockant des images de conteneurs distantes) et pour le contenu stocké en eux, afin que la configuration n'ait pas à être fournie dans les options de ligne de commande encore et encore pour chaque commande, et afin qu'elle puisse être partagée par tous les utilisateurs de containers/image

.

Par défaut, le répertoire de configuration des registres est $HOME/.config/containers/registries.d s'il existe, sinon /etc/containers/registries.d (sauf si remplacé à la compilation) ; les a

pplications peuvent permettre l'utilisa
tion d'un autre répertoire à la place.

Structure du

répertoire

Le répertoire peut contenir un nombre quelconque de fichiers avec l'extension .yaml, chacun utilisant le format YAML. En dehors de l'extension obligatoire, les noms des fichiers n'ont pas

d'importance.

Le contenu de ces fichiers est fusionné ensemble ; pour avoir un comportement bien défini et facile à comprendre, il ne peut y avoir qu'une seule section de configuration décrivant un espace de noms unique au sein d'un registre (en particulier il ne peut y avoir qu'une seule section default-docker à travers tous les fichiers, et il ne peut y avoir qu'une seule instance de n'importe quelle clé sous la section docker ; ces sections sont documentées plus loin)

.

Ainsi, il est interdit d'avoir deux configurations conflictuelles pour un seul registre o

u portée, et il est également interdit de répartir une configuration pour un seul regist
re ou portée sur plus d'un fichier (même si elles ne sont pas sémantiquement en conflit).

Registres, Portées et ordre de

recherche

Chaque fichier YAML doit contenir une « correspondance YAML » (paires clé-valeur). Deux clés de premier niveau sont définies

:
•
default-docker est la section de configuration (comme documenté ci-dessous) pour
les registres implémentant "
Docker Registry HTTP API V2".

Cette clé est

facultative.
•
docker est une correspondance, utilisant des registres individuels implémentant "Docker Registry HTTP API V2", ou des espaces de noms et des images individuelles au sein de ces registres, comme clés ; la valeur assignée à n'importe quelle telle clé est une section de c
onfigur
ation.

Cette clé est

facultative.

Les portées correspondant à des images individuelles sont nommées des références Docker sous forme entièrement développée, soit
en utilisant une étiquette ou un empreinte. Par exemple, docker.io/library/busybox:latest (pas busybox:lat

est).

Les portées plus générales sont des préfixes des portées d'images individuelles, et spécifient un dépôt (en omettant l'étiquette ou l'empreinte),
un espace de noms de dépôt, ou un hôte de registre (et un port s'il diffère de la valeur par défaut)

.

Notez que si un registre est accédé en utilisant une configuration hôte+port,
l'hôte sans port n'est pas utilisé comme portée

parente.

Lors de la recherche d'une configuration à appliquer pour une image de conteneur individuelle, seule la configuration pour la portée correspondant le plus précisément est utilisée ; la configuration utilisant des portées plus générales est ignorée. Par exemple, si n'importe quelle configuration existe pour docker.io/library/busybox, la configuration pour docker.io est ignorée (même si un élément de la configuration est défini pour docker.io et pas pour docker.io/library/

busybox).

Valeurs par défaut

intégrées

Si aucune section docker ne peut être trouvée pour l'image de conteneur, et qu'aucune section default-docker n'est configurée

:
  • Le répertoire par défaut, /var/lib/containers/sigstore pour root et $HOME/.local/share/containers/sigstore pour un utilisateur non privilégié, sera utilisé pour lire et écrire les
    • signatures.
  • Les pièces
    • jointes sig
store ne se
ront pas lu
es/écrites.

Sections de configuration

individuelles

Une seule section de configuration est sélectionnée pour une image de conteneur en utilisant le processus décrit ci-dessus. La section de configuration est une correspondance YAML, avec les clés suivantes

:
•
lookaside-staging définit une URL du stockage de signatures,
utilisée pour l'éditer (ajouter
ou supprimer des signatures).

Cette clé est facultative ; si elle est manquante, lookaside ci-dessous est

utilisé.
•
lookaside définit une URL du stockage de signatures. Cette URL est utilisée pour lire les signatures existantes, et si lookaside-staging n'existe pas, auss
i pour les ajouter
ou les supprimer.

Cette clé est facultative ; si elle est manquante, aucun stockage de signatures n'est défini (aucune signature
n'est téléchargée avec les images, l'ajout de nouvelles signatures n'est possible que si lookaside-staging est défini)

.
•
use-sigstore-attachments spécifie si les pièces jointes d'image sigstore (signatures, attestations et le reste) v
ont être lues/écrites avec l'image. Si désactivé, les ima
ges sont traitées comme si aucune pièce jointe n'existai
t ; les tentatives d'écriture de pièces jointes échouent.

Un défaut

global

Si une entreprise publie ses produits en utilisant un domaine différent, et un nom d'hôte de registre différent pour chacun d'eux, il est toujours possible d'utiliser un seul serveur de stockage de signatures sans lister chaque domaine individuellement. On s'attend à ce que cela arrive rarement, généralement seulement pour la pré-production de nouvelles

signatures.
