containerd-config.toml(5) Manuel des formats de fichiers containerd-config.toml(5)

NOM

containerd-config.toml - fichier de configuration pour containerd

SYNTAXE

Le fichier config.toml est un fichier de configuration pour le démon containerd. Le fichier doit être placé à /etc/containerd/config.toml ou spécifié avec l'option --config de containerd pour être utilisé par le démon. Si le fichier n'existe pas à l'emplacement approprié ou n'est pas fourni via l'option --config, containerd utilise ses paramètres de configuration par défaut, qui peuvent être affichés avec la commande containerd config(1).

DESCRIPTION

Le fichier TOML utilisé pour configurer les paramètres du démon containerd contient une courte liste de paramètres globaux suivie d'une série de sections pour des domaines spécifiques de la configuration du démon. Il y a également une section pour les plugins qui permet à chaque plugin de containerd d'avoir une zone pour la configuration et les paramètres spécifiques au plugin.

FORMAT

version
Le champ version dans le fichier de configuration spécifie la version de la configuration. Si aucun numéro de version n'est spécifié dans le fichier de configuration, il est supposé être une configuration de version 1 et est analysé comme telle. Veuillez utiliser version = 2 pour activer la configuration de version 2 car la version 1 a été dépréciée.
root
Le répertoire racine pour les métadonnées de containerd. (Par défaut : "/var/lib/containerd")
state
Le répertoire d'état pour containerd (Par défaut : "/run/containerd")
plugin_dir
Le répertoire où sont stockés les plugins dynamiques
[grpc]
Section pour les paramètres du listener de socket gRPC. Contient les propriétés suivantes :
  • address (Par défaut : "/run/containerd/containerd.sock")
  • tcp_address
  • tcp_tls_cert
  • tcp_tls_key
  • uid (Par défaut : 0)
  • gid (Par défaut : 0)
  • max_recv_message_size
  • max_send_message_size
[ttrpc]
Section pour les paramètres TTRPC. Contient les propriétés :
  • address (Par défaut : "")
  • uid (Par défaut : 0)
  • gid (Par défaut : 0)
[debug]
Section pour activer et configurer un listener de socket de débogage. Contient quatre propriétés :
  • address (Par défaut : "/run/containerd/debug.sock")
  • uid (Par défaut : 0)
  • gid (Par défaut : 0)
  • level (Par défaut : "info") définit le niveau de journalisation de débogage. Les niveaux pris en charge sont : "trace", "debug", "info", "warn", "error", "fatal", "panic"
  • format (Par défaut : "text") définit le format du journal. Les formats pris en charge sont "text" et "json"
[metrics]
Section pour activer et configurer un listener de métriques. Contient deux propriétés :
  • address (Par défaut : "") Le point de terminaison des métriques n'écoute pas par défaut
  • grpc_histogram (Par défaut : false) Active ou désactive les métriques histogramme gRPC
disabled_plugins
Les plugins désactivés sont les identifiants des plugins à désactiver. Les plugins désactivés ne seront ni initialisés ni démarrés.
required_plugins
Les plugins requis sont les identifiants des plugins nécessaires. Containerd s'arrête si un plugin requis n'existe pas ou échoue à être initialisé ou démarré.
[plugins]
La section plugins contient des options de configuration exposées par les plugins installés. Les plugins suivants sont activés par défaut et leurs paramètres sont présentés ci-dessous. Les plugins qui ne sont pas activés par défaut fourniront leur propre documentation sur les valeurs de configuration.
  • [plugins."io.containerd.monitor.v1.cgroups"] possède une option no_prometheus (Par défaut : false)
  • [plugins."io.containerd.service.v1.diff-service"] possède une option default, une liste par défaut définie à ["walking"]
  • [plugins."io.containerd.gc.v1.scheduler"] possède plusieurs options qui effectuent un réglage avancé pour le planificateur :
  • pause_threshold est le temps maximum pendant lequel le GC doit être planifié (Par défaut : 0.02),
  • deletion_threshold garantit que le GC est planifié après n suppressions (Par défaut : 0 [non déclenché]),
  • mutation_threshold garantit que le GC est planifié après n mutations de base de données (Par défaut : 100),
  • schedule_delay définit le délai après un événement déclencheur avant de planifier un GC (Par défaut "0ms" [immédiat]),
  • startup_delay définit le délai après le démarrage avant de planifier un GC (Par défaut "100ms")
•
[plugins."io.containerd.runtime.v2.task"] spécifie les options de configuration du shim d'exécution :
  • platforms spécifie la liste des plateformes prises en charge
  • sched_core L'ordonnancement des cœurs est une fonctionnalité qui permet à seulement des tâches fiables de s'exécuter simultanément sur des CPU partageant des ressources de calcul (par exemple, des hyperthreads sur un cœur). (Par défaut : false)
•
[plugins."io.containerd.service.v1.tasks-service"] possède des options de performance :
  • blockio_config_file (Linux uniquement) spécifie le chemin vers les définitions de classes blockio (Par défaut : ""). Contrôle la priorité du planificateur d'E/S et la limitation de la bande passante. Voir la configuration blockio ⟨https://github.com/intel/goresctrl/blob/main/doc/blockio.md#configuration⟩ pour les détails du format de fichier.
  • rdt_config_file (Linux uniquement) spécifie le chemin vers une configuration utilisée pour configurer RDT (Par défaut : ""). Active la prise en charge d'Intel RDT, une technologie de gestion de la bande passante du cache et de la mémoire. Voir la configuration RDT ⟨https://github.com/intel/goresctrl/blob/main/doc/rdt.md#configuration⟩ pour les détails du format de fichier.
•
[plugins."io.containerd.grpc.v1.cri".containerd] contient des options pour le plugin CRI, et des nœuds enfants pour les options CRI :
•
default_runtime_name (Par défaut : "runc") spécifie le nom d'exécution par défaut
  • [plugins."io.containerd.grpc.v1.cri".containerd.runtimes] un ou plusieurs runtimes de conteneurs, chacun avec un nom unique
  • [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.] un runtime nommé <runtime>
  • [plugins."io.containerd.grpc.v1.cri".containerd.runtimes..options] options pour le <runtime> nommé, le plus important :
•
BinaryName spécifie le chemin vers le runtime réel à invoquer par le shim, par exemple "/usr/bin/runc"
oom_score
Le score Out Of Memory (OOM) appliqué au processus démon containerd (Par défaut : 0)
[cgroup]
Section pour les paramètres spécifiques aux cgroup Linux
•
path (Par défaut : "") Spécifiez un chemin cgroup personnalisé pour les conteneurs créés
[proxy_plugins]
Les plugins proxy configurent les plugins qui sont communiqués via gRPC
  • type (Par défaut : "")
  • address (Par défaut : "")
timeouts
Section pour configurer les délais d'attente gRPC. Contient les propriétés suivantes :
  • "task.v1.ttrpc" (Par défaut : "0s") délai d'attente pour les appels ttrpc du serveur de tâches
  • "cri.v1.ttrpc" (Par défaut : "0s") délai d'attente pour les appels ttrpc du serveur CRI

outs
Délais d'attente spécifiés comme une durée
imports
Imports est une liste de fichiers de configuration supplémentaires à inclure. Cela permet de diviser le fichier de configuration principal et de conserver certaines sections séparément (par exemple, les fournisseurs peuvent conserver une configuration d'exécution personnalisée dans un fichier séparant sans modifier le principal config.toml). Les fichiers importés écraseront les champs simples tels que int ou string (s'ils ne sont pas vides) et ajouteront les champs array et map . Les fichiers importés sont également versionnés, et la version ne peut pas être supérieure à celle de la configuration principale.

stream_processors

  • accepts (Par défaut : "[]") Accepte des types de médias spécifiques
  • returns (Par défaut : "") Renvoie le type de média
  • path (Par défaut : "") Chemin ou nom du binaire
  • args (Par défaut : "[]") Arguments du binaire

EXEMPLES

Configuration Complète

Ce qui suit est un exemple de configuration config.toml par défaut complète :

version = 2
root = "/var/lib/containerd"
state = "/run/containerd"
oom_score = 0
imports = ["/etc/containerd/runtime_*.toml", "./debug.toml"]
[grpc]
  address = "/run/containerd/containerd.sock"
  uid = 0
  gid = 0
[debug]
  address = "/run/containerd/debug.sock"
  uid = 0
  gid = 0
  level = "info"
[metrics]
  address = ""
  grpc_histogram = false
[cgroup]
  path = ""
[plugins]
  [plugins."io.containerd.monitor.v1.cgroups"]
    no_prometheus = false
  [plugins."io.containerd.service.v1.diff-service"]
    default = ["walking"]
  [plugins."io.containerd.gc.v1.scheduler"]
    pause_threshold = 0.02
    deletion_threshold = 0
    mutation_threshold = 100
    schedule_delay = 0
    startup_delay = "100ms"
  [plugins."io.containerd.runtime.v2.task"]
    platforms = ["linux/amd64"]
    sched_core = true
  [plugins."io.containerd.service.v1.tasks-service"]
    blockio_config_file = ""
    rdt_config_file = ""

Environnements d'Exécution Multiples

Ce qui suit est un exemple de configuration partielle avec deux environnements d'exécution :

[plugins]
  [plugins."io.containerd.grpc.v1.cri"]
    [plugins."io.containerd.grpc.v1.cri".containerd]
      default_runtime_name = "runc"
      [plugins."io.containerd.grpc.v1.cri".containerd.runtimes]
        [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc]
          privileged_without_host_devices = false
          runtime_type = "io.containerd.runc.v2"
          [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options]
            BinaryName = "/usr/bin/runc"
        [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.other]
          privileged_without_host_devices = false
          runtime_type = "io.containerd.runc.v2"
          [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.other.options]
            BinaryName = "/usr/bin/path-to-runtime"

Ce qui précède crée deux configurations d'environnement d'exécution nommées - nommées runc et other - et définit l'environnement d'exécution par défaut sur runc. Ce qui précède est utilisé uniquement pour les environnements d'exécution invoqués via CRI. Pour utiliser l'environnement d'exécution non par défaut « other » dans cet exemple, une spécification inclura le gestionnaire d'exécution nommé « other » pour spécifier le souhait d'utiliser la configuration d'exécution nommée.

La spécification CRI inclut un ⟨https://github.com/kubernetes/cri-api/blob/de5f1318aede866435308f39cb432618a15f104e/pkg/apis/runtime/v1/api.proto#L476⟩, qui référencera l'environnement d'exécution nommé.

Il est important de noter la convention de nommage. Les environnements d'exécution se trouvent sous [plugins."io.containerd.grpc.v1.cri".containerd.runtimes], chaque environnement d'exécution recevant un nom unique, par exemple [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc]. De plus, chaque environnement d'exécution peut avoir des options spécifiques au shim sous [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.<runtime>.options], par exemple, [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options].

L'environnement d'exécution io.containerd.runc.v2 est utilisé pour exécuter des environnements d'exécution compatibles OCI sur Linux, tels que runc. Dans l'exemple ci-dessus, le champ runtime_type spécifie le shim à utiliser (io.containerd.runc.v2) tandis que le champ BinaryName est une option spécifique au shim qui spécifie le chemin vers l'environnement d'exécution OCI.

Pour la configuration d'exemple nommée « runc », le shim lancera /usr/bin/runc en tant qu'environnement d'exécution OCI. Pour la configuration d'exemple nommée « other », le shim lancera /usr/bin/path-to-runtime à la place.
