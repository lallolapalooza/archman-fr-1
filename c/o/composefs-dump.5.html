NOM

composefs-dump - format de fichier textuel pour le contenu de composefs

DESCRIPTION

Les commandes composefs-info et mkcompose prennent en charge la génération/consommation de descriptions textuelles du contenu d'une image composefs. Ceci peut être utilisé pour inspecter ou modifier une image, ou pour générer une image sans avoir à disposer d'un répertoire local avec les fichiers dedans.

Le format de fichier est très simple, avec un fichier par ligne, d'abord avec 11 champs fixes, suivis d'un nombre variable d'attributs étendus pour le fichier. Il est recommandé, mais pas obligatoire, d'inclure un saut de ligne final pour le dernier fichier.

Les champs sont séparés par un seul espace, et les lignes par un seul saut de ligne. Les attributs étendus utilisent en outre '=' pour séparer la clé de la valeur. Par conséquent, tous ces caractères, ainsi que les caractères non imprimables, sont échappés dans les champs ('=' uniquement dans les champs xattr). De plus, les barres obliques inversées doivent être échappées car elles sont utilisées comme mécanisme d'échappement.

Les échappements sont de la forme \xXY qui échappe un seul octet en utilisant deux chiffres hexadécimaux. Par exemple \x00 est l'octet nul et \xff est l'octet 255. Optionnellement, ces échappements personnalisés sont supportés :

*\\*
: barre oblique inversée.

\n
: saut de ligne.

\r
: retour chariot.

\t
: tabulation

Les champs optionnels qui ne sont pas définis contiennent '-', et si un champ a réellement cette valeur particulière, elle est échappée.

Les champs fixes sur une ligne sont (tous les nombres en base 10 sauf indication contraire) :

CHEMIN
Le chemin complet et absolu du fichier dans l'image. Tous les répertoires utilisés comme préfixe dans le chemin doivent avoir été présents dans le fichier avant cette ligne.
TAILLE
La taille du fichier. Ceci est ignoré pour les répertoires.
MODE
Le champ stat st_mode du fichier en octal, qui inclut à la fois les
permissions et le type de fichier.

De plus, si le fichier est un lien physique (hardlink), ce champ
commencera par un seul caractère '@', et le champ payload pointe
vers le fichier cible. Notez que tous les autres champs sont typiquement
remplis pour un lien physique comme la cible, mais pour la génération
d'un nouveau fichier, nous ignorons tous les champs sauf le payload.

NLINK
Le champ stat st_nlink.
UID
L'uid du propriétaire.
GID
Le gid du propriétaire.
RDEV
Le champ stat st_rdev.
MTIME
L'heure de modification en secondes et nanosecondes depuis l'époque unix
(epoch), séparées par '.'. Notez qu'il ne s'agit pas d'un flottant, "1.1"
signifie une seconde et une nanoseconde.
PAYLOAD
Le payload du fichier. Pour les liens symboliques, il s'agit des cibles de lien symbolique. Pour les fichiers réguliers, il s'agit du nom de chemin relatif des fichiers de support. Pour les liens physiques (voir MODE), il s'agit du chemin d'un autre fichier dans ce fichier dont il s'agit d'un lien physique.
CONTENU
Les petits fichiers peuvent intégrer le contenu réel dans l'image composefs. Ceci contient une version échappée du contenu. Ceci doit correspondre à la taille spécifiée dans TAILLE.
DIGEST
Un digest fs-verity pour le fichier (uniquement utilisé pour les fichiers réguliers, et pas si CONTENU est défini) qui sera validé par rapport aux fichiers de support lors de son utilisation.

Après les champs fixes vient le xattrs, échappé et séparé par des espaces sous la forme CLE=VALEUR. Notez que '=' doit être échappé dans CLE.
