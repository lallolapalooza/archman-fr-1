UTILISATION PAR LES

APPLICATIONS

L'ordre de recherche des commandes permet aux fonctions de remplacer les commandes internes régulières et les recherches dans le chemin. Cet utilitaire est nécessaire pour permettre à des fonctions portant le même nom qu'un utilitaire d'appeler cet utilitaire (au lieu d'un appel récursif à la fonction)

.

Le chemin par défaut du système est disponible en utilisant getconf ; cependant, comme getconf peut avoir besoin que PATH soit défini avant de pouvoir être appelé lui-même, ce qui suit peut être utilisé

: 
command
-p getc
onf PATH

Il y a certains avantages à supprimer occasionnellement les caractéristiques spéciales des commandes internes spéciales. Par exemple

: 
command exec > unwritable-fi
l
e

ne provoque pas l'abandon d'un script non interactif, de sorte que le script peut vérifier le statut de

sortie.

Les utilitaires command, env, nohup, time, et xargs ont été spécifiés pour utiliser le code de sortie 127 en cas d'erreur afin que les applications puissent distinguer « échec de la recherche d'un utilitaire » de « l'utilitaire appelé s'est terminé avec une indication d'erreur ». La valeur 127 a été choisie parce qu'elle n'est pas couramment utilisée pour d'autres significations ; la plupart des utilitaires utilisent de petites valeurs pour les « conditions d'erreur normales » et les valeurs supérieures à 128 peuvent être confondues avec une terminaison due à la réception d'un signal. La valeur 126 a été choisie de manière similaire pour indiquer que l'utilitaire a pu être trouvé, mais pas invoqué. Certains scripts produisent des messages d'erreur significatifs différenciant les cas 126 et 127. La distinction entre les codes de sortie 126 et 127 est basée sur la pratique de KornShell qui utilise 127 lorsque toutes les tentatives de exec de l'utilitaire échouent avec [ENOENT], et utilise 126 lorsque toute tentative de exec de l'utilitaire échoue pour toute autre

raison.

Étant donné que les options -v et -V de command produisent une sortie en relation avec l'environnement d'exécution du shell actuel, command est généralement fourni en tant que commande interne régulière du shell. S'il est appelé dans un sous-shell ou un environnement d'exécution d'utilitaire séparé, comme l'un des suivants

: 
(PATH=foo com
mand -v) noh
up command -v

il ne produit pas nécessairement des résultats corrects. Par exemple, lorsqu'il est appelé avec nohup ou une fonction exec, dans un environnement d'exécution d'utilitaire séparé, la plupart des implémentations ne sont pas capables d'identifier les alias, les fonctions ou les commandes internes

spéciales.

Deux types de commandes internes régulières peuvent être rencontrés sur un système et ceux-ci sont décrits séparément par command. La description de la recherche de commandes dans Section 2.9.1.1, Command Search and Execution permet qu'un utilitaire standard soit implémenté en tant que commande interne régulière tant qu'il est trouvé à l'endroit approprié dans une recherche PATH . Ainsi, par exemple, command -v true pourrait renvoyer /bin/true ou un chemin de fichier similaire. D'autres utilitaires définis par l'implémentation qui ne sont pas définis par ce volume de POSIX.1‐2017 pourraient n'exister que sous forme de commandes internes et n'avoir aucun chemin de fichier associé. Ceux-ci produisent une sortie identifiée comme (régulières) commandes internes. Les applications rencontrant celles-ci ne peuvent pas compter sur leur exécution via exec, sur leur utilisation avec nohup, sur leur remplacement avec un PATH différent, e

t ainsi d
e suite.

JUSTIFICATIO

N

Étant donné que command est un utilitaire interne régulier, il est toujours trouvé avant la recherche dans PATH

.

Rien dans la description de command n'implique que la ligne de commande est analysée différemment de celle de toute autre commande simple. Par exemple

: 
command a | b ;
c

n'est pas analysée d'une manière spéciale qui ferait que '|' ou ';' soient traités autrement qu'un opérateur pipe ou un <point-virgule> ou qui empêcherait la recherche de fonction sur b ou c

.

L'utilitaire command est quelque peu similaire à la commande interne builtin du shell de la huitième édition, mais comme command va aussi dans le système de fichiers pour rechercher des utilitaires, le nom builtin ne serait pas

intuitif.

L'utilitaire command est très probablement fourni en tant que commande interne régulière. Il n'est pas listé comme une commande interne spéciale pour les raisons suivantes

:
*
La suppression des fonctions exportables a rendu la prééminence spéciale d'une commande interne spéciale
inutile.
*
Une commande interne spéciale a des propriétés spéciales (voir Section 2.14, Special Built-In Utilities) qui étaient inappropriées pour invoqu
er d'autres utilitaires. Par exem
ple, deux commandes telles que : 
date > unwritable-fil
e 
command date > unwritable-fi
l
e

auraient des résultats entièrement différents ; dans un script non interactif, la prem

ière continuerait à exécuter la commande suivante, la seconde s'arrêterait. Introduire
cette différence sémantique tout en supprimant les fonctions a été jugé non intuitif.

L'option -p est présente parce qu'il est utile de pouvoir garantir une recherche de chemin sûre qui trouve tous les utilitaires standards. Cette recherche pourrait ne pas être identique à celle qui se produit à travers l'une des fonctions exec (telles que définies dans le volume des interfaces système de POSIX.1‐2017) lorsque PATH n'est pas défini. Au minimum, cette fonctionnalité est requise pour permettre au script d'accéder à la version correcte de getconf afin que la valeur du chemin par défaut puisse être récupérée avec

précision.

Les options command -v et -V ont été ajoutées pour satisfaire les besoins des utilisateurs qui sont actuellement accomplis par trois utilitaires historiques différents : type dans le shell System V, whence dans le KornShell, et which dans le C shell. Puisqu'il n'y a pas d'accord historique sur la manière et le contenu de ce qu'il faut accomplir ici, l'utilitaire POSIX command a été amélioré et les utilitaires historiques ont été laissés non modifiés. Le which du C shell effectue simplement une recherche de chemin. Le whence du KornShell est plus élaboré—en plus des catégories requises par POSIX, il rapporte aussi sur les alias suivis, les alias exportés et les fonctions

indéfinies.

Le format de sortie de -V a été laissé largement non spécifié parce que les utilisateurs humains sont son seul public. Les applications ne devraient pas être écrites pour se soucier de ces informations ; elles peuvent utiliser la sortie de -v pour différencier les différents types de commandes, mais les informations supplémentaires qui peuvent être émises par le -V plus verbeux ne sont pas nécessaires et ne devraient pas être arbitrairement contrainte

s dans leur verbosité ou leur localisation pou
r des raisons d'analyse par les applications.
