NOM

cockpit-ws - Service web de Cockpit

SYNTAXE

cockpit-ws [--help] [--port PORT] [--address ADRESSE] [--no-tls] [--for-tls-proxy] [--local-ssh] [--local-session BRIDGE]

DESCRIPTION

Le programme cockpit-ws est le composant de service web utilisé pour la communication entre l'application du navigateur et divers outils et services de configuration comme cockpit-bridge(1).

Les utilisateurs ou administrateurs n'auront jamais besoin de démarrer ce programme car il est automatiquement démarré par systemd(1) au démarrage, via cockpit-tls(8).

SÉCURITÉ DU TRANSPORT

cockpit-ws est normalement exécuté derrière le proxy de terminaison TLS cockpit-tls, et ne gère que le trafic HTTP non chiffré par lui-même. Mais pour des raisons de compatibilité ascendante, il peut également gérer les connexions TLS par lui-même lorsqu'il est exécuté directement. Pour plus de détails sur la configuration des certificats, veuillez vous référer à la documentation de cockpit-tls(8).

DÉLAI D'ATTENTE

Lorsqu'il est démarré via systemd(1), cockpit-ws se terminera après 90 secondes si personne ne se connecte, ou après la déconnexion du dernier utilisateur.

OPTIONS

--help

Affiche les options d'aide.

--port PORT

Sert les requêtes HTTP sur le port PORT au lieu du port 9090. Normalement, Cockpit est démarré à la demande par l'activation de socket de systemd, et cette option n'a aucun effet. Mettez à jour la directive ListenStream du fichier cockpit.socket de la manière habituelle de systemd.

--address ADRESSE

Se lie à l'adresse ADRESSE au lieu de se lier à toutes les adresses disponibles. Normalement, Cockpit est démarré à la demande par l'activation de socket de systemd, et cette option n'a aucun effet. Dans ce cas, mettez à jour la directive ListenStream dans le fichier cockpit.socket de la manière habituelle de systemd.

--no-tls

N'utilise pas TLS.

--for-tls-proxy

Indique à cockpit-ws qu'il s'exécute derrière un proxy inverse local qui gère la terminaison TLS. Cockpit insère alors des URL https:// dans la politique de sécurité de contenu (Content-Security-Policy) par défaut, et n'accepte que les origines https://, au lieu de http: par défaut. Cependant, si les Origines sont définies dans le fichier de configuration cockpit.conf(5), cela remplacera ce comportement par défaut.

--local-ssh

Normalement, cockpit-ws utilise cockpit-session et PAM pour authentifier l'utilisateur et démarrer une session utilisateur. Avec cette option activée, il s'authentifiera via SSH à 127.0.0.1 port 22.

--local-session BRIDGE

Ignore toute authentification et cockpit-session, et lance le cockpit-bridge spécifié dans BRIDGE dans la session locale. Si BRIDGE est spécifié comme -, attendez-vous à un pont déjà en cours d'exécution et connecté à stdin et stdout de ce processus cockpit-ws. Cela permet au serveur web de s'exécuter en tant que tout utilisateur non privilégié dans une session déjà en cours.

Ce mode implique --no-tls, donc vous devez utiliser des URL http:// avec ce mode.


Avertissement
Si vous utilisez ceci, vous devez isoler le port TCP ouvert d'une manière ou d'une autre (par exemple, dans un espace de noms réseau), sinon tous les autres utilisateurs (ou même les machines distantes si le port n'écoute que sur localhost) peuvent accéder à la session !

ENVIRONNEMENT

Le processus cockpit-ws utilisera la variable d'environnement XDG_CONFIG_DIRS de la spécification XDG basedir[1] pour trouver son fichier de configuration cockpit.conf(5).

De plus, la variable d'environnement XDG_DATA_DIRS de la spécification XDG basedir[1] peut être utilisée pour remplacer l'emplacement depuis lequel servir les fichiers statiques. Ce sont les fichiers qui sont servis à un utilisateur non connecté.
