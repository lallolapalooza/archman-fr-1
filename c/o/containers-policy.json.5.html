Transport Scopes

The following scopes are supported:

dir:

Supported scopes are paths to directories containing Singularity images.

Note: - The paths must be absolute and contain no symlinks. Paths violating these requirements may be silently ignored. - The top-level scope "/" is forbidden; use the transport default scope "",
for consistency with other transports.

docker:

Supported scopes are Docker image names, and their parent namespaces (e.g. docker.io/library/).

Note: - The paths must be absolute and contain no symlinks. Paths violating these requirements may be silently ignored. - The top-level scope "/" is forbidden; use the transport default scope "",
for consistency with other transports.

oci:

Supported scopes are OCI image names, and their parent namespaces.

Note: - The paths must be absolute and contain no symlinks. Paths violating these requirements may be silently ignored. - The top-level scope "/" is forbidden; use the transport default scope "",
for consistency with other transports.

sif:

Supported scopes are paths to Singularity images, and their parent directories (either containing images, or subdirectories possibly containing images).

Note: - The paths must be absolute and contain no symlinks. Paths violating these requirements may be silently ignored. - The top-level scope "/" is forbidden; use the transport default scope "",
for consistency with other transports.

tarball:

The tarball: transport is an implementation detail of some import workflows. Only the default "" scope is supported.

Exigences de politique

En utilisant les mécanismes ci-dessus, un ensemble d'exigences de politique est recherché. Les exigences de politique sont représentées comme un tableau JSON d'objets d'exigences individuels. Pour qu'une image soit acceptée, *toutes* les exigences doivent être satisfaites simultanément.

Les exigences de politique peuvent également être utilisées pour décider si une signature individuelle est acceptée (= est signée par une clé reconnue d'un auteur connu) ; dans ce cas, certaines exigences peuvent ne s'appliquer qu'à certaines signatures, mais chaque signature doit être acceptée par *au moins un* objet d'exigence.

Les objets d'exigence suivants sont pris en charge :

insecureAcceptAnything

Une exigence simple avec la syntaxe suivante

{"type":"insecureAcceptAnything"}

Cette exigence accepte n'importe quelle image (mais notez que d'autres exigences dans le tableau s'appliquent toujours).

Lors de la décision d'accepter une signature individuelle, cette exigence n'a aucun effet ; elle ne provoque *pas* l'acceptation de la signature, cependant.

Ceci est utile principalement pour les scopes de politique où aucune vérification de signature n'est requise ; parce que le tableau des exigences de politique ne doit pas être vide, cette exigence est utilisée pour représenter explicitement l'absence d'exigences.

reject

Une exigence simple avec la syntaxe suivante :

{"type":"reject"}

Cette exigence rejette toutes les images et toutes les signatures.

signedBy

Cette exigence requiert qu'une image soit signée en utilisant la "signature simple" avec une identité attendue, ou accepte une signature si elle utilise une identité et une clé attendues.

{
    "type":    "signedBy",
    "keyType": "GPGKeys", /* La seule valeur actuellement prise en charge */
    "keyPath": "/chemin/vers/fichier/keyring/local",
    "keyPaths": ["/chemin/vers/fichier/keyring/local1","/chemin/vers/fichier/keyring/local2"…],
    "keyData": "donnees-keyring-encodees-en-base64",
    "signedIdentity": exigence_identite
}

Exactement un parmi keyPath, keyPaths et keyData doit être présent, contenant un keyring GPG d'une ou plusieurs clés publiques. Seules les signatures faites par ces clés sont acceptées.

Le champ signedIdentity, un objet JSON, spécifie quelle identité d'image la signature revendique à propos de l'image. Une des alternatives suivantes est prise en charge :

  • L'identité dans la signature doit correspondre exactement à l'identité de l'image. Notez qu'avec cela, référencer une image par son digest (avec une signature revendiquant une identité de *référentiel*:*étiquette*) échouera. 
      {"type":"matchExact"}
  • Si l'identité de l'image porte une étiquette, l'identité dans la signature doit correspondre exactement ; si l'identité de l'image utilise une référence de digest, l'identité dans la signature doit être dans le même référentiel que l'identité de l'image (en utilisant n'importe quelle étiquette).

(Notez qu'avec les images identifiées par des références de digest, le digest de la référence est validé avant même le début de la vérification de la signature.)

  {"type":"matchRepoDigestOrExact"}
  • L'identité dans la signature doit être dans le même référentiel que l'image identifiée. Ceci est utile par ex. pour tirer une image en utilisant l'étiquette :latest lorsque l'image est signée avec une étiquette spécifiant une version d'image exacte. 
      {"type":"matchRepository"}
  • L'identité dans la signature doit correspondre exactement à une identité spécifiée. Ceci est utile par ex. lors de la mise en miroir locale d'images signées en utilisant leur identité publique. 
      {
      "type": "exactReference",
      "dockerReference": valeur_reference_docker
  }
  • L'identité dans la signature doit être dans le même référentiel qu'une identité spécifiée. Ceci combine les propriétés de matchRepository et exactReference. 
      {
      "type": "exactRepository",
      "dockerRepository": valeur_repository_docker
  }
  • Remappage de préfixe :

Si l'identité de l'image correspond au préfixe spécifié, ce préfixe est remplacé par le "préfixe signé" spécifié
(sinon, il est utilisé tel quel et aucun remappage n'a lieu) ;
la correspondance suit ensuite la sémantique de matchRepoDigestOrExact documentée ci-dessus
(c'est-à-dire si l'identité de l'image porte une étiquette, l'identité dans la signature doit correspondre exactement,
si elle utilise une référence de digest, le référentiel doit correspondre).

Les valeurs prefix et signedPrefix peuvent être soit des valeurs hôte[:port]
(correspondant exactement au même hôte[:port], chaîne),
des espaces de noms de référentiel, ou des référentiels (c'est-à-dire qu'ils ne doivent pas contenir d'étiquettes/digests),
et correspondent en tant que préfixes *de la forme entièrement développée*.
Par exemple, docker.io/library/busybox (*pas* busybox) pour spécifier ce référentiel unique,
ou docker.io/library (pas une chaîne vide) pour spécifier l'espace de noms parent de docker.io/library/busybox==busybox).

La valeur prefix est généralement la même que le scope contenant l'exigence signedBy parente.

  {
      "type": "remapIdentity",
      "prefix": prefix,
      "signedPrefix": prefix,
  }

Si le champ signedIdentity est absent, il est traité comme matchRepoDigestOrExact.

Note : matchExact, matchRepoDigestOrExact et matchRepository ne peuvent être utilisés que si une identité d'image de type Docker est fournie par le transport. En particulier, les transports dir: et oci: ne peuvent être utilisés qu'avec exactReference ou exactRepository.

sigstoreSigned

Cette exigence requiert qu'une image soit signée en utilisant une signature sigstore avec une identité et une clé attendues.

{
    "type":    "sigstoreSigned",
    "keyPath": "/chemin/vers/fichier/cle/publique/local",
    "keyPaths": ["/chemin/vers/premier/cle/publique/un", "/chemin/vers/premier/cle/publique/deux"],
    "keyData": "donnees-cle-publique-encodees-en-base64",
    "keyDatas": ["donnees-cle-publique-une-encodees-en-base64", "donnees-cle-publique-deux-encodees-en-base64"]
    "fulcio": {
        "caPath": "/chemin/vers/fichier/CA/local",
        "caData": "donnees-CA-encodees-en-base64",
        "oidcIssuer": "https://issuer.OIDC.attendu/",
        "subjectEmail", "utilisateur-signature-attendu@exemple.com",
    },
    "pki": {
        "caRootsPath": "/chemin/vers/fichier/CARoots/local",
        "caRootsData": "donnees-CARoots-encodees-en-base64",
        "caIntermediatesPath": "/chemin/vers/fichier/CAIntermediates/local",
        "caIntermediatesData": "donnees-CAIntermediates-encodees-en-base64",
        "subjectHostname": "hote-signature-attendu.exemple.com",
        "subjectEmail": "utilisateur-signature-attendu@exemple.com"
    },
    "rekorPublicKeyPath": "/chemin/vers/fichier/cle/publique/local",
    "rekorPublicKeyPaths": ["/chemin/vers/fichier/cle/publique/un","/chemin/vers/fichier/cle/publique/deux"],
    "rekorPublicKeyData": "donnees-cle-publique-encodees-en-base64",
    "rekorPublicKeyDatas": ["donnees-cle-publique-une-encodees-en-base64","donnees-cle-publique-deux-encodees-en-base64"],
    "signedIdentity": exigence_identite
}

Exactement un parmi keyPath, keyPaths, keyData, keyDatas, fulcio et pki doit être présent.

Si keyPath ou keyData est présent, il contient une clé publique sigstore. Seules les signatures faites par cette clé sont acceptées.

Si keyPaths ou keyDatas est présent, il contient des clés publiques sigstore. Seules les signatures faites par n'importe quelle clé de la liste sont acceptées.

Si fulcio est présent, la signature doit être basée sur un certificat délivré par Fulcio. Un parmi caPath et caData doit être spécifié, contenant la clé publique de l'instance Fulcio. oidcIssuer et subjectEmail sont tous deux obligatoires, spécifiant exactement le fournisseur d'identité attendu et l'identité de l'utilisateur obtenant le certificat Fulcio.

Si pki est présent, la signature doit être basée sur un certificat X.509 non-Fulcio. Un parmi caRootsPath et caRootsData doit être spécifié, contenant les certificats des CA. Un seul parmi caIntermediatesPath et caIntermediatesData peut être présent, contenant les certificats des CA intermédiaires. Un parmi subjectEmail et subjectHostname doit être spécifié, spécifiant exactement l'identité attendue à laquelle le certificat a été délivré.

Au plus un parmi rekorPublicKeyPath, rekorPublicKeyPaths, rekorPublicKeyData et rekorPublicKeyDatas peut être présent ; il est obligatoire si fulcio est spécifié. Si une clé publique Rekor est spécifiée, la signature doit avoir été téléchargée sur un serveur Rekor et la signature doit contenir un "timestamp d'entrée signé" (vérifiable hors ligne) prouvant l'existence de l'enregistrement de journal Rekor, signé par l'une des clés publiques fournies.

Le champ signedIdentity a la même sémantique que dans l'exigence signedBy décrite ci-dessus. Notez que les signatures créées par cosign ne contiennent qu'un référentiel, donc seuls matchRepository et exactRepository peuvent être utilisés pour les accepter (et cela ne protège pas contre la substitution d'une image signée par une étiquette inattendue).

Pour utiliser ceci avec des images hébergées sur des registres d'images, l'option use-sigstore-attachments doit être activée pour le registre pertinent

policy.json(5) — archlinux

NAME

policy.json — Policy file for controlling access to container registries

DESCRIPTION

The policy.json file defines the policies that the container runtime uses to control access to container images. It allows for fine-grained control over which container registries and repositories are trusted, and what types of cryptographic verification are required.

FORMAT

The policy file is a JSON file with the following structure:

{
    "default": policy_requirement_list,
    "transports": {
        transport_name: policy_requirement_list,
        ...
    }
}

default: A list of policy requirements that apply to all transports and repositories unless overridden by a more specific rule. If no specific rule matches, this list is used.

transports: An object where keys are transport names (e.g., docker, dir, atomic) and values are objects that define policies for specific repositories within that transport.

The policy requirements list is an array of objects, each specifying a policy requirement type and its associated parameters. For example:

[
    {"type": "acceptAll"},
    {"type": "reject"},
    {"type": "insecureAcceptAnything"},
    {"type": "signedBy", "keyType": "GPGKeys", "keyPath": "/etc/pki/containers/redhat.gpg"},
    {"type": "sigstoreSigned", "keyPath": "/etc/pki/containers/sigstore.pub"}
]

Supported transports and their scopes

The following transports are supported:

docker
Policies for images fetched from Docker-compatible registries. Scopes are repository names, including the registry hostname (e.g., docker.io/library/ubuntu, quay.io/coreos/etcd).
dir
Policies for images loaded from local directories. The scope is an empty string ("") which matches all local directories.
atomic
Policies for images fetched from Atomic-compatible registries. Scopes are repository names.

Policy Requirements

acceptAll
Accepts any image, regardless of its origin or signature.
reject
Rejects any image unless explicitly allowed by another policy.
insecureAcceptAnything
Accepts any image but does not verify any signatures. This is equivalent to acceptAll.
signedBy
Requires the image to be signed by a trusted key.
  • keyType: The type of key used for signing (e.g., GPGKeys).
  • keyPath: The path to the public key file.
  • signedIdentity: (Optional) An object that specifies constraints on the identity of the signer.
    • type: The type of identity constraint. Possible values:
      • exactRepository: The image must be signed by the specified repository.
        • dockerRepository: The exact Docker repository name.
      • remapIdentity: The image must be signed by the specified repository, but the repository name in the signature can be different from the one being accessed.
        • prefix: The prefix of the repository name being accessed.
        • signedPrefix: The prefix of the repository name in the signature.
      • matchRepository: The image must be signed by the repository that matches the repository being accessed.
sigstoreSigned
Requires the image to be signed using Sigstore.
  • keyPath: (Optional) The path to the public key file for verification. If not provided, Sigstore's default trust configuration is used.
  • fulcio: (Optional) Configuration for verifying Sigstore certificates issued by Fulcio.
    • caPath: Path to the Fulcio CA certificate.
    • oidcIssuer: The OIDC issuer URL.
    • subjectEmail: The expected email address of the certificate subject.
  • rekorPublicKeyPath: (Optional) Path to the Rekor public key for verifying Sigstore transparency log entries.
  • pki: (Optional) Configuration for verifying Sigstore certificates issued by a custom PKI.
    • caRootsPath: Path to the root CA certificates.
    • caIntermediatesPath: Path to the intermediate CA certificates.
    • subjectHostname: The expected hostname of the certificate subject.
    • subjectEmail: The expected email address of the certificate subject.
  • signedIdentity: (Optional) Constraints on the identity of the signer, similar to the signedBy policy.

When multiple policy requirements are specified for a transport or repository, all requirements must be met for the image to be accepted.

The policy evaluation proceeds as follows:

  1. Check for a specific policy defined for the transport and repository.
  2. If no specific policy is found, check for a policy defined for the transport only.
  3. If no transport-specific policy is found, use the global default policy.

Note that the policy file does not directly support wildcards. For example, to allow all subdomains of a registry, you would need to explicitly list each subdomain or use a tool that generates the policy file with all necessary entries. Comments enclosed in /* ... */ are not valid JSON and should not be included in actual policy files.

For detailed information on specific repository names and how to reference them, refer to the documentation for the respective container registry or transport, and specifically to the containers-registries.d(5) manual page for registry or repository in the client's containers-registries.d(5).

Examples

Il est fortement recommandé de définir la politique default sur reject, puis d'autoriser sélectivement les transports et scopes individuels selon vos besoins.

Un système raisonnablement verrouillé

(Notez que les commentaires /*…*/ ne sont pas valides en JSON et ne doivent pas être utilisés dans les politiques réelles.)

{
    "default": [{"type": "reject"}], /* Rejeter tout ce qui n'est pas explicitement autorisé */
    "transports": {
        "docker": {
            /* Autoriser l'installation d'images à partir d'un espace de noms de référentiel spécifique, sans vérification cryptographique.
               Cet espace de noms comprend des images comme openshift/hello-openshift et openshift/origin. */
            "docker.io/openshift": [{"type": "insecureAcceptAnything"}],
            /* De même, autoriser l'installation des images busybox « officielles ». Notez comment la forme entièrement développée,
               avec le /library/ explicite, doit être utilisée. */
            "docker.io/library/busybox": [{"type": "insecureAcceptAnything"}],
            /* Autoriser l'installation d'images à partir de tous les sous-domaines */
            "*.temporary-project.example.com": [{"type": "insecureAcceptAnything"}],
            /* Un référentiel signé par sigstore */
            "hostname:5000/myns/sigstore-signed-with-full-references": [
                {
                    "type": "sigstoreSigned",
                    "keyPath": "/path/to/sigstore-pubkey.pub"
                }
            ],
            /* Un référentiel signé par sigstore utilisant les serveurs communautaires Fulcio+Rekor.
               Les clés publiques des serveurs communautaires peuvent être obtenues à partir de
               https://github.com/sigstore/sigstore/tree/main/pkg/tuf/repository/targets .  */
            "hostname:5000/myns/sigstore-signed-fulcio-rekor": [
                {
                    "type": "sigstoreSigned",
                    "fulcio": {
                        "caPath": "/path/to/fulcio_v1.crt.pem",
                        "oidcIssuer": "https://github.com/login/oauth",
                        "subjectEmail": "test-user@example.com"
                    },
                    "rekorPublicKeyPath": "/path/to/rekor.pub",
                }
            ],
            /* Un référentiel signé par Sigstore utilisant un certificat généré par une infrastructure à clé publique personnalisée.*/
            "hostname:5000/myns/sigstore-signed-byopki": [
                {
                    "type": "sigstoreSigned",
                    "pki": {
                        "caRootsPath": "/path/to/pki_root_crts.pem",
                        "caIntermediatesPath": "/path/to/pki_intermediate_crts.pem",
                        "subjectHostname": "test-user.example.com"
                        "subjectEmail": "test-user@example.com"
                    }
                }

            "hostname:5000/myns/sigstore-signed-allows-malicious-tag-substitution": [

            "hostname:5000/myns/official": [
