containers.conf - Le fichier de configuration du moteur de contene

urs spécifie les options de configuration par défaut et les in
dicateurs de ligne de commande pour les moteurs de conteneurs.

DESCRIPTIO

N

Les moteurs de conteneurs comme Podman et Buildah lisent le fichier containers.conf, s'il existe, et modifient les valeurs par défaut pour l'exécution des conteneurs sur l'hôte. containers.conf utilise un format TOML qui peut être facilement modifié et

versionné.

Les moteurs de conteneurs lisent les fichiers /usr/share/containers/containers.conf, /etc/containers/containers.conf et /etc/containers/containers.conf.d/*.conf pour la configuration globale qui affecte tous les utilisateurs. Pour la configuration globale qui n'affecte que les utilisateurs rootless, utilisez /etc/containers/containers.rootless.conf, /etc/containers/containers.rootless.d/*.conf et /etc/containers/containers.rootless.d/\$UID/*.conf. Le UID est l'uid de l'utilisateur sous lequel podman s'exécute, il peut donc être utilisé pour spécifier une configuration pour un seul utilisateur sans avoir à placer la configuration dans le répertoire personnel de l'utilisateur. Pour la configuration spécifique à l'utilisateur, il lit les fichiers \$XDG_CONFIG_HOME/containers/containers.conf et \$XDG_CONFIG_HOME/containers/containers.conf.d/*.conf. Quand $XDG_CONFIG_HOME n'est pas défini, il utilise $HOME/.config à la

place.

Les champs spécifiés dans containers.conf remplacent les options par défaut, ainsi que les options des fichiers containers.conf lus

précédemment.

Les fichiers de configuration dans les répertoires .d sont ajoutés dans l'ordre alphanumérique et doivent se terminer par .con

f.

Toutes les options ne sont pas prises en charge dans tous les moteurs de

conteneurs.

Remarque : les moteurs de conteneurs utilisent également d'autres fichiers de configuration pour configurer l'environnement

.
  • storage.conf pour la configuration du stockage des conteneurs et des
    • images.
  • registries.conf pour la définition des registres de conteneurs à rechercher lors de l'extraction des images de
    • conteneurs.
  • policy.conf pour contrôler quelles images pe
    • uvent être extraites
vers le système.

Remarque : si Podman s'exécute dans une machine virtuelle en utilisant podman machine (cela inclut les hôtes Mac et Windows), assurez-vous que les fichiers de configuration sont modifiés dans la machine virtuelle en utilisant podman m

achin
e ssh.

VARIABLES

D'ENVIRONNEMENT

Si la variable d'environnement CONTAINERS_CONF est définie, tous les fichiers de configuration système et utilisateur sont ignorés et seul le fichier de configuration spécifié sera

chargé.

Si la variable d'environnement de chemin CONTAINERS_CONF_OVERRIDE est définie, le fichier de configuration sera chargé en dernier même quand CONTAINERS_CONF est

défini.

Les valeurs des deux variables d'environnement peuvent être des chemins absolus ou relatifs, par exemple, CONTAINERS_CONF=/tmp

/my_contai
ners.conf.

MODULE

S

Un module est un fichier containers.conf situé directement dans ou dans un sous-répertoire de l'un des trois répertoires suivants :
- \$XDG_CONFIG_HOME/containers/containers.conf.modules ou \$HOME/.config/containers/containers.conf.modules si $XDG_CONFIG_HOME n'est pas défini.
- /etc/containers/containers.conf.modules
- /usr/share/containers/containers.conf.

modules

Les fichiers à ces emplacements ne sont pas chargés par défaut, mais uniquement à la demande. Ils sont chargés après tous les fichiers de configuration système et utilisateur, mais avant CONTAINERS_CONF_OVERRIDE, permettant ainsi de remplacer les configurations système et

utilisateur.

Les modules sont actuellement pris en charge par podman(1). L'indicateur podman --module permet de charger un module et peut être spécifié plusieurs fois. Si la valeur spécifiée est un chemin absolu, le fichier de configuration sera chargé directement. Les chemins relatifs sont résolus par rapport aux trois répertoires de modules mentionnés ci-dessus et dans l'ordre spécifié, de sorte que les modules dans $XDG_CONFIG_HOME/$HOME permettent de remplacer ceux dans /etc et /usr/shar

e
.

CHAÎNES

Le comportement par défaut lors de la séquence de chargement de plusieurs fichiers containers.conf est de remplacer les données précédentes. Pour changer le comportement du remplacement à l'ajout, vous pouvez définir l'attribut append comme suit : array=["item-1", "item=2", ..., {append=true}]. Définir l'attribut append indique d'ajouter à ce tableau de chaînes spécifique pour l'étape de chargement actuelle et les étapes de chargement suivantes. Pour revenir au remplacement, définissez {append=fa

lse}.

Considérez l'exemple suivant

: 
modules1.conf: env=["1=true"]
modules2.conf: env=["2=true"]
modules3.conf: env=["3=true", {append=true}]
modules4.conf:
env=["4=true"]

Après le chargement des fichiers dans l'ordre donné, le contenu final est env=["2=true", "3=true", "4=true"]. Si modules4.conf définissait {append=false}, le contenu final serait env=["4=

tru
e"].

  • outbound_addr6=INTERFACE : Spécifie l'interface sortante sur laquelle slirp doit se lier (trafic IPv6 uniquement).

  • port_handler=slirp4netns : Utilise la redirection de ports slirp4netns, qui est plus lente que rootlesskit mais préserve la bonne adresse IP source. Ce gestionnaire de ports ne peut pas être utilisé pour les réseaux définis par l'utilisateur.

Ils peuvent également déposer des fichiers .conf dans /etc/containers/containers.conf.d qui seront chargés dans l'ordre alphanumérique.
