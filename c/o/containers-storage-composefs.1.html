NOM

containers-storage-composefs - Informations sur composefs et containers/storage

DESCRIPTION

Pour activer composefs à un niveau de base, la configuration suivante est requise dans containers-storage.conf :

[storage.options.overlay]
use_composefs = "true"

Cette valeur doit être une "chaîne booléenne", elle ne peut pas être un booléen TOML natif.

Cependant, à l'heure actuelle, composefs nécessite des images zstd:chunked. Assurez-vous donc d'abord que zstd:chunked est activé. Pour en savoir plus, voir zstd:chunked ⟨containers-storage-zstd-chunked.md⟩.

De plus, peu d'images sont au format zstd:chunked. Afin de combler cette lacune, convert_images = "true" peut être spécifié, ce qui effectue une conversion dynamique ; cela ajoute de la latence aux téléchargements d'images.

En combinant ces éléments, ce qui suit est requis (en plus de la configuration ci-dessus).

[storage.options.pull_options]
convert_images = "true"

Cette valeur doit être une "chaîne booléenne", elle ne peut pas être un booléen TOML natif.

IMPLÉMENTATION

Comme le suggère le réglage use_composefs = "true", composefs est actuellement implémenté comme une "option" pour le pilote overlay. Certains formats de fichiers restent inchangés et sont hérités du pilote overlay, même lorsque composefs est utilisé. Les principales différences sont énumérées ci-dessous.

Le répertoire diff/ pour chaque couche n'est plus un simple décompression de l'archive tar, mais devient un "répertoire de hachage d'objet", où chaque nom de fichier est le sha256 de son contenu. Ce répertoire diff/ est le support d'un composefs-data/composefs.blob créé pour chaque couche, qui est le "superbloc" de composefs contenant tout le contenu non-régulier (c'est-à-dire les métadonnées) de l'archive tar.

Comme avec zstd:chunked, les couches existantes sont scannées pour les objets correspondants, et réutilisées (via hardlink ou reflink selon la configuration) si des objets avec un "sha256 complet" correspondant sont trouvés.

Il n'y a actuellement aucun support pour l'intégrité forcée avec composefs ; une tentative est faite pour activer fsverity pour les fichiers sous-jacents et le fichier composefs, mais ce n'est pas une erreur si ce n'est pas supporté. Il n'existe pas encore de mécanisme défini pour vérifier le digest fsverity du bloc composefs avant le montage ; des travaux sont en cours à ce sujet.

Afin de monter une couche (ou une image complète, avec toutes ses dépendances), toute couche qui possède un blob composefs est montée et incluse dans la pile "finale" d'overlayfs. Ceci est facultatif - toutes les couches qui ne sont pas au "format composefs" mais au format "overlay par défaut" (décompressé) seront réutilisées telles quelles.

NOTES DE BAS DE PAGE

Le projet Containers Storage est engagé envers l'inclusivité, une valeur fondamentale de l'open source. La terminologie master et slave pour la propagation des montages est utilisée dans ce dépôt. Ce langage est problématique et diviseur, et devrait être modifié. Cependant, ces termes sont actuellement utilisés dans le noyau Linux et doivent être utilisés tels quels pour le moment. Lorsque les mainteneurs du noyau rectifieront cette utilisation, Containers Storage suivra immédiatement.
