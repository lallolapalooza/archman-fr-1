FILTER

Filtrage des événements. Cette clause vous permet de filtrer certains trafics.

Il existe actuellement trois ensembles de filtres : Protocol, Address et State. Le filtre est associé à une action qui peut être : Accept ou Ignore. Ainsi, vous pouvez définir la politique de filtrage des événements des ensembles de filtres en logique positive ou négative selon vos besoins.

Vous pouvez choisir si conntrackd(8) filtre les messages d'événements depuis l'espace utilisateur ou l'espace noyau. Le filtrage des événements depuis l'espace noyau économise des cycles CPU en évitant la copie du message d'événement de l'espace noyau vers l'espace utilisateur. Le filtrage depuis l'espace noyau est préféré, cependant, vous avez besoin d'un Noyau Linux >= 2.6.29 pour filtrer depuis l'espace noyau.

La syntaxe pour cette section est : Filter From <from> { }.

Si vous voulez sélectionner le filtrage des événements depuis l'espace noyau, utilisez le mot-clé Kernelspace au lieu de Userspace.

Exemple :

Filter From Userspace {
	Protocol Accept {
		TCP
		SCTP
		DCCP
	}
	Address Ignore {
		IPv4_address 127.0.0.1
		IPv6_address ::1
	}
	State Accept {
		ESTABLISHED CLOSED TIME_WAIT CLOSE_WAIT for TCP
	}
}
Protocol <policy> { <protocols list> }

La politique est l'une des suivantes : Accept ou Ignore.

Les protocoles sont : TCP, SCTP, DCCP, UDP, ICMP et IPv6-ICMP.

Les protocoles ICMP et IPv6-ICMP nécessitent un Noyau Linux >= 2.6.31.

Exemple :

	TCP

Ignorer le trafic pour un ensemble d'adresses IP : Généralement toutes les IP assignées au pare-feu puisque le trafic local doit être ignoré, seules les connexions transmises valent la peine d'être répliquées.

Notez que ces valeurs dépendent des IP locales qui sont assignées au pare-feu.

Vous pouvez spécifier plusieurs directives IPv4_address et/ou IPv6_address . Vous pouvez aussi spécifier des réseaux au format CIDR.

La politique est l'une des suivantes : Accept ou Ignore.

Exemple :

Address Ignore {

Les états TCP existants sont : SYN_SENT, SYN_RECV, ESTABLISHED, FIN_WAIT, CLOSE_WAIT, LAST_ACK, TIME_WAIT, CLOSED et LISTEN.

HELPER

Remarque : cette configuration est très avancée et n'a rien à voir avec la synchronisation ou la collecte de statistiquestion.

Cette section de premier niveau indique conntrackd(8) d'injecter des helpers espace utilisateur dans le sous-système noyau nf_conntrack de Linux. Cela entraînera le fait que le moteur nf_conntrack envoie les connexions à l'espace utilisateur pour un traitement ultérieur.

Avant cela, vous devez vous assurer d'avoir enregistré le bouchon d'helper espace utilisateur donné.

Exemple :

% nfct add helper ftp inet tcp

Chaque helper espace utilisateur doit être enregistré à l'aide d'une section Type, qui sont nommées de cette manière :

Type <name> <af> <transport>

Exemples :

Helper {
	Type ftp inet tcp {
		QueueNum 0
		QueueLen 10240
		Policy ftp {
			ExpectMax 1
			ExpectTimeout 300
		}
	}
	Type rpc inet tcp {
		QueueNum 1
		QueueLen 10240
		Policy rpc {
			ExpectMax 1
			ExpectTimeout 300
		}
	}
	Type rpc inet udp {
		QueueNum 2
		QueueLen 10240
		Policy rpc {
			ExpectMax 1
			ExpectTimeout 300
		}
	}
	Type tns inet tcp {
		QueueNum 3
		QueueLen 10240
		Policy tns {
			ExpectMax 1
			ExpectTimeout 300
		}
	}
	Type dhcpv6 inet6 udp {
		QueueNum 4
		QueueLen 10240
		Policy dhcpv6 {
			ExpectMax 1
			ExpectTimeout 300
		}
	}
	Type ssdp inet udp {
		QueueNum 5
		QueueLen 10240
		Policy ssdp {
			ExpectMax 1
			ExpectTimeout 300
		}
	}
}

Paramètres à l'intérieur de la section Type :

QueueNum <number>
Définissez le numéro NFQUEUE que vous souhaitez utiliser pour recevoir le trafic du noyau.

Exemple : QueueNum 0

QueueLen <number]]
Nombre maximal de paquets en attente dans la file d'attente pour recevoir un verdict de l'espace utilisateur.

Augmentez la valeur si vous rencontrez le message d'erreur suivant :

"nf_queue: full at X entries, dropping packet(s)"

La valeur par défaut est 1024.

Exemple : QueueLen 10240

Policy <name> { }
Définissez la politique d'attente pour l'helper donné.

Cette sous-section contient 2 directives : ExpectMax <number> (nombre maximal d'attentes simultanées) et ExpecTimeout <seconds> (durée de vie maximale pour une attente).
