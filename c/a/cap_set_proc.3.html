cap_set_proc(3)

CAP_GET_PROC(3) Manuel du programmeur Linux CAP_GET_PROC(3)

NOM

CAP_IS_SUPPORTED(cap_value_t cap);

	      long int arg3, long int arg4, long int arg5);
int cap_prctlw(long int pr_cmd, long int arg1, long int arg2,
	       long int arg3, long int arg4, long int arg5);

Lier avec -lcap.

DESCRIPTION

cap_get_proc() alloue un état de capacité dans la mémoire de travail, met à jour son état par rapport à celui du processus appelant, et retourne un pointeur vers cet état de capacité nouvellement créé. L'appelant doit libérer toute mémoire libérable, lorsque l'état de capacité en mémoire de travail n'est plus requis, en appelant cap_free() avec le cap_t comme argument.

cap_set_proc() définit les valeurs de tous les indicateurs de capacité pour toutes les capacités à l'état de capacité identifié par cap_p. Le nouvel état de capacité du processus sera complètement déterminé par le contenu de cap_p après un retour réussi de cette fonction. Si un indicateur quelconque dans cap_p est défini pour une capacité non actuellement permise pour le processus appelant, la fonction échouera, et l'état de capacité du processus restera inchangé.

cap_get_pid() retourne un cap_t, voir cap_init(3), avec les capacités de processus du processus connu de l'appelant par pid. Si pid est 0, alors les capacités du processus appelant sont retournées. Ces informations peuvent également être obtenues à partir du fichier /proc/<pid>/status. (Les entrées de ce fichier peuvent être traduites avec la commande capsh --decode=XXX.) Lorsque l'appelant opère dans un espace de noms (CLONE_NEWPID), l'argument pid numérique est interprété dans la plage de cet espace de noms. Ainsi, l'idée que l'appelant se fait du pid cible peut différer de celle du processus cible lorsqu'ils opèrent dans des espaces de noms pid différents. Voir pid_namespaces(7) pour plus de détails. De plus, le cap_t retourné contient les capacités que le processus pid cible pense avoir. Si la cible opère dans un espace de noms (CLONE_NEWUSER), le privilège système de ces capacités d'espace de noms utilisateur peut être considérablement réduit. Voir user_namespaces(7) pour plus de détails.

cap_get_bound() avec un argument cap retourne la valeur actuelle de cet indicateur de capacité de l'ensemble de délimitation en vigueur pour le processus appelant. Cette opération est non privilégiée. Notez qu'une macro fonction CAP_IS_SUPPORTED(cap_value_t cap) est fournie et évalue à vrai (1) si le système prend en charge la capacité spécifiée, cap. Si le système ne prend pas en charge la capacité, cette fonction retourne 0. Cette macro fonctionne en testant une condition d'erreur avec cap_get_bound().

cap_drop_bound() peut être utilisé pour abaisser la capacité spécifiée de l'ensemble de délimitation, cap. Pour réussir, l'ensemble de capacités effectif prédominant doit avoir la capacité CAP_SETPCAP relevée.

cap_get_ambient() retourne la valeur prédominante de la capacité ambiante spécifiée, ou -1 si la capacité n'est pas prise en charge par le noyau en cours d'exécution. Une macro CAP_AMBIENT_SUPPORTED() utilise cette fonction pour déterminer si les capacités ambiantes sont prises en charge par le noyau.

cap_set_ambient() définit la capacité ambiante spécifiée à une valeur spécifique. Pour relever une capacité ambiante spécifique, les indicateurs héritables et permis du processus appelant doivent contenir la valeur de capacité spécifiée. Les bits ambiants relevés ne seront conservés que tant que cela restera vrai pour les indicateurs héritables et permis.

cap_reset_ambient() réinitialise toutes les capacités ambiantes du processus appelant à leur valeur abaissée. Notez que l'ensemble ambiant est conçu pour fonctionner dans un environnement hérité où l'application a une conscience limitée des capacités en général. Lors de l'exécution d'un fichier, avec les capacités de système de fichiers associées, le noyau réinitialisera implicitement l'ensemble ambiant du processus. De plus, les modifications apportées à l'ensemble héritable par le code du programme sans correction explicite de l'ensemble ambiant peuvent également abaisser les bits ambiants.

cap_get_secbits() retourne les bits sécurisés (securebits) du processus appelant. Ces bits affectent la manière dont le processus appelant implémente des choses comme la correction setuid-root et les capacités ambiantes.

cap_set_secbits() tente de modifier les bits sécurisés du processus appelant. Notez que CAP_SETPCAP doit être présent dans l'ensemble de capacités effectif pour que cela soit efficace. Certains paramètres verrouillent les sous-états des bits sécurisés, de sorte que les tentatives de définition de valeurs peuvent être refusées par le noyau même lorsque la capacité CAP_SETPCAP est relevée.

Pour aider à gérer la complexité des bits sécurisés, libcap fournit un concept combiné de bits sécurisés et d'ensemble de capacités appelé mode libcap. cap_get_mode() tente de résumer l'environnement de sécurité prédominant sous la forme d'une valeur numérique cap_mode_t. Une représentation textuelle du mode peut être obtenue via la fonction cap_mode_name(). La grande majorité des combinaisons de ces valeurs ne sont pas bien définies en termes de mode libcap, et pour ces états cap_get_mode() retourne (cap_mode_t)0, que cap_get_name() identifie comme «UNCERTAIN». Les modes pris en charge sont : CAP_MODE_NOPRIV, CAP_MODE_HYBRID, CAP_MODE_PURE1E et CAP_MODE_PURE1E_INIT.

cap_prctl() peut être utilisé pour lire l'état via l'appel système prctl().

cap_prctlw() peut être utilisé pour écrire l'état via l'appel système prctl().

cap_set_mode() peut être utilisé pour définir le mode désiré. La capacité permise CAP_SETPCAP est requise pour que cette fonction réussisse.

cap_setuid() est une fonction de commodité pour l'appel système setuid(2). Où cap_setuid() organise le relèvement de la capacité effective droite pour effectuer l'appel système, et organise également la préservation de la disponibilité des capacités permises après le changement d'uid. Après cet appel, toutes les capacités effectives sont abaissées.

cap_setgroups() est une fonction de commodité pour effectuer les appels setgid(2) et setgroups(2) en un seul appel. L'appel cap_setgroups() relève la capacité effective droite pendant la durée de l'appel, et vide l'ensemble de capacités effectif avant de retourner.

VALEUR DE RETOUR

Les fonctions cap_get_proc() et cap_get_pid() retournent une valeur non NULL en cas de succès, et NULL en cas d'échec.

La fonction cap_get_bound() retourne -1 si la capacité demandée est inconnue, sinon la valeur de retour reflète l'état actuel de cette capacité dans l'ensemble de délimitation prédominant. Notez qu'une macro fonction,

Toutes les fonctions de réglage telles que cap_set_proc() et cap_drop_bound() retournent zéro en cas de succès, et -1 en cas d'échec.

En cas d'échec, errno est défini à EINVAL, EPERM, ou ENOMEM.

CONFORMITÉ

cap_set_proc() et cap_get_proc() sont spécifiés dans la spécification brouillon retirée POSIX.1e. cap_get_pid() est une extension Linux.

NOTES

Ni glibc, ni le noyau Linux ne respectent les sémantiques POSIX pour la définition des capacités et des bits sécurisés en présence de pthreads. C'est-à-dire que la modification des ensembles de capacités n'affecte, par défaut, que le thread en cours d'exécution. En guise de solution de contournement, libcap est conditionné avec une bibliothèque système distincte d'appels système aux sémantiques POSIX : libpsx. Si votre programme utilise des threads POSIX, pour obtenir une manipulation significative des capacités de sémantiques POSIX, vous devez lier votre programme avec :

ld ... -lcap $(pkg-config --libs --cflags libpsx)

ou,

gcc ... -lcap $(pkg-config --libs --cflags libpsx)

Lorsqu'il est lié de cette manière, grâce à la magie de l'éditeur de liens, libcap utilise psx_syscall(3) et psx_syscall6(3) pour effectuer des appels système de définition d'état. Notamment, cela garantit également que cap_prctlw() peut être utilisé pour garantir que les bits de contrôle de processus sont partagés sur tous les threads d'un seul processus.

capgetp() et capsetp()

La bibliothèque prend également en charge les fonctions obsolètes :

int capgetp(pid_t pid, cap_t cap_d) ;

int capsetp(pid_t pid, cap_t cap_d) ;

capgetp() tente d'obtenir les capacités d'un autre processus ; stockant les capacités dans un cap_d pré-alloué. Voir cap_init() pour des informations sur l'allocation d'un ensemble de capacités vide. Cette fonction est obsolète ; vous devriez utiliser cap_get_pid().

capsetp() tente de définir les capacités du processus appelant ou d'un ou plusieurs autres processus, pid. Notez que la définition des capacités d'un autre processus n'est possible que sur les anciens noyaux qui ne fournissent pas de prise en charge VFS pour la définition des capacités de fichiers. Voir capset(2) pour des informations sur les noyaux qui fournissent une telle prise en charge.

Si pid est positif, il fait référence à un processus spécifique ; s'il est zéro, il fait référence au processus appelant ; -1 fait référence à tous les processus autres que le processus appelant et le processus '1' (généralement init(8)) ; d'autres valeurs négatives font référence au groupe de processus -pid.

Pour utiliser cette fonction, le noyau doit la prendre en charge et le processus appelant doit avoir CAP_SETPCAP levé dans son ensemble de capacités effectives. Les capacités définies dans le ou les processus cibles sont celles contenues dans cap_d.

Les noyaux qui prennent en charge les capacités du système de fichiers redéfinissent les sémantiques de CAP_SETPCAP et sur de tels systèmes, capsetp() échouera toujours pour toute cible différente du processus appelant. capsetp() renvoie zéro en cas de succès et -1 en cas d'échec.

Sur les noyaux où elle était (était) prise en charge, capsetp() doit être utilisée avec précaution. Elle existait principalement pour surmonter un manque précoce de prise en charge des capacités dans les systèmes de fichiers pris en charge par Linux. Notez que sur les anciens noyaux où capsetp() pouvait être utilisé pour définir les capacités d'un autre processus, les seuls processus qui avaient CAP_SETPCAP disponible par défaut étaient les processus démarrés en tant que threads du noyau. (Généralement, cela inclut init(8), kflushd et kswapd.) Une recompilation du noyau était nécessaire pour modifier ce comportement par défaut.

EXEMPLE

Le segment de code ci-dessous élève les capacités effectives CAP_FOWNER et CAP_SETFCAP pour l'appelant :

    ...
    cap_t caps ;
    const cap_value_t cap_list[2] = {CAP_FOWNER, CAP_SETFCAP} ;
    if (!CAP_IS_SUPPORTED(CAP_SETFCAP))
        /* gérer l'erreur */
    caps = cap_get_proc() ;
    if (caps == NULL)
        /* gérer l'erreur */ ;
    if (cap_set_flag(caps, CAP_EFFECTIVE, 2, cap_list, CAP_SET) == -1)
        /* gérer l'erreur */ ;
    if (cap_set_proc(caps) == -1)
        /* gérer l'erreur */ ;
    if (cap_free(caps) == -1)
        /* gérer l'erreur */ ;
    ...

Alternativement, pour abandonner complètement les privilèges dans un programme lancé en tant que setuid-root mais souhaitant s'exécuter en tant qu'ID d'utilisateur spécifique, etc., de telle sorte que ni lui, ni aucun de ses enfants ne puisse acquérir à nouveau de privilèges :

    ...
    uid_t nobody = 65534 ;
    const gid_t groups[] = {65534} ;
    if (cap_setgroups(groups[0], 1, groups) != 0)
        /* gérer l'erreur */ ;
    if (cap_setuid(nobody) != 0)
        /* gérer l'erreur */ ;
    /*
     * les privilèges sont toujours disponibles ici
     */
    if (cap_set_mode(CAP_MODE_NOPRIV) != 0)
        /* gérer l'erreur */ ;
    ...

Notez que la séquence ci-dessus peut être effectuée par l'outil capsh comme suit :

sudo capsh --user=nobody --mode=NOPRIV --print

où --print affiche l'état des privilèges résultant.
