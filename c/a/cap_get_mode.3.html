L'appelant doit libérer toute mémoire libérable lorsque l'état de capacités dans le stockage de travail n'est plus requis, en appelant cap_free() avec le cap_t comme argument. cap_set_proc() définit les valeurs de tous les indicateurs de capacités pour toutes les capacités dans l'état de capacités identifié par

cap_p.

Le nouvel état de capacités du processus sera entièrement déterminé par le contenu de cap_p lors du retour réussi de cette fonction. Si un indicateur dans cap_p est défini pour une capacité actuellement non autorisée pour le processus appelant, la fonction échouera et l'état de capacités du processus restera inchangé. cap_get_pid() renvoie un cap_t, voir cap_init(3), avec les capacités du processus connu de l'appelant sous le nom de pid. Si pid vaut 0, les

capacités

du processus appelant sont renvoyées. Ces informations peuvent également être obtenues à partir du fichier /proc/<pid>/status. (Les entrées de ce fichier peuvent être traduites avec la ligne de commande capsh --decode= XXX.) Lorsque l'appelant opère à l'intérieur d'un espace de noms ( CLONE_NEWPID), l'argument numérique pid est interprété dans la plagede cet espace de noms. Ainsi, la conception de l'appelant du pidcible peut différer de celle du processus cible lorsqu'ils opèrent dans des espaces de noms de pid différents. Voir pid_namespaces(7) pour plus de détails. De plus, la valeur cap_t renvoyée contient les capacités que le pid cible pense avoir. Si la cible opère dans un espace de noms ( CLONE_NEWUSER), le privilège au niveau du système de ces capacités d'espace de noms utilisateur peut être considérablement réduit. Voir user_namespaces(7)pour plus de détails. cap_get_bound() avec un cap comme argument renvoie la valeur actuelle de cet indicateur de capacité de l'ensemble d'englobement en

vigueur

pour le processus appelant. Cette opération est non privilégiée. Notez qu'une macro de fonction CAP_IS_SUPPORTED(cap_value_t cap ) est fournie qui évalue à vrai (1) si le système prend en charge la capacité spécifiée, cap. Si le système ne prendpas en charge la capacité, cette fonction renvoie 0. Cette macro fonctionne en testant une condition d'erreur avec cap_get_bound(). cap_drop_bound() peut être utilisé pour abaisser la capacité spécifiée de l'ensemble d'englobement, cap. Pour se terminer

pas

prise en charge par le noyau en cours d'exécution. Une macro CAP_AMBIENT_SUPPORTED() utilise cette fonction pour déterminer si les capacités ambiantes sont prises en charge par le noyau. cap_set_ambient() définit la capacité ambiante spécifiée à une valeur spécifique. Pour lever

une

capacité ambiante spécifique, les héritables et indicateurs autorisés du processus appelant doivent contenir la valeur de capacité spécifiée. Les bits ambiants levés ne seront conservés que tant que cela reste vrai pour les indicateurs héritables et autorisés. cap_reset_ambient() réinitialise toutes les capacités ambiantes du processus appelant à leur

Lors de l'exécution d'un fichier avec des capacités de système de fichiers associées, le noyau réinitialisera implicitement l'ensemble ambiant du processus. De plus, les modifications de l'ensemble héritable par le code du programme sans réparer explicitement l'ensemble ambiant peuvent également faire tomber les bits ambiants. cap_get_secbits() renvoie les securebits du

Certains paramètres verrouillent les sous-états des securebits, de sorte que les tentatives de définir des valeurs peuvent être refusées par le noyau même lorsque la capacité CAP_SETPCAP est levée. Pour aider à

la complexité des securebits, libcap fournit un concept combiné de securebit et d'ensemble de capacités appelé un mode libcap. cap_get_mode() tente de résumer l'environnement de sécurité en vigueur sous la forme d'une valeur numérique cap_mode_t. Une représentation textuelle du mode peut être obtenue via la fonction cap_mode_name(). La grande majorité des combinaisons de ces valeurs n'est pas bien définie en termes de mode libcap, et pour ces états cap_get_mode() renvoie ( cap_mode_t)0 que cap_get_name() identifie comme« UNCERTAIN ». Là où cap_setuid() organise la levée de la bonne capacité effective afin d'effectuer l'appel système, et organise également la préservation de la disponibilité des capacités autorisées après que l'uid a changé. À la suite de cet appel, toutes les capacités effectives sont abaissées. cap_setgroups() est une

capgetp() et

capsetp()

La bibliothèque prend également en charge les fonctions dépréciées

:

int capgetp(pid_t pid, cap_t cap_d)

;

int capsetp(pid_t pid, cap_t cap_d)

capgetp() tente d'obtenir les capacités d'un autre processus ; stockant les capacités dans un cap_d préalloué. Voir cap_init() pour des informations sur l'allocation d'un ensemble de capacités vide. Cette fonction est dépréciée ; vous devriez utiliser cap_get_p

id().

capsetp() tente de définir les capacités du processus appelant ou d'un ou plusieurs autres processus, pid. Notez que définir les capacités d'un autre processus n'est possible que sur les anciens noyaux qui ne fournissent pas de support VFS pour la définition de capacités de fichiers. Voir capset(2) pour des informations sur les noyaux qui fournissent un tel

support.

Si pid est positif, il se réfère à un processus spécifique ; s'il est zéro, il se réfère au processus appelant ; -1 se réfère à tous les processus autres que le processus appelant et le processus '1' (typiquement init(8)) ; les autres valeurs négatives se réfèrent au groupe de processus

-pid.

Afin d'utiliser cette fonction, le noyau doit la prendre en charge et le processus appelant doit avoir CAP_SETPCAP activé dans son ensemble de capacités Effectives. Les capacités définies dans le ou les processus cibles sont celles contenues dans cap_d

.

Les noyaux qui prennent en charge les capacités de système de fichiers redéfinissent la sémantique de CAP_SETPCAP et sur de tels systèmes, capsetp() échouera toujours pour toute cible différente du processus appelant. capsetp() renvoie zéro en cas de succès, et -1 en cas

d'échec.

Sur les noyaux où cela est (était) pris en charge, capsetp() devrait être utilisé avec précaution. Elle existait principalement pour surmonter un manque précoce de support pour les capacités dans les systèmes de fichiers pris en charge par Linux. Notez que sur les anciens noyaux où capsetp() pouvait être utilisée pour définir les capacités d'un autre processus, les seuls processus qui avaient CAP_SETPCAP disponible par défaut étaient les processus démarrés en tant que threads du noyau. E

Le segment de code ci-dessous active les capacités effectives CAP_FOWNER et CAP_SETFCAP pour l'appelant

: 
    ...
    cap_t caps;
    const cap_value_t cap_list[2] = {CAP_FOWNER, CAP_SETFCAP};
    if (!CAP_IS_SUPPORTED(CAP_SETFCAP))
        /* handle error */
    caps = cap_get_proc();
    if (caps == NULL)
        /* handle error */;
    if (cap_set_flag(caps, CAP_EFFECTIVE, 2, cap_list, CAP_SET) == -1)
        /* handle error */;
    if (cap_set_proc(caps) == -1)
        /* handle error */;
    if (cap_free(caps) == -1)
        /* handle error */;
    ..
.
