Lorsque l'appelant opère à l'intérieur d'un espace de noms ( CLONE_NEWPID), l'argument numérique pid est interprété dans la plage decet espace de noms. Ainsi, la conception que l'appelant se faitdu pid cible peut différer de celle du processus cible lorsqu'ils opèrent dans des espaces de noms pid différents. Voir pid_namespaces(7) pour plus de détails. De plus, la valeur cap_t renvoyée contient les capacités que le pid cible pense posséder. Si la cible opère dans un espace de noms ( CLONE_NEWUSER), le privilège au niveau du système de ces capacités d'espace de noms utilisateur peut être considérablement réduit. La bibliothèque prend également en charge les fonctions dépréciées

capgetp() tente d'obtenir les capacités d'un autre processus ; stockant les capacités dans un cap_d pré-alloué. Voir cap_init() pour des informations sur l'allocation d'un ensemble de capacités vide. Cette fonction est dépréciée ; vous devriez utiliser cap_get_p

id().

capsetp() tente de définir les capacités du processus appelant ou d'un ou plusieurs autres processus, pid. Notez que définir les capacités d'un autre processus n'est possible que sur les anciens noyaux qui ne fournissent pas de support VFS pour définir les capacités de fichiers. Voir capset(2) pour des informations sur les noyaux qui fournissent un tel

support.

Si pid est positif, il fait référence à un processus spécifique ; s'il est zéro, il fait référence au processus appelant ; -1 fait référence à tous les processus autres que le processus appelant et le processus « 1 » (typiquement init(8)) ; les autres valeurs négatives font référence au groupe de processus

-pid.

Afin d'utiliser cette fonction, le noyau doit la prendre en charge et le processus appelant doit avoir CAP_SETPCAP activé dans son ensemble de capacités Effectives. Les capacités définies dans le ou les processus cibles sont celles contenues dans cap_d

.

Les noyaux qui prennent en charge les capacités du système de fichiers redéfinissent la sémantique de CAP_SETPCAP et sur de tels systèmes, capsetp() échouera toujours pour toute cible différente du processus appelant. capsetp() renvoie zéro en cas de succès, et -1 en cas

d'échec.

Sur les noyaux où cela est (était) pris en charge, capsetp() devrait être utilisé avec précaution. Elle existait principalement pour surmonter un manque précoce de support pour les capacités dans les systèmes de fichiers pris en charge par Linux. Notez que sur les anciens noyaux où capsetp() pouvait être utilisé pour définir les capacités d'un autre processus, les seuls processus qui avaient CAP_SETPCAP disponible pour eux par défaut étaient les processus démarrés en tant que threads du noyau.
