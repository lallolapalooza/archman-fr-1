capget(2) Manuel des appels système capget(2)

NOM

capget, capset - obtenir/définir les capacités d'un ou plusieurs fils d'exécution

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <linux/capability.h> /* Définition des constantes CAP_* et
                                 _LINUX_CAPABILITY_* */
#include <sys/syscall.h>      /* Définition des constantes SYS_* */
#include <unistd.h>
int syscall(SYS_capget, cap_user_header_t hdrp,
            cap_user_data_t datap);
int syscall(SYS_capset, cap_user_header_t hdrp,
            const cap_user_data_t datap);

Note : glibc ne fournit pas d'enveloppes pour ces appels système, ce qui nécessite l'utilisation de syscall(2).

DESCRIPTION

Ces deux appels système constituent l'interface brute du noyau pour l'obtention et la définition des capacités des fils d'exécution. Non seulement ces appels système sont spécifiques à Linux, mais l'API du noyau est susceptible de changer et l'utilisation de ces appels système (en particulier le format des types cap_user_*_t) est sujette à extension à chaque révision du noyau, mais les anciens programmes continueront de fonctionner.

Les interfaces portables sont cap_set_proc(3) et cap_get_proc(3) ; si possible, vous devriez utiliser ces interfaces dans vos applications ; voir NOTES.

Détails actuels

Maintenant que vous avez été prévenu, quelques détails actuels du noyau. Les structures sont définies comme suit.


#define _LINUX_CAPABILITY_VERSION_1  0x19980330
#define _LINUX_CAPABILITY_U32S_1     1
        /* V2 ajouté dans Linux 2.6.25 ; obsolète */
#define _LINUX_CAPABILITY_VERSION_2  0x20071026
#define _LINUX_CAPABILITY_U32S_2     2
        /* V3 ajouté dans Linux 2.6.26 */
#define _LINUX_CAPABILITY_VERSION_3  0x20080522
#define _LINUX_CAPABILITY_U32S_3     2
typedef struct __user_cap_header_struct {
   __u32 version;
   int pid;
} *cap_user_header_t;
typedef struct __user_cap_data_struct {
   __u32 effective;
   __u32 permitted;
   __u32 inheritable;
} *cap_user_data_t;

Les champs effective, permitted et inheritable sont des masques de bits des capacités définies dans capabilities(7). Notez que les valeurs CAP_* sont des indices de bits et doivent être décalées par bits avant d'être combinées par OR dans les champs de bits. Pour définir les structures à passer à l'appel système, vous devez utiliser les noms de structure struct __user_cap_header_struct et struct __user_cap_data_struct car les typedefs ne sont que des pointeurs.

Les noyaux antérieurs à Linux 2.6.25 préfèrent les capacités 32 bits avec la version _LINUX_CAPABILITY_VERSION_1. Linux 2.6.25 a ajouté les ensembles de capacités 64 bits, avec la version _LINUX_CAPABILITY_VERSION_2. Il y a cependant eu un bug dans l'API, et Linux 2.6.26 a ajouté _LINUX_CAPABILITY_VERSION_3 pour corriger le problème.

Notez que les capacités 64 bits utilisent datap[0] et datap[1], tandis que les capacités 32 bits n'utilisent que datap[0].

Sur les noyaux qui prennent en charge les capacités de fichier (support des capacités VFS), ces appels système se comportent légèrement différemment. Ce support a été ajouté en option dans Linux 2.6.24, et est devenu fixe (non optionnel) dans Linux 2.6.33.

Pour les appels capget(), on peut sonder les capacités de tout processus en spécifiant son ID de processus avec la valeur du champ hdrp->pid.

Pour plus de détails sur les données, voir capabilities(7).

Avec support des capacités VFS

Les capacités VFS utilisent un attribut étendu de fichier (voir xattr(7)) pour permettre aux capacités d'être attachées aux exécutables. Ce modèle de privilège rend obsolète le support du noyau pour qu'un processus définisse de manière asynchrone les capacités d'un autre. C'est-à-dire, sur les noyaux qui supportent les capacités VFS, lors de l'appel à capset(), les seules valeurs permises pour hdrp->pid sont 0 ou, de manière équivalente, la valeur retournée par gettid(2).

Sans support des capacités VFS

Sur les anciens noyaux qui ne fournissent pas de support des capacités VFS, capset() peut, si l'appelant possède la capacité CAP_SETPCAP, être utilisé pour modifier non seulement les capacités de l'appelant, mais aussi les capacités d'autres fils d'exécution. L'appel opère sur les capacités du fil d'exécution spécifié par le champ pid de hdrp lorsque celui-ci est différent de zéro, ou sur les capacités du fil d'exécution appelant si pid est 0. Si pid fait référence à un processus mono-fil d'exécution, alors pid peut être spécifié comme un ID de processus traditionnel ; opérer sur un fil d'exécution d'un processus multithread nécessite un ID de fil d'exécution du type retourné par gettid(2). Pour capset(), pid peut également être : -1, signifiant appliquer le changement à tous les fils d'exécution sauf l'appelant et init(1) ; ou une valeur inférieure à -1, auquel cas le changement est appliqué à tous les membres du groupe de processus dont l'ID est -pid.

VALEUR DE RETOUR

En cas de succès, zéro est retourné. En cas d'erreur, -1 est retourné, et errno est défini pour indiquer l'erreur.

Les appels échouent avec l'erreur EINVAL, et définissent le champ version de hdrp à la valeur préférée du noyau de _LINUX_CAPABILITY_VERSION_? lorsqu'une valeur version non prise en charge est spécifiée. De cette manière, on peut sonder quelle est la révision de capacité préférée actuelle.

ERREURS

EFAULT
Mauvaise adresse mémoire. hdrp ne doit pas être NULL. datap peut être NULL uniquement lorsque l'utilisateur tente de déterminer le format de version de capacité préféré supporté par le noyau.
EINVAL
L'un des arguments était invalide.
EPERM
Une tentative a été faite pour ajouter une capacité à l'ensemble autorisé, ou pour définir une capacité dans l'ensemble effectif qui n'est pas dans l'ensemble autorisé.
EPERM
Une tentative a été faite pour ajouter une capacité à l'ensemble héritable, et soit :
•
cette capacité n'était pas dans l'ensemble de limitation de l'appelant ; ou
•
la capacité n'était pas dans l'ensemble autorisé de l'appelant et l'appelant ne possédait pas la capacité CAP_SETPCAP dans son ensemble effectif.
EPERM
L'appelant a tenté d'utiliser capset() pour modifier les capacités d'un autre fil d'exécution que le sien, mais manquait de privilèges suffisants. Pour les noyaux supportant les capacités VFS, cela n'est jamais autorisé. Pour les noyaux n'ayant pas le support VFS, la capacité CAP_SETPCAP est requise. (Un bug dans les noyaux avant Linux 2.6.11 signifiait que cette erreur pouvait également survenir si un fil d'exécution sans cette capacité tentait de modifier ses propres capacités en spécifiant le champ pid comme une valeur non nulle (c'est-à-dire la valeur retournée par getpid(2)) au lieu de 0.)
ESRCH
Aucun fil d'exécution de ce type.

NORMES

Linux.

NOTES

L'interface portable vers les fonctions de requête et de définition des capacités est fournie par la bibliothèque libcap et est disponible ici :
http://git.kernel.org/cgit/linux/kernel/git/morgan/libcap.git
