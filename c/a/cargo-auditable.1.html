DESCRIPTIO

N

Connaissez les versions exactes des crates utilisées pour construire votre exécutable Rust. Auditez les binaires pour les bogues connus ou les vulnérabilités de sécurité en production, à grande échelle, sans aucune gestion

administrative.

Cela fonctionne en intégrant des données sur l'arbre de dépendances au format JSON dans une section de liaison dédiée de l'exécutable

compilé.

Linux, Windows et Mac OS sont officiellement pris en charge. Toutes les autres cibles ELF devraient fonctionner, mais ne sont pas testées sur l'intégration continue. WASM n'est actuellement pas pris en charge, mais les correctifs sont les

bienvenus.

L'objectif final est de faire en sorte que Cargo lui-même encode ces informations dans les binaires. Il existe un RFC pour une implémentation au sein de Cargo, pour lequel ce projet prépare le terrain : https://github.com/rust-lang/rfcs/pull/28

FA

Q

Est-ce que cela gonfle mon binaire

?

En un mot, non. La liste des dépendances intégrée utilise moins de 4 ko même sur de grands arbres de dépendances avec plus de 400 entrées. Cela se traduit généralement par entre 1/1000 et 1/10 000 de la taille du

binaire.

Puis-je faire en sorte que cargo construise toujours avec cargo auditable

?

Oui ! Par exemple, sur Linux/macOS/etc, ajoutez ceci à votre .bashrc

:

alias cargo="cargo

auditable"

Si vous utilisez un shell autre que bash, ou si l'utilisation d'un alias n'est pas une option, voir https://github.com/rust-secure-code/cargo-auditable/bl

ob/HEAD/REPLACING_CARGO.md.

Existe-t-il des outils pour consommer ces données

?

Signalement des

vulnérabilités


cargo audit v0.17.3+ peut détecter ces données dans les binaires et signaler les vulnérabilités. Voir ici pour plus de détails.
trivy v0.31.0+ détecte ces données dans les binaires et signale les vulnérabilités. Voir les notes de version de la v0.31.0 pour un exemple de bout en

bout.

Récupération de la liste des

dépendances


syft v0.53.0+ a une prise en charge expérimentale de la détection de ces données dans les binaires. Lorsqu'il est utilisé sur des images ou des répertoires, la prise en charge de Rust audit doit être activée en ajoutant l'option de ligne de commande --catalogers all, par exemple syft --catalogers all <image de conteneur contenant un binaire Rust auditable>.
rust-audit-info récupère la liste des dépendances à partir d'un binaire et l'affiche au format

JSON.

Il est également interopérable avec les outils existants qui consomment Cargo.lock via le convertisseur JSON-vers-TOML. Cependant, nous recommandons de prendre en charge le format nativement ; le format est conçu pour être très facile à analyser, même si votre langage n'a pas encore de bibliothèque pour

cela.

Puis-je lire ces données à l'aide d'un outil écrit dans un autre langage

?

Oui. Le format de données est conçu pour l'interopérabilité avec des implémentations alternatives. En fait, son analyse ne prend que 5 lignes de Python. Voir https://github.com/rust-secure-code/cargo-auditable/blob/HEAD/PARSING.md pour la documentation sur l'analyse des

données.

Quel est exactement le format de données

?

Le format de données est décrit par le schéma JSON https://github.com/rust-secure-code/cargo-auditable/blob/HEAD/cargo-auditable.schema.json. Le JSON est compressé avec Zlib et placé dans une section de liaison nommée .dep-v0. Vous pouvez trouver plus d'informations sur son analyse

ici.

Qu'en est-il des plateformes embarquées

?

Les plateformes embarquées où vous ne pouvez pas vous permettre de perdre un octet ne devraient rien ajouter à l'exécutable. Au lieu de cela, elles devraient enregistrer l'empreinte de chaque exécutable dans une base de données et associer l'empreinte à son Cargo.lock, la version du compilateur et de LLVM, la date de compilation, etc. Cela constituerait un excellent enveloppeur ou plugin pour Cargo. Puisque cela peut être fait dans un script shell de 5 lignes, l'écriture de cet outil est laissée comme exercice au

lecteur.

Cela a-t-il un impact sur les builds reproductibles

?

Le format de données est spécifiquement conçu pour ne pas perturber les builds reproductibles. Il ne contient aucun horodatage, et le JSON généré est trié pour s'assurer qu'il est identique entre les compilations. Si quoi que ce soit, cela aide les builds reproductibles, car vous connaissez désormais toutes les versions pour un binaire

donné.

Cela divulgue-t-il des informations sensibles

?

Non. Toutes les URL et les chemins de fichiers sont caviardés, mais les noms et versions des crates sont enregistrés tels quels. À l'heure actuelle, les messages de panique divulguent déjà toutes ces informations et plus encore. De plus, il est probable que vous soyez légalement obligé de divulguer l'utilisation de crates open-source spécifiques, car la licence MIT et de nombreuses autres licences

l'exigent.

Qu'en est-il de l'enregistrement de la version du compilateur

?

Le compilateur lui-même commencera bientôt à

l'intégrer.

Sur les anciennes versions, il est déjà présent dans les informations de débogage. Sur Unix, vous pouvez exécuter strings votre_exécutable | grep 'rustc version' pour le

voir.

Qu'en est-il du suivi des versions des bibliothèques C liées statiquement

?

Bonne question. Je ne pense pas qu'elles soient exposées de manière raisonnable actuellement. Ce serait une excellente addition, mais pas nécessaire pour le lancement initial. Nous pouvons l'ajouter plus tard de manière rétrocompatible. L'adoption de la convention de crate -src ferait que cela se produise naturellement, et aura aussi d'autres avantages, donc c'est probablement la meilleure

voie.

Qu'est-ce qui bloque l'intégration de cela dans Cargo

?

Cargo lui-même est actuellement en gel des

fonctionnalités
.
