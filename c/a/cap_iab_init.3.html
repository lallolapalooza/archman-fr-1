DESCRIPTIO

N

Les fonctions définies dans cette page man concernent les trois vecteurs de capacités de processus naïvement héritables : Inh, Amb et Bound. Ce IAB 3-uplet de vecteurs de capacités, capturé dans le type cap_iab_t, se combine pour transmettre des capacités d'un processus à un autre à travers des appels système execve(2). Les règles de convolution utilisant le IAB 3-uplet constituent un ensemble de règles de secours lorsque le fichier exécuté n'a pas de capacités de fichier c

onfigurées.

Le noyau impose certaines contraintes concernant les trois composantes d'un IAB 3-uplet et l'indicateur de capacités de processus Permitted. Elles sont : le vecteur Inh (CAP_IAB_INH) est entièrement égal à l'indicateur Inheritable du processus à tout moment ; le vecteur Amb (CAP_IAB_AMB) ne contient pas plus de valeurs de capacités que l'intersection du vecteur Inh et de l'indicateur Permitted pour le processus ; et le vecteur Bound (ou bloqué) (CAP_IAB_BOUND) est le complément à deux du vecteur bounding du

processus.

Dans certains environnements, il est considéré comme souhaitable d'hériter naïvement des capacités. C'est-à-dire transmettre des capacités, indépendamment de l'état du binaire exécuté, du parent à l'enfant à travers des appels système exec*. Les capacités survivantes deviennent l'indicateur Permitted pour le processus post-exec. Cette méthode d'héritage diffère considérablement de l'héritage par négociation entre un processus pré-exec* et un exécutable doté de capacités de fichier du mécanisme de capacités traditionnel (POSIX.1e)

.

Les règles de convolution pour l'héritage de style IAB sont : I'=I ; A'=A&I ; P'=A&I&P. Où P, etc. sont les valeurs pré-exec et P', etc. sont les valeurs

post-exec.

En comprenant ces règles de convolution, nous pouvons expliquer comment la prise en charge par libcap(3) du IAB 3-uplet est gérée : l'API

IAB.

cap_iab_init() renvoie une valeur IAB vide. C'est un 3-uplet largement inoffensif. Il ne bloquera aucune capacité de fichier Permitted à travers exec, mais il n'en conférera pas non plus. Le cap_iab_t retourné devrait être libéré avec cap_free

(3).

cap_iab_dup() renvoie une copie de la valeur IAB spécifiée. Le cap_iab_t retourné devrait être libéré avec cap_free

(3).

cap_iab_get_proc() renvoie une copie de la valeur IAB pour le processus courant. Le cap_iab_t retourné devrait être libéré avec cap_free

(3).

cap_iab_get_pid() renvoie une copie de la valeur IAB pour le processus spécifié. Le cap_iab_t retourné devrait être libéré avec cap_free(3). Cette fonction recherche par défaut /proc/<PID>/status pour les informations IAB, mais cet emplacement peut être remplacé en utilisant la fonction cap_proc_root()

.

cap_iab_set_proc() peut être utilisé pour définir la valeur IAB portée par le processus courant. Un tel réglage échouera si le processus n'est pas suffisamment capable. Pour élever des bits I absents de l'indicateur P, ou appliquer un nouveau masquage B, il faut que CAP_SETPCAP soit présent dans l'indicateur Permitted (la fonction l'élèvera temporairement dans l'indicateur Effective si nécessaire). Dans tous les cas, les valeurs A élevées doivent être présentes dans l'intersection des valeurs Permitted et

Inh.

cap_iab_to_text() convertira un IAB 3-uplet en une représentation textuelle IAB canonique. La représentation est légèrement redondante mais libcap(3)essaierade générer une représentation aussi courte que

possible.

cap_iab_from_text() génère un IAB 3-uplet à partir d'une chaîne de texte (probablement générée par la fonction précédente). Le IAB 3-uplet retourné devrait être libéré avec cap_fre

e().

cap_iab_get_vector() peut être utilisé pour déterminer la valeur de capacité spécifique d'un vecteur

IAB.

cap_iab_compare() peut être utilisé pour comparer deux IAB 3-uplets cap_iab_t. Quand la valeur de retour est non nulle, la macro CAP_IAB_DIFFERS(status, vector) évalue à non nul si le statut retourné diffère dans ses composantes vecto

rielles.

cap_iab_set_vector() peut être utilisé pour définir une valeur vectorielle spécifique sur le réglage

enable.

cap_iab_fill() peut être utilisé pour copier en masse une valeur d'indicateur cap_t dans le vecteur vec du IAB 3-uplet. Copier dans Amb (CAP_IAB_AMB) de cette manière peut implicitement élever les valeurs Inh (CAP_IAB_INH) dans le IAB 3-uplet. De même, copier dans le vecteur Inh peut implicitement abaisser les valeurs Amb qui ne sont pas présentes dans le vecteur Inh

résultant.

cap_proc_root() peut être utilisé pour déterminer l'emplacement courant interrogé par cap_iab_get_pid(). Les valeurs retournées devraient être libérées avec cap_free(3). Si l'argument de cap_proc_root() n'est pas NULL, une copie de celui-ci deviendra le remplaçant de /proc. Notez que cette fonction n'est pas thread-safe par rapport à des appels concurrents à cap_iab_g

et_pi
d().

NOTE

S

Contrairement à l'ensemble de capacités traditionnel cap_t, le IAB 3-uplet, pris dans son ensemble, est incompatible avec les capacités de système de fichiers créées via des outils comme setcap(8). C'est-à-dire que le vecteur Amb du IAB 3-uplet est rendu sans objet lorsqu'un exécutable avec une capacité de fichier est

exécuté.

De plus, il existe des cap_mode(3) de libcap qui rendent le vecteur Amb

et sa méthode d'héritag
e de processus désactivés.

HISTORIQU

E

Le format IAB pour les variantes héritables des capacités a d'abord été développé comme syntaxe de configuration pour le module pam_cap.so Linux-PAM dans libcap-2.29. Il a été introduit pour étendre la simple liste séparée par des virgules des capacités Inheritable du processus, que le module pouvait conférer à un arbre de processus authentifié, afin d'inclure des limites imposées sur le vecteur Bounding et d'introduire la prise en charge du vecteur Ambient des bits de

capacité.

Alors que les vecteurs Inheritable et Bounding étaient anticipés par le projet de norme POSIX.1e qui a introduit les capacités, le vecteur Ambient est une invention Linux, et incompatible avec le modèle de capacités de fichier POSIX.1e. En conséquence, il a été jugé que la tentative de fusionner les 5 vecteurs de capacités en une seule représentation textuelle ne fonctionnerait pas. À la place, la syntaxe de configuration de pam_cap.so a été généralisée en un ensemble complet de fonctions de libcap pour regrouper les trois

capacités naïvement héritables : le IAB 3-uplet. La prise en ch
arge de cette fonctionnalité a fait ses débuts dans libcap-2.33.
