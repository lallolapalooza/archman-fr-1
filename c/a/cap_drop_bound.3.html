C'est-à-dire que la modification des ensembles de capacités, par défaut, n'affecte que le thread en cours d'exécution. Pour être significativement sécurisé, cependant, les ensembles de capacités doivent être répliquéspar tous les threads au sein d'un programme commun car les threads ne sont pas isolés en mémoire. Pour contourner ce problème, libcap est empaqueté avec une bibliothèque système séparée à sémantique POSIX : libpsx. Si votre programme utilise des threads POSIX, pour obtenir une manipulation significative des capacités de sémantique POSIX, vous devez lancer votre programme avec :

ld ... -lcap $(pkg-config --libs --cflags libpsx)

ou,

gcc ... -lcap $(pkg-config --libs --cflags libpsx)

Lorsqu'il est lié de cette manière, grâce à la magie de l'éditeur de liens, libcap utilise psx_syscall(3) et psx_syscall6(3) pour effectuer des appels système de définition d'état. Notamment, cela garantit également que cap_prctlw() peut être utilisé pour garantir que les bits de contrôle du processus sont partagés entre tous les threads d'un même processus.

capgetp() et capsetp()

La bibliothèque prend également en charge les fonctions obsolètes :

int capgetp(pid_t pid, cap_t cap_d);

int capsetp(pid_t pid, cap_t cap_d);

capgetp() tente d'obtenir les capacités d'un autre processus ; stockant les capacités dans un cap_d pré-alloué. Voir cap_init() pour des informations sur l'allocation d'un ensemble de capacités vide. Cette fonction est obsolète ; vous devriez utiliser cap_get_pid().

capsetp() tente de définir les capacités du processus appelant ou d'un ou plusieurs autres processus, pid. Notez que la définition des capacités d'un autre processus n'est possible que sur les anciens noyaux qui ne fournissent pas de support VFS pour la définition des capacités de fichier. Voir capset(2) pour des informations sur les noyaux qui fournissent un tel support.

Si pid est positif, il fait référence à un processus spécifique ; s'il est nul, il fait référence au processus appelant ; -1 fait référence à tous les processus autres que le processus appelant et le processus '1' (typiquement init(8)) ; les autres valeurs négatives font référence au groupe de processus -pid.

Pour utiliser cette fonction, le noyau doit la prendre en charge et le processus appelant doit avoir CAP_SETPCAP élevé dans son ensemble de capacités effectives. Les capacités définies dans le(s) processus cible(s) sont celles contenues dans cap_d.

Les noyaux qui prennent en charge les capacités du système de fichiers redéfinissent la sémantique de CAP_SETPCAP et sur de tels systèmes, capsetp() échouera toujours pour toute cible autre que le processus appelant. capsetp() renvoie zéro en cas de succès, et -1 en cas d'échec.

Sur les noyaux où elle était (était) prise en charge, capsetp() doit être utilisée avec précaution. Elle existait principalement pour pallier un manque précoce de support pour les capacités dans les systèmes de fichiers pris en charge par Linux. Notez que sur les anciens noyaux où capsetp() pouvait être utilisé pour définir les capacités d'un autre processus, les seuls processus qui avaient CAP_SETPCAP disponibles pour eux par défaut étaient les processus lancés comme threads du noyau. (Généralement, cela inclut init(8), kflushd et kswapd.) Une recompilation du noyau était nécessaire pour modifier ce défaut.

EXEMPLE

Le segment de code ci-dessous élève les capacités effectives CAP_FOWNER et CAP_SETFCAP pour l'appelant :

    ...
    cap_t caps;
    const cap_value_t cap_list[2] = {CAP_FOWNER, CAP_SETFCAP};
    if (!CAP_IS_SUPPORTED(CAP_SETFCAP))
        /* gérer l'erreur */
    caps = cap_get_proc();
    if (caps == NULL)
        /* gérer l'erreur */;
    if (cap_set_flag(caps, CAP_EFFECTIVE, 2, cap_list, CAP_SET) == -1)
        /* gérer l'erreur */;
    if (cap_set_proc(caps) == -1)
        /* gérer l'erreur */;
    if (cap_free(caps) == -1)
        /* gérer l'erreur */;
    ...

Alternativement, pour abandonner complètement les privilèges dans un programme lancé setuid-root mais voulant s'exécuter en tant qu'ID utilisateur spécifique, etc., de manière à ce que ni lui ni aucun de ses enfants ne puissent à nouveau acquérir de privilèges :

    ...
    uid_t nobody = 65534;
    const gid_t groups[] = {65534};
    if (cap_setgroups(groups[0], 1, groups) != 0)
        /* gérer l'erreur */;
    if (cap_setuid(nobody) != 0)
        /* gérer l'erreur */;
    /*
     * les privilèges sont toujours disponibles ici
     */
    if (cap_set_mode(CAP_MODE_NOPRIV) != 0)
        /* gérer l'erreur */
    ...

Notez que la séquence ci-dessus peut être effectuée par l'outil capsh comme suit :

sudo capsh --user=nobody --mode=NOPRIV --print

où --print affiche l'état des privilèges résultant.
