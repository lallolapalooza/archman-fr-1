C'est-à-dire, changer les ensembles de capacités, par défaut, n'affecte que le thread en cours d'exécution. capgetp() et

capsetp()

La bibliothèque prend également en charge les fonctions dépréciées

:

int capgetp(pid_t pid, cap_t cap_d)

;

int capsetp(pid_t pid, cap_t cap_d)

capgetp() tente d'obtenir les capacités d'un autre processus ; stockant les capacités dans un cap_d préalloué. Voir cap_init() pour des informations sur l'allocation d'un ensemble de capacités vide. Cette fonction est dépréciée ; vous devriez utiliser cap_get_p

id().

capsetp() tente de configurer les capacités du processus appelant ou d'un ou plusieurs autres processus, pid. Notez que la configuration des capacités d'un autre processus n'est possible que sur les anciens noyaux qui ne fournissent pas de support VFS pour la configuration des capacités de fichier. Voir capset(2) pour des informations sur les noyaux qui fournissent un tel

support.

Si pid est positif, il fait référence à un processus spécifique ; s'il est zéro, il fait référence au processus appelant ; -1 fait référence à tous les processus autres que le processus appelant et le processus '1' (typiquement init(8)) ; les autres valeurs négatives font référence au groupe de processus

-pid.

Afin d'utiliser cette fonction, le noyau doit la prendre en charge et le processus appelant doit avoir CAP_SETPCAP activé dans son ensemble de capacités Effectives. Les capacités configurées dans le(s) processus cible(s) sont celles contenues dans cap_d

.

Les noyaux qui prennent en charge les capacités du système de fichiers redéfinissent la sémantique de CAP_SETPCAP et sur de tels systèmes, capsetp() échouera toujours pour toute cible différente du processus appelant. capsetp() renvoie zéro en cas de succès, et -1 en cas

d'échec.

Sur les noyaux où cela était (est) pris en charge, capsetp() devrait être utilisé avec précaution. Elle existait principalement pour surmonter un manque précoce de support pour les capacités dans les systèmes de fichiers pris en charge par Linux. Notez que sur les anciens noyaux où capsetp() pouvait être utilisé pour configurer les capacités d'un autre processus, les seuls processus qui avaient CAP_SETPCAP disponible pour eux par défaut étaient les processus démarrés en tant que threads du noyau. (Typiquement, cela inclut init(8), kflushd et kswapd.) Une recompilation

du noyau était néc

EXEMPL

E

Le segment de code ci-dessous active les capacités effectives CAP_FOWNER et CAP_SETFCAP pour l'appelant

: 
    ...
    cap_t caps;
    const cap_value_t cap_list[2] = {CAP_FOWNER, CAP_SETFCAP};
    if (!CAP_IS_SUPPORTED(CAP_SETFCAP))
        /* handle error */
    caps = cap_get_proc();
    if (caps == NULL)
        /* handle error */;
    if (cap_set_flag(caps, CAP_EFFECTIVE, 2, cap_list, CAP_SET) == -1)
        /* handle error */;
    if (cap_set_proc(caps) == -1)
        /* handle error */;
    if (cap_free(caps) == -1)
        /* handle error */;
    ..
.
