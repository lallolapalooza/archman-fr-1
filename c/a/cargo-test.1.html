NOM

cargo-test — Exécuter les tests unitaires et d'intégration d'un paquet

SYNOPSIS

cargo test [options] [nomdutest] [-- options-test]

DESCRIPTION

Compiler et exécuter les tests unitaires, d'intégration et de documentation.

L'argument de filtrage de test NOMDUTEST et tous les arguments qui suivent les deux tirets (--) sont transmis aux binaires de test et donc à libtest (le framework de tests unitaires et de micro-benchmarking intégré à rustc). Si vous transmettez des arguments à la fois à Cargo et au binaire, ceux d'avant le -- vont à Cargo, ceux d'après vont au binaire. Pour plus de détails sur les arguments de libtest, consultez la sortie de cargo test -- --help et le chapitre du livre de rustc sur le fonctionnement des tests à https://doc.rust-lang.org/rustc/tests/index.html.

Par exemple, ceci filtrera pour les tests dont le nom contient foo et les exécutera sur 3 threads en parallèle :

cargo test foo -- --test-threads 3

Les tests sont compilés avec l'option --test de rustc, qui crée un exécutable spécial en liant votre code avec libtest. L'exécutable exécute automatiquement toutes les fonctions annotées avec l'attribut #[test] sur plusieurs threads. Les fonctions annotées avec #[bench] seront également exécutées une fois pour vérifier leur fonctionnalité.

Si le paquet contient plusieurs cibles de test, chaque cible est compilée en un exécutable spécial comme mentionné ci-dessus, puis exécutée sériellement.

Le framework libtest peut être désactivé en définissant harness = false dans les paramètres du manifeste de la cible. Dans ce cas, votre code devra fournir sa propre fonction main pour gérer l'exécution des tests.

Tests de documentation

Les tests de documentation sont également exécutés par défaut, ce qui est géré par rustdoc. Il extrait les exemples de code des commentaires de documentation de la cible de bibliothèque, puis les exécute.

Contrairement aux cibles de test normales, chaque bloc de code est compilé à la volée en un exécutable de doctest avec rustc. Ces exécutables s'exécutent en parallèle dans des processus séparés. La compilation d'un bloc de code fait en réalité partie d'une fonction de test contrôlée par libtest, de sorte que certaines options comme --jobs peuvent ne pas prendre effet. Notez que ce modèle d'exécution des doctests n'est pas garanti et pourrait changer à l'avenir ; méfiez-vous d'en dépendre.

Consultez le livre rustdoc https://doc.rust-lang.org/rustdoc/ pour plus d'informations sur l'écriture des tests de documentation.

Répertoire de travail des tests

Le répertoire de travail lors de l'exécution de chaque test unitaire et d'intégration est défini sur le répertoire racine du paquet auquel le test appartient. La définition du répertoire de travail des tests sur le répertoire racine du paquet permet aux tests d'accéder de manière fiable aux fichiers du paquet en utilisant des chemins relatifs, indépendamment de l'endroit où cargo test a été exécuté.

Pour les tests de documentation, le répertoire de travail lors de l'appel de rustdoc est défini sur le répertoire racine de l'espace de travail, et constitue également le répertoire que rustdoc utilise comme répertoire de compilation de chaque test de documentation. Le répertoire de travail lors de l'exécution de chaque test de documentation est défini sur le répertoire racine du paquet auquel le test appartient, et est contrôlé via l'option --test-run-directory de rustdoc.

OPTIONS

Options de test

--no-run

Compile, mais n'exécute pas les tests.

--no-fail-fast

Exécute tous les tests indépendamment de leur échec. Sans cette option, Cargo s'arrête après le premier exécutable défaillant. Le framework de test Rust exécute tous les tests au sein de l'exécutable jusqu'à leur achèvement, cette option ne s'applique qu'à l'exécutable dans son ensemble.

Sélection de paquet

Par défaut, lorsqu'aucune option de sélection de paquet n'est donnée, les paquets sélectionnés dépendent du fichier manifeste sélectionné (basé sur le répertoire de travail actuel si --manifest-path n'est pas donné). Si le manifeste est la racine d'un espace de travail (workspace), les membres par défaut de l'espace de travail sont sélectionnés, sinon seul le paquet défini par le manifeste sera sélectionné.

Les membres par défaut d'un espace de travail peuvent être définis explicitement avec la clé workspace.default-members dans le manifeste racine. Si ce n'est pas défini, un espace de travail virtuel inclura tous les membres de l'espace de travail (équivalent à passer --workspace), et un espace de travail non virtuel inclura uniquement le crate racine lui-même.

-p spec…, --package spec…

Teste uniquement les paquets spécifiés. Voir cargo-pkgid(1) pour le format SPEC. Cet indicateur peut être spécifié plusieurs fois et prend en charge les motifs glob Unix courants comme *, ? et []. Cependant, pour éviter que votre shell n'étende accidentellement les motifs glob avant que Cargo ne les traite, vous devez utiliser des guillemets simples ou doubles autour de chaque motif.

--workspace

Teste tous les membres de l'espace de travail.

--all

Alias obsolète pour --workspace.

--exclude SPEC…

Exclut les paquets spécifiés. Doit être utilisé conjointement avec l'indicateur --workspace. Cet indicateur peut être spécifié plusieurs fois et prend en charge les motifs glob Unix courants comme *, ? et []. Cependant, pour éviter que votre shell n'étende accidentellement les motifs glob avant que Cargo ne les traite, vous devez utiliser des guillemets simples ou doubles autour de chaque motif.

Sélection de cible

Lorsque aucune option de sélection de cible n'est donnée, cargo test compile les cibles suivantes des paquets sélectionnés :

•lib — utilisé pour lier avec les binaires, les exemples, les tests d'intégration et les tests de documentation
•bins (seulement si des tests d'intégration sont compilés et que les fonctionnalités requises sont disponibles)
•examples — pour s'assurer qu'ils compilent
•lib comme test unitaire
•bins comme tests unitaires
•tests d'intégration
•tests de documentation pour la cible lib

Le comportement par défaut peut être modifié en définissant l'indicateur test pour la cible dans les paramètres du manifeste. Définir les exemples sur test = true compilera et exécutera l'exemple comme un test, remplaçant la fonction main de l'exemple par le framework libtest. Si vous ne souhaitez pas que la fonction main soit remplacée, incluez également harness = false, auquel cas l'exemple sera compilé et exécuté tel quel.

Définir les cibles sur test = false empêchera qu'elles ne soient testées par défaut. Les options de sélection de cible qui prennent une cible par nom (comme --example foo) ignorent l'indicateur test et testeront toujours la cible donnée.

Les tests de documentation pour les bibliothèques peuvent être désactivés en définissant doctest = false pour la bibliothèque dans le manifeste.

Voir Configuration d'une cible https://doc.rust-lang.org/cargo/reference/cargo-targets.html#configuring-a-target pour plus d'informations sur les paramètres par cible.

Les cibles binaires sont automatiquement compilées s'il existe un test d'intégration ou un benchmark sélectionné à tester. Cela permet à un test d'intégration d'exécuter le binaire pour vérifier et tester son comportement. La variable d'environnement CARGO_BIN_EXE_<nom> https://doc.rust-lang.org/cargo/reference/environment-variables.html#environment-variables-cargo-sets-for-crates est définie lors de la compilation du test d'intégration afin qu'il puisse utiliser la macro env https://doc.rust-lang.org/std/macro.env.html pour localiser l'exécutable.

NAME

cargo-test - Compile and run tests

SYNOPSIS

cargo test [OPTIONS] [filtrex]

DESCRIPTION

This command compiles all of the current package's tests (unit, integration, and documentation tests) and runs them.

When running tests, Cargo will first build all of the project's dependencies. If there are no tests to run, it will exit immediately.

The cargo test command has a few different modes of operation depending on whether you are running tests in a library or a binary crate.

This command will run tests in the current crate, or all crates in the workspace if the current directory is part of a workspace.

See cargo-test(1) for more information about the options for running tests. This page explains options that are common to most Cargo commands.

The name of the test executable is the same as the crate name, e.g. if the crate name is `my_crate`, the test executable will be `my_crate`.

Options for tests

--locked

Asserts that the exact same dependencies and versions are used as when the existing Cargo.lock file was originally generated. Cargo will exit with an error when either of the following scenarios arises:
•The lock file is missing.
•Cargo attempted to change the lock file due to a different dependency resolution.

It may be used in environments where deterministic builds are desired, such as in CI pipelines.

--offline

Prevents Cargo from accessing the network for any reason. Without this flag, Cargo will stop with an error if it needs to access the network and the network is not available. With this flag, Cargo will attempt to proceed without the network if possible.

Beware that this may result in different dependency resolution than online mode. Cargo will restrict itself to crates that are downloaded locally, even if there might be a newer version as indicated in the local copy of the index. See the cargo-fetch(1) command to download dependencies before going offline.

May also be specified with the net.offline config value https://doc.rust-lang.org/cargo/reference/config.html.

--frozen

Equivalent to specifying both --locked and --offline.

--lockfile-path PATH

Changes the path of the lockfile from the default (<workspace_root>/Cargo.lock) to PATH. PATH must end with Cargo.lock (e.g. --lockfile-path /tmp/temporary-lockfile/Cargo.lock). Note that providing --lockfile-path will ignore existing lockfile at the default path, and instead will either use the lockfile from PATH, or write a new lockfile into the provided PATH if it doesn’t exist. This flag can be used to run most commands in read-only directories, writing lockfile into the provided PATH.

This option is only available on the nightly channel https://doc.rust-lang.org/book/appendix-07-nightly-rust.html and requires the -Z unstable-options flag to enable (see #14421 https://github.com/rust-lang/cargo/issues/14421).

Common Options

+toolchain

If Cargo has been installed with rustup, and the first argument to cargo begins with +, it will be interpreted as a rustup toolchain name (such as +stable or +nightly). See the rustup documentation https://rust-lang.github.io/rustup/overrides.html for more information about how toolchain overrides work.

--config KEY=VALUE or PATH

Overrides a Cargo configuration value. The argument should be in TOML syntax of KEY=VALUE, or provided as a path to an extra configuration file. This flag may be specified multiple times. See the command-line overrides section https://doc.rust-lang.org/cargo/reference/config.html#command-line-overrides for more information.

-C PATH

Changes the current working directory before executing any specified operations. This affects things like where cargo looks by default for the project manifest (Cargo.toml), as well as the directories searched for discovering .cargo/config.toml, for example. This option must appear before the command name, for example cargo -C path/to/my-project build.

This option is only available on the nightly channel https://doc.rust-lang.org/book/appendix-07-nightly-rust.html and requires the -Z unstable-options flag to enable (see #10098 https://github.com/rust-lang/cargo/issues/10098).

-h, --help

Prints help information.

-Z flag

Unstable (nightly-only) flags to Cargo. Run cargo -Z help for details.

Miscellaneous Options

The --jobs argument affects the building of the test executable but does not affect how many threads are used when running the tests. The Rust test harness includes an option to control the number of threads used:

cargo test -j 2 -- --test-threads=2

-j N, --jobs N

Number of parallel jobs to run. May also be specified with the build.jobs config value https://doc.rust-lang.org/cargo/reference/config.html. Defaults to the number of logical CPUs. If negative, it sets the maximum number of parallel jobs to the number of logical CPUs plus provided value. If a string default is provided, it sets the value back to defaults. Should not be 0.

--future-incompat-report

Displays a future-incompat report for any future-incompatible warnings produced during execution of this command

See cargo-report(1)

While cargo test involves compilation, it does not provide a --keep-going flag. Use --no-fail-fast to run as many tests as possible without stopping at the first failure. To “compile” as many tests as possible, use --tests to build test binaries separately. For example:

cargo build --tests --keep-going
cargo test --tests --no-fail-fast

ENVIRONMENT

See the reference https://doc.rust-lang.org/cargo/reference/environment-variables.html for details on environment variables that Cargo reads.

EXIT STATUS

•0: Cargo succeeded.
•101: Cargo failed to complete.

EXAMPLES

1.Execute all the unit and integration tests of the current package: 
cargo test
2.Run only tests whose names match against a filter string: 
cargo test name_filter
3.Run only a specific test within a specific integration test: 
cargo test --test int_test_name -- modname::test_name
