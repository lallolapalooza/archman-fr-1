NOM

cap_iab_init, cap_iab_dup, cap_iab_get_proc, cap_iab_get_pid, cap_iab_set_proc, cap_iab_to_text, cap_iab_from_text, cap_iab_get_vector, cap_iab_compare, cap_iab_set_vector, cap_iab_fill, cap_proc_root - fonctions de support du tuple IAB héritable

SYNOPSIS

#include <sys/capability.h>
cap_iab_t cap_iab_init(void);
cap_iab_t cap_iab_dup(cap_iab_t iab);
cap_iab_t cap_iab_get_proc(void);
cap_iab_t cap_iab_get_pid(pid_t pid);
int cap_iab_set_proc(cap_iab_t iab);
char *cap_iab_to_text(cap_iab_t iab);
cap_iab_t cap_iab_from_text(const char *text);
cap_flag_value_t cap_iab_get_vector(cap_iab_t iab, cap_iab_vector_t vec,
    cap_value_t val);
int cap_iab_compare(cap_iab_t a, cap_iab_t b);
int cap_iab_set_vector(cap_iab_t iab, cap_iab_vector_t vec, cap_value_t val,
    cap_flag_value_t enable);
int cap_iab_fill(cap_iab_t iab, cap_iab_vector_t vec,
    cap_t set, cap_flag_t flag);
char *cap_proc_root(const char *root);

Lier avec -lcap.

DESCRIPTION

Les fonctions définies dans cette page de manuel concernent les trois vecteurs de capacités de processus naïvement héritables : Inh, Amb et Bound. Ce tuple IAB de 3 vecteurs de capacités, capturé dans le type cap_iab_t, est combiné pour passer des capacités d'un processus à un autre via les appels système execve(2). Les règles de convolution utilisant le tuple IAB sont un ensemble de règles de secours lorsque le fichier exécuté n'a pas de capacités de fichier configurées.

Il existe certaines contraintes imposées par le noyau concernant les trois composants d'un tuple IAB et le drapeau de processus Permitted. Ce sont : le vecteur Inh (CAP_IAB_INH) est entièrement égal au drapeau Héritable du processus à tout moment ; le vecteur Amb (CAP_IAB_AMB) ne contient pas plus de valeurs de capacité que l'intersection du vecteur Inh et du drapeau Permitted pour le processus ; et le vecteur Bound (ou bloqué) (CAP_IAB_BOUND) est le complément à deux du vecteur de limites du processus.

Dans certains environnements, il est considéré comme souhaitable d'hériter des capacités de manière naïve. C'est-à-dire passer des capacités, indépendamment de l'état du binaire exécuté, du parent à l'enfant via les appels système exec. Les capacités survivantes deviennent le drapeau Permitted pour le processus post-exécution. Cette méthode d'héritage diffère considérablement de l'héritage handshake entre un processus pré-exec* et un exécutable doté de capacités de fichier du mécanisme de capacité traditionnel (POSIX.1e).

Les règles de convolution pour l'héritage de style IAB sont : I'=I ; A'=A&I ; P'=A&I&P. Où P etc. sont les valeurs pré-exécution et P' etc. sont les valeurs post-exécution.

Avec une compréhension de ces règles de convolution, nous pouvons expliquer comment libcap(3) gère le support du tuple IAB : l'API IAB.

cap_iab_init() renvoie une valeur IAB vide. C'est-à-dire un tuple presque inoffensif. Il ne bloquera aucune capacité de fichier Permitted via exec, mais il n'en accordera aucune non plus. Le cap_iab_t renvoyé doit être libéré avec cap_free(3).

cap_iab_dup() renvoie une copie de la valeur IAB spécifiée. Le cap_iab_t renvoyé doit être libéré avec cap_free(3).

cap_iab_get_proc() renvoie une copie de la valeur IAB pour le processus courant. Le cap_iab_t renvoyé doit être libéré avec cap_free(3).

cap_iab_get_pid() renvoie une copie de la valeur IAB pour le processus spécifié. Le cap_iab_t renvoyé doit être libéré avec cap_free(3). Cette fonction recherche par défaut dans /proc/<PID>/status les informations IAB, mais cet emplacement peut être remplacé en utilisant la fonction cap_proc_root().

cap_iab_set_proc() peut être utilisé pour définir la valeur IAB portée par le processus courant. Un tel réglage échouera si le processus est insuffisamment capable. Pour augmenter les bits I non présents dans le drapeau P, ou pour appliquer de nouvelles masques B, il faut que CAP_SETPCAP soit présent dans le drapeau Permitted (la fonction l'augmentera temporairement dans le drapeau Effective si nécessaire). Dans tous les cas, les valeurs A augmentées doivent être présentes dans l'intersection des valeurs Permitted et Inh.

cap_iab_to_text() convertira un tuple IAB en une représentation textuelle IAB canonique. La représentation est légèrement redondante mais libcap(3) essaiera de générer la représentation la plus courte possible.

cap_iab_from_text() génère un tuple IAB à partir d'une chaîne de texte (probablement générée par la fonction précédente). Le tuple IAB renvoyé doit être libéré avec cap_free().

cap_iab_get_vector() peut être utilisé pour déterminer la valeur spécifique d'une capacité d'un vecteur IAB.

cap_iab_compare() peut être utilisé pour comparer deux tuples cap_iab_t. Lorsque la valeur de retour est non nulle, la macro CAP_IAB_DIFFERS(status, vector) est évaluée à non nulle si le statut renvoyé diffère dans ses composants vector.

cap_iab_set_vector() peut être utilisé pour définir une valeur de vecteur spécifique sur le paramètre d'activation.

cap_iab_fill() peut être utilisé pour copier en bloc une valeur de drapeau cap_t dans le vecteur vec du tuple IAB. La copie dans Amb (CAP_IAB_AMB) peut implicitement augmenter les valeurs Inh (CAP_IAB_INH) dans le tuple IAB. De même, la copie dans le vecteur Inh peut implicitement abaisser les valeurs Amb qui ne sont pas présentes dans le vecteur Inh résultant.

cap_proc_root() peut être utilisé pour déterminer l'emplacement actuel interrogé par cap_iab_get_pid(). Les valeurs renvoyées doivent être libérées avec cap_free(3). Si l'argument de cap_proc_root() n'est pas NULL, une copie sera utilisée pour remplacer /proc. Notez que cette fonction n'est pas thread-safe par rapport aux appels concurrents à cap_iab_get_pid().

ERREURS

Les fonctions renvoyant des valeurs cap_iab_t ou de la mémoire allouée sous forme de chaîne renvoient NULL en cas d'erreur.

Les valeurs de retour entières sont -1 en cas d'erreur et 0 en cas de succès.

En cas d'erreur, consultez errno.

NOTES

Contrairement à l'ensemble de capacités cap_t traditionnel, le tuple IAB, pris ensemble, est incompatible avec les capacités de système de fichiers créées via des outils comme setcap(8). C'est-à-dire que le vecteur Amb du tuple IAB est rendu caduc lorsqu'un exécutable avec une capacité de fichier est exécuté.

De plus, il existe des modes cap_mode(3) de libcap qui rendent le vecteur Amb et sa méthode d'héritage de processus désactivés.

HISTORIQUE

Le format IAB pour les variantes héritables de capacités a été initialement développé comme syntaxe de configuration pour le module Linux-PAM pam_cap.so dans libcap-2.29. Il a été introduit pour étendre la liste simple de capacités Héritables du processus séparées par des virgules, que le module pouvait attribuer à un arbre de processus authentifié, afin d'inclure des limites imposées sur le vecteur Bounding et d'introduire le support du vecteur Ambiant des bits de capacité.

Alors que les vecteurs Héritable et Bounding étaient anticipés par le projet POSIX.1e qui introduisait les capacités, le vecteur Ambiant est une invention Linux, et incompatible avec le modèle de capacité de fichier POSIX.1e. En tant que tel, il a été jugé que tenter de mélanger les 5 vecteurs de capacités en une seule représentation textuelle ne fonctionnerait pas. Au lieu de cela, la syntaxe de configuration de pam_cap.so a été généralisée en un ensemble complet de fonctions libcap pour regrouper les trois capacités naïvement héritables : le tuple IAB. Le support pour cela a débuté dans libcap-2.33.
