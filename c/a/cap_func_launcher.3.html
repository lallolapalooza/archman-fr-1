cap_func_launcher(3)

Paquet: libcap

CAP_LAUNCH(3) Manuel du programmeur Linux CAP_LAUNCH(3)

NOM

cap_new_launcher, cap_func_launcher, cap_launcher_callback, cap_launcher_set_mode, cap_launcher_set_iab, cap_launcher_set_chroot, cap_launch, cap_launcher_setuid, cap_launcher_setgroups - fonctionnalité de lancement de libcap

SYNOPSIS

#include <sys/capability.h>
cap_launch_t cap_new_launcher(const char *arg0, const char *const *argv,
    const char *const *envp);
cap_launch_t cap_func_launcher(int (callback_fn)(void *detail));
int cap_launcher_callback(cap_launch_t attr,
    int (callback_fn)(void *detail));
int cap_launcher_set_mode(cap_launch_t attr, cap_mode_t flavor);
cap_iab_t cap_launcher_set_iab(cap_launch_t attr, cap_iab_t iab);
int cap_launcher_set_chroot(cap_launch_t attr, const char *chroot);
#include <sys/types.h>
pid_t cap_launch(cap_launch_t attr, void *detail);
int cap_launcher_setuid(cap_launch_t attr, uid_t uid);
int cap_launcher_setgroups(cap_launch_t attr, gid_t gid,
    int ngroups, const gid_t *groups);

Lier avec -lcap.

DESCRIPTION

Un lanceur fournit un mécanisme permettant d'exécuter une fonction de rappel et/ou un exécutable de programme dans un environnement avec un contexte de sécurité modifié. Essentiellement, il fournit un mécanisme permettant à un programme de fork(2) un nouveau contexte à partir de celui du programme principal, de manipuler les capacités et d'autres états privilégiés dans ce fork(2)d processus avant (éventuellement) execve(2)un nouveau programme. Lorsque l'application est liée à -lpsx cette prise en charge est nécessaire pour exécuter robustement le code lancé sans modifier le privilège de toute l'application principale (qui respecte la sémantique POSIX).

Un lanceur est défini par l'une de ces deux fonctions : cap_new_launcher() ou cap_func_launcher(). La valeur de retour étant de type opaque cap_launch_t une valeur de retour NULL indique qu'une erreur s'est produite.

Une fois défini, une valeur cap_launch_t peut être utilisée avec cap_launch() pour exécuter ce lanceur. Dans de tels cas, une valeur de retour non négative indique le succès : zéro signifie le succès sans qu'un programme soit invoqué ; non nul étant égal à l'identifiant de processus (pid_t) du programme nouvellement lancé.

Un cap_launch_t occupe de la mémoire allouée et doit être libéré avec cap_free(3). Avant d'être cap_free(3)d, une valeur cap_value_t peut être réutilisée pour plusieurs lancements indépendants. L'argument detail de cap_launch(), en conjonction avec la fonction de rappel du lanceur, peut être utilisé pour personnaliser l'invocation du lancement. Il faut faire attention à utiliser de la mémoire partagée personnalisée (voir mmap(2)) ou une autre IPC pour renvoyer des valeurs au programme principal via detail car le rappel et toute exécution ultérieure de programme se produiront en dehors du processus principal de l'application appelante. Un exemple de cela serait d'allouer detail comme suit :

   const char *args[] = { "echo", "hello", NULL };
   cap_launch_t cmd = cap_new_launcher("/usr/bin/echo", args, NULL);
   int *detail = mmap(NULL, sizeof(int), PROT_READ | PROT_WRITE,
                      MAP_SHARED | MAP_ANONYMOUS, -1, 0);
   cap_launcher_callback(cmd, &answer_detail_fn);
   *detail = 41;
   pid_t pid = cap_launch(cmd, detail);
   printf("launcher callback set detail to %d\n", *detail);
   munmap(detail, sizeof(int));

Sauf si modifié par la fonction de rappel, le code lancé sera exécuté avec les capacités et le contexte de sécurité de l'application.

Si la fonction de rappel renvoie autre chose que zéro, un cap_launch() sera interrompu. Si les détails de l'échec sont importants pour l'appelant, ils doivent être communiqués via l'argument detail .

Les fonctions suivantes peuvent être utilisées pour indiquer au lanceur de modifier l'état de sécurité du programme invoqué sans altérer l'état du programme appelant. De telles modifications doivent être effectuées avant d'appeler cap_launch() si elles doivent avoir l'effet désiré. De plus, elles ne sont invoquées qu'après qu'un rappel installé ait été terminé. Par exemple, on peut abandonner ou modifier des capacités, juste pour exécuter un fichier.

Les fonctions suivantes indiquent au lanceur d'effectuer certaines tâches courantes de ce type (notez que certaines nécessitent des bits de capacité autorisés pour réussir) :

cap_launcher_callback() peut être utilisé pour installer ou remplacer la fonction de rappel actuellement installée du lanceur.

cap_launcher_set_mode() peut être utilisé pour s'assurer que le libcap-mode du programme lancé est celui désiré.

cap_launcher_set_iab() Cette fonction renvoie le cap_iab_t précédemment associé au lanceur. Appeler cette fonction avec une valeur IAB NULL configurera le lanceur pour ne pas définir une valeur IAB (par défaut). Voir cap_iab(3) pour des détails sur l'ensemble IAB. Notez que le lanceur est directement associé à la valeur iab fournie et n'en fait pas une copie. Cette valeur iab est verrouillée à la launcheur et ne peut pas être modifiée tant qu'elle est associée au lanceur. Définissez avec NULL pour reprendre le contrôle de la mémoire associée à cette valeur IAB, sinon la valeur IAB sera cap_free()'d lorsque le lanceur l'est.

cap_launcher_set_chroot() Cette fonction fait en sorte que l'exécutable du programme lancé soit invoqué à l'intérieur du répertoire chroot root .

cap_launcher_setuid() Cette fonction fait en sorte que l'exécutable du programme lancé soit invoqué avec l'identifiant utilisateur spécifié (uid_t).

cap_launcher_setgroups() Cette fonction fait en sorte que l'exécutable du programme lancé soit invoqué avec les identifiants de groupe principal et supplémentaires spécifiés.

Notez que si l'une des améliorations du lanceur effectuées par les fonctions ci-dessus devait échouer à prendre effet (généralement par manque de privilège suffisant), le lancement échouera et renverra -1.

ERREURS

Un retour de NULL pour un cap_launch_t doit être considéré comme une erreur.

cap_launch() renvoie -1 en cas d'erreur.

Dans tous ces cas, une valeur de retour de 0 implique le succès. Dans d'autres cas, consultez errno(3) pour plus de détails.

HISTORIQUE

La cap_launch() famille de fonctions a été introduite dans libcap 2.33. Elle traite principalement une complexité avec les applications pthreads(7) liées à -lpsx qui utilisent des capacités mais respectent aussi la sémantique POSIX.

Utiliser -lcap et -lpthread ensemble sans la prise en charge de la sémantique POSIX de -lpsx introduit une classe subtile d'exposition à l'élévation de privilèges. (Voir https://sites.google.com/site/fullycapable/who-ordered-libpsx pour une explication.)
