NOM

cap_get_proc, cap_set_proc, capgetp, cap_get_bound, cap_drop_bound, cap_get_ambient, cap_set_ambient, cap_reset_ambient, cap_get_secbits, cap_set_secbits, cap_get_mode, cap_set_mode, cap_mode_name, cap_get_pid, cap_setuid, cap_prctl, cap_prctlw, cap_setgroups - manipulation des capacités sur les processus

SYNOPSIS

#include <sys/capability.h>
cap_t cap_get_proc(void);
int cap_set_proc(cap_t cap_p);
int cap_get_bound(cap_value_t cap);
CAP_IS_SUPPORTED(cap_value_t cap);
int cap_drop_bound(cap_value_t cap);
int cap_get_ambient(cap_value_t cap);
int cap_set_ambient(cap_value_t cap, cap_flag_value_t value);
int cap_reset_ambient(void);
CAP_AMBIENT_SUPPORTED();
unsigned cap_get_secbits(void);
int cap_set_secbits(unsigned bits);
cap_mode_t cap_get_mode(void);
const char *cap_mode_name(cap_mode_t mode);
int cap_prctl(long int pr_cmd, long int arg1, long int arg2,
	      long int arg3, long int arg4, long int arg5);
int cap_prctlw(long int pr_cmd, long int arg1, long int arg2,
	       long int arg3, long int arg4, long int arg5);
int cap_set_mode(cap_mode_t mode);
#include <sys/types.h>
cap_t cap_get_pid(pid_t pid);
int cap_setuid(uid_t uid);
int cap_setgroups(gid_t gid, size_t ngroups, const gid_t groups);

Lier avec -lcap.

DESCRIPTION

cap_get_proc() alloue un état de capacité dans la mémoire de travail, définit son état sur celui du processus appelant, et retourne un pointeur vers cet état de capacité nouvellement créé. L'appelant doit libérer toute mémoire libérable, lorsque l'état de capacité en mémoire de travail n'est plus requis, en appelant cap_free() avec le cap_t comme argument.

cap_set_proc() définit les valeurs de tous les drapeaux de capacité pour toutes les capacités à l'état de capacité identifié par cap_p. Le nouvel état de capacité du processus sera complètement déterminé par le contenu de cap_p lors du retour réussi de cette fonction. Si un drapeau quelconque dans cap_p est défini pour une capacité non actuellement permise pour le processus appelant, la fonction échouera et l'état de capacité du processus restera inchangé.

cap_get_pid() retourne un cap_t, voir cap_init(3), avec les capacités de processus du processus connu de l'appelant sous pid. Si pid est 0, alors les capacités du processus appelant sont retournées. Cette information peut également être obtenue à partir du fichier /proc/<pid>/status. (Les entrées de ce fichier peuvent être traduites avec la commande capsh --decode=XXX.) Lorsque l'appelant opère dans un espace de noms (CLONE_NEWPID), le pid numérique argument est interprété dans la plage de cet espace de noms. Ainsi, l'idée de l'appelant du pid cible peut différer de celle du processus cible lorsqu'ils opèrent dans différents espaces de noms pid. Voir pid_namespaces(7) pour les détails. De plus, le cap_t retourné contient les capacités que le pid cible pense avoir. Si la cible opère dans un espace de noms (CLONE_NEWUSER), le privilège global de ces capacités d'espace de noms d'utilisateur peut être considérablement réduit. Voir user_namespaces(7) pour les détails.

cap_get_bound() avec un cap comme argument retourne la valeur actuelle de ce drapeau de capacité de l'ensemble de limitation en vigueur pour le processus appelant. Cette opération n'est pas privilégiée. Notez qu'une macro fonction, CAP_IS_SUPPORTED(cap_value_t cap), est fournie qui évalue à vrai (1) si le système prend en charge la capacité spécifiée, cap. Si le système ne prend pas en charge la capacité, cette fonction retourne 0. Cette macro fonctionne en testant une condition d'erreur avec cap_get_bound().

cap_drop_bound() peut être utilisée pour abaisser la capacité spécifiée de l'ensemble de limitation, cap. Pour réussir, l'ensemble de capacité *effectif* prévaut doit avoir une CAP_SETPCAP relevée.

cap_get_ambient() retourne la valeur prévalente de la capacité ambiante spécifiée, ou -1 si la capacité n'est pas prise en charge par le noyau en cours d'exécution. Une macro CAP_AMBIENT_SUPPORTED() utilise cette fonction pour déterminer si les capacités ambiantes sont prises en charge par le noyau.

cap_set_ambient() définit la capacité ambiante spécifiée à une valeur spécifique. Pour relever une capacité ambiante spécifique, les drapeaux *héritables* et *permis* du processus appelant doivent contenir la valeur de capacité spécifiée. Les bits ambiants relevés ne seront conservés tant que cela restera vrai pour les drapeaux héritables et permis.

cap_reset_ambient() réinitialise toutes les capacités ambiantes du processus appelant à leur valeur abaissée. Notez que l'ensemble ambiant est destiné à fonctionner dans un environnement hérité où l'application a une conscience limitée des capacités en général. L'exécution d'un fichier, avec des capacités de système de fichiers associées, le noyau réinitialise implicitement l'ensemble ambiant du processus. De plus, les modifications apportées à l'ensemble héritable par le code du programme sans ajustement explicite de l'ensemble ambiant peuvent également abandonner les bits ambiants.

cap_get_secbits() retourne les bits sécurisés du processus appelant. Ces bits affectent la manière dont le processus appelant implémente des choses comme la correction setuid-root et les capacités ambiantes.

cap_set_secbits() tente de modifier les bits sécurisés du processus appelant. Notez que CAP_SETPCAP doit être dans l'ensemble des capacités effectives pour que cela soit efficace. Certains paramètres verrouillent les sous-états des bits sécurisés, de sorte que les tentatives de définition de valeurs peuvent être refusées par le noyau même lorsque la capacité CAP_SETPCAP est relevée.

Pour aider à gérer la complexité des bits sécurisés, libcap fournit un concept combiné de bits sécurisés et d'ensemble de capacités appelé mode libcap. cap_get_mode() tente de résumer l'environnement de sécurité prévalant sous la forme d'une valeur numérique cap_mode_t. Une représentation textuelle du mode peut être obtenue via la fonction cap_mode_name(). La grande majorité des combinaisons de ces valeurs ne sont pas bien définies en termes de mode libcap, et pour ces états cap_get_mode() retourne (cap_mode_t)0 qui est identifié par cap_get_name() comme « UNCERTAIN ». Les modes pris en charge sont : CAP_MODE_NOPRIV, CAP_MODE_HYBRID, CAP_MODE_PURE1E et CAP_MODE_PURE1E_INIT.

cap_prctl() peut être utilisé pour lire l'état via l'appel système prctl().

cap_prctlw() peut être utilisé pour écrire l'état via l'appel système prctl().

cap_set_mode() peut être utilisé pour définir le mode désiré. La capacité permise CAP_SETPCAP est requise pour que cette fonction réussisse.

cap_setuid() est une fonction pratique pour l'appel système setuid(2). Où cap_setuid() arrange pour que la capacité effective droite soit relevée afin d'effectuer l'appel système, et arrange également pour préserver la disponibilité des capacités permises après que l'uid a changé. Suite à cet appel, toutes les capacités effectives sont abaissées.

cap_setgroups() est une fonction pratique pour effectuer les appels setgid(2) et setgroups(2) en un seul appel. L'appel cap_setgroups() relève la capacité effective droite pendant la durée de l'appel, et vide l'ensemble des capacités effectives avant de retourner.

VALEUR DE RETOUR

Les fonctions cap_get_proc() et cap_get_pid() retournent une valeur non NULL en cas de succès, et NULL en cas d'échec.

La fonction cap_get_bound() retourne -1 si la capacité demandée est inconnue, sinon la valeur de retour reflète l'état actuel de cette capacité dans l'ensemble de limitation prévalent. Notez qu'une macro fonction,

Toutes les fonctions de définition telles que cap_set_proc() et cap_drop_bound() retournent zéro en cas de succès, et -1 en cas d'échec.

En cas d'échec, errno est défini à EINVAL, EPERM, ou ENOMEM.

CONFORMITÉ

cap_set_proc() et cap_get_proc() sont spécifiées dans la brouillon POSIX.1e retirée. cap_get_pid() est une extension Linux.

NOTES

Ni glibc, ni le noyau Linux ne respectent les sémantiques POSIX pour la définition des capacités et des bits sécurisés en présence de pthreads. C'est-à-dire que la modification des ensembles de capacités, par défaut, n'affecte que le thread en cours d'exécution. Pour être significativement sécurisé, cependant, les ensembles de capacités devraient être reflétés par un

ll threads au sein d'un programme commun car les threads ne sont pas isolés en mémoire. En contournement pour cela, libcap est empaqueté avec une bibliothèque système d'appels séparée à sémantique POSIX : libpsx. Si votre programme utilise des threads POSIX, pour obtenir une manipulation des capacités avec une sémantique POSIX significative, vous devriez lier votre programme avec

:

ld ... -lcap $(pkg-config --libs --cflags

libpsx)

ou

,

gcc ... -lcap $(pkg-config --libs --cflags

libpsx)

Lorsqu'il est lié de cette manière, grâce à la magie de l'éditeur de liens, libcap utilise psx_syscall(3) et psx_syscall6(3) pour effectuer les appels système de configuration d'état. Notamment, cela garantit aussi que cap_prctlw() peut être utilisé pour s'assurer que les bits de contrôle du processus sont partagés sur tous les threads d'un seul

processus.

capgetp() et

capsetp()

La bibliothèque prend également en charge les fonctions dépréciées

:

int capgetp(pid_t pid, cap_t cap_d)

;

int capsetp(pid_t pid, cap_t cap_d)

;

capgetp() tente d'obtenir les capacités d'un autre processus ; stockant les capacités dans un cap_d préalloué. Voir cap_init() pour des informations sur l'allocation d'un ensemble de capacités vide. Cette fonction est dépréciée ; vous devriez utiliser cap_get_p

id().

capsetp() tente de définir les capacités du processus appelant ou d'un ou plusieurs autres processus, pid. Notez que définir les capacités d'un autre processus n'est possible que sur les anciens noyaux qui ne fournissent pas de support VFS pour la définition des capacités de fichiers. Voir capset(2) pour des informations sur les noyaux qui fournissent un tel

support.

Si pid est positif, il se réfère à un processus spécifique ; s'il est zéro, il se réfère au processus appelant ; -1 se réfère à tous les processus autres que le processus appelant et le processus « 1 » (typiquement init(8)) ; les autres valeurs négatives se réfèrent au groupe de processus

-pid.

Afin d'utiliser cette fonction, le noyau doit la prendre en charge et le processus appelant doit avoir CAP_SETPCAP activé dans son ensemble de capacités Effectives. Les capacités définies dans le ou les processus cibles sont celles contenues dans cap_d

.

Les noyaux qui prennent en charge les capacités du système de fichiers redéfinissent la sémantique de CAP_SETPCAP et sur de tels systèmes, capsetp() échouera toujours pour toute cible différente du processus appelant. capsetp() renvoie zéro en cas de succès, et -1 en cas

d'échec.

Sur les noyaux où cela est (était) pris en charge, capsetp() devrait être utilisé avec précaution. Elle existait principalement pour surmonter un manque précoce de support pour les capacités dans les systèmes de fichiers pris en charge par Linux. Notez que sur les anciens noyaux où capsetp() pouvait être utilisée pour définir les capacités d'un autre processus, les seuls processus qui avaient CAP_SETPCAP disponible pour eux par défaut étaient les processus démarrés en tant que threads du noyau. (Typiquement, cela inclut init(8), kflushd et kswapd.) Une recompilation

du noyau était néc
essaire pour modifier cette valeur par défaut.

EXEMPL

E

Le segment de code ci-dessous active les capacités effectives CAP_FOWNER et CAP_SETFCAP pour l'appelant

: 
    ...
    cap_t caps;
    const cap_value_t cap_list[2] = {CAP_FOWNER, CAP_SETFCAP};
    if (!CAP_IS_SUPPORTED(CAP_SETFCAP))
        /* handle error */
    caps = cap_get_proc();
    if (caps == NULL)
        /* handle error */;
    if (cap_set_flag(caps, CAP_EFFECTIVE, 2, cap_list, CAP_SET) == -1)
        /* handle error */;
    if (cap_set_proc(caps) == -1)
        /* handle error */;
    if (cap_free(caps) == -1)
        /* handle error */;
    ..
.

Alternativement, pour abandonner complètement les privilèges dans un programme lancé setuid-root mais souhaitant s'exécuter avec un identifiant utilisateur spécifique, etc., de telle manière que ni lui, ni aucun de ses enfants ne puissent acquérir à nouveau des privilèges

: 
    ...
    uid_t nobody = 65534;
    const gid_t groups[] = {65534};
    if (cap_setgroups(groups[0], 1, groups) != 0)
        /* handle error */;
    if (cap_setuid(nobody) != 0)
        /* handle error */;
    /*
     * privilege is still available here
     */
    if (cap_set_mode(CAP_MODE_NOPRIV) != 0)
        /* handle error */
    ..
.

Notez que la séquence ci-dessus peut être réalisée par l'outil capsh comme suit

:

sudo capsh --user=nobody --mode=NOPRIV

--print

où --print affiche l'état

de privilèg
e résultant.
