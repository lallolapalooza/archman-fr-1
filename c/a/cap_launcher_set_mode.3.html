NOM

cap_new_launcher, cap_func_launcher, cap_launcher_callback, cap_launcher_set_mode, cap_launcher_set_iab, cap_launcher_set_chroot, cap_launch, cap_launcher_setuid, cap_launcher_setgroups - fonctionnalité de lancement de libcap

SYNOP

#include <sys/capability.h>
cap_launch_t cap_new_launcher(const char *arg0, const char *const *argv,
    const char *const *envp);
cap_launch_t cap_func_launcher(int (callback_fn)(void *detail));
int cap_launcher_callback(cap_launch_t attr,
    int (callback_fn)(void *detail));
int cap_launcher_set_mode(cap_launch_t attr, cap_mode_t flavor);
cap_iab_t cap_launcher_set_iab(cap_launch_t attr, cap_iab_t iab);
int cap_launcher_set_chroot(cap_launch_t attr, const char *chroot);
#include <sys/types.h>
pid_t cap_launch(cap_launch_t attr, void *detail);
int cap_launcher_setuid(cap_launch_t attr, uid_t uid);
int cap_launcher_setgroups(cap_launch_t attr, gid_t gid,
    int ngroups, const gid_t *groups);

Lier avec -lcap.

DESCRIPTION

Un lanceur fournit un mécanisme permettant à du code d'exécuter une fonction de rappel et/ou un programme exécutable dans un environnement avec un contexte de sécurité modifié. Essentiellement, il fournit un mécanisme pour qu'un programme fasse un fork(2) dans un nouveau contexte à partir de celui du programme principal, manipule les capacités et d'autres états privilégiés dans ce processus fork(2)é avant (éventuellement) d'execve(2)r un nouveau programme. Lorsque l'application se lie avec -lpsx, ce support est nécessaire pour exécuter de manière robuste le code lancé sans modifier le privilège de l'ensemble de l'application principale (respectant la sémantique POSIX).

Un lanceur est défini par l'une de ces deux fonctions : cap_new_launcher() ou cap_func_launcher(). La valeur de retour étant d'un type opaque cap_launch_t, une valeur de retour NULL implique qu'une erreur s'est produite.

Une fois défini, une valeur cap_launch_t peut être utilisée avec cap_launch() pour exécuter ce lanceur. Dans de tels cas, une valeur de retour non négative indique le succès : zéro signifiant le succès sans invocation de programme ; non nul étant égal à l'ID du processus (pid_t) du nouveau programme lancé.

Une cap_launch_t occupe de la mémoire allouée et doit être libérée avec cap_free(3). Avant d'être cap_free(3)e, une valeur cap_value_t peut être réutilisée pour plusieurs lancements indépendants. L'argument detail de cap_launch(), conjointement avec la fonction de rappel du lanceur, peut être utilisé pour personnaliser l'invocation du lancement. Des précautions doivent être prises pour exploiter la mémoire partagée personnalisée (voir mmap(2)) ou un autre IPC pour retourner des valeurs au programme principal via detail, car la fonction de rappel et toute exécution de programme subséquente se produiront en dehors du processus principal de l'application appelante. Un exemple de cela serait d'allouer `detail` comme suit :

   const char *args[] = { "echo", "hello", NULL };
   cap_launch_t cmd = cap_new_launcher("/usr/bin/echo", args, NULL);
   int *detail = mmap(NULL, sizeof(int), PROT_READ | PROT_WRITE,
                      MAP_SHARED | MAP_ANONYMOUS, -1, 0);
   cap_launcher_callback(cmd, &answer_detail_fn);
   *detail = 41;
   pid_t pid = cap_launch(cmd, detail);
   printf("launcher callback set detail to %d\n", *detail);
   munmap(detail, sizeof(int));

Sauf si modifiée par la fonction de rappel, le code lancé s'exécutera avec les capacités et le contexte de sécurité de l'application.

Si la fonction de rappel retourne autre chose que zéro, un appel à cap_launch() sera abandonné. Si les détails de l'échec sont importants pour l'appelant, ils doivent être communiqués via l'argument detail.

Les fonctions suivantes peuvent être utilisées pour demander au lanceur de modifier l'état de sécurité du programme invoqué sans modifier l'état du programme appelant. De telles modifications doivent être effectuées avant d'appeler cap_launch() pour avoir l'effet désiré. De plus, elles ne sont invoquées qu'après la fin de toute fonction de rappel installée. Par exemple, on peut abandonner ou modifier des capacités, juste pour l'exécution d'un fichier.

Les fonctions suivantes demandent au lanceur d'effectuer certaines tâches courantes de ce type (notez que certaines nécessitent des bits de capacité autorisés pour réussir) :

cap_launcher_callback() peut être utilisée pour installer ou remplacer la fonction de rappel actuellement installée du lanceur.

cap_launcher_set_mode() peut être utilisée pour s'assurer que le mode libcap du programme lancé est celui souhaité.

cap_launcher_set_iab() Cette fonction retourne le cap_iab_t précédemment associé au lanceur. Appeler cette fonction avec une valeur IAB de NULL configurera le lanceur pour ne pas définir de valeur IAB (par défaut). Voir cap_iab(3) pour les détails sur l'ensemble IAB. Notez que le lanceur est associé directement à la valeur iab fournie, et n'en fait pas de copie. Cette valeur iab est verrouillée au lanceur et ne peut pas être modifiée tant qu'elle est associée au lanceur. Définir à NULL pour retrouver le contrôle sur la mémoire associée à cette valeur IAB, sinon la valeur IAB sera cap_free() lorsqu'elle sera libérée par le lanceur.

cap_launcher_set_chroot() Cette fonction fait en sorte que l'exécutable du programme lancé soit invoqué à l'intérieur du répertoire root de chroot.

cap_launcher_setuid() Cette fonction fait en sorte que l'exécutable du programme lancé soit invoqué avec l'identifiant utilisateur spécifié (uid_t).

cap_launcher_setgroups() Cette fonction fait en sorte que l'exécutable du programme lancé soit invoqué avec les identifiants de groupe primaires et supplémentaires spécifiés.

Notez que si l'une des améliorations du lanceur effectuées par les fonctions ci-dessus échoue à prendre effet (typiquement par manque de privilège suffisant), le lancement échouera et retournera -1.

ERREURS

Un retour NULL pour une cap_launch_t doit être considéré comme une erreur.

cap_launch() retourne -1 en cas d'erreur.

Dans tous ces cas, une valeur de retour de 0 implique le succès. Dans d'autres cas, consultez errno(3) pour plus de détails.

HISTORIQUE

La famille de fonctions cap_launch() a été introduite dans libcap 2.33. Elle aborde principalement une complexité avec les applications pthreads(7) liées avec -lpsx qui utilisent des capacités mais respectent également la sémantique POSIX.

Utiliser -lcap et -lpthread ensemble sans le support de la sémantique POSIX de -lpsx introduit une classe subtile d'exposition à l'escalade de privilèges. (Voir https://sites.google.com/site/fullycapable/who-ordered-libpsx pour une explication.)
