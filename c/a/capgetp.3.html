L'appelant devrait libérer toute mémoire libérable lorsque l'état de capacité dans le stockage de travail n'est plus requis, en appelant cap_free() avec le cap_t comme argument. cap_set_proc() définit les valeurs de tous les indicateurs de capacité pour toutes les capacités à l'état de

capacité

identifié par cap_p. Le nouvel état de capacité du processus sera complètement déterminé par le contenu de cap_p lors du retour réussi de cette fonction. Si un indicateur dans cap_p est défini pour une capacité actuellement non autorisée pour le processus appelant, la fonction échouera et l'état de capacité du processus restera inchangé. cap_get_pid() renvoie un cap_t, voir cap_init(3), avec les capacités du processus connu de l'appelant sous pid. Si pid vaut 0, alors

les

capacités du processus appelant sont renvoyées. Ces informations peuvent aussi être obtenues à partir du fichier /proc/<pid> /status. (Les entrées de ce fichier peuvent être traduites avec la ligne de commande capsh --decode= XXX.) Lorsque l'appelant opère à l'intérieur d'un espace de noms ( CLONE_NEWPID), l'argument numérique pid est interprété dans laplage de cet espace de noms. Ainsi, la notion de pid cible del'appelant peut différer de celle du processus cible lorsqu'ils opèrent dans des espaces de noms pid différents. Voir pid_namespaces(7) pour plus de détails. De plus, la valeur cap_t renvoyée contient les capacités que le pid cible pense avoir. Si la cible opère dans un espace de noms ( CLONE_NEWUSER), le privilège système de ces capacités d'espace de noms utilisateur peut être substantiellement réduit. Voir user_namespaces(7)pour plus de détails. cap_get_bound() avec un cap comme argument renvoie la valeur actuelle de cet indicateur de capacité de l'ensemble de délimitation en vigueur pour

le

Si le système ne prendpas en charge la capacité, cette fonction renvoie 0. une

L'exécution d'un fichier, avec des capacités système de fichiers associées, le noyau réinitialisera implicitement l'ensemble ambiant du processus. De plus, les modifications de l'ensemble héritable par le code du programme sans réparer explicitement l'ensemble ambiant peuvent aussi faire tomber des bits ambiants. cap_get_secbits() renvoie les securebits du processus

Une représentation textuelle du mode peut être obtenue via la fonction cap_mode_name(). C'est-à-dire que la modification des ensembles de capacités, par défaut, n'affecte que le thread en cours d'exécution. capgetp() et

capsetp()

La bibliothèque prend également en charge les fonctions dépréciées

:

int capgetp(pid_t pid, cap_t cap_d)

;

int capsetp(pid_t pid, cap_t cap_d)

;

capgetp() tente d'obtenir les capacités d'un autre processus ; stockant les capacités dans un cap_d préalloué. Voir cap_init() pour des informations sur l'allocation d'un ensemble de capacités vide. Cette fonction est dépréciée ; vous devriez utiliser cap_get_p

id().

capsetp() tente de configurer les capacités du processus appelant ou d'un ou plusieurs autres processus, pid. Notez que la configuration des capacités d'un autre processus n'est possible que sur les anciens noyaux qui ne fournissent pas de support VFS pour la configuration des capacités de fichiers. Voir capset(2) pour des informations sur les noyaux qui fournissent un tel

support.

Si pid est positif, il désigne un processus spécifique ; s'il est zéro, il désigne le processus appelant ; -1 désigne tous les processus autres que le processus appelant et le processus '1' (typiquement init(8)) ; les autres valeurs négatives désignent le groupe de processus

-pid.

Afin d'utiliser cette fonction, le noyau doit la prendre en charge et le processus appelant doit avoir CAP_SETPCAP activé dans son ensemble de capacités Effectives. Les capacités configurées dans le ou les processus cibles sont celles contenues dans cap_d

.

Les noyaux qui prennent en charge les capacités du système de fichiers redéfinissent la sémantique de CAP_SETPCAP et sur de tels systèmes, capsetp() échouera toujours pour toute cible différente du processus appelant. capsetp() renvoie zéro en cas de succès, et -1 en cas

d'échec.

Sur les noyaux où cela est (était) pris en charge, capsetp() devrait être utilisé avec prudence. Elle existait principalement pour surmonter un manque précoce de support pour les capacités dans les systèmes de fichiers pris en charge par Linux. Notez que sur les anciens noyaux où capsetp() pouvait être utilisé pour configurer les capacités d'un autre processus, les seuls processus qui avaient CAP_SETPCAP disponible pour eux par défaut étaient les processus démarrés en tant que threads du noyau. (Typiquement, cela inclut init(8), kflushd et kswapd.) Une recompilation

du noyau était néc

    const cap_value_t cap_list[2] = {CAP_FOWNER, CAP_SETFCAP};

    caps = cap_get_proc();
    if (caps == NULL)
        /* handle error */;
    if (cap_set_flag(caps, CAP_EFFECTIVE, 2, cap_list, CAP_SET) == -1)
        /* handle error */;
    if (cap_set_proc(caps) == -1)
        /* handle error */;
    if (cap_free(caps) == -1)
        /* handle error */;
