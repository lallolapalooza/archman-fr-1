DESCRIPTIO

N

L'outil de base de données de certificats, certutil, est une utilitaire en ligne de commande qui peut créer et modifier des bases de données de certificats et de clés. Il peut spécifiquement lister, générer, modifier ou supprimer des certificats, créer ou changer le mot de passe, générer de nouvelles paires de clés publiques et privées, afficher le contenu de la base de données de clés, ou supprimer des paires de clés dans la base de données de

clés.

L'émission de certificats, qui fait partie du processus de gestion des clés et des certificats, nécessite que les clés et les certificats soient créés dans la base de données de clés. Ce document traite de la gestion des bases de données de certificats et de clés. Pour des informations sur la gestion de la base de données du module de sécurité, voir la page man d

e mod
util.

Spécifier un moment auquel un certificat doit être valide. Utilisez lors de la vérification de la validité d'un certificat avec l'option -V. Le format de l'argument validity-time est YYMMDDHHMMSS[+HHMM|-HHMM|Z], ce qui permet de définir des décalages par rapport à l'heure de fin de validité. Spécifier les secondes (SS) est facultatif. Lorsque vous spécifiez une heure explicite, utilisez un Z à la fin du terme, YYMMDDHHMMSSZ, pour le fermer. Lorsque vous spécifiez un décalage horaire, utilisez YYMMDDHHMMSS+HHMM ou YYMMDDHHMMSS-HHMM pour ajouter ou soustraire du temps, respectivement.

La plupart des options de commande dans les exemples listés ici ont des arguments supplémentaires disponibles. Les arguments inclus dans ces exemples sont les plus courants ou sont utilisés pour illustrer un scénario spécifique. Utilisez l'option -H pour afficher la liste complète des arguments pour chaque option de commande.

Création de nouvelles bases de données de sécurité

Les certificats, les clés et les modules de sécurité liés à la gestion des certificats sont stockés dans trois bases de données connexes :

•cert8.db ou cert9.db
•key3.db ou key4.db
•secmod.db ou pkcs11.txt

Ces bases de données doivent être créées avant que les certificats ou les clés puissent être générés.

certutil -N -d directory

Création d'une demande de certificat

Une demande de certificat contient la plupart ou la totalité des informations utilisées pour générer le certificat final. Cette demande est soumise séparément à une autorité de certification et est ensuite approuvée par un mécanisme quelconque (automatiquement ou par examen humain). Une fois la demande approuvée, le certificat est généré.

$ certutil -R -k type-de-clé-ou-id [-q pqgfile|nom-de-courbe] -g taille-clé -s sujet [-h nom-jeton] -d répertoire [-p téléphone] [-o fichier-sortie] [-a]

Les options de commande -R nécessitent quatre arguments :

•-k pour spécifier soit le type de clé à générer, soit, lors du renouvellement d'un certificat, la paire de clés existante à utiliser
•-g pour définir la taille de la clé à générer
•-s pour définir le nom du sujet du certificat
•-d pour indiquer le répertoire de la base de données de sécurité

La nouvelle demande de certificat peut être sortie au format ASCII (-a) ou écrite dans un fichier spécifié (-o).

Par exemple :

$ certutil -R -k rsa -g 1024 -s "CN=John Smith,O=Example Corp,L=Mountain View,ST=California,C=US" -d $HOME/nssdb -p 650-555-0123 -a -o cert.cer
Génération de la clé. Cela peut prendre quelques instants...

Création d'un certificat

Un certificat valide doit être délivré par une AC de confiance. Cela peut être fait en spécifiant un certificat d'AC (-c) stocké dans la base de données de certificats. Si une paire de clés d'AC n'est pas disponible, vous pouvez créer un certificat auto-signé en utilisant l'argument -x avec l'option de commande -S.

$ certutil -S -k rsa|dsa|ec -n nom-certificat -s sujet [-c émetteur |-x] -t arguments-confiance -d répertoire [-m numéro-de-série] [-v mois-validité] [-w décalage-mois] [-p téléphone] [-1] [-2] [-3] [-4] [-5 mot-clé] [-6 mot-clé] [-7 adresse-email] [-8 noms-dns] [--extAIA] [--extSIA] [--extCP] [--extPM] [--extPC] [--extIA] [--extSKID]

La série de nombres et les options --ext* définissent les extensions de certificat qui peuvent être ajoutées au certificat lors de sa génération par l'AC. Des invites interactives apparaîtront.

Par exemple, cela crée un certificat auto-signé :

$ certutil -S -s "CN=Example CA" -n my-ca-cert -x -t "C,C,C" -1 -2 -5 -m 3650

Les invites interactives pour l'usage de la clé et si des extensions sont critiques, ainsi que les réponses, ont été omises pour des raisons de brièveté.

À partir de là, de nouveaux certificats peuvent référencer le certificat auto-signé :

$ certutil -S -s "CN=My Server Cert" -n my-server-cert -c "my-ca-cert" -t ",," -1 -5 -6 -8 -m 730

Génération d'un certificat à partir d'une demande de certificat

Lorsqu'une demande de certificat est créée, un certificat peut être généré en utilisant la demande, puis en référençant un certificat d'autorité de signature de certificat (l'émetteur spécifié dans l'argument -c). Le certificat d'émission doit se trouver dans la base de données de certificats du répertoire spécifié.

certutil -C -c émetteur -i fichier-demande-cert -o fichier-sortie [-m numéro-de-série] [-v mois-validité] [-w décalage-mois] -d répertoire [-1] [-2] [-3] [-4] [-5 mot-clé] [-6 mot-clé] [-7 adresse-email] [-8 noms-dns]

Par exemple :

$ certutil -C -c "my-ca-cert" -i /home/certs/cert.req -o cert.cer -m 010 -v 12 -w 1 -d $HOME/nssdb -1 nonRepudiation,dataEncipherment -5 sslClient -6 clientAuth -7 jsmith@example.com

NSS DATABASE TYPES

Prior to NSS version 3.1, the NSS security databases were stored in Berkeley DB (DBM) format. These databases were:

•certdata.txt for certificates
•key3.db for keys
•secmod.db for PKCS #11 module information

BerkeleyDB has performance limitations, though, which prevent it from being easily used by multiple applications simultaneously. NSS has some flexibility that allows applications to use their own, independent database engine while keeping a shared database and working around the access issues. Still, NSS requires more flexibility to provide a truly shared security database.

In 2009, NSS introduced a new set of databases that are SQLite databases rather than BerkeleyDB. These new databases provide more accessibility and performance:

•cert9.db for certificates
•key4.db for keys
•pkcs11.txt, a listing of all of the PKCS #11 modules, contained in a new subdirectory in the security databases directory

Because the SQLite databases are designed to be shared, these are the shared database type. The shared database type is preferred; the legacy format is included for backward compatibility.

By default, the tools (certutil, pk12util, modutil) assume that the given security databases use the SQLite type. Using the legacy databases must be manually specified by using the dbm: prefix with the given security directory. For example:

$ certutil -L -d dbm:/home/my/sharednssdb

To set the legacy database type as the default type for the tools, set the NSS_DEFAULT_DB_TYPE environment variable to dbm:

export NSS_DEFAULT_DB_TYPE="dbm"

This line can be set added to the ~/.bashrc file to make the change permanent.

•https://wiki.mozilla.org/NSS_Shared_DB_Howto

For an engineering draft on the changes in the shared NSS databases, see the NSS project wiki:

•https://wiki.mozilla.org/NSS_Shared_DB
