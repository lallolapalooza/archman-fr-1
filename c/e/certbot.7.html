Si l'émetteur est approuvé par le logiciel qui initie la communication et que la signature est valide, la clé peut alors être utilisée pour communiquer de manière sécurisée avec le serveur identifié par le certificat. L'utilisation d'un certificat est un bon moyen de prévenir les attaques par « homme du milieu », où une personne située entre vous et le serveur avec lequel vous pensez parler peut insérer son propre contenu (malveillant). Utilisez le mode standalone pour obtenir un certificat si vous ne voulez pas utiliser (ou n'avez actuellement pas) de logiciel de serveur existant. Le plugin standalone ne repose sur aucun autre logiciel de serveur s'exécutant sur la machine où vous obtenez le

Pour obtenir un certificat en utilisant un serveur web « standalone », vous pouvez utiliser le plugin standalone en incluant certonly et --standalone sur la ligne de commande. Ce plugin doit se lier au port 80 afin d'effectuer la validation du domaine, vous devrez donc peut-être arrêter votre serveur web

Il doit toujours être possible pour votre machine d'accepter des connexions entrantes depuis Internet sur le port spécifié en utilisant chaque nom de domaine

demandé.

Par défaut, Certbot tente d'abord de se lier au port pour toutes les interfaces en utilisant IPv6, puis de se lier à ce port en utilisant IPv4 ; Certbot continue tant qu'au moins une liaison réussit. Sur la plupart des systèmes Linux, le trafic IPv4 sera routé vers le port IPv6 lié et l'échec lors de la deuxième liaison est

attendu.

Recréation et mise à jour de certificats

existants

Vous pouvez utiliser les sous-commandes certonly ou run pour demander la création d'un nouveau certificat unique, même si vous avez déjà un certificat existant avec certains des mêmes noms de

domaine.

Si un certificat est demandé avec run ou certonly en spécifiant un nom de certificat qui existe déjà, Certbot met à jour le certificat existant. Sinon, un nouveau certificat est créé et se voit attribuer le nom

spécifié.

Les options --force-renewal, --duplicate et --expand contrôlent le comportement de Certbot lors de la recréation d'un certificat portant le même nom qu'un certificat existant. Si vous ne spécifiez pas de comportement souhaité, Certbot peut vous demander ce que vous

vouliez.

--force-renewal indique à Certbot de demander un nouveau certificat avec les mêmes domaines qu'un certificat existant. Chaque domaine doit être explicitement spécifié via -d. En cas de succès, ce certificat est enregistré à côté du précédent et les liens symboliques (la référencelive ) seront mis à jour pour pointer vers le nouveau certificat. C'est une méthode valide pour renouveler un certificat individuel

spécifique.

--duplicate indique à Certbot de créer un certificat séparé et sans rapport avec les mêmes domaines qu'un certificat existant. Ce certificat est enregistré complètement séparément du précédent. La plupart des utilisateurs n'auront pas besoin d'émettre cette commande dans des circonstances

normales.

--expand indique à Certbot de mettre à jour un certificat existant avec un nouveau certificat qui contient tous les anciens domaines et un ou plusieurs nouveaux domaines supplémentaires. Avec l'option --expand, utilisez l'option -d pour spécifier tous les domaines existants et un ou plusieurs nouveaux

domaines.

Changer le serveur ACME

Par défaut, Certbot utilise le serveur de production de Let's Encrypt à l'adresse https://acme-v02.api.letsencrypt.org/directory. Vous pouvez indiquer à Certbot d'utiliser une autre AC (Autorité de Certification) en fournissant --server sur la ligne de commande ou dans un fichier de configuration avec l'URL du répertoire ACME du serveur. Par exemple, si vous souhaitez utiliser le serveur de staging de Let's Encrypt, vous ajouteriez --server https://acme-staging-v02.api.letsencrypt.org/directory à la ligne de commande.

Note :

--dry-run utilise le serveur de staging de Let's Encrypt, sauf si --server est spécifié sur la ligne de commande ou dans le fichier de configuration cli.ini. Soyez prudent lorsque vous utilisez --dry-run avec un serveur personnalisé, car cela pourrait entraîner l'émission et le rejet de certificats réels.

Si Certbot ne fait pas confiance au certificat SSL utilisé par le serveur ACME, vous pouvez utiliser la variable d'environnement REQUESTS_CA_BUNDLE https://requests.readthedocs.io/en/latest/user/advanced/#ssl-cert-verification pour remplacer les certificats racine approuvés par Certbot. Certbot utilise la bibliothèque requests, qui n'utilise pas le magasin de confiance des racines du système d'exploitation. Assurez-vous que REQUESTS_CA_BUNDLE est défini globalement dans l'environnement et pas seulement sur la ligne de commande, sinon le renouvellement planifié pourrait échouer.

Fichiers de verrouillage

Lors du traitement d'une validation, Certbot écrit plusieurs fichiers de verrouillage sur votre système pour empêcher plusieurs instances d'écraser les modifications des autres. Cela signifie que, par défaut, deux instances de Certbot ne pourront pas s'exécuter en parallèle.

Étant donné que les répertoires utilisés par Certbot sont configurables, Certbot écrira un fichier de verrouillage pour tous les répertoires qu'il utilise. Cela inclut --work-dir, --logs-dir et --config-dir de Certbot. Par défaut, il s'agit de /var/lib/letsencrypt, /var/log/letsencrypt et /etc/letsencrypt respectivement. De plus, si vous utilisez Certbot avec Apache ou nginx, il verrouillera le dossier de configuration de ce programme, qui se trouve généralement dans le répertoire /etc.

Notez que ces fichiers de verrouillage empêcheront uniquement les autres instances de Certbot d'utiliser ces répertoires, et non les autres processus. Si vous souhaitez exécuter plusieurs instances de Certbot simultanément, vous devez spécifier des répertoires différents comme --work-dir, --logs-dir et --config-dir pour chaque instance de Certbot que vous souhaitez exécuter.

Fichier de configuration

Certbot accepte un fichier de configuration global qui applique ses options à toutes les invocations de Certbot. Les choix de configuration spécifiques aux certificats doivent être définis dans les fichiers .conf qui se trouvent dans /etc/letsencrypt/renewal.

Par défaut, aucun fichier cli.ini n'est créé (bien qu'il puisse déjà exister si vous avez installé Certbot via un gestionnaire de paquets, par exemple). Après en avoir créé un, il est possible de spécifier l'emplacement de ce fichier de configuration avec certbot --config cli.ini (ou plus court -c cli.ini). Un exemple de fichier de configuration est présenté ci-dessous :

# Ceci est un exemple des choses que vous pouvez faire dans un fichier de configuration.
# Tous les drapeaux utilisés par le client peuvent être configurés ici. Exécutez Certbot avec
# "--help" pour en savoir plus sur les options disponibles.
#
# Notez que ces options s'appliquent automatiquement à toute utilisation de Certbot pour
# obtenir ou renouveler des certificats, de sorte que les options spécifiques à un seul
# certificat sur un système avec plusieurs certificats ne devraient pas être placées
# ici.
# Utiliser ECC pour la clé privée
key-type = ecdsa
elliptic-curve = secp384r1
# Utiliser une clé RSA de 4096 bits au lieu de 2048
rsa-key-size = 4096
# Décommentez et mettez à jour pour vous enregistrer avec l'adresse e-mail spécifiée
# email = foo@example.com
# Décommentez pour utiliser l'authentificateur autonome sur le port 80
# authenticator = standalone
# Décommentez pour utiliser l'authentificateur webroot. Remplacez webroot-path par le
# chemin d'accès au dossier public_html / webroot servi par votre serveur web.
# authenticator = webroot
# webroot-path = /usr/share/nginx/html
# Décommentez pour accepter automatiquement les conditions d'utilisation du serveur ACME
# agree-tos = true
# Un exemple d'utilisation d'un serveur ACME alternatif qui utilise des identifiants EAB
# server = https://acme.sectigo.com/v2/InCommonRSAOV
# eab-kid = somestringofstuffwithoutquotes
# eab-hmac-key = yaddayaddahexhexnotquoted

Par défaut, les emplacements suivants sont recherchés :

  • /etc/letsencrypt/cli.ini
  • $XDG_CONFIG_HOME/letsencrypt/cli.ini (ou ~/.config/letsencrypt/cli.ini si $XDG_CONFIG_HOME n'est pas défini).

Étant donné que ce fichier de configuration s'applique à toutes les invocations de certbot, il est incorrect d'y lister des domaines. Lister des domaines dans cli.ini peut empêcher le renouvellement de fonctionner. De plus, en raison de la façon dont les arguments dans cli.ini sont analysés, les options qui ne souhaitent pas être définies ne devraient pas être listées. Les options définies sur false seront plutôt lues comme étant définies sur true par les anciennes versions de Certbot, car elles ont été listées dans le fichier de configuration.

Rotation des journaux

Par défaut, certbot stocke les journaux d'état dans /var/log/letsencrypt. Par défaut, certbot commence à faire pivoter les journaux une fois qu'il y a 1000 journaux dans le répertoire de journaux. Cela signifie qu'une fois que 1000 fichiers se trouvent dans /var/log/letsencrypt, Certbot supprimera le plus ancien pour faire de la place aux nouveaux journaux. Le nombre de journaux suivants peut être modifié en passant le nombre souhaité à l'indicateur de ligne de commande --max-log-backups. Définir cet indicateur sur 0 désactive complètement la rotation des journaux, faisant en sorte que certbot ajoute toujours au même fichier journal.

Note :

Certaines distributions, y compris Debian et Ubuntu, désactivent la rotation interne des journaux de certbot au profit d'un script logrotate plus traditionnel. Si vous utilisez les paquets d'une distribution et que vous souhaitez modifier la rotation des journaux, vérifiez dans /etc/logrotate.d/ un script de rotation certbot.

Architecture de

plugin

Certbot a une architecture de plugin pour faciliter la prise en charge de différents serveurs web, d'autres serveurs TLS et de systèmes d'exploitation. Les interfaces disponibles pour que les plugins les implémentent sont définies dans interfaces.py https://github.com/certbot/certbot/blob/main/certbot/src/certbot/interfaces.py et plugins/common.py https://github.com/certbot/certbot/blob/main/certbot/src/c

ertbot/plugins/common.py#L45.

Les deux principales interfaces de plugin sont Authenticator, qui implémente diverses manières de prouver le contrôle d'un domaine à une autorité de certification, et Installer, qui configure un serveur pour utiliser un certificat une fois qu'il est émis. Certains plugins, comme les plugins Apache et Nginx intégrés, imp

lémentent les deux interfaces et effectuent les deux tâches. D'autres, comme
l'authentificateur Standalone intégré, n'implémentent qu'une seule interface.

Authentificateur

s

Les authentificateurs sont des plugins qui prouvent le contrôle d'un nom de domaine en résolvant un défi fourni par le serveur ACME. ACME définit actuellement deux types de défis : HTTP et DNS, représentés par des classes dans acme.challenges https://acme-python.readthedocs.io/en/latest/api/challenges.html#module-acme.challenges. Un plugin authentificateur doit implémenter la prise en charge d'au moins un type de

défi.

Un Authenticator indique quels défis il prend en charge en implémentant get_chall_pref(domain) pour retourner une liste triée de types de défis par ordre de

préférence.

Un Authenticator doit également implémenter perform(achalls), qui « effectue » une liste de défis en, par exemple, provisionnant un fichier sur un serveur HTTP, ou en définissant un enregistrement TXT dans le DNS. Une fois que tous les défis ont réussi ou échoué, Certbot appellera la méthode cleanup(achalls) du plugin pour supprimer tous les fichiers ou enregistrements DNS qui n'étaient nécessaires que pendant l'authentificati

on
.

    nous prétendons prendre en charge. Les plus anciennes versions des

    dans nos fichiers setup.py pour communiquer cette information à nos

Choisir   les versions des 
dépendances

Lors du choix des versions des dépendances, nous devrions
    choisir les versions minimales qui simplifient le développement de Certbot
    et nos propres méthodes de distribution telles que les snaps, pip et
    docker. Puisque ces approches ont un accès complet à PyPI, c'est acceptable
    si les paquets requis déclarés dans setup.py
    sont assez 
récents.

Si cette approche de développement crée des problèmes importants
    pour certains de nos utilisateurs, nous pouvons reconsidérer cette
    décision et peser leurs difficultés contre les difficultés liées au
    maintien de la prise en charge d'
une gamme plus large de versions de
    paquets. Lorsque nous faisons cela, nous devons également nous assurer de
    considérer la faisabilité pour les utilisateurs d'accéder à ces paquets
    plus récents sur leur système plutôt que de changer 
notre propre approche
    ici. Leur distribution OS pourrait être en mesure de le packager,
    notamment dans un dépôt alternatif et/ou pour une version différente de
    Python afin d'éviter les conflits avec d'autres paquets sur leur système.

COMPATIBILITÉ 
DESCENDANTE

Tous les composants de Certbot, y compris acme
    https://acme-python.readthedocs.io/, Certbot et les plugins non tiers <#plugins> suivent le versionnement sémantique
    https://semver.org/ à la fois pour son API Python <> et pour
    l'application elle-même. Cela signifie que nous ne changerons pas le comportement de manière
    incompatible avec les versions antérieures, sauf dans une nouvelle version majeure du 
projet.

Remarque 
:



Rien de tout cela ne s'applique au comportement des mécanismes de distribution de Certbot
  tels que nos sna
ps <#snap-install> ou les paquets OS
  dont le comportement peut changer à tout moment. Le versionnement séma
ntique ne s'applique qu'aux
  composants communs de Certbot installés par diverses méthodes de distribution.

Pour Certbot en tant qu'application, l'interface en ligne de commande et
    le comportement non interactif peuvent être considérés comme stables, avec deux exceptions. La
    première est qu'aucun aspect de la sortie console ou du journal de Certbot ne doit être
    considéré comme stable et peut changer à tout moment. La seconde est que
    le comportement de Certbot ne doit être considéré comme stable que pour certains fichiers mais
    pas tous. Les fichiers pour lesquels les utilisateurs peuvent s'attendre à ce que Certbot maintienne son
    comportement actuel sont 
:



    
  
  • /etc/letsencrypt/live/$domain/{cert,chain,fullchain,privkey}.pem,
      où $domain est le nom du certificat (voir Où sont mes
      certificats ? <#where-certs> pour plus de 
    • détails)
  
  • Fichiers de configuration CLI 
    • <#config-file>
  
  • Répertoires de hooks dans /etc/letsencrypt/renewal-ho
    • o
k
s

Le comportement de Certbot avec d'autres fichiers peut changer à tout 
moment.

Un autre domaine où Certbot ne doit pas être considéré comme stable est son
    comportement lorsqu'il n'est pas exécuté en mode non interactif, ce qui peut également changer à tout
    
moment.

En général, si nous apportons un changement que nous pensons casser
    certains utilisateurs, nous incrémenterons la version majeure et nous l'aurons signalé dans
    une version précédente lorsque c'est possible. Pour notre API Python, nous émettrons des
    avertissements en utilisant le module warning de Python. Pour les changements au niveau de l'application, nous afficherons
    et journaliserons des messages 
d'avertissement
.
