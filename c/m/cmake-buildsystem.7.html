Débogage d'origine de propriété

Étant donné que les spécifications de construction peuvent être déterminées par les dépendances, le manque de localité du code qui crée une cible et du code responsable de la définition des spécifications de construction peut rendre le code plus difficile à comprendre. cmake(1) <#manual:cmake(1)> fournit une installation de débogage pour imprimer l'origine du contenu des propriétés qui peuvent être déterminées par les dépendances. Les propriétés qui peuvent être déboguées sont répertoriées dans la documentation de la variable CMAKE_DEBUG_TARGET_PROPERTIES <#variable:CMAKE_DEBUG_TARGET_PROPERTIES> :

set(CMAKE_DEBUG_TARGET_PROPERTIES
  INCLUDE_DIRECTORIES
  COMPILE_DEFINITIONS
  POSITION_INDEPENDENT_CODE
  CONTAINER_SIZE_REQUIRED
  LIB_VERSION
)
add_executable(exe1 exe1.cpp)

Dans le cas des propriétés listées dans COMPATIBLE_INTERFACE_BOOL <#prop_tgt:COMPATIBLE_INTERFACE_BOOL> ou COMPATIBLE_INTERFACE_STRING <#prop_tgt:COMPATIBLE_INTERFACE_STRING>, la sortie de débogage montre quelle cible était responsable de la définition de la propriété, et quelles autres dépendances ont également défini la propriété. Dans le cas de COMPATIBLE_INTERFACE_NUMBER_MAX <#prop_tgt:COMPATIBLE_INTERFACE_NUMBER_MAX> et COMPATIBLE_INTERFACE_NUMBER_MIN <#prop_tgt:COMPATIBLE_INTERFACE_NUMBER_MIN>, la sortie de débogage montre la valeur de la propriété de chaque dépendance, et si la valeur détermine le nouveau maximum ou minimum.

Spécification de construction avec expressions génératrices

Les spécifications de construction peuvent utiliser des expressions génératrices <#manual:cmake-generator-expressions(7)> contenant du contenu qui peut être conditionnel ou connu uniquement au moment de la génération. Par exemple, la valeur "compatible" calculée d'une propriété peut être lue avec l'expression TARGET_PROPERTY :

add_library(lib1Version2 SHARED lib1_v2.cpp)
set_property(TARGET lib1Version2 PROPERTY
  INTERFACE_CONTAINER_SIZE_REQUIRED 200)
set_property(TARGET lib1Version2 APPEND PROPERTY
  COMPATIBLE_INTERFACE_NUMBER_MAX CONTAINER_SIZE_REQUIRED
)
add_executable(exe1 exe1.cpp)
target_link_libraries(exe1 lib1Version2)
target_compile_definitions(exe1 PRIVATE
    CONTAINER_SIZE=$<TARGET_PROPERTY:CONTAINER_SIZE_REQUIRED>
)

Dans ce cas, les fichiers source de exe1 seront compilés avec -DCONTAINER_SIZE=200.

L'expression génératrice unaire TARGET_PROPERTY et l'expression génératrice TARGET_POLICY sont évaluées dans le contexte de la cible consommatrice. Cela signifie qu'une spécification d'exigence d'utilisation peut être évaluée différemment en fonction du consommateur :

add_library(lib1 lib1.cpp)
target_compile_definitions(lib1 INTERFACE
  $<$<STREQUAL:$<TARGET_PROPERTY:TYPE>,EXECUTABLE>:LIB1_WITH_EXE>
  $<$<STREQUAL:$<TARGET_PROPERTY:TYPE>,SHARED_LIBRARY>:LIB1_WITH_SHARED_LIB>
  $<$<TARGET_POLICY:CMP0182>:CONSUMER_CMP0182_NEW>
)
add_executable(exe1 exe1.cpp)
target_link_libraries(exe1 lib1)
cmake_policy(SET CMP0182 NEW)
add_library(shared_lib shared_lib.cpp)
target_link_libraries(shared_lib lib1)

L'exécutable exe1 sera compilé avec -DLIB1_WITH_EXE, tandis que la bibliothèque partagée shared_lib sera compilée avec -DLIB1_WITH_SHARED_LIB et -DCONSUMER_CMP0182_NEW, car la politique CMP0182 <#policy:CMP0182> est NEW au moment où la cible shared_lib est créée.

L'expression BUILD_INTERFACE enveloppe les exigences qui ne sont utilisées que lorsqu'elles sont consommées à partir d'une cible dans le même système de construction, ou lorsqu'elles sont consommées à partir d'une cible exportée vers le répertoire de construction à l'aide de la commande export() <#command:export>. L'expression INSTALL_INTERFACE enveloppe les exigences qui ne sont utilisées que lorsqu'elles sont consommées à partir d'une cible qui a été installée et exportée avec la commande install(EXPORT) <#export> :

add_library(ClimbingStats climbingstats.cpp)
target_compile_definitions(ClimbingStats INTERFACE
  $<BUILD_INTERFACE:ClimbingStats_FROM_BUILD_LOCATION>
  $<INSTALL_INTERFACE:ClimbingStats_FROM_INSTALLED_LOCATION>
)
install(TARGETS ClimbingStats EXPORT libExport ${InstallArgs})
install(EXPORT libExport NAMESPACE Upstream::
        DESTINATION lib/cmake/ClimbingStats)
export(EXPORT libExport NAMESPACE Upstream::)
add_executable(exe1 exe1.cpp)
target_link_libraries(exe1 ClimbingStats)

Dans ce cas, l'exécutable exe1 sera compilé avec -DClimbingStats_FROM_BUILD_LOCATION. Les commandes d'exportation génèrent des cibles IMPORTED <#prop_tgt:IMPORTED> avec soit INSTALL_INTERFACE soit BUILD_INTERFACE omis, et le marqueur *_INTERFACE supprimé. Un projet distinct consommant le package ClimbingStats contiendrait :

find_package(ClimbingStats REQUIRED)
add_executable(Downstream main.cpp)
target_link_libraries(Downstream Upstream::ClimbingStats)

Selon que le package ClimbingStats a été utilisé à partir de l'emplacement de construction ou de l'emplacement d'installation, la cible Downstream sera compilée avec soit -DClimbingStats_FROM_BUILD_LOCATION soit -DClimbingStats_FROM_INSTALL_LOCATION. Pour en savoir plus sur les packages et l'exportation, consultez le manuel cmake-packages(7) <#manual:cmake-packages(7)>.

Répertoires d'inclusion et exigences d'utilisation

Les répertoires d'inclusion nécessitent une attention particulière lorsqu'ils sont spécifiés comme exigences d'utilisation et lorsqu'ils sont utilisés avec des expressions génératrices. La commande target_include_directories() <#command:target_include_directories> accepte les répertoires d'inclusion relatifs et absolus :

add_library(lib1 lib1.cpp)
target_include_directories(lib1 PRIVATE
  /absolute/path
  relative/path
)

Les chemins relatifs sont interprétés par rapport au répertoire source où apparaît la commande. Les chemins relatifs ne sont pas autorisés dans INTERFACE_INCLUDE_DIRECTORIES <#prop_tgt:INTERFACE_INCLUDE_DIRECTORIES> des cibles IMPORTED <#prop_tgt:IMPORTED>.

Dans les cas où une expression génératrice non triviale est utilisée, l'expression INSTALL_PREFIX peut être utilisée dans l'argument d'une expression INSTALL_INTERFACE. C'est un marqueur de remplacement qui se développe en préfixe d'installation lorsqu'il est importé par un projet consommateur.

Les exigences d'utilisation des répertoires d'inclusion diffèrent couramment entre l'arbre de construction et l'arbre d'installation. Les expressions BUILD_INTERFACE et INSTALL_INTERFACE peuvent être utilisées pour décrire des exigences d'utilisation distinctes basées sur l'emplacement d'utilisation. Les chemins relatifs sont autorisés dans l'expression INSTALL_INTERFACE et sont interprétés par rapport au préfixe d'installation. Par exemple :

add_library(ClimbingStats climbingstats.cpp)
target_include_directories(ClimbingStats INTERFACE
  $<BUILD_INTERFACE:${CMAKE_CURRENT_BINARY_DIR}/generated>
  $<INSTALL_INTERFACE:/absolute/path>
  $<INSTALL_INTERFACE:relative/path>
  $<INSTALL_INTERFACE:$<INSTALL_PREFIX>/$<CONFIG>/generated>
)

Deux API de commodité sont fournies concernant les exigences d'utilisation des répertoires d'inclusion. La variable CMAKE_INCLUDE_CURRENT_DIR_IN_INTERFACE <#variable:CMAKE_INCLUDE_CURRENT_DIR_IN_INTERFACE> peut être activée, avec un effet équivalent à :

set_property(TARGET tgt APPEND PROPERTY INTERFACE_INCLUDE_DIRECTORIES
  $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR};${CMAKE_CURRENT_BINARY_DIR}>
)

pour chaque cible concernée. La commodité pour les cibles installées est un composant INCLUDES DESTINATION avec la commande install(TARGETS) <#targets> :

install(TARGETS foo bar bat EXPORT tgts ${dest_args}
  INCLUDES DESTINATION include
)
install(EXPORT tgts ${other_args})
install(FILES ${headers} DESTINATION include)

Ceci est équivalent à ajouter ${CMAKE_INSTALL_PREFIX}/include à INTERFACE_INCLUDE_DIRECTORIES <#prop_tgt:INTERFACE_INCLUDE_DIRECTORIES> de chacune des cibles IMPORTED <#prop_tgt:IMPORTED> installées lorsqu'elles sont générées par install(EXPORT) <#export>.

Lorsque INTERFACE_INCLUDE_DIRECTORIES <#prop_tgt:INTERFACE_INCLUDE_DIRECTORIES> d'une cible importée est consommée, les entrées de la propriété peuvent être traitées comme des répertoires d'inclusion système. Les effets de cela dépendent de la chaîne d'outils, mais un effet courant est d'omettre les avertissements du compilateur pour les en-têtes trouvés dans ces répertoires. La propriété SYSTEM <#prop_tgt:SYSTEM> de la cible installée détermine ce comportement (voir la propriété EXPORT_NO_SYSTEM <#prop_tgt:EXPORT_NO_SYSTEM> pour savoir comment modifier la valeur installée pour une cible). Il est également possible de modifier la façon dont les consommateurs interprètent le système

comportement des cibles importées consommées en définissant la NO_SYSTEM_FROM_IMPORTED <#prop_tgt:NO_SYSTEM_FROM_IMPORTED> propriété de la cible sur la cible consommatrice.

Si une cible binaire est liée transitivement à un FRAMEWORK <#prop_tgt:FRAMEWORK> macOS, le répertoire Headers du framework est également traité comme une exigence d'utilisation. Cela a le même effet que de passer le répertoire du framework comme répertoire d'inclusion.

Bibliothèques de liaison et expressions de générateur

Comme les spécifications de construction, les bibliothèques de liaison <#prop_tgt:LINK_LIBRARIES> peuvent être spécifiées avec des conditions d'expression de générateur. Cependant, comme la consommation des exigences d'utilisation est basée sur la collecte à partir des dépendances liées, il y a une limitation supplémentaire : les dépendances de liaison doivent former un « graphe orienté acyclique ». C'est-à-dire que si la liaison à une cible dépend de la valeur d'une propriété de cible, cette propriété de cible ne peut pas dépendre des dépendances liées :

add_library(lib1 lib1.cpp)
add_library(lib2 lib2.cpp)
target_link_libraries(lib1 PUBLIC
  $<$<TARGET_PROPERTY:POSITION_INDEPENDENT_CODE>:lib2>
)
add_library(lib3 lib3.cpp)
set_property(TARGET lib3 PROPERTY INTERFACE_POSITION_INDEPENDENT_CODE ON)
add_executable(exe1 exe1.cpp)
target_link_libraries(exe1 lib1 lib3)

Comme la valeur de la propriété POSITION_INDEPENDENT_CODE <#prop_tgt:POSITION_INDEPENDENT_CODE> de la cible exe1 dépend des bibliothèques liées (lib3), et que l'arête de liaison exe1 est déterminée par la même propriété POSITION_INDEPENDENT_CODE <#prop_tgt:POSITION_INDEPENDENT_CODE> , le graphe de dépendances ci-dessus contient un cycle. cmake(1) <#manual:cmake(1)> émet un message d'erreur.

Artefacts de sortie

Les cibles du système de construction créées par les commandes add_library() <#command:add_library> et add_executable() <#command:add_executable> créent des règles pour produire des sorties binaires. L'emplacement exact de sortie des binaires ne peut être déterminé qu'au moment de la génération car il peut dépendre de la configuration de construction et de la langue de liaison des dépendances liées, etc. TARGET_FILE, TARGET_LINKER_FILE et les expressions associées peuvent être utilisées pour accéder au nom et à l'emplacement des binaires générés. Ces expressions ne fonctionnent pas pour les bibliothèques OBJECT cependant, car aucun fichier unique n'est généré par de telles bibliothèques qui soit pertinent pour les expressions.

Il existe trois types d'artefacts de sortie qui peuvent être construits par les cibles, comme détaillé dans les sections suivantes. Leur classification diffère entre les plateformes DLL et les plateformes non-DLL. Tous les systèmes basés sur Windows, y compris Cygwin, sont des plateformes DLL.

Artefacts de sortie d'exécution

Un artefact de sortie d'exécution d'une cible du système de construction peut être :

  • Le fichier exécutable (par exemple .exe) d'une cible exécutable créée par la commande add_executable() <#command:add_executable>.
  • Sur les plateformes DLL : le fichier exécutable (par exemple .dll) d'une cible de bibliothèque partagée créée par la commande add_library() <#command:add_library> avec l'option SHARED .

Les propriétés de cible RUNTIME_OUTPUT_DIRECTORY <#prop_tgt:RUNTIME_OUTPUT_DIRECTORY> et RUNTIME_OUTPUT_NAME <#prop_tgt:RUNTIME_OUTPUT_NAME> peuvent être utilisées pour contrôler les emplacements et les noms des artefacts de sortie d'exécution dans l'arbre de construction.

Artefacts de sortie de bibliothèque

Un artefact de sortie de bibliothèque d'une cible du système de construction peut être :

  • Le fichier de module chargeable (par exemple .dll ou .so) d'une cible de bibliothèque module créée par la commande add_library() <#command:add_library> avec l'option MODULE .
  • Sur les plateformes non-DLL : le fichier de bibliothèque partagée (par exemple .so ou .dylib) d'une cible de bibliothèque partagée créée par la commande add_library() <#command:add_library> avec l'option SHARED .

Les propriétés de cible LIBRARY_OUTPUT_DIRECTORY <#prop_tgt:LIBRARY_OUTPUT_DIRECTORY> et LIBRARY_OUTPUT_NAME <#prop_tgt:LIBRARY_OUTPUT_NAME> peuvent être utilisées pour contrôler les emplacements et les noms des artefacts de sortie de bibliothèque dans l'arbre de construction.

Artefacts de sortie d'archive

Un artefact de sortie d'archive d'une cible du système de construction peut être :

  • Le fichier de bibliothèque statique (par exemple .lib ou .a) d'une cible de bibliothèque statique créée par la commande add_library() <#command:add_library> avec l'option STATIC .
  • Sur les plateformes DLL : le fichier de bibliothèque d'importation (par exemple .lib) d'une cible de bibliothèque partagée créée par la commande add_library() <#command:add_library> avec l'option SHARED . Ce fichier n'est garanti d'exister que si la bibliothèque exporte au moins un symbole non managé.
  • Sur les plateformes DLL : le fichier de bibliothèque d'importation (par exemple .lib) d'une cible exécutable créée par la commande add_executable() <#command:add_executable> lorsque sa propriété de cible ENABLE_EXPORTS <#prop_tgt:ENABLE_EXPORTS> est définie.
  • Sur AIX : le fichier d'importation du lien (par exemple .imp) d'une cible exécutable créée par la commande add_executable() <#command:add_executable> lorsque sa propriété de cible ENABLE_EXPORTS <#prop_tgt:ENABLE_EXPORTS> est définie.
  • Sur macOS : le fichier d'importation du lien (par exemple .tbd) d'une cible de bibliothèque partagée créée par la commande add_library() <#command:add_library> avec l'option SHARED et lorsque sa propriété de cible ENABLE_EXPORTS <#prop_tgt:ENABLE_EXPORTS> est définie.

Les propriétés de cible ARCHIVE_OUTPUT_DIRECTORY <#prop_tgt:ARCHIVE_OUTPUT_DIRECTORY> et ARCHIVE_OUTPUT_NAME <#prop_tgt:ARCHIVE_OUTPUT_NAME> peuvent être utilisées pour contrôler les emplacements et les noms des artefacts de sortie d'archive dans l'arbre de construction.

Commandes au niveau du répertoire

Les commandes target_include_directories() <#command:target_include_directories>, target_compile_definitions() <#command:target_compile_definitions> et target_compile_options() <#command:target_compile_options> n'ont un effet que sur une seule cible à la fois. Les commandes add_compile_definitions() <#command:add_compile_definitions>, add_compile_options() <#command:add_compile_options> et include_directories() <#command:include_directories> ont une fonction similaire, mais opèrent au niveau du répertoire plutôt qu'au niveau de la cible pour plus de commodité.

CONFIGURATIONS DE CONSTRUCTION

Les configurations déterminent les spécifications pour un certain type de construction, telles que Release ou Debug. La façon dont cela est spécifié dépend du type de générateur <#manual:cmake-generators(7)> utilisé. Pour les générateurs à configuration unique comme les générateurs Makefile <#makefile-generators> et Ninja <#generator:Ninja>, la configuration est spécifiée au moment de la configuration par la variable CMAKE_BUILD_TYPE <#variable:CMAKE_BUILD_TYPE>. Pour les générateurs à configuration multiple comme Visual Studio <#visual-studio-generators>, Xcode <#generator:Xcode>, et Ninja Multi-Config <#generator:Ninja Multi-Config>, la configuration est choisie par l'utilisateur au moment de la construction et CMAKE_BUILD_TYPE <#variable:CMAKE_BUILD_TYPE> est ignorée. Dans le cas à configuration multiple, l'ensemble des configurations disponibles est spécifié au moment de la configuration par la variable CMAKE_CONFIGURATION_TYPES <#variable:CMAKE_CONFIGURATION_TYPES>, mais la configuration réellement utilisée ne peut être connue qu'à l'étape de construction. Cette différence est souvent mal comprise, menant à du code problématique comme le suivant :

# AVERTISSEMENT : Ceci est incorrect pour les générateurs à configuration multiple car ils n'utilisent pas
#          et ne définissent généralement même pas CMAKE_BUILD_TYPE
string(TOLOWER ${CMAKE_BUILD_TYPE} build_type)
if (build_type STREQUAL debug)
  target_compile_definitions(exe1 PRIVATE DEBUG_BUILD)
endif()

Les expressions de générateur <#manual:cmake-generator-expressions(7)> devraient être utilisées à la place pour gérer correctement la logique spécifique à la configuration, quel que soit le générateur utilisé. Par exemple :

# Fonctionne correctement pour les générateurs à configuration unique et multiple
target_compile_definitions(exe1 PRIVATE
  $<$<CONFIG:Debug>:DEBUG_BUILD>
)

En présence de cibles IMPORTED <#prop_tgt:IMPORTED> , le contenu de MAP_IMPORTED_CONFIG_DEBUG <#prop_tgt:MAP_IMPORTED_CONFIG_<CONFIG>> est également pris en compte par l'expression $<CONFIG:Debug> <#genex:CONFIG> ci-dessus.

Sensibilité à la casse

CMAKE_BUILD_TYPE <#variable:CMAKE_BUILD_TYPE> et CMAKE_CONFIGURATION_TYPES <#variable:CMAKE_CONFIGURATION_TYPES> sont comme les autres variables en ce sens que toute comparaison de chaînes effectuée avec leurs valeurs sera sensible à la casse. L'expression de générateur $<CONFIG> <#genex:CONFIG> préserve également la casse de la configuration telle que définie par l'utilisateur ou par les valeurs par défaut de CMake. Par exemple :

# NOTE : N'utilisez pas ces modèles, ils sont à titre d'illustration uniquement.
set(CMAKE_BUILD_TYPE Debug)
if(CMAKE_BUILD_TYPE STREQUAL DEBUG)
  # ... n'atteindra jamais ce point, "Debug" != "DEBUG"
endif()
add_custom_target(print_config ALL
  # Affiche "Config is Debug" dans ce cas à configuration unique
  COMMAND ${CMAKE_COMMAND} -E echo "Config is $<CONFIG>"
  VERBATIM
)
set(CMAKE_CONFIGURATION_TYPES Debug Release)
if(DEBUG IN_LIST CMAKE_CONFIGURATION_TYPES)
  # ... n'atteindra jamais ce point, "Debug" != "DEBUG"
endif()

En revanche, CMake traite le type de configuration de manière insensible à la casse lorsqu'il l'utilise en interne dans des endroits qui modifient le comportement en fonction de la configuration. Par exemple, l'expression $<CONFIG:Debug>b> <#genex:CONFIG> generator expression will evaluate to 1 for a configuration of not only Debug , but also DEBUG , debug or even DeBuG . Therefore, you can specify configuration types in CMAKE_BUILD_TYPE <#variable:CMAKE_BUILD_TYPE> and CMAKE_CONFIGURATION_TYPES <#variable:CMAKE_CONFIGURATION_TYPES> with any mixture of upper and lowercase, although there are strong conventions (see the next section). If you must test the value in string comparisons, always convert the value to upper or lowercase first and adjust the test accordingly.
