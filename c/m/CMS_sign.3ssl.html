DESCRIPTIO

N

CMS_sign_ex() crée et renvoie une structure CMS SignedData. signcert est le certificat à utiliser pour la signature, pkey est la clé privée correspondante. certs est un ensemble facultatif de certificats supplémentaires à inclure dans la structure CMS (par exemple toute autorité de certification intermédiaire dans la chaîne). Le contexte de bibliothèque libctx et la requête de propriété propq sont utilisés lors de la récupération d'algorithmes auprès des fournisseurs. N'importe lequel ou tous ces paramètres peuvent être NULL, voir NOTES ci-de

ssous.

Les données à signer sont lues depuis le BIO data

.

flags est un ensemble facultatif de

drapeaux.

CMS_sign() est similaire à CMS_sign_ex() mais utilise les valeurs par défaut NULL pour le contexte de bibliothèque libctx et la requête de propriété pro

p
q.

NOTE

S

L'un des drapeaux suivants (combinés par ou logique) peut être passé dans le paramètre f

lags.

De nombreux clients S/MIME s'attendent à ce que le contenu signé inclue des en-têtes MIME valides. Si le drapeau CMS_TEXT est défini, des en-têtes MIME de type text/plain sont ajoutés avant les

données.

Si CMS_NOCERTS est défini, le certificat du signataire ne sera pas inclus dans la structure CMS_ContentInfo, mais le certificat du signataire doit tout de même être fourni dans le paramètre signcert. Cela peut réduire la taille de la signature si le certificat du signataire peut être obtenu par d'autres moyens : par exemple un message signé

précédemment.

Les données étant signées sont incluses dans la structure CMS_ContentInfo, sauf si CMS_DETACHED est défini, auquel cas elles sont omises. Cela est utilisé pour les signatures CMS_ContentInfo détachées qui sont utilisées dans les messages signés en texte clair S/MIME par

exemple.

Normalement, le contenu fourni est converti au format canonique MIME (comme requis par les spécifications S/MIME). Si CMS_BINARY est défini, aucune conversion n'a lieu. Cette option doit être utilisée si les données fournies sont au format binaire, sinon la conversion les

corromprait.

La structure SignedData inclut plusieurs signedAttributes CMS, incluant l'heure de signature, le type de contenu CMS et la liste des algorithmes de chiffrement pris en charge dans un attribut SMIMECapabilities. Si CMS_NOATTR est défini, aucun signedAttributes ne sera utilisé du tout. Si CMS_NOSMIMECAP est défini, les SMIMECapabilities seront omis. Si CMS_NO_SIGNING_TIME est défini, l'heure de signature sera

omise.

S'il est présent, l'attribut SMIMECapabilities indique la prise en charge des algorithmes suivants par ordre de préférence : AES 256 bits, Gost R3411-94, Gost 28147-89, AES 192 bits, AES 128 bits, triple DES, RC2 128 bits, RC2 64 bits, DES et RC2 40 bits. Si l'un de ces algorithmes n'est pas disponible, il ne sera pas inclus : par exemple les algorithmes GOST ne seront pas inclus si le moteur GOST n'est pas

chargé.

OpenSSL identifiera par défaut les certificats de signature à l'aide du nom de l'émetteur et du numéro de série. Si CMS_USE_KEYID est défini, il utilisera à la place la valeur de l'identifiant de clé du sujet. Une erreur se produit si le certificat de signature n'a pas d'extension d'identifiant de clé du

sujet.

Si les drapeaux CMS_STREAM sont définis, la structure CMS_ContentInfo renvoyée est simplement initialisée et prête à effectuer l'opération de signature. La signature n'est cependant pas effectuée et les données à signer ne sont pas lues depuis le paramètre data. La signature est différée jusqu'à ce que les données aient été écrites. De cette façon, les données peuvent être signées en une seule

passe.

Si le drapeau CMS_PARTIAL est défini, une structure CMS_ContentInfo partielle est produite à laquelle des signataires et des capacités supplémentaires peuvent être ajoutés avant la

finalisation.

Si le drapeau CMS_STREAM est défini, la structure CMS_ContentInfo renvoyée n'est pas complète et produire son contenu via une fonction qui ne finalise pas correctement la structure CMS_ContentInfo donnera des résultats

imprévisibles.

Plusieurs fonctions, y compris SMIME_write_CMS(), i2d_CMS_bio_stream(), PEM_write_bio_CMS_stream() finalisent la structure. Alternativement, la finalisation peut être effectuée en obtenant le BIO ASN1 en streaming directement via BIO_new_C

MS().

Si un signataire est spécifié, il utilisera le hachage par défaut pour l'algorithme de signature. Il s'agit de SHA256 pour les clés RSA et

DSA.

Si signcert et pkey sont NULL, une structure CMS contenant uniquement des certificats est

produite.

La fonction CMS_sign() est une fonction de signature CMS de base dont la sortie conviendra à de nombreux usages. Pour un contrôle plus fin du format de sortie, les paramètres certs, signcert et pkey peuvent tous être NULL et le drapeau CMS_PARTIAL défini. Puis un ou plusieurs signataires peuvent être ajoutés à l'aide de la fonction CMS_add1_signer(), des hachages non par défaut peuvent être utilisés et des attributs personnalisés ajoutés. CMS_final() doit ensuite être appelée pour finalis

er la structure si le st
reaming n'est pas activé.

HISTORIQU

E

Le drapeau CMS_STREAM n'est pris en charge que pour les données détachées dans OpenSSL 0.9.8, il est pris en charge pour les données intégrées dans OpenSSL 1.0.0 et

ultérieur.

La méthode CMS_sign_ex() a été ajoutée dans OpenSSL 3.

0.

Depuis OpenSSL 3.2, CMS_sign_ex() et CMS_sign() ignorent tout certificat en double dans leur argument certs et ne lèvent

plus d'erreur
pour ceux-ci.
