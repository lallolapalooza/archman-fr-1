Références de

variables

Une référence de variable a la forme ${<variable>} et est évaluée à l'intérieur d'un argument entre guillemets ou d'un argument non entouré de guillemets. Une référence de variable est remplacée par la valeur de la variable spécifiée ou de l'entrée de cache, ou si aucune des deux n'est définie, par la chaîne vide. Les références de variables peuvent être imbriquées et sont évaluées de l'intérieur vers l'extérieur, par exemple ${outer_${inner_variable

}_variable}.

Les références de variables littérales peuvent se composer de caractères alphanumériques, des caractères /_.+-, et des séquences d'échappement. Des références imbriquées peuvent être utilisées pour évaluer des variables de n'importe quel nom. Voir aussi la documentation de la politique CMP0053 <#policy:CMP0053> pour les considérations historiques et les raisons pour lesquelles le $ est aussi techniquement autorisé mais est

déconseillé.

La section Variables documente la portée des noms de variables et la manière dont leurs valeurs sont

définies.

Une référence de variable d'environnement a la forme $ENV{<variable>}. Voir la section Variables d'environnement pour plus

d'informations.

Une référence de variable de cache a la forme $CACHE{<variable>}, et est remplacée par la valeur de l'entrée de cache spécifiée sans vérifier l'existence d'une variable normale du même nom. Si l'entrée de cache n'existe pas, elle est remplacée par la chaîne vide. Voir CACHE <#variable:CACHE> pour plus

d'informations.

La commande if() <#command:if> a une syntaxe de condition spéciale qui permet les références de variables sous la forme courte <variable> au lieu de ${<variable>}. Cependant, les variables d'environnement doivent toujours être référencées sous la forme $ENV{<va

VARIABLE

S

Les variables sont l'unité de stockage de base dans le langage CMake. Leurs valeurs sont toujours de type chaîne de caractères, bien que certaines commandes puissent interpréter les chaînes comme des valeurs d'autres types. La commande set() <#command:set> et la commande unset() <#command:unset> définissent ou suppriment explicitement une variable, mais d'autres commandes ont également des sémantiques qui modifient des variables. Les noms de variables sont sensibles à la casse et peuvent se composer de presque n'importe quel texte, mais nous recommandons de s'en tenir à des noms composés uniquement de caractères alphanumériques plus _ et -

.

Les variables ont une portée dynamique. Chaque variable "définie" ou "supprimée" crée une liaison dans la portée courante

:
Portée de
bloc
La commande block() <#command:block> peut créer une nouvelle portée pour les liaisons de
variables.
Portée de
fonction
Les définitions de commandes créées par la commande function() <#command:function> créent des commandes qui, lorsqu'elles sont invoquées, traitent les commandes enregistrées dans une nouvelle portée de liaison de variable. Une variable "définie" ou "supprimée" est liée dans cette portée et est visible pour la fonction courante et tous les appels imbriqués à l'intérieur de celle-ci, mais pas après le retour de la
fonction.
Portée de
répertoire
Chacun des répertoires dans une arborescence de sources a sa propreable bindings. Avant de traiter le fichier CMakeLists.txt d'un répertoire, CMake copie toutes les liaisons de variables actuellement définies dans le répertoire parent, s'il y en a, pour initialiser la nouvelle portée de répertoire. Les scripts CMake, lorsqu'ils sont traités avec cmake -P <#cmdoption-cmake-P>, lient les variables dans une seule portée de « répertoire ».

Une variable « set » ou « unset » non située

à l'intérieur d'un appel de foncti
on se lie à la portée du répertoire courant.
Cache
persistant
CMake stocke un ensemble distinct de variables « cache », ou « entrées de cache », dont les valeurs persistent sur plusieurs exécutions au sein d'un arbre de build de projet. Les entrées de cache ont une portée de liaison isolée, modifiée uniquement sur demande explicite, par exemple par l'option CACHE de set() <#command:set> et unset() <#comman
d:unset
> co
mmandes.

Lors de l'évaluation des références de variables, CMake recherche d'abord la pile d'appels de fonctions, s'il y en a, pour une liaison, puis revient à la liaison dans la portée du répertoire courant, s'il y en a. Si une liaison « set » est trouvée, sa valeur est utilisée. Si une liaison « unset » est trouvée, ou si aucune liaison n'est trouvée, CMake recherche alors une entrée de cache. Si une entrée de cache est trouvée, sa valeur est utilisée. Sinon, la référence de variable est évaluée à une chaîne vide. La syntaxe $CACHE{VAR} peut être utilisée pour effectuer des recherches directes d'entrées de

cache.

LISTE

S

Bien que toutes les valeurs dans CMake soient stockées sous forme de chaînes, une chaîne peut être traitée comme une liste dans certains contextes, comme lors de l'évaluation d'un Argument non entre guillemets. Dans de tels contextes, une chaîne est divisée en éléments de liste en se séparant sur les caractères ; qui ne suivent pas un nombre inégal de [ et ] caractères et qui ne sont pas immédiatement précédés par un \. La séquence \; ne divise pas une valeur mais est remplacée par ; dans l'élément

résultant.

Une liste d'éléments est représentée sous forme de chaîne en concaténant les éléments séparés par ;. Par exemple, la commande set() <#command:set> stocke plusieurs valeurs dans la variable de destination sous forme de liste

: 
set(srcs a.c b
.c c.c) # déf
init "srcs" à
"a.c;b.c;c.c"

Les listes sont destinées aux cas d'utilisation simples tels qu'une liste de fichiers sources et ne doivent pas être utilisées pour des tâches de traitement de données complexes. La plupart des commandes qui construisent des listes n'échappent pas les caractères ; dans les éléments de liste, aplatissant ainsi les listes imbriquées

: 
set(x a "b;c"
) # définit "
x" à "a;b;c",
pas "a;b\;c"

En général, les listes ne prennent pas en charge les éléments contenant des caractères ; . Pour éviter les problèmes, considérez les conseils suivants

:
  • Les interfaces de nombreuses commandes, variables et propriétés CMake acceptent des listes séparées par des points-virgules. Évitez de passer des listes contenant des éléments avec des points-virgules à ces interfaces, sauf si elles documentent une prise en charge directe ou une manière d'échapper ou d'encoder les
    • points-virgules.
  • Lors de la construction d'une liste, substituez un espace réservé autrement inutilisé pour ; dans les éléments. Puis substituez ; pour l'espace réservé lors du traitement des éléments de liste. Par exemple, le code suivant utilise | à la place des caractères ;
: 
set(mylist a "b|c")
foreach(entry IN
LISTS mylist) string(REPLACE "|"
";" entry "${entry}") # utiliser
"${entry}" normalement endforeach()

L'option LIST_SEPARATOR du module ExternalProject <#module:ExternalProject> est un exemple d'interface construite en utilisant cette

approche.
  • Dans les listes de generator expressions <#manual:cmake-generator-expressions(7)>, utilisez l'expression génératrice $<SEMICOLON> <#genex:SEMICOLON>

  • Dans les appels de commandes, utilisez la syntaxe d'Argument entre guillemets autant que possible. La commande appelée recevra le contenu de l'argument avec les points-virgules préservés. Un Argument non entre guillemets sera divisé sur les
    • points-virgules.
  • Dans les implémentations de function() <#command:function>, évitez ARGV et ARGN, qui ne distinguent pas les points-virgules dans les valeurs de ceux qui séparent les valeurs. Préférez plutôt utiliser des arguments positionnels nommés et les variables ARGC et ARGV#. Lors de l'utilisation de cmake_parse_arguments() <#command:cmake_parse_arguments> pour analyser des arguments, préférez sa signature PARSE_ARGV, qui utilise les variables ARGV#.
