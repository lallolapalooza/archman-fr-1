Création de paquets

relocalisables

Un paquet relocalisable ne doit pas référencer de chemins absolus de fichiers sur la machine où le paquet est construit qui n'existeront pas sur les machines où le paquet peut être

installé.

Les paquets créés par install(EXPORT) <#export> sont conçus pour être relocalisables, en utilisant des chemins relatifs à l'emplacement du paquet lui-même. Lors de la définition de l'interface d'une cible pour EXPORT, gardez à l'esprit que les répertoires d'inclusion doivent être spécifiés comme des chemins relatifs par rapport à CMAKE_INSTALL_PREFIX <#variable:CMAKE_INSTALL_PREFIX>

: 
target_include_directories(tgt INTERFACE
  # Wrong, not rel
ocatable: $<INSTALL_INTERFACE:${CMAKE_INSTALL_PREFIX}/inc
lude/TgtName> ) target_include_directories(tgt INTERFACE
# Ok, relocatable: $<INSTALL_INTERFACE:include/TgtName> )

L'expression de générateur $<INSTALL_PREFIX> <#manual:cmake-generator-expressions(7)> peut être utilisée comme un espace réservé pour le préfixe d'installation sans entraîner un paquet non relocalisable. Cela est nécessaire si des expressions de générateur complexes sont utilisées

: 
target_include_directories(tgt INTERFACE
  # Ok, relocatable:
  $<INSTALL_INTERFACE:$<$<CONFIG:Debug>:$<INSTALL_PREFIX>/include/TgtName>
>
)

Cela s'applique également aux chemins référençant des dépendances externes. Il n'est pas conseillé de remplir des propriétés qui peuvent contenir des chemins, telles que INTERFACE_INCLUDE_DIRECTORIES <#prop_tgt:INTERFACE_INCLUDE_DIRECTORIES> et INTERFACE_LINK_LIBRARIES <#prop_tgt:INTERFACE_LINK_LIBRARIES>, avec des chemins pertinents pour les dépendances. Par exemple, ce code peut ne pas fonctionner correctement pour un paquet relocalisable

: 
target_link_libraries(ClimbingStats INTERFACE
  ${Foo_LIBRARIES} ${Bar_LIBRARIES}
  )
target_include_directories(ClimbingStats INTERFACE
  "$<INSTALL_INTERFACE:${Foo_INCLUDE_DIRS};${Bar_INCLUDE_DIRS}>"
)

Les variables référencées peuvent contenir les chemins absolus vers les bibliothèques et les répertoires d'inclusion tels que trouvés sur la machine où le paquet a été créé. Cela créerait un paquet avec des chemins codés en dur vers les dépendances et non adapté à la

relocalisation.

Idéalement, de telles dépendances devraient être utilisées via leurs propres cibles IMPORTED <#imported-targets> qui ont leurs propres IMPORTED_LOCATION <#prop_tgt:IMPORTED_LOCATION> et leurs propriétés d'exigences d'utilisation telles que INTERFACE_INCLUDE_DIRECTORIES <#prop_tgt:INTERFACE_INCLUDE_DIRECTORIES> remplies de manière appropriée. Ces cibles importées peuvent alors être utilisées avec la commande target_link_libraries() <#command:target_link_libraries> pour ClimbingSt

ats : 
target_link_libr
aries(ClimbingSt

Avec cette approche, le paquet ne référence ses dépendances externes qu'à travers les noms des cibles IMPORTED <#imported-targets>. Lorsqu'un consommateur utilise le paquet installé, le consommateur exécutera les commandes find_package() <#command:find_package> appropriées (via la macro find_dependency décrite ci-dessus) pour trouver les dépendances et remplir les cibles importées avec des chemins appropriés sur leur propre

Registre de paquets

utilisateur

Le registre de paquets utilisateur est stocké dans un emplacement propre à l'utilisateur. La commande export(PACKAGE) <#package> peut être utilisée pour enregistrer un arbre de build de projet dans le registre de paquets utilisateur. CMake ne fournit actuellement aucune interface pour ajouter des arbres d'installation au registre de paquets utilisateur. Propriété du Registre de

Paquets

Les entrées du registre de paquets appartiennent individuellement aux installations de projet qu'elles référencent. Un installateur de paquet est responsable de l'ajout de sa propre entrée et le désinstallateur correspondant est responsable de sa

suppression.

La commande export(PACKAGE) <#package> remplit le registre de paquets utilisateur avec l'emplacement d'un arbre de construction de projet. Les arbres de construction ont tendance à être supprimés par les développeurs et n'ont pas d'événement « désinstallation » qui pourrait déclencher la suppression de leurs entrées. Afin de garder les registres propres, la commande find_package() <#command:find_package> supprime automatiquement les entrées obsolètes qu'elle rencontre si elle dispose de permissions suffisantes. CMake ne fournit aucune interface pour supprimer une entrée référençant un arbre de construction existant une fois que export(PACKAGE) <#package> a été invoqué. Cependant, si le projet supprime son fichi

er de configuration de paquet de l'arbre
de construction, l'entrée référençant l'emp
lacement sera considérée comme obsolète.
