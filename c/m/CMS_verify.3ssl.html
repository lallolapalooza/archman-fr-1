NOM

CMS_verify, CMS_SignedData_verify, CMS_get0_signers - vérifier une structure CMS SignedData

SYNOPSIS

#include <openssl/cms.h>
int CMS_verify(CMS_ContentInfo *cms, STACK_OF(X509) *certs, X509_STORE *store,
               BIO *detached_data, BIO *out, unsigned int flags);
BIO *CMS_SignedData_verify(CMS_SignedData *sd, BIO *detached_data,
                           STACK_OF(X509) *scerts, X509_STORE *store,
                           STACK_OF(X509) *extra, STACK_OF(X509_CRL) *crls,
                           unsigned int flags,
                           OSSL_LIB_CTX *libctx, const char *propq);
STACK_OF(X509) *CMS_get0_signers(CMS_ContentInfo *cms);

DESCRIPTION

CMS_verify() est très similaire à PKCS7_verify(3). Elle vérifie une structure CMS SignedData contenue dans une structure de type CMS_ContentInfo. cms pointe vers la structure CMS_ContentInfo à vérifier. Le paramètre optionnel certs fait référence à un ensemble de certificats dans lequel rechercher les certificats de signature. Il est également utilisé comme source de certificats d'autorité de certification intermédiaires non fiables pour la construction de chaîne. cms peut contenir des certificats d'autorité de certification non fiables supplémentaires qui peuvent être utilisés pour la construction de chaîne ainsi que des listes de révocation de certificats (CRL) qui peuvent être utilisés pour la validation des certificats. store peut être NULL ou pointer vers le magasin de certificats de confiance à utiliser pour la vérification de la chaîne. detached_data fait référence aux données signées si le contenu est détaché de cms. Sinon, detached_data doit être NULL et les données signées doivent être dans cms. Le contenu est écrit dans le BIO out sauf s'il est NULL. flags est un ensemble de drapeaux optionnel qui peut être utilisé pour modifier l'opération.

CMS_SignedData_verify() est comme CMS_verify() sauf qu'elle opère sur une entrée CMS SignedData dans l'argument sd , qu'elle a quelques paramètres supplémentaires décrits ci-dessous, et qu'en cas de succès elle renvoie le contenu vérifié sous forme de BIO mémoire. Le paramètre optionnel extra peut être utilisé pour fournir des certificats d'autorité de certification non fiables qui peuvent être utiles pour la construction de chaîne lors de la validation des certificats. Cette liste de certificats ne doit pas contenir de doublons. Le paramètre optionnel crls peut être utilisé pour fournir des CRL supplémentaires. La liste des CRL ne doit pas non plus contenir de doublons. Les paramètres optionnels contexte de bibliothèque libctx et requête de propriété propq sont utilisés lors de la récupération d'algorithmes auprès des fournisseurs.

CMS_get0_signers() récupère le ou les certificats de signature depuis cms; elle ne peut être appelée qu'après une opération réussie de CMS_verify() ou CMS_SignedData_verify() .

PROCESSUS DE VÉRIFICATION

Normalement, le processus de vérification se déroule comme suit.

Initialement, quelques vérifications de cohérence sont effectuées sur cms. Le type de cms doit être SignedData. Il doit y avoir au moins une signature sur les données et si le contenu est détaché, detached_data ne peut pas être NULL.

Une tentative est faite pour localiser tous les certificats de signature, d'abord en cherchant dans le paramètre certs (s'il n'est pas NULL) puis en cherchant dans les certificats contenus dans la structure cms sauf si CMS_NOINTERN est défini. Si un certificat de signature ne peut pas être localisé, l'opération échoue.

Chaque certificat de signature est vérifié par chaîne en utilisant le but smimesign et en utilisant le magasin de certificats de confiance store s'il est fourni. Tout certificat interne dans le message, qui a pu être ajouté en utilisant CMS_add1_cert(3), est utilisé comme autorité de certification non fiable. Si la vérification des CRL est activée dans store et que CMS_NOCRL n'est pas défini, toute CRL interne, qui a pu être ajoutée en utilisant CMS_add1_crl(3), est utilisée en plus de la tentative de recherche dans store. Si store n'est pas NULL et qu'une vérification de chaîne échoue, un code d'erreur est renvoyé.

Enfin, le contenu signé est lu (et écrit dans out sauf s'il est NULL) et la signature est vérifiée.

Si toutes les signatures sont correctement vérifiées, la fonction réussit.

L'un des drapeaux suivants (combinés par un OU logique) peut être passé dans le paramètre flags pour modifier le comportement de vérification par défaut.

Si CMS_NOINTERN est défini, les certificats dans le message lui-même ne sont pas recherchés lors de la localisation des certificats de signature. Cela signifie que tous les certificats de signature doivent être dans le paramètre certs .

Si CMS_NOCRL est défini et que la vérification des CRL est activée dans store , alors toute CRL dans le message lui-même et fournie via le paramètre crls est ignorée.

Si le drapeau CMS_TEXT est défini, les en-têtes MIME pour le type "text/plain" sont supprimés du contenu. Si le contenu n'est pas de type "text/plain" , une erreur est renvoyée.

Si CMS_NO_SIGNER_CERT_VERIFY est défini, les certificats de signature ne sont pas vérifiés par chaîne, sauf si le drapeau CMS_CADES est également défini.

Si CMS_NO_ATTR_VERIFY est défini, la signature des attributs signés n'est pas vérifiée, sauf si le drapeau CMS_CADES est également défini.

Si CMS_CADES est défini, chaque certificat de signataire est vérifié par rapport à l'extension ESS signingCertificate ou ESS signingCertificateV2 requise dans les attributs signés de la signature.

Si CMS_NO_CONTENT_VERIFY est défini, l'empreinte du contenu n'est pas vérifiée.

REMARQUES

Une application de CMS_NOINTERN est d'accepter uniquement les messages signés par un petit nombre de certificats. Les certificats acceptables seraient passés dans le paramètre certs . Dans ce cas, si le certificat du signataire n'est pas l'un des certificats fournis dans certs , la vérification échouera car le signataire ne peut pas être trouvé.

Dans certains cas, les techniques standard pour rechercher et valider les certificats ne sont pas appropriées : par exemple, une application peut souhaiter rechercher des certificats dans une base de données ou effectuer une vérification personnalisée. Cela peut être réalisé en définissant et en vérifiant manuellement les certificats de signataire à l'aide des utilitaires de données signées.

Il faut faire attention lors de la modification du comportement de vérification par défaut ; par exemple, définir CMS_NO_CONTENT_VERIFY désactivera totalement toute vérification du contenu et tout contenu modifié sera considéré comme valide. Cette combinaison est cependant utile si l'on souhaite simplement écrire le contenu dans out et que sa validité n'est pas considérée comme importante.

La vérification de chaîne devrait à vrai dire être effectuée en utilisant l'heure de signature plutôt que l'heure actuelle. Cependant, comme l'heure de signature est fournie par le signataire, elle ne peut pas être considérée comme fiable sans preuve supplémentaire (comme un horodatage de confiance).

VALEURS RENVOYÉES

CMS_verify() renvoie 1 pour une vérification réussie et 0 si une erreur s'est produite.

CMS_SignedData_verify() renvoie un BIO mémoire contenant le contenu vérifié, ou NULL en cas d'erreur.

CMS_get0_signers() renvoie tous les signataires ou NULL si une erreur s'est produite.

L'erreur peut être obtenue depuis ERR_get_error(3).

ANOMALIES

Le magasin de certificats de confiance n'est pas recherché pour le certificat de signature. Cela est principalement dû aux insuffisances de la fonctionnalité actuelle X509_STORE .

L'absence de traitement en un seul passage signifie que le contenu signé doit entièrement être conservé en mémoire s'il n'est pas détaché.
