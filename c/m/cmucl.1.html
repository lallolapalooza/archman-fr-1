DESCRIPTIO

N

CMU Common Lisp est un environnement de programmation Common Lisp de qualité « industrielle » dans le domaine public. Beaucoup des changements X3J13 ont été incorporés dans CMU CL. Chaque fois que cela a été possible, cela a été fait de manière à permettre de manière transparente l'utilisation de CLtL1 ou du CL ANSI proposé. Probablement les nouvelles fonctionnalités les plus intéressantes pour les utilisateurs sont les fonctions SETF, LOOP et la macro WITH-COMPILATION-UN

IT
.

EXIGENCES

MATÉRIELLES

CMU CL est actuellement disponible pour diverses stations de travail Unix. Voir le

fichier README pour les plateformes actuelles. Au moins 16 mégaoctets de mémoire e
t 25 mégaoctets d'espace disque sont recommandés. Comme d'habitude, plus c'est mieux.

U

:
-
-
Le nouveau compilateur CMU CL (Python) est plus sophistiqué que d'autres compilateurs Common Lisp. Il produit à la fois un meilleur code et est plus facile à
utiliser.
-
-
L'environnement de programmation basé sur l'éditeur Hemlock est mie
ux intégré que les environnements basés sur gnu-emacs. (Bien q

CMU CL a aussi des avantages non techniques significatifs

:
-
-
Il a un bon support local pour les utilisateurs CMU, et est bien intégré avec l' environnement informatique (CS) du
CMU.
-

Il est dans le domaine public, et est libr

FONCTIONNALITÉS DU

COMPILATEUR

Le chapitre « Compilateur avancé » du manuel de l'utilisateur discute en détail des capacités d'optimisation de Python (Voir DOCUMENTATION ci-dessous.) Voici quelques points saillants

:
-
-
Bonne efficacité et vérification des types en même temps. Compiler du code sûr donne au pire une réduction de vitesse de
2x.
-
-
Dans le code sûr, les déclarations de type sont vérifiées, permettant de déboguer les déclarations dans le code sûr. Quand vous passez à la compilation non sûre, vous savez que les déclarations sont
correctes.
-
-
Débogage complet au niveau source du code compilé, incluant l'affichage de l'appel exact qui a causé une
erreur.
-
-
De bonnes notes d'efficacité qui vous disent pourquoi une opération ne peut pas être codée en ligne ou où vous créez des conses numériques, et qui fournissent un contexte source sans
précédent
-
-
La compilation par blocs, l'évaluation partielle
, les fonctions légères et la récursion terminal
e correcte permettent une utilisation à f
aible coût de l'abstraction d'appel de fonction.

SUPPORT DES

TYPES

Note importante : Même des programmes débogués peuvent contenir des erreurs de type qui restent indétectées par d'autres compilateurs. Lorsqu'ils sont compilés avec la vérification des types supprimée à l'aide du compilateur CMU Common Lisp, ces erreurs de type peuvent faire que ces programmes débogués meurent de manière étrange. Si la vérification des types n'est pas supprimée, ces programmes mourront avec une erreur de type

explicite.

La façon la plus visible dont Python diffère des compilateurs Common Lisp précédents est qu'il a une plus grande connaissance des types et une approche différente de la vérification des types. En particulier, Python implémente une vérification des types qui est « avide » et « précise »

:
-
-
Avid dans le sens où la vérification des types est faite immédiatement chaque fois qu'il y a une déclaration, plutôt que d'être retardée jusqu'à ce que la valeur soit réellement utilisée. Par exemple : 
    (let ((x ...))
      (declare (fixnum x))
      ...)
Ici, le type de la valeur initiale de X doit être un FIXNUM ou une erreur sera
signalée.
-
-
Précise dans le sens où le type exact spécifié est vérifié. Par
exemple, si une variable est déclarée de type (integer 3 7),
alors la valeur doit toujours être un entier entre 3 et 7.

Puisque Python fait plus de vérification des types, des programmes qui fonctionnent bien lorsqu' compilés avec d'autres compilateurs peuvent obtenir des erreurs de type lorsqu'ils sont compilés avec Python. Il est important de compiler initialement les programmes avec la politique par défaut (sûre), puis de tester cette version. Si un programme avec une déclaration erronée est compilé avec la vérification des types supprimée (en raison de la réduction de la qualité d'optimisation SAFETY), alors l'erreur de type peut causer des erreurs obscures ou une boucle infinie. Voir la section « Getting Existing Programs to Run » (6.6) dans le chapitre du compilateur du manuel de

l'utilisateur.

CMU CL adhère au nettoyage des types de fonction X3J13, ce qui signifie que les lis

tes de paramètres (lambda-lists) entre guillemets ne sont pas de type FUNCTION, et ne s
ont plus directement appelables. Utilisez COERCE avec le type de résultat FUNCTION.

OPTIMISATIO

N

Python fait de nombreuses optimisations qui sont absentes ou moins générales dans d'autres compilateurs Common Lisp : Récursion terminale correcte, appel de fonction léger, compilation par blocs, inférence de type inter-procédurale, analyse de flux globale, inférence de type dynamique, allocation globale de registres, allocation de nombres sur la pile, optimisation du contrôle, analyse de plage d'entiers, expansion en ligne améliorée, optimisation des valeurs multiples et transformations de source à

source.

L'optimisation et la vérification des types sont contr

ôlées par la déclaration OPTIMIZE. La politique d
e compilation par défaut est sûre au niveau des types.

SUPPORT

NUMÉRIQUE

Python est particulièrement bon pour le calcul numérique

:
-
-
Bon codage en ligne des opérations sur les flottants et les entiers de 32 bits, sans création de conses numériques. Cela inclut toutes les primitives matérielles ROUND, TRUNCATE, COERCE, ainsi que des routines de bibliothèque importantes comme SCALE-FLOAT et DECODE-FLOAT. Les résultats qui ne tiennent pas dans les registres vont sur une pile de nombres
spéciale.
-
-
Support complet pour les flottants simples et doubles IEEE (denorms, +-0,
etc.)
-
-
Dans le code compilé par blocs, les nombres sont passés en tant qu'arguments de fonction et valeurs de retour dans les registres (et sans création de conses numériques.
)
-
-
Les appels aux fonctions de bibliothèque (SIN, ...) sont optimisés en un appel direct à la routine de la bibliothèque C (sans création de conses numériques.) Sur du matériel avec un support direct pour de telles fonctions, ces opérations peuvent facilement être codées en
ligne.
-
-

Des performances sur les grands entiers (bignums) nettement mei

lleures que celles des implémentations commerciales (2x
-4x). Les grands entiers sont implémentés en Lisp à l'aide d'en
tiers de taille mot, vous pouvez donc créer les vôtres.

Les avertissements du compilateur et les notes d'efficacité de Python sont

particulièrement précieux dans le code numérique. Plus de 50 pages du ma
nuel de l'utilisateur décrivent les capacités de Python plus en détail.

LE

DÉBOGUEUR

En plus d'une interface fenêtrée basée sur Motif et d'une interface de ligne de commande basique, le débogueur a aussi plusieurs nouvelles fonctionnalités puissantes

:
-
-
Les commandes "source" et "vsource" affichent la forme source originale *précise* responsable de l'erreur ou de l'appel de fonction en attente. Il n'est plus nécessaire de deviner quel appel à CAR a causé une erreur « not a list
».
-
-
Les variables dans le code compilé peuvent être accessibles par nom, de sorte que le débogueur évalue toujours les formes dans l'environnement lexical du cadre courant. Cet accès aux variables est robuste en présence d'optimisations du compilateur --- bien que des niveaux d'optimisation plus élevés puissent rendre les valeurs des variables indisponibles à certains endroits dans la portée de la variable, le débogueur se trompe toujours du côté de la discrétion, refusant d'afficher des valeurs possiblement
incorrectes.
-
-
Le code compilé peut être pas à pas, s'arrêtant à chaque transfert de
contrôle.
-
-
Intégration avec l'éditeur Hemlock. Dans un esclave, la commande "edit" fait éditer la sou
rce pour la position de code courante. L'éditeur peut aussi envoyer des entrées non en mode
ligne au débogueur en utilisant les liaisons C-M-H. Essayez apropos "debug" dans Hemlock.

Voir le chapitre du débogueur dans le manuel de l'uti

lisateur pour plus de détails. Nous travaillons à
intégrer le débogueur avec Hemlock et les fenêtres X.

L'INTERFACE

GRAPHIQUE

CMU Common Lisp a une interface pour Motif qui est fonctionnellement similaire à CLM, mais fonctionne mieux dans CMU CL. Voir

:

doc/motif-toolkit.doc
doc/moti
f-inter
nals.doc

Cette interface motif aest utilisé pour écrire l'inspecteur et le débogueur graphique. Il existe également un panneau de contrôle Lisp avec une fonctionnalité simple de gestion de fichiers, des boîtes de dialogue apropos et inspecteur, et des commandes pour définir les options

globales.

Appelez INTERFACE:LISP-CONTROL-PANEL pour créer le panneau de contrôle. Lorsque INTERFACE:*INTERFACE-STYLE* est :GRAPHICS (la valeur par défaut) et que

la variable d'environnement DISPLAY est définie, l'inspecteur et le débogueur graphiques seront invoqués par INSPECT ou lorsqu'une erreur est signalée. Les
valeurs possibles sont :GRAPHICS et :TTY. Si la valeur est :GRAPHICS mais qu'il n'y a pas d'affichage X, nous utilisons alors discrètement l'interface TTY.

L'INTERPRÉTEU

R

En ce qui concerne la sémantique de Common Lisp, il n'y a pas d'interpréteur ; c'est effectivement une implémentation exclusivement de compilation. Les formes saisies dans la boucle lire-évaluer-afficher ou transmises à EVAL sont effectivement compilées avant d'être exécutées. Dans l'implémentation, il existe un interpréteur, mais il opère sur la représentation interne produite par la partie frontale du

compilateur.

Il n'est pas recommandé de déboguer des programmes en exécutant l'ensemble du programme en mode interprété, car Python et le débogueur éliminent les principales raisons de débogage à l'aide de l'interpréteur

:
-
-
Le code compilé effectue beaucoup plus de vérifications d'erreurs que le code
interprété.
-
-
Déboguer du code compilé
est aussi facile que déb
oguer du code interprété.

Notez que le débogueur ne prend actuellement pas en charge le pas à pas. De plus, le prétraitement de l'interpréteur fige les définitions de macro en

vigueur au moment où une fonction interprétée est définie. Tant que nous n'implémentons pas le retraitement automatique lorsque les macros sont red
éfinies, il est nécessaire de réévaluer la définition d'une fonction interprétée pour que les nouvelles définitions de macro soient prises en compte.

À PROPOS DU PROJET CMU COMMON

LISP

Organisationnellement, CMU Common Lisp était une petite partie, principalement autonome, du projet de système d'exploitation Mach. Le projet CMU CL était davantage un effort de développement d'outils qu'un projet de recherche. Le projet a commencé sous le nom de Spice Lisp, qui fournissait une implémentation Lisp moderne pour utilisation dans la communauté CMU. CMU CL est en développement continu depuis le début des années 1980 (concurrentement à l'effort de normalisation de Common Lisp.) La plupart des implémenteurs de CMU Common Lisp travaillent maintenant sur l'environnement Gwydion pour Dylan (voir http://legend.gwydion.cs.cmu.edu

:8001/gwydion/.)

CMU CL a été financé par la DARPA dans le cadre du contrat « Research on Parallel Computing » de CMU. Plutôt que de faire de la recherche pure sur les langages de programmation et les environnements, l'accent a été mis sur le développement d'outils de programmation pratiques. Cela a parfois nécessité de nouvelles technologies, mais une grande partie du travail a consisté à créer un environnement Common Lisp qui intègre des fonctionnalités de pointe issues de systèmes existants (à la fois Lisp et non-Lisp.

)

Étant donné que les sources sont librement disponibles, CMU Common Lisp a été porté sur du matériel expérimental et utilisé comme base pour la recherche sur la construction de langages de programmation et d'environnement

s
.
