INTRODUCTIO

N

CMake utilise une chaîne d'outils pour compiler, lier des bibliothèques et créer des archives, ainsi que d'autres tâches pour piloter la construction. Les utilitaires de la chaîne d'outils disponibles sont déterminés par les langages activés. Dans les constructions normales, CMake détermine automatiquement la chaîne d'outils pour les constructions sur l'hôte en se basant sur l'introspection du système et les valeurs par défaut. Dans les scénarios de compilation croisée, un fichier de chaîne d'outils peut être spécifié avec des informations sur les chemins du compilateur et des

utilitaires.

Ajouté dans la version 3.19 : on peut utiliser cmake-presets(7) <#manual:cmake-presets(7)>

pour spécifier des fich

FONCTIONNALITÉS DE LA CHAÎNE

D'OUTILS

CMake fournit la try_compile() <#command:try_compile> commande et des modules tels que CheckSourceCompiles <#module:CheckSourceCompiles>, CheckCXXSymbolExists <#module:CheckCXXSymbolExists> et CheckIncludeFile <#module:CheckIncludeFile> pour tester la capacité et la disponibilité de diverses fonctionnalités de la chaîne d'outils. Ces API testent la chaîne d'outils d'une certaine manière et mettent le résultat en cache afin que le test n'ait pas à être effectué à nouveau la prochaine fois que CMake

s'exécute.

Certaines fonctionnalités de la chaîne d'outils ont une gestion intégrée dans CMake et ne nécessitent pas de tests de compilation. Par exemple, POSITION_INDEPENDENT_CODE <#prop_tgt:POSITION_INDEPENDENT_CODE> permet de spécifier qu'une cible doit être construite en code indépendant de la position, si le compilateur prend en charge cette fonctionnalité. La <LANG>_VISIBILITY_PRESET <#prop_tgt:<LANG>_VISIBILITY_PRESET> et VISIBILITY_INLINES_HIDDEN <#prop_tgt:VISIBILITY_INLINES_HIDDEN> propriétés de cible aj

outent des drapeaux pour une visibilité masqu

COMPILATION

CROISÉE

Si cmake(1) <#manual:cmake(1)> est invoqué avec le paramètre de ligne de commande --toolchain chemin/vers/fichier <#cmdoption-cmake-toolchain> ou -DCMAKE_TOOLCHAIN_FILE=chemin/vers/fichier <#cmdoption-cmake-D>, le fichier sera chargé tôt pour définir les valeurs des compilateurs. La CMAKE_CROSSCOMPILING <#variable:CMAKE_CROSSCOMPILING> variable est définie à true lorsque CMake effectue une compilation

croisée.

Notez que l'utilisation des CMAKE_SOURCE_DIR <#variable:CMAKE_SOURCE_DIR> ou CMAKE_BINARY_DIR <#variable:CMAKE_BINARY_DIR> variables dans un fichier de chaîne d'outils est généralement indésirable. Le fichier de chaîne d'outils est utilisé dans des contextes où ces variables ont des valeurs différentes lorsqu'elles sont utilisées à différents endroits (par exemple, dans le cadre d'un appel à try_compile() <#command:try_compile>). Dans la plupart des cas, où il y a un besoin d'évaluer des chemins dans un fichier de chaîne d'outils, la variable la plus appropriée à utiliser serait CMAKE_CURRENT_LIST_DIR <#variable:CMAKE_CURRENT_LIST_DIR>, car elle a toujours une valeur non ambiguë et

prévisible.

    Processus de construction Android

    Le processus de construction pour Android utilise les variables suivantes pour configurer les compilateurs croisés et les outils du NDK.

    Trouver le NDK ou la chaîne d'outils autonome

    Lors de la configuration de la génération croisée pour Android, CMake recherche le NDK Android ou une chaîne d'outils autonome Android comme suit :

    • Si la variable d'environnement CMAKE_ANDROID_NDK est définie, sa valeur est utilisée comme chemin vers le répertoire racine du NDK Android. Si ce chemin ne pointe pas vers un NDK valide, un diagnostic d'erreur est émis.
    • Sinon, si la variable d'environnement ANDROID_STANDALONE_TOOLCHAIN est définie, elle est utilisée comme valeur de CMAKE_ANDROID_STANDALONE_TOOLCHAIN, et la chaîne d'outils autonome est utilisée.
    • Sinon, un diagnostic d'erreur est émis indiquant que ni le NDK ni la chaîne d'outils autonome n'ont pu être trouvés.

    Ajouté en version 3.20 : Si un NDK Android est sélectionné, son numéro de version est rapporté dans la variable CMAKE_ANDROID_NDK_VERSION.

    Compilation croisée pour Android avec le NDK

    Un fichier toolchain peut configurer les générateurs Makefile <#makefile-generators>, les générateurs Ninja <#ninja-generators> ou les générateurs Visual Studio <#visual-studio-generators> pour cibler Android pour la compilation croisée.

    Configurez l'utilisation d'un NDK Android avec les variables suivantes :

    CMAKE_SYSTEM_NAME <#variable:CMAKE_SYSTEM_NAME>
    Défini sur Android. Doit être spécifié pour activer la compilation croisée pour Android.
    CMAKE_SYSTEM_VERSION <#variable:CMAKE_SYSTEM_VERSION>
    Défini sur le niveau d'API Android. S'il n'est pas spécifié, la valeur est déterminée comme suit :
    • Si la variable CMAKE_ANDROID_API <#variable:CMAKE_ANDROID_API> est définie, sa valeur est utilisée comme niveau d'API.
    • Si la variable CMAKE_SYSROOT <#variable:CMAKE_SYSROOT> est définie, le niveau d'API est détecté à partir de la structure des répertoires du NDK contenant le sysroot.
    • Sinon, le dernier niveau d'API disponible dans le NDK est utilisé.
    CMAKE_ANDROID_ARCH_ABI <#variable:CMAKE_ANDROID_ARCH_ABI>
    Défini sur l'ABI (architecture) Android. S'il n'est pas spécifié, cette variable prendra par défaut le premier ABI pris en charge dans la liste armeabi, armeabi-v7a et arm64-v8a. La variable CMAKE_ANDROID_ARCH <#variable:CMAKE_ANDROID_ARCH> sera calculée automatiquement à partir de CMAKE_ANDROID_ARCH_ABI. Voir également les variables CMAKE_ANDROID_ARM_MODE <#variable:CMAKE_ANDROID_ARM_MODE> et CMAKE_ANDROID_ARM_NEON <#variable:CMAKE_ANDROID_ARM_NEON>.
    CMAKE_ANDROID_NDK <#variable:CMAKE_ANDROID_NDK>
    Défini sur le chemin absolu du répertoire racine du NDK Android. S'il n'est pas spécifié, une valeur par défaut pour cette variable sera choisie comme spécifié ci-dessus.
    CMAKE_ANDROID_NDK_DEPRECATED_HEADERS <#variable:CMAKE_ANDROID_NDK_DEPRECATED_HEADERS>
    Défini sur une valeur vraie pour utiliser les en-têtes obsolètes par niveau d'API au lieu des en-têtes unifiés. S'il n'est pas spécifié, la valeur par défaut sera fausse, sauf si vous utilisez un NDK qui ne fournit pas d'en-têtes unifiés.
    CMAKE_ANDROID_NDK_TOOLCHAIN_VERSION <#variable:CMAKE_ANDROID_NDK_TOOLCHAIN_VERSION>
    Sur NDK r19 ou supérieur, cette variable doit être désactivée ou définie sur clang. Sur NDK r18 ou inférieur, définissez-la sur la version de la chaîne d'outils NDK à sélectionner comme compilateur. S'il n'est pas spécifié, la valeur par défaut sera la dernière chaîne d'outils GCC disponible.
    CMAKE_ANDROID_STL_TYPE <#variable:CMAKE_ANDROID_STL_TYPE>
    Défini pour spécifier quelle bibliothèque standard C++ utiliser. S'il n'est pas spécifié, une valeur par défaut sera sélectionnée comme décrit dans la documentation de la variable.

    Les variables suivantes seront calculées et fournies automatiquement :

    CMAKE_<LANG>_ANDROID_TOOLCHAIN_PREFIX <#variable:CMAKE_<LANG>_ANDROID_TOOLCHAIN_PREFIX>
    Le préfixe du chemin absolu vers les binutils dans la chaîne d'outils NDK.
    CMAKE_<LANG>_ANDROID_TOOLCHAIN_SUFFIX <#variable:CMAKE_<LANG>_ANDROID_TOOLCHAIN_SUFFIX>

    Lorsque la chaîne d'outils autonome cible ARM, définissez éventuellement ceci sur ON pour cibler ARM 32 bits au lieu de Thumb 16 bits. Voir la documentation de la variable pour les détails.
    CMAKE_ANDROID_ARM_NEON <#variable:CMAKE_ANDROID_ARM_NEON>
    Lorsque la chaîne d'outils autonome cible ARM v7, définissez éventuellement ceci sur ON pour cibler les appareils ARM NEON. Voir la documentation de la variable pour les détails.

    Les variables suivantes seront calculées et fournies automatiquement :

    CMAKE_SYSTEM_VERSION <#variable:CMAKE_SYSTEM_VERSION>
    Le niveau d'API Android détecté à partir de la chaîne d'outils autonome.
    CMAKE_ANDROID_ARCH_ABI <#variable:CMAKE_ANDROID_ARCH_ABI>
    L'ABI Android détecté à partir de la chaîne d'outils autonome.
    CMAKE_<LANG>_ANDROID_TOOLCHAIN_PREFIX <#variable:CMAKE_<LANG>_ANDROID_TOOLCHAIN_PREFIX>
    Le préfixe du chemin absolu vers les binutils dans la chaîne d'outils autonome.
    CMAKE_<LANG>_ANDROID_TOOLCHAIN_SUFFIX <#variable:CMAKE_<LANG>_ANDROID_TOOLCHAIN_SUFFIX>
    Le suffixe de la plateforme hôte des binutils dans la chaîne d'outils autonome.

    Par exemple, un fichier toolchain pourrait contenir :

    set(CMAKE_SYSTEM_NAME Android)
set(CMAKE_ANDROID_STANDALONE_TOOLCHAIN /chemin/vers/android-toolchain)

    $ cmake ../src \

Signature de

code

Certains artefacts de build pour les plateformes Apple embarquées nécessitent une signature de code obligatoire. Si le générateur Xcode <#generator:Xcode> est utilisé et que la signature de code est requise ou souhaitée, l'identifiant de l'équipe de développement peut être spécifié via la variable CMake CMAKE_XCODE_ATTRIBUTE_DEVELOPMENT_TEAM. Cet identifiant d'équipe sera alors inclus dans le projet Xcode généré. Par défaut, CMake évite la

nécessité de la signature de code lors de la phase de configuration interne (c
'est-à-dire l'identification du compilateur et la détection des fonctionnalités).

Commutation entre l'appareil et le

simulateur

Lors de la configuration pour l'une des plateformes embarquées, on peut cibler soit de vrais appareils, soit le simulateur. Les deux ont leurs propres SDK distincts, mais CMake ne prend en charge que la spécification d'un seul SDK pour la phase de configuration. Cela signifie que le développeur doit en choisir un ou l'autre au moment de la configuration. Lors de l'utilisation du générateur Xcode <#generator:Xcode>, cette limitation est moins contraignante car Xcode vous permet toujours de compiler pour un appareil ou un simulateur, même si la configuration n'a été effectuée que pour l'un des deux. Depuis l'IDE Xcode, les compilations sont effectuées pour la plateforme "destination" sélectionnée. Lors de la compilation en ligne de commande, le SDK souhaité peut être spécifié directement en passant une option -sdk à l'outil de build sous-jacent (xcodebuild). Par exemple

: 
$ cmake --b
uild ... --
-sdk ipho
nesimulator

Veuillez noter que les vérifications effectuées lors de la configuration l'ont été par rapport au SDK au moment de la configuration et peuvent ne pas s'appliquer à d'autres SDK. Des commandes comme find_package() <#command:find_package>, find_library() <#command:find_library>, etc. stockent et utilisent des détails uniquement pour le SDK/plateforme configuré, elles peuvent donc poser problème si l'on souhaite basculer entre les compilations appareil et simulateur. Vous pouvez suivre les règles suivantes pour faire fonctionner la configuration appareil + simulateur

:
  • Utiliser le drapeau de liaison -l explicite, par ex. target_link_libraries(foo PUBLIC
    • "-lz")
  • Utiliser le drapeau de liaison -framework explicite, par ex. target_link_libraries(foo PUBLIC "-framework
    • CoreFoundation")
  • Utiliser find_package() <#command:find_package> uniquement pour les bibliothèques installées avec la fonctionnalité CMAKE_IOS_INSTALL_COMBIN
