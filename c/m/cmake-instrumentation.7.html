Fichiers Requêtes v1

Tout fichier avec l'extension .json dans le répertoire instrumentation/v1/query/ est reconnu comme une requête de données d'instrumentation.

Ces fichiers doivent contenir un objet JSON avec les clés suivantes. La clé version est requise, mais tous les autres champs sont facultatifs.

version
La version des données du fichier d'extrait à générer, un entier. Actuellement, la seule version prise en charge est 1.
callbacks
Une liste de chaînes de caractères de commandes pour que les rappels traitent les données d'instrumentation collectées. Chaque fois que ces rappels sont exécutés, le chemin complet vers un fichier d'index v1 est ajouté aux arguments inclus dans la chaîne.
hooks
Une liste de chaînes spécifiant quand l'indexation doit se produire automatiquement. Ce sont les intervalles auxquels les données d'instrumentation doivent être compilées et les rappels utilisateur doivent être invoqués pour traiter les données. Les éléments de cette liste doivent être l'un des suivants :
  • postGenerate
  • preBuild (appelé lorsque ninja ou make est invoqué)
  • postBuild (appelé lorsque ninja ou make se termine)
  • preCMakeBuild (appelé lorsque cmake --build est invoqué)
  • postCMakeBuild (appelé lorsque cmake --build se termine)
  • postCMakeInstall
  • postCTest

preBuild et postBuild ne sont pas pris en charge lors de l'utilisation des générateurs MSYS Makefiles <#generator:MSYS Makefiles> ou FASTBuild <#generator:FASTBuild>. De plus, ils ne seront pas déclenchés lorsque l'outil de build est invoqué par cmake --build.

options
Une liste de chaînes utilisées pour activer certains comportements optionnels, y compris la collecte de données supplémentaires. Les éléments de cette liste doivent être l'un des suivants :
staticSystemInformation
Active la collecte d'informations statiques sur la machine hôte sur laquelle CMake est exécuté. Ces données sont collectées lors de l'indexation et sont incluses dans le fichier d'index v1 généré.
dynamicSystemInformation
Active la collecte d'informations dynamiques sur la machine hôte sur laquelle CMake est exécuté. Les données sont collectées pour chaque fichier d'extrait v1 généré par CMake, et incluent des informations immédiatement avant et après l'exécution de la commande.
cdashSubmit
Active l'inclusion de données d'instrumentation dans CDash. Cela n'active pas automatiquement dynamicSystemInformation, mais est par ailleurs équivalent à avoir la variable d'environnement CTEST_USE_INSTRUMENTATION <#envvar:CTEST_USE_INSTRUMENTATION> activée.
cdashVerbose
Active l'inclusion des commandes complètes non tronquées dans les données soumises à CDash. Équivalent à avoir la variable d'environnement CTEST_USE_VERBOSE_INSTRUMENTATION <#envvar:CTEST_USE_VERBOSE_INSTRUMENTATION> activée.
trace
Active la génération d'un fichier de trace Google lors de l'indexation pour visualiser les données des fichiers d'extrait v1 collectés.

Les callbacks listés seront invoqués lors des hooks spécifiés, au minimum. Lorsqu'il y a plusieurs fichiers de requête, les callbacks, hooks et options entre eux seront fusionnés. Par conséquent, si un fichier de requête inclut des hooks, chaque callback de tous les fichiers de requête sera exécuté à chaque hook de tous les fichiers de requête. De plus, si un fichier de requête demande des données optionnelles en utilisant le champ options, les données associées seront présentes dans tous les fichiers d'extrait. Les callbacks écrits par l'utilisateur devraient être capables de gérer la présence de ces données optionnelles, car elles peuvent être demandées par une requête sans rapport.

Exemple :

{
  "version": 1,
  "callbacks": [
    "/usr/bin/python callback.py",
    "/usr/bin/cmake -P callback.cmake arg",
  ],
  "hooks": [
    "postCMakeBuild",
    "postCMakeInstall"
  ],
  "options": [
    "staticSystemInformation",
    "dynamicSystemInformation",
    "cdashSubmit",
    "trace"
  ]
}

Dans cet exemple, après chaque invocation de cmake --build ou cmake --install, un fichier d'index index-<timestamp>.json sera généré dans <build>/.cmake/instrumentation/v1/data/index contenant une liste de fichiers de données d'extrait créés depuis la précédente indexation. Les commandes /usr/bin/python callback.py index-<timestamp>.json et /usr/bin/cmake -P callback.cmake arg index-<timestamp>.json seront exécutées dans cet ordre. Le fichier d'index contiendra les données staticSystemInformation et chaque fichier d'extrait répertorié dans l'index contiendra les données dynamicSystemInformation. De plus, le fichier d'index contiendra le chemin vers le fichier de trace Google généré. Une fois que les deux rappels auront terminé, le fichier d'index et les fichiers de données qu'il répertorie (y compris les fichiers d'extrait, mais pas le fichier de trace) seront supprimés de l'arborescence de build du projet. Les données d'instrumentation seront présentes dans les fichiers XML soumis à CDash, mais avec des chaînes de commandes tronquées car cdashVerbose n'a pas été activé.

DONNÉES V1

La version des données spécifie le contenu des fichiers de sortie générés par l'API d'instrumentation CMake dans le cadre de la collecte et de l'indexation des données. Un nouveau numéro de version sera créé chaque fois que des données précédemment incluses seront supprimées ou reformatées de telle sorte que les scripts écrits pour analyser ces données puissent devenir incompatibles avec le nouveau format. Il existe quatre types de fichiers de données générés : le fichier d'extrait v1, le fichier d'index v1, le fichier de contenu CMake v1 et le fichier de trace Google. Lors de l'utilisation de l'API v1, ces fichiers se trouvent dans <build>/.cmake/instrumentation/v1/data/ sous l'arborescence de build du projet.

Fichier Extrait v1

Les fichiers d'extrait sont générés pour chaque commande de compilation, de liaison et personnalisée invoquée dans le cadre de l'étape de build ou d'installation de CMake et contiennent des données d'instrumentation sur la commande exécutée. De plus, des fichiers d'extrait sont créés pour les éléments suivants :

  • L'étape de configuration de CMake
  • L'étape de génération de CMake
  • L'étape de build complète (exécutée avec cmake --build)
  • L'étape d'installation complète (exécutée avec cmake --install)
  • Chaque invocation de ctest
  • Chaque test individuel exécuté par ctest.

Ces fichiers restent dans l'arborescence de build jusqu'à ce que l'indexation ait lieu et que tous les rappels spécifiés par l'utilisateur soient exécutés.

  • generate : l'étape de génération de CMake

  • link : une étape de liaison individuelle invoquée pendant le build
  • custom : une commande personnalisée individuelle invoquée pendant le build
  • build : une invocation complète de make ou ninja (pas via cmake --build).
  • cmakeBuild : une invocation complète de cmake --build
  • cmakeInstall : une invocation complète de cmake --install

  • test : un seul test exécuté par CTest
