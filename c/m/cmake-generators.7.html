INTRODUCTIO

N

Un générateur CMake est responsable de l'écriture des fichiers d'entrée pour un système de build natif. Exactement un des générateurs CMake doit être sélectionné pour un arbre de build afin de déterminer quel système de build natif doit être utilisé. En option, l'un des générateurs supplémentaires peut être sélectionné comme variante de certains générateurs d'outil de build en ligne de commande pour produire des fichiers de projet pour un IDE

auxiliaire.

Les générateurs CMake sont spécifiques à la plateforme, chacun n'étant donc disponible que sur certaines plateformes. La commande en ligne de commande cmake(1) <#manual:cmake(1)> --help <#cmdoption-cmake-h> liste les générateurs disponibles sur la plateforme actuelle. Utilisez son -G <#cmdoption-cmake-G> option pour spécifier le générateur pour un nouvel arbre de build. La cmake-gui(1) <#manual:cmake-gui(1)> offre une sélection interactiv

e d'un générateur lors de la cré
ation d'un nouvel arbre de build.

Ninja

Multi-Config

Ajouté dans la version 3.

17.

Génère plusieurs fichiers build-<Config>

.ninja.

Ce générateur est très semblable au générateur Ninja <#generator:Ninja>, mais avec quelques différences clés. Seules ces différences seront discutées dans ce

document.

Contrairement au générateur Ninja <#generator:Ninja>, Ninja Multi-Config génère plusieurs configurations à la fois avec CMAKE_CONFIGURATION_TYPES <#variable:CMAKE_CONFIGURATION_TYPES> au lieu d'une seule configuration avec CMAKE_BUILD_TYPE <#variable:CMAKE_BUILD_TYPE>. Un build-<Config>.ninja fichier sera généré pour chacune de ces configurations (avec <Config> étant le nom de la configuration.) Ces fichiers sont destinés à être exécutés avec ninja -f build-<Config>.ninja. Un fichier build.ninja est également généré, utilisant la configuration issue de soit CMAKE_DEFAULT_BUILD_TYPE <#variable:CMAKE_DEFAULT_BUILD_TYPE> ou le premier élément de CMAKE_CONFIGURATION_TYPES <#variable:CMAKE_CONFIGURATION_TYPES>

.

cmake --build . --config <Config> utilisera toujours build-<Config>.ninja pour construire. Si aucun --config <#cmdoption-cmake-build-config> argument n'est spécifié, cmake --build . <#cmdoption-cmake-build> utilisera build.ni

nja.

Chaque fichier build-<Config>.ninja contient <target> cibles ainsi que <target>:<Config> cibles, où <Config> est le même que la configuration spécifiée dans build-<Config>.ninja De plus, si le mode cross-config est activé, build-<Config>.ninja peut contenir <target>:<OtherConfig> cibles, où <OtherConfig> est un cross-config, ainsi que <target>:all, qui construit la cible dans tous les cross-configs. Voir ci-dessous pour savoir comment activer le mode

cross-config.

GS>
Spécifie une liste séparée par des points-virgules <#cmake-language-lists> de configurations disponibles depuis tous les fichiers build-<Config>.
ninja.

Commandes

personnalisées

Ajouté dans la version 3.

20.

Le générateur Ninja Multi-Config ajoute des fonctionnalités supplémentaires à add_custom_command() <#command:add_custom_command> et add_custom_target() <#command:add_custom_target> à travers son mode cross-config. Les arguments COMMAND, DEPENDS et WORKING_DIRECTORY peuvent être évalués dans le contexte soit de la « config de commande » (la configuration « native » du fichier build-<Config>.ninja en cours d'utilisation) soit de la « config de sortie » (la configuration utilisée pour évaluer le OUTPUT et BYPRODUC

TS).

Si soit OUTPUT soit BYPRODUCTS nomme un chemin qui est commun à plus d'une configuration (par ex. il n'utilise aucune expression de générateur), tous les arguments sont évalués dans la config de commande par défaut. Si tous les chemins OUTPUT et BYPRODUCTS sont uniques à chaque configuration (par ex. en utilisant l'expression de générateur $<CONFIG> <#genex:CONFIG>), le premier argument de COMMAND est toujours évalué dans la config de commande par défaut, tandis que tous les arguments suivants, ainsi que les arguments de DEPENDS et WORKING_DIRECTORY, sont évalués dans la config de sortie. Ces valeurs par défaut peuvent être remplacées avec les expressions de générateur $<OUTPUT_CONFIG:...> <#genex:OUTPUT_CONFIG> et $<COMMAND_CONFIG:...> <#genex:COMMAND_CONFIG>. Notez que si une cible est spécifiée par son nom dans DEPENDS, ou comme premier argument de COMMAND, elle est toujours évaluée dans la config de commande, même si elle est enveloppée dans $<OUTPUT_CONFIG:...> <#genex:OUTPUT_CONFIG> (car son nom simple n'est pas une expression de générateur)

.

À titre d'exemple, considérons ce qui suit

: 
add_custom_command(
  OUTPUT "$<CONFIG>.txt"
  COMMAND
    generator "$<CONFIG>.txt"
              "$<OUTPUT_CONFIG:$<CONFIG>>"
              "$<COMMAND_CONFIG:$<CONFIG>>"
  DEPENDS
    tgt1
    "$<TARGET_FILE:tgt2>"
    "$<OUTPUT_CONFIG:$<TARGET_FILE:tgt3>>"
    "$<COMMAND_CONFIG:$<TARGET_FILE:tgt4>>"
)

Supposez que generator, tgt1, tgt2, tgt3 et tgt4 sont toutes des cibles exécutables, et supposez que $<CONFIG>.txt est construit dans la config de sortie Debug en utilisant la config de commande Release. La version Release de la cible generator est appelée avec Debug.txt Debug Release comme arguments. La commande dépend des versions Release de tgt1 et tgt4, et des versions Debug de tgt2 et tgt3

.

Les commandes personnalisées PRE_BUILD, PRE_LINK et POST_BUILD pour les cibles ne sont exécutées que dans leur configuration « native » (la configuration Release dans le fichier build-Release.ninja) sauf si elles n'ont pas de BYPRODUCTS ou si leurs BYPRODUCTS sont uniques par config. Considérons l'exemple suivant

: 
add_executable(exe main.c)
add_custom_command(
  TARGET exe
  POST_BUILD
  COMMAND
    ${CMAKE_COMMAND} -E echo "Running no-byproduct command"
  )
add_custom_command(
  TARGET exe
  POST_BUILD
  COMMAND
    ${CMAKE_COMMAND} -E echo
    "Running separate-byproduct command for $<CONFIG>"
  BYPRODUCTS $<CONFIG>.txt
  )
add_custom_command(
  TARGET exe
  POST_BUILD
  COMMAND
    ${CMAKE_COMMAND} -E echo
    "Running common-byproduct command for $<CONFIG>"
  BYPRODUCTS exe.txt
)

Dans cet exemple, si vous construisez exe:Debug dans build-Release.ninja, la première et la deuxième commandes personnalisées sont exécutées, car leurs sous-produits sont uniques par config, mais la dernière commande personnalisée ne l'est pas. Cependant, si vous construisez exe:Release dans build-Release.ninja, les trois comma

ndes personnalisé
es sont exécutées.

NAME

cmake-generators - CMake Project Generators

INTRODUCTION

CMake supports multiple native build system generators. When CMake is run with the cmake command, it uses a generator to create the build files for a specific native build system. Some generators are multi-configuration and support building projects in multiple configurations (e.g., Debug, Release) from a single build tree. Others are single-configuration and generate build files for a specific build configuration.

The list of available generators can be found by running cmake with the --help --help option.

Generators are specified by name, for example:

cmake -G Ninja ..

The cmake command line tool cmake may be used to create build files for a native build system. The --help --help option of the cmake(1) command-line tool lists all available generators.

The generators have a name and an optional platform name, e.g. Ninja, Unix Makefiles, Visual Studio 10, Green Hills MULTI, etc.

Generators may also specify an extra generator for an auxiliary IDE tool. Such generator names have the form <extra-generator> - <main-generator>.

Support for cmake Generators EXTRA GENERATORS is deprecated and will be removed from a future version of CMake. IDEs may use the cmake-file-api(7) cmake-file-api(7) to view CMake-generated project build trees.
