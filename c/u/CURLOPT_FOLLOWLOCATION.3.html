CURLOPT_FOLLOWLOCATION(3) Manuel des fonctions de bibliothèque CURLOPT_FOLLOWLOCATION(3)

NOM

CURLOPT_FOLLOWLOCATION - suivre les redirections HTTP 3xx

SYNOPSIS

#include <curl/curl.h>
CURLcode curl_easy_setopt(CURL *handle, CURLOPT_FOLLOWLOCATION, long mode);

DESCRIPTION

Cette option indique à la bibliothèque de suivre les redirections Location: en-tête qu'un serveur HTTP envoie dans une réponse 30x. L'en-tête Location: peut spécifier une URL relative ou absolue à suivre. Le paramètre long mode mode indique comment libcurl doit se comporter pour les requêtes suivantes.

mode n'avait pendant longtemps qu'une seule valeur (1L) qui active le suivi des redirections. Depuis la version 8.13.0, deux modes supplémentaires sont également pris en charge. Voir ci-dessous.

Lors du suivi des redirections, libcurl émet une autre requête pour la nouvelle URL et suit les nouvelles redirections Location: successives jusqu'à ce que plus d'un tel en-tête soit renvoyé ou que la limite maximale soit atteinte. CURLOPT_MAXREDIRS(3) est utilisé pour limiter le nombre de redirections que libcurl suit.

libcurl restreint les protocoles pour lesquels il suit automatiquement les redirections. Les protocoles cibles acceptés sont définis avec CURLOPT_REDIR_PROTOCOLS_STR(3). Par défaut, libcurl autorise HTTP, HTTPS, FTP et FTPS pour les redirections.

Lors du suivi d'une redirection, le code de réponse 30x spécifique détermine également la méthode de requête que libcurl utilise pour la requête suivante : pour les réponses 301, 302 et 303, libcurl passe de la méthode POST à GET, sauf si CURLOPT_POSTREDIR(3) indique le contraire à libcurl. Tous les autres codes de réponse de redirection font que libcurl utilise à nouveau la même méthode.

Lorsque libcurl passe à la méthode GET, il utilise alors cette méthode sans envoyer de corps de requête. S'il ne change pas de méthode, il envoie la requête suivante de la même manière que la précédente ; y compris le corps de requête si un tel corps a été fourni.

Pour les utilisateurs qui trouvent le suivi de localisation existant trop naïf, trop simple ou simplement dépourvu de fonctionnalités, il est facile d'implémenter votre propre logique de suivi de redirection à l'aide de curl_easy_getinfo(3)'s CURLINFO_REDIRECT_URL(3) option au lieu d'utiliser CURLOPT_FOLLOWLOCATION(3).

Par défaut, libcurl n'envoie que les en-têtes Authentication: ou explicitement définis Cookie: à l'hôte initial donné dans l' URL originale, afin d'éviter de divulguer le nom d'utilisateur + mot de passe à d'autres sites. CURLOPT_UNRESTRICTED_AUTH(3) est fourni pour changer ce comportement.

En raison du fonctionnement d'HTTP, presque n'importe quel en-tête peut contenir des données qu'un client ne voudrait peut-être pas transmettre à d'autres serveurs qu'à l'hôte initialement prévu, et pour tous les autres en-têtes que les deux mentionnés ci-dessus, il n'y a aucune protection contre cela lorsque libcurl est invité à suivre les redirections.

Choisissez l'un des modes suivants :

CURLFOLLOW_ALL (1)
Avant la version 8.13.0, ce bit n'avait pas de nom et 1L était simplement la valeur pour activer cette option. Cela fait que la méthode personnalisée définie est utilisée dans toutes les requêtes HTTP, même après les redirections.
CURLFOLLOW_OBEYCODE (2)
Lorsqu'une méthode de requête personnalisée est définie avec CURLOPT_CUSTOMREQUEST(3), cette méthode définie remplace celle que libcurl utiliserait autrement. Si un code de réponse 301/302/303 est renvoyé pour signaler une redirection, la méthode est changée de POST à GET. Pour 307/308, la méthode personnalisée reste définie et utilisée.

Notez que seule POST (ou un post personnalisé) est changée en GET sur 301/302, PUT etc. n'est pas changé - et donc pas non plus lorsque libcurl émet un PUT personnalisé. Une réponse 303 le fait passer à GET indépendamment de la méthode d'origine (sauf pour HEAD).

Pour contrôler pour lesquels des codes d'état 301/302/303 libcurl ne doit pas revenir à GET lors d'un POST personnalisé, et à la place conserver la méthode personnalisée, utilisez CURLOPT_POSTREDIR(3).

Si vous préférez qu'une méthode POST personnalisée soit réinitialisée à exactement la méthode POST, utilisez CURLFOLLOW_FIRSTONLY à la place.

CURLFOLLOW_FIRSTONLY (3)
Lorsqu'une méthode de requête personnalisée est définie avec CURLOPT_CUSTOMREQUEST(3), cette méthode définie remplace celle que libcurl utiliserait autrement uniquement pour la première requête sortante. La deuxième requête est alors effectuée en fonction du code de réponse de redirection.

Si vous préférez que votre méthode personnalisée reste utilisée après une redirection 307/308, utilisez CURLFOLLOW_OBEYCODE à la place.

NOTE

Puisque libcurl change de méthode ou non en fonction du code de réponse HTTP spécifique, définir CURLOPT_CUSTOMREQUEST(3) lors du suivi des redirections peut changer ce que libcurl ferait autrement et, si ce n'est pas fait soigneusement, peut même le faire se comporter de manière incorrecte, car CURLOPT_CUSTOMREQUEST(3) remplace la méthode que libcurl sélectionnerait autrement en interne.

Définir le bit CURLFOLLOW_OBEYCODE fait que libcurl n'utilise pas la méthode personnalisée définie après les redirections pour les réponses 301, 302 et 303. Sauf si les bits CURLOPT_POSTREDIR(3) sont définis pour ces codes d'état.

PAR DÉFAUT

0, désactivé

PROTOCOLES

Cette fonctionnalité n'affecte que http

EXEMPLE

int main(void)
{
  CURL *curl = curl_easy_init();
  if(curl) {
    curl_easy_setopt(curl, CURLOPT_URL, "https://example.com");
    /* example.com is redirected, so we tell libcurl to follow redirection */
    curl_easy_setopt(curl, CURLOPT_FOLLOWLOCATION, 1L);
    curl_easy_perform(curl);
  }
}

DISPONIBILITÉ

Ajouté dans curl 7.1

VALEUR DE RETOUR

curl_easy_setopt(3) renvoie un CURLcode indiquant le succès ou une erreur.

CURLE_OK (0) signifie que tout s'est bien passé, une valeur non nulle signifie qu'une erreur s'est produite, voir libcurl-errors(3).

VOIR AUSSI
