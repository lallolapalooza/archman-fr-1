DESCRIPTIO

N

CUnit est un système pour écrire, administrer et exécuter des tests unitaires en C. Il utilise un framework simple

pour construire des structures de test et fournit un ensemble riche d'assertions pour tester les types de do
nnées courants. CUnit est construit comme une bibliothèque statique qui est liée au code de test de l'utilisateur.

STRUCTURE ET UTILISATION

GÉNÉRALE

CUnit est une combinaison d'un framework indépendant de la plateforme avec diverses interfaces utilisateur. Le framework central fournit un support de base pour gérer un registre de tests, des suites et des cas de test. Les interfaces utilisateur facilitent l'interaction avec le framework pour exécuter des tests et voir les

résultats.

L'organisation hiérarchique de base de CUnit est illustrée ici

:


Registre de tests
|
-----------------------------
| |
Suite '1' . . . . Suite 'N'
| |
--------------- ---------------
| | | |
Test '11' ... Test '1M' Test 'N1' ... Test 'NM'

Les cas de test individuels sont regroupés en suites, qui sont enregistrées auprès du registre de tests actif. Les suites peuvent avoir des fonctions d'initialisation et de nettoyage qui sont automatiquement appelées avant et après l'exécution des tests de la suite. Toutes les suites/tests du registre peuvent être exécutées à l'aide d'un seul appel de fonction, ou des suites ou tests sélectionnés peuvent être

exécutés.

L'utilisation typique de CUnit est

:

1. Écrire des fonctions pour les tests (et l'initialisation/le nettoyage de la suite si nécessaire)

.

2. Initialiser le registre de tests en utilisant CU_initialize_registry(

3. Ajouter des suites de test au registre en utilisant CU_add_suite(

Tous les noms publics dans CUnit sont préfixés par 'CU_'. Cela aide à minimiser les conflits avec les noms du code utilisateur. Notez que les versions antérieures de CUnit utilisaient des noms différents sans ce préfixe. Les anciens noms d'API sont obsolètes mais toujours pris en charge. Pour utiliser les anciens noms, le code utilisateur doit maintenant être compilé avec USE_DEPRECATED_CU

ÉCRIRE DES FONCTIONS DE

TEST

Un « test » est une fonction C ayant la signature : void test_func(void). Il n'y a aucune restriction sur le contenu d'une fonction de test, sauf qu'elle ne doit pas modifier le framework CUnit (p. ex. ajouter des suites ou des tests, modifier le registre de tests, ou lancer un test). Une fonction de test peut appeler d'autres fonctions (qui ne doivent pas non plus modifier le framework). Enregistrer un test entraînera l'exécution de sa fonction lorsque le test est

exécuté.

CUnit fournit un ensemble d'assertions pour tester des conditions logiques. Le succès ou l'échec de ces assertions est suivi par le framework et peut être consulté lorsqu'une exécution de test est terminée. Chaque assertion teste une seule condition logique et échoue si la condition s'évalue à CU_FALSE. En cas d'échec, le test continue à moins que l'utilisateur ne choisisse la version 'xxx_FATAL' d'une assertion. Dans ce cas, la fonction de test retourne

immédiatement.

CUnit fournit un ensemble d'assertions pour tester des conditions logiques. Le succès ou l'échec de ces assertions est suivi par le framework et peut être consulté lorsqu'une exécution de test est

terminée.

Chaque assertion teste une seule condition logique et échoue si la condition s'évalue à CU_FALSE. En cas d'échec, la fonction de test continue à moins que l'utilisateur ne choisisse la version 'xxx_FATAL' d'une assertion. Dans ce cas, la fonction de test est interrompue et retourne immédiatement. Les versions FATAL des assertions doivent être utilisées avec prudence ! Il n'y a aucune possibilité pour la fonction de test de se nettoyer après elle-même une fois qu'une assertion FATAL a échoué. La fonction de nettoyage normale de la suite n'est pas affectée,

cependant.

Il existe aussi des « assertions » spéciales pour enregistrer un succès ou un échec auprès du framework sans effectuer de test logique. Elles sont utiles pour tester le flux de contrôle ou d'autres conditions ne nécessitant pas de test

logique.

Les autres fonctions appelées par une fonction de test enregistrée peuvent utiliser librement les assertions CUnit. Ces assertions seront comptées pour la fonction appelante. Elles peuvent aussi utiliser les versions FATAL des assertions - un échec interrompra la fonction de test originale et toute sa chaîne

d'appels.

EXÉCUTION DES

TESTS

CUnit prend en charge l'exécution de tous les tests dans toutes les suites enregistrées, mais des tests ou des suites individuels peuvent également être exécutés. Pendant chaque exécution, le framework garde une trace du nombre de suites, de tests et d'assertions exécutées, réussies et échouées. Notez que les résultats précédents sont effacés chaque fois qu'une exécution de test est initiée (même si elle échoue)

.

Bien que CUnit fournisse des fonctions primitives pour exécuter des suites et des tests, la plupart des utilisateurs voudront utiliser l'une des interfaces utilisateur. Ces interfaces gèrent les détails de l'interaction avec le framework et fournissent la sortie des détails et des résultats des tests pour l'utilisateur. Pour plus d'informations sur les fonctions primitives, voir <CUnit/testRun.h>

.

L'interface automatisée est non-interactive. L'implémentation actuelle ne prend en charge que l'exécution de toutes les suites enregistrées. Les résultats sont écrits dans un fichier xml à visualiser par des outils externes appropriés. Les tests enregistrés peuvent également être listés dans un fichier xml pour visualisation. Actions

d'Erreur

Par défaut, CUnit continue l'exécution des tests lorsqu'une erreur du cadre de travail se produit. Dans ce contexte, les assertions échouées ne sont pas considérées comme des « erreurs du cadre de travail ». Toutes les autres conditions d'erreur, y compris les échecs d'initialisation ou de nettoyage des suites, les suites ou tests inactifs qui sont exécutés explicitement, etc., sont incluses. Cette « action d'erreur » peut être modifiée par l'utilisateur si souhaité. Les fonctions suivantes sont fournies
