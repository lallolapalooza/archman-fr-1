La directive
BrowsePoll interroge un serveur pour les imprimantes disponibles toutes les 60 secondes. Plusieurs directives BrowsePoll peuvent être spécifiées pour interroger plusieurs serveurs. Le port par défaut de connexion est le 631. 
        BrowsePoll 192.168.7.20
        BrowsePoll 192.168.7.65:631
        BrowsePoll host.example.com:631
La directive
BrowseLocalProtocols spécifie les protocoles à utiliser pour annoncer les imprimantes partagées locales sur le réseau. La valeur par défaut est "none". Le contrôle de l'annonce des imprimantes partagées locales via dnssd est effectué par CUPS et configuré dans /etc/cups/cupsd.conf. 
        BrowseLocalProtocols none
La directive
BrowseRemoteProtocols spécifie les protocoles à utiliser pour trouver les imprimantes partagées distantes sur le réseau. Plusieurs protocoles peuvent être spécifiés en les séparant par des espaces. La valeur par défaut est "dnssd". 
        BrowseRemoteProtocols none
        BrowseRemoteProtocols dnssd
La directive
BrowseProtocols spécifie les protocoles à utiliser pour trouver les imprimantes partagées distantes sur le réseau et annoncer les imprimantes partagées locales. Plusieurs protocoles peuvent être spécifiés en les séparant par des espaces. 
        BrowseProtocols none
        BrowseProtocols dnssd
La directive
DomainSocket spécifie le socket de domaine par lequel le démon CUPS s'exécutant localement est accessible. Si elle n'est pas spécifiée, le socket de domaine standard de CUPS est utilisé. Utilisez cette option si vous avez spécifié un socket de domaine alternatif pour CUPS via une directive Listen dans /etc/cups/cupsd.conf. Si cups-browsed ne peut pas accéder au démon CUPS local via un socket de domaine, il y accède via localhost. "None" ou "Off" empêche cups-browsed d'utiliser le socket de domaine de CUPS. 
        DomainSocket /var/run/cups/cups.sock
        DomainSocket None
        DomainSocket Off

Définir
OnlyUnsupportedByCUPS sur "Yes" fera que cups-browsed ne créera pas de files d'attente locales pour les imprimantes distantes pour lesquelles CUPS crée lui-même des files d'attente. Ces imprimantes sont des imprimantes annoncées via DNS-SD et effectuant une impression sans pilote prise en charge par CUPS (actuellement PWG Raster et Apple Raster), y compris les files d'attente CUPS distantes. Les files d'attente pour les autres imprimantes (comme pour les anciennes imprimantes PostScript/PCL) sont toujours créées (selon les autres paramètres de configuration de cups-browsed).

Avec OnlyUnsupportedByCUPS défini sur "No", cups-browsed crée des files d'attente pour toutes les imprimantes qu'il prend en charge, y compris les imprimantes pour lesquelles CUPS en créerait lui-même. Les files d'attente temporaires créées par CUPS seront écrasées. De cette manière, il est assuré que toute fonctionnalité supplémentaire de cups-browsed s'appliquera à ces files d'attente. Comme les files d'attente créées par cups-browsed sont des files d'attente CUPS permanentes, ce paramètre est également recommandé si des applications/boîtes de dialogue d'impression qui ne prennent pas en charge les files d'attente CUPS temporaires sont installées. Ce paramètre est la valeur par

défaut. 
        OnlyUnsupportedByCUPS Yes
Avec UseCUPSGeneratedPPDs
défini sur "Yes", cups-browsed crée des files d'attente pour les imprimantes IPP avec des PPD générés par le générateur de PPD de CUPS et non par celui de cups-browsed. Ainsi, toute nouvelle évolution du générateur de PPD de CUPS devient disponible. Comme le générateur de PPD de CUPS n'est pas directement accessible, nous devons faire en sorte que CUPS génère une file d'attente d'impression temporaire avec le PPD souhaité. Par conséquent, nous ne pouvons utiliser ces PPD que lorsque notre file d'attente remplace une file d'attente CUPS temporaire, ce qui signifie que la file d'attente est pour une imprimante sur laquelle CUPS prend en charge l'impression sans pilote (IPP 2.x, PDL : PDF, PWG Raster et/ou Apple Raster) et que son nom est le même que celui utilisé par CUPS pour la file d'attente temporaire ("LocalQueueNamingIPPPrinter DNS-SD" doit être défini). La directive ne s'applique qu'aux imprimantes IPP, pas aux files d'attente CUPS distantes, pour ne pas perturber le clustering. Définir cette directive sur "No" permet à cups-browsed de générer le fichier PPD. Le paramètre par défaut est "No". 
        UseCUPSGeneratedPPDs No
Avec les
directives LocalQueueNamingRemoteCUPS et LocalQueueNamingIPPPrinter, vous pouvez déterminer comment les noms des files d'attente locales générées par cups-browsed sont générés, séparément pour les imprimantes CUPS distantes et les imprimantes IPP.

"DNS-SD" (la valeur par défaut dans les deux cas) base la dénomination sur le nom de service de l'enregistrement DNS-SD annoncé de l'imprimante. C'est exactement le même schéma de dénomination que CUPS utilise pour ses files d'attente temporaires, de sorte que la file d'attente locale de cups-browsed empêche CUPS de lister et de créer une file d'attente supplémentaire. Comme les noms de service DNS-SD doivent être uniques, les noms de file d'attente des imprimantes de différents serveurs seront également uniques et il n'y a donc pas de clustering automatique pour l'impression en équilibrage de

charge.

"MakeModel" base le nom de la file d'attente sur les noms du fabricant et du modèle de l'imprimante. Ce schéma était utilisé précédemment par cups-browsed pour les imprimantes

IPP.

"RemoteName" n'est disponible que pour les files d'attente CUPS distantes et utilise le nom de la file d'attente sur le serveur CUPS distant comme nom de la file d'attente locale. Cela fait que les imprimantes sur différents serveurs CUPS avec des noms de file d'attente identiques forment automatiquement un cluster d'équilibrage de charge comme le faisait CUPS précédemment (CUPS 1.5.x et antérieur) avec les imprimantes distantes diffusées par CUPS. Ce schéma était utilisé précédemment par cups-browsed pour les imprimantes CUPS

distantes. 
        LocalQueueNamingRemoteCUPS DNS-SD
        LocalQueueNamingRemoteCUPS MakeModel
        LocalQueueNamingRemoteCUPS RemoteName
        LocalQueueNamingIPPPrinter DNS-SD
        LocalQueueNamingIPPPrinter MakeModel
Définissez DNSSDBasedDeviceURIs sur "Yes"
si cups-browsed doit utiliser des URI de périphérique basés sur le nom de service DNS-SD pour ses files d'attente locales, comme le fait également CUPS. Ces files d'attente utilisent le nom de service DNS-SD de l'imprimante découverte. Avec cela, l'URI est indépendant des interfaces réseau et des ports, offrant des connexions fiables vers toujours le même périphérique physique. Ce paramètre est la valeur par défaut.

Définissez DNSSDBasedDeviceURIs sur "No" si cups-browsed doit utiliser les URI conventionnels basés sur le nom

d'hôte/IP.

Notez que cette option n'a d'influence que sur les URI des imprimantes découvertes via DNS-SD, pas via BrowsePoll. Ces imprimantes se voient toujours attribuer les URI

conventionnels. 
        DNSSDBasedDeviceURIs Yes
Définissez
IPBasedDeviceURIs sur "Yes" si cups-browsed doit créer ses files d'attente locales avec des URI de périphérique avec les adresses IP au lieu des noms d'hôte des serveurs distants. Ce mode est là pour tous les problèmes de résolution de noms d'hôte dans le réseau, en particulier aussi si avahi-daemon n'est exécuté que pour la découverte d'imprimantes et est déjà arrêté pendant l'impression. Par défaut, ce mode est désactivé, ce qui signifie que nous utilisons des URI avec des noms d'hôte.

Notez que les adresses IP dépendent de l'interface réseau par laquelle l'imprimante est accessible. N'utilisez donc pas d'URI basés sur l'IP sur les systèmes avec de nombreuses interfaces réseau et où les interfaces peuvent apparaître et disparaître

fréquemment.

Ce mode pourrait également être utile pour le développement et le

débogage.

Si vous préférez les adresses IP IPv4 ou IPv6 dans les URI, vous pouvez définir IPBasedDeviceURIs sur "IPv4" pour n'obtenir que des adresses IP IPv4 ou IPBasedDeviceURIs sur "IPv6" pour n'obtenir que des adresses IP

IPv6. 
        IPBasedDeviceURIs No
        IPBasedDeviceURIs Yes
        IPBasedDeviceURIs IPv4
        IPBasedDeviceURIs IPv6

La directive NewIPPPrinterQueuesShared détermine si une file d'attente d'impression pour une imprimante réseau IPP nouvellement découverte (pas une file d'attente CUPS distante) sera partagée sur le réseau local ou non. Ceci n'est valide que pour les imprimantes nouvellement découvertes. Pour les imprimantes découvertes lors d'une session cups-browsed antérieure, cups-browsed se souviendra si l'imprimante était partagée, de sorte que les modifications apportées par l'utilisateur soient conservées. Par défaut, les imprimantes IPP nouvellement découvertes ne sont pas partagées. 
        NewIPPPrinterQueuesShared Yes
Comment gérer les files d'attente d'impression que cups-browsed crée lors de l'arrêt de cups-browsed :

« KeepGeneratedQueuesOnShutdown No » fait supprimer les files d'attente. Cela est logique car ces files d'attente ne fonctionnent que tant que cups-browsed est en cours d'exécution. cups-browsed doit déterminer à quel membre d'un cluster d'imprimantes passer le travail.

« KeepGeneratedQueuesOnShutdown Yes » (la valeur par défaut) empêche la suppression des files d'attente. C'est le paramètre recommandé pour un système où cups-browsed est exécuté en permanence et n'est arrêté que pour de courtes périodes (comme la rotation des journaux) ou lors de l'arrêt. Cela évite la recréation des files d'attente lors du redémarrage de cups-browsed, ce qui provoque souvent un encombrement des notifications CUPS sur le bureau.

        KeepGeneratedQueuesOnShutdown No
S'il existe plus d'une imprimante CUPS distante dont la file d'attente locale porterait le même nom et qu'AutoClustering est défini sur « Yes » (la valeur par défaut), une seule file d'attente locale est créée, formant un cluster d'équilibrage de charge des imprimantes distantes qui porteraient ce nom de file d'attente (classe implicite). Cela signifie que lorsque plusieurs travaux sont envoyés à cette file d'attente, ils sont distribués entre les imprimantes, en utilisant la méthode choisie par la directive LoadBalancing.

Notez que la formation de clusters dépend du schéma de nommage des files d'attente locales créées par cups-browsed. Si vous avez défini LocalQueueNamingRemoteCUPS sur « DNSSD », vous n'obtiendrez pas de clustering automatique car les noms de service DNS-SD sont toujours uniques. Avec LocalQueueNamingRemoteCUPS défini sur « RemoteName », les files d'attente locales portent le nom des files d'attente CUPS sur les serveurs distants, et ainsi les files d'attente portant le même nom sur différents serveurs sont regroupées (c'est ainsi que CUPS le faisait dans la version 1.5.x ou antérieure). LocalQueueNamingRemoteCUPS défini sur « MakeModel » fait regrouper les imprimantes distantes du même modèle. Notez qu'un cluster peut alors contenir plus d'une file d'attente du même serveur.

Avec AutoClustering défini sur « No », pour chaque imprimante CUPS distante, une file d'attente locale individuelle est créée, et pour éviter les conflits de noms lors de l'utilisation des paramètres LocalQueueNamingRemoteCUPS « RemoteName » ou « MakeModel », « @<nom du serveur> » est ajouté au nom de la file d'attente locale.

Seules les imprimantes CUPS distantes sont regroupées, pas les imprimantes réseau IPP ou les imprimantes IPP-sur-USB.

        AutoClustering Yes
        AutoClustering No
La formation de clusters d'imprimantes en équilibrage de charge peut également être contrôlée manuellement en définissant explicitement quelles imprimantes CUPS distantes doivent être regroupées.

Ceci est fait par la directive « Cluster » :

        Cluster <QUEUENAME>: <EXPRESSION1> <EXPRESSION2> ...
        Cluster <QUEUENAME>
Si aucune expression n'est donnée, <QUEUENAME> est utilisée comme première et unique expression pour ce cluster.

Les imprimantes découvertes sont comparées à toutes les expressions de tous les clusters définis. La première expression qui correspond à l'imprimante découverte détermine à quel cluster elle appartient. Notez qu'ainsi une imprimante ne peut appartenir qu'à un seul cluster. Une fois qu'une correspondance est trouvée, les définitions de clusters supplémentaires ne sont plus vérifiées.

Avec la première imprimante correspondant à une expression de cluster, une file d'attente locale portant le nom <QUEUENAME> est créée. Si d'autres imprimantes sont découvertes et correspondent à ce cluster, elles rejoignent le cluster. L'impression sur cette file d'attente imprime sur toutes ces imprimantes de manière équilibrée, conformément au réglage de la directive LoadBalancing.

Chaque expression doit être une chaîne de caractères sans espaces. Si des espaces sont nécessaires, remplacez-les par des underscores ('_').

Une expression peut être mise en correspondance de trois manières :

    1. Par le nom de la file d'attente CUPS sur le serveur distant
    2. Par le nom de marque et de modèle de l'imprimante distante
    3. Par le nom du service DNS-SD de l'imprimante distante
Notez que la correspondance est insensible à la casse et que tout groupe de caractères non alphanumériques est remplacé par un seul underscore.

Ainsi, si une expression est « HP_DeskJet_2540 » et que le serveur distant signale « hp Deskjet-2540 », l'imprimante correspondra à ce cluster.

Si « AutoClustering » n'est pas défini sur « No », vos définitions de clusters manuelles seront suivies et le clustering automatique des files d'attente distantes de même nom sera effectué. Si une imprimante correspond aux deux catégories, la correspondance au cluster défini manuellement a la priorité. Le clustering automatique des imprimantes distantes de même nom n'est pas effectué s'il existe un cluster défini manuellement portant ce nom (du moins tant que les imprimantes ne correspondent pas à ce cluster).

Exemples :

Pour regrouper toutes les files d'attente CUPS distantes nommées « laserprinter » sur votre réseau local, mais ne pas regrouper d'autres imprimantes CUPS distantes portant le même nom, utilisez (la file d'attente locale sera nommée « laserprinter ») :

        AutoClustering No
        Cluster laserprinter
Pour regrouper toutes les files d'attente CUPS distantes des imprimantes HP LaserJet 4050 dans une file d'attente locale nommée « LJ4050 » : 
        Cluster LJ4050: HP_LaserJet_4050
Les noms de service DNS-SD étant uniques sur un réseau, vous pouvez créer un cluster à partir d'imprimantes spécifiées exactement (espaces remplacés par des underscores) : 
        Cluster hrdep: oldlaser_@_hr-server1 newlaser_@_hr-server2
La directive LoadBalancing permet de choisir entre deux méthodes de gestion de l'équilibrage de charge entre des files d'attente distantes de même nom, représentées par une seule file d'attente d'impression locale formant un cluster (classe implicite).

Les deux méthodes sont :

Mise en file d'attente des travaux sur le client (LoadBalancing QueueOnClient) :

Ici, nous mettons en file d'attente les travaux sur le client et vérifions régulièrement les files d'attente d'impression distantes regroupées. Si nous trouvons une file d'attente inactive, nous lui transmettons un travail.

C'est aussi la méthode que CUPS utilise pour les classes. L'avantage est une distribution plus uniforme de la charge de travail des tâches sur les serveurs (surtout si la vitesse d'impression des serveurs est très différente), et si un serveur tombe en panne, il n'y a pas plusieurs travaux bloqués ou perdus. L'inconvénient est que si l'on retire le client (ordinateur portable, téléphone mobile, ...) du réseau local, l'impression s'arrête avec les travaux en attente dans la file d'attente locale.

Mise en file d'attente des travaux sur les serveurs (LoadBalancing QueueOnServers) :

Ici, nous vérifions le nombre de travaux sur chacune des imprimantes distantes regroupées et envoyons un travail entrant immédiatement à l'imprimante distante ayant le moins de travaux dans sa file d'attente. De cette manière, aucun travail n'est mis en file d'attente localement, tous les travaux en attente sont en attente sur l'un des serveurs distants.

Ne pas avoir de travaux en attente localement a l'avantage de pouvoir retirer la machine locale du réseau et tous les travaux seront imprimés. L'inconvénient est que si un serveur avec une file d'attente remplie de travaux disparaît, les travaux disparaissent également.

Par défaut, les travaux sont mis en file d'attente sur le client, car c'est ce que fait CUPS avec les classes.

        LoadBalancing QueueOnClient
        LoadBalancing QueueOnServers
Avec la directive DefaultOptions, un ou plusieurs paramètres d'option peuvent être définis pour être appliqués à chaque file d'attente d'impression nouvellement créée par cups-browsed. Chaque option est fournie comme on fournit des options avec l'argument de ligne de commande « -o » à la commande « lpadmin » (Exécutez « man lpadmin » pour plus de détails). Plusieurs options peuvent être fournies en séparant les options par des espaces. Par défaut, aucun paramètre d'option n'est prédéfini.

Notez que les files d'attente d'impression que cups-browsed a déjà créées se souviennent de leurs paramètres précédents et que ces paramètres ne sont donc pas appliqués.

        DefaultOptions Option1=Value1 Option2=Value2 Option3 noOption4
La directive AutoShutdown spécifie si cups-browsed doit se terminer automatiquement lorsqu'il n'y a plus de files d'attente locales brutes configurées pointant vers des imprimantes découvertes ou lorsqu'il n'y a plus de travaux sur ces files d'attente, selon le réglage AutoShutdownOn (mode d'arrêt automatique). Le définir sur « On » active le mode d'arrêt automatique, le définir sur « Off » le désactive (par défaut). Le mode spécial « avahi » désactive l'arrêt automatique pendant que avahi-daemon est en cours d'exécution et l'active lorsque avahi-daemon s'arrête. Cela permet d'exécuter cups-browsed à la demande lorsque avahi-daemon est exécuté à la demande.

        AutoShutdown Off
        AutoShutdown On
        AutoShutdown avahi
La directive AutoShutdownOn détermine quel événement cups-browsed considère comme une inactivité en mode d'arrêt automatique. « NoQueues » (la valeur par défaut) signifie que l'arrêt automatique est initié lorsqu'il n'y a plus de files d'attente pour les imprimantes découvertes générées par cups-browsed. « NoJobs » signifie que toutes les files d'attente générées par cups-browsed sont sans travaux.

        AutoShutdownOn NoQueues
        AutoShutdownOn NoJobs
DebugLogFileSize définit la taille maximale possible (en KBytes) des fichiers de journaux (cups-browsed_log et cups-browsed_previous_logs) créés en utilisant cups-browsed en mode de débogage. Définir sa valeur sur 0 désactiverait toute restriction sur la taille du fichier.

        DebugLogFileSize 300
La directive AutoShutdownTimeout spécifie après combien de secondes d'absence de files d'attente locales brutes configurées pointant vers des imprimantes découvertes ou des travaux sur ces files d'attente, cups-browsed doit réellement s'arrêter en mode d'arrêt automatique. La valeur par défaut est de 30 secondes, 0 signifie un arrêt immédiat.

        AutoShutdownTimeout 20
NotifLeaseDuration définit combien de temps l'abonnement D-BUS créé par cups-browsed dans cupsd durera avant que cupsd ne l'annule. La valeur par défaut est 1 jour en secondes - 86400. Le renouvellement de l'abonnement est programmé pour se produire après la moitié de NotifLeaseDuration. Les notifications D-BUS sont utilisées pour surveiller les files d'attente et effectuer des actions spécifiques lorsqu'une notification D-BUS arrive.

        NotifLeaseDuration 86400
FrequentNetifUpdate active/désactive les routines de mise à jour des interfaces réseau qui se produisent pour chaque entrée trouvée, ce qui peut ralentir considérablement cups-browsed si nous sommes sur un réseau avec de nombreux imprimantes partagées ou si nous utilisons BrowsePoll vers un serveur avec de nombreuses files d'attente. La mise à jour de l'interface réseau après réception d'une notification D-BUS de NetworkManager ne sera pas désactivée avec la directive. La valeur par défaut est 'Yes'.
