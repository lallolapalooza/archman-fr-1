Cual - Langage d'animation

Cuyo

Cual est le langage principal utilisé pour décrire les animations dans cuyo. Strictement parlant, il s'agit du contenu entre les crochets << >> dans les fichiers de description de niveau (xxx.ld)

.

D'autre part, cette page manuel vise à être une description complète de la manière d'écrire des niveaux pour cuyo. Mais elle est encore en cours de construction. Voir le fichier "example.ld" pour se faire une idée du fonctionnement du reste de la description de niveau. Il y a aussi un peu de code Cual d'exemple dans "example.ld". Et bien sûr, tous les niveaux existants sont des

exemples.

Notez que Cual est probablement encore très buggé. Donc si des choses étranges se produisent et que vous êtes sûr que ce n'est pas de votre faute, dites-le-moi (cuyo@karimmi.

de)
.

COMMENT ÇA

MARCHE

La description du niveau est organisée en sections. Il y a une section globale et chaque niveau a sa propre section, qui est une sous-section de la section globale. Il est d'usage de placer chaque niveau dans un fichier séparé, qui commence alors essentiellement par l'ouverture de sa section et se termine par sa

fermeture.

Une section est définie par nom = {contenu}. nom est le nom de la nouvelle section et contenu contient les définitions qui appartiennent à cette section. C'est une séquence de définitions de la forme nom = truc. Ici truc peut être {contenu} comme ci-dessus, ou il peut être une donnée unique, ou il peut être une liste de données séparées par des virgules. À l'intérieur d'une telle liste, donnée * nombre peut être utilisé comme raccourci pour donnée, ..., donnée, c'est-à-dire une répétition de donnée. Une donnée peut être un identificateur, une chaîne (encadrée par '"'), un mot, ou un nombre. À la place d'un nombre <expression> peut être utilisé, où expression est une expression arbitraire composée de nombres littéraux, de données numériques définies précédemment, et des opérateurs +, -, *, / et %

.

Les définitions peuvent aussi dépendre des versions. Voir la section GESTION DES VERSIONS

ci-dessous.

En plus des définitions, une section peut aussi contenir des définitions cual (voir ci-dessous). Celles-ci doivent être encadrées par << et >>

.

Chaque blob a sa propre procédure Cual (principale) qui effectue le dessin et l'animation. La procédure ne dépend que du type du blob, c'est-à-dire qu'elle est la même pour les blobs de même type. Cependant, chaque blob a sa propre instance des

variables.

À chaque étape de jeu, la procédure de chacun des blobs est appelée une fois. (Il y a 12,5 étapes de jeu par seconde.) Elle doit dessiner le blob à chaque fois, même si rien n'a changé. (Cependant, il y a une routine interne dans cuyo qui vérifie si la même chose est dessinée que lors de la dernière étape et qui supprime alors le dessin.

)

Il peut y avoir d'autres procédures associées à un type de blob, qui sont exécutées lors d'événements spéciaux, par exemple lorsqu'un blob en chute atterrit. Contrairement à la procédure principale, ces gestionnaires d'événements ne sont pas autorisés à dessiner quoi que ce soit. Voir la section GESTIONNAIRES D'ÉVÉNEMENTS pour une liste des événements

existants.

Le nom de la procédure principale d'un blob (celle qui dessine le blob) est le nom du type du blob. Normalement, ce nom est le mot listé après l'entrée pics= dans le fichier .ld ; mais si ce "mot" contient un point, seule la partie avant le point constitue le nom. (E. g. avec pics=redblob.xpm,greenblob.xpm, les noms sont "redblob" et "greenblob".

)

Le nom d'une procédure de gestionnaire d'événements est le nom du type, suivi d'un point, suivi du nom de l'événement. (E.g. "redblob.land" pour l'événement d'atterrissage du redblob venant d'en haut.

)

Il est parfois nécessaire de définir un niveau légèrement différemment selon les objectifs. Par exemple, vous pourriez avoir besoin de diminuer numexplode pour la version à deux joueurs afin qu'elle ne devienne pas injouable. Les paramètres de difficulté du menu principal de cuyo fournissent un autre

Cela se fait en qualifiant une définition avec les versions auxquelles elle doit s'appliquer. C'est mieux expliqué par un exemple

numexplode = 8

Ceci spécifie que normalement numexplode doit être 8. En mode deux joueurs il doit être 6. En mode un joueur difficile il doit être 10. Ici les spécificateurs 2 pour le mode deux joueurs, 1 pour le mode un joueur et hard pour le mode difficile sont utilisés. Avec easy pour le mode facile ce sont tous les spécificateurs prédéfinis destinés aux niveaux. De plus (et à des fins internes), il existe des spécificateurs pour les pistes de niveaux : main, all, game, extreme, nofx, weird, et contrib

.

De plus, vous pouvez créer et utiliser vos propres spécificateurs. Pour qu'ils prennent effet, cependant, vous devez donner à cuyo des informations supplémentaires sur la version courante. Cela se fait en ligne de commande à l'aide de l'option --version. Par

exemple

Spécifie à la fois la version difficile (vous pouvez la changer dans le menu) et la version « geek », qui n'est pas

prédéfinie.

Plusieurs contraintes doivent être respectées

:
—
Toutes les versions d'une définition doivent être faites avant la première utilisation de la chose définie. Comme il n'est pas toujours évident où la chose définie est utilisée (par exemple startpic utilise un greypic précédent en assignant des nombres successifs aux kinds), il est préférable de regrouper toutes ces versions dans un seul
bloc.
—
Une version donnée s'applique aussi à chaque version plus spécialisée pour laquelle aucune définition n'est donnée. Dans l'exemple ci-dessus, numexplode est défini à 6 en mode deux joueurs difficile et
en mode deux jou
eurs facile aussi.

Tous les conflits résultants doivent être résolus. Par exemple, si vous faites une définition pour [2] et une pour [hard], vous devez aussi faire une définition pour [2,hard] (ou, de manière équivalente, pour [hard,2]), car sinon il serait ambigu lequel des deux pre

mode deux joueurs difficile.
—
Cuyo sait que easy et hard s'excluent mutuellement. Par conséquent, il est inutile (et en fait interdit) de donner une définition [easy,hard], même si à la fois [easy] et [hard] sont donnés. Il en va de même pour 1 et 2, et pour les pistes de

Busieness est un concept pour faciliter l'implémentation de séquences d'animation simples qui sont déclenchées par certains événements. Chaque fragment de code a un état interne qui indique s'il est

occupé.
—
Les instructions normales comme les affectations ne sont jamais
occupées.
—
Une chaîne de commandes séparées par « , » est occupée tant que toutes les commandes n'ont pas été
exécutées.
—

t occ
upé.

Voici un exemple d'utilisation de busieness pour une animation qui apparaît à intervalles aléatoires

switch {
1:100 => {B*, C*, D*, E*};
-> A*;
}

;

Ce fragment de code dessine normalement l'icône à la position A (0). Mais à chaque étape, avec une probabilité de 1/100, une séquence d'animation composée des icônes B, C, D et E est démarrée. Mais avec la double flèche, l'instruction switch ne reviendra pas à A tant que l'animation n'est pas

terminée.

(Au fait : cela ne fait pas de différence s'

A* » ; A* n'est de toute façon pas occupé.)

LA VIE D'UN

BLOB

Les blobs normaux entrent dans la vie au début du jeu, ou ils tombent dans la vie : soit comme des blobs colorés, dirigés par l'utilisateur, soit comme des blobs gris. Plus précisément, les blobs dirigés entrent déjà dans la vie lorsqu'ils apparaissent en aperçu. Lorsqu'un blob se déplace (par gravité ou lorsque des rangées passent d'un joueur à l'autre), il emporte ses variables avec lui. Lorsqu'un blob explose, il ne cesse pas d'exister. Il se transforme plutôt en un blob vide. C'est important pour les variables : le blob vide a toujours toutes les variables définies aux valeurs qu'elles avaient avant ; seul son type est différent. Les blobs vides sont partout où il n'y a pas d'autre blob. (Cependant, les blobs tombants dirigés par l'utilisateur sont en quelque sorte « au-dessus » de tout le reste ; il y a des blobs vides en dessous d'eux.

)

La vie des blobs vides est différente de celle des blobs normaux. Les blobs vides ne sont pas affectés par la gravité, et ils commencent ou cessent souvent d'exister. Par exemple, lorsqu'un blob g

ris unique tombe, le blob vide en dessous de lui cesse d'exister lorsque le blob gris arrive, et un nouveau blob vide commence à exister lorsque le blob gris continue sa chute. Il n'y a qu'un
e seule situation dans laquelle les blobs vides se déplacent : lorsqu'une rangée passe d'un joueur à l'autre et que tout se déplace vers le haut ou vers le bas, les blobs vides se déplacent aussi.

La dernière ligne peut avoir une longueur de 4, 8, 10 ou 20. Si elle a une longueur de 10 ou 20, c'est juste une ligne normale comme ci-dessus. Sinon, elle décrit les blobs informatifs à côté du champ. Dans le cas d'une longueur de 4, la première entrée décrit le blob qui représente le nombre de gris. La deuxième entrée décrit le blob qui représente le nombre de blobs d'herbe. La troisième entrée décrit le blob qui représente les informations de connexion. La quatrième entrée décrit le blob qui représente les informations de chaingrass. Dans le cas d'une longueur de 8, ce qui précède s'applique au joueur de gauche. Les 4 entrées restantes décrivent alors la même chose pour le joueur de droite, mais dans l'ordre inverse. La valeur par défaut est "-*%&&%*-" (ou de manière
équivalente
"-*%&").

Comme vu ci-dessus, startdist peut référencer directement 62 combinaisons type/version (et plus au hasard). Parce que cela pourrait un jour ne pas suffire, l'extension multichar a été introduite. Dans ce cas, chaque blob est décrit par plus d'un caractère. Cependant, le nombre de caractères par blob doit être le même pour toutes les clés. Ainsi, les longueurs

des

lignes startdist doivent alors être ce nombre multiplié par 10 ou par 20. Toute combinaison multicharactère commençant par ".", "+", "-", ou "*" est traitée comme le caractère correspondant au format à caractère unique. Toutes les autres combinaisons de caractères sont traitées comme des nombres en représentation de base 62. Ici, "A" à "Z" sont des chiffres avec une valeur décimale de 10 à 35, et "a" à "z" sont des chiffres avec une valeur décimale de 36 à 61. Les espaces initiaux sont autorisés à la place des zéros (cependant, la chaîne entièrement composée d'espaces est interdite). Le distkey maximal qui (en tant que nombre) n'est pas plus grand que le nombre donné dans startdist, spécifie le type du blob. La différence entre le nombre startdist et le distkey spécifie alors la version du blob. Dans le cas des distkeys multichar, la valeur par défaut pour les distkeys des types déclarés par startpic= est 10 en décimal. Pour les blobs dont les types sont choisis au hasard (c'est-à-dire les

caractères

"+", "-", "*" dans les startdists à caractère unique), cuyo essaie de les rendre aussi différents que possible. Cela signifie que, par une certaine heuristique, cuyo minimise le nombre de blobs voisins de même type. « Voisin », bien sûr, fait référence à l'entrée neighbours. inhibit et le bit calculate_size de behaviour n'ont aucun effet (ceux-ci sont modifiables pendant la durée de vie des blobs, alors qu'au moment du traitement de startdist, la durée de vie d'aucun blob n'a encore commencé). Ainsi, la seule façon d'influencer le dévoisinage (si vous le souhaitez vraiment), est de définir neighbours de manière appropriée. (Bien sûr, cette possibilité est encore plus limitée, si vous avez l'intention de définir le bit calculate_size pendant l

a durée de v
ie du blob.)
