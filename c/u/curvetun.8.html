NOM

curvetun - un tunnel IP léger Curve25519

SYNTAXE

curvetun [options]

DESCRIPTION

curvetun est un tunnel IP multi-utilisateurs léger et rapide basé sur Curve25519 pour Linux, fondé sur epoll(2). curvetun utilise l'interface TUN/TAP de Linux et supporte {IPv4, IPv6} sur {IPv4, IPv6} avec UDP ou TCP comme protocoles de transport.

Il possède un arbre de transfert de paquets intégré, permettant ainsi à plusieurs utilisateurs avec différentes adresses IP d'être gérés via un unique périphérique de tunnel côté serveur, et les flux sont planifiés pour traitement de manière efficace en termes d'utilisation du CPU, du moins dans le cas où TCP est le protocole de transport.

Pour la gestion des clés, la cryptographie à clé publique basée sur les courbes elliptiques est utilisée, et les paquets sont chiffrés de bout en bout par le chiffrement de flux symétrique Salsa20 et authentifiés par le MAC Poly1305, où les clés ont été précédemment calculées avec le protocole d'accord de clés ECDH Curve25519.

La cryptographie est basée sur la bibliothèque de réseaux et de cryptographie “NaCl” de Daniel J. Bernstein. Par conception, curvetun ne fournit aucun modèle particulier ou numéro de port par défaut qui donnerait la certitude que la connexion d'un flux particulier utilise effectivement curvetun.

Cependant, si vous avez besoin de contourner la censure, vous pouvez essayer d'utiliser curvetun en combinaison avec obfsproxy ou Telex de Tor. De plus, curvetun vous protège également contre les attaques par rejeu et les attaques de type "man-in-the-middle" DH. En outre, la journalisation des événements syslog côté serveur peut également être désactivée pour éviter de révéler des données critiques de connexion utilisateur.

OPTIONS

-d <tundev>, --dev <tundev>
Définit le nom du périphérique de tunnel qui est créé. Si cette option n'est pas définie, les noms par défaut, curves{0,1,2,..} pour un serveur curvetun, et curvec{0,1,2,...} pour un client curvetun sont utilisés.
-p <num>, --port <num>
Définit le port sur lequel le serveur curvetun doit écouter. Il n'y a pas de port par défaut pour curvetun, donc la définition de cette option pour le démarrage du serveur est obligatoire. Cette option est uniquement pour les serveurs.
-t <serveur>, --stun <serveur>
Si nécessaire, cette option active une recherche STUN afin d'afficher le mapping IP publique vers port et de percer un trou dans le pare-feu. Si vous n'êtes pas sûr du serveur STUN à utiliser, utilisez simplement ''--stun stunserver.org''.
-c[=alias], --client[=alias]
Lance curvetun en mode client et se connecte à l'alias de connexion donné qui est défini dans le fichier de configuration.
-k, --keygen
Génère une paire de clés privée et publique. Ceci doit être fait initialement.
-x, --export
Exporte la combinaison utilisateur et clé vers stdout sous forme d'une ligne.
-C, --dumpc
Affiche tous les clients connus pouvant se connecter au serveur curvetun local et quitte.
-S, --dumps
Affiche tous les serveurs connus auxquels curvetun en tant que client peut se connecter, et quitte.
-D, --nofork
Ne pas se démultiplier (fork) en tant que client ou serveur au démarrage.
-s, --server
Lance curvetun en mode serveur. Des paramètres supplémentaires sont nécessaires, au moins la définition du port auquel les clients peuvent se connecter est requise.
-N, --no-logging
Désactive toute journalisation des informations utilisateur par curvetun. Cette option peut être utilisée pour permettre aux utilisateurs de curvetun de se connecter de manière plus anonyme. Cette option est uniquement pour les serveurs.
-u, --udp
Utilise UDP comme protocole de transport au lieu de TCP. Par défaut, TCP est le protocole de transport. Cette option est uniquement pour les serveurs.
-4, --ipv4
Définit IPv4 comme protocole réseau sous-jacent à utiliser sur le périphérique de tunnel. IPv4 est le défaut. Cette option est uniquement pour les serveurs.
-6, --ipv6
Définit IPv6 comme protocole réseau sous-jacent à utiliser sur le périphérique de tunnel. Cette option est uniquement pour les serveurs.
-v, --version
Affiche les informations de version et quitte.
-h, --help
Affiche l'aide utilisateur et quitte.

EXEMPLE D'UTILISATION

curvetun --server -4 -u -N --port 6666 --stun stunserver.org
Lance curvetun en mode serveur avec IPv4 comme protocole réseau et UDP comme protocole de transport. Le serveur curvetun écoute les connexions entrantes sur le port 6666 et effectue une recherche STUN au démarrage sur stunserver.org.
curvetun --client=ethz
Lance curvetun en mode client et se connecte à l'alias de connexion défini ''ethz'' dans le fichier de configuration de serveur curvetun ~/.curvetun/servers.
curvetun --keygen
Génère les paires de clés initiales et les stocke dans le répertoire ~/.curvetun/.
curvetun --export
Exporte les données utilisateur vers stdout pour la configuration d'un serveur curvetun.

CRYPTOGRAPHIE

Les tunnels IP chiffrés sont souvent utilisés pour créer des réseaux privés virtuels (VPN), où certaines parties du réseau ne sont accessibles que via un support non sécurisé ou non fiable comme Internet. Peu d'utilitaires logiciels existent pour créer de tels tunnels, ou VPN. Deux représentants populaires de tels logiciels sont OpenVPN et VTUN.

Ce dernier a également introduit les interfaces TUN/TAP dans le noyau Linux. VTUN n'a qu'un module de chiffrement assez basique, qui ne répond pas aux besoins cryptographiques actuels. Par défaut, MD5 est utilisé pour créer des clés de 128 bits pour le chiffrement symétrique BlowFish en mode ECB [1].

Bien qu'OpenSSL soit utilisé dans VTUN et OpenVPN, OpenVPN est beaucoup plus riche en fonctionnalités concernant les chiffrements et l'authentification des utilisateurs. Néanmoins, laisser les gens choisir les chiffrements ou les méthodes d'authentification n'est pas nécessairement une bonne chose : les administrateurs pourraient préférer la vitesse à la sécurité et donc choisir des chiffrements faibles, de sorte que le système de communication sera aussi bon que sans aucun chiffrement ; ils pourraient choisir des mots de passe faibles pour le chiffrement symétrique ou mal configurer le système de communication en ayant trop de choix de chiffrements et trop peu d'expérience pour choisir le bon.

Outre les problèmes d'administration, il y a aussi des problèmes de développement logiciel. Les bibliothèques cryptographiques comme OpenSSL sont un grand gâchis, trop bas niveau et complexes à comprendre ou à appliquer correctement, de sorte qu'elles constituent un terrain supplémentaire pour les vulnérabilités de tels logiciels.

En 2010, les cryptographes Tanja Lange et Daniel J. Bernstein ont donc créé et publié une bibliothèque cryptographique pour les réseaux, nommée NaCl (prononcé "sel"). NaCl résout des problèmes comme ceux mentionnés dans OpenSSL et, contrairement à l'utilisation plutôt générique d'OpenSSL, a été créé avec un fort accent sur le chiffrement authentifié à clé publique basé sur la cryptographie à courbe elliptique, qui est utilisée dans curvetun. Citant partiellement Daniel J. Bernstein :

"RSA est quelque peu plus ancien que la cryptographie à courbe elliptique : RSA a été introduit en 1977, tandis que la cryptographie à courbe elliptique a été introduite en 1985. Cependant, RSA a montré beaucoup plus de faiblesses que la cryptographie à courbe elliptique. La sécurité effective de RSA a été considérablement réduite par le crible linéaire à la fin des années 1970, par le crible quadratique et l'ECM dans les années 1980, et par le crible de corps de nombres dans les années 1990. IEEE P1363 a standardisé la cryptographie à courbes elliptiques à la fin des années 1990, y compris une liste rigoureuse de critères de sécurité pour les courbes elliptiques. NIST a utilisé les critères IEEE P1363 pour sélectionner quinze courbes elliptiques spécifiques à cinq niveaux de sécurité différents. En 2005, la NSA a publié une nouvelle norme « Suite B », recommandant les courbes elliptiques NIST (à deux niveaux de sécurité spécifiques) pour toute la cryptographie à clé publique et retirant les recommandations précédentes de

RSA.

curvetun utilise une courbe elliptique particulière, Curve25519, introduite dans l'article suivant : Daniel J. Bernstein, « Curve25519: new Diffie-Hellman speed records », pages 207-228 dans les actes de PKC 2006, édité par Moti Yung, Yevgeniy Dodis, Aggelos Kiayias et Tal Malkin, Lecture Notes in Computer Science 3958, Springer, 2006, ISBN

3-540-33851-9.

Cette courbe elliptique suit tous les critères de sécurité standard IEEE P1363. Elle suit également de nouvelles recommandations qui permettent d'atteindre une « immunité aux canaux auxiliaires » et une « sécurité contre les courbes miroir » tout en améliorant la vitesse. Cela signifie que les implémentations sécurisées de Curve25519 sont considérablement plus simples et plus rapides que les implémentations sécurisées de, par exemple, NIST P-256 ; il y a moins d'occasions pour les développeurs de commettre des erreurs qui compromettent la sécurité, et ces erreurs sont plus facilement détectées par les

réviseurs.

Un attaquant qui dépense un milliard de dollars en puces spécialisées pour attaquer Curve25519, en utilisant les meilleures attaques disponibles aujourd'hui, a environ 1 chance sur 1000000000000000000000000000 de casser Curve25519 après un an de calcul. On pourrait atteindre des niveaux de sécurité similaires avec RSA à 3000 bits, mais le chiffrement et l'authentification avec RSA à 3000 bits ne sont pas du tout assez rapides pour gérer le trafic de tunnel et nécessiteraient beaucoup plus d'espace dans les paquets

PROCÉDURE

D'INSTALLATION

Si vous n'avez jamais exécuté curvetun auparavant, vous devez effectuer une configuration initiale une seule

fois.

Tout d'abord, assurez-vous que les horloges des serveurs et des clients sont synchronisées périodiquement, par exemple en exécutant un démon NTP. Cela est nécessaire pour se protéger contre les attaques par rejeu. Assurez-vous également d'avoir un accès en lecture et en écriture à /dev/net/tun. Vous ne devriez pas exécuter curvetun en tant que root ! Ensuite, après vous être assuré de cela, la première étape consiste à générer les clés et les fichiers de configuration. Sur le client comme sur le serveur, exécutez

:

curvetun

-k

On vous demande un nom d'utilisateur. Vous pouvez utiliser une adresse courriel ou ce que vous voulez. Ici, nous supposons que vous avez entré 'mysrv1' sur le serveur et 'myclient1' côté

client.

Maintenant, tous les fichiers nécessaires ont été créés sous ~/.curvetun. Les fichiers incluent « priv.key », « pub.key », « username », « clients » et « servers »

.

« clients » et « servers » sont vides au début et doivent être remplis. Le fichier « clients » est destiné au serveur, afin qu'il sache quels clients sont autorisés à se connecter. Le fichier « servers » est pour le client, où il peut sélectionner les serveurs curvetun auxquels se connecter. Les deux fichiers sont gardés très simples, de sorte qu'une seule ligne de configuration par client ou par serveur est

suffisante.

Le client doit exporter ses données de clé publique pour le

serveur

curvetun

-x

où il affiche une chaîne au format suivant

:


myclient1;11:11:11:11:11:11:11:11:11:11:11:11:11:11:11:11:11:11:11:11:11:11:11:11:11:11:11:11:11:11:11:11
\_______/ \_____________________________________________________________________________________________/
nom d'utilisateur clé publique de 32 octets pour

'myclient1'

Cette ligne est transférée à l'administrateur du serveur (oui, nous supposons un scénario d'échange de clés manuel sur site où, par exemple, l'administrateur configure le serveur et les clients), où l'administrateur ajoute ensuite cette entrée dans son fichier ''clients'' comme suit

:


server$ echo "myclient1;11:11:11:11:11:11:11:11:11:11:11:11:11:11:11:11:11:" \
"11:11:11:11:11:11:11:11:11:11:11:11:11:11:11" >> ~/.curvetun/client

s

L'administrateur du serveur peut vérifier si le serveur l'a enregistré correctement comme suit

:


server$ curvetun

-C

ce qui affiche tous les clients analysés depuis ''~/.curvetun/clients''. Ce processus pourrait facilement être automatisé ou scripté avec, par exemple, Perl et

LDAP.

Maintenant, le client ''myclient1'' est connu du serveur ; cela termine la configuration du serveur. La prochaine étape est d'indiquer au client où il doit se connecter au

serveur.

Nous supposons dans cet exemple que le serveur de tunnel a une adresse IP publique, par exemple 1.2.3.4, fonctionne sur le port 6666 et utilise UDP comme protocole de transport. Si vous êtes derrière un NAT, vous pouvez utiliser l'option ''--stun'' de curvetun pour démarrer le serveur et obtenir votre correspondance. Cependant, dans cet exemple, nous continuons avec 1.2.3.4 et 6666,

UDP.

Tout d'abord, le serveur doit exporter sa clé vers le client, comme suit

:


server$ curvetun

-x

où il affiche une chaîne au format suivant

:


mysrv1;22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:22
\____/ \_____________________________________________________________________________________________/
nom d'utilisateur clé publique de 32 octets pour 'mysrv1'
^-- vous avez besoin de cette clé

publique

Ainsi, vous avez maintenant l'adresse IP du serveur, le port du serveur, le protocole de transport du serveur et la clé publique du serveur à portée de main. Côté client, tout cela peut être rassemblé dans la configuration comme suit

:


client$ echo "myfirstserver;1.2.3.4;6666;udp;22:22:22:22:22:22:22:22:22:22:" \
"22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:22:" \
"22:22" >> ~/.curvetun/server

s

Le client peut vérifier sa configuration en utilisant

:


client$ curvetun

-S

Ensuite, nous démarrons le serveur avec

:


server$ curvetun -s -p 6666 -u
server# ifconfig curves0 up
server# ifconfig curves0 10.0.0.

1/24

Puis, nous démarrons le client avec

:


client$ curvetun -c=myfirstserver
client# ifconfig curvec0 up
client# ifconfig curvec0 10.0.0.

2/24

De plus, les informations, erreurs ou avertissements côté client apparaîtront dans syslog ! À ce stade, nous devrions pouvoir faire un ping vers le serveur

:


client$ ping 10.0.0.

1

C'est tout ! Exemple de routage

:

L'adresse IP publique côté serveur sur eth0 est, par exemple, 1.2.3.4

:

server# ifconfig curves0 10.0.0.1/24
server# echo 1 > /proc/sys/net/ipv4/ip_forward
server# iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
server# iptables -A FORWARD -i eth0 -o curves0 -m state --state RELATED,ESTABLISHED -j ACCEPT
server# iptables -A FORWARD -i curves0 -o eth0 -j

client# ifconfig curvec0 10.0.0.2/24
