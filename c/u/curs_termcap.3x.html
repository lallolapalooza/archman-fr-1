curs_termcap(3X) Appels de bibliothèque curs_termcap(3X)

NOM

PC, UP, BC, ospeed, tgetent, tgetflag, tgetnum, tgetstr, tgoto, tputs - émulation curses de termcap

SYNTAXE

#include <curses.h>
#include <term.h>
char PC;
char * UP;
char * BC;
short ospeed;
int tgetent(char *bp, const char *name);
int tgetflag(const char *id);
int tgetnum(const char *id);
char *tgetstr(const char *id, char **area);
char *tgoto(const char *cap, int col, int row);
int tputs(const char *str, int affcnt, int (*putc)(int));

DESCRIPTION

ncurses fournit les variables et fonctions précitées comme couche de compatibilité pour les programmes utilisant la bibliothèque termcap. L'API est la même, mais le comportement est émulé à l'aide de la base de données terminfo. Ainsi, elle ne peut être utilisée que pour interroger les capacités des entrées de la base de données de terminaux pour lesquelles une entrée terminfo a été compilée.

Initialisation

tgetent charge l'entrée de la base de données du terminal pour name ; voir term(7). Ceci doit être fait avant d'appeler l'une des autres fonctions. Elle retourne

1
en cas de succès,
0
s'il n'existe pas d'entrée correspondante (ou si l'entrée correspondante décrit un terminal générique, avec trop peu d'informations pour que les applications curses puissent s'exécuter), et
-1
si la base de données terminfo n'a pas pu être trouvée.

Cette implémentation diffère de celles des bibliothèques termcap historiques.

  • ncurses ignore le pointeur de tampon bp, tout comme les autres implémentations termcap conformes à certaines parties de X/Open Curses maintenant retirées. La bibliothèque termcap BSD stockait une copie de la description du type de terminal dans la zone référencée par ce pointeur. terminfo stocke les descriptions de types de terminaux sous forme compilée, ce qui n'est pas la même chose.
  • Les significations des valeurs de retour diffèrent. La bibliothèque termcap BSD ne vérifie pas si la description du type de terminal inclut la capacité generic (gn), ni si la description du type de terminal prend en charge un curseur adressable, propriété essentielle pour toute implémentation curses.

Récupération des valeurs de capacité

tgetflag renvoie l'entrée booléenne pour id, ou zéro si elle n'est pas disponible.

tgetnum obtient l'entrée numérique pour id, ou -1 si elle n'est pas disponible.

tgetstr retourne l'entrée de chaîne pour id, ou NULL si elle n'est pas disponible. Utilisez tputs pour afficher la chaîne retournée. Le paramètre area est utilisé comme suit.

  • Il est supposé être l'adresse d'un pointeur vers un tampon géré par l'application appelante.
  • Cependant, ncurses vérifie que area n'est pas NULL, et que le pointeur de tampon résultant n'est pas non plus NULL. Si l'une des vérifications échoue, area est ignoré.
  • Si les vérifications réussissent, ncurses copie également la valeur de retour dans le tampon pointé par area, et la bibliothèque met à jour area pour qu'il pointe après le caractère nul terminant cette valeur.
  • La valeur de retour elle-même est une adresse dans la description du type de terminal chargée en mémoire.

Application des capacités de chaîne

Les capacités de chaîne peuvent être paramétrées ; voir la sous-section « Chaînes paramétrées » dans terminfo(5). tgoto applique ses deuxième et troisième arguments aux emplacements réservés paramétriques dans la capacité stockée dans le premier argument.

  • La capacité peut contenir des spécifications de remplissage ; voir la sous-section « Délais et remplissage » de terminfo(5). La sortie de tgoto doit donc être passée à tputs plutôt qu'à une autre fonction de sortie comme printf(3).
  • Bien que tgoto soit supposé être utilisé pour la capacité de positionnement du curseur à deux paramètres, les applications termcap l'utilisent également pour les capacités à un seul paramètre.
Cela révèle une particularité de tgoto : la plupart des terminaux matériels utilisent l'adressage du curseur avec la ligne row en premier, mais les développeurs originaux de l'interface termcap ont choisi de mettre le paramètre col (colonne) en premier. La fonction tgoto inverse l'ordre de ses paramètres. Elle le fait même pour les appels nécessitant un seul paramètre. Dans ce cas, le premier paramètre n'est qu'un espace réservé.
•
Normalement, la bibliothèque ncurses est compilée sans prise en charge complète de termcap. Dans ce cas, tgoto utilise une version interne de tparm(3X) (une fonction plus capable).
Parce qu'elle utilise tparm en interne, tgoto est capable d'utiliser certaines fonctionnalités terminfo, mais pas toutes. En particulier, elle n'autorise que les paramètres numériques ; tparm prend en charge les paramètres de chaîne.
Cependant, tparm n'est pas une fonctionnalité termcap, et les applications termcap portables ne devraient pas compter sur sa disponibilité.

tputs est décrite dans curs_terminfo(3X). Elle peut récupérer les capacités par code termcap ou terminfo.

Variables globales

Les variables PC, UP et BC sont définies par tgetent pour les données de l'entrée terminfo respectivement pour pad_char, cursor_up et backspace_if_not_bs. UP n'est pas utilisée par ncurses. PC est utilisée par delay_output(3X). BC est utilisée par l'émulation tgoto. La variable ospeed est définie par ncurses en utilisant un encodage spécifique au système pour indiquer le débit de transmission du terminal.

Libération de mémoire

Les fonctions termcap ne fournissent aucun moyen de libérer la mémoire, car les implémentations termcap héritées utilisaient uniquement les zones de tampon fournies par l'appelant via tgetent et tgetstr. Ces tampons ne sont pas utilisés dans terminfo.

En revanche, terminfo alloue de la mémoire. Elle utilise setupterm(3X) pour obtenir les données utilisées par tgetent et les fonctions qui récupèrent les valeurs de capacité. On pourrait utiliser

del_curterm(cur_term);

pour libérer cette mémoire, mais il y a une complication supplémentaire avec ncurses. Elle utilise un pool de taille fixe d'emplacements de stockage, un par valeur du nom de terminal passé à tgetent. Le programme screen(1) dépend de cet arrangement pour améliorer ses performances.

Une application qui utilise uniquement les fonctions termcap, et non l'API curses de plus haut niveau, pourrait libérer la mémoire en utilisant del_curterm(3X), car le pool est libéré à l'aide d'autres fonctions ; voir curs_memleaks(3X).

VALEUR DE RETOUR

Les valeurs de retour de tgetent, tgetflag, tgetname et tgetstr sont documentées ci-dessus.

tgoto retourne NULL en cas d'erreur. Les conditions d'erreur incluent :

  • état non initialisé (tgetent n'a pas été appelé avec succès),
  • cap étant un pointeur nul,
  • cap faisant référence à une capacité annulée,
  • cap étant une capacité avec des paramètres de type chaîne (une fonctionnalité exclusive à terminfo), et
  • cap étant une capacité avec plus de deux paramètres.

Voir curs_terminfo(3X) concernant tputs.

HISTORIQU

E

Bill Joy a créé un précurseur de termcap appelé « ttycap », daté de septembre 1977, et publié dans 1BSD (mars 1978). Il utilisait beaucoup des mêmes noms de fonctions que le termcap ultérieur, tels que tgetent, tgetflag, tgetnum et tgetstr

.

Un descendant clair, la bibliothèque termlib, a suivi dans 2BSD (mai 1979), ajoutant tgoto et tputs. La première s'appliquait à l'époque uniquement aux capacités de positionnement du curseur, d'où le nom excessivement spécifique. Peu de choses ont changé dans 3BSD (fin 1979) à part l'ajout de programmes de test et d'une page de manuel termlib, qui documentait l'API montrée dans la section « SYNOPSIS »

ci-dessus.

4BSD (novembre 1980) a renommé termlib en termcap et a ajouté un autre programme de test. La bibliothèque est restée largement la même jusqu'à 4.3BSD (juin 1986). 4.4BSD-Lite (juin 1994) l'a refactorée, laissant l'API

inchangée.

Les prototypes de fonctions étaient une caractéristique d'ANSI C (1989). La bibliothèque était bien antérieure à la norme et ne fournissait donc aucun fichier d'en-tête les déclarant. Néanmoins, les sources BSD ont inclus deux fichiers d'en-tête termcap.h différents au fil du

temps.
  • L'un était utilisé en interne par jove(1) à partir de 4.3BSD. Il déclarait des symboles globaux pour les variables termcap qu'il
    • utilisait.
  • L'autre est apparu dans 4.4BSD-Lite Release 2 (juin 1995) dans le cadre de libedit (aussi connu sous le nom de bibliothèque editline). L'historique des sources CSRG montre que cela a été ajouté au milieu de 1992. Le fichier d'en-tête libedit était utilisé en interne par commodité pour compiler la bibliothèque editline. Il déclarait des prototypes de fonctions, mais pas de variables globales. Ce fichier d'en-tête a été ajouté à la bibliothèque termcap de NetBSD
    • au milieu
de 1994.

Entre-temps, le développement de termcap de GNU a commencé en 1990. Sa première version (1.0) en 1991 incluait un en-tête termcap.h. Sa seconde (1.1) en septembre 1992 a modifié l'en-tête pour utiliser const pour les prototypes de fonctions dans l'en-tête là où on s'attendrait à ce que les paramètres soient en lecture seule. BSD termcap ne le faisait pas. Le prototype pour tputs différait également, mais dans ce cas, c'est libedit qui différait de termcap

BSD.

GNU termcap 1.3 a été regroupé avec bash(1) au milieu de 1993 pour prendre en charge la bibliothèque readline

(3).

ncurses 1.8.1 (novembre 1993) fournissait un fichier termcap.h. Il reflétait l'influence de termcap GNU et emacs(1) (plutôt que jove(1)), fournissant l'interface suivante

:
  • symboles globaux utilisés par emac
    • s,
  • prototypes de fonctions qualifiés par const,
    • et
  • un prototype pour tparam, une fonctionnalité de termca
    • p G
NU.

Plus tard (au milieu de 1996), la fonction tparam a été retirée de ncurses. Deux des quatre implémentations diffèrent donc entre elles, et les programmes qui visent à fonctionner avec toutes les interfaces de bibliothèque termcap doivent teni

r compte d
e ce fait.

BOGUE

S

Si vous appelez tgetstr pour récupérer column_address (ch) ou toute autre capacité de chaîne paramétrée, sachez qu'elle est retournée en notation terminfo, et non en la plus ancienne et pas tout à fait compatible notation termcap. Cela ne pose pas de problème si tout ce que vous en faites est d'appeler tgoto ou tparm, qui développent tous deux paramétriquement les capacités de chaîne de style terminfo comme le fait terminfo. (Si ncurses est configuré pour prendre en charge termcap, tgoto vérifie si la chaîne est de style terminfo en cherchant des paramètres «%p » ou des délais «<...> », et invoque un analyseur de style termcap si la chaîne semble ne pas utiliser la syntaxe terminf

o.)

Comme la syntaxe de terminfo pour le remplissage dans les capacités de chaîne diffère de celle de termcap, les utilisateurs peuvent être

surpris.
