CKSUM(1P) Manuel du programmeur POSIX CKSUM(1P)

PROLOGUE

Cette page manuelle fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page manuelle Linux correspondante pour les détails du comportement de Linux), ou l'interface peut ne pas être implémentée sur Linux.

NOM

cksum — écrire les sommes de contrôle et les tailles des fichiers

SYNOPSIS

cksum [fichier...]

DESCRIPTION

L'utilitaire cksum doit calculer et écrire sur la sortie standard une somme de contrôle par redondance cyclique (CRC) pour chaque fichier d'entrée, et doit également écrire sur la sortie standard le nombre d'octets dans chaque fichier. Le CRC utilisé est basé sur le polynôme utilisé pour la vérification d'erreurs CRC dans la norme ISO/IEC 8802‐3:1996 (Ethernet).

L'encodage de la somme de contrôle CRC est défini par le polynôme générateur :

G(x)=x32+x26+x23+x22+x16+x12+x11+x10+x8+x7+x5+x4+x2+x+1

Mathématiquement, la valeur CRC correspondant à un fichier donné doit être définie par la procédure suivante :

1.
Les n bits à évaluer sont considérés comme les coefficients d'un polynôme modulo 2 M(x) de degré n-1. Ces n bits sont les bits du fichier, le bit de poids fort étant le bit de poids fort du premier octet du fichier et le dernier bit étant le bit de poids faible du dernier octet, complétés par des bits zéro (si nécessaire) pour obtenir un nombre entier d'octets, suivis d'un ou plusieurs octets représentant la longueur du fichier comme une valeur binaire, l'octet de poids faible en premier. Le plus petit nombre d'octets capable de représenter cet entier doit être utilisé.
2.
M(x) est multiplié par x32 (c'est-à-dire décalé de 32 bits vers la gauche) et divisé par G(x) en utilisant une division modulo 2, produisant un reste R(x) de degré ≤ 31.
3.
Les coefficients de R(x) sont considérés comme une séquence de 32 bits.
4.
La séquence de bits est complémentée et le résultat est le CRC.

OPTIONS

Aucune.

OPÉRANDES

L'opérande suivante doit être prise en charge :

fichier
Chemin d'accès d'un fichier à vérifier. Si aucun fichier opérande n'est spécifié, l'entrée standard doit être utilisée.

STDIN

L'entrée standard doit être utilisée si aucun fichier opérande n'est spécifié, et doit être utilisée si un fichier opérande est '-' et que l'implémentation traite le '-' comme signifiant l'entrée standard. Sinon, l'entrée standard ne doit pas être utilisée. Voir la section FICHIERS D'ENTRÉE.

FICHIERS D'ENTRÉE

Les fichiers d'entrée peuvent être de n'importe quel type.

VARIABLES D'ENVIRONNEMENT

Les variables d'environnement suivantes doivent affecter l'exécution de cksum:

LANG
Fournir une valeur par défaut pour les variables d'internationalisation qui ne sont pas définies ou qui sont nulles. (Voir le volume Définitions de base de POSIX.1‐2017, Section 8.2, Variables d'internationalisation pour la priorité des variables d'internationalisation utilisées pour déterminer les valeurs des catégories de locale.)
LC_ALL
Si défini à une valeur de chaîne non vide, remplace les valeurs de toutes les autres variables d'internationalisation.
LC_CTYPE
Détermine la locale pour l'interprétation des séquences d'octets de données de texte en tant que caractères (par exemple, caractères d'un seul octet par opposition à caractères multi-octets dans les arguments).
LC_MESSAGES

Détermine la locale qui doit être utilisée pour affecter le format et le contenu des messages de diagnostic écrits sur l'erreur standard.
NLSPATH
Détermine l'emplacement des catalogues de messages pour le traitement de LC_MESSAGES.

ÉVÉNEMENTS ASYNCHRONES

Par défaut.

STDOUT

Pour chaque fichier traité avec succès, l'utilitaire cksum doit écrire au format suivant :

"%u %d %s\n", <somme de contrôle>, <nb d'octets>, <chemin d'accès>

Si aucun fichier opérande n'a été spécifié, le chemin d'accès et son <espace> initial doivent être omis.

STDERR

L'erreur standard ne doit être utilisée que pour les messages de diagnostic.

FICHIERS DE SORTIE

Aucun.

DESCRIPTION ÉTENDUE

Aucune.

CODE DE RETOUR

Les codes de retour suivants doivent être renvoyés :

0
Tous les fichiers ont été traités avec succès.
>0
Une erreur s'est produite.

UTILISATION PAR LES APPLICATIONS

L'utilitaire cksum est typiquement utilisé pour comparer rapidement un fichier suspect à une version de confiance du même fichier, par exemple pour s'assurer que les fichiers transmis sur des supports bruyants arrivent intacts. Cependant, cette comparaison ne peut pas être considérée comme cryptographiquement sûre. Les chances qu'un fichier endommagé produise le même CRC que l'original sont faibles ; la tromperie délibérée est difficile, mais probablement pas impossible.

Bien que les fichiers d'entrée de cksum puissent être de n'importe quel type, les résultats ne correspondent pas nécessairement à ce qui serait attendu sur des fichiers de périphériques spéciaux de caractère ou sur des types de fichiers non décrits par le volume Interfaces système de POSIX.1‐2017. Puisque ce volume de POSIX.1‐2017 ne spécifie pas la taille de bloc utilisée lors de l'entrée, les sommes de contrôle des fichiers spéciaux de caractère ne traitent pas nécessairement toutes les données de ces fichiers.

L'algorithme est exprimé en termes d'un flux de bits divisé en octets. Si un fichier est transmis entre deux systèmes et subit une transformation de données (comme le changement de l'ordre des octets little-endian en big-endian), des valeurs CRC identiques ne peuvent pas être attendues. Les implémentations effectuant de telles transformations peuvent étendre cksum pour gérer de telles situations.

unsigned long memcrc(const unsigned char *b, size_t n)
{
/*  Arguments d'entrée :
 *  const unsigned char*   b == séquence d'octets pour laquelle calculer la somme de contrôle
 *  size_t                 n == longueur de la séquence
 */
    register size_t i;
    register unsigned c, s = 0;
    for (i = n; i > 0; --i) {
        c = *b++;
        s = (s << 8) ^ crctab[(s >> 24) ^ c];
    }
    /* Étendre avec la longueur de la chaîne. */
    while (n != 0) {
        c = n & 0377;
        n >>= 8;
        s = (s << 8) ^ crctab[(s >> 24) ^ c];
    }
    return ~s;
}

La pratique historique d'écrire le nombre de « blocs » a été remplacée par l'écriture du nombre d'octets, car ce dernier est non seulement plus utile, mais aussi parce que les implémentations historiques n'ont pas été cohérentes dans la définition de ce qu'était un « bloc ».

L'algorithme utilisé a été choisi pour accroître la robustesse opérationnelle de cksum. Ni l'algorithme de System V ni celui de BSD sum n'ont été choisis. Comme chacun de ces algorithmes était différent et que chacun était le comportement par défaut sur ces systèmes, aucun compromis réaliste n'était disponible si l'un d'eux était choisi — un ensemble d'applications historiques se serait brisé. Par conséquent, le nom a été changé en cksum. Bien que les commandes sum historiques soient probablement fournies pendant de nombreuses années, les programmes conçus pour la portabilité entre systèmes devraient utiliser le nouveau nom.

L'algorithme choisi est basé sur celui utilisé par la norme ISO/IEC 8802‐3:1996 (Ethernet) pour le champ de séquence de contrôle de trame. L'algorithme utilisé ne correspond pas à la définition technique d'une somme de contrôle; le terme est utilisé pour des raisons historiques. La longueur du fichier est incluse dans le calcul du CRC car cela fait écho à l'inclusion d'un champ de longueur par Ethernet dans son CRC, mais aussi car cela protège contre les collisions involontaires entre des fichiers commençant par des séries différentes d'octets zéros. La probabilité que deux fichiers différents produisent des CRC identiques est bien plus grande lorsque leurs longueurs ne sont pas prises en compte. Séparer la longueur et la somme de contrôle du fichier lui-même produirait un algorithme légèrement plus robuste, mais l'usage historique a toujours été qu'un seul nombre (la somme de contrôle telle qu'imprimée) représente la signature du fichier. Il a été décidé que l'usage historique était la considération la plus importante.

Les propositions initiales contenaient des modifications à l'algorithme Ethernet impliquant l'extraction de valeurs du tableau chaque fois qu'un résultat intermédiaire devenait zéro. Il a été démontré que cela était moins robuste que la méthode actuelle et mathématiquement difficile à décrire ou à justifier.

Le calcul utilisé est identique à celui donné en pseudo-code dans l'article de Sarwate référencé. La représentation en pseudo-code est :

X <- 0; Y <- 0;
for i <- m -1 step -1 until 0 do
    begin
    T <- X(1) ^ A[i];
    X(1) <- X(0); X(0) <- Y(1); Y(1) <- Y(0); Y(0) <- 0;
    commentaire : f[T] et f'[T] désignent les mots d'indice T dans
        les tableaux f et f' ;
    X <- X ^ f[T]; Y <- Y ^ f'[T];
    end

Le pseudo-code est reproduit exactement tel que donné ; cependant, notez que dans le cas de cksum, A[i] représente un octet du fichier, les mots X et Y sont traités comme une seule valeur de 32 bits, et les tableaux f et f' sont un tableau unique contenant des valeurs de 32 bits.

L'article de Sarwate référencé discute également de la génération du tableau.
