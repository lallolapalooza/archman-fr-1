NOM

Glib::xsapi - Référence de l'API interne pour GPerl.

SYNTAXE

#include <gperl.h>

DESCRIPTION

Ceci est la référence de l'API pour les développeurs de liaisons de GPerl, générée automatiquement à partir des fichiers source xs. Cet en-tête définit l'interface publique à utiliser lors de la création de nouvelles liaisons de langage Perl pour les bibliothèques C basées sur GLib.

gperl.h inclut pour vous tous les en-têtes nécessaires à l'écriture de XSUBs (EXTERN.h, perl.h et XSUB.h), ainsi que tout GLib (via glib-object.h).

Objets Exception GError

GError est un mécanisme pour propager les informations d'erreur / exception d'exécution en C, qui est un langage sans support natif pour les exceptions. GError utilise un code d'erreur simple, généralement défini comme un énuméré. Comme les énumérés se chevaucheront, GError inclut le GQuark correspondant à un "domaine" d'erreur particulier pour vous dire quels codes d'erreur seront utilisés. Il y a aussi une chaîne contenant un message d'erreur spécifique. Les chaînes sont arbitraires et peuvent être traduites, mais les domaines et les codes sont définis.

Perl a un support natif pour les exceptions, en utilisant "eval" comme "try", "croak" ou "die" comme "throw", et "if ($@)" comme "catch". $@ peut, en fait, être n'importe quel scalaire, y compris des objets bénis.

Ainsi, GPerl associe GError de GLib aux exceptions Perl.

Étant donné que, comme nous l'avons décrit ci-dessus, les messages d'erreur ne sont pas garantis d'être uniques partout, nous devons prendre en charge l'utilisation des domaines d'erreur et des codes. Le choix évident ici est d'utiliser des objets exception ; cependant, pour prendre en charge les objets exception bénis, nous devons effectuer un peu de magie noire dans les liaisons. Il n'y a pas d'association intégrée entre un quark de domaine d'erreur et le GType de l'énumération de code d'erreur correspondante, donc les liaisons fournissent les deux lors de la spécification du nom du package dans lequel bénir les exceptions de ce domaine. Toutes les exceptions basées sur GError dérivent de Glib::Error, bien sûr, et cette classe de base fournit toute la fonctionnalité, y compris la conversion en chaîne.

Tout ce que vous aurez vraiment besoin de faire est d'enregistrer les domaines d'erreur avec "gperl_register_error_domain", et de lancer des erreurs avec "gperl_croak_gerror".

void gperl_register_error_domain (GQuark domain, GType error_enum, const char * package)
Indique aux liaisons de bénir les GErrors avec error->domain == domain dans package, et d'utiliser error_enum pour trouver les pseudonymes des codes d'erreur. Cela appellera "gperl_set_isa" sur package pour ajouter "Glib::Error" à @ISA de package.

domain ne peut pas être 0, et package ne peut pas être NULL ; quel serait l'intérêt ? error_enum peut être 0, auquel cas vous n'obtiendrez pas de valeurs d'erreur fantaisistes en chaîne.

GLog

GLib possède un mécanisme de journalisation des messages qu'il utilise pour les macros d'assertion g_return_if_fail(), etc. ; il est vraiment polyvalent et vous permet de définir divers niveaux comme fatals et autres. Les bibliothèques utilisent cela pour divers types de rapports de messages.

Ces fonctions vous permettent de rediriger ces messages depuis Perl. Par défaut, les niveaux warning, critical et message passent par warn() de perl, et les niveaux fatals passent par croak(). [je ne suis pas sûr que ces messages parviennent à croak() avant que GLib ne les fasse abort()...]

gint gperl_handle_logs_for (const gchar * log_domain)
Redirige tous les g_logs pour log_domain vers la gestion des logs de gperl. Vous devrez enregistrer les domaines dans chaque sous-module de liaison, car il n'y a aucun moyen pour nous de les connaître ici.

Et, techniquement, cela intercepte tous les niveaux de log prédéfinis, pas ceux que vous (ou votre bibliothèque) pouvez définir pour vous-même.

Chaînes UTF-8 avec gchar

Par convention, gchar* est supposé pointer vers des données de chaîne UTF8, et char* pointe vers des données de chaîne ascii. Ici, nous définissons une paire de wrappers pour le code répétitif de mise à niveau des chaînes Perl. Ils sont implémentés sous forme de fonctions plutôt que de macros, car les expressions avec virgule dans les macros ne sont pas prises en charge par tous les compilateurs.

Ces fonctions doivent être utilisées à la place de newSVpv et SvPV_nolen dans tous les cas qui traitent des types gchar*.

GObjec

t

Pour gérer l'interaction complexe des différentes sémantiques de comptage de références des objets perl par rapport aux GObjects, les liaisons créent un PerlObject+GObject combiné, avec le pointeur du GObject dans la magie attachée à l'objet perl, et le pointeur de l'objet perl dans les données utilisateur du GObject. Ainsi, ce n'est pas vraiment un « wrapper », mais nous le désignons ainsi, car « objet perl + GObject combiné » est une expression lourde et

confuse.

Les GObjects sont représentés comme des références de hash bénies. Le mécanisme de données utilisateur du GObject n'est pas typesafe, et n'est donc utilisé que pour des valeurs entières non signées ; le hash au niveau perl est disponible pour tout type de données utilisateur. La nature combinée du wrapper signifie que les données stockées dans le hash persisteront tant que l'objet est en

vie.

Puisque le pointeur C est stocké dans la magie attachée, le pointeur C n'est pas disponible pour le développeur perl via l'objet hash, il n'y a donc pas de risque de le casser depuis

perl.

Les remerciements vont à Marc Lehmann pour avoir imaginé la plupart de

cela.
