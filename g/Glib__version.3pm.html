SYNOPSI

# exiger au moins la version 1.021 du module Glib
use Glib '1.021';
# g_set_application_name() a été introduite dans GLib 2.2.0, et
# a été prise en charge pour la première fois par la version 1.040 du module Perl Glib.
if ($Glib::VERSION >= 1.040 and Glib->CHECK_VERSION (2,2,0)) {
   Glib::set_application_name ('My Cool Program');

DESCRIPTIO

N

Le module Glib et la bibliothèque C GLib sont tous deux en cours de développement, et leurs interfaces évoluent avec le temps. À mesure que de nouvelles fonctionnalités sont ajoutées à chacun, et que votre code utilise ces nouvelles fonctionnalités, vous introduirez des dépendances spécifiques à la version, et naturellement, vous voudrez pouvoir contourner ces dépendances dans votre code. Voici l'API de gestion des

versions.

Pour les modules Perl simples, un seul numéro de version est suffisant ; cependant, Glib est un lien vers une autre bibliothèque logicielle, ce qui introduit une certaine complexité. Nous avons trois versions qui spécifient complètement l'API qui vous est

disponible.
Version des liens
Perl
Les modules Perl utilisent un numéro de version, et Glib ne fait pas exception. $Glib::VERSION est la version du module Glib actuel. Par convention informelle, les modules gtk2-perl utilisent généralement des numéros de version de la forme x.yyz, où les valeurs paires de yy indiquent des versions stables et z est un niveau de correctif.

Laquelle utiliser et quand

?

Où utiliser quelle version ? Cela dépend entièrement de ce que vous faites. Expliquons par un exemple

:
o Utiliser la version du module Perl pour les problèmes de support des
liens
Vous devez enregistrer une nouvelle énumération pour l'utiliser en tant que type d'une propriété d'objet. C'est quelque chose que vous pouvez faire avec toutes les versions de la bibliothèque C sous-jacente, mais qui n'était pas pris en charge dans le module Perl Glib jusqu'à $Glib::VERSION >= 1.
040.
o Utiliser la version liée pour les fonctionnalités de la
bibliothèque
Vous voulez appeler Glib::set_application_name pour définir un nom lisible par l'humain pour votre application (qui est utilisé par diverses parties de Gtk2 et Gnome2). g_set_application_name() (la fonction C sous-jacente) a été ajoutée dans la version 2.2.0 de glib, et la prise en charge a été introduite dans le module Perl Glib dans la version 1.040. Cependant, vous pouvez compiler le module Perl contre n'importe quelle version stable 2.x.x de glib, vous pourriez donc ne pas avoir cette fonction disponible même si votre module Glib est assez récent !
Ainsi, vous devez vérifier deux choses pour voir si cette fonction est disponible : 
if ($Glib::VERSION >= 1.040 && Glib->CHECK_VERSION (2,2,0)) {
    # elle est disponible, et nous pouvons l'appeler !
    Glib::set_application_name ('My Cool Application')
; }

Que se passe-t-il maintenant si vous avez installé le module Perl lorsque votre système avait glib 2.0.6, et que vous avez mis à niveau glib vers 2.4.1 ? Ne serait-il pas que g_set_application_name() soit disponible ? Eh bien, elle est là, sous le capot, mais les liens ont été compilés lorsqu'elle n'y était pas, vous ne pourrez donc pas l'appeler ! C'est pour

quoi nous vérifions la version "liée" ou à la compilation. Par ailleurs, pour activer la prise e
n charge de la nouvelle fonction, vous devriez réinstaller (ou mettre à niveau) le module Perl.
o Utiliser la version liée pour les contournements à
l'exécution
Supposons qu'il y ait une fonction dont l'API n'a pas changé, mais dont l'implémentation avait un bogue dans une version qui a été corrigé dans une autre version. Pour déterminer si vous devez appliquer un contournement, vous vérifieriez la version qui est réellement utilisée à l'exécution. 
if (Glib::major_version == 2 &&
    Glib::minor_version == 2 &&
    Glib::micro_version == 1) {
   # contourner le bogue qui n'existe que dans glib 2.
2.1. }
