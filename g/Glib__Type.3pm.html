Enregistre new_package comme un dérivé officiellement sanctionné par GLib du (dérivé GObject) parent_package. Cela configure automatiquement une entrée @ISA pour vous et crée un nouveau GObjectClass en

interne.

Les paramètres ... sont des paires clé/valeur, prenant actuellement en charge

:
signals =>
HASHREF
La clé "signals" contient un hachage, indexé par les noms de signaux, qui décrit comment configurer les signaux pour new_package.

Si la valeur est une référence de code, le signal nommé doit exister quelque part dans parent_package ou son ascendance ; la référence de code sera utilisée pour remplacer la fermeture de classe pour ce signal. C'est la façon officiellement sanctionnée de remplacer les méthodes virtuelles sur les Glib::Objects. La valeur peut être une chaîne plutôt qu'une référence de code, auquel cas le sous-programme avec ce nom dans new_package sera utilisé. (La fonction ne doit pas être

héritée.)

Si la valeur est une référence de hachage, la clé sera le

nom d'un nouveau signal créé avec les propriétés
définies dans le hachage. Toutes les propriétés
sont facultatives, avec des valeurs par défaut fournies :
class_closure => sous-programme ou
undef
Utilisez cette référence de code (ou nom de sous-programme) comme fermeture de classe (c'est-à-dire le gestionnaire par défaut pour le signal). Si non spécifié, "do_signal_name", dans le paquet courant, est
utilisé.
return_type => nom de paquet ou
undef
Type de retour pour le signal. Si non spécifié, le signal a un retour
void.
param_types =>
ARRAYREF
Référence vers une liste de types de paramètres (noms de paquets), en omettant l' instance et les données utilisateur. Les rappels connectés à ce signal recevront l'objet d'instance comme premier argument, suivis des arguments avec les types listés ici, et enfin par les données utilisateur fournies lors de la connexion du rappel. Ne pas spécifier cette clé équivaut à fournir une liste vide, ce qui signifie en réalité instance et peut-être
data.
flags => Glib::
SignalFlags
Drapeaux décrivant les propriétés de ce signal. Voir la description de GSignalFlags dans la référence de l'API C de GObject pour une description
complète.
accumulator => sous-programme ou
undef
L'accumulateur de signal est un rappel spécial qui peut être utilisé pour collecter les valeurs de retour des dif
férents rappels appelés lors d'une émission de signal. Généralement, vous pouvez omettre ce paramètre ; les accum
ulateurs personnalisés sont utilisés pour faire des choses comme arrêter la propagation du signal par valeur de
retour ou créer une liste de retours, etc. Voir "SIGNALS" dans Glib::Object::Subclass pour plus de détails.
properties =>
ARRAYREF
Tableau d'objets Glib::ParamSpec, chacun décrivant une propriété d'objet à ajouter au nouveau type. Ces propriétés sont disponibles pour une utilisation par tout le code qui peut accéder à l'objet, quelle que soit la langue d'implémentation. Voir Glib::ParamSpec. Cette liste peut être vide ; si elle ne l'est pas, les fonctions "GET_PROPERTY" et "SET_PROPERTY" dans $new_package seront appelées pour obtenir et définir les valeurs. Notez qu'une propriété d'objet est simplement un mécanisme pour obtenir et définir une valeur -- cela n'implique aucun stockage. Cependant, par commodité, Glib::Object fournit des solutions de repli pour GET_PROPERTY et SET_PROPERTY qui utilisent les surnoms de propriété comme clés de hachage dans la variable d'objet pour le stockage.

De plus, vous pouvez spécifier des ParamSpecs sous forme de hachage descriptif au lieu d'un objet ; cette forme vous permet de fournir des méthodes getter et setter explicites qui remplacent GET_PROPERY et SET_PROPERTY. Le getter et le setter sont tous deux facultatifs dans la forme hachage. Par

exemple : 
Glib::Type->register_object ('Glib::Object', 'Foo',
   properties => [
      # spécifié normalement
      Glib::ParamSpec->string (...),
      # spécifié explicitement
      {
         pspec => Glib::ParamSpec->int (...),
         set => sub {
            my ($object, $newval) = @_;
            ...
         },
         get => sub {
            my ($object) = @_;
            ...
            return $val;
         },
      },
] );

Vous pouvez mélanger les deux styles de déclaration comme vous le souhaitez. Si vous avez des méthodes individuelles "get_foo" / "set_foo" avec le code opérationnel pour une propriété, alors la forme "get"/"set" est une façon pr

atique d'y accéd
er directement.

ARRAYREF
Tableau de noms de paquets d'interfaces que le nouvel objet implémente. Les interfaces sont la façon GObject de faire de l'héritage multiple, ainsi, en Perl, les noms de paquets seront préfixés à @ISA et certaines méthodes ALLCAPS héritables et surchargeables seront automatique
ment appelées lorsque nécessaire. Quelles mé
thodes exactement dépend de l'interface -- Gt

DITING, EDITING_DONE et REMOVE_WIDGET.
