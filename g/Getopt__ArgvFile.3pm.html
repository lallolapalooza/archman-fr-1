NOM

Getopt::ArgvFile - interpole les options de script depuis des fichiers dans @ARGV ou un autre tableau

VERSION

Ce manuel décrit la version 1.11.

RÉSUMÉ

Invocation en une ligne - les indications d'options sont traitées pendant le chargement du module :

# charge le module et traite les indications de fichier d'options dans @ARGV
use Getopt::ArgvFile default=>1;

# charge un autre module pour évaluer les options, par ex. :
use Getopt::Long;
...
# évalue les options, par ex. de cette manière courante :
GetOptions(\%options, 'any');    # cette fonction est définie dans Getopt::Long

Ou supprimez le traitement des indications d'options lors du chargement du module, pour le faire plus tard :

# charge le module, ne *traite pas* les indications de fichier d'options
use Getopt::ArgvFile justload=>1;

# charge un autre module pour évaluer les options, par ex. :
use Getopt::Long;
...
# *maintenant*, résolvez les indications de fichier d'options
Getopt::ArgvFile::argvFile(default=>1);
# évalue les options, par ex. de cette manière courante :
GetOptions(\%options, 'any');    # cette fonction est définie dans Getopt::Long

Ou utilisez l'invocation traditionnelle en deux étapes du chargement du module avec l'importation de symboles et le traitement explicite du fichier d'options :

# Charge le module et importe le symbole &argvFile
# - ceci ne *traitera pas* les indications d'options.
# Utilisez *cette* syntaxe pour ce faire, *exactement*.
use Getopt::ArgvFile qw(argvFile);
# charge un autre module pour évaluer les options, par ex. :
use Getopt::Long;
...
# *maintenant*, résolvez les indications de fichier d'options
argvFile(default=>1);
# évalue les options, par ex. de cette manière courante :
GetOptions(\%options, 'any');    # cette fonction est définie dans Getopt::Long

Si les options doivent être traitées dans un autre tableau, cela peut se faire de cette manière :

# prépare le tableau cible
my @options=('@options1', '@options2', '@options3');
...
# remplace les indications de fichier par les options stockées dans les fichiers
argvFile(array=>\@options);

Si vous n'aimez pas le préfixe "@", il est possible de définir une option à utiliser à la place :

# prépare le tableau cible
my @options=('-options', 'options1', '-options', 'options2');
...
# remplace les indications de fichier par les options stockées dans les fichiers
argvFile(fileOption=>'options', array=>\@options);

DESCRIPTION

Ce module interpole simplement les indications de fichier d'options dans @ARGV par le contenu des fichiers pointés. Cela permet la lecture des options depuis des fichiers au lieu de ou en plus de la lecture habituelle depuis la ligne de commande.

Alternativement, vous pouvez traiter n'importe quel tableau au lieu de @ARGV qui est utilisé par défaut et mentionné principalement dans ce manuel.

Le @ARGV interpolé pourrait être traité ultérieurement par le traitement d'options habituel, par ex. par un module Getopt::xxx. Getopt::ArgvFile ne effectue aucun traitement d'options lui-même, il prépare seulement le tableau @ARGV.

Les fichiers d'options peuvent simplifier considérablement l'appel d'un script. Imaginez ce qui suit :

Dépasser les limites de la ligne de commande
Un script peut offrir de nombreuses options, certaines prenant éventuellement des paramètres. Si ces options et leurs paramètres sont transmis directement à l'appel du programme, le nombre de caractères accepté par la ligne de commande de votre shell peut être dépassé.

Perl lui-même ne limite pas le nombre de caractères transmis à un script par des paramètres, mais le shell ou l'interpréteur de commandes définit souvent une limite ici. Le même problème peut survenir si vous voulez stocker un long appel dans un fichier système comme crontab.

Si une telle limite vous restreint, les options et les paramètres peuvent être déplacés dans des fichiers d'options, ce qui résultera en un appel de ligne de commande plus court.

Appels de script préparés par des scripts
Parfois un script appelle un autre script. Les options transmises au script imbriqué pourraient dépendre de situations variables, comme la saisie d'un utilisateur ou l'environnement détecté. Dans un tel cas, il peut être plus facile de générer un fichier d'options intermédiaire qui est ensuite transmis au script imbriqué.

Ou imaginez deux tâches cron l'une préparant l'autre : la première peut générer un fichier d'options qui est ensuite utilisé par la seconde.

Accès simple à des scénarios d'appel typiques
Si plusieurs options doivent être définies, mais sont toujours les mêmes dans certaines circonstances, cela peut devenir légèrement agaçant de les saisir encore et encore. Avec un fichier d'options, elles peuvent être stockées une fois et rappelées facilement aussi souvent que nécessaire.

De plus, les fichiers d'options peuvent être utilisés pour regrouper des options. Plusieurs paramètres peuvent configurer un certain comportement du programme, tandis que d'autres en influencent un autre. Ou un certain ensemble d'options peut être utile dans une situation typique, tandis qu'un autre devrait être utilisé ailleurs. Ou il y a un ensemble commun d'options qui doit être utilisé dans chaque appel, tandis que d'autres options sont ajoutées en fonction des besoins actuels. Ou il y a quelques groupes d'utilisateurs avec des manières différentes mais typiques d'appeler votre script. Dans tous ces cas, les fichiers d'options peuvent rassembler les options appartenant ensemble, et peuvent être combinées par les utilisateurs du script pour configurer un certain appel. En conjonction avec la possibilité de imbriquer de telles collections, c'est peut-être la fonctionnalité la plus puissante offerte par cette méthode.

Options par défaut individuelles et valables pour toute l'installation
Le module permet au programmeur d'activer des configurations d'options par défaut par les utilisateurs ; à la fois pour les utilisateurs individuels ou généralement pour tous les appelants d'un script. C'est particulièrement utile pour les administrateurs qui peuvent configurer le comportement par défaut d'un script en configurant son fichier d'options de démarrage valable pour toute l'installation. Tous les utilisateurs du script sont alors libres d'oublier complètement toute option de configuration déjà configurée. Et si l'un d'entre eux ajoute régulièrement certaines options à chaque appel, il pourrait les stocker dans son fichier d'options de démarrage individuel.

Par exemple, j'utilise cette fonctionnalité pour rendre mes scripts à la fois flexibles et utilisables. J'ai plusieurs scripts accédant à une base de données via DBI. Les paramètres du compte de base de données ainsi que les paramètres de démarrage DBI ne devraient pas être codés à l'intérieur des scripts car ce n'est pas très flexible, donc je les ai implémentés par des options. Mais d'un autre côté, il ne devrait pas y avoir besoin pour un utilisateur normal de transmettre tous ces paramètres à chaque appel de script. Ma solution pour cela est d'utiliser des fichiers d'options par défaut configurés et maintenus par un administrateur. C'est très transparent, la plupart des utilisateurs ne savent rien de ces paramètres de configuration (documentés ;-) ... et si quelque chose change, seuls les fichiers d'options doivent être adaptés.

EXPORTS

Aucun symbole n'est exporté par défaut, mais vous pouvez explicitement importer la fonction "argvFile()" en utilisant la syntaxe exacte de l'exemple suivant:

use Getopt::ArgvFile qw(argvFile);

Veuillez noter que cette interface est fournie pour la rétrocompatibilité avec les versions jusqu'à 1.06. En chargeant le module de cette manière, les mécanismes d'importation traditionnels prennent effet et argvFile() n'est pas appelée implicitement.

Cela signifie que tandis que les indications de fichier d-options sont généralement traitées implicitement quand "Getopt::ArgvFile" est chargé, la syntaxe

use Getopt::ArgvFile qw(argvFile);

nécessite un appel supplémentaire de argvFile() pour traiter les fichiers d'options.

FONCTIONS

Il n'y a qu'une seule fonction, argvFile(), qui fait tout le travail de traitement des indications de fichier d'options.

Veuillez noter qu'avec la version 1.07 et supérieure argvFile() est appelée implicitement quand le module est chargé, sauf si cela est fait de l'une des manières suivantes :

# l'interface traditionnelle - fournie pour
# la rétrocompatibilité - ceci charge le
# module et importe le symbole &argvFile
use Getopt::ArgvFile qw(argvFile);
--
# le traitement du fichier d'options est explicitement supprimé
use Getopt::ArgvFile justload=>1;

Excepté pour le chargement traditionnel, l'interface complète de argvFile() est disponible via "use", mais dans la syntaxe "use" typique sans parenthèses.

# appel implicite de argvFile(default=>1, home=>1)
use Getopt::ArgvFile default=>1, home=>1;t;1;

OPTIONS PAR FICHIER

Il est également possible de définir une option qui peut être utilisée à la place d'un préfixe, en utilisant le paramètre optionnel fileOption :

# installer une option de fichier
# (toutes les lignes sont équivalentes)
argvFile(fileOption=>'options');
argvFile(fileOption=>'-options');
argvFile(fileOption=>'+options');
argvFile(fileOption=>'--options');

Le nom de l'option peut être spécifié avec ou sans les préfixes d'option habituels "-", "--" et "+".

Une fois qu'une option est déclarée, elle *peut* remplacer un préfixe. (Les préfixes restent actifs également.)

# avec -options déclaré comme option de fichier,
# ces séquences sont équivalentes
@file
-options file
# cinq cascades équivalentes
@@@@file
-options @@@file
-options -options @@file
-options -options -options @file
-options -options -options -options file

Veuillez noter que les préfixes sont joints au nom du fichier sans espaces entre eux, tandis que l'option déclarée via -fileOption est séparée du nom du fichier par un espace blanc, comme pour les options normales.

INVOCATION EN UNE LIGNE

La séquence traditionnelle en deux lignes

# charger le module
use Getopt::ArgvFile qw(argvFile);
...
# résoudre les fichiers d'options
argvFile(default=>1);

peut être réduite à une seule ligne - il suffit de passer les paramètres de argvFile() à use() :

# charger le module et traiter les indications de fichiers d'options dans @ARGV
use Getopt::ArgvFile default=>1;

Veuillez noter que dans ce cas, les indications de fichiers d'options sont traitées au moment de la compilation. Cela signifie que si vous souhaitez traiter des tableaux alternatifs, ces tableaux doivent être préparés à l'avance, généralement dans un bloc "BEGIN".

Dans les versions 1.07 et supérieures, la gestion implicite des fichiers d'options est la *valeur par défaut* et n'est supprimée que pour le chargement traditionnel

use Getopt::ArgvFile qw(argvFile);

pour des raisons de compatibilité ascendante. Un chargement simple comme

use Getopt::ArgvFile;

traitera *les* indications d'options ! Si vous souhaitez supprimer cela, utilisez le commutateur "justload" :

use Getopt::ArgvFile justload=>1;

Voir FONCTIONS pour des informations supplémentaires.

NOTES

Si un script appelant argvFile() avec le commutateur "default" est invoqué en utilisant un chemin relatif, il est fortement recommandé d'effectuer l'appel de argvFile() dans le répertoire de démarrage car argvFile() utilise alors également le chemin relatif du script.

LIMITES

Si un fichier d'options n'existe pas, argvFile() l'ignore simplement. Aucun message ne sera affiché, aucun code de retour spécial ne sera défini.
