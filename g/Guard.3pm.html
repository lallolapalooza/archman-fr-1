NOM

Guard - blocs de nettoyage sécurisés

SYNTAXE

use Guard;

# changer temporairement de répertoire pour "/etc", mais s'assurer
# de revenir à "/" quelle que soit la manière dont myfun se termine :
sub myfun {
   scope_guard { chdir "/" };
   chdir "/etc";

   code_that_might_die_or_does_other_fun_stuff;
}
# créer un objet qui, lorsque la dernière référence à celui-ci disparaît,
# exécute le bloc de code donné :
my $guard = guard { print "détruit !\n" };
undef $guard; # probablement détruit ici

DESCRIPTION

Ce module implémente les soi-disant "garde" (guards). Une garde est quelque chose (généralement un objet) qui "garde" une ressource, garantissant qu'elle sera nettoyée comme prévu.

Plus précisément, ce module prend en charge deux types de gardes différents : les objets garde, qui exécutent un bloc de code donné lorsqu'ils sont détruits, et les gardes de portée (scoped guards), qui sont liées à la sortie de portée.

FONCTIONS

Ce module exporte actuellement les fonctions "scope_guard" et "guard" par défaut.

scope_guard BLOC
scope_guard ($coderef)
Enregistre un bloc qui est exécuté lorsque la portée actuelle (bloc, fonction, méthode, eval, etc.) est quittée.

Voir la section EXCEPTIONS pour une explication sur la manière dont les exceptions (c'est-à-dire "die") sont gérées dans les blocs de garde.

La description ci-dessous peut sembler un peu compliquée, mais c'est juste parce que "scope_guard" essaie d'obtenir même les cas limites "justes" : l'objectif est de vous fournir un outil de nettoyage solide comme le roc.

Le comportement est similaire à ce fragment de code :

eval ... code suivant scope_guard ...
{
   local $@;
   eval BLOCK;
   eval { $Guard::DIED->() } if $@;
}
die if $@;

Sauf que c'est beaucoup plus rapide, et l'ensemble est exécuté même lorsque le BLOC appelle "exit", "goto", "last" ou s'échappe par d'autres moyens.

Si plusieurs BLOCs sont enregistrés pour la même portée, ils seront exécutés dans l'ordre inverse. D'autres choses liées à la portée telles que "local" sont gérées via le même mécanisme, donc les variables "local"isées après avoir appelé "scope_guard" seront restaurées lorsque la garde s'exécutera.

Exemple : changer temporairement le fuseau horaire du processus actuel, en s'assurant qu'il sera réinitialisé à la sortie de la portée "if" :

use Guard;
use POSIX ();
if ($need_to_switch_tz) {
   # s'assurer que tzset est appelé après que $ENV{TZ} a été restauré
   scope_guard { POSIX::tzset };
   # localiser après le scope_guard, de sorte qu'il soit annulé à temps
   local $ENV{TZ} = "Europe/London";
   POSIX::tzset;
   # faire quelque chose avec le nouveau fuseau horaire
}
my $guard = guard BLOC
my $guard = guard ($coderef)
Se comporte de la même manière que "scope_guard", sauf qu'au lieu d'exécuter le bloc à la sortie de la portée, il renvoie un objet dont la durée de vie détermine quand le BLOC est exécuté : lorsque la dernière référence à l'objet disparaît, le BLOC est exécuté comme avec "scope_guard".

Voir la section EXCEPTIONS pour une explication sur la manière dont les exceptions (c'est-à-dire "die") sont gérées dans les blocs de garde.

Exemple : acquérir un sémaphore Coro::Semaphore pour une seconde en enregistrant un minuteur. Le rappel du minuteur référence la garde utilisée pour le déverrouiller à nouveau. (Veuillez ignorer le fait que "Coro::Semaphore" possède une méthode "guard" qui fait déjà cela) :

use Guard;
use Coro::AnyEvent;
use Coro::Semaphore;
my $sem = new Coro::Semaphore;
sub lock_for_a_second {
   $sem->down;
   my $guard = guard { $sem->up };
   Coro::AnyEvent::sleep 1;
   # $sem->up est exécuté au retour
}

L'avantage de faire cela avec une garde au lieu d'appeler simplement "$sem->down" dans le rappel est que vous pouvez choisir de ne pas créer le minuteur, ou votre code peut lancer une exception avant qu'il ne puisse créer le minuteur (ou que le thread ne soit annulé), ou vous pouvez créer plusieurs minuteurs ou d'autres watchers d'événements et ce n'est que lorsque le dernier est exécuté que le verrou sera déverrouillé. En utilisant "guard", vous n'avez pas à vous soucier de rattraper tous les endroits où vous devez déverrouiller le semaphore.

$guard->cancel
Appeler cette fonction va "désactiver" l'objet garde retourné par la fonction "guard", c'est-à-dire qu'elle va libérer le BLOC passé initialement à "guard " et organisera pour que le BLOC ne soit pas exécuté.

Cela peut être utile lorsque vous utilisez "guard" pour créer un gestionnaire de nettoyage à appeler en cas de conditions fatales et que vous décidez plus tard qu'il n'est plus nécessaire.

EXCEPTIONS

Les blocs de garde ne devraient normalement pas lancer d'exceptions (c'est-à-dire "die"). Après tout, ils sont généralement utilisés pour nettoyer après de telles exceptions. Cependant, si quelque chose de vraiment exceptionnel se produit, un bloc de garde devrait bien sûr être autorisé à mourir. De plus, les erreurs de programmation sont une source majeure d'exceptions, et le programmeur veut certainement en être informé.

Comme dans la plupart des cas, le bloc exécuté lorsque la garde est exécutée ne connaît pas ou ne se soucie pas des blocs de garde, il est peu logique de laisser le code contenant gérer l'exception.

Par conséquent, chaque fois qu'un bloc de garde lance une exception, il sera capturé par Guard, suivi de l'appel du bloc de code stocké dans $Guard::DIED (avec $@ défini sur l'exception réelle), ce qui est similaire à la façon dont la plupart des boucles d'événements gèrent ce cas.

La valeur par défaut pour $Guard::DIED est d'appeler "warn "$@"", c'est-à-dire que l'erreur est imprimée sous forme d'avertissement et le programme continue.

La variable $@ sera restaurée à sa valeur avant l'appel de garde dans tous les cas, donc les gardes ne perturberont pas $@ d'une quelconque manière.

Le bloc de code stocké dans $Guard::DIED ne devrait pas mourir (le comportement n'est pas garanti, mais pour l'instant, l'exception sera simplement ignorée).

VOIR AUSSI

Scope::Guard et Sub::ScopeFinalizer, qui implémentent réellement uniquement des gardes à portée dynamique, pas les gardes à portée lexicale que leur documentation promet, et ont un surcoût CPU, mémoire et de frappe beaucoup plus élevé.

Hook::Scope, qui apparemment n'a jamais été terminé et peut corrompre la mémoire lors de son utilisation.

Scope::Guard semble avoir une grande section VOIR AUSSI pour encore plus de modules comme celui-ci.
