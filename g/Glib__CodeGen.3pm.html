Glib::CodeGen(3) Documentation Perl Contribuée par l'Utilisateur Glib::CodeGen(3)

NOM

Glib::CodeGen - utilitaires de génération de code pour les bindings basés sur Glib.

SYNOPSIS

# généralement dans Makefile.PL
use Glib::CodeGen;
# le plus courant, utilise tous les défauts
Glib::CodeGen->parse_maps ('monprefix');
Glib::CodeGen->write_boot;
# plus exotique, change tout
Glib::CodeGen->parse_maps ('foo',
                           input => 'foo.maps',
                           header => 'foo-autogen.h',
                           typemap => 'foo.typemap',
                           register => 'register-foo.xsh');
Glib::CodeGen->write_boot (filename => 'bootfoo.xsh',
                           glob => 'Foo*.xs',
                           ignore => '^(Foo|Foo::Bar)$');
# ajoute un gestionnaire de type personnalisé (rarement nécessaire)
Glib::CodeGen->add_type_handler (FooType => \&gen_foo_stuff);
# (voir la section EXTENSION DU SUPPORT DES TYPES pour plus d'infos.)

DESCRIPTION

Ce module regroupe une partie du code de base nécessaire pour effectuer la génération de code typiquement utilisée par les bindings Perl pour les bibliothèques basées sur GObject, en utilisant le module Glib comme base.

Les noms de fichiers de sortie par défaut se trouvent dans le sous-répertoire 'build', qui sera généralement présent si vous utilisez ExtUtils::Depends (comme devraient probablement le faire la plupart des extensions basées sur Glib).

MÉTHODES

Glib::CodeGen->write_boot;
Glib::CodeGen->write_boot (CLÉ => VALEUR, ...)
De nombreuses bibliothèques basées sur GObject à lier à Perl seront trop volumineuses pour être placées dans un seul fichier XS ; cependant, un seul fichier PM n'initialise généralement que le code d'un fichier XS. "write_boot" génère un fichier XSH à inclure dans la section BOOT du module qui est initialisé, en appelant le code de démarrage pour tous les autres fichiers XS du projet.

Les options sont passées à la fonction sous forme de paires clé/valeur, et toutes les options peuvent avoir une valeur par défaut.

filename     le nom du fichier de sortie à créer.
             la valeur par défaut est 'build/boot.xsh'.
glob         un motif glob qui spécifie les noms des
             fichiers xs à scanner pour les lignes MODULE.
             la valeur par défaut est 'xs/*.xs'.
xs_files     utilisez ceci pour fournir une liste explicite de
             noms de fichiers (sous forme de référence de tableau)
             à utiliser au lieu d'un motif glob. la valeur par
             défaut est d'utiliser le motif glob.
ignore       une expression régulière correspondant à tous les
             noms de modules qui doivent être ignorés, c'est-à-dire
             NON inclus dans la liste des symboles à démarrer.
             ce paramètre est extrêmement important pour
             éviter les boucles infinies au démarrage ; voir la
             discussion pour une explication et une justification.
             la valeur par défaut est '^[^:]+$', ou, tout nom qui
             ne contient pas de deux-points, c'est-à-dire tout
             nom de package de niveau supérieur.

Cette fonction effectue un glob (en utilisant l'opérateur glob intégré de Perl) sur le motif spécifié par l'option 'glob' pour obtenir une liste de noms de fichiers. Elle scanne ensuite chaque fichier de cette liste à la recherche de lignes correspondant au motif "^MODULE" -- c'est-à-dire la directive MODULE dans un fichier XS. Le nom du module est extrait et comparé à l'expression régulière spécifiée par le paramètre ignore. Si ce module ne doit pas être ignoré, nous vérifions ensuite si le nom a déjà été vu. Si ce n'est pas le cas, le nom sera converti en un symbole de démarrage (en gros, remplacer les ':' par '_' et préfixer par "boot_") et ce symbole sera ajouté à un appel à GPERL_CALL_BOOT dans le fichier généré ; il est ensuite marqué comme vu afin que nous ne l'appelions pas à nouveau.

À quoi tout cela sert-il, demandez-vous ? Pour lier une XSub à Perl, la fonction C doit être enregistrée auprès de l'interpréteur. C'est le rôle du code de "boot", qui est généralement appelé lors du processus d'initialisation. Cependant, lorsque plusieurs fichiers XS sont utilisés avec un seul fichier PM, un autre mécanisme doit appeler le code de démarrage de chaque fichier XS avant que toutes les fonctions qu'il contient ne soient disponibles.

Une configuration typique pour un module multi-XS, mono-PM consistera à appeler les différents morceaux de code de démarrage depuis la section BOOT: du fichier XS du module de niveau supérieur.

Pour utiliser Gtk2 comme exemple, lorsque vous faites 'use Gtk2', Gtk2.pm appelle bootstrap sur Gtk2, qui appelle la fonction C boot_Gtk2. Cette fonction appelle les symboles de démarrage pour tous les autres fichiers xs du module. La distinction est que le module de niveau supérieur, Gtk2, n'a pas de deux-points dans son nom.

"xsubpp" génère le nom de la fonction de démarrage en remplaçant les deux-points dans le nom du MODULE par des underscores et en préfixant par "boot_". Nous devons faire attention à ne pas inclure le code de démarrage du module initialisé (disons Toplevel, ou Gtk2, ou quoi que ce soit) car le code d'initialisation dans Toplevel.pm appellera boot_Toplevel lors de son chargement, et boot_Toplevel devrait en fait inclure le fichier que nous créons ici.

La valeur par défaut pour le paramètre ignore ignore tout nom ne contenant pas de deux-points, car on suppose qu'il s'agit d'un module de niveau supérieur, et tous les autres packages/modules qu'il initialise seront *en dessous* de cet espace de noms, c'est-à-dire qu'ils contiendront des deux-points. Cette hypothèse est valable pour Gtk2 et Gnome2, mais échoue évidemment pour quelque chose comme Gnome2::Canvas. Pour initialiser correctement ce module, vous devez utiliser une expression régulière telle que "^Gnome2::Canvas$".

Notez que vous pouvez, bien sûr, faire correspondre plus d'un nom, par exemple "^(Foo|Foo::Bar)$", si vous vouliez que Foo::Bar soit inclus dans le même objet chargé dynamiquement mais ne soit démarré que lorsque absolument nécessaire. (Si vous y parvenez, tant mieux pour vous.)

De plus, comme ce code scanne pour ^MODULE, vous devez commenter la section MODULE avec des marques # de début si vous voulez la cacher à "write_boot".

Glib::CodeGen->parse_maps (PREFIX, [CLÉ => VALEUR, ...])
La convention au sein de Glib/Gtk2 et leurs dérivés est d'utiliser des macros de préprocesseur dans le style de SvMyType et newSVMyType pour faire entrer et sortir des valeurs de/vers Perl, et d'utiliser ces mêmes macros à la fois dans le code écrit à la main ainsi que dans les typemaps. Cependant, si vous avez beaucoup de types dans votre bibliothèque (comme les près de 200 types de Gtk+ 2.x), alors l'écriture de ces macros devient incroyablement fastidieuse, surtout si l'on prend en compte toutes les variantes et autres.

Ainsi, cette fonction peut transformer un fichier plat contenant des descriptions concises des types en un fichier d'en-tête contenant toutes les macros de transtypage, un fichier typemap les utilisant, et un fichier XSH contenant le code approprié pour enregistrer chacun de ces types (à inclure par le code BOOT de votre module).

Le *PREFIX* est obligatoire, et est utilisé dans certains des noms de fichiers résultants. Vous pouvez également remplacer les valeurs par défaut en fournissant des paires clé=>valeur :

input    nom du fichier d'entrée. la valeur par défaut est 'maps'. si
         la valeur de cette clé est une référence de tableau, tous les
         noms de fichiers dans le tableau seront scannés.
header   nom du fichier d'en-tête à créer, la valeur par défaut est
         build/$prefix-autogen.h
typemap  nom du fichier typemap à créer, la valeur par défaut est
         build/$prefix.typemap
register nom du fichier xsh à contenir tous les
         enregistrements de types, la valeur par défaut est build/register.xsh

le fichier maps est une table de descriptions de types, une par ligne, avec des champs séparés par des espaces blancs. les champs devraient être :

TYPE macro    par exemple, GTK_TYPE_WIDGET
nom de classe    par exemple. GtkWidget, nom du type C
type de base     l'un de GObject, GBoxed, GEnum, GFlags.
              pour supporter d'autres types de base, voir
              EXTENSION DU SUPPORT DES TYPES pour des infos sur
              comment ajouter un gestionnaire de type personnalisé.
package       nom du package Perl auquel ce
              nom de classe doit être mappé, par exemple.
              Gtk2::Widget

Comme cas spécial, vous pouvez également utiliser ce même format pour enregistrer des domaines d'erreur ; dans ce cas, deux des quatre colonnes prennent des significations légèrement différentes :

domaine macro     par exemple, GDK_PIXBUF_ERROR
macro de type enum  par exemple, GDK_TYPE_PIXBUF_ERROR
type de base        GError
package           nom du package Perl auquel ce
                  nom de classe doit être mappé, par exemple.
                  Gtk2::Gdk::Pixbuf::Error.

EXTENSION DU SUPPORT DES TYPES

"parse_maps" utilise l'entrée de type de base dans chaque enregistrement de maps pour décider comment générer

sortie pour ce type. Dans le module de base, la prise en charge des types est incluse pour les types de base fournis par Glib. Il est facile d'ajouter la prise en charge de vos propres types, simplement en ajoutant un gestionnaire de type. Ce gestionnaire de type appellera des fonctions utilitaires pour ajouter des typemaps, des lignes BOOT et des lignes

d'en-tête.
Glib::CodeGen->add_type_handler ($base_type =>
$handler)
$base_type (chaîne) Nom C du type de base à
traiter.
$handler (sous-routine) Callback utilisé pour traiter ce
type.

Utilisez $handler pour générer la sortie pour les enregistrements dont le type de base est $base_type. $base_type est le nom de type C tel que trouvé dans la troisième colonne d'une entrée de fichier de

maps.

$handler sera appelé avec le contenu (éventuellement prétraité) de l'enregistrement courant du fichier de maps, et doit appeler les fonctions "add_typemap", "add_register" et "add_header" pour configurer le collage C/XS nécessaire pour ce

type.

Par exemple

: 
Glib::CodeGen->add_type_handler (CoolThing => sub {
    my ($typemacro, $classname, $base, $package) = @_;

    # $typemacro est la macro de type C, comme COOL_TYPE_THING.
    # $classname est le nom de type C réel, comme CoolFooThing.
    # $base est le nom C du type de base. Si CoolFooThing
    #     est un CoolThing, $base sera CoolThing. Ce
    #     paramètre est utile lors de l'utilisation du même gestionnaire de type
    #     pour plusieurs types de base.
    # $package est le nom du paquet correspondant à
    #     $classname, tel que spécifié dans le fichier de maps.

    ...
}
)
;
add_typemap $type, $typemap [, $input,
$output]
Ajoute une entrée typemap pour $type, nommée $typemap. Si $input et/ou $output sont définis, leur texte sera utilisé comme les implémentations typemap "INPUT" et/ou "OUTPUT" (respectivement) pour $typemap. Notez que généralement, vous utiliserez "T_GPERL_GENERIC_WRAPPER" ou un autre typemap existant pour $typemap, donc $input et $output sont très rarement utilisés.

Exemple

: 
# mappe les pointeurs $classname et toutes leurs variantes vers le typemap
# générique wrapper.
add_typemap "$classname *", "T_GPERL_GENERIC_WRAPPER";
add_typemap "const $classname *", "T_GPERL_GENERIC_WRAPPER";
add_typemap "$classname\
_ornull *", "T_GPERL_GENERIC_WRAPPER"; add_typemap "const $classname\_ornull *", "T_GPERL_GENERIC_WRAPPER"; add_typemap "$classname\_own *", "T_GPERL_GENERIC_WRAPPER"; add_typemap "$classname\_copy *", "T_GPERL_GENERIC_WRAPPER"; add_typ
emap "$classname\_own_ornull *", "T_GPERL_GENERIC_WRAPPER"; # code personnalisé pour un enum de type int : add_typemap $class => T_FOO, "\$var = foo_unwrap (\$arg);", # input "\$arg = foo_wrap (\$var);"; # output
add_register
$text
Ajoute $text au "register.xsh" généré. C'est généralement utilisé pour enregistrer les types avec les bindings, par ex. : 
add_register "#ifdef $typemacro\n"
       .
"gperl_register_object ($typemacro, \"$packag
e\");\n" . "#endif /* $typemacro */";
add_header
$text
Ajoute $text à l'en-tête C généré. Vous placerez les typedefs de variantes et les macros wrap/unwrap dans l'en-tête, et voudrez généralement envelopper les déclarations dans "#ifdef $t
ypemacr
o" par sécurité.
