SYNOPSI

S 
use Glib::Object::Subclass
   Some::Base::Class::,   # classe parente, dérivée de Glib::Object
   signals => {
          something_changed => {
             class_closure => sub { do_something_fun () },
             flags         => [qw(run-first)],
             return_type   => undef,
             param_types   => [],
          },
          some_existing_signal => \&class_closure_override,
   },
   properties => [
      Glib::ParamSpec->string (
         'some_string',
         'Some String Property',
         'This property is a string that is used as an example',
         'default value',
         [qw/readable writable/]
      ),
]
;

DESCRIPTIO

N

Ce module vous permet de créer vos propres classes GObject, ce qui est utile pour, par exemple, implémenter vos propres widgets

Gtk2.

Il n'« exporte » rien dans votre espace de noms, mais agit plutôt comme un module pragmatique qui modifie votre classe pour la faire fonctionner comme une classe

GObject.

Vous vous demandez peut-être pourquoi vous ne pouvez pas simplement bénir un Glib::Object dans un paquet différent et ajouter quelques sous-routines. Eh bien, si vous n'êtes pas intéressé par les paramètres d'objet, les signaux, ou le fait que votre nouvelle classe interopère de manière transparente avec d'autres modules basés sur GObject (par exemple, Gtk2 et ses amis), alors vous pouvez simplement

re-bénir.

Cependant, les signaux, les propriétés, les fonctions virtuelles et les implémentations GInterface d'un GObject sont spécifiques à sa GObjectClass. Si vous voulez créer un nouveau GObject qui soit un dérivé de GtkDrawingArea, mais qui ajoute un nouveau signal, vous devez créer une nouvelle GObjectClass à laquelle ajouter le nouveau signal. Si vous ne le faites pas, alors tous les GtkDrawingArea de votre application recevront ce nouveau signal

!

Ainsi, la seule façon de créer un nouveau signal ou une nouvelle propriété d'objet dans les liaisons Perl pour Glib est d'enregistrer une nouvelle sous-classe avec le système de types GLib via Glib::Type::register_object(). Le module Glib::Object::Subclass est une interface conviviale pour les développeurs Perl à ce morceau d'inadéquation de

paradigme.

UTILISATI

ON

Ce module fonctionne de manière similaire au pragma « use base » en ce qu'il enregistre le paquet courant comme une sous-classe d'une autre classe (qui doit être une GObjectClass implémentée soit en C, soit dans une autre langue)

.

Le pragma requiert au moins un argument, le nom de la classe parente. Les arguments restants sont des paires clé/valeur, dans n'importe quel ordre, toutes optionnelles

:
- properties =>
[]
Ajoute des propriétés d'objet ; voir « PROPERTIES
».
- signals =>
{}
Ajoute ou remplace des signaux ; voir « SIGNALS » et « OVERRIDING BASE METHODS
».
- interfaces =>
[]
Ajoute des GInterfaces à votre classe ; voir « INTERFACES
»
.

(En fait, ces paramètres sont tous transmis directement à Glib::Type::register_object(), en ajoutant __PACKAGE__ (le nom

du paquet courant) comme no
m de la nouvelle classe fille.)

MÉTHODES ET FONCTIONS

D'OBJET

Les méthodes suivantes sont soit ajoutées à votre classe sur demande (pas encore implémenté), soit par défaut à moins que votre propre classe ne les implémente elle-même. Cela signifie que toutes ces méthodes et fonctions recevront des implémentations par défaut raisonnables, sauf si vous les écrasez explicitement (en définissant votre propre version)

.

À l'exception de « new », tout ce qui suit sont des fonctions et non des méthodes. Cela signifie que vous ne devriez pas appeler la méthode de la superclasse. À la place, le système GObject appellera ces fonctions par classe au besoin, émulant l'héritage

normal.
$class->new (attr => valeur, .
..)
Le constructeur par défaut appelle simplement « Glib::Object::new », ce qui vous permet de définir des propriétés sur l'objet nouvellement créé. Cela est fait parce que beaucoup de méthodes « new » héritées de Gtk2 ou d'autres bibliothèques n'ont pas de méthodes « new » adaptées à la sous-classificat
ion.
INIT_INSTANCE $self [pas une
méthode]
« INIT_INSTANCE » est appelé sur chaque classe de la hiérarchie à mesure que l'objet est créé (c'est-à-dire depuis « Glib::Object::new » ou notre « new » par défaut). Utilisez cette fonction pour initialiser n'importe quelle donnée membre. L'implémentation par défaut laissera l'objet
intact.
GET_PROPERTY $self, $pspec [pas une
méthode]
SET_PROPERTY $self, $pspec, $newval [pas une
méthode]
« GET_PROPERTY » et « SET_PROPERTY » sont appelés chaque fois que quelqu'un fait « $object->get ($propname) » ou « $object->set ($propname => $newval) » (aussi depuis d'autres langages). Les implémentations par défaut stockent les valeurs des propriétés dans le hash de l'objet, équivalent à 
sub GET_PROPERTY {
  my ($self, $pspec) = @_;
  my $pname = $pspec->get_name;
  return (exists $self->{$pname} ? $self->{$pname}
          : $pspec->get_default_value);  # until set
}
sub SET_PROPERTY {
  my ($self, $pspec, $newval) = @_;
  $self->{$pspec->get_name} = $newval;
}

Parce que « $pspec->get_name » convertit les tirets en underscores, une propriété « line-style » est dans le hash sous la forme « line_sty

le ».

Ces méthodes vous permettent de stocker/récupérer les propriétés de la manière dont vous en avez besoin. Elles n'ont pas à être dans le hash, vous pouvez calculer quelque chose, lire un fichier, peu

importe.

Le plus souvent, vous écrirez votre propre « SET_PROPERTY » afin de pouvoir réagir quand une propriété change, comme redessiner ou redimensionner un widget.

Par exemple. 
sub SET_PROPERTY {
  my ($self, $pspec, $newval) = @_;
  my $pname = $pspec->get_name
  $self->{$pname} = $newval; # ready for default GET_PROPERTY
  if ($pname eq 'line_style') {
    $self->queue_draw;  # redraw with new lines
} }

Il faut faire attention avec les types boxed non comptés par référence tels que « Gtk2::Gdk::Color ». Dans « SET_PROPERTY », le $newval n'est généralement valable que pour la durée de l'appel. Utilisez « copy » ou similaire si vous devez le conserver plus longtemps (voir Glib::Boxed). Dans « GET_PROPERTY », la mémoire retournée doit durer suffisamment longtemps pour atteindre l'appelant, ce qui signifie généralement de retourner un champ, et non un objet nouvellement créé (qui est détruit avec le scalaire qui le

contient).

« GET_PROPERTY » est différent d'une méthode get_property en C en ce que la méthode perl retourne la valeur récupérée. Pour la symétrie, les $newval et $pspec args sur « SET_PROPERTY » sont inversés par rapport à l'utilisation

en C.
FINALIZE_INSTANCE $self [pas une
méthode]
« FINALIZE_INSTANCE » est appelé lorsque le GObject est finalisé, c'est-à-dire lorsqu'il est réellement détruit. Cela est indépendant du DESTROY plus courant sur l'objet perl ; en fait, vous devez NE PAS écraser « DESTROY » (ce n'est d'aucune utilité pour vous, de toute façon, car il est appelé plusieurs fois !).

Utilisez ce hook pour libérer tout ce que vous devez nettoyer manuellement. FINALIZE_INSTANCE sera appelé pour chaque instance perl, dans l'ordre inverse de la

construction.

Le finaliseur

par défaut
ne fait rien.
$object->DESTROY [NE PAS
ÉCRASER]
N'écrasez jamais « DESTROY », utilisez plutôt « FINALIZE_INSTANCE ».

La méthode DESTROY de toutes les classes perl dérivées des GTypes est implémentée dans le module Glib et (ab-)utilisée à ses propres fins internes.ting it is not useful as it will be called multiple times, and often long before the object actually gets destroyed. Overwriting might be very harmful to your program, so never do that. Especial

ly watch ou
t for other
classes in
your ISA
tree.

PROPERTIE

S

To create gobject properties, supply a list of Glib::ParamSpec objects as the value for the key 'properties'. There are lots of different paramspec constructors, documented in the C API reference's Parameters and Values page, as well as Glib::

ParamSpec.

As of Glib 1.060, you can also specify explicit getters and setters for your properti

es at creation time. The default values in your properties are also honored if you d
on't set anything else. See Glib::Type::register_object in Glib::Type for an example.

SIGNAL

S

Creating new signals for your new object is easy. Just provide a hash of signal names and signal descriptions under the key 'signals'. Each signal description is also a hash, with a few expected keys. All the keys are allowed to

default.
flags =>
GSignalFlags
If not present, assumed to be
'run-first'.
param_types => reference to a list of package
names
If not present, assumed to be empty (no parameters)
.
class_closure => reference to a subroutine to call as the class
closure.
may also be a string interpreted as the name of a subroutine to call, but you should be very very very careful about that.

If not present, the library will attempt to call the method named "do_signal_name" for the signal "signal_name" (uses underscores)

.

You'll want to be careful not to let this handler method be a publically callable method, or one that has the name name as something that emits the signal. Due to the funky ways in which Glib is different from Perl, the class closures should not inherit through nor

mal pe
rl inheritance.
return_type => package name for return
value.
If undefined or not present, the signal expects no return value. if defined, the signal is expected to return a value; flags must be set such that the signal does not run only first (at least use 'run-last')
.
accumulator => signal return value
accumulator
quoting the Glib manual: "The signal accumulator is a special callback function that can be used to collect return values of the various callbacks that are called during a signal emission."

If not specified, the default accumulator is used, and you just get the return value of the last handler to

run.

Accumulators are not really documented very much in the C reference, and the perl interface here is slightly different, so here's an inordinate amount of detail for this arcane

feature:

The accumulator function is called for every

handler as 
($cont, $acc) = &$func ($invocation_hint, $acc,
$ret)

$invocation_hint is an anonymous hash (including the signal name); $acc is the current accumulated return value; $ret is the value from the most recent

handler.

The two return values are a boolean $cont for whether signal emission should continue (false to stop); and a new $acc accumulated return value. (T

his is different fro
m the C version, whi
ch writes thr
ough a return_accu.)

OVERRIDING BASE

METHODS

GLib pulls some fancy tricks with function pointers to implement methods in C. This is not very language-binding-friendly, as you might

guess.

However, as described above, every signal allows a "class closure"; you may override the class closure with your own function, and you can chain from the overridden method to the original. This serves to implement virtual overrides for language

bindings.

So, to override a method, you supply a subroutine reference instead of a signal description hash as the value for the name of the existing signal in the "signals" hash described in

"SIGNALS". 
# override some important widget methods:
use Glib::Object::Subclass
      Gtk2::Widget::,
      signals => {
              expose_event => \&expose_event,
              configure_event => \&configure_event,
              button_press_event => \&button_press_event,
              button_release_event => \&button_release_event,
              motion_notify_event => \&motion_notify_event,
              # note the choice of names here... see the discussion.
              size_request => \&do_size_request,
}

It's important to note that the handlers you supply for these are class-specific, and that normal perl method inheritance rules are not followed to invoke t

hem from within the library. However, perl code can still find them! Therefore it's rather important that you choose your handlers' names carefully, avoiding
any public interfaces that you might call from perl. Case in point, since size_request is a widget method, i chose do_size_request as the override handler.

INTERFACE

S

GObject supports only single inheritance; in place of multiple inheritance, GObject uses GInterfaces. In the Perl bindings we have mostly masqueraded this with multiple inheritance (that is, simply adding the GInterface class to the @ISA of the implementing class), but in deriving new objects the facade breaks and the magic leaks

out.

In order to derive an object that implements a GInterface, you have to tell the GLib type system you want your class to include a GInterface. To do this, simply pass a list of package names through the "interfaces" key; this will add these packages to your @ISA, and cause perl to invoke methods that you must

provide. 
package Mup::MultilineEntry;
use Glib::Object::Subclass
    'Gtk2::TextView',
    interfaces => [ 'Gtk2::CellEditable' ],
    ;
# perl will now invoke these methods, which are part of the
# GtkCellEditable GInterface, when somebody invokes the
# corresponding lower-case methods on your objects.
sub START_EDITING { warn "start editing\n"; }
sub EDITING_DONE { warn "editing done\n"; }
sub REMOVE_WIDGET { warn "remove widget\n";
}
